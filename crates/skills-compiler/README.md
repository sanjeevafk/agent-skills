# skills-compiler

Structure-preserving static compiler for coding-agent skill documents
(`SKILL.md`). This is the **only** tool in this repository capable of producing
the delivery arms and ablation conditions reported in the manuscript.

## Why this exists (and why it is Rust)

The manuscript's 18-task benchmark compares five skill-delivery strategies and
runs three component ablations (A2 `no_examples`, A3 `no_tables`, A4
`no_types`). Every one of those artifacts is generated by this crate.

A predecessor Python implementation, `scripts/compile_checklists_v2.py`, is
retained for historical reference only and **cannot** produce any ablation
condition: its entire CLI is `--tasks`, `--skills`, `--out`. It also disagrees
with this crate byte-for-byte across the benchmark corpus (33.2% vs 29.5%
aggregate reduction) and parses frontmatter with `text.split("---", 2)`, which
truncates any skill containing `---` in prose or inside a fence.

Rust is doing three specific jobs here:

1. **Ablation modes.** `no_examples` / `no_tables` / `no_types` are not
   optional extras; they *are* the RQ4 experiment (§8.4). Python could not
   express them.
2. **Correct frontmatter parsing.** Handles UTF-8 BOM, CRLF, indented closing
   delimiters, and block scalars. Six dedicated tests pin this. Across 2,725
   markdown files with embedded code, the naive `split("---", 2)` approach is
   not safe.
3. **Deterministic output.** `BTreeMap`-ordered manifests and byte-identical
   artifacts. The published manifest's SHA-256 provenance chain depends on
   this, and CI enforces it on every push.

Compilation runs 18 times per benchmark. Speed is not a consideration; the
crate exists for capability and determinism, not throughput.

## Build

```bash
cargo build --release
cargo test --release        # 24 tests, 14 of them A4-specific
cargo clippy --all-targets -- -D warnings
```

## Usage

```bash
BIN=./target/release/skills-compiler

# Batch-compile the benchmark corpus (this is what produced checklists_v2/)
$BIN from-tasks --tasks benchmarks/tasks_ieee.json --out-dir benchmarks/checklists_v2

# Full A0-A5 ablation series for one skill (what produced benchmarks/ablations/)
$BIN ablate --input skills/tdd/SKILL.md --out-dir benchmarks/ablations

# Single skill, with an ablation flag
$BIN compile --input skills/security-review/SKILL.md --no-types --output /tmp/a4.txt

# Structural composition + token metrics
$BIN analyze --input skills/tdd/SKILL.md
```

Ablation modes are opt-in (`--no-types` etc.). Default `v2` compilation is
unaffected by their presence, which is why compiler v0.1.0 → v0.2.0 reproduces
committed artifacts byte-for-byte.

## Reproducibility

The published artifacts are machine-verified, not asserted. CI job
`artifact-reproducibility` recompiles the corpus and compares SHA-256 digests
against `benchmarks/checklists_v2/manifest.json`:

```bash
cd ../.. && uv run python scripts/verify_compiled_artifacts.py
```

Current state: **16 of 18 artifacts reproduce byte-for-byte.** The two
exceptions (`tdd`, source edited after the run; `debugging-code`, absent from
the tree) are declared in that script's `KNOWN_EXCEPTIONS` table with reasons,
and the check fails if a declared exception starts reproducing or if any
undeclared skill drifts.

Full audit, including the compiler version comparison and known limitations of
the A4 type eraser: [`benchmarks/COMPILER_PROVENANCE.md`](../../benchmarks/COMPILER_PROVENANCE.md).

## Known limitations

The A4 type eraser leaves three constructs un-erased, pinned by
`a4_known_gap_*` tests that characterise current behaviour deliberately:

- optional parameter annotations (`b?: number`)
- variable annotations (`const arr: string[] = []`)
- generic call type arguments (`new Map<string, number>()`)

Realised impact on the evaluated corpus is negligible: A4 magnitude is 0.9%
for `security-review` and 0.0% for the other 17 skills. The tests exist so a
future fix surfaces as a deliberate review rather than silently mutating
recorded artifacts.
