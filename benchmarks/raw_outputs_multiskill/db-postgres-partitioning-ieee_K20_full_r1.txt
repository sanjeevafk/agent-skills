The zero-downtime PostgreSQL partitioning migration strategy is already implemented across three scripts in your repo. Here's how it all fits together:

---

## Migration Strategy Overview

**Files:**
- `scripts/partition_migration_v2.sql` — Full migration DDL
- `scripts/pg_partman_maintenance.sql` — Ongoing automation
- `scripts/verify_pruning.sql` — Pruning verification tests

---

## Architecture: Shadow Table + Dual-Write + Cutover

The migration uses the **expand-contract pattern** with a dual-write trigger so there's no data loss and minimal downtime (seconds, not hours).

| Phase | What Happens | Downtime |
|-------|-------------|----------|
| 1-2 | Create partitioned `audit_logs_new` with monthly partitions | None |
| 3 | Install trigger to dual-write to both tables | None |
| 4 | Backfill 500M rows in 50K batches with lock timeouts | None |
| 5-6 | Create indexes CONCURRENTLY | None |
| 7 | Validate row counts match | None |
| 8 | Atomic rename + final sync | **Seconds** |
| 9-10 | pg_partman automation + cleanup | None |

---

## Key Design Decisions

**Partition Key:** `occurred_at` (timestamptz) — must be part of the PK, so the primary key is composite `(id, occurred_at)`.

**Batch Backfill:** Uses keyset pagination (`WHERE id > last_id ORDER BY id LIMIT 50000`) not OFFSET — O(1) per batch vs O(n). Configurable lock timeout (5s default) and max runtime (6h) prevents runaway batches. Supports parallel sessions by splitting on ID ranges.

**Indexes Created Concurrently:**
- B-tree on `occurred_at DESC` (time-range queries)
- Composite `(user_id, occurred_at DESC)` (user activity)
- Partial index on `occurred_at WHERE severity IN ('error','critical')` (small, fast)
- Covering index with `INCLUDE` (index-only scans)
- GIN on `details` and `metadata` (JSONB containment)
- BRIN on `occurred_at` (tiny size for naturally ordered data)

## Partition Pruning Verification

Run `verify_pruning.sql` after migration. Key tests:

```sql
-- Single month: should scan ONE partition
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM audit_logs
WHERE occurred_at >= '2025-06-01' AND occurred_at < '2025-07-01';

-- Full year: should scan 12 partitions, NOT default
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM audit_logs
WHERE occurred_at >= '2024-01-01' AND occurred_at < '2025-01-01';
```

Verify `enable_partition_pruning = on` — without this, all partitions get scanned.

## pg_partman Automation

After cutover, pg_partman handles future partitions automatically:

```sql
-- Creates 3 months ahead, drops partitions older than 24 months
SELECT partman.create_parent(
    p_parent_table := 'public.audit_logs',
    p_control := 'occurred_at',
    p_type := 'range',
    p_interval := '1 month',
    p_premake := 3
);

-- Monthly cron job (2 AM on 1st)
SELECT cron.schedule('audit-logs-maintenance', '0 2 1 * *',
    $$SELECT partman.run_maintenance('public.audit_logs', p_analyze := true)$$);
```

Alerting queries in `pg_partman_maintenance.sql` monitor: future partition count, default partition bloat, retention-age partitions, and maintenance job failures.

## Execution Order

```bash
# 1. Run migration (takes hours for backfill, but zero downtime)
psql -f scripts/partition_migration_v2.sql

# 2. Verify pruning works
psql -f scripts/verify_pruning.sql

# 3. Set up ongoing maintenance
psql -f scripts/pg_partman_maintenance.sql
```

The migration is designed to be **resumable** — if the backfill procedure dies, it picks up from `last_backfill_id` on restart.
