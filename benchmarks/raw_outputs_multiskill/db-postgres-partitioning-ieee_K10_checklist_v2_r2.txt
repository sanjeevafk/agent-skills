## Complete Migration Strategy Summary

### Files in Repository

| File | Purpose |

### Migration Phases Overview

```
Phase 0:  Preparation (extensions, control table)
Phase 1:  Create partitioned shadow table (audit_logs_new)
Phase 2:  Generate monthly partitions (DO loop)
Phase 3:  Install dual-write trigger (captures live changes)
Phase 4:  Batch backfill procedure (keyset pagination, lock timeouts)
Phase 5:  Execute backfill (parallel sessions possible)
Phase 6:  Create indexes CONCURRENTLY (composite, covering, partial, GIN)
Phase 7:  Data validation (row counts, missing rows, checksums)
Phase 8:  Atomic cutover (< 10s metadata lock)
Phase 9:  pg_partman setup (automated future partitions + retention)
Phase 10: Post-migration cleanup (after validation period)
```

### Key Engineering Standards Applied

| Standard | Implementation |
|----------|---------------|
| **bigint IDs** | `id bigint GENERATED ALWAYS AS IDENTITY` |
| **timestamptz** | All timestamp columns use `timestamptz` |
| **text strings** | No `varchar(255)` anywhere |
| **Composite indexes** | Equality-first: `(user_id, occurred_at DESC)` |
| **Covering indexes** | `INCLUDE (resource_type, resource_id, severity)` |
| **Partial indexes** | `WHERE severity IN ('error', 'critical')` |
| **GIN indexes** | `jsonb_path_ops` for JSONB containment |
| **Concurrent DDL** | All `CREATE INDEX CONCURRENTLY` |
| **Lock timeouts** | `set_config('lock_timeout', '5000ms')` |
| **Keyset pagination** | `WHERE id > last_id LIMIT batch_size` |

### Verification Suite (`verify_pruning.sql`)

The pruning verification includes 10 tests:

1. Single month range query
2. Multi-month range query  
3. Single day query (highly selective)
4. User activity across partitions
5. JSONB containment query
6. Aggregation with partition-wise operations
7. Force pruning test
8. Verify no default partition access
9. Partial index usage
10. Covering index usage

Each test uses `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` to confirm only relevant partitions are scanned.

### Rollback Safety

The rollback script (`rollback_migration.sql`) provides:
- State verification before rollback
- Reverse rename in a single transaction
- Trigger reinstallation for retry
- Validation queries post-rollback
