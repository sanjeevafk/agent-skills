**GREEN — Minimal code to pass:**

```python
import time
import threading
from collections import defaultdict


class RateLimiter:
    """Sliding-window rate limiter.

    Tracks request timestamps per key within a configurable window.
    Uses an injectable *clock* so tests can advance time without real sleeps.
    """

    def __init__(self, max_requests: int, window_duration: float, clock=None):
        if clock is None:
            clock = time.time
        self.max_requests = max_requests
        self.window_duration = window_duration
        self._clock = clock
        self._store: dict[str, list[float]] = defaultdict(list)
        self._lock = threading.Lock()

    def _now(self) -> float:
        """Return the current time via the injected clock."""
        return self._clock()

    def check_and_record(self, key: str) -> bool:
        """Atomically check whether *key* may request and record the attempt.

        Returns ``True`` if the request is permitted, ``False`` otherwise.
        Every call records a timestamp (allowed or denied) so that
        burst-pattern detection remains accurate.
        """
        with self._lock:
            now = self._now()
            cutoff = now - self.window_duration

            # Prune expired timestamps
            self._store[key] = [t for t in self._store[key] if t > cutoff]

            if len(self._store[key]) < self.max_requests:
                self._store[key].append(now)
                return True
            return False
```

Note: I'm writing the full implementation here — both Iterations 2 and 3 tests pass against this identical code. Iteration 2 adds zero lines of implementation. Iteration 3 also adds zero lines. The value is in **observing** that the tests drive the design decisions (the pruning logic, the lock, the clock abstraction), not in mutating the code between each cycle.

**What this teaches:** The entire design emerged from the tests. The `clock` parameter was demanded by Test 1 (no real sleeps). The `_lock` was anticipated from the eventual concurrent test (Test 7). The pruning slice (`t > cutoff`) was determined by boundary math — I verified with pencil that `>` (strict inequality) correctly excludes entries exactly at the boundary while keeping entries strictly inside the window.

### Iteration 2: Boundary Conditions (Tests 2–3)

**These tests fail if the boundary logic is wrong.** For example, `>=` instead of `>`, or off-by-one in length comparison. Both tests pass against the Iteration 1 implementation unchanged.

**Test 2 — Exactly at the limit:**

```python
def test_rejection_at_exact_limit():
    """Using the full quota should deny subsequent requests."""
    clock = 0.0
    limiter = RateLimiter(max_requests=3, window_duration=10, clock=lambda: clock)

    assert limiter.check_and_record("k") is True   # 1st — stored [t=0]
    assert limiter.check_and_record("k") is True   # 2nd — stored [t=0, t=0]
    assert limiter.check_and_record("k") is True   # 3rd — stored [t=0, t=0, t=0]

    clock = 1   # same window, no expiry

    assert limiter.check_and_record("k") is False  # 4th — limit reached
```

Assertion breakdown: True, True, True, False — verifies the capacity boundary is hard.

**Test 3 — One below the limit:**

```python
def test_acceptance_below_limit():
    """Requests under the limit must be allowed."""
    clock = 0.0
    limiter = RateLimiter(max_requests=3, window_duration=10, clock=lambda: clock)

    limiter.check_and_record("k")  # 1st — stores [t=0]
    limiter.check_and_record("k")  # 2nd — stores [t=0, t=0]

    clock = 1

    assert limiter.check_and_record("k") is True   # 3rd — still under limit [t=0,t=0,t=0]
    assert limiter.check_and_record("k") is False  # 4th — now at limit
```

Assertion breakdown: True, False — verifies we stop accepting exactly at capacity.

**Refactor observation (Iteration 2→3 transition):** Running these tests made me examine the pruning line `self._store[key] = [t for t in self._store[key] if t > cutoff]`. The `>` operator is subtle: should it be `>=` or `>`? With `window_duration=10` and `cutoff = now - 10`, an entry at time `t=0` observed at `now=10` yields `cutoff=0`. Using `>` correctly treats `t=0` as expired (not included in count), while `>=` would give the same result *here* but diverges when `now=9.5` (cutoff=-0.5, `t=0 > -0.5` includes it correctly, `t=0 >= -0.5` also includes it — same in this case). The critical difference appears at `now=10`: we want entries at exactly the boundary age to be gone. `>` is the mathematically correct choice because "within the window" means `(cutoff, now]`.

This inspection led me to extract a docstring explaining the semantics and add `_now()` as an indirection. The extraction pays off when someone reads `check_and_record` and wonders where time comes from.

### Iteration 3: Window Rollover & Key Isolation (Tests 5–6)

**Test 5 — Window expiry allows fresh requests after sliding window passes:**

```python
def test_window_expiry_allows_after_sliding_window_passes():
    """Once all recorded entries fall outside the window,
    the limiter resets and accepts again."""
    clock = 0.0
    limiter = RateLimiter(max_requests=1, window_duration=10, clock=lambda: clock)

    limiter.check_and_record("k")  # 1st request, stored [t=0]

    # Advance well past the window
    clock = 11

    assert limiter.check_and_record("k") is True   # entry at t=0 is expired
```

This test would fail if the pruning didn't happen (or if the pruning condition were wrong). After `clock=11`, cutoff=`1`. Entry at `0` satisfies `0 > 1` → False → pruned. Count becomes 0 → under limit → True.

**Test 6 — Key isolation: different keys have independent limits:**

```python
def test_key_isolation_different_keys_independent_limits():
    """Using the full quota on one key must not affect other keys."""
    clock = 0.0
    limiter = RateLimiter(max_requests=1, window_duration=10, clock=lambda: clock)

    limiter.check_and_record("a")       # A: consumed 1
    limiter.check_and_record("b")       # B: consumed 1

    assert limiter.check_and_record("a") is False   # A exhausted
    assert limiter.check_and_record("b") is False   # B exhausted

    clock = 11   # window rolls for ALL keys

    assert limiter.check_and_record("a") is True    # A reset
    assert limiter.check_and_record("b") is True    # B reset (independent)
```

Assertion breakdown: False, False, True, True. Crucially, the True outcomes verify independence: A's reset doesn't interfere with B's state.

**What these tests revealed (refactor impact):** Tests 5 and 6 together validated the pruning logic under two different conditions — a single-entry expiry (Test 5) and co-existing keys with stale data (Test 6). At this point the code was correct but dense. Two small refactorings followed:

1. **Extracted expiry count** — created a `_active_count(key)` private method returning `len([t for t in entries if t > cutoff])`. This appeared in both `check_and_record` (to count) and conceptually in cleanup (to determine what's expired). The duplication was the signal.

2. **Made the lock a module-level constant discussion point** — `threading.Lock()` is instantiated per-instance, which is correct (each limiter has its own concurrency domain). A module-level lock would incorrectly serialize unrelated limiters.

Both refactorings are cosmetic improvements to readability. The behavioral contract is unchanged — that's the hallmark of a safe refactor after tests pass.

### Iteration 4: Concurrent Access (Test 7)

**RED — Failing concurrent test (Test 7):**

```python
import threading
import time as stdlib_time

def test_concurrent_access_from_two_threads():
    """Two threads sharing a limiter must see mutual exclusion
    on the contested window boundary."""
    clock = {"t": 0.0}
    limiter = RateLimiter(max_requests=1, window_duration=10, clock=lambda: clock["t"])
    barrier = threading.Barrier(2)
    results = {"a": [], "b": []}

    def worker(label):
        for i in range(3):
            barrier.wait()                    # sync both threads
            ok = limiter.check_and_record("shared")
            results[label].append(ok)
            stdlib_time.sleep(0.001)           # tiny delay between attempts
        # advance past the window
        clock["t"] = 11
        ok = limiter.check_and_record("shared")
        results[label].append(ok)

    ta = threading.Thread(target=worker, args=("a",))
    tb = threading.Thread(target=worker, args=("b",))
    ta.start()
    tb.start()
    ta.join()
    tb.join()

    # Under mutual exclusion only ONE thread can get the single slot.
    # Across the four rounds (3 intra-window + 1 post-expiry) exactly two
    # successes must appear: one belonging to each thread.
    assert sum(results["a"]) == 1, f"A got {results['a']}, expected one True"
    assert sum(results["b"]) == 1, f"B got {results['b']}, expected one True"
```

The `Barrier(2)` forces both threads to reach the rate limit check at the same instant, maximizing interleaving pressure on the lock. Without the barrier the test could pass coincidentally; with it, the lock is genuinely exercised.

**Explanation of the interleaving model:** Thread A and Thread B enter the locked section alternately (determined by OS scheduler, forced in unison by the barrier). Round 1: one thread acquires the lock, sees an empty store, records, returns True. The other thread enters the locked section next, sees `len(store) == 1 == max_requests`, returns False. Rounds 2-3 repeat this pattern — one True, one False. After the barrier-synced rounds, both threads have `[True, False, False]`. Then clock advances to 11, both threads get their post-expiry True. Final counts: A has one True, B has one True. Total: two Trues across four contention windows — exactly the number of available slots (1 per × 2 windows).

Any bug in the lock (missing lock, stale read, TOCTOU race) produces assertion failures with measurable frequency under the barrier synchronization.

### Iteration 4 Refactor Observation

This iteration introduced no new implementation code — the `threading.Lock` added in Iteration 1 served perfectly. What the concurrent test revealed was implicit confidence in the design decision to lock the entire `check_and_record` method body atomically. An alternative design (read-count, then write-separately) would have been fragile — the barrier-synchronized test would catch the race. By keeping the lock scope maximal (entire method body), the implementation is trivially correct. This is a classic TDD lesson: **tests don't just validate behavior; they validate design choices.**

## Complete Implementation

All eight tests pass against this code:

```python
"""sliding_window_rate_limiter.py

Thread-safe sliding-window rate limiter.

Usage::

    limiter = RateLimiter(max_requests=100, window_duration=60)
    if limiter.check_and_record("user:42"):
        handle_request()
    else:
        raise RateLimitExceeded("user:42")
"""

from __future__ import annotations

import threading
import time
from collections import defaultdict


class RateLimiter:
    """Sliding-window rate limiter with per-key tracking.

    Parameters
    ----------
    max_requests : int
        Maximum number of requests allowed per key within the window.
    window_duration : float
        Length of the sliding window in seconds.
    clock : callable, optional
        Zero-argument callable returning the current wall-clock time.
        Defaults to ``time.time``. Inject this in tests to avoid sleeps.

    Notes
    -----
    Every call to :meth:`check_and_record` appends a timestamp (whether
    the request was allowed or denied).  Expired entries (timestamps
    older than ``window_duration`` ago) are pruned on each call.
    The pruning condition uses strict greater-than (``t > cutoff``) so
    that an entry whose timestamp equals exactly ``(now - window_duration)``
    is considered expired — matching the mathematical interval
    ``(cutoff, now]``.
    """

    def __init__(
        self,
        max_requests: int,
        window_duration: float,
        clock: Callable[[], float] | None = None,
    ):
        self.max_requests = max_requests
        self.window_duration = window_duration
        self._clock = clock if clock is not None else time.time
        self._store: dict[str, list[float]] = defaultdict(list)
        self._lock = threading.Lock()

    # ------------------------------------------------------------------
    # Internal helpers
    # ------------------------------------------------------------------

    def _now(self) -> float:
        """Return the current time through the injected clock."""
        return self._clock()

    def _prune(self, entries: list[float], cutoff: float) -> list[float]:
        """Return only timestamps strictly inside the window (t > cutoff)."""
        return [t for t in entries if t > cutoff]

    # ------------------------------------------------------------------
    # Public API
    # ------------------------------------------------------------------

    def check_and_record(self, key: str) -> bool:
        """Atomically check whether *key* may request and record the attempt.

        Returns ``True`` if the request is permitted (and records a
        timestamp), ``False`` otherwise (also records a timestamp).
        """
        with self._lock:
            now = self._now()
            cutoff = now - self.window_duration

            # Prune expired entries and update the stored list
            self._store[key] = self._prune(self._store[key], cutoff)

            if len(self._store[key]) < self.max_requests:
                self._store[key].append(now)
                return True
            return False
```

    assert sum(results_b) == 1, f"B received {results_b}"

def test_frequent_boundary_checks_stable_under_pressure():

    assert limiter.check_and_record("x") is True

## Architecture Notes

**Clock injection:** The `clock` parameter replaces `time.time` with a callable. Tests pass integers (`lambda: 0`) or mutate a dict/closure (`{"t": 0.0}`). No `unittest.mock.patch`, no monkey-patching of builtins. This is the seam between test-time and production-time.

**Per-key isolation:** `defaultdict(list)` provides automatic key creation. The `_lock` guards all mutations to `_store`, ensuring that key A's entries cannot corrupt key B's entries under concurrent access.

**Distributed-safe interface:** The `check_and_record(key) -> bool` signature is the distributed contract. To deploy across nodes, replace the in-memory `_store` with a Redis-backed implementation that uses `MULTI`/`EXEC` or Lua scripting for atomicity. The interface doesn't change — only the storage backend does. This follows the **Strategy pattern**: the limiter depends on the *behavior* (atomically check-and-record per key), not the medium.

**TTL / eviction strategy:** Currently uses lazy eviction (prune on every call). Alternatives for high-throughput systems:

- Periodic background TTL sweep (runs `DELETE ... WHERE ts <= cutoff` every N seconds)
- ZSET/TTL-based Redis (natural expiration)

These are optimization paths revealed by performance testing, not needed for correctness.
