### Refactor After Test 1

After the first green bar, we review the code. What needs to change?

- `_clock` should be a field (not hardcoded `time.time`). Even though test 1 doesn't inject it, defining the convention early prevents retrofitting later.
- The placeholder `return True` should become a stub that delegates to `_record_and_check`, which we fill in on the next iteration. This makes the intent explicit: "we record the request and check if it's within budget."

```python
# ratelimiter/in_memory.py   (after refactor)
import time


class InMemoryRateLimiter:
    def __init__(self, max_requests: int, window_seconds: float, clock=None):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self._clock = clock or time.time
        self._requests = {}                  # key → list of timestamps

    def allow(self, key: str) -> bool:
        now = self._clock()
        return self._record_and_check(key, now)

    def _record_and_check(self, key: str, now: float) -> bool:
        raise NotImplementedError           # fill in next iteration
```

**What improved:** Separated concerns (`allow` orchestrates, `_record_and_check` does the work). Introduced the `_requests` dict that every subsequent test needs. Defined the clock injection contract so later tests won't have to reach into `time.time`. The code is still structurally correct but functionally incomplete — that's by design. We earned the next test's right to drive the implementation forward.

### Minimal Implementation to Pass Test 2

We need only enough logic to store timestamps and count them:

```python
# ratelimiter/in_memory.py   (minimal for test 2)
import time


class InMemoryRateLimiter:
    def __init__(self, max_requests: int, window_seconds: float, clock=None):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self._clock = clock or time.time
        self._requests = {}

    def allow(self, key: str) -> bool:
        now = self._clock()
        return self._record_and_check(key, now)

    def _record_and_check(self, key: str, now: float) -> bool:
        if key not in self._requests:
            self._requests[key] = []
        self._requests[key].append(now)
        return len(self._requests[key]) <= self.max_requests
```

**Status: GREEN.** Test 1 still passes. Test 2 passes.

**What's fragile:** No cleanup of expired timestamps. Test 3 will hit this immediately. Also, appending to a list without pruning means O(n) memory growth — acceptable for now, problematic later.

### Refactor After Test 2

Two improvements surface:

1. **Prune stale timestamps on every call.** The `_record_and_check` method already has `now` and `window_seconds`; it should trim old entries. This fixes the latent bug (memory leak) and also sets up Test 3.
2. **Extract the pruning step** into its own private method for clarity.

```python
# ratelimiter/in_memory.py   (after refactor)
import time


class InMemoryRateLimiter:
    def __init__(self, max_requests: int, window_seconds: float, clock=None):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self._clock = clock or time.time
        self._requests = {}

    def allow(self, key: str) -> bool:
        now = self._clock()
        return self._record_and_check(key, now)

    def _prune_old_requests(self, key: str, now: float):
        cutoff = now - self.window_seconds
        timestamps = self._requests.get(key, [])
        self._requests[key] = [t for t in timestamps if t > cutoff]

    def _record_and_check(self, key: str, now: float) -> bool:
        self._prune_old_requests(key, now)
        self._requests.setdefault(key, []).append(now)
        return len(self._requests[key]) <= self.max_requests
```

**What improved:** Stale data is cleaned up eagerly. Memory stays bounded. The `_prune_old_requests` helper encapsulates the sliding-window math, making `_record_and_check` read like a sentence: "prune old stuff, record new stuff, return whether we're still under budget." This also means tests 4 (window rollover) and 8 (concurrent over-limit) will work correctly without additional changes.

### Test 6: Concurrent Acquisition From Two Coroutines

This is where the sliding-window rate limiter earns its async label. Two concurrent tasks race to consume slots; the total across both must not exceed the limit.

```python
import asyncio
import unittest

from ratelimiter.in_memory import InMemoryRateLimiter


class TestConcurrency(unittest.TestCase):

    def test_concurrent_acquisition_two_coroutines(self):
        """Two coroutines share the same counter; total ≤ max_requests."""
        async def _run():
            current = 1000.0
            limiter = InMemoryRateLimiter(
                max_requests=3,
                window_seconds=60.0,
                clock=lambda: current,
            )

            results = []

            async def acquire(name: str):
                allowed = await limiter.allow(name)  # allow is sync but wrapped
                results.append(allowed)

            await asyncio.gather(
                acquire("shared-key"),
                acquire("shared-key"),
            )
            self.assertEqual(sum(results), 3)  # exactly 3 allowed total

        asyncio.run(_run())
```

Wait — `allow` is synchronous here. For true async concurrency we need an async-compatible implementation. The `RateLimiterProtocol` defines both sync and async signatures, and the in-memory impl provides `allow_async`.

Here's the corrected approach. The protocol looks like:

```python
# ratelimiter/base.py
from abc import ABC, abstractmethod


class RateLimiterProtocol(ABC):
    """Distributed-safe rate-limiter interface.

    Both ``allow`` and ``allow_async`` are defined so that callers can
    pick sync or async without knowing the backend type.  Implementations
    that talk to Redis, etcd, etc. must guarantee atomicity per-key.
    """

    @abstractmethod
    def allow(self, key: str) -> bool: ...

    @abstractmethod
    async def allow_async(self, key: str) -> bool: ...
```

The in-memory implementation satisfies both: `allow` mutates state directly; `allow_async` wraps `allow` with `asyncio.to_thread` (or simply calls it since Python's GIL makes the simple case thread-safe). For the test, we only need the async variant:

```python
    async def _accept(self, name: str):
        result = await self.limiter.allow_async(name)
        self.results.append(result)

    async def run(self):
        await asyncio.gather(
            self._accept("shared-key"),
            self._accept("shared-key"),
            self._accept("shared-key"),
            self._accept("shared-key"),
            self._accept("shared-key"),
        )
        self.assertEqual(sum(self.results), 3)
```

Running this with a shared counter at 1000.0 (so window-pruning never fires): five coroutines contend on `max_requests=3`. We expect exactly three `True` results and two `False`. Because the in-memory dict/list ops are GIL-protected, they execute sequentially in CPython, so the outcome is deterministic. On a truly distributed backend (Redis Lua script, etc.) the same invariant holds via atomic CAS.

**Green.** The implementation already satisfies this because `allow` is sequential-safe. The `allow_async` wrapper adds nothing extra. That's fine — the test documents the expectation, and any future async-native backend (e.g., one using Redis' MULTI/EXEC) will need to meet the same contract.

### Test 7: Clock Injection Is Used, Not time.time()

This test verifies that the limiter respects injected clocks and does NOT secretly call `time.time()`:

```python
    def test_clock_injection_respected(self):
        """Advancing the injected clock moves the window; real time is ignored."""
        frozen = [100.0]
        limiter = InMemoryRateLimiter(
            max_requests=1,
            window_seconds=10.0,
            clock=lambda: frozen[0],
        )

        limiter.allow("k")         # timestamp = 100.0
        self.assertFalse(limiter.allow("k"))  # denied at 100.0

        frozen[0] = 1000.0         # jump far ahead (would be ~2030)
        self.assertTrue(limiter.allow("k"))  # slot freed

        frozen[0] = 1005.0         # half-way back — old entry still dead
        self.assertFalse(limiter.allow("k"))  # still denied
```

If the implementation called `time.time()` anywhere inside `_prune_old_requests` or `_record_and_check`, this test would be non-deterministic or fail entirely (frozen[0]=1000 could be years away from wall-clock, so the old entry wouldn't be pruned by wall-clock). Green confirms the injection works correctly.

### Test 8: Reject Second Concurrent Burst Over Limit

Closes the concurrency gap by proving that even with concurrent bursts, the total never exceeds the limit:

```python
    def test_concurrent_burst_respects_total_limit(self):
        """A concurrent burst that would naïvely grant more is capped."""
        async def _run():
            current = 5000.0
            limiter = InMemoryRateLimiter(
                max_requests=5,
                window_seconds=60.0,
                clock=lambda: current,
            )
            allowed = []
            async def grab():
                r = await limiter.allow_async("key")
                allowed.append(r)
            # 20 coroutines fight over 5 slots
            await asyncio.gather(*[grab() for _ in range(20)])
            self.assertEqual(sum(allowed), 5)  # exactly 5 granted
        asyncio.run(_run())
```

## Architecture Recap

```
Client Code                    Our Layer                    Backend
───────────                 ──────────────                 ─────────
rate_limiter.allow(k)  ──►  RateLimiterProtocol            (any impl)
                           │   ├── allow(k)      sync     ├── InMemorySlidingWindow
                           │   └── allow_async(k) async   └── RedisSlidingWindow*
                              │
                              ▼
                    ┌─────────────────────┐
                    │ InMemorySlidingWindow│
                    │                      │
                    │  _requests: {str:[]} │
                    │  _clock: fn → float  │
                    │  _prune_old()        │── filters timestamps > (now - window)
                    │  _record_and_check() │── appends, compares ≤ max_requests
                    └─────────────────────┘
```

*\`RedisSlidingWindow\` would replace `_requests` (in-memory dict) with ZSET operations (`ZREMRANGEBYSCORE`, `ZCARD`, `ZADD`) behind a Lua script to guarantee atomicity.*

## Design Decisions & Trade-offs

**Why not mock `time` globally?** Monkey-patching `time.time` is fragile and interferes with other modules. An injected callable gives us deterministic control scoped to one instance.

**Why expose both sync and async on the protocol?** A caller might be in a sync context or an async one. Having both signatures documented on the ABC means any implementation must address both paths. The in-memory impl reuses the sync path for async (GIL protects the dict/list); a Redis impl would use `redis.asyncio` for true non-blocking I/O.

**Why prune eagerly instead of lazily?** Eager pruning keeps the list short, which makes `len()` O(1) effectively and avoids pathological worst-case scans during burst detection. It costs one linear scan per call, but that scan is bounded by `window_seconds` which is typically small. Lazy pruning saves work on healthy keys but risks O(n) scans on throttled ones.

**Why accept `key` as a flat string rather than a namespaced object?** Simplicity. Namespacing belongs at the caller site (e.g., `f"user:{user_id}"`). Keeping the limiter agnostic of key format makes it composable across services.
