## Issue 1: SQL Injection via F-String Concatenation

**CWE:** CWE-89 — *SQL Injection*

### The Vulnerability

```python
# VULNERABLE views/report.py
from django.db import connection

def generate_report(request):
    tenant_id = request.query_params.get('tenant', 'default')
    start_date = request.query_params.get('start_date')
    end_date = request.query_params.get('end_date')
    status = request.query_params.get('status', 'active')

    query = f"""
        SELECT id, name, total
        FROM reports
        WHERE tenant_id = '{tenant_id}'
          AND created_at BETWEEN '{start_date}' AND '{end_date}'
          AND status = '{status}'
    """

    with connection.cursor() as cursor:
        cursor.execute(query)   # ← raw string execution
        rows = cursor.fetchall()

    return Response(rows)
```

### Exploit Demonstration

An attacker crafts a malicious `tenant_id` parameter:

```
GET /api/report/?tenant='; DROP TABLE reports; --&start_date=2026-01-01&end_date=2026-12-31
```

This produces the final query:
```sql
SELECT id, name, total
FROM reports
WHERE tenant_id = ''; DROP TABLE reports; --'
  AND created_at BETWEEN '2026-01-01' AND '2026-12-31'
  AND status = 'active'
```

The semicolon terminates the `SELECT`, `DROP TABLE reports` executes, and the `--` comments out the rest. In a multi-tenant setup, the attacker could also exfiltrate another tenant's data:

```
GET /api/report/?tenant=' UNION SELECT password, credit_card, ssn FROM users WHERE tenant_id='acme' --
```

### The Fix

Use parameterized queries — never interpolate user input into SQL strings:

```python
# FIXED views/report.py
import logging
from datetime import date
from django.db import connection
from rest_framework.response import Response
from rest_framework.views import APIView

logger = logging.getLogger(__name__)


class ReportView(APIView):
    def get(self, request):
        tenant_id = request.query_params.get('tenant')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')
        status = request.query_params.get('status', 'active')

        # Validate inputs first
        if not tenant_id or not start_date or not end_date:
            return Response(
                {'error': 'Missing required parameters'},
                status=400,
            )

        try:
            start = date.fromisoformat(start_date)
            end = date.fromisoformat(end_date)
        except ValueError:
            return Response(
                {'error': 'Invalid date format. Use YYYY-MM-DD'},
                status=400,
            )

        if status not in ('active', 'completed', 'archived'):
            return Response(
                {'error': 'Invalid status value'},
                status=400,
            )

        # Parameterized query — all values passed as a list
        query = """
            SELECT id, name, total
            FROM reports
            WHERE tenant_id = %s
              AND created_at BETWEEN %s AND %s
              AND status = %s
        """

        try:
            with connection.cursor() as cursor:
                cursor.execute(query, [tenant_id, start, end, status])
                columns = [col[0] for col in cursor.description]
                rows = [dict(zip(columns, row)) for row in cursor.fetchall()]
        except Exception as exc:
            logger.error("Report query failed: %s", exc)
            return Response(
                {'error': 'Internal report generation error'},
                status=500,
            )

        return Response(rows)
```

**Why this works:** The `%s` placeholders are sent separately from the query string via the PostgreSQL protocol. The database driver handles proper escaping and type handling. The attacker's injected SQL becomes a literal string value that gets searched — it cannot alter query structure.

If you can avoid raw SQL entirely, prefer the ORM:

```python
# BEST: ORM-based approach
from django.utils import timezone
from .models import Report

def generate_report(tenant_id, start_date, end_date, status):
    qs = Report.objects.filter(
        tenant_id=tenant_id,
        created_at__range=[start_date, end_date],
        status=status,
    )
    return list(qs.values('id', 'name', 'total'))
```

Server-side object-level permissions using DRF's `BasePermission`:

```python
# FIXED permissions/report_permissions.py
from rest_framework import permissions
from rest_framework.exceptions import NotFound


class IsReportTenantOwner(permissions.BasePermission):
    """
    Object-level permission: only users belonging to the same tenant
    may read, modify, or delete a report.
    """

    message = 'You do not have access to this report.'

    def has_object_permission(self, request, view, obj):
        # Both the requesting user and the report must have a tenant
        if not hasattr(request.user, 'tenant') or not hasattr(obj, 'tenant'):
            return False

        return request.user.tenant == obj.tenant


class IsAdminOrTenantOwner(permissions.BasePermission):
    """
    Admin staff can access all reports; regular tenants only their own.
    Safe methods (GET, HEAD, OPTIONS) follow object-level rules.
    Write methods require admin OR owner.
    """

    message = 'You lack permission to perform this action.'

    def has_permission(self, request, view):
        # All requests require authentication
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        # Admins can access everything
        if request.user.is_staff:
            return True

        return request.user.tenant == obj.tenant
```

```python
# FIXED views/report.py
from rest_framework.permissions import IsAuthenticated
from rest_framework.generics import RetrieveAPIView, DestroyAPIView, ListAPIView
from .models import Report
from .serializers import ReportSerializer
from .permissions import IsReportTenantOwner, IsAdminOrTenantOwner


class ReportListView(ListAPIView):
    """List only reports belonging to the requesting user's tenant."""
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        # Server-side tenant scoping — impossible to bypass
        return Report.objects.filter(tenant=self.request.user.tenant)


class ReportDetailView(RetrieveAPIView):
    queryset = Report.objects.all()          # Base queryset (further filtered by permission)
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated, IsReportTenantOwner]


class ReportDeleteView(DestroyAPIView):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated, IsAdminOrTenantOwner]

    def get_queryset(self):
        if self.request.user.is_staff:
            return Report.objects.all()
        return Report.objects.filter(tenant=self.request.user.tenant)
```

```python
# FIXED urls.py — use path parameter routing
from django.urls import path
from .views import ReportListView, ReportDetailView, ReportDeleteView

urlpatterns = [
    path('reports/', ReportListView.as_view(), name='report-list'),
    path('reports/<int:pk>/', ReportDetailView.as_view(), name='report-detail'),
    path('reports/<int:pk>/delete/', ReportDeleteView.as_view(), name='report-delete'),
]
```

**Why this works:** Every request — whether from the React SPA, a browser, curl, or a compromised JWT token — passes through the permission classes before any data touches the response. The ORM's `.filter()` on `get_queryset` means even if permissions were misconfigured, unscoped objects are never returned. Together they provide defense-in-depth.

## Issue 1 — Server-Side SQL Injection via Dynamic Query Building

### CWE
**CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')**

### Vulnerable Code (`reports/views.py`)

```python
from django.db import connection
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticated

@api_view(["GET"])
@permission_classes([IsAuthenticated])
def tenant_report(request):
    """Builds report filters by concatenating user input directly into SQL."""
    date_from = request.query_params.get("date_from", "")
    date_to = request.query_params.get("date_to", "")
    status = request.query_params.get("status", "")
    min_revenue = request.query_params.get("min_revenue", "")
    sort_by = request.query_params.get("sort_by", "created_at")
    order = request.query_params.get("order", "DESC")

    # 🚧 CRITICAL: f-string interpolation into SQL — entirely un-sanitized
    sql = f"""
        SELECT id, name, created_at, revenue, status
        FROM tenants_project
        WHERE tenant_id = {request.user.tenant.id}
          AND created_at BETWEEN '{date_from}' AND '{date_to}'
          {'AND status = ' + status if status else ''}
          {'AND revenue >= ' + min_revenue if min_revenue else ''}
        ORDER BY {sort_by} {order}
        LIMIT 50
    """

    with connection.cursor() as cursor:
        cursor.execute(sql)
        rows = cursor.fetchall()

    return Response(rows)
```

### Exploit Demonstration

An attacker sends a crafted `status` parameter:

```
GET /api/reports/?status=active'%20OR%201=1--&sort_by=id&order=ASC
```

The interpolated SQL becomes:

```sql
SELECT id, name, created_at, revenue, status
FROM tenants_project
WHERE tenant_id = 42
  AND created_at BETWEEN '' AND ''
  AND status = active' OR 1=1--
ORDER BY id ASC
LIMIT 50
```

The `OR 1=1` bypasses the status filter, returning **every row in the table**. Worse still, the attacker could append a UNION-based extraction:

```
status=%27%20UNION%20SELECT%20username,password,email,'x','y'%20FROM%20auth_user--
```

This returns plain-text credentials from an unrelated table. The `sort_by`, `order`, and numeric `min_revenue` parameters are also injectable since they pass straight into the query with zero validation.

### Corrected Code

```python
import datetime

from django.db import connection
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework import status

# Whitelist of allowed column names; anything else is rejected
ALLOWED_SORT_COLUMNS = frozenset({
    "id", "name", "created_at", "updated_at", "revenue", "status",
})

TENANT_COLUMN_SAFE = frozenset(
    {f.name for f in __import__("tenants.models").models.Project._meta.fields}
)


def _safe_integer(value, name="value"):
    """Return int(value) or raise 400 if it cannot be parsed."""
    try:
        return int(value)
    except (TypeError, ValueError):
        raise ValueError(f"{name!r} must be an integer")


@api_view(["GET"])
@permission_classes([IsAuthenticated])
def tenant_report(request):
    tenant_id = request.user.tenant.id

    date_from_raw = request.query_params.get("date_from")
    date_to_raw = request.query_params.get("date_to")
    status = request.query_params.get("status")
    min_revenue_raw = request.query_params.get("min_revenue")
    sort_by = request.query_params.get("sort_by", "created_at")
    order = request.query_params.get("order", "DESC")

    # ---- Parameterise every value ------------------------------------------
    params = {"tenant_id": tenant_id}
    conditions = ["tenant_id = %s"]

    if date_from_raw:
        try:
            df = datetime.datetime.fromisoformat(date_from_raw).date()
        except (ValueError, TypeError):
            return Response(
                {"detail": f"Invalid date_from: {date_from_raw}"},
                status=status.HTTP_400_BAD_REQUEST,
            )
        conditions.append("created_at >= %s")
        params[f"df_{len(conditions)}"] = df

    if date_to_raw:
        try:
            dt = datetime.datetime.fromisoformat(date_to_raw).date()
        except (ValueError, TypeError):
            return Response(
                {"detail": f"Invalid date_to: {date_to_raw}"},
                status=status.HTTP_400_BAD_REQUEST,
            )
        conditions.append("created_at <= %s")
        params[f"dt_{len(conditions)}"] = dt

    if status:
        # Restrict to known enum values
        valid_statuses = {"draft", "active", "archived"}
        if status.lower() not in valid_statuses:
            return Response(
                {"detail": f"Invalid status. Choose from: {valid_statuses}"},
                status=status.HTTP_400_BAD_REQUEST,
            )
        conditions.append("LOWER(status) = %s")
        params[f"st_{len(conditions)}"] = status.lower()

    if min_revenue_raw:
        try:
            min_rev = _safe_integer(min_revenue_raw, "min_revenue")
        except ValueError as exc:
            return Response({"detail": str(exc)}, status=status.HTTP_400_BAD_REQUEST)
        conditions.append("revenue >= %s")
        params[f"mr_{len(conditions)}"] = min_rev

    # Sort column/order must be whitelisted against schema, never interpolated
    sort_col = sort_by.strip().rstrip("_asc").rstrip("_desc")
    if sort_col not in ALLOWED_SORT_COLUMNS:
        return Response(
            {"detail": f"Sort column must be one of: {sorted(ALLOWED_SORT_COLUMNS)}"},
            status=status.HTTP_400_BAD_REQUEST,
        )
    dir_part = "ASC" if order.upper() == "ASC" else "DESC"
    if dir_part not in ("ASC", "DESC"):
        return Response(
            {"detail": "order must be 'ASC' or 'DESC'"},
            status=status.HTTP_400_BAD_REQUEST,
        )

    where_clause = " AND ".join(conditions)
    sql = (
        f"SELECT id, name, created_at, revenue, status "
        f"FROM tenants_project "
        f"WHERE {where_clause} "
        f"ORDER BY {sort_col} {dir_part} "
        f"LIMIT 50"
    )

    with connection.cursor() as cursor:
        cursor.execute(sql, params)
        columns = [col[0] for col in cursor.description]
        rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

    return Response(rows)
```

**Key changes:**
| Before | After |
|--------|-------|
| `f-string` interpolation into SQL | `%s` placeholders passed as `params` dict to `cursor.execute(sql, params)` |
| Arbitrary column names accepted | `ALLOWED_SORT_COLUMNS` whitelist enforced before ORDER BY |
| No validation on dates/status | Explicit format parsing + enum restriction |
| Numeric field accepts strings | `_safe_integer()` rejects non-integers |

```python
# apps/reports/views.py — HARDENED
from rest_framework import viewsets, permissions, status
from rest_framework.response import Response
from django.db import connection
from .models import Report
from .serializers import ReportSerializer


class IsTenantMember(permissions.BasePermission):
    """Ensure the requesting user belongs to the queried tenant."""

    def has_permission(self, request, view):
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        return obj.tenant.users.filter(id=request.user.id).exists()


class ReportViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer
    permission_classes = [permissions.IsAuthenticated, IsTenantMember]

    def get_queryset(self):
        qs = Report.objects.filter(tenant__users=self.request.user)

        tenant_filter = self.request.query_params.get("tenant")
        if tenant_filter:
            # Validate against known tenants — never pass directly into SQL
            valid_tenant_ids = set(
                self.request.user.tenant_set.values_list("id", flat=True)
            )
            if str(tenant_filter) not in {str(tid) for tid in valid_tenant_ids}:
                raise PermissionDenied("Access denied to specified tenant.")
            qs = qs.filter(tenant_id=tenant_filter)

        status_filter = self.request.query_params.get("status")
        if status_filter:
            qs = qs.filter(status=status_filter)

        start_date = self.request.query_params.get("start_date")

    def _run_safe_raw_query(self, tenant_id: int, filters: dict) -> list[dict]:
        """Example of how to safely execute raw SQL when ORM can't express the query."""
        base = "SELECT id, name, revenue FROM reports_report WHERE tenant_id = %s"
```


The API endpoint accepts the PUT/PATCH because DRF's generic `UpdateAPIView` has no object-level permission check — it trusts the client decided who gets to edit. An authenticated user simply crafts a direct curl:

```bash

  -H "Authorization: Bearer <user-token>" \
  -H "Content-Type: application/json" \
```

### The Fix

Server-side object-level permissions enforced at the DRF level. Every read/write action must verify ownership *before* touching the database.

```python
# apps/common/permissions.py — HARDENED
from rest_framework import permissions
from django.core.exceptions import PermissionDenied


class IsOwnerOrReadOnly(permissions.BasePermission):
    """
    Global: reads allowed for any authenticated user.
    Per-object: writes require object ownership or staff status.
    """

    def has_permission(self, request, view):
        if request.method in permissions.SAFE_METHODS:
            return request.user and request.user.is_authenticated
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
```

## Vulnerability 1: SQL Injection via `cursor.execute()`

**CWE:** 89 (SQL Injection) — Unsanitized input passed directly to database queries through string concatenation/f-string interpolation.

### The Exploit

Given code like this in a report view:

```python
# VULNERABLE — report/views.py
def generate_report(request):
    tenant = request.tenant
    column = request.GET.get('column', 'created_at')
    operator = request.GET.get('operator', '>='')
    value = request.GET.get('value', '')

    query = f"""
        SELECT id, name, status
        FROM {tenant}_orders
        WHERE {column} {operator} %s
    """
    # BUG: column and operator are interpolated from user input;
    # value is parameterized but the other two are not.
    with connection.cursor() as cursor:
        cursor.execute(query, [value])
        rows = cursor.fetchall()
```

An attacker calls:

```
GET /api/reports/generate?column=1;DROP TABLE orders;--&operator=&value=x
```

Or a more targeted blind injection:

```
GET /api/reports/generate?column=name&operator=AND+1=CONCAT((SELECT+password+FROM+admin_users+LIMIT+1),'x')&value=a
```

Because `{column}` and `{operator}` are part of the query structure (not values), `%s` parameterization can't protect them — they're injected at execution time as SQL syntax.

### The Fix

Never interpolate untrusted data into query strings. Use an allowlist for structural elements (table names, column names, operators) and parameterize only actual values. When possible, prefer the ORM:

```python
# HARDENED — report/views.py
from django.db import connection
from django.http import JsonResponse, BadRequest
from django.views.decorators.http import require_http_methods
import logging

logger = logging.getLogger(__name__)

# --- Allowlists (authoritative list, not runtime-checked) ---
SUPPORTED_TABLES = {
    "orders": {"base_table": "{tenant}_orders"},
    "invoices": {"base_table": "{tenant}_invoices"},
    "users": {"base_table": "{tenant}_users"},
}

ALLOWED_COLUMNS = {
    "orders": {"id", "name", "status", "created_at", "updated_at", "total"},
    "invoices": {"id", "order_id", "amount", "issued_at", "status"},
    "users": {"id", "email", "first_name", "last_name", "created_at"},
}

ALLOWED_OPERATORS = {"=", "!=", "<", ">", "<=", ">="}

MAX_QUERY_LENGTH = 2048


def _validate_column(table_group: str, column: str) -> str:
    """Return validated column or raise BadRequest."""
    if table_group not in ALLOWED_COLUMNS:
        logger.warning("Unknown table group: %s", table_group)
        raise BadRequest("Invalid report type.")
    if column not in ALLOWED_COLUMNS[table_group]:
        logger.warning("Column %s disallowed for table group %s", column, table_group)
        raise BadRequest(f"Column '{column}' is not supported for {table_group}.")
    return column


def _validate_operator(operator: str) -> str:
    if operator not in ALLOWED_OPERATORS:
        logger.warning("Operator %s rejected", operator)
        raise BadRequest("Invalid comparison operator.")
    return operator


@require_http_methods(["GET"])
def generate_report(request):
    tenant = getattr(request, "tenant", None)
    if not tenant:
        return JsonResponse({"error": "Tenant context missing."}, status=400)

    report_type = request.GET.get("report", "orders")
    column = request.GET.get("column", "created_at")
    operator = request.GET.get("operator", ">=")
    value = request.GET.get("value", "")

    # Step 1: Validate every user-supplied *structural* element against allowlists
    base_table_template = SUPPORTED_TABLES[report_type]["base_table"]
    validated_column = _validate_column(report_type, column)
    validated_operator = _validate_operator(operator)

    # Step 2: Build the safe query — only the value is parameterized
    sql = (
        f"SELECT id, name, status "
        f"FROM {base_table_template.format(tenant=tenant)} "
        f"WHERE {validated_column} {validated_operator} %s"
    )

    if len(sql) > MAX_QUERY_LENGTH:
        logger.warning("Query length %d exceeds maximum %d", len(sql), MAX_QUERY_LENGTH)
        raise BadRequest("Query too long.")

    try:
        with connection.cursor() as cursor:
            cursor.execute(sql, [value])
            columns = [desc[0] for desc in cursor.description]
            rows = [dict(zip(columns, row)) for row in cursor.fetchall()]
    except Exception as exc:
        logger.error("Report generation failed: %s", exc)
        return JsonResponse({"error": "Internal server error."}, status=500)

    return JsonResponse({"data": rows})
```

Key principles:
1. **Allowlists** control all structural elements — table names, columns, operators. User input can never inject new tokens.
2. **Value parameters** (`%s`) remain parameterized so the DB driver handles escaping.
3. **Query length cap** provides defense-in-depth against DoS-style blow-up.
4. Prefer ORM `.filter(**{f"{column}{operator}": value})` when the pattern allows it — it handles parameterization entirely. Reserve raw SQL for complex aggregation that the ORM can't express.

## Vulnerability 2: Client-Side-Only Object Permissions

**CWE:** 862 (Missing Authorization) — Access control enforced solely in the frontend means any attacker with HTTP tools bypasses it entirely. Server-side authorization is non-negotiable.

### The Exploit

Frontend code:

```jsx

  const isOwned = ownOrders.some(o => o.id === id);
  if (!isOwned) throw new Error("You cannot view this order.");
  return api.get(`/api/orders/${id}/`);  // Only after client-side check
```

But API views don't re-check ownership on the server:

### The Fix

```python
# HARDENED — order/views.py
from rest_framework import generics, permissions, serializers
from rest_framework.exceptions import NotFound, PermissionDenied
from .models import Order
from .serializers import OrderSerializer


class OwnerPermission(permissions.BasePermission):
    """Object-level permission: only the owner may access the object.
    
    Multi-tenant aware: also restricts to the requesting user's tenant.
    """

    def has_object_permission(self, request, view, obj):
        # Tenant isolation — hard requirement
        if not hasattr(request, "tenant"):
            raise PermissionDenied("No tenant context.")
        if obj.tenant != request.tenant:
            return False
        # Ownership check
        return obj.owner == request.user


class OrderDetailView(generics.RetrieveAPIView):
    """Retrieve a single order — with full server-side authorization."""

    serializer_class = OrderSerializer
    permission_classes = [permissions.IsAuthenticated, OwnerPermission]

    def get_queryset(self):
        """CRITICAL: Filter by tenant AND owner BEFORE fetching.
        
        This prevents mass enumeration even if the permission mixin
        somehow fails to block the request.
        """
        user = self.request.user
        tenant = getattr(self.request, "tenant", None)
        if not tenant:
            return Order.objects.none()
        return Order.objects.filter(tenant=tenant, owner=user).select_related("tenant")

    def retrieve(self, request, *args, **kwargs):
        try:
            return super().retrieve(request, *args, **kwargs)
        except NotFound:
            # Never reveal whether an order exists outside the user's scope
            raise PermissionDenied("This resource cannot be accessed.")
```

For bulk/list operations, the same principle applies:

```python
class OrderListView(generics.ListCreateAPIView):
    serializer_class = OrderSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):
        user = self.request.user
        tenant = getattr(self.request, "tenant", None)
        if not tenant:
            return Order.objects.none()
        return Order.objects.filter(tenant=tenant, owner=user).select_related("tenant")

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user, tenant=self.request.tenant)
```

And for update/delete:

```python
class OrderUpdateView(generics.UpdateDestroyAPIView):
    serializer_class = OrderSerializer
    permission_classes = [permissions.IsAuthenticated, OwnerPermission]

    def get_queryset(self):

        if not tenant:
            return Order.objects.none()
        return Order.objects.filter(tenant=tenant, owner=user)
```

Key principles:
1. **Filter the queryset first** — `get_queryset()` limits what objects can ever be fetched. This is your primary defense.
2. **Object-level permission class** — double-check ownership in `has_object_permission`. Defense in depth.
3. **Generic messages** — `PermissionDenied` for missing resources rather than `NotFound`, preventing information leakage about record existence.
4. **`perform_create` sets owner/tenant** — the authenticated user and their tenant are set server-side, never trusted from request data.

## Issue 1: SQL Injection via f-string Cursor Query

### CWE-89 (SQL Injection)

**Vulnerable pattern:**

**Exploit:**



**Fix — parameterized queries only, no string concatenation for values:**

```python
from django.db import connection

def get_report(request, tenant_id):
    conditions = ["tenant_id = %s"]
    params = [tenant_id]

    status = request.GET.get("status")
    if status:
        conditions.append("status = %s")
        params.append(status)

    category = request.GET.get("category")
    if category:
        conditions.append("category = %s")
        params.append(category)

    where_clause = " AND ".join(conditions)
    sql = f"SELECT id, title, created_at FROM reports WHERE {where_clause}"

    with connection.cursor() as cursor:
        cursor.execute(sql, params)  # ← parameterized, DB driver handles escaping
        columns = [desc[0] for desc in cursor.description]
        rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

    return JsonResponse({"reports": rows})
```

Key points:
- `%s` placeholders go in `cursor.execute(sql, params)` — never inline them into the string
- User input can only fill `params`, never part of `sql` itself
- Table/column names CANNOT be parameterized; whitelist those separately if needed
