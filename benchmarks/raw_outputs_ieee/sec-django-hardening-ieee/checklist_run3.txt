# Multi-Tenant Django REST — Security Audit & Remediation

## Vulnerability #1: SQL Injection via F-String Concatenation

**CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')**

### Exploit

```python
# VULNERABLE VIEW — builds filters by f-string into cursor.execute()
class ReportView(APIView):
    def get(self, request):
        tenant_id = request.query_params.get('tenant', '')
        start_date = request.query_params.get('start_date', '')
        end_date = request.query_params.get('end_date', '')
        status = request.query_params.get('status', '')

        query = f"SELECT id, amount, created_at FROM transactions "
        query += f"WHERE tenant_id = '{tenant_id}' "
        if start_date:
            query += f"AND created_at >= '{start_date}' "
        if end_date:
            query += f"AND created_at <= '{end_date}' "
        if status:
            query += f"AND status = '{status}' "

        with connection.cursor() as cursor:
            cursor.execute(query)          # ← raw SQL with interpolated strings
            rows = cursor.fetchall()

        return Response(rows)
```

A malicious actor crafts a `tenant` parameter that closes the string and appends arbitrary SQL:

```
GET /api/report/?tenant=' UNION SELECT password,username,email FROM auth_user WHERE '1'='1&status=active
```

The resulting SQL becomes:

```sql
SELECT id, amount, created_at FROM transactions
WHERE tenant_id = '' UNION SELECT password,username,email FROM auth_user WHERE ''='1' AND status='active'
```

This dumps every user's password hash and email across all tenants. It can also drop tables, exfiltrate data via error-based subqueries, or leverage time-based blind injection.

### Fix: Parameterized queries

```python
# CORRECTED — use Django ORM exclusively; never raw SQL with f-strings

from rest_framework.views import APIView
from rest_framework.response import Response
from django.db import connection
from datetime import datetime


class ReportView(APIView):
    """Safe report endpoint using Django ORM."""

    VALID_STATUSES = {'pending', 'processed', 'failed', 'completed'}

    def get(self, request):
        tenant_id = request.query_params.get('tenant', '')
        start_date_str = request.query_params.get('start_date')
        end_date_str = request.query_params.get('end_date')
        status = request.query_params.get('status')

        # Validate tenant_id is numeric (prevents basic injection even at validation layer)
        try:
            tenant_id = int(tenant_id)
        except (ValueError, TypeError):
            return Response({'detail': 'Invalid tenant ID'}, status=400)

        # Build ORM queryset — parameters are escaped automatically
        qs = Transaction.objects.filter(tenant_id=tenant_id)

        if start_date_str:
            try:
                qs = qs.filter(created_at__gte=datetime.fromisoformat(start_date_str))
            except ValueError:
                return Response({'detail': 'Invalid start_date format'}, status=400)

        if end_date_str:
            try:
                qs = qs.filter(created_at__lte=datetime.fromisoformat(end_date_str))
            except ValueError:
                return Response({'detail': 'Invalid end_date format'}, status=400)

        if status:
            if status not in self.VALID_STATUSES:
                return Response({'detail': f'Invalid status. Choose from: {self.VALID_STATUSES}'}, status=400)
            qs = qs.filter(status=status)

        results = list(qs.values('id', 'amount', 'created_at'))
        return Response(results)
```

**Key principles:**
- **Never** pass user input directly into `cursor.execute()` or any raw SQL string
- Use `model.objects.filter()` — Django escapes parameters via the DB driver
- Whitelist allowed enum values (`status`) so attackers can't guess new predicates
- Parse and validate date strings before passing them anywhere

## Vulnerability #2: Client-Side-Only Object-Level Authorization

**CWE-284: Improper Access Control / CWE-862: Missing Authorization**

### Exploit

```python
# VULNERABLE — permissions checked only in React frontend
class TenantDocumentView(APIView):
    """Documents belong to a tenant; only the owning tenant should view them."""

    # ❌ No DRF permission classes defined
    # ✅ Authenticated users get here with any token

    def get(self, request, document_id):
        doc = Document.objects.get(id=document_id)   # no tenant check!

        # The REAL guard lives in the React component:
        #   if (doc.tenantId !== currentTenant.id) setShowAlert();
        # But a curl request completely bypasses it.
        return Response({
            'id': doc.id,
            'tenant_id': doc.tenant_id,     # ← leaked data
            'content': doc.content,         # ← leaked data
            'file_url': doc.file.url,       # ← leaked data
        })
```

An attacker authenticates as User A, guesses `document_id=42`, and retrieves a document owned by Tenant B. Or worse — they iterate IDs to enumerate every document in the system. The frontend check does nothing because HTTP is stateless; there is no "client" enforcing anything.

### Fix: Server-side object-level authorization via DRF `BasePermission`

```python
from rest_framework.permissions import BasePermission, SAFE_METHODS
from rest_framework.exceptions import PermissionDenied


class IsTenantOwner(BasePermission):
    """Server-side enforcement: only objects belonging to the requesting user's tenant."""

    def has_object_permission(self, request, view, obj):
        # Works for single-object lookups where obj is a model instance
        if not hasattr(obj, 'tenant'):
            return False
        return obj.tenant in request.user.tenants.all()


class IsTenantMemberOrReadOnly(BasePermission):
    """Allows safe methods for any authenticated member; restricts writes to owners."""

    def has_permission(self, request, _view):
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        if not hasattr(obj, 'tenant'):
            return False

        is_member = obj.tenant.members.filter(id=request.user.id).exists()

        if request.method in SAFE_METHODS:
            return is_member           # members can read their tenant's objects

        # For writes, require ownership (creator or explicit role)
        if request.method == 'PUT':
            return obj.owner_id == request.user.id or is_member
        return is_member               # PATCH/micro-edits allowed for members


# CORRECTED VIEW — server enforces everything
class TenantDocumentView(generics.RetrieveUpdateDestroyAPIView):
    queryset = Document.objects.none()  # <-- see get_queryset below
    serializer_class = DocumentSerializer
    permission_classes = [IsAuthenticated, IsTenantMemberOrReadOnly]

    def get_queryset(self):
        # Scope to the user's own tenants — impossible to reach another tenant's rows
        return Document.objects.filter(
            tenant__members=self.request.user
        ).select_related('tenant', 'owner')
```

**Key principles:**
- Define `permission_classes` on every DRF view/set/endpoint
- Scope `get_queryset()` to the current user's tenants so the queryset itself cannot return foreign data
- Implement `has_object_permission()` as a second gate for individual object access
- Never trust the frontend to enforce data boundaries — the browser is an untrusted client

## Vulnerability #3: Hardcoded Secrets in Committed Settings

**CWE-798: Use of Hard-coded Credentials**

### Exploit

```python
# VULNERABLE — secrets baked into source code, committed to Git
# settings.py

DEBUG = False
ALLOWED_HOSTS = ['prod.example.com']

SECRET_KEY = 'django-insecure-k$7@2x!9p#vz&q5m^b1c+hf(wrjg_0t^yq*s1n8e!z2wv4p$x'  # ← hardcoded

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'tenant_db',
        'USER': 'admin',                # ← hardcoded
        'PASSWORD': 'SuperSecret123!',  # ← hardcoded
        'HOST': 'db.internal.example.com',
        'PORT': '5432',
    }
}

# If this file is committed (even to a private repo), anyone with
# repo access gets: full DB access + ability to forge JWTs/sessions
# via the SECRET_KEY. A git history search exposes the rotated key
# long after you "fixed" it.
```

Consequences:
1. Any developer, CI runner, or fork of the repo gets production database credentials
2. Attacker can reset passwords (forging session cookies via known `SECRET_KEY`)
3. Rotating the key requires a full code deployment, not just env var change
4. `git log -p` reveals old keys still valid for signed tokens

### Fix: Environment-variable-backed secrets management

```python
# settings/base.py  (committed to git — contains NO secrets)

import os
from pathlib import Path

from dotenv import load_dotenv

BASE_DIR = Path(__file__).resolve().parent.parent

# Load .env file if present (local dev); never commit .env
load_dotenv(BASE_DIR / '.env')

SECRET_KEY = os.environ['DJANGO_SECRET_KEY']

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': os.environ.get('DB_NAME', 'tenant_db'),
        'USER': os.environ.get('DB_USER', ''),
        'PASSWORD': os.environ.get('DB_PASSWORD', ''),
        'HOST': os.environ.get('DB_HOST', 'localhost'),
        'PORT': os.environ.get('DB_PORT', '5432'),
    }
}
```

```bash
# .env  (IN .gitignore — populated per-environment by operator/CI)
DJANGO_SECRET_KEY=$(openssl rand -base64 64)
DB_NAME=tenant_db
DB_USER=dbadmin
DB_PASSWORD=$(openssl rand -base64 32)
DB_HOST=db.internal.example.com
DB_PORT=5432
ALLOWED_HOSTS=prod.example.com,www.prod.example.com
```

```python
# settings/production.py  (injected by the deployment platform, not git-tracked)

LOGGING['handlers']['security_file'] = {
    'level': 'WARNING',
    'class': 'logging.FileHandler',
    'filename': '/var/log/django/security.log',
}
```

```
# .gitignore
.env
.env.*.local
credentials/*.json
```

**Key principles:**
- `SECRET_KEY`, database passwords, API keys → always from `os.environ`
- Never put sensitive values in any file tracked by version control
- `.env` lives in `.gitignore`; populate it per environment (CI pipelines inject via secret managers like AWS Secrets Manager / HashiCorp Vault)
- Rotate keys independently of code deployments; if a key leaks, changing the env variable takes effect immediately without a dep cycle

## Vulnerability #4: Mass Assignment via Unrestricted Serializer Fields

**CWE-200: Exposure of Sensitive Information to an Unauthorized Actor / CWE-915: Improperly Controlled Modification of Dynamically-Determined Object Attributes**

### Exploit

```python
# VULNERABLE — ModelSerializer with no explicit fields lets attackers set anything
class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = '__all__'       # ← includes is_staff, is_superuser, password_hash, ...

    # No override — attacker posts:
    # POST /api/users/create/  {"email":"attacker@evil.com", "is_staff": true}
```

Payload:

```json
{
    "email": "hacker@evil.com",
    "password": "p@ssw0rd!",
    "is_staff": true,
    "is_superuser": true,
    "role": "admin"
}
```

Result: a regular request creates a staff/admin account. The same pattern applies to `ReportSerializer` exposing `tenant_id` (cross-tenant write) or audit-logs exposing `deleted_at`.

### Fix: Explicit field whitelisting + read-only protection

```python
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class UserSerializer(serializers.ModelSerializer):
    """Whitelisted fields only. Staff/superuser flags writable by admin only."""

    class Meta:
        model = User
        # ✅ Explicit allowlist — new fields added to the model won't auto-expose
        fields = ['id', 'email', 'username', 'first_name', 'last_name']

    # ✅ Password must go through .set_password() (hashing), never stored raw
    password = serializers.CharField(write_only=True, required=False)

    def create(self, validated_data):
        password = validated_data.pop('password', None)
        user = self.Meta.model(**validated_data)
        if password:
            user.set_password(password)
        user.save()
        return user


class UserUpdateSerializer(serializers.ModelSerializer):
    """Restricted update: only modifiable profile fields, staff protected behind is_staff check."""

    class Meta:
        model = User
        fields = ['first_name', 'last_name']  # very narrow allowlist for updates

    # Prevent mass-assignment of identity-critical fields
    id = serializers.IntegerField(read_only=True)
    email = serializers.EmailField(read_only=True)
    username = serializers.CharField(read_only=True)
    is_staff = serializers.BooleanField(read_only=True)
    is_superuser = serializers.BooleanField(read_only=True)
    role = serializers.CharField(read_only=True)


class AdminUserCreateSerializer(serializers.ModelSerializer):
    """Admin-only: creates include password but NEVER expose staff/superuser unless admin."""

    class Meta:
        model = User
        fields = ['email', 'username', 'first_name', 'last_name', 'password']
        extra_kwargs = {'password': {'write_only': True}}

    def create(self, validated_data):
        user = User.objects.create_user(**validated_data)
        return user


# --- View wiring ---
from rest_framework import generics, permissions


class CreateUserView(generics.CreateAPIView):
    queryset = User.objects.all()
    serializer_class = UserCreateSerializer  # minimal fields, no is_staff leak

    def perform_create(self, serializer):
        # Ensure callers who aren't admins cannot promote themselves
        if not self.request.user.is_staff:
            raise permissions.PermissionDenied(
                'Non-admin users cannot create accounts'
            )
        super().perform_create(serializer)


class UpdateCurrentUserView(generics.UpdateAPIView):
    serializer_class = UserUpdateSerializer

    def get_object(self):
        return self.request.user            # users can only update their own record
```

**Key principles:**
- Always use explicit `fields = [...]` instead of `fields = '__all__'`
- Add new `read_only=True` annotations for sensitive columns (`is_staff`, `is_superuser`, `tenant_id`)
- Use `extra_kwargs={'password': {'write_only': True}}` so hashes never leak in responses
- Override `create()` to call `set_password()` — prevents plaintext storage
- Separate serializers for different roles (create vs. update vs. admin-create) rather than one giant serializer
