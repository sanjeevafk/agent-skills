## 1. SQL Injection — f-string concatenation into `cursor.execute()`

**CWE-89: SQL Injection (Improper Neutralization of Special Elements Used in an SQL Command)**

### Exploit

```python
# VULNERABLE REPORT ENDPOINT
def get_report(request):
    tenant_id = request.query_params.get('tenant', 'default')
    date_from = request.query_params.get('date_from', '')
    
    # F-string SQL construction — completely unsanitized
    sql = f"""
        SELECT * FROM reports 
        WHERE tenant_id = '{tenant_id}'
        AND created_at >= '{date_from}'
    """
    with connection.cursor() as cursor:
        cursor.execute(sql)  # ← raw SQL with interpolated strings
        return cursor.fetchall()
```

An attacker passes crafted query parameters:

```
GET /api/reports/?tenant=foo' UNION SELECT password,username,email,credit_card,user_agent FROM users--&date_from=2024-01-01
```

The resulting query becomes:

```sql
SELECT * FROM reports
WHERE tenant_id = 'foo' UNION SELECT password,username,email,credit_card,user_agent FROM users--'
AND created_at >= '2024-01-01'
```

Result: **complete database exfiltration** — passwords, PII, payment data from every tenant. Even without UNION, parameter tampering lets attackers bypass tenant isolation (data leakage across tenants) or drop tables.

### Fix: Parameterized queries

```python
from django.db import connection


def get_report(request):
    tenant_id = request.query_params.get('tenant', 'default')
    date_from = request.query_params.get('date_from', None)

    if not tenant_id:
        return Response(
            {"error": "tenant parameter required"},
            status=status.HTTP_400_BAD_REQUEST
        )

    sql = """
        SELECT id, title, content, created_at, updated_at
        FROM reports
        WHERE tenant_id = %s
          AND created_at >= %s
        ORDER BY created_at DESC
    """

    params = [tenant_id, date_from or '1970-01-01']

    try:
        with connection.cursor() as cursor:
            cursor.execute(sql, params)
            columns = [col[0] for col in cursor.description]
            rows = cursor.fetchall()

        results = [dict(zip(columns, row)) for row in rows]
        return Response({"reports": results})
    except Exception as exc:
        logger.exception("Report query failed")
        return Response(
            {"error": "Internal report generation failure"},
            status=status.HTTP_500_INTERNAL_SERVER_ERROR
        )
```

Key changes:
- `%s` placeholders with a separate `params` list — the DB driver handles escaping; no string interpolation occurs
- Whitelisted column selection (no `SELECT *`)
- Validation that `tenant_id` is present
- Safe default when `date_from` is omitted instead of allowing empty strings
- Error handler that doesn't leak stack traces to the client

## 2. Client-Side-Only Permission Checks

**CWE-285: Improper Authorization (Server-Side Access Control Missing)**

### Exploit

```jsx
// VULNERABLE: React frontend permission gate
function ReportDetail({ reportId }) {
  const [report, setReport] = useState(null);

  useEffect(() => {
    // Only check permission in React — server returns ANY report ID
    fetch(`/api/reports/${reportId}/`)
      .then(res => res.json())
      .then(data => {
        if (data.access === true) {   // ← trust the frontend
          setReport(data.report);
        } else {
          showError("No access");
        }
      });
  }, [reportId]);

  return <div>{report?.content}</div>;
}
```

The API endpoint itself performs **zero authorization**:

```python
# VULNERABLE: No server-side permission check
class ReportDetailView(APIView):
    def get(self, request, report_id):
        report = Report.objects.filter(id=report_id).first()  # No tenant isolation!
        serializer = ReportSerializer(report)
        return Response(serializer.data)
```

Attack scenarios:
1. **Direct API abuse** — cURL the endpoint directly, bypassing React entirely. The `/api/reports/9999/` returns someone else's confidential report.
2. **Modified frontend** — An attacker modifies their local JS bundle to always send `"access": true`, or strips the permission check out. The server never re-checks.
3. **ID enumeration** — Iterate report IDs sequentially (1, 2, 3…) dumping the entire database regardless of tenant membership.

### Fix: Server-side object-level authorization

```python
import logging
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from django.shortcuts import get_object_or_404
from django.contrib.auth.models import User

logger = logging.getLogger(__name__)


class ObjectPermissionRequiredMixin:
    """
    Mixin that enforces server-side object-level permissions.
    Each subclass implements has_object_permission(self, request, obj)
    for its own policy logic.
    """
    def has_object_permission(self, request, obj):
        raise NotImplementedError(
            "Subclasses must implement has_object_permission()"
        )

    def _check_permission(self, request, obj):
        if not self.has_object_permission(request, obj):
            logger.warning(
                "User %s denied access to %s id=%s",
                request.user.pk,
                type(obj).__name__,
                getattr(obj, "id", "?"),
            )
            raise PermissionDenied("You do not have permission to access this resource.")


class ReportDetailView(ObjectPermissionRequiredMixin, APIView):
    """
    Secure report detail with server-side tenant enforcement.
    """
    def get(self, request, report_id):
        # Tenant-scoped lookup — filters by authenticated user's tenant
        report = get_object_or_404(
            Report.objects.filter(tenant=request.user.tenant),
            id=report_id
        )

        self._check_permission(request, report)
        serializer = ReportSerializer(report)
        return Response(serializer.data)

    def has_object_permission(self, request, obj):
        # Role-based + ownership check on the server
        user = request.user
        if user.is_staff:
            return True
        return user.tenant == obj.tenant


class ReportViewSet(viewsets.ModelViewSet):
    """
    Secured report list/create/update/destroy with proper scoping.
    """
    serializer_class = ReportSerializer

    def get_queryset(self):
        """Always scope to the requesting user's tenant."""
        user = self.request.user
        return Report.objects.filter(tenant=user.tenant)

    def perform_create(self, serializer):
        """Inject tenant from request context, not the payload."""
        serializer.save(tenant=self.request.user.tenant)
```

Additionally, at the middleware/Django settings level:

```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticated",
    ],
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.SessionAuthentication",
        "rest_framework.authentication.TokenAuthentication",
    ],
}

# Optional: install django-guardian for granular object-level perms
INSTALLED_APPS += ["guardian"]
```

Key changes:
- Every queryset is filtered by `request.user.tenant` — no cross-tenant data leaks
- `has_object_permission` runs on every request, independently of UI behavior
- `perform_create` injects tenant from the authenticated session, rejecting it from the serializer payload
- Django REST Framework's built-in `IsAuthenticated` requirement means anonymous requests are rejected before any business logic

## 3. Hardcoded SECRET_KEY and Database Credentials

**CWE-798: Use of Hard-coded Credentials**  
**CWE-259: Use of Hard-coded Password**

### Exploit

```python
# VULNERABLE: secrets in source control
# settings.py
SECRET_KEY = "django-insecure-x$k9#z@y4q7r2b8f^p!w3n5j6h1m0t8v"
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "myapp_production",
        "USER": "admin",
        "PASSWORD": "SuperSecret123!",
        "HOST": "db.internal.example.com",
        "PORT": "5432",
    }
}
```

Anyone who clones the repo, finds the backup in `.git/logs/`, or discovers the commit history gets:
- The **SECRET_KEY** — which allows forging DRF authentication tokens, signing session cookies, and breaking cryptographic protection on signed tokens used elsewhere
- **Database credentials** — direct read/write access to production data

```bash
# Attacker scans git history
$ git log --all --full-history --settings.py | grep PASSWORD
# Finds the hardcoded password in the earliest commit

# Or simply: the file is committed, so everyone with clone access
# sees plaintext credentials
$ cat settings.py
PASSWORD = "SuperSecret123!"
```

### Fix: Environment-variable-backed secrets management

```python
import os
import logging
from pathlib import Path
from django.core.exceptions import ImproperConfigured

BASE_DIR = Path(__file__).resolve().parent.parent
logger = logging.getLogger(__name__)


def _get_secret(name: str, fallback: str | None = None) -> str:
    """Retrieve a secret from environment, raising if missing."""
    value = os.environ.get(name, fallback)
    if not value:
        raise ImproperConfigured(
            f"Environment variable {name} is required but not set."
        )
    return value


# ------------------------------------------------------------------ #
# SECRET_KEY — never in source; mandatory env var                     #
# ------------------------------------------------------------------ #
SECRET_KEY = _get_secret("DJANGO_SECRET_KEY")

DEBUG = os.environ.get("DJANGO_DEBUG", "false").lower() == "true"
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "*").split(",")


# ------------------------------------------------------------------ #
# DATABASE — credentials from env                                     #
# ------------------------------------------------------------------ #
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("DB_NAME", "myapp"),
        "USER": os.environ.get("DB_USER", "postgres"),
        "PASSWORD": _get_secret("DB_PASSWORD"),
        "HOST": os.environ.get("DB_HOST", "localhost"),
        "PORT": os.environ.get("DB_PORT", "5432"),
    }
}


# ------------------------------------------------------------------ #
# Additional secrets                                                   #
# ------------------------------------------------------------------ #
JWT_SECRET_KEY = _get_secret("JWT_SECRET_KEY")
SIMPLE_JWT = {
    "SIGNING_KEY": JWT_SECRET_KEY,
    "ALGORITHM": "HS256",
}

EMAIL_HOST_PASSWORD = _get_secret("EMAIL_HOST_PASSWORD")
AWS_SECRET_ACCESS_KEY = os.environ.get("AWS_SECRET_ACCESS_KEY")
```

Supporting `.env` template (never committed with real values):

## 4. Mass Assignment via Undeserialized Fields

**CWE-284: Improper Access Control (Mass Assignment / Over-privileged Serialization)**

### Exploit

```python
# VULNERABLE: Using ModelSerializer with no field restrictions
class ReportSerializer(serializers.ModelSerializer):
    class Meta:
        model = Report
        fields = "__all__"       # ← serializes EVERY field including internal ones

    # Or even worse — adding extra writable fields exposed to API callers
    is_active = serializers.BooleanField(default=True)
    role = serializers.ChoiceField(choices=["viewer", "editor", "admin"])
```

An attacker sends:

```json
PATCH /api/reports/42/ HTTP/1.1
Host: app.example.com
Authorization: Token abc123

{
    "title": "My Report",
    "content": "Updated content",
    "is_admin": true,
    "role": "admin",
    "created_by_superuser": true,
    "deleted_at": null,
    "tenant_id": 9999
}
```

Because `fields = "__all__"` includes *every* model field and extra serializer fields like `role` accept input, the attacker gains admin privileges, impersonates superusers, hijacks other tenants, or resurrects soft-deleted records.

### Fix: Explicit field allowlisting + computed/read-only fields

```python
from rest_framework import serializers


class ReportSerializer(serializers.ModelSerializer):
    """
    Serializer with strict field allowlisting.
    Only explicitly named fields are accepted for write operations.
    Extra non-model fields are readOnly (display-only).
    """

    # Display-only computed fields — NEVER writable
    author_name = serializers.CharField(
        source="created_by.get_full_name",
        read_only=True,
    )
    tenant_name = serializers.CharField(
        source="tenant.name",
        read_only=True,
    )

    class Meta:
        model = Report
        # Explicit allowlist — add/remove fields deliberately
        fields = [
            "id",
            "title",
            "content",
            "created_at",
            "updated_at",
            "author_name",
            "tenant_name",
        ]
        # These fields can be written by clients
        read_only_fields = [
            "id",
            "created_at",
            "updated_at",
            "author_name",
            "tenant_name",
        ]

    def validate_title(self, value: str) -> str:
        if len(value.strip()) < 1:
            raise serializers.ValidationError("Title must not be blank.")
        if len(value) > 500:
            raise serializers.ValidationError("Title must not exceed 500 characters.")
        return value

    def validate_content(self, value: str) -> str:
        if len(value) > 50_000:
            raise serializers.ValidationError("Content exceeds maximum length.")
        return value


class CreateUserSerializer(serializers.ModelSerializer):
    """
    Strictly scoped serializer for user creation.
    Never expose staff flags, superuser status, or group assignments
    through user-facing endpoints.
    """
    password = serializers.CharField(write_only=True, style={"input_type": "password"})
    password_confirm = serializers.CharField(write_only=True, style={"input_type": "password"})

    class Meta:
        model = User
        fields = [
            "id",
            "username",
            "email",
            "first_name",
            "last_name",
            "password",
            "password_confirm",
        ]
        read_only_fields = ["id"]

    def validate(self, attrs: dict) -> dict:
        if attrs.pop("password") != attrs.pop("password_confirm"):
            raise serializers.ValidationError(
                {"password_confirm": "Passwords do not match."}
            )

        # Block dangerous defaults — staff/superuser MUST be set admin-only
        attrs["is_staff"] = False
        attrs["is_superuser"] = False
        attrs.pop("is_active", None)
        attrs["is_active"] = True
        return attrs

    def create(self, validated_data: dict) -> User:
        user = User.objects.create_user(**validated_data)
        return user


class StaffUserUpdateSerializer(serializers.ModelSerializer):
    """
    Restricted serializer available ONLY to is_staff users.
    Allows toggling staff flag but nothing else sensitive.
    """
    class Meta:
        model = User
        fields = [
            "id",
            "username",
            "email",
            "is_staff",
            "is_active",
        ]
        read_only_fields = ["id"]

    def update(self, instance: User, validated_data: dict) -> User:
        # Enforce: only staff can update these specific fields
        allowed_fields = {"is_staff", "is_active"}
        clean_data = {
            k: v for k, v in validated_data.items() if k in allowed_fields
        }
        for attr, value in clean_data.items():
            setattr(instance, attr, value)
        instance.save()
        return instance
```

Usage pattern — ensure staff-only actions hit the restricted serializer:

```python
class UserViewSet(viewsets.ModelViewSet):
    queryset = User.objects.all()
    serializer_class = CreateUserSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_serializer_class(self):
        """
        Route write actions to appropriate serializers based on authZ.
        Regular users → CreateUserSerializer (no staff toggle).
        Staff → StaffUserUpdateSerializer (staff toggle allowed).
        """
        user = self.request.user
        if user.is_staff and self.action in ("update", "partial_update"):
            return StaffUserUpdateSerializer
        return CreateUserSerializer

    def perform_create(self, serializer):
        """Staff/superuser fields injected server-side, never from payload."""
        instance = serializer.save(is_staff=False, is_superuser=False)
        return instance
```

## Summary of All Fixes Applied

| Issue | CWE | Attack Surface | Fix |
|-------|-----|----------------|-----|
| SQL via f-string in `cursor.execute()` | CWE-89 | Query params on report endpoint | Parameterized `%s` placeholders + safe defaults |
| Permissions checked only in React | CWE-285 | Direct API calls, modified frontends | `ObjectPermissionRequiredMixin` with `has_object_permission()` on every request |
| Hardcoded SECRET_KEY & DB creds | CWE-798 / CWE-259 | Public repo, backups, anyone with clone access | Environment variables via `_get_secret()` + mandatory validation |
| Mass-assignment serializer | CWE-284 | JSON payloads setting arbitrary model fields | Explicit `fields` allowlist + `read_only_fields` + server-side injection of privileged fields |

The single most impactful change is the server-side permission mixin combined with tenant-scoped querysets — together they eliminate both cross-tenant data leakage and unauthorized object access, regardless of what the frontend does or whether an attacker bypasses it entirely.
