## Issue 1: SQL Injection via F-String Concatenation

**CWE:** CWE-89 — *SQL Injection*

### The Vulnerability

```python
# VULNERABLE views/report.py
from django.db import connection

def generate_report(request):
    tenant_id = request.query_params.get('tenant', 'default')
    start_date = request.query_params.get('start_date')
    end_date = request.query_params.get('end_date')
    status = request.query_params.get('status', 'active')

    query = f"""
        SELECT id, name, total
        FROM reports
        WHERE tenant_id = '{tenant_id}'
          AND created_at BETWEEN '{start_date}' AND '{end_date}'
          AND status = '{status}'
    """

    with connection.cursor() as cursor:
        cursor.execute(query)   # ← raw string execution
        rows = cursor.fetchall()

    return Response(rows)
```

### Exploit Demonstration

An attacker crafts a malicious `tenant_id` parameter:

```
GET /api/report/?tenant='; DROP TABLE reports; --&start_date=2026-01-01&end_date=2026-12-31
```

This produces the final query:
```sql
SELECT id, name, total
FROM reports
WHERE tenant_id = ''; DROP TABLE reports; --'
  AND created_at BETWEEN '2026-01-01' AND '2026-12-31'
  AND status = 'active'
```

The semicolon terminates the `SELECT`, `DROP TABLE reports` executes, and the `--` comments out the rest. In a multi-tenant setup, the attacker could also exfiltrate another tenant's data:

```
GET /api/report/?tenant=' UNION SELECT password, credit_card, ssn FROM users WHERE tenant_id='acme' --
```

### The Fix

Use parameterized queries — never interpolate user input into SQL strings:

```python
# FIXED views/report.py
import logging
from datetime import date
from django.db import connection
from rest_framework.response import Response
from rest_framework.views import APIView

logger = logging.getLogger(__name__)


class ReportView(APIView):
    def get(self, request):
        tenant_id = request.query_params.get('tenant')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')
        status = request.query_params.get('status', 'active')

        # Validate inputs first
        if not tenant_id or not start_date or not end_date:
            return Response(
                {'error': 'Missing required parameters'},
                status=400,
            )

        try:
            start = date.fromisoformat(start_date)
            end = date.fromisoformat(end_date)
        except ValueError:
            return Response(
                {'error': 'Invalid date format. Use YYYY-MM-DD'},
                status=400,
            )

        if status not in ('active', 'completed', 'archived'):
            return Response(
                {'error': 'Invalid status value'},
                status=400,
            )

        # Parameterized query — all values passed as a list
        query = """
            SELECT id, name, total
            FROM reports
            WHERE tenant_id = %s
              AND created_at BETWEEN %s AND %s
              AND status = %s
        """

        try:
            with connection.cursor() as cursor:
                cursor.execute(query, [tenant_id, start, end, status])
                columns = [col[0] for col in cursor.description]
                rows = [dict(zip(columns, row)) for row in cursor.fetchall()]
        except Exception as exc:
            logger.error("Report query failed: %s", exc)
            return Response(
                {'error': 'Internal report generation error'},
                status=500,
            )

        return Response(rows)
```

**Why this works:** The `%s` placeholders are sent separately from the query string via the PostgreSQL protocol. The database driver handles proper escaping and type handling. The attacker's injected SQL becomes a literal string value that gets searched — it cannot alter query structure.

If you can avoid raw SQL entirely, prefer the ORM:

```python
# BEST: ORM-based approach
from django.utils import timezone
from .models import Report

def generate_report(tenant_id, start_date, end_date, status):
    qs = Report.objects.filter(
        tenant_id=tenant_id,
        created_at__range=[start_date, end_date],
        status=status,
    )
    return list(qs.values('id', 'name', 'total'))
```

## Issue 2: Client-Side-Only Permission Checks

**CWE:** CWE-862 — *Missing Authorization* / CWE-913 — *Perceived Wrong Code Quality* (false sense of security)

### The Vulnerability

```jsx
// VULNERABLE React component
function ReportDetail({ reportId }) {
  const [report, setReport] = useState(null);

  useEffect(() => {
    fetch(`/api/reports/${reportId}`)
      .then(res => res.json())
      .then(data => {
        // Client-side ownership check ONLY
        if (data.tenant_id !== myTenantId) {
          navigate('/forbidden');   // ← This is easily bypassed
          return;
        }
        setReport(data);
      });
  }, []);

  function handleDelete() {
    if (report.tenant_id !== myTenantId) {
      alert('Not authorized');   // ← Still client-side
      return;
    }
    fetch(`/api/reports/${reportId}`, { method: 'DELETE' });
  }
}
```

The server endpoint returns unrestricted data — it trusts the frontend to gate access:

```python
# VULNERABLE views/report.py
class ReportDetailView(APIView):
    # No server-side permission enforcement
    authentication_classes = [TokenAuthentication]

    def get(self, request, pk):
        # Only checks existence, NOT ownership on the server
        report = Report.objects.get(pk=pk)
        serializer = ReportSerializer(report)
        return Response(serializer.data)   # ← Any authenticated user sees any report
```

An attacker uses curl (or intercepts with Burp Suite/OWASP ZAP) to bypass React entirely:

```bash
# Attacker knows report IDs incrementally or guesses them
curl -H "Authorization: Token deadbeef" https://api.example.com/api/reports/42

# Or enumerate via the reports list endpoint
curl -H "Authorization: Token deadbeef" \
  "https://api.example.com/api/reports/?tenant=competitor_corp"
```

### The Fix

Server-side object-level permissions using DRF's `BasePermission`:

```python
# FIXED permissions/report_permissions.py
from rest_framework import permissions
from rest_framework.exceptions import NotFound


class IsReportTenantOwner(permissions.BasePermission):
    """
    Object-level permission: only users belonging to the same tenant
    may read, modify, or delete a report.
    """

    message = 'You do not have access to this report.'

    def has_object_permission(self, request, view, obj):
        # Both the requesting user and the report must have a tenant
        if not hasattr(request.user, 'tenant') or not hasattr(obj, 'tenant'):
            return False

        return request.user.tenant == obj.tenant


class IsAdminOrTenantOwner(permissions.BasePermission):
    """
    Admin staff can access all reports; regular tenants only their own.
    Safe methods (GET, HEAD, OPTIONS) follow object-level rules.
    Write methods require admin OR owner.
    """

    message = 'You lack permission to perform this action.'

    def has_permission(self, request, view):
        # All requests require authentication
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        # Admins can access everything
        if request.user.is_staff:
            return True

        return request.user.tenant == obj.tenant
```

```python
# FIXED views/report.py
from rest_framework.permissions import IsAuthenticated
from rest_framework.generics import RetrieveAPIView, DestroyAPIView, ListAPIView
from .models import Report
from .serializers import ReportSerializer
from .permissions import IsReportTenantOwner, IsAdminOrTenantOwner


class ReportListView(ListAPIView):
    """List only reports belonging to the requesting user's tenant."""
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        # Server-side tenant scoping — impossible to bypass
        return Report.objects.filter(tenant=self.request.user.tenant)


class ReportDetailView(RetrieveAPIView):
    queryset = Report.objects.all()          # Base queryset (further filtered by permission)
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated, IsReportTenantOwner]


class ReportDeleteView(DestroyAPIView):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated, IsAdminOrTenantOwner]

    def get_queryset(self):
        if self.request.user.is_staff:
            return Report.objects.all()
        return Report.objects.filter(tenant=self.request.user.tenant)
```

```python
# FIXED urls.py — use path parameter routing
from django.urls import path
from .views import ReportListView, ReportDetailView, ReportDeleteView

urlpatterns = [
    path('reports/', ReportListView.as_view(), name='report-list'),
    path('reports/<int:pk>/', ReportDetailView.as_view(), name='report-detail'),
    path('reports/<int:pk>/delete/', ReportDeleteView.as_view(), name='report-delete'),
]
```

**Why this works:** Every request — whether from the React SPA, a browser, curl, or a compromised JWT token — passes through the permission classes before any data touches the response. The ORM's `.filter()` on `get_queryset` means even if permissions were misconfigured, unscoped objects are never returned. Together they provide defense-in-depth.

## Issue 3: Hardcoded Secrets in settings.py Committed to Git

**CWE:** CWE-798 — *Use of Hard-coded Credentials* / CWE-259 — *Use of Hard-coded Password*

### The Vulnerability

```python
# VULNERABLE settings/base.py  (committed to version control)
SECRET_KEY = 'django-insecure-k8#fj2$9x@bv1^r@m&tq!wz4*y+p_6s$cnx@e5n^m'

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'production_db',
        'USER': 'admin',
        'PASSWORD': 'P@ssw0rd123!',       # ← Plaintext creds in repo history
        'HOST': 'db.internal.example.com',
        'PORT': '5432',
    }
}

# Also leaked via .env tracking, docker-compose.yml secrets, or CI logs
AWS_ACCESS_KEY_ID = 'AKIAIOSFODNN7EXAMPLE'
AWS_SECRET_ACCESS_KEY = 'wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY'
```

Even with a `.gitignore`, these values live in every commit that touched `settings.py`. `git log -p` and `git blame` expose them indefinitely. Anyone with repository access (or a fork, leak, or breach) gains production credentials.

### The Fix

Three layers: externalize secrets, load them at runtime, and validate presence.

```python
# FIXED settings/base.py
import os
from pathlib import Path
from django.core.exceptions import ImproperlyConfigured

BASE_DIR = Path(__file__).resolve().parent.parent


def env(key, default=None, cast=None):
    """
    Read an environment variable with optional casting.
    Raises ImproperlyConfigured if a required var is missing.
    """
    value = os.environ.get(key, default)
    if value is None and default is None:
        raise ImproperlyConfigured(f"Environment variable '{key}' is required")
    if cast and value is not None:
        value = cast(value)
    return value


# ---- Secret Key ----
# NEVER hardcode. Loaded from env; fail loudly if absent.
SECRET_KEY = env('DJANGO_SECRET_KEY')

# ---- Database ----
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': env('DB_NAME', 'app_db'),
        'USER': env('DB_USER', 'app_user'),
        'PASSWORD': env('DB_PASSWORD'),            # ← From env, never hardcoded
        'HOST': env('DB_HOST', 'localhost'),
        'PORT': env('DB_PORT', '5432'),
    }
}

# ---- AWS Credentials (if used) ----
AWS_ACCESS_KEY_ID = env('AWS_ACCESS_KEY_ID', default=None)
AWS_SECRET_ACCESS_KEY = env('AWS_SECRET_ACCESS_KEY', default=None)

# ---- Allowed Hosts ----
ALLOWED_HOSTS = env('ALLOWED_HOSTS', '').split(',')
if not ALLOWED_HOSTS:
    raise ImproperlyConfigured(
        "Set the ALLOWED_HOSTS environment variable "
        "(comma-separated domain list)"
    )

# ---- Redis / Cache ----
REDIS_URL = env('REDIS_URL', 'redis://localhost:6379/0')

SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
SESSION_CACHE_ALIAS = 'default'
CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.redis.RedisCacheBack'
                  'end',
        'LOCATION': REDIS_URL,
    }
}
```

```python
# management command to detect accidental hardcoding (run in CI)
# manage.py check_secrets
from django.core.management.base import BaseCommand
from django.conf import settings
import inspect
import re


class Command(BaseCommand):
    help = 'Check for hardcoded secrets in settings'

    def handle(self, *args, **options):
        errors = []
        settings_source = inspect.getsource(settings)

        patterns = {
            'hardcoded_secret_key': r"""SECRET_KEY\s*=\s*['\"][^'\"]+['\"]""",
            'hardcoded_password': r"""'PASSWORD'\s*:\s*['\"][^'\"]+['\"]""",
            'aws_access_key': r"""'AKIA[0-9A-Z]{16}""",
        }

        for name, pattern in patterns.items():
            matches = re.findall(pattern, settings_source)
            if matches:
                errors.append(f"{name}: {matches}")

        if errors:
            for err in errors:
                self.stderr.write(self.style.ERROR(f"Secret leak detected: {err}"))
            raise SystemExit(1)

        self.stdout.write(self.style.SUCCESS('No hardcoded secrets detected.'))
```

Add this check to your CI pipeline (`pre-commit` or GitHub Actions). A tool like [`gitleaks`](https://github.com/gitleaks/gitleaks) or [`detect-secrets`](https://github.com/Yelp/detect-secrets) provides more thorough scanning.

## Issue 4: Mass Assignment in Serializers

**CWE:** CWE-915 — *Improperly Controlled Modification of Dynamically-Determined Object Attributes* (aka Over Posting / Mass Assignment)

### The Vulnerability

```python
# VULNERABLE serializers/report_serializers.py
from rest_framework import serializers
from .models import Report


class ReportSerializer(serializers.ModelSerializer):
    class Meta:
        model = Report
        fields = '__all__'           # ← Exposes EVERY field, including sensitive ones

    # Staff status can be toggled because 'is_staff' is in the writable fields
    # An attacker sends: {"title": "...", "is_staff": true}
    # and becomes a staff member.
```

```json
{
    // Attacker modifies this in the network tab
    {
        "title": "Quarterly Revenue",
        "is_staff": true,
        "is_superuser": true,
        "role": "admin",
        "tenant": null
    }
}
```

Even with `fields = ['id', 'title', 'content']` explicitly listed, a related nested serializer can still allow over-posting of privileged fields on the relationship side. And `read_only_fields` alone isn't enough when `fields = '__all__'` is used.

### The Fix

Explicit white-listing: separate read-write fields from read-only fields. Never use `fields = '__all__'` on serializers exposed to users.

```python
# FIXED serializers/report_serializers.py
from rest_framework import serializers
from django.contrib.auth import get_user_model
from .models import Report

User = get_user_model()


class ReportSerializer(serializers.ModelSerializer):
    # Explicitly declare the API-facing schema
    # READ/WRITE fields (what the API accepts)
    title = serializers.CharField(max_length=200)
    content = serializers.CharField(required=False, allow_blank=True)
    status = serializers.ChoiceField(
        choices=['draft', 'published', 'archived'],
        default='draft',
    )

    # Derived/read-only fields (populated by the server, rejected in writes)
    author_email = serializers.EmailField(source='author.email', read_only=True)
    created_at = serializers.DateTimeField(read_only=True)
    updated_at = serializers.DateTimeField(read_only=True)

    class Meta:
        model = Report
        # White-list: only these fields are accepted from clients
        fields = [
            'id',
            'title',
            'content',
            'status',
            'author_email',
            'created_at',
            'updated_at',
        ]
        # Extra safety net: mark anything not in 'fields' as read-only
        extra_kwargs = {
            'author': {'read_only': True},          # Cannot be reassigned
            'tenant': {'read_only': True},           # Tenant forced server-side
            'created_by_staff_action': {'read_only': True},
        }

    def create(self, validated_data):
        # Enforce multi-tenancy: the tenant is always the requester's, never the payload's
        validated_data['author'] = self.context['request'].user
        validated_data['tenant'] = self.context['request'].user.tenant
        return super().create(validated_data)

    def update(self, instance, validated_data):
        # Prevent privilege escalation: reject attempts to change protected fields
        disallowed_changes = {'tenant', 'author'}
        if disallowed_changes & validated_data.keys():
            raise serializers.ValidationError(
                'Cannot modify tenant or author through this endpoint.'
            )
        return super().update(instance, validated_data)
```

```python
# FIXED views/report.py — tie the serializer to the permission system
from rest_framework import generics, permissions
from .models import Report
from .serializers import ReportSerializer
from .permissions import IsAdminOrTenantOwner


class ReportCreateView(generics.CreateAPIView):
    serializer_class = ReportSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):
        return Report.objects.filter(tenant=self.request.user.tenant)

    def perform_create(self, serializer):
        # Serializer gets the request context for tenant/author injection
        serializer.save(author=self.request.user, tenant=self.request.user.tenant)


class ReportUpdateView(generics.UpdateAPIView):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer
    permission_classes = [IsAdminOrTenantOwner]

    def get_queryset(self):
        if self.request.user.is_staff:
            return Report.objects.all()
        return Report.objects.filter(tenant=self.request.user.tenant)
```

## Defense-in-Depth Summary

| Layer | Control | Mitigates |
|-------|---------|-----------|
| **Query layer** | Parameterized `cursor.execute(query, params)` | CWE-89 SQL Injection |
| **Permission layer** | DRF `BasePermission.has_object_permission()` + scoped `get_queryset()` | CWE-862 Missing Authorization |
| **Configuration layer** | `os.environ` loading + runtime validation + CI secret scanning | CWE-798 Hard-coded Credentials |
| **Serialization layer** | Explicit `fields` whitelist + `extra_kwargs` + contextual `save()` | CWE-915 Mass Assignment |

Each control independently blocks the attack. Even if one fails (a broken permission class, a developer adding `fields = '__all__'` temporarily), the other layers contain the blast radius. That is the essence of layered security.
