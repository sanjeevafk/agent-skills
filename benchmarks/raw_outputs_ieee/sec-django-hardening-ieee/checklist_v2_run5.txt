# Multi-Tenant Django REST Security Hardening Report

## Executive Summary

Four critical vulnerabilities identified and remediated: SQL injection (CWE-89), broken access control at the API layer (CWE-284), secrets in source code (CWE-798), and mass assignment / insecure direct object reference at the serialization layer (CWE-915). All fixes follow Django's documented defensive patterns.

## Issue 1: SQL Injection via F-String in `cursor.execute()`

**CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')**

### Vulnerable Code

```python
# apps/reports/views.py — VULNERABLE
from django.db import connection

def report_endpoint(request):
    tenant_id = request.query_params.get('tenant', '')
    start_date = request.query_params.get('start_date', '')
    end_date = request.query_params.get('end_date', '')

    query = (
        f"SELECT id, name, total FROM orders "
        f"WHERE tenant_id = '{tenant_id}' "
        f"AND created_at BETWEEN '{start_date}' AND '{end_date}'"
    )
    with connection.cursor() as cursor:
        cursor.execute(query)  # f-string → raw SQL injection
        rows = cursor.fetchall()
    return Response(rows)
```

### Exploit

```bash
# Attacker injects arbitrary SQL via the tenant parameter
curl 'http://api.example.com/reports/?tenant=0%27%20UNION%20SELECT%20id,password,email,created_at%20FROM%20users%23'

# Decoded: tenant=' UNION SELECT id,password,email,created_at FROM users#
# Result: Every user credential set dumped into the report endpoint response.
```

### Remediated Code

```python
# apps/reports/views.py — HARDENED
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated
from django.db import connection, transaction


class ReportEndpoint(APIView):
    """Parameterized queries protect against SQL injection."""

    permission_classes = [IsAuthenticated]

    def get(self, request):
        tenant_id = request.query_params.get('tenant')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')

        # Validate types before querying — rejects non-integer / malformed values early
        try:
            tenant_id = int(tenant_id)
        except (TypeError, ValueError):
            return Response(
                {'error': 'Invalid tenant_id. Must be an integer.'},
                status=400,
            )

        if not start_date or not end_date:
            return Response(
                {'error': 'start_date and end_date are required.'},
                status=400,
            )

        # PARAMETERIZED query — Django replaces %s placeholders with safely escaped values
        sql = (
            "SELECT id, name, total FROM orders "
            "WHERE tenant_id = %s "
            "AND created_at BETWEEN %s AND %s"
        )
        params = [tenant_id, start_date, end_date]

        with transaction.atomic():
            with connection.cursor() as cursor:
                cursor.execute(sql, params)  # ← safe parameter binding
                columns = [desc[0] for desc in cursor.description]
                rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

        return Response(rows)
```

### Why This Is Secure

| Mechanism | What It Does |
|-----------|-------------|
| `%s` placeholders | Django's psycopg2 adapter parameterizes; values are never interpolated into the SQL string |
| `int()` coercion | Rejects anything that isn't a pure integer before it reaches the query |
| `transaction.atomic()` | Wraps the read in a savepoint for consistency if downstream writes are added |

The OWASP definition applies verbatim: the fix *prevents* special elements (`UNION`, comments, quote closures) from being interpreted as SQL syntax because they travel as data — bound parameters — separate from the command text. See the Django docs for [`raw()`](https://docs.djangoproject.com/en/stable/topics/db/sql/#performing-raw-querysets) and [`connection.cursor()` parameter binding](https://docs.djangoproject.com/en/stable/ref/databases/#third-party-database-notes).

## Issue 2: Object-Level Authorization Checked Only in React

**CWE-284: Improper Access Control (client-side enforcement)**

### Vulnerable Pattern

```jsx
// frontend/src/components/ReportPanel.jsx — VULNERABLE (client-side check only)
function ReportPanel({ tenantId }) {
  const [report, setReport] = useState(null);

  useEffect(() => {
    // Frontend checks ownership BEFORE fetching
    if (!user.isOwnerOfTenant(tenantId)) {
      showError("You can't view this tenant's reports.");
      return;
    }
    fetch(`/reports/?tenant=${tenantId}`)
      .then(r => r.json())
      .then(setReport);
  }, [tenantId]);
}
```

### Exploit

An authenticated attacker simply calls the API directly — curl, Postman, or a script — bypassing the React check entirely:

```bash
# User A logs in, then requests User B's tenant data directly
curl -H "Authorization: Token <user_a_token>" \
     'http://api.example.com/reports/?tenant=<user_b_tenant_id>'
```

No middleware validates that `request.user.tenant == tenant_id`. The backend trusts the client-side gate.

```python
# apps/common/permissions.py — Server-side object-level enforcement
from rest_framework import permissions
from django.core.exceptions import PermissionDenied


class IsTenantMember(permissions.BasePermission):
    """
    Enforce that the requesting user belongs to the requested tenant.

    Checks both:
      1. The URL parameter `tenant` maps to an object the user owns/is member of.
      2. The queryset itself is scoped to the user's tenants (DRF standard pattern).
    """

    def has_permission(self, request, view):
        return request.user and request.user.is_active

    def has_object_permission(self, request, view, obj):
        """Object must belong to one of the user's authorized tenants."""
        # Generic FK support: try owner_tenant first, then fall back to tenant
        tenant_field = getattr(obj, 'owner_tenant', None) or getattr(obj, 'tenant', None)
        if tenant_field is None:
            return False
        return request.user.tenants.filter(id=tenant_field.id).exists()

    def scope_queryset(self, request, qs):
        """
        CRITICAL: Limit the base queryset to objects belonging to
        the user's authorized tenants. This prevents IDOR even when
        has_object_permission is bypassed.
        """
        return qs.filter(owner_tenant__in=request.user.tenants.all())
```

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated
from rest_framework.throttling import UserRateThrottle
from django.db import connection, transaction
from apps.common.permissions import IsTenantMember
from apps.reports.serializers import ReportSerializer
from apps.orders.models import Order


class ReportEndpoint(APIView):
    permission_classes = [IsAuthenticated, IsTenantMember]

    throttle_classes = [UserRateThrottle]

    def get_queryset(self):
        """Scope to user's tenants — prevents listing other tenants' data."""
        return Order.objects.filter(
            owner_tenant__in=self.request.user.tenants.all()
        ).select_related('owner_tenant')

    def get(self, request):
        tenant_id = request.query_params.get('tenant')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')

        try:
            tenant_id = int(tenant_id)
        except (TypeError, ValueError):
            return Response(
                {'error': 'Invalid tenant_id. Must be an integer.'},
                status=400,
            )

        # Verify tenant membership at the instance level (not just query scope)
        try:
            tenant = request.user.tenants.get(id=tenant_id)
        except (ValueError, AssertionError):
            return Response({'error': 'Tenant not found.'}, status=404)
        except request.user.tenants.model.DoesNotExist:
            raise PermissionDenied(
                'You do not have access to this tenant.'
            )

        sql = (
            "SELECT id, name, total FROM orders "
            "WHERE tenant_id = %s AND created_at BETWEEN %s AND %s"
        )
        params = [tenant_id, start_date, end_date]

        with transaction.atomic():
            with connection.cursor() as cursor:
                cursor.execute(sql, params)
                columns = [desc[0] for desc in cursor.description]
                rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

        serialized = ReportSerializer(rows, many=True)
        return Response(serialized.data)
```

## Issue 4: Mass Assignment via Serializer

**CWE-915: Improper Restriction of Excessive Authentication Entitlements (serializer-level mass assignment)**

### Vulnerable Code

```python
# apps/users/serializers.py — VULNERABLE
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class UserRegistrationSerializer(serializers.ModelSerializer):
    """Allows registering a new user. Also accepts staff_is_true from payload."""

    class Meta:
        model = User
        fields = '__all__'          # ← includes is_staff, is_superuser, role, …
        extra_kwargs = {
            'password': {'write_only': True},
        }

    def create(self, validated_data):
        password = validated_data.pop('password')
        user = User(**validated_data)   # mass-assigned!
        user.set_password(password)
        user.save()
        return user
```

A malicious POST body creates admin accounts:

```json
{
  "email": "attacker@evil.com",
  "username": "eviladmin",
  "password": "StrongPass1!",
  "is_staff": true,
  "is_superuser": true,
  "role": "admin"
}
```

```bash
curl -X POST http://api.example.com/register/ \
     -H "Content-Type: application/json" \
     -d '{"email":"attacker@evil.com","username":"eviladmin",
          "password":"StrongPass1!","is_staff":true,"is_superuser":true}'
# Result: attacker now has admin panel access.
```

### Remediated Code

```python
# apps/users/serializers.py — HARDENED
from rest_framework import serializers
from django.contrib.auth import get_user_model
from django.conf import settings

User = get_user_model()

# Whitelist of fields clients may set during registration
REGISTER_ALLOWED_FIELDS = frozenset([
    'username',
    'email',
    'password',
    'phone',
    'first_name',
    'last_name',
])


class UserRegistrationSerializer(serializers.ModelSerializer):
    """
    Strictly whitelisted fields prevent mass assignment of is_staff,
    is_superuser, and role.
    """

    class Meta:
        model = User
        fields = list(REGISTER_ALLOWED_FIELDS)
        extra_kwargs = {
            'password': {'write_only': True, 'min_length': 8},
            'email': {'required': True},
            'username': {'required': True, 'min_length': 3},
        }

    def create(self, validated_data):
        password = validated_data.pop('password')
        user = User(**validated_data)
        user.set_password(password)
        user.save()
        return user


class UserUpdateSerializer(serializers.ModelSerializer):
    """
    Fields allowed for self-update vs. admin update are separated.
    Clients cannot modify is_staff, is_superuser, email, or username
    through the public update endpoint.
    """

    class Meta:
        model = User
        # Safe self-service fields only — no privilege escalation paths
        fields = ['first_name', 'last_name', 'phone']
        extra_kwargs = {
            'first_name': {'required': False, 'max_length': 150},
            'last_name': {'required': False, 'max_length': 150},
            'phone': {'required': False, 'max_length': 20},
        }

    def validate_phone(self, value):
        if value and not value.replace('+', '').replace('-', '').replace(' ', '').isdigit():
            raise serializers.ValidationError('Phone number must contain only digits, +, -, or spaces.')
        return value

    def update(self, instance, validated_data):
        # Extra guard: re-check that no forbidden fields slipped through
        disallowed_fields = set(validated_data.keys()) - set(self.Meta.fields)
        if disallowed_fields:
            raise serializers.ValidationError(
                f'This endpoint does not permit updating: {", ".join(disallowed_fields)}'
            )
        return super().update(instance, validated_data)


class AdminUserSerializer(serializers.ModelSerializer):
    """
    Admin-only serializer. Used exclusively by internal admin endpoints
    that require Staff permissions.
    """

    class Meta:
        model = User
        fields = [
            'id', 'username', 'email', 'first_name', 'last_name',
            'phone', 'is_active', 'is_staff', 'is_superuser', 'role',
            'date_joined', 'last_login',
        ]
        read_only_fields = ['id', 'date_joined', 'last_login']
```

## Fix Summary Matrix

| # | Issue | CWE | Root Cause | Fix Applied |
|---|-------|-----|------------|-------------|
| 1 | SQL injection in `cursor.execute()` | **CWE-89** | `f"...{tenant_id}..."` concatenated into raw SQL string | Parameterized `%s` placeholders + `int()` type coercion |
| 2 | Object-level permission only in React | **CWE-284** | No `has_object_permission` / queryset scoping in DRF views | `IsTenantMember` BasePermission with `scope_queryset` override + instance-level tenant verification |
| 3 | Hardcoded SECRET_KEY & DB creds | **CWE-798** | Plaintext credentials in committed `settings.py` | `django-environ` reading from `.env` (ignored in git); Runtime validation raises `ImproperConfigured` |
| 4 | Mass-assign `is_staff` via serializer | **CWE-915** | `fields = '__all__'` on registration serializer | Separate `UserRegistrationSerializer` (whitelist) + `UserUpdateSerializer` (self-service subset) + `AdminUserSerializer` (admin-only); disallowed-field guard in `update()` |

All four mitigations align with the Django project's own security guidance: parameterized SQL, server-side permission classes, environment-variable-based secrets, and explicit serializer field lists over `__all__`.
