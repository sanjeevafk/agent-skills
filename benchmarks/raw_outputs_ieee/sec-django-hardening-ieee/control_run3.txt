# Multi-Tenant Django REST Security Hardening Report

## Issue 1: SQL Injection via F-String Concatenation in Raw Query

### CWE: [CWE-89](https://cwe.mitre.org/data/definitions/89/) — Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')

### Vulnerable Code

```python
# reports/views.py
from django.db import connection

class TenantReportView(APIView):
    authentication_classes = [SessionAuthentication]
    permission_classes = [IsAuthenticated]

    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')
        status = request.query_params.get('status', 'all')

        # VULNERABLE: f-string concatenation into raw SQL
        sql = f"""
            SELECT r.id, r.title, r.amount, r.created_at
            FROM reports.report r
            JOIN tenants.tenant t ON r.tenant_id = t.id
            WHERE t.slug = '{tenant_id}'
              AND r.status = '{status}'
              AND r.created_at BETWEEN '{start_date}' AND '{end_date}'
        """

        with connection.cursor() as cursor:
            cursor.execute(sql)  # ← direct execution of untrusted string
            rows = cursor.fetchall()

        return Response(rows)
```

### Exploit Demonstration

An attacker crafts `tenant_id` to escape the single-quote context and run arbitrary SQL:

```
GET /api/reports/?tenant_id=' OR 1=1; DROP TABLE tenants.tenant --&start_date=2025-01-01&end_date=2026-12-31&status=all
```

**What happens:** The resulting SQL becomes:
```sql
WHERE t.slug = '' OR 1=1; DROP TABLE tenants.tenant --'
```
This returns **all reports from every tenant** and **deletes the tenant table**. With a UNION-based injection:

```
GET /api/reports/?tenant_id=' UNION SELECT id,password,email,'admin' FROM auth_user --&start_date=&end_date=&status=all
```

Can dump password hashes and user emails. In PostgreSQL or MySQL with appropriate privileges, this can escalate to **full database compromise or remote code execution** (`pg_exec`, `LOAD_FILE`).

### Root Cause

Every value from `request.query_params` is interpolated directly into the SQL string via f-strings. Even values the developer believes are "safe" (dates, statuses) become attack vectors when any parameter is exposed.

### Corrected Code — Parameterized Queries

```python
# reports/views.py
from django.db import connection

class TenantReportView(APIView):
    authentication_classes = [SessionAuthentication]
    permission_classes = [IsAuthenticated]

    ALLOWED_STATUSES = {'pending', 'approved', 'rejected', 'all'}

    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')
        status = request.query_params.get('status', 'all')

        # FIX 1: Validate enum-like fields against an allowlist
        if status not in self.ALLOWED_STATUSES:
            return Response(
                {'error': 'Invalid status filter'},
                status=400
            )

        if not tenant_id or not start_date or not end_date:
            return Response(
                {'error': 'Missing required parameters'},
                status=400
            )

        # FIX 2: Use parameterized query with named placeholders
        sql = """
            SELECT r.id, r.title, r.amount, r.created_at
            FROM reports.report r
            JOIN tenants.tenant t ON r.tenant_id = t.id
            WHERE t.slug = %(tenant_id)s
              AND r.status = %(status)s
              AND r.created_at BETWEEN %(start_date)s::date AND %(end_date)s::date
        """

        params = {
            'tenant_id': tenant_id,
            'status': status,
            'start_date': start_date,
            'end_date': end_date,
        }

        with connection.cursor() as cursor:
            cursor.execute(sql, params)  # ← parameterized, safe
            columns = [col[0] for col in cursor.description]
            rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

        return Response(rows)
```

**Key changes:**
- Named `%()` placeholders replace every f-string interpolation
- Values passed separately in `params` dict → DB driver handles escaping
- Enum field (`status`) validated against a hardcoded allowlist before even reaching the query
- Missing-required-fields check prevents empty-string edge cases
- Results mapped to dicts for consistent serialization

**Even better long-term:** Replace raw SQL entirely with Django ORM:

```python
from reports.models import Report
from tenants.models import Tenant

qs = Report.objects.filter(
    tenant__slug=tenant_id,
    status=status if status != 'all' else None,
    created_at__range=(start_date, end_date),
).select_related('tenant')
```

The ORM parameterizes everything automatically and eliminates raw SQL risk altogether.
