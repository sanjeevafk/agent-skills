## 1. SQL Injection via F-String Query Construction

**CWE-89: Improper Neutralization of Special Elements Used in an SQL Command (SQL Injection)**

### Vulnerable Code

```python
# reports/views.py — INSECURE
import sqlite3
from rest_framework.views import APIView
from rest_framework.response import Response

class ReportEndpoint(APIView):
    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')

        # CRITICAL: f-string concatenation into raw SQL
        query = (
            f"SELECT id, name, revenue FROM orders "
            f"WHERE tenant_id = {tenant_id} "
            f"AND order_date BETWEEN '{start_date}' AND '{end_date}'"
        )

        with self._get_db_cursor() as cur:
            cur.execute(query)  # SQLi vulnerability
            rows = cur.fetchall()

        return Response({'results': rows})
```

### Exploit

An attacker crafts `tenant_id` as:

```
GET /api/report?tenant_id=1;DROP TABLE orders--&start_date=&end_date=
```

Resulting SQL executes:

```sql
SELECT id, name, revenue FROM orders WHERE tenant_id = 1;DROP TABLE orders-- AND order_date BETWEEN '' AND ''
```

Or blind exfiltration:

```
GET /api/report?tenant_id=1 UNION SELECT password,username,email FROM users--&start_date=&end_date=
```

### Hardened Fix

Use parameterized queries exclusively:

```python
# reports/views.py — SECURE
import logging
from datetime import date
from rest_framework.views import APIView
from rest_framework.response import Response
from django.db import connection

logger = logging.getLogger(__name__)


def validate_date(value: str) -> date | None:
    """Parse and validate a YYYY-MM-DD date string."""
    if not value:
        return None
    try:
        return date.fromisoformat(value)
    except ValueError:
        return None


class ReportEndpoint(APIView):
    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        start_date_str = request.query_params.get('start_date')
        end_date_str = request.query_params.get('end_date')

        # 1. Validate types at the application layer
        if not tenant_id or not tenant_id.isdigit():
            return Response(
                {'error': 'Valid integer tenant_id is required'},
                status=400,
            )
        tenant_id = int(tenant_id)

        start_date = validate_date(start_date_str)
        end_date = validate_date(end_date_str)

        if start_date is None or end_date is None:
            return Response(
                {'error': 'Valid start_date and end_date (YYYY-MM-DD) are required'},
                status=400,
            )

        # 2. Parameterized query — values are never interpolated into SQL text
        sql = (
            "SELECT id, name, revenue FROM orders "
            "WHERE tenant_id = %s "
            "AND order_date BETWEEN %s AND %s"
        )
        params = [tenant_id, start_date.isoformat(), end_date.isoformat()]

        with connection.cursor() as cur:
            cur.execute(sql, params)
            columns = [desc[0] for desc in cur.description]
            rows = [dict(zip(columns, row)) for row in cur.fetchall()]

        logger.info("Report generated for tenant_id=%d", tenant_id)
        return Response({'results': rows})
```

**Key changes:**
- Integer validation strips numeric strings before any DB use
- Dates are parsed by Python's `date.fromisoformat()`, then passed as `.isoformat()` strings
- `%s` placeholders + separate `params` list ensures the database driver handles escaping
- Column metadata is read from `cur.description` rather than trusting schema names from input

## 2. Client-Side-Only Object Permission Checks

**CWE-284: Improper Access Control (Insecure Direct Object Reference / Missing Server-Side Authorization)**

### Vulnerable Code

```python
# tenants/serializers.py — INSECURE
from rest_framework import serializers
from .models import TenantData

class TenantDataSerializer(serializers.ModelSerializer):
    class Meta:
        model = TenantData
        fields = ['id', 'title', 'content', 'tenant']

    def create(self, validated_data):
        # Trusts the authenticated user — no object-level check
        obj = TenantData.objects.create(**validated_data)
        return obj


# tenants/views.py
from rest_framework.views import APIView
from rest_framework.response import Response

class TenantDataDetailView(APIView):
    def get(self, request, pk):
        obj = TenantData.objects.get(pk=pk)  # No ownership check
        serializer = TenantDataSerializer(obj)
        return Response(serializer.data)

    def delete(self, request, pk):
        # Frontend shows "you can't delete others' data"
        # but there's NO server-side enforcement
        obj = TenantData.objects.get(pk=pk)
        obj.delete()
        return Response(status=204)
```

The frontend React component renders a `"Delete"` button conditionally:

```jsx
{item.ownerId === currentUserId && <button onClick={() => handleDelete(item.id)}>
  Delete
</button>}
```

**This means any authenticated user who guesses another tenant's object ID can read, modify, or delete it.**

### Exploit

```bash
# User A owns objects 1–5. Attacker iterates to find User B's data:
curl -H "Authorization: Token attacker-token" \
     http://api.example.com/api/tenant-data/6/   # Returns User B's data
curl -X DELETE -H "Authorization: Token attacker-token" \
     http://api.example.com/api/tenant-data/6/  # Deletes it
```

### Hardened Fix

Implement server-side object-level authorization with a custom permission class and view-level filtering:

```python
# tenants/permissions.py — SECURE
from rest_framework import permissions
from django.core.exceptions import PermissionDenied


class IsTenantMemberOrReadOnly(permissions.BasePermission):
    """
    Object-level permission that enforces tenant membership and ownership.

    Only members of the same organization (tenant) can access objects.
    Ownership checks govern write operations.
    """

    def has_object_permission(self, request, view, obj):
        # Read access: allowed only if the requesting user belongs to
        # the same tenant/org as the object being accessed.
        if request.method in permissions.SAFE_METHODS:
            return getattr(obj, 'tenant', None) == request.user.tenant
        # Write/delete access: only the owner may mutate.
        if request.method in permissions.SAFE_METHODS:
            return True
        return obj.tenant == request.user.tenant and obj.author == request.user


class StaffCanToggleButNotSuperuser(permissions.BasePermission):
    """Staff members can toggle their own staff flag during editing;
    non-staff cannot escalate privileges."""

    def has_permission(self, request, view):
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        if request.method in ('PUT', 'PATCH'):
            # Only allow staff field changes on the requesting user's own record
            if request.user != obj:
                return False
        return True
```

```python
# tenants/permissions.py — helper for generic views
from rest_framework.permissions import SAFE_METHODS


class SafeMethodReadOnlyMixin:
    """Restricts unsafe-method queryset to tenant-scoped results only."""

    def get_queryset(self):
        qs = super().get_queryset() if hasattr(super(), 'get_queryset') else self.model.objects.all()
        return qs.filter(tenant=self.request.user.tenant)
```

Updated view enforcing server-side checks:

```python
# tenants/views.py — SECURE
from rest_framework import generics, permissions
from .models import TenantData
from .serializers import TenantDataSerializer
from .permissions import IsTenantMemberOrReadOnly


class TenantDataDetailView(generics.RetrieveUpdateDestroyAPIView):
    """Object-level authorization enforced on the SERVER."""
    permission_classes = [IsAuthenticated, IsTenantMemberOrReadOnly]
    serializer_class = TenantDataSerializer

    def get_queryset(self):
        # Even for GET requests we scope to the user's tenant
        return TenantData.objects.filter(tenant=self.request.user.tenant)
```

With DRF's `generics` classes the `permission_classes` list is evaluated automatically — `has_object_permission` is called after the filtered queryset resolves each instance, returning HTTP 403 before any data is returned or modified.

### Vulnerable Code

This file is committed and visible in git history — anyone with repo access has full infrastructure credentials.

### Hardened Fix

Move every secret to environment variables with runtime validation:

```python
# core/settings.py — SECURE
import environ
from pathlib import Path

env = environ.Env(
    DEBUG=(bool, False),
)

BASE_DIR = Path(__file__).resolve().parent.parent

# Read .env locally; never commit it (.gitignore: *.env)
environ.Env.read_env(BASE_DIR / '.env')

# --- Secrets loaded at startup; fail loudly if absent ---
SECRET_KEY = env('DJANGO_SECRET_KEY')
if not SECRET_KEY:
    raise ImproperlyConfigured(
        'DJANGO_SECRET_KEY environment variable is required.'
    )

DATABASES = {
    'default': env.db('DATABASE_URL'),  # postgres://user:pass@host:port/dbname
}

if not DATABASES['default'].get('PASSWORD'):
    raise ImproperlyConfigured('DATABASE_URL missing password component.')

# Email & third-party keys
EMAIL_HOST_PASSWORD = env('EMAIL_HOST_PASSWORD', default=None)
AWS_SECRET_ACCESS_KEY = env('AWS_SECRET_ACCESS_KEY', default=None)

DEBUG = env('DEBUG')
ALLOWED_HOSTS = env.list('ALLOWED_HOSTS', default=[])

# Production hardening
if not DEBUG:
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 31536000
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    SECURE_HSTS_PRELOAD = True
    SECURE_CONTENT_TYPE_NOSNIFF = True
    X_FRAME_OPTIONS = 'DENY'

    PASSWORD_HASHERS = [
        'django.contrib.auth.hashers.Argon2PasswordHasher',
        'django.contrib.auth.hashers.PBKDF2PasswordHasher',
        'django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher',
    ]
```

## 4. Mass Assignment Through Undeserialized Serializer Fields

**CWE-915: Improperly Controlled Modification of Dynamically-Determined Object Attributes**

### Vulnerable Code

```python
# accounts/serializers.py — INSECURE
from rest_framework import serializers
from django.contrib.auth.models import User  # AbstractBaseUser


class AccountSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = '__all__'          # SERIALIZES EVERY FIELD including sensitive ones
        extra_kwargs = {}           # No field restrictions

    def update(self, instance, validated_data):
        # Accepts arbitrary POST body — attacker sends:
        # {"is_staff": true, "is_superuser": true, ...}
        for attr, value in validated_data.items():
            setattr(instance, attr, value)
        instance.save()
        return instance
```

A PUT/PATCH request like:

```json
{
    "first_name": "Evil",
    "last_name": "Doer",
    "is_staff": true,
    "is_superuser": true
}
```

Escalates a regular user to admin instantly.

### Hardened Fix

Whitelist exactly which fields are writable, map write fields separately from read fields, and protect privileged fields:

```python
# accounts/serializers.py — SECURE
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class AccountListSerializer(serializers.ModelSerializer):
    """Read-only profile listing — never includes sensitive flags."""

    class Meta:
        model = User
        fields = ['id', 'username', 'email', 'first_name', 'last_name', 'date_joined']


class AccountDetailSerializer(serializers.ModelSerializer):
    """Detailed read — still excludes privilege-escalation fields."""

    is_active = serializers.BooleanField(read_only=True)
    date_joined = serializers.DateTimeField(read_only=True)
    last_login = serializers.DateTimeField(read_only=True)

    class Meta:
        model = User
        fields = ['id', 'username', 'email', 'first_name', 'last_name',
                   'is_active', 'date_joined', 'last_login']


class AccountUpdateSerializer(serializers.ModelSerializer):
    """
    Write-only serializer with explicit allowlist.

    Privilege fields (is_staff, is_superuser, groups, user_permissions)
    are NEVER accepted from this endpoint.  Only authorized admins may
    change them via a dedicated AdminAccountSerializer.
    """

    class Meta:
        model = User
        # Explicit allowlist — NOT __all__
        fields = ['first_name', 'last_name', 'email']

        extra_kwargs = {
            'email': {'required': False, 'allow_null': True},
        }

    def validate_email(self, value):
        """Prevent duplicate email across users."""
        if User.objects.filter(email=value).exclude(pk=self.instance.pk).exists():
            raise serializers.ValidationError('A user with this email already exists.')
        return value

    def update(self, instance, validated_data):
        """Safe update — only whitelisted fields are ever present."""
        for field, value in validated_data.items():
            setattr(instance, field, value)
        instance.save()
        return instance


class AdminAccountUpdateSerializer(AccountUpdateSerializer):
    """
    Restricted to staff/superusers — exposes role-change fields.
    Checked at the view layer, not here.
    """

    class Meta(AccountUpdateSerializer.Meta):
        model = User
        fields = ['first_name', 'last_name', 'email', 'is_active']


class SelfUpdateSerializer(serializers.ModelSerializer):
    """Allow users to edit their own profile without touching other fields."""

    class Meta:
        model = User
        fields = ['first_name', 'last_name']
```

Corresponding views enforce role boundaries:

```python
# accounts/views.py — SECURE
from rest_framework import generics, permissions, status
from rest_framework.response import Response
from django.contrib.auth import get_user_model

User = get_user_model()


class AccountDetailView(generics.RetrieveUpdateAPIView):
    """Standard users update only their own non-sensitive fields."""
    serializer_class = AccountUpdateSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_object(self):
        return self.request.user

    def retrieve(self, request, *args, **kwargs):
        return Response(self.serializer_class(request.user).data)


class AdminAccountListView(generics.ListAPIView):
    """Admin-only: list all accounts."""
    serializer_class = AccountDetailSerializer
    permission_classes = [permissions.IsAdminUser]
    queryset = User.objects.all()


class AdminAccountUpdateView(generics.UpdateAPIView):
    """Admin-only account modification including is_active."""
    serializer_class = AdminAccountUpdateSerializer
    permission_classes = [permissions.IsAdminUser]
    queryset = User.objects.all()
```

**Why this blocks the exploit:** the POST body `{"is_staff": true}` is silently ignored because `is_staff` is not in `fields`. DRF raises no error (no unexpected-field rejection needed) but simply drops unrecognized attributes. A separate admin view requires `IsAdminUser` even for privilege changes.
