## Issue 1: SQL Injection via F-String Query Construction

### Vulnerability

The report endpoint constructs SQL by interpolating user input directly into `cursor.execute()`:

```python
# VULNERABLE views.py
from django.db import connection

def generate_report(request, tenant_id):
    filter_value = request.query_params.get('category', '')
    
    # ❌ F-string interpolation into raw SQL
    sql = f"""
        SELECT * FROM reports
        WHERE tenant_id = {tenant_id} AND category = '{filter_value}'
    """
    with connection.cursor() as cursor:
        cursor.execute(sql)
        results = cursor.fetchall()
    return Response(results)
```

**CWE-89 (SQL Injection)** — OWASP Top 10 A03:2021

### Exploit

An attacker sends:

```
GET /api/reports/?category=' UNION SELECT username, password, 1, 2, 3 FROM users --
```

The resulting query becomes:

```sql
SELECT * FROM reports
WHERE tenant_id = 1 AND category = '' 
  UNION SELECT username, password, 1, 2, 3 FROM users --'
```

This extracts ALL user credentials from the database. The same technique achieves arbitrary data exfiltration, data modification (`INSERT`/`UPDATE`/`DELETE`), and potentially server compromise via `INTO OUTFILE`.

### Fix — Parameterized Queries + ORM

```python
# FIXED views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated
from rest_framework import status
import logging

logger = logging.getLogger(__name__)


class ReportListView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        category = request.query_params.get('category')

        if not tenant_id or not category:
            return Response(
                {'error': 'tenant_id and category are required'},
                status=status.HTTP_400_BAD_REQUEST
            )

        # --- Approach A: Pure ORM (preferred) --------------------------
        try:
            from .models import Report
            reports = Report.objects.filter(
                tenant_id=tenant_id,
                category=category
            ).values()  # Returns a queryset of dicts
            return Response(list(reports))
        except Exception as exc:
            logger.error("Report query failed", exc_info=True)
            return Response(
                {'error': 'Internal error'},
                status=status.HTTP_500_INTERNAL_SERVER_ERROR
            )

        # --- Approach B: Parameterized raw SQL (when ORM isn't enough) -
        # NOTE: Only use this when you MUST use raw SQL.
        #
        # with connection.cursor() as cursor:
        #     cursor.execute(
        #         "SELECT * FROM reports WHERE tenant_id = %s AND category = %s",
        #         [int(tenant_id), str(category)],   # ← parameters are escaped
        #     )
        #     results = cursor.fetchall()
        # return Response(results)
```

Key principles:

| Bad | Good |
|-----|------|
| `f"…{user_input}…"` | `%s` placeholders + `[params]` list |
| `str(user_input)` | `int()`, `Decimal()`, etc. — explicit type coercion |
| `.execute(sql_with_interpolation)` | `.execute(sql_template, [safe_params])` |

Never construct SQL strings by string interpolation. Always pass user input through the parameter array.

## Issue 2: Client-Side-Only Object Permissions

### Vulnerability

Object-level access control is enforced only in the React frontend:

```javascript
// ❌ VULNERABLE — Frontend-only check
function handleEditReport(reportId, data) {
  const userReports = useSelector(state => state.reports.userReports);
  // If the user doesn't own the report, disable the button.
  // BUT an attacker can just send the POST request directly!
  const owned = someCheck(userReports, reportId);  // browser-side logic
  if (!owned) { alert('Not authorized'); return; }
  api.put(`/reports/${reportId}`, data);
}
```

No server-side authorization middleware guards write operations on objects belonging to other tenants/users.

**CWE-284 (Improper Access Control)** — Insecure Direct Object Reference (IDOR). Also **CWE-862 (Missing Authorization)**.

### Exploit

A normal user views report `/api/reports/42` (owned by another tenant). They then send:

```bash
curl -X PUT https://api.example.com/api/reports/42 \
  -H "Authorization: Bearer <my_token>" \
  -H "Content-Type: application/json" \
  -d '{"title": "Modified by attacker"}'
```

The server processes the update without checking ownership. Attackers can enumerate sequential IDs and read/modify/arbitrarily change any object in the system.

### Fix — Server-Side Object-Level Authorization

```python
# FIXED permissions.py
from rest_framework import permissions
from .models import Report


class IsOwnerOrReadOnly(permissions.BasePermission):
    """Server-side check: only the owner may modify their objects."""

    def has_permission(self, request, view):
        # All authenticated users can READ
        if request.method in permissions.SAFE_METHODS:
            return True
        # Write requires authentication
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        # Anyone can read individual objects (after has_permission passes)
        if request.method in permissions.SAFE_METHODS:
            return True
        # Only the owner (or staff) can modify
        return obj.author == request.user or request.user.is_staff


class TenantIsolation(permissions.BasePermission):
    """Multi-tenant isolation: users can only see/access their own data."""

    MESSAGE = "You do not have access to this resource."

    def has_object_permission(self, request, view, obj):
        # Ensure the object's tenant matches the request user's tenant
        return getattr(obj, 'tenant', None) == request.user.tenant or request.user.is_staff
```

```python
# FIXED models.py
from django.contrib.auth.models import AbstractUser
from django.db import models


class Tenant(models.Model):

    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        db_table = 'reports'
        indexes = [
            models.Index(fields=['tenant', 'category']),
            models.Index(fields=['author']),
        ]

```

```python
# FIXED views.py
from rest_framework import generics, status
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from django.shortcuts import get_object_or_404

from .models import Report
from .serializers import ReportSerializer
from .permissions import IsOwnerOrReadOnly, TenantIsolation


class ReportDetailView(generics.RetrieveUpdateDestroyAPIView):
    """Single report CRUD — fully guarded server-side."""
    permission_classes = [IsAuthenticated, IsOwnerOrReadOnly, TenantIsolation]
    serializer_class = ReportSerializer

    def get_queryset(self):
        # Each user sees ONLY their tenant's reports
        return Report.objects.filter(tenant=self.request.user.tenant)

    def perform_update(self, serializer):
        # Force-update tenant to prevent tenant-swap attacks
        instance = serializer.save(author=self.request.user)
        instance.tenant = self.request.user.tenant
        instance.save()


class ReportListView(generics.ListCreateAPIView):
    """List reports (GET) and create a new one (POST)."""
    permission_classes = [IsAuthenticated]
    serializer_class = ReportSerializer

    def get_queryset(self):
        return Report.objects.filter(tenant=self.request.user.tenant)

    def perform_create(self, serializer):
        serializer.save(author=self.request.user, tenant=self.request.user.tenant)
```

Now **every route** that handles an object calls `has_object_permission` before processing the request. The React frontend buttons can be disabled for UX, but they have zero security effect.

### Vulnerability


Committed to Git → searchable on GitHub/GitLab → scraped by credential scanners within minutes.

**CWE-798 (Use of Hard-coded Credentials)** — OWASP Top 10 A07:2021. Also **CWE-312 (Clear-text Storage of Sensitive Information)**.

## Issue 4: Mass-Assignment Privilege Escalation via Serializer

### Vulnerability

```python
# ❌ VULNERABLE — serializer allows writing every model field
class UserSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = '__all__'       # ← exposes is_staff, is_superuser, etc.

class CreateUserView(generics.CreateAPIView):
    serializer_class = UserSerializer

    def perform_create(self, serializer):
        serializer.save()          # No restriction on fields at all
```

A client sends:

```json
{
    "email": "attacker@evil.com",
    "password": "strongpass123!",
    "is_staff": true,
    "is_superuser": true
}
```

The server creates a staff admin account automatically.

**CWE-915 (Improperly Controlled Modification of Dynamically-Dynamic Object References)** — Classic mass-assignment / excessive `fields = '__all__'`.

### Fix — Explicit Field Allowlisting + Server-Controlled Fields

```python
# ✅ CORRECT — serializers.py
from rest_framework import serializers
from django.contrib.auth.password_validation import validate_password
from django.core.exceptions import ValidationError as DjangoValidationError

from .models import User, Report


class UserSerializer(serializers.ModelSerializer):
    """Read-write for profile data only. Never exposes auth flags."""
    password = serializers.CharField(write_only=True, required=True,
                                     validators=[validate_password])
    password_confirm = serializers.CharField(write_only=True, required=True)

    class Meta:
        model = User
        # Explicit whitelist — NO is_staff, is_superuser, is_active, …
        fields = ('id', 'email', 'username', 'phone',
                  'password', 'password_confirm', 'is_verified')

    def validate_password(self, value):
        # Already validated by the validator, but re-confirm here
        return value

    def validate(self, attrs):
        if attrs.pop('password') != attrs.pop('password_confirm'):
            raise serializers.ValidationError(
                {"password": "Password fields did not match."}
            )
        return attrs

    def create(self, validated_data):
        # Create as a regular user — NEVER auto-promote
        user = User.objects.create_user(**validated_data)
        return user


class AdminUserSerializer(serializers.ModelSerializer):
    """EXCLUSIVE to internal admin endpoints — NOT exposed to public API."""
    class Meta:
        model = User
        fields = ('id', 'email', 'username', 'phone',
                  'is_staff', 'is_superuser', 'is_verified',
                  'date_joined', 'last_login')
        read_only_fields = ('id', 'date_joined', 'last_login')

    def create(self, validated_data):
        return User.objects.create_user(**validated_data)

    def update(self, instance, validated_data):
        # Even admins can only set these flags explicitly;
        # no accidental mass-assignment from unknown payloads.
        for attr in ('is_staff', 'is_superuser', 'is_verified'):
            if attr in validated_data:
                setattr(instance, attr, validated_data[attr])
        instance.username = validated_data.get('username', instance.username)
        instance.phone = validated_data.get('phone', instance.phone)
        instance.save()
        return instance


class ReportSerializer(serializers.ModelSerializer):
    class Meta:
        model = Report
        fields = ('id', 'title', 'category', 'content',
                  'created_at', 'updated_at')
        read_only_fields = ('id', 'created_at', 'updated_at')

    def create(self, validated_data):
        # author and tenant come from the request context, not the payload
        return Report.objects.create(**validated_data)
```

## Summary Table

| # | Vuln | CWE | Impact | Fix Category |
|---|------|-----|--------|--------------|
| 1 | f-string in `cursor.execute()` | **CWE-89** SQL Injection | Full DB compromise | Parameterized queries (`%s` + param list) or ORM |
| 2 | Frontend-only permission checks | **CWE-284** / **CWE-862** | IDOR — read/modify others' objects | Server-side `has_object_permission` + tenant isolation |
| 3 | Hardcoded SECRET_KEY / DB creds in git | **CWE-798** / **CWE-312** | Credential theft, full app takeover | `django-environ` / `os.environ`; `.env` ignored in git; TLS for DB |
| 4 | `fields = '__all__'` exposes `is_staff` | **CWE-915** mass-assignment | Privilege escalation to admin | Explicit serializer field allowlist + `read_only_fields` + server-controlled flag setting |

Each fix is independent and additive — deploying any single one materially raises the attack cost. Together they bring the application from critically vulnerable to production-ready.
