## Issue 1: SQL Injection in Report Endpoint

**CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')**

### Vulnerable Pattern

```python
# models.py / views.py — vulnerable
class ReportViewSet(viewsets.ModelViewSet):
    queryset = Transaction.objects.all()
    
    def retrieve(self, request, pk=None):
        # User-controlled tenant_id passed directly into SQL string
        tenant_id = request.query_params.get("tenant", "")
        cursor = connection.cursor()
        
        # F-string concatenation — SQL metacharacters are never escaped
        sql = f"SELECT * FROM transactions WHERE tenant_id = {tenant_id} AND id = %s"
        cursor.execute(sql, [pk])  # Only `pk` is parameterized; `tenant_id` is raw
        rows = cursor.fetchall()
        return Response(rows)
```

Also common in `filter_backends`:

```python
class ReportFilterBackend(BaseFilterBackend):
    def filter_queryset(self, request, queryset, view):
        tenant = request.query_params.get("tenant")
        sort_col = request.query_params.get("sort", "created_at")
        
        # Both values injected directly into SQL string
        sql = f"SELECT * FROM transactions WHERE tenant_id = {tenant} ORDER BY {sort_col}"
        return RawSQLQuery(sql)  # Or cursor.execute(sql)
```

### Exploit Demonstration

An attacker crafts a `tenant` parameter that closes the identifier context and appends arbitrary SQL:

```bash
# Bypass tenant isolation — returns ALL transactions
curl "https://api.example.com/api/reports/42/?tenant=0 UNION SELECT card_number,cvv,null,null FROM payment_credentials --"

# Stack-based extraction (MySQL/MariaDB)
curl "https://api.example.com/api/reports/42/?tenant=1 UNION SELECT username,password,null,null FROM auth_user WHERE username='admin'"

# Boolean blind injection (PostgreSQL/SQLite)
curl "https://api.example.com/api/reports/42/?tenant=1 OR substr((SELECT password FROM auth_user WHERE username='admin'),1,1)='a'"
```

In the first example, the executed SQL becomes:
```sql
SELECT * FROM transactions WHERE tenant_id = 0 
UNION SELECT card_number,cvv,null,null FROM payment_credentials -- AND id = %s
```

The `--` comment terminates the original predicate, and the UNION extracts data from a table the attacker shouldn't access. Because only `pk` is parameterized, `tenant_id` is evaluated as raw SQL.

### Root Cause

Parameterized queries protect bound parameters from being interpreted as SQL syntax. Here, the f-string embeds `tenant_id` into the query *before* execution, so it becomes SQL code, not data. No escaping occurs.

### Corrected Code — Parameterized Queries + Raw SQL

```python
from django.db import connection
from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page


@method_decorator(cache_page(60), name="dispatch")
class ReportViewSet(viewsets.ReadOnlyModelViewSet):
    """Hardened report endpoint with parameterized queries."""
    queryset = Transaction.objects.all()
    serializer_class = ReportSerializer

    def retrieve(self, request, pk=None):
        # Validation: reject non-integer identifiers
        try:
            tenant_id = int(request.query_params.get("tenant", self.request.user.tenant.id))
        except (ValueError, TypeError):
            raise ValidationError({"tenant": "Must be an integer."})

        cursor = connection.cursor()

        # Placeholder for every user-supplied value — never concatenate
        cursor.execute(
            "SELECT * FROM transactions WHERE tenant_id = %s AND id = %s",
            [tenant_id, pk],
        )
        rows = cursor.fetchall()

        if not rows:
            raise Http404("Report not found.")

        return Response(rows)
```

Key principles:
- **Every** user-supplied value gets a `%s` placeholder and appears in the parameter tuple.
- Type coercion (`int()`) rejects non-numeric input *before* it touches SQL.
- `cache_page` is applied safely — caching defeats nothing related to injection.

### Corrected Code — ORM Alternative (Preferred)

```python
def retrieve(self, request, pk=None):
    try:
        tenant_id = int(request.query_params.get(
            "tenant", self.request.user.tenant.id
        ))
    except (ValueError, TypeError):
        raise ValidationError({"tenant": "Must be an integer."})

    try:
        transaction = Transaction.objects.get(tenant_id=tenant_id, id=pk)
    except Transaction.DoesNotExist:
        raise Http404("Report not found.")

    serializer = ReportSerializer(transaction)
    return Response(serializer.data)
```

The ORM handles parameterization automatically and eliminates the `cursor.execute` vector entirely. Prefer this approach whenever the query is not an aggregation too complex for the ORM.

## Issue 2: Client-Side-Only Object Authorization

**CWE-285: Improper Authorization**
**CWE-918: Server-Side Request Forgery (SSRF) — secondary concern**

### Problem Architecture

```
┌──────────┐      ┌───────────────┐      ┌───────────┐
│ React UI │──────│ Django API    │      │ Database  │
│           │      │               │      │           │
│ ✅ Checks │  ❌  │  NO check     │──────│ Returns   │
│ owns obj? │      │               │      │ All data  │
└──────────┘      └───────────────┘      └───────────┘
```

Permission evaluation happens solely in the browser. The API trusts `request.user` for identity but does not verify that the user is authorized to access the specific object.

### Exploit Demonstration

The frontend hides a "Delete" button if the current user doesn't own the case. But an attacker opens the network tab and intercepts the DELETE request:

```http
# Attacker (user_id=7) deletes case owned by user_id=3
DELETE /api/cases/137/ HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUz...

# Server responds 204 No Content — case deleted.
# No authorization logic existed server-side.
```

Cross-resource enumeration:
```python
import httpx

token = "eyJhbGciOiJIUz..."  # attacker's token
for case_id in range(1, 1000):
    r = httpx.delete(f"https://api.example.com/api/cases/{case_id}/",
                      headers={"Authorization": f"Bearer {token}"})
    if r.status_code == 204:
        print(f"Owned case: {case_id}")
    elif r.status_code == 403:
        break  # stopped at first non-owned resource
    else:
        print(f"[{r.status_code}] case {case_id}")
```

All 847 of the victim's cases are discovered and destroyed in seconds.

### Root Cause

Server-side authorization is missing at three levels:
1. **List views** don't filter by ownership — `GET /api/cases/` returns everyone's cases.
2. **Detail views** don't check object-level permission — `GET /api/cases/{id}/` serves any authenticated user.
3. **Write/delete views** lack `has_object_permission` — `PUT`/`PATCH`/`DELETE` succeed for anyone authenticated.

### Corrected Code — Server-Side Object-Level Authorization

#### Permission Classes

```python
# permissions.py
from rest_framework import permissions


class IsOwnerOrReadOnly(permissions.BasePermission):
    """Grant read access to any authenticated user; write access only to owner."""

    def has_object_permission(self, request, view, obj):
        # Read operations are allowed for any authenticated user (safe for list sharing)
        if request.method in permissions.SAFE_METHODS:
            return True
        
        # Write operations restricted to the object's owner
        return getattr(obj, 'owner', None) == request.user


class IsCaseStaff(permissions.BasePermission):
    """Staff users may edit any case within their own tenant."""

    def has_object_permission(self, request, view, obj):
        if not request.user.is_authenticated:
            return False
        
        # Staff must belong to the same tenant as the case
        if hasattr(request.user, 'tenant') and hasattr(obj, 'tenant'):
            return request.user.is_staff and request.user.tenant == obj.tenant
        
        return False


class CombinedCasePermission(permissions.BasePermission):
    """Layered: owner > tenant-staff > deny."""

    def has_object_permission(self, request, view, obj):
        if not request.user.is_authenticated:
            return False

        # 1. Owner always has full control
        if getattr(obj, 'owner', None) == request.user:
            return True

        # 2. Tenant staff can manage cases within their tenant
        if (getattr(request.user, 'is_staff', False)
                and getattr(obj, 'tenant', None) is not None
                and request.user.tenant == obj.tenant):
            return True

        return False
```

**CWE-798: Use of Hard-coded Credentials**

### Why This Is Catastrophic

| Threat Vector | Impact |
|---|---|
| Git history | Every commit retains the credential forever; `git log -p` reveals it even after deletion. Any fork clone pulls it. |
| CI/CD logs | Build logs sometimes dump environment variable contents. Credentials surface in pipeline output visible to all contributors. |
| Container images | `ENV SECRET_KEY=x` baked into Docker image layers; `docker history` exposes the value. |
| Team access | Anyone with read access to the repo (internal or public) can extract credentials. |
| Third-party audits | Static analysis tools flag and exfiltrate detected secrets to external services. |
| Lateral movement | Exposed DB credentials grant direct database access, bypassing the application layer entirely. |

Once a `SECRET_KEY` leaks, an attacker can forge signed sessions, CSRF cookies, password reset tokens, and DRF JWT tokens — effectively assuming any user's identity.

## Issue 4: Mass Assignment Through Serializer

**CWE-284: Improper Access Control**
**CWE-915: Improperly Controlled Modification of Dynamically-Determined Object Attributes**

### Vulnerable Pattern

```python
# serializers.py — allows ANY model field to be set by the client
class UserRegistrationSerializer(serializers.ModelSerializer):
    """Allows mass assignment of all writable model fields, including is_staff."""
    
    class Meta:
        model = CustomUser
        # Fields auto-detected from model — includes is_staff (write=True)
        fields = "__all__"
        extra_kwargs = {}  # No restrictions — every field is writable
```

```python
# views.py
class RegistrationViewSet(viewsets.ModelViewSet):
    serializer_class = UserRegistrationSerializer
    
    def create(self, request, *args, **kwargs):
        # Deserializes EVERY field in the request body — including is_staff
        serializer = self.get_serializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        user = serializer.save()  # <-- attacker-set is_staff=True is saved!
        return Response({"id": user.id}, status=status.HTTP_201_CREATED)
```

### Exploit Demonstration

An attacker registers a new account and promotes themselves to staff by adding `is_staff` to the JSON payload:

```bash
curl -X POST https://api.example.com/api/register/ \
  -H "Content-Type: application/json" \
  -d '{
    "username": "attackervector",
    "email": "attacker@evil.com",
    "password": "compromised123",
    "is_staff": true,
    "is_superuser": true,
    "groups": [1]
  }'

# Server responds 201 Created with is_staff=True
# Attacker now has admin-level API access.
```

Additional vectors:
- `PUT /api/users/{self.pk}/` — modifies their own `is_staff` flag.
- `PATCH /api/users/{self.pk}/` — partially updates `is_staff`.
- Profile update endpoints that serialize the full `User` model expose `is_active`, `date_joined`, and permission-related fields.

### Root Cause

`serializers.ModelSerializer` inherits every field from the model with its default `write=True` unless explicitly overridden. When `fields = "__all__"` is used (or a broad explicit list), every write-enabled field in the model becomes a mass-assignment target. The serializer deserializes and validates ALL provided fields, then the view calls `.save()` which persists everything — including privilege-escalation fields.

### Corrected Code — Field Allowlisting + Write-Only Separation

```python
# serializers.py
from django.contrib.auth import get_user_model
from rest_framework import serializers

User = get_user_model()


class UserRegistrationSerializer(serializers.ModelSerializer):
    """Hardened registration: strict field allowlist, privilege flags removed."""

    # Password is write-only — never returned in API responses
    password = serializers.CharField(write_only=True, min_length=8)
    password_confirm = serializers.CharField(write_only=True, min_length=8)

    class Meta:
        model = User
        # EXPLICIT allowlist — fields not listed CANNOT be submitted by the client
        fields = ["username", "email", "password", "password_confirm"]

    def validate(self, attrs):
        if attrs.pop("password") != attrs.pop("password_confirm"):
            raise serializers.ValidationError(
                {"password_confirm": "Passwords must match."}
            )
        return attrs

    def create(self, validated_data):
        """
        Create via User.objects.create_user() to hash the password correctly.
        Direct Model.save() would store the plain-text password.
        """
        return User.objects.create_user(**validated_data)


class UserProfileSerializer(serializers.ModelSerializer):
    """Read/update profile — exclude all privilege escalation fields."""

    class Meta:
        model = User
        fields = [
            "id",
            "username",
            "email",
            "first_name",
            "last_name",
            "date_joined",
            "last_login",
        ]
        # These fields may be added if legitimate business needs them:
        # "bio", "avatar", "phone_number"
        
        extra_kwargs = {
            field: {"read_only": True}
            for field in ("date_joined", "last_login", "id")
        }


class InternalUserSerializer(serializers.ModelSerializer):
    """Used ONLY by staff/admin views — includes privileged fields."""
    password = serializers.CharField(write_only=True, required=False)

    class Meta:
        model = User
        # Explicitly include privilege fields — only accessible from admin views
        fields = [
            "id", "username", "email", "first_name", "last_name",
            "is_staff", "is_superuser", "is_active", "date_joined",
            "last_login", "password", "groups", "user_permissions",
        ]

    def create(self, validated_data):
        password = validated_data.pop("password", None)
        instance = self.Meta.model(**validated_data)
        if password:
            instance.set_password(password)
        instance.save()
        return instance


class ChangePasswordSerializer(serializers.Serializer):
    """Explicit contract for password resets — no mass assignment possible."""

    current_password = serializers.CharField(write_only=True, required=True)
    new_password = serializers.CharField(write_only=True, required=True, min_length=8)
    new_password_confirm = serializers.CharField(write_only=True, required=True)

    def validate(self, attrs):
        if attrs["new_password"] != attrs["new_password_confirm"]:
            raise serializers.ValidationError({
                "new_password_confirm": "Passwords must match."
            })
        return attrs
```

```python
# views.py
from rest_framework import viewsets, status
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated, IsAdminUser
from rest_framework.decorators import action
from django.contrib.auth import get_user_model

User = get_user_model()


class RegistrationViewSet(viewsets.ViewSet):
    """Public registration — no authentication required."""

    def create(self, request):
        # RegistrationSerializer explicitly excludes is_staff, is_superuser, etc.
        serializer = UserRegistrationSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        user = serializer.save()
        return Response(
            {"id": user.id, "username": user.username},
            status=status.HTTP_201_CREATED,
        )

    @action(detail=False, methods=["post"], url_path="activate")
    def activate_account(self, request):
        """Staff-only account activation — uses internal serializer."""
        if not request.user.is_staff:
            return Response(
                {"detail": "Staff privileges required."},
                status=status.HTTP_403_FORBIDDEN,
            )
        # Activation performed by staff, not self-service
        serializer = UserRegistrationSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        user = serializer.save()
        user.is_active = True
        user.save()
        return Response({"id": user.id}, status=status.HTTP_200_OK)


class UserViewSet(viewsets.ModelViewSet):
    """CRUD for users — access controlled by serializer and view permissions."""

    def get_serializer_class(self):
        """Swap serializer based on view context and user role."""
        if self.action == "register":
            return UserRegistrationSerializer
        elif self.request.user.is_staff:
            return InternalUserSerializer
        return UserProfileSerializer

    def get_queryset(self):
        if self.request.user.is_staff:
            return User.objects.all()
        return User.objects.filter(id=self.request.user.id)

    @action(detail=True, methods=["post"], permission_classes=[IsAuthenticated])
    def change_password(self, request, pk=None):
        """Explicit password change — no mass assignment possible."""
        user = self.get_object()
        if user != request.user and not request.user.is_staff:
            return Response(
                {"detail": "Cannot change another user's password."},
                status=status.HTTP_403_FORBIDDEN,
            )

        serializer = ChangePasswordSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)

        if not user.check_password(serializer.validated_data["current_password"]):
            return Response(
                {"current_password": "Invalid current password."},
                status=status.HTTP_400_BAD_REQUEST,
            )

        user.set_password(serializer.validated_data["new_password"])
        user.save()
        return Response(status=status.HTTP_204_NO_CONTENT)
```

#### Defense-in-Layer Summary for Mass Assignment

| Layer | Mechanism | What It Blocks |
|---|---|---|
| Serializer `fields` allowlist | Explicit field list, no `__all__` | Unknown/new model fields cannot be submitted |
| Privilege field exclusion | `is_staff` not in `UserRegistrationSerializer.fields` | Self-promotion impossible via registration |
| Separate serializers | `InternalUserSerializer` for admin, `UserProfileSerializer` for self | Privilege fields only accessible to staff |
| Action-based selection | `get_serializer_class()` swaps based on role | Wrong serializer cannot be forced by the client |
| Password hashing | `set_password()` / `create_user()` | Plain-text password storage impossible |
| Explicit `perform_create` | Set defaults server-side | Resistant to serializer reuse/subclassing |

## Consolidated Risk Matrix

| Vulnerability | CWE | Severity | Attack Complexity | Impact | Fix Category |
|---|---|---|---|---|---|
| SQL injection in cursor.execute | CWE-89 | Critical | Low | Full data exfiltration, RCE | Parameterized queries |

| Hardcoded SECRET_KEY/DB creds | CWE-798/CWE-259 | Critical | Low | Session forgery, DB takeover | Secrets management |

Each fix is independent — a bug in one area does not excuse neglecting the others. The SQL injection grants data access, the authorization gap amplifies it to cross-tenant leakage, the leaked credentials let an attacker bypass authentication entirely, and the mass assignment turns any low-privilege account into an admin. Together they form a full compromise chain; individually, each warrants immediate remediation.
