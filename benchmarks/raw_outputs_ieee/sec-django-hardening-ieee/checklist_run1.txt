## Issue 1: SQL Injection via f-string Cursor Query

### CWE-89 (SQL Injection)

**Vulnerable pattern:**

```python
def get_report(request, tenant_id):
    filters = ""
    if request.GET.get("status"):
        status = request.GET["status"]
        filters += f" AND status = '{status}'"
    if request.GET.get("category"):
        cat = request.GET["category"]
        filters += f" AND category = '{cat}'"

    sql = f"SELECT id, title, created_at FROM reports WHERE tenant_id = '{tenant_id}'{filters}"
    with connection.cursor() as cursor:
        cursor.execute(sql)  # ← raw concatenation
        rows = cursor.fetchall()
    return JsonResponse({"reports": rows})
```

**Exploit:**

```
GET /api/reports/?tenant_id=1&status=%27%3B%20DROP%20TABLE%20reports%3B%20--
```

Resulting query:
```sql
SELECT id, title, created_at FROM reports WHERE tenant_id = '1' AND status = ''; DROP TABLE reports; --'
```

Corrupted or dropped tables. Also exfiltrates data via `UNION SELECT`:

```
GET /api/reports/?tenant_id=1&status=%27%20UNION%20SELECT%20password%2Cusername%2Cemail%20FROM%20auth_user%20--
```

**Fix — parameterized queries only, no string concatenation for values:**

```python
from django.db import connection

def get_report(request, tenant_id):
    conditions = ["tenant_id = %s"]
    params = [tenant_id]

    status = request.GET.get("status")
    if status:
        conditions.append("status = %s")
        params.append(status)

    category = request.GET.get("category")
    if category:
        conditions.append("category = %s")
        params.append(category)

    where_clause = " AND ".join(conditions)
    sql = f"SELECT id, title, created_at FROM reports WHERE {where_clause}"

    with connection.cursor() as cursor:
        cursor.execute(sql, params)  # ← parameterized, DB driver handles escaping
        columns = [desc[0] for desc in cursor.description]
        rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

    return JsonResponse({"reports": rows})
```

Key points:
- `%s` placeholders go in `cursor.execute(sql, params)` — never inline them into the string
- User input can only fill `params`, never part of `sql` itself
- Table/column names CANNOT be parameterized; whitelist those separately if needed

## Issue 2: Client-Side Object Permission Checks Only

### CWE-284 (Improper Access Control) / CWE-862 (Missing Authorization)

**Vulnerable pattern (React frontend):**

```javascript
// Frontend-only check — trivially bypassed by curl / Postman / browser devtools
async function fetchReport(reportId) {
    const response = await fetch(`/api/reports/${reportId}`);
    // User's own token says they're admin here, but the server trusts it blindly
    if (!response.ok) throw new Error("Not authorized");
    return response.json();
}
```

**Server-side lacks any object-level permission check:**

```python
class ReportDetailView(APIView):
    def get(self, request, pk):
        report = get_object_or_404(Report, pk=pk)
        # No authorization — returns any report in the system!
        serializer = ReportSerializer(report)
        return Response(serializer.data)
```

**Exploit:**

```bash
curl -H "Authorization: Bearer <user_A_token>" \
     https://app.example.com/api/reports/9999   # Belongs to tenant B → data leaked
```

**Fix — server-side object-level authorization with custom permissions:**

```python
# permissions.py
from rest_framework.permissions import BasePermission, SAFE_METHODS


class IsTenantMember(BasePermission):
    """User must belong to the tenant that owns the requested object."""
    message = "You do not have access to this resource."

    def has_object_permission(self, request, view, obj):
        # obj must have a .tenant attribute
        return request.user.tenant == obj.tenant


class IsReportOwnerOrReadOnly(BasePermission):
    """Owners can modify; everyone with access gets read."""
    message = "You can only modify your own reports."

    def has_object_permission(self, request, view, obj):
        if not IsTenantMember().has_object_permission(request, view, obj):
            return False
        if request.method in SAFE_METHODS:
            return True
        return obj.created_by == request.user


# views.py
from rest_framework.permissions import IsAuthenticated
from reports.permissions import IsTenantMember, IsReportOwnerOrReadOnly


class ReportDetailView(generics.RetrieveUpdateDestroyAPIView):
    queryset = Report.objects.select_related("tenant", "created_by")
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated, IsTenantMember, IsReportOwnerOrReadOnly]
```

For bulk operations, filter at the queryset level so unauthenticated actors get empty sets:

```python
class ReportListView(generics.ListCreateAPIView):
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        # Server-enforced tenant scoping — not an optional filter
        return Report.objects.filter(tenant=self.request.user.tenant)
```

## Issue 3: Hardcoded Secrets in settings.py Committed to Git

### CWE-798 (Use of Hard-coded Credentials) / CWE-799 (Improper Limitation of a Protective Mechanism)

**Vulnerable pattern:**

```python
# settings.py — committed to git
SECRET_KEY = "super-secret-key-12345-do-not-share"
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "production_db",
        "USER": "admin",
        "PASSWORD": "P@ssw0rd!2024",
        "HOST": "db.internal.example.com",
        "PORT": "5432",
    }
}
```

**Exploit:** Any repo clone gains full production database access. GitHub/GitLab search indexes will leak credentials.

**Fix — environment-variable–only secrets management:**

```python
import os
from pathlib import Path
from django.core.exceptions import ImproperlyConfigured


def _get_env(key, required=False, default=None):
    value = os.environ.get(key, default)
    if required and not value:
        raise ImproperlyConfigured(f"Environment variable {key!r} is required.")
    return value


# ── Secrets ───────────────────────────────────────────────────────
SECRET_KEY = _get_env("DJANGO_SECRET_KEY", required=True)

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": _get_env("DB_NAME"),
        "USER": _get_env("DB_USER"),
        "PASSWORD": _get_env("DB_PASSWORD"),
        "HOST": _get_env("DB_HOST", default="localhost"),
        "PORT": _get_env("DB_PORT", default="5432"),
    }
}

# ── Optional: use django-environ for even cleaner management ──────
# import environ
# env = environ.Env(
#     DJANGO_SECRET_KEY=(str, ""),
#     DB_NAME=(str, ""),
#     DB_USER=(str, ""),
#     DB_PASSWORD=(str, ""),
#     DB_HOST=(str, "localhost"),
#     DB_PORT=(int, 5432),
# )
# environ.Env.read_env(Path(__file__).resolve().parent.parent / ".env")
# SECRET_KEY = env("DJANGO_SECRET_KEY")
# DATABASES = {"default": env.db()}
```

**Complement with `.gitignore`:**

```gitignore
.env
.env.*
!/.env.example
```

**And document what each variable expects:**

```bash
# .env.example (safe to commit)
DJANGO_SECRET_KEY=CHANGE_ME_GENERATE_RANDOM_KEY
DB_NAME=tenant_db
DB_USER=dbuser
DB_PASSWORD=CHANGE_ME_STRONG_PASSWORD
DB_HOST=localhost
DB_PORT=5432
```

Production should inject these via CI/CD secrets (AWS Secrets Manager, HashiCorp Vault, etc.) rather than plain `.env` files on disk.

## Issue 4: Serializer Mass Assignment Leaking Sensitive Fields

### CWE-915 (Improperly Controlled Modification of Dynamically-Determined Object Attributes)

**Vulnerable pattern:**

```python
# serializers.py
class StaffUpdateSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = "__all__"          # ← includes is_staff, is_superuser, password, ...
        extra_kwargs = {}           # ← no field locking
```

**Exploit:**

```bash
curl -X PATCH https://app.example.com/api/users/42/ \
     -H "Authorization: Bearer <moderate_privilege_token>" \
     -H "Content-Type: application/json" \
     -d '{"is_staff": true, "is_superuser": true}'
```

Any authenticated user promotes themselves to staff.

**Fix — explicit field allowlisting + `read_only_fields` + server-side validation:**

```python
# serializers.py
from django.contrib.auth import get_user_model
from rest_framework import serializers

User = get_user_model()


class StaffUpdateSerializer(serializers.ModelSerializer):
    """Only allow safe, non-privilege fields to be updated."""

    class Meta:
        model = User
        # Explicit allowlist — nothing beyond these can be submitted
        fields = ("first_name", "last_name", "email")
        extra_kwargs = {
            "first_name": {"required": False},
            "last_name": {"required": False},
            "email": {"required": False},
        }

    # These NEVER appear in the input schema and cannot be set via API payload
    is_staff = serializers.ReadOnlyField()
    is_superuser = serializers.ReadOnlyField()
    password = serializers.ReadOnlyField()  # passwords always changed via dedicated endpoint
    date_joined = serializers.ReadOnlyField()
    last_login = serializers.ReadOnlyField()


class StaffCreationSerializer(serializers.ModelSerializer):
    """Dedicated serializer for POST only — called by admin/staff only."""
    password = serializers.CharField(write_only=True)

    class Meta:
        model = User
        fields = ("username", "email", "password", "first_name", "last_name")

    def create(self, validated_data):
        user = User.objects.create_user(**validated_data)
        return user
```

**Enforce serializer selection in views based on action:**

```python
# views.py
class StaffViewSet(viewsets.ModelViewSet):
    queryset = User.objects.all()
    permission_classes = [IsAuthenticated, IsStaffOrReadOnly]

    def get_serializer_class(self):
        if self.action == "create":
            return StaffCreationSerializer
        return StaffUpdateSerializer

    def get_queryset(self):
        # Prevent enumeration beyond what the user has permission to see
        qs = super().get_queryset()
        if not self.request.user.is_staff:
            qs = qs.filter(id=self.request.user.id)  # users see only themselves
        return qs
```

|---|---|---|---|---|
| 1 | SQL injection via f-string `cursor.execute()` | CWE-89 | Raw value interpolation into SQL string | Parameterized queries (`%s` + `params`) |
| 2 | Object permissions enforced only in React | CWE-284 / CWE-862 | Missing `has_object_permission` on DRF | Custom `BasePermission` + `get_queryset` filtering |
