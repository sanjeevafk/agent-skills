# Issue 1 — SQL Injection via f-string in `cursor.execute()`

## CWE

**CWE-89: Improper Neutralization of Special Elements used in an SQL Command (SQL Injection)**

## Vulnerable Code

```python
# reports/views.py
from django.db import connection

def report_endpoint(request):
    start = request.query_params.get('start_date')
    end = request.query_params.get('end_date')
    tenant_id = request.query_params.get('tenant_id')

    query = f"""
        SELECT id, amount, created_at
        FROM transactions
        WHERE tenant_id = {tenant_id}
          AND created_at BETWEEN '{start}' AND '{end}'
    """

    with connection.cursor() as cursor:
        cursor.execute(query)  # DANGER: raw interpolation
        rows = cursor.fetchall()

    return Response(rows)
```

## Exploit Demonstration

An attacker sends:

```http
GET /api/reports/?tenant_id=1 OR 1=1;--&start_date=&end_date=
```

The rendered query becomes:

```sql
SELECT id, amount, created_at
FROM transactions
WHERE tenant_id = 1 OR 1=1;--
  AND created_at BETWEEN '' AND ''
```

Every row across every tenant is returned. An attacker could also append `UNION SELECT` payloads to exfiltrate other tables, drop data, or escalate privileges.

## Corrected Code

```python
# reports/views.py
from django.db import connection
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated
from datetime import datetime, date

class ReportEndpoint(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        tenant_id = request.query_params.get('tenant_id')
        start_date = request.query_params.get('start_date')
        end_date = request.query_params.get('end_date')

        if not all([tenant_id, start_date, end_date]):
            return Response({'error': 'Missing required parameters'}, status=400)

        try:
            start_dt = datetime.fromisoformat(start_date)
            end_dt = datetime.fromisoformat(end_date)
        except ValueError:
            return Response({'error': 'Invalid date format, use ISO 8601'}, status=400)

        # FIX: Use positional %s placeholders with a Python list (or tuple)
        query = """
            SELECT id, amount, created_at
            FROM transactions
            WHERE tenant_id = %s
              AND created_at BETWEEN %s AND %s
        """

        params = [int(tenant_id), start_dt, end_dt]

        with connection.cursor() as cursor:
            cursor.execute(query, params)   # <-- param list, never interpolated
            columns = [col[0] for col in cursor.description]
            rows = [dict(zip(columns, row)) for row in cursor.fetchall()]

        return Response(rows)
```

**Why this works:** PostgreSQL's psycopg2 driver replaces `%s` placeholders with properly escaped values at the protocol level. The query plan is compiled separately from the data — an attacker-controlled string can no longer alter the SQL structure. Wherever possible, prefer the ORM (`Transaction.objects.filter(...)`) which handles escaping automatically, but when raw SQL is unavoidable, always use parameter lists.

# Issue 2 — Client-Side-Only Object Permission Checks

## CWE

**CWE-284: Improper Access Control (authorization enforced only on the client side)**

## Vulnerable Code

```python
# tenants/views.py
from rest_framework.views import APIView
from rest_framework.response import Response

class TenantReportView(APIView):
    permission_classes = []          # No DRF permission class at all

    def get(self, request, pk):      # pk = report_id
        # Believes the "frontend" will verify ownership before sending this URL
        report = get_object_or_404(Report, pk=pk)
        return Response({
            'id': report.id,
            'data': report.data,      # Entire dataset exposed
        })
```

```javascript
// frontend (React) — the ONLY place ownership is checked
async function viewReport(reportId) {
    // BUG: If someone crafts a direct curl request, this check never runs
    const ownsReport = await checkOwnsReportAPI(reportId);
    if (!ownsReport) throw new Error('Not authorized');
    const res = await fetch(`/api/tenants/report/${reportId}`);
    return res.json();
}
```

An attacker bypasses the React check entirely:

```bash
curl https://app.example.com/api/tenants/report/42
```

Since the view has no server-side restriction, the response is returned regardless of who made the request. This is a horizontal privilege escalation across every tenant.

## Corrected Code

```python
# tenants/models.py
class TenantReport(models.Model):
    tenant = models.ForeignKey('Tenants', on_delete=models.CASCADE)
    created_by = models.ForeignKey(User, on_delete=models.CASCADE)
    data = models.JSONField(default=dict)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        db_table = 'tenant_reports'

    def is_owner(self, user):
        """Determine whether *user* owns this report."""
        return self.tenant.owner == user or self.created_by == user
```

```python
# tenants/permissions.py
from rest_framework import permissions
from .models import TenantReport


class IsReportOwner(permissions.BasePermission):
    """Server-side ownership gate. Runs BEFORE the view method executes."""

    def has_object_permission(self, request, view, obj):
        if not isinstance(obj, TenantReport):
            return False
        return obj.is_owner(request.user)
```

```python
# tenants/views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import IsAuthenticated
from rest_framework.exceptions import PermissionDenied
from .models import TenantReport
from .permissions import IsReportOwner


class TenantReportDetailView(APIView):
    permission_classes = [IsAuthenticated, IsReportOwner]   # <-- server-enforced

    def get(self, request, pk):
        report = TenantReport.objects.select_related('tenant').get(pk=pk)
        # Because IsReportOwner.has_object_permission runs here:
        self.check_object_permissions(request, report)

        return Response({
            'id': report.id,
            'data': report.data,
            'created_at': report.created_at.isoformat(),
        })
```

**Why this works:** DRF calls `check_object_permissions()` after `get_object_or_404()` resolves the instance. The permission class evaluates against the *actual request user*, not anything that comes from the browser. Even a blind `/api/tenants/report/{id}` crawl returns `403 Forbidden`. Using `select_related` also prevents an N+1 query against the tenant lookup.

# Issue 3 — Hardcoded Secrets in Source-Controlled `settings.py`

## CWE

**CWE-798: Use of Hard-coded Credentials**

## Vulnerable Code

```python
# settings.py — committed to git
import os

SECRET_KEY = 'django-insecure-k#9$z!m@x7p+v2q&b5w*8n^t6r3h1j4y'  # LEAKED
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'prod_db',
        'USER': 'admin',                     # credentials in plaintext
        'PASSWORD': 'Sup3r$ecretP@ss!',      # commit history exposes forever
        'HOST': 'db.internal.example.com',
        'PORT': '5432',
    }
}
```

Once pushed to a remote (or shared internally), these secrets are permanently accessible to anyone with repository history access. Rotation requires changing what would normally be static config — an operational headache.

## Corrected Code

```python
# settings/base.py
import environ
from pathlib import Path

env = environ.Env(
    DEBUG=(bool, False),
)

BASE_DIR = Path(__file__).resolve().parent.parent

# ---------------------------------------------------------------------------
# Secrets come exclusively from environment variables (or a vault like AWS
# Secrets Manager / HashiCorp Vault injected at deployment time).
# ---------------------------------------------------------------------------
environ.Env.read_env(BASE_DIR / '.env.local')   # optional, gitignored

SECRET_KEY = env('DJANGO_SECRET_KEY')
if not SECRET_KEY:
    raise RuntimeError(
        'DJANGO_SECRET_KEY must be set as an environment variable. '
        'Run: export DJANGO_SECRET_KEY="$(openssl rand -base64 64)"'
    )

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': env('DB_NAME', default='prod_db'),
        'USER': env('DB_USER'),
        'PASSWORD': env('DB_PASSWORD'),
        'HOST': env('DB_HOST', default='localhost'),
        'PORT': env('DB_PORT', default='5432'),
    }
}

# ---------------------------------------------------------------------------
# Optional: per-environment overrides
# ---------------------------------------------------------------------------
ENVIRONMENT = env('DJANGO_ENV', default='development')

if ENVIRONMENT == 'production':
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 31536000
    ALLOWED_HOSTS = env.list('ALLOWED_HOSTS')
else:
    ALLOWED_HOSTS = ['localhost', '127.0.0.1']
```

**Why this works:** Secrets never touch the repository. # Issue 4 — Mass Assignment Allowing Staff Status Escalation

## CWE

**CWE-285: Improper Authorization (mass assignment / over-posted attributes)**

## Vulnerable Code

```python
# accounts/serializers.py
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class UserCreateSerializer(serializers.ModelSerializer):
    password = serializers.CharField(write_only=True)

    class Meta:
        model = User
        fields = '__all__'           # <-- includes is_staff, is_superuser, etc.

    def create(self, validated_data):
        user = User.objects.create_user(**validated_data)
        return user
```

A regular user sends:

```json
POST /api/accounts/users/
{
    "username": "hax0r",
    "email": "hax0r@example.com",
    "password": "strongPass!",
    "is_staff": true,             ← escalates themselves
    "is_active": true
}
```

The view creates a staff account. Now the attacker has admin panel access and can modify any user, reassign roles, or delete data.

## Corrected Code

```python
# accounts/serializers.py
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class UserCreateSerializer(serializers.ModelSerializer):
    password = serializers.CharField(write_only=True, min_length=8)

    class Meta:
        model = User
        # FIX: Explicit whitelist — NEVER use __all__.
        fields = ('id', 'username', 'email', 'password', 'first_name', 'last_name')

    def create(self, validated_data):
        # Strip any rogue keys just in case (belt-and-suspenders)
        safe_fields = set(self.Meta.fields)
        cleaned = {k: v for k, v in validated_data.items() if k in safe_fields}
        return User.objects.create_user(**cleaned)

    def validate_password(self, value):
        if len(value) < 8:
            raise serializers.ValidationError('Password must be at least 8 characters.')
        return value


class UserUpdateSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        # Different whitelist for updates — still excludes privilege fields.
        fields = ('email', 'first_name', 'last_name', 'phone')

    def update(self, instance, validated_data):
        safe_fields = set(self.Meta.fields)
        cleaned = {k: v for k, v in validated_data.items() if k in safe_fields}
        return super().update(instance, cleaned)
```

```python
# accounts/views.py
from rest_framework import generics, status
from rest_framework.decorators import api_view, permission_classes
from rest_framework.response import Response
from rest_framework.permissions import IsAdminUser, AllowAny

from .models import User
from .serializers import UserCreateSerializer, UserUpdateSerializer


class CreateUserView(generics.CreateAPIView):
    permission_classes = [AllowAny]          # public registration allowed
    serializer_class = UserCreateSerializer


class UpdateUserView(generics.UpdateAPIView):
    permission_classes = [IsAdminUser]       # only admins may edit accounts
    queryset = User.objects.all()
    serializer_class = UserUpdateSerializer
```

```python
# accounts/models.py (optional belt-and-suspenders)
class User(AbstractUser):
    @property
    def is_staff(self):
        # Force-isolate staff flag behind Group membership instead of a raw bool
        return self.groups.filter(name='Staff').exists()

    @property
    def is_superuser(self):
        return self.groups.filter(name='SuperUsers').exists()
```

**Why this works:** The serializer whitelist guarantees that fields like `is_staff`, `is_superuser`, or `groups` can never arrive from HTTP input and affect model creation/update. Combined with `IsAdminUser` on the write path, even if a future bug opens an endpoint, privilege escalation through posted JSON is impossible. The group-based override adds another layer: `is_staff` is no longer a plain boolean column but a derived property.
