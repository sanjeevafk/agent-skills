## Vulnerability 1: SQL Injection via Report Endpoint

**CWE-89: Improper Neutralization of Special Elements used in an SQL Command (SQL Injection)**

The report endpoint uses f-string interpolation to build dynamic SQL filters directly into `cursor.execute()`:

```python
# VULNERABLE CODE — reports/views.py
from django.db import connection

class ReportViewSet(viewsets.ModelViewSet):
    queryset = Report.objects.all()
    
    def retrieve(self, request, pk=None):
        filter_field = request.query_params.get('filter_by', 'created_at')
        filter_value = request.query_params.get('filter_value')
        tenant_id = request.user.tenant_id
        
        # CWE-89: User input concatenated directly into SQL string
        query = f"""
            SELECT * FROM reports
            WHERE tenant_id = {tenant_id}
            AND {filter_field} > '{filter_value}'
            ORDER BY created_at DESC
        """
        with connection.cursor() as cursor:
            cursor.execute(query)
            rows = cursor.fetchall()
        return Response(rows)
```

### Exploit

An attacker sends:
```
GET /api/reports/1/?filter_by=1; DROP TABLE users--&filter_value=anything
```

The f-string produces:
```sql
SELECT * FROM reports
WHERE tenant_id = 1
AND 1; DROP TABLE users-- > 'anything'
ORDER BY created_at DESC
```

Result: arbitrary SQL execution — data exfiltration, modification, or destruction across all tenants. With UNION-based injection, the attacker can also read arbitrary columns:
```
?filter_by=1 UNION SELECT username,password,email,is_staff FROM users--&filter_value=x
```

### Fix: Parameterized Queries + Allowlisted Field Names

`cursor.execute()` supports positional parameters (`%s`) but **only for values**, never identifiers. Column/table names must be allowlisted:

```python
# FIXED CODE — reports/views.py
REPORT_FILTER_ALLOWLIST = {
    'created_at': models.DateTimeField,
    'updated_at': models.DateTimeField,
    'title': models.CharField,
    'status': models.CharField,
    'author__email': models.EmailField,
}

def validate_filter_field(field_name: str) -> str:
    """Return validated field name from allowlist, raising ValueError otherwise."""
    if field_name not in REPORT_FILTER_ALLOWLIST:
        raise ValueError(f"Disallowed filter field: {field_name}")
    return field_name


class ReportViewSet(viewsets.ModelViewSet):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer

    def retrieve(self, request, request_obj=None, *args, **kwargs):
        instance = self.get_object()  # handles object-level perms below

        filter_field = request.query_params.get('filter_by', 'created_at')
        filter_value = request.query_params.get('filter_value')
        tenant_id = request.user.tenant_id

        # Step 1: Validate identifier against allowlist (safe for %s escaping)
        validated_field = validate_filter_field(filter_field)

        # Step 2: Use parameterized query for VALUES only
        sql = (
            "SELECT id, title, status, content, created_at, updated_at "
            "FROM reports "
            "WHERE tenant_id = %s "
            "AND {} > %s "
            "ORDER BY created_at DESC"
        ).format(validated_field)  # .format() is safe here — validated_field is constant

        with connection.cursor() as cursor:
            cursor.execute(sql, [tenant_id, filter_value])
            rows = cursor.fetchall()

        column_names = [col[0] for col in cursor.description]
        results = [dict(zip(column_names, row)) for row in rows]
        return Response(results)
```

**Even better approach** — skip raw SQL entirely and use the ORM, which handles parameterization automatically:

```python
# BEST: Pure ORM approach — no raw SQL needed
class ReportViewSet(viewsets.ModelViewSet):
    queryset = Report.objects.all()
    serializer_class = ReportSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        tenant_id = self.request.user.tenant_id
        qs = Report.objects.filter(tenant_id=tenant_id)

        filter_field = self.request.query_params.get('filter_by')
        filter_value = self.request.query_params.get('filter_value')

        if filter_field and filter_field in REPORT_FILTER_ALLOWLIST:
            # Handle both model fields and related lookups (e.g., author__email)
            lookup = f"{filter_field}__gt" if '__' not in filter_field else f"{filter_field}_gt"
            qs = qs.filter(**{lookup: filter_value})

        return qs
```

**Key protections:**
| Layer | What it blocks |
|-------|---------------|
| Allowlist on field names | Identifier injection (`DROP`, `UNION`, `--`) |
| `%s` parameters | Value injection (`'; DROP...`, `' OR '1'='1`) |
| ORM `.filter()` | Entire class of injection — DRY and safe |

## Vulnerability 2: Client-Side Only Authorization (BOLA/IDOR)

**CWE-284: Improper Access Control (Broken Object Level Authorization)**

Object permissions are enforced only in the React frontend, meaning anyone can access any object simply by changing its ID in the API URL:

```python
# VULNERABLE CODE — reports/permissions.py
from rest_framework import permissions

class TenantPermission(permissions.BasePermission):
    """WRONG: Only exists in the frontend, missing from backend."""

class ReportPermission(permissions.BasePermission):
    """WRONG: Checks nothing at the view level."""
    def has_permission(self, request, view):
        return request.user.is_authenticated  # That's it
    
    # MISSING has_object_permission entirely
```

### Exploit

User Alice has `tenant_id=5`. She accesses her report fine:
```
GET /api/reports/100  →  200 OK  (her report)
```

She changes the ID:
```
GET /api/reports/100   →  still works because the backend never checks ownership
GET /api/reports/100   →  200 OK  (Bob's report from tenant 7 — data leak)
DELETE /api/reports/100 →  204 No Content  (data destruction)
PATCH /api/reports/100 →  200 OK  (arbitrary write)
```

Without server-side `has_object_permission`, **every CRUD operation is blind** to object ownership. The frontend check is trivially bypassed with `curl`, Burp Suite, or Postman.

### Fix: Server-Side Object-Level Permissions

```python
# FIXED CODE — reports/permissions.py
from rest_framework import permissions
from django.core.exceptions import PermissionDenied


class ObjectOwnerPermission(permissions.BasePermission):
    """
    Enforce object-level access control on the SERVER.
    
    Each request must verify that the authenticated user owns
    or is authorized for the specific object being accessed.
    """

    def has_permission(self, request, view):
        return request.user and request.user.is_authenticated

    def has_object_permission(self, request, view, obj):
        """
        Called after has_permission. Validates access to a SPECIFIC instance.
        
        Returns False → Django returns HTTP 403 Forbidden immediately.
        """
        # Case 1: Objects have a direct owner field
        if hasattr(obj, 'owner'):
            return obj.owner == request.user

        # Case 2: Objects belong to a tenant scope
        if hasattr(obj, 'tenant_id'):
            return obj.tenant_id == request.user.tenant_id

        # Case 3: Custom method (e.g., groups, roles)
        if callable(getattr(obj, 'user_can_access', None)):
            return obj.user_can_access(request.user)

        return False


class ReadOnlyIfNotStaff(permissions.BasePermission):
    """Non-staff can READ but not modify objects."""

    def has_object_permission(self, request, view, obj):
        if not request.user.is_staff:
            return request.method in permissions.SAFE_METHODS
        return True
```

Wire it into the viewset:

```python
# FIXED CODE — reports/views.py
from rest_framework import viewsets, permissions
from .permissions import ObjectOwnerPermission, ReadOnlyIfNotStaff

class ReportViewSet(viewsets.ModelViewSet):
    queryset = Report.objects.select_related('tenant').all()  # prevent N+1
    serializer_class = ReportSerializer

    permission_classes = [
        permissions.IsAuthenticated,           # global: must be logged in
        ObjectOwnerPermission(),               # per-object: must own it
        ReadOnlyIfNotStaff(),                  # role guard
    ]

    def get_queryset(self):
        """Scope to current tenant — prevents cross-tenant enumeration."""
        return Report.objects.filter(tenant_id=self.request.user.tenant_id)

    def perform_create(self, serializer):
        """Ensure created objects inherit the creator's tenant."""
        serializer.save(owner=self.request.user, tenant_id=self.request.user.tenant_id)
```

**CWE-798: Use of Hard-coded Credentials**

```python

        'HOST': 'db.internal.example.com',
        'PORT': '5432',
    }
}

REDIS_URL = 'redis://:r3d1s_p@ss@cache.internal:6379/0'

AWS_SECRET_ACCESS_KEY = 'wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY'
```

### Exploit

1. An attacker clones the public repo → finds credentials in `settings.py`
2. Connects directly to PostgreSQL: `psql -h db.internal.example.com -U admin -d myapp_production` → reads/writes all data
3. Impersonates the app to S3/RDS/etc. using AWS keys
4. If secrets rotate on a schedule, the hardcoding causes downtime until someone notices
5. Any contributor who commits changes re-exposes the same secrets

A leaked `SECRET_KEY` alone breaks Django's cryptographic guarantees: signed cookies, CSRF tokens, and session integrity are all compromised, enabling full session hijack.

### Fix: Environment Variables + Validation + `.gitignore`


## Vulnerability 4: Mass Assignment — Staff Status Toggle

**CWE-915: Improper Restriction of Renovations of Resources Using Excessively Mutable Mechanisms (Mass Assignment / Insecure Direct Object Reference on User Model)**

```python
# VULNERABLE CODE — accounts/serializers.py
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()


class UserSerializer(serializers.ModelSerializer):
    """Serializes ALL model fields — including sensitive flags."""

    class Meta:
        model = User
        fields = '__all__'          # <-- grants EVERY writable field to the client
        # Missing read_only_fields

    # The client can pass staff=True, is_superuser=True, etc.
    # because there is no field whitelist restricting what goes IN.
```

```python
# vulnerable — views
class UserViewSet(viewsets.ModelViewSet):
    queryset = User.objects.all()
    serializer_class = UserSerializer
    permission_classes = []   # wide-open, or even IsAuthenticated on a regular user
```

### Exploit

A regular authenticated user sends:

```json
PATCH /api/users/42/
Authorization: Bearer <valid_jwt>
Content-Type: application/json

{
  "staff": true,
  "is_superuser": true
}
```

Django's `ModelSerializer` maps JSON keys directly to model fields (unless explicitly overridden). `staff` and `is_superuser` are standard `BooleanField`s on `AbstractBaseUser` — they accept `True` like any other value. Result: instant privilege escalation. The user now sees the Django admin panel, can create/delete users, and access everything.

Even more subtle: mass assignment lets a regular user modify another user's record:
```json
PUT /api/users/42/
{
  "first_name": "Evil",
  "last_name": "Impersonator",
  "email": "evil@attacker.com"
}
```

No object-level check, no field restrictions — total compromise.

### Fix: Explicit Field Whitelist + Admin-Only Endpoints + Server-Side Ownership Check

```python
# FIXED CODE — accounts/serializers.py
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_password_hasher  # for hash enforcement

User = get_user_model()


class UserListSerializer(serializers.ModelSerializer):
    """
    Read-only representation for list endpoints.
    Excludes passwords, flags, tokens, and audit fields.
    """
    class Meta:
        model = User
        fields = ('id', 'username', 'email', 'first_name', 'last_name',
                  'date_joined', 'is_active')
        read_only_fields = fields


class UserRegistrationSerializer(serializers.ModelSerializer):
    """Write-only: accepts CREATE but exposes nothing sensitive."""
    password = serializers.CharField(write_only=True, min_length=8,
                                     style={'input_type': 'password'})
    password_confirm = serializers.CharField(write_only=True, min_length=8,
                                             style={'input_type': 'password'})

    class Meta:
        model = User
        fields = ('username', 'email', 'password', 'password_confirm',
                  'first_name', 'last_name')

    def validate(self, attrs):
        if attrs.pop('password') != attrs.pop('password_confirm'):
            raise serializers.ValidationError({'password_confirm': 'Passwords do not match'})
        return attrs

    def create(self, validated_data):
        user = User.objects.create_user(**validated_data)
        return user


class UserProfileSerializer(serializers.ModelSerializer):
    """
    PATCH-safe: regular users can only update non-sensitive profile fields.
    Staff/admin flags are STRICTLY write-only on the server side.
    """
    class Meta:
        model = User
        # EXPLICIT WHITELIST — no __all__, no wildcard
        fields = ('id', 'first_name', 'last_name', 'bio', 'avatar')
        read_only_fields = ('id',)


class AdminUserUpdateSerializer(serializers.ModelSerializer):
    """
    Restricted to superusers/staff only.
    Every mutable field is declared — no hidden paths for privilege escalation.
    """
    class Meta:
        model = User
        fields = ('id', 'username', 'email', 'first_name', 'last_name',
                  'is_active', 'is_staff', 'is_superuser', 'groups', 'user_permissions',
                  'date_joined')
        read_only_fields = ('id', 'date_joined')
```

Wire it up with dedicated action endpoints so mass-assignment fields live behind proper authorization:

```python
# FIXED CODE — accounts/views.py
from rest_framework import viewsets, status, permissions
from rest_framework.decorators import action
from rest_framework.response import Response
from django.contrib.auth import get_user_model
from .serializers import (
    UserListSerializer,
    UserRegistrationSerializer,
    UserProfileSerializer,
    AdminUserUpdateSerializer,
)

User = get_user_model()


class UserViewSet(viewsets.ModelViewSet):
    """
    Users can read their own profile. Staff can manage others.
    Registration is anonymous.
    """

    def get_queryset(self):
        # Regular users see nobody; staff see everyone
        if self.request.user.is_staff:
            return User.objects.all()
        # Non-staff should not be listing users at all
        return User.objects.none()

    def get_serializer_class(self):
        if self.action == 'create':
            return UserRegistrationSerializer
        if self.action == 'update' or self.action == 'partial_update':
            # Only reachable after proper auth checks
            return AdminUserUpdateSerializer
        return UserListSerializer

    @action(detail=False, methods=['get', 'patch'])
    def me(self, request):
        """Self-service profile endpoint — users can only touch their own record."""
        user = request.user
        if request.method == 'GET':
            return Response(UserProfileSerializer(user).data)
        # PATCH: restricted to profile-only fields
        serializer = UserProfileSerializer(user, data=request.data, partial=True)
        serializer.is_valid(raise_exception=True)
        serializer.save()
        return Response(serializer.data)

    @action(detail=True, methods=['patch'], url_path=r'(?P<pk>\d+)/profile')
    def update_profile(self, request, pk=None):
        """Another route to the profile endpoint — ensures object ownership."""
        target = self.get_object()

        # HARD GUARD: cannot edit another user's profile
        if request.user != target and not request.user.is_staff:
            return Response(
                {'detail': 'You can only update your own profile.'},
                status=status.HTTP_403_FORBIDDEN
            )

        if not request.user.is_staff:
            # Non-staff users hit the restrictive serializer
            serializer = UserProfileSerializer(target, data=request.data, partial=True)
        else:
            # Staff hit the full serializer
            serializer = AdminUserUpdateSerializer(target, data=request.data, partial=True)

        serializer.is_valid(raise_exception=True)
        serializer.save()
        return Response(serializer.data)

    def perform_create(self, serializer):
        # Registration never creates staff/superuser
        user = serializer.save()
        user.is_staff = False
        user.is_superuser = False
        user.save(update_fields=['is_staff', 'is_superuser'])
```

Add an explicit permission class to close any gaps around object-level access:

```python
# accounts/permissions.py
from rest_framework import permissions


class IsOwnOrStaff(permissions.BasePermission):
    """Allows owners to edit themselves; staff can edit anyone."""

    def has_object_permission(self, request, view, obj):
        if request.user.is_staff:
            return True
        return obj == request.user
```

## Summary Matrix

| Issue | CWE | Root Cause | Fix |
|-------|-----|-----------|-----|
| SQL Injection | **CWE-89** | f-string concat into `cursor.execute()` | Parameterized queries + identifier allowlist + prefer ORM |
| BOLA / IDOR | **CWE-284** | Object-level check only in frontend | `has_object_permission()` in DRF permission classes; scope `get_queryset()` by tenant |
| Hardcoded Secrets | **CWE-798** | `SECRET_KEY`/DB creds literal in `settings.py` | `os.environ[]` via `dj_database_url` + pre-commit guard + rotation procedure |
| Mass Assignment | **CWE-915** | `fields = '__all__'` with no `read_only_fields` | Explicit field whitelist per serializer role; separate registration/profile/admin serializers; `perform_create` nullify flags |

**Critical pattern across all four**: every vulnerability shares one root cause — trusting input (user-supplied SQL fragments, API IDs, configuration literals, and JSON body keys) without validating it against an expected set on the server. Defense-in-depth means validating at the boundary (allowlists, parameterization, env-gated config) and enforcing authority inside (server-side permissions, serializer scoping, explicit write/read masks).
