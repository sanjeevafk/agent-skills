```yaml

kind: Deployment
metadata:
  name: go-api
  namespace: api
  labels:
    app: go-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: go-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       1          # allow 1 extra pod during rollout
      maxUnavailable: 0          # never drop below desired count
  template:
    metadata:
      labels:
        app: go-api
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port:   "9090"
    spec:
      serviceAccountName: go-api
      terminationGracePeriodSeconds: 45
      priorityClassName: high-priority      # evict low-priority first

      # imagePullSecrets:
      #   - name: reg-creds

      # ── Anti-affinity: spread across nodes / zones ──────────
      affinity:

              containerPort: 8080
              protocol: TCP
            - name: metrics
              containerPort: 9090

            - name: DB_PASSWORD
              valueFrom: { secretKeyRef: { name: api-secrets, key: db-password } }
            # All other secrets are consumed via mounted files (below)

          # PROBE THRESHOLD ARITHMETIC
          #
          # Application profile:
          #   • Cold-start cache warmup  : 20 s  (startup)
          #   • Health-check overhead     : ≤ 50 ms per probe
          #   • Readiness gate depends on cache being warm
          #   • Liveness = liveness check (does nothing bad; just pings /healthz)
          #
          # startupProbe  → gives the container full warmup runway
          #   periodSeconds = 5  → check every 5 s
          #   failureThreshold = 8 → tolerates 8 consecutive failures
          #   total allowed time = 5 × 8 = 40 s  (> 20 s warmup + margin)
          #   periodSeconds * failureThreshold ≥ warmup_seconds + headroom
          #
          # readinessProbe  → begins immediately (parallel with startup),
          #   but won't succeed until the app's /readyz returns 200, which
          #   it does only after cache warmup completes (~20 s).
          #   periodSeconds = 3  → lightweight polling
          #   failureThreshold = 3 → 3 successive misses drops from svc endpoint
          #   initialDelaySeconds = 0 → no delay; start checking right away
          #   timeoutSeconds = 2  → abort if probe hangs
          #
          # livenessProbe  → identical timing to readiness but semantically different:
          #   A failure kills (and restarts) the pod.  We want it lenient so
          #   a GC pause or momentary spike doesn't cause unnecessary churn.
          #   initialDelaySeconds = 30  → skip while startup is happening
          #   periodSeconds = 10
          #   failureThreshold = 3      → 30 s of genuine unresponsiveness needed
          #   timeoutSeconds = 5
          # ═══════════════════════════════════════════════════════

          startupProbe:
            httpGet:
              path: /healthz
              port: http
              scheme: HTTP
            periodSeconds:    5
            failureThreshold: 8      # 5×8 = 40 s budget  > 20 s warmup
            successThreshold: 1
            timeoutSeconds:   2

          readinessProbe:
            httpGet:
              path: /readyz
              port: http
              scheme: HTTP
            periodSeconds:    3
            failureThreshold: 3
            successThreshold: 1
            initialDelaySeconds: 0
            timeoutSeconds:   2

          livenessProbe:
            httpGet:
              path: /healthz
              port: http
              scheme: HTTP
            periodSeconds:    10
            failureThreshold: 3      # 10×3 = 30 s dead-man window
            successThreshold: 1
            initialDelaySeconds: 30  # overlap-safe
            timeoutSeconds:   5

          # ── Resource requests / limits  ─────────────────────────
          # Rationale (Go API at p99 under load):
          #   CPU request 250 m guarantees scheduler places pod on a node
          #   with enough capacity.  With 10 replicas × 250 m = 2.5 cores
          #   minimum cluster-wide reservation.
          #   CPU limit 500 m allows bursting to handle transient spikes
          #   without immediate OOM Kill.  At p99 we want < 1 % throttling;
          #   empirically 2× request = burst room for short bursts.
          #   Memory request 512 Mi ≈ median RSS.  Limit 1 Gi caps tail-RSS
          #   and leaves ~50 % headroom on a 2 Gi node before OOM score adjusts.
          resources:
            requests:
              cpu:           250m
              memory:        512Mi
            limits:
              cpu:           500m
              memory:        1Gi

          # ── Volume mounts ───────────────────────────────────────
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp
            - name: cache
              mountPath: /var/cache/app
          lifecycle:
            preStop:
              exec:
                # See termination-drain section below for the full sequence.
                command: [sh, -c, sleep 10]
            postStart:
              exec:
                # Quick bootstrap hint; actual warmup happens in app main().
                command: [sh, -c, echo starting]

      volumes:
        - name: secrets
          secret:
            secretName: api-secrets
        - name: vault-token
          projected:
            sources:
              - serviceAccountToken:
                  path: token
                  expirationSeconds: 3600
                  audience: vault
        - name: tmp
          emptyDir: { sizeLimit: 100Mi }
        - name: cache
          emptyDir: { medium: Memory, sizeLimit: 256Mi }   # fast, volatile cache layer
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api-hpa
  namespace: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    # ── Metric 1: Average CPU util vs request ─────────────────
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60   # scale up when avg > 60 % of request
    # ── Metric 2: Custom queue depth from Prometheus adapter ──
    #    The Go app exposes pending_requests as a gauge:
    #    go_api_queue_depth{job="go-api"}  per-replica or aggregated.
    #
    #    Rule in prometheus/rules/kustomize.yml:
    #      record: job:pending_requests_sum
    #      expr: sum by(job) (go_api_queue_depth)
    #
    #    Target: average value across pods.  E.g., 5 means "average
    #    replica sees 5 pending items → trigger scale-up".
    #
    #    Formula in HPA calc (raw metric mode):
    #      desiredReplicas = ceil(currentReplicas × (currentMetricValue / targetValue))
    #    With targetValue = 3, current = 15 → ceil(3 × 15/3) = 15 → clamped to max 10.
    - type: Pods
      pods:
        metric:
          name: pending_requests_per_pod
        target:
          type: AverageValue
          averageValue: "3"         # scale up when each-pod avg queue > 3
    # ── Optional: scale-down stabilization ────────────────────
    # (handled below via behavior section)
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 5 min hold before scaling down
      policies:
        - type: Percent
          value: 25        # never drop more than 25 % per period
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0     # react immediately to traffic spikes
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60
        - type: Pods
          value: 4
          periodSeconds: 60
      selectPolicy: Max                 # pick the most aggressive policy
```

## Probe Threshold Arithmetic

### Timeline diagram

```
t=0s    Container starts. Startup & readiness probes begin (zero initialDelay).
        App enters cache-warm phase.

t=0s    Liveness probe blocked by initialDelaySeconds=30.

t=0-20s App is warming cold cache (reads, populates structures).
        /healthz → 200  (healthy process, even if slow)
        /readyz  → 503   (cache not ready yet — readiness stays false)
        startup  : failure counts up. Each period 5 s, threshold 8 → 40 s total budget.

t≈20s   Cache warm complete. /readyz flips to 200.
        Startup probe also succeeds on its next check.
        Pod transitions: Uninitialized → Ready. Traffic flows.

t=30s   Liveness probe now active. Checks every 10 s.
        Needs 3 consecutive failures (30 s) to kill the pod.

t>30s   Normal operation.
        Any of the three failing independently:
          startup expired → K8s assumes permanent crash → restart pod
          readiness lost  → remove from Service endpoints → zero new traffic
          liveness gone   → restart container → zero dropped (endpoints already drained)
```

### Why each number is correct

| Probe | periodSeconds | failureThreshold | successThreshold | initialDelay | Total Window | Why |
|---|---|---|---|---|---|---|
| **startup** | 5 | 8 | 1 | 0 | **40 s** | Must exceed 20 s warmup with 2× safety margin. `5 × 8 = 40`. |
| **readiness** | 3 | 3 | 1 | 0 | ~9 s detection | Fast detection keeps pods out of rotation during warmup. `3 × 3 = 9 s` stale. |
| **liveness** | 10 | 3 | 1 | 30 | 30 s dead-man | Won't fire until past warmup (`initialDelay=30`). Then needs 30 s truly broken. |

**Key design decisions:**
- `failureThreshold: 3` (not 1) on readiness/liveness prevents a single GC pause or network blip from removing or restarting pods.
- `successThreshold: 1` means the very next successful check restores state — minimal flap risk.
- Liveness `initialDelaySeconds=30` prevents it from competing with startup during the vulnerable warmup window. If both probed simultaneously, they'd double-count failures.

## Termination Drain Sequence

When a rolling update starts or a node is cordoned, the following sequence ensures zero dropped requests:

```
t=0    kubelet receives SIGTERM for the pod (from Deploy update / node drain).

t=0    preStop hook runs:  `sleep 10`
        ┌─ Load balancer (Cloud LB / NLB / Istio) removes pod IPs from backends.
        │   Typically takes 2-5 seconds depending on LB health-check interval.
        │   The 10-second sleep ensures removal completes before app starts shutting down.
        └─ During sleep, in-flight requests finish normally. New requests stop arriving.

t=10   preStop exits. App's signal handler catches SIGTERM.
        ┌─ Stop accepting NEW connections (listener closes).
        │
        │  ┌── graceful shutdown:
        │  │  1. http.Server.Shutdown(ctx)  – stops listening, drains existing conns.
        │  │  2. Context canceled after 25 s (terminationGracePeriod=45 minus 10 preStop
        │  │     minus 10 buffer for OS cleanup → 25 s for work).
        │  │  3. Flushes in-progress DB transactions, message bus acks.
        │  │  4. Log buffers flushed.
        │  └→ os.Exit(0) or return from main().
        │
        │  Math: 45 s grace − 10 s preStop − 10 s OS/buffer = 25 s application drain.
        │  25 s is enough for any realistic p99 request (< 10 s for Go APIs at normal load).
        └─ If still running at t=45, SIGKILL sent by kubelet.

t=10-35  Application draining in-flight requests.
         Requests completed within this window are NOT dropped.

t=35+  Pod exits cleanly.  New ReplicaSet picks up the slot.
```

### Application-side implementation (Go snippet)

```go
package main

import (
    "context"
    "fmt"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "google.golang.org/grpc"
)

func main() {
    srv := &http.Server{Addr: ":8080", Handler: router()}
    
    // Start in goroutine
    go func() {
        log.Fatal(srv.ListenAndServe())
    }()

    // Wait for interrupt
    sig := make(chan os.Signal, 1)
    signal.Notify(sig, syscall.SIGTERM, syscall.SIGINT)
    <-sig
    log.Println("SIGTERM received, draining...")

    // 25-second drain context (matches K8s math above)
    ctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
    defer cancel()

    // Shutdown gracefully: stops accepting, waits for inflight to finish
    if err := srv.Shutdown(ctx); err != nil {
        log.Fatalf("shutdown failed: %v", err)
    }

    fmt.Println("drained successfully")
}
```

### Why this achieves zero-dropped requests

1. **`maxUnavailable: 0`** on the Deployment — old pods never die until new ones are Ready.
2. **preStop sleep** — lets the cloud LB take endpoints offline *before* the app closes its listener. Without this, the LB sends traffic to a dying pod for the duration of its health-check interval (typically 5-30 s).
3. **Readiness removal** — readiness flips to false at deploy time, causing K8s Service to remove the pod from iptables/IPVS rules immediately, independent of LB propagation.
4. **Server.Shutdown** — drains existing TCP connections, responds with proper 200s to in-flight requests, then closes the listener.
5. **45 s grace period** — ample for any reasonable request latency plus cleanup. SIGKILL is the last-resort exit, not the normal path.

## Resource Sizing — Avoiding p99 Throttling

| Dimension | Request | Limit | Rationale |
|---|---|---|---|
| **CPU** | 250 m | 500 m | 250 m guarantees placement; 500 m allows 2× burst for GC pauses / spike handling. At 60 % target utilization, HPA adds capacity before throttling becomes persistent. p99 latencies stay under SLA because sustained throttling only occurs at >100 % utilization, well beyond our burst ceiling. |
| **Memory** | 512 Mi | 1 Gi | Go's default GOGC=100 doubles heap RSS briefly. 512 Mi request ≈ typical steady-state; 1 Gi limit accommodates post-GC peaks without hitting OOM. Memory-limit-based eviction beats CPU-throttle degradation. |
| **Pods × requests** | — | — | 10 replicas × 250 m = **2.5 cores** minimum guaranteed across the fleet. On a standard 4-core node you fit 2 pods comfortably (500 m used, 3 Gi RAM free for burst). |

## PDB Strategy

With `minAvailable: 1`:

- During a **node drain**, kubelet honors the PDB — it will only evict a pod if ≥ 1 matching pod remains running.
- With 3 replicas minimum (HPA lower bound), losing 1 pod leaves 2 — the system stays healthy.
- **Alternative**: `maxUnavailable: 1` is equivalent here but better for bulk operations (e.g., cluster autoscaler upgrading multiple nodes), as it processes drain jobs in parallel rather than forcing sequential drains that `minAvailable` can sometimes imply.

Choose based on your operational tooling — `minAvailable` is the conservative choice; `maxUnavailable` scales better for automated node upgrades.
