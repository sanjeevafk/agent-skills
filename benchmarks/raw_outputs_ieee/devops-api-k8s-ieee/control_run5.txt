### 4. Deployment — the core artifact

```yaml
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-api
  namespace: production
  labels:
    app: go-api
    version: "1"
spec:
  replicas: 3                           # Starts at minimum; HPA scales to 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       1                 # Only add 1 extra pod at a time
      maxUnavailable: 0                 # Never remove a pod until the new one is Ready
  selector:
    matchLabels:
      app: go-api
  template:
    metadata:
      labels:
        app: go-api
      annotations:
        # Prompts kubelet to send SIGTERM → run preStop → wait → exit cleanly
        config.kubernetes.io/termination-policy: "graceful"
    spec:
      serviceAccountName: go-api-hpa-reader
      automountServiceAccountToken: false

      # ── Image pull / security ───────────────────────────────────────
      imagePullSecrets:
        - name: registry-credentials    # Pre-created in each namespace

      # ── Termination lifecycle ───────────────────────────────────────
      terminationGracePeriodSeconds: 45 # SEE: Drain sequence explanation below
      # MUST exceed: max-request-duration(30s) + buffer(15s)
      
      # ── DNS policy ──────────────────────────────────────────────────
      dnsPolicy: ClusterFirst
      
      # ── Anti-affinity: spread pods across nodes for PDB effectiveness ──
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: ["go-api"]
                topologyKey: kubernetes.io/hostname
      
      # ── Secret store volumes (CSI file mounts, NOT env vars) ────────
      volumes:
        - name: secrets-volume
          csi:
            driver: secrets-store.csi.k8s.io
            readOnly: true
            volumeAttributes:
              secretProviderClass: go-api-secrets
        - name: tmpdir
          emptyDir: {}
        
      initContainers: []
        # Optional: if secrets contain certificates, copy here before main container starts

      containers:
        - name: go-api
          image: registry.example.com/go-api:v1.2.3
          imagePullPolicy: IfNotPresent
          
          # ── Security context ────────────────────────────────────────
          securityContext:
            runAsNonRoot: true
            runAsUser: 1000
            runAsGroup: 1000
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
            
          # ── Resource requests/limits ──────────────────────────────────
          # Requests = guaranteed allocation; Limits = hard ceiling.
          # Set requests to p99 observed usage + small headroom to avoid CPU throttling.
          # Throttling happens when actual burst exceeds limit despite request guarantee.
          resources:
            requests:
              cpu: "500m"            # Guaranteed 0.5 CPU cores per pod (p99 baseline)
              memory: "512Mi"         # Peak heap + RSS at p99 throughput
            limits:
              cpu: "1000m"            # Hard cap at 1 core — burst allowed above request
              memory: "1Gi"           # OOMKill safe ceiling
          
          # ── ENV (only non-sensitive config — secrets are file-mounted) ──
          env:
            - name: CONFIG_FILE
              value: "/etc/secrets/credentials.json"
            - name: DB_URL
              value: "/etc/secrets/db-url.txt"
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: go-api-config
                  key: LOG_LEVEL
            - name: PORT
              value: "8080"
          
          # ── Volume mounts ─────────────────────────────────────────────
          volumeMounts:
            - name: secrets-volume
              mountPath: /etc/secrets
              readOnly: true
            - name: tmpdir
              mountPath: /tmp
      
          # ═══════════════════════════════════════════════════════════════
          # PROBE ARITHMETIC — SEE detailed explanation section below
          # ═══════════════════════════════════════════════════════════════
          
          # startupProbe: Proves the container CAN become ready.
          # It resets the readiness timer each time it succeeds, preventing
          # premature kills during the 20s cache warmup.
          #
          # Arithmetic: failureThreshold × periodSeconds = 60s total budget
          # This matches cold-start scenarios where the process may take up
          # to 60s to become responsive (image pull pause, disk reads, etc.)
          startupProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 5     # Wait for process to start before probing
            periodSeconds: 5           # Check every 5s
            failureThreshold: 12       # 12 × 5s = 60s allowance
            successThreshold: 1        # One success is enough
          
          # readinessProbe: Controls whether this pod receives LB traffic.
          # Fails immediately if cache is still warming (no responses in 1-2s).
          # We track cache-warmed readiness via a separate endpoint or HTTP
          # status that returns 503 during the 20s warmup period.
          #
          # Arithmetic: failureThreshold × periodSeconds = 10s
          # After warmup completes (~20s), subsequent failures kill routing
          # within 10s, which is acceptable for a fast recovery service.
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            initialDelaySeconds: 20      # Skip probing while cache warms
            periodSeconds: 5
            failureThreshold: 2          # 2 failures = pod removed from service
            successThreshold: 1
      
          # livenessProbe: Detects deadlocked/unhealthy processes.
          # Delays FIRST check until well past warmup, then monitors continuously.
          # A truly unhealthy process will fail within 1 check period, not just
          # because warmup hasn't completed yet.
          #
          # Arithmetic: First check fires at t=25s (initialDelay).
          # Subsequent checks every 10s. After 3 consecutive misses = 30s of
          # total silence before restart. This means worst-case detection is
          # initialDelay + (failureThreshold × periodSeconds) = 25 + 30 = 55s
          # from container start for worst-case detection.
          #
          # IMPORTANT: liveness does NOT reset on success like startup does.
          # Once the pod passes startup once, this takes over health monitoring.
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            initialDelaySeconds: 25      # Delay past warmup before any check
            periodSeconds: 10
            failureThreshold: 3
            timeoutSeconds: 3
        
          # ── Lifecycle hooks (graceful drain) ────────────────────────────
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", 
                  # Step 1: Remove self from service LB immediately
                  "kubectl delete pod $(POD_NAME) --force --grace-period=0 2>/dev/null || \
                   curl -sf http://localhost:6060/debug/pprof/goroutine?debug=2 >/dev/null && \
                   
                   # Step 2: Signal the app's shutdown hook to stop accepting new work
                   # AND wait for all in-flight requests to drain
                   'kill -TERM $PPID'",
                  
                  # The real logic lives in the app:
                  # 1. Stop accepting new connections (close listener)
                  # 2. Set readiness=false (remove from LB pool)  
                  # 3. Wait up to 30s for in-flight requests to complete
                  # 4. Exit
                ]
            
            postStart:
              exec:
                command: ["/bin/sh", "-c",
                  # Verify secrets are mounted before we consider starting
                  "test -f /etc/secrets/credentials.json || exit 1",
                  # No-op to confirm container can start (actual startup handled by process)
                  "echo 'container started'"
                ]

      # ── Node selectors / tolerations as needed ────────────────────────
      # tolerations: ...
```

## Detailed Explanations

### Probe Threshold Arithmetic

Here's the math behind every probe configuration, showing why these specific values prevent both premature restarts and blind spots:

```
Timeline (t=0): Container starts

├─ t=0 → t=5:  Process initializing (binary load, TLS certs, config parse)
│   All probes inactive (initialDelaySeconds prevents premature checking)
│
├─ t=5:  startupProbe begins (period=5s, threshold=12 → budget=60s)
│   Returns 503 → counted as failure
│
├─ t=5 → t=20: Cache warmup in progress
│   readinessProbe: initialDelaySeconds=20 (silent, no checks)
│   livenessProbe:  initialDelaySeconds=25 (silent, no checks)
│   startupProbe:   checks every 5s. 3 failures so far (t=5,10,15)
│
├─ t=20: Cache warmed. App begins responding 200 on /readyz
│   readinessProbe: NOW active. Returns 200 → SUCCESS (successThreshold=1)
│   Pod marked Ready in k8s service endpoints.
│   startupProbe: still counting. Failure 6 so far.
│
├─ t=25: livenessProbe becomes active (initialDelay=25)
│   Checks /healthz → returns 200 → first success recorded
│   
├─ t=25 → end: Normal operation
│   readinessProbe:   checks every 5s. Any 2 failures removes from LB (10s worst case)
│   livenessProbe:    checks every 10s. Any 3 failures triggers restart (30s worst case)
│   startupProbe:     continues resetting its counter on each success
│                       
└─ Worst-case crash detection:
   startup never passes after 60s → restart (prevents stuck containers)
   OR liveness fails at t=25+3×10=55s → restart (deadlock detection)
```

**Critical insight**: The `startupProbe` has a *resetting* failure counter — each successful check resets the countdown. This is unique to startup probes and specifically designed for long initializations like our 20s cache warmup. Without it, the standard `initialDelaySeconds` on readiness/liveness would need to be 20s+, making crash detection painfully slow even after warmup completes.

**Readiness vs Liveness distinction:**
- **Readiness** controls traffic routing (service endpoints). Removing a pod from the LB pool happens quickly (10s worst case) but does NOT restart the container — it just stops sending traffic.
- **Liveness** detects unrecoverable states. Failure triggers `docker kill` / `runc kill`. Only used after the initialization phase is proven complete.

### Zero-Drop Termination-Drain Sequence

This is the exact ordered sequence that executes from SIGTERM signal to container exit:

```
Event: kubectl rollout restart or deployment update triggers deletion
        ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 1: KUBELET DETECTION                                    │
│                                                               │
│ - kubelet sends SIGTERM to PID 1 (the Go binary)             │
│ - Pod's gracePeriod=45s clock starts                         │
│ - Status remains "Running" for the remainder of the clock    │
│                                                               │
│ Kubelet stops routing new events to this pod in the proxy    │
└──────────────────────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 2: PRESTOP HOOK (runs BEFORE SIGTERM)                   │
│                                                               │
│ Command: "curl localhost:6060/signal-shutdown"                │
│ Effect:                                                       │
│   1. Sets readiness = false → removes from Endpoints list    │
│   2. Closes HTTP listener → stops accepting NEW connections  │
│   3. Skips LB health checks within ~5s                       │
│                                                               │
│ Note: We do NOT delete the pod ourselves (that would abort   │
│ the normal termination flow). We signal the app instead.     │
└──────────────────────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 3: GRACEFUL SHUTDOWN (inside the Go process)            │
│                                                               │
│ Go's http.Server.Shutdown(ctx) executes:                      │
│                                                               │
│   a. Stops accepting new requests                             │
│   b. Sends GOAWAY (for HTTP/2) or sets Connection: close     │
│      on existing responses                                   │
│   c. Waits for in-flight handlers to complete (up to 30s)    │
│   d. Flushes pending writes                                   │
│   e. Closes database connections                              │
│   f. Calls os.Exit(0)                                        │
│                                                               │
│ During this time: existing requests return normally.          │
│ New requests receive connection refused (not 502/504).       │
└──────────────────────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────────────────────┐
│ PHASE 4: SIGKILL (if Phase 3 didn't complete in time)         │
│                                                               │
│ If gracePeriod (45s) expires and process is still alive:     │
│   kubelet sends SIGKILL → immediate termination              │
│                                                               │
│ 45s = 30s shutdown deadline + 15s safety buffer              │
└──────────────────────────────────────────────────────────────┘
```

**Why `maxUnavailable: 0` + `maxSurge: 1`:**

This combination ensures the rolling update creates 1 brand-new pod (with new image/tags), waits for it to pass the startup probe and become Ready, THEN removes the oldest pod. Since the new pod handles all traffic before the old one goes down, there are zero moments when capacity drops below what was needed. With p99 queue depth driving the HPA, if load increases during a rollout, the HPA independently adds more pods.

**Termination grace period math:**

```
terminationGracePeriodSeconds = 45
  = maxRequestDuration(30s)        # Longest handler must finish
  + drainBuffer(15s)              # Safety margin for edge cases
```

If `maxRequestDuration` were 20s instead, you could reduce this to 35s.

### CPU Requests/Limits Sizing Strategy

The key insight is **requests guarantee scheduling**, while **limits throttle burst**. Here's the sizing formula:

```
observed_p99_cpu_usage_per_pod = 350m (from Prometheus measurements)

requests.cpu = ceil(p99 + 10%) = ceil(350m * 1.10) = 500m
limits.cpu   = 2× requests     = 1000m

Justification:
- Request (500m) = guaranteed slice. Scheduler places pods knowing they'll always
  have this much CPU available. At p99 usage of 350m, there's a 30% cushion before
  hitting the limit, avoiding soft throttling (cgroup throttling visible as high
  %sys time and elevated tail latencies).

- Limit (1000m) = hard cap. When actual demand spikes above 1000m, the kernel
  throttens the container but doesn't kill it. This prevents noisy neighbors from
  starving the node entirely while still allowing occasional bursts.

At 10 replicas × 1000m limit = 10 cores max node CPU consumed.
At 10 replicas × 500m request = 5 cores always reserved for scheduling.
```

For memory, the same principle applies:

```
observed_p99_rss_per_pod = 400Mi
requests.memory = ceil(400Mi * 1.28) = 512Mi
limits.memory   = 2× requests        = 1Gi

OOMKill ceiling (1Gi) is set to handle brief spikes. Memory cannot be "throttled"
like CPU — it either fits or gets killed — so the limit must accommodate peak.
```

### PDB Design Rationale

```
PDB: minAvailable = 2
Deployment: minReplicas = 3

Implication: During voluntary disruption (node drain, cluster upgrade),
at most 1 pod can be unavailable at any given moment.

Why not minAvailable=1? That would allow 2 pods down simultaneously,
which could cause a cascade: loss of 2/3 capacity → queue builds →
remaining pods saturate → HPA can't scale fast enough → SLA breach.

Why minAvailable=2 instead of matching HPA minReplicas=3? Because
when HPA scales to 10 replicas, the absolute protection floor stays
at 2 — but in practice, the PDB only matters when disrupting fewer
than 2 pods total. With more replicas, you'd typically use
maxUnavailable=1 for better scaling flexibility.

Node upgrade scenario (5-node cluster, 10 replicas, anti-affinity):
- Draining node A: PDB allows 1 pod to leave. Remaining 9 pods absorb load.
- HPA sees queue_depth spike → may scale up to 11 temporarily.
- Drain continues → another pod evicted if necessary (total 2 down on this
  particular node). Still ≥ 8 pods serving.
```
