```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api-hpa
  namespace: go-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api

  minReplicas: 3
  maxReplicas: 10

  metrics:
    # ── CPU-based scaling ──────────────────────────────────────────
    # Scales up when average CPU across pods exceeds 60% of the
    # requested 100m. This fires well before hitting the 250m limit,
    # preventing p99 tail latencies from CPU starvation.
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60

    # ── Custom metric: queue depth per pod ─────────────────────────
    # Assuming you expose a Prometheus metric like:
    #   go_api_queue_depth{namespace="go-api",pod="go-api-abc12"} = 17
    #
    # TargetAverageValue means each pod should see this value on
    # average. Set it to the concurrency limit where latency starts
    # climbing (measure with benchmarking).
    - type: Pods
      pods:
        metric:
          name: go_api_queue_depth
        target:
          type: AverageValue
          averageValue: "5"

    # ── Optional: add HTTP requests-per-second if available ───────
    # - type: Pods
    #   pods:
    #     metric:
    #       name: http_requests_total_rate
    #     target:
    #       type: AverageValue
    #       averageValue: "50"

  behavior:
    # Scale-up: aggressive — evaluate every 15s, allow scaling to
    # 2× current replicas quickly.
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Percent
          value: 100
          periodSeconds: 30
        - type: Pods
          value: 4
          periodSeconds: 30
      selectPolicy: Max           # Pick the most aggressive policy

    # Scale-down: conservative — wait 5 minutes between scaling
    # events to prevent flapping when traffic drops temporarily.
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60
      selectPolicy: Min           # Pick the gentler policy
```

**Why averageValue for custom metrics?** Because the HPA divides `sum(all pod queue depths) / replica_count`. If you have 5 pods with queue depths [2, 3, 8, 1, 6], the sum is 20, divided by 5 = average of 4. Since the target is 5, no scale-up triggers. When one pod spikes to 15 ([2, 3, 15, 1, 6]), average = 5.4 → exceeds target → HPA adds pods.

With `replicas: 3` and `minAvailable: 2`, Kubernetes allows **at most 1 pod disruption at a time**. During a node drain:

1. Kubelet signals the first pod → receives SIGTERM
2. PDB blocks eviction of a second pod until the first is fully Terminated
3. Zero risk of all-replicas dropping simultaneously

If you increase replicas to 4+, consider switching to `maxUnavailable: 1` which behaves identically but reads more clearly at higher replica counts.

## Probe Threshold Arithmetic

The three probes operate in a handoff pattern, not concurrently:

### Timeline

```
t=0s      Container starts
t=2s      First startupProbe check (initialDelaySeconds: 2)
...       Every 5s thereafter (periodSeconds: 5)
t=2s-42s  Cache warming happens inside the process
t=44s     readinessProbe returns 200 (cache warmed ≈20s, +buffer)
          ⬆ Pod added to kube-proxy endpoints — receives traffic
...
t=202s    Last possible startupProbe success (40 failures × 5s)
          ⬇ After any single success, startup probe DISAPPEARS
          
          Liveness probe activates (no overlap with startup probe)
          Periodic checks every 15s
          
          Readiness continues running independently
```

### Key Math

| Probe | Config | Effective Window | What It Catches |
|-------|--------|-----------------|-----------------|
| **startup** | `failureThreshold: 40 × periodSeconds: 5` | Up to **200s** max | Process hangs during init, slow cold-start, missing deps |
| **liveness** | `failureThreshold: 3 × periodSeconds: 15` | **45s** between consecutive failures | Deadlock, goroutine leak, perpetual error loop |
| **readiness** | `failureThreshold: 3 × periodSeconds: 5` | **15s** between consecutive failures | DB down, cache miss cascade, downstream outage |

## Probe Threshold Arithmetic

| Probe | Endpoint | Period | FailureThreshold | Effective Window | Triggered Action |
|---|---|---|---|---|---|
| `startupProbe` | `GET /health` | 2 s | 40 | **80 s** | Kills container if not alive within 80 s |
| `livenessProbe` | `GET /health` | 2 s | 3 | **6 s** | Restarts container after 6 s of unresponsiveness (deadlock/hang) |
| `readinessProbe` | `GET /ready` | 2 s | 2 | **4 s** | Removes pod from Service endpoints after 4 s of failures |

**Why these numbers:**

- **Startup: 80 s** — Your cold cache warmup takes ~20 s. The 80 s window gives a 4× safety margin for slow disk I/O, large images, or cold database connections. `failureThreshold(40) × periodSeconds(2) = 80`. If the probe succeeds even once, the startup probe disarms permanently and liveness/readiness take over.

- **Liveness: 6 s** — After startup succeeds, liveness checks for *deadlocks* or hung goroutines. Two-second polling catches hangs quickly. Three consecutive failures means the process genuinely isn't processing HTTP — restart. `3 × 2 = 6`.

- **Readiness: 4 s** — `/ready` returns 503 until `atomic.Bool` is set to `true` after cache initialization. Once warm, the pod joins endpoints immediately. On the flip side, if the pod becomes unhealthy, it's removed from endpoints within 4 s so traffic shifts to healthy pods. `2 × 2 = 4`.

**Application-side implementation:**

```go
var cacheReady atomic.Bool

func main() {
    initColdCache() // blocks ~20s until fully populated
    cacheReady.Store(true)

    mux := http.NewServeMux()
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK) // always returns 200 once process is alive
    })
    mux.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
        if !cacheReady.Load() {
            http.Error(w, "cache warming", http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    })

    srv := &http.Server{Addr: ":8080", Handler: mux}
    // register os/signal handler for SIGTERM → srv.Shutdown()
}
```

The separation is intentional: `/health` answers *"is the process alive?"* (startup+liveness). `/ready` answers *"can this pod accept traffic?"* (readiness). They are independent checks with independent failure thresholds.

### Probe Threshold Arithmetic Explained

| Probe | How It Works | Your Numbers | What It Means |
|-------|-------------|-------------|---------------|
| **startupProbe** (`tcpSocket`, `port:8080`) | Checks once every `periodSeconds`. After `failureThreshold` consecutive failures, container dies. But: **once the FIRST check succeeds**, K8s assumes startup is complete and disables the startupProbe. | `initialDelaySeconds: 5` → start checking at t=5s.<br>`periodSeconds: 3` → every 3s.<br>`failureThreshold: 40` → 40 × 3 = **120s max**. | Your Go API needs ~20s cold cache warmup. We give 120s headroom (6×). If the TCP handshake succeeds before attempt #40, startupProbe is retired and liveness/readiness take over. No race condition. |
| **livenessProbe** (`httpGet /healthz`) | Only active **after** startupProbe has succeeded. Restarts container if it fails consecutively. | `periodSeconds: 30`, `failureThreshold: 3` → 3 × 30 = **90s before restart**. | Guards against hangs/deadlocks. Won't trigger during cold-start because startupProbe shields it. |
| **readinessProbe** (`httpGet /readyz`) | Active immediately (with `initialDelaySeconds`). Removes pod from Service endpoints if it fails consecutively. Traffic stops routing but container stays alive. | `periodSeconds: 10`, `failureThreshold: 2` → 2 × 10 = **20s before drain**. | `/readyz` checks DB connectivity + whether cold cache has warmed. During those 20s the pod won't receive new traffic. Fast removal > fast re-add. |

**Key design**: By using all three probes, we eliminate the classic race condition where `livenessProbe.initialDelaySeconds` can cause a restart mid-warmup. With `startupProbe`, K8s defers liveness entirely until cold-start completes. This is the pattern recommended in the [Kubernetes docs](https://kubernetes.io/docs/concepts/workloads/pods/suspend-liveness-readiness-probes/) since 1.18.

    scaleUp:
      stabilizationWindowSeconds: 60     # Don't react to momentary spikes

        - type: Percent

        - type: Pods

| Probe | Period | Failure Threshold | Total Budget | What it controls |
|-------|--------|-------------------|--------------|------------------|
| **Startup** | 5 s | 6 | **30 s** | Prevents liveness from killing the pod during the 20 s cold-cache warmup. After 6 consecutive failures × 5 s = 30 s, Kubernetes gives up and restarts the container. Since warmup needs ~20 s, the 10 s safety margin covers GC pauses, slow DNS, etc. |

**Why two separate health paths?** The Go HTTP handler serves three routes under one server:

```go
mux.HandleFunc("/healthz/startup", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK) // alive but doesn't require warmed cache
})

mux.HandleFunc("/healthz/ready", func(w http.ResponseWriter, r *http.Request) {
    if !cache.IsReady() || pendingRequests.Load() > maxPending {
        http.Error(w, "not ready", http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
})

mux.HandleFunc("/healthz/live", func(w http.ResponseWriter, r *http.Request) {
    // simple ping that requires no lock acquisition
    w.WriteHeader(http.StatusOK)
})
```

This matters because readiness must reflect *capacity*, not just process liveness. If the cache isn't warmed or the queue is backing up, we remove the pod from rotation even though the process is fine.

### Why `averageUtilization: 60` instead of the default 80?

At p99, tail latency is dominated by scheduler-induced jitter when CPU throttles. With a 500 m request and 1 vCPU hard-limit:

- At **80% target** → scheduler allows burst to 800 m → cgroups throttle the remainder
- At **60% target** → maximum ~300 m sustained → no throttling → p99 stays flat
- The 2× headroom (`requests: 500m / limits: 1000m`) accommodates spikes without throttling because the kernel BPF scheduler can borrow up to the limit

The custom metric handles traffic bursts that arrive faster than CPU reacts (scale-up is reactive to CPU utilization over 1–3 minutes). Queue depth reacts in seconds.
