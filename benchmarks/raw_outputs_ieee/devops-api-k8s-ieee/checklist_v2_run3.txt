### 5. Deployment — Production Template

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: api-prod
  labels:
    app: api
    version: "1.0.0"
spec:
  replicas: 3                       # minReplicas enforced by HPA; this is baseline
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0             # never kill an existing pod before new one is ready
      maxSurge: 1                   # add only 1 extra pod during upgrade
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
        version: "1.0.0"
    spec:
      serviceAccountName: api-sa
      automountServiceAccountToken: false

      # Termination sequence: give pods up to 30s to finish in-flight requests.
      terminationGracePeriodSeconds: 30

      # Security hardening
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 1000
        fsGroup: 1000
      containers:
        - name: api
          image: ghcr.io/org/api:1.0.0@sha256:<digest>  # pinned immutable tag
          ports:
            - name: http
              containerPort: 3000
              protocol: TCP
            - name: metrics
              containerPort: 8080
              protocol: TCP

          # ---- Probe Threshold Arithmetic (see explanation section below) ----
          # startupProbe: covers the 20s cold cache warmup + some margin
          #   failureThreshold(30) × periodSeconds(5) = 150s budget
          #   This means: if the container hasn't started responding at all within
          #   150s, Kubernetes kills it. For most Go apps 20s warmup << 150s,
          #   so this just protects against hung Docker pulls or init deadlocks.
          startupProbe:
            httpGet:
              path: /healthz        # healthz returns 200 immediately once process boots
              port: http
            failureThreshold: 30
            periodSeconds: 5
            initialDelaySeconds: 5

          # livenessProbe: restarted only on deadlock / hang
          #   failureThreshold(3) × periodSeconds(10) = 30s
          #   After startupProbe stops firing, if /ready stops returning 200 for 30s
          #   straight, the container is considered dead and restarted.
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            failureThreshold: 3
            periodSeconds: 10
            initialDelaySeconds: 15   # brief grace period after startup probe ends

          # readinessProbe: drains traffic during warmup & deploys
          #   failureThreshold(3) × periodSeconds(5) = 15s
          #   If /ready returns non-200 for 15s consecutive checks, pod is removed
          #   from the Service endpoint → no more new requests flow here.
          #   In-flight requests keep running until TERM signal + terminationGracePeriod.
          readinessProbe:
            httpGet:
              path: /ready            # returns 200 only after cache is warm
              port: http
            failureThreshold: 3
            periodSeconds: 5
            initialDelaySeconds: 10

          # ---- Resource Sizing (avoid CPU throttling at p99) ----
          # Rule: request = expected p50–p75 usage; limit ≈ request + headroom.
          # For Go, set CPU limit high enough that GC pauses + burst paths
          # don't hit throttling under load. We recommend requests=500m, limits=1000m.
          resources:
            requests:
              cpu: "500m"
              memory: "256Mi"
            limits:
              cpu: "1000m"            # 1 core cap; monitor p99 throttle metrics
              memory: "512Mi"         # 2× request; Go's allocator overhead

          # File-mount secrets (never env vars)
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp
            - name: cache
              mountPath: /var/cache/api

      # Volumes: secrets from Secret, ephemeral scratch space
      volumes:
        - name: secrets
          secret:
            secretName: api-secrets
        - name: tmp
          emptyDir:
            sizeLimit: 100Mi
        - name: cache
          emptyDir:
            sizeLimit: 1Gi            # local cache for fast rebuild on reschedule

      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: ["api"]
                topologyKey: kubernetes.io/hostname  # spread across nodes
```

### 6. Probes — Endpoints Design

Your Go application must expose three distinct endpoints:

| Path | Returns | Purpose |
|------|---------|---------|
| `/healthz` | `200 OK` when process is alive (always available) | Liveness — "is it dead?" |
| `/ready` | `200 OK` when DB connected + cache warmed | Readiness — "can it serve?" |
| `/metrics` | Prometheus format on `:8080` | Monitoring / HPA scraping |

The critical detail: **`/ready` should return `503` during the 20s cold cache warmup**. Once warm, it returns `200`. This is what keeps traffic off pods still initializing.

```go
// Example readiness handler (Go pseudo-code)
func readyHandler(w http.ResponseWriter, r *http.Request) {
    select {
    case <-cacheWarmed:    // channel closed after 20s of loading
        w.WriteHeader(http.StatusOK)
    default:
        http.Error(w, "not ready", http.StatusServiceUnavailable)
    }
}
```

### 7. Horizontal Pod Autoscaler — CPU + Custom Metric (Queue Depth)

HPA v2 supports both traditional and custom metrics in a single policy.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
  namespace: api-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    # --- Primary: Average CPU Utilization ---
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # scale when avg CPU > 70% of requests
    # --- Secondary: Custom metric from prometheus-adapter ---
    #   Metric name on Prometheus: api_queue_depth_avg (per-pod gauge)
    - type: Pods
      pods:
        metric:
          name: api_queue_depth_avg   # custom metric exported per pod
        target:
          type: AverageValue
          averageValue: "5"            # scale if avg queue depth > 5/pod

  # Behavior: smooth scaling
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # wait 60s after last scale event
      policies:
        - type: Percent
          value: 100                    # allow doubling max
          periodSeconds: 120
        - type: Pods
          value: 4                      # or +4 pods max
          periodSeconds: 120
      selectPolicy: Max                 # take the most aggressive policy
    scaleDown:
      stabilizationWindowSeconds: 300   # 5min cooldown — prevents flapping
      policies:
        - type: Percent
          value: 25                     # remove at most 25% per interval
          periodSeconds: 120
        - type: Pods
          value: 2                      # or -2 pods per interval
          periodSeconds: 120
      selectPolicy: Min                 # take the least aggressive (safer)
```

**Why two metrics?** CPU detects general load; queue depth detects backlog specifically. When queue depth climbs while CPU is normal, it signals the bottleneck is I/O-bound (downstream calls), not compute — and HPA will scale out regardless.

### 10. PodDisruptionBudget — Protect During Node Upgrades

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
  namespace: api-prod
spec:
  minAvailable: 2               # always keep at least 2 pods running
  selector:
    matchLabels:
      app: api
```

During a voluntary disruption (node drain, cluster autoscaler downgrade), Kubernetes respects the PDB — it won't evict pods below the threshold. With `minAvailable: 2` and 3+ replicas, one node can be drained safely at a time.

If your HPA scales above 3, the PDB continues protecting 2 minimum, leaving headroom for scaling. You could alternatively use `maxUnavailable: 1` which has identical semantics when replicas ≥ 2.

## Probe Threshold Arithmetic Explained

Here is the exact timeline for a cold-starting pod:

```
Time    Event                                                    Probe State
─────────────────────────────────────────────────────────────────────────────
0s      Container starts, process boots                         startupProbe: first check pending
5s      StartupProbe fires (period=5). Process alive, /healthz → 200
10s     ReadinessProbe begins (initialDelay=10). /ready → 503 (cache warming)
15s     LivenessProbe begins (initialDelay=15). /healthz → 200 ✓
20s     Cache warms. /ready → 200 ✓                           Readiness accepts traffic
...     Normal operation                                        All 3 probes cycling
25m     Deploy starts (maxUnavailable=0, maxSurge=1)            New pod starts in parallel
...     Old pod stays in endpoints until new pod hits /ready    Zero dropped requests
```

**Key math:**

| Probe | Formula | Budget | What it catches |
|-------|---------|--------|----------------|
| startup | `failureThreshold(30) × periodSeconds(5)` | **150s** | Docker pull hangs, init deadlocks, catastrophic boot failures |
| liveness | `failureThreshold(3) × periodSeconds(10)` | **30s** | Deadlocked process, unresponsive goroutines |
| readiness | `failureThreshold(3) × periodSeconds(5)` | **15s** | Temporarily unavailable (DB disconnect, cache miss spike) |

**Why separate `/healthz` (liveness) and `/ready` (readiness)?** A process can be alive but unable to serve — e.g., database connection pool exhausted, cache needs warming, dependency unavailable. Liveness says "alive." Readiness says "can handle traffic." Never merge them.

**Why `startupProbe` exists:** Without it, Kubernetes would start the liveness probe too early and restart a legitimately slow-starting container before it finishes booting. The startupProbe disables the liveness/restart logic until it succeeds, then hands off.

## Zero-Drop Termination Drain Sequence

Here is exactly what happens during a rolling deploy with `maxUnavailable: 0`:

```
Phase 1: Scaling Up
───────────────────
1. RollingUpdate creates a new ReplicaSet with 1 extra pod (maxSurge=1)
2. New pod starts → startupProbe fires → container boots
3. ReadinessProbe fires → /ready returns 503 (cache warming) → pod REMOVED from Service endpoints
4. No new traffic flows to the new pod yet (correct behavior)

Phase 2: Cache Warm-up
──────────────────────
5. New pod loads cache for ~20s → /ready → 200
6. ReadinessProbe sees success → pod ADDED to Service endpoints → NEW traffic starts flowing
7. Service now serves from BOTH old and new pods (round-robin at kube-proxy level)

Phase 3: Terminating Old Pod
────────────────────────────
8. Deployment strategy: maxUnavailable=0 blocks deletion of old pod until new one is ready
9. Kubernetes sends SIGTERM to the old pod's container
10. Go application receives SIGTERM → stopHTTPServer():
    a. Close listener (stop accepting NEW connections)
    b. Create context with 30s timeout (matches terminationGracePeriodSeconds)
    c. GraceShutdown(context.WithTimeout) → waits for in-flight requests to complete,
       or cancels after 30s if any hang
11. ReadinessProbe fails (server stopped) → pod removed from endpoints
    BUT: all in-flight requests already received responses (step 10b)

Phase 4: Cleanup
────────────────
12. After in-flight requests drain or 30s elapses, container stops
13. Pod transitions to Terminated → deleted
14. New pod handles all traffic (now at 100%)
15. Old ReplicaSet cleaned up
```

**Critical: Your Go server MUST implement graceful shutdown:**

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    srv := &http.Server{Addr: ":3000"}

    go func() {
        if err := srv.ListenAndServe(); err != http.ErrServerClosed {
            log.Fatalf("listen: %v", err)
        }
    }()

    // Graceful shutdown on SIGTERM/SIGINT
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)
    sig := <-quit

    log.Printf("received %s, shutting down gracefully", sig)

    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    if err := srv.Shutdown(ctx); err != nil {
        log.Fatalf("server forced to shutdown: %v", err)
    }

    log.Println("server exiting")
}
```

Without this pattern, `maxUnavailable: 0` is meaningless — if the container dies without draining, requests get dropped regardless of deployment strategy.

## Resource Sizing Rationale

For a Go API targeting p99 latency without CPU throttling:

| Metric | Value | Why |
|--------|-------|-----|
| CPU Request | 500m | Guarantees 0.5 core consistently. Go's scheduler is work-stealing — predictable CPU scheduling prevents goroutine starvation under contention. |
| CPU Limit | 1000m | 1 core ceiling. Go's runtime throttles to this limit. At p99 load, occasional bursts above p50 are fine as long as total doesn't exceed 1 core. |
| Memory Request | 256Mi | Baseline for Go binary + dependencies + heap. |
| Memory Limit | 512Mi | 2× request. Go's memory allocator over-commits (~20-40% overhead). OOMKilled at 512Mi is cleaner than throttled p99 latency spikes. |

**Rule:** Requests define what gets scheduled. Limits define what gets throttled/killed. Set limits 2-4× requests for web APIs. Workers get tighter ratios since their load is more predictable. Monitor `rate(container_cpu_throttled_seconds_total[5m])` on Prometheus — if it climbs above 0.1s/s, increase limits.
