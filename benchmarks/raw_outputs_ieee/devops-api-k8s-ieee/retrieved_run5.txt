## Resource sizing rationale (Go API)

| Workload | Request CPU | Limit CPU | Request Mem | Limit Mem | Why |
|-----------|-------------|-----------|-------------|-----------|-----|
| Go HTTP/API | `100m` | `500m` | `128Mi` | `256Mi` | Go has ~10-30MB base + heap growth. `100m` request guarantees headroom; `500m` limit allows burst without starving other pods on the node. If your p99 tail latency is still >400ms under load, bump limit to `750m-1000m` — but start conservatively so the scheduler packs pods efficiently.

## Deployment (`deployment.yaml`)

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: go-api
  namespace: production
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: go-api
  namespace: production
rules: []                     # No API-server access needed for a stateless API
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: go-api
  namespace: production
subjects:
  - kind: ServiceAccount
    name: go-api
roleRef:
  kind: Role
  name: go-api
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-api
  namespace: production
spec:
  replicas: 3                 # HPA will scale 3→10
  selector:
    matchLabels:
      app: go-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0       # Never terminate a pod until a replacement is Ready
      maxSurge: 1             # Add one extra pod during each rollout wave
  template:
    metadata:
      labels:
        app: go-api
    spec:
      serviceAccountName: go-api
      terminationGracePeriodSeconds: 60   # Graceful-drain window (see §Drain Sequence)
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 1000
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: go-api
          image: registry.internal/go-api:v1.2.3
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP

          # ── Probes (§ Probe Arithmetic) ──────────────────────────────
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 10
            failureThreshold: 30    # 30 × 10s = 300s budget (warm cache ≤ 20s → comfortable margin)
            successThreshold: 1     # One quick pass is enough to declare healthy
            failureCountReset: true

          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3     # 3 failures = potentially stuck; restart the pod

          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 25
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 3     # 3 consecutive misses → remove from service endpoints

          # ── Resources (§ Sizing) ─────────────────────────────────────
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"

          # ── Environment (non-secret config from ConfigMap) ────────────
          envFrom:
            - configMapRef:
                name: go-api-config

          # ── Secrets mounted as files (NOT env vars) ──────────────────
          volumeMounts:
            - name: secrets
              mountPath: /secrets
              readOnly: true
          volumes:
            - name: secrets
              projected:
                sources:
                  # ExternalSecret controller syncs these into temp dir;
                  # replace with your actual ExternalSecret or CSI secret driver.
                  - secret:
                      name: go-api-secrets
                      items:
                        - key: api-key
                          path: api-key
                        - key: db-password
                          path: db-password
                        - key: tls-cert
                          path: tls.crt
                        - key: tls-key
                          path: tls.key
```

### Key points in the Deployment

- **`maxUnavailable: 0` + `terminationGracePeriodSeconds: 60`** guarantees zero dropped requests during rolling updates — K8s won't kill the old pod until a new one passes its readiness check, and the old pod gets a full 60s SIGTERM-to-SIGKILL window to finish in-flight handlers.
- **`securityContext`** enforces non-root, applies `RuntimeDefault` seccomp, and sets filesystem group for clean secret-file permissions.
- **Projected volumes** for secrets means they appear as regular files (`/secrets/api-key`, `/secrets/db-password`, etc.), avoiding env-var exposure in `kubectl describe pod`, debugger output, or log leakage.

## HPA (`hpa.yaml`)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70       # Scale up when average CPU > 70%
    - type: Pods                       # Custom metric via Prometheus Adapter
      pods:
        metric:
          name: queue_depth_per_pod     # e.g. histogram of pending requests / pod count
        target:
          type: AverageValue
          averageValue: "5"           # Scale up when avg queue depth > 5 per pod
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0   # React immediately to load spike
      policies:
        - type: Pods
          value: 2                    # Allow adding up to 2 pods per stabilization period
          periodSeconds: 60
        - type: Percent
          value: 100                  # Or 100% of current replicas, whichever is more restrictive
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300 # Don't thrash — wait 5 minutes after last scale-down trigger
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120
```

### HPA tuning notes

- **CPU target 70%** leaves headroom for traffic bursts without over-provisioning.
- **Custom `queue_depth_per_pod`** metric gives you fine-grained control — if the app exposes a Prometheus histogram of in-flight/pending requests, the adapter surfaces it here. This often scales better than CPU alone because it predicts demand *before* CPU spikes.
- **`scaleDown.stabilizationWindowSeconds: 300`** prevents rapid scale-down/scale-up oscillation (thrashing) when traffic dips briefly.
- **`scaleUp.stabilizationWindowSeconds: 0`** ensures immediate reaction to sudden traffic surges — you don't want to wait 300s before scaling up.

## PDB (`pdb.yaml`)

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: go-api
  namespace: production
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: go-api
```

### PDB logic

During a node drain (upgrade, spot interruption, maintenance), the disruption controller calculates:

```
max_unavailable_during_drain = min(replicas - minAvailable, max(PDB allows))
                            = min(3 - 2, ∞)
                            = 1
```

So only **one pod at a time** can be voluntarily disrupted. The remaining **2+ pods always stay running**, meaning clients never lose all backends. With 5–10 replicas (HPA-scaled), you could lower `minAvailable` if desired, but keeping it at 2 guarantees baseline capacity even at minimum replica count.

## § Probe Threshold Arithmetic

This decision table drives every probe's parameters:

| Probe | Purpose | When to act | Math → Budget |
|-------|---------|-------------|---------------|
| **Startup** | App + cold-cache warmup (≤20s). Prevents liveness from killing the pod during bootstrap. | Restart ONLY if the pod hasn't passed `/healthz` within the budget. | `failureThreshold × periodSeconds = 30 × 10s = 300s`. The 20s warmup fits with 15× margin. After success, liveness/readiness take over. |
| **Liveness** | Detect hangs / goroutine leaks / deadlocks where the process still responds to some endpoints but is fundamentally broken. | Kill & restart if no response to `/healthz` for 3 consecutive checks. | `failureThreshold × periodSeconds = 3 × 10s = 30s`. Fast enough to unstick a hung process, slow enough to ignore brief network blips. |
| **Readiness** | Remove unhealthy pods from Service load-balancing so in-flight requests route to healthy pods. | Stop sending new traffic if `/readyz` fails 3 times in a row. | `failureThreshold × periodSeconds = 3 × 5s = 15s`. Quicker feedback than liveness — traffic shifts away faster than we kill the pod. |

### Critical distinction

- **Readiness fails first** (15s) → pod removed from Service endpoints → no new requests sent → connection drains gracefully → *then* liveness may fire (30s later) if the pod is truly broken.
- **Startup probe blocks liveness entirely** until it succeeds. During the 20s cold cache window, liveness doesn't count against it. This is why `initialDelaySeconds` on liveness would NOT work correctly — the startup probe approach is the modern, reliable pattern.

## § Zero-Drop Drain Sequence

When `kubectl rollout restart` or a deployment update runs, here's exactly what happens with `maxUnavailable: 0`:

```
Time  Event                              What K8s does
─────────────────────────────────────────────────────────────────────
T=0   Rollout starts                     Creates ReplicaSet v2, starts Pod v2a
T=0+5s Pod v2a passes readiness           Adds v2a to Service endpoints
T=5   Load balancer shifts               New traffic → v2a, existing → v1a
T=5+  (repeat for v2b, v2c…)            Each new pod must pass readiness
                                         before any old pod is terminated
T=N   All old pods terminating           K8s sends SIGTERM to v1a/v1b/v1c
T=N   SIGTERM received                   Go handler: stop accepting new reqs,
         [60s window]                     finish current in-flight requests
         ┌─────────────────────┐
         │ In-flight: OK ✓✓✓   │ ← Completes normally
         │ Pending: dropped    │ ← None exist (readiness blocked them)
         └─────────────────────┘
T=N+60  SIGKILL (only if graceful fails)  Rare edge-case; usually not reached
T=N+60  Old ReplicSet deleted            Cleanup complete, rollout finished
```

**Why zero requests drop:**

1. `maxUnavailable: 0` → old pod stays alive until replacement is ready.
2. Readiness gate → new pod joins the Service only after it can serve real traffic.
3. 60s `terminationGracePeriodSeconds` → old pod finishes existing requests. Since no new traffic routes to it (it's being drained by the load balancer updating endpoint slices), there are **zero pending requests** waiting at SIGTERM time — only completing in-flight ones.
4. Proper Go HTTP server shutdown: call `srv.Shutdown(ctx)` with a 60s context deadline, which stops accepting new connections but completes ongoing ones.
