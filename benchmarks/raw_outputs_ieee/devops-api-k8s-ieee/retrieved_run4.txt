## 1. Deployment

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: go-api-sa
  namespace: production
automountServiceAccountToken: false
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-api
  namespace: production
  labels:
    app: go-api
    version: "1.0.0"
spec:
  replicas: 3
  selector:
    matchLabels:
      app: go-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       1        # one extra pod above desired count during update
      maxUnavailable:  0        # never drop below desired count — zero downtime
  template:
    metadata:
      labels:
        app: go-api
        version: "1.0.0"
    spec:
      serviceAccountName: go-api-sa
      automountServiceAccountToken: false

      # --- Graceful shutdown budget ---
      # 0s means "use system default (10s)" — we override this to 30s so
      # SIGTERM → shutdown has enough time to drain in-flight requests.
      terminationGracePeriodSeconds: 30

      securityContext:
        runAsNonRoot:  true
        runAsUser:     1001
        fsGroup:       1001

      containers:
        - name: go-api
          image: ghcr.io/org/go-api:v1.0.0   # pinned — no :latest
          imagePullPolicy: IfNotPresent

          ports:
            - containerPort: 8080
              protocol: TCP

          # --- Resources (see Section 5 for sizing rationale) ---
          resources:
            requests:
              cpu:    "200m"      # ~20% of a core — sets minimum guaranteed
              memory: "256Mi"
            limits:
              cpu:    "500m"      # cap at half a core — avoids noisy neighbours
              memory: "512Mi"

          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem:  true
            capabilities:
              drop: [ALL]

          # =====================================================================
          # PROBE ARITHMETIC — see Section 4 for full explanation
          # =====================================================================

          startupProbe:
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 10      # ← key number
            periodSeconds:    5       # 10 × 5s = 50s total startup window
                                      # covers 20s cache warmup + buffer

          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 0    # start checking immediately after startupProbe passes
            periodSeconds:     10
            failureThreshold:  3      # 3 × 10s = 30s before restart

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds:     5
            failureThreshold:  2      # 2 × 5s = 10s before removed from endpoints

          envFrom:
            - configMapRef:
                name: go-api-config

          # Secrets as files (not env vars)
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp
            - name: cache
              mountPath: /var/cache/go-api   # ephemeral cache store

      volumes:
        - name: secrets
          secret:
            secretName: go-api-secrets
        - name: tmp
          emptyDir: {}
        - name: cache
          emptyDir:
            sizeLimit: 1Gi               # bounded local cache; evicts under pressure
```

## 2. HorizontalPodAutoscaler (HPA) — CPU + Custom Queue Depth

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api

  minReplicas: 3
  maxReplicas: 10

  metrics:
    # ── Metric 1: CPU utilization ────────────────────────────────────
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60    # scale up when avg pod CPU > 60%
                                    # lower than default (70%) because
                                    # Go + gRPC/HTTP needs headroom at p99

    # ── Metric 2: Custom metric — queue depth (prometheus-adapter) ──
    - type: Pods
      pods:
        metric:
          name: queue_depth_per_pod    # must expose gauge per-pod
        target:
          type: AverageValue
          averageValue: "5"            # scale up when avg queued jobs/pod > 5
```

**Prerequisites for custom metrics:**

```bash
# 1. Install prometheus-adapter (or equivalent)
kubectl apply -f https://github.com/kubernetes-sigs/prometheus-adapter/releases/download/v0.11.0/artifacts.yaml

# 2. In your Go app, export via Prometheus /metrics endpoint:
#    queue_depth_per_pod (gauge) — current pending jobs per pod
#    prometheus-adapter maps this to the HPA queryable metric name.
```

## 3. PodDisruptionBudget (PDB)

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: go-api-pdb
  namespace: production
spec:
  minAvailable: 2           # keep at least 2 pods available during drains
                            # OR use maxUnavailable: 1 if cluster is large
  selector:
    matchLabels:
      app: go-api
```

**Behavior:** When `replicas=3`, the PDB allows only 1 pod to be disrupted at a time (3−2=1). When scaled to 10, it still protects 2 minimum regardless. This guarantees availability during node upgrades, autoscaler scale-downs, and maintenance windows.

## 4. Probe Threshold Arithmetic Explained

### Startup Probe — covering the 20-second cold cache warmup

```
failureThreshold × periodSeconds ≥ cold_warmup_seconds + safety_buffer
10         × 5             = 50 seconds
                          ≈ 20s warmup + 30s buffer
```

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `path` | `/health` | Lightweight; does NOT check cache status (liveness-safe) |
| `periodSeconds` | 5 | Check every 5 seconds — reasonable for HTTP |
| `failureThreshold` | 10 | Allows 50 seconds of total startup time |
| **Effective window** | **50s** | 20s cold cache + 30s operational margin |

**Why this matters:** Without a startup probe, Kubernetes would start the liveness probe immediately (after its own `initialDelaySeconds`). If the liveness probe fires while the process is still initializing, it could see a transient failure and kill the container — restarting it before the cache had warmed. The startup probe *disables* the liveness probe entirely until it succeeds. Once `/health` returns 200 for 10 consecutive checks, the startup phase is done and liveness takes over.

### Liveness Probe — detecting hung processes

```
failureThreshold × periodSeconds = restart_delay
3      × 10              = 30 seconds
```

After startup completes, the liveness probe fires every 10 seconds. Three failures in a row (30s) means the process is genuinely stuck (not just slow), and K8s restarts it. `initialDelaySeconds: 0` is safe here because the startup probe gates it.

### Readiness Probe — controlling traffic flow

```
failureThreshold × periodSeconds = removal_delay
2      × 5               = 10 seconds
```

During deployment or cache miss, the readiness probe removes the pod from Service endpoints within 10 seconds, preventing new requests from routing to a pod that can't serve yet. It uses `/ready` (a separate endpoint) that checks whether the cache has finished warming — unlike `/health` which only confirms the process is alive.

**Complete lifecycle timeline:**

```
T=0s      Container starts
T=0–50s   startupProbe: POSTPONED (liveness probe blocked)
T=20s     Cache warmup finishes (internal to app)
T=20–50s  /health starts returning 200 consistently
T=~25s    startupProbe succeeds (5th check) → liveness gate lifted
T=25s+    livenessProbe & readinessProbe both active
T=25–30s  readinessProbe: /ready returns 200 → added to endpoints
T=30s     Fully serving traffic
```

## 5. Resource Sizing Rationale (Avoiding CPU Throttling at p99)

| Parameter | Value | Why |
|-----------|-------|-----|
| CPU request | 200m | Guarantees 0.2 cores — sufficient baseline for Go's low idle footprint (~10–20m) plus request handling |
| CPU limit | 500m | 2.5× request ratio — gives burst capacity for traffic spikes but caps runaway threads. Go's GIL-like scheduler rarely needs more than 2 cores, and p99 latencies stay stable at 500m |
| Memory request | 256Mi | Go binaries are statically linked; runtime overhead is ~50–80m RSS. 256Mi covers heap + GC + goroutine stacks comfortably |
| Memory limit | 512Mi | 2× request — leaves room for GC bursts without triggering OOMKill |

**Key rule:** Requests are what the HPA reads (`current/request`) to compute utilization. Higher requests mean the HPA triggers scaling sooner (lower actual CPU). We keep requests modest relative to limits so the HPA scales *before* CPU contention hurts p99 tail latency.

## 6. Zero-Dropped-Requests Termination Sequence

This is what happens from `kubectl rollout deploy` (or an upgrade) to old pods going away:

```
┌──────────────────────────────────────────────────────────────┐
│  ROLLING UPDATE TRIGGERS                                     │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│  1. NEW pod starts (maxSurge=1)                             │
│     startupProbe blocks readiness                           │
│     New pod cannot receive traffic                          │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│  2. Old pod signals:                                         │
│     readinessProbe fails (/ready returns non-200)            │
│     → Kubernetes removes pod from Service endpoint IP list   │
│     → NO NEW requests routed to this pod                     │
│     → Existing in-flight requests continue                   │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│  3. New pod becomes ready (/ready returns 200)               │
│     → Added to Service endpoints                             │
│     → Traffic shifts gradually as connections rotate         │
└──────────────────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────────────────┐
│  4. SIGTERM sent to old pod                                  │
│     terminationGracePeriodSeconds=30                         │
│     → App receives signal at T=0                              │
│     → Stop accepting new connections                         │
│     → Drain existing requests (up to 30s)                    │
│     → Close listeners                                          │
│     → Shutdown gracefully                                      │
│     → Exit code 0 at T≤30                                     │
└──────────────────────────────────────────────────────────────┘
```

**Go-side implementation pattern:**

```go
// Minimal graceful shutdown handler
shutdownCtx, shutdown := context.WithTimeout(context.Background(), 25*time.Second)
defer shutdown()

signalCh := make(chan os.Signal, 1)
signal.Notify(signalCh, syscall.SIGTERM)

// Block until SIGTERM
<-signalCh

log.Info("SIGTERM received, draining...")
srv.Shutdown(shutdownCtx) // stops accepting, waits for in-flight to finish
```

**How each piece contributes to zero drops:**

| Piece | Role |
|-------|------|
| `maxUnavailable: 0` | Never kills old pods until new ones are ready |
| `readinessProbe` failure | Immediate endpoint removal — traffic stops routing before shutdown begins |
| `terminationGracePeriodSeconds: 30` | Gives the app time to finish in-flight requests (20s warmup ≠ shutdown time; shutdown depends on concurrent active requests, typically < 10s for Go) |
| `PDB minAvailable: 2` | Even during node drains, 2 pods survive to handle traffic |
| `maxSurge: 1` | One extra pod exists during the transition to absorb traffic from draining pods |
