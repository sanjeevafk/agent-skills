## § PROBE ARITHMETIC DERIVATION

### Startup Probe — covers the 20s cache-warm window

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `path` | `/healthz` | Returns 200 as soon as the HTTP server binds (no cache dependency) |
| `failureThreshold` | 30 | Conservative safety margin |
| `periodSeconds` | 6 | Aggressive-enough polling, conservative enough to not hammer |
| **Total budget** | **30 × 6 = 180s** | Enough time for: process init (~5s) + bind (~1s) + cold cache warmup (~20s) + safety headroom (154s) |

**Why 6s interval, not 1s?** A 1s interval would give 120 polls — excessive API calls during startup and wastes kubelet cycles. With a 20s warmup and 30-threshold, 6s already provides 180s of budget which is 9× the warmup time.

**What happens if it succeeds early?** After the first successful `/healthz` check, the startup probe is considered passed and is permanently disabled for the container's lifetime. Liveness/readiness take over immediately.

### Liveness Probe — detects hangs, not slow starts

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `initialDelaySeconds` | 15 | Overlap with late stage of startup probe; avoids race |
| `periodSeconds` | 10 | Moderate frequency — Go's scheduler makes 10s plenty responsive |
| `failureThreshold` | 3 | 3 consecutive misses = container truly hung |
| **Real-time trigger** | **15 + 3×10 = 45s** | Minimum wall-clock time before first possible restart |

**Key decision:** `initialDelaySeconds: 15` means the liveness probe starts checking at t=15s. Before that, only the startup probe governs. If the cache finishes warming at t=20s and the app begins serving, liveness will see healthy responses at t=20+ and continue normally. No restart ever occurs during normal boot.

### Readiness Probe — gate traffic until warmed

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `path` | `/readyz` | Returns 503 while cache warming, 200 once warmed |
| `initialDelaySeconds` | 10 | Start checking slightly before cache should be warm |
| `periodSeconds` | 5 | Quick feedback loop — lose traffic after at most 10s |
| `failureThreshold` | 2 | 2 consecutive misses → remove from endpoints quickly |

**Endpoint behavior during warmup:**

```
t=0s    Container starts
t=5s    /healthz → 200  (startup probe passes individual polls)
t=15s   /healthz → 200  (liveness probe starts)
t=18s   /readyz → 503   (cache not yet warm → NOT added to endpoints)
t=22s   /readyz → 200   (cache warmed → ADDED to endpoints, receives traffic)
```

Your Go `/readyz` handler should track cache-warm status:
```go
var cacheWarmed atomic.Bool

// After cache population completes:
cacheWarmed.Store(true)

http.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
    if !cacheWarmed.Load() {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
})
```

### Summary timeline

```
Phase          | Probe Governing    | Traffic?
---------------|-------------------|----------
t=0–180s       | startupProbe       | No (/readyz returns 503)
t≥180s         | liveness+readiness | Yes (if ready)
Normal runtime | liveness+readiness | Yes
Container hang | liveness fires     | Removed by readiness, then restarted
```

## § GRACEFUL TERMINATION / DRAIN SEQUENCE

### How Kubernetes triggers the drain

```
1. kubelet initiates pod deletion (SIGTERM)
   ↓
2. Pod status transitions: Running → Terminating
   ↓
3. Service endpoints controller removes pod IP from all Services
   ↓
4. Ingress/Nginx picks up endpoint changes (~0-2s propagation)
   ↓
5. Readiness probe starts failing (app signals unavailability)
   ↓
6. App finishes in-flight requests
   ↓
7. terminationGracePeriodSeconds expires → SIGKILL
```

### What your Go app must do

```go
func setupShutdown(sigChan chan os.Signal) {
    sigChan = make(chan os.Signal, 1)
    signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)

    go func() {
        <-sigChan  // receives SIGTERM from kubelet

        // Step 1: Stop accepting NEW connections
        // (Set listener deadline, reject new accepts)
        srv.Shutdown(context.Background())

        // Step 2: Wait for in-flight requests to complete
        // (Use a sync.WaitGroup or context with deadline)
        doneCh := make(chan struct{})
        go func() {
            wg.Wait()
            close(doneCh)
        }()

        select {
        case <-doneCh:
            log.Info("drained")
        case <-time.After(30 * time.Second):
            log.Warn("drain timeout, forcing shutdown")
        }
    }()
}
```

### Why the numbers matter

| Resource | Value | Justification |
|----------|-------|---------------|
| `terminationGracePeriodSeconds` | 45s | 30s graceful drain + 15s headroom for edge cases (network partition mid-shutdown, stuck goroutines) |
| `maxUnavailable` (Deployment) | 0 | Never reduce replica count below desired. Combined with PDB `minAvailable: 2`, ensures no pod removal unless replacement is Ready |
| `minReadySeconds` | 5s | After new pod is Ready, wait 5s before K8s considers the rollout step stable (gives health checks to stabilize) |
| `minAvailable` (PDB) | 2 | During node drain/upgrade, allows at most `replicas - 2` voluntary disruptions. At 3 replicas = 1 at a time |

### End-to-end rollout scenario

```
Before rollout:  [pod-A] [pod-B] [pod-C]  (all healthy, serving traffic)
                 ↑
                 3 endpoints in Service

Rollout starts (new image v1.2.4):
  [pod-A] [pod-B] [pod-C] [NEW:starting...]
                    ↑
                  maxSurge=1 allows this extra pod

  NEW pod passes startup → readiness → becomes endpoint
  [pod-A] [pod-B] [pod-C] [NEW:READY]
                         ↑
                  4 endpoints now serving

  kubelet SIGTERM on pod-A → readiness fails → removed from endpoints
  [pod-A:terminating] [pod-B] [pod-C] [NEW:READY]
                                  ↑
                          3 endpoints, traffic flows through B,C,NEW

  pod-A finishes draining (≤45s), container dies
  [pod-B] [pod-C] [NEW:READY]
          ↑
          3 endpoints, at min-replica threshold

  maxUnavailable=0 allows next old pod to terminate
  (repeat for pod-B, then pod-C)

  Final state: 3 pods with v1.2.4
```

**Zero dropped requests achieved because:**
1. New pod adds endpoint BEFORE old pod removes it (`maxUnavailable: 0`)
2. Service endpoints controller updates iptables/IPVS rules atomically
3. Readiness gate ensures no unready pod receives traffic
4. App-level graceful shutdown drains in-flight requests within the 45s window
