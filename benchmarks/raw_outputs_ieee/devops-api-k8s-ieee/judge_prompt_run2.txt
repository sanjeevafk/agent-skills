## Probe Threshold Arithmetic

```
startupProbe:
  failureThreshold: 10 × periodSeconds: 2 = 20 seconds total budget
  → Container MUST be passing /health within 20s.
  → This covers the 20s cold-cache warmup exactly. Anything slower = container killed.
  → Once one check passes, startupProbe is "successful" and DISABLED forever.

livenessProbe (only active AFTER startupProbe succeeds):
  failureThreshold: 2 × periodSeconds: 15 = 30 seconds before restart
  → If the app deadlocks at t=300s, the liveness probe won't kill it for another 30s.
  → initialDelaySeconds: 0 is safe because startupProbe was already guarding the start.
  → This is NOT a race condition: Kubernetes does NOT run both probes simultaneously.

readinessProbe (active from start, independent of startup):
  failureThreshold: 1 × periodSeconds: 5 = 5 seconds removal latency
  → Returns 200 ONLY when /ready confirms the cache warm-up loop completed.
  → Before warmup finishes, readiness fails → pod removed from Service endpoints →
    zero in-flight requests routed to an unready pod.
  → During drain, /ready starts returning 503 → rapid endpoint removal → zero drops.
```

Key distinction: `startupProbe` prevents premature liveness kills during warmup. `readinessProbe` controls whether the pod receives traffic (endpoint membership). They serve entirely different purposes — startup is about *container lifecycle*, readiness is about *traffic gating*.

This works end-to-end through coordinated probe timing and deployment strategy:

```
t=0: kubectl rollout restart or image update triggers RollingUpdate

┌───────────────────────────────────────────────────────────────┐
│ ROLLING UPDATE PHASE                                           │
│                                                               │
│ 1. maxUnavailable=0 means old pods stay RUNNING until         │
│    the replacement pod passes BOTH startup + readiness probes │
│                                                               │
│ 2. Replacement pod: startupProbe runs (≤20s for warmup)       │
│    → readinessProbe FAILS during warmup (cache not ready)     │
│    → replacement NOT added to Service endpoints               │
│    → ALL traffic continues to old pods                        │
│                                                               │
│ 3. After warmup completes, readinessProbe passes (200)        │
│    → replacement enters endpoints                             │
│    → OLD pod is then terminated                               │
│                                                               │
│ Result: Zero dropped requests throughout deploy                │
└───────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────┐
│ SHUTDOWN DRAIN SEQUENCE                                        │
│                                                               │
│ t=0ms:   Kubelet sends SIGTERM to main process                 │
```

### Probe Threshold Arithmetic

Your service has a **20-second cold cache warmup**. Here's how each probe works together:

| Probe | What It Does | Why It Works For This Case |
|-------|-------------|--------------------------|
| `startupProbe` | Tells K8s "don't apply other probes until this succeeds" | Covers the entire cold-start phase including 20s cache warmup. Once it fires successfully, K8s considers the container started and stops killing it for startup failures. |
| `livenessProbe` | Restarts the container if unresponsive | Only runs after startupProbe passes. Detects deadlocks or hung goroutines, not slow starts. |
| `readinessProbe` | Removes/adds pod from Service IP tables | Probes `/ready`. Returns 200 only when the hot cache is populated. K8s won't route traffic until ready. |

**Startup probe timing:**

```
failureThreshold × periodSeconds = total startup budget
30 × 10s                           = 300s (5 minutes)
```

This gives you 5 minutes of leeway. The cold cache warmup is 20s, but the HTTP handler might be slow initially because every request triggers a DB fetch until the cache fills. A generous threshold like this lets the first batch of in-flight requests succeed while the warmup completes. After the first successful response, startupProbe stops checking entirely.

If you want tighter control (e.g., 60s instead of 300s):

```yaml
# 10 × 6s = 60s — tight but safe for a well-behaved Go binary
startupProbe:
  httpGet:
    path: /health          # Always returns 200 even during warmup
    port: 8080
  failureThreshold: 6
  periodSeconds: 10
```

**Liveness probe timing:**

```
failureThreshold × periodSeconds = time before restart
3 × 10s                        = 30s — aggressive enough to catch hangs
```

A single second of latency in a health check is fine. Only three consecutive failures trigger a restart, preventing false positives from brief GC pauses or lock contention.

**Readiness probe timing:**

```
failureThreshold × periodSeconds = time without endpoints
2 × 15s                        = 30s — removes pod from Service if /ready fails twice consecutively
```

During a rolling deploy, the new pod's readiness stays negative until its own 20s cache warms. Meanwhile the old pods continue serving. When the new pod becomes ready, traffic shifts automatically.

## Probe Threshold Arithmetic Explained

Three phases, each with its own probe:

| Phase | Probe | Max Duration | What It Guards |
|-------|-------|-------------|----------------|
| Cold start (0–40s) | **startupProbe** | `40 × 1s = 40s` | Container dies if it hasn't passed `/health` within 40s |
| Deadlock detection (post-warmup) | **livenessProbe** | `3 × 10s = 30s` per check window | Container killed after 3 consecutive missed checks |
| Endpoint routing | **readinessProbe** | `2 × 5s = 10s` per check window | Pod removed from Service endpoints |

**Timeline for cold start:**

```
t=0      Process starts, opens listeners
t=2      Startup probe first attempt
t=2–22   Cache warms in background (POST /cache/warm or lazy-loading)
t=22     /health returns 200 (cache warmup done)
t=22–40  Startup probe succeeds → livenessProbe becomes active at t=45
t=45     Liveness probe begins (initialDelaySeconds ensures we're past worst-case warmup)
t=55     Readiness probe begins (slightly earlier to confirm traffic routing)
t=55+    Normal operations: /healthy every 10s, /ready every 5s
```

Key insight: **Do not use `initialDelaySeconds` on livenessProbe alone.** Without a startupProbe, a pod that takes 30s to warm would get killed by liveness after `initialDelaySeconds` expires mid-warmup. The startupProbe gives deterministic bound (`failureThreshold × periodSeconds`), and livenessProbe starts *after* that window closes (`initialDelaySeconds > startup total`).
