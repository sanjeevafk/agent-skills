## 4. Core Workload — Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: api-production
  labels:
    app: api
    version: "2.1.0"
spec:
  selector:
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0          # never drop traffic during rollout
      maxSurge: 1                # add exactly one extra pod, then remove old
  # --- replica count left unset; HPA controls it ---

  template:
    metadata:
      labels:
        app: api
        version: "2.1.0"
    spec:
      serviceAccountName: api-sa
      automountServiceAccountToken: false

      # Graceful shutdown budget — must exceed PreStop sleep
      terminationGracePeriodSeconds: 30

      containers:
        - name: api
          image: ghcr.io/org/api:2.1.0       # NEVER :latest
          imagePullPolicy: IfNotPresent

          ports:
            - name: http
              containerPort: 8080
              protocol: TCP

          # ---- Environment from ConfigMap (non-secret only) ----
          envFrom:
            - configMapRef:
                name: api-config

          # ---- Resource sizing: no p99 CPU throttling ----
          # Request = sustainable baseline; limit = burst ceiling
          resources:
            requests:
              cpu: "250m"           # ~1/4 core guaranteed → p50 sustained load
              memory: "256Mi"       # Go runtime is lean; this covers GC overhead
            limits:
              cpu: "1000m"          # 1 full core burst cap — prevents noisy neighbor
              memory: "512Mi"       # 2× request for burst / GC pauses

          # ---- Security Context ----
          securityContext:
            runAsNonRoot: true
            runAsUser: 65534        # nobody
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL

          # ---- Probes ----
          startupProbe:
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 40     # critical: 40 * 2s = 80s total startup window
            periodSeconds: 2         # polls every 2s during cold start
            # After 80s without success → restart
            # Covers: binary load + DB connect + 20s cache warmup + margin

          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5   # don't probe until past startup phase
            periodSeconds: 5
            failureThreshold: 3      # 3 failures = 15s → kills & restarts
            timeoutSeconds: 3        # per-request timeout (don't wait forever)

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
            successThreshold: 1      # recover immediately when /ready returns 200
            timeoutSeconds: 3

          # ---- Secret volume mounts (file-based, not env vars) ----
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp

        - name: secrets
          secret:
            secretName: api-secrets
        - name: tmp
          emptyDir: {}               # scratch space for temp files

      # ---- Anti-affinity: spread pods across nodes ----
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:

│                                                             │

┌─────────────────────────────────────────────────────────────┐

│                                                             │

## 6. Horizontal Pod Autoscaler — CPU + Custom Queue Depth

```yaml
# deploy/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
  namespace: api-production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 3
  maxReplicas: 10

  metrics:
    # Primary: CPU utilization across pods
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65

    # Secondary: Custom metric from application — queue depth
    # Requires Prometheus Adapter exposing the metric
    # Metric name format: api_queue_depth_per_pod (histogram/gauge summed per-pod)
    - type: Pods
      pods:
        metric:
          name: api_queue_depth_per_pod
        target:
          type: AverageValue
          averageValue: "50"

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0     # react immediately to load spikes
      policies:
        - type: Percent
          value: 100                     # can add up to 100% of current replicas per period
          periodSeconds: 60
        - type: Pods
          value: 4                       # OR add up to 4 pods per period
          periodSeconds: 60
      # Select the most aggressive policy
      selectPolicy: Max

    scaleDown:
      stabilizationWindowSeconds: 300    # 5-minute cooldown — prevents flapping
      policies:
        - type: Percent
          value: 25                      # remove at most 25% of replicas per period
          periodSeconds: 60
        - type: Pods
          value: 1                       # OR remove 1 pod per period
          periodSeconds: 60
      # Select the least aggressive to de-scale slowly
      selectPolicy: Min
```

### HPA Behavior Notes

- **scaleUp** has `stabilizationWindowSeconds: 0` so we react instantly to CPU or queue-depth spikes. The two policies cap how aggressive we are per minute.
- **scaleDown** has a **300-second (5-minute) cooldown** because spinning down then back up ("flapping") wastes more resources and hurts latency than keeping a couple extra pods around.
- Both CPU (65% utilization) and queue depth (avg 50 per pod) must be satisfied — HPA scales to whichever demand is higher.

## 7. PodDisruptionBudget

```yaml
# deploy/pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
  namespace: api-production
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api
```

### PDB Rationale

| Scenario | Replicas Available | Pods Drained | Min Available Protected |
|----------|-------------------|--------------|------------------------|
| 3 pods running | 2 stay up | 1 voluntarily disrupted | ✅ |
| 4 pods running (HPA scaled up) | 2 stay up | 2 drained | ✅ |
| Node upgrade evicts | scheduler respects PDB | gradual drain | ✅ |
| minAvailable: 2 ensures at least 2 pods always serve traffic even during voluntary disruptions (drain, rolling updates with maxSurge limited by PDB) |

If you want to guarantee 100% availability during PDB-controlled disruptions, use `maxUnavailable: 0` instead, but that blocks all voluntary disruptions including some node drains. The `minAvailable: 2` approach is the standard trade-off.

### Critical Go Code Requirements for This to Work

Your Go HTTP server MUST handle SIGTERM properly. Here's the minimal correct pattern:

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    srv := &http.Server{
        Addr:         ":8080",
        Handler:      router(), // your mux
        ReadTimeout:  15 * time.Second,
        WriteTimeout: 30 * time.Second,
        IdleTimeout:  60 * time.Second,
    }

    // Start server in background
    go func() {
        log.Printf("listening on %s", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("listen: %v", err)
        }
    }()

    // Graceful shutdown on SIGTERM
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGTERM)
    <-quit
    log.Println("shutting down gracefully...")

    ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
    defer cancel()

    if err := srv.Shutdown(ctx); err != nil {
        log.Fatalf("server forced to shutdown: %v", err)
    }
    log.Println("server exited")
}
```

Without this `srv.Shutdown()` pattern, the container will receive SIGKILL at `terminationGracePeriodSeconds=30` deadline, dropping whatever in-flight requests haven't completed.
