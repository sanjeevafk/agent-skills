### Probe Arithmetic Explained

| Probe | What happens on failure | Threshold math | Total allowed time |
|-------|------------------------|----------------|-------------------|
| **startupProbe** | Keeps killing/restarting until first success — no other probes run yet | `failureThreshold(40) × periodSeconds(5)` | **200 seconds** (3 min 20s) |
| **livenessProbe** | Restarts the container if it has been healthy since startup | `failureThreshold(3) × periodSeconds(10)` | **30 seconds** before kill |
| **readinessProbe** | Removes pod from Service endpoints (no new traffic) | `failureThreshold(2) × periodSeconds(5)` | **10 seconds** before draining |

**Sequence over cold-start timeline:**

```
0s ──┬─ startupProbe fires every 5s ──────────────┐
     │                                            │ failureThreshold=40
200s│── First success → liveness & readiness take over
     │                                             │
     ▼                                         After startup succeeded:
liveness:  check every 10s, survive 3 misses     reads every 5s, survive 2 misses
           = 30s before restart                    = 10s before de-registration
```

**Key design decisions:**
- `startupProbe` covers the **20s cold-cache warmup with headroom** — 40×5=200s absorbs worst-case network latency + cache population + goroutine ramp-up. No race condition between startup and liveness because they're mutually exclusive.
- `livenessProbe` uses `/healthz` (process-alive check). Only restart if the process itself is deadlocked or segfaulting — not for transient dep pressure.
- `readinessProbe` uses `/readyz` (application-ready check including DB/connectors). Removing from endpoints ensures the load balancer stops routing *new* requests while in-flight requests continue draining.

## 5. Resource Sizing Rationale (p99 CPU throttling avoidance)

| Parameter | Value | Why |
|-----------|-------|-----|
| CPU request | 250m | This is the denominator for HPA utilization: `(used_cpu / 250m) × 100`. A 65% target means HPA scales at ~162m actual usage per pod. |
| CPU limit | 500m | 2× the request provides burst headroom. Above this, the CFS scheduler throttles. For a Go app (preemptive GC, fast scheduling), 500m handles short p99 spikes without triggering OOM or connection timeouts. |
| Memory request | 256Mi | Go runtime RSS typically 80–150Mi at steady state. |
| Memory limit | 512Mi | 2× buffer accounts for heap fragmentation after burst GC cycles. |

**Rule applied:** limits are 2× requests. Requests set the HPA baseline and scheduling floor; limits absorb burst but cap soft-throttling. If you observe consistent CPU throttle at p99 (check `kube_pod_container_resource_limits` vs observed usage), consider raising both proportionally and adjusting the HPA target accordingly.

### Probe Threshold Arithmetic Explained

| Probe | `periodSeconds` | `failureThreshold` | Total Failure Budget | What It Catches |
|---|---|---|---|---|
| **startup** | 5s | 30 | **150s** (with 5s initial delay = 155s) | Slow cold-cache warmup (20s) — gives 7.5× headroom |
| **liveness** | 10s | 3 | **30s** (15s initial skip + 15s grace) | Deadlock or hung goroutines — total unresponsiveness |
| **readiness** | 5s | 3 | **15s** (10s initial skip + 15s grace) | Temporary inability (DB reconnect, cache empty) |

**Why these numbers:**

- **Startup**: The 20s cold cache warmup means `/healthz` may return 5xx for the first ~20 seconds. With `initialDelaySeconds: 5`, we get 5s free, then 30×5s=150s of probing. That's 155s total budget against a 20s requirement — 7.75× headroom. If the app fails to start within 155s, it's genuinely stuck (not just warming up), so killing and restarting is correct.

- **Liveness**: After startupProbe succeeds, liveness starts kicking in. We skip the first 15s (`initialDelaySeconds`) so there's no probe overlap. Then 3 consecutive failures at 10s intervals = 30s before restart. This catches deadlocks where the process is running but goroutines are blocked. A single GC pause won't trip this since GC in Go typically takes < 10ms even at high throughput.

- **Readiness**: 10s initial delay avoids false negatives during early startup. 3 failures at 5s = 15s. When deploy triggers `maxUnavailable: 0`, the new pod hits readiness and only then does the old one get SIGTERM. The readiness gate ensures no in-flight requests are dropped because the old pod stays in the endpoint list until the new one reports ready.

### Termination-Drain Sequence During Deploy

```
Time 0:     kubectl rollout updates Deployment (strategy: maxSurge=0, maxUnavailable=0)
            New Pod creates → pending → scheduling (no old pods terminated yet)

Time N:     New Pod passes startupProbe → starts receiving liveness checks
            New Pod passes readinessProbe → kubelet adds to Service endpoints

Time N+1s:  Ingress/Service now routes ~50% traffic to both old + new pods
            New ReplicaSet has enough ready pods → old Pod receives SIGTERM

Time N+1s:  Kubelet sets ReadinessGate=false on old pod (removes from endpoints)
            Client requests stop routing to old pod immediately

Time N+1s:  preStop hook fires: `sleep 30 && echo drained`
            Go app receives SIGTERM → stops accepting NEW connections
            Existing connections (in-flight requests) keep processing

Time N+31s: preStop completes → Kubelet sends SIGKILL if still alive
            By now all in-flight requests have completed (terminationGracePeriod=60s
            gives ample time beyond the 30s preStop sleep)

Result:     Zero dropped in-flight requests. Old pod fully terminated. New pod serving
            with full traffic. Repeat per replica (one-at-a-time due to maxSurge=0).
```

Key enablers:
1. **`maxSurge: 0`** — new pods must be ready before any old pod dies
2. **`maxUnavailable: 0`** — prevents killing pods while insufficient replacements exist
3. **`preStop: sleep 30`** — sleeps for half the terminationGracePeriod, giving time for readiness to propagate and new pods to take over
4. **`terminationGracePeriodSeconds: 60`** — Go's `http.Server.Shutdown()` should be configured with this timeout so it waits for in-flight requests before force-killing

          type: Utilization
          averageUtilization: 70  # target 70% CPU utilization across all pods
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0     # scale up aggressively when under pressure
      policies:
        - type: Pods
          value: 2                      # add up to 2 pods per policy period
          periodSeconds: 60             # every 60 seconds
    scaleDown:
      stabilizationWindowSeconds: 300   # wait 5 minutes before scaling down (cool-off)
      policies:
        - type: Pods
          value: 1                      # remove at most 1 pod per period
          periodSeconds: 120            # every 2 minutes
    selectPolicy: Min                   # use most conservative of all policies
```

**Design notes:**

- The custom metric `go_api_queue_depth` is assumed to be exported by your Go app (e.g., via Prometheus client_golang) as the number of requests waiting to be processed at any moment. Targeting `averageValue: 5` means each pod tries to maintain ~5 queued requests — below that threshold, scale down; above, scale up.
- CPU at 70% provides a safety net for traffic spikes that hit compute rather than queuing. The `stabilizationWindowSeconds: 0` on scale-up ensures the HPA reacts immediately to load.
- Scale-down is deliberately slower (5min cool-off, 1 pod at a time) to avoid flapping when traffic dips transiently.

## 4. Probe Threshold Arithmetic Explained

### Startup Probe — covering the 20-second cold cache warmup

```
failureThreshold × periodSeconds ≥ cold_warmup_seconds + safety_buffer
10         × 5             = 50 seconds
                          ≈ 20s warmup + 30s buffer
```

| Parameter | Value | Purpose |
|-----------|-------|---------|
| `path` | `/health` | Lightweight; does NOT check cache status (liveness-safe) |
| `periodSeconds` | 5 | Check every 5 seconds — reasonable for HTTP |
| `failureThreshold` | 10 | Allows 50 seconds of total startup time |
| **Effective window** | **50s** | 20s cold cache + 30s operational margin |

**Why this matters:** Without a startup probe, Kubernetes would start the liveness probe immediately (after its own `initialDelaySeconds`). If the liveness probe fires while the process is still initializing, it could see a transient failure and kill the container — restarting it before the cache had warmed. The startup probe *disables* the liveness probe entirely until it succeeds. Once `/health` returns 200 for 10 consecutive checks, the startup phase is done and liveness takes over.

### Liveness Probe — detecting hung processes

```
failureThreshold × periodSeconds = restart_delay
3      × 10              = 30 seconds
```

After startup completes, the liveness probe fires every 10 seconds. Three failures in a row (30s) means the process is genuinely stuck (not just slow), and K8s restarts it. `initialDelaySeconds: 0` is safe here because the startup probe gates it.

### Readiness Probe — controlling traffic flow

```
failureThreshold × periodSeconds = removal_delay
2      × 5               = 10 seconds
```

During deployment or cache miss, the readiness probe removes the pod from Service endpoints within 10 seconds, preventing new requests from routing to a pod that can't serve yet. It uses `/ready` (a separate endpoint) that checks whether the cache has finished warming — unlike `/health` which only confirms the process is alive.

**Complete lifecycle timeline:**

```
T=0s      Container starts
T=0–50s   startupProbe: POSTPONED (liveness probe blocked)
T=20s     Cache warmup finishes (internal to app)
T=20–50s  /health starts returning 200 consistently
T=~25s    startupProbe succeeds (5th check) → liveness gate lifted
T=25s+    livenessProbe & readinessProbe both active
T=25–30s  readinessProbe: /ready returns 200 → added to endpoints
T=30s     Fully serving traffic
```

## 5. Resource Sizing Rationale (Avoiding CPU Throttling at p99)

| Parameter | Value | Why |
|-----------|-------|-----|
| CPU request | 200m | Guarantees 0.2 cores — sufficient baseline for Go's low idle footprint (~10–20m) plus request handling |
| CPU limit | 500m | 2.5× request ratio — gives burst capacity for traffic spikes but caps runaway threads. Go's GIL-like scheduler rarely needs more than 2 cores, and p99 latencies stay stable at 500m |
| Memory request | 256Mi | Go binaries are statically linked; runtime overhead is ~50–80m RSS. 256Mi covers heap + GC + goroutine stacks comfortably |
| Memory limit | 512Mi | 2× request — leaves room for GC bursts without triggering OOMKill |

**Key rule:** Requests are what the HPA reads (`current/request`) to compute utilization. Higher requests mean the HPA triggers scaling sooner (lower actual CPU). We keep requests modest relative to limits so the HPA scales *before* CPU contention hurts p99 tail latency.
