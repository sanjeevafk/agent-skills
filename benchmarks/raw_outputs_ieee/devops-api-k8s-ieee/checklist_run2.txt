### Probe Threshold Arithmetic

Your service has a **20-second cold cache warmup**. Here's how each probe works together:

| Probe | What It Does | Why It Works For This Case |
|-------|-------------|--------------------------|
| `startupProbe` | Tells K8s "don't apply other probes until this succeeds" | Covers the entire cold-start phase including 20s cache warmup. Once it fires successfully, K8s considers the container started and stops killing it for startup failures. |
| `livenessProbe` | Restarts the container if unresponsive | Only runs after startupProbe passes. Detects deadlocks or hung goroutines, not slow starts. |
| `readinessProbe` | Removes/adds pod from Service IP tables | Probes `/ready`. Returns 200 only when the hot cache is populated. K8s won't route traffic until ready. |

**Startup probe timing:**

```
failureThreshold × periodSeconds = total startup budget
30 × 10s                           = 300s (5 minutes)
```

This gives you 5 minutes of leeway. The cold cache warmup is 20s, but the HTTP handler might be slow initially because every request triggers a DB fetch until the cache fills. A generous threshold like this lets the first batch of in-flight requests succeed while the warmup completes. After the first successful response, startupProbe stops checking entirely.

If you want tighter control (e.g., 60s instead of 300s):

```yaml
# 10 × 6s = 60s — tight but safe for a well-behaved Go binary
startupProbe:
  httpGet:
    path: /health          # Always returns 200 even during warmup
    port: 8080
  failureThreshold: 6
  periodSeconds: 10
```

**Liveness probe timing:**

```
failureThreshold × periodSeconds = time before restart
3 × 10s                        = 30s — aggressive enough to catch hangs
```

A single second of latency in a health check is fine. Only three consecutive failures trigger a restart, preventing false positives from brief GC pauses or lock contention.

**Readiness probe timing:**

```
failureThreshold × periodSeconds = time without endpoints
2 × 15s                        = 30s — removes pod from Service if /ready fails twice consecutively
```

During a rolling deploy, the new pod's readiness stays negative until its own 20s cache warms. Meanwhile the old pods continue serving. When the new pod becomes ready, traffic shifts automatically.

func readyHandler(w http.ResponseWriter, r *http.Request) {
    if !hotCache.WarmedUp() {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)

## HorizontalPodAutoscaler — CPU + Custom Metric

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api
  minReplicas: 3
  maxReplicas: 10

  # Behavior controls scaling speed and stabilization windows
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30    # Don't add pods on transient spikes
      policies:
        - type: Percent
          value: 50                     # Max 50% scale-up per selection period
          periodSeconds: 60
        - type: Pods
          value: 2                      # Or max 2 new pods per period
          periodSeconds: 60
      selectPolicy: Max                 # Use whichever policy is more conservative

    scaleDown:
      stabilizationWindowSeconds: 300   # Wait 5 min before scaling down — protects against thundering herd
      policies:
        - type: Percent
          value: 10                     # Remove max 10% of current replicas per window
          periodSeconds: 60
      selectPolicy: Min                 # Be conservative on scale-down

  metrics:
    # ── CPU target ────────────────────────────────────────────
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60        # Scale up when avg pod CPU > 60% of request

    # ── Custom metric: average queue depth per pod ───────────
    # Exposed by Prometheus Adapter from your application metrics.
    # Metric name must follow <metric-name>_average_utilization convention.
    # Assumed metric: go_api_queue_depth (Gauge per pod; adapter computes per-pod average)
    - type: Pods
      pods:
        metric:
          name: go_api_queue_depth
        target:
          type: AverageValue
          averageValue: "5"            # Scale up when average queue depth per pod > 5
```

**How the two metrics interact:**

- HPA evaluates ALL metrics and scales to satisfy the **most demanding one** at any point.
- Under normal load: CPU keeps replicas at 3–5 based on throughput.
- During cache misses or traffic bursts: queue depth drives scaling independently, preventing latency regression.
- The `behavior.stabilizationWindowSeconds` on scale-down (5 min) is critical — it prevents churning between 10→3 replicas when a spike subsides and a thundering herd of new requests arrives immediately after.

**Prerequisites for the custom metric:**
- Your Go app exports `go_api_queue_depth` (one gauge per pod) via Prometheus `/metrics` endpoint.
- Install the [Prometheus Adapter](https://github.com/kubernetes-sigs/prometheus-adapter) and configure an appropriate rule:

```yaml
# prometheus-adapter custom-metrics-config.yaml excerpt
rules:
  - seriesQuery: 'go_api_queue_depth{namespace="production",pod!=""}'
    resources:
      overrides:
        pod: {resource: "pod"}
    name:
      as: "go_api_queue_depth"
    metricsQuery: 'avg(go_api_queue_depth{namespace="production",pod="<<.Pod>>}) by (pod)'
```

## PodDisruptionBudget

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: go-api-pdb
  namespace: production
spec:
  minAvailable: 2               # At least 2 pods always running during voluntary disruptions
  selector:
    matchLabels:
      app: go-api
```

With `minReplicas: 3` and `minAvailable: 2`, only **one** pod can be voluntarily disrupted at a time (node drain, cluster autoscaler upgrade). Combined with `maxUnavailable: 0` on the Deployment rollout strategy, this guarantees:

- During a **rolling deploy**: old pods aren't terminated until the new replacement is ready. Zero requests dropped.
- During a **node drain**: at most 1 pod goes down at a time. Remaining 2+ handle all traffic.
- During a **cluster upgrade**: PDB blocks the drain operator from evicting beyond the budget.

If you ever increase minReplicas above 4, consider tightening to `maxUnavailable: 1` instead:

```yaml
spec:
  maxUnavailable: 1             # Same semantics but easier to reason about at scale
  selector:
    matchLabels:
      app: go-api
```

## Graceful Shutdown Sequence

This is the full lifecycle when K8s decides to terminate a pod (deploy, scale-down, node drain):

```
T=0s     SIGTERM sent to PID 1 (your Go binary)
         ├── PreStop hook begins executing concurrently
         │
         ▼
T=0s     kubectl exec —pre-stop → sleep 10
         (hook blocks; pod remains in Terminating state)
         │
         ▼
T=0–10s  K8s removes pod from all Service endpoints IMMEDIATELY on SIGTERM
         → No NEW traffic reaches this pod (load balancers update within ~100ms–2s)
         │
         ▼
T=10s    Hook finishes → K8s starts counting down terminationGracePeriodSeconds (30s total)
         → All in-flight requests MUST complete by T=40s
         │
         ▼
T=40s    If pods still have open connections, K8s sends SIGKILL (hard stop)
         → Requests still in progress at this point are dropped
```

**What you MUST implement in your Go code** for zero dropped requests:

```go
func main() {
    srv := &http.Server{Addr: ":8080", Handler: mux}

    // Signal setup
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
    defer stop()

    go func() {
        fmt.Println("listening on :8080")
        if err := srv.ListenAndServe(); err != http.ErrServerClosed {
            log.Fatal(err)
        }
    }()

    // Wait for OS signal or context cancellation
    <-ctx.Done()
    fmt.Println("shutting down, draining in-flight requests...")

    // Give existing requests time to finish (matches terminationGracePeriodSeconds)
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
    defer cancel()

    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Fatalf("server shutdown failed: %v", err)
    }

    fmt.Println("graceful shutdown complete")
}
```

Key points:
- `srv.Shutdown()` accepts the new `context.Context` but continues accepting existing connections, processes them, then closes idle ones. This is the correct way to shut down an HTTP server.
- The 25s timeout leaves 5s of buffer before K8s sends SIGKILL at T=40s.
- Do **not** use `srv.Close()` — it drops all in-flight requests immediately.
- The PreStop `sleep 10` gives K8s time to remove the pod from Service endpoint lists, so no new traffic arrives while you're finishing existing requests.
