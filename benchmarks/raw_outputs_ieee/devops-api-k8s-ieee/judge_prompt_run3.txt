### 6. Probes — Endpoints Design

Your Go application must expose three distinct endpoints:

| Path | Returns | Purpose |
|------|---------|---------|
| `/healthz` | `200 OK` when process is alive (always available) | Liveness — "is it dead?" |
| `/ready` | `200 OK` when DB connected + cache warmed | Readiness — "can it serve?" |
| `/metrics` | Prometheus format on `:8080` | Monitoring / HPA scraping |

The critical detail: **`/ready` should return `503` during the 20s cold cache warmup**. Once warm, it returns `200`. This is what keeps traffic off pods still initializing.

```go
// Example readiness handler (Go pseudo-code)
func readyHandler(w http.ResponseWriter, r *http.Request) {
    select {
    case <-cacheWarmed:    // channel closed after 20s of loading
        w.WriteHeader(http.StatusOK)
    default:
        http.Error(w, "not ready", http.StatusServiceUnavailable)
    }
}
```

```yaml
    scaleDown:
      stabilizationWindowSeconds: 300   # 5-min cooldown to avoid flapping
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120         # shed 1 pod every 2min max

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70     # scale up when avg pod CPU > 70% of request (150m)

    - type: External
      external:
        metric:
          name: queue_depth_per_pod
        selector:
          matchLabels:
            queue_name: orders
        target:
          type: AverageValue
          averageValue: "100"       # ~100 pending msgs/pod triggers scale-up
```

**Why two different metric types:**

- **CPU** handles general load spikes (new connections, compute-heavy routes)
- **External** (`queue_depth_per_pod`) handles back-pressure — the Queue Depth adapter (via Prometheus Adapter) exposes your consumer lag metric. Scaling on this keeps p99 latency flat regardless of how CPU-heavy each message is.

**Behavior tuning rationale:**

- Scale-up window of 60s avoids reacting to momentary blips
- Scale-down window of 300s prevents thrash when traffic oscillates
- Asymmetric policy (2 up, 1 down) favors responsiveness over cost savings

**Prerequisite:** You need a custom metrics API server running in-cluster (Prometheus Adapter or kube-state-metrics + custom-metrics-adapter) scraping the `queue_depth_per_pod` gauge from your app.

With `replicas: 3` minimum, `minAvailable: 2` means K8s will allow at most **one** pod to be voluntarily disrupted at a time (node drain, cluster upgrade). Combined with `maxUnavailable: 0` on the Deployment strategy, this guarantees:

- During a rolling deploy: old pod terminates → new pod becomes ready → old pod fully removed. At no point are active pods reduced below the current count minus one (and the PDB enforces that even that one requires approval).
- During a node drain: if 2 pods land on the same node, the PDB blocks the drain until one pod is safely rescheduled elsewhere.

## Probe Threshold Arithmetic

Here's the timeline for a fresh pod starting up:

```
Time (s)    Event
───────────────────────────────────────────────────────────────
0           Container starts; all three probes begin checking
0–5         startupProbe: 1st attempt (period=5s)
5           startupProbe: 2nd attempt ← if /healthz passes here, startup succeeds immediately
...
20          Cold cache finishes warming (application internal milestone)
25          readinessProbe has seen ≥2 consecutive successes → pod added to Service endpoints
30          startupProbe has now passed; it stops being evaluated entirely
>30         Only liveness + readiness are active
```

**Startup probe: 30 × 5s = 150s budget**

This is the maximum wall-clock time from container start to the first successful `/healthz`. A compiled Go binary starts fast; the bottleneck is cache warmup (20s) plus network/DNS to dependencies. Even with a conservative retry budget, 150s covers 7× the actual warmup time. If the cache never warms, the container dies after 150s instead of sitting in a degraded state forever.

**Liveness probe: 3 × 10s = 30s before restart**

No `initialDelaySeconds` because the startup probe already validated the process could start. Once it transitions past startup, liveness takes over. If the process deadlocks, `timeoutSeconds: 3` ensures a single failed check completes within 3s (avoids blocking the period window). After 3 consecutive failures (30s), K8s kills and restarts the container. This catches goroutine leaks where the process is alive but unresponsive.

**Readiness probe: 3 × 5s = 15s before traffic stops**

The `/readyz` endpoint checks whether the cold cache is warmed. While it returns HTTP 503, K8s removes the pod from the Service's endpoint slice — no new requests land here. Consecutive failures (`failureThreshold: 3`) trigger removal. Note this uses `successThreshold: 1` — once the cache warms and `/readyz` returns 200, the pod rejoins endpoints after just one successful check (no unnecessary delay on recovery).

**What happens at each phase:**

| Phase | Startup | Liveness | Readiness | Traffic? |
|-------|---------|----------|-----------|----------|
| 0–20s (warming) | Failing → eventually succeeds | May pass (process alive) | Failing (cache cold) | No (not in endpoints) |
| 20–150s (running) | Passed → disabled | Checks continue | Passing | Yes |
| Deadlock after 150s | N/A | Fails → restart | Irrelevant (pod dying) | None |
| Crash after startup | Would fail if happened | Would fail → restart | Irrelevant | Depends on timing |

## Graceful Drain Sequence

When K8s decides a pod should terminate (deploy, scale-down, node drain), the sequence is:

```
Step 1 ─ SIGTERM sent to PID 1 (the Go process)
         ↓
Step 2 ─ Server.Shutdown(ctx) begins:
         • New requests are rejected (HTTP 503 from router layer)
         • In-flight requests continue processing
         ↓
Step 3 ─ Readiness probe returns 503 → K8s removes from endpoints immediately
         ↓
Step 4 ─ [Up to terminationGracePeriodSeconds (30s)]
         Active requests finish. Each request handler should
         respect the context cancellation deadline.
         ↓
Step 5 ─ SIGKILL sent (if still alive at 30s) → hard kill
```

```yaml
          periodSeconds: 15
```

### Why these numbers

| Parameter | Value | Rationale |
|---|---|---|
| `averageUtilization: 50` | 50% CPU | Headroom so a burst to p99 doesn't trigger cooldown immediately; gives the scheduler room to place new pods |
| `averageValue: "100"` | 100 queue / replica | When p99 latency climbs because the system is saturated, the queue depth hits 100 and scales up *before* requests start timing out |
| `scaleDown.stabilizationWindowSeconds: 300` | 5 min cooldown | Deploy rollout creates a brief dip in total capacity → old pods terminate, traffic rebalances → HPA must NOT scale down during this transient. 300 s covers the typical rolling-update window |
| `scaleUp.stabilizationWindowSeconds: 60` | 60 s | Once demand is confirmed (not a spike), react fast |

The external metric (`http_request_queue_depth_per_replica`) is exported by the application itself via an OpenTelemetry/StatsD histogram. If using KEDA instead of native HPA, the same logic applies but the source is KEDA's ScaledObject targeting the same Prometheus query.

```yaml
              readOnly: true

            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c

                  |
                  echo "Removing pod from Service endpoints..."
                  # Wait for readiness gate to be removed (~4s propagation delay)
                  sleep 5
                  # 2. Drain in-flight requests — stop accepting, let existing finish
                  echo "Draining in-flight requests (timeout=20s)..."

                    http://localhost:8080/healthz/drain || true

                  echo "Graceful drain complete. Proceeding to termination."

            driver: secrets-store.csi.k8s.io
            readOnly: true

              secretProviderClass: go-api-postgres

              secretProviderClass: go-api-tls
```

## 4. Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: go-api
  namespace: go-api
  labels:
    app: go-api
spec:
  # HPA controls replica count; baseline is 3
  replicas: 3
  selector:
    matchLabels:
      app: go-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                  # Bring up 1 new pod before tearing down old
      maxUnavailable: 0            # Never drop below desired count — zero-downtime guarantee

  template:
    metadata:
      labels:
        app: go-api
    spec:
      serviceAccountName: go-api-sa
      automountServiceAccountToken: false

      # Total time we give pods to finish draining before K8s SIGKILLs them.
      # Must be >= slowest expected request duration.
      terminationGracePeriodSeconds: 45

      containers:
        - name: go-api
          image: ghcr.io/org/go-api:v1.2.3   # Immutable tag — never :latest
          imagePullPolicy: IfNotPresent

          ports:
            - containerPort: 8080
              protocol: TCP

          # ---------- Probes ----------
          # Startup probe: covers the full 20s cache warmup with generous headroom.
          #   10 failures × 5s period = 50s maximum startup window.
          #   This must be LONGER than the liveness probe's effective initial window
          #   so liveness doesn't fire while the cache is still warming.
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            failureThreshold: 10       # Give it 50s total
            periodSeconds: 5           # Check every 5 seconds

          # Liveness probe: restarts on deadlock/hang, only runs AFTER startup succeeds.
          #   2 failures × 5s period = 10s before restart.
          #   initialDelaySeconds: 0 — safe because startupProbe protects us from early-fire.
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 0
            periodSeconds: 5
            failureThreshold: 2

          # Readiness probe: removes pod from Service endpoints when draining or unhealthy.
          #   We implement endpoint deactivation during server shutdown (see drain section below).
          #   3 failures × 3s period = 9s before pod drops from service — short enough
          #   that the old pod is fully drained and new one is ready before this happens.
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 3
            failureThreshold: 3

          # ---------- Resources ----------
          # Requests sized for p99 CPU without over-reserving.
          # Go has very low overhead (<50MB RSS idle), so memory request can be lean.
          # Limits set ~3x requests to allow bursty CPU without throttling p99.
          resources:
            requests:
              cpu: "100m"        # 0.1 CPU guaranteed — scheduler placement
              memory: "128Mi"    # Baseline RSS for stateless Go service
            limits:
              cpu: "500m"        # 5x request headroom for burst/saturation
              memory: "256Mi"    # OOM guard — most Go services stay well under this

          # ---------- Security ----------
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
            runAsNonRoot: true
            runAsUser: 65534     # nobody
            runAsGroup: 65534

          # ---------- Env ----------
          env:
            - name: APP_ENV
              value: production
            - name: PORT
              value: "8080"

          # ---------- Secret volume mount (NOT env vars) ----------
          # Using emptyDir placeholder — replace secretRef with your Secret
          # name (or External Secrets Operator-managed Secret). Volume mount
          # ensures secrets don't appear in `kubectl exec` /proc or container diffs.
          volumeMounts:
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
            - name: tmp
              mountPath: /tmp

          # ---------- Lifecycle hooks for graceful drain ----------
          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  # Step 1: Remove from Service endpoints immediately so no NEW traffic arrives.
                  #         The readiness probe fails first (application-level deactivation),
                  #         K8s takes 1-3 seconds to propagate endpoint removal.
                  # Step 2: Sleep until old pods are terminated (max: 45s grace period minus
                  #         5s buffer for health check propagation). Then signal the Go HTTP
                  #         server to stop accepting. The application must close its listener
                  #         here so existing connections complete gracefully.
                  - |
                    # Wait for readiness to fail and endpoints to be removed
                    while kill -0 $(cat /var/run/goserver.pid) 2>/dev/null; do
                      sleep 1
                    done
                    # Give K8s a moment to propagate endpoint removal
                    sleep 5
                    # Signal server shutdown (SIGTERM reaches this process automatically,
                    # but some setups send it explicitly via a Unix socket or HTTP call)
                    kill -TERM $(cat /var/run/goserver.pid) 2>/dev/null || true
                    # Hard exit after 10s safety net
                    sleep 10

      # ---------- Volumes ----------
      volumes:
        - name: secrets
          secret:
            secretName: go-api-secrets
        - name: tmp
          emptyDir: {}
```

**Go side — server shutdown implementation:**

## 5. HorizontalPodAutoscaler (CPU + custom queue depth)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: go-api-hpa
  namespace: go-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: go-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    # --- Metric 1: CPU utilization ---
    # Target 70% — scales up when aggregate CPU exceeds 70% of sum(requested CPUs).
    # At minReplicas=3 with 100m request each, scale-up triggers at ~210m cluster-wide.
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

    # --- Metric 2: Custom metric — queue depth ---
    # Requires Metrics Server or Prometheus Adapter to expose custom metrics.
    # Exposed via the custom.metrics.k8s.io API by something like prometheus-adapter.
    # Assumes you export a metric named `queue_depth_per_pod` (float gauge, averaged per pod).
    - type: Pods
      pods:
        metric:
          name: queue_depth_per_pod
        target:
          type: AverageValue
          averageValue: "5"    # Scale up when avg queue depth > 5 per pod
  behavior:
    # Scale-up: aggressive but smooth — 1 pod every 30s, up to 2 at a time
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Pods
          value: 2
          periodSeconds: 30
    # Scale-down: conservative — waits 5 minutes to avoid flapping
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 1
          periodSeconds: 60
```

> **Note on custom metrics:** The `Pods` metric type requires the Kubernetes Metrics Server extension (`custom-metrics-apiserver`) or Prometheus Adapter. Your Go service must export the `queue_depth_per_pod` counter via OpenTelemetry/Prometheus, and the adapter must expose it as a metric on the `custom.metrics.k8s.io` API.
