## § PROBE ARITHMETIC DERIVATION

### Startup Probe — covers the 20s cache-warm window

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `path` | `/healthz` | Returns 200 as soon as the HTTP server binds (no cache dependency) |
| `failureThreshold` | 30 | Conservative safety margin |
| `periodSeconds` | 6 | Aggressive-enough polling, conservative enough to not hammer |
| **Total budget** | **30 × 6 = 180s** | Enough time for: process init (~5s) + bind (~1s) + cold cache warmup (~20s) + safety headroom (154s) |

**Why 6s interval, not 1s?** A 1s interval would give 120 polls — excessive API calls during startup and wastes kubelet cycles. With a 20s warmup and 30-threshold, 6s already provides 180s of budget which is 9× the warmup time.

**What happens if it succeeds early?** After the first successful `/healthz` check, the startup probe is considered passed and is permanently disabled for the container's lifetime. Liveness/readiness take over immediately.

### Liveness Probe — detects hangs, not slow starts

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `initialDelaySeconds` | 15 | Overlap with late stage of startup probe; avoids race |
| `periodSeconds` | 10 | Moderate frequency — Go's scheduler makes 10s plenty responsive |
| `failureThreshold` | 3 | 3 consecutive misses = container truly hung |
| **Real-time trigger** | **15 + 3×10 = 45s** | Minimum wall-clock time before first possible restart |

**Key decision:** `initialDelaySeconds: 15` means the liveness probe starts checking at t=15s. Before that, only the startup probe governs. If the cache finishes warming at t=20s and the app begins serving, liveness will see healthy responses at t=20+ and continue normally. No restart ever occurs during normal boot.

```go
func readyHandler(c *Controller) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if !c.Cache.IsWarmed() || !c.DB.Ping() {
            http.Error(w, "not ready", http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    }
}

## 5. Probe Threshold Arithmetic

Three probes serve three independent concerns. Here's the math for each:

| **readinessProbe** | HTTP GET `/readyz` | 10 s | 2 | **2 × 10 = 20 s** | Pod removed from Service endpoints after 20s of continuous failures |

1. **startupProbe covers the cold-start + cache-warm window.** It's a lightweight TCP check: "is the process alive and listening?" At 3s intervals with a threshold of 20, the pod gets up to **60 seconds** to open its listen socket. This comfortably exceeds your 20s cache warmup because the cache warms *while* the socket is already open — startupProbe doesn't wait for the cache, only for the listener.

## PDB (`pdb.yaml`)

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: go-api
  namespace: production
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: go-api
```

### PDB logic

During a node drain (upgrade, spot interruption, maintenance), the disruption controller calculates:

```
max_unavailable_during_drain = min(replicas - minAvailable, max(PDB allows))
                            = min(3 - 2, ∞)
                            = 1
```

So only **one pod at a time** can be voluntarily disrupted. The remaining **2+ pods always stay running**, meaning clients never lose all backends. With 5–10 replicas (HPA-scaled), you could lower `minAvailable` if desired, but keeping it at 2 guarantees baseline capacity even at minimum replica count.

## § Probe Threshold Arithmetic

This decision table drives every probe's parameters:

| Probe | Purpose | When to act | Math → Budget |
|-------|---------|-------------|---------------|
| **Startup** | App + cold-cache warmup (≤20s). Prevents liveness from killing the pod during bootstrap. | Restart ONLY if the pod hasn't passed `/healthz` within the budget. | `failureThreshold × periodSeconds = 30 × 10s = 300s`. The 20s warmup fits with 15× margin. After success, liveness/readiness take over. |
| **Liveness** | Detect hangs / goroutine leaks / deadlocks where the process still responds to some endpoints but is fundamentally broken. | Kill & restart if no response to `/healthz` for 3 consecutive checks. | `failureThreshold × periodSeconds = 3 × 10s = 30s`. Fast enough to unstick a hung process, slow enough to ignore brief network blips. |
| **Readiness** | Remove unhealthy pods from Service load-balancing so in-flight requests route to healthy pods. | Stop sending new traffic if `/readyz` fails 3 times in a row. | `failureThreshold × periodSeconds = 3 × 5s = 15s`. Quicker feedback than liveness — traffic shifts away faster than we kill the pod. |

### Critical distinction

- **Readiness fails first** (15s) → pod removed from Service endpoints → no new requests sent → connection drains gracefully → *then* liveness may fire (30s later) if the pod is truly broken.
- **Startup probe blocks liveness entirely** until it succeeds. During the 20s cold cache window, liveness doesn't count against it. This is why `initialDelaySeconds` on liveness would NOT work correctly — the startup probe approach is the modern, reliable pattern.
