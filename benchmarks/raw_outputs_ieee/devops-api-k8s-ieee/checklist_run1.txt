## SecretStore Integration (CSI driver)

The `volumeMounts` section in the Deployment references a CSI volume. Configure it with a `SecretProviderClass` matching your secret store:

```yaml
# ── Example: AWS Secrets Manager CSI Driver ──
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: go-api-secrets
  namespace: default
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "go-api/prod-db-password"
        objectAlias: "db-password"
        jmesPath:
          - path: 'db_password'
            objectAlias: "db-password"
      - objectName: "go-api/prod-api-key"
        objectAlias: "api-key"
        jmesPath:
          - path: 'service_api_key'
            objectAlias: "api-key"
  secretObjects:                        # optional: also create K8s Secret copies
    - secretName: go-api-secrets
      type: Opaque
      data:
        - objectName: db-password
          key: db-password
        - objectName: api-key
          key: api-key
```

Files appear at `/etc/secrets/db-password` and `/etc/secrets/api-key` — readable by UID 1000. No env var injection, no base64 in etcd.

Other drivers: GCP Secret Manager CSI (`provider: gcp`), Azure Key Vault CSI (`provider: azure`), HashiCorp Vault Agent CSI (`provider: vault`). The volume mount pattern is identical across all providers.

## Probe Threshold Arithmetic

| Probe | Endpoint | Period | FailureThreshold | Effective Window | Triggered Action |
|---|---|---|---|---|---|
| `startupProbe` | `GET /health` | 2 s | 40 | **80 s** | Kills container if not alive within 80 s |
| `livenessProbe` | `GET /health` | 2 s | 3 | **6 s** | Restarts container after 6 s of unresponsiveness (deadlock/hang) |
| `readinessProbe` | `GET /ready` | 2 s | 2 | **4 s** | Removes pod from Service endpoints after 4 s of failures |

**Why these numbers:**

- **Startup: 80 s** — Your cold cache warmup takes ~20 s. The 80 s window gives a 4× safety margin for slow disk I/O, large images, or cold database connections. `failureThreshold(40) × periodSeconds(2) = 80`. If the probe succeeds even once, the startup probe disarms permanently and liveness/readiness take over.

- **Liveness: 6 s** — After startup succeeds, liveness checks for *deadlocks* or hung goroutines. Two-second polling catches hangs quickly. Three consecutive failures means the process genuinely isn't processing HTTP — restart. `3 × 2 = 6`.

- **Readiness: 4 s** — `/ready` returns 503 until `atomic.Bool` is set to `true` after cache initialization. Once warm, the pod joins endpoints immediately. On the flip side, if the pod becomes unhealthy, it's removed from endpoints within 4 s so traffic shifts to healthy pods. `2 × 2 = 4`.

**Application-side implementation:**

```go
var cacheReady atomic.Bool

func main() {
    initColdCache() // blocks ~20s until fully populated
    cacheReady.Store(true)

    mux := http.NewServeMux()
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK) // always returns 200 once process is alive
    })
    mux.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
        if !cacheReady.Load() {
            http.Error(w, "cache warming", http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    })

    srv := &http.Server{Addr: ":8080", Handler: mux}
    // register os/signal handler for SIGTERM → srv.Shutdown()
}
```

The separation is intentional: `/health` answers *"is the process alive?"* (startup+liveness). `/ready` answers *"can this pod accept traffic?"* (readiness). They are independent checks with independent failure thresholds.

## Termination-Drain Sequence (Zero Dropped Requests)

The zero-drop guarantee comes from three coordinated mechanisms working together:

```
T=0s       │  Deployment update starts: 3 new Pods spin up alongside 3 old Pods
           │  (maxSurge=1 allows only 1 extra at a time)

T=0–25s    │  New Pod-B boots → startupProbe passes → cache warms (~20s)
           │  → /ready returns 200 → Pod-B added to Service endpoints
           │  → Traffic splits: OLD pods + NEW Pod-B share load

T=25s      │  Old Pod-A receives SIGTERM (first to go, oldest in the set)
           │  Kubelet removes Pod-A from endpoints IMMEDIATELY (concurrent with preStop)
           │  BUT: pending TCP connections and load-balancer backend pool updates lag
           │  by 1–5s behind the endpoint removal.

T=25–70s   │  preStop hook runs: 45s sleep (curl localhost:8080/health || sleep 45)
           │  During this window:
           │    • Straggler requests from stale LB backends reach Pod-A
           │    • Existing TCP streams complete normally
           │    • Pod-A responds to all requests
           │    • No new requests route here (endpoint controller already removed it)

T=70s      │  preStop completes. Kubelet sends SIGTERM to PID 1.
           │  Go handler: server.Shutdown() → stops accepting, drains active handlers

T=70–85s   │  Remaining in-flight requests on Pod-A finish (≤15s SIGTERM grace).
           │  If not exited by T=85s → SIGKILL (should never reach here if
           │  max-request-duration < 15s, which is true for most APIs).

T=85s      │  Pod-A fully terminated. K8s deletes it.
           │  Moves to terminate Pod-C (second oldest). Same sequence repeats.

T=170s     │  All 3 old Pods replaced. Zero dropped requests.
           │  (3 replicas × ~55s drain each, sequential with maxUnavailable=0)
```

**Why this works:**

1. **`maxUnavailable: 0`** — K8s never terminates an old pod until replacements are passing readiness. Capacity never dips below `minReplicas`.

2. **`preStop: 45s`** — The endpoint controller removes the pod from Services instantly, but cloud load balancers and kube-proxy (iptables/IPVS) take 1–5s to propagate rule updates. The preStop sleep acts as a buffer for these stale routes and for existing TCP connections whose clients are still transmitting.

3. **`terminationGracePeriodSeconds: 60`** — Total wall-clock time from SIGTERM to forced SIGKILL. `60 − 45 = 15s` for SIGTERM handler. Must exceed your API's max in-flight request duration. For a typical Go API (<5s per request), 15s is generous.

4. **Readiness gate on `/ready`** — No new traffic ever reaches a pod before its cache is warm. Combined with `maxUnavailable: 0`, you never replace a warm pod with a cold one without both coexisting.

## Resource Sizing Rationale

| Metric | Value | Rationale |
|---|---|---|
| CPU request | `250m` | Scheduler guarantees 0.25 cores per pod. Fits ~4 pods on a 1-core node. |
| CPU limit | `1000m` | 4× burst headroom above request. Prevents p99 CPU throttling under load spikes. Go's GC pauses rarely spike above sustained usage. |
| Memory request | `256Mi` | Go runtime baseline ~30–50 MB + hot cache + HTTP buffers. 256 MiB comfortably covers normal operating conditions. |
| Memory limit | `512Mi` | 2× request headroom. Allows cache growth under heavy load without triggering OOMKill. |

The HPA calculates utilization as `current_usage / request`. With a request of `250m`, a pod using `150m` sits at 60% — the HPA scale-up trigger. At p99, the `1000m` limit means a single pod can consume a full core for short bursts without being throttled, keeping tail latencies stable.
