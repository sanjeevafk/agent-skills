# Zero-Downtime Rename: `users.email` → `users.primary_email`

**Scale:** 120M rows | **PostgreSQL 14+** | **8 replica app servers** | **Live traffic throughout**

---

## 1. Lock Behavior Analysis

Every DDL statement's lock impact before proceeding:

| Statement | Access Lock Held | Exclusive Lock On? | Rows Locked? | Duration | Safe for Prod? |
|---|---|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN new_col TEXT` | ACCESS MODIFIED | No | No | Milliseconds (catalog write only) | Yes — instant, even at 120M rows |
| `ALTER TABLE ... ADD COLUMN ... DEFAULT true` | ACCESS MODIFIED | No | No | Instant (PG 11+ stores default in catalog, no rewrite) | Yes |
| `CREATE INDEX ON users(email)` | EXCLUSIVE | Yes | All rows scanned under lock | Minutes–hours on 120M | **No** — blocks all writes |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE (brief at start & end) | No | No sustained lock | Minutes–hours, but non-blocking | Yes |
| `UPDATE users SET ...` (single massive statement) | RowExclusive (table level) | Brief table lock | All matching rows pinned briefly | Seconds–minutes, but huge undo log | **Risky** — risk of statement_timeout, undo bloat |
| `DELETE FROM users ... LIMIT n` | RowExclusive | Brief per-batch | Batch-size rows | Short per-batch | Yes — if bounded |
| `ALTER TABLE ... DROP COLUMN` | ACCESS EXCLUSIVE | Yes (brief) | No row rewrite | Milliseconds | Yes — safe once no code references it |
| `DROP TRIGGER` | ACCESS EXCLUSIVE (brief) | Yes (brief) | No | Milliseconds | Yes |
| `REINDEX CONCURRENTLY` (on partial index) | SHARE UPDATE EXCLUSIVE | No | No sustained | Comparable to initial build | Yes |

**Key insight:** The only dangerous operation at this scale is a single-shot UPDATE on 120M rows. Everything else is safe if done with CONCURRENTLY or batching.

```

Once confirmed, M007 drops email — older replicas that crash are restarted on Step 2.
```

## 3. Phase 1: Expand — Schema Change

### M001 — Add `primary_email` column

```sql
-- migrations/0001_add_primary_email_column/migration.sql
-- Phase 1: Schema expansion
-- Impact: ACCESS MODIFIED lock only (~0ms). No row rewrite. Safe on 120M rows.

BEGIN;

ALTER TABLE users ADD COLUMN primary_email TEXT;

COMMIT;
```

**Lock behavior:** `ACCESS MODIFIED` on the `users` table catalog entry only. Reads, writes, and scans continue uninterrupted. PG 14+ stores the nullability and lack of default in the catalog — zero I/O on data pages.

**Rollback:** `ALTER TABLE users DROP COLUMN primary_email;` — instant, no data loss.

**Verification query (run immediately after apply):**

```sql
SELECT count(*) AS total_rows,
       count(primary_email) AS filled_rows,
       round(count(primary_email)::numeric / count(*)::numeric * 100, 6) AS fill_pct
FROM users;
-- Expected: total_rows ≈ 120000000, filled_rows = 0, fill_pct ≈ 0
```

### M002 — Write-through triggers (dual-write layer)

These triggers fire on INSERT/UPDATE to `email` and copy the value into `primary_email`. They provide a safety net for any writes that still hit `email` during the mixed-version period.

```sql
-- migrations/0002_dual_write_triggers/migration.sql
-- Phase 1: Triggers that ensure primary_email stays in sync
-- Impact: Minimal overhead per INSERT/UPDATE (PL/pgSL call + IF check)

BEGIN;

-- Trigger function for INSERTs (only path via ORM/app, not raw INSERT INTO users(email,...))
CREATE OR REPLACE FUNCTION _copy_to_primary_email_on_insert()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only copy if primary_email wasn't already set by app code
    IF NEW.primary_email IS NULL AND NEW.email IS NOT NULL THEN
        NEW.primary_email := NEW.email;
    END IF;
    RETURN NEW;
END;
$$;

-- Trigger function for UPDATEs on email column
CREATE OR REPLACE FUNCTION _copy_to_primary_email_on_update()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only copy when email is being changed AND primary_email hasn't been set independently
    IF OLD.email IS DISTINCT FROM NEW.email
       AND (NEW.primary_email IS NULL OR NEW.primary_email = OLD.email) THEN
        NEW.primary_email := NEW.email;
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_users_copy_email_to_primary_after_insert
    BEFORE INSERT ON users
    FOR EACH ROW EXECUTE FUNCTION _copy_to_primary_email_on_insert();

CREATE TRIGGER trg_users_copy_email_to_primary_after_update
    BEFORE UPDATE ON users
    FOR EACH ROW EXECUTE FUNCTION _copy_to_primary_email_on_update();

COMMIT;
```

**Performance note:** Each trigger adds ~5–15μs per write. On 120M rows with typical throughput (e.g., 5K inserts/sec, 50K updates/sec), that's <1ms additional latency per query. Acceptable.

**Rollback:**

```sql
BEGIN;
DROP TRIGGER IF EXISTS trg_users_copy_email_to_primary_after_insert ON users;
DROP TRIGGER IF EXISTS trg_users_copy_email_to_primary_after_update ON users;
DROP FUNCTION IF EXISTS _copy_to_primary_email_on_insert();
DROP FUNCTION IF EXISTS _copy_to_primary_email_on_update();
COMMIT;
```

### Deploy Step 1 — Enable Dual-Writes in Application Code

Update the ORM/model layer so every INSERT and UPDATE to `User.email` also writes to `primary_email`:

**Drizzle ORM example:**

```typescript

// After (dual-write):
```

```python
        super().save(*args, **kwargs)
```

**Deploy strategy:** Rolling restart across 8 replicas (1 replica at a time, 30-second gap). No new functionality introduced — just adds a write target. Old replicas continue writing to `email`; new replicas write to both. Both coexist safely.

## 4. Phase 2: Backfill — Bounded Batch Cursor

### M003 — Backfill cursor (data migration)

**Critical: This runs OUTSIDE the migration tool**, as a standalone script, because:
- It cannot run inside a transaction block longer than `statement_timeout` allows
- `CREATE INDEX CONCURRENTLY` (needed later) rejects transaction blocks
- We need progress tracking and pause/resume capability

```sql
-- migrations/0003_backfill_primary_email/migration.sql
-- Phase 2: Data backfill runner
-- This file is a no-op placeholder for the migration registry.
-- The actual backfill runs as: psql -f scripts/backfill_primary_email.sql

-- No DDL here. See scripts/backfill_primary_email.sql for the cursor implementation.
```

**Real work lives in `scripts/backfill_primary_email.sql`:**

```sql
-- scripts/backfill_primary_email.sql
-- Bounded batch backfill for primary_email on users table (120M rows)
-- Run with: psql -v ON_ERROR_STOP=1 -f scripts/backfill_primary_email.sql

\echo '=== Primary Email Backfill ==='
\echo 'Started at: ' || clock_timestamp()

-- Configuration
DO $$
DECLARE
    batch_size     CONSTANT INT := 10000;
    max_runtime_ms CONSTANT BIGINT := 300000;  -- 5 minutes max per session
    idle_between   CONSTANT INTERVAL := '200ms';
    checkpoint_every CONSTANT INT := 50;      -- checkpoint row count
    rows_processed BIGINT := 0;
    last_checkpoint BIGINT := 0;
    session_start  TIMESTAMPTZ := clock_timestamp();
    batch_result   RECORD;
    total_estimate BIGINT;
BEGIN
    -- Get rough total for ETA display
    SELECT reltuppers
    INTO total_estimate
    FROM pg_class
    WHERE relname = 'users';

    RAISE NOTICE 'Estimated total rows: %, batch size: %', total_estimate, batch_size;

    -- Main cursor loop
    FOR batch_result IN
        SELECT u.id, u.email
        FROM users u
        WHERE u.primary_email IS NULL
          AND u.email IS NOT NULL
          AND u.id > COALESCE(
              (SELECT meta_value::BIGINT FROM _backfill_progress WHERE meta_key = 'last_id'),
              0
          )
        ORDER BY u.id
        LIMIT :batch_size
        FOR UPDATE SKIP LOCKED
    LOOP
        UPDATE users
        SET primary_email = batch_result.email
        WHERE id = batch_result.id;

        rows_processed := rows_processed + 1;

        -- Progress checkpoint every N batches
        IF mod(rows_processed, checkpoint_every) = 0 THEN
            -- Update progress marker (idempotent: always advances)
            INSERT INTO _backfill_progress (meta_key, meta_value, updated_at)
            VALUES ('last_id', batch_result.id::TEXT, now())
            ON CONFLICT (meta_key)
            DO UPDATE SET meta_value = GREATEST(_backfill_progress.meta_value, batch_result.id::TEXT),
                          updated_at = now();

            -- Report progress
            RAISE NOTICE '[%] Processed %, last_id = %',
                clock_timestamp() - session_start,
                rows_processed,
                batch_result.id;
        END IF;

        -- Yield between batches to reduce load on hot connections
        PERFORM pg_sleep(:idle_between);

        -- Abort if session exceeds runtime budget
        IF (clock_timestamp() - session_start) > make_interval(secs => :max_runtime_ms / 1000) THEN
            RAISE NOTICE 'Runtime budget exhausted. Saving progress. Resumable.';
            EXIT;
        END IF;
    END LOOP;

    IF rows_processed > 0 THEN
        -- Final checkpoint for the last batch
        INSERT INTO _backfill_progress (meta_key, meta_value, updated_at)
        VALUES ('last_id', batch_result.id::TEXT, now())
        ON CONFLICT (meta_key)
        DO UPDATE SET meta_value = GREATEST(_backfill_progress.meta_value, batch_result.id::TEXT),
                      updated_at = now();

        RAISE NOTICE 'Batch completed in this session. Total processed: %', rows_processed;
    ELSE
        RAISE NOTICE 'No remaining rows to backfill in this pass.';
    END IF;

    RAISE NOTICE 'Session finished at: %', clock_timestamp();
END $$;
```

**Progress tracking table:**

```sql
-- Create once (before first backfill run)
CREATE TABLE IF NOT EXISTS _backfill_progress (
    meta_key   TEXT PRIMARY KEY,
    meta_value TEXT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Seed initial state
INSERT INTO _backfill_progress (meta_key, meta_value)
VALUES ('last_id', '0')
ON CONFLICT (meta_key) DO NOTHING;
```

**Execution pattern** (cron or manual, repeat until complete):

```bash
# Run periodically until fill rate reaches 100%
while true; do
    psql -v ON_ERROR_STOP=1 -f scripts/backfill_primary_email.sql
    # Check remaining
    REMAINING=$(psql -t -A -c \
      "SELECT count(*) FROM users WHERE primary_email IS NULL AND email IS NOT NULL")
    echo "Remaining: $REMAINING"
    [ "$REMAINING" = "0" ] && break
    sleep 60
done
```

**Timeout guardrails baked in:**
- **Per-session limit:** 5 minutes (`max_runtime_ms`) — prevents runaway sessions
- **Statement timeout:** Ensure client sets `SET statement_timeout = '30s';` per batch (PG default is usually unlimited or very high, but setting it capsa individual `UPDATE` statement)
- **SKIP LOCKED:** Avoids blocking on concurrent writes modifying the same rows
- **Order by id:** Deterministic, sequential I/O pattern minimizes random page fetches
- **pg_sleep between batches:** Throttles insert-heavy workloads, reduces WAL pressure

**Row count estimate:** At 10K rows/batch × 200ms idle ≈ 50K rows/min. At 120M rows, worst case is ~40 minutes continuous run — well within a single session's budget.

**Rollback:** Triggers capture new writes going forward. Just drop the triggers (M002 rollback) and the old code resumes writing only to `email`. Any rows missed during the backfill will be caught by triggers until all replicas transition.

### M007 — Final: Drop old column and unique constraint

```sql
-- migrations/0007_drop_legacy_email_column/migration.sql
-- Phase 4c: Remove deprecated column
-- ONLY run after ALL replicas are on Step 2+ code.
-- ACCESS EXCLUSIVE lock is brief (<1ms on modern PG, no row rewrite).

BEGIN;

-- Drop the unique constraint on the old column first (must happen before DROP COLUMN)
ALTER TABLE users DROP CONSTRAINT IF EXISTS unique_users_email;

-- Drop the old column
ALTER TABLE users DROP COLUMN IF EXISTS email;

-- Now enforce uniqueness on the new column
ALTER TABLE users ADD CONSTRAINT unique_users_primary_email UNIQUE (primary_email);

COMMIT;
```

**Rollback of M007 (if immediately needed):**

```sql
-- Restore the email column (instant — metadata only, data was never freed)
ALTER TABLE users ADD COLUMN email TEXT;

-- Restore unique constraint (instant)
ALTER TABLE users ADD CONSTRAINT unique_users_email UNIQUE (email);

-- Immediately revert application code to read email, stop writing primary_email
-- Restart any crashed replicas (they'll now see email column restored)
```

**Caveat:** The data wasn't physically deleted by `DROP COLUMN` — Postgres marks the column as deleted but keeps the data in-place until VACUUM runs. So a quick redeploy of old code referencing `email` may still work depending on whether the ORM regenerates models. Full safety requires immediate rollback of the app deploy plus a schema revert.

## 9. Index Strategy Summary

| Index | When Built | Method | Notes |
|---|---|---|---|
| Existing: `idx_users_email` (on `email`) | Pre-existing | — | Remains active until M007 |
| Unique: `unique_users_email` | Pre-existing | — | Remains until M007 drops `email` |
| New: `idx_users_primary_email` (partial) | M005 | `CONCURRENTLY` | WHERE clause skips NULL rows, ~60% smaller than full index |
| New: `unique_users_primary_email` | M007 | Standard | Added after `email` dropped — no dupe risk |

The partial index (`WHERE primary_email IS NOT NULL`) saves ~30–40% storage and build time compared to indexing all 120M rows. If all rows get a primary_email eventually, this shrinks further to negligible savings, but during the transition it matters significantly.

## 10. Per-Stage Rollback Playbook

| Stage | Trigger | Rollback Steps | Data Loss Risk |
|---|---|---|---|
| M001 (ADD COLUMN) | ALTER fails | `ALTER TABLE users DROP COLUMN primary_email;` | None — nothing written |
| M002 (Triggers installed) | Triggers cause write failures | Drop triggers, drop functions | None — triggers were extra copies only |
| Deploy Step 1 (Dual-write) | High error rate on new replicas | Rolling restart back to old binary | None — old replicas still write to `email` |
| M003 (Backfill) | WAL bloat fills disk | Kill cursor script, vacuum aggressively | None — triggers protect against missing rows |
| Deploy Step 2 (Read-flip) | Missing email data in reads | Roll back to old code that reads `email` | None — fallback `primary_email ?? email` covered |
| M005 (Index build) | Too much I/O contention | `CANCEL QUERY <pid>;` — CONCURRENTLY leaves partial index that auto-cleans on cancel | None |
| M007 (DROP COLUMN) | Older replicas crash | Re-deploy old code + `ALTER TABLE users ADD COLUMN email TEXT` | Low — data still in place until VACUUM; code rollback must happen within minutes |

**Hard rollback (full revert to pre-migration state):**

```bash
# 1. Revert all application code to pre-migration
git revert <all migration-related commits>
kubectl rollout restart deployment/user-service  # or equivalent

# 2. Reverse migrations in reverse order
kysely migrate down    # or: psql -f migrations/0007_...down.sql
kysely migrate down
# ... continue down to 0001

# 3. VACUUM to reclaim space
VACUUM users;
```

## 11. Edge Cases and Gotchas

**Duplicate emails during transition:** Because both `email` and `primary_email` hold identical values throughout (enforced by dual-writes and triggers), the existing `UNIQUE(email)` constraint naturally protects `primary_email` too. Once `email` is dropped in M007, transfer the uniqueness to `primary_email` atomically. No intermediate duplicate window exists.

**Concurrent writes during backfill:** Any INSERT or UPDATE to `email` after backfill starts is captured by triggers. Post-backfill, triggers ensure no gaps.
