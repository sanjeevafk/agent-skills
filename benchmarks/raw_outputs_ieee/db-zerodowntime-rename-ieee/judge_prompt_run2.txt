```sql
-- Returns number of rows actually updated
-- Uses row-level locks with timeout to avoid long waits
-- ============================================
CREATE OR REPLACE FUNCTION backfill_primary_email_batch(
    p_limit         INT  DEFAULT 5000,
    p_statement_timeout_ms INT DEFAULT 5000  -- 5 seconds per batch
)
RETURNS TABLE (
    rows_updated    BIGINT,
    batch_start_id  BIGINT,
    batch_end_id    BIGINT
) AS $$
DECLARE
    v_limit       INT := LEAST(p_limit, 10000);  -- Cap at 10k to keep row locks bounded
    v_timeout_ms  INT := GREATEST(p_statement_timeout_ms, 1000);
    v_start       timestamptz := clock_timestamp();
    v_ct          BIGINT;
BEGIN
    -- Enforce statement timeout for THIS function call
    PERFORM set_config('statement_timeout', v_timeout_ms::text, true);
    PERFORM set_config('lock_timeout', '2000', true);

    -- Process a batch ordered by PK to avoid deadlocks and ensure deterministic progress
    UPDATE users u
    SET primary_email = u.email
    FROM (
        SELECT id, email
        FROM users
        WHERE primary_email IS NULL
        ORDER BY id
        LIMIT v_limit
        FOR UPDATE SKIP LOCKED   -- Critical: avoids waiting on rows held by other workers
    ) ranked
    WHERE u.id = ranked.id
      AND u.primary_email IS NULL  -- Idempotency guard
    RETURNING count(*) INTO v_ct;

    RETURN QUERY
        SELECT
            COALESCE(v_ct, 0)::BIGINT,
            min(ranked.id)::BIGINT,
            max(ranked.id)::BIGINT

            SELECT id
            FROM users
            WHERE primary_email IS NULL
            ORDER BY id
            LIMIT v_limit
            FOR UPDATE SKIP LOCKED

    INSERT INTO migration_users_primary_email (phase, step, rows_processed, status,
```

## Phase 1: Expand (Schema Change Only)

**File:** `2026_08_26_001_add_users_primary_email.sql`

### DDL

```sql
-- Step 1a: Add nullable column — SHARE ROW EXCLUSIVE lock (~instant, no row rewrite)
ALTER TABLE users ADD COLUMN primary_email TEXT;

-- Step 1b: Create supporting index concurrent­ly — does NOT block writes
CREATE INDEX CONCURRENTLY idx_users_primary_email ON users (primary_email);

-- Step 1c: Build a trigger to keep columns in sync for NEW inserts and updates
CREATE OR REPLACE FUNCTION mirror_email_to_primary_email()
RETURNS TRIGGER AS $body$
BEGIN
  -- If the application hasn't yet set primary_email (old code path),
  -- copy whatever is in email into primary_email.
  IF NEW.primary_email IS DISTINCT FROM OLD.primary_email THEN
    -- New code already wrote primary_email; do not overwrite.
    NULL;  -- intentional: let explicit writes stand.
  END IF;

  IF NEW.primary_email IS NULL AND NEW.email IS NOT NULL THEN
    NEW.primary_email := NEW.email;
  ELSIF NEW.primary_email IS NULL AND NEW.email IS NULL THEN
    NULL;
  ELSE
    -- Both columns populated — trust the explicit primary_email value.
    NULL;
  END IF;

  RETURN NEW;
END;
$body$ LANGUAGE plpgsql IMMUTABLE;

DROP TRIGGER IF EXISTS trg_mirror_email_to_primary_email ON users;
CREATE TRIGGER trg_mirror_email_to_primary_email
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION mirror_email_to_primary_email();
```

### Lock behaviour

| Statement | Lock acquired | Blocks? | Duration |
|-----------|---------------|---------|----------|
| `ALTER TABLE ... ADD COLUMN primary_email TEXT` | `SHARE ROW EXCLUSIVE` on table | No row-level blocking. Other DDL (RENAME/DROP) waits; SELECT/UPDATE proceed unimpeded. | ~instant |
| `CREATE INDEX CONCURRENTLY` | `ACCESS SHARE` (during scan) → `ROW EXCLUSIVE` (while building) | **Does not block** concurrent SELECTs, INSERTs, UPDATEs, DELETEs. Does wait for other `CREATE INDEX CONCURRENTLY` on the same table to finish. | Scans 120M rows twice (once to snapshot, once to build). May take minutes depending on `maintenance_work_mem` / disk IO. |
| `CREATE / DROP TRIGGER` | `ACCESS EXCLUSIVE`? — NO. Triggers are catalog objects. Only requires `TRIGGER` privilege. No table lock beyond brief metadata validation. | No. | ~instant |

### What this leaves behind

- `email` column intact — old app code unchanged
- `primary_email` nullable — null for existing rows
- Trigger fires on every INSERT/UPDATE — adds negligible CPU (one variable comparison per row)
- New index built alongside old index — dual storage, but both needed during transition

### Rollback: `2026_08_26_001_rollback.sql`

```sql
-- Drop trigger (no lock impact)
DROP TRIGGER IF EXISTS trg_mirror_email_to_primary_email ON users;
DROP FUNCTION IF EXISTS mirror_email_to_primary_email();

-- Concurrent index drop — non-blocking
DROP INDEX CONCURRENTLY IF EXISTS idx_users_primary_email;
```

**Caveat:** `ALTER TABLE ... DROP COLUMN` acquires `ACCESS EXCLUSIVE`. On a live table it blocks ALL writes until it completes. For 120M rows this may take seconds to a minute. Acceptable for an emergency rollback of Phase 1 (which hasn't changed app code). If even that window is unacceptable, skip Phase 1 entirely — don't run the expansion at all.

### Bounded-batch backfill (run as a script, not a single transaction)

This is intentionally NOT pure DDL — it's a stored procedure designed to be invoked repeatedly or called once from an external orchestrator (Python shell script, pg_cron, etc.). It uses `FOR UPDATE SKIP LOCKED` to avoid contention with active application transactions.

```sql
DO $$
DECLARE
  v_batch     INT  := 5000;
  v_last_id   BIGINT := 0;
  v_total     BIGINT := 0;
  v_count     BIGINT;
  v_max_idle_ms INT := 500;  -- pause after each batch to let app traffic breathe

  v_total_rows BIGINT;
BEGIN
  SELECT COUNT(*) INTO v_total_rows FROM users WHERE primary_email IS NULL;
  RAISE NOTICE 'Total rows needing backfill: %', v_total_rows;

  WHILE v_last_id < (SELECT COALESCE(MAX(id), 0) FROM users) LOOP
    UPDATE users
    SET primary_email = u.email
    FROM (
      SELECT id, email
      FROM users
      WHERE id > v_last_id
        AND primary_email IS NULL
      ORDER BY id
      LIMIT v_batch
      FOR UPDATE SKIP LOCKED
    ) u
    WHERE users.id = u.id;

    GET DIAGNOSTICS v_count = ROW_COUNT;
    v_total := v_total + v_count;

    IF v_count = 0 THEN
      -- All remaining rows either already have primary_email (concurrent app write)
      -- or we've passed MAX(id); exit cleanly.
      EXIT;
    END IF;

    -- Update progress tracking
    UPDATE migration_progress
    SET last_id = v_last_id + v_batch
    WHERE name = '002_backfill_primary_email';

    v_last_id := v_last_id + v_batch;

    RAISE NOTICE 'Backfilled %.  Total so far: %/% (%.1f%%)',
      v_last_id, v_total, v_total_rows,
      (v_total::float / v_total_rows * 100);

    -- Yield: sleep in small increments so statement_timeout isn't triggered
    PERFORM pg_sleep((v_max_idle_ms::numeric / 1000));
  END LOOP;

  UPDATE migration_progress
  SET finished_at = now()
  WHERE name = '002_backfill_primary_email';

  RAISE NOTICE 'Backfill complete. Processed %, estimated total %.',
    v_total, v_total_rows;
END $$;
```

### Key design decisions

**Why `FOR UPDATE SKIP LOCKED`?** Active application transactions may hold row locks on rows that match the WHERE clause. `SKIP LOCKED` tells Postgres to skip those rows rather than waiting, so the backfill thread never blocks on app traffic. Rows skipped in one batch will appear as candidates again in the next iteration.

**Why `ORDER BY id LIMIT n` with `last_id` cursor?** Without ordering, the scan may revisit the same hot regions repeatedly. Scanning by ascending PK gives predictable sequential IO and lets us resume from exactly where we left off if interrupted.

**Batch size tuning — 5K rows:**
- At 5K rows × ~200 bytes per row ≈ 1 MB of WAL per batch — well within typical `wal_buffers` (64 MB+) and avoids WAL-fsync storms
- Transaction duration is short (< 500 ms on SSD) so autovacuum sees quick commit and cleans dead tuples promptly
- Adjust up to 10–20K if throughput allows and statement timeout is set appropriately

**Statement timeout guardrails:**

Run this *before* the DO block:
```sql
SET statement_timeout = '30s';   -- kills the whole DO block, not good
```

Better: wrap execution in a session-level config that the orchestrating script controls. A Python caller should:
- Set `statement_timeout = 0` (disabled) per-transaction inside the loop, since the outer DO handles its own timeouts via `pg_sleep`
- Or, better yet, split the backfill into a **reusable stored procedure** that returns row counts per invocation, letting the client loop externally without any transaction-spanning risk.

# Zero-Downtime `email → primary_email` Migration: 120M Rows, 8 Mixed-Version Replicas

## Architecture Overview

The core constraint is **mixed-version deployments** — some replicas still read `email`, others expect `primary_email`. Direct RENAME (`ALTER TABLE RENAME COLUMN`) fails because it takes an ACCESS EXCLUSIVE lock and instantly breaks anything referencing the old name. You must use the expand-contract pattern across five phases spanning several days.

---

## Lock Behavior Reference

Before the timeline, here's exactly what locks each operation takes and why:

| Operation | Lock Acquired | Blocks | Duration | Safe? |
|---|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN text` | `ACCESS SHARE` (on table) | Other schema changes | Instant (Postgres 11+) | ✅ Yes |
| `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 'x'` | `ACCESS SHARE` + rewrite | Reads/writes briefly | Full table scan | ⚠️ Risky on 120M |
| `CREATE INDEX CONCURRENTLY` | `INDEX_CONCURRENTLY` (very weak) | Nothing | Minutes–hours depending on throughput | ✅ Yes |
| `UPDATE ... WHERE id IN (subquery)` | Row-level `FOR UPDATE` on matched rows | Other writers to those rows | Per-batch only | ✅ Yes |
| `CREATE TRIGGER` | `ACCESS SHARE` | Schema mutations briefly | Instant | ✅ Yes |
| `DROP TRIGGER` | `ACCESS EXCLUSIVE` on trigger only | No table access blocked | Instant | ✅ Yes |
| `DROP COLUMN` | `ACCESS SHARE` | Other schema changes on same table | Fast (just metadata + TOAST cleanup) | ✅ Yes if TOAST handled |

Key takeaway: every single step listed below avoids `ACCESS EXCLUSIVE` on the `users` table. That means SELECTs, INSERTs, and UPDATEs continue serving traffic throughout.

## Phase 1 — Expand: Add Column + Index + Trigger Backward Compatibility

### Migration 01: `add_primary_email_column`

```sql
-- Forward-only, instant, no rewrite
ALTER TABLE users ADD COLUMN primary_email TEXT;

-- Concurrent index enables fast lookups on primary_email without blocking writes
CREATE INDEX CONCURRENTLY idx_users_primary_email ON users (primary_email);
```

**Lock behavior:** `ACCESS SHARE` on `users` — blocks other `ALTER TABLE` statements momentarily but not one reader or writer. `CREATE INDEX CONCURRENTLY` does not block reads or writes.

**Rollback:** Drop the index concurrently, then drop the column. Both are forward migrations:

```sql
DROP INDEX CONCURRENTLY IF EXISTS idx_users_primary_email;
ALTER TABLE users DROP COLUMN IF EXISTS primary_email;
```

> **Note:** You won't need this rollback if you keep the trigger alive. But having it proves reversibility.

### Migration 02: `dual_write_trigger`

Two approaches exist. Pick based on your stack:

#### Option A: Database Trigger (recommended for raw SQL / no-ORM environments)

```sql
CREATE OR REPLACE FUNCTION sync_primary_email() RETURNS TRIGGER AS $$
BEGIN
  -- If primary_email is being set explicitly, don't override it
  IF NEW.primary_email IS NOT NULL AND NEW.primary_email != '' THEN
    RETURN NEW;
  END IF;

  -- Otherwise copy from email (NULL-safe comparison)
  IF COALESCE(NEW.email, '') <> COALESCE(OLD.email, '') THEN
    NEW.primary_email := LOWER(TRIM(COALESCE(NEW.email, '')));
  ELSIF NEW.primary_email IS NULL AND COALESCE(NEW.email, '') = '' THEN
    -- Explicitly clear primary_email too
    NEW.primary_email := NULL;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql VOLATILE;

CREATE TRIGGER trg_sync_primary_email
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION sync_primary_email();
```

**Lock behavior:** CREATE TRIGGER acquires `ACCESS SHARE` on the table — instantaneous, no impact on traffic.

**What it achieves:** Any replica still calling `UPDATE users SET email = ?` will transparently populate `primary_email` as well. This is the safety net while mixed versions coexist.

**Rollback:**

```sql
DROP TRIGGER IF EXISTS trg_sync_primary_email ON users;
DROP FUNCTION IF EXISTS sync_primary_email();
```

Also forwards-only — harmless if run again.

#### Option B: ORM-Level Dual-Write (Django, Prisma, Drizzle, Kysely)

If you control the application code, prefer this over triggers. It avoids database-side execution context overhead (~5-15% per write) and gives you observability:

```python
# Django example — override save() or use a signal

    # model definitions...

    def save(self, *args, **kwargs):
        # Always maintain dual-write
        if self.email is not None:
            self.primary_email = self.email.strip().lower()
        super().save(*args, **kwargs)
```

Or at the repository level:

```python
async def update_email(user_id: UUID, new_email: str):
    conn = await get_db_connection()
    async with conn.transaction():
        await conn.execute(
            "UPDATE users SET email = $1, primary_email = LOWER(TRIM($1)) WHERE id = $2",
            new_email, user_id
        )
```

**Trade-offs:** Triggers guarantee coverage regardless of which code path writes. ORM-level dual-write is lighter but requires auditing every INSERT/UPDATE path. I recommend triggers initially, then removing them after Phase 4 when all code paths know about `primary_email`.

## Phase 2 — Bounded Batch Backfill with Lock-Aware Progress Tracking

### The Problem

A naive `UPDATE users SET primary_email = LOWER(email)` on 120M rows:
- Runs in a single transaction → holds locks indefinitely → causes connection pool exhaustion
- Fills WAL → potential disk space emergencies
- Can exceed `statement_timeout` if set

You're not just renaming a column. You're navigating:

### Stage 1: Expand — Add Column + Dual-Write Triggers

**Goal:** Introduce `primary_email` alongside `email`, ensuring both stay in sync from this point forward.

#### 1a. DDL — Add the new column (NO DATA LOSS risk)

```sql
ALTER TABLE users ADD COLUMN primary_email VARCHAR(255);
```

**Lock behavior:** `ALTER TABLE ... ADD COLUMN` without `DEFAULT` acquires only an `ACCESS ROW` lock (PostgreSQL 11+) because it writes no data — the column is simply NULL for all existing rows. This takes milliseconds and does NOT block reads or writes. If you add `NOT NULL`, it requires rewriting the entire table under `ACCESS EXCLUSIVE`. So we explicitly avoid defaults and null constraints here.

**Rollback:** `ALTER TABLE users DROP COLUMN primary_email;` — instant, zero cost. Safe at any point before stage 4.

#### 1b. Index the new column (CONCURRENTLY)

```sql
CREATE INDEX CONCURRENTLY idx_users_primary_email ON users (primary_email);
```

**Lock behavior:** `CONCURRENTLY` builds the index without blocking reads or writes. It runs in multiple passes and can take hours on 120M rows, but it never holds more than an `INDEX WRITE` lock which coexists with everything else. Two caveats:

1. It cannot run inside a transaction block. Run it standalone.
2. If interrupted, partially-built index files are cleaned up automatically.

**Rollback:** `DROP INDEX CONCURRENTLY idx_users_primary_email;` — fast, blocks briefly for `ACCESS EXCLUSIVE` only on the index, not the table.

#### 1c. Deploy code changes to ALL 8 replicas FIRST

Before triggers go live, every replica must be able to handle `primary_email` in INSERT/UPDATE paths. Deploy this change across all pods first, rolling restart one at a time. At this point, both columns exist in the database schema, but triggers don't yet exist on disk — old code stops reading/writing `email` (but nothing breaks since the column still exists).

This is the critical "all replicas ready" gate. No trigger fires until every pod has been cycled.

```sql
CREATE OR REPLACE FUNCTION fn_mirror_email_to_primary()
RETURNS TRIGGER AS $$
BEGIN
    NEW.primary_email := NEW.email;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql VOLATILE;

CREATE OR REPLACE FUNCTION fn_mirror_primary_to_email()
RETURNS TRIGGER AS $$
BEGIN
    NEW.email := NEW.primary_email;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql VOLATILE;

CREATE OR REPLACE FUNCTION fn_insert_both_email_fields()
RETURNS TRIGGER AS $$
BEGIN
    -- If caller provided neither (edge case), set both to whatever default exists
    IF NEW.email IS NULL AND NEW.primary_email IS NULL THEN
        RAISE EXCEPTION 'Neither email nor primary_email was provided for users insert';
    END IF;

    -- If only one was provided, mirror it to the other
    IF NEW.email IS NULL THEN
        NEW.email := NEW.primary_email;
    ELSIF NEW.primary_email IS NULL THEN
        NEW.primary_email := NEW.email;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql VOLATILE;
```

**Lock behavior:** `CREATE TRIGGER` acquires `ACCESS SHARE` on the table. This is acquired and released instantly. It does NOT block inserts, updates, or selects. Triggers fire inline with the triggering statement.

**Cost analysis:** Each affected row now pays for an extra field assignment per write. For a high-TPS system this matters. Consider whether ORM-level hooks (deployed earlier) alone could handle this instead of DB triggers. If using ORM events, skip triggers entirely — they're cheaper in application memory than roundtripping through PL/pgSQL execution context per row. Using triggers here keeps it database-level and immune to ORM version mismatches.

**Rollback:** `DROP TRIGGER trg_*_after ON users;` — each individually dropped, instant, no data impact. All triggers gone = dual-write stops. Old code continues writing to `email` safely.

### Stage 2: Backfill Existing Data — Bounded Batches with Lock-Aware Progress

**Goal:** Copy `email → primary_email` for all ~120M existing rows without locking out writes or exhausting memory/bandwidth.

#### 2a. Batching strategy

Process in batches of 5,000–10,000 rows. Why not millions? Larger batches increase transaction duration, which:

- Increases WAL growth
- Increases lock contention windows
- Increases replay time on standby replicas if any
- Risks hitting `statement_timeout` or connection pool timeouts

```sql
-- Single-batch example (wrapped in application logic, not a SQL script):
UPDATE users
SET primary_email = email
WHERE primary_email IS NULL
  AND id BETWEEN :batch_start AND :batch_end
RETURNING id;
```

Key details:

- **Use primary key range scanning** (`id BETWEEN`) not `LIMIT/OFFSET`. Offsets on 120M rows cause sequential scans over already-processed rows. Primary key ranges give exact partitioning.
- **Order by id ascending** within each batch to minimize hot-spotting if your PK uses a sequence.
- **Transaction-per-batch**: wrap each batch in its own transaction. This limits WAL retention, prevents long-running transaction IDs from aging out (which would force vacuum to keep dead tuples), and lets you resume after failure.
