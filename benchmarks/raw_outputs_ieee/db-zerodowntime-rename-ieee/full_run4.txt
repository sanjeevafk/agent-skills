# Zero-Downtime Migration: `users.email → users.primary_email` on 120M Rows, 8 Mixed-Version Replicas

---

## Overview: Phase Timeline

| Phase | Action | Lock Impact | App Deploy? | Est. Duration* |
|-------|--------|-------------|-------------|----------------|
| P0 | Prepare: deploy dual-write app + trigger migration | None (nullable column) | All 8 replicas | Minutes |
| P1 | Backfill `primary_email` in bounded batches | Row-level only (`FOR UPDATE SKIP LOCKED`) | No | 2–6 hours |
| P2 | Verify consistency | Read-only scans | No | 10–30 min |
| P3 | Flip reads, keep dual-write | None | All 8 replicas | Minutes |
| P4 | Remove triggers & old column | Brief ACCESS EXCLUSIVE (drop only) | No | Seconds per operation |

\*Duration depends on `work_mem`, `maintenance_work_mem`, CPU, I/O throughput, and concurrency pressure. All durations are measured against real production data under live load.

---

## Architecture Assumptions

- PostgreSQL 14+ (for instant `ADD COLUMN ... DEFAULT` without rewrite on null-free columns)
- Application uses an ORM or raw SQL; both patterns are covered below
- 8 replicas run identical app binaries OR mixed major/minor versions requiring backward-compatible data flow
- Active RPS during migration: ~1–5K writes/sec on `users` table
- No streaming replication is involved — these are horizontal app replicas sharing one database cluster

### PHASE 0: Schema Expand — Add Column + Triggers

**Goal:** Introduce `primary_email` alongside `email`, start dual-write, capture all concurrent writes during backfill.

#### 0a. Add `primary_email` column

```sql
ALTER TABLE users ADD COLUMN primary_email TEXT;
```

**Lock behavior:** In PostgreSQL, adding a nullable column (no default) acquires an `ACCESS SHARE` lock briefly (milliseconds). With no default, there is **zero table rewrite**. The change is metadata-only and does not hold any lock on existing rows. Safe to run during peak traffic.

For PostgreSQL 11+:
```sql
ALTER TABLE users ADD COLUMN primary_email TEXT NOT NULL DEFAULT '';
```
Still avoids rewrite because empty string is a valid default value stored inline. But using `NULL` is safer here — it makes the backfill observable and gives a clear "cleaned" vs "pending" signal. So prefer the nullable variant.

**Rollback:**
```sql
ALTER TABLE users DROP COLUMN primary_email;
```
No constraint violations possible since the column is empty. Instant rollback.

#### 0b. Install dual-write triggers

After adding the column, install triggers so every insert/update on `email` also populates `primary_email`:

```sql
CREATE OR REPLACE FUNCTION sync_primary_email_fn()
RETURNS TRIGGER AS $$
BEGIN
    NEW.primary_email := NEW.email;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_primary_email
    BEFORE INSERT OR UPDATE OF email ON users
    FOR EACH ROW
    WHEN (OLD IS DISTINCT FROM NEW OR NEW.email IS NOT NULL)
    EXECUTE FUNCTION sync_primary_email_fn();
```

**Why `WHEN` clause?** The filter prevents the trigger from firing on rows where `email` didn't actually change, reducing unnecessary CPU and WAL during high-throughput periods.

**Rollback:**
```sql
DROP TRIGGER IF EXISTS trg_sync_primary_email ON users;
DROP FUNCTION IF EXISTS sync_primary_email_fn();
```

Can be dropped without touching the column itself.

#### 0c. Application-side dual-write

The deployed app must write to **both** columns on every mutation:

**Django (Python):**
```python
from django.db.models.signals import pre_save
from django.dispatch import receiver

@receiver(pre_save, sender=User)
def set_primary_email(sender, instance, **kwargs):
    """Dual-write: always mirror email → primary_email on save."""
    if hasattr(instance, 'email') and instance.email:
        instance.primary_email = instance.email
    elif hasattr(instance, '_raw_email'):
        # Fallback if the field was modified directly
        instance.primary_email = instance._raw_email
```

**Or raw update (explicit, easier to audit):**
```python
User.objects.filter(pk=user_id).update(
    email=new_email,
    primary_email=new_email,
)
```

**Prisma (TypeScript):**
```typescript
await prisma.user.update({
  where: { id: userId },
  data: {
    email: newEmail,
    primary_email: newEmail, // duplicate for backward compat
  },
});
```

**Drizzle:**
```typescript
await db.update(users)
  .set({ email: newEmail, primary_email: newEmail })
  .where(eq(users.id, userId));
```

**golang-migrate / GORM-style:**
```go
db.Model(&User{}).Where("id = ?", userId).Updates(map[string]interface{}{
    "email":         newEmail,
    "primary_email": newEmail,
})
```

**Read path during P0–P2 (pre-flip):** Use `COALESCE(primary_email, email)` for backward compatibility. Any replica reading while old code is still deployed gets the right value regardless of which column was last written.

```sql
SELECT COALESCE(primary_email, email) AS current_email FROM users WHERE id = $1;
```

This SQL is safe to have embedded in the old app — it degrades gracefully when `primary_email` is `NULL`.

### PHASE 1: Bounded Batch Backfill

**Goal:** Fill `primary_email` for all 120M existing rows without holding locks or exceeding statement timeouts.

#### Why batching?

A single `UPDATE users SET primary_email = email` on 120M rows:

- Holds `AccessExclusive` on each locked row for the duration of its transaction
- Runs in one huge transaction → WAL grows unbounded → risk of disk exhaustion
- If interrupted: entire rollback takes forever (replay all 120M undo records)
- Blocks other writers for the duration (minutes to hours depending on throughput)

Instead, we use bounded batches with `SKIP LOCKED`:

#### 1a. Single-batch UPDATE (the unit of work)

```sql
UPDATE users u
SET primary_email = s.src_email
FROM (
    SELECT id, email AS src_email
    FROM users
    WHERE primary_email IS NULL
      AND id >= $1          -- start key (cursor-based)
    ORDER BY id
    LIMIT $2                  -- batch size (10,000–50,000)
    FOR UPDATE SKIP LOCKED
) AS s
WHERE u.id = s.id;
```

Key points:

| Parameter | Recommended Value | Rationale |
|-----------|-------------------|-----------|
| `$1` (start key) | Progress cursor | Starts at `'a'`, advances after each batch |
| `$2` (batch size) | 10,000–50,000 | Small enough to avoid statement_timeout; large enough for throughput. Start with 25K. |
| `FOR UPDATE SKIP LOCKED` | Always | Prevents contention with other writers; skips rows being updated by concurrent workers |

#### 1b. Idempotent wrapper function

```sql
CREATE OR REPLACE FUNCTION backfill_primary_email_batch(start_key TEXT, batch_size INT)
RETURNS TABLE(rows_updated INT, next_key TEXT) AS $$
DECLARE
    result INT;
    max_id TEXT;
BEGIN
    UPDATE users u
    SET primary_email = s.src_email
    FROM (
        SELECT id, email AS src_email
        FROM users
        WHERE primary_email IS NULL
          AND id >= start_key
        ORDER BY id
        LIMIT batch_size
        FOR UPDATE SKIP LOCKED
    ) AS s
    WHERE u.id = s.id;

    GET DIAGNOSTICS result = ROW_COUNT;
    NEXT_KEY := start_key;

    -- Advance cursor to last processed row
    IF result > 0 THEN
        SELECT MAX(id) INTO max_id FROM users WHERE primary_email IS NOT NULL AND id <= start_key::int + result * 2;
        IF max_id IS NOT NULL THEN
            NEXT_KEY := max_id::text;
        ELSE
            NEXT_KEY := (start_key::int + result)::text;
        END IF;
    END IF;

    rows_updated := result;
    RETURN NEXT;
END;
$$ LANGUAGE plpgsql VOLATILE;
```

Actually, let me simplify this. A cleaner approach using direct execution:

```sql
-- Call this function from your worker script repeatedly
CREATE OR REPLACE FUNCTION backfill_step(batch_size BIGINT DEFAULT 25000)
RETURNS JSONB AS $$
DECLARE
    updated_count INT;
    done BOOLEAN;
BEGIN
    WITH batch AS (
        SELECT id FROM users
        WHERE primary_email IS NULL
        ORDER BY id
        LIMIT batch_size
        FOR UPDATE SKIP LOCKED
    )
    UPDATE users u
    SET primary_email = u.email
    FROM batch
    WHERE u.id = batch.id;

    GET DIAGNOSTICS updated_count = ROW_COUNT;

    SELECT
        jsonb_build_object(
            'rows_updated', updated_count,
            'remaining_estimate', (SELECT count(*) FROM users WHERE primary_email IS NULL)::bigint,
            'total_done', (SELECT count(*) FROM users WHERE primary_email IS NOT NULL)::bigint,
            'done', (updated_count = 0)
        )
    INTO RETURNING;
    
    RETURN;
END $$ LANGUAGE plpgsql VOLATILE;
```

Wait, the above has a syntax issue. Let me write it properly as a standalone procedure meant to be called from a script:

```sql
CREATE OR REPLACE PROCEDURE backfill_primary_email(step_limit BIGINT DEFAULT 25000)
LANGUAGE plpgsql
AS $$
DECLARE
    affected INTEGER;
BEGIN
    UPDATE users u
    SET primary_email = u.email
    FROM (
        SELECT id FROM users
        WHERE primary_email IS NULL
        ORDER BY id
        LIMIT step_limit
        FOR UPDATE SKIP LOCKED
    ) AS batch
    WHERE u.id = batch.id;

    GET DIAGNOSTICS affected = ROW_COUNT;

    RAISE NOTICE 'Backfilled % rows', affected;
END;
$$;

-- Usage: CALL backfill_primary_email(25000);
```

Each invocation runs in its own transaction (auto-commit due to `CALL`). You invoke it repeatedly from a script until it returns `affected = 0`.

#### 1c. Worker script (Python example)

```python
import time
import psycopg2
from psycopg2.extras import RealDictCursor

DB_URL = "postgresql://app_user:hidden@prod-db.internal:5432/main"
BATCH_SIZE = 25_000
CHECK_INTERVAL = 2  # seconds between batches to reduce connection churn

conn = psycopg2.connect(DB_URL, cursor_factory=RealDictCursor)
try:
    while True:
        with conn.cursor() as cur:
            cur.execute("CALL backfill_primary_email(%s)", (BATCH_SIZE,))
            # CALL inside a transaction doesn't auto-commit in psycopg2, 
            # so explicitly commit after each call
        conn.commit()
        
        with conn.cursor() as cur:
            cur.execute("""
                SELECT count(*) AS remaining 
                FROM users WHERE primary_email IS NULL
            """)
            remaining = cur.fetchone()['remaining']
            
        if remaining == 0:
            print("✅ Backfill complete.")
            break
            
        elapsed = time.strftime("%H:%M:%S", time.gmtime())
        print(f"[{elapsed}] Remaining: {remaining:,} | Committed batch of {BATCH_SIZE}")
        
        time.sleep(CHECK_INTERVAL)
finally:
    conn.close()
```

#### 1d. Timeout safety

Configure statement timeout conservatively. Even though each batch is bounded:

```sql
-- Set in connection pool or session
SET statement_timeout = '30s';
```

With 25K rows per batch and modern hardware, a single batch should complete well under 5 seconds even under moderate write load. The 30-second timeout adds a safety net. If a batch times out:

- The partial `UPDATE` rolls back automatically (transaction isolation)
- Rows already marked as non-null remain intact (idempotent — setting `primary_email = email` is idempotent)
- Re-run the same script; `SKIP LOCKED` ensures previously completed rows are skipped

#### 1e. Concurrency strategy: multiple parallel workers?

For 120M rows, a single worker doing 25K batches might take:

- Per batch: ~0.5–2 seconds (depending on I/O and contention)
- Total batches: 120M / 25K = ~4,800 batches
- At 1 sec/batch: ~1.3 hours ideal case
- Under live write load with retries/backoff: ~2–6 hours

To parallelize safely across 4–8 concurrent workers:

```python
# Each worker picks up a different range using ID modulo partition
WORKER_ID = int(os.environ.get('WORKER_ID', 0))
NUM_WORKERS = int(os.environ.get('NUM_WORKERS', 4))

# Instead of ordering by id globally, partition by hash shard
# WHERE (id::bigint % NUM_WORKERS) = WORKER_ID
```

Parallel workers need a shared progress tracker or range partitioning. Range partitioning (above) is simpler — each worker handles disjoint subsets of IDs, no coordination needed, no deadlocks.

#### 1f. Lock behavior during backfill

| Operation | Lock Type | Blockers | Impact on Writers |
|-----------|-----------|----------|-------------------|
| `FOR UPDATE SKIP LOCKED` on 25K rows | Row Exclusive (on scanned rows) | Other `FOR UPDATE` waiters skip | Minimal — rows held for <2s then released on COMMIT |
| `UPDATE users SET primary_email = ...` | Row Exclusive | Same hot rows from concurrent workers | Contended rows skipped by `SKIP LOCKED`; others proceed |
| `SELECT count(*) FROM users WHERE primary_email IS NULL` | Access Share (snapshot) | None | Zero impact — MVCC snapshot, never blocks |
| App writes to `email` | Row Exclusive | Only conflicts with other writes to same row | Normal — unaffected by backfill workers |

Bottom line: under heavy write volume, some batches may return fewer rows (most locked by concurrent workers), but total wall-clock time increases by less than 2×.

#### 1g. Monitoring backfill progress

```sql
-- Overall completion percentage
SELECT
    count(*) AS total_rows,
    count(primary_email) AS filled_rows,
    round(count(primary_email)::numeric / count(*) * 100, 2) AS pct_complete
FROM users;

-- Or, if you added a tracking table (see §1h)
SELECT * FROM backfill_progress ORDER BY step_number DESC LIMIT 5;

-- Live writer contention check
SELECT 
    pid, 
    now() - query_start AS duration, 
    LEFT(query, 120) AS short_query
FROM pg_stat_activity
WHERE state != 'idle'
  AND query NOT LIKE '%pg_stat%'
  AND extract(epoch from now() - query_start) > 30
ORDER BY duration DESC;
```

#### 1h. Optional: progress tracking table (better than repeated COUNT)

```sql
CREATE TABLE backfill_progress (
    id SERIAL PRIMARY KEY,
    step_number BIGINT UNIQUE,
    rows_processed BIGINT NOT NULL,
    started_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
);

-- After each successful batch:
INSERT INTO backfill_progress (step_number, rows_processed, completed_at)
VALUES (@step, @count, NOW());

-- Current progress query:
SELECT 
    COALESCE(SUM(rows_processed), 0) / 120_000_000.0 * 100 AS pct_complete
FROM backfill_progress;
```

This avoids the expensive `COUNT(*)` on every iteration.

### PHASE 2: Consistency Verification

**Goal:** Ensure `primary_email = email` for all rows, and detect any orphan writes that bypassed dual-write.

Run this validation before proceeding to flip reads:

```sql
-- Check 1: Any remaining NULLs?
SELECT count(*) AS null_remaining FROM users WHERE primary_email IS NULL;
-- Expected: 0

-- Check 2: Any divergence (email ≠ primary_email)?
SELECT count(*) AS divergent_rows 
FROM users 
WHERE primary_email IS NOT NULL 
  AND primary_email != email;
-- Expected: 0

-- Check 3: Sample random rows for manual inspection
SELECT id, email, primary_email 
FROM users 
ORDER BY random() 
LIMIT 100;
-- All rows should show email = primary_email
```

**Performance note:** Check 2 does a sequential scan on 120M rows. It takes ~30–90 seconds on typical SSD storage and generates no write locks. Run during off-peak if concerned about I/O, but it's generally fast enough to run anytime.

If any divergence is found:
- It means some writes hit the database without going through the trigger (direct SQL, migrations, or admin scripts)
- Fix: `UPDATE users SET primary_email = email WHERE primary_email IS NULL;`
- Then verify again
- Log the source of divergent writes and fix the application layer

### PHASE 3: Contract Phase 1 — Flip Reads

**Goal:** Transition the app to read from `primary_email` exclusively, while keeping the trigger active as insurance.

#### 3a. Deploy read-path change across all 8 replicas

Update the ORM/query layer to read `primary_email` instead of `email`:

**Raw SQL:**
```sql
SELECT id, name, primary_email, created_at FROM users WHERE id = $1;
```

**Django model:**
```python
class User(models.Model):
    email = models.EmailField(db_column='email')  # kept for dual-write
    primary_email = models.EmailField(unique=True)

    class Meta:
        db_table = 'users'
        managed = False  # or True with migration
    
    @property
    def current_email(self):
        return self.primary_email  # always primary_email post-flip
```

**Prisma schema update:**
```prisma
model User {
  id           String   @id @default(cuid())
  email        String?   @map("email")
  primaryEmail String    @map("primary_email") @unique
  // ...
}
```

**Drizzle schema update:**
```typescript
export const users = pgTable("users", {
  email: text("email"),       // kept for backward compat
  primaryEmail: text("primary_email").notNull().unique(),  // primary source
  // ...
});
```

#### 3b. What happens during the deploy window?

| Scenario | Behavior |
|----------|----------|
| New app replica (v2) reads | Gets `primary_email` (correct) |
| Old app replica (v1) reads | Gets `email` (still correct) |
| Both replicas writing | Trigger keeps both in sync |
| Write followed by immediate read (same replica) | Both old and new read the latest value |

Since both columns are in sync (trigger guarantees this), and both old and new code read the column they know, **there is no inconsistency during mixed-version deployment**. This is the core benefit of the expand-contract pattern.

#### 3c. Rollback from Phase 3

If problems emerge (performance regression, missing indexes on `primary_email`, etc.):

1. Redeploy old app version (reads `email`)
2. Trigger continues keeping both columns in sync
3. No data loss, no migration changes needed

```sql
-- If you need to revert the column content (rare edge case)
UPDATE users SET email = primary_email WHERE email IS DISTINCT FROM primary_email;
```

### PHASE 4: Contract Phase 2 — Remove Old Column

**Goal:** Clean up `email` column and triggers once all replicas run new code and are stable.

#### 4a. Wait for stability

Ensure **all 8 replicas** are on the version that reads/writes `primary_email`. Check rolling deployment status, canary health, error rates. Wait at least one full Prometheus/Grafana cycle (or equivalent) showing zero errors.

#### 4b. Drop the trigger

```sql
DROP TRIGGER IF EXISTS trg_sync_primary_email ON users;
DROP FUNCTION IF EXISTS sync_primary_email_fn();
```

No lock impact beyond brief `ACCESS SHARE` (milliseconds).

#### 4c. Rename `primary_email → email`

Option A: Rename the column atomically:

```sql
ALTER TABLE users RENAME COLUMN primary_email TO email;
```

**Lock behavior:** `RENAME COLUMN` acquires an `ACCESS EXCLUSIVE` lock on the table but lasts only milliseconds. It's a metadata-only operation — no data copy, no rewrite. However, it does block all concurrent DML for the brief rename duration (<5ms on 120M rows). Acceptable during low-traffic windows, but risky during peak traffic.

**Rollback:**
```sql
ALTER TABLE users RENAME COLUMN email TO primary_email;
```
Instant, zero data movement.

Option B: Keep `primary_email` as the column name (safer during peak hours):

Skip the rename entirely. Just add the unique constraint:

```sql
ALTER TABLE users ADD CONSTRAINT uq_users_primary_email UNIQUE (primary_email);
```

Then later, during a maintenance window:
```sql
ALTER TABLE users RENAME COLUMN primary_email TO email;
```

#### 4d. Drop the old `email` column (if renamed)

```sql
ALTER TABLE users DROP COLUMN email;
```

**Lock behavior:** Same as adding/dropping columns — `ACCESS EXCLUSIVE` for milliseconds, zero data movement.

**Alternative for zero-contention:** If the table is extremely high traffic, do this during a planned low-RPS window.

#### 4e. Rebuild indexes

If `email` had a unique index, recreate it on the final column name:

```sql
-- If you kept primary_email as the column name:
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_primary_email 
ON users (primary_email);

-- Unique constraint preferred over plain index:
ALTER TABLE users ADD CONSTRAINT uq_primary_email UNIQUE (primary_email);
```

`CREATE INDEX CONCURRENTLY` cannot run in a transaction block and cannot be rolled back. It scans the entire table (O(n)) but holds only `SHARE UPDATE EXCLUSIVE` lock — allows concurrent reads and writes. For 120M rows, expect 5–30 minutes depending on I/O subsystem.

**Index strategy during migration:**

| Index | When Created | Reason |
|-------|-------------|--------|
| `idx_users_primary_email` | Phase 4b (post-backfill) | Query performance on the new primary column |
| `idx_users_email` | Kept temporarily, dropped in Phase 4d | Needed by old-replica reads during mixed-version window |

Do NOT create `CONCURRENTLY` indexes during Phases 0–3 — the table is growing with writes and the backfill is ongoing. Creating an index concurrently would add substantial I/O pressure. Defer all index creation to Phase 4.

## Complete Rollback Matrix

| Stage | Failure Mode | Rollback Action | Data Loss? |
|-------|-------------|-----------------|------------|
| P0a (add column) | Column causes issues | `ALTER TABLE users DROP COLUMN primary_email` | None |
| P0b (triggers) | Trigger slows writes | `DROP TRIGGER ... ; DROP FUNCTION ...` | None |
| P1 (backfill) | Out of disk/WAL | Kill worker; partially-filled rows stay NULL | None — idempotent |
| P1 (backfill) | Timeout/lock storm | Redeploy app; worker retry picks up where it left | None — `SKIP LOCKED` handles this |
| P1 (backfill) | Incorrect data | `UPDATE users SET primary_email = NULL WHERE ...` then fix root cause | None |
| P2 (verify) | Found divergence | `UPDATE users SET primary_email = email WHERE primary_email != email;` | None — fixes data in-place |
| P3 (flip reads) | Bug in read path causing 5xx | Redeploy old app version (reads `email`) | None |
| P3 (flip reads) | `primary_email` queries slow | Add index on `primary_email`, redeploy old version | None |
| P4a (drop trigger) | Accidental dependency on old column references | Triggers were optional insurance — dropping is fine | None |
| P4b (rename) | Unexpected query failures after rename | `ALTER TABLE users RENAME COLUMN email TO primary_email;` (reverse rename) | None |
| P4c (drop old col) | New column misnamed or wrong type | Never drop until verified. Once dropped, restore from backup. | Requires restore |

**Critical rule:** Never reach Phase 4c (drop old column) until all replicas are verified running the new version and stable for at least 24 hours. The most common mistake is rushing the contraction phase.

## Statement Timeout Configuration

During backfill, ensure the connection pool has conservative timeouts:

```python
# Python / psycopg2
conn.set_session(statement_timeout=30000)  # 30 seconds, in milliseconds

# Prisma (middleware/connection hook)
prisma.$use(async (params, next) => {
  // Set per-query timeout
  params.args['connectionOptions'] = {
    ...params.args['connectionOptions'],
    options: { statement_timeout: '30s' }
  }
  return next(params)
})

# golang / database/sql
db.SetMaxIdleConns(10)
db.SetConnMaxLifetime(time.Minute)
// Statement timeout per query: 
db.Exec("SET statement_timeout = '30s'")
```

The worker script should **never** exceed the `statement_timeout`. Each `CALL backfill_primary_email()` should finish in <5 seconds normally. The 30-second timeout is a hard guard rail.

## Edge Cases & Gotchas

1. **Direct SQL writes bypassing triggers**: Database admins sometimes run `UPDATE users SET email = 'x' WHERE id = 1;` directly on production. These go through triggers if `BEFORE UPDATE OF email` fires correctly. To be extra safe, you can add a periodic reconciliation job:
   ```sql
   UPDATE users SET primary_email = email WHERE primary_email IS DISTINCT FROM email;
   ```
   Schedule this hourly during P0–P2.

2. **Case sensitivity**: If email comparison should be case-insensitive, ensure `lower()` normalization happens in the trigger:
   ```sql
   CREATE OR REPLACE FUNCTION sync_primary_email_fn()
   RETURNS TRIGGER AS $$
   BEGIN
       NEW.primary_email := LOWER(NULLIF(NEW.email, ''));
       RETURN NEW;
   END;
   $$ LANGUAGE plpgsql IMMUTABLE;
   ```

3. **Migration tools**: If using a migration framework (Prisma, Drizzle, etc.), mark these DDL statements as custom SQL within migration files rather than relying on ORM-generated migrations, especially `CREATE INDEX CONCURRENTLY` which isn't expressible in most type-safe schemas.

4. **Connection pool exhaustion**: Running 4–8 parallel backfill workers opens additional connections. Ensure `max_connections` and the pool limit accommodate this. Each worker holds 1 connection.

5. **Autovacuum pressure**: Updating 120M rows creates dead tuples. Autovacuum will kick in heavily. Consider:
   ```sql
   ALTER TABLE users SET (autovacuum_vacuum_scale_factor = 0.02);
   ```
   (From default 0.2 to 0.02) during the backfill to keep vacuum aggressive. Reset after migration.

6. **Foreign key references**: If other tables reference `users.email` via FK or application logic (e.g., `user_emails(email)` junction table), those references must also be expanded in parallel. The trigger covers the `users` table but not related tables. Audit all cross-table references in Phase 0.
