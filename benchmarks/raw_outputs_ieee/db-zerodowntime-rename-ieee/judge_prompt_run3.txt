## Schema & Lock Behavior Reference

| DDL Statement | Lock Type | Duration | Blocks App Writes? |
|---|---|---|---|
| `ALTER TABLE ADD COLUMN <nullable>` | `ACCESS EXCLUSIVE` (catalog only) | <1s | No (metadata-only) |
| `CREATE INDEX ON huge_table` | `EXCLUSIVE` | minutes-hours | **Yes** — blocks all writes |
| `CREATE INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` → brief `ACCESS EXCLUSIVE` | minutes-hours | No except final ~seconds |
| `REINDEX CONCURRENTLY` | same as above | minutes | No except final ~seconds |
| `ALTER TABLE DROP COLUMN` | `ACCESS EXCLUSIVE` | seconds-minutes (vacuum scan) | **Yes** — must wait for all replicas off |

On a 120M-row table with typical indexes on `email`, a non-concurrent index would hold an `EXCLUSIVE` lock for many minutes, killing live traffic. Every step below uses `CONCURRENTLY` or metadata-only ops.

### Migration 1b — Triggers for Dual-Write

```sql
-- migrations/000011_dual_write_triggers.up.sql

-- 1. Function: keep primary_email synced on INSERT
CREATE OR REPLACE FUNCTION sync_primary_email_on_insert()
RETURNS TRIGGER AS $$
BEGIN
  NEW.primary_email := NEW.email;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_insert
  BEFORE INSERT ON users
  FOR EACH ROW
  WHEN (NEW.primary_email IS NULL AND NEW.email IS NOT NULL)
  EXECUTE FUNCTION sync_primary_email_on_insert();

-- 2. Function: keep primary_email synced on UPDATE (when email changes)
CREATE OR REPLACE FUNCTION sync_primary_email_on_update()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.email IS DISTINCT FROM NEW.email THEN
    -- Only update primary_email if it hasn't diverged
    IF OLD.primary_email = OLD.email OR OLD.primary_email IS NULL THEN
      NEW.primary_email := NEW.email;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_update
  BEFORE UPDATE ON users
  FOR EACH ROW
  WHEN (OLD.email IS DISTINCT FROM NEW.email AND (OLD.primary_email IS NULL OR OLD.primary_email = OLD.email))
  EXECUTE FUNCTION sync_primary_email_on_update();

-- 3. Function: set primary_email to NULL when email is cleared
CREATE OR REPLACE FUNCTION sync_primary_email_on_delete()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.primary_email = OLD.email THEN
    RETURN OLD;  -- will naturally null out primary_email via FK/cascade if needed
  END IF;
  RETURN OLD;
END;
$$ LANGUAGE plpgsql IMMUTABLE;
```

**Lock analysis:** Trigger creation is `ACCESS EXCLUSIVE` on the specific relation for a few seconds only (DdlCommandEnd lock). Very short. No row-level impact. Rollback: `DROP TRIGGER` — instant.

## 1. Lock Behavior Analysis

Every DDL statement's lock impact before proceeding:

| Statement | Access Lock Held | Exclusive Lock On? | Rows Locked? | Duration | Safe for Prod? |
|---|---|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN new_col TEXT` | ACCESS MODIFIED | No | No | Milliseconds (catalog write only) | Yes — instant, even at 120M rows |
| `ALTER TABLE ... ADD COLUMN ... DEFAULT true` | ACCESS MODIFIED | No | No | Instant (PG 11+ stores default in catalog, no rewrite) | Yes |
| `CREATE INDEX ON users(email)` | EXCLUSIVE | Yes | All rows scanned under lock | Minutes–hours on 120M | **No** — blocks all writes |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE (brief at start & end) | No | No sustained lock | Minutes–hours, but non-blocking | Yes |
| `UPDATE users SET ...` (single massive statement) | RowExclusive (table level) | Brief table lock | All matching rows pinned briefly | Seconds–minutes, but huge undo log | **Risky** — risk of statement_timeout, undo bloat |
| `DELETE FROM users ... LIMIT n` | RowExclusive | Brief per-batch | Batch-size rows | Short per-batch | Yes — if bounded |
| `ALTER TABLE ... DROP COLUMN` | ACCESS EXCLUSIVE | Yes (brief) | No row rewrite | Milliseconds | Yes — safe once no code references it |
| `DROP TRIGGER` | ACCESS EXCLUSIVE (brief) | Yes (brief) | No | Milliseconds | Yes |
| `REINDEX CONCURRENTLY` (on partial index) | SHARE UPDATE EXCLUSIVE | No | No sustained | Comparable to initial build | Yes |

**Key insight:** The only dangerous operation at this scale is a single-shot UPDATE on 120M rows. Everything else is safe if done with CONCURRENTLY or batching.

### M002 — Write-through triggers (dual-write layer)

These triggers fire on INSERT/UPDATE to `email` and copy the value into `primary_email`. They provide a safety net for any writes that still hit `email` during the mixed-version period.

```sql
-- migrations/0002_dual_write_triggers/migration.sql
-- Phase 1: Triggers that ensure primary_email stays in sync
-- Impact: Minimal overhead per INSERT/UPDATE (PL/pgSL call + IF check)

BEGIN;

-- Trigger function for INSERTs (only path via ORM/app, not raw INSERT INTO users(email,...))
CREATE OR REPLACE FUNCTION _copy_to_primary_email_on_insert()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only copy if primary_email wasn't already set by app code
    IF NEW.primary_email IS NULL AND NEW.email IS NOT NULL THEN
        NEW.primary_email := NEW.email;
    END IF;
    RETURN NEW;
END;
$$;

-- Trigger function for UPDATEs on email column
CREATE OR REPLACE FUNCTION _copy_to_primary_email_on_update()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only copy when email is being changed AND primary_email hasn't been set independently
    IF OLD.email IS DISTINCT FROM NEW.email
       AND (NEW.primary_email IS NULL OR NEW.primary_email = OLD.email) THEN
        NEW.primary_email := NEW.email;
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_users_copy_email_to_primary_after_insert
    BEFORE INSERT ON users
    FOR EACH ROW EXECUTE FUNCTION _copy_to_primary_email_on_insert();

CREATE TRIGGER trg_users_copy_email_to_primary_after_update
    BEFORE UPDATE ON users
    FOR EACH ROW EXECUTE FUNCTION _copy_to_primary_email_on_update();

COMMIT;
```

**Performance note:** Each trigger adds ~5–15μs per write. On 120M rows with typical throughput (e.g., 5K inserts/sec, 50K updates/sec), that's <1ms additional latency per query. Acceptable.

**Rollback:**

```sql

DROP TRIGGER IF EXISTS trg_users_copy_email_to_primary_after_update ON users;
DROP FUNCTION IF EXISTS _copy_to_primary_email_on_insert();
DROP FUNCTION IF EXISTS _copy_to_primary_email_on_update();
COMMIT;

```sql

-- Migration tools wrap in BEGIN/COMMIT and may hit statement_timeout.
-- Execute with: psql -f scripts/backfill_primary_email.sql

-- Configure session-level timeouts
SET statement_timeout = '25s';       -- Kill individual batches at 25s (buffer under 30s DB limit)
SET lock_timeout = '5s';             -- Fail fast if we can't get a row lock
SET idle_in_transaction_session_timeout = '0';  -- Disable idle tx timeout (we commit frequently)

## 2. Phase 1b — Expand: Dual-Write Triggers

### Why Not ORM Events Alone

A replica running the old code won't know about `primary_email`, but writes via `INSERT/UPDATE` still fire triggers regardless of app version. This catches race conditions where the old replica wrote to `email` but never touched `primary_email`.

### Migration

```sql

### Trigger Function

```sql
CREATE OR REPLACE FUNCTION fn_sync_primary_email_from_email()
RETURNS TRIGGER AS $func$
BEGIN
  -- Only copy when:
  --   • primary_email is NULL (first write / backfill hasn't reached it yet), OR
  --   • email changed but primary_email didn't follow
  -- This avoids a tiny amount of extra WAL traffic after convergence.
  IF NEW.primary_email IS DISTINCT FROM NEW.email THEN
    NEW.primary_email := NEW.email;
  END IF;
  RETURN NEW;
END;
$func$ LANGUAGE plpgsql VOLATILE;
```

**Important:** The trigger uses `IS DISTINCT FROM` (not `<>`) so `NULL` values are handled correctly without special-casing.

### Rollback

```sql

DROP FUNCTION IF EXISTS fn_sync_primary_email_from_email() CASCADE;
```

> **Safe to remove at any time.** If you drop the trigger, nothing bad happens — old data in `primary_email` remains intact; only future writes to `email` will fail to propagate. You can re-add it later.

  END IF;

  rows_updated := v_count;
  RETURN NEXT;

## Architecture Overview

The core constraint: **you cannot atomically rename a column at schema level while running mixed app versions.** The solution is the expand/contract (alias) pattern with version-gated rollout.

```
Stage 1: Add `primary_email` (index-ONLY, instant)
Stage 2: Dual-write triggers → backfill
Stage 3: Verify consistency
Stage 4: Deploy new code to all 8 replicas
Stage 5: Flip reads → drop old column (contract)
Stage 6: Roll triggers, clean up
```

## DDL Lock Behavior Reference

| Statement | AccessModel lock | Wait behavior | Duration on 120M rows |
|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN ... TEXT` (no default) | ACCESS SHARE (reads continue) | Instant | ~0ms |
| `CREATE INDEX CONCURRENTLY ...` | No blocking writes | Waits for snapshots | Hours (parallel scan) |
| `ALTER TABLE ... RENAME COLUMN` | ACCESS EXCLUSIVE | **Blocks ALL reads/writes** | Seconds (catalog-only), but WAL flush may stall if concurrent queries |
| `ALTER TABLE ... DROP COLUMN` | ACCESS EXCLUSIVE | **Blocks ALL reads/writes** | Seconds + vacuum time |

**Key rule:** The only truly destructive DDL (`RENAME COLUMN`, `DROP COLUMN`) must happen after all replicas are on the new code. Every other step uses ACCESS SHARE or non-blocking concurrent indexes.

### 2a. Triggers for dual-write (before code deploy)

-- Only fire if old code hasn't already set it (avoids write amplification once new code ships)
CREATE OR REPLACE FUNCTION sync_email_to_primary_email() RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'DELETE' THEN
        DELETE FROM users WHERE id = OLD.id AND primary_email IS NOT NULL; -- cleanup edge case
        RETURN OLD;
    END IF;
    
    NEW.primary_email := COALESCE(NEW.primary_email, NEW.email);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

DROP TRIGGER IF EXISTS trg_users_sync_email ON users;
CREATE TRIGGER trg_users_sync_email

    FOR EACH ROW EXECUTE FUNCTION sync_email_to_primary_email();

DROP TRIGGER IF EXISTS trg_users_on_delete ON users;

    AFTER DELETE ON users
    FOR EACH ROW EXECUTE FUNCTION sync_email_to_primary_email();

Lock-aware: detects pg_lock contention and backs off.
Progress tracked in a lightweight metadata table so the process is resumable across restarts.
"""

import psycopg2
import psycopg2.extras
import time
import sys
import json
from contextlib import contextmanager

BATCH_SIZE = 10_000
IDLE_TIMEOUT_S = 30          # abort if stuck
HEARTBEAT_INTERVAL_S = 10    # how often to update progress
MAX_RETRIES = 5              # retry deadlocks/idle-txns

PROGRESS_TABLE = "_migration_progress"

@contextmanager
def db_conn(dsn):

    try:

        conn.commit()
    except Exception:

        raise
    finally:

    row = cur.fetchone()
    return int(row[0]) if row and row[0] else 0

    cur.execute(
        f"INSERT INTO {PROGRESS_TABLE} (key, value) VALUES ('users_backfill', %s) "

        (json.dumps({"last_id": last_id}), json.dumps({"last_id": last_id})),
    )

    """Main backfill loop."""
    with db_conn(dsn) as conn1:
        cur = conn1.cursor(name="backfill_cursor", cursor_factory=psycopg2.extras.RealDictCursor)
        
        # Idempotent setup
        init_progress(cur)
        last_id = get_offset(cur)
        
        # Skip rows already populated by triggers
        cur.execute("SELECT COUNT(*) FROM users WHERE primary_email IS NULL",)
        total = cur.fetchone()[0]
        print(f"Rows remaining to backfill: {total:,}")
        
        iterations = 0
        last_save = time.time()
        
        while True:
            retries = 0
            while retries < MAX_RETRIES:

                    # Cursor fetchmany avoids loading entire result into memory.
                    # We filter out rows that triggers already filled.
                    cur.itersize = BATCH_SIZE
                    cur.execute(
                        "SELECT id, email FROM users WHERE primary_email IS NULL AND id > %s ORDER BY id LIMIT %s",
                        (last_id, BATCH_SIZE),
                    )
                    batch = cur.fetchmany(BATCH_SIZE)

                        print("Backfill complete.")
                        cur.execute(

                        )
                        return

                    break  # success, exit retry loop
                
                except psycopg2.extensions.QueryCanceledError:
                    # Deadlock or lock timeout — the most common blocker
                    retries += 1
                    wait = min(retries * 2, 30)
                    print(f"  Lock detected, backing off {wait}s (retry {retries}/{MAX_RETRIES})")
                    time.sleep(wait)
                
                except psycopg2.errors.DeadlockDetected:
                    retries += 1
                    wait = min(retries * 3, 60)
                    print(f"  Deadlock, waiting {wait}s (retry {retries}/{MAX_RETRIES})")
                    time.sleep(wait)

                    conn1.rollback()
                    print(f"  Unexpected error: {e}, retrying...")
                    retries += 1
                    time.sleep(min(retries, 5))

            with db_conn(dsn) as conn2:

                    last_save = time.time()
