## Lock Behavior Reference

| Statement | Lock Mode | Blocks? | Duration |
|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN` (nullable) | AccessShare | Nothing | Instant |
| `CREATE INDEX` (concurrent) | IndexShareLock | Readers + other indexes only, NOT writes | Minutes for 120M |
| `UPDATE ... WHERE` (batched) | RowExclusiveRow | Rows being updated | Short per batch |
| `ALTER TABLE ... ALTER COLUMN ... SET NOT NULL` | AccessExclusive | Full table lock for seconds-minutes while checking | **Blocks writes during check** |
| `DROP COLUMN` | AccessExclusive | Full table lock while rewriting | Never do this on 120M without precautions |
| `ALTER TABLE ... RENAME COLUMN` | AccessExclusive | Brief (metadata-only) | Seconds — acceptable |

Key insight: you must **never** run `ALTER TABLE ... DROP COLUMN` or `SET NOT NULL` without first verifying no old replica will read the column. The rewrite cost on 120M is catastrophic.

## Phase 2: Dual-Write via Triggers

Deploy new code that writes to BOTH columns on INSERT and UPDATE. Existing code continues writing `email`. Triggers ensure `primary_email` mirrors it.

```sql
-- Migration 2: trigger-based dual-write (no DML, zero risk)
CREATE OR REPLACE FUNCTION users_sync_primary_email()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    NEW.primary_email := NEW.email;
    RETURN NEW;
  ELSIF TG_OP = 'UPDATE' THEN
    -- Only set if email changed OR primary_email was NULL (stale from backfill)
    IF NEW.email IS DISTINCT FROM OLD.email OR NEW.primary_email IS NULL THEN
      NEW.primary_email := NEW.email;
    END IF;
    RETURN NEW;
  ELSE
    RETURN OLD;
  END IF;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

DROP TRIGGER IF EXISTS sync_primary_email_insert ON users;
DROP TRIGGER IF EXISTS sync_primary_email_update ON users;

CREATE TRIGGER sync_primary_email_insert
  BEFORE INSERT ON users
  FOR EACH ROW EXECUTE FUNCTION users_sync_primary_email();

CREATE TRIGGER sync_primary_email_update
  BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION users_sync_primary_email();
```

**Lock:** No table locks. Functions are created in the catalog. Triggers fire per-row during existing INSERTs/UPDATEs — negligible overhead (< 1%).

**Important nuance:** The trigger uses `IS DISTINCT FROM` so NULL ↔ value transitions are caught. The `OR NEW.primary_email IS NULL` clause is critical: it catches rows backfilled by Phase 3 but which were subsequently updated on old replicas that wrote only `email`. Without this, a stale row could end up with mismatched values.

**Rollback:** Drop the triggers and function. The column remains for later use. Code continues dual-writing until rollback completes.

```sql
-- Batch size tuned for your latency budget.
-- For 120M rows at ~5K batches/sec throughput, expect ~1-2 hours.
-- Adjust BATCH_SIZE based on your p99 write latency. Lower = faster completion but more batches.

DO $$
DECLARE
  BATCH_SIZE CONSTANT BIGINT := 10000;
  last_id    BIGINT := COALESCE(
                 (SELECT last_id FROM migration_progress WHERE key = 'backfill_users'),
                 0);
  affected   INT;
  start_ts   TIMESTAMPTZ := NOW();
BEGIN
  LOOP
    -- Exit when we've covered the entire table
    EXIT WHEN last_id >= (SELECT MAX(id) FROM users);

    -- Check if someone paused us
    IF (SELECT paused FROM migration_progress WHERE key = 'backfill_users') THEN
      RAISE NOTICE 'Backfill paused';
      PERFORM pg_sleep(30);
      CONTINUE;
    END IF;

    -- Update the target column using the same value source as the trigger would
    -- This keeps consistency with live writes
    UPDATE users u
    SET primary_email = u.email
    WHERE u.id BETWEEN last_id + 1 AND last_id + BATCH_SIZE
      AND u.primary_email IS NULL;

    GET DIAGNOSTICS affected = ROW_COUNT;

    -- Record progress ATOMICALLY in the same transaction
    INSERT INTO migration_progress (key, last_id, synced_at)
      VALUES ('backfill_users', last_id + BATCH_SIZE, NOW())
      ON CONFLICT (key) DO UPDATE
        SET last_id = EXCLUDED.last_id,
            synced_at = EXCLUDED.synced_at;

    COMMIT;

    -- Reset statement timeout for next batch (default may be 1s in some setups)
    SET LOCAL statement_timeout = '5min';

    last_id := last_id + BATCH_SIZE;

    -- Report progress every 500 batches (~5M rows)
    IF (last_id % 5000000) < BATCH_SIZE THEN
      RAISE NOTICE 'Backfilled %.6M / %.6M rows (%.1f%%)',
        last_id::bigint / 1000000,
        (SELECT id::bigint FROM users ORDER BY id DESC LIMIT 1)::bigint / 1000000,
        (last_id * 100.0 / (SELECT COUNT(*) FROM users));
    END IF;

    -- Brief pause between batches to reduce WAL pressure and let replication keep up
    -- Increase if streaming replication is falling behind
    PERFORM pg_sleep(0.01);
  END LOOP;

  RAISE NOTICE 'Backfill complete at %, processed % in %',
    NOW(), last_id, NOW() - start_ts;
END $$;
```

### 3c. Why `BETWEEN id AND id + N` instead of OFFSET/LIMIT?

Postgres evaluates `WHERE` against physical tuple order, not logical id order. Using sequential `id` ranges gives optimal sequential scan behavior, avoids N+1 queries, and ensures no rows are skipped even under concurrent inserts. Adding `AND u.primary_email IS NULL` skips already-synced rows (from both backfill and live dual-writes), making repeated runs safe.

### 3d. Monitoring and control endpoints

You need these operational controls available via your admin API or CLI:

```bash

# Pause mid-flight

# Resume
```

### 3e. Statement timeout management

Each batch runs in its own transaction. Set `statement_timeout = '5min'` (or lower) per transaction via `SET LOCAL`. With `BATCH_SIZE = 10000` on an indexed `id` column, each batch typically completes in < 100ms. The timeout is a safety net for runaway scans (e.g., missing index). Make sure your connection pool doesn't override this — set it at the session level, not just globally.

### 3f. Lock behavior during backfill

Each `UPDATE ... WHERE id BETWEEN ...` acquires **RowExclusiveLock** on the matching rows. This means:
- Concurrent application writes wait briefly for rows in the batch window, then proceed
- No table-level locks
- No deadlocks (all operations touch by primary key range)
- Replication lag depends on throughput vs. write volume — monitor with `pg_replication_lag()`

If you observe unacceptable latency spikes, reduce `BATCH_SIZE` to 1000–5000 and accept longer wall-clock time.

### 3g. Rollback at Phase 3

Drop triggers, delete progress row. Application resumes normal writes to `email` only. New rows written during backfill are fine because triggers will re-sync them when re-deployed. Safe to revert the application code at any time.

**Backfill script** (`scripts/backfill_primary_email.py`):

```python
"""
Bounded-batch backfill for users.primary_email.
Safe to interrupt and resume. Runs under lock timeouts to avoid blocking app writes.
"""

import psycopg2
import time

BATCH_SIZE = 50_000          # ~50k rows per commit — balances WAL pressure vs throughput
LOCK_TIMEOUT_MS = 2_000      # abort if we block app writes for > 2s
STATEMENT_TIMEOUT_MS = 30_000  # kill long-running statements
SLEEP_BETWEEN_BATCHES_MS = 50  # yield CPU/time to other transactions

PG_CONN = psycopg2.connect("postgres:///yourdb")
MIGRATION_NAME = "add_primary_email_backfill"


def get_last_offset(conn):
    cur = conn.cursor()
    cur.execute(
        "SELECT last_pk FROM _migration_progress "
        "WHERE migration_name = %s ORDER BY updated_at DESC LIMIT 1",
        (MIGRATION_NAME,),
    )
    row = cur.fetchone()
    cur.close()
    return row[0] if row else 0


def save_offset(conn, pk):
    cur = conn.cursor()
    cur.execute(
        "INSERT INTO _migration_progress "
        "(migration_name, last_pk, committed, updated_at) "
        "VALUES (%s, %s, TRUE, NOW()) "
        "ON CONFLICT (migration_name) "
        "DO UPDATE SET last_pk = %s, committed = TRUE, updated_at = NOW()",
        (MIGRATION_NAME, pk, pk),
    )
    conn.commit()
    cur.close()


def run_backfill():
    conn = psycopg2.connect(PG_CONN.dsn)
    conn.set_session(readonly=False, autocommit=False)
    conn.set_client_encoding("UTF8")

    # Set timeouts to prevent locking issues
    conn.set_session(transaction_read_only=False)
    with conn.cursor() as cur:
        cur.execute(f"SET lock_timeout = '{LOCK_TIMEOUT_MS}ms'")
        cur.execute(f"SET statement_timeout = '{STATEMENT_TIMEOUT_MS}ms'")
        cur.execute("SET idle_in_transaction_session_timeout = '0'")  # don't timeout between batches

    offset = get_last_offset(conn)

    # Get max PK
    with conn.cursor() as cur:
        cur.execute("SELECT max(id) FROM users")
        max_pk = cur.fetchone()[0]

    total_rows = 0

    while offset < max_pk:
        batch_start = offset
        try:
            with conn.cursor() as cur:
                # Update next batch where primary_email IS NULL or was overwritten
                cur.execute("""
                    UPDATE users
                    SET primary_email = email
                    WHERE id > %s
                      AND id <= %s
                      AND (primary_email IS NULL OR primary_email <> email)
                    RETURNING 1;
                """, (offset, offset + BATCH_SIZE))

                count = sum(1 for _ in cur.fetchall())
                total_rows += count

            # Commit before saving progress so we never lose the checkpoint
            conn.commit()
            offset = offset + BATCH_SIZE
            save_offset(conn, offset)

            if total_rows % 1_000_000 == 0:
                print(f"Backfilled {total_rows:,} rows (offset={offset:,}/{max_pk:,})")

            # Small sleep to reduce contention on hot tables
            time.sleep(SLEEP_BETWEEN_BATCHES_MS / 1000.0)

        except psycopg2.LockTimeout:
            conn.rollback()
            print(f"Lock timeout at offset {offset:,}, retrying in 1s...")
            time.sleep(1)
        except psycopg2.Error as exc:
            conn.rollback()
            print(f"Error at offset {offset:,}: {exc}")
            raise

    print(f"Backfill complete: {total_rows:,} rows updated.")
    conn.close()


if __name__ == "__main__":
    run_backfill()
```

### DDL Lock Behavior

| Statement | Lock Type | Held For | Blocks DML? | Blocks Read? |
|---|---|---|---|---|
| `ALTER TABLE ... ADD COLUMN text` | **AccessExclusive** (but lightweight for nullable default-less column) | Schema transaction only | No (acquired & released instantly in PG ≥ 11 for null/no-default) | No |
| `CREATE TRIGGER ...` | **AccessExclusive** on the table | Schema transaction only | Briefly blocks DDL, not DML | No |

In PostgreSQL 11+, adding a nullable column with NO DEFAULT does not rewrite the table. It's a catalog-only metadata change. The AccessExclusive lock is held only for milliseconds.

### Migration SQL

```sql

-- Step 1a: Add the new column (instant, ~0ms lock in PG ≥ 11)
ALTER TABLE users ADD COLUMN primary_email TEXT;

-- Step 1b: Build a non-blocking B-tree index on the new column
-- Uses CONCURRENTLY so it doesn't block reads OR writes
CREATE INDEX CONCURRENTLY idx_users_primary_email ON users (primary_email);

-- Step 1c: Create AFTER INSERT OR UPDATE trigger for dual-write
-- Runs in the same transaction as the original write, so if dual-write fails,
-- the whole transaction rolls back — atomicity preserved

RETURNS TRIGGER AS $$
BEGIN
    IF NEW.email IS DISTINCT FROM OLD.email THEN
        -- Only set when email is being written/changed; leave primary_email alone
        -- if this is an insert where someone might have written primary_email directly
        NEW.primary_email := NEW.email;

    BEFORE INSERT OR UPDATE OF email ON users
    FOR EACH ROW
    WHEN (OLD IS DISTINCT FROM NEW OR TG_OP = 'INSERT')
```

## Phase 2 — Backfill Existing Rows in Bounded Batches

### Why Not a Single UPDATE?

A single `UPDATE users SET primary_email = email WHERE primary_email IS NULL` would:
1. Hold a RowExclusiveLock for minutes/hours on 120M rows
2. Create massive WAL generation, potentially filling disk
3. Risk statement_timeout kills mid-backfill (partial state)

### Batch Strategy with Progress Tracking

```sql
-- Create a durable progress-tracking table
CREATE TABLE IF NOT EXISTS migration_progress (
    phase       TEXT PRIMARY KEY,
    status      TEXT NOT NULL DEFAULT 'pending',  -- pending | running | done | failed
    batch_no    BIGINT NOT NULL DEFAULT 0,
    total_batch BIGINT NOT NULL DEFAULT 0,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    error_msg   TEXT
);

-- Seed Phase 2 progress entry
INSERT INTO migration_progress (phase, status)
VALUES ('backfill_email', 'pending')
ON CONFLICT (phase) DO NOTHING;

-- ===================================================================
-- BACKFILL PROCEDURE (call this repeatedly until done)
-- ===================================================================
-- Recommended batch size: 50,000–100,000 rows.
-- Each batch holds RowExclusiveLock for ~100-500ms on modern hardware.
-- With 120M rows at 50k/batch = 2,400 batches.

DO $$
DECLARE
    batch_size   INT := 50000;
    affected    INT;
    started_at  TIMESTAMPTZ := clock_timestamp();
    latest_batch BIGINT;
    total_est   BIGINT;
BEGIN
    -- Mark running
    UPDATE migration_progress
    SET status = 'running', updated_at = now(), error_msg = NULL
    WHERE phase = 'backfill_email';

    -- Estimate total batches (approximate, acceptable for display)
    SELECT
        GREATEST(CEIL(count / batch_size::BIGINT), 1)
    INTO total_est
    FROM users
    WHERE primary_email IS NULL;

    LOOP
        -- Update progress before each batch
        UPDATE migration_progress
        SET batch_no = COALESCE(batch_no, 0) + 1,
            total_batch = total_est,
            updated_at = now()
        WHERE phase = 'backfill_email';

        -- Get current batch number for reporting
        SELECT batch_no INTO latest_batch FROM migration_progress WHERE phase = 'backfill_email';

        -- ---- THE ACTUAL BACKFILL BATCH ----
        -- Uses a CTE with LIMIT for clean, bounded work per statement.
        -- Returns count of affected rows into 'affected'.
        WITH batch AS (
            SELECT ctid
            FROM ONLY users           -- skip inherited tables
            WHERE primary_email IS NULL
            ORDER BY ctid             -- predictable, cache-friendly order
            LIMIT batch_size
            FOR SHARE SKIP LOCKED     -- don't wait on concurrently-updated rows
        )
        UPDATE users u
        SET primary_email = u.email
        FROM batch b
        WHERE u.ctid = b.ctid;

        GET DIAGNOSTICS affected = ROW_COUNT;

        -- Done?
        EXIT WHEN affected = 0;

        -- Commit: loop ends, current transaction commits, next iteration starts fresh.
        -- This prevents long-running transactions.

        -- Optional: yield briefly between batches if the server is under load
        PERFORM pg_sleep(0.05);
    END LOOP;

    -- Mark done
    UPDATE migration_progress
    SET status = 'done', updated_at = now()
    WHERE phase = 'backfill_email';

RAISE NOTICE 'Backfill complete in %', clock_timestamp() - started_at;
END $$;
```

### Resume-After-Crash Behavior

If the process crashes mid-backfill:
1. Check `migration_progress` — status shows `running` with last `batch_no`
2. Re-run the same DO block. The `WHERE primary_email IS NULL` condition ensures already-backfilled rows are skipped.
3. The CTID scan is idempotent — a row that was already updated but whose batch didn't commit will just be re-set to the same value (harmless).

| Blocks READS? | No |
