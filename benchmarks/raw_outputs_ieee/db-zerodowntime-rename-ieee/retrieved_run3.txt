## Schema & Lock Behavior Reference

| DDL Statement | Lock Type | Duration | Blocks App Writes? |
|---|---|---|---|
| `ALTER TABLE ADD COLUMN <nullable>` | `ACCESS EXCLUSIVE` (catalog only) | <1s | No (metadata-only) |
| `CREATE INDEX ON huge_table` | `EXCLUSIVE` | minutes-hours | **Yes** — blocks all writes |
| `CREATE INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` → brief `ACCESS EXCLUSIVE` | minutes-hours | No except final ~seconds |
| `REINDEX CONCURRENTLY` | same as above | minutes | No except final ~seconds |
| `ALTER TABLE DROP COLUMN` | `ACCESS EXCLUSIVE` | seconds-minutes (vacuum scan) | **Yes** — must wait for all replicas off |

On a 120M-row table with typical indexes on `email`, a non-concurrent index would hold an `EXCLUSIVE` lock for many minutes, killing live traffic. Every step below uses `CONCURRENTLY` or metadata-only ops.

### Migration 1b — Triggers for Dual-Write

```sql
-- migrations/000011_dual_write_triggers.up.sql

-- 1. Function: keep primary_email synced on INSERT
CREATE OR REPLACE FUNCTION sync_primary_email_on_insert()
RETURNS TRIGGER AS $$
BEGIN
  NEW.primary_email := NEW.email;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_insert
  BEFORE INSERT ON users
  FOR EACH ROW
  WHEN (NEW.primary_email IS NULL AND NEW.email IS NOT NULL)
  EXECUTE FUNCTION sync_primary_email_on_insert();

-- 2. Function: keep primary_email synced on UPDATE (when email changes)
CREATE OR REPLACE FUNCTION sync_primary_email_on_update()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.email IS DISTINCT FROM NEW.email THEN
    -- Only update primary_email if it hasn't diverged
    IF OLD.primary_email = OLD.email OR OLD.primary_email IS NULL THEN
      NEW.primary_email := NEW.email;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_update
  BEFORE UPDATE ON users
  FOR EACH ROW
  WHEN (OLD.email IS DISTINCT FROM NEW.email AND (OLD.primary_email IS NULL OR OLD.primary_email = OLD.email))
  EXECUTE FUNCTION sync_primary_email_on_update();

-- 3. Function: set primary_email to NULL when email is cleared
CREATE OR REPLACE FUNCTION sync_primary_email_on_delete()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.primary_email = OLD.email THEN
    RETURN OLD;  -- will naturally null out primary_email via FK/cascade if needed
  END IF;
  RETURN OLD;
END;
$$ LANGUAGE plpgsql IMMUTABLE;
```

**Lock analysis:** Trigger creation is `ACCESS EXCLUSIVE` on the specific relation for a few seconds only (DdlCommandEnd lock). Very short. No row-level impact. Rollback: `DROP TRIGGER` — instant.

### App Code Changes (Deploy in Parallel with 1a/1b)

Every replica runs mixed versions, so the app must be backward compatible:

```python
# ORM layer example (PostgreSQL / SQLAlchemy style)

class User(Base):
    __table_args__ = {'schema': 'public'}

    id = Column(BigInteger, primary_key=True)
    email = Column(Text, nullable=True)            # legacy — still written
    primary_email = Column(Text, nullable=True)    # new — dual-written

    @classmethod
    def create_user(cls, session, email: str, **extra):
        """Dual-write: always set both columns."""
        user = cls(email=email, primary_email=email, **extra)
        session.add(user)
        return user

    def set_email(self, session, new_email: str):
        """Update both columns atomically within the same transaction."""
        self.email = new_email
        self.primary_email = new_email           # stays in sync
        session.flush()

    @property
    def display_email(self):
        """GRACE PERIOD: prefer primary_email, fall back to email."""
        return self.primary_email or self.email
```

Key rules during Phases 1–2:
- **All writes go to both `email` AND `primary_email`** (same transaction)
- **Reads still use `email`** (every replica version, including old ones, understand it)
- The `display_email` property gives a clean transition path

## Phase 2 — BACKFILL (Bounded Batches + Progress Tracking)

**Goal:** Populate `primary_email` for all existing rows where it's `NULL` without long transactions or statement timeouts.

### Batch Backfill Script

```sql
-- migrations/000012_backfill_primary_email.up.sql
-- Run via psql or your migration runner with --single-transaction OFF
-- Each invocation processes one batch, commits, records progress

-- 1. Create progress tracking table (idempotent)
CREATE TABLE IF NOT EXISTS migration_progress (
    migration_name   TEXT PRIMARY KEY,
    last_processed_id BIGINT DEFAULT 0,
    rows_processed   BIGINT DEFAULT 0,
    completed        BOOLEAN DEFAULT FALSE,
    last_run_at      TIMESTAMPTZ DEFAULT now(),
    error_message    TEXT
);

-- Ensure clean state
INSERT INTO migration_progress (migration_name, last_processed_id, rows_processed, completed)
VALUES ('backfill_12_primary_email', 0, 0, FALSE)
ON CONFLICT (migration_name) DO UPDATE
SET last_processed_id = GREATEST(migration_progress.last_processed_id, EXCLUDED.last_processed_id),
    rows_processed    = GREATEST(migration_progress.rows_processed, EXCLUDED.rows_processed),
    completed         = FALSE,
    last_run_at       = now(),
    error_message     = NULL;

-- 2. Helper: batch upsert (runs in <=500ms per batch, well under any timeout)
DO $$
DECLARE
    batch_size   INT := 5000;                          -- tune: ~100-500ms per batch
    start_id     BIGINT;
    end_id       BIGINT;
    rows_updated BIGINT;
    total_start  BIGINT := (SELECT COALESCE(MAX(id), 0) FROM users);
    current_id   BIGINT := (SELECT last_processed_id FROM migration_progress WHERE migration_name = 'backfill_12_primary_email');
BEGIN
    -- Process in batches until done
    WHILE current_id < total_start LOOP
        end_id := current_id + batch_size;

        UPDATE users
        SET primary_email = email
        WHERE id > current_id
          AND id <= end_id
          AND (primary_email IS NULL OR primary_email = email);

        GET DIAGNOSTICS rows_updated = ROW_COUNT;

        -- Update progress (this commit point lets us resume safely)
        UPDATE migration_progress
        SET last_processed_id = end_id,
            rows_processed    = rows_processed + rows_updated,
            last_run_at       = now()
        WHERE migration_name = 'backfill_12_primary_email';

        -- Brief pause to limit throughput pressure (adjust sleep duration)
        PERFORM pg_sleep(0.05);  -- 50ms between batches

        RAISE NOTICE 'Batch complete: processed up to id % (% rows updated)', end_id, rows_updated;

        current_id := end_id;
    END LOOP;

    -- Mark complete
    UPDATE migration_progress
    SET completed = TRUE,
        last_run_at = now()
    WHERE migration_name = 'backfill_12_primary_email';

    RAISE NOTICE 'Backfill complete: all % users processed', total_start;
END $$;
```

**Lock behavior:** `UPDATE ... WHERE id BETWEEN x AND y` acquires row-level locks on affected tuples, held only until the transaction commits (5000 rows ≈ instant). No table-level blocking. Other transactions can read/write unaffected rows concurrently.

**Timeout strategy:**
```ini
# postgresql.conf or session level — ensure this is generous
statement_timeout = 30s              -- individual query timeout (much less than batch duration)
lock_timeout = 5s                    -- fail fast if we can't acquire a row lock
idle_in_transaction_session_timeout = 60s
```

With `pg_sleep(0.05)` between batches and 5000-row chunks, each iteration completes in ~100-500ms, well within any timeout. If interrupted mid-batch, the progress table holds exactly where to resume.

**Rollback:** Drop the column and triggers. No data loss — `email` was never touched.

## Lock Behavior Deep Dive by Operation

### What Happens When Each DDL Runs

```
ALTER TABLE ADD COLUMN                  — Modifies pg_attribute (system catalog). No heap scan.
                                          Lock: AccessExclusive on table catalog (milliseconds).
                                          Heap tuples untouched. Active connections unaffected.

CREATE INDEX CONCURRENTLY               — Builds index in background.
                                          Phase 1: ShareUpdateExclusive (allows normal reads/writes)
                                          Phase 2: IndexBuildRegisterConstraint (brief)
                                          Phase 3: AcquireAccessShare on table (brief — ensures no one deletes it)
                                          Phase 4: AcquireAccessExclusive for validation (~seconds — blocks writes momentarily)
                                          Total: ~minutes to hours, but interactive downtime ~2-5 seconds.

DROP INDEX CONCURRENTLY                 — Similar profile. Brief AccessExclusive at end.

ALTER TABLE DROP COLUMN                 — ⚠️ ACTUALLY REMOVES ATTRIBUTE SLOT FROM EVERY TUPLE
                                          Requires a full table scan to rewrite heap pages.
                                          Lock: AccessExclusive held for the ENTIRE operation (2-5 minutes).
                                          During this window: NO reads, NO writes, NO queries of any kind.
                                          This is the only truly disruptive step. Schedule wisely.

ALTER TABLE ADD CONSTRAINT              — ShareLock on table (allows reads, blocks conflicting writes briefly)
                                          For unique constraints: validates all existing rows first
                                          (ScanLock — no write blocking). Then promotes to unique index.

TRIGGER CREATE/DROP                     — AccessExclusive on the table (milliseconds)
                                          No heap access. Just updates pg_trigger catalog.
```

### Why Non-Concurrent Index is Forbidden Here

```sql
-- ❌ NEVER DO THIS on 120M rows during production hours:
CREATE INDEX idx_users_primary_email ON users (primary_email);
-- Result: EXCLUSIVE lock on the table for the entire duration.
-- On 120M rows: could hold EXCLUSIVE for 10-30 minutes depending on storage speed.
-- Effect: ALL 8 app replicas deadlock. Connection pool exhausted. API down.

-- ✅ ALWAYS USE:
CREATE INDEX CONCURRENTLY idx_users_primary_email ON users (primary_email);
-- Result: Brief ~second-long pause at the end. Otherwise transparent.
```

## Timeout Configuration

Apply these settings per-session before running migrations:

```sql
-- Session-level timeouts (set via connection string or psql \set)
SET statement_timeout = '30s';           -- Kill runaway queries before they cascade
SET lock_timeout = '10s';                -- Fail fast if we can't grab a row lock
SET idle_in_transaction_session_timeout = '60s';  -- Prevent abandoned txns holding locks

-- Permanent postgresql.conf recommendations:
# statement_timeout = 30000            -- 30 seconds (already default in many setups)
# lock_timeout = 5000                  -- 5 seconds
# idle_in_transaction_session_timeout = 60000  -- 60 seconds
```

For the `DROP COLUMN` operation specifically, **do not rely on timeouts** — it will run its course. Instead, drain connections proactively:

```bash
# Before DROP COLUMN, kill idle connections:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = current_database()
  AND state = 'idle'
  AND state_change < now() - interval '5 minutes'
  AND pid <> pg_backend_pid();

# Wait for active transactions to finish (monitor):
watch -n 2 "psql -c \"SELECT count(*) FROM pg_stat_activity WHERE datname=current_database() AND state != 'idle' AND pid != pg_backend_pid()\""
```

When `count(*) = 0`, proceed with the drop.

```
     triggers live)       + reads flipped)      dropped)
              │                   │                   │
              ▼                   ▼                   ▼
      DROP COLUMNS/TRIGGERS   RESTORE old          FULL ROLLBACK
      Leave email untouched   code deployed         Requires:
                              for reads             1. Restore backups
                              (still dual-writes)   2. Restore triggers
                                                      3. Restore email column
                                                      4. Redeploy previous app version
```

### Detailed Rollback Scripts Per Stage

**After Phase 1 (safest rollback):**
```sql
-- Everything is additive. Just undo what we added.
DROP TRIGGER IF EXISTS trg_sync_insert ON users;
DROP TRIGGER IF EXISTS trg_sync_update ON users;
DROP FUNCTION IF EXISTS sync_primary_email_on_insert();
DROP FUNCTION IF EXISTS sync_primary_email_on_update();
DROP INDEX IF EXISTS idx_users_primary_email_unique;
DROP INDEX IF EXISTS idx_users_primary_email_lower;
ALTER TABLE users DROP COLUMN IF EXISTS primary_email;
-- Deploy old app version. Done. Zero data loss.
```

**After Phase 2 (backfill complete, Phase 1+2 rolled back):**
Same as above. The backfill writes are harmless — `primary_email = email` is a no-op duplication. Dropping the column erases all backfilled data.

**After Phase 3a (reads flipped, all replicas on new code):**
```sql
-- 1. Roll back app code first (deploy old version that reads email again)
-- 2. Then undo DB changes from Phases 1-2
DROP TRIGGER IF EXISTS trg_sync_insert ON users;
DROP TRIGGER IF EXISTS trg_sync_update ON users;
DROP FUNCTION IF EXISTS sync_primary_email_on_insert();
DROP FUNCTION IF EXISTS sync_primary_email_on_update();
DROP INDEX IF EXISTS idx_users_primary_email_unique;
DROP INDEX IF EXISTS idx_users_primary_email_lower;
ALTER TABLE users DROP COLUMN IF EXISTS primary_email;
```

**After Phase 3b (triggers dropped, before 3c):**
```sql
-- 1. Re-enable triggers to stop further divergence
CREATE TRIGGER trg_sync_insert
  BEFORE INSERT ON users
  FOR EACH ROW
  WHEN (NEW.primary_email IS NULL AND NEW.email IS NOT NULL)
  EXECUTE FUNCTION sync_primary_email_on_insert();
CREATE TRIGGER trg_sync_update
  BEFORE UPDATE ON users
  FOR EACH ROW
  WHEN (OLD.email IS DISTINCT FROM NEW.email AND (OLD.primary_email IS NULL OR OLD.primary_email = OLD.email))
  EXECUTE FUNCTION sync_primary_email_on_update();

-- 2. Redeploy app that reads email
-- 3. Fix root cause of failure
-- 4. Restart from Phase 3a when ready
```

**After Phase 3c (email column dropped):**
```sql
-- Full disaster recovery — restore from backup
-- 1. Restore database to pre-migration PITR snapshot
-- 2. Restore app to pre-migration version
-- 3. Drop any new indexes/constraints created after the savepoint
-- This is why we schedule DROP COLUMN during a maintenance window
-- and take a guaranteed-good backup immediately prior.
```

## Monitoring Dashboard Queries

Run these continuously during the migration window:

```sql
-- Active transactions holding locks on users table
SELECT pid, state, query, now() - query_start AS duration
FROM pg_stat_activity
WHERE datname = current_database()
  AND query LIKE '%users%'
  AND state != 'idle'
ORDER BY duration DESC;

-- Long-running queries (>10s)
SELECT pid, now() - query_start AS duration, LEFT(query, 100) AS snippet
FROM pg_stat_activity
WHERE datname = current_database()
  AND state = 'active'
  AND now() - query_start > interval '10 seconds'
  AND pid != pg_backend_pid()
ORDER BY duration DESC;

-- Table size over time (tracks backfill progress implicitly)
SELECT
    nspname AS schema,
    relname AS table,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_live_tup AS live_rows
FROM pg_stat_user_tables
WHERE relname = 'users';

-- Replicas lag (ensure all 8 are caught up)
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;
```

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Mixed-version replica reads email after Phase 3a flip | High | Null pointer crash | `display_email` returns error on null; alert immediately |
| Backfill slower than expected due to I/O saturation | Medium | Extends maintenance window | Reduce batch size to 2000; increase sleep to 100ms; monitor IOPS |
| Unique index conflict during backfill | Low | Transaction abort on batch | Triggers keep email=primary_email; check divergence post-backfill |
| DROP COLUMN hangs due to orphaned connections | Medium | Extended downtime | Drain idle connections beforehand; monitor pg_stat_activity |
| Trigger fires incorrectly causing infinite recursion | Near-zero | N/A | Triggers use `WHEN` clause; Plpgsql handles correctly |

---

That's the full sequence. The critical invariant at every stage: **nothing breaks if an old replica is still running**. The only truly risky operation is the final `DROP COLUMN email` — and that's confined to a maintenance window with drained connections.
