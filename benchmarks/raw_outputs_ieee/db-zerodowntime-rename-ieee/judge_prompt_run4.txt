    conn.set_session(autocommit=True)

    # accumulate long-running transactions or hold locks too long.
    cur = conn.cursor()
    cur.execute(f"SET statement_timeout TO '{MAX_STATEMENT_TIMEOUT_MS}ms'")
    cur.close()
    return conn

    cur.execute("""
        INSERT INTO schema_backfills (name, last_value)
        VALUES ('backfill_users_primary_email', NULL)
        ON CONFLICT (name) DO NOTHING
    """)

        UPDATE schema_backfills
        SET locked = true
        WHERE name = 'backfill_users_primary_email' AND locked = false
        RETURNING id
    """)

        raise SystemExit(1)

### Stage 1: EXPAND — Add New Column (Schema Expansion)

**DDL:**

```sql
ALTER TABLE users ADD COLUMN primary_email TEXT;

-- If NOT NULL will be required eventually, leave it nullable now.
-- We populate in Stage 2.

-- Concurrently build the index so reads never block.
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_primary_email
  ON users (primary_email) WHERE primary_email IS NOT NULL;
```

**Lock behavior:**

| Operation | Lock Type | Duration | Impact |
|---|---|---|---|
| `ADD COLUMN` (nullable/default) | `AccessExclusiveLock` on catalog only | **Milliseconds** | Blocks DDL, not DML. Reads/writes continue uninterrupted. This is safe because adding a column with no default does not require a full table rewrite. |
| `CREATE INDEX CONCURRENTLY` | `ShareUpdateExclusiveLock` (brief at start and end) | Minutes–hours depending on size | Allows concurrent reads and writes. The two brief lock acquisitions at start/end are < 1 second each. No DML is blocked. |

**Key details:**

- Adding a nullable column in Postgres does NOT trigger a heap rewrite. It just updates the catalog and sets a null bitmap per row (existing rows get a single null bit set). No long-running transaction, no WAL explosion.
- The `WHERE primary_email IS NOT NULL` partial index keeps the index small during the empty-and-filling period.
- If the eventual target is `NOT NULL`, add that constraint later when all rows are populated.

**Statement timeout considerations:** Neither operation uses long transactions. `CREATE INDEX CONCURRENTLY` runs outside any transaction block — it auto-commits after each step. Statement timeouts do not apply.

**Rollback path:**

```sql
DROP INDEX CONCURRENTLY IF EXISTS idx_users_primary_email;
ALTER TABLE users DROP COLUMN IF EXISTS primary_email;
```

Both are fast catalog operations. Zero data loss possible.

### Stage 2: Dual-Write Activation + Application Deployment

The exact implementation depends on the ORM/languages in use. Here are the canonical patterns:

#### ORM-level dual-write (e.g., SQLAlchemy-style)

```python
class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True)
    email = Column(TEXT, nullable=False)          # old column (kept)
    primary_email = Column(TEXT, nullable=True)   # new column (added)

    def set_email(self, value: str) -> None:
        """Single entry point for setting email — dual writes."""
        self.email = value
        self.primary_email = value

    @classmethod
    def upsert_email(cls, session, user_id: int, value: str) -> None:
        """Bypass getter/setter for bulk/update-from-SQL scenarios."""
        session.execute(
            text("""
                UPDATE users
                SET email = :value, primary_email = :value
                WHERE id = :id
            """),
            {"value": value, "id": user_id}
        )
```

#### Trigger fallback (defensive double-buffer)

Even if app code misses a write path, the database trigger ensures consistency. Deploy this as part of the same migration batch:

```sql
CREATE OR REPLACE FUNCTION sync_emails() RETURNS TRIGGER AS $$
BEGIN
    -- Guard against infinite recursion via triggers fired by triggers
    IF TG_OP = 'UPDATE' AND (NEW.email IS DISTINCT FROM OLD.email OR NEW.primary_email IS DISTINCT FROM OLD.primary_email) THEN
        -- Whichever one was written gets mirrored to the other
        IF NEW.email IS DISTINCT FROM NEW.primary_email THEN
            -- Heuristic: prefer primary_email (new column), fall back to email
            IF NEW.primary_email IS NOT NULL THEN
                NEW.email := NEW.primary_email;
            ELSE
                NEW.primary_email := NEW.email;
            END IF;
        END IF;
    ELSIF TG_OP = 'INSERT' AND NEW.email IS DISTINCT FROM COALESCE(NEW.primary_email, NEW.email) THEN
        IF NEW.primary_email IS NULL THEN
            NEW.primary_email := NEW.email;
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_sync_emails ON users;
CREATE TRIGGER trg_sync_emails
    BEFORE INSERT OR UPDATE ON users
    FOR EACH ROW
    EXECUTE FUNCTION sync_emails();
```

**Important:** This trigger mirrors the NEW value to whichever column is NULL. During dual-write, both columns are set by the app, so the trigger fires harmlessly. During migration (Stage 4), when some replicas still write only `email`, the trigger fills `primary_email`. After Stage 5, when the old column is dropped, the trigger becomes redundant.

### PHASE 0: Schema Expand — Add Column + Triggers

**Goal:** Introduce `primary_email` alongside `email`, start dual-write, capture all concurrent writes during backfill.

#### 0a. Add `primary_email` column

```sql
ALTER TABLE users ADD COLUMN primary_email TEXT;
```

**Lock behavior:** In PostgreSQL, adding a nullable column (no default) acquires an `ACCESS SHARE` lock briefly (milliseconds). With no default, there is **zero table rewrite**. The change is metadata-only and does not hold any lock on existing rows. Safe to run during peak traffic.

For PostgreSQL 11+:
```sql
ALTER TABLE users ADD COLUMN primary_email TEXT NOT NULL DEFAULT '';
```
Still avoids rewrite because empty string is a valid default value stored inline. But using `NULL` is safer here — it makes the backfill observable and gives a clear "cleaned" vs "pending" signal. So prefer the nullable variant.

**Rollback:**
```sql
ALTER TABLE users DROP COLUMN primary_email;
```
No constraint violations possible since the column is empty. Instant rollback.

#### 0b. Install dual-write triggers

After adding the column, install triggers so every insert/update on `email` also populates `primary_email`:

```sql
CREATE OR REPLACE FUNCTION sync_primary_email_fn()
RETURNS TRIGGER AS $$
BEGIN
    NEW.primary_email := NEW.email;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE TRIGGER trg_sync_primary_email
    BEFORE INSERT OR UPDATE OF email ON users
    FOR EACH ROW
    WHEN (OLD IS DISTINCT FROM NEW OR NEW.email IS NOT NULL)
    EXECUTE FUNCTION sync_primary_email_fn();
```

**Why `WHEN` clause?** The filter prevents the trigger from firing on rows where `email` didn't actually change, reducing unnecessary CPU and WAL during high-throughput periods.

**Rollback:**
```sql

DROP FUNCTION IF EXISTS sync_primary_email_fn();
```

Can be dropped without touching the column itself.

### PHASE 1: Bounded Batch Backfill

**Goal:** Fill `primary_email` for all 120M existing rows without holding locks or exceeding statement timeouts.

#### Why batching?

A single `UPDATE users SET primary_email = email` on 120M rows:

- Holds `AccessExclusive` on each locked row for the duration of its transaction
- Runs in one huge transaction → WAL grows unbounded → risk of disk exhaustion
- If interrupted: entire rollback takes forever (replay all 120M undo records)
- Blocks other writers for the duration (minutes to hours depending on throughput)

Instead, we use bounded batches with `SKIP LOCKED`:

#### 1a. Single-batch UPDATE (the unit of work)

```sql
UPDATE users u
SET primary_email = s.src_email
FROM (
    SELECT id, email AS src_email
    FROM users
    WHERE primary_email IS NULL
      AND id >= $1          -- start key (cursor-based)
    ORDER BY id
    LIMIT $2                  -- batch size (10,000–50,000)
    FOR UPDATE SKIP LOCKED
) AS s
WHERE u.id = s.id;
```

Key points:

| Parameter | Recommended Value | Rationale |
|-----------|-------------------|-----------|
| `$1` (start key) | Progress cursor | Starts at `'a'`, advances after each batch |
| `$2` (batch size) | 10,000–50,000 | Small enough to avoid statement_timeout; large enough for throughput. Start with 25K. |
| `FOR UPDATE SKIP LOCKED` | Always | Prevents contention with other writers; skips rows being updated by concurrent workers |

#### 1b. Idempotent wrapper function

```sql

    result INT;
    max_id TEXT;
BEGIN
    UPDATE users u
    SET primary_email = s.src_email
    FROM (
        SELECT id, email AS src_email
        FROM users
        WHERE primary_email IS NULL
          AND id >= start_key
        ORDER BY id
        LIMIT batch_size
        FOR UPDATE SKIP LOCKED

            NEXT_KEY := (start_key::int + result)::text;
        END IF;
```

## Phase 1 — Expand: Add Column + Dual-Write Triggers

### Step 1.1: Create the new column (concurrent, no exclusive lock)

**Lock behavior:** `ALTER TABLE ... ADD COLUMN` acquires `ACCESS EXCLUSIVE` but is essentially instant since it's just a catalog update (PG 11+). Duration: milliseconds. No data rewrite. Safe during production load.

**Rollback:** `BEGIN; ALTER TABLE users DROP COLUMN primary_email; COMMIT;` — also instant, catalog-only.

### Step 1.2: Write migration triggers (bidirectional guard rails)

These ensure every INSERT/UPDATE after this point writes to *both* columns until cutover.

```sql
CREATE OR REPLACE FUNCTION trg_sync_email_to_primary_email()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'DELETE' THEN
    RETURN NEW;
  END IF;

  -- Only sync when email was actually touched (avoid cascade updates from other columns)
  IF TG_OP = 'INSERT' OR (TG_OP = 'UPDATE' AND (NEW.email IS DISTINCT FROM OLD.email)) THEN
    NEW.primary_email := NEW.email;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_sync_email ON users;
CREATE TRIGGER trg_sync_email
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION trg_sync_email_to_primary_email();
```

**What this does:** Every app row that touches `email` now auto-fills `primary_email`. Old code writes `email`; the trigger copies it forward. New code can write to either column — if both are set, trust `primary_email` explicitly (see Step 1.3).

**Rollback:** Drop the trigger. Existing trigger-created data persists harmlessly in `primary_email`. Old code never references `primary_email`, so it's fine.

### Step 1.3: Deploy new code alongside old (canary rollout)

Update the application layer to handle both columns:

```python
# Pseudocode — ORM model update

    # old column stays, new column gets populated
    email = Column(String(320), index=True)
    primary_email = Column(String(320), nullable=True)

    def effective_email(self):

        self.primary_email = value
```

- Reads use `primary_email or email` — works on old code reads (uses `email`) and new code reads (prefers `primary_email`).

**Rollback at any point before backfill:** Stop deploying new code. Existing `primary_email` values are harmless nulls or stale copies. Old path unaffected.

### Step 2.3: Backfill worker (retryable, lock-aware)

```python
import psycopg2
from psycopg2 import sql, extras

def backfill(primary_host_config, max_runtime_s=None):
    conn = psycopg2.connect(**primary_host_config)
    conn.set_session(readonly=False, autocommit=False)
    cur = conn.cursor()

    start_time = time.monotonic()
    processed_total = 0
    consecutive_failures = 0

    while True:
        elapsed = time.monotonic() - start_time
        if max_runtime_s and elapsed >= max_runtime_s:
            print(f"[{elapsed:.0f}s] Time budget exhausted. Stopping safely.")
            break

        # ---- Atomic cursor acquisition (idempotent) ----
        cur.execute(
            "SELECT value FROM _migration_state WHERE key = 'email_backfill_cursor' "
            "FOR UPDATE SKIP LOCKED"
        )
        row = cur.fetchone()
        min_id = row[0] if row else 0

        # ---- Fetch & copy -----
        cur.execute(sql.SQL("""
            SELECT id, email
            FROM   users
            WHERE  id > %s AND primary_email IS NULL
            ORDER  BY id
            LIMIT  %s
        """), (min_id, BATCH_SIZE))
        rows = cur.fetchall()

        if not rows:
            # Nothing left — final consistency pass will confirm
            print("[backfill] Queue empty. Running final verification...")
            break

        # ---- Bulk UPDATE (single round-trip per batch) ----
        extras.execute_batch(
            cur,
            sql.SQL("UPDATE users SET primary_email = %s WHERE id = %s"),
            [(r[1], r[0]) for r in rows],
            page_size=BATCH_SIZE
        )
        affected = cur.rowcount
        conn.commit()

        # ---- Advance cursor atomically ----
        new_cursor = rows[-1][0]
        cur.execute(
            "UPDATE _migration_state SET value = %s, updated_at = now() "
            "WHERE key = 'email_backfill_cursor'",
            (new_cursor,)
        )
        conn.commit()

        processed_total += affected

        print(f"[{elapsed:.0f}s] Processed {processed_total} total "
              f"(batch: {affected}, cursor: {new_cursor})")

        consecutive_failures = 0
        time.sleep(POLL_INTERVAL_MS / 1000.0)

    conn.close()

    # Final stats
    print(f"[DONE] Backfill finished: {processed_total} rows updated. "
          f"Remaining NULL: {count_remaining()}")


def count_remaining():
    conn = psycopg2.connect(**primary_host_config)
    cur = conn.cursor()
```

### Step 2.4: Statement timeout avoidance

```sql
-- Set conservative timeouts in your connection pool config or session level:
SET statement_timeout = '10s';     -- kills runaway queries before they block
SET lock_timeout = '5s';            -- fail fast instead of waiting forever
SET idle_in_transaction_session_timeout = '30s';  -- prevents zombie txns
```

**Critical:** Do NOT set these globally for all connections — only in the migration worker's connection. Application connections should have their own (likely longer) timeouts. A good practice:

```python
conn = psycopg2.connect(**config)
cur = conn.cursor()
for stmt in ("SET statement_timeout = '10s'", "SET lock_timeout = '5s'"):
    cur.execute(stmt)
```

With 10s statement timeout + 10K batch size, a single batch takes <1s under normal conditions. Under extreme contention, the query dies cleanly and retries on next loop iteration — no partial corruption possible because we commit *after* the whole batch succeeds.
