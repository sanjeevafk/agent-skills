## Architecture Overview

```
ci.yml                      release.yml
├── detect-changes         ├── build-release
│   └── dorny/paths-filter    ├── per-app image build
├── dependency-cache        ├── SBOM generation
├── lint-all               └── attestation + signing
├── build-all
├── test-matrix            └── publish to GHCR
│   ├── node:20 | 22          └── tag push → prod deploy
│   └── shard 1/4 .. 4/4
├── preview-environments
│   ├── deploy per PR        OIDC Trust Flow
│   └── cleanup on close       GitHub ←→ AWS STS
└── merge-queue-check      └── no long-lived credentials
```

name: Release Pipeline

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:
    inputs:
      version:
        description: 'Release version (e.g., v1.2.3)'
        required: true
        type: string

permissions:
  contents: write
  packages: write
  id-token: write        # Required for OIDC + sigstore signing
  attestations: write

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

env:
  PNPM_VERSION: '9'
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

# ──────────────────────────────────────────────
# Job 1: Extract version and validate
# ──────────────────────────────────────────────
jobs:
  release-prepare:
    name: Prepare Release
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.version.outputs.version }}
      is_tag_release: ${{ steps.version.outputs.is_tag_release }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Extract version
        id: version
        run: |
          if [[ "${{ github.event_name }}" == "push" && "${{ github.event.ref }}" =~ ^refs/tags/v ]]; then
            VERSION="${GITHUB_REF#refs/tags/}"
            echo "is_tag_release=true" >> $GITHUB_OUTPUT
          else

## Section A: Cache-Key Design — Detailed Explanation

### Problem Statement

In a monorepo with 11 packages (3 apps + 8 libs), a naive caching approach fails in two ways:
1. **One global key** (`deps`) — stale data persists forever after a minor lockfile change since the key never rotates.
2. **No version prefix** — you can't evict old entries because every run reuses the same key name.

### Solution: Two-Layer Strategy with Versioned Keys

#### Layer 1 — Dependency Cache

```yaml
key:    deps-v1-${{ matrix.node-version }}-linux-${{ sha256sum(pnpm-lock.yaml)|cut(c1-16) }}
```

| Component | Purpose |
|-----------|---------|
| `deps-v1` | Eviction prefix — bump to `v2` to invalidate everything atomically |
| `$matrix.node-version` | Node major version isolates native modules (bcrypt, sqlite, etc.) |
| `linux` | Runner OS — Windows/macOS have different binary compatibility |
| `sha256sum(pnpm-lock.yaml)\|cut(1-16)` | First 16 hex chars (~64 bits) of the lockfile hash |

**Restore fallback chain:**
```
deps-v1-20-linux-<full-hash>     ← exact match, fast restore
deps-v1-20-linux-                 ← partial match, gets ~80% of cache
deps-v1-                          ← last resort, minimal restore
```

**Why SHA256 instead of MD5 or plain text hash:**
- pnpm-lock.yaml includes exact checksums of every resolved package tarball (from npm/registry, git URLs, local paths). Any change in *any* dependency, transitive dep, or peer-dep constraint changes the hash.
- The 16-char prefix is sufficient entropy for practical purposes — two different lockfiles having the same first 16 hex chars is astronomically unlikely (~1 in 2⁶⁴).
- We compute it once in `setup-env` job and pass the value through `needs.setup-env.outputs.lockfile_hash`. This avoids recomputing the hash 18+ times (11 packages × 2 Node versions).

**What gets cached:**
- `~/.local/share/pnpm/store/v3` — pnpm's global content-addressable store (the real savings)
- `node_modules/` — workspace symlinks (needed for monorepo inter-package resolution)
- `.next/cache` — framework-specific caches that are fast to regenerate but slow to fill

#### Layer 2 — Build Cache

```yaml
key: builds-v1-linux-<lockfile-hash>-<hash(tsconfig**.json, **/src/**/*.ts)>
```

| Component | Purpose |
|-----------|---------|
| `builds-v1` | Build cache eviction prefix |
| `linux` | OS gate |
| `<lockfile-hash>` | If deps change, downstream rebuilds may be needed |
| `<hash(all-tsconfigs + sources)>` | Source content hash — invalidated on any `.ts`/`.tsx` change |

**Critical detail:** The source hash globs over ALL source files in `packages/**/src/` and `apps/**/src/`, not just the changed package. This is the correct behavior for Turborepo-style caching because:

1. When `packages/core/src/index.ts` changes, `apps/web` depends on it and must rebuild
2. If we only hashed `apps/web/src/`, the rebuild would be skipped and the app would use stale `core/dist/`
3. Lockfile inclusion ensures that even a non-source-change dep upgrade triggers rebuilds

**Without Turborepo**, use per-package granularity:
```bash
for pkg in packages/core packages/utils apps/web; do
  PKG_HASH=$(sha256sum $pkg/src/**/*.ts | sort | sha256sum | cut -c1-16)
  CACHE_KEY="build-${pkg//\//_}-v1-linux-$PKG_HASH"
  actions/cache ...
done
```

But this costs 11 extra cache API calls per run — only worth it past ~15 packages.

#### Performance Impact

| Scenario | Without Cache | With Layer 1 | With Both Layers |
|----------|--------------|-------------|------------------|
| First run | ~3 min install | ~30 s download + ~30 s install | ~15 s download only |
| Dep change | ~3 min install | ~15 s install (re-hashed) | ~15 s download + rebuild |
| Docs-only change | N/A | ~15 s download only | ~15 s download only |
| App source change | ~3 min install + ~2 min build | ~15 s + ~30 s build | ~15 s + ~10 s (incremental) |

## Section B: OIDC Trust Configuration

### Why OIDC Instead of Long-Lived AWS Keys?

| Aspect | Static Keys | OIDC Federation |
|--------|------------|-----------------|
| Credential lifetime | Permanent (until rotated) | Per-job (~1 hour session) |
| Rotation burden | Manual every 30–90 days | Automatic per workflow run |
| Blast radius if leaked | Full AWS account access until rotation | Single job's scope, auto-expiring |
| Audit granularity | Shows key ID used | Shows exact workflow, branch, PR number |
| Compliance posture | Requires secret rotation policy | Natively zero-trust |

### AWS Side: IAM Role + Trust Policy

**Step 1: Create an OIDC identity provider in AWS**

In the AWS console (or via terraform/aws cli):
```
Provider URL: token.actions.githubusercontent.com
Audience: sts.amazonaws.com
```

**Step 2: Create roles with scoped trust policies**

Three roles for three tiers of access:

#### Production Role (strictest — main branch only)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringEquals": {
          "token.actions.githubusercontent.com:sub": "repo:<ORG>/<REPO>:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

Attach a minimal permissions policy:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecs:UpdateService",
        "ecs:DescribeServices",
        "ecs:DescribeTaskDefinition",
        "ecs:RegisterTaskDefinition",
        "ecr:GetAuthorizationToken",
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:*:<ACCOUNT_ID>:log-group:/ecs/<REPO>*"
    }
  ]
}
```

#### Preview Role (broader — any PR)

The only difference from the production role is the `sub` condition:
```json
"StringLike": {
  "token.actions.githubusercontent.com:sub": "repo:<ORG>/<REPO>:pull_request"
}
```

This allows OIDC tokens from *any* PR branch but still within your repository. Fork PRs are excluded because GitHub adds `head.repo.fork == false` guard in the workflow (line visible in `ci.yml` preview jobs).

#### Cleanup Role (minimal — delete only)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "ecs:DeleteService",
      "ecs:DescribeServices",
      "ecs:ListServices"
    ],
    "Resource": "*"
  }]
}
```

You can combine cleanup into the preview role to save a role, but separation follows least-privilege.

### GitHub Side: Secret Reference

Store the role ARNs as repository secrets:

| Secret Name | Value | Used By |
|------------|-------|---------|
| `AWS_PRODUCTION_ROLE_ARN` | `arn:aws:iam::<ACC>:role/GitHubActions-ProdBlast` | `release.yml` → `deploy-production` |
| `AWS_PREVIEW_ROLE_ARN` | `arn:aws:iam::<ACC>:role/GitHubActions-PreviewBlast` | `ci.yml` → preview jobs + cleanup |

No `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` secrets needed.

### How It Works at Runtime

```
┌──────────────────────────────────────────────────┐
│  GitHub Actions Runner                           │
│                                                    │
│  1. Workflow starts with:                          │
│     permissions:                                   │
│       id-token: write                              │
│                                                    │
│  2. aws-actions/configure-aws-credentials@v4       │
│     reads:                                         │
│       role-to-assume = ${{ secrets.AWS_... }}      │
│                                                    │
│  3. GitHub issues a JWT                          │
│     (expires in 5 min)                            │
│     payload:                                       │
│       sub: repo:org/repo:ref:refs/heads/main       │
│       aud: sts.amazonaws.com                       │
│       exp: <epoch + 300>                           │
│       iat: <epoch>                                 │
│       iss: https://token.actions.githubusercontent.com │
│                                                    │
│  4. AWS STS exchanges JWT for creds              │
│     AssumeRoleWithWebIdentity()                    │
│     → validates trust policy matches sub claim     │
│     → returns temporary AWS credentials            │
│     → valid for session duration (default 1h)      │
│                                                    │
│  5. Subsequent aws CLI commands use these creds    │
└──────────────────────────────────────────────────┘
```

The JWT is short-lived (5-minute expiration), the resulting AWS session credentials expire after the role's session duration (typically 1 hour), and each workflow run gets its own unique session via the `role-session-name` parameter. There is zero persistence of credentials between runs.

### Verification Checklist

- [ ] IAM Identity Provider created with URL `token.actions.githubusercontent.com` and audience `sts.amazonaws.com`
- [ ] Production role's trust policy restricts `sub` to `ref:refs/heads/main`
- [ ] Preview role's trust policy restricts `sub` to `pull_request`
- [ ] No `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets exist in the repo
- [ ] Branch protection rules require `Deploy to Production` environment approval
- [ ] AWS CloudTrail logs are enabled (audit trail for every OIDC-assumed role)
- [ ] Role session duration set to ≤ 1 hour

## Section C: Merge Queue Wiring

GitHub's **merge queue** feature serializes PR merges so each queued commit is tested against *all* previously queued PRs merged on top — catching cross-PR conflicts before they reach main.

### Setup Steps

1. **Enable merge queue in branch protection** (Settings → Branches → Branch protection rules → Enable "Include administrators"):
   - ☑ Require pull request reviews
   - ☑ Require status checks to pass
   - ☑ Require branches to be up to date
   - ☑ Include administrator changes
   - ☑ **Require status checks to pass before merging** — select:
     - `lint`
     - `build`
     - `test` (all combinations resolve as one check via the aggregate job)
     - `ci-complete`

2. **Add `merge_group` trigger** — already included in the `on:` block of `ci.yml`:
   ```yaml
   on:
     push:
       branches: [main, develop]
     pull_request:
       branches: [main]
     merge_group:       # ← GitHub fires this when a PR enters the queue
   ```

3. **How GitHub handles it:**
   - PR enters queue → GitHub creates a merge commit (combining PR + all ahead commits)
   - Triggers `ci.yml` with `event_name == 'merge_group'` and `merge_group.head_sha` set
   - All status checks run against the merge commit
   - If all pass → GitHub merges the PR and removes it from the queue
   - If any fail → PR moves to back of the queue (doesn't block others)

4. **Optional: Limit queue size**
   - In Settings → General → Merge queue, set "Maximum number of PRs in queue" (default 5)
