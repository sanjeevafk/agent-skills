### Path-Filtering Behavior

| Changed Files | `web` | `admin` | `api_server` | `shared` | Jobs That Run |
|---|---|---|---|---|---|
| `apps/web/pages/...` | ✅ | ❌ | ❌ | ❌ | `detect-changes` sets only `web=true` → downstream jobs use `if: needs.detect-changes.outputs.web == 'true' || needs.detect-changes.outputs.shared == 'true'` |
| `packages/ui/...` | ✅ | ✅ | ❌ | ✅ | All 3 apps + shared jobs run |
| `README.md` | ❌ | ❌ | ❌ | ❌ | No job triggered (filters reject `.md`) |

To wire path-filters to downstream conditionals, append to each job:
```yaml
if: >-
  needs.detect-changes.outputs.shared == 'true'
  || (needs.detect-changes.outputs.web == 'true'  && github.repository_path == 'apps/web')
  || (needs.detect-changes.outputs.admin == 'true' && github.repository_path == 'apps/admin')
  || (needs.detect-changes.outputs.api_server == 'true' && github.repository_path == 'apps/api-server')
```

Or simpler: run `test`, `build-all`, and `deploy-preview` unconditionally (they're fast enough post-cache) and rely on the path-filtered job to only mark relevant apps as changed for review/reporting purposes.

```yaml
name: Deploy Production

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      version:
        description: 'Release version (e.g., v1.2.3)'
        required: true
        type: string

permissions:
  contents: read

jobs:
  prepare:
    name: Prepare Release
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.version.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Determine version
        id: version
        run: |
          if [ -n "${{ github.event.inputs.version }}" ]; then
            echo "tag=${{ github.event.inputs.version }}" >> "$GITHUB_OUTPUT"
          else
            echo "tag=v$(date +%Y%m%d%H%M%S)" >> "$GITHUB_OUTPUT"
          fi

  build-prod:
    name: Build Production Artifacts
    runs-on: ubuntu-latest
    needs: [prepare]
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Restore pnpm store
        uses: actions/cache@v4
        with:
          path: ~/.local/share/pnpm/store
          key: pnpm-store-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}
          restore-keys: |
            pnpm-store-${{ runner.os }}-

      - run: pnpm install --frozen-lockfile
      - run: pnpm build

      - name: Upload release artifacts
        uses: actions/upload-artifact@v4
        with:
          name: release-artifacts
          path: |
            apps/*/dist/
            apps/.next/
            packages/*/dist/
          retention-days: 30

  # ── PRODUCTION DEPLOY ────────────────────────────────
  # Gates:
  #   1. GitHub Environment "production" requires manual approval
  #      (configured in Settings → Environments → production)
  #   2. OIDC Federated identity → AWS STS AssumeRoleWithWebIdentity
  #      (no LONG-LIVED AWS_ACCESS_KEY_ID / SECRET_ACCESS_KEY)
  # ──────────────────────────────────────────────────────
  deploy-production:
    name: Deploy to Production
    runs-on: ubuntu-latest
    needs: [build-prod]
    environment:
      name: production
      url: https://myapp.com
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - uses: actions/download-artifact@v4
        with:
          name: release-artifacts

      # ── OIDC Step ─────────────────────────────────────
      # 1. GitHub provides a JWT signed by GitHub's OIDC
      #    key pair (rotates automatically) in the ID token.
      # 2. aws sts assume-role-with-web-identity swaps that
      #    JWT for short-lived AWS credentials via the trust
      #    policy defined in AWS IAM.
      # 3. Credentials expire after the session duration
      #    (default 1h), leaving zero persistent secrets.
      #
      # Trust policy requirement (AWS side):
      # {
      #   "Condition": {
      #     "StringEquals": {
      #       "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      #       "token.actions.githubusercontent.com:sub": "repo:<org>/<repo>:ref:refs/heads/main"
      #     }
      #   }
      # }
      # ───────────────────────────────────────────────────
      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::ACCOUNT_ID:role/github-ci-production
          aws-region: us-east-1
          role-session-name: github-ci-deploy-${{ github.run_id }}

      - name: Deploy to ECS / Kubernetes / Lambda
        run: |
          # Example: AWS ECS blue-green deployment
          aws ecs update-service \
            --cluster production \
            --service api-server \
            --force-new-deployment \
            --desired-count 3

          # Example: kubectl rollout (if using EKS)
          # kubectl set image deployment/api-server \
          #   api-server=myapp/api-server:${{ needs.prepare.outputs.version }}
          # kubectl rollout status deployment/api-server --timeout=300s

      - name: Health check
        run: |
          for i in $(seq 1 12); do
            if curl -sf https://myapp.com/health > /dev/null; then
              echo "Health check passed on attempt $i"
              exit 0
            fi
            echo "Health check attempt $i failed, retrying in 15s..."
            sleep 15
          done
          echo "Health check failed after 12 attempts"
          exit 1

      - name: Rollback on failure
        if: failure()
        run: |
          echo "Deploy failed — rolling back to previous revision"
          aws ecs update-service \
            --cluster production \
            --service api-server \
            --force-new-deployment \
            --deployment-configuration maximumPercent=200,healthCheckGracePeriodSeconds=30
```

```yaml
name: Release

on:
  release:
    types: [published]

permissions:
  contents: read

jobs:
  publish-and-attest:
    name: Publish & Attest Release ${{ github.ref_name }}
    runs-on: ubuntu-latest
    permissions:
      contents: write         # create release assets
      id-token: write         # OIDC for cosign / sigstore
      packages: write         # publish to ghcr.io
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Restore pnpm store
        uses: actions/cache@v4
        with:
          path: ~/.local/share/pnpm/store
          key: pnpm-store-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}
          restore-keys: |
            pnpm-store-${{ runner.os }}-

      - run: pnpm install --frozen-lockfile

      # Generate SBOM (Software Bill of Materials)
      # Using Syft — produces SPDX JSON + CycloneDX XML
      - name: Install syft
        run: pip install grype syft

      - name: Generate SBOM (SPDX)
        run: >
          syft .
          --source .
          --output spdx-json=sbom.spdx.json
          --license-score 0
          --exclude '*.git*'
          --exclude 'node_modules'

      - name: Generate SBOM (CycloneDX)
        run: >
          syft .
          --source .
          --output cyclonedx-json=sbom.cyclonedx.json

      - name: Publish to npm (private scope)
        run: |
          pnpm config //registry.npmjs.org/:_authToken=${NPM_TOKEN}
          pnpm -r --filter=@myorg/api-server publish --access public
        env:
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

      # Sign published artifacts with Sigstore/cosign
      # Uses GitHub's OIDC token — no cosign keypair stored
      - name: Authenticate to Sigstore (oidc)
        uses: sigstore/gh-action-sigstore-python@v3
        with:
         -release-signing-artifacts: false

      - name: Sign SBOM
        run: |
          cosign sign-blob \
            --yes \
            --rekor-url https://rekor.sigstore.dev \
            sbom.spdx.json > sbom.spdx.json.sig

      - name: Upload release assets
        uses: softprops/action-gh-release@v2
        with:
          files: |
            sbom.spdx.json
            sbom.spdx.json.sig
            sbom.cyclonedx.json
          fail-on-unmatched-files: true
```

```yaml
          --outputFile=test-results/node${{ matrix.node-version }}-shard${{ matrix.shard-index }}.json
        env:
          NODE_ENV: test

  build:
    runs-on: ubuntu-latest
    needs: [lint, typecheck]
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm build

  merge-queue-ok:
    needs: [lint, typecheck, test, build]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: |
          python3 -c "
          import os, json, sys
          needs = json.loads(os.environ['NEEDS'])
          failed = [k for k,v in needs.items() if v != 'success']
          if failed:
              print(f'MERGE BLOCKED: {failed}')
              sys.exit(1)
          print('All merge-queue checks passed')
          "
        env:
          NEEDS: '${{ toJson(needs) }}'
```

### Merge Queue Wiring

In **Settings → Branches → Branch protection rules** for `main`:

1. **Require a pull request before merging** ✓
2. **Require reviews before merging** ✓ (1 approver)
3. **Require status checks to pass BEFORE merging** ✓
   - Select these required checks:
     - `CI / lint`
     - `CI / typecheck`
     - `CI / test (20 / shard 1/4)` … `(22 / shard 4/4)` (all 8)
     - `CI / Integration Tests`
     - `CI / Build All Packages`
     - `CI / CI Passed`
     - `Merge Queue / lint`
     - `Merge Queue / typecheck`
     - `Merge Queue / test (20 / shard 1/4)` … etc.
     - `Merge Queue / build`

GitHub's merge queue runs `merge_group` workflows on the **merged commit**, preventing the "lgtm + flaky test" race condition where a test passes on the PR but flakes on the resulting main-branch commit.

## Cache Key Design — Deep Dive

### Strategy Overview

Three independent cache dimensions, each keyed on **content hashes** (not timestamps or run numbers):

| Cache | Key Pattern | Granularity | Invalidation Trigger |
|---|---|---|---|
| **pnpm store** | `pnpm-store-{os}-{hash(pnpm-lock.yaml)}` | Whole monorepo | Any dep version/change |
| **Package builds** | `build-packages-{os}-{hash(all packages/*/package.json)}` | Per-package subset | Package-level dependency change |
| **App builds** | `build-apps-{os}-{hash(all apps/*/package.json)}` | Per-app subset | App-level dependency change |

### Why Full Lockfile Hash for Store?

The pnpm store holds resolved tarballs. Two scenarios:

1. **Same lockfile, same key** → store hit → zero network calls for deps. The `--prefer-offline` second install picks up the already-fetched tars from the workspace cache layer.
2. **Different lockfile (even a single transitive dep bump)** → different hash → cache miss → full re-fetch. The new store entry is cached for future runs.

Fallback key `pnpm-store-{os}-` catches partial matches when the lockfile hash is absent (first run ever). It may return stale store entries but pnpm deduplicates them internally.

### Why Per-Package Hash for Builds?

Using `hashFiles('packages/*/package.json')` collapses all package manifests into ONE hash. If `packages/ui/package.json` changes, the hash changes → all package builds rebuild. This is slightly conservative compared to individual package hashes but avoids creating 8 separate cache entries and the complexity of multi-cache restore.

Tradeoff accepted: 8 libs typically change together during refactors, and the rebuild cost is dominated by TypeScript emission (~10-30s), not the cache lookup.

### Cache Warming Pattern

```
Install phase:  pnpm install --frozen-lockfile
                ↓
Workspace cache: pnpm install --prefer-offline  (populates node_modules/.cache/)
                ↓
Build phase:    pnpm build                      (uses warm caches)
                ↓
Build cache:    actions/cache persist dist/     (survives across jobs/runs)
```

This two-layer cache (pnpm store + fs artifact cache) gives ~60% faster cold starts and ~90% faster hot runs.

## OIDC Trust Configuration — Deep Dive

### Architecture

```
┌─────────────────────┐     JWT (signed by GitHub)      ┌──────────────────┐
│                     │  ──────────────────────────────>  │                  │
│  GitHub Actions     │                                   │  AWS IAM         │
│  (runner)           │  Id Token                         │  (STS)           │
│                     │  <──────────────────────────────  │                  │
│  Subject: repo:org/repo:ref:refs/heads/main             │                  │
│  Audience: sts.amazonaws.com                            │  Short-lived     │
│                                                     ◄──│  AWS Credentials │
└─────────────────────┘                                   └──────────────────┘
```

No `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` exists anywhere in the repo or GitHub Secrets. Credentials are minted on-demand and expire after the session.

### Step 1: Create IAM Role in AWS

```bash
# 1. Fetch GitHub's OIDC public key JWK set
curl -s https://token.actions.githubusercontent.com/.well-known/openid-configuration | jq -r .jwks_uri
curl -s <jwks_uri_url> > github-jwks.json

# 2. Create the trust policy (replace placeholders)
cat > gh-trust-policy.json <<'JSONEOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:YOUR_ORG/YOUR_REPO:ref:refs/heads/main"
        }
      }
    }
  ]
}
JSONEOF

# 3. Register GitHub as an IAM OIDC provider (one-time)
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list d0b6474db472427ae4e8b1e4a36a3b3fbfc64e8e

# 4. Create the role
aws iam create-role \
  --role-name github-ci-production \
  --assume-role-policy-document file://gh-trust-policy.json \
  --description "Assumed by GitHub Actions CI for production deployments"

# 5. Attach the minimal deployment policy
cat > deploy-policy.json <<'JSONEOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecs:UpdateService",
        "ecs:DescribeServices",
        "ecs:DescribeClusters"
      ],
      "Resource": "arn:aws:ecs:*:ACCOUNT_ID:service/production/*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ecr:BatchGetImage",
        "ecr:GetDownloadUrlForLayer",
        "ecr:GetAuthorizationToken"
      ],
      "Resource": "*"
    }
  ]
}
JSONEOF

aws iam put-role-policy \
  --role-name github-ci-production \
  --policy-name deploy-permissions \
  --policy-document file://deploy-policy.json
```

### Step 2: Separate Roles for Preview vs Production

| Role | Workflow | Branch Guard | Permission Scope |
|---|---|---|---|
| `github-ci-preview` | `ci.yml` (PR) | `ref:refs/pull/**` | Can deploy to preview ECS cluster or spin up ephemeral infra |
| `github-ci-production` | `deploy-prod.yml` | `ref:refs/heads/main` | Can deploy to prod ECS, EKS, Lambda |

Preview trust policy adds `"RefPullRequest": "*"` condition and uses a less restrictive resource ARN.

### Why This Is Secure

1. **No static credentials** — keys rotate automatically (GitHub rotates signing keys quarterly; the IAM provider thumbprint captures this).
2. **Scope-bound** — the `sub` claim restricts which branch/ref can assume the role. A forked PR cannot assume `github-ci-production`.
3. **Audience-gated** — `sts.amazonaws.com` in the JWT audience claim prevents replay attacks against other providers.
4. **Session-limited** — default 1-hour TTL on assumed credentials. Even if leaked, they expire quickly.
5. **Least privilege** — the attached policy only allows `ecs:UpdateService` on the production cluster ARN, not `*` resources.

### Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `Unable to assume role` | Wrong repo/org in trust policy | Verify `sub` claim matches exactly |
| `Invalid identity token` | Old GitHub Actions runners | Upgrade to latest `actions/checkout@v4` |
| `Not authorized` | Policy missing ECS actions | Check `Resource` ARN pattern matches |
| Preview leaks to prod | Missing branch condition | Add `StringLike` on `sub` for `refs/heads/*` |

## Summary of Pipeline Flow

```
PR opens/push to main
  │
  ├─→ CI: lint (single job) ──────────────────────────┐
  ├─→ CI: typecheck (single job) ─────────────────────┤
  ├─→ CI: test × 8 (Node 20/22 × 4 shards) ← depends on install cache hit
  ├─→ CI: integration tests (postgres + redis services)
  ├─→ CI: build-all (depends on lint + typecheck, build cache hit)
  ├─→ CI: deploy-preview (PR only → Vercel ephemeral URL)
  │
  ├─→ Push to main: deploy-production
  │   ├─→ build-prod (artifact upload)
  │   ├─→ manual gate in GitHub Environment "production"
  │   └─→ OIDC → AWS STS → ECS/EKS deploy → health check
  │
  ├─→ Release published: release
  │   ├─→ Syft SBOM (SPDX + CycloneDX)
  │   ├─→ npm publish
  │   └─→ cosign sign-blob → rekor transparency log
  │
  └─→ Merge queue: merge-group
      ├─→ lint, typecheck, test×4, build
      └─→ Status gate prevents merge if any fails
```
