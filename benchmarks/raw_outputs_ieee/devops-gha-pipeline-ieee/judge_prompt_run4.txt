### Cache-Key Design Explained

There are **three independent caches**, each keyed differently:

| Cache | Key Pattern | What It Stores | Why This Key |
|-------|-------------|----------------|--------------|
| **Dependencies** | `deps-{OS}-{hash(pnpm-lock.yaml)}` | `.pnpm-store` (~2–4 GB extracted modules) | The lockfile is the *only* thing that determines exact installed versions. Hashing it means any dependency change invalidates the cache. A fallback prefix `deps-{OS}-` catches partial restores when the lockfile changes but many packages are unchanged. |
| **Build artifacts** | `build-{app}-{OS}-{hash(lockfile + all src/**/*.ts)}` | `.turbo/`, module graph cache, build outputs | Includes the lockfile (in case resolved packages affect compilation) *plus* every source file glob. Adding the app scope limits cross-app pollution. When only an unrelated app's code changes, that app's build cache still hits because its src hash didn't change. |
| **Node module cache** | `pnpm` managed via `actions/setup-node` | `.cache` inside node_modules (esbuild/swc binary caches) | Built-in to the Node action; scoped to the Node version. Cheap to regenerate, so we let it flow through naturally. |

**Key principles:**

1. **Single canonical hash anchor** — every key references `hashFiles('pnpm-lock.yaml')`. This prevents cache poisoning where a new lockfile silently reuses stale modules.
2. **Fallback keys for warm-up** — `restore-keys` use prefix matching so a lockfile-only change (e.g., adding one new library) still restores the bulk of the previous cache, then just re-downloads the delta.
3. **Per-app build isolation** — the build cache includes the app name in the key, so two apps changing simultaneously don't invalidate each other's incremental builds.
4. **Cache size awareness** — `.pnpm-store` can grow large; the `if: steps.restore.outputs.cache-hit != 'true'` guard on save prevents endlessly growing caches during PR comments/re-runs.

## Architecture Overview

The solution uses **two workflow files**:

- **`.github/workflows/ci.yml`** — Main pipeline: detection → lint → test matrix → build → publish
- **`.github/workflows/release.yml`** — Release gating: environment approval → deploy → SBOM → attestation

A **single reusable workflow** pattern is used to avoid duplication between CI and release jobs where applicable.

---

## Cache-Key Design Philosophy

Three distinct cache namespaces, each with layered key strategies:

### 1. Dependency cache (`pnpm-store`)

```
key: pnpm-linux-node-${{ runner.os }}-node@${{ matrix.node-version }}-${{ hashFiles('pnpm-lock.yaml') }}
restore-keys: |
  pnpm-linux-node-${{ runner.os }}-node@${{ matrix.node-version }}-
  pnpm-linux-node-${{ runner.os }}-
```

- Full match on OS + Node major + lockfile hash — zero stale deps
- Progressive restore keys fall back gracefully when lockfile changes (keeps partial hits)
- Single store shared across all matrix combinations via `${HOME}/.local/share/pnpm/store`

### 2. Build artifact cache

```
key: build-${{ runner.os }}-node@${{ matrix.node-version }}-${{ github.ref_name }}-${{ github.sha }}
restore-keys: |
  build-${{ runner.os }}-node@${{ matrix.node-version }}-${{ github.ref_name }}-
  build-${{ runner.os }}-node@${{ matrix.node-version }}-
```

- Unique per commit for exact reproducibility (`github.sha`)
- Prefix-based restore from same branch for incremental speed
- Stores `.turbo` cache dir and workspace `.dts` outputs

### 3. Turbo/monorepo cache (remote fallback)

When configured with a remote cache (GitHub Artifacts), turbo falls back to HTTP after local cache misses. The `--remote-cache-expiration 90` flag ensures stale entries don't linger.

**Why three layers:** Dependencies change infrequently (lockfile-driven), builds change per-commit (sha-driven), and turbo cache bridges branches. Each namespace avoids collision.

## Summary of Key Design Decisions

**Cache key design**: Three-layer hierarchy (store / symlinks / build outputs). Each layer uses lockfile hash as primary invalidator with prefix-based restore keys so partial cache hits still provide value when the lockfile changes. Source-level hashes only applied to build caches where they actually matter.

**OIDC trust chain**: GitHub's OIDC JWT exchanged for temporary STS credentials via IAM role trust policy. Three layers of conditions enforce least privilege — audience validation prevents token misuse, environment tag gates which workflows can assume the role, and ref match prevents arbitrary branch deploys. Preview environments get their own lower-privilege roles scoped to `ref:refs/pull/*/head`.

**Path filtering**: `dorny/paths-filter` maps app directories to logical groups including transitive dependency paths, so changing `packages/validation` triggers rebuilds for both `api-server` and `web-app` without requiring every possible pair to be listed.

## Cache-Key Design

The cache uses two layers:

| Layer | Key Pattern | Invalidation Trigger | Purpose |
|-------|-------------|---------------------|---------|
| **Dependency cache** | `deps-${{ runner.os }}-${{ hashFiles('**/pnpm-lock.yaml') }}` | Any lockfile change | Full `node_modules/.pnpm/store` — shared across all jobs |
| **Build cache** | `build-${{ runner.os }}-${{ hashFiles('.cache/**') }}` | Source changes tracked via `.cache/<hash>` | Stale detection per package, enables fine-grained reuse |

**Why two layers:** `hashFiles('**/pnpm-lock.yaml')` catches every version bump anywhere in the monorepo (correct but coarse). Build cache uses a stamping convention: if a package's source changed, we delete its `.cache` entry next run, causing a full rebuild of just that package while others hit cache.

**Key salting:** `${{ runner.os }}` prevents cross-OS corruption. No branch prefix on keys — CI cache is shared PR-to-PR which maximizes hit rate.
