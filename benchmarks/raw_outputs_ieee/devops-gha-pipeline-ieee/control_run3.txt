## Workflow 1: CI — Path-Filtered Per App (`ci.yml`)

This is the main gate. Every push and PR runs a single matrix job that filters by changed paths. Apps get a full build+test cycle. Libs only rebuild if their own files change (other apps are fast-failed since libs haven't changed).

```yaml
name: CI

on:
  push:
    branches: [main, 'release/**']
  pull_request:
    branches: [main]

env:
  PNPM_CACHE_FOLDER: .pnpm-store
  NODE_VERSION: '20'

permissions:
  contents: read

jobs:
  # ── Matrix dispatcher: runs one row per app + libs once ──
  changes:
    runs-on: ubuntu-latest
    outputs:
      apps: ${{ steps.filter.outputs.apps }}
      libs: ${{ steps.filter.outputs.libs }}
      any: ${{ steps.filter.outputs.any }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            apps:
              - 'apps/web-app/**'
              - 'apps/api-server/**'
              - 'apps/admin-panel/**'
            libs:
              - 'libs/**'
              - 'pnpm-lock.yaml'
              - '.github/workflows/ci.yml'

  # ── Core bootstrap: install + cached build, shared by all consumers ──
  bootstrap:
    needs: changes
    if: needs.changes.outputs.any == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # ── Cache key design (explained below) ──
      - name: Cache pnpm dependencies
        uses: actions/cache@v4
        with:
          path: |
            .pnpm-store
            **/node_modules
          key: ${{ runner.os }}-pnpm-${{ hashFiles('pnpm-lock.yaml') }}-${{ hashFiles('.nvmrc') }}
          restore-keys: |
            ${{ runner.os }}-pnpm-

      - name: Install system deps (optional, e.g. node-gyp)
        run: sudo apt-get update && sudo apt-get install -y pkg-config libudev-dev

      - uses: pnpm/action-setup@v4
        with: { version: 9 }

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'pnpm'

      - name: Install deps
        run: pnpm install --frozen-lockfile

      - name: Build all libs (incremental)
        run: pnpm --filter './libs/**' build

      - name: Upload dependency cache artifact
        uses: actions/upload-artifact@v4
        with:
          name: pnpm-cache
          path: .pnpm-store
          retention-days: 5

  # ── Lint: always runs on every PR, independent of path filters ──
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint

  # ── Type check root workspace ──
  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck

  # ── Test matrix per app: Node × shard ──
  test-app:
    needs: [changes, bootstrap]
    if: ${{ needs.changes.outputs.apps != '[]' && needs.changes.outputs.apps != '' }}
    strategy:
      fail-fast: false
      matrix:
        app: ${{ fromJSON(needs.changes.outputs.apps) }}
        node-version: [20, 22]
        shard: ['1/4', '2/4', '3/4', '4/4']
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Download pnpm cache
        uses: actions/download-artifact@v4
        with: { name: pnpm-cache }
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - name: Run tests
        env:
          SHARD: ${{ matrix.shard }}
          CI: 'true'
        run: |
          cd ${{ matrix.app }}
          pnpm test -- --ci --shard=${SHARD}

  # ── Lib unit tests ──
  test-lib:
    needs: [changes, bootstrap]
    if: ${{ needs.changes.outputs.libs != '[]' && needs.changes.outputs.libs != '' }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Download pnpm cache
        uses: actions/download-artifact@v4
        with: { name: pnpm-cache }
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter './libs/**' test

  # ── Integration smoke tests (single Node version, no sharding needed) ──
  test-integration:
    needs: [changes, bootstrap]
    if: ${{ github.event_name == 'pull_request' && needs.changes.outputs.any == 'true' }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Download pnpm cache
        uses: actions/download-artifact@v4
        with: { name: pnpm-cache }
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm test:integration
      - name: Upload coverage
        uses: codecov/codecov-action@v4
        with:
          token: ${{ secrets.CODECOV_TOKEN }}
          files: ./coverage/lcov.info
          flags: ci
```

**Why the matrix is structured this way:**

The `dorny/paths-filter` returns JSON arrays like `["apps/web-app", "apps/api-server"]`. By splitting into separate jobs (`test-app` vs `test-lib`), we avoid wasting compute on a matrix row whose app didn't change. The `fromJSON()` call parses the string output into an actual GitHub Actions matrix expression. Sharding distributes Jest/Vitest work across 4 parallel instances within each Node version, so even large test suites finish fast. `fail-fast: false` ensures partial failures don't cancel siblings — we want to know exactly which app/node/shard failed.

## Workflow 2: Preview Environments (`preview.yml`)

Spins up a unique URL per PR, torn down on close/merge. Uses Docker Compose or containerized deploys depending on your stack.

```yaml
name: Preview Environment

on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened, closed]

concurrency:
  group: preview-${{ github.ref }}
  cancel-in-progress: false

permissions:
  contents: read
  pull-requests: write
  deployments: write

jobs:
  preview:
    runs-on: ubuntu-latest

    # Only create previews for open PRs; destroy on close
    if: github.event.action != 'closed' || always()

    environment:
      name: preview-${{ github.event.pull_request.number }}
      url: ${{ steps.deploy.outputs.url }}

    strategy:
      matrix:
        app:
          - apps/web-app
          - apps/api-server
          - apps/admin-panel

    env:
      APP_DIR: ${{ matrix.app }}
      PR_NUMBER: ${{ github.event.pull_request.number }}
      SHA: ${{ github.sha }}

    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter "$APP_DIR" build

      # ── Deploy via cloud provider CLI (OIDC — see trust config below) ──
      - name: Configure Cloud Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-preview-role
          aws-region: us-east-1
          role-session-name: preview-pr-${{ env.PR_NUMBER }}
          role-chaining: true

      - name: Deploy preview
        id: deploy
        run: |
          # Example: Fly.io or similar — replace with your cloud provider
          DEPLOY_OUTPUT=$(pnpm --filter "$APP_DIR" run deploy:preview \
            --pr-number="$PR_NUMBER" --sha="$SHA")
          echo "url=$DEPLOY_OUTPUT" >> "$GITHUB_OUTPUT"

      - name: Comment PR with preview URL
        if: github.event.action != 'closed'
        uses: marocchino/sticky-pull-request-comment@v2
        with:
          header: preview-url
          message: |
            ✅ Preview ready!
            - Web App: https://pr${{ env.PR_NUMBER }}-web.preview.example.com
            - API Server: https://pr${{ env.PR_NUMBER }}-api.preview.example.com
            - Admin Panel: https://pr${{ env.PR_NUMBER }}-admin.preview.example.com

  destroy-preview:
    # Runs when PR is closed or merged
    runs-on: ubuntu-latest
    if: github.event.action == 'closed'
    needs: preview
    environment:
      name: preview-${{ github.event.pull_request.number }}
    strategy:
      matrix:
        app:
          - apps/web-app
          - apps/api-server
          - apps/admin-panel

    env:
      APP_DIR: ${{ matrix.app }}
      PR_NUMBER: ${{ github.event.pull_request.number }}

    steps:
      - uses: actions/checkout@v4

      - name: Delete preview resources
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-preview-role
          aws-region: us-east-1
          role-session-name: destroy-pr-${{ env.PR_NUMBER }}

      - name: Destroy preview environment
        run: |
          pnpm --filter "$APP_DIR" run destroy:preview \
            --pr-number="$PR_NUMBER"
```

**Concurrency guard:** `group: preview-${{ github.ref }}` ensures only one deployment set per PR at a time. We don't cancel-in-progress because stale preview teardown must finish before new resources spin up.

## Workflow 3: Production Deploy (`deploy-production.yml`)

Uses **GitHub Environments** for the approval gate + **OIDC federation** for cloud authentication. No long-lived AWS/GCP/Azure keys stored as secrets.

```yaml
name: Deploy to Production

on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    environment: production  # ← triggers manual approval gate

    # ── Re-use the cached bootstrap from CI, or re-run a lightweight build ──
    steps:
      - uses: actions/checkout@v4

      # ── OIDC configuration happens here — no secrets needed ──
      - name: Configure AWS Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-prod-role
          aws-region: us-east-1
          role-session-name: github-actions-prod-deploy
          duration-seconds: 900  # 15 min session max

      # ── Dependent setup (skip heavy bootstrap since CI already ran) ──
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - name: Fast install (cache hit expected)
        run: pnpm install --frozen-lockfile || pnpm install

      # ── Production build per app ──
      - name: Build all apps
        run: |
          pnpm --filter "./apps/**" build

      # ── Database migration (safe, dry-run first) ──
      - name: Dry-run migrations
        run: |
          pnpm --filter '@monorepo/db' migrate:deploy --dry-run
        env:
          DATABASE_URL: ${{ secrets.PRODUCTION_DATABASE_URL }}

      # ── Deploy each app sequentially ──
      - name: Deploy web-app
        run: |
          pnpm --filter apps/web-app run deploy:production
        env:
          API_URL: https://api.example.com

      - name: Deploy api-server
        run: |
          pnpm --filter apps/api-server run deploy:production

      - name: Deploy admin-panel
        run: |
          pnpm --filter apps/admin-panel run deploy:production
        env:
          ADMIN_API_URL: https://api.example.com

      - name: Health check
        run: |
          curl -sf https://web-app.example.com/health || exit 1
          curl -sf https://api-server.example.com/health || exit 1

      - name: Notify Slack
        if: always()
        uses: slackapi/slack-github-action@v1
        with:
          channel-id: 'prod-deploys'
          slack-message: |
            ${{ github.job }} ${{ job.status == 'success' && '✅ succeeded' || '❌ failed' }}
            Ref: ${{ github.sha }} by @${{ github.actor }}
        env:
          SLACK_BOT_TOKEN: ${{ secrets.SLACK_BOT_TOKEN }}
```

## Workflow 4: Release — SBOM + Attestation (`release.yml`)

Triggers on tag creation. Produces a signed SBOM (SPDX/CycloneDX format) and uses Sigstore cosign for artifact attestation/proof-of-build.

```yaml
name: Release — SBOM + Attestation

on:
  push:
    tags:
      - 'v*'

permissions:
  contents: write          # for creating releases
  packages: write          # for pushing artifacts
  id-token: write          # REQUIRED for OIDC signing (sigstore)
  attestations: write      # for upload attestation

jobs:
  release:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        app:
          - apps/web-app
          - apps/api-server
          - apps/admin-panel

    env:
      APP_DIR: ${{ matrix.app }}
      VERSION: ${{ github.ref_name }}

    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter "$APP_DIR" build

      # ── Set version in package.json ──
      - name: Bump version
        run: pnpm --filter "$APP_DIR" version --new-version "$VERSION" --git-tag-version false

      # ── Generate SBOM (Syft + SPDX) ──
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          path: ${{ env.APP_DIR }}
          format: spdx-json
          output-file: sbom.spdx.json
          artifact-name: sbom-${{ env.APP_DIR }}

      # ── Create distribution archive ──
      - name: Package artifact
        run: |
          tar czf "${APP_DIR//\//-}-${VERSION}.tar.gz" -C "${APP_DIR}" .
          sha256sum "${APP_DIR//\//-}-${VERSION}.tar.gz" > checksums.sha256

      # ── Upload to release draft ──
      - name: Create release assets
        uses: svenstaro/upload-release-action@v2
        with:
          repo_token: ${{ secrets.GITHUB_TOKEN }}
          file: |
            ${APP_DIR//\//-}-${VERSION}.tar.gz
            sbom.spdx.json
            checksums.sha256
          asset_name: "${{ env.APP_DIR//\//- }}"
          tag: ${{ env.VERSION }}
          overwrite: true

      # ── Sigstore attestation via cosign (OIDC-backed, no keys) ──
      - name: Install cosign
        uses: sigstore/cosign-installer@v3
        with:
          cosign-release: 'v2.2.2'

      - name: Attest build provenance
        run: |
          cosign attest --yes \
            --type slsa-provenance \
            --predicate https://slsa.dev/provenance/v0.2 \
            "${{ github.server_url }}/${{ github.repository }}@${{ github.sha }}"

      - name: Attest SBOM
        run: |
          cosign attach sbom \
            --sbom sbom.spdx.json \
            "${{ github.server_url }}/${{ github.repository }}@${{ github.sha }}"
```

## Workflow 5: Merge Queue Status Checks (`merge-queue-status.yml`)

This ties everything together. A separate workflow (or workflow dispatch) ensures only green builds enter the merge queue. This can be wired into GitHub's branch protection rules.

```yaml
name: Merge Queue Gate

on:
  merge_group:               # Built-in GitHub merge queue event
  pull_request_target:
    branches: [main]
    types: [queued]

permissions:
  contents: read
  statuses: write

jobs:
  # Verify merge-base is green before entering queue
  merge-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: refs/merge-requests/${{ github.run_id }}/merge

      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile

      # Re-run critical checks on the exact merge commit
      - name: Type check on merge base
        run: pnpm typecheck

      - name: Lint on merge base
        run: pnpm lint

      - name: Unit tests (fast subset)
        run: |
          pnpm --filter './apps/**' test -- --shard=1/4 --maxWorkers=2

      - name: Mark merge gate passed
        if: success()
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.checks.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              name: 'Merge Gate',
              status: 'completed',
              conclusion: 'success',
              head_sha: context.sha
            })
```

## How Required-Status-Checks Wire Together

In **Settings → Branches → Branch protection rules** for `main`:

```
Required status checks:
  ✓ ci / lint
  ✓ ci / typecheck
  ✓ ci / test-app (web-app, 20, 1/4)   ← 4 rows x 3 apps = 12 entries
  ✓ ci / test-app (web-app, 20, 2/4)
  ✓ ci / test-app (web-app, 20, 3/4)
  ✓ ci / test-app (web-app, 20, 4/4)
  ✓ ci / test-app (web-app, 22, 1/4)   ← etc. (12 total for test-app)
  ✓ ci / test-app (api-server, 20, 1/4)
  ... (all combinations)
  ✓ ci / test-lib
  ✓ ci / test-integration

Require status checks to pass before merging: [ENABLED]
Include approving reviewers: [DISABLED — use environment gate instead]
Require review from code owners: [ENABLED if CODEOWNERS exists]

Pull request tasks:
  Require threads to be resolved: [ENABLED]
  Require upstream status: [ENABLED]

Merge queues: [ENABLED]
```

**Critical detail:** Because GitHub merges matrix jobs into composite names like `ci / test-app (apps/web-app, 22, 3/4)`, each combination appears as its own required check. When `needs.changes.outputs.apps` doesn't include an app, that specific matrix row is skipped entirely (via `if:`). Skipped checks count as passing in branch protection — this is why path-filtering via the `changes` job matters. If you used simple `paths-ignore` without skipping, a skipped check would block merging.

For the merge queue specifically, `merge_group` triggers a separate workflow that validates the **merge commit** (the squash of PR + latest main), not just the PR tip. This prevents merge-time conflicts from breaking prod.

## Deep Dive: Cache-Key Design

### The Problem

A pnpm monorepo has ~8K+ dependency edges across 11 packages. Cold installs take 3-5 minutes. Without caching, CI spends more time installing than building.

### The Key Strategy

```
key: ${{ runner.os }}-pnpm-${{ hashFiles('pnpm-lock.yaml') }}-${{ hashFiles('.nvmrc') }}
```

| Component | Rationale |
|-----------|-----------|
| `${{ runner.os }}` | Isolates caches by platform — Linux nodes never share with macOS runners |
| `-pnpm-` | Namespace separator — distinct from npm/yarn caches to prevent collisions |
| `hashFiles('pnpm-lock.yaml')` | **Core**: full SHA-256 of the lockfile. Any dependency addition, removal, or version bump changes the hash invalidating the cache atomically. Lockfiles are deterministic — same lockfile = identical transitive tree. |
| `-` + `hashFiles('.nvmrc')` | Node version is ABI-sensitive. Native modules (bcrypt, node-addon-api) compiled for Node 20 binary-incompatible with Node 22. This suffix forces cache invalidation on engine bump. |

### Why Not Cache Individual Packages?

pnpm's content-addressable store (`.pnpm-store`) makes package-level caching counterproductive. Every package depends transitively on the store layout. Splitting cache by top-level package causes massive cache fragmentation and fill-rate degradation. One monolithic cache keyed on the complete lockfile has near-100% hit rate after the initial cold run.

### Restore Keys for Partial Hits

```yaml
restore-keys: |
  ${{ runner.os }}-pnpm-
```

If `pnpm-lock.yaml` changed but only added a new optional dependency, the full hash won't match. But `restore-keys` finds the nearest partial match (e.g., yesterday's lockfile). pnpm installs incrementally — only the diff needs downloading. Cost: slightly larger download, but still 10× faster than full cold install.

### Build Caching Bonus

After `bootstrap` builds all libs once, `actions/upload-artifact` persists `.pnpm-store` for downstream jobs. This means `test-app` and `lint` don't re-download or rebuild dependencies — they just pick up the already-installed copy. Cross-job cache sharing avoids redundant `pnpm install` calls that would otherwise compete for the same GitHub Actions cache bucket.

## Deep Dive: OIDC Trust Configuration

### The Architecture

```
┌──────────────┐     HTTP POST       ┌──────────────────┐
│ GitHub Actions│ ──────────────────▶ │  GitHub OIDC     │
│   Runner      │   Token request     │  Provider        │
│               │                     │  (sts.actions    │
│               │   Short-lived       │   .amazonaws.com)│
│               │   JWT (~5min)       └────────┬─────────┘
│               │                              │
│               │     sts:AssumeRoleWithWebIdentity   │
│               │     (federated trust)               │
└──────────────┘                               │
                                               ▼
                                      ┌──────────────────┐
                                      │ AWS IAM Role     │
                                      │ (repo policy     │
                                      │  scoped trust)   │
                                      └────────┬─────────┘
                                               │
                                     AssumeRole succeeds
                                     → Temporary creds (15min TTL)
                                     → Deploy to cloud
```

### Step 1: GitHub Side — Repository Settings

Go to **Settings → Secrets and variables → Actions → OpenID connect (custom scopes)**. Enable default scope. This publishes a public JWKS endpoint at `https://token.actions.githubusercontent.com/.well-known/jwks.json`.

### Step 2: AWS Side — Identity Provider

```bash
# Create the federated provider (run once per AWS account)
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list a031c46782e6e6c662c2c87c76da9aa62ccabd8e \
  --attribute-string jwt.github.io:audience:sts.amazonaws.com
```

### Step 3: AWS Side — Trust Policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<AWS_ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": [
            "repo:<OWNER>/<REPO>:environment:production",
            "repo:<OWNER>/<REPO>:ref:refs/heads/main",
            "repo:<OWNER>/<REPO>:ref:refs/tags/v*"
          ]
        }
      }
    }
  ]
}
```

**What this restricts:**

| Condition | Effect |
|-----------|--------|
| `aud: sts.amazonaws.com` | Tokens can only be exchanged for AWS STS — not arbitrary services |
| `environment:production` | Only the `production` environment trigger can assume this role |
| `ref:refs/heads/main` | Only pushes to `main` (not feature branches) |
| `ref:refs/tags/v*` | Only tagged releases can assume the release role |

Three separate roles exist:
- `github-actions-preview-role` → broadest permissions (can create/delete any resource)
- `github-actions-prod-role` → deploy-only (ECS/lambda/S3), database migrations
- `github-actions-release-role` → SBOM generation + cosign signing, read-only deploy

### Step 4: Store Account ID as Secret

```
secrets.AWS_ACCOUNT_ID = "123456789012"   # numeric AWS account ID
```

### Step 5: Workflow Usage

```yaml
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-prod-role
    aws-region: us-east-1
    duration-seconds: 900
```

The `configure-aws-credentials` action detects that no `aws-access-key-id` / `aws-secret-access-key` are provided, so it automatically uses OIDC flow:
1. Requests a JWT from the runner's instance metadata service
2. Sends it to AWS STS `AssumeRoleWithWebIdentity`
3. Receives temporary `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`
4. Exports them as environment variables

**No secrets to rotate. No keys stored anywhere.** The JWT is signed by GitHub's private key, validated by AWS against the known thumbprint. Session expires after `duration-seconds` (default 1 hour, capped to 900 for prod).

### Security Properties vs Long-Lived Keys

| Property | Long-Lived Keys | OIDC Federation |
|----------|----------------|-----------------|
| Credential exposure | Risk of leak in logs/Docker layers | JWT lives only in memory, <5min TTL |
| Rotation | Manual, quarterly | Automatic per-run |
| Scope | Static IAM permissions | Scoped by branch, environment, tag |
| Audit trail | CloudTrail shows role assumption | CloudTrail shows exact PR/run/git ref |
| Compromise impact | Attacker can use leaked key until rotation | Stolen JWT is useless (<5min + wrong ref) |
