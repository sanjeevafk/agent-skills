## Phase 1: Root Cause Investigation — Hypotheses Ranked by Likelihood

### Test 1: Formatted Timestamp Assertion

**Likelihood: HIGH**

| Hypothesis | Evidence Match | Severity |
|---|---|---|
| Timezone mismatch: test asserts on local datetime but runs in UTC-based CI, and developer's machine uses a different TZ offset | Correlates with timezone; passes in CI, fails locally | Deterministic once the TZ difference is identified |
| Second-boundary race: assertion checks `strftime("%H:%M:%S")` against a manually-created record; test triggers exactly when wall-clock rolls over second | Intermittent; correlates with machine load (slower machines more likely to cross boundary) | Explains "reruns usually go green" |
| System clock drift: developer's NTP sync lags behind CI's monotonic clock | Low likelihood unless dev machine has known clock issues | Unlikely given pattern |

**Most probable root cause:** The test formats a timestamp via `datetime.now()` (local TZ) and compares it to either a hardcoded expected string, or to a timestamp generated in a context where the TZ differs. When run under high CPU load, the operation takes just long enough to cross a second boundary, producing `"14:00:00"` instead of `"13:59:59"` (or vice versa). In CI, the environment is always UTC and the system is fast enough to never cross the boundary within the test window.

### Test 2: Async Worker Poll with `sleep(2)`

**Likelihood: HIGH**

| Hypothesis | Evidence Match | Severity |
|---|---|---|
| Race condition: `sleep(2)` assumes the worker finishes in <2s, but under load it sometimes takes >2s, causing timeout/assertion-before-completion | Correlates with machine load; 3/240 is classic timing-race rate (~1.25%) | Non-deterministic by nature |
| Semaphore/event storm: another test modifies shared async state; the worker sees stale data due to lack of isolation | Possible if fixtures share mutable state | Would show as correlated failures, not random |
| GIL contention: Python's GIL delays coroutine scheduling under heavy CPU load | Consistent with "load correlation" | Subset of hypothesis #1 |

**Most probable root cause:** The test fires an async task then polls with a fixed `await asyncio.sleep(2)` expecting completion. Under normal load the worker finishes in ~1.5s. Under load it may take 2.5-3s. The assertion runs before the worker completes, reads incomplete/partial state, and fails. Rerun goes green because the next attempt starts fresh and happens to finish within the window.

### Test 3: Dict Iteration Order Over Fixture IDs

**Likelihood: MEDIUM-HIGH**

| Hypothesis | Evidence Match | Severity |
|---|---|---|
| Hash randomization: Python seeds `hash()` per-process for str/int keys (`PYTHONHASHSEED`); fixture IDs stored in a set→dict lose insertion order across runs | Python 3.7+ dicts are insertion-ordered, but **set iteration order is NOT guaranteed**, so `dict.fromkeys(some_set)` or `{k: v for k in some_set}` produces unpredictable ordering | Fully explains "intermittent + reruns go green" |
| OS-level filesystem ordering: fixture IDs are file basenames discovered via `os.listdir()` or `Path.glob()`, which returns entries in filesystem hash order (ext4), varying with directory size/load | Matches fixture ID pattern; ext4 dir ordering is semi-stable but not deterministic | Less likely if IDs are constructed in-code rather than discovered from disk |
| Pandas/DataFrame index shuffle if the fixture pipeline touches any DataFrame | Only applicable if data processing is involved | Lower likelihood without evidence |

**Most probable root cause:** The test builds a dict by iterating over a `set` of fixture IDs (e.g., `{fid: result[fid] for fid in fixture_ids}`). Sets have no guaranteed iteration order in CPython (guaranteed randomized by default since Python 3.3). On low-load runs the internal hash table layout may happen to produce a stable order that matches the assertion expectation. On loaded runs or different hash seeds, the order changes and the ordered assertion fails.

### Fix 1 — Timestamp Assertion: Freeze Time

**Root cause:** `datetime.now()` varies with real clock; CI runs fast-in-UTC while developer runs slower-in-local-TZ.

**Reproduction script** — forces the failure by advancing the clock across a boundary:

```python
"""Reproduce timestamp flake: advance past second boundary."""
from unittest import mock
from datetime import datetime, timedelta
import zoneinfo

def test_timestamp_crosses_boundary():
    """
    Simulates the exact failure: a slow machine crosses into the next second,
    so strftime produces a different formatted output.
    """
    # Start at :59 seconds — close enough to roll over
    base = datetime(2025, 6, 15, 14, 0, 0, tzinfo=zoneinfo.ZoneInfo("America/New_York"))
    
    # Fast-forward by 2 seconds (simulating a slow machine)
    later = base + timedelta(seconds=2)
    
    # If the test naively compares now()-derived strings, they diverge
    assert later.strftime("%Y-%m-%d %H:%M:%S") != base.strftime("%Y-%m-%d %H:%M:%S")


def test_deterministic_with_freezegun():
    """Fix: freeze time so the assertion is invariant across machines/timezones."""
    from freezegun import freeze_time
    
    # Freezing to an absolute instant removes both clock drift AND timezone variation
    with freeze_time("2025-06-15T14:00:00+00:00"):
        from app.models import format_event_timestamp
        # Whatever the production code calls internally (whether time.time(),
        # datetime.now(), or datetime.utcnow()), freezegun patches it
        result = format_event_timestamp()
        assert result == "2025-06-15T14:00:00Z"
```

**Prescribed fix for the actual test:**

```python
# BEFORE (vulnerable):
def test_event_timestamp_is_formatted_correctly():
    event = EventFactory(created_at=datetime.now())
    assert event.formatted_timestamp() == datetime.now().strftime("%Y-%m-%d %H:%M:%S")


# AFTER (deterministic — two approaches, pick one):

# Option A: freezegun (recommended — patches all time sources globally)
@pytest.mark.freeze_time("2025-06-15T12:00:00")
def test_event_timestamp_is_formatted_correctly():
    event = EventFactory()  # created_at is frozen automatically
    assert event.formatted_timestamp() == "2025-06-15 12:00:00"


# Option B: explicit injection (no dependency — pass the frozen time as param)
def test_event_timestamp_is_formatted_correctly(monkeypatch):
    frozen = datetime(2025, 6, 15, 12, 0, 0, tzinfo=timezone.utc)
    monkeypatch.setattr("app.models.datetime", FrozenDatetime(fake=frozen))
    event = EventFactory()
    assert event.formatted_timestamp() == "2025-06-15 12:00:00 UTC"
```

Key detail: the freeze point must use an **absolute** instant (with timezone info or UTC), not a naive local time, so CI and developer machines converge on the same value regardless of their system TZ.

### Fix 2 — Async Worker Poll: Replace Sleep with Bounded Wait

**Root cause:** `await asyncio.sleep(2)` is a blind stall. It doesn't know if the work succeeded, failed, or is still running. Load makes the worker occasionally exceed 2s.

**Reproduction script** — forces the failure by artificially slowing the worker:

```python
"""Reproduce async-worker flake: add latency until sleep(2) is insufficient."""
import asyncio
import time

async def unreliable_worker(delay):
    """Worker that takes variable time — simulates load-induced delay."""
    await asyncio.sleep(delay)
    return {"status": "done", "items": [1, 2, 3]}


async def test_poll_fails_under_load():
    """Demonstrates the race: 2s sleep isn't enough when worker takes 2.5s."""
    start = time.monotonic()
    task = asyncio.create_task(unreliable_worker(delay=2.5))
    
    # Current (flaky) pattern:
    await asyncio.sleep(2)
    assert task.done(), "FAIL: worker hasn't finished yet — assertion runs too early"
    
    elapsed = time.monotonic() - start
    print(f"Test completed in {elapsed:.1f}s but took {elapsed} → incorrect outcome")


async def test_poll_succeeds_normally():
    """Under normal load, the worker finishes in <2s — test passes (masking the bug)."""
    task = asyncio.create_task(unreliable_worker(delay=1.5))
    await asyncio.sleep(2)
    assert task.done()  # passes, but hides the underlying fragility
```

**Prescribed fix for the actual test:**

```python
# BEFORE (vulnerable):
async def test_worker_completes_and_returns_results():
    handle = await spawn_async_worker(config)
    await asyncio.sleep(2)  # ← magic number, blind wait
    results = await handle.get_results()
    assert len(results["items"]) >= 3


# AFTER (deterministic — replace sleep with explicit waiting):

# Option A: asyncio.wait_for with timeout (preferred)
async def test_worker_completes_and_returns_results():
    handle = await spawn_async_worker(config)
    results = await asyncio.wait_for(handle.get_results(), timeout=10.0)
    assert len(results["items"]) >= 3


# Option B: Manual polling loop with backoff + max retries
async def test_worker_completes_and_returns_results():
    handle = await spawn_async_worker(config)
    for attempt in range(20):
        try:
            results = await asyncio.wait_for(handle.get_results(), timeout=0.5)
            break
        except asyncio.TimeoutError:
            if attempt == 19:
                raise TimeoutError("Worker did not complete within 10s")
            await asyncio.sleep(0.25)  # exponential-ish backoff
    assert len(results["items"]) >= 3


# Option C: Event/signaling (best architecture — but requires code change)
class AsyncWorker:
    def __init__(self):
        self._finished = asyncio.Event()
        
    async def start(self):
        try:
            await self._do_work()
        finally:
            self._finished.set()
    
    async def wait_for_completion(self, timeout=None):
        await asyncio.wait_for(self._finished.wait(), timeout=timeout)


async def test_worker_completes_and_returns_results():
    worker = AsyncWorker(config)
    asyncio.create_task(worker.start())
    await worker.wait_for_completion(timeout=10.0)
    results = worker.get_results()
    assert len(results["items"]) >= 3
```

Option A is the minimal invasive fix. Option C is the architecturally correct fix if you control the worker class — it eliminates polling entirely.

### Fix 3 — Dict Over Set: Sort Before Iterating

**Root cause:** `set` → `dict` construction iterates the set in an undefined (hash-randomized) order. Since Python 3.7 dicts preserve insertion order, the resulting dict's key order depends on whatever order the set yielded items — which differs per-process due to `PYTHONHASHSEED` randomization, and under load may differ due to memory allocator state affecting hash table layout.

**Reproduction script** — forces the failure by varying hash seeds:

```python
"""Reproduce set-ordering flake: run with different PYTHONHASHSEED values."""
import hashlib
import os


def _make_fixture_dict():
    """Simulates the vulnerable pattern: set → dict loses deterministic order."""
    fixture_ids = {"alpha", "beta", "gamma", "delta", "epsilon"}
    results = {fid: {"score": hash(fid)} for fid in fixture_ids}
    return results


def test_order_is_non_deterministic_across_hashes():
    """Running this under different PYTHONHASHSEED values shows instability."""
    orders_seen = []
    for seed in ["", "0", "12345", "98765", "-1"]:
        old_seed = os.environ.pop("PYTHONHASHSEED", None)
        if seed:
            os.environ["PYTHONHASHSEED"] = seed
        try:
            d = _make_fixture_dict()
            orders_seen.append(tuple(d.keys()))
        finally:
            if old_seed:
                os.environ["PYTHONHASHSEED"] = old_seed

    # With hash randomization enabled (default in Python 3.3+),
    # these tuples will differ across seeds:
    unique_orders = set(orders_seen)
    print(f"Unique orderings seen: {len(unique_orders)} out of 5 hash seeds")
    assert len(unique_orders) > 1, \
        f"All orders happened to match (unlikely). See: {unique_orders}"


def test_stress_reveal_crashes():
    """Run many times rapidly — under load, memory allocator changes increase variance."""
    orders = set()
    for _ in range(100):
        d = _make_fixture_dict()
        orders.add(tuple(d.keys()))
    print(f"Across 100 rapid invocations: {len(orders)} unique orderings")
    # This often reveals 2-5 distinct orderings even without env vars,
    # because memory fragmentation affects internal set hash table traversal
```

**Prescribed fix for the actual test:**

```python
# BEFORE (vulnerable):
@pytest.fixture
def multi_result_fixture(fixture_ids_from_set):
    """fixture_ids_from_set comes from a pytest-set or dynamic discovery → returns a set."""
    results = {}
    for fid in fixture_ids_from_set:   # ← set iteration order undefined!
        results[fid] = compute_result(fid)
    yield results


def test_all_results_are_consistent(multi_result_fixture):
    # Asserts implicitly depend on key ordering (e.g., json.dumps comparison,
    # or positional assertions on dict.values())
    expected_keys = ["alpha", "beta", "gamma"]
    assert list(multi_result_fixture.keys()) == expected_keys


# AFTER (deterministic — sort before constructing or asserting):

@pytest.fixture
def multi_result_fixture(fixture_ids_from_set):
    results = {}
    for fid in sorted(fixture_ids_from_set):  # ← sorted list, deterministic
        results[fid] = compute_result(fid)
    yield results


def test_all_results_are_consistent(multi_result_fixture):
    assert sorted(multi_result_fixture.keys()) == ["alpha", "beta", "gamma"]
    # If asserting on JSON serialization:
    assert json.dumps(multi_result_fixture, sort_keys=True) == expected_json


# Alternative: if the consumer needs insertion order preserved downstream,
# convert the set to a sorted list at the boundary:
def get_ordered_ids(raw_ids: set[str]) -> list[str]:
    """Turn unordered fixture IDs into a stable, reproducible order."""
    return sorted(raw_ids)
```

If the fixture IDs come from filesystem discovery (`Path.glob()` / `os.listdir()`), the fix is identical — wrap the discovery call with `sorted()`:

```python
def discover_fixture_files(directory: Path) -> list[Path]:
    """Discover YAML fixtures — deterministically ordered."""
    return sorted(directory.glob("*.yaml"))  # sorted by name, not filesystem hash order
```
