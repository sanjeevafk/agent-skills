## Systematic Debugging Analysis: Three Intermittent Test Failures

### Failure 1: Timestamp Formatting Assertion

**Symptom:** Fails 3/240 times; correlates with developer timezone. Reruns green.

#### Root Cause Trace

```
Expected timestamp  → datetime.now() / datetime.utcnow()
                     ↓ called without mocking
                   real wall-clock time at assertion moment
                     ↓ formatted via strftime or isoformat
                   "2025-08-25T14:03:27+00:00"
                     ↓ compared against expected literal
                   AssertionError (off by hours/days/months)
```

The assertion uses a **real current timestamp** as expected output instead of fixing/capturing the reference value. When developers in different timezones run the same test, `datetime.now()` returns different values, and if the test spans a UTC boundary (e.g., midnight UTC), even the *same* machine can produce different results between runs.

**Hypothesis ranking:**
1. (95%) `datetime.now()` or `datetime.utcnow()` used inside tested code or in test setup, but the expected value was computed at a different point in time (or hardcoded during authoring) without mocking.
2. (4%) Zone-dependent string formatting (e.g., `%Z` abbreviation like "EDT" vs "EST") used in comparison.

#### Minimal Reproduction

```python
# reproduces_the_bug.py
import os, sys
os.environ["TZ"] = "America/New_York"          # simulate EDT deviation
from freezegun import freeze_time

def test_timestamp_assertion_fails_without_freeze():
    """Demonstrates that an un-mocked datetime assertion is non-deterministic."""
    from module_under_test import generate_report_id
    
    actual = generate_report_id()                # internally calls now()
    
    # Without freezing, this is equivalent to writing your expected value
    # in your local timezone — it will differ across machines/timezones.
    import datetime
    assert actual == datetime.datetime.now().isoformat()   # race condition
```

Stress-run it ten times across two timezones:

```bash
TZ=UTC python -m pytest reproduces_the_bug.py -v --count=10
TZ=Asia/Kolkata python -m pytest reproduces_the_bug.py -v --count=10
```

#### Deterministic Fix

**Option A — Freeze time at the test boundary (recommended):**

```python
from freezegun import freeze_time

@freeze_time("2025-01-15T12:00:00+00:00")
def test_reports_use_correct_start_date():
    from mylib.reports import generate_report_id
    result = generate_report_id()
    assert "2025-01-15" in result                    # explicit reference date
```

**Option B — Capture, then assert:**

```python
def test_reports_use_correct_start_date():
    from mylib.reports import generate_report_id
    
    frozen = "2025-01-15T12:00:00+00:00"
    patcher = patch("mylib.reports.datetime")
    patcher.now.return_value = datetime.fromisoformat(frozen)
    
    with patcher:
        result = generate_report_id()
    
    assert "2025-01-15" in result
```

**Rule:** Never assert on a real-time value derived from `datetime.now()`, `time.time()`, or similar without first freezing or mocking the clock.

### Failure 2: Async Worker Polling with `sleep(2)`

**Symptom:** Fails when machine load is high. Correlates with other processes consuming CPU/IO. Reruns typically go green because the next run has a lighter load.

#### Root Cause Trace

```
Worker start          → asyncio.create_task(some_coro())
Poll loop              for _ in range(6):
                         sleep(2)                          ← fixed 2-second gap
                         check worker.done()
                           ├─ done → pass
                           └─ not done yet → continue loop
                       end for                             ← after 12 seconds total
                       assert worker.done()                 ← FAILS if still running
```

The poll loop waits exactly 2 seconds per tick, runs for at most 6 iterations (12 seconds total), then asserts the worker is done. On a loaded machine the coroutine may take 15–20 seconds — the fixed timeout is too short. The test **assumes bounded execution time** without any way to express the assumption.

**Hypothesis ranking:**
1. (90%) Hardcoded `sleep(2)` with insufficient maximum retries. The worker's worst-case duration exceeds the fixed budget under contention.
2. (8%) Worker has a real internal dependency (disk flush, network call, DB commit) that slows under load and the poll never accounts for it.

#### Minimal Reproduction

```python
# reproduces_flaky_poll.py
import asyncio, random

async def slow_worker():
    """Simulates variable-latency work."""
    await asyncio.sleep(random.uniform(0.1, 3.0))
    return "done"

async def flaky_poller(worker, max_wait=12):
    """Original pattern: fixed sleep with cap."""
    ticks = max_wait // 2         # 6 ticks × 2 s
    for _ in range(ticks):
        await asyncio.sleep(2)    # <── always 2 seconds
        if worker.done():
            return True
    return False                  # timed out

# Run under load to reproduce:
# asyncio.run(flaky_poller(asyncio.create_task(slow_worker())))
# fails ~30% of the time when slow_worker's delay > 12s
```

#### Deterministic Fix

**Replace fixed `sleep` with a proper retry-with-deadline loop using `asyncio.wait_for`:**

```python
async def robust_poller(coro_or_task, *, timeout=30, interval=0.5):
    """Poll until done or timeout; adapts to actual wall-clock drift."""
    if not asyncio.isfuture(coro_or_task):
        coro_or_task = asyncio.create_task(coro_or_task)
    
    deadline = asyncio.get_event_loop().time() + timeout
    
    while asyncio.get_event_loop().time() < deadline:
        if coro_or_task.done():
            return coro_or_task.result()
        await asyncio.sleep(interval)
    
    raise TimeoutError(
        f"worker did not finish within {timeout}s"
    )
```

**Usage in the test:**

```python
@pytest.mark.asyncio
async def test_async_worker_completes_under_load():
    result = await robust_poller(my_worker_task(), timeout=15)
    assert result.status == "complete"
```

**Why this is better:**
- `interval=0.5s` gives faster feedback on fast machines without wasting cycles.
- Absolute deadline prevents indefinite hanging while allowing the worker to exceed the old 12-second budget.
- Under low load, both versions pass quickly; under high load, the deadline version gives the worker a fair shot.

If the worker exposes a completion event/signalling primitive, prefer that over polling entirely:

```python
done = asyncio.Event()
asyncio.create_task(worker(done))
await asyncio.wait_for(done.wait(), timeout=30)
```

### Failure 3: Dict Iteration Order Over a Set of Fixture IDs

**Symptom:** Non-deterministic assertion failures. Correlates with machine load (because higher CPU → more thread scheduler churn → changes hash seed assignment order). Python 3.7+ guarantees *insertion order* for dicts, but **sets have no guaranteed ordering**, and converting a set to a dict (or iterating a set while building expectations) produces platform-dependent results.

#### Root Cause Trace

```python
# Typical buggy pattern:
fixture_ids = {"alpha", "beta", "gamma"}        # unordered set
computed = process(fixture_ids)                  # iteration order of fixture_ids varies
assert list(computed.keys()) == ["alpha", "beta", "gamma"]  # order-dependent compare
```

When `fixture_ids` is a `set`, its iteration order depends on:
1. The **hash seed** (`PYTHONHASHSEED`), which Python randomizes by default (since Python 3.3).
2. The **hash function's state** at runtime, which can shift slightly between processes or under load.
3. Collision resolution chain length in the underlying hash table.

Different hash seeds → different iteration order → keys built into dict appear in different order → assertion compares `[A, B, C]` against `[C, A, B]` → intermittent failure.

**Hypothesis ranking:**
1. (92%) Test builds an ordered expectation against a value produced by iterating a `set`. The set itself isn't wrong — the *comparison* assumes insertion order where none exists.
2. (6%) `pytest_configure` or conftest sets `PYTHONHASHSEED=0` in CI but not locally, so CI is deterministic while dev machines use randomized seeds.
3. (2%) OrderedDict was intended but `{...}` literal creates a regular `dict`.

#### Minimal Reproduction

```python
# Reproduces nondeterminism across multiple runs:
import subprocess, sys

code = """
s = {"x", "y", "z"}
d = {k: len(k) for k in s}
print(list(d.keys()))
"""

for i in range(20):
    r = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True)
    print(r.stdout.strip())
```

On some machines this prints `['z', 'x', 'y']` consistently (stable seed in one process); across many machines/processes you'll see varied orders — and sometimes the same order repeating (which explains why only 3/240 tests fail and reruns often go green).

#### Deterministic Fixes

**Fix 1 — Sort before comparing (quickest, no behavioral change):**

```python
# Before (flaky):
assert list(result.keys()) == sorted_fixture_ids  # sorted_fixture_ids is a list from a set

# After (deterministic):
assert sorted(result.keys()) == sorted(sorted_fixture_ids)
```

**Fix 2 — Use a `list` or `tuple` as input instead of `set` (prevents the problem upstream):**

```python
# Before (ambiguous intent):
fixture_ids = {"alpha", "beta", "gamma"}    # set — unordered

# After (explicit order):
fixture_ids = ("alpha", "beta", "gamma")    # tuple — ordered
# or
fixture_ids = ["alpha", "beta", "gamma"]    # list  — ordered
```

**Fix 3 — Assert membership without order dependence (if order truly doesn't matter):**

```python
assert set(result.keys()) == {"alpha", "beta", "gamma"}
assert all(result[k] == expected[k] for k in ["alpha", "beta", "gamma"])
```

**Fix 4 — Force deterministic hash seed in CI and local testing (environmental guard):**

Add to `.github/workflows/test.yml` and the local `Makefile`:

```yaml
env:
  PYTHONHASHSEED: 0
```

This makes Python's set/dict iteration deterministic across runs. It does **not** fix the root cause (unordered comparison) but makes the bug reproducible everywhere and serves as a safety net. Prefer fixes 1–3 and use #4 as a secondary layer.
