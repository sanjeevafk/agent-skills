# Systematic Debugging Analysis

## Phase 1: Root Cause Investigation

### Symptom Summary
- 3 of 240 tests fail intermittently (~1.25% failure rate)
- Passes reliably in CI, fails on developer machines
- Failures correlate with machine load + developer timezone
- Reruns usually go green

### Failure Modes Observed

|-----------|---------|------------|----------------|
| Formatted timestamp assertion | 0% | ~15% | Green on rerun |
| Async worker poll with `sleep(2)` | 0% | ~20% | Green on rerun |
| Dict order over set of fixture IDs | 0% | ~12% | Green on rerun |

### Hypothesis Ranking (by likelihood)

| # | Hypothesis | Evidence Support | Confidence |
|---|-----------|-----------------|------------|
| H1 | Timestamp test reads `datetime.now()` affected by timezone offset (TZ env var differs between CI=UTC and local) | Correlates with timezone; exact boundary failures happen when `now()` crosses the second/minute mark being asserted | ★★★★★ |
| H2 | Async worker uses fixed `sleep(2)` instead of condition-based waiting; machine load extends worker time beyond 2s | Correlates with machine load; retry goes green because worker eventually completes | ★★★★☆ |
| H3 | Dict/set iteration over unordered collection subject to Python's `PYTHONHASHSEED` randomization (default randomized since Py 3.3) | Hash seed varies per process invocation; CI may pin `PYTHONHASHSEED=0` while locals use random | ★★★★☆ |
| H4 | Race condition between test setup/teardown sharing mutable state across tests | Explains intermittency but less directly tied to timezone/load correlation | ★★☆☆☆ |

### Why CI Passes While Locals Fail

- **CI**: Typically runs on isolated VMs with `TZ=UTC`, fixed `PYTHONHASHSEED`, minimal background load, fresh environment per job
- **Local**: Variable `TZ` setting, randomized hash seeds, competing CPU/io from IDE/editor/sync tools, potentially stale test runner state

## Phase 2-3: Hypotheses Validated Against Code Patterns

Each hypothesis maps to a specific anti-pattern. Below are the reconstructed test code exhibiting each bug, followed by diagnosis.

### Bug 1: Timestamp Assertion Affected by Timezone Offset

**Root cause:** Test captures `datetime.now()` at call site A, but the SUT formats using `datetime.now()` at call site B. Between A and B, wall-clock advances past the expected boundary. Under timezone offsets (non-UTC), the boundary shifts. Machine load increases latency between A and B, making the race more likely.

### Bug 2: Fixed Sleep Instead of Condition-Based Waiting

**Root cause:** Test polls an async worker with a fixed `time.sleep(2)`. Worker takes <2s under low load (CI/fast machines) but >2s under high load (dev machines). The race condition is inherently timing-dependent. `PYTHONHASHSEED` isn't involved here — the load correlation alone confirms this is a timing bug.

### Bug 3: Set Iteration Order Determinism

**Root cause:** Test iterates over a `set` expecting deterministic order (e.g., for comparison against a list, or for string formatting that depends on element position). Python sets are unordered — iteration order depends on `hash()` values, which are randomized per-process via `PYTHONHASHSEED`. This means different test runs produce different iteration orders, causing flaky assertions.

def reproduce_bug_2_timing_race():
    """
    Demonstrates Bug 2: fixed sleep vs condition-based wait.
    """
    async def slow_worker(duration):
        await asyncio.sleep(duration)
        return "done"

    async def run_test(sleep_duration, worker_duration):
        task = asyncio.create_task(slow_worker(worker_duration))
        await asyncio.sleep(sleep_duration)
        try:
            done, _ = await asyncio.wait({task}, timeout=0.0)
            if done:
                result = next(iter(done)).result()
                print(f"  [TIME-BASED] sleep={sleep_duration}s, worker={worker_duration}s → {result!r} ✓")
                return True
            else:
                task.cancel()
                print(f"  [TIME-BASED] sleep={sleep_duration}s, worker={worker_duration}s → TIMEOUT ✗")
                return False
        except Exception as e:
            task.cancel()
            print(f"  [TIME-BASED] sleep={sleep_duration}s, worker={worker_duration}s → ERROR ✗")
            return False

    async def run_fix(timeout, worker_duration):
        task = asyncio.create_task(slow_worker(worker_duration))
        try:
            result = await asyncio.wait_for(task, timeout=timeout)
            print(f"  [CONDITION-BASED] timeout={timeout}s, worker={worker_duration}s → {result!r} ✓")
            return True
        except asyncio.TimeoutError:
            print(f"  [CONDITION-BASED] timeout={timeout}s, worker={worker_duration}s → TIMEOUT ✗")
            return False

    asyncio.run(run_test(2.0, 0.5))   # Low load: passes
    asyncio.run(run_test(2.0, 3.0))   # High load: fails
    print()
    asyncio.run(run_fix(10.0, 0.5))   # Always works
    asyncio.run(run_fix(10.0, 3.0))   # Always works

## Summary of Fixes

| Bug | Root Cause | Fix | Technique |
|-----|-----------|-----|-----------|
| **Timestamp** | Wall-clock drift between data capture and assertion point | `freezegun.freeze_time()` to freeze `datetime.now()` at a known value | Time freezing |
| **Async poll** | Fixed `time.sleep(N)` instead of waiting for actual completion condition | `asyncio.wait_for(task, timeout=T)` with explicit timeout guard | Condition-based waiting |
| **Set order** | `PYTHONHASHSEED` randomization causes set iteration order to vary per process | `sorted(set)` before iteration to guarantee deterministic ordering | Sorting unordered collections |

### Why Reruns Go Green

- **Bug 1**: Second attempt happens at a slightly different wall-clock moment, possibly still within the expected second boundary
- **Bug 2**: Retry gives the worker more total elapsed time across attempts, eventually completing within a poll window
- **Bug 3**: By pure chance, the new process hash seed produces the "right" ordering again

### Recommended CI Hardening

The core lesson from all three bugs: **tests must be deterministic**. Any reliance on wall-clock time, fixed delays, or unordered iteration introduces non-determinism that manifests as intermittent failures correlated with the very factors you can't control (load, timezone, hash seed).
