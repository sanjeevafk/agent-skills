## Complete Analysis & Fixes

### Phase 1: Hypotheses Ranked by Likelihood

**Hypothesis 1 — Time is not frozen. Root cause: timezone-dependent formatting.**

Test A asserts on a formatted timestamp like `"2024-03-15 14:30:00"` but derives it from `datetime.now()` or equivalent. CI runs in UTC; developer machines run in local timezones. The string changes when the timezone differs, so the assertion passes in CI but fails intermittently locally depending on what second you happen to run it and whether the boundary falls on an hour/day change. The "reruns go green" pattern occurs because retries land at a different clock reading. This explains the correlation with both machine load (system time can drift under load via scheduler ticks) and timezone.

**Hypothesis 2 — Real-time sleeps mask async timing races. Root cause: non-deterministic polling budget.**

Test B polls an async worker using fixed `await asyncio.sleep(2)` iterations. Under low CPU pressure on dev machines, the sleep + event loop overhead adds up—each iteration takes ~2.1-2.3s instead of exactly 2s. Over multiple iterations, this compounds until the total poll budget exceeds the test timeout or the worker hasn't started yet. In CI (lighter load, deterministic scheduling), the loop completes before the timeout. "Reruns go green" simply means the random jitter one retry happened to be fast enough.

**Hypothesis 3 — Set-to-dict introduces hash-randomized ordering. Root cause: `set()` → dict insertion order depends on `PYTHONHASHSEED`.**

Test C builds a dict by iterating over a `set` of fixture IDs. Even though Python 3.7+ dicts preserve insertion order, the *insertion order itself* comes from iterating the set—and `set` iteration order is randomized per process via `PYTHONHASHSEED` (affects string/bytes/datetime hashing). Different fixture collection order → different key order in the dict → different test execution path → non-deterministic results. This doesn't require timezone or load correlation; it just needs enough runs to hit the "unlucky" ordering. Explains why Test C is the third intermittent failure and correlates with the overall instability pattern.

**Priority: H1 ≥ H2 > H3** — Together they explain all three signals (timezone, load, and raw randomness).

### Phase 4: Deterministic Fixes

#### Fix A: Freeze time with `freezegun`

**Install**: `pip install freezegun` (dev dependency)

**Before (flaky)**:
```python
def test_timestamp_format():
    result = my_module.format_timestamp(my_module.get_current_time())
    assert result == "2024-03-15 14:30:00"  # breaks if TZ differs
```

**After (deterministic)**:
```python
from freezegun import freeze_time

@freeze_time("2024-03-15 14:30:00+00:00")
def test_timestamp_format():
    result = my_module.format_timestamp(my_module.get_current_time())
    assert result == "2024-03-15 14:30:00+00:00"
```

If `freezegun` is too heavyweight for your project, use `pytest-timeout` with explicit mock injection instead:

```python
def test_timestamp_format(mocker):
    fake_time = datetime.datetime(2024, 3, 15, 14, 30, 0, tzinfo=timezone.utc)
    mocker.patch.object(my_module, "get_current_time", return_value=fake_time)
    result = my_module.format_timestamp(my_module.get_current_time())
    assert result == "2024-03-15 14:30:00+00:00"
```

Either approach makes the test independent of system timezone and wall-clock time.

#### Fix B: Replace sleep-loop with proper async wait

**Before (flaky)**:
```python
@pytest.mark.asyncio
async def test_async_worker_completes():
    task = asyncio.create_task(worker_process(items))
    
    for _ in range(5):                    # poll loop
        if task.done():
            break                         # ← succeeds only by luck
        await asyncio.sleep(2)            # ← blocks event loop, wastes budget
    assert not task.cancelled()
```

**After (deterministic)**:
```python
@pytest.mark.asyncio
async def test_async_worker_completes():
    task = asyncio.create_task(worker_process(items))
    
    try:
        result = await asyncio.wait_for(task, timeout=10.0)
        assert result == expected_result
    except asyncio.TimeoutError:
        pytest.fail("Worker did not complete within timeout")
```

Key differences:
- `wait_for` measures real elapsed time against a precise deadline, not "number of sleep iterations"
- `assert task.done()` replaced by awaiting `task.result()` — the test genuinely waits for completion
- Timeout is declared once, not accumulated through sleep iterations
- Under load, the test fails *predictably* with a clear error rather than silently succeeding on a rerun

Alternative if `wait_for` isn't suitable (e.g., you need partial progress checks):

```python
@pytest.mark.asyncio
async def test_async_worker_progressive():
    task = asyncio.create_task(worker_process(items))
    deadline = asyncio.get_event_loop().time() + 10.0
    
    while asyncio.get_event_loop().time() < deadline:
        if task.done():
            break
        await asyncio.sleep(0.1)  # small interval, not blocking budget
    else:
        pytest.fail("Worker timed out")
    
    assert task.result() == expected_result
```

This polls every 100ms instead of every 2 seconds — far more responsive, no wasted budget.

#### Fix C: Ensure deterministic dict insertion order

**Before (flaky)**:
```python
@pytest.fixture(params={"test_alpha", "test_bravo", "test_charlie"})  # ← set literal!
def fixture_ids(request):
    ...

def test_dict_order(fixture_ids):
    ids = {fid: fid.upper() for fid in fixture_ids}  # iterates from set
    assert list(ids.keys()) == ["test_alpha", ...]   # breaks with different hash order
```

**After (deterministic)**:
```python
@pytest.fixture(params=["test_alpha", "test_bravo", "test_charlie"])  # ← sorted list!
def fixture_ids(request):
    ...

def test_dict_order(fixture_ids):
    # Option 1: build from sorted sequence
    ids = {fid: fid.upper() for fid in sorted(fixture_ids)}
    
    # Option 2 (better): don't build a dict at all, use OrderedDict or list
    ordered_pairs = sorted([(fid, fid.upper()) for fid in fixture_ids])
    assert ordered_pairs == [("test_alpha", "TEST_ALPHA"), ...]
```

Two fixes here:
1. **Fixture params**: Use a `list` (or `tuple`), not a `set`. Lists preserve declaration order. If you want guaranteed alphabetical order, wrap with `sorted()`.
2. **Dict construction**: When building a dict from a collection, always sort first: `{k: v for k, v in sorted(collection)}`. This makes the dict immune to `PYTHONHASHSEED`, `set` implementation details, and anything else that randomizes iteration.

If the production code *itself* (not just tests) uses set→dict ordering and relies on a specific order, that's a separate bug. Test C exposes that the production logic has a hidden dependency on iteration order — fix the production code to either use `sorted()` or maintain an explicit ordering mechanism.
