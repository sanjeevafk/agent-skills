## Systematic Debugging Analysis

### Phase 1 — Symptoms & Pattern Recognition

Three distinct failure modes, each with a different root cause pattern:

| Test | Trigger | Why Reruns Go Green | Timezone/Machine Link |
|------|---------|---------------------|-----------------------|
| Timestamp assertion | Clock boundary crossing during test execution | Next attempt starts at a "safe" offset | Directly tied to timezone offset (UTC ± N hours changes which hour/day boundaries are crossed during formatting) |
| Async worker poll (`sleep(2)`) | Worker doesn't complete within expected window | Retry succeeds because worker eventually finishes | Heavy machines = slower workers = more timeouts; also ties to timezone if worker logs use local timestamps that shift under load |
| Dict/set iteration order | Hash randomization + non-sorted key access | Python's hash seeds may differ per process; rerun often lands in a "good" order | Not directly timezone-linked, but `PYTHONHASHSEED` defaults vary by distro/CI config vs dev environment |

---

### Phase 2 — Hypotheses Ranked by Likelihood

**H1 (Timestamp test): Test runs across an hour/day boundary.** The formatter produces `"2026-08-25T23:59:59Z"` on one run and `"2026-08-26T00:00:00Z"` on the next. The assertion hardcodes an expected value that only matches if no boundary is crossed. *Likelihood: HIGH* — timezone correlation confirms it depends on the system clock relative to UTC.

**H2 (Async worker): Insufficient timeout / busy-loop with fixed `sleep(2)`.** The test sleeps for a fixed number of cycles assuming the worker completes within N seconds. Under load, the worker exceeds the total wait time. *Likelihood: HIGH* — load correlation is classic timing-race.

**H3 (Set iteration): Non-deterministic ordering due to hashing / unordered collection.** The test compares a dict built from iterating a set, then asserts structural equality. Sets have no guaranteed order; `dict` preserves insertion order in Python 3.7+, so the resulting key order varies between runs. *Likelihood: MEDIUM-HIGH* — explains intermittent failures; CI likely pins `PYTHONHASHSEED=0` while dev machines don't.

**H4 (Cascading resource contention):** Low-probability shared-resource bottleneck (filesystem lock, database connection pool exhaustion). Would explain general load sensitivity but not the specific symptoms observed. *Likelihood: LOW* — the other three hypotheses already fully explain all observed patterns.

### Phase 3 — Minimal Reproduction Strategy

#### Test A: Forcing a Timestamp Boundary Fail

```python
import time
from datetime import datetime, timezone, timedelta
from unittest.mock import patch

def test_timestamp_assertion_boundary():
    """Reproduce H1: force the clock to cross an hour boundary mid-test."""
    
    real_time = datetime(2026, 8, 25, 23, 59, 58, tzinfo=timezone.utc)
    call_count = [0]

    def fake_now():
        call_count[0] += 1
        # First call: 23:59:58 → Second call: 23:59:59 → Third call: 00:00:00 next day
        offset = timedelta(seconds=call_count[0])
        return real_time + offset

    with patch("module_under_test.datetime", wraps=datetime), \
         patch.object(datetime, "now", fake_now):
        result = module_under_test.format_current_timestamp()  # whatever function you're testing
        # This will now be deterministic — reproduce consistently whether
        # the formatted string uses the first tick, second, or third.
```

**Even simpler** — inject `freezegun`:

```python
from freezegun import freeze_time

@freeze_time("2026-08-25 23:59:58")
def test_timestamp_does_not_cross_boundary():
    with freeze_time("2026-08-25 23:59:58"):
        ts = format_current_timestamp()
        assert ts == "2026-08-25 23:59:58 UTC"  # frozen, never drifts
```

#### Test B: Stress-Running the Async Polling Test

Fix is simply `asyncio.wait_for` or `await worker.task` directly.

#### Test C: Forcing Set Iteration Failure

```python
import os

# Before running this specific test suite:
os.environ["PYTHONHASHSEED"] = "random"

# Run repeatedly: pytest tests/test_set_iteration.py -v --count=100
```

Python's `-R` flag or `PYTHONHASHSEED=random` forces hash randomization. Running the test hundreds of times makes the wrong-order collisions surface deterministically.

To *force* a specific bad order:

```python
def test_dict_from_set_ignores_order():
    """Demonstrate the bug: iteration order is undefined, so comparing dicts
       that depend on that order is inherently flaky."""
    
    fixture_ids = {"alpha", "bravo", "charlie"}  # plain set, unordered
    mapping = {fid: f"label-{fid}" for fid in fixture_ids}  # insertion order ≠ defined order
    
    # This is what the broken test probably does:
    expected = {"alpha": "label-alpha", "bravo": "label-bravo", "charlie": "label-charlie"}
    
    # On some hash seeds this passes; on others it fails.
    # The fix: compare as sets of items, not as dicts with positional expectations.
    assert set(mapping.items()) == set(expected.items())  # order-independent
```

### Phase 4 — Deterministic Fixes

#### Fix A: Timestamp Test — Freeze or Offset the Clock

```python
import pytest
from freezegun import freeze_time

# Option 1: Freeze time entirely (preferred)
@pytest.mark.freeze_time("2026-08-25T12:00:00Z")
def test_formatted_timestamp():
    from module_under_test import format_current_timestamp
    ts = format_current_timestamp()
    assert ts == "2026-08-25 12:00:00 UTC"  # always identical

# Option 2: Inject a fixed datetime object
def test_formatted_timestamp_injected(fixtures_dt):
    with patch("module_under_test.datetime") as mock_dt:
        mock_dt.now.return_value = fixtures_dt.fixed_now
        ts = format_current_timestamp()
        assert ts == fixtures_dt.expected_string
```

**Why this works:** No wall-clock dependency, no timezone edge cases, no variance between machines or reruns. Freezegun is the standard library-approved way to solve exactly this problem.

---

#### Fix B: Async Worker — Replace Sleeping with Proper Await

```python
# BEFORE (broken — relies on sleep cycles):
async def test_worker_completes():
    worker.start()
    for _ in range(5):
        await asyncio.sleep(2)
        if worker.is_ready():
            break
    assert worker.is_ready()           # flaky under load

# AFTER (fixed — explicit await of completion):
async def test_worker_completes():
    task = asyncio.create_task(worker.run())
    result = await asyncio.wait_for(task, timeout=30.0)  # waits for actual completion
    assert result.status == "completed"
    assert result.data == expected_payload
```

Key principle: **never `sleep` to wait for asynchronous events**. Either:
- `await` the task/coroutine directly (best, if the API supports it)
- Use `asyncio.wait_for()` with a generous timeout
- Use an `asyncio.Event` signal from the worker rather than polling

#### Fix C: Set Iteration Order — Eliminate Ordering Assumptions

```python
# BEFORE (broken — treats set iteration as ordered):
def test_fixture_output_order():
    fixture_ids = {"id-a", "id-b", "id-c"}       # unordered set
    output = {fid: build_fixture(fid) for fid in fixture_ids}  # unpredictable key order
    expected = {"id-a": ..., "id-b": ..., "id-c": ...}    # expects sorted/pinned order
    assert output == expected                     # flaky

# AFTER (fixed — sort keys explicitly, or compare order-independently):
def test_fixture_output_sorted():
    fixture_ids = {"id-a", "id-b", "id-c"}
    output = {}
    for fid in sorted(fixture_ids):               # deterministic order
        output[fid] = build_fixture(fid)
    expected = {"id-a": ..., "id-b": ..., "id-c": ...}
    assert output == expected

# OR, if order truly doesn't matter semantically:
def test_fixture_output_unordered():
    fixture_ids = {"id-a", "id-b", "id-c"}
    output = {fid: build_fixture(fid) for fid in fixture_ids}
    expected_items = {("id-a", ...), ("id-b", ...), ("id-c", ...)}
    assert set(output.items()) == expected_items  # position-independent
```

**Also pin CI:** Add `PYTHONHASHSEED=0` to the CI environment to make it match the common local default, preventing false confidence. But the code fix above is the real solution.

### Summary Table

| Root Cause | Category | Fix | Determinism Guarantees |
|---|---|---|---|
| Wall clock crosses boundary | Time-dependent | `freezegun.freeze_time()` around the assertion | Zero clock variance |
| Fixed `sleep(2)` < worker latency | Race condition | `await asyncio.wait_for(task, timeout=N)` | Waits for actual completion |
| Unordered set → dict insertion | Hash/randomization | `sorted()` iteration or `set(dict.items())` comparison | Eliminates ordering assumption |

All three fixes are **deterministic by construction** — they remove the stochastic element (clock, scheduler, hash seed) from the assertion itself rather than trying to control the environment.
