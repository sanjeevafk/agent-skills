## Ranked Hypotheses (by likelihood given evidence)

### H1: `test_timestamp_format` — clock drift between expectation and assertion

**Likelihood: Very High**

The timezone correlation + machine-load correlation points directly at wall-clock formatting. The likely bug is constructing a "expected" timestamp from system time at setup and comparing it against a formatted result at assertion, where the second can roll over into a new minute/second/hour if the machine is under load. Timezone enters if the code parses local time or formats naive datetimes as UTC.

```python
# --- REPRODUCTION: forces failure by sleeping across a boundary ---
import time
from datetime import datetime, timezone

def test_timestamp_format_repro():
    """Reproduce: expected built from now(), compared after blocking call."""
    expected = datetime.now(timezone.utc).replace(microsecond=0)
    time.sleep(1.1)  # simulate load
    actual = format_recorded_timestamp()  # real function under test
    assert actual == expected.strftime("%Y-%m-%dT%H:%M:%SZ")
    # On a slow machine ~at :59s→:00s of a new minute, this diverges by 1 unit.
```

**Fix:** Freeze time via `pytest-freezegun` (or factory-boy's frozen property, or a test double on whatever abstraction the production code uses):

```python
# --- DETERMINISTIC FIX ---
from freezegun import freeze_time

@freeze_time("2026-08-26T12:00:00Z")
def test_timestamp_format():
    result = format_recorded_timestamp()
    assert result == "2026-08-26T12:00:00Z"
```

Key rule: **never derive expected values from `datetime.now()` inside a test**. Always inject or freeze.

### H2: `test_async_worker_polling` — fixed sleep instead of bounded retry with jitter

**Likelihood: Very High**

The `sleep(2)` polling pattern is a textbook timing race. Under low machine load, the worker finishes before the first poll wakes up → pass. Under high load, the worker starts but hasn't completed when the final poll returns → fail. CI machines are consistently fast/lightly loaded; dev machines vary widely.

```python
# --- REPRODUCTION: stress-runs the fix loop under load ---
import asyncio
import random
import threading
import time

async def worker():
    """Simulates async worker whose latency varies under load."""
    await asyncio.sleep(random.uniform(0.5, 3.5))  # sometimes > 2s total
    return "done"

async def current_polling_impl():
    """Buggy version: sleeps exactly 2 seconds once."""
    _ = await worker()
    await asyncio.sleep(2)          # <<— single fixed wait, no retry
    result = check_worker_status()
    assert result == "completed"   # may see "running" or "pending"
```

**Fix:** Replace the fixed sleep with a bounded retry loop with exponential backoff and a hard timeout:

```python
# --- DETERMINISTIC FIX ---
import asyncio
from datetime import timedelta
import pytest_freezegun  # or just unittest.mock

TIMEOUT_SECONDS = 10
BASE_DELAY = 0.1

async def test_async_worker_polling_fixed():
    handle = spawn_worker()
    deadline = asyncio.get_event_loop().time() + TIMEOUT_SECONDS

    while asyncio.get_event_loop().time() < deadline:
        status = await check_worker_status(handle)
        if status == "completed":
            return  # passed
        remaining = deadline - asyncio.get_event_loop().time()
        if remaining <= 0:
            break
        delay = min(BASE_DELAY * 2 ** retries, 1.0)
        await asyncio.sleep(delay)

    raise AssertionError(f"Worker did not complete within {TIMEOUT_SECONDS}s; final status={status}")
```

Key rules:
- **Never use a single fixed `sleep` to wait for an external event.**
- Every poll has: (a) a hard deadline, (b) exponential backoff, (c) a clear error message showing final state.
- In CI-fast environments the test still passes instantly (first poll succeeds); on slow devs it waits deterministically rather than flaking.

### H3: `test_fixture_id_iteration_order` — set/dict non-determinism

**Likelihood: Medium-High**

Python's `dict` insertion order is guaranteed since 3.7+, BUT if the code constructs the key set from a `set()` literal or `set(...)` constructor, then iterates over it as keys in a dict, the iteration order is deterministic per-process but **not** consistent across runs or machines. Pytest fixture IDs derived from unordered sets will produce tests in varying order; if a test itself *asserts* something about the order of iteration (e.g., positional comparison against a list), it flakes.

```python
# --- REPRODUCTION: shows non-deterministic iteration ---
def test_fixture_id_order_repro():
    """Bug: iterating a set-derived dict expects positional match."""
    ids = {"alpha", "beta", "gamma"}          # set — no guaranteed order
    mapping = {fid: fid.upper() for fid in ids}
    labels = [mapping[k] for k in mapping.keys()]  # order is hash-randomized
    assert labels == ["ALPHA", "BETA", "GAMMA"]      # arbitrary order
    # Passes when CPython seed happens to sort them, fails otherwise.
```

Why does it correlate with machine load? Higher load → more memory pressure → different GC timing → different hash seeds for built-in `random` (PYTHONHASHSEED is `None` by default, i.e. randomized per process). CI typically pins `PYTHONHASHSEED=random` deterministically or the containers reuse the same seed.

**Fix:** Sort explicitly before any assertion that cares about order:

```python
# --- DETERMINISTIC FIX ---
@pytest.mark.parametrize("fixture_id", sorted({"alpha", "beta", "gamma"}))
def test_fixture_id_iteration_order(fixture_id):
    """Each ID tested individually in sorted order."""
    label = resolve_label(fixture_id)
    assert label == fixture_id.upper()

# Or, if you need the whole collection together:
def test_fixture_collection_ordered():
    ids = {"alpha", "beta", "gamma"}
    mapping = {fid: fid.upper() for fid in ids}
    labels = [mapping[k] for k in sorted(mapping.keys())]  # <-- sorted()
    assert labels == ["ALPHA", "BETA", "GAMMA"]
```

Key rules:
- **If order matters, sort it.** Never trust set or dict-unordered iteration.
- When deriving pytest `@parametrize` IDs from a dynamic set, wrap it in `sorted(...)`.
- Set `PYTHONHASHSEED=0` in CI (pytest already does this implicitly in some versions) and document it so locals reproduce.

## General Anti-Flake Rules (add to project CONTRIBUTING)

1. **No wall-clock reads in tests.** Use `freezegun.freeze_time`, `time-monotonic` for durations, or inject a clock interface.
2. **No fixed sleeps for synchronization.** All external-event waits must be bounded retries with deadlines.
3. **Sort everything that's ordered.** Sets → `sorted()`, dicts → iterate only when order doesn't matter.
4. **Pin `PYTHONHASHSEED` in CI.** Run `PYTHONHASHSEED=0 python -m pytest` in the pipeline and document it.
5. **Stress-test before merge.** The `test_flaky_stress.py` module above (50+ iterations with varying seeds) must pass before a PR lands.
