## Systematic Debugging Analysis: Three Flaky Tests

### Phase 1: Root Cause Investigation

#### Symptom Profile

| Attribute | Detail |
|-----------|--------|
| CI passes | Every time |
| Local fails | ~3/240 tests, intermittent |
| Reruns usually go green | → race condition or timing dependency |
| Correlates with machine load | → real-time sensitivity (sleep, wall-clock) |
| Correlates with timezone | → UTC/local conversion somewhere in the assertion |

These are textbook **determinism failures**: the tests depend on external clock, thread scheduling, or unordered collections.

### Phase 2: Ranked Hypotheses

**H1 (Most Likely): Timestamp assertion using local wall-clock**

The formatted-timestamp test likely formats `datetime.now()` or a model's `.created_at` field into an ISO string or human-readable format, then asserts exact equality against an expected value. Under high CPU load on a developer machine, the wall-clock advances during the SUT execution window between "capture now" and "assert now", producing a mismatch. Timezone correlation means the test uses `datetime.now()` instead of `datetime.utcnow()` (or `time.UTC`), so different timezones see different formatted outputs even if latency is constant.

Root cause: comparing mutable, non-deterministic values without freezing time.

```
BAD:    assert response["ts"] == datetime.now().strftime("%Y-%m-%d %H:%M")
                    ^^^^^^^^^^^^  ← changes between capture and assertion
GOOD:   with freeze_time("2025-01-01"):
            ts = generate_timestamp()
            assert ts == "2025-01-01T00:00:00Z"
```

**H2 (Very Likely): Async worker polling with fixed `sleep(2)`**

A test that creates an async background worker, signals it, then does `sleep(2); assert worker.done()` relies on the assumption that the work always completes within 2 seconds. On a loaded dev machine the GIL contention or event-loop scheduling delays can push completion past 2s. CI runs on isolated low-load machines where 2s is always sufficient.

Root cause: fixed sleep replaces proper async readiness probe (future/result/wait).

**H3 (Likely): Dict/set iteration order over fixture IDs**

A test iterates over a `set()` of fixture IDs and asserts output ordering or positional mapping. CPython has had stable hash randomization since Python 3.3, but setting `PYTHONHASHSEED` differently (e.g., CI seeds it, a developer doesn't, or vice-versa) produces different traversal orders. Alternatively, the test collects results into a plain `dict` keyed by set elements and asserts `list(dict.keys())` order — which is insertion-order dependent, not sorted.

Root cause: treating an unordered collection (`set`) as if its iteration order is deterministic.

| # | Root Cause | Broken Pattern | Fix | Key Principle |
