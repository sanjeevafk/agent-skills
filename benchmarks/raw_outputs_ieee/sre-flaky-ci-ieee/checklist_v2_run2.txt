# Flaky Test Analysis — Systematic Investigation & Fixes

## Phase 1: Root Cause Investigation

### Common Thread Across All Three Failures

All three failures share a single underlying class: **non-deterministic behavior sourced from the machine environment** (load → timing variance, timezone → wall clock variance, memory allocator → iteration order variance). CI typically runs on clean, low-load runners with UTC as the default timezone, making these latent races never surface there.

---

### Test 1: Timestamp Assertion

**Symptom:** Failure correlates with developer timezone; passes in CI.

**Hypothesis (Rank 1 — Most Likely):** The code uses a naive local-time formatter (e.g., `datetime.now()` or `strftime` without timezone specification), and the test compares against an expected string built in a different timezone context than the code under test. When the developer's timezone offset puts them in a different hour/day than the "expected" value, assertion fails. Intermittent because some tests run across midnight boundaries or DST transitions.

**Data flow trace:**
```
Code: datetime.now().strftime("%Y-%m-%d %H:%M:%S")  → produces "2026-08-25 23:45:12" (local)
Test: f"Expected '2026-08-25 20:45:12'"              → built with assumed tz
Assertion: "23:45:12" != "20:45:12"                   → FAIL
```

**Pattern evidence:** Working CI runs because GitHub Actions runners default to UTC. Developer machines don't.

---

### Test 2: Async Worker Poll with `sleep(2)`

**Symptom:** Fails intermittently (~3/240); reruns go green; correlates with machine load.

**Hypothesis (Rank 1 — Most Likely):** Hardcoded `sleep(2)` assumes the async worker completes within exactly 2 seconds. On a loaded machine, event loop scheduling delay + CPU contention pushes completion past 2 seconds → timeout/poll limit reached before the task finishes. Rerun succeeds because subsequent runs have fresher state, shorter warmup, or just get lucky with scheduling.

**Data flow trace:**
```
Test starts async task → polls every 0.5s for up to 5 iterations (2.5s total)
                       → actual poll loop: check() if done break, else sleep(0.5)
Wait — sleep(2) is the polling interval? Or a single sleep? Let me consider both:

Scenario A (single sleep):
  start(task) → sleep(2) → assert task.done()    → if task takes 2.1s → FAIL

Scenario B (polling loop):
  start(task) → for _ in range(5): if done: break; sleep(0.5)   → standard pattern
  If the original is actually `await asyncio.sleep(2)` instead of polling: same issue.

Most likely: a bare `time.sleep(2)` or `await asyncio.sleep(2)` where the work has variable latency
and the fixed duration doesn't account for system load variance.
```

**Pattern evidence:** Correlation with machine load is the tell — purely timing-dependent code exposed by OS scheduler jitter.

---

### Test 3: Dict Iteration Order Over Set of Fixture IDs

**Symptom:** Relies on dict iteration order over a set of fixture IDs. Python dicts are insertion-ordered since 3.7, but iteration over a `set` fed into dict construction is non-deterministic.

**Hypothesis (Rank 1 — Most Likely):** The test builds a dict from an unordered iterable (a `set`), then iterates that dict expecting a specific order. CPython's hash seed randomization (PYTHONHASHSEED, enabled by default since 3.3) makes set iteration order vary between process invocations. Sometimes two adjacent runs happen to hash to the same order → appears to pass. CI may run with a fixed PYTHONHASHSEED or happen to get the same ordering consistently.

**Data flow trace:**
```
Fixture IDs = {"B", "A", "C"}       # a set literal — already unordered
result_dict = {k: fixture(k) for k in Fixture IDs}  # set iteration order is undefined
assert list(result_dict.keys()) == ["A", "B", "C"]  # expects sorted → sometimes FAILS
```

**Pattern evidence:** This is a textbook non-determinism bug. There's no "intermittent" mystery — it's mathematically guaranteed to produce different orders across runs when PYTHONHASHSEED changes (which Python does automatically).

Let me identify what the correct patterns look like:

| Issue | Wrong Pattern | Correct Pattern |
|-------|--------------|-----------------|
| Time assertions | `datetime.now()` compared literally | `unittest.mock.patch('datetime.datetime')` with frozen time |
| Async waits | `time.sleep(N)` hard cutoff | `asyncio.wait_for()` or polling loop with configurable timeout + asyncio primitives |
| Ordered assertions from sets | Iterate set → compare list order | Sort keys before comparison, or use a list/set for the source |

## Phase 4: Deterministic Fixes

### Fix 1 — Timestamp Assertion

**Root cause:** Using local wall-clock time (`datetime.now()`) in a comparison against a fixed expected value, with timezone dependency causing divergence.

**Fix:** Freeze time using `freezegun`. This eliminates both timezone variance and any clock-drift between test setup and assertion.

```python
# BEFORE (flaky)
from datetime import datetime

def test_report_generation():
    report = generate_report()
    # generate_report internally calls datetime.now()
    assert report.timestamp == "2026-08-25 12:00:00"  # flaky by timezone


# AFTER (deterministic)
from freezegun import freeze_time

@freeze_time("2026-08-25 12:00:00")
def test_report_generation():
    report = generate_report()
    assert report.timestamp == "2026-08-25 12:00:00"  # always passes
```

**Why this works:** `freeze_time` patches `datetime.datetime.now`, `time.time`, and related functions globally within the decorated/test-context scope. Both the code under test AND the assertion see the identical frozen time. Timezone becomes irrelevant — you control the exact instant.

**Alternative (no extra dependency):**

```python
from unittest.mock import patch

def test_report_generation():
    frozen = datetime(2026, 8, 25, 12, 0, 0, tzinfo=timezone.utc)
    with patch("datetime.datetime") as mock_dt:
        mock_dt.now.return_value = frozen
        mock_dt.side_effect = lambda *args, **kw: frozen
        report = generate_report()
        assert report.timestamp == "2026-08-25T12:00:00+00:00"
```

### Fix 2 — Async Worker Polling

**Root cause:** Blocking `time.sleep(2)` (or a single `await asyncio.sleep(2)`) is a wall-clock deadline that doesn't adapt to event-loop scheduling delays caused by CPU contention or I/O pressure.

**Fix:** Replace the hardcoded sleep with `asyncio.wait_for()`, which is genuinely cooperative — it cancels the task after the timeout rather than blindly sleeping.

```python
# BEFORE (flaky under load)
import time

async def test_async_worker():
    task = asyncio.create_task(process_items(items))
    time.sleep(2)                          # blocks the entire event loop!
    assert task.done()                     # race: task might need 2.3s
    assert task.result() == expected


# AFTER (deterministic)
async def test_async_worker():
    task = asyncio.create_task(process_items(items))
    result = await asyncio.wait_for(task, timeout=5.0)
    assert result == expected
```

**Key difference explained:**
- `time.sleep(2)` **blocks the event loop itself** for 2 seconds — no other coroutines can run during that window, including the task you're waiting for. This is doubly bad.
- `asyncio.wait_for()` yields control back to the event loop and checks completion asynchronously. It respects cancellation and gives accurate timeouts.

**If you need to poll a long-running background service (not a single task):**

```python
async def test_worker_becomes_ready():
    task = asyncio.create_task(service_worker())
    deadline = asyncio.get_event_loop().time() + 10.0
    while not task.done():
        if asyncio.get_event_loop().time() > deadline:
            raise TimeoutError("worker did not complete in 10s")
        await asyncio.sleep(0.1)           # small yield, cooperative
    assert task.result() == expected
```

### Fix 3 — Set-Based Dict Iteration Order

**Root cause:** Constructing a dict from a `set` and asserting key order. CPython 3.3+ randomizes `PYTHONHASHSEED` per process by default, so set iteration order differs across test invocations. The dict preserves insertion order (insertion being the unpredictable set iteration), so the resulting key order is also unpredictable.

**Fix:** One of three approaches depending on intent:

```python
# OPTION A — If order IS the thing you care about, use a list:
def test_ordered_fixtures():
    ids = ["apple", "banana", "zebra"]    # list preserves order
    d = {k: k.upper() for k in ids}
    assert list(d.keys()) == ["apple", "banana", "zebra"]

# OPTION B — If order is incidental and you only care about membership, sort:
def test_fixture_contents():
    ids = {"zebra", "apple", "banana"}
    d = {k: k.upper() for k in ids}
    assert sorted(d.keys()) == ["apple", "banana", "zebra"]

# OPTION C — If using a pytest fixture parametrized by a set, don't rely on order:
@pytest.fixture(params=frozenset(["zebra", "apple", "banana"]))
def item(request):
    return request.param
```

**Option A is the correct choice** when the test was written expecting a particular order. Options B and C are correct when order was never semantically meaningful — the test was just accidentally dependent on it.

## Summary Table

| Test | Root Cause | Fix | Category |
|------|-----------|-----|----------|
| Timestamp assertion | `datetime.now()` uses local time; test expects fixed UTC string | `@freeze_time("...")` from `freezegun` | Time non-determinism |

All three fix types convert **environment-dependent behavior** into **explicitly controlled behavior**. That's the unifying principle — stop relying on the environment doing what it happens to do, and instead pin the variables that matter.
