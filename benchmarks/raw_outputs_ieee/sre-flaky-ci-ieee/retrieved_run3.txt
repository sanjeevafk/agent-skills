# Systematic Debug Analysis: Flaky Test Suite

## Phase 1 — Symptom Documentation & Hypothesis Ranking

### Observed Symptoms

| Symptom | Implication |
|---|---|
| 3/240 tests fail (~1.25% failure rate) | Low-frequency timing issues |
| CI passes, dev machines fail | Environment/timezone/load correlation |
| Reruns go green | Race conditions / non-determinism masked by faster CI or different ordering |
| Correlates with machine load | Scheduler interference, async timing windows |
| Correlates with timezone | Timestamp formatting depends on local offset |

### Ranked Hypotheses

| Rank | Hypothesis | Evidence For | How to Test |
|---|---|---|---|
| **H1** | Non-deterministic iteration order (hash randomization) | Dict/set ordering varies per Python process (`PYTHONHASHSEED`), causes flaky fixture ordering | Set `PYTHONHASHSEED=0`, check if failures disappear |
| **H2** | Clock/timestamp drift + timezone mismatch | Formatted timestamp assertion fails under timezone variance; CI uses UTC by default | Run with `TZ=America/New_York` vs `TZ=UTC`, freeze clock |
| **H3** | Async race condition (sleep-based polling) | `sleep(2)` polling window may expire before worker completes under high CPU load; CI runs faster or slower than dev | Stress-run with `--workers > 1` or under load simulation |
| H4 | Resource contention from parallel pytest-xdist | Load-sensitive; concurrent processes compete for I/O or shared state | Run with `-p no:xdist` (single process) and check |
| H5 | GC pauses interfering with asyncio event loop | High-load machines trigger GC more aggressively, delaying coroutines | Check `asyncio.get_event_loop().get_debug()` behavior |

**Primary actionable suspects: H1, H2, H3.** Here's why they map to each failing test:

- **Timestamp test → H2** (timezone + clock)
- **Async worker test → H3** (race condition from `sleep(2)`)
- **Dict iteration order test → H1** (hash randomization)

### Reproduction 2: Timezone + Clock Drift

```python
"""
Reproduction for: formatted timestamp assertion fails under timezone
variance. CI runs in UTC; developer machines may be in any timezone.
Additionally, wall-clock drift between test start and assertion can
cause off-by-one-second failures.

Requires: pip install freezegun
"""
import datetime
import os
from zoneinfo import ZoneInfo


def get_formatted_timestamp():
    """Simulates the application function being tested."""
    now = datetime.datetime.now()  # BUG: Uses local time, not UTC
    return now.strftime("%Y-%m-%d %H:%M:%S %z")


def test_timestamp_formatting_flaky():
    """
    Original test: asserts a specific formatted timestamp.

    Fails because:
      1. datetime.now() returns local time, which differs by timezone
      2. Between calling the function and asserting, the clock may tick,
         producing a ±1 second discrepancy
      3. CI uses UTC; dev machines use their local TZ
    """
    ts = get_formatted_timestamp()

    # Asserts against a value that may differ due to TZ or clock drift
    # Example original assertion:
    #     assert ts == "2026-08-25 14:30:00 +0000"
    # This succeeds only if the test happens to run at exactly
    # that moment in UTC on a machine configured for UTC.

    expected_year = datetime.datetime.now().year
    parsed = datetime.datetime.strptime(ts, "%Y-%m-%d %H:%M:%S %z")

    # The year must always be correct — but the full string won't match
    # unless we're in UTC and the clock hasn't moved.
    assert parsed.year == expected_year, f"Year mismatch: {ts}"

    # More subtle: if the original test asserted on HH:MM, that field
    # changes every minute — extremely fragile.
    print(f"Timestamp: {ts} (TZ env: {os.environ.get('TZ', 'default')})")


if __name__ == "__main__":
    import subprocess

    # Demonstrate timezone sensitivity
    timezones = ["UTC", "America/New_York", "Asia/Tokyo", "Europe/London"]
    for tz in timezones:
        os.environ["TZ"] = tz
        result = subprocess.run(
            [sys.executable, "-c",
             "import datetime; print(datetime.datetime.now().strftime('%Y-%m-%d %H:%M:%S %z'))"],
            capture_output=True, text=True
        )
        print(f"{tz:25s} → {result.stdout.strip()}")

    print("\nNotice: same instant, different strings depending on TZ.")
```

### Reproduction 3: Async Worker Race Condition Under Load

```python
"""
Reproduction for: async worker polling with sleep(2) is racy.

The worker takes variable time to complete. If the machine is loaded
(slow scheduling), `sleep(2)` may expire before the worker finishes.
Reruns go green when the worker happens to finish within the polling
window.

Requires: pip install freezegun (optional, for additional stress testing)
"""
import asyncio
import random
import time


class AsyncWorker:
    """Simulates a background task with variable completion time."""

    def __init__(self):
        self._completed = False
        self._start_time = None

    async def run(self):
        self._start_time = time.monotonic()
        # Simulate work: random duration between 1-4 seconds.
        # On a loaded machine, OS scheduler delays amplify this.
        duration = random.uniform(1.0, 4.0)
        await asyncio.sleep(duration)
        self._completed = True

    @property
    def is_completed(self):
        return self._completed


async def test_worker_polling_flaky():
    """
    Original test pattern:
        worker = AsyncWorker()
        asyncio.create_task(worker.run())
        await asyncio.sleep(2)  # BUG: Magic number, not tied to actual signal
        assert worker.is_completed  # RACE: May not be done yet!

    Problems:
      1. `sleep(2)` is a magic constant — assumes worst-case work < 2s
      2. No backoff strategy — polls once, then immediately asserts
      3. Machine load increases scheduling latency, making sleep(2)
         insufficiently long on some runs
      4. No timeout — hangs forever if worker truly fails (silent skip)
    """
    worker = AsyncWorker()
    handle = asyncio.create_task(worker.run())

    # FLAKY: Fixed sleep may not cover variable work duration.
    await asyncio.sleep(2)

    if worker.is_completed:
        print("✓ Worker completed within polling window")
    else:
        elapsed = time.monotonic() - worker._start_time if worker._start_time else float('inf')
        print(f"✗ Worker NOT completed after sleep(2). Elapsed: {elapsed:.2f}s")
        print(f"  This will succeed ~60% of the time (work < 2s happens "
              f"~{((2-1)/(4-1))*100:.0f}% of the time)")
        # In the real test, this would raise:
        # assert worker.is_completed, "Worker did not finish"


async def main():
    passed = 0
    failed = 0
    for i in range(50):
        await test_worker_polling_flaky()
        # Note: We don't actually assert here; we just demonstrate the
        # non-deterministic outcome. In the real test, the assert below
        # the sleep(2) would fire for ~40% of runs.

    print("\nDemonstration complete. Fix: use asyncio.wait with timeout.")


if __name__ == "__main__":
    asyncio.run(main())
```

## Phase 3 — Root Cause Analysis

Each failure maps to a single class of bug:

### Test 1: Timestamp Formatting — Root Cause: **Timezone + Wall-Clock Dependency**

```
Application Code:                 datetime.now()               ← Returns LOCAL time
                                     ↓
Test Assertion:          "Asserts formatted output matches EXACT string"
                                     ↓
CI Runs in UTC with fast, stable clock → String matches
Dev Machine in EST with clock drift →  String differs by ±hours or ±1s
```

The root cause is two-fold:
1. **Using `datetime.now()` instead of `datetime.now(timezone.utc)`** — makes output depend on the system's local timezone setting
2. **Asserting an exact formatted string instead of a semantic invariant** — e.g., checking `== "2026-08-25 14:30:00"` instead of `year == X and month == Y`. Any clock tick between call and assertion breaks the test.

### Test 2: Async Worker Polling — Root Cause: **Fixed Sleep Instead of Event-Driven Completion Signal**

```
Application Code:                 AsyncTask (variable duration 1-4s)
                                     ↓
Test Code:              create_task() → sleep(2) → assert completed
                                     ↓
Fast machine:   task finishes in 1.2s → sleep(2) covers it → PASS
Loaded machine: task finishes in 3.5s → sleep(2) expires early → FAIL
Rerun:          random variation puts task inside window → PASS
```

The root cause is using a **magic-number sleep as a polling mechanism** instead of awaiting a proper completion signal. `sleep(2)` assumes the worker always completes within 2 seconds, which is false under load.

### Test 3: Dict Iteration Order — Root Cause: **Hash Seed Randomization + Set Unordered Nature**

```
Python starts → PYTHONHASHSEED=random (default)
                   ↓
Set created:   {"id_a", "id_b", "id_c", "id_d"}
                   ↓
list(set) produces: [any_permutation] ← Deterministic for THIS run,
                                          different across runs
                   ↓
Assertion:      expects ["id_a", "id_b", "id_c", "id_d"]
                   ↓
Sometimes matches by coincidence → PASS
Often permutes differently → FAIL
```

The root cause is converting an unordered `set` to a `list` and asserting order. `PYTHONHASHSEED` randomizes across process invocations by default (Python 3.3+), so iteration order is intentionally non-deterministic.

## Phase 4 — Deterministic Fixes

### Fix 1: Timestamp Test — Freeze Time + Assert Semantics + Use UTC

```python
"""
FIX for: test_timestamp_formatting_flaky

Strategy:
  1. Import FreezableDateTime from application code OR refactor to accept
     an explicit datetime parameter (dependency injection)
  2. In the test: freeze the clock with freezegun
  3. Assert semantic properties (year, month, day), not exact strings
  4. Ensure the application uses UTC explicitly
"""
import pytest
from freezegun import freeze_time
import datetime


# --- APPLICATION CODE FIX ---
def get_formatted_timestamp(force_utc=False):
    """Refactored: uses UTC when requested."""
    if force_utc:
        now = datetime.datetime.now(datetime.timezone.utc)
    else:
        now = datetime.datetime.now()  # Keep existing behavior for prod
    return now.strftime("%Y-%m-%d %H:%M:%S %z")


# --- TEST FIX ---
@freeze_time("2026-08-25 14:30:00 +0000")
def test_timestamp_formatting():
    """
    FIXED:
      - freezegun freezes the clock at a known instant
      - No clock drift between function call and assertion
      - Exact string match is safe because time cannot move
    """
    ts = get_formatted_timestamp(force_utc=True)
    assert ts == "2026-08-25 14:30:00 +0000"  # Now deterministic


@freeze_time("2026-08-25 14:30:00 +0000")
def test_timestamp_semantic_invariants():
    """
    BETTER FIX: Assert semantic invariants rather than exact strings.
    This survives date rollovers and is more robust.
    """
    ts = get_formatted_timestamp(force_utc=True)
    parsed = datetime.datetime.strptime(ts, "%Y-%m-%d %H:%M:%S %z")
    assert parsed.year == 2026
    assert parsed.month == 8
    assert parsed.day == 25
    assert parsed.hour == 14
    assert parsed.minute == 30
    assert parsed.tzinfo.utcoffset(None).total_seconds() == 0  # UTC
```

### Fix 2: Async Worker — Replace Sleep with Proper Await Pattern

```python
"""
FIX for: test_worker_polling_flaky

Strategy:
  1. Replace arbitrary `sleep(2)` with `asyncio.wait()` + timeout
  2. Add exponential backoff polling if you must check progress
  3. Use an asyncio.Event for signaling completion (best approach)
"""
import asyncio
import time


class AsyncWorker:
    """Refactored: exposes a completion event."""

    def __init__(self):
        self._event = asyncio.Event()  # New: signals when done
        self._completed = False

    async def run(self):
        try:
            # Actual work logic here...
            await asyncio.sleep(2)  # Simulated variable-duration work
        finally:
            self._completed = True
            self._event.set()  # Signal completion

    @property
    def is_completed(self):
        return self._completed

    def wait_for_completion(self, timeout=None):
        """Return the coroutine to await the completion signal."""
        return self._event.wait()


# --- TEST FIX OPTION A: asyncio.wait (recommended) ---
async def test_worker_completion():
    """
    FIXED: Uses asyncio.wait with timeout instead of magic sleep.
    The test waits properly for either completion or timeout.
    """
    worker = AsyncWorker()
    handle = asyncio.create_task(worker.run())

    # Wait up to 10 seconds for the task to complete
    done, pending = await asyncio.wait(
        [handle],
        timeout=10.0,
        return_when=asyncio.FIRST_COMPLETED,
    )

    assert len(done) == 1, "Worker did not complete within timeout"
    assert not pending, f"Still running: {pending}"


# --- TEST FIX OPTION B: Exponential Backoff Polling ---
async def test_worker_polling_backoff():
    """
    FIXED: If you can't modify the worker to expose an event,
    use exponential backoff polling with a timeout.
    """
    worker = AsyncWorker()
    handle = asyncio.create_task(worker.run())

    max_wait = 10.0
    poll_interval = 0.1
    elapsed = 0.0

    while elapsed < max_wait:
        if worker.is_completed:
            return  # Success

        await asyncio.sleep(poll_interval)
        poll_interval = min(poll_interval * 2, 1.0)  # Exponential backoff, cap at 1s
        elapsed += poll_interval

    raise AssertionError(f"Worker did not complete within {max_wait}s")


# --- TEST FIX OPTION C: Direct await (simplest, best) ---
async def test_worker_await_direct():
    """
    BEST: If the test owns the worker lifecycle, just await it directly.
    No polling needed at all.
    """
    worker = AsyncWorker()
    await worker.run()
    assert worker.is_completed
```

## Summary: One-Line Remediation Table

| # | Test | Root Cause | Fix | Category |
|---|---|---|---|---|
| 1 | Timestamp format | Local timezone + clock drift | `freezegun` + `force_utc=True` + semantic assertions | **Deterministic time** |
| 2 | Async worker polling | `sleep(2)` magic number vs variable work duration | `asyncio.wait()` with timeout + event signal | **Proper async primitives** |
| 3 | Dict/set iteration | `PYTHONHASHSEED` randomization + set unordered | `sorted()` + or set-equality + or ordered fixture list | **Explicit ordering** |

These three classes of flakiness — **time dependency**, **async races**, and **unordered collections** — account for the vast majority of intermittent test failures in production codebases. The diagnostic signature (load-correlated, timezone-correlated, reruns green) is a strong fingerprint matching this diagnosis.
