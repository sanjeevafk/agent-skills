## Test 1: Formatted Timestamp Assertion

**Hypothesis:** The test asserts on a string that depends on UTC offset or locale-sensitive formatting, so it passes when CI runs at a fixed time/offset but fails when the dev machine local time falls in a different hour/day.

### Minimal Reproduction

```python
import os, datetime, pytest, time_machine

def test_timestamp_format_fails_in_diff_timezone():
    """Reproduce: assert on now() formatted as ISO-like string."""
    result = format_event_timestamp(datetime.datetime.now())
    # CI always sees e.g. "2026-08-25T14:00:00+00:00"
    # Dev at UTC+5:30 may see "2026-08-25T19:30:00+05:30" — assertion differs
    assert result == "2026-08-25T14:00:00+00:00"
```

### Root Cause

`datetime.now()` returns local wall-clock time. If the production code uses naive datetimes or zone-ambiguous formatting, the expected literal changes per timezone. Even if the code uses `datetime.utcnow()`, a `strftime` format like `%Y-%m-%d %H:%M:%S` has no zone suffix, making it impossible to compare deterministically.

### Deterministic Fix

Freeze time explicitly. Never use real-time in assertions unless you're comparing elapsed deltas:

```python
import time_machine

@time_machine.travel("2026-08-25T14:00:00+00:00", tick=False)
def test_event_timestamp_is_utc_iso8601():
    result = format_event_timestamp(datetime.datetime.now(datetime.timezone.utc))
    assert result == "2026-08-25T14:00:00+00:00"
```

Key rules:
1. **Always pass `datetime.timezone.utc`** — never use naive datetimes for serialization/assertion.
2. **Freeze clock** with `time_machine` (or `freezegun`) for any test touching timestamps.
3. If the function under test calls `now()` internally without accepting a `now=` parameter, inject it: refactor to `format_event_timestamp(now_fn=datetime.datetime.now)` and call it with `lambda: frozen_time` in tests.

## Test 2: Async Worker Polling with `sleep(2)`

**Hypothesis:** A bare `time.sleep(2)` as a polling interval is a heuristic, not a guarantee. On a loaded machine the worker might take >2s, causing a premature timeout or missing state. On an unloaded machine it succeeds — explaining the load correlation.

### Minimal Reproduction

```python
import asyncio, time

async def test_worker_completes_quickly():
    worker = MyWorker()
    worker.start()
    await asyncio.sleep(2)          # bare poll
    assert worker.ready              # flaky: worker might still be running
```

### Root Cause

Two problems stacked:
1. **Arbitrary sleep**: `sleep(2)` assumes the worker completes within exactly 2s. CPU contention makes this assumption invalid.
2. **No proper event loop coordination**: The test polls by sleeping instead of awaiting a completion signal (future, queue put, event).

### Deterministic Fix

Replace polling-sleep with either an **awaitable condition** or a **bounded retry loop** with exponential backoff:

```python
import asyncio, pytest

@pytest.mark.asyncio
async def test_worker_completes_within_timeout():
    worker = MyWorker()
    worker.start()
    try:
        await asyncio.wait_for(worker.ready_event.wait(), timeout=10.0)
    except asyncio.TimeoutError:
        pytest.fail("Worker did not complete within 10s")
    assert worker.status == "done"
```

If the worker doesn't expose an event/future, wrap the assertion in a retry loop instead of raw sleeps:

```python
@pytest.mark.asyncio
async def test_worker_completes_with_retry():
    worker = MyWorker()
    worker.start()
    for _ in range(50):               # up to ~10s total
        if worker.ready:
            return
        await asyncio.sleep(0.2)      # 200ms between checks, not 2s
    assert worker.ready, "Worker did not complete"
```

Key rules:
1. **Never use bare `time.sleep()` in async tests** — use `await asyncio.sleep()`.
2. **Await events**, don't poll with arbitrary delays.
3. When polling is unavoidable, use a **bounded loop** with short intervals and a hard timeout — make the bound explicit, not magical.

## Test 3: Dict Iteration Order Over Set of Fixture IDs

**Hypothesis:** In Python 3.7+, dict insertion order is preserved, but iterating over a **set** is unordered. If the test collects fixture IDs into a `set`, then builds a dict or iterates to assert results, the iteration order is nondeterministic across runs — especially correlated with hash seed (`PYTHONHASHSEED`), which CI typically fixes (e.g., `PYTHONHASHSEED=0`) while dev machines do not.

### Minimal Reproduction

```python
import os, pytest

@pytest.mark.parametrize("fixture_id", ["b", "a", "c"])
def test_result_order(fixture_id, some_data_provider):
    results = {}
    results[fixture_id] = some_data_provider(fixture_id)
    # Problem: fixture_ids came from a set somewhere upstream;
    # if we iterate `results` keys, their order mirrors the set's hash order
    keys = list(results.keys())
    assert keys == ["a", "b", "c"]   # FAILS: actual order varies per PYTHONHASHSEED
```

### Root Cause

The pipeline does one of:
- Collects IDs into a `set`, losing insertion order, then converts to dict/list later.
- Uses `pytest.mark.parametrize` with values derived from a set rather than a sorted/list/tuple.
- Relies on `dict.keys()` iteration order to validate a specific sequence when the source was a set.

Python dicts preserve *insertion* order, but if items are inserted via `for k in some_set:`, the insertion order = the set's iteration order, which is randomized by `PYTHONHASHSEED`.

### Deterministic Fix

Eliminate the set entirely. Use an ordered collection at the point where IDs enter the system:

```python
import pytest

# Fix: parametrize from a sorted tuple, not a set
@pytest.mark.parametrize("fixture_id", sorted(("b", "a", "c")))
def test_result_order(fixture_id, some_data_provider):
    results = {}
    results[fixture_id] = some_data_provider(fixture_id)
    keys = list(results.keys())
    assert keys == ["a", "b", "c"]   # DETERMINISTIC
```

If the IDs come from a set returned by a fixture or helper function, reorder at the boundary:

```python
# Before (flaky):
fixture_ids = {"b", "a", "c"}      # set — random iteration order

# After (deterministic):
fixture_ids = sorted({"b", "a", "c"})  # list — guaranteed order
```

And if the test constructs a dict then validates iteration:

```python
# Better yet — don't rely on key order for verification:
def test_results_contain_expected(fixture_id, some_data_provider):
    results = {fid: some_data_provider(fid)
               for fid in sorted(("b", "a", "c"))}
    # Assert on contents, not traversal order:
    assert set(results.values()) == {"result_a", "result_b", "result_c"}
    assert results["a"] == "result_a"    # keyed access is deterministic
```

Key rules:
1. **Never use `set` when order matters.** Use `list` or `tuple`.
2. **Sort sets before iteration** wherever order is significant.
3. **Assert on content** (sorted lists, sets, keyed lookups), not on traversal order of dicts built from unordered sources.
4. Consider setting `export PYTHONHASHSEED=0` in CI (many teams already do this) — but don't rely on it as your only safeguard, because local devs won't have it.
