## Systematic Debugging Analysis

### Phase 1: Root Cause Investigation

**Symptoms observed:**
- 3 out of 240 tests fail intermittently (~1.25% failure rate)
- CI passes consistently; developer machines fail
- Reruns usually go green
- Failures correlate with machine load AND developer timezone

This pattern — passing in CI but failing locally under load, with timezone correlation — screams **three distinct categories of non-determinism**. Let me trace each.

### Test 1: Timestamp Formatting Assertion

#### Hypothesis Formation

**H1 (most likely):** The test formats a datetime using local timezone without controlling `os.environ['TZ']` or using `zoneinfo`. CI runs in UTC; a developer in `America/New_York` gets different formatted output.

*Evidence chain:* Timezone correlation + CI pass + format assertion = timestamp rendering depends on system TZ.

**H2 (less likely):** The test uses `datetime.now()` which returns wall clock time that differs between environments. But H1 subsumes this — wall clock variance alone wouldn't correlate with timezone specifically.

#### Minimal Reproduction

```python
import os, tempfile, subprocess, sys

# Reproduces the exact failure by forcing NYC timezone while
# asserting a UTC-formatted string — identical to what a dev in
# Eastern would hit locally after CI set UTC.
repro_script = '''
import os
from datetime import datetime

def test_timestamp_format():
    ts = datetime.utcnow().strftime("%Y-%m-%d %H:%M:%S UTC")
    # CI sets TZ=UTC → passes. Dev in America/New_York → FAILS
    # because datetime.now() produces EST/EDT offsets differently.
    assert ts == "2026-08-26 12:00:00 UTC"

if __name__ == "__main__":
    os.environ["TZ"] = "America/New_York"
    import time; time.tzset()
    test_timestamp_format()
'''

with tempfile.NamedTemporaryFile('w', suffix='.py', delete=False) as f:
    f.write(repro_script)
result = subprocess.run([sys.executable, f.name], capture_output=True, text=True)
print("STDOUT:", result.stdout)
print("STDERR:", result.stderr)
print("Return code:", result.returncode)
```

When run, this either passes (CI/UTC) or fails (dev/local/TZ-aware), proving H1.

#### Deterministic Fix

```python
# BEFORE (broken — timezone-dependent):
def test_event_log_contains_timestamp():
    event_time = datetime.now()  # depends on system TZ!
    log_entry = format_log(event_time)
    assert log_entry == "2026-08-26 12:00:00 UTC [INFO] event"

# AFTER (fixed — explicit timezone):
from datetime import datetime, timezone

def test_event_log_contains_timestamp():
    event_time = datetime.now(timezone.utc)  # always UTC
    log_entry = format_log(event_time)
    assert log_entry == "2026-08-26 12:00:00 UTC [INFO] event"

# ALTERNATIVE FIX — freeze time entirely for determinism:
from freezegun import freeze_time

@freeze_time("2026-08-26T12:00:00Z")
def test_event_log_contains_timestamp():
    event_time = datetime.now(timezone.utc)
    log_entry = format_log(event_time)
    assert log_entry == "2026-08-26 12:00:00 UTC [INFO] event"
```

**Why both fixes matter:** The first (`timezone.utc`) eliminates timezone variance. The second (`freezegun`) eliminates *all* time dependence, making the test reproducible even if the function under test does `datetime.utcnow()` internally. In production-grade test suites, prefer `freezegun` or `time_machine` for anything touching real clocks.

### Test 2: Async Worker Polling with `sleep(2)`

#### Hypothesis Formation

**H1 (most likely):** The test polls an async worker by sleeping a fixed interval (e.g., `for _ in range(10): sleep(2); check_done()`). On a loaded machine, the worker takes >2s per iteration. By iteration 3–5, the worker is still running → timeout/error. A rerun succeeds because the worker finishes within the window on the fresher system state.

*Evidence chain:* Machine-load correlation + rerun-goes-green + `sleep(2)` polling = timing-dependent assertion race condition.

**H2 (less likely):** The async worker itself has a resource leak or deadlock triggered by prior tests. Less likely because reruns succeed independently of test order.

#### Minimal Reproduction

```python
import asyncio, time, random

async def slow_worker(delay=None):
    """Simulates worker whose latency varies with machine load."""
    d = delay or random.uniform(0.5, 4.0)  # high load → higher d
    await asyncio.sleep(d)
    return "done"

# BEFORE (broken — arbitrary sleep):
def test_worker_completes():
    task = asyncio.create_task(slow_worker())
    for _ in range(10):          # max 20s total, assuming 2s rounds
        time.sleep(2)             # busy-wait, no feedback from task
        if task.done():           # checks done flag only every 2s
            assert task.result() == "done"
            return
    raise AssertionError("worker timed out")

# This fails when delay > 2 because we only check every 2s
# and the loop ends before task completes.
```

Running this under load (simulated by capping CPU via `taskset` or container limits) will cause repeated failures until retries align favorably.

#### Deterministic Fix

Replace `sleep()` polling with proper async waiting:

```python
# AFTER (fixed — use asyncio.wait_with_timeout):
import asyncio

async def test_worker_completes():
    task = asyncio.create_task(slow_worker())
    done, pending = await asyncio.wait(
        [task],
        timeout=30.0,       # generous ceiling, not tied to sleep granularity
    )
    assert len(pending) == 0, f"worker did not complete: {pending}"
    assert task.result() == "done"

# OR — for pytest-asyncio users, simplest fix:
@pytest.mark.asyncio
async def test_worker_completes():
    task = asyncio.create_task(slow_worker())
    result = await asyncio.wait_for(task, timeout=30.0)
    assert result == "done"

# EVEN BETTER — inject the delay so tests are fast and deterministic:
class Worker:
    def __init__(self, tick=0.1):
        self.tick = tick      # configurable speed for testing vs prod

async def test_worker_completes():
    worker = Worker(tick=0.01)   # instant-ish during tests
    result = await worker.process()
    assert result == "done"
```

**Key insight:** Never poll with `time.sleep()` in async tests. Use `asyncio.wait`, `asyncio.wait_for`, or dependency-inject a controllable abstraction. The fix isn't "increase the sleep" — it's "stop polling altogether."

### Test 3: Dict Iteration Order Over Fixture IDs

#### Hypothesis Formation

**H1 (most likely):** The test builds a dict from unordered fixture IDs (e.g., a `set` or list fed to `dict(zip(keys, values))` where keys come from `set(...)`). Python 3.7+ dicts preserve insertion order, but **sets do not**. Different Python versions, hash seed environments (`PYTHONHASHSEED`), or compilation states produce different set iteration orders, changing the dict's key order. If the test asserts on positional indexing, sorted output, or string representation including bracket order, it flaps.

*Evidence chain:* Set → dict conversion + fixture ID ordering + intermittent = hash randomization / set iteration non-determinism.

**Note on timezone correlation:** Hash randomization seeds may be derived from process start conditions (including system time/entropy pool), creating a secondary correlation with timezone-relevant metadata like PID generation or monotonic clock values used in hash mixing.

**H2 (less likely):** Pytest fixture parametrization over a set yields non-deterministic execution order. Also plausible and related — the same set-ordering issue manifests as test execution order variance.

#### Minimal Reproduction

```python
# Demonstrates the root cause: set-to-dict order changes with PYTHONHASHSEED
def test_dict_order_flaps():
    fixture_ids = {"alpha", "beta", "gamma", "delta"}  # SET — unordered!
    values = [1, 2, 3, 4]
    mapping = dict(zip(sorted(fixture_ids), values))     # sort kills it ✓
    
    # BROKEN version (what the test probably does):
    broken_mapping = dict(zip(fixture_ids, values))  # set order = undefined
    
    # Asserting index-based access on this dict will differ across runs:
    # assert list(broken_mapping.values())[0] == 1  # FAILS — order unknown
    print(list(broken_mapping.items()))  # order varies with PYTHONHASHSEED
```

Run this twice with different `PYTHONHASHSEED` values to see different iteration orders.

#### Deterministic Fix

There are two independent fixes depending on what the test actually asserts:

```python
# FIX A — if the test sorts/compares the resulting dict:
def test_fixture_mapping_is_correct():
    fixture_ids = {"alpha", "beta", "gamma", "delta"}
    values = {"alpha": 1, "beta": 2, "gamma": 3, "delta": 4}
    mapping = dict(zip(sorted(fixture_ids), values[k] for k in sorted(fixture_ids)))
    # NOW: insertion order is guaranteed alphabetical, assertions stable

# FIX B — if the test iterates and asserts positionally (common pattern):
def test_all_fixtures_produce_expected_results():
    fixture_ids = frozenset({"alpha", "beta", "gamma"})
    expected = {"alpha": "ok", "beta": "ok", "gamma": "ok"}
    
    # DON'T convert to dict and index by position:
    # result = dict(map(lambda fid: (fid, run_fixture(fid)), fixture_ids))
    # assert list(result.values())[0] == "ok"   # BROKEN
    
    # DO iterate the set explicitly:
    for fid in fixture_ids:
        assert run_fixture(fid) == expected[fid]

# FIX C — best practice: use tuples/lists instead of sets for ordered fixtures:
@pytest.fixture(params=["alpha", "beta", "gamma"])  # LIST, not set
def some_fixture(request):
    return request.param

# OR parameterize directly:
@pytest.mark.parametrize("fixture_id", ["alpha", "beta", "gamma"])
def test_parameterized(fixture_id):
    assert process(fixture_id) == expected[fixture_id]
```

### Phase 2: Pattern Analysis

All three failures share a root category: **the test suite depends on non-deterministic external state**:

| Test | Depends On | Non-Deterministic Because |
|------|-----------|--------------------------|
| 1. Timestamp | System clock + TZ setting | CI runs in `TZ=UTC`; dev runs in local TZ |
| 2. Async polling | Wall-clock time | Machine load alters wall-clock duration of async work |
| 3. Dict iteration | Python set hashing | `PYTHONHASHSEED` / Python build config varies across environments |

These are all **environmental coupling bugs** — the test logic silently reaches outside its control boundary into OS-level, process-level, or runtime-level variables.

### Phase 4: Prescribed Fixes Summary

| # | Issue | Root Cause | Fix Category | Specific Fix |
|---|-------|------------|--------------|--------------|
| 1 | Timestamp assertion | Local TZ vs CI's UTC | **Freeze + explicit TZ** | Use `datetime.now(timezone.utc)` + `freezegun.freeze_time()` at module level |
| 2 | Async worker polling | Busy-wait with fixed `sleep(2)` under variable load | **Async-native wait** | Replace `time.sleep()` loop with `asyncio.wait_for(task, timeout=N)` |
| 3 | Dict iteration order | `set` → `dict` order varies with hash seed | **Deterministic ordering** | Use `sorted(set)` for keys, or replace sets with lists/tuples for fixture params |
