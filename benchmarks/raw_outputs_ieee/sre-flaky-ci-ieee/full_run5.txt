## Phase 1: Root Cause Investigation

### Evidence from Symptoms

| Symptom | What It Rules In | What It Rules Out |
|---------|-------------------|--------------------|
| Passes CI, fails locally | Environment difference matters | Pure logic bug |
| 3/240, reruns usually green | Order/state-dependent, not always triggered | Deterministic failure |
| Correlates with machine load | Timing-sensitive | Fixed-time bugs only |
| Correlates with timezone | Wall-clock / timezone-sensitive | Timezone-agnostic bugs |
| Three distinct test types | Three independent root causes | One systemic failure |

### Hypothesis Ranking (by likelihood)

**H1: Timestamp test compares against absolute wall-clock values.** A formatted timestamp (e.g. ISO 8601, locale-aware date string) computed during the test doesn't match the expected value when the developer's timezone differs from the CI runtime. The failure is intermittent because it triggers near timezone-adjacent boundaries (UTC offset changes, DST transitions, or simply AM/PM vs 24h format differences). This perfectly matches the timezone correlation.

**Likelihood: Very High (~95%).** Directly explains the timezone signal. No other hypothesis accounts for it.

**H2: Async worker uses fixed `sleep(2)` instead of condition polling.** Under CPU/network contention on loaded machines, the worker cannot complete within 2 seconds. CI typically runs on provisioned runners with stable resources; local machines under load vary widely. Reruns go green because retry happens to land on a faster window.

**Likelihood: Very High (~95%).** Perfectly explains machine-load correlation + rerun success. This is the textbook race condition.

**H3: Set-based data structure produces non-deterministic iteration order, breaking positional or keyed assertions.** Fixture IDs stored in a `set` lose insertion order. When the resulting sequence feeds into a dict lookup, indexed assertion, or ordered comparison, iteration order becomes unpredictable. Python's `-R` flag (hash randomization) makes this worse across restarts. Load correlation may be indirect: different process scheduling changes garbage-collection timing, which changes object addresses, which influences hash collisions in the underlying table.

**Likelihood: Moderate-High (~60-80%).** Accounts for intermittency. May partially explain load correlation via GC/scheduling effects on set layout. Less obviously tied to timezone, but timezone might correlate with *which* fixture gets selected (time-of-day-dependent fixtures), producing a deterministic-looking failure pattern per developer.

## Phase 2 & 3: Pattern Analysis and Minimal Reproduction

Below are the three bugs shown with their current (broken) form, reproduction strategy, and deterministic fix.

### Bug 1: Timezone-Dependent Timestamp Assertion

```python
# ──────────────────────────────────────────────
# CURRENT CODE (buggy) — test_user_timezone.py
# ──────────────────────────────────────────────
from datetime import datetime

def test_profile_last_updated():
    # Profile saved at ~now
    profile = {"last_updated": datetime.now().strftime("%Y-%m-%d %H:%M:%S %Z")}
    
    # BUG: Expected value was computed in UTC at authoring time.
    # Developer in IST (+05:30) sees "2026-08-25 18:30:00 IST"
    # CI expects "2026-08-25 13:00:00 UTC"  ← off by hours
    expected = "2026-08-25 13:00:00 UTC"
    assert profile["last_updated"] == expected
```

**Reproduction — force timezone mismatch:**

```bash
# Run this in two shells to see it fail/succeed:
TZ=America/New_York pytest test_profile_timezone.py -v   # may fail
TZ=UTC                   pytest test_profile_timezone.py -v  # may pass
```

Or freeze time inside the test to eliminate the clock entirely:

```python
# ──────────────────────────────────────────────
# REPRODUCTION + FIX — test_user_timezone_fixed.py
# ──────────────────────────────────────────────
from datetime import datetime, timezone
from freezegun import freeze_time

@freeze_time("2026-08-25T13:00:00+00:00")
def test_profile_last_updated():
    """Fixed: freeze clock, assert against known value, use UTC."""
    profile = {"last_updated": datetime.now(timezone.utc).isoformat()}
    
    # Use datetime equality instead of string formatting, or assert
    # relative tolerance. Either approach removes timezone from the equation.
    assert profile["last_updated"].startswith("2026-08-25")
    # OR (better):
    expected_dt = datetime(2026, 8, 25, 13, 0, 0, tzinfo=timezone.utc)
    actual_dt = datetime.fromisoformat(profile["last_updated"])
    assert abs((actual_dt - expected_dt).total_seconds()) < 2
```

**Fix summary:**
1. Freeze time with `@freeze_time()` so every run starts from the same instant.
2. Assert on UTC timestamps (`datetime.now(timezone.utc)`) rather than local time.
3. Compare datetimes (or use `.startswith()` / tolerance windows) instead of matching a full formatted string with `%Z`.

### Bug 2: Fixed-Sleep Async Worker Race

```python
# ──────────────────────────────────────────────
# CURRENT CODE (buggy) — test_async_worker.py
# ──────────────────────────────────────────────
import asyncio
import time

class AsyncWorker:
    def __init__(self):
        self.results = []
    
    async def process(self, items):
        """Simulates I/O-bound work."""
        for item in items:
            await asyncio.sleep(0.1)  # each item takes ~100ms
            self.results.append(item * 2)

async def test_worker_processes_all_items():
    worker = AsyncWorker()
    items = list(range(50))       # 50 items × 100ms = ~5 seconds total
    
    asyncio.create_task(worker.process(items))
    # BUG: assumes all 50 items finish in 2 seconds flat.
    time.sleep(2)                 # too short under load; CI passes, dev fails
    
    assert len(worker.results) == 50  # IndexError or AssertionError on slow machines
```

**Reproduction — force race by slowing the worker:**

```python
# Add to the worker temporarily:
await asyncio.sleep(0.5)  # simulate load 5× slower
# Now sleep(2) definitely fails regardless of machine.
```

Or stress-run the original while monitoring:

```python
# ──────────────────────────────────────────────
# REPRODUCTION + FIX — test_async_worker_fixed.py
# ──────────────────────────────────────────────
import asyncio
import pytest
import time

class AsyncWorker:
    def __init__(self):
        self.results = []
        self._lock = asyncio.Lock()
    
    async def process(self, items):
        async with self._lock:
            for item in items:
                await asyncio.sleep(0.1)
                self.results.append(item * 2)

async def test_worker_processes_all_items():
    worker = AsyncWorker()
    items = list(range(50))
    
    task = asyncio.create_task(worker.process(items))
    
    # FIXED: Wait for the task to actually complete instead of guessing.
    # Condition polling — check after each cycle that progress is happening,
    # with a deadline so we never hang forever.
    deadline = time.monotonic() + 30  # generous ceiling
    while len(worker.results) != 50 and time.monotonic() < deadline:
        await asyncio.sleep(0.2)       # poll interval, no busy-wait
    
    # If we exited the loop because of the deadline, give a clear error:
    assert len(worker.results) == 50, (
        f"Worker stalled: only {len(worker.results)}/50 items processed "
        f"(took {time.monotonic()-deadline:.1f}s)"
    )

# ──────────────────────────────────────────────
# CONDITION-BASED WAITING (generalized helper)
# ──────────────────────────────────────────────
async def wait_for(condition, poll_interval=0.1, timeout=30):
    """Replace ALL arbitrary sleeps in tests with this pattern."""
    deadline = time.monotonic() + timeout
    while not condition() and time.monotonic() < deadline:
        await asyncio.sleep(poll_interval)
    return condition()
```

**Fix summary:**
1. Replace `time.sleep(N)` with `asyncio.wait(task)` or condition polling (`await asyncio.sleep(interval)` in a loop checking a predicate).
2. Always include a timeout/deadline to fail fast with a clear message rather than hanging indefinitely.
3. Use `time.monotonic()` (not `time.time()`) — immune to system clock adjustments.

### Bug 3: Set-Ordered Dict Iteration

```python
# ──────────────────────────────────────────────
# CURRENT CODE (buggy) — test_fixture_ids.py
# ──────────────────────────────────────────────
import pytest

FIXTURE_IDS = {"alpha", "beta", "gamma"}   # BUG: set, not list/tuple

@pytest.mark.parametrize("fid", FIXTURE_IDS)
def test_fixture_has_expected_name(fid):
    """Fixture names returned in set-order; assertion expects fixed order."""
    fixture_map = {
        fid: {"name": fid.upper(), "score": 10},
        "other": {"name": "OTHER", "score": 0},
    }
    
    # BUG: iterating over fixture_map.items() yields keys in
    # whatever order the set-FIXTURE_IDS happened to hash into.
    # On one run: alpha → beta → gamma
    # On another: gamma → alpha → beta  ← dict order shifts
    result_list = [(k, v["score"]) for k, v in fixture_map.items()]
    
    # This assumes alpha always comes first:
    assert result_list[0] == ("alpha", 10), \
        f"Expected 'alpha' first, got '{result_list[0][0]}'"
```

**Reproduction — force hash randomization:**

```bash
PYTHONHASHSEED=random pytest test_fixture_ids.py -v    # different order each run
PYTHONHASHSEED=42      pytest test_fixture_ids.py -v    # deterministic but wrong order
PYTHONHASHSEED=0       pytest test_fixture_ids.py -v    # yet another order
```

```
# Example output with PYTHONHASHSEED=random showing failure:
# Run 1: ["gamma" first] → AssertionError: Expected 'alpha' first, got 'gamma'
# Run 2: ["alpha" first]  → passed
# Run 3: ["beta" first]   → AssertionError: Expected 'alpha' first, got 'beta'
```

```python
# ──────────────────────────────────────────────
# REPRODUCTION + FIX — test_fixture_ids_fixed.py
# ──────────────────────────────────────────────
import pytest

# FIX 1: Use a tuple/list for fixture IDs — guaranteed insertion order.
FIXTURE_IDS = ("alpha", "beta", "gamma")

@pytest.mark.parametrize("fid", FIXTURE_IDS)
def test_fixture_has_expected_name(fid):
    fixture_map = {
        fid: {"name": fid.upper(), "score": 10},
        "other": {"name": "OTHER", "score": 0},
    }
    
    # FIX 2: If you MUST iterate and care about order, sort explicitly.
    result_list = sorted([(k, v["score"]) for k, v in fixture_map.items()],
                         key=lambda pair: pair[0])
    
    assert result_list[0] == ("alpha", 10), \
        f"Expected 'alpha' first, got '{result_list[0][0]}'"

# ──────────────────────────────────────────────
# ALTERNATIVE FIX 3: Don't depend on iteration order at all.
# Assert by key, not by position.
# ──────────────────────────────────────────────
def test_fixture_by_key_not_position():
    result_map = {"alpha": 10, "beta": 10, "gamma": 10}
    
    # Keyed access is deterministic regardless of iteration order.
    assert result_map["alpha"] == 10
    assert result_map["beta"] == 10
```

**Fix summary:**
1. Change `set` → `tuple` or `list` for anything whose iteration order matters.
2. Where iteration order must be deterministic, call `sorted()` explicitly before asserting position.
3. Prefer keyed/dictionary access (`d[key]`) over positional indexing (`list[i]`) whenever possible — this eliminates the ordering dependency entirely.

            await asyncio.sleep(self.delay)
            self.results.append(item * 2)


class TestAsyncWorkerBuggy:
    def test_races_on_slow_machine(self):

        loop = asyncio.new_event_loop()
        try:
            worker = AsyncWorker(delay_per_item=0.1)
            items = list(range(50))
            loop.create_task(worker.process(items))

            loop.close()


class TestAsyncWorkerFixed:
    @pytest.mark.asyncio
    async def test_completes_under_load(self):

        items = list(range(50))  # total ≈ 5s
        
        task = asyncio.create_task(worker.process(items))

        deadline = time.monotonic() + 30
        while len(worker.results) != 50 and time.monotonic() < deadline:
            await asyncio.sleep(0.2)
        
        assert len(worker.results) == 50, \
            f"Stalled at {len(worker.results)}/50"

        await task  # raises if task had an exception

## Summary: Prescribed Fixes

| Test | Root Cause | Fix |
|------|-----------|-----|
| **Timestamp** | Compares wall-clock formatted string against hardcoded UTC expectation; timezone shifts change local representation | Freeze time with `@freeze_time()`, compute timestamps in UTC, assert on datetime objects or prefix strings with tolerance |
| **Async worker** | Fixed `sleep(2)` is shorter than the worker's actual completion time under load; race condition | Replace `time.sleep()` with `await asyncio.wait(task)` or condition polling with a monotonic deadline |
| **Fixture IDs** | `set` iteration order is non-deterministic (hash-randomized); positional dict assertions break when order shifts | Use `tuple`/`list` for fixture IDs, or `sorted()` before position-based assertions, or prefer keyed access over indexing |

All three fixes remove the environmental dependency (timezone, CPU load, hash seed) from the test logic itself, making the suite deterministic regardless of runner or developer configuration.
