# FastAPI p99 Spike Investigation Plan

## Problem Summary

p50 stayed nearly flat (**80→85 ms**) while p99 **spiked 9×** (210→1900 ms). CPU and memory are flat — ruling out compute pressure. Dashboards show:

- ↑ DB connections active
- ↑ Query count per request

This is a **tail-latency pattern**: most requests are unaffected; a minority suffer orders-of-magnitude slowdown pointing at an external resource bottleneck, not application-level compute.

---

## Root Cause Hypotheses

| # | Hypothesis | Mechanism | Explains Connections? | Explains Query Count↑? |
|---|---|---|---|---|
| A | **N+1 query regression** | Route fires K individual queries instead of 1 (missing `joinedload`, loop over paginated rows, eager loading removed). Small pages stay fast; large pages blow up p99. | Yes — each query acquires a connection; many concurrent requests exhaust the pool | Yes — directly multiplies queries per request |
| B | **Connection pool saturation / leak** | All pool connections occupied by long-running queries. New requests block on `acquire()`. One stuck query pins a connection for seconds. | Yes — pool is fully consumed | Not necessarily high median, but occasional bursts |
| C | **Lock contention / deadlocks** | Missing index on JOIN/WHERE column → table scan → heavier row locks. Concurrent transactions wait on each other. Retries multiply queries. | Yes — blocked transactions hold connections | Variable — normal until retry kicks in |
| D | **Network egress timeout** | Downstream service returns slowly for specific payloads. | No | No | Ruled out: doesn't match dashboard signals |

Hypotheses A, B, C account for all observed signals. The investigation distinguishes among them.

### 1c. Application-Level Query Tracer

```python
# app/instruments/query_tracer.py
import time
import logging
from contextlib import contextmanager
from typing import Generator, Dict, Any

logger = logging.getLogger("perf.query")


class RequestQueryTracker:
    """Tracks query count and timing per HTTP request."""

    def __init__(self):
        self._counters: Dict[str, Dict[str, Any]] = {}

    def start_request(self, request_id: str) -> None:
        self._counters[request_id] = {
            "query_count": 0,
            "total_db_ms": 0.0,
            "pool_wait_ms": 0.0,
            "queries": [],  # sample of last 20 query times
        }

    def record_query(self, request_id: str, duration_ms: float, pool_wait_ms: float = 0) -> None:
        entry = self._counters.get(request_id)
        if entry is None:
            return
        entry["query_count"] += 1
        entry["total_db_ms"] += duration_ms
        entry["pool_wait_ms"] += pool_wait_ms
        if len(entry["queries"]) < 20:
            entry["queries"].append(duration_ms)

    def end_request(self, request_id: str) -> Dict[str, Any]:
        return self._counters.pop(request_id, {})


tracker = RequestQueryTracker()
```

### 1d. Request Profiler Middleware

```python
# app/middleware/request_profiler.py
import time
import uuid
import asyncio
import logging
from fastapi import Request, Response
from starlette.middleware.base import BaseHTTPMiddleware, RequestResponseEndpoint
from app.instruments.query_tracer import tracker

logger = logging.getLogger("perf.middleware")

N_PLUS_ONE_THRESHOLD = 5  # queries per request


class RequestProfilerMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next: RequestResponseEndpoint) -> Response:
        request_id = f"req-{str(uuid.uuid4())[:8]}"
        request.state.request_id = request_id

        tracker.start_request(request_id)
        t0 = time.monotonic()

        try:
            response = await call_next(request)
        except Exception as exc:
            elapsed_ms = (time.monotonic() - t0) * 1000
            stats = tracker.end_request(request_id)
            logger.error("request_error", request_id=request_id,
                         method=request.method, url=str(request.url),
                         status=500, duration_ms=elapsed_ms, query_stats=stats,
                         exc_info=exc)
            raise

        elapsed_ms = (time.monotonic() - t0) * 1000
        stats = tracker.end_request(request_id)

        # Attach diagnostic headers
        response.headers["X-Request-ID"] = request_id
        response.headers["X-Duration-Ms"] = str(round(elapsed_ms, 2))
        response.headers["X-Query-Count"] = str(stats.get("query_count", "?"))

        # Flag potential N+1
        if stats.get("query_count", 0) > N_PLUS_ONE_THRESHOLD:
            response.headers["X-Potential-N-Plus-One"] = "true"

        # Log per-request summary
        logger.info("request_complete",
                    method=request.method,
                    path=request.url.path,
                    status_code=response.status_code,
                    request_id=request_id,
                    duration_ms=round(elapsed_ms, 2),
                    query_count=stats.get("query_count", 0),
                    total_db_ms=round(stats.get("total_db_ms", 0), 2),
                    pool_wait_ms=round(stats.get("pool_wait_ms", 0), 2),
                    n_plus_one_flagged=stats.get("query_count", 0) > N_PLUS_ONE_THRESHOLD)

        return response
```

## Phase 3: Distinguishing Between Hypotheses

### Decision Matrix

Run these diagnostics in parallel during live traffic or load test. Match the signal pattern.

| Diagnostic Signal | N+1 Queries (A) | Pool Saturation (B) | Lock Contention (C) |
|---|---|---|---|
| **Query count / request (median)** | High (5–100+), wide variance | Low (1–3), occasional burst | Normal (1–3), variable under retries |
| **Individual query duration** | Most < 5ms; cumulative time drives tail | Few very long queries (> 500ms each) | One or two extremely long; rest short |
| **Pool wait time histogram (p50 vs p99)** | Flat — p99 ≈ p50 | Right-skewed — p99 >> p50 (seconds) | Spikes correlating with lock-holding queries |
| **Active pool connections (% of max)** | Spreads evenly; rarely hits 100% | Consistently near 100% | Periodic spikes to 100% |
| **Pg_stat_activity: `waiting` state** | Rarely in `waiting` | In `waiting` on `AwaitingConnection` | In `waiting` on `TupleLock` or `PageLatch` |
| **Duration vs query count (scatter plot)** | Strong positive linear correlation | No correlation; some slow with 1 query | Clustered around same SQL text |
| **Postgres log: `log_lock_waits`** | Empty | Empty | Entries with `deadlock detected` or `statement canceled` |
| **1 VU (single-user) test** | P99 stays high (inherent to query shape) | P99 drops to baseline (no contention) | May persist if single-user triggers the long scan |
| **Py-spy flame graph hot path** | Many thin leaf nodes — repeated identical SELECTs | Thick vertical bars at `pool.acquire()` | Thick bars inside transaction boundary with lock waits |

## Phase 4: Reading the Flame Graph

After generating `profile-regression.svg` with py-spy, open in browser and apply this scanning methodology:

### Step 1: Identify Blocking vs Compute

Look at the **bottom-most layer** of the stacked rectangles (the leaf functions):

- **I/O-heavy**: Stacks dominated by `recvfrom`, `socket.read`, `select.select`, `epoll_wait` → the process is **blocked waiting** on network/Disk. For a FastAPI+DB app, this means "waiting for PostgreSQL to respond."
- **Compute-heavy**: Stacks dominated by Python bytecodes (`_PyEval_EvalFrameDefault`) → actual CPU work. Since your CPU is flat, this should be minor.

If I/O dominates: the bottleneck is downstream (DB), not the app itself. Move to step 2.

### Step 2: Find Hot Paths by Width

Rectangle width = wall-clock time proportionally. Look for:

- **Wide rectangles near bottom** = frequently-called functions consuming significant time
- **Narrow but tall rectangles** = infrequently called but each takes a lot of time (these are your tail offenders)

In an N+1 scenario, you'll see **many thin, repeating leaf nodes** — the same query executed 50 times in rapid succession, each taking ~2ms, but cumulatively consuming 100ms.

### Step 3: Spot Lock / Contention Patterns

- Search stacks for `asyncio.Lock.acquire`, `threading.Lock.acquire`, `pool.acquire()`, `Semaphore.acquire`
- If these appear at the bottom of **many different stack traces**, threads are queuing — that's contention
- **Compare width pre/post**: if lock-acquire accounts for 60% of total graph width in the regression version but was 0% in baseline, you found the contention hotspot

### Interpretation Guide

| Pattern in Flame Graph | Likely Cause | Action |
|---|---|---|
| Bottom layer full of `socket.*` / `select.*` | Waiting on DB/network | Profile the DB, not the app |
| Repeated small rectangles with identical query names in middle layer | N+1: same query looping | Add eager loading / batching |
| Wide bar at `pool.acquire()` / `ConnectionPool.getconn()` | Pool starvation | Tune pool size / find long queries |
| Bars at `asyncio.Lock.acquire()` across many stacks | Code-level lock contention | Reduce critical section scope |
| `Seq Scan` visible in slow queries (via PG log + EXPLAIN) | Missing index | CREATE INDEX |

## Phase 5: Proposed Fixes Ranked by Expected p99 Impact

### Fix 1: Eliminate N+1 Queries (Expected p99 reduction: **500–1500ms**, Effort: **Low**, Risk: **Low**)

The #1 suspect given query-count-per-request increased. Typical pattern:

```python
# ANTI-PATTERN: N+1 queries (likely introduced by recent deploy)
async def list_items(page: int = 1, limit: int = 50):
    items = await db.execute(select(Item).offset(page * limit).limit(limit))
    result = []
    for item in items.scalars():
        # Each iteration fires a NEW query — this is N+1
        categories = await db.execute(
            select(Category).where(Category.id == item.category_id)
        )
        item.categories = categories.scalars().all()
        result.append(item)
    return {"items": result, "total": total_count}
# At limit=50: 51 individual queries per request
```

```python
# FIX: Eager loading with joinedload / selectinload
from sqlalchemy.orm import joinedload, selectinload

async def list_items(page: int = 1, limit: int = 50):
    # Single query with JOIN, plus one more for categories
    stmt = (
        select(Item)
        .options(joinedload(Item.categories))  # joins categories in ONE query
        .offset(page * limit)
        .limit(limit)
    )
    items = (await db.execute(stmt)).unique().scalars().all()
    return {"items": items, "total": total_count}
# Total: 2 queries regardless of page size
```

```python
# ALTERNATIVE FIX: Batch lookups with WHERE IN
async def list_items(page: int = 1, limit: int = 50):
    items = await db.execute(select(Item).offset(page * limit).limit(limit))
    item_list = items.scalars().all()
    
    category_ids = [item.category_id for item in item_list]
    if category_ids:
        categories = await db.execute(
            select(Category).where(Category.id.in_(category_ids))  # ONE query
        )
        cat_map = {c.id: c for c in categories.scalars().all()}
        for item in item_list:
            item.categories = [cat_map[cid] for cid in item.category_ids if cid in cat_map]
    
    return {"items": item_list, "total": total_count}
# Total: 2 queries regardless of page size
```

### Fix 2: Add Missing Database Indexes (Expected p99 reduction: **200–800ms**, Effort: **Low**, Risk: **None**)

From the `seq_scan` query results, create indexes on the highest-seq-scan tables:

```sql
-- Create indexes based on actual sequential scan evidence
-- Target tables with highest seq_tup_read first

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_items_category_id 
    ON items (category_id);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_items_created_at_desc 
    ON items (created_at DESC);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_item_id_status 
    ON orders (item_id, status);

-- Verify they're being used
EXPLAIN ANALYZE SELECT * FROM items WHERE category_id = 42 ORDER BY created_at DESC LIMIT 50;
-- Should show "Index Scan using idx_items_category_id" not "Seq Scan"
```

`CONCURRENTLY` avoids locking the table during index creation (required for zero-downtime deploys).

### Fix 3: Batch / Coalesce Related Queries (Expected p99 reduction: **100–500ms**, Effort: **Medium**, Risk: **Low**)

When you can't use JOIN (different databases, ORM limitations):

```python
# Instead of K individual SELECTs, use parameterized IN clause
async def get_item_details(item_ids: list[int]) -> dict[int, ItemDetail]:
    if not item_ids:
        return {}
    
    # ONE query instead of K queries
    results = await db.execute(
        select(ItemDetail)
        .where(ItemDetail.id.in_(item_ids))
    )
    
    return {r.id: r for r in results.scalars().all()}

# Usage replaces a loop:
# OLD: for id in ids: detail = await get_detail(id)  ← O(n) queries
# NEW: details = await get_item_details(ids)          ← 1 query
```

For bulk inserts/updates:

```python
# Use executemultiplary for batch inserts
await db.execute(
```

```python
    pool_size=20,           # WAS 10 or less — increase to handle concurrent handlers
    max_overflow=10,        # Keep some headroom; consider 0 for strict rejection
    pool_pre_ping=True,     # Verify connections before use (avoid stale socket errors)
    pool_recycle=300,       # Recycle connections every 5min (avoids proxy/firewall timeouts)
    connect_args={
        "command": "SET statement_timeout = '5s'",  # Fail-fast on hung queries
    },
)
```

Pool sizing formula:
```
Recommended pool_size = min(worker_count × concurrent_db_ops_per_worker, DB_MAX_CONNECTIONS * 0.7)

Example: 4 workers × 3 concurrent DB ops = 12 minimum
         With margin: pool_size = 15–20
```

Consider `max_overflow=0` if you prefer **fail-fast queue rejection** over silent queuing. When pool is full, reject immediately (503) rather than letting requests accumulate behind queued connections — this keeps p99 predictable even if overall throughput is lower.

### Fix 5: Add Circuit Breaker / Request Timeout (Expected p99 reduction: **direct 0–100ms, prevents cascade 1500ms+**, Effort: **Medium**, Risk: **Low**)

Never let a single slow query hang an entire request:

```python
# Wrap DB operations with hard timeouts
async def safe_db_execute(session, stmt, timeout: float = 3.0):
    """Execute a query with a hard timeout — fails fast rather than hanging."""
    try:
        return await asyncio.wait_for(session.execute(stmt), timeout=timeout)
    except asyncio.TimeoutError:
        logger.warning("db_timeout", sql=str(stmt)[:200], timeout_s=timeout)
        raise HTTPException(status_code=504, detail="Database operation timed out")

# Usage in route:
async def list_items(...):
    result = await safe_db_execute(
        db, 
        select(Item).options(joinedload(Item.categories)),
        timeout=2.0  # 2 second hard cap
    )
    return result
```

Add exponential-backoff retry for transient failures:

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
```

## Key Principles Remembered

1. **Measure first, always.** Record p50/p95/p99, RPS, error rate, and pool metrics BEFORE touching anything.
2. **One change at a time.** Isolate the variable — never deploy multiple fixes simultaneously and attribute gains.
3. **Profile with realistic data.** Dev has 10 rows; production has millions. Different bottlenecks at different scales.
4. **Don't ignore P99.** P50 looked fine while P99 was catastrophic. Tail latency IS the bug here.
5. **Set performance budgets in CI.** `p99 < 200ms` as a gate on merge prevents future regressions.
