## Investigation Design: FastAPI P99 Regression (210ms → 1900ms)

### Signal Analysis

The symptom profile tells the story immediately:

| Metric | Before | After | Delta |
|--------|--------|-------|-------|
| P50 | 80ms | 85ms | +6% — **negligible** |
| P99 | 210ms | 1900ms | **+805% — catastrophic** |
| CPU | flat | flat | no compute bottleneck |
| Memory | flat | flat | no leak visible yet |
| DB connections | normal | **spiked** | pool pressure |
| Queries/req | normal | **spiked** | query explosion |

**This is a latency tail problem, not a throughput problem.** The P50 barely moved because most requests still get served fast from the pool head. The P99 broke because a fraction of requests hit a queueing/stalled path. Three competing hypotheses:

1. **N+1 query pattern** — a change introduced a loop making per-item DB calls (e.g., fetching related objects one-at-a-time instead of joined/batched)
2. **Pool saturation / connection starvation** — queries take longer now, holding connections longer than the pool size, causing new requests to wait for a freed slot
3. **Slow query + lock contention** — one query got slower (missing index, changed join order), blocking a row/table lock that serializes other requests

Hypotheses aren't mutually exclusive — N+1 causes pool pressure which causes queuing. But we need to distinguish the *root cause* from the *cascading symptom*.

```python
# instrumentation/query_profiler.py
import logging
from sqlalchemy import event
from sqlalchemy.engine import Engine
from collections import defaultdict
import time
from starlette.requests import Request
from starlette.middleware.base import BaseHTTPMiddleware, AsyncRequestResponseEndpoint

logger = logging.getLogger("perf.profiler")

class QueryTrackingMiddleware(BaseHTTPMiddleware):
    """Tracks all SQL queries per request with timing."""

    def __init__(self, app, engine: Engine, sample_rate: float = 1.0):
        super().__init__(app)
        self.engine = engine
        self.sample_rate = sample_rate
        self._request_queries: dict[str, list[dict]] = {}

    async def dispatch(self, request: Request, call_next):
        if random.random() > self.sample_rate:
            return await call_next(request)

        request_id = request.headers.get("x-request-id", str(id(request)))
        queries = []

        # Attach per-request tracking to the state
        request.state.sql_queries = queries

        @event.listens_for(self.engine, "before_cursor_execute")
        def before_cursor(conn, cursor, statement, parameters, context, executemany):
            conn.info.setdefault("query_start_time", []).append(time.monotonic())

        @event.listens_for(self.engine, "after_cursor_execute")
        def after_cursor(conn, cursor, statement, parameters, context, executemany):
            start = conn.info["query_start_time"].pop()
            duration_ms = (time.monotonic() - start) * 1000
            queries.append({
                "sql": self._truncate(statement, 2000),
                "duration_ms": round(duration_ms, 2),
                "parameters_count": len(parameters) if parameters else 0,
                "executemany": executemany,
            })

        try:
            response = await call_next(request)
            return response
        finally:
            total = sum(q["duration_ms"] for q in queries)
            if queries:
                logger.warning(
                    "SQL_REQUEST [%s] %s %s queries=%d sql_total_ms=%.1f p99_query_ms=%.1f "
                    "longest_query=%s",
                    request_id,
                    request.method,
                    request.url.path,
                    len(queries),
                    total,
                    sorted([q["duration_ms"] for q in queries])[-1] if queries else 0,
                    max(queries, key=lambda q: q["duration_ms"])["sql"][:200] if queries else "",
                )
            # Remove listeners to avoid memory leaks
            event.remove(self.engine, "before_cursor_execute", before_cursor)
            event.remove(self.engine, "after_cursor_execute", after_cursor)

    @staticmethod
    def _truncate(sql: str, max_len: int) -> str:
        if len(sql) <= max_len:
            return sql
        return sql[:max_len] + "... [truncated]"
```

What this gives you in your logs:
- Exact query count per request path
- Per-query timing distribution
- Which SQL statements are repeated many times (N+1 signature: same query, different params, 10-100 iterations)
- The single longest query (bottleneck candidate)

### Distinguishing the Three Hypotheses

Here's the decision matrix based on what each instrument will tell you:

| Evidence Pattern | Root Cause | Cascade |
|-----------------|------------|---------|
| Same SELECT executed 20-200× per req, each <5ms | **N+1 queries** | More queries → longer hold time → pool pressure → P99 tail |
| One query at 500-800ms, others fine | **Slow query** (missing index, bad plan) | Lock held long → pool drain → other requests queue |
| Pool active=max constantly, checkout waits 500-2000ms | **Pool exhaustion** | Requests queue in pool internals, never get slots fast enough |
| Threads blocked on `Lock.acquire()` in psycopg2/cursor | **Row/table lock contention** | Another transaction holds lock, serialize everything |
| `checkouts` metric equals `queries_per_request` × baseline | **N+1** (proportional increase) | — |
| `checkouts` << `queries_per_request` but queries dominate P99 | **Slow individual query** | — |

```python
# profiling/instrument_sql.py — drop this into a health route or middleware
from sqlalchemy import event, text
from collections import defaultdict
import traceback
import time

class QueryTracer:
    """Records every SQL execution with call stack and timing."""
    
    def __init__(self):
        self.queries_by_request = defaultdict(list)
        self.request_ids = {}
    
    @staticmethod
    def before_cursor_execute(conn, cursor, statement, parameters,
                              context, executemany):
        conn._query_start = time.perf_counter()
    
    @staticmethod
    def after_cursor_execute(conn, cursor, statement, parameters,
                             context, executemany, rowcount, duration):
        start = getattr(conn, '_query_start', None)
        elapsed_ms = duration * 1000
        if start is None:
            elapsed_ms = duration * 1000
        
        # Capture a truncated call stack to identify the application-level caller
        stack = []
        for frame_info in traceback.extract_stack()[-15:-1]:
            if 'site-packages' not in frame_info.filename and \
               '/lib/python' not in frame_info.filename:
                stack.append(f"{frame_info.filename}:{frame_info.lineno} in {frame_info.name}")
        
        key = getattr(conn, '_request_id', 'unknown')
        tracer.queries_by_request[key].append({
            "sql": str(statement)[:200],          # truncate long queries
            "duration_ms": round(elapsed_ms, 2),
            "parameters_count": len(parameters) if parameters else 0,
            "executemany": executemany,
            "call_stack": stack[-5:],              # top 5 app frames
        })
    
    def snapshot_for_request(self, request_id: str) -> list[dict]:
        return self.queries_by_request.get(request_id, [])


# Register globally (do this once at app startup, gated behind a flag):
if ENABLE_SQL_TRACING:
    tracer = QueryTracer()
    event.listen(QueryTracer.before_cursor_execute.__globals__['engine'], 
                 "before_cursor_execute", QueryTracer.before_cursor_execute)
    event.listen(QueryTracer.before_cursor_execute.__globals__['engine'], 
                 "after_cursor_execute", QueryTracer.after_cursor_execute)
```

### 1.2 SQLAlchemy Query Tracer (Middyware / Event Listener)

If using SQLAlchemy, install an event listener that logs every query with timestamp, duration, SQL (truncated), and call stack. This is how you prove N+1:

```python
#!/usr/bin/env python3
"""
SQLAlchemy event listener that traces all queries at WARNING level.
Install in your FastAPI app startup: install_query_tracer(engine).
Requires SQLAlchemy >= 1.4.
"""
import logging
import time
import traceback
from sqlalchemy import event

logger = logging.getLogger("query.tracer")

_QUERY_SAMPLE_RATE = 0.10  # Sample 10% of queries to avoid log storms
import random

@event.listens_for(logging.getLogger("sqlalchemy.engine").parent or None, "before_execute")
def _noop():
    pass  # placeholder — real tracer uses "after_execute" below


def install_query_tracer(engine, sample_rate: float = 0.10, max_sql_len: int = 500):
    """
    Attach to engine. Every executed query fires a warning with:
      - start/end timestamps → computes duration
      - first line of SQL (truncated)
      - current stack frame (caller module + function)
    
    Samples randomly to avoid overwhelming logs.
    """
    global _QUERY_SAMPLE_RATE
    _QUERY_SAMPLE_RATE = sample_rate

    @event.listens_for(engine, "before_execute")
    def before_execute(conn, element, multiparams, params):
        conn.info["_query_start"] = time.monotonic()
        conn.info["_query_element_type"] = type(element).__name__

    @event.listens_for(engine, "after_execute")
    def after_execute(conn, element, multiparams, params, retval):
        start = conn.info.pop("_query_start", None)
        duration_ms = (time.monotonic() - start) * 1000 if start else 0

        # Determine caller (skip internals)
        stack = traceback.extract_stack()
        caller = None
        for frame in reversed(stack[:-2]):  # skip this function + event dispatch
            mod = frame.filename.rsplit("/", 1)[-1] if "/" in frame.filename else frame.filename
            func_name = frame.name
            # Stop at sqlalchemy internals
            if "sqlalchemy" in mod or "starlette" in mod or "uvicorn" in mod:
                continue
            caller = f"{mod}:{func_name}"
            break

        sql_str = str(element) if hasattr(element, "__str__") else "?"
        if len(sql_str) > max_sql_len:
            sql_str = sql_str[:max_sql_len] + "…"

        # Sample-based logging to avoid flood
        if random.random() > _QUERY_SAMPLE_RATE:
            return

        logger.warning(
            "[qtrace] %.1fms | %-8s | %s\n  FROM: %s\n  SQL: %s",
            duration_ms,
            conn.info.get("_query_element_type", "?"),
            sql_str[:120],
            caller,
            sql_str[:max_sql_len],
        )

    logger.info(
        "Installed query tracer on engine=%s (sample_rate=%.0%%)",
        engine.url.get_backend_name(),
        _QUERY_SAMPLE_RATE * 100,
    )
```

# Performance Investigation: FastAPI Service P99 Regression

## Signal Interpretation

| Metric | Before | After | Delta | What It Tells Us |
|--------|--------|-------|-------|------------------|
| P50 latency | 80ms | 85ms | +6% | Core path unchanged — not systemic |
| P99 latency | 210ms | 1,900ms | +805% | Tail is getting fatter — fan-out distribution shift |
| CPU | flat | flat | — | Not compute-bound; something else is blocking |
| Memory | flat | flat | — | Not a leak; no OOM pressure building |
| DB connections | spike | — | ↑↑ | More concurrent sessions opened |
| Queries/req | spike | — | ↑↑ | Query count per request jumped |

The P50 staying nearly identical while P99 explodes is the textbook signature of **request-level N+1 fan-out** (not uniform slowdown). Some percentage of requests now execute 10x–50x more queries than before, stretching tail latency. Flat CPU and memory confirm the bottleneck is external: database I/O wait and/or connection pool exhaustion from accumulated open connections.

### 2. SQLAlchemy Execution Interceptor (structured query logging)

Add an event listener to emit structured metadata alongside every query. This works even if you don't have an APM pipeline wired up.

```python
import time
import logging
from sqlalchemy import event

logger = logging.getLogger("query_trace")

@event.listens_for(engine, "before_cursor_execute")
def before_execute(conn, cursor, statement, parameters, context, executemany):
    conn.info.setdefault("query_start_time", []).append(time.perf_counter())
    # Store client correlation id if available via ASGI scope
    if hasattr(conn, "_correlation_id"):
        logger.warning(
            "QUERY_START|%s|%s|%s",
            conn._correlation_id,
            " ".join(statement.split()),
            len(parameters),
        )

@event.listens_for(engine, "after_cursor_execute")
def after_execute(conn, cursor, statement, parameters, context, executemany):
    start = conn.info["query_start_time"].pop()
    duration_ms = (time.perf_counter() - start) * 1000
    logger.warning(
        "QUERY_END|%s|%d.%03d|%s",
        conn._correlation_id,
        int(duration_ms),
        int((duration_ms % 1) * 1000),
        " ".join(statement.split()[:50]),  # truncate long statements
    )

@app.middleware("http")
async def attach_correlation(request, call_next):
    import uuid
    request.state.correlation_id = str(uuid.uuid4())
    # Inject into SQLAlchemy connection
    async with db.session() as s:
        s.connection()._connection_record.info["_correlation_id"] = request.state.correlation_id
    response = await call_next(request)
    response.headers["X-Correlation-ID"] = request.state.correlation_id
    return response
```

Parse the log output to compute:
- **Queries-per-request distribution**: count QUERY_START lines per correlation ID
- **Query latency histogram**: per-statement average and p99
- **Duplicate query detection**: group by first 40 chars of statement; if same query appears 5+ times in one request, it's N+1

## Phase 2: Distinguishing the Three Root Causes

The three suspects all increase query count and DB connections, but they produce distinctly different signal patterns. Here's how to separate them:

### Decision Matrix

| Signal | N+1 Fan-Out | Pool Saturation | Lock Contention |
|--------|-------------|-----------------|-----------------|
| Query duration within a single request | Varies wildly; first few fast, later ones slow (progressive accumulation) | All queries take similar time (the delay is in acquiring the connection, not execution) | Individual queries run fine, but multiple requests block on the same row/table |
| Queries-per-request distribution | Heavy right tail; median ~2-3, max 50-200 | Uniformly elevated; every request gets same number of queries, just slower | Moderate query count per request, but requests queue behind each other |
| Query signatures | Many repeated queries with different parameter values (same SQL template, different WHERE clause params) | Normal query distribution, no repetition | Queries targeting same rows (same PK values in WHERE) |
| Connection behavior | Connections checked out and back in quickly (short-lived), but in large numbers | Checked-out connections stay alive for extended periods (waiting for available slot) | Checked-out connections hold rows locked for unusual durations |
| P95 vs P99 | P99 much higher than P95 (tail outliers drive P99) | P95 ≈ P99 (uniform slowdown across all requests hitting the pool limit) | P95 moderately elevated, P99 very high (some requests get lucky and aren't blocked) |
| Slow query log | Queries appear individually short (<50ms each) but accumulate | Short queries that never fire because they're stuck in the pool queue | Long-running transactions holding locks visible in `pg_locks` or equivalent |

### Concrete Diagnostic Queries

**Check for N+1 via query deduplication (PostgreSQL example):**
```sql
-- Find the same statement template appearing multiple times in recent queries
SELECT substring(query from 1 for 80) as template,
       count(*) as occurrences,
       round(avg(EXTRACT(EPOCH FROM end_time - start_time))::numeric, 3) as avg_ms
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1
HAVING count(*) > 5
ORDER BY count(*) DESC
LIMIT 20;
```

**Check for pool saturation:**
```sql
-- Connection counts by status over time (if you export pool metrics)
SELECT time_bucket('1min', ts) as window,
       avg(pool_checked_out) as avg_active,
       max(pool_checked_out) as peak_active,
       pool_size as total_pool
FROM pool_metrics
GROUP BY 1, pool_size
ORDER BY 1;
```
If `peak_active >= pool_size` for sustained windows, you're saturated.
