# Performance Investigation Plan: FastAPI Regression (P99: 210ms → 1900ms)

## Executive Summary

CPU/memory are flat while DB connections and query count per request spiked. This pattern points to an **N+1 query explosion** causing either connection-pool saturation or lock contention — not CPU-bound work. The P50 barely budged (80→85ms), confirming most requests still hit happy-path code paths; the P99 tail is what gets poisoned by queueing behind slow queries or exhausted pools.

---

## Phase 1: Instrumentation Under Real Traffic

### Attach These Concurrently During a Traffic Window

| Instrument | What It Proves | How to Run |
|---|---|---|
| **py-spy** (sampling profiler) | Flamegraph — CPU time per function | `py-spy record -d 60 -o profile.svg --pid <fastapi-pid>` |
| **pg_stat_statements** (PostgreSQL extension) | Per-query aggregate latency + call count | Query `pg_stat_statements` sorted by `total_exec_time`; compare pre-deploy baseline |
| **SQL query log** (statement logging) | Exact queries fired per request ID | Set `log_min_duration_statement = 0` temporarily + add `X-Request-ID` correlation via middleware |
| **Connection-pool metrics** (DB-API or ORM) | Pool size, checked-out count, wait time | If using SQLAlchemy AsyncEngine: listen on `checkin`/`checkout` events and emit to Prometheus |
| **Redis/Memcache cache hit rate** (if applicable) | Whether cache bypassed something | Monitor cache stats before/during incident window |
| **HTTP access logs with timing** | P50/P95/P99 broken down by endpoint | Add middleware that records `start → end → status → query_count` per request and emits to observability backend |

### Minimal Middleware to Instrument

```python
import time
import uuid
from starlette.middleware.base import BaseHTTPMiddleware
from prometheus_client import Counter, Histogram, Gauge

request_duration = Histogram(
    "http_request_duration_seconds", "HTTP request latency",
    ["method", "path", "status"], buckets=[0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0]
)
db_query_count = Counter("db_queries_per_request", "Count of SQL queries per HTTP request", ["path"])
db_pool_in_use = Gauge("db_pool_connections_in_use", "Connections currently checked out from pool")

class MetricsMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        req_id = str(uuid.uuid4())
        extra = {"x-request-id": req_id}
        response = await call_next(request)
        
        elapsed = time.perf_counter() - start
        path = request.url.path
        method = request.method
        status = response.status_code
        
        response.headers["x-request-id"] = req_id
        request_duration.labels(method=method, path=path, status=str(status)).observe(elapsed)
        
        # Expose query count if we tagged it
        qc = getattr(request.state, "_db_query_count", 0)
        if qc > 0:
            db_query_count.labels(path=path).inc(qc)
        
        return response
```

Add `_db_query_count` tracking inside your database layer (see Phase 2 diagnostics).

## Phase 2: Distinguishing the Three Root Causes

The spike could be N+1 queries, pool saturation, or lock contention. Here's how to isolate each.

### A. N+1 Query Pattern

**How to spot it:**

```sql
-- pg_stat_statements query (run during incident):
SELECT 
    query,
    calls,
    mean_exec_time AS avg_ms,
    total_exec_time / 1000 AS total_secs,
    rows
FROM pg_stat_statements
WHERE query LIKE '%your_table%'
ORDER BY total_exec_time DESC
LIMIT 20;
```

Look for:
- One query calling 10–200× more than before the deploy
- `calls` correlating with request volume × objects-per-response
- High `mean_exec_time` relative to simple primary-key lookups

**Confirm with py-spy flamegraph:**
- Stack frames show many repeated patterns of DB round-trips nested in view/response serialization loops
- Look for patterns like:

```
get_related_user  ← repeated hundreds of times in flame
├── execute_select
├── network_write
├── network_read
└── parse_result
```

Each "leaf" of the flame represents one DB round-trip stacked over request processing time.

**Quick confirmatory test:**

```python
# Patch at runtime (via py-spy python-mode or hot-reload):
import functools

_original_execute = Session.execute

@functools.wraps(_original_execute)
def _counting_execute(self, *args, **kwargs):
    self._query_count += 1
    return _original_execute(self, *args, **kwargs)

# Add query counter to session per request context
# Count queries during one typical request → if >5, likely N+1
```

### B. Connection Pool Saturation

**How to spot it:**

```sql
-- Current pool state:
SELECT 
    client_addr,
    state,
    query,
    now() - state_change AS idle_duration,
    now() - xact_start AS xact_duration
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY xact_start;

-- Pool exhaustion signal: many connections in 'waiting' or
-- extremely long 'active' durations (>5s for SELECT suggests 
-- table-level lock)
```

At application level, check pool metrics:

```python
# SQLAlchemy AsyncPool metrics (instrument these):
# pool_size = engine.pool.size()         ← max connections
# checked_out = engine.pool.checkedout() ← currently in use
# overflow = engine.pool.overflow()      ← beyond pool_size

# If checked_out ≈ pool_size for extended periods → saturation
# Requests queuing up waiting for a free connection → P99 spikes
```

**Diagnostic indicators:**
- `checked_out` hits `pool_size` boundary consistently
- `create_engine()` had pool size reduced or changed in the deploy
- Request latency shows quantized spikes matching queue depth (requests stack 2-3 deep)
- py-spy shows stacks blocked on `connection.get()` rather than within query execution

### C. Lock Contention

**How to spot it:**

```sql
-- Find blocking queries:
SELECT 
    blocked_locks.pid AS blocked_pid,
    blocked_activity.query AS blocked_query,
    blocking_locks.pid AS blocking_pid,
    blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

**Diagnostic indicators:**
- `pg_stat_activity` shows many transactions holding locks waiting on others
- Long-running transactions visible in `xact_duration` columns
- py-spy shows Python threads sitting in `select()` or `epoll_wait()` with no Python stack — OS-level sleep waiting for kernel lock release
- P99 correlates with write-heavy endpoints, not reads

## Phase 3: Reading the Py-Spy Flame Graph

After running `py-spy record -d 60 -o flame.svg`:

```
Open flame.svg in browser. Read bottom-to-top:

y-axis = call stack depth
x-axis = proportional width = CPU/profiling samples

What to look for:

  ╔══════════════════════════════════╗
  ║  fastapi/app.py:142              ║  ← Top: request lifecycle
  ║  routers/users.py:89             ║  ← Your route handler
  ║                                    ║
  ║  serializers/user.py:234  ██████  ║  ← WIDE frame = lots of time
  ║  databases/repo.py:56   ███       ║  ← Narrower = less time  
  ║  postgres/execute.py:78 █████████  ║  ← SPIKE = bottleneck
  ║  network/socket.py:12 ████         ║  ← Network wait visible
  ╚══════════════════════════════════╝

Flame graph signals for our case:

N+1 PATTERN: Many narrow tall spines repeating the same query 
             function, stacked vertically — each spine is one 
             round-trip. Like a sawtooth pattern climbing upward.

POOL SATURATION: Stacks terminate at the top of your DB client 
                 library (e.g., sqlalchemy/pool.py, psycopg/connect)
                 showing you're stuck getting a connection, not 
                 executing queries.

LOCK CONTENTION: py-spy will show very little activity — mostly 
                 idle/waiting frames — because threads are blocked 
                 at the kernel level waiting for row locks, not 
                 doing CPU work.
```

### Concrete Example — N+1 Detected

If the flamegraph looks like this:

```
UserDetailHandler (100%)
├── build_response (25%)
│   ├── serialize_name (2%)
│   └── serialize_email (3%)
├── fetch_orders [] (15%) ← ONE query, fine
├── fetch_orders[0].customer [30%] ← QUERY PER ORDER ITEM
├── fetch_orders[1].customer [30%] ← QUERY PER ORDER ITEM
├── fetch_orders[2].customer [30%] ← QUERY PER ORDER ITEM
└── ...repeat n times...
```

Each leaf `[fetch_orders[N].customer]` is one sequential DB round-trip. With 50 items in the list, that's potentially 50 serial queries stacked into one request's critical path — explaining the P99 explosion.

## Phase 4: Recommended Fixes Ranked by Expected P99 Impact

### Fix 1: Eliminate N+1 Queries — Highest Impact (Expected P99 reduction: 70–90%)

**If N+1 is confirmed:**

```python
# BEFORE: N+1 in loop
async def get_user_detail(user_id: int):
    user = await db.get(User, user_id)
    orders = await db.fetch_many(Order, where=Order.user_id == user_id)
    order_details = []
    for order in orders:          # Each iteration fires a NEW query
        items = await db.fetch(LineItem, where=LineItem.order_id == order.id)
        shipping = await db.fetch(ShippingAddress, where=ShippingAddress.id == order.shipping_id)
        order_details.append({...})  # ~50 additional queries per request
    return UserDetailResponse(...)

# AFTER: Eager loading with JOINs or batch IN clause
async def get_user_detail(user_id: int):
    user = await db.get(User, user_id)
    
    # Single query for all orders
    orders = await db.fetch(
        Order,
        where=Order.user_id == user_id,
        options=joinedload(Order.line_items),
        options=joinedload(Order.shipping_address)
    )
    
    # Or if ORM doesn't support joins:
    # order_ids = [o.id for o in orders]
    # line_items = await db.fetch_all(
    #     LineItem, where=LineItem.order_id.in_(order_ids)
    # )  # ONE query with IN (...) instead of N queries
    
    order_details = [_build_order_detail(o) for o in orders]
    return UserDetailResponse(...)
```

**Rollback first.** If there's been a recent commit adding loop-based queries, revert it. This is the highest-confidence, fastest fix.

### Fix 2: Database Indexes — High Impact on Slow Queries (Expected P99 reduction: 30–50% if indexes missing)

```sql
-- Analyze which queries are slow:
SELECT relname, seq_scan, idx_scan, 
       seq_tup_read, idx_tup_fetch
FROM pg_stat_user_tables
ORDER BY seq_scan DESC;

-- If seq_scan >> idx_scan on tables with frequent WHERE clauses:
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user_id 
    ON orders(user_id);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_lineitems_order_id 
    ON line_items(order_id);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_shipping_order_id 
    ON shipping_addresses(order_id);

-- For queries with multiple filter columns:
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user_created 
    ON orders(user_id, created_at DESC);
```

Use `CONCURRENTLY` to avoid blocking writes. Run during off-peak. Verify with `EXPLAIN ANALYZE`.

### Fix 3: Parallelize Independent Queries — Medium Impact (Expected P99 reduction: 20–40%)

```python
# BEFORE: Serial awaits
user = await db.get(User, user_id)          # 15ms
orders = await fetch_orders(user_id)         # 45ms
preferences = await fetch_preferences(user_id)  # 30ms
activity = await fetch_recent_activity(user_id)  # 60ms
# Total: ~150ms serial

# AFTER: Promise.all equivalent
user, orders, preferences, activity = await asyncio.gather(
    db.get(User, user_id),
    fetch_orders(user_id),
    fetch_preferences(user_id),
    fetch_recent_activity(user_id),
)
# Total: ~60ms (bound by slowest concurrent query)
```

Caveat: More parallel queries increase pool pressure. Coordinate with Fix 4.

### Fix 4: Connection Pool Tuning — Medium Impact (Expected P99 reduction: 15–30%)

```python
from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine(
    DATABASE_URL,
    pool_size=20,           # Increase from default (usually 5)
    max_overflow=10,        # Allow bursting beyond pool_size
    pool_timeout=30,        # Seconds to wait for free connection
    pool_recycle=1800,      # Recycle connections every 30min
    pool_pre_ping=True,     # Validate connections before checkout
)
```

**Key decisions:**
- `pool_size` should be set considering: `max_concurrent_requests / avg_query_duration * 1.2`. If you get 100 RPS and average query takes 50ms, you need `100 * 0.05 = 5` minimum, but N+1 with 10 queries/request changes this to `100 * 0.5 = 50` — which means the fix has to be query optimization, not just pool tuning.
- `max_overflow` lets requests burst above pool capacity rather than failing immediately
- `pool_pre_ping=True` prevents stale closed connections causing errors under load

### Fix 5: Response Caching — Sustained Impact (Expected P99 reduction: depends on read/write ratio)

```python
from fastapi_cache import FastAPICache
from fastapi_cache.backends.redis import RedisBackend

FastAPICache.init(RedisBackend(url="redis://localhost:6379"))

@fastapi_cache(expire=60)  # Cache for 60 seconds
@router.get("/users/{user_id}/detail")
async def get_user_detail(user_id: int):
    # Expensive computation goes through cache on repeat requests
    return build_user_detail(user_id)
```

Set short TTLs for frequently-changing data, longer for static content. Invalidates on mutations.

### Fix 6: API-Level Defensive Measures — Lower Direct Impact, High Resilience Value

```python
# Add circuit breaker to slow dependency
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(2), wait=wait_exponential(multiplier=0.1, max=1.0))
async def fetch_with_retry(query_func, *args, **kwargs):
    return await query_func(*args, **kwargs)

# Paginate all list endpoints
@router.get("/users/{user_id}/orders")
async def list_orders(
    user_id: int,
    offset: int = Query(0, ge=0),
    limit: int = Query(25, ge=1, le=100),
):
    return await db.paginated(Order, 
                               where=Order.user_id == user_id,
                               skip=offset, 
                               limit=limit)
```

## Decision Guide: Which Fix First?

| Evidence | Priority Fix |
|---|---|
| Query count/user jumped 5×+, repetitive query patterns in flamegraph | **Fix 1** (N+1 elimination) |
| Pool `checked_out` near `pool_size`, queues forming | **Fix 4** (pool tuning) + Fix 1 |
| `seq_scan >> idx_scan` on filtered tables | **Fix 2** (indexes) |
| `pg_stat_activity` shows blocking/waiting transactions | **Fix 6** (locking strategy) |
| Same response served repeatedly with expensive computation | **Fix 5** (caching) |
| Multiple independent queries firing serially | **Fix 3** (parallelize) |

When in doubt, start with **py-spy + pg_stat_statements** (Steps 2–3 above). Those two alone almost always distinguish between N+1, pool saturation, and lock contention within 30 minutes.
