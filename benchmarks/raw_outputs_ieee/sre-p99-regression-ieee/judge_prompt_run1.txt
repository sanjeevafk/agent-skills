### 1. Application-Level Query Tracing (Highest Signal)

**SQLAlchemy/asyncpg query logging.** Add a middleware that counts and timestamps every DB query per-request:

```python
import time
import asyncio
from starlette.middleware.base import BaseHTTPMiddleware
from prometheus_client import Counter, Histogram

query_counter = Counter("db_queries_total", "Total DB queries", ["endpoint", "method"])
query_duration = Histogram("db_query_duration_seconds", "Per-query duration")
queries_per_request = Histogram("queries_per_request", "Queries emitted per HTTP request")

class QueryCountMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        req_id = id(request)
        endpoint_queries: list[dict] = []

        # Hook into the connection's execute if using SQLAlchemy
        original_exec = None
        if hasattr(request.state, "db"):
            conn = request.state.db
            if hasattr(conn, "execute"):
                _original = conn.execute
                async def traced_exec(*args, **kwargs):
                    t0 = time.monotonic()
                    try:
                        result = await _original(*args, **kwargs)
                        return result
                    finally:
                        elapsed = time.monotonic() - t0
                        endpoint_queries.append({"elapsed_ms": round(elapsed*1000, 1)})

                conn.execute = traced_exec

        response = await call_next(request)

        duration_ms = round((time.perf_counter() - start) * 1000)
        n_queries = len(endpoint_queries)
        queries_per_request.labels(endpoint=request.url.path).observe(n_queries)

        if n_queries > 3:  # threshold for alerting
            slow = [q for q in endpoint_queries if q["elapsed_ms"] > 50]
            if slow:
                logger.warning(
                    "HIGH_QUERY_COUNT path=%s queries=%d slow_queries=%d "
                    "p50_estimate=%dms",
                    request.url.path, n_queries, len(slow),
                    min(q["elapsed_ms"] for q in endpoint_queries),
                )

        response.headers["X-DB-Queries"] = str(n_queries)
        response.headers["X-Request-Duration-Ms"] = str(duration_ms)
        return response
```

**What you'll see:** Endpoints where queries/request jumped from ~2–4 to ~20–100 are your N+1 culprit. You'll also see which specific queries are slow enough to push a request over 1 second.

```python
    from sqlalchemy.event import listens_for

    @listens_for(engine.pool, "checkout")
    def on_checkout(dbapi_conn, connection_record, connection_proxy):
        t0 = time.monotonic()
        record_checkout_start(connection_record, t0)

    @listens_for(engine.pool, "checkin")

        record_checkout_end(connection_record)
```

**How to distinguish N+1 vs pool saturation:**

| Observation | Diagnosis |
|---|---|
| More queries/request + pool idle stays near `pool_size` | **N+1** — new queries but pool isn't saturated |
| Fewer queries/request + pool idle at 0 + checkout_time high | **Pool saturation** — requests queuing for connections |
| More queries/request + pool idle at 0 + checkout_time high | **Both** — N+1 creates more demand, pool becomes bottleneck, tail explodes |
| Checkout time spikes only under load, not at low concurrency | **Lock contention** or network-latency amplified by concurrency |

```
Legend: Width = CPU time spent; Depth = Call stack depth

├── asyncio.run → main event loop          (narrow bar = mostly idle-waiting)
│  └── uvicorn.middleware ...               (thin)
│     └── FastAPI route handler             (moderate width)

│        ├── session.execute() x50          ← after: 50 sequential SELECTs = N+1
│        │   └── asyncpg.Connection.execute ← actual DB round-trip
│        └── json.dumps(response)           (thin = fast serialization)
```

**Interpretation:**
- A **wide vertical column of repeated `session.execute()` calls** stacked one below the other = N+1 queries doing sequential work
- A **wide block inside `_do_get()` / `QueuePool.get()`** = threads sitting in the pool wait queue (saturation)
- **Asyncio event loop showing sleep/yield** between queries = async I/O multiplexing (good); **no yields between queries** = suspicious sync wrapper blocking the event loop
- If most CPU is in `select()/poll()` inside asyncio selectors = waiting on socket readiness, not computation

# Performance Investigation: FastAPI p99 Regression

## Problem Statement

p50 stable at ~80-85ms while p99 jumped from 210ms to 1900ms (~9x). CPU and memory flat. DB connection count and queries-per-request both spiked. This is a textbook **tail-latency explosion** caused by something that only blocks under specific conditions — not a systemic resource exhaustion.

---

## Root Cause Hypotheses (Ranked)

### H1: N+1 Query Pattern Introduced (Most Likely)

The queries-per-request spike directly points here. A new join was removed, a subquery wasn't batched, or list endpoints started fetching related records one-at-a-time inside loops.

**Why it explains the data:**
- p50 unaffected: most requests hit simple paths or cache hits
- p99 explodes: once you trigger the N+1 path (e.g., paginated list + eager load missing), each extra query adds ~10-50ms in round-trip time
- Connection count spikes: more concurrent in-flight queries = more pooled connections
- CPU flat: waiting on the database, not doing computation

### H2: Connection Pool Saturation Under Burst

Pool size may be undersized relative to new query volume. When all connections are occupied waiting on slow queries, new requests queue behind pool checkout.

**Why it partially fits:**
- Explains p99 spike and connection count increase
- But wouldn't explain queries-per-request spike unless combined with H1

### H3: Lock Contention / Advisory Locks

Some write path introduced table-level locks or `SELECT FOR UPDATE` that serializes reads.

**Less likely:** would show as increased wait events, usually also bumps CPU context-switch overhead.

### H4: Slow Query Becoming Common

A previously rare edge case now runs frequently due to changed data distribution or index loss.

### 1. Database Query Tracing (Immediate, Zero Overhead)

Attach SQLAlchemy event listeners or use middleware to log every query with timing:

```python
import time
import logging
from collections import defaultdict
from flask import Flask  # or fastapi equivalent

logger = logging.getLogger("query_trace")

class QueryProfiler:
    def __init__(self):
        self.request_queries = defaultdict(list)
        self._in_flight = {}

    def on_request_start(self, request_id):
        self._in_flight[request_id] = []

    def on_query_executed(self, request_id, sql, duration_ms, params_count=1):
        entry = {
            "sql": sql[:200],  # truncate long queries
            "duration_ms": round(duration_ms, 1),
            "params": params_count,
        }
        self._in_flight[request_id].append(entry)

    def on_request_end(self, request_id):
        queries = self._in_flight.pop(request_id, [])
        if not queries:
            return

        total_db_ms = sum(q["duration_ms"] for q in queries)
        query_count = len(queries)

        # Log structural info
        logger.warning(
            "REQ|%s|QPS=%d|DB_MS=%.1f|PCT=%.0f%%",
            request_id,
            query_count,
            total_db_ms,
            (total_db_ms / max(1, total_request_ms)) * 100,
        )

        # Detect N+1: multiple similar queries with different params
        self._detect_n_plus_1(queries, request_id)

    def _detect_n_plus_1(self, queries, request_id):
        """Group queries by canonical SQL (strip params) and find loops."""
        canonical = defaultdict(list)
        for q in queries:
            # Remove WHERE params to get template
            template = q["sql"].split("WHERE")[0].rstrip() if "WHERE" in q["sql"] else q["sql"].rstrip()
            canonical[template].append(q)

        for sql_template, occurrences in canonical.items():
            if len(occurrences) >= 3:
                logger.warning(
                    "N+1_DETECTED|%s|%s|REPEATS=%d|TOTAL_DB_MS=%.1f",
                    request_id,
                    sql_template[:120],
                    len(occurrences),
                    sum(o["duration_ms"] for o in occurrences),
                )
```

**Key signals to look for:**
- Same canonical SQL repeated 3+ times with varying parameters within a single request
- `total_db_ms > request_total_ms` (impossible without parallelism → sequential loop)
- Queries per request median vs p95 distribution shift

### 3. Connection Pool Metrics

Instrument the pool itself. For `SQLAlchemy + psycopg2`:

```python
from sqlalchemy.pool import Pool
import threading

class MonitoredPool:
    """Drop-in pool wrapper that tracks utilization in real-time."""
    
    def __init__(self, pool: Pool):
        self._pool = pool
        self._lock = threading.Lock()
        self._checkouts = 0
        self._checkins = 0
        self._checkout_times = []  # (timestamp, duration_ms)
        self._peak_size = pool.size()

    def checkout(self, *args, **kwargs):
        start = time.perf_counter()
        try:
            delegate = self._pool.checkout(*args, **kwargs)
            elapsed_ms = (time.perf_counter() - start) * 1000
            with self._lock:
                self._checkouts += 1
                self._checkout_times.append(elapsed_ms)
                # Keep last 10000
                if len(self._checkout_times) > 10000:
                    self._checkout_times = self._checkout_times[-5000:]
            return delegate
        except Exception:
            elapsed_ms = (time.perf_counter() - start) * 1000
            with self._lock:
                self._checkout_times.append(elapsed_ms)
            raise

    def checkin(self, *args, **kwargs):
        with self._lock:
            self._checkins += 1
        return self._pool.checkin(*args, **kwargs)

    @property
    def stats(self):
        with self._lock:
            times = sorted(self._checkout_times[-5000:])
            return {
                "checkouts": self._checkouts,
                "checkins": self._checkins,
                "checkout_p50": times[len(times)//2] if times else 0,
                "checkout_p99": times[int(len(times)*0.99)] if times else 0,
                "overflow_rate": (self._checkouts - self._checkins) / max(1, self._checkins),
            }
```

**Reading pool stats:**
- `checkout_p99 > 50ms` → pool saturated, connections busy
- `overflow_rate > 0.1` → sustained demand exceeds pool capacity
- If `checkout_p99` correlates with p99 request time → confirmed pool bottleneck

## 1. Root Hypothesis Space

The pattern is diagnostic:

| Metric | P50 | P99 | Signal |
|---|---|---|---|
| Latency | 80→85ms (+6%) | 210→1900ms (+800%) | **Tail-only degradation** — most requests fine, some get stuck |
| CPU, Memory | flat | flat | **Not compute-bound or leaky** — threads are idle, blocked on something |
| DB connections | spiked | — | Pool at or near max; new waits forming behind existing checkouts |
| Queries/request | spiked | — | More round-trips per request, likely N+1 or missing index |

Three mutually-exclusive-or-synergistic hypotheses:

- **H1: N+1 queries.** A single request now fires O(n) small queries instead of one JOIN. Under production cardinality, each extra round-trip adds ~5–15ms. With 20–50 extras, tail latencies explode as requests queue behind the DB.
- **H2: Connection pool saturation + lock contention.** Checkouts exceed pool size. Requests block waiting for `pool.acquire()`. P50 requests slip through before the pool fills; P99 requests arrive after enough checkouts to hit a wait.
- **H3: Both.** The deploy introduced N+1 *and* the query volume exhausts the pool faster, compounding the tail-latency spiral.

P99-only blowout with flat CPU almost always means **thread starvation behind a blocking resource** (DB connection acquire, lock wait). Pure N+1 without pool saturation typically degrades both P50 and P99 proportionally. The fact that P50 barely moved strongly suggests H2 (pool saturation) is the dominant mechanism, possibly triggered by H1 (N+1 creating more concurrent checkouts).

## Problem Statement

A Python FastAPI service regressed after deploy:
- **p50**: 80ms → 85ms (+6%) — barely noticeable
- **p99**: 210ms → 1900ms (+800%) — catastrophic tail latency
- CPU/memory: flat (rules out OOM, runaway compute)
- Dashboard signals: DB connections spiked, query count per request increased

This pattern screams **N+1 queries + connection pool exhaustion**. Few requests are dragging down the entire tail because connections are sitting blocked waiting for each other.

## Part 1: Detection — N+1 Query Pattern Identifiers

### N+1 Query Detector (SQLAlchemy Middleware)

```python
"""
sqlalchemy_n_plus_one_detector.py

Attach this to any FastAPI app using SQLAlchemy. Captures every SQL statement
per-request, identifies repetition patterns, computes queries-per-request
distribution, and flags suspected N+1 patterns.
"""

import time
import uuid
from collections import defaultdict
from dataclasses import dataclass, field
from typing import Optional


@dataclass
class SQLStatement:
    sql: str
    params: tuple
    duration_ms: float
    timestamp: float
    request_id: str


@dataclass
class RequestProfile:
    request_id: str
    endpoint: str
    method: str
    start_time: float
    end_time: float = 0.0
    status_code: int = 0
    statements: list[SQLStatement] = field(default_factory=list)
    total_duration_ms: float = 0.0

    @property
    def query_count(self) -> int:
        return len(self.statements)

    @property
    def unique_queries(self) -> set[str]:
        return {s.sql for s in self.statements}

    @property
    def total_query_time_ms(self) -> float:
        return sum(s.duration_ms for s in self.statements)

    def n_plus_one_score(self) -> float:
        """
        Heuristic score for N+1 probability.
        Returns 0.0–1.0 where >0.7 indicates likely N+1.

        Logic: if many identical parameterized queries execute with different
        parameter values within a single request, flag it.
        """
        if not self.statements:
            return 0.0
        # Group by normalized SQL (strip param markers)
        by_template = defaultdict(list)
        for stmt in self.statements:
            template = _normalize_template(stmt.sql)
            by_template[template].append(stmt.params)
        # Check templates that fire multiple times with distinct params
        suspicious = 0
        for template, param_groups in by_template.items():
            if len(param_groups) > 3:  # more than 3 executions
                distinct_params = set(
                    _hash_params(pg) for pg in param_groups
                )
                if len(distinct_params) > 2:  # different inputs each time
                    suspicious += len(param_groups)
        # Ratio of suspicious queries to total
        return min(suspicious / max(len(self.statements), 1), 1.0)

    def deduplicated_query_time_savings(self) -> float:
        """Estimate how much time we'd save if we batched repeated queries."""
        by_template = defaultdict(list)
        for stmt in self.statements:
            by_template[_normalize_template(stmt.sql)].append(stmt)
        savings = 0.0
        for template, stmts in by_template.items():
            if len(stmts) > 3:
                # Keep first execution, eliminate rest
                savings += sum(s.duration_ms for s in stmts[1:])
        return savings


def _normalize_template(sql: str) -> str:
    import re
    sql = re.sub(r"\?\s*", "?", sql)
    sql = re.sub(r":\w+", ":", sql)
    sql = re.sub(r"\d+", "?", sql)
    return sql.strip().upper()[:120]


def _hash_params(params: tuple) -> str:
    return str(params)


# ── Global state for request tracking ──────────────────────────────
_request_profiles: dict[str, RequestProfile] = {}
_endpoint_cache: dict[int, str] = {}


def get_active_profile(request_id: str) -> Optional[RequestProfile]:
    return _request_profiles.get(request_id)


def record_statement(
    request_id: str,
    sql: str,
    params: tuple,
    duration_ms: float,
):
    profile = _request_profiles.get(request_id)
    if profile is None:
        return
    profile.statements.append(SQLStatement(
        sql=sql,
        params=params,
        duration_ms=duration_ms,
        timestamp=time.monotonic(),
        request_id=request_id,
    ))


def begin_request(request_id: str, endpoint: str, method: str):
    _request_profiles[request_id] = RequestProfile(
        request_id=request_id,
        endpoint=endpoint,
        method=method,
        start_time=time.monotonic(),
    )


def end_request(
    request_id: str,
    status_code: int,
    endpoint: Optional[str] = None,
):
    profile = _request_profiles.pop(request_id, None)
    if profile is None:
        return
    profile.end_time = time.monotonic()
    profile.status_code = status_code
    profile.total_duration_ms = (profile.end_time - profile.start_time) * 1000
    if endpoint:
        profile.endpoint = endpoint


def summarize_recent(n: int = 50) -> list[dict]:
    profiles = sorted(_request_profiles.values(), key=lambda p: p.end_time)[-n:]
    results = []
    for p in profiles:
        results.append({
            "request_id": p.request_id,
            "endpoint": p.endpoint,
            "status_code": p.status_code,
            "total_duration_ms": round(p.total_duration_ms, 2),
            "query_count": p.query_count,
            "unique_queries": len(p.unique_queries),
            "query_time_ms": round(p.total_query_time_ms, 2),
            "n_plus_one_score": round(p.n_plus_one_score(), 3),
            "dedup_savings_ms": round(p.deduplicated_query_time_savings(), 2),
        })
    return results
```

### Connection Pool Metrics — asyncpg / SQLAlchemy QueuePool Instrumentation

```python
from sqlalchemy.pool import QueuePool
import asyncio

class InstrumentedQueuePool(QueuePool):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self._stats = {"checkout_count": 0, "checkout_timeouts": 0,
                       "active": 0, "idle": 0, "max_reached": False}
        self._lock = asyncio.Lock()
    
    @property
    def stats(self):
        return dict(self._stats)
    
    def _checkout(self, pool, conn=None, record=None, timeout=None):
        start = time.monotonic()
        try:
            result = super()._checkout(pool, conn, record, timeout)
            self._stats["checkout_count"] += 1
            self._stats["active"] = self._checkedout
            self._stats["idle"] = self.size() - self._checkedout
            return result
        except Exception as e:
            self._stats["checkout_timeouts"] += 1
            raise
    
    def _return(self, pool, conn):
        self._stats["active"] = max(0, self._checkedout - 1)
        self._stats["idle"] += 1
        super()._return(pool, conn)
```

Here's the diagnostic tree:

```

         │
         ├─ Queries per request distribution?
         │   ├─ Most requests still low, long tail has 50-500 queries

         │      (single endpoint doing SELECT in a loop)

         │   ├─ ALL requests uniformly 2-10x more queries than baseline
         │   └→ BROKEN EAGER LOADING or missing index causing full table scans
```

```sql
    blocking.pid AS blocking_pid,
    blocking.query AS blocking_query,
    age(now(), blocking.xact_start) AS lock_wait_duration

JOIN pg_stat_activity blocked ON blocked.pid = blocked_locks.pid
JOIN pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_stat_activity blocking ON blocking.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```
