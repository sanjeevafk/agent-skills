## 1. Root Hypothesis Space

The pattern is diagnostic:

| Metric | P50 | P99 | Signal |
|---|---|---|---|
| Latency | 80→85ms (+6%) | 210→1900ms (+800%) | **Tail-only degradation** — most requests fine, some get stuck |
| CPU, Memory | flat | flat | **Not compute-bound or leaky** — threads are idle, blocked on something |
| DB connections | spiked | — | Pool at or near max; new waits forming behind existing checkouts |
| Queries/request | spiked | — | More round-trips per request, likely N+1 or missing index |

Three mutually-exclusive-or-synergistic hypotheses:

- **H1: N+1 queries.** A single request now fires O(n) small queries instead of one JOIN. Under production cardinality, each extra round-trip adds ~5–15ms. With 20–50 extras, tail latencies explode as requests queue behind the DB.
- **H2: Connection pool saturation + lock contention.** Checkouts exceed pool size. Requests block waiting for `pool.acquire()`. P50 requests slip through before the pool fills; P99 requests arrive after enough checkouts to hit a wait.
- **H3: Both.** The deploy introduced N+1 *and* the query volume exhausts the pool faster, compounding the tail-latency spiral.

P99-only blowout with flat CPU almost always means **thread starvation behind a blocking resource** (DB connection acquire, lock wait). Pure N+1 without pool saturation typically degrades both P50 and P99 proportionally. The fact that P50 barely moved strongly suggests H2 (pool saturation) is the dominant mechanism, possibly triggered by H1 (N+1 creating more concurrent checkouts).

- `psycopg2.pool.ThreadedConnectionPool.getconn` → actual checkout wait

If you see a visible "pyramid" of async task creation above a blocking call at the base, that's the smoking gun for a pool/thread-starvation chain.

### Query Tracing: Middleware + DB Logging

```python
import time
import logging
from starlette.middleware.base import BaseMiddleware
from fastapi import Request

logger = logging.getLogger("query_trace")

class QueryTraceMiddleware(BaseMiddleware):
    """Captures per-request SQL query log for N+1 detection."""
    
    def __init__(self, app, sample_rate=1.0, db_pool=None):
        super().__init__(app)
        self.sample_rate = sample_rate
        self.db_pool = db_pool  # optional: also read pool stats
    
    async def dispatch(self, request: Request, call_next):
        start = time.perf_counter_ns()
        
        # Hook into the DB driver if possible (see below for psycopg2 hook)
        query_log = []
        
        try:
            response = await call_next(request)
            
            elapsed_ms = (time.perf_counter_ns() - start) / 1e6
            
            # Log summary at INFO level
            logger.info(
                "| %-30s | %5d ms | %4d queries | path=%s",
                f"{request.method} {request.url.path}",
                elapsed_ms,
                len(query_log),
                request.url.path,
            )
            
            # Sample full query details for P99-tier requests
            if elapsed_ms > 500:
                total_sql_time = sum(q["duration_ms"] for q in query_log)
                sorted_queries = sorted(query_log, key=lambda q: q["duration_ms"], reverse=True)
                logger.warning(
                    "SLOW REQUEST DETAIL: method=%s path=%s p99_candidate=true "
                    "total_sql_ms=%.1f avg_query_ms=%.1f query_count=%d",
                    request.method, request.url.path,
                    total_sql_time,
                    total_sql_time / max(len(query_log), 1),
                    len(query_log),
                )
                for i, q in enumerate(sorted_queries[:50]):
                    logger.warning(
                        "  [%02d] sql=%s duration=%.1fms rows_affected=%s",
                        i, q["sql"][:200], q["duration_ms"], q.get("rows"),
                    )
            
            return response
            
        except Exception:
            logger.exception("request error path=%s", request.url.path)
            raise

# Install: app.add_middleware(QueryTraceMiddleware, sample_rate=0.1)
```

Custom pool wrapper to instrument everything:

```python
from contextlib import contextmanager
import time

class InstrumentedPool:
    """Thin wrapper around asyncpg.pool.Pool or sqlalchemy.pool that emits metrics."""
    
    def __init__(self, pool, metrics_registry=None):
        self._pool = pool
        self.registry = metrics_registry
    
    @property
    def status(self):
        s = self._pool.status()  # asyncpg returns "open"/"closed"
        size = self._pool.get_size()
        size = getattr(s, 'size', size)
        free = getattr(s, 'idle', self._pool.get_idle_size())
        return {"size": size, "idle": free, "busy": size - free}
    
    @contextmanager
    def acquire_with_timing(self):
        acquire_start = time.perf_counter()
        conn = self._pool.acquire()
        wait_seconds = time.perf_counter() - acquire_start
        
        if self.registry and wait_seconds > 0.01:
            db_pool_acquisitions_wait.observe(wait_seconds)
            db_pool_acquisitions.inc()
        
        if wait_seconds > 0.1:
            import logging
            logging.warning(f"POOL ACQUIRE WAIT: {wait_seconds:.3f}s")
        
        try:
            yield conn
        finally:
            self._pool.release(conn)
```

## 3. Diagnosing the Pattern: N+1 vs Pool Saturation vs Lock Contention

Apply this decision matrix to the gathered data:

| Observation | Diagnosis |
|---|---|
| Flame graph shows many async tasks spawned from one handler, each doing a small DB call | **N+1** |
| Query trace shows 1 path emitting 15–50 queries sequentially, each <5ms | **N+1** |
| Multiple requests firing ~5–10 identical small queries in parallel to the same table | **N+1 cascade** |
| Flame graph shows threads blocked at `acquire()` with `await asyncio.lock.acquire()` stacks | **Lock contention** |
| `getconn()` wait times clustered right at pool.max seconds | **Pool saturation** |
| Prometheus: `db_pool_waiters` stays >0 for extended periods; `pool_acquisitions` histograms peak at 100–500ms bucket | **Pool saturation** |
| Pool size = max_connections × 0.9; active ≈ pool max on P99 requests | **Pool saturation** |
| All slow requests target 1–2 paths; healthy paths unaffected | **N+1 in specific endpoint** |
| ALL paths affected equally (including simple health checks hitting DB) | **Pool saturation / global lock** |
| `pg_stat_activity` shows many transactions at "idle in transaction" | **Long-lived txns starving pool** |
| `pg_locks` shows lock waits (>0 rows in `wait_event_type = 'Lock'`) | **Row/table lock contention** |

Confirmatory experiment: temporarily double the pool size (`pool_size=40` → `80`). If P99 drops back toward baseline immediately → confirmed pool saturation. If no change → N+1 without pool exhaustion (unlikely given dashboard signals, but possible).

Another test: add explicit `LIMIT` guards to suspicious queries in the traced endpoints. If the P99 distribution tightens significantly → confirms N+1 scaling with result set size.

## 4. Reading the Flame Graph

Navigate the py-spy/speedscope output with this reading order:

1. **Identify the longest axis first** — thick horizontal bands represent high sampling density. The widest node at the bottom tells you what the thread was doing most often.
2. **Count async task frames above blocking calls** — if you see a single handler frame spawning 20+ child task frames above it, that's your N+1 fan-out.
3. **Look at the very bottom tip** — if the leaf node is `asyncio.Lock.acquire` or `psycopg2.pool.ConnectionPool.getconn` sleeping/waiting, everything above is "blocked waiting for X."
4. **Check for duplicate subtrees** — two nearly identical branch structures under different handlers means two different endpoints share the same problematic pattern.
5. **Find "hot spots"** — blue-to-red gradient (depending on renderer). Red means >50% of wall-clock time spent in that function.
6. **Spot thread gaps** — dead space between thread activity means the thread was blocked (waiting), not idle (doing nothing). In GIL-based Python, a thread stopped producing frames because it's waiting on I/O or a futex, not because Python has work scheduled elsewhere.

Example flame graph interpretation:
```
                     ┌─ main_task_runner
                     │  ├─ /api/v1/items (handler)         ← entry point
                     │  │  ├─ ORM query: SELECT users...     ← 8ms sync
                     │  │  ├─ async task fetch_orders        ← spawned
                     │  │  ├─ async task fetch_items          ← spawned (×15)
                     │  │  │    └─ psycopg2.connect/getconn    ← LEAF: 120ms average wait
                     │  │  └─ async task fetch_categories     ← spawned
                     │  │     └─ psycopg2.getconn              ← same leaf
                     │  └─ /api/v1/reports (concurrent)      ← overlapping
                     │     └─ same pattern                   ← confirming N+1 cascade
├─ gevent_hub.wait                                    ← greenlet scheduler (if used)
└─ select.select                                      ← reactor polling
```

Interpretation: 15+ concurrent task spawns above a `getconn` leaf with high sampling = N+1 causing pool pressure. The fix is either batch those N+1 calls (one query replaces 15) or increase pool_size so each doesn't queue.

## 5. Proposed Fixes Ranked by Expected P99 Impact

### Rank 1: Fix N+1 Query Fan-out (Expected P99 reduction: 60–80%)
**Highest impact — removes the root cause of concurrent pool consumption.**

Identify the offending query loop from the trace data, then refactor to eager loading or JOINs:

```python
# BEFORE: N+1 pattern in ORM
for user in users:
    orders = session.query(Order).filter_by(user_id=user.id).all()
    items = session.query(Item).join(Order).filter(Order.user_id == user.id).all()

# AFTER: Single-query batch using IN clause + prefetch
user_ids = [u.id for u in users]
orders = session.query(Order).filter(Order.user_id.in_(user_ids)).all()
items = session.query(Item).join(Order).filter(Order.user_id.in_(user_ids)).all()
# Group results in Python instead of per-user queries
orders_by_user = defaultdict(list)
for o in orders:
    orders_by_user[o.user_id].append(o)
```

```python
         .filter(...).all())
```

### Rank 2: Connection Pool Tuning (Expected P99 reduction: 20–40%)
**Quick win — reduces tail latency from queue waits without code changes.**

Current likely configuration (default fastapi/starlette/sqlalchemy settings):
```python
# DEFAULT: very conservative
pool_size=5, max_overflow=10, pool_timeout=30
# Total max = 15. With 20 VUs, you're already overcommitted.
```

Recommended staging-to-prod sizing:
```python
pool_size=max_concurrent_connections * 0.7,      # reserve headroom
max_overflow=max_concurrent_connections * 0.5,     # burst allowance
pool_timeout=5,                                     # fail fast instead of 30s hangs
pool_recycle=1800,                                  # reconnect stale sessions
pool_pre_ping=True,                                 # detect dead connections
```

Calculate `max_concurrent_connections`:
```
VUs = 50 (peak observed)
Each request checks out 1 connection
Concurrency factor (overlapping requests) ≈ 2–3
max_concurrent = VUs * concurrency = 150
pool_size ≈ 100–110
max_overflow ≈ 40–50
Total allowed = 140–160 (under your Postgres max_connections)
```

With `pool_timeout=5`, failing requests get a clear `TimeoutError` instead of 30-second hangs that pile up in the async task queue and inflate P99 to 1900ms.

### Rank 3: Add Missing Indexes (Expected P99 reduction: 10–30%)
**Targeted to the slowest individual queries revealed by the trace.**

From `pg_stat_statements`, pick the top 3 slowest queries identified in the trace and verify indexes:

```sql
-- Find queries with high mean_exec_time but low rows returned
-- These likely lack proper indexes
SELECT 
    query,
    calls,
    mean_exec_time AS avg_ms,
    total_exec_time / 1000 / calls AS total_seconds_per_call,
    shared_blks_hit / NULLIF(shared_blks_read, 0) AS cache_ratio
FROM pg_stat_statements
WHERE dbid = current_database()::oid
    AND query !~ '^DISCARD|^COMMIT|^ROLLBACK'
ORDER BY total_exec_time DESC
LIMIT 10;

-- For each slow query, verify it uses an index
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = $1 ORDER BY created_at DESC;

-- Look for "Seq Scan" in the output — that's a missing index
-- Create the recommended index
CREATE INDEX CONCURRENTLY idx_orders_user_id_created_at 
    ON orders (user_id, created_at DESC);
```

Prioritize indexes on columns used in:
- WHERE clauses of the highest-frequency queries
- JOIN keys between tables with >100k rows
- ORDER BY columns that force disk sorts

### Rank 4: Response-Level Caching (Expected P99 reduction: 5–15%)
**Reduces query count at the HTTP layer for repeat requests.**

```python
from functools import lru_cache
from redis.asyncio import Redis

redis = Redis.from_url("redis://cache:6379/0", decode_responses=True)

@lru_cache(maxsize=256)
def _cached_dashboard_data(cache_key: str) -> dict:
    """In-process LRU for sub-second dedup within one worker."""
    return fetch_from_db(cache_key)

async def get_dashboard(key: str):
    cached = await redis.get(f"dash:{key}")
    if cached:
        return json.loads(cached)
    
    data = _cached_dashboard_data(key)
    await redis.setex(f"dash:{key}", 60, json.dumps(data))  # 60s TTL
    return data
```

### Rank 5: Request-Level Timeouts & Circuit Breakers (Expected P99 improvement: defensive)
**Prevents cascades — does not reduce latency but prevents worst-case tails.**

```python
class TimeoutMiddleware(BaseMiddleware):
    """Hard timeout per request to prevent tail amplification."""
    
    def __init__(self, app, timeout=5.0):
        super().__init__(app)
        self.timeout = timeout
    
    async def dispatch(self, request: Request, call_next):
        try:
            response = await asyncio.wait_for(
                call_next(request),
                timeout=self.timeout
            )
            return response
        except asyncio.TimeoutError:
            return JSONResponse(
                status_code=504,
                content={"detail": "Request timed out"},
            )
```
