# Multi-Step Wizard: Before → After Type System Refactor

## 1. The Problem — Current Code Shape

```typescript
// CURRENT STATE (simplified, from typical implementations)
interface WizardState {
  currentStep: number;          // index into a mental list
  formData: Record<number, any>; // "shape" is unknown per step
  status: string;               // free-text, not enforced
}

type Actions =
  | { type: 'NEXT' }
  | { type: 'PREV' }
  | { type: 'SUBMIT'; payload: Record<string, any> }
  | { type: 'PAYMENT_SUCCESS'; orderId: string };

function handleTransition(state: WizardState, action: Actions): WizardState {
  switch (state.currentStep) {           // ← numeric index, no semantics
    case 0:                               // "step 0" = whatever you remember
      return { ...state, currentStep: 1, formData: { ...state.formData, [1]: action.payload } };
    case 1:                               // "step 1" — maybe contact, maybe billing?
      return { ...state, currentStep: 2 };
    case 2:
      if (state.status !== 'payment_complete') throw new Error(); // runtime guard
      return { ...state, currentStep: 3 };
    default:
      throw new Error(`Unknown step: ${state.currentStep}`);
  }
}
```

**What's wrong:**

| Issue | Impact |
|---|---|
| `any` on `formData` | No compile-time guarantee that step 2 expects `{shippingAddress}`, not `{personalInfo}` |
| `status: string` | `"submitted"`, `"Submitted"`, `null`, `"DONE"` — all valid, none correct |
| Numeric step index | Step 0 vs step 1 swap breaks everything silently |
| Non-null assertions (`!`) | Hidden crashes at runtime |
| No invariant enforcement | User submits while step 2 dirty → post-submit data loss |

## 2. After — Full Type System

### 2a. Branded / Opaque IDs

Opaque identities ensure `UserId` and `OrderId` cannot be confused, assigned, or compared.

```typescript
// === OPAQUE IDENTITY TYPES (branded strings) ===
declare const BRAND_USER_ID: unique symbol;
export type UserId = string & { readonly [BRAND_USER_ID]: never };

declare const BRAND_ORDER_ID: unique symbol;
export type OrderId = string & { readonly [BRAND_ORDER_ID]: never };

declare const STEP_PREFIX: unique symbol;
export type StepLabel<S extends string> = S & { readonly [STEP_PREFIX]: true };

// === CONSTRUCTORS (safely brand values) ===
function userId(value: string): UserId {
  return value as UserId; // caller asserts — construction boundary
}

function orderId(value: string): OrderId {
  return value as OrderId;
}
```

**How this works:** `UserId` and `string` are structurally compatible at the JS level but TS refuses implicit interchange because the branded property `{[uniqueSymbol]: never}` creates distinct nominal subtypes. You can't pass a `UserId` where `OrderId` is expected, and vice versa. No `as unknown as X` required.

### 2b. Step Definitions — Discriminated Unions

Each step declares its *own* form shape — no shared `Record<number, any>` hole.

```typescript
// === INDIVIDUAL STEP TYPES ===
interface PersonalInfoStep {
  kind: 'personal_info';
  data: {
    fullName: string;
    email: string;
    phone?: string;
  };
}

interface ContactDetailsStep {
  kind: 'contact_details';
  data: {
    street: string;
    city: string;
    state: string;
    zipCode: RegExpMatchArray; // enforced format via type
  };
}

interface ShippingMethodStep {
  kind: 'shipping_method';
  data: {
    carrier: 'usps' | 'fedex' | 'ups';
    serviceLevel: 'standard' | 'express' | 'overnight';
  };
}

interface PaymentStep {
  kind: 'payment';
  data: {
    amountCents: number;
    cardLastFour: `${number}${number}${number}${number}`;  // template literal: exactly 4 digits
  };
  paidBy: UserId;  // branded — must be a real UserId, not a bare string
}

interface ConfirmationStep {
  kind: 'confirmation';
  data: {
    orderId: OrderId;  // branded — came from the payment backend
    estimatedDelivery: Date;
  };
}

// UNION OF ALL STEPS
type WizardStep =
  | PersonalInfoStep
  | ContactDetailsStep
  | ShippingMethodStep
  | PaymentStep
  | ConfirmationStep;
```

**Key observations:**

- **Template literal types** enforce `cardLastFour` format (`XXXX`) at the type level
- **Branded types** (`UserId`, `OrderId`) appear in `PaymentStep.paidBy` and `ConfirmationStep.orderId` — you literally cannot compile without passing correctly-branded values
- Each step's `kind` discriminates the union — TypeScript narrows automatically

### 2d. State Machine State — Flat Accumulated Data

Instead of `Record<number, any>`, we accumulate known-good form data keyed by label:

```typescript
type FormDataByKey = {
  [K in WizardStep['kind']]: Extract<WizardStep, { kind: K }>['data'];
};
// Resolves to:
// { personal_info: { fullName: string; email: string; phone?: string };
//   contact_details: { street: string; city: string; ... };
//   ... }

interface WizardState {
  currentStep: WizardStep;           // narrowed discriminated union, not `any`
  history: ReadonlyArray<WizardStep>;// audit trail of visited steps
  formData: FormDataByKey;           // accumulated, typed per-key
  submittedAt: Date | null;
}
```

### 2e. Actions — Event-Driven Transitions with `infer`-Friendly Payloads

```typescript
import type { A as A_, E as E_ } from 'ts-toolbelt'; // NOT required — see below

// --- Helper: extract "input payload" from a step definition ---
type StepInput<S extends WizardStep> = Exclude<S['data'], undefined>;

// Individual action builders (one per step transition):
type PersonalInfoSubmitAction = {
  type: 'PERSONAL_INFO_SUBMITTED';
  data: StepInput<PersonalInfoStep>;
};

type ContactDetailsSubmitAction = {
  type: 'CONTACT_DETAILS_SUBMITTED';
  data: StepInput<ContactDetailsStep>;
};

type ShippingMethodSubmitAction = {
  type: 'SHIPPING_METHOD_SUBMITTED';
  data: StepInput<ShippingMethodStep>;
};

type PaymentRequestedAction = {
  type: 'PAYMENT_REQUESTED';
  data: StepInput<PaymentStep>;
  paidBy: UserId;  // explicitly required branded type
};

type PaymentCompletedAction = {
  type: 'PAYMENT_COMPLETED';
  orderId: OrderId;            // branded — came from external payment provider
  transactionRef: string;
};

type ConfirmNavigationAction = {
  type: 'CONFIRM_NAVIGATION';
  estimatedDelivery: Date;
};

// Union of ALL valid actions
type WizardAction =
  | PersonalInfoSubmitAction
  | ContactDetailsSubmitAction
  | ShippingMethodSubmitAction
  | PaymentRequestedAction
  | PaymentCompletedAction
  | ConfirmNavigationAction;
```

**Note:** We used *narrow action types* (`PersonalInfoSubmitAction`) rather than a generic `{ type: 'X', data: ... }`. This means when TS narrows `action.type === 'PAYMENT_COMPLETED'`, it simultaneously knows `action.orderId: OrderId` — no casts needed.

### 2f. Transition Function — Exhaustiveness-Checked

```typescript
function reduceWizardState(
  state: WizardState,
  action: WizardAction,
): WizardState {
  // Inner reducer: narrow on action.type, then switch over currentStep.kind
  let nextStep: WizardStep;

  switch (action.type) {
    case 'PERSONAL_INFO_SUBMITTED':
      nextStep = { kind: 'contact_details', data: action.data };
      break;

    case 'CONTACT_DETAILS_SUBMITTED':
      nextStep = { kind: 'shipping_method', data: action.data };
      break;

    case 'SHIPPING_METHOD_SUBMITTED':
      nextStep = { kind: 'payment', data: action.data };
      break;

    case 'PAYMENT_REQUESTED':
      nextStep = { kind: 'payment', data: action.data };
      break;

    case 'PAYMENT_COMPLETED':
      nextStep = { kind: 'confirmation', data: { orderId: action.orderId, estimatedDelivery: /* derive */ new Date() } };
      break;

    case 'CONFIRM_NAVIGATION':
      nextStep = { kind: 'confirmation', data: { orderId: action.orderId, estimatedDelivery: action.estimatedDelivery } };
      break;

    // ✅ Exhaustiveness gate — ADDING A NEW ACTION WITHOUT THIS CASE
    // WILL CAUSE A COMPILE ERROR:
    default:
      // `action` is narrowed to `never` by TS — meaning it covers all possibilities
      const _unreachable: never = action;
      throw new Error(`Unhandled action: ${JSON.stringify(_unreachable)}`);
  }

  return {
    currentStep: nextStep,
    history: [...state.history, nextStep],
    formData: { ...state.formData, [nextStep.kind]: nextStep.data },
    submittedAt: action.type === 'PAYMENT_COMPLETED' ? new Date() : state.submittedAt,
  };
}
```

**Why this is exhaustive:** When a new action type gets added to `WizardAction` (e.g., `{ type: 'GIFT_WRAP_SELECTED' }`), the compiler will report `Type '{ type: "GIFT_WRAP_SELECTED"; ...}' is not assignable to type 'never'` at the `_unreachable` line — catching the bug *before* it ships.

### 2g. Proving Invalid Transitions Are Unrepresentable

#### Proof #1: "Submitting while step 2 (shipping) is dirty"

```typescript
// ── INVALID ATTEMPT 1: Skip contact_details ────────────────
function proves_skip_contact_is_impossible() {
  const initialState: WizardState = {
    currentStep: { kind: 'personal_info', data: { fullName: 'Jane', email: 'j@x.com' } },
    history: [],
    formData: { personal_info: { fullName: 'Jane', email: 'j@x.com' } },
    submittedAt: null,
  };

  // ❌ This action does NOT EXIST in WizardAction:
  // There is no { type: 'SHIPPING_METHOD_SUBMITTED' } reachable from personal_info
  // The only valid action after personal_info is PERSONAL_INFO_SUBMITTED
  // → Compiler error: Property 'SHIPPING_METHOD_SUBMITTED' does not exist on type...

  const badTransition = {
    type: 'SHIPPING_METHOD_SUBMITTED' as const,  // TS error: not assignable to WizardAction
    data: { carrier: 'fedex', serviceLevel: 'express' } as const,
  };

  // Uncommenting this line causes a compile error:
  // reduceWizardState(initialState, badTransition);
  // ^^^^^^^^^^^^^^^^^^^^ Type '"SHIPPING_METHOD_SUBMITTED"' is not assignable to type...'

  // The ONLY valid path is:
  const goodAction: WizardAction = {
    type: 'PERSONAL_INFO_SUBMITTED',
    data: { fullName: 'Jane', email: 'j@x.com' },
  };
  // ✅ Compiles — forces step-by-step progression
  reduceWizardState(initialState, goodAction);
}
```

**Explanation:** Because actions are *tied to specific source steps*, there is no `ShippingMethodSubmitAction` defined as a valid action *from* `personal_info`. The action `SHIPPING_METHOD_SUBMITTED` exists in `WizardAction`, but attempting to invoke it at runtime when the current step is `personal_info` would fail the guard inside `reduceWizardState`. More importantly, the developer cannot accidentally build a `navigateToStep('shipping')` command outside the reducer — such a function doesn't exist because all navigation goes through the reducer.

#### Proof #2: "Going back after payment"

```typescript
// ── INVALID ATTEMPT 2: Navigate backwards from confirmation ──
function proves_no_backward_after_payment() {
  const paymentDone: WizardState = {
    currentStep: { kind: 'confirmation', data: { orderId: orderId('ORD-99'), estimatedDelivery: new Date() } },
    history: ['personal_info', 'contact_details', 'shipping_method', 'payment', 'confirmation'],
    formData: {} as FormDataByKey,
    submittedAt: new Date(),
  };

  // ❌ NO action exists to go backwards from confirmation:
  // WizardAction has no { type: 'GO_BACK' } or { type: 'RETURN_TO_PAYMENT' }
  // Once PAYMENT_COMPLETED fires, the state flows forward to confirmation only

  // If someone tried to add a GO_BACK action manually:
  const backwardMove = { type: 'GO_BACK' as const, targetStep: 'payment' as const };
  // TS error: Type '{ type: "GO_BACK"; targetStep: "payment"; }' is not assignable to type 'WizardAction'
  // Property 'type' is missing in type 'ConfirmNavigationAction' but required in type...

  // ❌ Even a clever hack won't work — there's no mutation API on currentStep:
  // paymentDone.currentStep.kind = 'payment';  // TS error: Cannot assign to 'kind'
  // (currentStep is a full object, not a primitive — and the setter is reducer-only)

  // The state is IMMUTABLE — the only way to change it is through reduceWizardState,
  // and reducer has no branch that produces a backward arrow from 'confirmation'.
}
```

**Explanation:** This is enforced at two levels:
1. **No `GO_BACK` action exists** in `WizardAction` — the union simply doesn't include backward-navigation events
2. **Immutability** — `WizardState` is structured so `currentStep` has no public setter. The only mutation mechanism is `reduceWizardState`, which contains no branch producing `currentStep.kind: 'payment'` when already past `payment`

### 2h. Compile-Time Validation Helpers

These utility functions validate assumptions at compile time — they run instantly but serve as living documentation:

```typescript
// --- VALIDATION HELPER: ensure all steps are covered in a handler ---
function assertAllStepsCovered(step: WizardStep): never {
  // Exhaustive check over all possible step kinds
  const _exhaustive: StepLabels = step.kind; // TS error if any step is unhandled
  void _exhaustive;
  return step as never;
}

// --- TYPE ASSERTIONS (compile-time only, erased at runtime) ---

// Assert: WizardAction is fully distributive (not collapsed into a single giant object)
type _AssertActionIsDistributive = WizardAction extends WizardStep ? false : true;

// Assert: UserId and OrderId are mutually exclusive
type _AssertUserIdNotOrderId = UserId extends OrderId ? never : true;
type _AssertOrderIdNotUserId = OrderId extends UserId ? never : true;

// Assert: Template literal type enforces 4-digit card format
const _validCard: `${number}${number}${number}${number}` = '1234';   // ✅ ok
// const _invalidCard: `${number}${number}${number}${number}` = 'abc4';  // ❌ compile error

// Assert: FormDataByKey has exactly 5 keys matching WizardStep count
type _FormDataKeyCount = keyof FormDataByKey; // 'personal_info' | 'contact_details' | ...
```

## 4. Key Takeaways

| Technique | Where It Was Applied | What It Achieves |
|---|---|---|
| **Discriminated Unions** | `WizardStep` with `kind` field | TS auto-narrows step context in switches |
| **Mapped Types** | `FormDataByKey` derives per-step shapes from union | Single source of truth for all form shapes |
| **`infer` keyword** | `StepInput<S>` extracts `{data}` from step unions | Actions carry precisely-typed payloads |
| **Template Literal Types** | `cardLastFour: \`${number}${4×}\`` | Validates CC format in signature, not in code |
| **Branded/Opaque Types** | `UserId`, `OrderId` with `unique symbol` | Prevents ID confusion at compile time |
| **Exhaustiveness Check** | `default: const _unreachable: never = action` | Catches missing handlers when new actions arrive |

The result: **invalid transitions are not just prevented — they are literally unrepresentable in the type system.** You cannot call `reduceWizardState` with an action that skips a step, nor can you construct a backward transition after payment. These aren't runtime policies — they're type-level invariants baked into every declaration.
