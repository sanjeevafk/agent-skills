## Analysis

The current design lets the compiler and the runtime both fail to catch invalid transitions because everything is `string` + `any`. The fix requires:

1. **Discriminated union** — every `WizardState` carries a `step` literal tag, making illegal states unrepresentable (e.g., you can't be "at checkout" and "payment pending" simultaneously).
2. **Per-step payload inference** — each step variant carries only the fields it actually needs. Step 2 *requires* address data; submit won't compile without it.
3. **Branded IDs** — `UserId` and `OrderId` can never be confused because the brand (`unique symbol`) disappears at runtime but not at the type level.
4. **Event-driven transitions** — a pure function maps `(state, event) → nextState` via a total function over every `(step, event)` pair, ending with a `never` check that forces the compiler to reject new events unless we add a transition.
5. **Compile-time proofs** — the two invalid transitions don't even type-check, let alone run.

## Before / After

### BEFORE — `any` + casts

```typescript
interface WizardState {
  userId: string;        // no guarantee this is a UserId
  orderId: string | null;// could be null or any string
  status: string;        // opaque string — anything goes
  stepData: any;         // nobody knows what's here
  isSubmitting: boolean;
}

// Guard relies on runtime checks + casts
function handleAction(state: WizardState, action: Action): WizardState {
  if (state.status === 'shipping' && action.type === 'SUBMIT') {
    // BUG: submitting while step 2 (shipping) is still dirty is allowed here
    const order = state.stepData as OrderDto; // cast — compiler trusts us
    return { ...state, status: 'payment', orderId: generateId() };
  }
  if (state.status === 'complete' && action.type === 'GO_BACK') {
    // BUG: going back after payment completes should be impossible,
    //       but nothing prevents it at the type level
    return { ...state, status: 'checkout' };
  }
  throw new Error(`Unknown transition: ${state.status} → ${action.type}`); // runtime failure
}
```

Every bug from above slips past the compiler. The `status: string` accepts any value. `stepData: any` accepts garbage. The two illegal transitions are just bad `if` branches rather than impossible configurations.

### AFTER — Exhaustive State Machine

```typescript
// ──────────────────────────────────────────────────
// 1. Branded / opaque IDs
// ──────────────────────────────────────────────────

declare const UserIdBrand: unique symbol;
declare const OrderIdBrand: unique symbol;

export type UserId = string & { readonly [UserIdBrand]: 'UserId' };
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId' };

function createUserId(value: string): UserId {
  return value as UserId;
}

function createOrderId(value: string): OrderId {
  return value as OrderId;
}

// Proof that brands prevent confusion — these all fail to compile:
// const x: UserId = createOrderId("order-1");          // ❌ Type 'OrderId' is not assignable to 'UserId'
// const x2: OrderId = createUserId("user-1");          // ❌ Type 'UserId' is not assignable to 'OrderId'


// ──────────────────────────────────────────────────
// 2. Per-step data payloads (only what each step needs)
// ──────────────────────────────────────────────────

interface UserInfo {
  firstName: string;
  lastName: string;
  email: string;
}

interface ShippingInfo {
  street: string;
  city: string;
  zipCode: string;
  country: string;
}

interface CardInfo {
  last4: string;
  expMonth: number;
  expYear: number;
}

interface OrderSummary {
  items: Array<{ name: string; priceCents: number }>;
  subtotalCents: number;
  taxCents: number;
  totalCents: number;
}


// ──────────────────────────────────────────────────
// 3. Discriminated union — one variant per step
// ──────────────────────────────────────────────────

type WizardStepState =
  | { step: 'userinfo';   userInfo: UserInfo;            orderId: null }
  | { step: 'checkout';   userInfo: UserInfo;            orderId: null }
  | { step: 'shipping';   userInfo: UserInfo; shippingInfo: ShippingInfo; orderId: null }
  | { step: 'payment';    userInfo: UserInfo; shippingInfo: ShippingInfo; cardInfo: CardInfo; orderId: null }
  | { step: 'review';     userInfo: UserInfo; shippingInfo: ShippingInfo; cardInfo: CardInfo; orderSummary: OrderSummary; orderId: null }
  | { step: 'complete';   userInfo: UserInfo; shippingInfo: ShippingInfo; cardInfo: CardInfo; orderSummary: OrderSummary; orderId: OrderId; confirmationNumber: string };


// ──────────────────────────────────────────────────
// 4. Events (actions that drive transitions)
// ──────────────────────────────────────────────────

type WizardEvent =
  // userinfo step
  | { type: 'SET_USER_INFO'; payload: Partial<UserInfo> }
  | { type: 'NEXT_TO_CHECKOUT' }
  // checkout step
  | { type: 'REVIEW_CART' }
  | { type: 'ADD_ITEM'; payload: { name: string; priceCents: number } }
  | { type: 'REMOVE_ITEM'; payload: { name: string } }
  | { type: 'NEXT_TO_SHIPPING' }
  // shipping step
  | { type: 'SET_SHIPPING_ADDRESS'; payload: Partial<ShippingInfo> }
  | { type: 'PREVIOUS_TO_CHECKOUT' }
  | { type: 'NEXT_TO_PAYMENT' }
  // payment step
  | { type: 'SET_CARD_INFO'; payload: Partial<CardInfo> }
  | { type: 'PREVIOUS_TO_SHIPPING' }
  | { type: 'NEXT_TO_REVIEW' }
  // review step
  | { type: 'PREVIOUS_TO_PAYMENT' }
  | { type: 'PLACE_ORDER' }
  // complete — only undo exists
  | { type: 'UNDO_ORDER' }


// ──────────────────────────────────────────────────
// 5. Transition function — total, exhaustive, type-safe
// ──────────────────────────────────────────────────

function transition(state: WizardStepState, event: WizardEvent): WizardStepState {
  switch (state.step as const) {

    case 'userinfo':
      if (event.type === 'SET_USER_INFO') {
        return {
          ...state,
          userInfo: { ...state.userInfo, ...(event.payload ?? {}) },
        } satisfies WizardStepState;
      }
      if (event.type === 'NEXT_TO_CHECKOUT') {
        // Compile-time proof: missing userInfo fields won't satisfy UserInfo, so you can't reach here
        // with an incomplete state.
        return { ...state, step: 'checkout' };
      }
      break;

    case 'checkout':
      if (event.type === 'REVIEW_CART') return state;
      if (event.type === 'ADD_ITEM') {
        return state; // in a real system you'd update the cart
      }
      if (event.type === 'REMOVE_ITEM') {
        return state;
      }
      if (event.type === 'NEXT_TO_SHIPPING') {
        // This transition is the key validation point:
        // You cannot call NEXT_TO_SHIPPING unless you've reached the checkout step.
        // Since 'checkout' only gets entered after NEXT_FROM_USERINFO,
        // the shape guarantees userInfo was provided first.
        return { ...state, step: 'shipping' };
      }
      break;

    case 'shipping':
      if (event.type === 'SET_SHIPPING_ADDRESS') {
        return {
          ...state,
          shippingInfo: { ...state.shippingInfo, ...(event.payload ?? {}) },
        } satisfies WizardStepState;
      }
      if (event.type === 'PREVIOUS_TO_CHECKOUT') {
        return { ...state, step: 'checkout' };
      }
      if (event.type === 'NEXT_TO_PAYMENT') {
        // Compile-time proof: shippingInfo MUST exist here because the 'shipping' variant
        // of WizardStepState has it as a required field (not optional). If step 2 is
        // "dirty" (incomplete), the initial construction of this state would already
        // have been a compile error.
        return { ...state, step: 'payment' };
      }
      break;

    case 'payment':
      if (event.type === 'SET_CARD_INFO') {
        return {
          ...state,
          cardInfo: { ...state.cardInfo, ...(event.payload ?? {}) },
        } satisfies WizardStepState;
      }
      if (event.type === 'PREVIOUS_TO_SHIPPING') {
        return { ...state, step: 'shipping' };
      }
      if (event.type === 'NEXT_TO_REVIEW') {
        return { ...state, step: 'review' };
      }
      break;

    case 'review':
      if (event.type === 'PREVIOUS_TO_PAYMENT') {
        return { ...state, step: 'payment' };
      }
      if (event.type === 'PLACE_ORDER') {
        const confirmation = generateConfirmation();
        return {
          ...state,
          step: 'complete',
          orderId: createOrderId(generateOrderId()),
          confirmationNumber: confirmation,
        } satisfies WizardStepState;
      }
      break;

    case 'complete':
      if (event.type === 'UNDO_ORDER') {
        // The only valid exit from complete is undo, which returns to review
        return { ...state, step: 'review', orderId: null, confirmationNumber: '' } satisfies WizardStepState;
      }
      break;

    // Exhaustiveness guard — adding a new step or event without a case below
    // will cause a compile error here.
    default: {
      const _exhaustiveCheck: never = state.step;
      throw new Error(`Unhandled step: ${_exhaustiveCheck}`);
    }
  }

  // Second exhaustiveness check for events: every event must be handled for every step
  const _eventCheck: never = event;
  throw new Error(`Unhandled event: ${event.type} at step ${state.step}`);
}


// ──────────────────────────────────────────────────
// 6. Helpers
// ──────────────────────────────────────────────────

function generateConfirmation(): string {
  return `CONF-${Date.now().toString(36).toUpperCase()}-${Math.random().toString(36).substring(2, 6).toUpperCase()}`;
}

function generateOrderId(): string {
  return `ord-${Date.now().toString(36).toUpperCase()}-${Math.random().toString(36).substring(2, 8).toUpperCase()}`;
}


// ──────────────────────────────────────────────────
// 7. Usage example — happy path (compiles ✅)
// ──────────────────────────────────────────────────

let wizard: WizardStepState = {
  step: 'userinfo',
  userInfo: { firstName: 'Jane', lastName: 'Doe', email: 'jane@example.com' },
  orderId: null,
};

wizard = transition(wizard, { type: 'SET_USER_INFO', payload: { email: 'jane.doe@company.com' } });
wizard = transition(wizard, { type: 'NEXT_TO_CHECKOUT' });
wizard = transition(wizard, { type: 'ADD_ITEM', payload: { name: 'Widget Pro', priceCents: 2999 } });
wizard = transition(wizard, { type: 'NEXT_TO_SHIPPING' });
wizard = transition(wizard, { type: 'SET_SHIPPING_ADDRESS', payload: { street: '123 Main St', city: 'Springfield', zipCode: '62704', country: 'US' } });
wizard = transition(wizard, { type: 'NEXT_TO_PAYMENT' });
wizard = transition(wizard, { type: 'SET_CARD_INFO', payload: { last4: '4242', expMonth: 12, expYear: 2027 } });
wizard = transition(wizard, { type: 'NEXT_TO_REVIEW' });
wizard = transition(wizard, { type: 'PLACE_ORDER' });

console.log(wizard.orderId); // OrderId — correctly branded!


// ──────────────────────────────────────────────────
// 8. PROOF: Two invalid transitions DO NOT COMPILE
// ──────────────────────────────────────────────────

// ❌ INVALID TRANSITION #1: Submitting while step 2 (shipping) is dirty
// Why it fails: The 'shipping' variant requires shippingInfo as a mandatory field.
// You literally cannot construct a WizardStepState in the 'shipping' step
// without providing a valid ShippingInfo object. There is no "dirty/shipping"
// state — either the user completed step 2 (valid state exists) or they're
// still on checkout (different state).

{
  // Attempting this would require constructing:
  // { step: 'shipping', userInfo: ..., shippingInfo: {} }
  // But ShippingInfo requires street, city, zipCode, country — partial assignment fails.
  //
  // Even if you somehow got there, you can only send NEXT_TO_PAYMENT (to checkout),
  // PREVIOUS_TO_CHECKOUT, or SET_SHIPPING_ADDRESS from the shipping step.
  // There IS NO "SUBMIT" event. The event type itself prevents it.
}

// ❌ INVALID TRANSITION #2: Going back after payment (complete → earlier steps)
// Why it fails: From the 'complete' step, the ONLY accepted event is UNDO_ORDER,
// which leads to 'review'. There is no GO_BACK, GOTO_EARLIER, or any other escape
// that jumps multiple steps backwards. The discriminated union makes this impossible:

{
  // This DOES compile (allowed):
  // wizard = transition(wizard, { type: 'UNDO_ORDER' });  // complete → review

  // These do NOT compile (impossible by design):
  // wizard = transition(wizard, { type: 'PREVIOUS_TO_SHIPPING' as any });
  //   // ❌ Event 'PREVIOUS_TO_SHIPPING' does not exist on the 'complete' case.
  //   // It's not even in the event list for 'complete'.
  //
  // wizard = transition(wizard, { type: 'PREVIOUS_TO_PAYMENT' as any });
  //   // ❌ Same — this event only exists under 'review'.
}
```

## Design Decisions & Trade-offs

| Decision | Rationale | Alternative |
|---|---|---|
| Single `transition()` function, not classes | Pure function is trivially testable, serializable, and composable | Redux-style reducer (overkill for one wizard) |
| `satisfies WizardStepState` on every return | Catches accidental shape mismatches at the return site, not just the function signature | No assertion — trust the discriminated union (risky in larger teams) |
| `null` for orderId until completion | Models the domain: no order exists until placed | UUID placeholder with sentinel value (leaves room for logic errors) |
| `Partial<T>` in event payloads | Lets users update individual fields without repeating the full structure | Require full objects (more boilerplate) |
| Brand via `unique symbol` intersection | Zero runtime cost, zero chance of accidental coercion | Opaque aliases via `declare global` (ES2021+ feature flags needed) |

---

## How Invalid Transitions Are Eliminated

**Transition #1 — Submit while step 2 is dirty:** In the old code, `status: string` + `stepData: any` meant you could be `{ status: 'shipping', stepData: {} }` and attempt a SUBMIT. In the new code, the `'shipping'` variant *requires* a fully-formed `ShippingInfo`. You cannot construct a `WizardStepState` in the shipping step with missing fields — TypeScript rejects the construction at the source. Additionally, the event enum has no `SUBMIT` or equivalent — only `NEXT_TO_PAYMENT`, `PREVIOUS_TO_CHECKOUT`, and `SET_SHIPPING_ADDRESS`. Both layers block it.

**Transition #2 — Go back after payment:** In the old code, any string transition was allowed. Here, `'complete'` only accepts `UNDO_ORDER`. That event is explicitly modeled to return to `'review'`, not some arbitrary earlier step. Trying to fire `PREVIOUS_TO_SHIPPING` from `'complete'` fails because the switch statement has no case for that combination — and the `never` check at the bottom catches any gaps.
