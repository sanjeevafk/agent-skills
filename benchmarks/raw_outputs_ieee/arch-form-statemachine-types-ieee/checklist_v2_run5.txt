## Problem Statement

A multi-step checkout wizard stores its entire form state as `any`. Each step has a loose `status: string` field. Navigating between steps uses `as` casts and `!` non-null assertions. Two specific runtime bugs exist:

1. **Submitting while step 2 is dirty** — the user hasn't completed shipping info, but the flow fires `handleSubmit` and crashes downstream when accessing `state.shippingAddress?.line1`.
2. **Going back after payment** — the user pays, then clicks "Back", resetting state mid-flight and causing double-charges or lost order data.

## Before: The Anti-Pattern

```typescript
// ──────────────────────────────────────────────
// ANTI-PATTERN: any-typed state machine
// All fields are guessable-at-runtime only
// ──────────────────────────────────────────────

interface WizardState {
  currentStep: string;        // should be 'step1' | 'step2' | ... but nobody checks
  formData: any;              // 🔴 THE ROOT CAUSE
  errors: Record<string, string>;
}

// Action definitions — no type safety
type WizardAction = {
  type: string;               // should be literal union, not string
  payload?: any;              // 🔴 any payload, zero validation
};

const initialState: WizardState = {
  currentStep: 'step1',
  formData: {},
  errors: {},
};

// Transition logic — purely runtime-checked
function reducer(state: WizardState, action: WizardAction): WizardState {
  switch (action.type) {
    case 'NEXT':
      return {
        ...state,
        currentStep: advanceStep(state.currentStep),  // returns string — who validates?
        formData: { ...state.formData, ...action.payload },
      };
    case 'BACK':
      return {
        ...state,
        currentStep: retreatStep(state.currentStep),
      };
    case 'SUBMIT':
      // 🔴 No guard: we blindly access nested data that may not exist
      const address = state.formData!.shippingAddress!.line1;
      processPayment(state.formData!.paymentDetails!).then(() => { /* ... */ });
      break;
    default:
      return state;
  }
}
```

**What's wrong:**

| Issue | Impact |
|---|---|
| `formData: any` | Compiler lets you read `state.formData.doesNotExist` without complaint |
| `currentStep: string` | You can set it to `'foo'`, `'42'`, or `''` — no structural invariant |
| `action.type: string` | Typo `"SUBMITE"` silently falls through to `default` |
| Non-null assertions (`!`) | Crash on null/undefined at runtime, not at compile time |
| No transition guards | Dirty-step submission and post-payment rewind are valid actions |

## After: Exhaustive State Machine

### 1. Branded/Opaque IDs

Opaque identifiers prevent conflating different entity types at compile time. There is no way to construct a `UserId` or `OrderId` from a bare `string` without going through the factory.

```typescript
// ──────────────────────────────────────────────
// SECTION 1: Branded / opaque identifiers
// Branding uses a phantom property that appears
// in the type but has no runtime footprint.
// ──────────────────────────────────────────────

/** Opaque brand — `string & { readonly __brand: unique symbol }`.
 *
 * Reading `UserId` tells you: "this is not a plain string;
 * it was constructed by UserFactory.make()." */
declare const UserId: unique symbol;
declare const OrderId: unique symbol;
declare const StepToken: unique symbol;

export type UserId = string & { readonly [UserId]: true };
export type OrderId = string & { readonly [OrderId]: true };
export type StepToken = string & { readonly [StepToken]: unique symbol };

/** Factory functions — the only way to construct these IDs.
 *
 * Because of the brand, a raw `string` cannot be assigned to
 * `UserId` without casting, which signals to the developer
 * that verification is needed first. */
export const UserFactory = {
  make(raw: string): UserId {
    if (!raw || !/^U\d{6}$/.test(raw)) throw new Error(`Invalid userId: ${raw}`);
    return raw as UserId;          // cast only here, validated immediately
  },
};

export const OrderFactory = {
  make(raw: string): OrderId {
    if (!raw || !/^ORD-\d{8}$/.test(raw)) throw new Error(`Invalid orderId: ${raw}`);
    return raw as OrderId;
  },
};

/* ── Compile-time proof: you CANNOT mix up a UserId with an OrderId ── */

// ✅ works: both are strings under the hood
function formatId(id: string): string { return `[${id}]`; }
formatId('hello');                       // fine for generic id formatting

// ❌ COMPILE ERROR: UserId is not assignable to OrderId
function linkUserToOrder(userId: UserId, orderId: OrderId): void {}
const uid = UserFactory.make('U000001');
const oid = OrderFactory.make('ORD-000001');
linkUserToOrder(uid, oid);               // ✅ correct order

// linkUserToOrder(oid, uid);             // 🔴 ERROR: OrderId ≠ UserId
// linkUserToOrder('U000001', oid);       // 🔴 ERROR: string ≠ UserId
```

### 2. Discriminated Union Per Step

Each step is a variant of a discriminated union carrying its own required data shape. The `step` field acts as the discriminator. There is no `any` anywhere.

```typescript
// ──────────────────────────────────────────────
// SECTION 2: Step variants — discriminated unions
// Each step carries exactly the data it requires.
// Step N+1 cannot exist without completing step N.
// ──────────────────────────────────────────────

interface Address {
  line1: string;
  line2?: string;
  city: string;
  state: string;
  zip: string;
  country: string;
}

interface CardInfo {
  lastFour: string;
  expiryMonth: number;
  expiryYear: number;
}

// Step 1: account creation — must have email + password
interface Step1_AccountData {
  step: 'step1';                              // discriminator
  submittable: false;                           // cannot submit from step 1
  email: string;
  passwordHash: string;                         // already hashed server-side or by client lib
}

// Step 2: shipping info — must have full address
interface Step2_ShippingData {
  step: 'step2';
  submittable: false;                           // not yet complete
  address: Address;
  shippingMethod: 'standard' | 'express' | 'overnight';
}

// Step 3: review — everything gathered, ready to submit
interface Step3_ReviewData {
  step: 'step3';
  submittable: false;                           // review only, still not submitted
  items: Array<{ sku: string; qty: number; priceCents: number }>;
  subtotalCents: number;
  taxCents: number;
  totalCents: number;
  estimatedDelivery: string;                    // ISO date
}

// Step 4: payment — card info collected, pending confirmation
interface Step4_PaymentData {
  step: 'step4';
  submittable: false;                           // awaiting confirmation
  card: CardInfo;
  billingSameAsShipping: boolean;
  billingAddress?: Address;                     // only needed when != shipping
}

// Step 5: confirmed — final state, contains order ID
interface Step5_ConfirmedData {
  step: 'step5';
  submittable: true;                            // done, fully submitted
  orderId: OrderId;                             // opaque — could never confuse with UserId
  confirmationToken: string;
  shippedAt: string | null;                     // may be null initially
}

// ── The complete step union ──
export type WizardStep =
  | Step1_AccountData
  | Step2_ShippingData
  | Step3_ReviewData
  | Step4_PaymentData
  | Step5_ConfirmedData;

/* ── Compile-time proof: exhaustive discrimination ── */

function describeCurrentStep(step: WizardStep): string {
  switch (step.step) {
    case 'step1':  return `Account for ${step.email}`;
    case 'step2':  return `Ship to ${step.address.city}, ${step.address.state}`;
    case 'step3':  return `Review: $${(step.totalCents / 100).toFixed(2)} for ${step.items.length} items`;
    case 'step4':  return `Pay with card ending in ${step.card.lastFour}`;
    case 'step5':  return `Confirmed: ${step.orderId}`;
    // 🔴 If we add Step6 later and forget this branch:
    //   COMPILE ERROR: not all union cases handled
    //   Type '"step6"' is not assignable to type '"step5"'
    //   Property 'orderId' does not exist on type 'WizardStep'.
    //   Add a `case 'step6':` or a `default` with a `never` check.
  }
}
```

### 3. Event-Driven Transitions with `never` Exhaustiveness Check

Transitions are modeled as events. Each event describes what changes AND guarantees preconditions via its type.

```typescript
// ──────────────────────────────────────────────
// SECTION 3: Events (actions) — one per legal transition
// Each event type encodes its source → target mapping.
// The `never` check guarantees no transition is missed.
// ──────────────────────────────────────────────

interface SubmitEvent {
  event: 'SUBMIT';
  /** The form data being submitted — guaranteed to be complete because
   *  only Step3 produces this event type. */
  reviewData: Step3_ReviewData;
}

interface ConfirmPaymentEvent {
  event: 'CONFIRM_PAYMENT';
  card: CardInfo;
}

interface CancelPaymentEvent {
  event: 'CANCEL_PAYMENT';
}

interface GoBackFromShippingEvent {
  event: 'GO_BACK_FROM_SHIPPING';
  /** Preserve partial email so user doesn't re-type on step 1 */
  preservedEmail: string;
}

interface GoBackFromReviewEvent {
  event: 'GO_BACK_FROM_REVIEW';
  stepNumber: 1 | 2;                          // only allowed to go back to steps 1 or 2
}

interface GoBackFromPaymentEvent {
  event: 'GO_BACK_FROM_PAYMENT';
  /** Returning to review retains the selected card option */
  returnToStep: Exclude<WizardStep['step'], 'step5'>;
}

interface SkipCardValidationEvent {
  event: 'SKIP_CARD_VALIDATION';
  /** Only admins with this flag can bypass — explicit trust boundary */
  adminOverride: true;
}

// ── The event union — adding any new transition means
//    adding a new interface above AND a new case below ──
export type WizardEvent =
  | SubmitEvent
  | ConfirmPaymentEvent
  | CancelPaymentEvent
  | GoBackFromShippingEvent
  | GoBackFromReviewEvent
  | GoBackFromPaymentEvent
  | SkipCardValidationEvent;

/* ── The transition function: pure, typed, exhaustive ── */

export function transition(
  currentState: WizardStep,
  event: WizardEvent,
): WizardStep {
  // ── Guard: blocked transitions checked BEFORE pattern matching ──

  // Block: submitting from step 4 (payment stage) instead of step 3 (review)
  if (event.event === 'SUBMIT') {
    if (currentState.step !== 'step3') {
      throw new Error(
        `Cannot SUBMIT from step "${currentState.step}". ` +
        `SUBMIT is only valid from step "step3".`
      );
    }
  }

  // Block: any backward navigation from step 5 (confirmed)
  if (currentState.step === 'step5') {
    const backwardEvents: WizardEvent['event'][] = ['GO_BACK_FROM_SHIPPING', 'GO_BACK_FROM_REVIEW', 'GO_BACK_FROM_PAYMENT'];
    if ((backwardEvents as string[]).includes(event.event)) {
      throw new Error(`Cannot go back from step 5 (confirmed). The order is final.`);
    }
  }

  // ── Exhaustive match ──
  switch (currentState.step) {
    case 'step1': {
      // From step1: only NEXT is valid
      switch (event.event) {
        case 'SUBMIT':
        case 'CONFIRM_PAYMENT':
        case 'CANCEL_PAYMENT':
        case 'GO_BACK_FROM_REVIEW':
        case 'GO_BACK_FROM_PAYMENT':
        case 'SKIP_CARD_VALIDATION': {
          // These events are typed but unreachable from step1 — handled by the never below
          const _unreachable: never = event;  // forces TS to verify we covered everything
          throw new Error(`Event "${event.event}" cannot occur from step1.`);
        }
        case 'GO_BACK_FROM_SHIPPING': {
          // Special: rewinding from step2→step1 preserves email
          return {
            step: 'step1',
            submittable: false,
            email: event.preservedEmail ?? currentState.email,
            passwordHash: currentState.passwordHash,
          };
        }
      }
    }

    case 'step2': {
      switch (event.event) {
        case 'SUBMIT':
        case 'CONFIRM_PAYMENT':
        case 'CANCEL_PAYMENT':
        case 'GO_BACK_FROM_SHIPPING':
        case 'GO_BACK_FROM_PAYMENT':
        case 'SKIP_CARD_VALIDATION': {
          const _unreachable: never = event;
          throw new Error(`Event "${event.event}" cannot occur from step2.`);
        }
        case 'GO_BACK_FROM_REVIEW': {
          // Back from step3 → step2: retain shipping address
          if (event.stepNumber !== 2) throw new Error('Go back from review must target step2 when coming from step2.');
          return {
            step: 'step2',
            submittable: false,
            address: currentState.address,
            shippingMethod: currentState.shippingMethod,
          };
        }
      }
    }

    case 'step3': {
      switch (event.event) {
        case 'GO_BACK_FROM_SHIPPING':
        case 'GO_BACK_FROM_PAYMENT':
        case 'CONFIRM_PAYMENT':
        case 'CANCEL_PAYMENT':
        case 'SKIP_CARD_VALIDATION': {
          const _unreachable: never = event;
          throw new Error(`Event "${event.event}" cannot occur from step3.`);
        }
        case 'GO_BACK_FROM_REVIEW': {
          // Review → back to step1 or step2
          return event.stepNumber === 1
            ? { step: 'step1', submittable: false, email: currentState.items[0]?.sku ?? '', passwordHash: '' } // simplified
            : { step: 'step2', submittable: false, address: { line1: '', city: '', state: '', zip: '', country: '' }, shippingMethod: 'standard' };
        }
        case 'SUBMIT': {
          // step3.submit → generate order → step5
          // In real code: async call to backend, then emit CONFIRMED event
          // For this demo, we skip straight through:
          return {
            step: 'step5',
            submittable: true,
            orderId: OrderFactory.make(`ORD-${Date.now().toString().slice(-8)}`),
            confirmationToken: Math.random().toString(36).slice(2),
            shippedAt: null,
          } satisfies Step5_ConfirmedData;
        }
      }
    }

    case 'step4': {
      switch (event.event) {
        case 'SUBMIT':
        case 'GO_BACK_FROM_SHIPPING':
        case 'GO_BACK_FROM_REVIEW':
        case 'SKIP_CARD_VALIDATION': {
          const _unreachable: never = event;
          throw new Error(`Event "${event.event}" cannot occur from step4.`);
        }
        case 'GO_BACK_FROM_PAYMENT': {
          // Payment → back to review (step3), retaining chosen items
          return {
            step: 'step3',
            submittable: false,
            items: [{ sku: 'DEMO', qty: 1, priceCents: 999 }],
            subtotalCents: 999,
            taxCents: 99,
            totalCents: 1098,
            estimatedDelivery: '2026-09-01',
          };
        }
        case 'CANCEL_PAYMENT': {
          // Payment → also goes back to review
          return {
            step: 'step3',
            submittable: false,
            items: [{ sku: 'DEMO', qty: 1, priceCents: 999 }],
            subtotalCents: 999,
            taxCents: 99,
            totalCents: 1098,
            estimatedDelivery: '2026-09-01',
          };
        }
        case 'CONFIRM_PAYMENT': {
          // step4.confirm → step5 (final)
          return {
            step: 'step5',
            submittable: true,
            orderId: OrderFactory.make(`ORD-${Date.now().toString().slice(-8)}`),
            confirmationToken: Math.random().toString(36).slice(2),
            shippedAt: null,
          };
        }
      }
    }

    case 'step5': {
      switch (event.event) {
        // step5 is terminal — every remaining event is unreachable
        case 'SUBMIT':
        case 'CONFIRM_PAYMENT':
        case 'CANCEL_PAYMENT':
        case 'GO_BACK_FROM_SHIPPING':
        case 'GO_BACK_FROM_REVIEW':
        case 'GO_BACK_FROM_PAYMENT':
        case 'SKIP_CARD_VALIDATION': {
          const _unreachable: never = event;
          throw new Error(`Event "${event.event}" cannot occur from step5 (confirmed).`);
        }
      }
    }
  }
}
```

Wait — the above is verbose with `never` checks inline. A cleaner approach separates the transition table into a type-level specification. Let me refactor to the idiomatic pattern:

```typescript
// ──────────────────────────────────────────────────────────
// REFINED APPROACH: type-level transition matrix
// The permitted edges encode the FSM directly in types.
// ──────────────────────────────────────────────────────────

// A transition maps <sourceStep, event> → targetStep.
// If there's no edge, the event simply doesn't exist for
// that source — it cannot be constructed.

interface NextFromStep1 {
  event: 'NEXT';
  accountEmail: string;
  passwordHash: string;
}

interface NextFromStep2 {
  event: 'NEXT';
  address: Address;
  shippingMethod: 'standard' | 'express' | 'overnight';
}

interface NextFromStep3 {
  event: 'NEXT';
}

interface ReviewFromStep2 {
  event: 'REVIEW';
  items: Array<{ sku: string; qty: number; priceCents: number }>;
  subtotalCents: number;
  taxCents: number;
  totalCents: number;
}

interface PayFromStep3 {
  event: 'PAY';
  card: CardInfo;
  billingSameAsShipping: boolean;
  billingAddress?: Address;
}

interface ConfirmedFromStep4 {
  event: 'CONFIRM';
}

interface CancelledFromStep4 {
  event: 'CANCEL';
}

interface RewindToStep1 {
  event: 'REWIND';
  target: 'step1';
}

interface RewindToStep2 {
  event: 'REWIND';
  target: 'step2';
}

// Every possible event in the system — adding one means
// defining BOTH this interface AND adding it to the union
// AND handling it in the reducer. Three places to sync —
// but TypeScript enforces all three simultaneously.
export type WizardEvent =
  | NextFromStep1
  | NextFromStep2
  | NextFromStep3
  | ReviewFromStep2
  | PayFromStep3
  | ConfirmedFromStep4
  | CancelledFromStep4
  | RewindToStep1
  | RewindToStep2;

// ── Pure transition reducer (no side effects, fully inferable) ──

export function reduceWizardStep(
  state: WizardStep,
  event: WizardEvent,
): WizardStep {

  /* ═══════════════════════════════════════════
   * EXHAUSTIVE MATCH: outer switch on step
   * Inner switch on event.event with never-check
   * ═══════════════════════════════════════════ */

  switch (state.step) {

    case 'step1': {
      if (event.event !== 'NEXT') {
        const _exhaustive: never = event;
        throw new TypeError(`No transition from step1 with event: "${_exhaustive.event}"`);
      }
      // Narrowed: event is NextFromStep1
      return {
        step: 'step2',
        submittable: false,
        address: { line1: '', city: '', state: '', zip: '', country: '' }, // placeholder until actual fill
        shippingMethod: 'standard',
      };
    }

    case 'step2': {
      // Either REVIEW (forward to step3) or REWIND (back to step1)
      if (event.event === 'REVIEW') {
        // event is ReviewFromStep2 — carry step2 data forward
        return {
          step: 'step3',
          submittable: false,
          items: event.items,
          subtotalCents: event.subtotalCents,
          taxCents: event.taxCents,
          totalCents: event.totalCents,
          estimatedDelivery: 'TBD',
        };
      }
      if (event.event === 'REWIND' && event.target === 'step1') {
        return {
          step: 'step1',
          submittable: false,
          email: '',   // would preserve from step1 data in real impl
          passwordHash: '',
        };
      }
      // Unhandled event from step2 — never reached due to exhaustive check
      const _exhaustive: never = event;
      throw new TypeError(`No transition from step2 with event: "${_exhaustive.event}"`);
    }

    case 'step3': {
      // Can go forward to PAY (step4) or REWIND to step1/step2
      if (event.event === 'PAY') {
        return {
          step: 'step4',
          submittable: false,
          card: event.card,
          billingSameAsShipping: event.billingSameAsShipping,
          billingAddress: event.billingAddress,
        };
      }
      if (event.event === 'REWIND') {
        if (event.target === 'step1') {
          return { step: 'step1', submittable: false, email: '', passwordHash: '' };
        }
        if (event.target === 'step2') {
          return { step: 'step2', submittable: false, address: { line1: '', city: '', state: '', zip: '', country: '' }, shippingMethod: 'standard' };
        }
      }
      // Unhandled — never path
      const _exhaustive: never = event;
      throw new TypeError(`No transition from step3 with event: "${_exhaustive.event}"`);
    }

    case 'step4': {
      // CONFIRM → step5, or CANCEL → step3
      if (event.event === 'CONFIRM') {
        return {
          step: 'step5',
          submittable: true,
          orderId: OrderFactory.make(`ORD-${Date.now().toString().slice(-8)}`),
          confirmationToken: Math.random().toString(36).slice(2),
          shippedAt: null,
        };
      }
      if (event.event === 'CANCEL') {
        return {
          step: 'step3',
          submittable: false,
          items: [],
          subtotalCents: 0,
          taxCents: 0,
          totalCents: 0,
          estimatedDelivery: 'TBD',
        };
      }
      const _exhaustive: never = event;
      throw new TypeError(`No transition from step4 with event: "${_exhaustive.event}"`);
    }

    case 'step5': {
      // TERMINAL STATE — every event type is unreachable
      const _exhaustive: never = event;
      throw new TypeError(`Cannot transition from step5 (terminal) with event: "${_exhaustive.event}"`);
    }
  }
}
```

### How the Never-Check Guarantees Future-Safety

```typescript
// ──────────────────────────────────────────────────────────
// FUTURE-PROOFING: Adding a new step or event
// ──────────────────────────────────────────────────────────

// Scenario: Product team asks for a "step6: delivery tracking"
// Developer adds Step6_TrackingData to the WizardStep union.

interface Step6_TrackingData {
  step: 'step6';
  submittable: true;
  trackingNumber: string;
  carrier: string;
}

// Now WizardStep must include it:
// export type WizardStep = Step1 | Step2 | Step3 | Step4 | Step5 | Step6;

// TypeScript now complains at EVERY unhandled location:
//
// 1. In reduceWizardStep's outer switch:
//    "Type 'step6' is not comparable to 'step1' | ... | 'step5'"
//    → Developer MUST add a case 'step6' block.
//
// 2. Inside any inner switch where a new event could apply:
//    The never-check `_exhaustive: never` becomes a compile error
//    if a newly added event isn't handled.
//
// 3. In describeCurrentStep() or similar consumer functions:
//    Switch over step.step now needs a 'step6' case.
//    Missing it = compile error, not a silent bug.

// The never-check transforms what would be a silent runtime
// bug ("new event ignored, nothing happens") into a compile
// error that blocks the PR. Every single transition point
// must acknowledge the new type.
```

## Summary: Before vs. After Comparison

```
┌─────────────────────┬──────────────────────────┬──────────────────────────┐
│ Aspect              │ BEFORE                   │ AFTER                    │
├─────────────────────┼──────────────────────────┼──────────────────────────┤
│ State shape         │ any                      │ Discriminated union      │
│ Step identity       │ string                   │ Literal type ('step1'..5)│
│ Action types        │ string + any payload     │ Event interfaces (typed) │
│ Transition guards   │ Runtime ifs              │ Absence of event type    │
│ Null safety         │ ! non-null assertions    │ Required fields only     │
│ ID confusion risk   │ string everywhere        │ Branded opaque types     │
│ Missing transitions │ Silent fall-through      │ never-check compile fail │
│ New step cost       │ Easy to forget guards    │ TS complains everywhere  │
│ IDE support         │ Minimal (no autocomplete)│ Full autocomplete + jumps│
│ Test burden         │ Must test every guard    │ Tests cover business     │
│                     │                          │ logic, not guards        │
└─────────────────────┴──────────────────────────┴──────────────────────────┘
```

### Key Takeaway

The `never` exhaustiveness check is the linchpin. By placing `const _exhaustive: never = event` in every case arm that should be unreachable, you convert **structural incompleteness** from a runtime concern into a compile-time guarantee. Every time someone adds a variant to `WizardStep` or `WizardEvent`, the compiler points to every single place that needs updating. There is no way to merge, ship, or deploy without addressing every touchpoint.
