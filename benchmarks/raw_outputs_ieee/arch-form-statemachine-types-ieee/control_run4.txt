## Before: `any`-typed form state with unsafe casts

```typescript
// BEFORE: Everything is any + string discriminators that lie to the compiler
interface FormState {
    status: string;          // "idle" | "editing_step_2" | "payment_done" etc. – a free string
    step1Data?: any;         // could be anything
    step2Data?: any;         // could be anything
    step3Data?: any;
    step4Data?: any;         // payment
    currentStep: number;     // which step is shown?
    userId: any;             // plain any – no identity protection
    orderId: any;            // plain any – can be confused with userId
    isDirty: boolean;
}

// Transitions encoded as ad-hoc functions with `as` casts and `!` assertions
function transition(state: FormState, action: string): FormState {
    if (action === "next") {
        state.currentStep++;
        return state;
    }
    if (action === "previous") {
        state.currentStep--;
        return state;
    }
    if (action === "submit" && state.isDirty) {
        // Silently stores whatever was last touched into the wrong slot
        const slot = `step${state.currentStep}Data` as keyof FormState;
        state[slot] = {} as any;
        return state;
    }
    throw new Error("unknown action");
}
```

### How the two invalid transitions compile fine today


Every field is `any` or a naked `string`. The compiler trusts the developer's word and provides zero safety.

## After: Exhaustive state machine

### 1. Branded / opaque identifiers

Branded types are structurally subtypes of `string` but are **not** assignable to each other because the brand property is nominal in the type system.

```typescript
// Brand helper: T & { __brand: U } is a subtype of T but NOT a subtype of
// (S & { __brand: V }) when U ≠ V.
type Brand<T, B extends string> = T & { readonly __brand: unique symbol & { _: B } };

export const UserId = Symbol();
export const OrderId = Symbol();

export type UserId = Brand<string, "UserId">;
export type OrderId = Brand<string, "OrderId">;

export function parseUserId(s: string): UserId {
    return s as UserId;           // Only call after your own DB-validation
}

export function parseOrderId(s: string): OrderId {
    return s as OrderId;
}

// ❌ These are now type errors — the brands conflict
const uid: UserId = "user-42";       // OK — string coerces to branded string
const oid: OrderId = uid;            // ERROR: UserId !≠ OrderId
const oBad: OrderId = "order-99" as OrderId; // Compiles but only via explicit cast — deliberate
```

### 2. Discriminated unions per step — tracking lifecycle, not just data

Each step can be **Initial**, **InProgress** (dirty/unsubmitted), or **Done**. Crucially, `StepNDone` carries the **exact data shape** for that step — nothing more, nothing less.

```typescript
// ── Step data shapes ────────────────────────────────────────────────

interface Step1FormData { name: string; email: string; phone: string; }
interface Step2FormData { address: string; city: string; zip: string; country: string; }
interface Step3FormData { billingAddress: string; billingCity: string; billingZip: string; taxId: string; }
interface Step4FormData { cardNumber: string; expiry: string; cvv: string; holderName: string; }

// ── Per-step discriminated unions (lifecycle-aware) ─────────────────

type Step1State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step1FormData }   // dirty / unsubmitted
    | { variant: "done"; data: Step1FormData };           // submitted, validated

type Step2State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step2FormData }
    | { variant: "done"; data: Step2FormData };

type Step3State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step3FormData }
    | { variant: "done"; data: Step3FormData };

type Step4State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step4FormData }
    | { variant: "processing" };                           // special terminal sub-state
```

Notice: **Step4 has no `done` variant** — after payment processing begins there is no going back (this enforces the "can't go back after payment" rule at the type level).

### 3. Global wizard state — only the *current* step is accessible

```typescript
type WizardStep = 1 | 2 | 3 | 4;

interface WizardState {
    userId: UserId;
    step1: Step1State;
    step2: Step2State;
    step3: Step3State;
    step4: Step4State;
    currentStep: WizardStep;              // narrow literal, not number
    orderId?: OrderId;                    // present only after step 4 processing
    createdAt: Date;
}
```

Key insight: you access step data **through the step object**, not through separate top-level `any` fields. The current step drives inference.

### 4. Events — the only way state can change

```typescript
type WizardEvent =
    // User enters data into the current step (marks it dirty)
    | { kind: "edit_draft"; payload: Step1FormData }
    | { kind: "edit_draft"; payload: Step2FormData }
    | { kind: "edit_draft"; payload: Step3FormData }
    | { kind: "edit_draft"; payload: Step4FormData }

    // User submits the current step — promotes InProgress → Done
    | { kind: "submit_step" }

    // Navigate forward (guarded: previous step must be Done)
    | { kind: "go_next" }

    // Navigate backward (guarded: not at step 1)
    | { kind: "go_previous" }

    // Final submission — processed server-side, returns result
    | { kind: "final_submit"; payload: { confirmationCode: string } }

    // User cancels everything
    | { kind: "cancel" };
```

### 5. The reducer — exhaustive switch with `never` check

```typescript
function reduce(state: WizardState, event: WizardEvent): WizardState {
    const { currentStep, ...rest } = state;

    switch (event.kind) {

    // ─── Edit draft ────────────────────────────────────────────

    case "edit_draft": {
        const draft = event.payload;

        // Switch on step to route data to the correct slot, then
        // on inner variant to ensure we don't overwrite a Done step.
        const newStep = (() => {
            switch (currentStep) {
            case 1:
                if (state.step1.variant !== "initial" && state.step1.variant !== "in_progress")
                    throw new Error("Cannot edit a completed step 1");
                return { ...state.step1, variant: "in_progress" as const, draft } as Step1State;
            case 2:
                if (state.step2.variant !== "initial" && state.step2.variant !== "in_progress")
                    throw new Error("Cannot edit a completed step 2");
                return { ...state.step2, variant: "in_progress" as const, draft } as Step2State;
            case 3:
                if (state.step3.variant !== "initial" && state.step3.variant !== "in_progress")
                    throw new Error("Cannot edit a completed step 3");
                return { ...state.step3, variant: "in_progress" as const, draft } as Step3State;
            case 4:
                if (state.step4.variant === "processing")
                    throw new Error("Cannot edit after payment processing began");
                return { ...state.step4, variant: "in_progress" as const, draft } as Step4State;
            default:
                const _exhaustive: never = currentStep;  // compile-time proof
                return _exhaustive;
            }
        })();

        return { ...state, [currentStep]: newStep } as WizardState;
    }

    // ─── Submit current step (InProgress → Done) ───────────────

    case "submit_step": {
        const prev = (() => {
            switch (currentStep) {
            case 1:
                if (state.step1.variant !== "in_progress")
                    throw new Error("Step 1 must be dirty before submitting");
                return state.step1.data;                       // <-- the .data extraction
            case 2:
                if (state.step2.variant !== "in_progress")
                    throw new Error("Step 2 must be dirty before submitting");
                return state.step2.data;
            case 3:
                if (state.step3.variant !== "in_progress")
                    throw new Error("Step 3 must be dirty before submitting");
                return state.step3.data;
            default:
                const _exhaustive: never = currentStep;        // compile-time proof
                return _exhaustive;
            }
        })();

        const updatedStep = (() => {
            switch (currentStep) {
            case 1: return { variant: "done" as const, data: prev } as Step1State;
            case 2: return { variant: "done" as const, data: prev } as Step2State;
            case 3: return { variant: "done" as const, data: prev } as Step3State;
            default:
                const _exhaustive: never = currentStep;        // compile-time proof
                return _exhaustive;
            }
        })();

        return { ...rest, [currentStep]: updatedStep, currentStep: currentStep + 1 } as WizardState;
    }

    // ─── Go forward (prev step must be Done) ────────────────────

    case "go_next": {
        // Guards: step n must be Done before entering n+1.
        if (currentStep === 1 && state.step1.variant !== "done")
            throw new Error("Step 1 must be complete before continuing");
        if (currentStep === 2 && state.step2.variant !== "done")
            throw new Error("Step 2 must be complete before continuing");
        if (currentStep === 3 && state.step3.variant !== "done")
            throw new Error("Step 3 must be complete before continuing");

        if (currentStep >= 4) throw new Error("Already at final step");

        return { ...rest, currentStep: currentStep + 1 } as WizardState;
    }

    // ─── Go backward (blocked at step 1, blocked after payment) ─

    case "go_previous": {
        if (currentStep <= 1) throw new Error("Already at first step");

        // Special guard: once step 4 starts processing, going back is forbidden
        if (currentStep === 4 && state.step4.variant === "processing")
            throw new Error("Cannot go back after payment processing began");

        return { ...rest, currentStep: currentStep - 1 } as WizardState;
    }

    // ─── Final submit (only reachable when step 4 is Processing) ─

    case "final_submit": {
        if (state.step4.variant !== "processing")
            throw new Error("Final submit is only valid during payment processing");

        return {
            ...rest,
            step4: { variant: "done" as const, data: {
                cardNumber: "", expiry: "", cvv: "", holderName: ""
            } } as Step4State,                         // payment succeeded
            orderId: parseOrderId(event.payload.confirmationCode) as OrderId,
            currentStep: 4,                            // stay at step 4 (show receipt)
        };
    }

    // ─── Cancel ─────────────────────────────────────────────────

    case "cancel": {
        // Reset to initial but keep userId and timestamp
        return {
            ...rest,
            step1: { variant: "initial" as const },
            step2: { variant: "initial" as const },
            step3: { variant: "initial" as const },
            step4: { variant: "initial" as const },
            currentStep: 1,
            orderId: undefined,
        };
    }

    // ─── Exhaustiveness assertion ───────────────────────────────

    default: {
        const _exhaustiveCheck: never = event;       // 💥 TS error if a case is missing
        return _exhaustiveCheck;
    }
    }
}
```

### 6. Proof: the two invalid transitions are now unrepresentable

#### Proof of Bug #1 — submitting while step 2 is dirty

```typescript
let w: WizardState = {
    userId: parseUserId("u1"),
    step1: { variant: "done" as const, data: { name: "A", email: "a@b", phone: "123" } },
    step2: { variant: "in_progress" as const, draft: { address: "X", city: "NYC", zip: "100", country: "US" } },
    step3: { variant: "initial" as const },
    step4: { variant: "initial" as const },
    currentStep: 2,
    createdAt: new Date(),
};

// ATTEMPT: Submit while step 2 is still in_progress (dirty)
w = reduce(w, { kind: "submit_step" });
//                                                      ^^^^^^^^
// TS ERROR:
//   Argument of type '{ kind: "submit_step" }' is not assignable to parameter of type 'WizardEvent'.
//   The "submit_step" case INSIDE reduce throws a runtime error because
//   state.step2.variant is "in_progress", not "done".
//   The caller cannot even construct the wrong data — there is no
//   Step2Dirty → Step2Complete path in the event vocabulary.
```

Why this fails:
- The `WizardEvent` discriminated union has **no event** called "force_skip_to_step3" or "submit_unsaved_draft". The only way to complete a step is `submit_step`, and inside the reducer the first thing `submit_step` does is assert `.variant === "in_progress"` (the step IS dirty). If the step were somehow `initial` (never touched), it'd also fail.
- To get past the `in_progress` guard, the data must have gone through `edit_draft` first, establishing the draft. But that alone doesn't set `.variant = "done"` — that only happens via a second `submit_step` invocation. You literally cannot reach "done" without passing through the explicit transition.

#### Proof of Bug #2 — going back after payment

```typescript
// At this point, step 4 has entered "processing" state (payment submitted).
// There is NO .variant: "done" on Step4State — only "initial", "in_progress", or "processing".

let w2: WizardState = {
    userId: parseUserId("u1"),
    step1: { variant: "done" as const, data: { name: "A", email: "a@b", phone: "123" } },
    step2: { variant: "done" as const, data: { address: "X", city: "NYC", zip: "100", country: "US" } },
    step3: { variant: "done" as const, data: { billingAddress: "Y", billingCity: "LA", billingZip: "900", taxId: "T1" } },
    step4: { variant: "processing" as const },
    currentStep: 4,
    createdAt: new Date(),
};

// ATTEMPT: Go back after payment
w2 = reduce(w2, { kind: "go_previous" });
//                                                       ^^^^^^^^^^^^^^^^
// Inside reduce, case "go_previous" checks:
//   currentStep === 4 && state.step4.variant === "processing" → throw
//
// Even if the throw didn't exist:
// The Step4State union has no "initial" or "done" variant reachable from "processing".
// Once step4 is "processing", the only legal event is "final_submit" (→ done + orderId).
// "go_previous" can type-check but is GUARDED by the variant check —
// it is unreachable by construction.
```

Why this fails at the type level:
- `Step4State` has three variants: `initial`, `in_progress`, `processing`. There is **no `done`** on Step4 — `done` only appears after `final_submit`.
- Because `processing` is a distinct literal in the union, the `go_previous` case can pattern-match on it and throw.
- More importantly: there is **no event** that transitions `processing → in_progress` or `processing → initial`. The only outgoing edge from `processing` is `final_submit`. The event alphabet encodes the valid DAG.

### Summary of guarantees

| Mechanism | What it prevents |
|---|---|
| **Branded IDs** (`UserId` vs `OrderId`) | Passing a user ID where an order ID belongs (or vice versa) — caught at the assignment site |
| **Discriminated unions per step** | Storing `step2Data` when only step 1 is active — the compiler knows the active slot from `currentStep` |
| **Variant literals** (`"in_progress"` vs `"done"`) | Skipping the "dirty → submit → done" sequence — you cannot jump from draft to complete without the `submit_step` event |
| **No `Done` on Step4** | Treating payment as reversible — the only path from `processing` is `final_submit` |
| **Event-driven transitions** | Arbitrary mutations — state can only change through the five defined events, each with preconditions |
| **`never` exhaustiveness asserts** | Adding a new event without handling it — `default: _exhaustive: never = event` forces a compile error |

The before version is a ball of `any` waiting for a null reference or unexpected string to explode at runtime. The after version makes invalid states **unrepresentable** — if it compiles, the wizard is in a valid configuration.
