## Before: The `any` State Problem

```ts
type WizardState = {
  status: string          // "idle" | "step1" | "step2" | "payment" | "submitting" | "done" — nobody enforces this
  currentStep: number
  data: any               // loses all per-step shape information
  userId?: any
  orderId?: any           // UserId and OrderId are the same runtime type → easily swapped
}

// Transitions are just functions that mutate state — no compile-time guard on what's valid
function submitWizard(state: WizardState) {
  if (state.status !== "step2") throw new Error("must be at step2") // caught only at runtime
  state.status = "submitting"
}

function goToBack(state: WizardState) {
  if (state.currentStep > 0) state.currentStep-- // allows going back after payment — no guard
}
```

**What breaks:**
- Calling `submitWizard` when `currentStep === 2` but step 3 (payment) has unsaved data
- Clicking "back" after payment completes, re-entering a completed step with stale data
- `userId` and `orderId` are both `any` — no compiler error swapping them

## After: Exhaustive Discriminated Union State Machine

### Step 1 — Branded/Opaque Types

```ts
// Opaque IDs: cannot be confused, cannot be constructed outside the module
export type UserId = string & { readonly __brand: "UserId" };
export type OrderId = string & { readonly __brand: "OrderId" };

declare function makeUserId(s: string): UserId;
declare function makeOrderId(s: string): OrderId;

// These do NOT compile — different brands:
// const bad: UserId = makeOrderId("abc");   // Error!
// const bad2: OrderId = "plain-string";     // Error!
```

### Step 2 — Action Types (Event-Driven, Inference-Friendly, No `any`)

```ts
// Each action carries its own payload type. The discriminating field (`kind`) 
// makes narrowing automatic via switch inference.
type WizardAction =
  // Step 1: Shipping address
  | { kind: "SET_ADDRESS"; street: string; city: string; zip: string }
  // Step 2: Billing details + optional promo
  | { kind: "SET_BILLING"; name: string; email: string; promoCode?: string }
  // Step 3: Payment — requires valid card token (not a plain string)
  | { kind: "PAY"; cardToken: string; amount: number; currency: string }
  // Step 4: Submit order — only valid after PAY completes
  | { kind: "SUBMIT" }
  // Navigation — backwards allowed only from certain steps
  | { kind: "GO_BACK"; targetStep: "address" | "billing" }
  // Terminal events
  | { kind: "RESET" }
  | { kind: "CANCEL" };
```

### Step 3 — Per-Step Data Interfaces

```ts
interface AddressData  { street: string; city: string; zip: string }
interface BillingData  { name: string; email: string; promoCode?: string }
interface PaymentData  { cardToken: string; amount: number; currency: string }

// Total order record — fully typed, no `any`
interface OrderRecord {
  userId: UserId;
  orderId: OrderId;
  shipping: AddressData;
  billing: BillingData;
  payment: PaymentData;
  submittedAt: Date;
}
```

### Step 4 — The State (Discriminated Union by Status)

```ts
type WizardStatus =
  | { kind: "IDLE" }
  | { kind: "ADDRESS"; data: AddressData }
  | { kind: "BILLING"; address: AddressData; data: BillingData }
  | { kind: "PAYMENT"; address: AddressData; billing: BillingData; data: PaymentData }
  | { kind: "CONFIRMED"; address: AddressData; billing: BillingData; payment: PaymentData }
  | { kind: "DONE"; order: OrderRecord }
  | { kind: "ERROR"; message: string };
```

Each state variant carries exactly the data it needs. You can see at a glance what's available in each branch.

### Step 5 — The Transition Function with Exhaustiveness Check

```ts
function transition(
  state: WizardStatus,
  action: WizardAction,
): WizardStatus {
  // TypeScript narrows `state.kind` via the union discrimination.
  // The `never` check at the end catches *compile-time* gaps — if you add
  // a new status variant but forget a case here, TS errors: "Type 'X' is not
  // assignable to type 'never'"
  
  switch (state.kind) {
    case "IDLE": {
      if (action.kind === "SET_ADDRESS")
        return { kind: "ADDRESS", data: action };
      if (action.kind === "CANCEL")
        return { kind: "ERROR", message: "Nothing to cancel" };
      return assertUnreachable(action);
    }

    case "ADDRESS": {
      // Going back to IDLE is allowed; SET_ADDRESS just updates current data
      if (action.kind === "SET_ADDRESS")
        return { kind: "ADDRESS", data: action };
      
      // Valid forward: address → billing
      if (action.kind === "SET_BILLING")
        return { kind: "BILLING", address: state.data, data: action };
      
      // GO_BACK only to a known target
      if (action.kind === "GO_BACK" && action.targetStep === "address")
        return state; // stay put (already there)
      
      // BLOCKED: ADDRESS → PAY or ADDRESS → SUBMIT are impossible types
      return assertUnreachable(action);
    }

    case "BILLING": {
      if (action.kind === "SET_BILLING")
        return { kind: "BILLING", address: state.address, data: action };
      
      // Valid forward: billing → payment
      if (action.kind === "PAY")
        return { kind: "PAYMENT", address: state.address, billing: state.data, data: action };
      
      // GO_BACK: only to address
      if (action.kind === "GO_BACK" && action.targetStep === "address")
        return { kind: "ADDRESS", data: state.address };
      
      // BLOCKED: billing → submit (skipped payment), billing → reset mid-stream
      return assertUnreachable(action);
    }

    case "PAYMENT": {
      if (action.kind === "PAY")
        return { kind: "PAYMENT", address: state.address, billing: state.billing, data: action };
      
      // Valid forward: payment → confirmed
      if (action.kind === "SUBMIT")
        return { kind: "CONFIRMED", address: state.address, billing: state.billing, payment: state.data };
      
      // GO_BACK: only to billing (NOT address — you've committed to payment)
      if (action.kind === "GO_BACK" && action.targetStep === "billing")
        return { kind: "BILLING", address: state.address, data: state.billing };
      
      return assertUnreachable(action);
    }

    case "CONFIRMED": {
      // After confirmation, ONLY RESET or CANCEL are valid
      if (action.kind === "RESET")
        return { kind: "IDLE" };
      if (action.kind === "CANCEL")
        return { kind: "ERROR", message: "Order already confirmed" };
      
      // BLOCKED: CONFIRMED → SUBMIT, CONFIRMED → GO_BACK are impossible
      return assertUnreachable(action);
    }

    case "DONE": {
      if (action.kind === "RESET")
        return { kind: "IDLE" };
      // From DONE, nothing goes backward or forward except full reset
      return assertUnreachable(action);
    }

    case "ERROR": {
      if (action.kind === "RESET")
        return { kind: "IDLE" };
      return assertUnreachable(action);
    }
  }

  // Exhaustiveness: after the exhaustive switch above, `action` must be `never`
  // for every reachable branch. If a new action is added without updating cases,
  // this returns a type error.
  return assertUnreachable(state);
}

// Helper: forces compilation failure on unexhausted unions
function assertUnreachable(_x: never): never {
  throw new Error("Invalid action/state combination");
}
```

### Step 6 — Proving the Two Invalid Transitions Are Unrepresentable

**Invalid Transition #1: Submitting while step 2 (billing) is dirty (hasn't reached payment yet)**

```ts
const billingState: WizardStatus = {
  kind: "BILLING",
  address: { street: "1 Main St", city: "NYC", zip: "10001" },
  data: { name: "John", email: "john@example.com" }
};

// ❌ THIS DOES NOT COMPILE:
transition(billingState, { kind: "SUBMIT" });
// Error: Argument of type '{ kind: "SUBMIT"; }' is not assignable to parameter 
// of type 'never'. 
//
// Why: Inside the switch(case "BILLING"), the only recognized actions are 
// SET_BILLING, PAY, and GO_BACK. SUBMIT is not handled, so it falls through 
// to assertUnreachable(action), which has signature (x: never) => never. 
// The compiler infers that { kind: "SUBMIT" } is not assignable to `never`, 
// producing a hard compile-time error.
```

**Invalid Transition #2: Going back after payment (from CONFIRMED or PAYMENT)**

```ts
const confirmedState: WizardStatus = {
  kind: "CONFIRMED",
  address: { street: "1 Main St", city: "NYC", zip: "10001" },
  billing: { name: "John", email: "john@example.com" },
  payment: { cardToken: "tok_abc", amount: 99.99, currency: "USD" }
};

// ❌ THIS DOES NOT COMPILE:
transition(confirmedState, { kind: "GO_BACK", targetStep: "billing" });
// Error: Argument of type '{ kind: "GO_BACK"; targetStep: "billing"; }' 
// is not assignable to parameter of type 'never'.
//
// Why: Inside case "CONFIRMED", the only accepted actions are RESET and CANCEL. 
// GO_BACK falls through to assertUnreachable() → type `never`. Compile error.

// Also blocked from PAYMENT:
const paymentState: WizardStatus = {
  kind: "PAYMENT",
  address: { street: "1 Main St", city: "NYC", zip: "10001" },
  billing: { name: "John", email: "john@example.com" },
  data: { cardToken: "tok_xyz", amount: 99.99, currency: "USD" }
};

// Can go back TO billing from PAYMENT (that's explicitly allowed):
transition(paymentState, { kind: "GO_BACK", targetStep: "billing" }); // ✅ OK

// But GO_BACK to "address" from PAYMENT is blocked:
transition(paymentState, { kind: "GO_BACK", targetStep: "address" as const });
// Error: Type '"address"' is not assignable to type '"billing"'.
//
// Why: GO_BACK's targetStep is narrowed to `"address" | "billing"` at the type level,
// but inside case "PAYMENT" only "billing" is handled. The "address" target reaches
// assertUnreachable() → compile error.
```

## What Makes This Work

| Mechanism | What It Guards |
|---|---|
| **Discriminated unions** (`state.kind`) | Which fields are available in each state — no more accessing `orderId` when the wizard hasn't paid yet |
| **Per-action payloads** | Every event carries exactly what it needs; no `any` smuggling |
| **Branded types** (`UserId` vs `OrderId`) | Swap protection at compile time; both resolve to `string` at runtime but TS keeps them distinct |
| **`assertUnreachable` / `never` check** | Adding a new `kind` to either the state or action union produces a compiler error unless ALL transition cases are updated |
| **Narrowed `targetStep` in GO_BACK** | `targetStep: "address" \| "billing"` lets us control per-state navigation rules — e.g., payment can only go back to billing, not address |
| **No explicit casts, no `as`, no `!`** | All typing flows structurally from the union shapes |

The key insight: instead of checking guards at runtime (`if (state.step !== 2) throw`), we encode validity into the type system itself. An invalid action simply cannot exist as a value of type `WizardAction` when paired with a given `WizardStatus` — the `never` in `assertUnreachable` acts as the exhaustiveness trap that fires at compile time, not at runtime.
