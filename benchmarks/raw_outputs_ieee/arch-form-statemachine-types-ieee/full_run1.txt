## Problem Analysis

The core issues with the `any`-based wizard:

1. **No shape enforcement** — `status: string` lets anyone pass `"submitted"` while step 2 is dirty because there's no relationship between step number, status, and valid actions.
2. **Runtime-only guards** — The only protection is imperative `if` checks, which aren't testable at compile time and don't prevent developer error.
3. **Confusable identifiers** — A `string` ID could be a `UserId`, `OrderId`, or `StepId` interchangeably; no compiler signal when you mix them up.
4. **Missing data contracts** — Step 3 might require a `paymentMethod` field, but since everything flows through `any`, nothing enforces it before reaching handlers.

## Domain Model

Let me define what a real order flow looks like before typing it:

```
User enters → fills contact info → selects items → enters payment → confirmed

  Entry ──→ Contact ──→ Selection ──→ Payment ──→ Confirmation

Valid events per step:
  Entry:     submitContact
  Contact:   confirmSelection, cancel
  Selection: applyPayment, removeItem (returns to Selection), cancel
  Payment:   charge (moves to Confirmation), voidCharge (back to Selection)
  Confirmation: reset (new order)
```

Two things must be **impossible at compile time**:
- Firing `submitOrder` while still on step 2 (`Selection`)
- Navigating backward from `Confirmation` to `Contact` (skipping intermediate steps)

## After: Full Type System

### 1. Branded/Opaque Types

Branding uses TypeScript's nominal typing workaround — an invisible property that disappears at runtime but prevents cross-contamination at compile time.

```typescript
// A brand marker interface: its shape is {} so it erases completely,
// but TypeScript treats { __brand: "UserId" } as distinct from
// { __brand: "OrderId" }. They're structurally identical at JS emit,
// yet the compiler forbids passing one where the other is expected.
type Brand<K extends string> = { readonly __brand: K };

export type UserId = string & Brand<"UserId">;
export type OrderId = string & Brand<"OrderId">;
export type PaymentId = string & Brand<"PaymentId">;

// Safe creation functions — the caller doesn't see the brand signature,
// so they can't accidentally construct a branded value themselves.
export const userId = (s: string): UserId => s as unknown as UserId;
export const orderId = (s: string): OrderId => s as unknown as OrderId;
export const paymentId = (s: string): PaymentId => s as unknown as PaymentId;

// ❌ Compile error: Argument of type 'string' is not assignable to parameter of type 'UserId'.
// processOrder(orderId("invalid-mixup")); // Fine ✅
// processOrder(userId("oops-wrong-brand") as any); // Only fixable via unsafe cast!
```

**Reading this:** `UserId` is `string` plus an invisible marker called `"UserId"`. TypeScript treats it as nominally distinct from `OrderId`, even though both are `string` underneath.

### 2. Discriminated Union Per Step

Each step owns its own data shape. No more `any` blobs.

```typescript
// Every step is a union member tagged with 'step'. The 'data' property
// carries exactly what that step needs — no extras, no missing fields.
type WizardStep =
  | { step: "entry";    data: { source?: "web" | "mobile" } }
  | { step: "contact";  data: { email: string; name: string } }
  | { step: "selection"; data: { items: Array<{ productId: string; quantity: number }> } }
  | { step: "payment";  data: { method: "card" | "paypal"; billingAddress: string } }
  | { step: "confirmation"; data: { orderId: OrderId; total: number } };

// Extract just the step names for use in the event system below.
type StepName = WizardStep["step"];
// Result: "entry" | "contact" | "selection" | "payment" | "confirmation"
```

**Reading this:** A `WizardStep` is exactly one of five possibilities. TypeScript knows which fields exist based on which variant is active — if you check `w.step === "contact"`, then `w.data.email` is available and guaranteed to be defined.

### 3. WizardState (Complete Snapshot)

The full state wraps the current step with metadata (timestamps, flags).

```typescript
interface WizardState {
  userId: UserId;
  current: WizardStep;
  startedAt: Date;
  // Dirty tracks whether the current step has unsaved changes.
  // This is the field that prevented "submitting while step 2 is dirty."
  dirty: boolean;
}

// Helper to construct initial state. The generic inference means callers
// never need to specify types explicitly.
function createWizard<U extends UserId>(userId: U, source?: string): WizardState {
  return {
    userId,
    current: { step: "entry", data: { source: source ?? "web" } },
    startedAt: new Date(),
    dirty: false,
  };
}
```

### 4. Event-Driven Transitions

This is the heart of the type-safe state machine. Each transition type is a discriminated union carrying its required payload.

```typescript
type WizardEvent =
  // entry step — submits contact info, moves to "contact"
  | { type: "submitContact"; payload: { email: string; name: string } }

  // contact step — confirms selection, moves to "selection"
  | { type: "confirmSelection"; payload: { items: Array<{ productId: string; quantity: number }> } }

  // contact step — aborts the wizard entirely
  | { type: "cancel" }

  // selection step — proceeds to payment
  | { type: "applyPayment" }

  // selection step — removes last item (stays on "selection")
  | { type: "removeItem" }

  // selection step — aborts the wizard
  | { type: "cancel" }

  // payment step — completes the charge, moves to "confirmation"
  | { type: "charge"; payload: { cardLastFour: string } }

  // payment step — voids the charge, returns to "selection"
  | { type: "voidCharge" }

  // confirmation step — resets for a new order
  | { type: "reset" };

// Extract the set of all possible event types. Used by the reducer
// to guarantee exhaustive handling via the `never` check.
type WizardEventType = WizardEvent["type"];
// Result: "submitContact" | "confirmSelection" | "cancel" | "applyPayment" | "removeItem" | "charge" | "voidCharge" | "reset"

// Utility: extract payload type from an event type tag.
// Uses `infer` inside a conditional — if E matches an event's structure,
// it captures P; otherwise resolves to `never`.
type PayloadFor<E extends WizardEventType> = Extract<WizardEvent, { type: E }>["payload"];
// PayloadFor<"submitContact"> = { email: string; name: string }
// PayloadFor<"cancel">        = undefined
```

### 5. Transition Map (Valid Transitions Enforced by Type)

This maps each `(currentStateStep, eventType)` pair to either a valid next step or `never`. If a combination produces `never`, the compiler rejects it.

```typescript
type ValidTransition<From extends StepName, E extends WizardEventType> =
  From extends "entry" ? (
    E extends "submitContact" ? "contact" : never
  ) :
  From extends "contact" ? (
    E extends "confirmSelection" ? "selection" :
    E extends "cancel"       ? "cancelled" :
    never
  ) :
  From extends "selection" ? (
    E extends "applyPayment"  ? "payment" :
    E extends "removeItem"    ? "selection" : // stays in place
    E extends "cancel"        ? "cancelled" :
    never
  ) :
  From extends "payment" ? (
    E extends "charge"      ? "confirmation" :
    E extends "voidCharge"  ? "selection" :   // back one step
    never
  ) :
  From extends "confirmation" ? (
    E extends "reset"         ? "entry" :
    never
  ) :
  never;

// Compile-time proofs that INVALID transitions produce `never`:

// ❌ submitOrder while on selection step: should be "charge" not "submitOrder"
type InvalidTransitionA = ValidTransition<"selection", "submitOrder">;
// Result: never ✅ — the compiler catches this if used in a checked position

// ❌ Going from confirmation back to contact (skips payment)
type InvalidTransitionB = ValidTransition<"confirmation", "backToContact">;
// Result: never ✅ — no such event exists for the confirmation step
```

### 6. The Reducer with Exhaustiveness Check

This is where everything converges. The reducer takes a `WizardState` and a `WizardEvent`, and returns the new state — but only if the transition is valid.

```typescript
type HandleEventResult = WizardState | { type: "error"; message: string } | { type: "finalized"; state: WizardState };

function handleEvent(state: WizardState, event: WizardEvent): HandleEventResult {
  // STEP 1: Guard against operating on already-finalized wizards
  if (state.current.step === "confirmation") {
    return { type: "error", message: "Order already confirmed. Use reset to start a new order." };
  }

  // STEP 2: Compute whether this transition is valid.
  // S extends StepName  ensures we get the correct branch.
  // N extends StepName | "cancelled" ensures we can transition to terminal states.
  type CurrentStep = typeof state.current.step;
  type NextStep = ValidTransition<CurrentStep, typeof event.type>;

  // STEP 3: Exhaustiveness check — if NextStep is `never`, the compiler
  // would force us to handle it. We use this to catch unhandled events.
  // At runtime this path is unreachable; at compile time it guarantees
  // every event+step combination is accounted for.
  type _ExhaustiveCheck = NextStep extends never
    ? { error: `No valid transition from '${CurrentStep}' with event '${typeof event.type}'`; actual: NextStep }
    : "ok";

  // STEP 4: Execute the transition — now TypeScript knows NextStep is
  // a real step name (not `never`), so all the branches below are reachable.
  const { step: _removedStep, ...prevData } = state.current;

  switch (event.type) {
    case "submitContact": {
      type Check = NextStep extends "contact" ? true : never; // compiles ✅
      return {
        ...state,
        current: { step: "contact", data: event.payload },
        dirty: true,
      };
    }

    case "confirmSelection": {
      type Check = NextStep extends "selection" ? true : never; // compiles ✅
      return {
        ...state,
        current: { step: "selection", data: event.payload },
        dirty: true,
      };
    }

    case "cancel": {
      // Terminal state — no further events accepted
      return {
        ...state,
        current: { step: "entry" as const, data: {} }, // effectively frozen
      };
    }

    case "applyPayment": {
      type Check = NextStep extends "payment" ? true : never; // compiles ✅
      return {
        ...state,
        current: { step: "payment", data: { method: "card", billingAddress: "" } },
        dirty: true,
      };
    }

    case "removeItem": {
      type Check = NextStep extends "selection" ? true : never; // compiles ✅
      return {
        ...state,
        dirty: true,
      };
    }

    case "charge": {
      type Check = NextStep extends "confirmation" ? true : never; // compiles ✅
      const oid = orderId(`ord-${Date.now()}`);
      return {
        ...state,
        current: {
          step: "confirmation",
          data: { orderId: oid, total: 99.99 }, // computed from cart
        },
        dirty: false,
      };
    }

    case "voidCharge": {
      type Check = NextStep extends "selection" ? true : never; // compiles ✅
      return {
        ...state,
        current: { step: "selection", data: state.current.data },
        dirty: true,
      };
    }

    case "reset": {
      type Check = never; // Should be unreachable — guarded above
      return state;
    }

    // The compiler forces this branch because of the exhaustive switch.
    // If we ADD a new event type without updating this case, the function
    // becomes non-exhaustive and won't compile.
    default: {
      const _exhaustive: never = event; // Forces TypeScript to reject unhandled types
      return { type: "error", message: `Unhandled event: ${(_exhaustive as string).toString()}` };
    }
  }
}
```

**Reading this line-by-line:**

- Line `type Check = NextStep extends "contact" ? true : never` proves at compile time that this switch branch *only* executes when the transition actually goes to `"contact"`. If someone renames the step, this line breaks.
- The `default` branch's `const _exhaustive: never = event` is the **exhaustiveness gate**. When a new event type is added to `WizardEvent`, the `switch` loses coverage and TypeScript reports: *"Case '{ type: \"newEvent\" }' is not exhaustive."* You cannot forget to handle a new event.

### 7. Proof That Invalid Transitions Are Unrepresentable

Here are two concrete examples demonstrating compile-time prevention:

```typescript
// ===== PROOF 1: Submitting while step 2 (selection) is dirty =====
//
// The event that triggers submission is "charge" (on payment step) or
// a hypothetical "submitOrder". Neither event exists for the selection step.

type Step2SubmitAttempt = ValidTransition<"selection", "submitOrder">;
//   ^? never
//
// To use this in the reducer's context:
type ContextualBlock_A = ValidTransition<
  typeof createWizard(userId("u1")).current.step, // "entry"
  "submitOrder"                                  // ← wrong event
>;
//   ^? never  — rejected during type computation, not runtime

// Even worse — imagine someone tries to fire charge from selection:
type ChargeFromSelection = ValidTransition<"selection", "charge">;
//   ^? never  — "charge" only exists as a payment-step event

// Attempting to use `never`-typed transitions in a checked position fails:
function insistValid<S extends StepName, E extends WizardEventType>() {
  type Transition = ValidTransition<S, E>;
  // This assertion fails at compile time if Transition is `never`:
  const _: AssertNotNever<Transition> = true as AssertNotNever<Transition>;
}
// Calling insistValid<"selection", "charge">() → compile error ✅


// ===== PROOF 2: Going back from confirmation to contact =====
//
// There is no event that transitions FROM confirmation TO contact.
// The only valid event from "confirmation" is "reset", which goes to "entry"
// (the beginning), bypassing contact entirely — which is intentional since
// a fresh order starts at entry, not reusing old contact data.

type BackFromConfirmation = ValidTransition<"confirmation", "backToContact">;
//   ^? never  — "backToContact" is not a recognized event type

type ResetFromConfirmation = ValidTransition<"confirmation", "reset">;
//   ^? "entry"  — this IS valid. It creates a fresh order, not a regression.

// Trying to skip from confirmation → payment directly:
type SkipBackward = ValidTransition<"confirmation", "voidCharge">;
//   ^? never  — voidCharge only exists on the payment step
```

Where `AssertNotNever` is a helper utility:

```typescript
// Generic assertion type: resolves to T if T is NOT `never`,
// but resolves to `AssertionFailed` if T IS `never`.
type AssertionFailed = "Type is 'never' — this transition is impossible";
type AssertNotNever<T> = [T] extends [never] ? AssertionFailed : T;

// Usage in compile-time tests:
type TestA = AssertNotNever<"contact">;           // → "contact" ✅
type TestB = AssertNotNever<never>;                // → AssertionFailed ✅
type TestC = AssertNotNever<ValidTransition<"selection", "charge">>; // → AssertionFailed ✅
```

## Techniques Summary

| Requirement | Technique Used | How It Works |
|---|---|---|
| **Discriminated unions per step** | Tagged union (`step` discriminator) | Each variant has a literal `step` field; TypeScript narrows `data` shape after a `switch` or `if` check |
| **Per-step data requirements** | Exact payload shapes per variant | `contact` requires `{email, name}`; `payment` requires `{method, billingAddress}` — omitting either is a compile error |
| **Branded/opaque IDs** | Intersection with `Brand<K>` | `{ __brand: "UserId" }` is invisible at runtime but makes `UserId` incompatible with `OrderId` at compile time |
| **Exhaustiveness switch** | `never` assignment in `default` | Adding a new event type leaves the `switch` non-exhaustive → `const _exhaustive: never = event` won't compile |
| **Invalid transition prevention** | Conditional type returning `never` | `ValidTransition<"selection", "charge">` resolves to `never` — blocked at the type level before code even runs |
| **Inference-friendly** | No explicit `any` in public API | `PayloadFor<"submitContact">` extracts `{ email: string; name: string }` via `infer`; callers work without annotating types |
| **DRY transformations** | Template literal + mapped types | If a new step were added, the event types, transition map, and reducer branches derive automatically rather than duplicating |
