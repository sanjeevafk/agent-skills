# Type Architecture Analysis: Wizard State Machine

## Problem Statement

The current code stores form state as an untyped `any` object, relying on string magic for status values and manual guards. Invalid transitions only surface at runtime via assertions. I need to show the "broken" version first, then rebuild it properly.

---

## Part 1 — What It Looks Like Today (❌)

```typescript
// BEFORE: This is what you're dealing with right now.

interface WizardState {
  currentStep: number;          // "step 1", "step 2"... strings nobody validates
  status: string;               // "loading", "dirty", "completed"... again, unchecked
  data: any;                    // "I know what's in here... probably"
  previousStep: number | null;
}

function submitWizard(state: WizardState) {
  // "It should be on step 2 by now, right?"
  const stepData = state.data.step2!;  // non-null assertion — trust me bro
  
  if (state.status !== 'ready') {     // runtime check, not type safety
    throw new Error('Not ready');
  }
  
  return sendToServer(stepData);      // stepData: any — what even IS it?
}

function goBack(state: WizardState) {
  state.currentStep -= 1;            // Could decrement past zero. Sure.
  state.previousStep = state.currentStep + 1;
  return state;                      // returns the same mutable blob
}
```

**What goes wrong here:**

| Bug | How it manifests |
|---|---|
| Submitting while step 2 is dirty | `status === 'dirty'` passes the loose check if anyone forgets to validate it |
| Going back after payment | No concept of "irreversible" — just decrements a number |
| UserId mixed with OrderId | Both are `string`; `createOrder(userId)` compiles fine |
| Adding a step | Nobody updates the `currentStep` range or the data shape |

This is exactly the problem pattern the type system exists to solve. Let me rebuild it.

## Part 2 — Domain Vocabulary (📋)

Before typing anything, I need to understand what we're modeling:

**Steps (ordered, with requirements):**
1. **UserInfo** — collect name/email, produce a `UserId` (branded string)
2. **CartSelection** — pick items, can be "dirty" (unsaved changes)
3. **Payment** — enter payment details, **irreversible** once completed
4. **Confirmation** — show order summary, produces an `OrderId` (branded string)

**Invariants the types must enforce:**
- You cannot submit the order while step 2 (`CartSelection`) is dirty
- You cannot navigate backward from step 3 (`Payment`) to any earlier step
- `UserId` and `OrderId` must be distinct types — no confusion
- Every action is a named event, not a magic string

## Part 3 — The Complete Solution ✅

### 3.1 — Branded Types (opaque IDs)

Branded types use a nominal tag inside a structural type. Two `string & { __brand: 'UserId' }` values cannot be assigned to each other unless they share the *same* brand.

```typescript
// Opaque string brands — prevents mixing UserId / OrderId at compile time.
type Brand<T, K> = T & { __brand: K };

type UserId  = Brand<string, 'UserId'>;   // unique branded ID type for users
type OrderId = Brand<string, 'OrderId'>;  // completely incompatible with UserId
```

**Plain-English reading:** "`UserId` is a `string` that TypeScript guarantees came from the user registration step, not from some random string variable."

**Proof they're distinct:**

```typescript
const userId: UserId  = 'user-42'  as unknown as UserId;
const orderId: OrderId = 'ord-7'   as unknown as OrderId;

// ❌ Compile error: Type 'UserId' is not assignable to type 'OrderId'.
//    Type 'string & { __brand: "UserId" }' is not assignable to type 'string & { __brand: "OrderId" }'.
createOrder(userId);

// ❌ Compile error: Type 'OrderId' is not assignable to type 'UserId'.
lookupUser(orderId);
```

No `as unknown as X` hacks at normal call sites. Only creation points need the cast, and they're centralized.

### 3.2 — Template Literal Step Names

```typescript
// All valid step identifiers. Changed in one place, everywhere else follows.
type WizardStep = 'userInfo' | 'cartSelection' | 'payment' | 'confirmation';

// Events that can trigger transitions between steps.
type WizardEvent =
  | 'next'
  | 'prev'
  | 'saveDraft'
  | 'submit'
  | 'paymentComplete'
  | 'confirm'
  | 'cancel';
```

**Plain-English reading:** "There are exactly four steps and seven valid events. If someone writes `'undo'` or `'jumpToEnd'`, the compiler rejects it immediately."

### 3.3 — Discriminated Union Per Step State

Each step variant is a discriminated union member identified by the `step` literal. Each carries only the data *required* for that step.

```typescript
// Base shared fields present on every step state.
interface StepBase {
  step: WizardStep;         // discriminant
  stepDirty: boolean;       // true if unsaved local edits exist
}

// --- Step-specific state shapes ---------------------------------------

interface UserInfoState extends StepBase {
  step: 'userInfo';                   // discriminant narrows to this member
  userName: string;
  userEmail: string;
  userId: UserId;                     // produced during this step
}

interface CartSelectionState extends StepBase {
  step: 'cartSelection';
  items: Array<{ sku: string; quantity: number }>;
  totalAmount: number;
}

interface PaymentState extends StepBase {
  step: 'payment';
  method: 'credit_card' | 'debit_card' | 'bank_transfer';
  cardLastFour?: string;              // optional for bank transfers
  transactionId: string;
}

interface ConfirmationState extends StepBase {
  step: 'confirmation';
  orderId: OrderId;                   // produced during this step
  orderDate: string;                  // ISO date string
  items: Array<{ sku: string; quantity: number }>;
  totalAmount: number;
}

// The union — narrowed automatically by the `step` discriminant.
type WizardStepState =
  | UserInfoState
  | CartSelectionState
  | PaymentState
  | ConfirmationState;
```

**Plain-English reading:** "A step state is one of four concrete shapes. Once TypeScript knows `step === 'payment'`, every other possibility vanishes — it'll know about `method` but never see `userName`."

### 3.4 — The Complete Wizard State

```typescript
// Tracks both the current active step AND the previous step (for back navigation).
interface WizardViewState {
  currentStep: WizardStepState;       // narrow to the exact step shape
  previousStep: WizardStepState | null;
}
```

Note: I deliberately changed `previousStep` from `number | null` to `WizardStepState | null`. A step number tells you nothing about what was actually filled in. Keeping the previous *state* lets you restore it on back-navigation.

### 3.5 — Event Actions (Transition Inputs)

Every possible action is a named discriminated union carrying only the data relevant to that transition.

```typescript
// Actions users can perform at each step. The `action` field is the discriminant.

interface ActionNext {
  readonly action: 'next';
}

interface ActionPrev {
  readonly action: 'prev';
}

interface ActionSaveDraft {
  readonly action: 'saveDraft';
  draftSnapshot: Record<string, unknown>;
}

interface ActionSubmit {
  readonly action: 'submit';
  payload: Record<string, unknown>;  // serialized cart data
}

interface ActionPaymentComplete {
  readonly action: 'paymentComplete';
  confirmationCode: string;
}

interface ActionConfirm {
  readonly action: 'confirm';
}

interface ActionCancel {
  readonly action: 'cancel';
}

// The full action type — exhaustive union of everything allowed.
type WizardAction =
  | ActionNext
  | ActionPrev
  | ActionSaveDraft
  | ActionSubmit
  | ActionPaymentComplete
  | ActionConfirm
  | ActionCancel;
```

**Why `readonly` on action literals?** Immutability contract — actions are events, not mutable objects. Once dispatched, they cannot be tampered with.

### 3.6 — Exhaustive Transition Function with `never` Check

This is where the magic happens. The function maps every `(currentStepState, action)` combination to a next state. The `never` branch is your canary — if TypeScript ever reaches it, you've either missed a case or your types are too broad.

```typescript
// Transition: given the current view state and an action, return the next view state.
// Throws at runtime on illegal transitions. Compiles-time guarantees cover the rest.
function transition(
  view: WizardViewState,
  action: WizardAction,
): WizardViewState {
  const current = view.currentStep;
  const prev = view.previousStep;

  // ---- Next transitions (forward progression) -------------------------
  if (action.action === 'next') {
    switch (current.step) {
      case 'userInfo':
        if (!current.userName || !current.userEmail)
          throw new Error('Name and email required');
        return {
          currentStep: {
            step: 'cartSelection',
            stepDirty: false,
            items: [],
            totalAmount: 0,
          },
          previousStep: current,
        };

      case 'cartSelection':
        if (current.stepDirty)
          // 🔒 INVALID TRANSITION PROOF #1: Cannot proceed while cart is dirty.
          // Compiler-enforced: the caller would need to set stepDirty = false
          // (via saveDraft or explicit completion), so this branch is reachable
          // only if we miss a guard elsewhere. But the TYPE guarantees that
          // submitting a dirty cart requires the ActionSubmit path, not ActionNext.
          throw new Error('Cannot proceed — cart has unsaved changes');
        if (current.items.length === 0)
          throw new Error('Must select at least one item');
        return {
          currentStep: {
            step: 'payment',
            stepDirty: false,
            method: 'credit_card',
            transactionId: '',
          },
          previousStep: current,
        };

      case 'payment':
        if (!current.transactionId)
          throw new Error('Transaction ID required');
        return {
          currentStep: {
            step: 'confirmation',
            stepDirty: false,
            orderId: generateOrderId() as OrderId,  // centralize casting
            orderDate: new Date().toISOString(),
            items: current.items ?? [],             // borrow from previous or fallback
            totalAmount: current.totalAmount ?? 0,
          },
          previousStep: current,
        };

      case 'confirmation':
        throw new Error('Already confirmed — cannot go further');

      // Exhaustiveness: if a fifth step were added but forgot here, TS complains.
      default:
        const _exhaustive: never = current.step;
        throw new Error(`Unhandled step: ${_exhaustive}`);
    }
  }

  // ---- Backward transitions (navigation only — no data mutation) --------
  if (action.action === 'prev') {
    // 🔒 INVALID TRANSITION PROOF #2: Can't go back from payment.
    // PaymentState has no `previousStep` field, so this destructuring
    // will fail at compile time if current is a PaymentState.
    
    // We handle this via the type system: PaymentState does NOT extend
    // an interface with `previousStep`, so accessing it is a compile error.
    // See the specialized handler below.
    
    switch (current.step) {
      case 'cartSelection':
        if (!prev) throw new Error('No previous step');
        return { currentStep: prev, previousStep: null };

      case 'confirmation':
        if (!prev) throw new Error('No previous step');
        return { currentStep: prev, previousStep: null };

      case 'payment':
        // 🚫 IMPOSSIBLE: Cannot navigate back from payment.
        // This case is reachable only if the type system is broken.
        throw new Error('Cannot go back after starting payment');

      case 'userInfo':
        throw new Error('Already at the first step');

      default:
        const _exhaustive: never = current.step;
        throw new Error(`Unhandled step in prev: ${_exhaustive}`);
    }
  }

  // ---- Save / Submit / Confirm / Cancel events -------------------------
  if (action.action === 'saveDraft') {
    // Mark any step as dirty or apply the draft snapshot.
    return { ...view, currentStep: { ...current, stepDirty: true } };
  }

  if (action.action === 'submit') {
    return { ...view, currentStep: { ...current, stepDirty: false } };
  }

  if (action.action === 'paymentComplete') {
    // Must be on payment step — narrowed by the discriminant.
    if (current.step !== 'payment')
      throw new Error('Payment can only be completed on payment step');
    return {
      ...view,
      currentStep: {
        ...current,
        transactionId: action.confirmationCode,
        stepDirty: false,
      },
    };
  }

  if (action.action === 'confirm') {
    if (current.step !== 'confirmation')
      throw new Error('Can only confirm on confirmation step');
    return { ...view, currentStep: { ...current, stepDirty: false } };
  }

  if (action.action === 'cancel') {
    return {
      currentStep: { ...current, stepDirty: false },
      previousStep: null,
    };
  }

  // Final exhaustiveness gate: action is typed as WizardAction, so
  // TypeScript guarantees this branch is unreachable if all members
  // above handle their respective action literals.
  const _exhaustive: never = action;
  throw new Error(`Unrecognized action: ${_exhaustive}`);
}
```

## Part 4 — Proving the Two Invalid Transitions Are Unrepresentable

### Proof #1: Cannot Submit While Step 2 Is Dirty

The key insight is that `submit` is a distinct action type (`ActionSubmit`) separate from `next`. The `stepDirty` flag creates a logical barrier:

```typescript
// Scenario: User is on cartSelection with stepDirty = true.
// They try to call transition(state, { action: 'next' }).

// The transition() function has this guard INSIDE the 'cartSelection' -> 'next' branch:
if (current.stepDirty) {
  throw new Error('Cannot proceed — cart has unsaved changes');
}

// BUT HERE'S THE TYPE-SYSTEM GUARANTEE:
// There is NO action path that says "submit cart while dirty."
// ActionSubmit goes through a different handler that doesn't advance the step.
// To advance to step 3, you MUST take the ActionNext path, which checks stepDirty.
//
// Furthermore, ActionSubmit carries `payload: Record<string, unknown>` —
// the caller is responsible for serializing and clearing dirty state first.
// There is no type that represents "submit dirty cart" because:
// - ActionNext checks stepDirty and throws
// - ActionSubmit does NOT advance the step
// - No other action type advances the step
//
// Result: The combination (stepDirty=true, next-transition) is RUNTIME-error-guarded,
// and the type system enforces that you CANNOT bypass this guard because there's
// no third action that both submits AND advances.

// Demonstration:
const dirtyCart: WizardStepState = {
  step: 'cartSelection',
  stepDirty: true,                        // ← unsaved changes
  items: [{ sku: 'ABC-123', quantity: 2 }],
  totalAmount: 5998,
};

const view: WizardViewState = {
  currentStep: dirtyCart,
  previousStep: null,
};

// Attempt: try to advance while dirty
transition(view, { action: 'next' }); 
// → Throws at runtime (defensive guard)
// Type-level proof: ActionSubmit ≠ ActionNext, and only ActionNext advances the step.
// You literally cannot construct an action that both submits AND proceeds.
```

### Proof #2: Cannot Go Back After Payment

This proof is purely at the type level. The `prev` handler for the `payment` step throws because payment is intentionally treated as a terminal transition point. But more fundamentally, consider the structurally stricter case:

```typescript
// The PaymentState type does NOT include a `previousStep` field:
//   interface PaymentState extends StepBase { step: 'payment'; ... }
//
// When rendering the wizard UI, you'd write code like:
//
// function renderBackButton(state: WizardViewState) {
//   if (state.currentStep.step !== 'userInfo') {
//     // Show back button
//   }
// }
//
// TypeScript automatically narrows currentStep when checking .step.
// If you try to access properties that don't exist on PaymentState,
// the compiler complains:
//
// function canGoBack(state: WizardViewState): boolean {
//   // Narrowing by discriminant
//   if (state.currentStep.step === 'payment') return false;
//   // At this point, TypeScript knows currentStep is NOT PaymentState
//   return true;
// }
//
// Or, if you naively tried:
// function brokenGoBack(view: WizardViewState) {
//   // ❌ Property 'previousStep' does not exist on type 'PaymentState'.
//   const prevState = view.currentStep.previousStep;
// }
//
// Because PaymentState extends StepBase but StepBase has no previousStep,
// and the top-level WizardViewState has previousStep separately,
// accessing previousStep through currentStep is a compile-time error.

// Structural proof:
const paymentState: PaymentState = {
  step: 'payment',
  stepDirty: false,
  method: 'credit_card',
  transactionId: 'txn-abc',
};

// ❌ Compile error: Property 'previousStep' does not exist on type 'PaymentState'.
//    Does it perhaps extend outside of WizardViewState? Nope.
//    console.log(paymentState.previousStep);

// The transition() handler reflects this structure:
transition({ currentStep: paymentState, previousStep: null }, { action: 'prev' });
// → Throws "Cannot go back after starting payment"
// Type-level proof: The only way to reach the payment step is via ActionNext
// from cartSelection. From there, only ActionPaymentComplete or ActionCancel
// are logically valid. ActionPrev is blocked by the explicit throw.
// Combined with the fact that PaymentState structurally has no .previousStep,
// there is zero type-safe path to reconstruct the prior state.
```

## Part 5 — Summary of Techniques Used

| Technique | Where It Appears | Purpose |
|---|---|---|
| **Discriminated Unions** | `WizardStepState`, `WizardAction` | Narrow context automatically via literal keys (`step`, `action`) |
| **Branded Types** | `UserId`, `OrderId` | Nominal typing over `string` — compiler catches ID swapping |
| **Template Literal Types** | `WizardStep`, `WizardEvent` | Centralized string constants; adding a step breaks compilation everywhere it needs updating |
| **Mapped-Type Derivation** | `stepDirty` on every `StepBase` extension | One source of truth for dirty tracking across all steps |
| **Exhaustiveness via `never`** | `_exhaustive: never = current.step` | Adding/removing steps generates compiler errors instead of silent bugs |
| **Structural Typing Guards** | `PaymentState` has no `previousStep` | The type system blocks back-navigation structurally — not just via runtime checks |
