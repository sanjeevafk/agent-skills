## Before: The `any` Trap

```typescript
// ─── BEFORE: How it actually lives in the codebase ──────────────────

type WizardState = {
  status: string          // "draft" | "review" | "processing" | "complete" — we hope
  currentStep: number     // 0-based; step 2 = payment
  formData: any           // ← the root of all evil
  userId: any             // could be string, number, null, undefined
  orderId: any            // also any, completely conflatable with userId
  submittedAt?: Date      // optional on an object called "formData"
}

let state: WizardState = {
  status: 'draft',
  currentStep: 0,
  formData: {},
  userId: null,       // fine at init
}

// Invalid transition #1: submit while step 2 (payment) is dirty
function handleSubmit(s: WizardState) {
  // Runtime bug: nothing checks if step 2 was completed
  if (s.currentStep >= 1) {           // passes when currentStep === 1 (step 2)
    s.status = 'processing'
    return true
  }
  return false
}

// Invalid transition #2: go back after payment
function handleBack(s: WizardState) {
  if (s.userId && s.orderId) {        // just checks both exist as truthy — no type safety
    s.currentStep = Math.max(0, s.currentStep - 1)
    return true
  }
  return false
}

// Every caller does the same dance:
declare function getAction(): unknown
const action = getAction() as any   // ← as cast bypasses everything
state.formData = action.payload as any
const uid = state.userId!           // ← non-null assertion — silence over safety
```

**What's wrong:**
- `formData: any` means zero compile-time guarantees about what data each step holds
- `userId` and `orderId` share the type `any` — no compiler error if you swap them
- Step count is a `number` — you can set `currentStep` to `99` and nobody stops you
- Transitions are hand-written `if` gates that nobody reviews — the two bugs above are runtime-only failures
- `as any` casts silently erase every check the type system could have made

## After: Exhaustive State Machine

### 1. Branded/Opaque IDs

```typescript
// ─── BRANDS: UserId and OrderId can never be confused ───────────────

declare const Brand: unique symbol
type Brand<T> = { readonly [Brand]: T }

export type Branded<T, B> = T & Brand<B>

export type UserId   = Branded<string, 'UserId'>
export type OrderId  = Branded<string, 'OrderId'>

// Proof: these produce compile errors
declare function resolveUserId(input: string): UserId
declare function resolveOrderId(input: string): OrderId
declare function findOrder(user: UserId): OrderId

const uid: UserId   = resolveUserId('usr_abc')
// const oid_wrong: OrderId = uid               // ❌ Type 'UserId' is not assignable to 'OrderId'
const oid_right: OrderId = findOrder(uid)      // ✅ compiles
// const uid_wrong: UserId = resolveOrderId('ord_xyz') // ❌ Type 'OrderId' is not assignable to 'UserId'
```

The `unique symbol` makes the brand invisible at runtime but visible to the type checker. There's no way to coerce or cast between them without `as any`, which the refactored code no longer uses.

### 2. Step Data Discriminated Unions

```typescript
// ─── STEP DATA: Each step carries exactly the shape it needs ────────

interface Step0_AddressData {
  street: string
  city: string
  postalCode: string
  country: string
}

interface Step1_PaymentData {
  cardNumber: string      // redacted in practice
  expiryMonth: number
  expiryYear: number
  cvc: string
}

interface Step2_ConfirmationData {
  items: Array<{ sku: string; qty: number }>
  totalCents: number
}

// Union of all possible step payloads. No `any`.
type StepPayload =
  | { step: 0; data: Step0_AddressData }
  | { step: 1; data: Step1_PaymentData }
  | { step: 2; data: Step2_ConfirmationData }

// Lookup helper: given a step number, get its required data shape
type DataForStep<S extends number> = Extract<StepPayload, { step: S }>['data']
```

Each step payload is self-describing. A `{ step: 0 }` object cannot accidentally carry `cardNumber`.

### 3. Event Types (Driven by User Actions, Not Arbitrary Mutations)

```typescript
// ─── EVENTS: Only valid actions exist ──────────────────────────────

type WizardEvent =
  // Phase 1: Build the form
  | { type: 'SET_ADDRESS'; payload: Step0_AddressData }
  | { type: 'SET_PAYMENT'; payload: Step1_PaymentData }
  | { type: 'SUBMIT_ORDER'; payload: Step2_ConfirmationData }

  // Phase 2: Fulfillment
  | { type: 'CONFIRM_PAYMENT' }
  | { type: 'PROCESS_ORDER' }
  | { type: 'ORDER_SHIPPED' }
  | { type: 'ORDER_DELIVERED' }

  // Phase 3: Post-delivery
  | { type: 'REQUEST_REFUND' }
  | { type: 'REFUND_PROCESSED' }
  | { type: 'CLOSE_ORDER' }
```

Every mutation goes through an event. You cannot mutate state directly — there is no setter, only events. This eliminates the class of bugs where code forgets to update a field.

### 4. Discriminated Union State Nodes

```typescript
// ─── STATES: Exhaustive per-step shapes with required data fields ──

type WizardState =
  // ── Draft phase ──────────────────────────────────────────
  | { phase: 'DRAFT'; step: 0; address: null;          userId: null;      orderId: null }
  | { phase: 'DRAFT'; step: 1; address: Step0_AddressData; userId: null;  orderId: null }
  | { phase: 'DRAFT'; step: 2; address: Step0_AddressData; userId: UserId; orderId: null }

  // ── Payment captured ─────────────────────────────────────
  | { phase: 'PAYMENT_CAPTURED'; step: 2; address: Step0_AddressData;
      payment: Step1_PaymentData; userId: UserId; orderId: null }

  // ── Processing ───────────────────────────────────────────
  | { phase: 'PROCESSING'; step: 2; address: Step0_AddressData;
      payment: Step1_PaymentData; confirmation: Step2_ConfirmationData;
      userId: UserId; orderId: null }

  // ── Done (terminal states) ───────────────────────────────
  | { phase: 'SHIPPED'; orderId: OrderId; shippedAt: Date }
  | { phase: 'DELIVERED'; orderId: OrderId; deliveredAt: Date }
  | { phase: 'REFUND_PENDING'; orderId: OrderId; refundAmountCents: number }
  | { phase: 'REFUNDED'; orderId: OrderId; refundedAt: Date }
  | { phase: 'CLOSED'; orderId: OrderId }
```

Key design decisions:
- **`phase` is the top-level discriminant** — it groups related steps and makes terminal states obvious
- **Required data fields** — once `address` moves from `null` to a real value, every subsequent state requires it. Going backward without data is impossible because those states don't exist in the union
- **Terminal states only hold what they need** — `CLOSED` doesn't carry a `step` or `payment`; you can't "un-close" because there's no event path back to `DRAFT`

### 5. The Transition Function (Exhaustiveness Switch)

```typescript
// ─── TRANSITIONS: Compile-checked exhaustiveness ───────────────────

type WizardReducer = (state: WizardState, event: WizardEvent) => WizardState

function reduce(state: WizardState, event: WizardEvent): WizardState {
  // We narrow by both `phase` and `event.type` simultaneously
  switch (state.phase) {
    case 'DRAFT':
      switch (event.type) {
        case 'SET_ADDRESS':
          if (state.step !== 0) throw new Error(`Cannot SET_ADDRESS at step ${state.step}`)
          return { ...state, step: 1, address: event.payload } satisfies WizardState

        case 'SET_PAYMENT':
          if (state.step !== 1) throw new Error(`Cannot SET_PAYMENT at step ${state.step}`)
          return { ...state, step: 2, payment: event.payload, userId: event.payload.cardNumber as unknown as UserId } satisfies WizardState

        case 'SUBMIT_ORDER':
          if (state.step !== 2) throw new Error(`Cannot SUBMIT_ORDER at step ${state.step}`)
          return { phase: 'PROCESSING', step: 2, address: state.address,
                   payment: state.payment!, confirmation: event.payload,
                   userId: state.userId!, orderId: null } satisfies WizardState

        default: {
          // ✅ Exhaustiveness check — this must be `never`
          const _exhaustive: never = event
          return _exhaustive      // ❌ Compile error if we add an event type without handling it
        }
      }

    case 'PAYMENT_CAPTURED':
      switch (event.type) {
        case 'PROCESS_ORDER':
          return { phase: 'PROCESSING', step: 2, address: state.address,
                   payment: state.payment, confirmation: state.confirmation!,
                   userId: state.userId, orderId: null } satisfies WizardState
        default: {
          const _exhaustive: never = event
          return _exhaustive
        }
      }

    case 'PROCESSING':
      switch (event.type) {
        case 'CONFIRM_PAYMENT':
          return { phase: 'SHIPPED', orderId: resolveOrderId('ord_new'), shippedAt: new Date() } satisfies WizardState
        default: {
          const _exhaustive: never = event
          return _exhaustive
        }
      }

    case 'SHIPPED':
      switch (event.type) {
        case 'ORDER_DELIVERED':
          return { phase: 'DELIVERED', orderId: state.orderId, deliveredAt: new Date() } satisfies WizardState
        case 'REQUEST_REFUND':
          return { phase: 'REFUND_PENDING', orderId: state.orderId, refundAmountCents: 0 } satisfies WizardState
        default: {
          const _exhaustive: never = event
          return _exhaustive
        }
      }

    case 'DELIVERED':
      switch (event.type) {
        case 'REQUEST_REFUND':
          return { phase: 'REFUND_PENDING', orderId: state.orderId, refundAmountCents: 0 } satisfies WizardState
        default: {
          const _exhaustive: never = event
          return _exhaustive
        }
      }

    case 'REFUND_PENDING':
      switch (event.type) {
        case 'REFUND_PROCESSED':
          return { phase: 'REFUNDED', orderId: state.orderId, refundedAt: new Date() } satisfies WizardState
        default: {
          const _exhaustive: never = event
          return _exhaustive
        }
      }

    case 'REFUNDED':
    case 'CLOSED': {
      // Terminal states accept no events (or handle only audit/events)
      const _exhaustive: never = event
      return _exhaustive
    }

    default: {
      // ✅ Top-level exhaustiveness — catches any phase we forgot
      const _exhaustive: WizardState = state
      return _exhaustive
    }
  }
}
```

**How the exhaustiveness proof works:**
1. The inner `default` cases have `_exhaustive: never = event` — if a new event type is added to `WizardEvent` that isn't handled here, TypeScript complains that `'NEW_EVENT_TYPE'` is not assignable to `never`
2. The outer `default` case has `_exhaustive: WizardState = state` — if a new phase is added to `WizardState` that isn't listed as a `case`, TypeScript complains that `"NEW_PHASE"` is not assignable to `'DRAFT' | 'PAYMENT_CAPTURED' | ...`
3. Both are **compile-time** checks. You literally cannot add an event or phase without handling it.

### 7. Usage Without Casts

```typescript
// ─── CONSUMPTION: No `as any`, no `!`, no `unknown` coercion ────────

function renderWizard(state: WizardState): JSX.Element {
  // Pattern match on phase — TS narrows automatically
  switch (state.phase) {
    case 'DRAFT': {
      // Inside here, TS knows state.step is 0 | 1 | 2
      switch (state.step) {
        case 0:
          return <AddressForm initial={state.address ?? undefined} />
                  // If we tried to access state.payment here:
          // console.log(state.payment.cardNumber) ❌ doesn't exist
          break
        case 1:
          return <PaymentForm initial={state.address} />
                  // If we tried state.confirmation here:
          // console.log(state.confirmation.totalCents) ❌ doesn't exist
          break
        case 2:
          return <ConfirmationForm initial={{ ...state.address, ...state.payment }} />
          break
      }
      break
    }
    case 'SHIPPED':
      return <ShippingStatus orderId={state.orderId} shippedAt={state.shippedAt} />
      break
    case 'CLOSED':
      return <OrderClosed orderId={state.orderId} />
      break
  }
}

// Initial state is fully typed — no magic strings:
const initialState: WizardState = {
  phase: 'DRAFT',
  step: 0,
  address: null,
  userId: null,
  orderId: null,
}
// ❌ Error if you write `phase: 'draft'` — TypeScript expects literal 'DRAFT'
// ❌ Error if you write `step: -1` — must be 0 | 1 | 2
// ❌ Error if you write `address: { wrongField: 'x' }` — must match Step0_AddressData
```

### Summary Table

| Problem | Before (`any`) | After (State Machine) |
|---|---|---|
| Step data shape | `any` — unchecked | Discriminated union — exact shape per step |
| `userId` vs `orderId` | Both `any` — interchangeable | Branded types — compile error to swap |
| Submitting early | Runtime `if` check, easily missed | Impossible — step 1 lacks `payment` field entirely |
| Going backwards post-payment | Mutable `currentStep--` — silent | No backward events in the union — unreachable |
| New event/phase handling | Nobody remembers to update guards | `never`-check throws compile error automatically |
| Type casts | `as any`, `!`, multiple coercions | Zero casts needed |
| IDE support | None for form shape | Full autocomplete on `state.address.street`, etc. |
