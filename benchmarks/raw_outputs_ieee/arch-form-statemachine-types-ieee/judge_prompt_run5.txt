## Problem Statement

A multi-step checkout wizard stores its entire form state as `any`. Each step has a loose `status: string` field. Navigating between steps uses `as` casts and `!` non-null assertions. Two specific runtime bugs exist:

1. **Submitting while step 2 is dirty** — the user hasn't completed shipping info, but the flow fires `handleSubmit` and crashes downstream when accessing `state.shippingAddress?.line1`.
2. **Going back after payment** — the user pays, then clicks "Back", resetting state mid-flight and causing double-charges or lost order data.

**What's wrong:**

| Issue | Impact |
|---|---|
| `formData: any` | Compiler lets you read `state.formData.doesNotExist` without complaint |
| `currentStep: string` | You can set it to `'foo'`, `'42'`, or `''` — no structural invariant |
| `action.type: string` | Typo `"SUBMITE"` silently falls through to `default` |
| Non-null assertions (`!`) | Crash on null/undefined at runtime, not at compile time |
| No transition guards | Dirty-step submission and post-payment rewind are valid actions |

### 1. Branded/Opaque IDs

Opaque identifiers prevent conflating different entity types at compile time. There is no way to construct a `UserId` or `OrderId` from a bare `string` without going through the factory.

```typescript
// ──────────────────────────────────────────────
// SECTION 1: Branded / opaque identifiers
// Branding uses a phantom property that appears
// in the type but has no runtime footprint.
// ──────────────────────────────────────────────

/** Opaque brand — `string & { readonly __brand: unique symbol }`.
 *
 * Reading `UserId` tells you: "this is not a plain string;
 * it was constructed by UserFactory.make()." */
declare const UserId: unique symbol;
declare const OrderId: unique symbol;
declare const StepToken: unique symbol;

export type UserId = string & { readonly [UserId]: true };
export type OrderId = string & { readonly [OrderId]: true };
export type StepToken = string & { readonly [StepToken]: unique symbol };

/** Factory functions — the only way to construct these IDs.
 *
 * Because of the brand, a raw `string` cannot be assigned to
 * `UserId` without casting, which signals to the developer
 * that verification is needed first. */
export const UserFactory = {
  make(raw: string): UserId {
    if (!raw || !/^U\d{6}$/.test(raw)) throw new Error(`Invalid userId: ${raw}`);
    return raw as UserId;          // cast only here, validated immediately
  },
};

export const OrderFactory = {
  make(raw: string): OrderId {
    if (!raw || !/^ORD-\d{8}$/.test(raw)) throw new Error(`Invalid orderId: ${raw}`);
    return raw as OrderId;
  },
};

/* ── Compile-time proof: you CANNOT mix up a UserId with an OrderId ── */

// ✅ works: both are strings under the hood

// ❌ COMPILE ERROR: UserId is not assignable to OrderId
function linkUserToOrder(userId: UserId, orderId: OrderId): void {}
const uid = UserFactory.make('U000001');
const oid = OrderFactory.make('ORD-000001');

// linkUserToOrder(oid, uid);             // 🔴 ERROR: OrderId ≠ UserId
// linkUserToOrder('U000001', oid);       // 🔴 ERROR: string ≠ UserId
```

## After — Exhaustive State Machine

### 1. Branded/Opaque IDs

Branding makes `UserId` and `OrderId` structurally distinct. You cannot assign one to the other, pass one where the other is expected, or accidentally compare them.

```ts
// Opaque brands — these properties are erased at emit, but exist at type level
declare const UserIdBrand: unique symbol;
export type UserId = string & { readonly [UserIdBrand]: 'UserId'; };

declare const OrderIdBrand: unique symbol;
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId'; };

// Constructor helpers — single point of entry, guarantees branding
function UserId(value: string): UserId {
  return value as UserId;
}
function OrderId(value: string): OrderId {
  return value as OrderId;
}

// Proof: cross-assignment fails at compile time
const uid: UserId = UserId("user-123");
const oid: OrderId = OrderId("order-456");

// @ts-expect-error — OrderId is not assignable to UserId
const bad1: UserId = uid as OrderId;

// @ts-expect-error — OrderId is not assignable to UserId
const bad2: UserId = oid;

// These work fine:
const good1: UserId = uid;
const good2: OrderId = oid;
```

**Why this works:** TypeScript's structural typing treats `string & { __brand: "UserId" }` as a separate type from `string & { __brand: "OrderId" }`. The intersection with a nominal brand property makes them incompatible, yet both remain compatible with `string` via explicit cast through the constructor helper.
