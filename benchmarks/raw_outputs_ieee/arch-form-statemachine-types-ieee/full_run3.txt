## The Problem with `any` + `as` Casts

The original code looks something like this:

```typescript
// BEFORE: What everyone writes first because it "compiles"
type WizardState = {
  status: string;        // "step1", "step2_dirty", "submitted"... magic strings everywhere
  data: any;             // no shape enforcement
  step: number;
};

function goTo(state: WizardState, step: number): WizardState {
  // Runtime guards instead of compile-time guarantees
  if (step === 3 && !state.data.shippingAddress) throw new Error("missing address");
  const newState = { ...state, step };
  // Caller must also use as-casts downstream
  return newState;
}

function submit(state: WizardState): Promise<Order> {
  const user = state.data.user as User;       // cast!
  const order = state.data.order as Order;     // another cast!
  // No way for the compiler to know user.email is required or that
  // paymentStatus === 'paid' — those are just string checks at runtime.
  return api.createOrder(order);
}
```

**What's wrong:**

| Issue | Consequence |
|---|---|
| `status: string` | Can be `"foo"` or `"undefined"` — no structural constraints |
| `data: any` | Loses ALL type information; `user.email?.toUpperCase()` compiles but crashes |
| `as User` casts | Silently swallows mismatches; `{ name: "x" } as User` passes |
| `!!` assertions | `!!state.data.payment` hides the null/undefined reality |
| Invalid transitions | Submitting while `step === 2 && dirty`? Go-back after payment? All silent runtime bugs |

TypeScript can't help because every field is typed as `any`, `string`, or both. We need to **encode the business rules as types**.

## After: Exhaustive State Machine Types

### 1. Branded/Opaque IDs

Prevents confusing `UserId` and `OrderId` at the type level — they share the same underlying `string` representation but are structurally distinct.

```typescript
// ── Branded IDs ──────────────────────────────────────────────

/**
 * An opaque brand. BrandId<User> narrows to just `string` underneath,
 * but BrandId<User> ≠ BrandId<Order> because the brand key is unique.
 */
declare const UserIdBrand: unique symbol;
export type UserId = string & { readonly [UserIdBrand]: 'UserId' };

declare const OrderIdBrand: unique symbol;
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId' };

/** Factory helpers — the only way to construct branded values. */
export const makeUserId = (id: string): UserId => id as UserId;
export const makeOrderId = (id: string): OrderId => id as OrderId;
```

**Plain-English reading:** A `UserId` is a `string` that carries a hidden tag called `UserIdBrand`. Since `unique symbol` creates a singleton type that can't be constructed by other code, no external value can accidentally produce a `UserId` without going through `makeUserId`. This means `assignOrder(makeUserId("abc"), makeOrderId("def"))` won't compile — the types are incompatible even though both are strings underneath.

### 2. Step Data Interfaces (Per-Step Requirements)

Each step carries only the data it owns. This eliminates `any` and ensures the compiler always knows what fields exist at each position.

```typescript
// ── Per-step data contracts ──────────────────────────────────

interface UserInfo {
  readonly userId: UserId;
  name: string;
  email: string;            // required — no optional marker
}

interface ShippingAddress {
  street: string;
  city: string;
  country: string;
  postalCode: string;
}

interface PaymentDetails {
  cardNumber: string;       // in production: tokenized reference
  expiryMonth: number;
  expiryYear: number;
  cvv: string;
}

type DeliveryConfirmation = {
  readonly orderId: OrderId;
  signatureCaptured: boolean;
  deliveredAt: Date;
};
```

No `any`, no loose shapes. If a step requires `email`, it's there and mandatory.

### 3. Discriminated Union States

Each state variant has a literal `step` discriminant and the specific data that step holds.

```typescript
// ── Exhaustive Step States ───────────────────────────────────

interface Step1_UserInfo {
  readonly step: 1;
  phase: 'idle';             // haven't started filling out
}

interface Step2_UserInfoFilled {
  readonly step: 2;
  phase: 'idle' | 'dirty';   // changed inputs but not yet submitted
  userInfo: UserInfo;
}

interface Step3_AddressSubmitted {
  readonly step: 3;
  phase: 'idle' | 'dirty';
  userInfo: UserInfo;
  address: ShippingAddress;
}

interface Step4_PaymentRequired {
  readonly step: 4;
  phase: 'idle' | 'dirty';
  userInfo: UserInfo;
  address: ShippingAddress;
  payment: PaymentDetails;
}

interface Step5_Complete {
  readonly step: 5;
  phase: 'complete';
  userInfo: UserInfo;
  address: ShippingAddress;
  payment: PaymentDetails;
  delivery: DeliveryConfirmation;
}

type WizardState =
  | Step1_UserInfo
  | Step2_UserInfoFilled
  | Step3_AddressSubmitted
  | Step4_PaymentRequired
  | Step5_Complete;
```

**Plain-English reading:** A `WizardState` can be one of five concrete shapes. If I pattern-match on `wizard.step === 1`, the compiler knows there's only `step` and `phase` — no `userInfo` exists yet. If `wizard.step === 3`, then `wizard.userInfo` and `wizard.address` are guaranteed present because they're declared on the `Step3_AddressSubmitted` interface. Zero `as` casts needed.

This is a **discriminated union** — TypeScript uses the literal `step: N` property to narrow the type automatically inside switches and conditionals.

### 4. Event Actions (Type-Safe Transitions)

Events encode what the user *did*. Each event explicitly states the source step (`from`) and target step (`to`). This makes the transition graph self-documenting.

```typescript
// ── Action Events ────────────────────────────────────────────

interface ActionSaveUserInfo {
  readonly kind: 'saveUserInfo';
  readonly from: 1;
  readonly to: 2;
  readonly payload: { userInfo: UserInfo };
}

interface ActionNextToAddress {
  readonly kind: 'nextToAddress';
  readonly from: 2;
  readonly to: 3;
  readonly payload: { address: ShippingAddress };
}

interface ActionBackFromAddress {
  readonly kind: 'backFromAddress';
  readonly from: 3;
  readonly to: 2;
  readonly payload: {};
}

interface ActionSavePayment {
  readonly kind: 'savePayment';
  readonly from: 3;
  readonly to: 4;
  readonly payload: { payment: PaymentDetails };
}

interface ActionBackFromPayment {
  readonly kind: 'backFromPayment';
  readonly from: 4;
  readonly to: 3;
  readonly payload: {};
}

interface ActionSubmitOrder {
  readonly kind: 'submitOrder';
  readonly from: 4;
  readonly to: 5;
  readonly payload: { delivery: DeliveryConfirmation };
}

type WizardAction =
  | ActionSaveUserInfo
  | ActionNextToAddress
  | ActionBackFromAddress
  | ActionSavePayment
  | ActionBackFromPayment
  | ActionSubmitOrder;
```

**Key observation:** The `from` and `to` fields are literal numbers. This is what makes the exhaustive switch below work. There is no room for ambiguity — `ActionSaveUserInfo.from` is literally the type `1`, not `number`.

### 5. The Transition Function with Never-Checked Exhaustiveness

```typescript
// ── Type inference helper ────────────────────────────────────

/**
 * Given a WizardAction, infer which data field gets added
 * during the transition. Uses `infer` inside a conditional type
 * to extract the payload shape from the action.
 */
type ExtractAddedField<A extends WizardAction> =
  A extends { payload: { [K: string]: unknown } }
    ? keyof A['payload'] extends infer K
      ? K extends string ? K : never
      : never
    : never;

// ── Pure transition function ─────────────────────────────────

function transition(
  state: WizardState,
  action: WizardAction
): WizardState {
  // Discriminate on both step AND action.kind for maximum safety
  switch (`${state.step}-${action.kind}`) {

    case '1-saveUserInfo':
      if (action.to !== 2) return unreachable(action);
      return { step: 2, phase: 'idle', userInfo: action.payload.userInfo };

    case '2-nextToAddress':
      if (action.to !== 3) return unreachable(action);
      return { step: 3, phase: 'idle', userInfo: state.userInfo, address: action.payload.address };

    case '3-backFromAddress':
      if (action.to !== 2) return unreachable(action);
      return { step: 2, phase: 'idle', userInfo: state.userInfo };

    case '3-savePayment':
      if (action.to !== 4) return unreachable(action);
      return {
        step: 4, phase: 'idle',
        userInfo: state.userInfo,
        address: state.address,
        payment: action.payload.payment,
      };

    case '4-backFromPayment':
      if (action.to !== 3) return unreachable(action);
      return {
        step: 3, phase: 'idle',
        userInfo: state.userInfo,
        address: state.address,
      };

    case '4-submitOrder':
      if (action.to !== 5) return unreachable(action);
      return {
        step: 5, phase: 'complete',
        userInfo: state.userInfo,
        address: state.address,
        payment: state.payment,
        delivery: action.payload.delivery,
      };

    // ── Exhaustiveness assertion ─────────────────────────────
    // If the compiler reaches here, we forgot a case.
    // The type of `action` narrows to `never` in every reachable branch above,
    // so this parameter receives only the impossible remainder.
    default:
      const _exhaustiveCheck: never = action;
      return _exhaustiveCheck;
  }
}
```

**Why this is powerful:**

1. **The `_exhaustiveCheck: never` line**: At this point, TypeScript has narrowed `action` through every `case` string match. If we ever add a new action to `WizardAction` without handling it, the `default` block's `_exhaustiveCheck` assignment would fail to compile — `action` wouldn't be assignable to `never`. This is the "compile-time lint" that catches missed transitions.

2. **State narrowing via discriminants**: Inside `'3-backFromAddress'`, `state` has been narrowed to `Step3_AddressSubmitted` by the switch string. Therefore `state.userInfo` and `state.address` are fully typed — no `as` casts, no `undefined` checks.

3. **Forward references are safe**: `state.userInfo` in step 3→4 works because the state entering step 4 already contains `userInfo` (carried over from step 2). The type system tracks this chain implicitly through the transition outputs matching the next state's inputs.

```typescript
  //         Type '{ kind: "submitOrder"; from: 2; ... }' is not assignable to type
```

The literal type mismatch (`from: 2` vs. required `from: 4`) is caught at compile time. There is no `any` to hide behind.

```typescript
let state: WizardState = { step: 1, phase: 'idle' };

  from: 1,
  to: 2,
  payload: { userInfo: makeUser() },
});
//     ^ state is now WizardState narrowed to Step2_UserInfoFilled
//     ^ state.userInfo is available directly — no casting

// Navigate to address → step 2 → step 3

  kind: 'nextToAddress',
  from: 2,
  to: 3,
  payload: { address: makeAddress() },
});
//     ^ state now carries userInfo + address

// Oops, want to go back → step 3 → step 2
state = transition(state, {
  kind: 'backFromAddress',
  from: 3,
  to: 2,
  payload: {},
});
//     ^ state is Step2_UserInfoFilled again, userInfo preserved

// Confirm address → step 2 → step 3 (re-entered)
state = transition(state, {
  kind: 'nextToAddress',
  from: 2,
  to: 3,
  payload: { address: makeAddress() },
});

// Submit payment → step 3 → step 4
state = transition(state, {
  kind: 'savePayment',
  from: 3,
  to: 4,
  payload: { payment: makePayment() },
});

// Finalize → step 4 → step 5
state = transition(state, {
  kind: 'submitOrder',
  from: 4,
  to: 5,
  payload: { delivery: makeDelivery() },
});

//     ^ state is now Step5_Complete — terminal
//     ^ state.delivery.signatureCaptured: boolean is known
//     ^ state.delivery.orderId: OrderId is the branded type
//     ^ No casts, no null checks, no runtime surprises
```

### 8. Pattern Matching at Call Sites

Because every state is a discriminated union, consumers of `WizardState` get automatic narrowing:

```typescript
function renderWizard(wizard: WizardState): JSX.Element {
  switch (wizard.step) {
    case 1:
      return <UserInfoForm />;
      //     ^ TypeScript knows: wizard has { step: 1; phase: 'idle' }
      //       No userInfo available — compiler enforces you can't read it

    case 2:
    case 3:
      // Here: wizard is Step2_UserInfoFilled | Step3_AddressSubmitted
      // wizard.userInfo is available in both variants (same shape!)
      return <ReviewStep userInfo={wizard.userInfo} />;

    case 3:
      // Here: wizard is specifically Step3_AddressSubmitted
      return <AddressForm address={wizard.address} />;
      //     ^ wizard.address is ShippingAddress — fully typed

    case 4:
      return <PaymentForm payment={wizard.payment} />;

    case 5:
      return <DeliveryReceipt orderId={wizard.delivery.orderId} />;
      //     ^ wizard.delivery: DeliveryConfirmation, orderId: OrderId (branded)

    // Exhaustiveness: if we ever add a Step6, the compiler warns
    const _unreachable: never = wizard.step;
    return <UnexpectedStepError step={_unreachable} />;
  }
}
```

## Summary of Techniques Used

| Technique | Where It Appears | Purpose |
|---|---|---|
| **Discriminated Unions** | `WizardState` variants | Step-based narrowing with zero `any` |
| **Branded Types** (`unique symbol`) | `UserId`, `OrderId` | Prevent ID confusion at compile time |
| **Literal Types** | `from: 1`, `to: 2`, `step: 3` | Encode transition graph as type-level constraints |
| **Exhaustiveness Check** (`: never`) | `transition()` default, `renderWizard()` fallthrough | Catch missing cases when adding new steps/actions |
| **Mapped Type Extraction** (`infer` in `ExtractAddedField`) | Payload field inference | Derive what data each action introduces |
| **`satisfies` operator** | Proof blocks | Validate object literals against type constraints without widening |

The total payoff: **zero runtime guards for valid-state assumptions**, **zero `as` casts**, and **two previously invisible runtime bugs are now impossible to express** because the type system rejects them before they reach the browser.
