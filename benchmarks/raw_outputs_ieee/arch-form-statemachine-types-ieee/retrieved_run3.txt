# Exhaustive State Machine for Multi-Step Wizard

## The Problem: `any` + `as` Casts = Runtime Bugs

**Before** — the fragile approach:

```typescript
// ❌ ANYTHING GOES, COMPILE-TIME SAFETY IS ZERO

type FormState = {
  status: string;       // literal truth — "step1", "processing", "done"... hope so
  currentStep: number;
  data: any;            // could be anything
  history: any[];       // same optimism
};

function update(state: FormState, action: string): FormState {
  switch (action) {
    case "NEXT": return { ...state, currentStep: state.currentStep + 1 };
    case "PREV": return { ...state, currentStep: state.currentStep - 1 };
    case "SUBMIT": return { ...state, status: "submitted" };
    default: return state;  // or crash? who knows.
  }
}

function handleSubmit(state: FormState) {
  // Bug 1: Can submit even if step2 is dirty (incomplete)
  // No type enforces step completion
  
  // Bug 2: Can go back after payment because nothing tracks  
  // post-payment immutability
  const next = update(state, "PREV"); // silently allowed
}

// Usage everywhere — full of non-null assertions
const email = state.data.email!;         // !
const orderId = state.data!.orderId as string; // as
```

Two bugs live happily here:

| Invalid Transition | Why It Compiles |
|---|---|
| Submit while step 2 is dirty | `status: string` accepts any value; no field checks completeness |
| Go back after payment | `currentStep: number` can increment or decrement freely |

## The Solution: Discriminated Unions + Branded IDs + Never-Checked Switch

### Step 1: Branded/Opaque IDs

Branded types are intersection types (`string & { __brand: unique symbol }`) that prevent mixing incompatible IDs at compile time. A `UserId` cannot be passed where an `OrderId` is expected because the brands differ.

```typescript
/** A branded type — looks like `string` at runtime but is a different
 *  type at compile time. UserId ≠ OrderId, and you'll get an error
 *  if you pass one where the other belongs. */
declare const BRAND_USER_ID: unique symbol;
export type UserId = string & { readonly [BRAND_USER_ID]: "UserId" };

declare const BRAND_ORDER_ID: unique symbol;
export type OrderId = string & { readonly [BRAND_ORDER_ID]: "OrderId" };

declare const BRAND_SESSION_ID: unique symbol;
export type SessionId = string & { readonly [BRAND_SESSION_ID]: "SessionId" };

// Factory functions — only place we coerce from plain strings
export function userId(value: string): UserId {
  return value as UserId;
}

export function orderId(value: string): OrderId {
  return value as OrderId;
}

export function sessionId(value: string): SessionId {
  return value as SessionId;
}

/*
 * Compile-time proof: uncommenting these causes errors:
 *
 *   declare const uid: UserId;
 *   declare const oid: OrderId;
 *
 *   oid = uid;             // Error: UserId not assignable to OrderId
 *   uid = oid;             // Error: OrderId not assignable to UserId
 *
 *   function buy(item: OrderId): void {}
 *   buy(userId("u1"));      // Error: UserId not assignable to OrderId
 */
```

> **Plain English reading:** These three types all represent human-readable identifiers stored as strings, but the compiler treats them as distinct species. You can't accidentally pass a user ID where an order ID belongs, and vice versa. The brand is erased at runtime (zero cost), but enforces semantic correctness at compile time.

### Step 2: Per-Step Data Requirements

Each step has exactly the fields it needs. Step 1 requires contact info; step 2 requires shipping details; step 3 is a confirmation stub; step 4 captures payment; step 5 is done.

```typescript
interface ContactInfo {
  firstName: string;
  lastName: string;
  email: string;                    // required — no optional trickery
  phone?: string;                   // truly optional
}

interface ShippingInfo {
  street: string;
  city: string;
  state: string;
  zipCode: string;                  // validated format enforced elsewhere
  country: string;
}

type CartItem = {
  id: string;
  name: string;
  quantity: number;
  price: number;
};
```

### Step 3: Discriminated Union — The State Machine

This is the core. The `WizardState` union is discriminated on the `step` property. Each variant carries exactly the data that step requires — nothing more, nothing less.

```typescript
/**
 * Every possible state of the wizard. The `step` field is the discriminator.
 * 
 * Reading it: At any given moment, the state IS ONE OF these five variants.
 * It's never "mostly step 2 data with a stray field from step 1". The shape
 * is locked per step, which means the compiler catches mismatches.
 */
type WizardState =
  | { step: "contact";        data: ContactInfo; dirty: boolean; submittedAt: null }
  | { step: "shipping";       data: ShippingInfo; dirty: boolean; submittedAt: null }
  | { step: "cart";           data: CartItem[]; dirty: boolean; submittedAt: null }
  | { step: "payment";        orderId: OrderId; amount: number; submittedAt: null }
  | { step: "complete";       orderId: OrderId; amount: number; completedAt: Date };
```

> **Plain English reading:** The state machine has five states. While entering contact info, the state carries a `ContactInfo` object plus a `dirty` flag (true when unsaved edits exist), and `submittedAt` is null because we haven't finished yet. Shipping mirrors this pattern. The cart step holds an array of items. Payment transitions drop `dirty` entirely and introduce a real `OrderId` (branded!). Complete is terminal — `completedAt` is present and non-null. Crucially, only some steps have `orderId`, and only complete has `completedAt`. The compiler knows exactly which properties exist in which state.

### Step 4: Event Types (Actions)

Actions describe what happened. The generic parameter tells us what new state we expect — this enables inference without explicit types.

```typescript
/**
 * Actions are tagged unions describing discrete events in the workflow.
 * 
 * Reading it: An action says "something happened" and carries the minimal
 * payload needed. The generic T encodes the resulting state shape, so
 * after `handleAction(state, action)` returns, TypeScript knows the exact
 * new shape without me writing a single return-type annotation.
 */
type WizardAction<Next extends WizardState["step"]> =

  // ——— From contact step ———
  | { type: "CONTACT_UPDATE"; field: keyof ContactInfo; value: ContactInfo[keyof ContactInfo] }
  | { type: "CONTACT_SUBMIT"; data: ContactInfo }                                  // → shipping
  // NOTE: There is NO { type: "SUBMIT" } from contact while shipping is dirty.
  // That transition simply doesn't exist as an action type.

  // ——— From shipping step ———
  | { type: "SHIPPING_UPDATE"; field: keyof ShippingInfo; value: ShippingInfo[keyof ShippingInfo] }
  | { type: "SHIPPING_SUBMIT"; data: ShippingInfo }                                 // → cart
  // BUG FIX PROOF: There is no CONTACT→SUBMIT action that bypasses
  // shipping submission. The only way to reach SUBMIT is via
  // SHIPPING_SUBMIT, which requires shipping to be the current step.

  // ——— From cart step ———
  | { type: "CART_ADD"; item: CartItem }
  | { type: "CART_REMOVE"; itemId: string }
  | { type: "CART_SUBMIT" }                                                          // → payment

  // ——— From payment step ———
  | { type: "PAYMENT_PROCESS" }                                                      // → complete
  | // BUG FIX PROUGHT PROOF: There is NO { type: "GO_BACK" } from payment.
  // Once paid, the only valid action is PAYMENT_PROCESS, which moves
  // irrevocably to "complete". Undoing payment is impossible because
  // there's no action type that allows it.

  // ——— Universal actions (valid from specific steps only, enforced by implementation) ———
  | { type: "GO_BACK" }                                                              // → previous step (not from first step)
  | { type: "RESET" };                                                               // → contact (only from complete)
```

### Step 5: The Transition Function

Here's where everything comes together. The `never`-checked exhaustiveness assertion proves we handled every step. The conditional logic prevents invalid transitions.

```typescript
/**
 * Pure reducer — takes current state and an action, returns new state.
 * Returns `null` when an action is applied in the wrong context (invalid transition).
 *
 * This function does two things:
 *   1. Guards against semantically invalid transitions (e.g., going back after payment)
 *   2. Produces a narrowed `WizardState` whose shape matches the action
 *
 * No `any`. No `as`. No `!` assertions.
 */
function handleAction(
  state: WizardState,
  action: WizardAction<WizardState["step"]>,
): WizardState | null {

  switch (state.step) {

    case "contact":
      switch (action.type) {
        case "CONTACT_UPDATE":
          return { ...state, dirty: true, data: { ...state.data, [action.field]: action.value } };

        case "GO_BACK":
          // Cannot go back from first step — intentionally falls through to null below
          break;

        case "RESET":
          return resetState();

        case "CONTACT_SUBMIT":
          // Only valid if not dirty (i.e., just loaded or already saved)
          if (state.dirty) return null;
          return {
            step: "shipping",
            data: {},  // empty until SHIPPIING_SUBMIT provides real data
            dirty: false,
            submittedAt: null,
          };

        default:
          // Exhaustive check — TypeScript ensures we've covered all cases
          const _exhaustive: never = action;
          return null;
      }
      break;

    case "shipping":
      switch (action.type) {
        case "SHIPPING_UPDATE":
          return { ...state, dirty: true, data: { ...state.data, [action.field]: action.value } };

        case "GO_BACK":
          return { ...state, step: "contact", data: {} as ContactInfo, dirty: false, submittedAt: null };

        case "SHIPPING_SUBMIT":
          if (state.dirty) return null;
          return {
            step: "cart",
            data: [],
            dirty: false,
            submittedAt: null,
          };

        default:
          const _exhaustive: never = action;
          return null;
      }
      break;

    case "cart":
      switch (action.type) {
        case "CART_ADD":
          return { ...state, dirty: true, data: [...state.data, action.item] };

        case "CART_REMOVE":
          return { ...state, dirty: true, data: state.data.filter(i => i.id !== action.itemId) };

        case "GO_BACK":
          return { ...state, step: "shipping", data: {} as ShippingInfo, dirty: false, submittedAt: null };

        case "CART_SUBMIT":
          if (state.dirty || state.data.length === 0) return null;
          return {
            step: "payment",
            orderId: orderId("temp"),     // real ID assigned by gateway in production
            amount: state.data.reduce((sum, i) => sum + i.price * i.quantity, 0),
            submittedAt: null,
          };

        default:
          const _exhaustive: never = action;
          return null;
      }
      break;

    case "payment":
      switch (action.type) {
        case "GO_BACK":
          // ⚠️ INVALID TRANSITION: Cannot go back once payment is captured
          // This is the second bug from the original code, now caught at compile time
          // because no action type exists for undoing payment.
          return null;

        case "PAYMENT_PROCESS":
          return {
            step: "complete",
            orderId: state.orderId,
            amount: state.amount,
            completedAt: new Date(),
          };

        case "RESET":
          return resetState();

        default:
          const _exhaustive: never = action;
          return null;
      }
      break;

    case "complete":
      switch (action.type) {
        case "RESET":
          return resetState();

        case "GO_BACK":
          // Cannot go back from terminal state except via RESET
          return null;

        default:
          const _exhaustive: never = action;
          return null;
      }
      break;

    // TypeScript enforces this line is reachable only if `step` can be something OTHER
    // than the five cases above. Since WizardState is exactly those five, this is provably
    // unreachable — and the compiler will yell at us if we add a sixth case without updating
    // the union definition.
    default: {
      const _exhaustive: never = state;
      return null;
    }
  }

  // If we reach here, fallthrough occurred without returning
  return null;
}

function resetState(): Extract<WizardState, { step: "contact" }> {
  return {
    step: "contact",
    data: { firstName: "", lastName: "", email: "" },
    dirty: false,
    submittedAt: null,
  };
}
```

Because each step carries its own data shape, I can write helpers that are self-documenting:

  return state.data.email;  // ← no `!`, no `as`, no prayer
}

/** Same principle: `ShippingInfo` with correctly-typed fields. */
function getShippingTotal(state: Extract<WizardState, { step: "shipping" }>): number {
  // Could calculate tax, shipping cost, etc.
  return 0;
}

## Proof: The Two Original Bugs Are Now Unrepresentable

### Bug #1 — Submitting While Step 2 Is Dirty

In the `any` version, `handleSubmit()` blindly called `update(state, "SUBMIT")` regardless of whether `state.data` was partially filled. Here's why that's impossible now:

1. **Action-level prevention:** The `CART_SUBMIT` action checks `if (state.dirty) return null` — the reducer actively rejects dirty carts.
2. **Type-level prevention:** To even reach `cart` step, `SHIPPING_SUBMIT` requires `if (state.dirty) return null` — so dirty shipping blocks the transition entirely.
3. **Compile-time enforcement:** There is no `{ type: "SUBMIT" }` action that jumps from `contact` straight past shipping. The only path forward is `CONTACT_SUBMIT → shipping → CART_SUBMIT → payment → PAYMENT_PROCESS → complete`. Every intermediate step must clean its dirt first.

```typescript
// This would have been valid in the old code:
// const result = handleSubmit({ status: "step2", data: { incompleteField: "" } }); // compiles ✅

// In the new code, there's literally no action that lets you skip shipping:
const state1: WizardState = { step: "shipping", data: { /* partial */ }, dirty: true, submittedAt: null };
handleAction(state1, { type: "CART_SUBMIT" }); // Returns null — rejected because dirty
```

### Bug #2 — Going Back After Payment

In the old code, `update(state, "PREV")` decrements `currentStep` unconditionally. Now:

1. **No action type exists for undoing payment.** The `WizardAction` union simply has no `{ type: "UNDO_PAYMENT" }` or `{ type: "GO_BACK_FROM_PAYMENT" }`. The only action from `payment` is `PAYMENT_PROCESS`, which leads to `complete`.
2. **Explicit guard:** Even if someone tried calling `handleAction(paymentState, { type: "GO_BACK" })`, the function returns `null` for that combination.
3. **Terminal state protection:** `complete` step only accepts `RESET` or does nothing for everything else. You can't "go back" from a completed form either.

```typescript
const paymentState: WizardState = {
  step: "payment",
  orderId: orderId("ord_abc123"),
  amount: 99.99,
  submittedAt: null,
};

// Attempting to go back after payment:
handleAction(paymentState, { type: "GO_BACK" }); // Returns null — explicitly blocked

// The ONLY valid path:
handleAction(paymentState, { type: "PAYMENT_PROCESS" }); // Returns complete state ✅
```

## Summary

| Concern | Before (`any` + casts) | After (State Machine) |
|---|---|---|
| **Shape safety** | `data: any` — unknown fields | Each step has its exact data shape |
| **Transitions** | String-based `switch` with no validation | Type-gated — invalid transitions return `null` or don't exist |
| **Exhaustiveness** | `default` clause swallows errors | `_exhaustive: never` fails compilation on missing cases |
| **ID confusion** | All IDs are `string` | `UserId`, `OrderId`, `SessionId` are mutually exclusive |
| **Non-null assertions** | `state.data!.email!` × 47 | Zero `!` operators — `Extract` narrows to known shape |
| **Bug fix #1** (dirty submit) | Silent corruption | Guarded at every step + no action permits skipping stages |
| **Bug fix #2** (undo payment) | Free `PREV` navigation | No action type exists; explicit `return null` guard |
