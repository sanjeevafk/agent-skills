## Before — What's Broken

Here's the anti-pattern the question describes — `any`, string-literal guards, `as` casts, non-null asserts, and switch-on-string that the compiler won't check:

```ts
type FormState = {
  userId: any;        // 🚨 any — could be number, string, null, Date, anything
  orderId: any;       // 🚨 same — indistinguishable from userId at compile time
  status: string;     // 🚨 "dirty" vs "StepInProgress" vs whatever you call it
  currentStep: string;// 🚨 not constrained
  steps: any[];       // 🚨 array of unknowns
};

// Event types — all loosely-typed
type FormAction =
  | { type: 'SET_STEP'; payload: { step: string } }
  | { type: 'SUBMIT_STEP'; payload: { stepId: string } }
  | { type: 'GO_BACK' }
  | { type: 'PROCESS_PAYMENT'; payload: any }
  | { type: 'COMPLETE_ORDER' };

// Transition function — runtime-only guards, unchecked switches
function reduce(state: FormState, action: FormAction): FormState {
  switch (state.status) {          // ← NOT exhaustive; compiler ignores missing cases
    case 'StepInProgress':
      if (action.type === 'SUBMIT_STEP') {
        const stepIndex = state.steps.findIndex(s => s.stepId === action.payload.stepId);
        state.steps[stepIndex].valid = true;  // 🚨 non-null assertion chain
        return { ...state, status: 'StepCompleted' };
      }
      break;

    case 'StepCompleted':
      if (action.type === 'GO_BACK') {
        return { ...state, currentStep: String(Number(state.currentStep) - 1) };
      }
      if (action.type === 'PROCESS_PAYMENT') {
        return {
          ...state,
          orderId: action.payload.orderId as any,
          status: 'PaymentProcessing',
        };
      }
      break;

    case 'PaymentProcessing':
      if (action.type === 'COMPLETE_ORDER') {
        return { ...state, status: 'OrderComplete' };
      }
      break;

    default:
      // 🚨 No `never` check — silently ignores unknown statuses forever
  }
  throw new Error(`Invalid transition: ${state.status} + ${action.type}`);
}
```

**What this means for the two invalid transitions:**

| Transition | What happens today | Why |
|---|---|---|
| `SUBMIT_STEP` while step 2 is dirty | **Compiles fine**, crashes at runtime inside `findIndex` / bracket access | `status: 'dirty'` falls into `default` → throws at runtime, but nothing stops calling `SUBMIT_STEP` when step data is absent |
| `GO_BACK` after payment | **Compiles fine**, corrupts state (numeric conversion of orderId, wrong next step) | Any action goes to any state; `GO_BACK` works against `'OrderComplete'` with zero guard |

Both are silent compilation-success bugs. Let me fix them with proper typing.

## After — Exhaustive State Machine

### 1. Branded/Opaque IDs

Branding makes `UserId` and `OrderId` structurally distinct. You cannot assign one to the other, pass one where the other is expected, or accidentally compare them.

```ts
// Opaque brands — these properties are erased at emit, but exist at type level
declare const UserIdBrand: unique symbol;
export type UserId = string & { readonly [UserIdBrand]: 'UserId'; };

declare const OrderIdBrand: unique symbol;
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId'; };

// Constructor helpers — single point of entry, guarantees branding
function UserId(value: string): UserId {
  return value as UserId;
}
function OrderId(value: string): OrderId {
  return value as OrderId;
}

// Proof: cross-assignment fails at compile time
const uid: UserId = UserId("user-123");
const oid: OrderId = OrderId("order-456");

// @ts-expect-error — OrderId is not assignable to UserId
const bad1: UserId = uid as OrderId;

// @ts-expect-error — OrderId is not assignable to UserId
const bad2: UserId = oid;

// These work fine:
const good1: UserId = uid;
const good2: OrderId = oid;
```

**Why this works:** TypeScript's structural typing treats `string & { __brand: "UserId" }` as a separate type from `string & { __brand: "OrderId" }`. The intersection with a nominal brand property makes them incompatible, yet both remain compatible with `string` via explicit cast through the constructor helper.

### 2. Step Data Types (Discriminated Unions per Step)

Each step contributes specific data fields. Only the currently-active step's data shape exists in the state at any given time.

```ts
// Each step carries its own required fields — nothing is optional within its shape
interface Step1PersonalData {
  firstName: string;
  lastName: string;
  email: string;
}

interface Step2AddressData {
  street: string;
  city: string;
  zipCode: string;
  country: string;
}

interface Step3PaymentData {
  cardNumber: string;
  expiryMonth: number;
  expiryYear: number;
  cvv: string;
}
```

### 3. The State Discriminated Union

This is the core model. The `step` discriminant determines which data field exists and what actions are valid. There are no `any`, no loose strings.

```ts
type FormState =
  | {
      step: 'personal';           // Exact literal — not a free string
      status: 'draft' | 'dirty';  // Within this step, these are the only valid statuses
      data: Step1PersonalData;
    }
  | {
      step: 'address';
      status: 'draft' | 'dirty';
      data: Step2AddressData;
    }
  | {
      step: 'payment';
      status: 'draft' | 'dirty' | 'processing';  // Has an extra "processing" intermediate
      data: Step3PaymentData;
    }
  | {
      step: 'complete';
      status: 'paid';
      orderId: OrderId;
      // No `data` field here — payment data was consumed
    };
```

### 4. The Action Discriminated Union

Every action encodes the exact transition. Notice: actions are not independent from states — the action payload carries the *result* state's required data.

```ts
type FormAction =
  // --- Personal step transitions ---
  | {
      type: 'SUBMIT_PERSONAL';
      data: Step1PersonalData;        // Payload carries what the resulting state needs
    }

  // --- Address step transitions ---
  | {
      type: 'SUBMIT_ADDRESS';
      data: Step2AddressData;         // Payload carries address fields
    }
  | {
      type: 'BACK_FROM_ADDRESS_TO_PERSONAL';  // Explicit named transition
    }

  // --- Payment step transitions ---
  | {
      type: 'SUBMIT_PAYMENT';
      data: Step3PaymentData;
    }
  | {
      type: 'PAYMENT_SUCCEEDED';
      orderId: OrderId;               // Only emitted when payment succeeds
    }
  | {
      type: 'BACK_FROM_PAYMENT_TO_ADDRESS'; // Explicit named transition
    }

  // --- Final states have NO outgoing actions ---
  | { type: '__NEVER__'; }           // Placeholder for exhaustiveness proof
```

### 5. Type-Safe Reducer with Exhaustiveness Check

```ts
function reduce(
  state: FormState,
  action: FormAction,
): FormState {
  // === EXHAUSTIVENESS PROOF ===
  // This line will NOT compile if a new state variant is added
  // but the corresponding case handler is missing.
  const _exhaustiveCheck: never = state.step;
  // ^-- If we add a new step type, `_exhaustiveCheck` becomes
  // something other than `never`, and TS complains.

  // Also exhaustively check all action types:
  const _actionExhaustiveCheck: never = action.type;
  // Same principle — every action type must be handled.

  // === TRANSITION LOGIC ===
  // Because of discriminated unions, TypeScript narrows `state`
  // AND `action` simultaneously, giving us precise typing in each branch.

  switch (state.step) {
    case 'personal': {
      if (action.type === 'SUBMIT_PERSONAL') {
        // At this point: state.data is Step1PersonalData
        //                    action.data is Step1PersonalData (the submitted version)
        // Result: narrow to address step
        return {
          step: 'address',
          status: 'draft',
          data: action.data,
        } satisfies typeof state extends infer T ? T : never;
      }
      // If action.type doesn't match, fall through to unreachable below
      break;
    }

    case 'address': {
      if (action.type === 'SUBMIT_ADDRESS') {
        return {
          step: 'payment',
          status: 'draft',
          data: action.data,
        };
      }
      if (action.type === 'BACK_FROM_ADDRESS_TO_PERSONAL') {
        return {
          step: 'personal',
          status: 'dirty',                  // Marked dirty when going back
          data: state.data,                 // Preserves previous personal data
        };
      }
      break;
    }

    case 'payment': {
      if (action.type === 'SUBMIT_PAYMENT') {
        return {
          step: 'payment',
          status: 'processing',
          data: action.data,
        };
      }
      if (action.type === 'BACK_FROM_PAYMENT_TO_ADDRESS') {
        return {
          step: 'address',
          status: 'dirty',
          data: state.data,                 // Preserves address data
        };
      }
      if (action.type === 'PAYMENT_SUCCEEDED') {
        // At this point: action.orderId is OrderId
        return {
          step: 'complete',
          status: 'paid',
          orderId: action.orderId,          // Branded — can't confuse with UserId
        };
      }
      break;
    }

    case 'complete': {
      // Terminal state — no transitions are possible
      // Accessing .orderId is safe; .data does not exist
      void state.orderId;
      break;
    }
  }

  // UNREACHABLE SECTION
  // If we got here, either:
  // 1. An unhandled action type for this state, or
  // 2. A new state/action variant was added without a handler
  const unhandledAction: never = action;
  const unhandledState: never = state;
  const unhandledStateStep: never = state.step;
  const unhandledActionType: never = action.type;

  throw new Error(
    `Unhandled transition: state=${JSON.stringify(state)} + action=${action.type}`,
  );
}
```

### 6. Compile-Time Proofs That Invalid Transitions Are Unrepresentable

This is the critical part. I'll demonstrate that both invalid transitions fail at compile time.

#### Proof A: Submitting While Step 2 Is Dirty

The invalid scenario: user is on the address step (`step: 'address'`) with dirty data, and tries to "submit" using an action shaped for personal-step submission.

```ts
// ── Start state: user is on address step, data is dirty ──
let currentState: FormState = {
  step: 'address',
  status: 'dirty',
  data: {
    street: '123 Main St',
    city: 'Portland',
    zipCode: '97201',
    country: 'US',
  },
};

// ── INVALID ACTION: SUBMIT_PERSONAL while on address step ──
// This action requires step-personal context. We're on step-address.

const submitPersonalAction: Extract<FormAction, { type: 'SUBMIT_PERSONAL' }> = {
  type: 'SUBMIT_PERSONAL',
  data: {                              // ← Requires Step1PersonalData fields
    firstName: 'Jane',
    lastName: 'Doe',
    email: 'jane@example.com',
  },
};

// @ts-expect-error — ❌ RED: Cannot apply SUBMIT_PERSONAL action to address-step state
reduce(currentState, submitPersonalAction);
//
// TS Error trace:
//   • currentState resolves to `{ step: 'address', ... }`
//   • Inside case 'address': TypeScript sees action.type === 'SUBMIT_PERSONAL'
//   • But in the 'address' case block, the ONLY accepted actions are
//     'SUBMIT_ADDRESS' and 'BACK_FROM_ADDRESS_TO_PERSONAL'
//   • 'SUBMIT_PERSONAL' falls through to the unreachable section
//   • `unhandledAction` is typed `never` — action does not widen to never
//   • Compiler error: Type '{ type: "SUBMIT_PERSONAL"; ... }' is not assignable
//     to type 'never'.
```

**Why the compiler catches this:** In the `case 'address':` branch, TypeScript has narrowed `state.step` to exactly `'address'`. When we check `action.type === 'SUBMIT_PERSONAL'`, the control flow knows this condition is false — `SUBMIT_PERSONAL` is only valid from `'personal'` step. The action falls through to the unreachable `never` check, producing a compile error. There is no way to construct an action object that represents this transition correctly.

You might argue: "Could I construct a raw object literal?" Even so:

```ts
// Can I cheat by bypassing the union?
const rogueAction = {
  type: 'SUBMIT_PERSONAL' as const,    // Explicit const assertion — still fails
  data: { firstName: 'Jane', lastName: 'Doe', email: 'jane@x.com' },
} satisfies typeof submitPersonalAction;

// @ts-expect-error — ❌ Still caught
reduce(currentState, rogueAction);
```

#### Proof B: Going Back After Payment Completes

The invalid scenario: user has completed the entire flow (`step: 'complete'`) and tries to navigate backwards.

```ts
// ── Terminal state: order is fully complete ──
currentState = {
  step: 'complete',
  status: 'paid',
  orderId: OrderId('ORD-9999'),
};

// ── INVALID ACTION: Go back from complete state ──
const goBackAction = {
  type: 'BACK_FROM_ADDRESS_TO_PERSONAL' as const,
} as const;

// @ts-expect-error — ❌ RED: No transition defined from 'complete' to any prior step
reduce(currentState, goBackAction);
//
// TS Error trace:
//   • currentState resolves to `{ step: 'complete', ... }`
//   • Enters `case 'complete':`
//   • This case has NO action-handling logic — it's the terminal state
//   • Every action checked inside this case falls through to unreachable
//   • `unhandledActionType` is typed `never` — action.type does not narrow to never
//   • Compiler error: Type '"BACK_FROM_ADDRESS_TO_PERSONAL"' is not assignable
//     to type 'never'.
```

Even if we invented a fresh action name:

```ts
// Can I invent a new action?
const madeUpAction = { type: 'WENT_BACK_AFTER_COMPLETE' as const };

// @ts-expect-error — ❌ Caught: 'WENT_BACK_AFTER_COMPLETE' is not a member of FormAction
reduce(currentState, madeUpAction);
```

**Why the compiler catches this:** The `case 'complete':` block has zero action handlers. It's intentionally empty (with a `void` access to prove `orderId` is available and safe). Any action entering this case inevitably hits the unreachable section. Since every variant of `FormAction` is exhaustively listed and none map out of `'complete'`, the action type does not collapse to `never`, and the compiler reports an error.

//   ↳ state is now { step: 'complete', status: 'paid', orderId: OrderId('ORD-7890') }

// Verify type narrowing at the end:

## Summary of Safety Properties

| Property | Before (`any` + strings) | After (discriminated union) |
|---|---|---|
| Step data fields | `any[]`, accessible arbitrarily | Exact shape per step via narrowing |
| Status values | Free string, typos silent | `'draft' \| 'dirty' \| 'processing' \| 'paid'` — literal-enforced |
| UserId vs OrderId | Both `any` — interchangeable | Branded types — assignment rejected |
| Transition validity | Runtime throw with JSON dump | Compile error at the call site |
| New step handling | Forget it → silent bug | `_exhaustiveCheck` fails immediately |
| New action handling | Falls through to default → throw | `_actionExhaustiveCheck` fails immediately |
| Terminal states | No concept — can mutate freely | No outgoing edges — compiler enforces immutability |

The key insight: the invalid transitions aren't just "hard to represent" — they're **structurally unrepresentable**. The shape of `SUBMIT_PERSONAL` requires `Step1PersonalData`; the shape of the address state requires `Step2AddressData`. There is no overlap, no coercion path, and no `as` cast that makes them compatible without explicitly telling TypeScript to lie (`satisfies`, `as any`). With disciplined use of the branded types and discriminated unions, the compiler becomes the validation layer — catching these bugs before they leave your editor.
