## After: Exhaustive State Machine

### 1. Branded / Opaque IDs

Opaque types prevent `UserId` and `OrderId` from being confused — the brand makes them distinct at the type level without runtime overhead.

```typescript
// ──────────────────────────────────────────────
// BRANDED TYPES: compile-time ID separation
// ──────────────────────────────────────────────

/** A brand is a phantom property baked into the type — erased at runtime. */
declare const UserIdBrand: unique symbol;
export type UserId = string & { readonly [UserIdBrand]: 'UserId' };

declare const OrderIdBrand: unique symbol;
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId' };

/** Safe constructors — callers must use these, never cast raw strings. */
function makeUserId(id: string): UserId {
  return id as UserId;
}

function makeOrderId(id: string): OrderId {
  return id as OrderId;
}

// Proof of safety:
const uid = makeUserId("u-1");     // ✅ UserId
const oid = makeOrderId("o-2");    // ✅ OrderId

// @ts-expect-error — UserId ≠ OrderId
const bad: OrderId = uid;
//          ^^^^^^^^ Type 'UserId' is not assignable to type 'OrderId'.
```

No runtime cost. `string & { [brand]: 'UserId' }` intersects `string` with a branded object type — the `string` part carries the value at runtime, the branded part is a **phantom property** that exists only for type checking. This is called a *nominal type* emulation in structural TS.

### 2. Per-Step Data Requirements (Discriminated Unions)

Each step demands a different shape of data. We model this with discriminated unions — the compiler knows which fields exist for each step.

```typescript
// ──────────────────────────────────────────────

  firstName: string;
  lastName: string;
  email: string;                       // required — not optional
  phone?: string;                      // truly optional
}

  street: string;
  city: string;
  state: string;
  zipCode: string;                     // pattern validation happens elsewhere;

  country: string;

  cardNumber: string;
  expiryMonth: number;
  expiryYear: number;
  cvv: string;                         // we store tokenized ref, not raw CVV
  billingAddress: ShippingInfoData;    // must have already entered shipping
}

interface ConfirmationData {
  orderId: OrderId;                    // branded
  userId: UserId;                      // branded

  items: ReadonlyArray<{
    name: string;
    quantity: number;
    priceCents: number;

}
```

Key observation: `PaymentInfoData.billingAddress` references `ShippingInfoData`. If someone tries to pay without shipping, the type chain forces the data to exist. ### 3. Step-Specific State Nodes

This is where discriminated unions shine. Each step variant carries its own payload and discriminates via the `step` field.

```typescript
  step: 'payment';
```

```typescript
  readonly kind: 'CANCEL_TO_USER';

  readonly kind: 'COMPLETE_PAYMENT';

  readonly orderId: OrderId;
  readonly userId: UserId;

    quantity: number;
    priceCents: number;
```

Read the action list: "You can submit user info, save shipping, cancel back to user, initiate payment, complete payment, or confirm the order." That's it. Try adding another action — say `GoBackFromConfirmationAction` — and TypeScript rejects it because no state transition supports it. Or rather: the absence of such an action type **is the proof** that the transition is invalid.

## After: Exhaustive state machine

### 1. Branded / opaque identifiers

Branded types are structurally subtypes of `string` but are **not** assignable to each other because the brand property is nominal in the type system.

```typescript
// Brand helper: T & { __brand: U } is a subtype of T but NOT a subtype of
// (S & { __brand: V }) when U ≠ V.
type Brand<T, B extends string> = T & { readonly __brand: unique symbol & { _: B } };

export const UserId = Symbol();
export const OrderId = Symbol();

export type UserId = Brand<string, "UserId">;
export type OrderId = Brand<string, "OrderId">;

export function parseUserId(s: string): UserId {
    return s as UserId;           // Only call after your own DB-validation
}

export function parseOrderId(s: string): OrderId {
    return s as OrderId;
}

// ❌ These are now type errors — the brands conflict
const uid: UserId = "user-42";       // OK — string coerces to branded string
const oid: OrderId = uid;            // ERROR: UserId !≠ OrderId
const oBad: OrderId = "order-99" as OrderId; // Compiles but only via explicit cast — deliberate
```

### 2. Discriminated unions per step — tracking lifecycle, not just data

Each step can be **Initial**, **InProgress** (dirty/unsubmitted), or **Done**. Crucially, `StepNDone` carries the **exact data shape** for that step — nothing more, nothing less.

```typescript
// ── Step data shapes ────────────────────────────────────────────────

interface Step2FormData { address: string; city: string; zip: string; country: string; }
interface Step3FormData { billingAddress: string; billingCity: string; billingZip: string; taxId: string; }
interface Step4FormData { cardNumber: string; expiry: string; cvv: string; holderName: string; }

// ── Per-step discriminated unions (lifecycle-aware) ─────────────────

type Step1State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step1FormData }   // dirty / unsubmitted
    | { variant: "done"; data: Step1FormData };           // submitted, validated

type Step2State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step2FormData }
    | { variant: "done"; data: Step2FormData };

type Step3State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step3FormData }
    | { variant: "done"; data: Step3FormData };

type Step4State =
    | { variant: "initial" }
    | { variant: "in_progress"; draft: Step4FormData }
    | { variant: "processing" };                           // special terminal sub-state
```

Notice: **Step4 has no `done` variant** — after payment processing begins there is no going back (this enforces the "can't go back after payment" rule at the type level).

### 1. Branded/Opaque Types

Branding uses intersection with a literal type + unique symbol to create types that are structurally identical but nominally distinct at compile time.

```typescript

    return value as UserId & { [_UserIdBrand]: true };

  export function OrderId(value: string): OrderId {
    return value as OrderId & { [_OrderIdBrand]: true };
```
