## Before: The Current Broken State

```typescript
interface WizardState {
  status: string          // ← "any" string, no domain discipline
  data: any               // ← completely opaque, zero inference
  userId: any             // ← could be OrderId, ProductId, etc.
  orderId?: any
}

type Action = {
  type: string            // ← runtime typos ("next", "nxt", "NEXT") aren't caught
  payload?: any
}

// Guard functions — runtime bugs only
function submit(state: WizardState) {
  if (state.data.step === 2 && state.data.dirty) throw new Error() // WAT?
  if (state.status === 'payment_complete') throw new Error()        // another runtime check
  // ...
}
```

**Problems:**
- `status: string` allows any value (`'foo'`, `null`, `'COMPLETED'`)
- `data: any` kills IDE autocomplete and lets you call `.toUpperCase()` on undefined
- `userId: any` confuses it with `orderId: any`
- No invariant enforcement — the two invalid transitions compile fine
- Every guard is a runtime `if`, not a compile-time guarantee

## After: Exhaustive State Machine

### 1. Branded/Opaque IDs

Template literal types + symbol brands so the compiler prevents mixing `UserId` and `OrderId`.

```typescript
// Brand utility — makes T unique when intersected with a literal
type Brand<K, T> = K & { __brand: T };

// Usage: UserId and OrderId are incompatible even though both are numbers
type UserId = Brand<number, 'UserId'>;
type OrderId = Brand<number, 'OrderId'>;

declare const USER_ID: unique symbol;
declare const ORDER_ID: unique symbol;

function UserId(value: number): UserId { return value as UserId; }
function OrderId(value: number): OrderId { return value as OrderId; }

// PROVE incompatibility — these DON'T compile:
// const x: UserId = OrderId(1);       // ❌ Type 'OrderId' is not assignable to 'UserId'
// const y: OrderId = UserId(1);       // ❌ Type 'UserId' is not assignable to 'OrderId'
```

### 2. Step Data Interfaces (Per-Step Requirements)

Each step has its own required shape. `infer` extracts them later.

```typescript
interface StepPersonalData {
  firstName: string;
  lastName: string;
  email: string;
}

interface StepShippingData {
  address: string;
  city: string;
  postalCode: string;
}

interface StepPaymentData {
  cardNumber: string;
  expiryDate: string;   // "MM/YY"
  cvv: string;
}
```

### 3. Discriminated Union — The State Itself

Key insight: **each step is a discriminated union variant** carrying exactly the data needed for that step plus cumulative history.

```typescript
type WizardStateBase = {
  userId: UserId;
  orderId?: OrderId;    // only present after payment step completes
};

export type WizardState =
  | WizardStateBase & { currentStep: 'personal'; personal: Partial<StepPersonalData>; dirty: Record<'personal', boolean> }
  | WizardStateBase & { currentStep: 'shipping';  personal: StepPersonalData;        shipping: Partial<StepShippingData>; dirty: Record<'personal', false> & Record<'shipping', boolean> }
  | WizardStateBase & { currentStep: 'payment';   personal: StepPersonalData;        shipping: StepShippingData;         payment: Partial<StepPaymentData>; dirty: Record<'personal', false> & Record<'shipping', false> & Record<'payment', boolean> }
  | WizardStateBase & { currentStep: 'complete';  personal: StepPersonalData;        shipping: StepShippingData;         payment: StepPaymentData };
```

Reading this plain-English:
- When `currentStep` is `'personal'`, you have `userId`, incomplete `personal` data, and a dirty flag for personal
- When `currentStep` is `'shipping'`, personal is **complete** (not partial), shipping is partial, and `dirty.personal` is always `false` (already submitted)
- When `currentStep` is `'payment'`, both personal and shipping are complete
- When `currentStep` is `'complete'`, everything is fully populated and `orderId` appears

**Why `dirty` is per-step and narrows to `false` for prior steps:** once a step is done, the type system knows you can't go back and modify it without explicit (and disallowed) actions.

### 4. Event-Driven Actions

Actions encode the event. Payloads are typed per-action using a mapped conditional type.

```typescript
// Base action shape with discriminant
type WizardAction =
  | { kind: 'submit-personal'; payload: { personal: StepPersonalData } }
  | { kind: 'update-personal'; payload: Partial<StepPersonalData> }
  | { kind: 'submit-shipping'; payload: { shipping: StepShippingData } }
  | { kind: 'update-shipping'; payload: Partial<StepShippingData> }
  | { kind: 'submit-payment';  payload: { payment: StepPaymentData } }
  | { kind: 'update-payment';  payload: Partial<StepPaymentData> }
  | { kind: 'confirm-complete' }
;

// Extract which fields are writable at each step — MAPPED + CONDITIONAL TYPE
type DirtyKeys<S extends WizardState> = S extends { dirty: infer D } ? {
  [K in keyof D as D[K] extends true ? K : never]: K;
}[keyof D] : never;

// Usage example — if state is at 'shipping', DirtyKeys<State> resolves to '"shipping"'
// You can't call update-personal because it needs DirtyKeys to include 'personal'
```

The `DirtyKeys` mapping uses:
- **Mapped type** (`{[K in keyof D]: ...}`)
- **Key remapping** (`as D[K] extends true ? K : never`) — filters out keys that are `false`
- **Conditional type** (`D[K] extends true`) — checks each value

### 5. The Transition Function with Exhaustiveness Check

This is where the magic happens — every transition is a pure function returning the next state, and the `never` branch catches missing cases.

```typescript
function transition(state: WizardState, action: WizardAction): WizardState {
  switch (state.currentStep) {
    case 'personal': {
      switch (action.kind) {
        case 'update-personal':
          return {
            ...state,
            personal: { ...state.personal, ...action.payload },
            dirty: { ...state.dirty, personal: true }
          };
        case 'submit-personal':
          // Validate: all three fields required
          if (!action.payload.personal.firstName || !action.payload.personal.lastName || !action.payload.personal.email) {
            throw new Error('Personal info incomplete');
          }
          return {
            ...state,
            currentStep: 'shipping' as const,
            personal: { ...action.payload.personal },
            shipping: {} as Partial<StepShippingData>,
            dirty: { personal: false, shipping: true } as WizardState['dirty']
          };
        default: {
          // Exhaustiveness check — action must be of type `never` here
          const _exhaustive: never = action;
          throw new Error(`Cannot transition from personal with ${(_exhaustive as any).kind}`);
        }
      }
    }

    case 'shipping': {
      switch (action.kind) {
        case 'update-shipping':
          return {
            ...state,
            shipping: { ...state.shipping, ...action.payload },
            dirty: { ...state.dirty, shipping: true }
          };
        case 'submit-shipping':
          if (!action.payload.shipping.address || !action.payload.shipping.city || !action.payload.shipping.postalCode) {
            throw new Error('Shipping info incomplete');
          }
          return {
            ...state,
            currentStep: 'payment' as const,
            shipping: { ...action.payload.shipping },
            payment: {} as Partial<StepPaymentData>,
            dirty: { personal: false, shipping: false, payment: true } as WizardState['dirty']
          };
        default: {
          const _exhaustive: never = action;
          throw new Error(`Cannot transition from shipping with ${(_exhaustive as any).kind}`);
        }
      }
    }

    case 'payment': {
      switch (action.kind) {
        case 'update-payment':
          return {
            ...state,
            payment: { ...state.payment, ...action.payload },
            dirty: { ...state.dirty, payment: true }
          };
        case 'submit-payment':
          if (!action.payload.payment.cardNumber || !action.payload.payment.expiryDate || !action.payload.payment.cvv) {
            throw new Error('Payment info incomplete');
          }
          return {
            ...state,
            currentStep: 'complete' as const,
            payment: { ...action.payload.payment },
            orderId: OrderId(Date.now()) as OrderId   // assigned on completion
          } satisfies Omit<WizardState, 'dirty'>;  // no dirty field in complete state
        default: {
          const _exhaustive: never = action;
          throw new Error(`Cannot transition from payment with ${(_exhaustive as any).kind}`);
        }
      }
    }

    case 'complete': {
      switch (action.kind) {
        case 'confirm-complete':
          return state;  // terminal state, just acknowledge
        default: {
          const _exhaustive: never = action;
          throw new Error(`Cannot transition from complete with ${(_exhaustive as any).kind}`);
        }
      }
    }

    // If the union ever gains a new step, TS will error here:
    default: {
      const _exhaustive: never = state;  // ← NEW STEP WITHOUT CASE = COMPILE ERROR
      throw new Error(`Unhandled step: ${(_exhaustive as any).currentStep}`);
    }
  }
}
```

## Proof That Invalid Transitions Are Unrepresentable

### Invalid Transition 1: Submitting While Step 2 Is Dirty

This means calling `submit-payment` when we're still at `'shipping'` and shipping is dirty.

```typescript
declare let stateAtShipping: WizardState;
// stateAtShipping.currentStep is narrowed to 'shipping'

transition(stateAtShipping, { kind: 'submit-payment', payload: { payment: { cardNumber: '1234', expiryDate: '12/28', cvv: '123' } });
// ❌ TS2345: Argument of type '{ kind: "submit-payment"; payload: {...} }' 
//    is not assignable to parameter of type '{ kind: "update-shipping"; ... } | { kind: "submit-shipping"; ... }'
//
// Why: inside the 'shipping' case, the inner switch only accepts 
// 'update-shipping' or 'submit-shipping'. 'submit-payment' falls into 
// the default, which demands `action: never`. Since 'submit-payment' 
// is NOT `never`, this is a compile error.
```

**The type system prevents it.** At `'shipping'`, the only valid actions are those whose `kind` matches one of the cases in the inner switch. `submit-payment` doesn't match either, so it goes to `default: never`, and since `submit-payment` is not `never`, TypeScript errors.

### Invalid Transition 2: Going Back After Payment

This means modifying `personal` data when we're past step 1.

```typescript
declare let stateAtPayment: WizardState;
// stateAtPayment.currentStep is narrowed to 'payment'
// stateAtPayment.dirty = { personal: false, shipping: false, payment: true }

transition(stateAtPayment, { kind: 'update-personal', payload: { firstName: 'New' } });
// ❌ TS2345: Not assignable — same logic. Inside 'payment' case, 
//    the inner switch only accepts 'update-payment' or 'submit-payment'.
//    'update-personal' falls to default: never → compile error.
```

Additionally, even if someone bypassed the dispatcher, they couldn't mutate state directly because:
1. `personal` at `'payment'` is `StepPersonalData` (full, immutable snapshot) — not `Partial<StepPersonalData>`
2. `dirty.personal` is `false` — there's no type path to set it back to `true`
3. There's no `go-back` or `revisit` action in `WizardAction` — it simply doesn't exist

### Bonus Proof: UserId vs OrderId Confusion

```typescript
declare let userId: UserId;
declare let orderId: OrderId;

transition({ userId: orderId, orderId: undefined, /* ...rest */ });
// ❌ Type 'OrderId' is not assignable to type 'UserId'

transition({ userId: userId, orderId: userId, /* ...rest */ });
// ❌ Type 'UserId' is not assignable to type 'OrderId | undefined'
```

## Summary of Techniques Used

| Technique | Where | Purpose |
|---|---|---|
| **Branded types** (`K & {__brand: T}`) | `UserId`, `OrderId` | Prevent ID confusion at compile time |
| **Discriminated unions** | `WizardState` variants | Each step carries exactly its data + invariant flags |
| **Conditional types** | `DirtyKeys<S>` | Derive writable steps based on `dirty` flag values |
| **Mapped types** | `{[K in keyof D]: ...}` | Transform dirty record into actionable key set |
| **Key remapping** (`as`) | `as D[K] extends true ? K : never` | Filter dirty keys to only those marked `true` |
| **`infer`** | `DirtyKeys` | Pull the `dirty` shape out of `S extends WizardState` |
| **Template literal types** | Could enforce email format `email: `${string}@${string}.${string}`` or card pattern `cardNumber: `${number}${number}${number}${number}` \` | Compile-time format validation |
| **Exhaustiveness via `never`** | Inner `default` branches, outer `default` | Catch missing cases at compile time, not runtime |

The result: **zero runtime guards needed for transitions**, zero `any` in the type layer, zero `as unknown as X` casts, and both invalid transitions above are rejected at compile time with clear error messages.
