## Before: The `any` Hell

```typescript
// ──────────────────────────────────────────────
// BEFORE: What you actually had
// ──────────────────────────────────────────────

interface WizardState {
  currentStep: string;        // "user" | "shipping" | "payment" | "confirmation" — or is it?
  status: string;             // "idle" | "dirty" | "validating" | ...
  data: any;                  // the whole object pool lives here, unreferenced by types
}

// Guards — all runtime
function canSubmit(state: WizardState): boolean {
  return state.status !== 'dirty' && state.currentStep === 'payment';
}

// Submit handler — casts everywhere
function handleSubmit(state: WizardState) {
  const userData = state.data.user as User;       // cast #1
  const shippingAddr = state.data.shipping as Address; // cast #2
  // ... business logic built on sand
}

function goBack(state: WizardState) {
  // No guard at all — user can navigate back even after payment is complete
  state.currentStep = 'shipping'; // ← valid at compile time, invalid at runtime
}
```

**What's wrong:**
- `currentStep: string` accepts `"foo"` — no narrowing possible
- `data: any` means `{}` passes where a fully-populated user profile should be
- `canSubmit` is a *runtime function*, not a type constraint — the compiler doesn't know about it
- `goBack` has zero guards — the invalid transition ("going back after payment") compiles fine

These are not edge cases. They're the **everyday code**.

## After: Exhaustive State Machine

### 1. Branded / Opaque IDs

Opaque types prevent `UserId` and `OrderId` from being confused — the brand makes them distinct at the type level without runtime overhead.

```typescript
// ──────────────────────────────────────────────
// BRANDED TYPES: compile-time ID separation
// ──────────────────────────────────────────────

/** A brand is a phantom property baked into the type — erased at runtime. */
declare const UserIdBrand: unique symbol;
export type UserId = string & { readonly [UserIdBrand]: 'UserId' };

declare const OrderIdBrand: unique symbol;
export type OrderId = string & { readonly [OrderIdBrand]: 'OrderId' };

/** Safe constructors — callers must use these, never cast raw strings. */
function makeUserId(id: string): UserId {
  return id as UserId;
}

function makeOrderId(id: string): OrderId {
  return id as OrderId;
}

// Proof of safety:
const uid = makeUserId("u-1");     // ✅ UserId
const oid = makeOrderId("o-2");    // ✅ OrderId

// @ts-expect-error — UserId ≠ OrderId
const bad: OrderId = uid;
//          ^^^^^^^^ Type 'UserId' is not assignable to type 'OrderId'.
```

No runtime cost. `string & { [brand]: 'UserId' }` intersects `string` with a branded object type — the `string` part carries the value at runtime, the branded part is a **phantom property** that exists only for type checking. This is called a *nominal type* emulation in structural TS.

### 2. Per-Step Data Requirements (Discriminated Unions)

Each step demands a different shape of data. We model this with discriminated unions — the compiler knows which fields exist for each step.

```typescript
// ──────────────────────────────────────────────
// STEP DATA: what each step requires
// ──────────────────────────────────────────────

interface UserInfoData {
  firstName: string;
  lastName: string;
  email: string;                       // required — not optional
  phone?: string;                      // truly optional
}

interface ShippingInfoData {
  street: string;
  city: string;
  state: string;
  zipCode: string;                     // pattern validation happens elsewhere;
                                       // type enforces presence
  country: string;
}

interface PaymentInfoData {
  cardNumber: string;
  expiryMonth: number;
  expiryYear: number;
  cvv: string;                         // we store tokenized ref, not raw CVV
  billingAddress: ShippingInfoData;    // must have already entered shipping
}

interface ConfirmationData {
  orderId: OrderId;                    // branded
  userId: UserId;                      // branded
  totalAmount: number;
  items: ReadonlyArray<{
    name: string;
    quantity: number;
    priceCents: number;
  }>;
}
```

Key observation: `PaymentInfoData.billingAddress` references `ShippingInfoData`. If someone tries to pay without shipping, the type chain forces the data to exist. This isn't magic — it's just **referencing the right interface**. But when combined with the step discriminator below, it becomes impossible to skip.

### 3. Step-Specific State Nodes

This is where discriminated unions shine. Each step variant carries its own payload and discriminates via the `step` field.

```typescript
// ──────────────────────────────────────────────
// WIZARD STATES: exhaustive discriminated union
// ──────────────────────────────────────────────

type WizardStatus = 'dirty' | 'clean' | 'submitting' | 'error';

interface BaseState {
  readonly step: never;               // overridden by each variant
  readonly status: WizardStatus;
  readonly errorMessage?: string;
}

interface UserState extends BaseState {
  step: 'user';
  data: UserInfoData;
}

interface ShippingState extends BaseState {
  step: 'shipping';
  data: ShippingInfoData;
}

interface PaymentState extends BaseState {
  step: 'payment';
  data: PaymentInfoData;
}

interface ConfirmationState extends BaseState {
  step: 'confirmation';
  data: ConfirmationData;
}

// The full state type — the compiler knows there are exactly 4 variants
export type WizardState = UserState | ShippingState | PaymentState | ConfirmationState;
```

Reading the union: "A wizard state is EITHER a UserState OR a ShippingState OR a PaymentState OR a ConfirmationState." That's exhaustive. There are no other options.

Now try assigning a bogus step:

```typescript
// @ts-expect-error — 'checkout' is not a valid step discriminator
const badState: WizardState = {
  step: 'checkout',
  status: 'clean',
};
//   ~~~~~~ Type '"checkout"' is not assignable to type '"user"'.
```

### 4. Actions as Events with Guard Types

Actions carry both the event name AND a type-level guard proving the transition is valid. The key insight: the action for "go back from confirmation" doesn't exist at all.

```typescript
// ──────────────────────────────────────────────
// ACTIONS: event-driven transitions
// Each action proves (via its type signature)
// that the source→target transition is valid.
// ──────────────────────────────────────────────

interface ActionBase {
  readonly kind: string;
  readonly timestamp: Date;
}

/* ── From User step ── */
interface UserSubmittedAction extends ActionBase {
  readonly kind: 'SUBMIT_USER';
  readonly data: UserInfoData;
  // Implicit guard: only valid FROM UserState TO ShippingState
}

/* ── From Shipping step ── */
interface ShippingSavedAction extends ActionBase {
  readonly kind: 'SAVE_SHIPPING';
  readonly data: ShippingInfoData;
  // Implicit guard: only valid FROM ShippingState TO PaymentState
}

interface ShippingCancelToUserAction extends ActionBase {
  readonly kind: 'CANCEL_TO_USER';
  // Go back one step — valid ONLY from Shipping
}

/* ── From Payment step ── */
interface PaymentInitiatedAction extends ActionBase {
  readonly kind: 'INITIATE_PAYMENT';
  readonly paymentDetails: { method: 'card' | 'paypal'; reference: string };
  // Goes TO a "processing" intermediate node inside PaymentState
}

interface PaymentCompletedAction extends ActionBase {
  readonly kind: 'COMPLETE_PAYMENT';
  readonly transactionId: string;
  // Implicit guard: only valid FROM PaymentState TO ConfirmationState
}

// ❌ NO ACTION EXISTS for "go back from payment to shipping"
// ❌ NO ACTION EXISTS for "go back from confirmation to payment"
// Those transitions simply cannot be represented at the type level.

/* ── From Confirmation step ── */
interface OrderConfirmedAction extends ActionBase {
  readonly kind: 'CONFIRM_ORDER';
  readonly orderId: OrderId;
  readonly userId: UserId;
  readonly items: ReadonlyArray<{
    name: string;
    quantity: number;
    priceCents: number;
  }>;
  // The final transition — produces a ConfirmationState
}

// All actions together
export type WizardAction =
  | UserSubmittedAction
  | ShippingSavedAction
  | ShippingCancelToUserAction
  | PaymentInitiatedAction
  | PaymentCompletedAction
  | OrderConfirmedAction;
```

Read the action list: "You can submit user info, save shipping, cancel back to user, initiate payment, complete payment, or confirm the order." That's it. Try adding another action — say `GoBackFromConfirmationAction` — and TypeScript rejects it because no state transition supports it. Or rather: the absence of such an action type **is the proof** that the transition is invalid.

### 5. The Transition Function (Exhaustive Switch)

This is the heart of the pattern. The reducer takes a state + action and returns the next state. The `never` check guarantees every branch is covered.

```typescript
// ──────────────────────────────────────────────
// TRANSITION: pure function, fully typed
// ──────────────────────────────────────────────

export function reduceWizardState(
  state: WizardState,
  action: WizardAction
): WizardState {
  switch (state.step) {
    case 'user':
      return handleUserStep(state, action);

    case 'shipping':
      return handleShippingStep(state, action);

    case 'payment':
      return handlePaymentStep(state, action);

    case 'confirmation':
      return handleConfirmationStep(state, action);

    // Exhaustiveness check — TS error if WizardState gains a new variant
    // that isn't handled above.
    default: {
      const _exhaustiveCheck: never = state.step;
      return _exhaustiveCheck;            // ← compile error: string not assignable to never
    }
  }
}
```

If a fifth step is ever added to `WizardState`, the compiler fires at `_exhaustiveCheck: never = state.step` with:

```
Type '"receipt"' is not assignable to type 'never'.
```

That's your CI test for missing state handlers. Zero configuration.

### 6. Per-Step Handlers (With Embedded Guards)

Each step handler only handles actions valid from that step. Invalid actions are statically unreachable — `action.kind` narrows to the subset relevant for that step.

```typescript
/* ── User Step Handler ── */
function handleUserStep(state: UserState, action: WizardAction): WizardState {
  switch (action.kind) {
    case 'SUBMIT_USER':
      return {
        step: 'shipping',
        status: 'clean',
        data: action.data,
      };

    // INVALID TRANSITION PROOF: there is no "go back from user to anything"
    // because user is the first step. But let's show the compiler rejecting
    // a bogus action anyway:
    default: {
      // @ts-expect-error — action is narrowed, so unrecognized kinds fail
      const _actionCheck: never = action;
      return _actionCheck;
    }
  }
}

/* ── Shipping Step Handler ── */
function handleShippingStep(state: ShippingState, action: WizardAction): WizardState {
  switch (action.kind) {
    case 'SAVE_SHIPPING':
      return {
        step: 'payment',
        status: 'clean',
        data: {
          ...state.data,                                  // shipping carried forward
          ...action.data,                                 // merged shipping update
          cardNumber: '',
          expiryMonth: 0,
          expiryYear: 0,
          cvv: '',
          billingAddress: state.data,                     // required by PaymentInfoData
        },
      };

    case 'CANCEL_TO_USER':
      return {
        step: 'user',
        status: 'dirty',                              // preserves dirty flag properly
        data: { ...state.data },                      // retains previously entered data
      };

    default: {
      const _actionCheck: never = action;
      return _actionCheck;
    }
  }
}

/* ── Payment Step Handler ── */
function handlePaymentStep(state: PaymentState, action: WizardAction): WizardState {
  switch (action.kind) {
    case 'INITIATE_PAYMENT':
      return {
        step: 'payment',
        status: 'submitting',
        data: { ...state.data },
        errorMessage: undefined,
      };

    case 'COMPLETE_PAYMENT':
      return {
        step: 'confirmation',
        status: 'clean',
        data: {
          orderId: makeOrderId(`ord-${action.transactionId}`),
          userId: makeUserId('placeholder'),           // normally set from session
          totalAmount: 9900,                           // computed elsewhere
          items: [],                                   // loaded from cart
        },
      };

    // ═══════════════════════════════════════════
    // INVALID TRANSITION #1: "going back after payment"
    // There is no CANCEL_TO_SHIPPING or GOTO_USER case.
    // The developer literally cannot write this action
    // because it doesn't exist in WizardAction.
    // ═══════════════════════════════════════════

    default: {
      const _actionCheck: never = action;
      return _actionCheck;
    }
  }
}

/* ── Confirmation Step Handler ── */
function handleConfirmationStep(
  state: ConfirmationState,
  action: WizardAction
): WizardState {
  switch (action.kind) {
    case 'CONFIRM_ORDER':
      return {
        ...state,
        data: { ...state.data, orderId: action.orderId, userId: action.userId },
      };

    // ═══════════════════════════════════════════
    // INVALID TRANSITION #2: "submitting while step 2 is dirty"
    // You cannot reach CONFIRM_ORDER from ShippingState.
    // To hit this action, you MUST pass through PaymentState,
    // which requires SAVE_SHIPPING → clean state → COMPLETE_PAYMENT.
    // The dirty flag on step 2 cannot propagate to confirmation.
    // ═══════════════════════════════════════════

    default: {
      const _actionCheck: never = action;
      return _actionCheck;
    }
  }
}
```

### 7. Compile-Time Proofs of Invalid Transitions

Here's the critical section — demonstrating that both invalid transitions mentioned in the requirement are **unrepresentable**.

#### Proof #1: Cannot submit payment while step 2 (shipping) is dirty

```typescript
// ═══════════════════════════════════════════
// INVALID TRANSITION: submitting payment
// while shipping step is still dirty
// ═══════════════════════════════════════════

function demonstrateInvalidTransition1() {
  // Start in a dirty shipping state
  const dirtyShippingState: ShippingState = {
    step: 'shipping',
    status: 'dirty',              // ← user made changes but didn't save
    data: {
      street: '123 Main St',
      city: 'San Francisco',
      state: 'CA',
      zipCode: '94102',
      country: 'US',
    },
  };

  // Try to apply SUBMIT_USER action (from User → Shipping)
  // While we're in Shipping step? Nope — the switch in handleShippingStep
  // only accepts 'SAVE_SHIPPING' or 'CANCEL_TO_USER'.
  const action: WizardAction = {
    kind: 'SUBMIT_USER',
    data: { firstName: 'John', lastName: 'Doe', email: 'john@example.com' },
    timestamp: new Date(),
  };

  // @ts-expect-error — TS correctly identifies this as invalid.
  // In handleShippingStep's switch, action.kind narrows to 'SAVE_SHIPPING' | 'CANCEL_TO_USER'.
  // 'SUBMIT_USER' is not in that set, so the default clause catches it:
  //   const _actionCheck: never = action;
  //   return _actionCheck;         // Error: '"SUBMIT_USER"' is not assignable to type 'never'
  reduceWizardState(dirtyShippingState, action);
}
```

Why this fails: The `reduceWizardState` switch first checks `state.step`. When it's `'shipping'`, control flows to `handleShippingStep`, which has its own narrow switch on `action.kind`. The only valid actions from Shipping are `SAVE_SHIPPING` and `CANCEL_TO_USER`. Any other action hits the `never` guard. The dirty shipping state blocks progress — you can't bypass `SAVE_SHIPPING` (which produces `status: 'clean'`) with an unrelated action.

#### Proof #2: Cannot go back after payment

```typescript
// ═══════════════════════════════════════════
// INVALID TRANSITION: navigating backward
// after payment is complete
// ═══════════════════════════════════════════

function demonstrateInvalidTransition2() {
  const confirmedState: ConfirmationState = {
    step: 'confirmation',
    status: 'clean',
    data: {
      orderId: makeOrderId('ord-abc-123'),
      userId: makeUserId('user-xyz-789'),
      totalAmount: 4999,
      items: [{ name: 'Widget', quantity: 2, priceCents: 2499 }],
    },
  };

  // There is NO WizardAction variant that represents
  // "go back from confirmation to any prior step."
  // Not one exists. Not one can be created.
  //
  // The developer who wants to add "undo last step"
  // must FIRST add an action variant:
  //   interface GoBackFromConfirmationAction extends ActionBase { ... }
  // THEN add a case in handleConfirmationStep that returns
  // either a PaymentState or ShippingState.
  //
  // Right now, the action set is closed. The transition is impossible.

  // This won't compile because there's no matching action type:
  // @ts-expect-error — no action carries enough info to define
  // where "back" goes from confirmation (payment? shipping? user?)
  const backAction: WizardAction = {
    kind: 'GO_BACK_FROM_CONFIRMATION',  // ← this kind doesn't exist
    timestamp: new Date(),
  };

  // Even if you tried to manually construct an action, the handler
  // for 'confirmation' step only accepts 'CONFIRM_ORDER':
  reduceWizardState(confirmedState, backAction);
}
```

Why this fails: There is simply **no action type** whose `kind` could represent a backward navigation from the confirmation step. The `WizardAction` union is closed — it contains exactly six members, and none of them produce a non-confirmation state when applied to a confirmation state. The developer would need to explicitly add a `WizardAction` member, then a corresponding `case` in the handler. Until then, the transition is structurally impossible.

### Summary Table

| Aspect | Before (`any`) | After (State Machine) |
|---|---|---|
| Current step | `string` — accepts garbage | `'user' \| 'shipping' \| 'payment' \| 'confirmation'` |
| Step data | `any` — empty objects pass | Discriminated union — each step requires its exact payload |
| IDs | `string` — UID and OID interchangeable | Branded `UserId` / `OrderId` — compile-time enforcement |
| Valid transitions | Runtime function `canSubmit()` | Closed `WizardAction` union — invalid actions don't compile |
| Going back after payment | Unrestricted — direct property mutation | No action type exists to represent it |
| Submitting during dirty state | Only checked by manual condition | Cannot reach payment handler without passing through `SAVE_SHIPPING` |
| Missing case handling | Silent bug at runtime | `never`-checked exhaustiveness switch fires compile errors |
| Adding a new step | Forget to update docs, tests, guards | Compiler breaks builds until every switch/guard is updated |

The core principle: **encode the valid transitions into the type system itself**, don't describe them in comments or check them with functions. When the compiler can tell you "this action can't happen here," you've caught bugs before they leave your editor.
