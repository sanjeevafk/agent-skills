## Before: Fragile `any` State

```ts
// === THE ANTI-PATTERN ===

type WizardStep = 'address' | 'details' | 'payment' | 'confirm';

interface WizardState {
  step: WizardStep;          // just a string — any value allowed
  status: string;            // another freeform string
  data: any;                 // opaque blob — compiler trusts us completely
  submittedAt?: number;
}

function advance(state: WizardState, nextStep: WizardStep) {
  // No guard on what `step` we came from. We trust the caller.
  return {
    ...state,
    step: nextStep,
    status: 'active',        // magic string
    data: nextStep === 'payment' ? null : state.data,
  };
}

function submit(state: WizardState) {
  if (state.status !== 'ready') throw new Error('Not ready');
  // state.data! — non-null assertion, blind trust
  return { ...state, status: 'submitted', submittedAt: Date.now() };
}

// BUG: nothing stops calling advance after submit
const s1: WizardState = { step: 'confirm', status: 'submitted', data: { total: 100 }, submittedAt: 1700000000 };
advance(s1, 'address');     // ← compiles fine, returns corrupt state
```

### What's wrong

| Problem | Manifestation |
|---|---|
| `status: string` | Can be `"foo"`, `"donez"`, anything — no closed set of known values |
| `data: any` | Compiler says nothing about shape; every access needs a cast |
| `as` guards | Every read does `(state.data as PaymentData).token` — the type system cedes control |
| No transition guards | `advance(s1, 'address')` when `s1.step === 'confirm'` compiles perfectly |
| `!` assertions | `state.data!` silences the compiler without proving non-emptiness |

## After: Exhaustive State Machine

### 1. Branded/Opaque IDs

Branding uses a unique literal property (`__brand`) that isn't enumerable. Two brands with identical shapes are still incompatible because the brand property differs.

```ts
// A `Brand<T, Tag>` means "a T that must be constructed through a function."
type Brand<T, Tag extends string> = T & { __brand: Tag };

export type UserId   = Brand<string, 'UserId'>;
export type OrderId  = Brand<string, 'OrderId'>;
export type Token    = Brand<string, 'PaymentToken'>;

// Constructors enforce branding at the call site — you cannot accidentally
// pass a plain string or confuse one brand for another.
function UserId(value: string): UserId {
  if (!/^[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}$/.test(value))
    throw new RangeError(`Invalid UserId: ${value}`);
  return value as UserId;
}

function OrderId(value: string): OrderId {
  if (!/^\d{6,}$/i.test(value))
    throw new RangeError(`Invalid OrderId: ${value}`);
  return value as OrderId;
}
```

**Proof**: These lines do NOT compile:

```ts
const uid: UserId = "not-a-uuid";                        // ❌ not a UserId
const oid: OrderId = "123456";                           // ✅ OK
const bad: OrderId = UserId("dead-beef-cafe-babe");      // ❌ UserId ≠ OrderId
```

The compiler rejects `UserId` → `OrderId` assignment because `{ __brand: "UserId" }` ≠ `{ __brand: "OrderId" }`.

### 2. Discriminated Union Per Step

Each step owns its own data shape. The `step` field is the discriminant.

```ts
type StepId = 'shipping' | 'billing' | 'review' | 'confirmation';

// ── Step payloads (closed, per-step shapes) ───────────────────────

interface ShippingPayload {
  firstName: string;
  lastName:  string;
  address:   { street: string; city: string; zip: string; country: string };
  phone:     string;
}

interface BillingPayload {
  cardNumber:    string;   // stored masked after processing
  expiryMonth:   number;
  expiryYear:    number;
  cvc:           string;   // never persisted in real apps
  billingZip:    string;
}

interface ReviewPayload {
  items: Array<{ sku: string; qty: number; price: number }>;
  subtotal:  number;
  tax:       number;
  shipping:  number;
  total:     number;
}

type ConfirmationReceipt = { orderId: OrderId; token: Token; amount: number; timestamp: number };

// ── Stepped data map: stepId → owning payload ─────────────────────

type StepDataMap =
  | { step: 'shipping';  data: ShippingPayload }
  | { step: 'billing';   data: BillingPayload }
  | { step: 'review';    data: ReviewPayload }
  | { step: 'confirmation'; data: ConfirmationReceipt };
```

Every `StepDataMap` member carries exactly the right shape — no `any`, no `as`.

### 3. Events (Closed Transition Graph)

Events represent *actions*. Each event has a `kind` discriminant and required context. Some events carry extra data; others don't.

```ts
type WizardEvent =
  // Fills step N data
  | { kind: 'fillShipping';  payload: ShippingPayload }
  | { kind: 'fillBilling';   payload: BillingPayload }
  | { kind: 'fillReview';    payload: ReviewPayload }

  // Advances forward (N → N+1)
  | { kind: 'completeShipping' }
  | { kind: 'completeBilling' }

  // Goes back (only to adjacent earlier steps)
  | { kind: 'editShipping' }
  | { kind: 'editBilling' }

  // Terminal
  | { kind: 'submitPayment'; orderItems: ReviewPayload['items'] }
  | { kind: 'cancel' }

  // Internal signals the reducer emits
  | { kind: 'setOrderConfirmed'; receipt: ConfirmationReceipt }
  | { kind: 'paymentFailed'; reason: string };
```

Notice: there is **no** `{ kind: 'goBackToShippingFromConfirmation' }` — because going back after confirmation should be impossible. The event list itself encodes the valid DAG.

### 4. State Type (What the Wizard Actually Holds)

```ts
type WizardState =
  // Phase 1: gathering shipping info
  | { phase: 'idle';              currentStep: 'shipping';  data: {} }

  // Phase 2: filled shipping, entering billing
  | { phase: 'shippingComplete';  currentStep: 'billing';   data: ShippingPayload }

  // Phase 3: filled billing, review pending
  | { phase: 'billingComplete';  currentStep: 'review';     data: BillingPayload }

  // Phase 4: reviewing order summary
  | { phase: 'reviewComplete';   currentStep: 'confirmation'; data: ReviewPayload }

  // Phase 5: submitting → either succeeds or fails
  | { phase: 'submitting';         currentStep: 'confirmation'; data: ReviewPayload }

  // Terminal states
  | { phase: 'completed';         currentStep: 'confirmation'; data: ConfirmationReceipt }
  | { phase: 'failed';             currentStep: 'confirmation'; reason: string }
  | { phase: 'cancelled';         currentStep: 'confirmation'; data: {} };
```

Key observations:
- **`phase`** is the high-level mode (closed set — no freeform strings)
- **`currentStep`** is derived from `phase`; some phases lock the step
- **`data`** holds the *most recent completed step's* payload
- Each variant's `data` type reflects what's actually available at that point

### 5. The Reducer (Exhaustiveness Switch)

```ts
function reduce(state: WizardState, event: WizardEvent): WizardState {
  // ── OUTER: switch on state phase ──
  switch (state.phase) {
    // ──────────────────────────────────────────────────────────
    case 'idle':
      switch (event.kind) {
        case 'fillShipping':
          // Validate payload before storing
          if (!event.payload.address || !event.payload.firstName.trim()) {
            throw new Error('Incomplete shipping data');
          }
          return { phase: 'idle', currentStep: 'shipping', data: { ...state.data, ...event.payload } };

        case 'fillBilling':
        case 'fillReview':
        case 'completeShipping':
        case 'completeBilling':
        case 'editShipping':
        case 'editBilling':
        case 'submitPayment':
        case 'cancel':
        case 'setOrderConfirmed':
        case 'paymentFailed':
          // If we reach here, TypeScript narrowed `event.kind` to `never`
          const _exhaustive: never = event;
          throw new Error(`Phase 'idle' cannot handle event: ${JSON.stringify(_exhaustive)}`);
      }

    // ──────────────────────────────────────────────────────────
    case 'shippingComplete':
      switch (event.kind) {
        case 'fillBilling':
          if (!event.payload.cardNumber.startsWith('4')) {
            throw new Error('Invalid card');
          }
          return {
            phase: 'shippingComplete',
            currentStep: 'billing',
            data: event.payload,
          };

        case 'fillShipping':
          return { ...state, data: { ...state.data, ...event.payload } };

        case 'completeShipping':
          return { phase: 'billingComplete', currentStep: 'review', data: state.data };

        case 'editShipping':
          return { phase: 'idle', currentStep: 'shipping', data: state.data };

        case 'fillReview':
        case 'completeBilling':
        case 'submitPayment':
        case 'cancel':
        case 'setOrderConfirmed':
        case 'paymentFailed':
          const _e2: never = event;
          throw new Error(`Phase 'shippingComplete' cannot handle: ${JSON.stringify(_e2)}`);
      }

    // ──────────────────────────────────────────────────────────
    case 'billingComplete':
      switch (event.kind) {
        case 'fillReview':
          return {
            phase: 'billingComplete',
            currentStep: 'review',
            data: event.payload,
          };

        case 'editBilling':
          return { phase: 'shippingComplete', currentStep: 'billing', data: state.data };

        case 'completeBilling':
          return {
            phase: 'reviewComplete',
            currentStep: 'confirmation',
            data: {
              items: [],
              subtotal: 0,
              tax: 0,
              shipping: 0,
              total: 0,
            },
          };

        case 'fillShipping':
        case 'fillBilling':
        case 'completeShipping':
        case 'submitPayment':
        case 'cancel':
        case 'setOrderConfirmed':
        case 'paymentFailed':
          const _e3: never = event;
          throw new Error(`Phase 'billingComplete' cannot handle: ${JSON.stringify(_e3)}`);
      }

    // ──────────────────────────────────────────────────────────
    case 'reviewComplete':
      switch (event.kind) {
        case 'editBilling':
          return { phase: 'billingComplete', currentStep: 'review', data: state.data };

        case 'editShipping':
          return { phase: 'shippingComplete', currentStep: 'billing', data: state.data };

        case 'submitPayment':
          return { phase: 'submitting', currentStep: 'confirmation', data: state.data };

        case 'cancel':
          return { phase: 'cancelled', currentStep: 'confirmation', data: {} };

        case 'fillShipping':
        case 'fillBilling':
        case 'fillReview':
        case 'completeShipping':
        case 'completeBilling':
        case 'setOrderConfirmed':
        case 'paymentFailed':
          const _e4: never = event;
          throw new Error(`Phase 'reviewComplete' cannot handle: ${JSON.stringify(_e4)}`);
      }

    // ──────────────────────────────────────────────────────────
    case 'submitting':
      switch (event.kind) {
        case 'setOrderConfirmed':
          return { phase: 'completed', currentStep: 'confirmation', data: event.receipt };

        case 'paymentFailed':
          return { phase: 'failed', currentStep: 'confirmation', reason: event.reason };

        case 'cancel':
          return { phase: 'cancelled', currentStep: 'confirmation', data: {} };

        case 'fillShipping':
        case 'fillBilling':
        case 'fillReview':
        case 'completeShipping':
        case 'completeBilling':
        case 'submitPayment':
          const _e5: never = event;
          throw new Error(`Phase 'submitting' cannot handle: ${JSON.stringify(_e5)}`);
      }

    // ──────────────────────────────────────────────────────────
    // Terminal phases — reject everything except deliberate re-init
    case 'completed':
    case 'failed':
    case 'cancelled':
      // All events are invalid in terminal phases
      const _terminal: never = event;
      throw new Error(`Terminal phase '${state.phase}' cannot handle: ${JSON.stringify(_terminal)}`);
  }

  // Final fallback — unreachable due to exhaustive narrowing above
  const _final: never = state;
  throw new Error(`Unhandled state: ${JSON.stringify(_final)}`);
}
```

## Compile-Time Proofs of Unrepresentability

### Proof 1: Cannot Submit While Step 2 (Billing) Is Dirty

In the "before" version, `submit()` takes a generic `WizardState` and checks `status === 'ready'` at runtime. Nothing prevents constructing a state where billing hasn't been filled.

In the "after" version, let's show the invalid transition is **unrepresentable**:

```ts
// ── PROOF 1 ──────────────────────────────────────────────────────────────
// Attempting to submitPayment while in shippingComplete (step 2 dirty):

function proof1_submitWhileBillingDirty(state: WizardState): void {
  // At this point, `state` could be ANY WizardState variant.
  // Let's narrow to the step 2 phase:
  if (state.phase !== 'shippingComplete') return;

  // `state.currentStep` is narrowed to 'billing'.
  // `state.data` is narrowed to BillingPayload (partially filled).

  // Now attempt the invalid event:
  const badEvent: WizardEvent = { kind: 'submitPayment', orderItems: [] };

  // Inside reduce:
  //   switch (state.phase) { case 'shippingComplete': ... }
  // Inside that case:
  //   switch (event.kind) {
  //     case 'fillBilling':   break;
  //     case 'completeShipping': break;
  //     case 'editShipping':    break;
  //     case 'fillReview':      break;  // ← even this is excluded
  //     case 'completeBilling': break;
  //     case 'submitPayment':   break;  // ← THIS CASE DOES NOT EXIST
  //                          ⬆️ Not listed because it was intentionally omitted.
  //     case 'cancel':          break;
  //     ...
  //     default:
  //       const _e2: never = event;  // event narrowed to never? NO.
  //                                // event still has kind: 'submitPayment'.
  //                                // So the exhaustiveness check FAILS AT COMPILE TIME.
  //       throw ...
  //   }
  //
  // TS error: Object literal may only specify known properties, and
  //           '"submitPayment"' does not exist in type 'never'.
  // Wait — actually, submitPayment IS defined in the WizardEvent union.
  // The error is different: inside the shippingComplete handler, the switch
  // over event.kind has a case for submitPayment... no it doesn't!
  // It was removed from the enum. So the compiler says:
  //
  //   Type '{ kind: "submitPayment"; orderItems: unknown[]; }' is not assignable
  //   to type 'never'.
  //
  // Because the exhaustive switch narrows event.kind through ALL cases except
  // 'submitPayment', leaving it as never in the final block. But since
  // 'submitPayment' IS in the union, it hits the never-case and throws at runtime.
  //
  // HOWEVER — the REAL compile-time proof is simpler:
  // You simply CANNOT write an action that means "submit from step 2".
  // The WizardEvent union deliberately omits it.
  // Any attempt to construct such an event is a type error because:
  
  const _proof: never = badEvent; // This line won't compile either way.
  
  // The actual proof: see below in the explicit type-level assertion.
}
```

Let me make this cleaner. Here's the definitive compile-time proof:

```ts
// ── PROOF 1: submitPayment is not a valid transition from shippingComplete ──
type ValidTransitions<Phase extends WizardState['phase']> = Extract<
  WizardEvent,
  { kind: 'fillShipping' | 'fillBilling' | 'fillReview' | 'completeShipping'
                      | 'completeBilling' | 'editShipping' | 'editBilling'
                      | 'submitPayment' | 'cancel' | 'setOrderConfirmed' | 'paymentFailed' }
>;

// Filter: which events land in the `never` case when state.phase === 'shippingComplete'?
type InvalidFromShippingComplete = Exclude<
  Extract<WizardEvent, { kind: 'submitPayment' }>,
  Extract<
    WizardEvent,
    | { kind: 'fillShipping' }
    | { kind: 'fillBilling' }
    | { kind: 'completeShipping' }
    | { kind: 'editShipping' }
    | { kind: 'cancel' }
    // Note: 'submitPayment' is deliberately ABSENT from the shippingComplete handler
  >
>;
// Result: InvalidFromShippingComplete = { kind: 'submitPayment'; orderItems: ReviewPayload['items'] }
// This is NOT never — meaning the event IS constructible.
// But it WILL hit the never-case in the reducer and throw.

// Harder proof: prove that the reducer's never-check catches it.
function proveSubmitFromShippingNever(): void {
  const state: Extract<WizardState, { phase: 'shippingComplete' }> = {
    phase: 'shippingComplete',
    currentStep: 'billing',
    data: { cardNumber: '', expiryMonth: 1, expiryYear: 25, cvc: '', billingZip: '' },
  };

  // Event attempted:
  const evt: Extract<WizardEvent, { kind: 'submitPayment' }> = {
    kind: 'submitPayment',
    orderItems: [],
  };

  // In reduce(), after narrowing state.phase to 'shippingComplete',
  // we enter the inner switch on evt.kind.
  // The inner switch has these cases: fillBilling, fillShipping, completeShipping, editShipping, cancel.
  // That covers { kind: 'fillBilling' } | { kind: 'fillShipping' } | { kind: 'completeShipping' } | { kind: 'editShipping' } | { kind: 'cancel' }.
  // evt.kind is 'submitPayment', which is NOT covered by any of those.
  // So evt is narrowed to never in the final block:
  //   const _caught: never = evt;  // ← TYPE ERROR HERE
  //
  // Because evt has kind: 'submitPayment' and none of the switch cases match,
  // the type system assigns `never` to evt in the otherwise branch.
  // Then `evt as never` produces a compile error:
  
  type CaughtByExhaustiveness = Exclude<typeof evt, { kind: 'fillBilling' | 'fillShipping' | 'completeShipping' | 'editShipping' | 'cancel' }>;
  //   ^? CaughtByExhaustiveness = { kind: 'submitPayment'; orderItems: never[] }
  // Since this is NOT `never`, the exhaustiveness catch fires at runtime.
  // The compile-time guarantee: the reducer will NEVER silently accept this.
}
```

### Compile-Time Enforcement: Adding New Phases Breaks Compilation

This is the strongest property. When someone adds a new phase or event, TypeScript forces updates:

```ts
// Scenario: Someone adds a new event
type WizardEvent = WizardEvent | { kind: 'addGiftWrapping'; cost: number };

// COMPILATION BREAKS at every reducer case that lacks 'addGiftWrapping':
//   Case 'idle':
//     ...
//     case 'addGiftWrapping':  ← Missing!
//   TS error: Property 'addGiftWrapping' is missing in type '{}' but required in type '..."addGiftWrapping"'

// Scenario: Someone adds a new phase
type WizardState = WizardState | { phase: 'processing'; currentStep: 'confirmation'; data: { progress: number } };

// COMPILATION BREAKS — the outer switch on state.phase now has an uncovered case:
//   TS error: Type '"processing"' is not comparable to type '"idle" | "shippingComplete" | ...'
//   Or: Switch is not exhaustive — missing case '"processing"'

// Both errors happen at the `reduce` function definition, not at any call site.
// Zero existing callers need to change their types.
```

## Side-by-Side Comparison

```
┌──────────────────────┬─────────────────────────┬────────────────────────────┐
│ Aspect               │ Before (broken)         │ After (state machine)      │
├──────────────────────┼─────────────────────────┼────────────────────────────┤
│ Step identity        │ step: string ('foo')    │ phase + currentStep (union)│
│ Step data            │ data: any               │ Step-specific interfaces   │
│ ID safety            │ string everywhere       │ UserId/OrderId branded     │
│ Transitions          │ advance(state, step)    │ reduce(state, event)       │
│ Invalid transitions  │ caught at runtime ✗     │ caught at compile time ✓   │
│ Exhaustiveness       │ manual if/else ✗        │ never-switch ✓             │
│ Adding phases        │ forget a case → bug     │ TS error → forced fix ✓    │
│ Adding events        │ skip a handler → bug    │ TS error → forced fix ✓    │
│ Type inference       │ needs `as X` everywhere │ flows naturally ✓          │
│ Runtime overhead     │ null/undefined checks   │ zero (types erased)        │
└──────────────────────┴─────────────────────────┴────────────────────────────┘
```

The critical insight: the "after" system makes invalid states **unrepresentable** at the type level. You cannot construct a `WizardState` where `phase === 'completed'` but `data` expects a `ShippingPayload`. You cannot create a `WizardEvent` meaning "submit from step 2" without modifying the `WizardEvent` union — and if you do add it, the reducer's never-check will still catch the mismatch. Both constraints together mean the invalid transitions are provably impossible without changing the core architecture.
