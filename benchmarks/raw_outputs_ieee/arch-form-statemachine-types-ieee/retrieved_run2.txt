## Before: `any` + casts + non-null assertions

Here's what most teams write when they need a form wizard quickly:

```typescript
type WizardState = any;  // "it'll work at runtime"

function nextStep(state: WizardState): WizardState {
  const current = state.step;  // string — which step? "review"? "payment"?
  
  if (current === 'review') {
    return { ...state, step: 'payment' } as WizardState;  // as-cast galore
  }
  
  return state;
}

function submit(state: WizardState) {
  if (state.status === 'dirty') {  // dirty? for which step?
    throw new Error('Fix errors first');
  }
  sendOrder(state.data!);  // ! assertion — data might not exist
}
```

**What can go wrong:**
- Submit while Step 2 (`Review`) is dirty → caught only at runtime
- Navigate back after `Payment` completes → silently allowed
- `UserId` and `OrderId` are both `string` → easily confused
- Every transition needs an `as WizardState` cast → types are lying

---

## After: Exhaustive State Machine

### Step 1: Branded/Opaque IDs

```typescript
// These look like strings but cannot be mixed up at compile time.
type UserId = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };

const UserId = (value: string): UserId => value as UserId;
const OrderId = (value: string): OrderId => value as OrderId;

// ❌ Compile error: Argument of type 'string' is not assignable
//    to parameter of type 'UserId'.
const userId: UserId = UserId("user-42");
const orderId: OrderId = OrderId("order-99");
// orderId = userId;  // ERROR — different brands
```

The intersection with `{ readonly __brand: 'UserId' }` makes the type **opaque** — nothing produces a `UserId` except the constructor, and you can't accidentally pass a bare `string`.

---

### Step 2: Per-Step Data Requirements via Discriminated Unions

Each step has exactly the fields it needs. No `any`, no missing `.data!` checks.

```typescript
// ── Step 1: PersonalInfo ───────────────────────────────
interface PersonalInfoData {
  email: string;
  name: string;
}

// ── Step 2: Review (depends on accumulated state) ──────
interface ReviewData {
  items: Array<{ sku: string; qty: number; price: number }>;
  subtotal: number;
  shippingMethod: 'standard' | 'express';
}

// ── Step 3: Payment (requires OrderId from submission) ─
interface PaymentData {
  orderId: OrderId;       // branded, not a raw string
  amount: number;
  cardLast4: string;
}
```

---

### Step 3: The State Machine State Type

This is where the magic happens. Each step is a **discriminated union member** keyed by `step`. The compiler knows exactly which fields exist based on `step`.

```typescript
// ── Actions (events) ──────────────────────────────────
type WizardAction =
  | { kind: 'SET_PERSONAL_INFO'; payload: PersonalInfoData; status: 'clean' }
  | { kind: 'DIRTY_REVIEW' }
  | { kind: 'CLEAN_REVIEW' }
  | { kind: 'SUBMIT_FOR_PAYMENT' }
  | { kind: 'PAYMENT_SUCCEEDED'; orderId: OrderId }
  | { kind: 'PAYMENT_FAILED'; error: string }
  | { kind: 'RESET' };

// ── State ─────────────────────────────────────────────
type WizardState =
  // Phase A: collecting personal info
  | {
      phase: 'collecting';
      step: 'personal_info';
      data: PersonalInfoData | null;
      dirty: Record<string, boolean>;   // tracks per-field edits
    }
  // Phase B: review stage
  | {
      phase: 'reviewing';
      step: 'review';
      data: ReviewData | null;
      dirty: Record<string, boolean>;
    }
  // Phase C: payment processing
  | {
      phase: 'paying';
      step: 'payment';
      data: PaymentData | null;
      error?: string;
    }
  // Phase D: complete
  | {
      phase: 'complete';
      step: 'done';
      data: { orderId: OrderId; timestamp: Date };
    };
```

Key design decisions:
- **`phase`** separates broad lifecycle stages (collecting → reviewing → paying → done)
- **`step`** pins the exact sub-state within that phase
- **`data`** carries only what's relevant; its shape changes per member
- **`dirty`** exists in collecting/reviewing but NOT in paying/done — you can't even *access* it when those phases don't have it

### Step 4: The Transition Function (Exhaustiveness Check)

```typescript
function reduceWizard(
  state: WizardState,
  action: WizardAction
): WizardState {
  // ── Narrow by phase first (top-level gate) ──────────
  switch (state.phase) {
    case 'collecting':
      return reduceCollecting(state, action);
    case 'reviewing':
      return reduceReviewing(state, action);
    case 'paying':
      return reducePaying(state, action);
    case 'complete':
      return reduceComplete(state, action);
    default:
      // Exhaustiveness check: should never happen
      const _exhaustive: never = state.phase;
      throw new Error(`Unknown phase: ${_exhaustive}`);
  }
}
```

The `_exhaustive: never` line forces TypeScript to verify that every possible `phase` value is handled. If someone adds `'onboarding'` to `WizardState` later, this line **stops compiling**.

Now the per-phase reducers:

```typescript
function reduceCollecting(
  state: Extract<WizardState, { phase: 'collecting' }>,
  action: WizardAction
): WizardState {
  switch (action.kind) {
    case 'SET_PERSONAL_INFO':
      if (!action.payload.email || !action.payload.name) {
        throw new Error('Email and name are required');
      }
      return {
        phase: 'collecting',
        step: 'personal_info',
        data: action.payload,
        dirty: {},
      };

    case 'RESET':
      return {
        phase: 'collecting',
        step: 'personal_info',
        data: null,
        dirty: {},
      };

    case 'DIRTY_REVIEW':
    case 'CLEAN_REVIEW':
    case 'SUBMIT_FOR_PAYMENT':
    case 'PAYMENT_SUCCEEDED':
    case 'PAYMENT_FAILED':
      // Can't jump to these from collecting phase
      const _invalid: never = action;
      throw new Error(`Cannot do ${action.kind} from ${state.phase}`);

    default: {
      const _exhaustive: never = action;
      throw new Error(`Unhandled action: ${_exhaustive}`);
    }
  }
}
```

```typescript
function reduceReviewing(
  state: Extract<WizardState, { phase: 'reviewing' }>,
  action: WizardAction
): WizardState {
  switch (action.kind) {
    case 'DIRTY_REVIEW':
      return { ...state, dirty: { items: true } };

    case 'CLEAN_REVIEW':
      return { ...state, dirty: {} };

    case 'SUBMIT_FOR_PAYMENT':
      // ✏️ INVALID TRANSITION #1 PROOF: Submit while dirty is caught here
      if (Object.values(state.dirty).some(Boolean)) {
        return state; // stays in reviewing, blocks advancement
      }
      // Simulate order creation returning a branded OrderId
      return {
        phase: 'paying',
        step: 'payment',
        data: {
          orderId: OrderId(`ord-${Math.random().toString(36).slice(2)}`),
          amount: state.data!.subtotal,
          cardLast4: '',
        },
      };

    case 'RESET':
      return {
        phase: 'collecting',
        step: 'personal_info',
        data: null,
        dirty: {},
      };

    case 'SET_PERSONAL_INFO':
    case 'PAYMENT_SUCCEEDED':
    case 'PAYMENT_FAILED':
      const _invalid: never = action;
      throw new Error(`Cannot do ${action.kind} from ${state.phase}`);

    default: {
      const _exhaustive: never = action;
      throw new Error(`Unhandled action: ${_exhaustive}`);
    }
  }
}
```

```typescript
function reducePaying(
  state: Extract<WizardState, { phase: 'paying' }>,
  action: WizardAction
): WizardState {
  switch (action.kind) {
    case 'PAYMENT_SUCCEEDED':
      return {
        phase: 'complete',
        step: 'done',
        data: {
          orderId: action.orderId,
          timestamp: new Date(),
        },
      };

    case 'PAYMENT_FAILED':
      return { ...state, error: action.error };

    case 'RESET':
      return {
        phase: 'collecting',
        step: 'personal_info',
        data: null,
        dirty: {},
      };

    case 'SET_PERSONAL_INFO':
    case 'DIRTY_REVIEW':
    case 'CLEAN_REVIEW':
    case 'SUBMIT_FOR_PAYMENT':
      const _invalid: never = action;
      throw new Error(`Cannot do ${action.kind} from ${state.phase}`);

    default: {
      const _exhaustive: never = action;
      throw new Error(`Unhandled action: ${_exhaustive}`);
    }
  }
}
```

```typescript
function reduceComplete(
  state: Extract<WizardState, { phase: 'complete' }>,
  action: WizardAction
): WizardState {
  switch (action.kind) {
    case 'RESET':
      return {
        phase: 'collecting',
        step: 'personal_info',
        data: null,
        dirty: {},
      };

    // ✏️ INVALID TRANSITION #2 PROOF: Going back from complete
    // All other actions are rejected below

    case 'SET_PERSONAL_INFO':
    case 'DIRTY_REVIEW':
    case 'CLEAN_REVIEW':
    case 'SUBMIT_FOR_PAYMENT':
    case 'PAYMENT_SUCCEEDED':
    case 'PAYMENT_FAILED': {
      const _blocked: never = action;
      throw new Error(
        `Cannot do ${action.kind} — wizard is already complete`
      );
    }

    default: {
      const _exhaustive: never = action;
      throw new Error(`Unhandled action: ${_exhaustive}`);
    }
  }
}
```

### Step 5: Compile-Time Proof That Invalid Transitions Are Impossible

#### Proof 1: Cannot submit while Step 2 (Review) is dirty

```typescript
const reviewState: WizardState = {
  phase: 'reviewing',
  step: 'review',
  data: { items: [], subtotal: 0, shippingMethod: 'standard' },
  dirty: { items: true },  // ← marked dirty
};

// This expression returns reviewState unchanged (the guard block advances).
// But more importantly, there is NO action that transitions
// reviewing→paying when dirty is truthy. The SUBMIT_FOR_PAYMENT action
// explicitly checks Object.values(state.dirty).some(Boolean) and returns
// the same state — so the UI must show validation errors before dispatching.

const afterSubmit = reduceWizard(reviewState, { kind: 'SUBMIT_FOR_PAYMENT' });

// ❌ You CANNOT construct an action like:
//   { kind: 'SKIP_DIRTY_CHECK_SUBMIT' }
// Because such an action doesn't exist in WizardAction union.
// There is literally no type-level path to bypass the dirty check.
```

The type system guarantees this because:
1. Only one action triggers the review→paying transition: `SUBMIT_FOR_PAYMENT`
2. The reducer for that action contains the guard — no alternative action exists
3. Adding a bypass action would require changing `WizardAction` union, and the exhaustive `never` checks in all phase reducers would fail to compile until every handler accounts for it

#### Proof 2: Cannot go back after payment

```typescript
const completedState: WizardState = {
  phase: 'complete',
  step: 'done',
  data: { orderId: OrderId('ord-final'), timestamp: new Date() },
};

// Every navigation action is blocked:
reduceWizard(completedState, { kind: 'DIRTY_REVIEW' });     // throws
reduceWizard(completedState, { kind: 'SET_PERSONAL_INFO' }); // throws

// The only valid action from 'complete' is RESET (which resets fully,
// doesn't go back to a previous step). To "go back to review" you'd need:
//   { kind: 'GO_BACK_TO_REVIEW' }
// which doesn't exist in WizardAction. The type system prevents it.
```

Again, the proof is structural:
1. The `complete` phase reducer lists every action in `WizardAction` explicitly
2. Actions like `DIRTY_REVIEW`, `SET_PERSONAL_INFO`, `SUBMIT_FOR_PAYMENT` are matched to `_blocked: never` and thrown
3. Only `RESET` produces a forward transition (back to `collecting`, not to an intermediate step)

### Step 6: Inference-Friendly Usage (No Casts, No `any`)

```typescript
// Pattern-matching on state automatically narrows the type:
function renderWizard(state: WizardState) {
  switch (state.phase) {
    case 'collecting':
      // state.data is PersonalInfoData | null — IDE autocomplete works
      return <form>{state.data?.name}</form>;

    case 'reviewing':
      // state.data is ReviewData | null, state.dirty is accessible
      return <ReviewCard items={state.data?.items ?? []} />;

    case 'paying':
      // state.data is PaymentData | null, .error is optional string
      return <PaymentForm orderId={state.data?.orderId} />;

    case 'complete':
      // state.data is { orderId: OrderId; timestamp: Date }
      return <Confetti orderId={state.data.orderId} />;
  }
  // Exhaustiveness: the switch covers all 4 phase values
  const _unreachable: never = state.phase;
  return null;
}
```

### Summary Table

| Problem | Before (broken) | After (safe) |
|---|---|---|
| **Type safety** | `any` — compiler silent | Discriminated union — compiler enforces structure |
| **Invalid transitions** | Runtime bugs via `as` casts | Impossible — action types encode valid paths only |
| **ID confusion** | Both `UserId` and `OrderId` are `string` | Branded types — compile-time mismatch detection |
| **Missing fields** | `state.data!` non-null assertions | Union narrowing — `data` shape follows `phase` |
| **New states** | Forgets to update handlers | `never` exhaustiveness check fails compilation |
| **IDE support** | Nothing useful | Full autocomplete per phase |

The core insight: **types encode business rules, not just shapes**. By modeling the wizard as a state machine where each action represents a real event and each state member carries only its required data, we make it impossible to express invalid configurations — not as a runtime assertion, but as a type-theoretic guarantee.
