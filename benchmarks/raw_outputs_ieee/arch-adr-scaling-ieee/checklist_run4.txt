# ADR-001: Retain Modular Monolith; Isolate Notifications as a Sidecar Process

**Status:** Proposed
**Date:** 2026-08-26
**Supersedes:** n/a

## Context

The application is a modular monolith built on Rails with PostgreSQL. We operate under these concrete constraints:

| Factor | Current State | Impact |
|---|---|---|
| Deploy frequency | ~2 deploys/week across the entire app | Every change to any module requires a full redeploy of all modules |
| Team size | 12 engineers, shared codebase | Cross-module coupling causes merge conflicts and blocking PR reviews |
| Traffic pattern | Realtime notifications is the only hot path — handles 5× the request volume of any other module | Cannot scale the notification path independently of the rest of the app |
| Database | Single shared PostgreSQL instance | All modules share tables; cross-module boundaries are convention-based, not enforced |
| Leadership concern | Full microservices rewrite is being proposed as the solution | Estimated at 6–9 months engineering effort with high operational overhead |

**Forcing factors** — decisions we cannot reverse cheaply:
- PostgreSQL schema is shared; extracting a service boundary would require duplication or network calls for every join that spans modules
- The team has zero production Kubernetes experience; running separate services means rolling our own deployment infrastructure
- 12 engineers on a lean roadmap means architectural overhead directly competes with feature delivery

## Decision

We **retain the modular monolith** and solve the notification scaling problem by **extracting only the realtime notification module as an independent sidecar process**, not a full microservice.

Concretely:
- Extract `NotificationWorker` into its own small Rails/Sinatra service that connects to the same PostgreSQL database (read replica if needed) and subscribes to notification events via ActiveJob background jobs or a pub/sub channel
- The main monolith publishes notification events to Redis Streams (or pg_notify) — the sidecar consumes them and manages WebSocket connections
- Deployment is independent for notifications; the monolith deploys at the current cadence
- Module boundaries within the monolith are strengthened via clear package conventions (e.g., `app/modules/*/`) and inter-module dependency rules enforced by standard lint tooling
- Shared models stay in the monolith; the sidecar owns only its own controllers, workers, and connection-management layer

**What "sidecar" means here:** Separate deployment unit (one `docker compose` stack or two Procfiles). Same shared database. Zero new orchestration complexity beyond what we already run.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
Break the monolith into independent services, each with its own database, deployed on Kubernetes.

**Why rejected:** The blast radius is enormous — 6–9 months, 12 engineers reassigning from features to infra. We lose single-query transactions across domains (orders + inventory + notifications today require one DB transaction). Most of our modules don't have enough traffic to justify independent scaling. Operational cost (Kubernetes, service mesh, distributed tracing) dwarfs our actual deploy pain (2 deploys/week is modest).

### Alternative 2: Extract Only Notifications + Strengthen Monolith Boundaries (CHOSEN)
As documented above.

**Why chosen:** Addresses both forcing factors simultaneously. Deploy pain is reduced because the hot module ships independently. Scaling is solved because notifications run isolated. Cost is minimal — one extra service file and deployment configuration. No infrastructure upgrades required. Reversible: the sidecar can be merged back into the monolith if traffic patterns change.

### Alternative 3: Vertical Scaling (Do Nothing Extra)
Keep everything as-is but upgrade the server capacity for the monolith. Add CDN/caching to reduce load on the notification path.

**Why rejected:** Doesn't solve the deploy-coupling problem at all. Every notification model change still requires a full redeploy. Vertical scaling has a ceiling (PostgreSQL connection limits, Ruby GIL for concurrent request handling) and doesn't address the independent release velocity problem. This paper-cuts both issues.

### Alternative 4: Feature Flag + Incremental Extraction Over 12 Months
Extract modules one-by-one behind feature flags over a year-long program.

**Why rejected:** Introduces permanent dual-state complexity (flag checks sprinkled through code, half-extracted services calling back into the monolith). The flag burden becomes technical debt we never pay down. Given the team size and product stage, this timeline is unrealistically slow and delays real improvement for too long.

## Consequences

### Positive
- Notifications can scale independently without taking down or restarting the main app
- Deployment of the notification layer is now uncoupled — hotfixes to push logic ship instantly
- Operational overhead stays low: two processes, one database, no K8s, no service mesh
- Clearer module boundaries in the monolith improve maintainability even without extraction
- Team can keep shipping features instead of spending months on platform engineering

### Negative
- Shared database means we still need coordination when migration touches both sides (mitigated by using the same migration pipeline)
- Cross-service calls for data the sidecar doesn't own introduce eventual consistency — acceptable for notifications but must be understood
- Slightly more deployment targets (2 instead of 1), though both are trivial Docker containers
- New engineers need to understand two repo/service configurations during setup
- If notification traffic drops, the sidecar sits idle — minor cost inefficiency

### What Becomes Easier
- Hotfixing notification behavior without deploying the entire app
- Adding more notification channels (email, SMS, push) without touching core Rails code
- Monitoring and alerting for the notification path separately

### What Becomes Harder
- Debugging flows that span the notification boundary (requires distributed tracing we don't currently have)
- Ensuring data consistency between the monolith's event emission and the sidecar's consumption (accepting eventual consistency)

## Reversal Triggers

This decision remains valid until any of the following conditions materialize. When triggered, we revisit with a fresh ADR:

1. **Two or more additional modules** consistently hit performance or deployment bottlenecks that vertical scaling and stronger boundaries cannot resolve — indicating the monolith has grown past its organizational capacity
2. **Team grows to 30+ engineers** with overlapping ownership on the same modules, causing chronic deploy conflicts and review bottlenecks despite modular boundaries
3. **Independent compliance requirements** arise for specific modules (e.g., PCI scope isolation, HIPAA data segregation) that make shared databases legally impractical
4. **Sidecar traffic exceeds horizontal scaling thresholds** — e.g., needing hundreds of notification worker instances where independent deployment loses its advantage

If any trigger fires, we move toward either further incremental extractions (Alternative 2, scaled up) or the full microservices path (Alternative 1), whichever the current evidence supports.
