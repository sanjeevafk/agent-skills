# ADR-0001: Preserve Modular Monolith, Extract Only Realtime Notifications Service

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering Leadership, Backend Team Leads, DevOps

## Context

The application is a Rails + PostgreSQL modular monolith shipping ~2 deploys/week. One domain — realtime push notifications — is experiencing CPU-bound WebSocket fan-out and event-stream contention that the shared process cannot absorb without degrading core API latency for other modules (billing, catalog, user profiles). Load patterns show the notification module consumes 40% of request-handling threads during peak but only owns 8% of business value.

Leadership has proposed a full microservices rewrite across all modules to enable independent scaling per domain. The forcing factors are: (1) notification throughput is growing 3x quarter-over-quarter, (2) deploy friction for the monolith is real but manageable at current velocity, and (3) organizational size (12 engineers) does not yet justify the operational overhead of separate services for every domain. We are seeing deployment pain, but not at a scale that demands full decomposition.

## Decision

We **do not** perform a full microservices rewrite. Instead we extract the realtime notification module into its own service while keeping the remaining modules as a single Rails monolith sharing the same PostgreSQL database (one-schema-per-module via namespace convention).

### Architecture

```
┌─────────────────────┐    ┌──────────────────┐
│  Rails Monolith      │    │ Notification Svc  │
│  ┌────────────────┐  │    │ (FastAPI/Ruby)    │
│  │ Billing        │  │    │                  │
│  ├────────────────┤  │    │ • WebSocket pool  │
│  │ Catalog        │  │    │ • Push gateways   │
│  ├────────────────┤  │    │ • Event consumers │
│  │ Users          │  │    └────────┬─────────┘
│  └────────────────┘  │             │ async
└──────────┬───────────┘    ┌───────┴────────┐
           │ sync queries   │ PostgreSQL     │
           └────────────────│ (shared DB)    │
                            └────────────────┘
```

- The notification service gets its own process, own WebSocket pool, and can scale independently behind a load balancer.
- Communication between monolith and notification service uses asynchronous messaging (PostgreSQL `LISTEN/NOTIFY` for low-latency, Redis Streams for durable retry/dead-letter). No synchronous HTTP calls across service boundary for event dispatch.
- Database remains shared to avoid distributed transactions during this extraction phase. Each module keeps its own schema namespace (`billing.*`, `catalog.*`, `notifications.*`).
- Deployment pipeline stays singular for the monolith; notification service gets its own CI/CD stack but shares the same repository (monorepo layout).

### Concrete boundaries

- Notifications service owns: WebSocket connections, push provider integrations (APNs, FCM, WebPush), notification delivery status tracking, and preference storage under `notifications.*` schema.
- Monolith owns: everything else, including the notification *preferences* write-path (users update prefs through billing/user APIs); read-path for preferences goes from the shared DB.
- The notification service is an eventual-consistency reader of user state via change-data-capture or periodic polling over shared tables until a dedicated user-profile projection layer is built.

### Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Shared-database anti-pattern creates implicit coupling between monolith and notification service | High | Enforce schema ownership via lint rules and migrations gated by ownership checks; document the shared-db contract as a SLA |
| Operational surface area grows (2 processes instead of 1) | Medium | Containerize both early; use same orchestrator (Kubernetes/Docker Compose) with feature flags to control rollout |
| Notification service becomes a copy of monolith patterns, defeating purpose | Medium | Restrict its tech stack choice to technologies optimized for long-lived connections and high fan-out (FastAPI, Node, or Go) |

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite (leadership proposal)

Extract **all** modules into independently deployed, independently-scaled services with separate databases and inter-service gRPC/HTTP communication.

**Rejected because**: The team of 12 engineers lacks the operational bandwidth for n services. Network failure modes multiply combinatorially (n² communication paths vs 1 monolith). Distributed tracing, sagas, and idempotency become mandatory everywhere. At current revenue and traffic levels, independent scaling for billing/catalog/users provides zero ROI — only notifications shows measurable scaling pressure. Estimated 6-9 months of engineering time for zero user-visible benefit beyond incremental infra flexibility.

### Alternative 2: Vertical Slice + Thread Pool Isolation (keep monolith, add concurrency tuning)

Keep the monolith intact but isolate notification handling using dedicated background worker pools (Sidekiq queues with separate thread counts), pre-forked Puma workers pinned to notification endpoints, and connection pooling tuned per-route.

**Rejected because**: WebSocket long-lived connections cannot coexist efficiently with HTTP request processing in the same Ruby process group. Even with IO multiplexing, the GVL limits true concurrency for CPU-bound serialization work (payload assembly, template rendering). Sidekiq worker isolation pushes hot work off the request path but does not solve the live WebSocket fan-out problem. Measured capacity ceiling still falls short of projected Q4 load (3x growth trajectory).

### Alternative 3: Plugin-Based Extraction (keep monolith, compile notification module as an isolated gem/plugin)

Use a compiled Rails plugin or main-app isolation pattern where the notification module lives as a self-contained package within the monolith, with its own routes, models, background jobs, and test suite — deployable separately via bundler version pinning, but still running in the same process.

**Rejected because**: Process-level isolation is required to handle the WebSocket fan-out workload independently. Same-process separation provides dependency isolation but not resource isolation — the notification module can still starve other modules of GVL time and GC pauses. Gem-based separation delays the inevitable when the module outgrows what a shared process can offer.

## Consequences

### Positive
- **Independent scaling** for the highest-growth module without paying infrastructure cost for all others
- **Minimal operational overhead** — two services vs twelve; most tooling (CI, monitoring, logging) works unchanged
- **Zero downtime migration** — shared database avoids data migration complexity; notification service starts reading existing rows immediately
- **Learning ramp** — team gains experience with service extraction on the easiest boundary before considering further splits if needed
- **Preserves developer velocity** — 12 engineers can still maintain one primary codebase for the majority of features

### Negative
- **Shared database coupling** creates an implicit contract that must be manually enforced; future developers may incorrectly query cross-schema tables without going through the notification service's API
- **Two deployment targets** introduces a small coordination burden (migration ordering, rollback sequencing)
- **Inconsistent scaling** — the monolith hits the same wall again eventually, making a follow-up decision inevitable
- **Debugging complexity** increases slightly — events cross a process boundary, requiring correlation IDs in logs

## Reversal Triggers

This decision will be re-evaluated automatically when any of the following conditions are met:

1. **Notification service reaches <15% of total engineering capacity** — indicates other modules also need independent scaling, suggesting a broader extraction
2. **Shared database row count exceeds 50M** or p99 query latency consistently exceeds 50ms — indicates database-level bottleneck requiring schema-level splitting
3. **Team grows beyond 20 engineers** — increasing coordination cost makes the monolith's single-deploy model a bottleneck worth replacing
4. **Notification service requires capabilities incompatible with shared-process architecture** (e.g., native extensions, non-Ruby runtime requirements for hardware integration)
5. **Infrastructure cost of running notification service independently exceeds 40% of total platform spend** — signals that the extraction created more cost than value, and alternatives should be reconsidered

Any reversal changes status to `superseded by ADR-NNNN` and triggers a new architectural review with leadership input.

# ADR-0001: Extract Only Realtime Notifications Module

**Date**: 2026-08-26
**Status**: accepted
**Deciders**: Engineering leadership, product lead, CTO

## Context

The codebase is a Rails modular monolith backed by PostgreSQL, currently deploying twice per week. Each deployment touches all modules due to the shared deployment pipeline, creating release bottlenecks and blast-radius risk. One module — realtime notifications — has outgrown its fair share: high read/write ratios from WebSocket connections and push dispatch require more instances than the rest of the application justifies. Infrastructure costs are rising because we scale the entire monolith to accommodate notification traffic spikes. Leadership has proposed extracting the entire application into microservices to solve scaling, deploys, and organizational boundaries simultaneously. However, this project has significant coupling concerns: shared models, cross-module service calls, and complex database transactions mean a full decomposition would take an estimated 6–9 months with ongoing regression risk during the transition period.

## Decision

Extract only the realtime notifications module into its own horizontally-scaled service with a separate deployment pipeline, leaving the rest of the application as a modular monolith. Provide the notification service through a well-defined API boundary and move its data into a dedicated schema (or small subset of tables). Use event sourcing / change-data-capture to handle cross-module communication instead of direct service calls. Deploy both services from the same repository but with separate CI/CD pipelines until further proven value emerges.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
- **Pros**: Eliminates monolith constraints entirely; each service owns its own lifecycle, database, deployment, and scaling independently.
- **Cons**: Estimated 6–9 months of decommissioning work; distributed transaction complexity across all bounded contexts; network failure modes replace single-process failures; organizational context-switching overhead; testing becomes exponentially harder with integration points across every team.
- **Why not**: The forcing factors that matter (notification scaling, deploy frequency) represent a fraction of the application's behavior. Decoupling everything solves problems that don't exist while introducing new systemic risks. The cost-benefit ratio doesn't justify scope this broad when a surgical extraction addresses the actual pain points.

### Alternative 2: Extract Notifications + Identify Second Service After Learning
- **Pros**: Same benefits as Alternative 1 but de-risked through iteration; validates whether independent deployment actually improves developer velocity before committing to broader decomposition.
- **Cons**: Requires accepting a mixed architecture longer-term; potential inconsistency if the second extraction never happens and two deployment patterns coexist indefinitely.
- **Why not**: This IS what we're doing — it's the baseline choice. We're not committing to exactly one extraction; we're committing to the principle of extracting *proven hot modules*. If after 3 deployments of the notification service we identify a second module needing independent scaling, the process and patterns will already be established, reducing future extraction effort.

### Alternative 3: Stay in Monolith with Scaling Workarounds
- **Pros**: Zero architectural churn; preserves single-codebase simplicity; no inter-service communication patterns needed.
- **Cons**: Cannot scale notifications independently — still over-provisions the entire app for notification load; deployment blast radius remains large; cannot hire or organize teams around notifications as a distinct product area.
- **Why not**: Does not address the concrete business need (realtime notifications requiring dedicated infrastructure) and continues to degrade developer experience with full-app deploys for every change.

## Consequences

### Positive
- Notification module scales independently, eliminating wasted compute during low-notification periods and handling spikes without affecting other services.
- Notification changes deploy on their own cadence — hotfixes to push delivery or WebSocket handling go live without touching the main application.
- Reduces deployment blast radius for non-notification changes since those modules no longer share a deployment artifact.
- Establishes a reproducible extraction pattern (API boundary, event-based communication, separate CI) for any future hot modules.
- Keeps overall system complexity manageable — most of the application retains the simplicity of a well-organized monolith.

### Negative
- Two services sharing part of the same repository introduces organizational friction around ownership boundaries and CI configurations.
- Cross-module queries that previously used joins now require API calls or replicated data, adding latency and failure surface area.
- Eventual consistency between the monolith core and the notification service means downstream consumers may see stale state briefly.
- Adds operational overhead: two deployment pipelines, two sets of health checks, dual logging/metrics routing.

### Risks
- **Shared schema drift**: Both services evolve the domain model independently. Mitigation: extract owned tables entirely for the notification service; monolith accesses notifications only via API, never direct DB queries.
- **Mixed architecture lock-in**: Accepting "monolith plus two services" could harden into permanent technical debt if never re-evaluated. Mitigation: set a 6-month review milestone tied to specific metrics (deploy frequency improvement, scaling cost reduction, developer satisfaction scores).
- **Inter-service call storms**: Direct synchronous calls between services create cascading failure paths. Mitigation: enforce async event-driven communication for all cross-boundary interactions; circuit breakers on any remaining sync calls.

## Reversal Triggers

This decision should be reconsidered if any of the following conditions materialize:

1. **Three+ hot modules identified** within 12 months of this decision — the pattern proves the monolith can no longer contain independently-scaling domains, warranting either deeper extraction or architectural reassessment.
2. **Cross-service call count exceeds 50/day** between the monolith and notification service — indicates the boundary was drawn at the wrong point and the modules share too much context to be meaningfully separated.
3. **Notification service does not achieve ≥40% infrastructure cost savings** within 6 months — suggests independent scaling was not the primary constraint and the root cause lies elsewhere.
4. **Deployment frequency fails to increase** (target: ≤30 minutes from commit to production for non-notification changes, ≤5 minutes for notification-only changes) after one quarter — indicates the extracted pipeline is bottlenecked by something other than notification code.

# ADR-042: Retain Modular Monolith with Selective Extraction of Notifications Module

**Status**: Proposed
**Date**: 2026-08-26
**Deciders**: Engineering Lead, CTO, Product Director
**Context**: Rails modular monolith, 12 engineers, Postgres, deploy bottleneck on realtime notifications

---

## Context

Our Rails application is a well-organized modular monolith with isolated concerns per module (routing, isolation via service boundaries, separate test suites). We have **12 engineers** working across it, deploying **twice per week**. The team has reached consensus that the architectural organization is sound — modular folders, clear boundaries, shared Postgres instance, no cross-module direct DB calls.

**Problem**: The `realtime_notifications` module is a single point of operational failure during deploys. Every deploy restarts the entire app, including this module which handles WebSocket connections and requires rolling restarts with zero downtime to avoid disconnecting active users. Current strategy — full app restart — causes **3–8 second notification outages per deploy**, generating ~40 support tickets/month and one P1 incident in Q2 when 2,300 concurrent users were dropped simultaneously.

**Forcing factors**:
- Deploy frequency is already stable at 2/week; increasing it further is desired but risky today
- Notification traffic has grown 3x YoY (from 5k to 15k concurrent WS connections); it's the only module needing horizontal scaling
- Infrastructure cost for full microservices rewrite: estimated $18k/mo additional (Kubernetes, service mesh, observability tooling, SRE overhead)
- Team size: 12 FTE — large enough to run multiple services, small enough that coordination overhead matters

## Decision

**Retain the modular monolith as the primary architecture.** Extract **only** the `realtime_notifications` module into its own lightweight service (Go or Node.js) with its own deployment pipeline, independent scaling, and its own Redis-backed pub/sub layer. All other modules remain in the Rails modular monolith.

This is a *selective extraction*, not a full decomposition. The extracted service communicates with the monolith via:
- API gateway (internal, Nginx or Kong) for synchronous calls (push notification dispatch, user preferences lookup)
- Redis Streams for async events (event sourcing for notification delivery receipts)
- Shared Postgres read replica (not write — the monolith owns writes)

The extracted service must be thin: no business logic duplication, just the transport layer (WS handling, connection management, fan-out) and a message queue consumer.

## Alternatives Considered

### Alternative 1 — Full Microservices Rewrite
Extract every module into independently deployable, independently scalable services (user service, order service, catalog service, notification service, etc.), each with its own database, deployment pipeline, and infrastructure.

**Rejected because**: The 12-engineer team would spend 6–9 months rebuilding what we already have in a distributed form. Cross-service consistency (currently handled by Postgres transactions) becomes a permanent complexity tax. Operational overhead (CI/CD pipelines, monitoring, tracing, deployment orchestration) multiplies without proportional benefit — only *one* module has scaling problems, not all twelve. Cost exceeds budget. No forcing factor demands this level of decomposition.

### Alternative 2 — Extract Only Notifications (Chosen)
Extract only the `realtime_notifications` module into a separate service while keeping everything else in the Rails modular monolith.

### Alternative 3 — Horizontal Pod Scaling Within the Monolith
Add Kubernetes pod autoscaling with canary deployments using something like AWS App Runner or ECS Service Split Traffic — essentially running multiple instances of the monolith behind a load balancer with gradual rollout, so only non-notification endpoints are affected by rolling restarts. Use Sidekiq for background jobs and keep WebSocket connections sticky.

**Rejected because**: Sticky WebSocket sessions make graceful rolling restarts fundamentally unreliable — you either accept dropped connections (the current problem) or implement complex session state replication across pods (adding coupling and latency). Passenger/Puma graceful restart doesn't help — it still reloads the entire app binary. The cost-benefit ratio favors extracting the one problematic module rather than rearchitecting the deployment model for a system where only one component has this problem.

### Alternative 4 — Upgrade Existing CI/CD for Zero-Downtime Deploys
Invest in Blue-Green deployments or Strangler Fig patterns *without* code extraction — add dual environments, traffic switching, and feature flags within the existing monolith. Keep all code in one repo, one deploy.

**Rejected because**: Blue-green doubles infra costs permanently (two identical environments always running). It solves the outage problem but not the scaling problem — the notification module still shares memory and CPU with everything else during peak traffic. Feature flag complexity grows unboundedly without addressing the root constraint: one process, one address space.

## Consequences

### Positive
- **Deploy stability**: Notification module gets independent zero-downtime deploys; other modules continue on the existing schedule
- **Targeted scaling**: Notifications scale horizontally based on concurrent connections; the rest of the app scales independently
- **Minimal disruption**: 12 engineers continue working in the same codebase for 95% of features; learning curve is limited to one new service
- **Cost control**: Additional infra cost estimated at $3–5k/mo (single extra service + Redis), compared to $18k/mo for full microservices
- **Lower cognitive load**: Engineers don't need distributed systems expertise for 95% of daily work; service boundary is one clear interface, not dozens
- **Reversibility**: Extraction can be reversed if traffic doesn't grow as projected (see Reversal Triggers)
- **Proof of pattern**: Establishes a repeatable extraction pattern for future needs without committing to full decomposition

### Negative
- **Hybrid architecture**: Running two different stacks (Rails + Go/Node) adds minor devops complexity (two build pipelines, two runtime environments)
- **Cross-service communication**: Must handle eventual consistency for notification delivery receipts; lost messages become possible (mitigated by Redis Streams durability)
- **Deployment coordination**: Need to coordinate version compatibility between monolith and extraction service during migration window (~4 weeks)
- **Observability gaps**: Distributed tracing across service boundary requires adding tools (OpenTelemetry) not previously needed
- **Database coupling**: Read replica lag introduces stale data risk for notification lookups (mitigated by caching warm defaults and TTL < 5s)

## Reversal Triggers

This decision becomes invalid and triggers a re-evaluation if any of the following occur:

1. **Traffic growth**: Concurrent WebSocket connections exceed 100k (current: 15k), making even extracted deployment insufficiently granular
2. **Team growth**: Team expands beyond 25 FTE such that cross-team coordination on the monolith creates >30% context-switching overhead (measured quarterly)
3. **Feature velocity**: Two or more additional modules (beyond notifications) independently require different scaling profiles or deployment frequencies within 12 months
4. **Infra economics**: Cloud provider pricing changes make containerized service hosting cheaper than VM-based monolith hosting by >2x
5. **Time limit**: If after 18 months the extracted service hasn't demonstrably reduced deploy-related incidents by ≥80%, reconsider whether extraction was the right lever (might indicate the real problem is CI/CD pipeline quality, not architecture)

# ADR-001: Retain Modular Monolith; Isolate Notifications as a Sidecar Process

**Status:** Proposed
**Date:** 2026-08-26
**Supersedes:** n/a

## Context

The application is a modular monolith built on Rails with PostgreSQL. We operate under these concrete constraints:

| Factor | Current State | Impact |
|---|---|---|
| Deploy frequency | ~2 deploys/week across the entire app | Every change to any module requires a full redeploy of all modules |
| Team size | 12 engineers, shared codebase | Cross-module coupling causes merge conflicts and blocking PR reviews |
| Traffic pattern | Realtime notifications is the only hot path — handles 5× the request volume of any other module | Cannot scale the notification path independently of the rest of the app |
| Database | Single shared PostgreSQL instance | All modules share tables; cross-module boundaries are convention-based, not enforced |
| Leadership concern | Full microservices rewrite is being proposed as the solution | Estimated at 6–9 months engineering effort with high operational overhead |

**Forcing factors** — decisions we cannot reverse cheaply:
- PostgreSQL schema is shared; extracting a service boundary would require duplication or network calls for every join that spans modules
- The team has zero production Kubernetes experience; running separate services means rolling our own deployment infrastructure
- 12 engineers on a lean roadmap means architectural overhead directly competes with feature delivery

## Decision

We **retain the modular monolith** and solve the notification scaling problem by **extracting only the realtime notification module as an independent sidecar process**, not a full microservice.

Concretely:
- Extract `NotificationWorker` into its own small Rails/Sinatra service that connects to the same PostgreSQL database (read replica if needed) and subscribes to notification events via ActiveJob background jobs or a pub/sub channel
- The main monolith publishes notification events to Redis Streams (or pg_notify) — the sidecar consumes them and manages WebSocket connections
- Deployment is independent for notifications; the monolith deploys at the current cadence
- Module boundaries within the monolith are strengthened via clear package conventions (e.g., `app/modules/*/`) and inter-module dependency rules enforced by standard lint tooling
- Shared models stay in the monolith; the sidecar owns only its own controllers, workers, and connection-management layer

**What "sidecar" means here:** Separate deployment unit (one `docker compose` stack or two Procfiles). Same shared database. Zero new orchestration complexity beyond what we already run.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
Break the monolith into independent services, each with its own database, deployed on Kubernetes.

**Why rejected:** The blast radius is enormous — 6–9 months, 12 engineers reassigning from features to infra. We lose single-query transactions across domains (orders + inventory + notifications today require one DB transaction). Most of our modules don't have enough traffic to justify independent scaling. Operational cost (Kubernetes, service mesh, distributed tracing) dwarfs our actual deploy pain (2 deploys/week is modest).

### Alternative 2: Extract Only Notifications + Strengthen Monolith Boundaries (CHOSEN)
As documented above.

**Why chosen:** Addresses both forcing factors simultaneously. Deploy pain is reduced because the hot module ships independently. Scaling is solved because notifications run isolated. Cost is minimal — one extra service file and deployment configuration. No infrastructure upgrades required. Reversible: the sidecar can be merged back into the monolith if traffic patterns change.

### Alternative 3: Vertical Scaling (Do Nothing Extra)
Keep everything as-is but upgrade the server capacity for the monolith. Add CDN/caching to reduce load on the notification path.

**Why rejected:** Doesn't solve the deploy-coupling problem at all. Every notification model change still requires a full redeploy. Vertical scaling has a ceiling (PostgreSQL connection limits, Ruby GIL for concurrent request handling) and doesn't address the independent release velocity problem. This paper-cuts both issues.

### Alternative 4: Feature Flag + Incremental Extraction Over 12 Months
Extract modules one-by-one behind feature flags over a year-long program.

**Why rejected:** Introduces permanent dual-state complexity (flag checks sprinkled through code, half-extracted services calling back into the monolith). The flag burden becomes technical debt we never pay down. Given the team size and product stage, this timeline is unrealistically slow and delays real improvement for too long.

## Consequences

### Positive
- Notifications can scale independently without taking down or restarting the main app
- Deployment of the notification layer is now uncoupled — hotfixes to push logic ship instantly
- Operational overhead stays low: two processes, one database, no K8s, no service mesh
- Clearer module boundaries in the monolith improve maintainability even without extraction
- Team can keep shipping features instead of spending months on platform engineering

### Negative
- Shared database means we still need coordination when migration touches both sides (mitigated by using the same migration pipeline)
- Cross-service calls for data the sidecar doesn't own introduce eventual consistency — acceptable for notifications but must be understood
- Slightly more deployment targets (2 instead of 1), though both are trivial Docker containers
- New engineers need to understand two repo/service configurations during setup
- If notification traffic drops, the sidecar sits idle — minor cost inefficiency

### What Becomes Easier
- Hotfixing notification behavior without deploying the entire app
- Adding more notification channels (email, SMS, push) without touching core Rails code
- Monitoring and alerting for the notification path separately

### What Becomes Harder
- Debugging flows that span the notification boundary (requires distributed tracing we don't currently have)
- Ensuring data consistency between the monolith's event emission and the sidecar's consumption (accepting eventual consistency)

## Reversal Triggers

This decision remains valid until any of the following conditions materialize. When triggered, we revisit with a fresh ADR:

1. **Two or more additional modules** consistently hit performance or deployment bottlenecks that vertical scaling and stronger boundaries cannot resolve — indicating the monolith has grown past its organizational capacity
2. **Team grows to 30+ engineers** with overlapping ownership on the same modules, causing chronic deploy conflicts and review bottlenecks despite modular boundaries
3. **Independent compliance requirements** arise for specific modules (e.g., PCI scope isolation, HIPAA data segregation) that make shared databases legally impractical
4. **Sidecar traffic exceeds horizontal scaling thresholds** — e.g., needing hundreds of notification worker instances where independent deployment loses its advantage

If any trigger fires, we move toward either further incremental extractions (Alternative 2, scaled up) or the full microservices path (Alternative 1), whichever the current evidence supports.
