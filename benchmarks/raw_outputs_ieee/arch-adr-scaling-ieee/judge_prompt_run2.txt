## ADR-042: Modular Monolith Strategy Over Microservices Rewrite

**Status:** Accepted
**Date:** 2026-08-26
**Authors:** Engineering Lead
**Deciders:** Engineering Team (12 engineers), CTO

---

### Context

Our codebase is a single Rails application backed by Postgres. The team of 12 engineers currently deploys **2 times per week** with a combined cycle time of ~4 hours from commit to production. This is workable but not fast enough for our growth trajectory.

**The forcing factors driving this discussion:**

| Factor | Current State | Target |
|---|---|---|
| Deploy frequency | 2/week | Daily+ |
| Notification throughput | Scaled with entire app; wastes 60% compute on non-WS workers during low traffic | Scale web vs. WS independently |
| Team allocation | ~3 engineers (25%) constantly context-switched into realtime notification bugs | Dedicated subteam ownership |
| Blast radius of incidents | Any deploy risks the notification pipeline (and vice versa) | Isolate failure domains |

Leadership has proposed a **full microservices rewrite** across all modules. Several senior engineers have voiced strong reservations — citing precedent from comparable rewrites at similar-stage companies — but lack a structured alternative proposal.

This ADR documents the team's decision on how to proceed.

---

### Concerns

- **Deploy pain** must decrease; the current 2-deploys-weekly cadence is causing release-day toil and preventing feature velocity
- **Notification scalability** is a real problem — WebSocket connections consume memory and CPU, inflating costs when the rest of the app is idle
- **Team coordination overhead** scales superlinearly with service count; a 12-person team cannot efficiently maintain 15+ services without heavy DevOps investment
- **Migration risk** — any rewrite carries delivery delay risk that directly impacts revenue commitments
- **Reversibility** — if the wrong path is chosen, how easily can we pivot later?

---

### Decision

We adopt a **modular monolith first, surgical extraction second** strategy:

1. **Immediately:** Restructure the Rails monolith into explicit, test-isolated modules using the modularity patterns described by Martin Fowler (sealed modules with defined interfaces, no cross-module direct DB access, each module owns its schema namespace). Apply this to the notification module first as a pilot.

2. **Extract only the notification service** within 90 days — the one module that demonstrably requires independent scaling. Deploy it separately, communicate via message queue (Redis Streams or RabbitMQ), and run both the monolith and the extracted service from the same repo (monorepo).

3. **Defer all other service boundaries.** Do not decompose users, payments, content, search, or any other domain. If a second extraction is warranted after 90 days, it must pass the same forcing-factor review that justified notifications.

4. **Run both from the same repository** under `app/modules/notifications` (monolith) → `services/notifications` (extracted). Shared dependencies go in a gemspec (`lib/notifications_client`). No fork-and-forget.

This is not a "never do microservices" decision. It is a "don't boil the ocean" decision — bounded experimentation with actual extraction, not theoretical decomposition.

---

### Alternatives Considered

#### Alternative 1: Full Microservices Rewrite (Proposed by Leadership)

Decompose every domain into independently deployed services (users, auth, payments, content, search, notifications, analytics, admin, plus shared infrastructure). Each gets its own database, deployment pipeline, and monitoring stack.

#### Alternative 2: Extract Only the Notification Module (Chosen)

Restructure the monolith modularly while keeping everything in one deployable unit, then extract only the notification subsystem as a separate process. All other modules remain co-located.

#### Alternative 3: Stay as Monolith, Improve CI/CD Only

Keep the existing flat Rails structure. Invest exclusively in faster CI pipelines, blue-green or canary deployments, and operational discipline to reduce deploy friction without architectural change.

---

### Consequences

#### Positive

- **Deploy frequency increases** — modular boundaries give us clear integration-test contracts. Even within one repo, we can parallelize testing per-module and achieve daily-ish deploys without extracting anything
- **Notification scaling becomes real** — the extracted service runs horizontally on its own, sized purely for WebSocket connections. Estimated 40–60% cost reduction on notification infra
- **Team ownership aligns** — the 2-person realtime squad owns the notification service end-to-end. Other teams touch their modules without needing realtime-domain knowledge
- **Blast radius shrinks** — a notification outage doesn't take down payments; a payment deploy doesn't restart WebSocket servers
- **Low migration risk** — no rip-out-and-rebuild timeline. We keep delivering features while iterating toward this state incrementally
- **Reversible** — the extracted service stays in the same repo. We can re-merge it into the monolith if the data shows it wasn't worth the complexity, or extract further modules if needed

#### Negative

- **Dual-run complexity** — for ~60–90 days we operate both the monolith and an extracted service, adding integration-testing surface and deployment orchestration
- **Cross-process calls are slower** — replacing in-process module calls with message-queue communication introduces latency (~5–15ms p99 additional per call). We mitigate by keeping synchronous paths in-process where possible
- **Dev environment heaviness** — `docker-compose up` must start Rails + notification worker + Redis/RabbitMQ. Onboarding new engineers takes ~15 minutes longer until they're green
- **Not a silver bullet for all teams** — only 2 of 12 engineers benefit immediately from reduced context-switching. The remaining 10 see incremental improvement (better tests, module isolation) but don't get dedicated ownership yet
- **Architecture drift risk** — without continued discipline, the extracted service could become another tangled mess that's hard to move or merge. Requires deliberate interface design reviews
- **Doesn't satisfy leadership's preferred path** — some stakeholders expected the "big bang" rewrite. Pushback may arise if they perceive this as insufficient ambition

# ADR 0001: Resist Full Microservices Rewrite; Extract Only Realtime Notifications Module

**Status:** Accepted  
**Date:** 2026-08-26  
**Deciders:** Engineering leadership, Tech leads  

---

## Context

We are a team of 12 engineers operating a **modular monolith** built on Ruby on Rails + PostgreSQL. Two forcing factors are driving a proposal from leadership to undertake a **full microservices rewrite**:

1. **Deploy pain — 2 deploys/week.** Our current CI/CD pipeline can safely handle this cadence without incident, but we're hitting a practical ceiling. Developers report that even small changes carry disproportionate coordination cost due to our single-deploy model. This is a *process* problem, not necessarily an *architecture* problem.

2. **Realtime notifications module needs independent scaling.** The notifications handler is CPU-bound (WebSocket fan-out, push notification dispatching, rate-limit checks) and has different load characteristics than the rest of the app. Scaling it horizontally within the monolith means over-provisioning everything else.

Leadership's instinct is a full rewrite into microservices. We need to evaluate whether that's the right move versus targeted extraction.

---

## Decision

We choose to **extract only the realtime notifications module as an independent service** while keeping the remainder of the application as a modular monolith. This balances the two forcing factors without paying the full cost of a distributed-systems rewrite.

Specifically:

- The notifications module runs as its own process, deployed independently, with its own database schema (can share the same Postgres cluster initially).
- Inter-service communication uses async events via Sidekiq / Redis pub-sub — no synchronous HTTP calls between the service and the monolith.
- The remaining ~95% of the codebase stays in the Rails monolith, preserving developer velocity and reducing cognitive overhead.
- We invest parallel effort in improving deployment automation (blue-green or canary) to increase our safe deploy frequency beyond 2/week.

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite

Re-architect the entire application into independently deployable services, each with its own database, technology stack chosen per-service, orchestrated by an API gateway.

**Rejected because:**

- **Cognitive cost scales super-linearly with team size.** For a 12-engineer team, tracking inter-service contracts, distributed tracing, eventual consistency, and deployment orchestration across 8-12 services adds a significant overhead tax on every feature. This is the well-documented Conway's Law trap.
- **Deploy pain persists after rewrite** unless you also build a robust deployment platform (service mesh, CI/CD pipelines per service, rolling update strategy). The tools cost is real. We'd spend 3-4 months building infrastructure before shipping our first business-facing service.
- **Data consistency becomes hard.** Every domain event that currently crosses a method boundary now requires sagas, compensating transactions, or outbox patterns. Bug surface area grows significantly.
- **The core issue — deploy frequency — is solvable without rewriting.** Blue-green or canary deployment for a monolith gets us to daily deploys without breaking the data layer.
- **Opportunity cost is enormous.** Those 3-4 months could ship real features or solve other scaling bottlenecks.

### Alternative 2: Extract Only Realtime Notifications (Chosen)

Pull the notifications module into its own thin service while leaving the rest of the monolith intact. Use async messaging for cross-cutting concerns.

**Accepted because:**

- **Addresses the actual scaling bottleneck.** Notifications are the only module with truly different resource profiles. Isolating it solves the over-provisioning problem.
- **Minimal blast radius.** Only one service boundary to design, test, and operate. The rest of the team continues working in familiar territory.
- **Proves the extraction pattern.** If we later need to split another module (say, billing or search), we already have the playbook.
- **Deploy pain improves incrementally.** Two deployments (monolith + notifications) vs twelve is still manageable for a 12-person team. We gain confidence before committing to more splits.
- **Low migration complexity.** Notifications is already loosely coupled internally. The extraction is mostly configuration and wiring, not re-architecture.

### Alternative 3: Big Ball of Mud — Stay Monolithic, Add Connection Pooling & Horizontal Scaling at App Tier

Keep everything in one Rails app, scale vertically (larger instances) and add horizontal app-tier scaling via load-balanced containers sharing the same database. Use connection pool tuning and read replicas for performance.

**Rejected because:**

- **Doesn't solve the notifications scaling problem.** Notification workers consume memory and CPU in the same process as API handlers. You can't scale them independently without over-provisioning the rest of the app unnecessarily.
- **Database connection pooling hits diminishing returns.** With many long-lived WebSocket connections from the notifications subsystem, pgbouncer or Heroku-style pooling struggles with connection exhaustion during traffic spikes.
- **Still capped at one deploy unit.** Doesn't address the root cause of deploy friction.

### Alternative 4: Modularize Within the Monolith Using Railways/Separeted Concerns Pattern

Use strong modular boundaries inside Rails (e.g., `app/modules/notifications`, engine isolation) without extracting to a separate process. Isolate the module through dependency injection and interface contracts.

**Rejected because:**

- **Helpful for code organization but does nothing for scaling.** All code still shares the same process, same resources, same deployment. The notifications module would still drag down the whole app under load.
- **Deploy frequency remains unchanged.** Still one artifact, one deploy window, one rollback scope.
- **Partial value.** Better code hygiene than doing nothing, but insufficient against the stated forcing factors.

---

## Consequences

### Positive

- **Targeted scaling works.** Notifications scale independently without wasting resources on unrelated request handling.
- **Team velocity preserved.** The 12 engineers work in one dominant codebase, avoiding the coordination tax of a full service sprawl.
- **Incremental learning path.** We validate our service-extraction instincts and tooling with low risk before splitting more modules.
- **Simpler operations.** Fewer running processes, fewer databases, fewer observability headaches than a full microservices architecture.
- **Easier debugging.** One trace ID crosses fewer network boundaries. No need for distributed tracing tooling yet.

### Negative

- **One hybrid boundary to manage.** We now maintain both monolith conventions and one service contract. The edge case is: what if the notifications service fails? The monolith must degrade gracefully.
- **Shared data access temptation.** There will be pressure to have the notifications service query the monolith's primary tables directly, which creates a coupling anti-pattern. This must be enforced rigorously.
- **Not a forever answer.** Eventually, further module extractions may require similar decisions. That's fine — each one should be evaluated when it arrives.
- **Deploy frequency won't reach "daily" overnight.** Two weekly deploys → two daily deploys (monolith + notifications) is progress but may still feel slow. We must pair this decision with CI/CD investment.

---

## Reversal Triggers

This decision stands until one or more of these conditions materializes:

1. **We attempt to extract a second or third module from the monolith and find the shared data layer or inconsistent APIs make clean extraction painful repeatedly**, indicating the underlying architectural debt warrants deeper re-evaluation.
2. **Our deploy frequency fails to improve above 5-7 deploys/week within 6 months of implementing blue-green/canary deployment**, suggesting the monolith itself has become too large or complex for effective deployment practices.
3. **A business requirement emerges that demands technology-specific optimization for a non-notification module** (e.g., a search module needing Elasticsearch-native indexing, or a payments module requiring Go/Fintech-grade concurrency patterns that Rails cannot provide).
4. **The team grows beyond 25 engineers**, where the communication overhead of maintaining a single codebase begins exceeding the benefits of shared context and rapid iteration.
5. **Observability data shows that >40% of production incidents are caused by the notifications service crashing dependent parts of the monolith**, despite isolation, indicating that the failure-domain boundary isn't sufficient.

Any of these conditions should trigger a new ADR evaluating a broader architectural shift.

- **Why not**: We'd pay the stragner tax for 6 months without actually solving the deploy problem until the end. The extraction approach does the same thing faster and cleaner.

## Consequences

### Positive
- Notifications can be horizontally scaled independently based on WebSocket connection count, not total request volume.
- Notifications deploys are independent — notification-layer changes don't require rebuilding and redeploying the entire monolith.
- The 12-person team avoids the cognitive tax of managing 8+ independently deployed services.
- Shared PostgreSQL simplifies transactions across the non-notification domains; the notification DB can use a leaner schema optimized for high-write throughput.
- Rollback surface is minimized — breaking notifications doesn't take down the rest of the application.

### Negative
- Inter-service communication introduces failure modes (network timeouts, event delivery guarantees) that didn't exist in-process.
- Debugging issues spanning both services requires correlating logs across two separate infrastructure stacks.
- The monolith still deploys as a unit — if a second hot module emerges, we'll face the same question again sooner rather than later.
- Team must maintain two deployment configs, two CI pipelines, and two sets of secrets.

### Risks
- **Risk**: Notification service becomes too coupled to the monolith database, preventing true independence. **Mitigation**: Define a strict event-driven interface; the notification service reads from a materialized view, never joins monolith tables directly.
- **Risk**: Team over-extracts additional modules after extracting notifications, drifting toward microservices by accident. **Mitigation**: Establish a gate — any further extraction requires a new ADR and VP approval.
- **Risk**: Notifications proves unstable, requiring frequent rollouts that erode the "deploy independence" benefit. **Mitigation**: Treat this as a learning experiment — if notifications doesn't justify the infra cost after one quarter, re-evaluate and consider absorbing it back.

### Reversal Triggers

This decision will be revisited if any of the following conditions materialize:

1. **A second module reaches equivalent heat** (≥30% of resource consumption for <15% of feature demand), making incremental extraction worthwhile.
2. **Deployment duration exceeds 60 minutes** even after notification extraction, indicating the remaining monolith has become too large to be practical.
3. **Team grows beyond 20 engineers** working on the same codebase concurrently, where the monolith's shared database becomes a bottleneck despite proper schema partitioning.
4. **The notification service itself needs to be decomposed** into multiple sub-services (e.g., push, email, SMS channels separated), suggesting the original granularity was insufficient.

If any trigger fires, a new ADR will be authored to decide whether to pursue broader extraction or address the constraint through different means (read replicas, query optimization, sharding).
