# ADR-0001: Preserve Modular Monolith; Extract Only Notifications to Independent Service

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering Lead, VP of Engineering, 12-onboard engineering team

## Context

The codebase is a Rails + PostgreSQL modular monolith maintained by a 12-person engineering team. Two forcing factors are driving the debate:

1. **Deploy friction:** The team averages 2 deployments per week, and each deployment touches the entire monolith. Merges into `main` trigger monolithic builds and integration test suites that consistently take 40+ minutes, creating merge conflict churn and slowing feature delivery.

2. **Notification module overload:** The real-time notifications module (Action Cable/WebSocket layer + dedicated Postgres tables) accounts for ~35% of its application's memory footprint under peak load but receives only ~8% of overall feature requests. It cannot be scaled independently because it shares the same deployment container and database pool.

Leadership has proposed a full microservices rewrite — decomposing every domain boundary into independently deployed services. The question is whether to embrace that rewrite or pursue a less disruptive path.

## Decision

We preserve the modular monolith as the primary application and extract **only** the notifications module into a standalone service. This gives us independent deploy and scale capability for the hot path while preserving the integration simplicity, developer velocity, and operational overhead of a single deployable unit for all other domains.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
- **Pros**: Each service deploys, scales, and fails independently. Tight bounded contexts eliminate cross-module coupling concerns.
- **Cons**: 4–6 month minimum rewrite timeline with zero new features delivered during that period. Introduces distributed tracing, eventual consistency, inter-service authentication, and multi-database migrations. For a 12-person team, context-switching across 8+ services adds more cognitive overhead than it saves. Network latency between services makes the local dev loop significantly slower.
- **Why not**: The ROI is negative for a team our size. We would spend 6 months rebuilding what we already have, then add 3–4 more months wiring up distributed observability. Meanwhile, the business gets no new features for half a year.

### Alternative 2: Extract Only the Notifications Service
- **Pros**: Solves both problems directly. Notifications gets independent deploy and horizontal scaling within 2–3 weeks. The remaining 92% of the app continues shipping with predictable monthly release cadence. Database connections are reduced by isolating the WebSocket connection pool from the main request pool. Developer tooling stays unchanged for the bulk of the codebase.
- **Cons**: Adds one inter-service dependency (notifications → core via async events). Slightly increases infra complexity (one extra service, one extra database schema). The team must coordinate the API contract between the two modules.
- **Why chosen**: It addresses 100% of the motivating problems with the smallest feasible scope and risk.

### Alternative 3: Strangler Fig Pattern — Incremental Extraction Over 6 Months
- **Pros**: Gradually reduces blast radius of mistakes. Each extracted module can prove its case before committing more resources.
- **Cons**: Requires maintaining dual implementations during the transition window (the classic "strangler" tax). The system spends 6 months in an awkward hybrid state with more complexity, not less. The team still faces the same deploy friction during the entire transition since most modules remain in the monolith.
- **Why not**: We'd pay the stragner tax for 6 months without actually solving the deploy problem until the end. The extraction approach does the same thing faster and cleaner.

## Consequences

### Positive
- Notifications can be horizontally scaled independently based on WebSocket connection count, not total request volume.
- Notifications deploys are independent — notification-layer changes don't require rebuilding and redeploying the entire monolith.
- The 12-person team avoids the cognitive tax of managing 8+ independently deployed services.
- Shared PostgreSQL simplifies transactions across the non-notification domains; the notification DB can use a leaner schema optimized for high-write throughput.
- Rollback surface is minimized — breaking notifications doesn't take down the rest of the application.

### Negative
- Inter-service communication introduces failure modes (network timeouts, event delivery guarantees) that didn't exist in-process.
- Debugging issues spanning both services requires correlating logs across two separate infrastructure stacks.
- The monolith still deploys as a unit — if a second hot module emerges, we'll face the same question again sooner rather than later.
- Team must maintain two deployment configs, two CI pipelines, and two sets of secrets.

### Risks
- **Risk**: Notification service becomes too coupled to the monolith database, preventing true independence. **Mitigation**: Define a strict event-driven interface; the notification service reads from a materialized view, never joins monolith tables directly.
- **Risk**: Team over-extracts additional modules after extracting notifications, drifting toward microservices by accident. **Mitigation**: Establish a gate — any further extraction requires a new ADR and VP approval.
- **Risk**: Notifications proves unstable, requiring frequent rollouts that erode the "deploy independence" benefit. **Mitigation**: Treat this as a learning experiment — if notifications doesn't justify the infra cost after one quarter, re-evaluate and consider absorbing it back.

### Reversal Triggers

This decision will be revisited if any of the following conditions materialize:

1. **A second module reaches equivalent heat** (≥30% of resource consumption for <15% of feature demand), making incremental extraction worthwhile.
2. **Deployment duration exceeds 60 minutes** even after notification extraction, indicating the remaining monolith has become too large to be practical.
3. **Team grows beyond 20 engineers** working on the same codebase concurrently, where the monolith's shared database becomes a bottleneck despite proper schema partitioning.
4. **The notification service itself needs to be decomposed** into multiple sub-services (e.g., push, email, SMS channels separated), suggesting the original granularity was insufficient.

If any trigger fires, a new ADR will be authored to decide whether to pursue broader extraction or address the constraint through different means (read replicas, query optimization, sharding).
