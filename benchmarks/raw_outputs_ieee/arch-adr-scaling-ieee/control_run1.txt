# ADR-042: Modular Monolith Retention with Targeted Module Extract

**Status:** Accepted  
**Date:** 2026-08-26  
**Owners:** Platform Engineering, Engineering Leadership  
**Deciders:** CTO, VP Engineering, Principal Engineers  

---

## Context

Our application is a Rails modular monolith backed by Postgres. Current operational reality:

- **Deploy pain:** Average of 2 deploys/week per module, all sharing the same deployment pipeline and release train. A change to one area requires rebuilding and redeploying the entire application.
- **One scaling outlier:** The `notifications` module handles real-time WebSocket connections and push delivery. It consistently sits at ~85% CPU during peak while other modules average <30%. Scaling the whole app to serve notifications is wasteful — we're paying for and deploying unused controller logic alongside each notification worker.
- **Team structure:** 12 engineers across 4 squads (Core Product, Notifications, Integrations, Platform). Cross-module coupling exists but is bounded by explicit module boundaries using the "service locator" pattern via Rails concerns and `app/modules/`.
- **Data integrity concern:** No existing event-sourcing or sagas layer. Multiple modules share rows in `orders`, `users`, and `account_balances` tables.

**Forcing factors (non-negotiable constraints):**
1. We cannot tolerate more than 6 months of additional cycle time on the current roadmap.
2. We must retain single-database simplicity (no distributed transactions today).
3. Team velocity cannot drop below our current throughput of ~14 story points/squad/sprint.

---

## Decision

We **retain the modular monolith** and make a **targeted extraction** of only the `notifications` module into its own service with an independent deploy and scale boundary. All other modules remain in the monolith indefinitely unless new forcing factors emerge.

### What this means concretely

| Aspect | Decision |
|---|---|
| Deploy boundary | All modules except `notifications` continue in a shared CI/CD pipeline. |
| Scale boundary | `notifications` runs as a separate process (`notifications-worker`) behind its own container image, deployed independently, scaled horizontally via K8s HPA based on connection count / message queue depth. |
| Data ownership | `notifications` owns a read replica copy of relevant data (`users.last_name`, `users.push_token`, `notification_events`). Write access remains in-app through domain events published from the monolith. |
| Inter-service communication | Event-driven via Kafka topics (`domain.events.orders`, `domain.events.users_updated`). No synchronous REST calls between the monolith and the extracted service. |
| Shared dependencies | Extract `notifications-core` as a local gem, publish to private Gemnasium registry. Other modules depend on it for domain types (models, value objects) so the API contract is versioned and type-safe. |

## Alternatives Considered

### Alternative 1 — Full Microservices Rewrite

Extract *all* modules into independent services. Each gets its own database, deploy pipeline, and team ownership.

| | Assessment |
|---|---|
| Positives | Each team can deploy, scale, and choose technology independently. True organizational alignment with Conway's Law. |
| Negatives | ~18–24 month rewrite estimate at 12 engineers. Distributed tracing, saga patterns, eventual consistency overhead. 8–12x increase in infrastructure cost. Massive cognitive load switching context between services. High probability of missing the 6-month roadmap constraint. |

**Rejected.** Over-engineered for the problem. Only one module has a genuine scaling need; the rest have none.

### Alternative 2 — Extract Only Notifications (CHOSEN)

As described in the decision above. Minimal structural change, maximum payoff on the actual pain point.

| | Assessment |
|---|---|
| Positives | Solves the hot module scaling problem immediately. Independent deploy frequency for notifications eliminates its merge conflicts with core code. Single database retained for all other modules — no distributed transaction complexity. Low risk: one service, one team owns it (~3 engineers). Estimated extraction time: 6–8 weeks. |
| Negatives | Two systems to operate in production (monolith + notification service). Read replica management adds ~4 hrs/month SRE time. The monolith still deploys as a unit — slow deploy pain persists for other modules. |

### Alternative 3 — Multi-Process Rails (Puma Workers)

Use Puma's multi-process mode within the monolith to isolate `notifications` workers from request handling threads. Share the same binary, same deploy, same DB. Configure different worker counts per role (`WEB_MAX=4 NOTIFICATIONS_MAX=32`).

| | Assessment |
|---|---|
| Positives | Zero structural change. Same deploy pipeline, same schema migrations, zero inter-service communication cost. Fastest to implement (~1 week). |
| Negatives | Cannot scale notifications independently without scaling web processes too. Shared GIL/memory pressure still couples the two workloads. Memory leaks in one affect the other. Deploy friction remains unchanged — the root cause isn't process isolation, it's a shared release train. |

### Alternative 4 — Sidecar / Worker Queue Offload

Keep everything in the monolith but offload all notification jobs to background workers (Sidekiq), deploy them on a separate schedule from web workers, and use a separate Redis cluster for queuing. Add K8s resources limits on the Sidekiq pods.

| | Assessment |
|---|---|
| Positives | Simple configuration change. No new service boundary. |
| Negatives | Doesn't solve deploy pain (still one binary, one release train). Doesn't solve independent scaling (Sidekiq workers still live in the same namespace and share node resources). Real-time WebSocket handling still lives inside the Rails process. Marginal improvement over current state. |

## Consequences

### Positive

- **Independent scaling of the hot module:** Notifications can scale to 50+ WebSocket handlers during spikes without paying for web capacity.
- **Reduced blast radius:** A notification deployment failure (e.g., APNS auth token rotation) does not take down the core application.
- **Faster notification deploys:** The notification team deploys on their cadence (~daily) instead of waiting for the weekly monolith release window.
- **Preserves monolith advantages elsewhere:** No distributed tracing, no CAP theorem tradeoffs, no polyglot persistence decisions for the remaining 90% of the codebase.
- **Low migration cost:** Extraction estimated at 6–8 weeks. Read replica setup, event publishing, and the `notifications-core` gem are incremental changes.

### Negative

- **Operational surface area doubles:** Monitoring, logging, and incident runbooks now cover two deployable units instead of one.
- **Eventual consistency exposure:** If the monolith publishes a `user.updated` event and the notification service fails to consume it before restarting, there's a gap. Retry dead-letter queues add complexity.
- **Cross-team coordination still required:** Schema changes to `users` table require notification team awareness (they depend on the read replica schema).
- **Deferred monolith decompression:** If the extract succeeds, leadership may expect quicker extracts of other modules next quarter, creating dependency churn. This must be explicitly scoped out.
- **Gem registry maintenance:** Versioning `notifications-core` introduces a new internal dependency that needs bumping, changelogs, and backward-compatibility checks.

---

## Reversal Triggers

This decision is valid until any of the following conditions are met. Detection of any trigger initiates a re-evaluation window (2-week investigation sprint):

1. **Two or more additional modules** develop independent scaling requirements (not just job queues — actual horizontal scaling needs for request-handling capacity). Currently only `notifications` qualifies.
2. **Two or more teams** require truly decoupled release trains (needing to deploy without coordinating with other teams' timelines). Currently only the Notification team has this requirement.
3. **Monolith deploy frequency degrades below once per month** due to growing module count, breaking the assumption that "the monolith is small enough to manage."
4. **The combined cost of running the monolith + notification service exceeds the cost of a full microservices migration** (measured as >30% premium for 2+ quarters).
5. **Inter-service event lag becomes a product blocker** — e.g., customers notice delayed notifications (>30 seconds) at ≥5% request volume, indicating Kafka is introducing unacceptable latency for the domain.
6. **Team growth exceeds 20 engineers**, making cross-module collaboration in the monothorn untenable (Conway's Law threshold).

Any reversal triggers this ADR to transition to **Review** status and initiate an alternative analysis per ADR-001 process.
