# ADR-0001: Modular monolith over microservices rewrite for notification scaling

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering leadership, Platform team, CTO
## Context

The application is a modular monolith built on Rails + PostgreSQL serving five domain modules (billing, users, catalog, orders, notifications). We currently deploy twice per week via a single Rails app, and deployment friction is visible: a one-line change in any module triggers a full rebuild and redeploy of all five modules, resulting in ~15-minute deployment windows that block the team's delivery cadence.

The real-time notifications module is the hot module: it accounts for 60% of active WebSocket connections and processes 3× more requests per second than any other module, yet cannot scale independently. Traffic spikes from notification bursts cause tail-latency regression across billing and checkout during peak hours because they share process pools and database connection pools.

Leadership has proposed a full microservices rewrite, estimating 4–6 engineers for 6 months. The forcing factors are clear: independent horizontal scaling for notifications and shorter deployment times for the remaining four modules. However, we have no observability gaps, no data-silos issues, and our inter-module boundaries map cleanly to separate concerns—no distributed transaction complexity requiring eventual-consistency patterns outside of notifications.
## Decision

We adopt three focused changes instead of a microservices rewrite:

1. **Extract only the notifications module as an independent service.** This module alone exhibits the scaling pressure justifying the operational overhead of a separate service (independent deploy artifact, own connection pool, explicit API boundary). We extract it using the Strangler Fig pattern over 3 sprints, with a feature-flagged dual-write during transition.

2. **Maintain the remaining four modules (billing, users, catalog, orders) as a modular monolith.** These modules share a single codebase, deploy as one unit, and communicate via in-process calls within Rails' routing layer. Module boundaries are enforced by package-level directories and interface modules—not by network edges.

3. **Adopt parallel CI pipelines in the existing GitHub Actions workflow.** The monolith pipeline runs tests in parallel shards (~4 minutes), and deploys use a blue-green strategy with connection draining (~90 seconds total downtime). Deployment time drops from 15 minutes to under 3 minutes for the monolith portion.

### Implementation specifics

```
Monolith (billing, users, catalog, orders):
  └── Rails app → single container → scaled vertically (16GB RAM instances × 2 replicas)
  
Notifications (extracted):
  ├── Service container → horizontally scalable (N replicas based on queue depth)
  ├── Redis Stream → decoupled pub/sub bridge from monolith
  └── Own PostgreSQL schema → isolated connection pool
  
Communication:
  ├── Monolith → Redis Stream (fire-and-forget)
  └── Notifications → WebSockets → browsers/clients
```

### Reversal Triggers

This decision will be reconsidered and potentially superseded if any of the following conditions occur:

| Trigger | Threshold | Review Cadence |
|---------|-----------|----------------|
| Notifications traffic exceeds current capacity despite 8× horizontal scaling | Sustained p99 > 200ms after 3 consecutive scaling events | Immediate |
| Billing module requires its own scaling dimension (e.g., payment batch processing spikes) | Independent throughput needs detected for 2+ non-notification modules | Quarterly |
| Deployment pain returns post-CI improvement (parallel tests + blue-green) below current threshold | Deploy window > 5 minutes sustained for 2+ weeks | Monthly |
| Team size grows beyond 10 engineers working concurrently on the monolith | Multiple PR merge conflicts per sprint across different modules | Quarterly |
| Inter-module communication cost exceeds in-process call latency by > 3× at normal load | Network round-trip > 30ms average for cross-module calls | Continuous monitoring |

If reversal is triggered, we escalate to a full microservices evaluation with a formal decision review covering all five domains.
### Risks

- **Operational complexity from two services instead of one** — Monitoring, logging, and deployment now span two artifacts. Mitigation: both services ship identical Docker images with standardized health checks, structured JSON logging, and a single Grafana dashboard; weekly ops reviews catch regressions early.
- **Data consistency during the extraction window** — Dual writes between the monolith DB and the notification service's event stream risk duplicate or missed notifications. Mitigation: idempotent consumers backed by deduplication keys (event_id UUIDs) stored in Redis; automated reconciliation jobs run hourly during the 3-week transition period.
- **Partial rewrite perception among stakeholders** — Other teams may interpret this as endorsing microservices and file similar extraction requests, fragmenting the platform. Mitigation: document ADR-0001 broadly with the criteria above; require a new ADR approval gate for each subsequent extraction request.
- **Increased infrastructure cost** — Running two service containers with separate DB schemas costs ~2.5× more than the single monolith container. Mitigation: the monolith scales vertically (cheaper per-request-cost at moderate load); the notification service scales horizontally only under demand (auto-scaling policies cap costs within 15% of budget); estimated delta is $400/month vs. a full rewrite costing $30K–$50K in engineering time.
