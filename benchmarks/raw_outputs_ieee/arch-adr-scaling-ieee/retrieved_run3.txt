# ADR-001: Retain Modular Monolith and Extract Only Realtime Notifications as Separate Service

**Status**: Proposed  
**Created**: 2026-08-26  
**Owners**: Engineering Lead, CTO  

---

## Decision

Retain the Rails + Postgres modular monolith for all business domains. Extract **only** the realtime notifications module into its own independently deployable service with its own process and database connection pool. Reject the full microservices rewrite proposed by leadership.

---

## Context

Our 12-engineer team on a modular monolith (Rails + Postgres) is experiencing:

1. **Deploy bottleneck**: 2 deployments per week across the entire monolith, where both developers often have their PRs blocked waiting for CI to pass and manual staging validation. This creates merge conflicts and delays feature delivery by days.

2. **Resource contention**: The realtime notifications module is our single hottest domain — it runs background workers, manages WebSocket connections, and handles push notification fan-out. It currently consumes ~40% of application memory and CPU during peak load, starving other domains in the same process despite being only ~15% of the codebase.

3. **Scaling mismatch**: We need to scale notifications horizontally (more processes/connections) while keeping the rest of the app vertically. Scaling the entire monolith 2x to handle notifications is wasteful and expensive.

4. **Team pressure**: With 12 engineers sharing one codebase, we're hitting coupling friction — every change touches shared models, serializers, or infrastructure concerns. Leadership has become nervous about long-term maintainability and has proposed a "full microservices rewrite" as the escape hatch.

**Constraints**:
- Our team size (12) sits in the middle range — large enough to feel monolith pain, small enough that a full split would over-distributed ownership.
- We have no existing Kubernetes cluster; most teams don't before committing to the full rewrite.
- Revenue and runway are limited — extra infrastructure from splitting everything is unacceptable right now.
- The current system works correctly. No critical bugs motivate speed of execution.

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite (leadership proposal)

Extract all 7–9 logical modules into independently deployed services with separate databases, inter-service RPC communication, event-driven messaging, and full distributed systems tooling.

**Pros:**
- Each service scales independently — solves the notification hot-spot problem cleanly
- Teams can deploy without coordination — eliminates the 2-deploy/week bottleneck entirely
- Technology heterogeneity becomes possible (Node.js for real-time, Go for data pipelines, etc.)
- Long-term scalability ceiling is highest

**Cons:**
- Massive effort estimate: 6–9 months for a team of 12, during which feature development stalls
- Distributed systems complexity: eventual consistency, network failures, tracing, distributed transactions
- Infrastructure overhead: requires K8s/container orchestration, service mesh, observability stack — none of which we have
- Team fragmentation risk: at 12 people, splitting into individual service owners means most services get 1 person — fragile ownership
- Existing monolith code doesn't translate 1:1 to boundaries that make sense microservice-style — re-implementation will expose different design flaws

### Alternative 2: Extract Only Notifications Module (DECISION)

Keep the monolith as-is. Identify the notifications module boundary and extract it into its own Rails process with its own database connection pool, deployed independently via sidecar pattern or separate Heroku/PaaS app, communicating via background jobs (Sidekiq) over existing Redis.

**Pros:**
- Solves the two concrete problems we have: deploy freedom for notifications + independent resource allocation
- Lowest effort: estimated 3–4 weeks for one senior engineer
- Minimal infra change: we keep running what we know (single PaaS, same deployment pipeline)
- Preserves developer velocity on all other modules
- Can use our existing Sidekiq/Redis backbone — no new message queue needed
- Sets a precedent: "extract hot modules incrementally" rather than "rip everything out"
- Reversible: if more modules get hot, we repeat the pattern for the next one

**Cons:**
- Not a permanent solution — other modules may heat up and need extraction too
- Cross-module boundaries still share code/models — coupling friction remains for non-notification changes
- Slightly increases operational surface area (one extra service to monitor)
- Data duplication risk: notifications table replicated, requiring either cross-db joins or sync logic

### Alternative 3: Stay Pure Monolith — Fix Deployment Pipeline & Add Workers Only

Keep everything in the monolith. Address the deploy bottleneck by improving CI/CD (parallel CI runs, canary deploys, automated integration tests). Address the resource contention by configuring Rails worker pools differently or using threaded concurrency (Puma threaded servers, Ruby 3+ fibers) instead of spawning additional processes.

**Pros:**
- Zero architectural change — simplest path
- Eliminates all cross-boundary concerns forever
- Fastest to implement (days, not weeks)
- Strongest coupling of data and behavior

**Cons:**
- Does nothing to solve the resource contention problem — thread-based concurrency helps somewhat but doesn't isolate garbage collection pauses or allow horizontal scaling of the hot module
- Pipeline improvements alone won't address the fundamental coupling that causes merge conflicts among 12 developers
- Pushes the scaling problem indefinitely — eventually we'll hit infrastructure limits the monolith can't overcome

### Alternative 4: Strangler Fig Partial Migration

Begin migrating specific features incrementally to separate services using the Strangler Fig pattern — migrate one feature at a time over 6–12 months while the monolith gradually shrinks. This isn't a full rewrite but achieves a similar outcome piece-by-piece.

**Pros:**
- Lower risk than big-bang rewrite
- Features deliver value as they're migrated
- Allows learning and course correction

**Cons:**
- Still requires building distributed systems tooling from scratch
- At least as complex because you run both monolith and services in parallel during migration
- Doesn't solve the immediate deploy/scaling pain quickly enough
- Overkill when only one module has these problems today

---

## Consequences

### Positive

- **Deployment velocity**: Notifications can now deploy independently whenever ready. Other modules stay on the current 2-deploy/week cadence but can improve that separately through CI investment.
- **Resource isolation**: The notifications process gets dedicated CPU/memory. Peak notification loads no longer starve API requests.
- **Incremental path forward**: If another module (e.g., search, analytics) later needs independent scaling, we've proven the extraction pattern works and can repeat it.
- **Low cost, fast win**: 3–4 weeks of work vs 6–9 month rewrite estimate. Immediate ROI on infrastructure savings.
- **Decision preservation**: Keeps the team happy without over-engineering. Avoids the "distributed systems trap" where you solve organizational pain with infrastructure complexity.
- **Team alignment**: Addresses leadership's actual concerns (deploy pain + scaling) without accepting their preferred but incorrect solution.

### Negative

- **Technical debt accumulation**: If 3+ modules eventually need extraction, we end up managing 4+ services anyway with incremental gaps in tooling and patterns.
- **Partial coupling problem**: Cross-module API calls and shared database tables mean the monolith doesn't fully "let go" — some releases still require coordination.
- **Operational gap**: Running one service slightly outside the monolith means our monitoring, logging, and alerting coverage must expand minimally.
- **Moral hazard**: May give leadership false confidence that "this pattern scales" — if they demand extraction of low-value modules soon after, we lose focus.
- **Data sync burden**: Some notification state (user preferences, unread counts) needs to flow between monolith DB and notification service DB. We need a reliable replication strategy.

---

## Reversal Triggers

This decision becomes invalid and triggers a review of the full microservices alternative if **any** of the following occur:

1. **Three or more additional modules** need independent scaling beyond what connection pooling and process tuning can handle within 6 months of this decision.

2. **Cross-module coupling exceeds thresholds**: More than 40% of all PRs touch multiple logical modules' code simultaneously (measured over a 4-week window). This indicates the monolith's boundaries are fundamentally broken, not just resource-constrained.

3. **Team grows beyond 18 engineers** and the extract-only-one-module approach no longer provides adequate autonomy. At larger sizes, more granular ownership becomes necessary.

4. **Infrastructure requirements evolve**: If we adopt K8s or similar orchestration for unrelated reasons (multi-region deployment needs, compliance mandates), the marginal cost of additional services drops significantly, potentially making a broader migration worthwhile.

5. **Notifications itself requires technology incompatibility**: If the notifications domain outgrows Ruby/Rails capabilities (e.g., needing WebRTC signaling servers, custom protocol handling, or sub-millisecond latency guarantees), we'd revisit whether the monolith framework was ever the right choice for this module.

When any trigger fires, we convene a lightweight architecture review (engineering leads + product) within two weeks to assess whether to continue the extraction pattern broadly, begin a targeted migration, or reconsider the full rewrite with updated cost/benefit analysis informed by experience from the first extraction.

## Appendix: Extraction Sketch

*What the extracted notification service looks like:*

```
notifications_service/
├── app/                      # Standalone Rails app
│   ├── models/notification.rb
│   ├── workers/fanout_worker.rb
│   └── channels/websocket_channel.rb
├── config/database.yml       # Separate notification_db instance
├── Dockerfile                # Independent container
└── spec/                     # Tests

communication_with_monolith:
  - Writes → Sidekiq job → Redis → monolith consumer
  - Reads → GraphQL/gRPC call OR direct DB query (read replica)
  - State sync → Postgreslogical replication / CDC stream
```

**Estimate**: 2 weeks scaffolding + testing, 1 week data migration/sync, 1 week production rollout and monitoring.
