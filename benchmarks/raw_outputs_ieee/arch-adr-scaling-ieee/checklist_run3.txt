# Architecture Decision Record

---

## ADR-0024: Modular Monolith Retention Over Microservices Rewrite

| Field | Value |
|-------|-------|
| **Status** | accepted |
| **Date** | 2026-08-26 |
| **Deciders** | Engineering Leadership, CTO |
| **Supersedes** | — |

---

### Context

We are a 12-engineer team operating a modular monolith built on Rails + PostgreSQL. We deploy ~2×/week, which leadership considers unacceptably slow. The bottleneck is one domain—realtime notifications—that experiences traffic spikes requiring independent horizontal scaling but cannot scale within the monolith without pulling all shared state and gems along with it. This creates two competing pressures:

1. **Deploy friction**: Every notification change requires a full monolith deploy, increasing blast radius and deployment time.
2. **Scaling ceiling**: The notification module cannot be independently scaled because it shares the same process, database connections, and memory footprint.

Leadership has proposed a full microservices rewrite of the entire application. The question this ADR addresses is whether we should execute that rewrite or pursue a different strategy.

### Problem Framing

This is not a capacity problem—the monolith handles current load fine. It is a **scaling boundary problem** applied to a single hot module, compounded by **deployment coupling**. The correct solution must address both constraints without introducing unnecessary complexity across domains that do not need it.

---

### Decision

**We retain the modular monolith and extract only the realtime notification module as a standalone service.**

The notification module becomes its own Rails app (or lightweight Ruby service using Hanami/Granite) with its own Postgres schema (separate database), its own deploy pipeline, and its own scaling group (via Kubernetes pods or container orchestration). The rest of the monolith remains intact. Cross-domain communication from the monolith to the notification service happens via domain events published to a message bus (e.g., Sidekiq-backed Redis streams, Kafka, or NATS), and read access flows through a materialized view or dedicated query table kept in sync.

All other modules continue deploying together under the existing CI/CD pipeline.

---

### Why Not a Full Microservices Rewrite?

A full rewrite would introduce distributed-systems complexity (consistency, latency, observability, operational tooling) across every domain—not just notification—without solving any constraint those domains actually face. The deployment pain exists only because the notification module blocks it. Extracting the notification module alone solves both problems: it gets that module its own deploy pipeline *and* its own scaling group, while leaving the remaining modules undisturbed.

---

### Alternatives Considered

#### 1. Full Microservices Rewrite

Split the entire monolith into independently deployable, independently scaled services aligned with bounded contexts (users, orders, catalog, notifications, etc.). Each service owns its database and communicates over RPC/message bus.

**Rejected because:** It multiplies operational overhead (circuit breakers, distributed tracing, eventual consistency handling) across 5–7× more deployment units than currently needed. 12 engineers would spend ~30–40% of capacity on infra and plumbing rather than features. The business case does not justify the cost: only one module faces scaling pressure; the others are perfectly healthy. A full rewrite also carries massive migration risk (data loss, downtime, regression) with no incremental ROI before completion.

#### 2. Extract Only the Notification Module (chosen path)

Isolate the real-time notification subsystem into its own deployable service. Keep all non-notification modules inside the existing monolith. Introduce async cross-service boundaries only where needed (events flowing from monolith → notification service).

**Chosen because:** It directly addresses both forcing factors—deploy friction and scaling ceiling—with minimal additional complexity. The extraction surface is well-defined (notifications have a clear bounded context: they consume events, store them, and deliver them via WebSocket/SSE/push). The shared-db pattern initially keeps data access simple (same Postgres instance, different schemas), and we evolve toward separate databases only if needed. 12 engineers can maintain a 10-module monolith comfortably; adding one extra deploy target is tractable.

#### 3. Vertical Scaling + Connection Pool Optimization Within the Monolith

Scale the single Rails instance vertically (more RAM, CPU, better connection pooling via PgBouncer, tuned `database.yml`) and accept continued deployment coupling.

**Rejected because:** This ignores the fundamental issue—the problem isn't raw capacity, it's *bounded-context coupling*. Vertical scaling buys time at diminishing returns (you hit instance-size limits and cost curves quickly). It also does nothing to solve deploy friction: the notification module still forces every deploy to include it. After 6–9 months we'd be back having the same conversation, but now with a larger bill.

#### 4. Multi-Database Sharding Within the Monolith (single binary, multiple databases)

Keep one application binary but shard tables across multiple PostgreSQL instances managed internally (Shoryku/Rails' native sharding support). Route notification tables to a dedicated database, improving isolation.

**Rejected because:** Rails-native multi-database support is mature but adds internal complexity (cross-database joins are prohibited, migrations are harder, monitoring is fragmented). It improves data isolation without solving deployment coupling—we still deploy one artifact containing everything. It's a partial solution that defers rather than resolves the core problem. Worth considering later if we add more independently-scaling modules beyond notifications.

---

### Consequences

#### Positive
- **Independent notification deploys**: The notification service gets its own CI/CD pipeline, tested and deployed on its own schedule.
- **Independent notification scaling**: The notification layer can scale horizontally (more pods) during traffic spikes without affecting the rest of the application.
- **Low disruption cost**: Existing modules, tests, developer workflows, and infrastructure remain untouched. ~2 weeks of engineering effort.
- **Clear bounded-context boundary**: Notifications have well-defined inputs (domain events) and outputs (deliveries), making the extraction surface clean.
- **Learning runway**: The team gains operational experience with inter-service communication before deciding whether more extractions make sense.
- **Preserved cohesion**: Domains with strong transactional relationships (e.g., orders ↔ inventory) stay together and avoid distributed transactions.

#### Negative
- **Two deployment models to manage**: One CI/CD pipeline for the monolith, another for the notification service. Slight increase in DevOps burden.
- **Eventual consistency gap**: Events flowing from monolith to notification service introduces a window where notifications may lag. Must be communicated in context (e.g., "sending" rather than "sent").
- **Schema evolution coordination**: Changes to event payloads require versioning discipline. Backward-compatible schema changes are mandatory to avoid breaking the notification consumer.
- **Operational surface grows**: One extra service means one extra set of logs, metrics, alerts, and failure modes to monitor.
- **Deferred decision**: If additional hot modules emerge (e.g., search/analytics), we'll need ADR-NNN covering whether to extract those too. The hybrid model is stable but requires vigilance about when it transitions to fragmentation.

---

### Reversal Triggers

This decision stands until any of the following conditions materialize:

1. **Two or more additional modules** develop sustained, independent scaling demand (not transient spikes) that the monolith architecture cannot satisfy within acceptable resource cost. Extraction would then cascade, and the strategic question of a full split reopens.

2. **Team growth exceeds 20 engineers** working concurrently on the same monolith, causing merge-conflict velocity, dependency-resolution friction, or coordination overhead to measurably degrade deployment cadence below once per week despite best practices.

3. **PostgreSQL connection pool saturation** becomes a recurring production incident root cause even after maxing out reasonable connection pooling (PgBouncer + connection recycling), indicating the monolith's single-process-per-request model cannot serve concurrent load profiles.

4. **Regulatory or data-residency requirements** mandate strict separation of data stores for specific modules (beyond what schema-level isolation provides), forcing physical data segmentation that the monolith cannot efficiently accommodate.

Any trigger met would call for a new ADR evaluating whether a phased full-split or an expanded hybrid extraction model is warranted.

---

### Implementation Notes

- Use existing event infrastructure (Sidekiq + Redis Streams or a lightweight broker like NATS) rather than adding Kafka unless throughput demands it.
- Start with same-PG-instance, different-schema layout for the notification DB. Move to a separate database cluster only if connection counts or backup windows become problematic.
- Establish an API contract (protobuf, JSON Schema, or OpenAPI spec) for all events emitted from the monolith to the notification service before extracting.
