# ADR-0001: Retain Modular Monolith; Extract Only the Realtime Notifications Module

**Status:** Proposed
**Date:** 2026-08-26
**Deciders:** Engineering Leadership, Architecture Team
**Technical Story:** Deployment frequency and scaling pressure on the real-time notifications module are creating organizational tension. Leadership proposes a full microservices rewrite of the modular monolith. This ADR evaluates that proposal against concrete forcing factors and documents the team's decision.

---

## Context

Our application is a Rails + PostgreSQL modular monolith. It currently runs two production deploys per week across all modules sharing one codebase and deployment pipeline. Pain points are concentrated:

| Forcing Factor | Current State |
|---|---|
| Deployment frequency | ~2 deploys/week system-wide; change lead time ~4 hours from PR to prod |
| Notification traffic | Realtime push notifications consume ~35% of request queue depth during peak; WebSockets pool saturates at 12k concurrent connections |
| Hot module isolation | All modules share connection pools, Redis pub/sub, and the Unicorn/Puma worker pool — a notification burst can starve core API routes |
| Team structure | 3 teams own distinct bounded contexts (orders, catalog, notifications); only the notifications team experiences cross-module contention |
| Organizational preference | Leadership has observed competitors operating fully decoupled services and has directed investigation into a microservices rewrite |

### Non-goals
- Achieving zero-downtime deployments (not a current blocker)
- Horizontal scale beyond the next 3x traffic projection (infrastructure budget capped)

---

## Decision

We **retain the modular monolith** and **extract only the realtime notifications module** as an independently deployed service. The remaining domains (orders, catalog, user management) continue running within the shared Rails app under the existing 2-deploys-per-week cadence.

This produces a **strangler-pattern hybrid**: one extracted service plus the original monolith, with no planned migration path toward further decomposition unless explicit triggers fire (see Reversal Triggers).

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
Extract every bounded context into its own service with separate codebases, databases, and deployment pipelines.

- **Rejected.** Blast radius is disproportionate: 6–9 months of engineering effort, ~$500K incremental infrastructure cost (service mesh, distributed tracing, multi-database ops tooling), and a significant operational learning curve (distributed transactions, eventual consistency, network fault handling). The deploy-frequency problem affects only one module; rewriting four healthy modules adds risk without proportional benefit.

### Alternative 2: Extract Only Notifications (Selected)
Identify the single hot module, break its boundaries cleanly via a published domain event contract, give it an independent database and deployment, and communicate through async events + synchronous REST calls where needed. Keep everything else in the monolith.

- **Accepted.** Addresses the concrete scaling bottleneck and cross-module starvation problem. Preserves the fast iteration loop for nine out of ten modules. Total extraction effort estimated at 6–8 weeks across one engineer and one DevOps partner. Operational complexity increases modestly — we go from one deployment artifact to two — which is manageable.

### Alternative 3: In-Monolith Process Isolation (Do Nothing Beyond Configuration Changes)
Keep everything in one codebase but solve the contention with targeted configuration changes: dedicate a separate Puma worker pool to the notifications engine, partition the Redis pub/sub channels, and run the actioncable WebSocket server on a dedicated port with process-level resource capping.

- **Rejected.** This addresses the symptom (worker starvation) without removing the coupling that causes slow deploys. Connection-pool contention between the WS server and API workers persists even with process isolation. Furthermore, the monitoring/observability gap remains: we cannot measure per-module latency percentiles when everything shares one router and one log stream. Worth trying as a short-term bandage (we're doing it now while the extract proceeds), not as a final solution.

### Alternative 4: Vertical Slice Extraction of High-Traffic Endpoints
Use a sidecar reverse-proxy approach (e.g., Kong or Envoy) to route the top 20% most-requested endpoints (including notification send/receive) to a lightweight Go-sidecar service while leaving the Rails monolith untouched.

- **Rejected.** Introduces proxy complexity, TLS termination overhead, and a second language runtime inside our deployment footprint. We gain partial scaling isolation without gaining any deployment independence. The cost/benefit profile sits between Alternatives 2 and 3 but achieves neither goal fully.

---

## Consequences

### Positive
- **Notification module scales independently** — can add WebSocket worker instances without affecting orders/catalog availability.
- **Deployment blast radius stays small** — a buggy notification release doesn't risk breaking checkout flows.
- **Team autonomy improves** — the notifications team ships on its own timeline.
- **Operational complexity increase is bounded** — two deployment artifacts vs one, shared Postgres becomes two Postgres instances. No service mesh required.
- **Low sunk cost** — if the decision proves wrong, rolling back means merging the extracted service back into the monolith (a well-understood reverse-strangler operation).

### Negative
- **Cross-boundary communication overhead** — some direct model associations must become HTTP calls or async events, adding latency and failure modes.
- **Database duplication** — the notifications module will own its own schema; some queries will require joins across service boundaries (solved with materialized views or read replicas).
- **Dual deployment coordination** — release notes and CI pipelines need awareness of both artifacts. Requires a minimal orchestration convention.
- **Developer mental overhead** — engineers may work across both the monolith and the extracted service, requiring familiarity with two deployment models.
- **Partial architectural purity** — this hybrid state could persist longer than intended if reversal triggers don't fire. We commit to re-evaluating every 6 months.

---

## Reversal Triggers

This decision becomes invalid and triggers a mandatory re-evaluation (and potential pivot toward fuller decomposition) if any of the following occur:

1. **Deploy pain migrates** — If any module outside notifications begins causing cross-module deployment failures (measured by rollback rate > 10% across non-notification PRs over 2 consecutive quarters).
2. **Scaling demand spreads** — If two additional modules consistently require independent horizontal scaling beyond the capacity of process-level isolation (measured by sustained p99 latency degradation in core APIs during their traffic spikes over 2 consecutive quarters).
3. **Organizational restructuring** — If teams split into 4+ independent squads each requiring truly autonomous CI/CD pipelines incompatible with a shared codebase.
4. **Maintenance cost exceeds threshold** — If the combined maintenance burden of running the monolith + extracted notification service (person-hours/month) exceeds the estimated cost of a full rewrite (> 24 person-months/year across the engineering org).

Re-evaluation occurs automatically every 6 months regardless of triggers, using the quality scorecard (`docs/QUALITY_SCORECARD.md`) and operations dashboard (`docs/HEALTH_DASHBOARD.md`) as input data sources.

## 2 Problem Statement

**Should we pursue a full microservices rewrite of the modular monolith, or address the two concrete forcing factors with a less disruptive approach?**

Sub-questions:
- Can we increase deploy frequency from 2×/week to ≥ daily without architectural change?
- Can we independently scale notifications without splitting the codebase?
- Does the cost of staying monolithic outweigh the cost of migrating?

---

## 3 Options Considered

### Option A: Extract Only `realtime_notifications` as a Separate Service

Extract the notification module into its own Ruby process with its own Redis connection and a dedicated DB schema (schema-per-module via pg namespace). Communicate via async events (Redis streams → Sidekiq consumers). Keep all other modules in the Rails app.

### Option B: Full Microservices Rewrite

Rewrite the application as independent services (likely Go or Rust for performance-critical paths, Rails for business logic). Each service owns its database, communicates over gRPC/HTTP, and has independent CI/CD, deployment, and scaling.

### Option C: Stay Fully Monolithic — Optimize Within the Rails App

Keep everything in one repository and one process. Address both forcing factors through operational changes: improve CI pipeline speed, implement trunk-based development to justify daily deploys, use PostgreSQL advisory locks and partitioned tables for the hot module, and vertically scale the instance.

---

## 4 Decision

**Choose Option A: Extract Only `realtime_notifications`.**

### Rationale

This decision balances the forcing factors against migration cost:

1. **Deploy frequency does not require microservices.** With trunk-based development, automated staging environments, and GitHub Actions matrix builds, we can move from 2×/week to daily deploys within the monolith. This addresses half the perceived problem without any code movement.

2. **Notifications is a clear bounded context.** It has distinct data requirements (message queue, delivery receipts, fan-out patterns), different resource profiles (CPU for WebSocket management, not database queries), and no inbound dependencies from other modules. Single responsibility makes it ideal for isolation; it's also the *only* module with these characteristics today.

3. **A full rewrite is misaligned with team size.** Twelve engineers can maintain one well-structured monolith effectively. The distributed systems complexity (service mesh, observability across boundaries, eventual consistency, network topology) multiplies cognitive load by approximately 3–5×. That overhead would exceed the benefit until we have either significantly more traffic, more teams working in parallel domains, or additional hot modules needing independent scale.

4. **Option C leaves the scaling gap unanswered.** Vertical scaling helps until we hit the hardware ceiling (or AWS RDS max instance class). Horizontal scaling the entire monolith is wasteful — we're allocating resources to inactive modules just to serve notifications throughput.

### Implementation Boundaries

- Extract `realtime_notifications` to a separate service using Event Sourcing + CQRS pattern
- Shared library (`notifications_protocol`) handles message contract between monolith and extracted service
- Use Fly.io for deployment (same platform, zero added DevOps friction)
- All other modules remain in the Rails app
- Timeline: 6 weeks for extraction, including dual-run validation period

---

## 5 Consequences

### Positive

- Independent horizontal scaling of notifications removes the primary bottleneck
- Deploy frequency increases within 2 weeks (trunk-based dev in parallel with extraction)
- Reduced blast radius: a notification failure cannot crash the entire app
- Team learns gradual extraction skills before they might be needed again
- Zero downtime migration path: dual-write during transition validates correctness
- Preserves the modular monolith benefits: simple local development, single debugger session, ACID transactions within the app

### Negative

- One additional service means one additional deploy target and one additional set of ops concerns
- Inter-process communication replaces intra-process method calls — network errors become possible
- Cross-boundary debugging requires distributed tracing (OpenTelemetry setup)
- Eventual consistency window during the dual-write period means rare stale reads (acceptable for notifications)
- Added infra cost: running two processes instead of one (estimated $80–120/mo extra on Fly.io)

### What Is Explicitly Not Changed

- No change to the repository structure initially — extracted service lives alongside but is deployed separately
- No change to database strategy — PostgreSQL remains single instance with schema separation
- No change to team organization — same 12 engineers, same squad

# ADR-0001: Retain Modular Monolith with Targeted Vertical Scaling Instead of Microservices Rewrite

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering lead, CTO, Product manager

## Context

Our Rails application is a modular monolith backed by PostgreSQL. We deploy ~2× per week without incident. However, leadership has expressed concern about two issues: (1) deploy pain perceived as too slow, and (2) the real-time notifications module must scale independently because its load profile spikes unpredictably during events. Leadership proposes rewriting the entire codebase into microservices to solve both concerns simultaneously.

This request conflates two separate problems — deploy cadence and compute scaling — and proposes a massive architectural change that introduces distributed-system complexity across all modules, not just notifications. The decision required evaluating whether the cost of a full rewrite (6–9 months engineering time, regression risk, operational overhead) is justified versus targeted solutions that address each problem individually.

Current metrics: average deploy takes 4 minutes with zero-downtime strategy; notification module consumes ~65% of worker processes during peak events but <5% at baseline; other modules are stable under current capacity.

## Decision

We retain the modular monolith and apply targeted vertical scaling **only** to the notifications module, decoupling it behind a bounded context boundary with a dedicated Redis-backed job queue and optional horizontal pod count via container orchestration (e.g., K8s `replicas` field on that service alone). This provides independent scaling without a full rewrite.

We improve deploy confidence through automated test gates (contract tests between bounded contexts, performance regression suite) and pre-deploy smoke checks — reducing deploy anxiety without changing architecture.

Concretely:

```
┌──────────────────────────────────────────┐
│          Modular Monolith (Rails)         │
│                                          │
│  ┌────────────┐  ┌────────────────────┐  │
│  │   Users     │  │  Notifications     │  │ ← Bounded context
│  │   Orders    │  │  ├── Worker process│  │     isolated
│  │   Billing   │  │  ├── Redis queue   │  │     boundary
│  │   ...       │  │  └── Scale n→m pods│  │
│  └────────────┘  └────────────────────┘  │
│                                          │
│  Shared Postgres                          │
└──────────────────────────────────────────┘
```

Each bounded context owns its own database schema prefix. The notification context publishes domain events via a lightweight event log table shared with the monolith but subscribable externally if needed later.

### Risks
- **Notifications module drifts**: If the notification module grows unbounded and becomes a "microservice in everything but name," we revisit this decision. Mitigation: enforce interface boundaries via contract tests and cap team ownership.
- **Shared Postgres bottleneck**: Concurrent heavy loads from multiple contexts could stress the database. Mitigation: connection pooling tuning (PgBouncer), read replicas for reporting-heavy contexts, and periodic query audit.
- **Deploy anxiety persists**: If automated test gates don't reduce deploy fear, leadership may push for rewrite again. Mitigation: invest in test reliability first before escalating.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
Extract every module into an independent service with its own database, API gateway, and deployment pipeline.

**Rejected because**: Estimated 6–9 months of engineering effort for a team of 12, with high regression risk (every inter-module call becomes network-bound). Introduces distributed tracing, saga patterns, eventual consistency bugs, and infrastructure overhead that benefits none of the stable modules. Solves the notifications problem but at 10× the cost and introduces new failure modes across the entire system. The existing 2×/week deploy cadence is not actually problematic — perceived pain stems from lack of automation, not architecture.

### Alternative 2: Extract Only the Notifications Module (Standalone Service)
Rewrite only the notification module as a Go/Rust service with its own datastore, communicating with the monolith over gRPC/REST. Keep everything else in Rails.

**Rejected because**: It still requires maintaining two codebases, two CI pipelines, two monitoring stacks, and managing cross-service consistency. It creates an inconsistency tax — developers onboarding need to understand two architectures immediately. While cheaper than Alternative 1 (~3 months vs 9 months), it still introduces distributed systems complexity for a single module that can be scaled vertically. The communication overhead (API contracts, versioning, retry logic) outweighs the benefit when container-level isolation already solves the scaling problem.

### Alternative 3: Do Nothing / Accept Current State
Keep the monolith exactly as-is, accept that notifications get throttled during peak and deploys remain manual-sounding.

**Rejected because**: Unacceptable customer experience during peak notification events (late/blocked delivery leads to churn); deploy anxiety will cause engineers to batch changes, increasing blast radius per deploy. Ignoring the signal would let technical debt compound until a crisis forces a reactive, poorly-planned decision.

## Consequences

### Positive
- No rewrite: development continues on existing codebase with zero context switch.
- Independent scaling of notifications achieved at the container/orchestration layer, not the code layer.
- Single deploy pipeline maintained with proven reliability.
- Database remains simple — one Postgres instance with clean schema partitioning.
- Team velocity unaffected — all engineers work in one language, one framework, one mental model.
- Future-proof: if notifications truly outgrow vertical scaling, they can be extracted then with domain context fully captured and minimal disruption.

### Negative
- Notification module is still technically part of the monolith, which may confuse external stakeholders who hear "not a true microservice."
- Shared Postgres means a bug in one context can affect another via connection exhaustion or table lock contention.
- Vertical scaling has a hardware limit — if notification volume grows 100×, we hit a wall and will need to extract.
- Deploy process improvement requires upfront investment in testing infrastructure that might feel like a distraction from feature work.

## Reversal Triggers

This decision is reversible. We re-evaluate and escalate to a full extraction/rewrite if **any** of the following conditions are met:

| # | Trigger | Measurement | Escalation |
|---|---------|-------------|------------|
| 1 | Notification module exceeds vertical scaling ceiling | Worker pod hits CPU/memory limits at >90% utilization despite autoscaling, and further scaling causes degradation in other contexts due to shared Postgres connections | Initiate Alternative 2 within one quarter |
| 2 | Notifications team velocity drops below 25% of other modules | Lead engineer reports that co-locating notifications with unrelated modules creates unacceptable coupling or merge conflicts | Extract notifications module immediately |
| 3 | Deploy pain increases beyond 2× degraded deployments per month | Rollback rate >10% or mean time to recovery (MTTR) exceeds 30 minutes over any rolling 30-day window | Invest in full integration test suite before reconsidering Architecture |
| 4 | Business mandates multi-region deployment with per-module latency requirements | Latency SLAs require geo-distributed service instances that a single monolith cannot satisfy | Full microservices evaluation within one quarter |
| 5 | More than two additional modules independently need different runtime languages or memory profiles | Pattern emerges that bounded contexts have diverging non-functional requirements fundamentally incompatible with Rails + Postgres | Consider splitting into two monoliths before going full microservices |

These triggers are reviewed quarterly. Any trigger firing twice consecutively triggers an automatic Architecture Review Board session.
