# ADR-042: Retain Modular Monolith with Selective Extraction of Notifications Module

**Status**: Proposed
**Date**: 2026-08-26
**Deciders**: Engineering Lead, CTO, Product Director
**Context**: Rails modular monolith, 12 engineers, Postgres, deploy bottleneck on realtime notifications

---

## Context

Our Rails application is a well-organized modular monolith with isolated concerns per module (routing, isolation via service boundaries, separate test suites). We have **12 engineers** working across it, deploying **twice per week**. The team has reached consensus that the architectural organization is sound — modular folders, clear boundaries, shared Postgres instance, no cross-module direct DB calls.

**Problem**: The `realtime_notifications` module is a single point of operational failure during deploys. Every deploy restarts the entire app, including this module which handles WebSocket connections and requires rolling restarts with zero downtime to avoid disconnecting active users. Current strategy — full app restart — causes **3–8 second notification outages per deploy**, generating ~40 support tickets/month and one P1 incident in Q2 when 2,300 concurrent users were dropped simultaneously.

**Forcing factors**:
- Deploy frequency is already stable at 2/week; increasing it further is desired but risky today
- Notification traffic has grown 3x YoY (from 5k to 15k concurrent WS connections); it's the only module needing horizontal scaling
- Infrastructure cost for full microservices rewrite: estimated $18k/mo additional (Kubernetes, service mesh, observability tooling, SRE overhead)
- Team size: 12 FTE — large enough to run multiple services, small enough that coordination overhead matters

## Decision

**Retain the modular monolith as the primary architecture.** Extract **only** the `realtime_notifications` module into its own lightweight service (Go or Node.js) with its own deployment pipeline, independent scaling, and its own Redis-backed pub/sub layer. All other modules remain in the Rails modular monolith.

This is a *selective extraction*, not a full decomposition. The extracted service communicates with the monolith via:
- API gateway (internal, Nginx or Kong) for synchronous calls (push notification dispatch, user preferences lookup)
- Redis Streams for async events (event sourcing for notification delivery receipts)
- Shared Postgres read replica (not write — the monolith owns writes)

The extracted service must be thin: no business logic duplication, just the transport layer (WS handling, connection management, fan-out) and a message queue consumer.

## Alternatives Considered

### Alternative 1 — Full Microservices Rewrite
Extract every module into independently deployable, independently scalable services (user service, order service, catalog service, notification service, etc.), each with its own database, deployment pipeline, and infrastructure.

**Rejected because**: The 12-engineer team would spend 6–9 months rebuilding what we already have in a distributed form. Cross-service consistency (currently handled by Postgres transactions) becomes a permanent complexity tax. Operational overhead (CI/CD pipelines, monitoring, tracing, deployment orchestration) multiplies without proportional benefit — only *one* module has scaling problems, not all twelve. Cost exceeds budget. No forcing factor demands this level of decomposition.

### Alternative 2 — Extract Only Notifications (Chosen)
Extract only the `realtime_notifications` module into a separate service while keeping everything else in the Rails modular monolith.

### Alternative 3 — Horizontal Pod Scaling Within the Monolith
Add Kubernetes pod autoscaling with canary deployments using something like AWS App Runner or ECS Service Split Traffic — essentially running multiple instances of the monolith behind a load balancer with gradual rollout, so only non-notification endpoints are affected by rolling restarts. Use Sidekiq for background jobs and keep WebSocket connections sticky.

**Rejected because**: Sticky WebSocket sessions make graceful rolling restarts fundamentally unreliable — you either accept dropped connections (the current problem) or implement complex session state replication across pods (adding coupling and latency). Passenger/Puma graceful restart doesn't help — it still reloads the entire app binary. The cost-benefit ratio favors extracting the one problematic module rather than rearchitecting the deployment model for a system where only one component has this problem.

### Alternative 4 — Upgrade Existing CI/CD for Zero-Downtime Deploys
Invest in Blue-Green deployments or Strangler Fig patterns *without* code extraction — add dual environments, traffic switching, and feature flags within the existing monolith. Keep all code in one repo, one deploy.

**Rejected because**: Blue-green doubles infra costs permanently (two identical environments always running). It solves the outage problem but not the scaling problem — the notification module still shares memory and CPU with everything else during peak traffic. Feature flag complexity grows unboundedly without addressing the root constraint: one process, one address space.

## Consequences

### Positive
- **Deploy stability**: Notification module gets independent zero-downtime deploys; other modules continue on the existing schedule
- **Targeted scaling**: Notifications scale horizontally based on concurrent connections; the rest of the app scales independently
- **Minimal disruption**: 12 engineers continue working in the same codebase for 95% of features; learning curve is limited to one new service
- **Cost control**: Additional infra cost estimated at $3–5k/mo (single extra service + Redis), compared to $18k/mo for full microservices
- **Lower cognitive load**: Engineers don't need distributed systems expertise for 95% of daily work; service boundary is one clear interface, not dozens
- **Reversibility**: Extraction can be reversed if traffic doesn't grow as projected (see Reversal Triggers)
- **Proof of pattern**: Establishes a repeatable extraction pattern for future needs without committing to full decomposition

### Negative
- **Hybrid architecture**: Running two different stacks (Rails + Go/Node) adds minor devops complexity (two build pipelines, two runtime environments)
- **Cross-service communication**: Must handle eventual consistency for notification delivery receipts; lost messages become possible (mitigated by Redis Streams durability)
- **Deployment coordination**: Need to coordinate version compatibility between monolith and extraction service during migration window (~4 weeks)
- **Observability gaps**: Distributed tracing across service boundary requires adding tools (OpenTelemetry) not previously needed
- **Database coupling**: Read replica lag introduces stale data risk for notification lookups (mitigated by caching warm defaults and TTL < 5s)

## Reversal Triggers

This decision becomes invalid and triggers a re-evaluation if any of the following occur:

1. **Traffic growth**: Concurrent WebSocket connections exceed 100k (current: 15k), making even extracted deployment insufficiently granular
2. **Team growth**: Team expands beyond 25 FTE such that cross-team coordination on the monolith creates >30% context-switching overhead (measured quarterly)
3. **Feature velocity**: Two or more additional modules (beyond notifications) independently require different scaling profiles or deployment frequencies within 12 months
4. **Infra economics**: Cloud provider pricing changes make containerized service hosting cheaper than VM-based monolith hosting by >2x
5. **Time limit**: If after 18 months the extracted service hasn't demonstrably reduced deploy-related incidents by ≥80%, reconsider whether extraction was the right lever (might indicate the real problem is CI/CD pipeline quality, not architecture)
