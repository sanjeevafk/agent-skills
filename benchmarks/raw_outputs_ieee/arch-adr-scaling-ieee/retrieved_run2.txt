# ADR-001: Retain Modular Monolith; Extract Only Realtime Notifications as Independent Service

**Status**: Proposed  
**Date**: 2026-08-26  
**Deciders**: Engineering Leadership, Architecture Review Board  
**Technical Stories**: TBD

---

## Decision

We will **retain the current modular monolith (Rails + Postgres)** as the primary application architecture and **extract only the realtime notifications module into an independent service**. We explicitly reject leadership's proposal for a full microservices rewrite at this time. This is a reversible decision subject to defined reversal triggers.

---

## Context

Our modular monolith ships ~2 deploys/week with occasional rollout friction, but it functions correctly for the vast majority of the codebase. The following concrete forcing factors shape our options:

1. **Deploy pain is real but contained.** At 2 deploys/week, deployments are manageable but each one touches the entire Rails app. Rollback takes ~15 minutes across all modules simultaneously, even when a change affects only one.

2. **The notifications module has genuinely different scaling needs.** Realtime notification delivery requires persistent WebSocket connections, high concurrency per user, and bursty traffic patterns that are orthogonal to the request/response throughput demands of the rest of the application. Our current resource allocation underutilizes compute on non-notification routes while the notification workers contend for shared database connections.

3. **A full microservices rewrite carries unacceptable risk.** Estimating ~9–14 months of engineering effort, significant data migration complexity, increased operational overhead (service discovery, distributed tracing, inter-service networking), and a period where feature velocity drops by ~60% during the transition. The business cannot sustain that timeline.

4. **Team size and coordination overhead favor the monolith.** With the current team composition, introducing 8–12 independently deployed services would increase cross-team coordination costs more than the autonomy gained, given that most changes touch multiple domains.

### Risks
- The single binary deployment model may become harder to reason about as the codebase exceeds ~500k lines of Ruby.
- Keeping some things monolithic while others are extracted introduces architectural hybridity that can confuse new team members.
- The notification service's database split creates a potential consistency boundary we must manage carefully.

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite (rejected)

Decompose the entire Rails monolith into 8–12 independently deployed microservices, each owning its own database, infrastructure, and deployment pipeline.

| Pros | Cons |
|---|---|
| Maximum independence — each team owns a service end-to-end; truly fine-grained scaling per domain; clear bounded contexts enforced at runtime | 9–14 months to decompose; ~60% drop in feature velocity during transition; significant distributed-system complexity (network failures, eventual consistency, saga orchestration); operational burden of managing 8–12 deploy pipelines, service meshes, and distributed observability; no evidence that the remaining modules need separate scaling |

**Cost**: High — estimated 3 FTEs fully occupied for 6+ months minimum.

**Verdict: Rejected.** The cost-benefit ratio is poor. Only one module actually needs independent scaling, and the decomposed work required for clean bounded context extraction alone would take 4–6 months — nearly half the rewrite estimate — for gains that apply almost entirely to one module.

### Alternative 2: Extract Only Realtime Notifications (selected)

Keep the Rails monolith intact. Isolate the notifications module into a standalone service (e.g., Go or Node.js + Redis Streams or NATS for pub/sub) with its own database, while maintaining the monolith for all other domains. Communication between the monolith and the notification service happens via async events through a message broker and synchronous HTTP APIs for lookup.

| Pros | Cons |
|---|---|
| Solves the genuine scaling problem for the notifications module only (~3 weeks engineering effort); minimal organizational change; the monolith retains its deployment simplicity for the 95% of code that doesn't need separate scaling; serves as a controlled learning experiment in service extraction without the commitment of a full rewrite; low risk — the monolith remains unchanged if the experiment fails | Hybrid architecture adds mental overhead; must handle cross-boundary consistency (outbox pattern, idempotent consumers); the notifications service becomes a dependent external system requiring uptime SLAs and network error handling within the monolith |

**Cost**: Low-Medium — estimated 1–2 engineers over 3–4 weeks.

**Verdict: Selected.** It addresses the actual problem (notifications scaling) without incurring rewrite-level cost, risk, or organizational disruption.

### Alternative 3: Keep Everything Monolithic, Add Process-Level Isolation

Do not extract any service. Instead, improve the monolith by adding worker processes for notifications (Sidekiq clusters scaled independently), connection pool tuning, and optimizing the deployment pipeline (e.g., blue-green or canary deploys). Optionally move the notification data to a separate schema within the same Postgres database to reduce lock contention.

| Pros | Cons |
|---|---|
| Zero architectural change; fastest to implement (~1 week); no distributed-system complexity; simplest debugging and deployment story | Scaling is limited to coarse-grained (entire app vs. Sidekiq workers); WebSocket server still shares some resources (memory, CPU) with the Rails app under extreme load; does not solve the deploy-pain problem where changing notifications requires redeploying everything |

**Cost**: Low — estimated < 1 week.

**Verdict: Rejected.** While this partially addresses the immediate scaling symptom, it doesn't solve the structural issue: the notification transport layer (WebSockets) and the Rails HTTP process cannot scale independently at the process level with acceptable isolation. Deploy pain also remains unaddressed. This could be a stopgap if budget is constrained, but not a sustainable solution.

---

## Consequences

### Positive

1. **Notifications scale independently.** The new service can scale its WebSocket connection pool and message-processing workers without affecting API response times for other modules.
2. **Deployment frequency improves for the monolith.** Removing the notifications module from the deployable unit eliminates one source of coupling-related rollouts.
3. **Low-cost validation of service extraction.** We learn what distributed operations look like for our team before committing to any further decompositions. If the experience teaches us that other modules face similar scaling issues, we have empirical evidence to justify those extracts.
4. **Monolith productivity preserved.** The bulk of feature development continues in the established Rails workflow with zero learning curve for team members who don't work on the notification service.
5. **Reversible path.** If the notification service turns out to add more friction than value, we can merge it back into the monolith with a well-defined migration strategy (see Reversal Triggers).

### Negative

1. **Hybrid architecture complexity.** Team members need to understand both Rails conventions and the interface contracts of the notification service. Documentation and onboarding materials must cover two technology stacks (or at least two communication patterns).
2. **Cross-service consistency burden.** Eventual consistency for notification delivery means the monolith must use the Outbox pattern and the notification service must be idempotent. These are not hard problems, but they require deliberate discipline and introduce subtle failure modes (duplicate notifications, lost events) that did not exist in the monolith.
3. **Monitoring and observability fragmentation.** Distributed tracing across the monolith-service boundary requires additional tooling investment (OpenTelemetry instrumentation, correlated request IDs). Debugging a notification delivery failure now spans two codebases and potentially two teams.
4. **Potential for architectural drift.** Other modules may observe the notification extraction and argue for similar treatment prematurely, creating pressure to decompose before domain boundaries are clearly justified by scaling or deploy metrics. This requires explicit governance — see Reversal Triggers.
5. **Inter-service communication latency.** Synchronous lookups from the monolith to the notification service introduce network latency that did not previously exist. All such calls must be cached or batched where possible.

---

## Reversal Triggers

This decision is provisional and will be revisited if any of the following conditions materialize:

1. **Feature velocity does not recover within 2 quarters.** If extracting only notifications does not demonstrably improve release cadence (target: ≥ 4 deploys/week with ≤ 5-minute rollback) after 8 weeks, we re-evaluate whether the root cause is deeper than deployment scope.

2. **Two or more additional modules demonstrate independent scaling needs.** If, within 6 months, ≥ 2 other modules consistently hit resource ceilings that cannot be resolved by process-level isolation (Sidekiq, connection pooling, read replicas), the case for broader decomposition strengthens. Each such module must present hard metrics (CPU/memory utilization > 80% sustained, P99 latency degradation > 200ms during peak) before triggering review.

3. **The notification service introduces more operational burden than it relieves.** Measured by: on-call incidents attributed to the service's inter-process communication exceeding 1/quarter, or MTTR for cross-service incidents exceeding 30 minutes consistently. If the distributed-system complexity we accepted proves unsustainable for the team's current skill set and staffing levels, we reverse toward full monolith restoration.

4. **Codebase exceeds 750k lines of Ruby without meaningful modular boundaries.** If the monolith grows past this threshold and modules within it begin sharing databases, models, or transaction scopes in ways that recreate the coupling we're trying to avoid, we revisit full decomposition with the benefit of lessons learned from the notification extract.

---

## Notes

This ADR intentionally avoids prescribing specific technology choices (e.g., Go vs. Node.js for the notification service, PostgreSQL vs. DynamoDB for its datastore) because those are implementation decisions best made when the extract actually occurs. The purpose of this record is to capture *why* we chose this direction, not *how*.
