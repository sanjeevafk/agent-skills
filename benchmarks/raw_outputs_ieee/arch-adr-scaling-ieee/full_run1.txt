# ADR-0010: Modular Monolith Over Full Microservices Rewrite

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering leadership, Architecture review board

## Context

The codebase is a Rails modular monolith backed by PostgreSQL, currently organized into domains (core API, billing, notifications, search, reporting) within a single application. We've hit three compounding problems:

1. **Deploy pain**: With changes touching multiple domains, we have merge conflicts and brittle integration test suites. Our current deployment frequency is ~2 deploys/week because we can't release domains independently — every domain change requires a full application redeploy and risk-assessment cycle.
2. **Realtime notifications needs independent scaling**: The notification hot module handles WebSockets, push notifications, and email queues under spiky traffic patterns (e.g., batch notification blasts during billing cycles). Scaling it means duplicating the entire Rails process and DB connection pool, consuming 3-4x more resources than necessary.
3. **Leadership is pushing a full microservices rewrite** based on the assumption that microservices solve these problems. This pressure came from VP Engineering citing competitors' distributed architectures and stakeholder anxiety about "technical debt accumulation."

The forcing function is concrete: our last production incident took 6 hours of coordinated rollback across all domains because a change in billing crashed the monolith-wide deployment pipeline. Team velocity has dropped 40% over six months, and one engineer quit citing "unbearable coupling stress."

We have ~18 months runway before our Series B funding cliff. Any architectural decision must balance speed-to-market against long-term maintainability. The cost of a full rewrite (estimated 9-12 months engineering time for zero incremental product features) directly threatens fundraising milestones.

## Decision

We reject the full microservices rewrite and instead adopt a **strangler-pattern evolution**: extract the realtime notifications module as an independently deployable service while keeping the rest of the application as a well-bounded modular monolith.

Notifications will be extracted as a small Go service communicating via asynchronous event bus (Kafka) and direct HTTP API calls for webhook delivery. The core Rails application publishes `NotificationSent` events; the new service consumes them and scales the WebSocket/push layer independently.

All other domains remain modularly decoupled within Rails using the Service Layer pattern and explicit domain boundaries enforced through rspec integration tests per domain. We establish clear criteria for when future modules *must* be extracted (see Reversal Triggers below).

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite

Re-architect the entire application as a suite of independently deployable services, each with its own database and API surface. Rebuild authentication, billing, search, and reporting as separate services.

- **Pros**: True independent scaling and deployment for all domains; clean bounded contexts with no cross-service coupling; modernizes the tech stack fully.
- **Cons**: Estimated 9-12 months with zero product value delivered during rebuild; massive operational overhead (distributed tracing, saga coordination, eventual consistency handling, service mesh); team would lose velocity entirely for a year+; introduces network failure modes the monolith never had; high risk of partial rewrite abandonment (the "partial rewrite graveyard" anti-pattern).
- **Why not**: The rewrite buys us nothing the strangler approach won't deliver faster, and introduces systemic risk. If half the rewrite gets cut due to funding pressures, we have two broken systems instead of one working one.

### Alternative 2: Extract Only the Notifications Module (Chosen)

Extract the realtime notifications module as a standalone service behind a feature flag boundary, leaving the rest of the Rails application intact. Use an event bus for async communication.

- **Pros**: Solves the immediate scaling problem (notifications scale independently); eliminates deployment contention between notifications and other domains (~30% of our deploy conflicts involve notifications); low-risk migration with a clear rollback path via feature flags; delivers visible architectural progress in <8 weeks instead of invisible progress over 9 months; demonstrates the extraction pattern so other teams can replicate it for future module extractions.
- **Cons**: We maintain two deployments (Rails app + notification service) and their interop; creates a precedent that may increase extraction requests; some cross-domain queries still require internal HTTP calls; temporary dual-stack increases CI complexity until all modules are evaluated.
- **Why not**: These are manageable trade-offs that decrease over time as more modules stabilize. The concerns are implementation-level, not architectural blockers.

### Alternative 3: Stay Fully Monolithic — Fix Deploy Pain at Application Level

Keep everything in one Rails app but improve the development workflow: implement trunk-based development, add parallelized per-domain test suites, use CI sharding, and invest heavily in the test infrastructure to reduce false-positive integration failures.

- **Pros**: Zero architectural change; lowest immediate cost; team stays focused on product delivery rather than infrastructure work.
- **Cons**: Does not solve the notifications scaling problem (still requires full-process duplication); deploy contention persists because Rails middleware and initializers load globally — even without code changes, a bad deployment of any module brings down everything; CI improvement has diminishing returns once the integration test matrix exceeds ~5,000 examples; doesn't address leadership's strategic concern about scalability constraints.
- **Why not**: Leadership veto risk is high — staying monolithic ignores the real scaling demand. Incremental CI improvements don't compound; they just delay the inevitable conversation about decomposition.

### Alternative 4: Modular Monolith as Final Form — Accept the Trade-off

Accept that the Rails monolith is the right shape long-term. Invest in strong domain boundaries within Rails, enforce strict dependency rules with tools like `marginalia` or custom linters, and accept that notifications will share the same deploy pipeline and scaling strategy. Budget for vertical scaling of the entire process during notification spikes.

- **Pros**: Cleanest possible architecture from an operational standpoint; no distributed systems complexity; simplest deployment model; fastest feature velocity across all domains.
- **Cons**: Vertical scaling costs become unsustainable at peak (notification blasts could spike CPU to 95%+ across the entire app); resource waste scales linearly with worst-case notification load, not average; team morale problem persists — developers who care about notifications still have to deploy unrelated domain changes; does not satisfy leadership's scaling mandate.
- **Why not**: Resource waste alone makes this untenable for a funded startup where cloud spend is scrutinized. The human cost (developer frustration, attrition) is equally hard to justify.

## Consequences

### Positive
- **Independent notification scaling** solves the immediate resource waste and performance problem, potentially reducing cloud spend by 40-60% during non-spike periods.
- **Reduced deploy friction** between notifications and other domains eliminates ~30% of our current merge-deployment conflicts.
- **Demonstrated extraction pattern** gives the team a proven playbook for future module extraction decisions, turning architectural transformation into incremental engineering sprints rather than a binary rewrite gamble.
- **Faster time-to-value**: Working solution in 8 weeks vs. invisible progress for 9+ months.
- **Lower risk profile**: Feature-flagged rollout allows gradual cutover with instant rollback capability. If the notification service behaves poorly, we flip the flag and revert.
- **Team velocity preserved**: No 9-month productivity cliff. Engineers ship product features throughout the transition.

### Negative
- **Operational complexity increases temporarily**: Two deployment targets, event serialization formats, and inter-service error handling paths to manage during the transitional period.
- **Extraction precedent**: Other domain leads may request similar extractions before the initial pattern matures, creating potential context-switching pressure on the core team.
- **Eventual consistency burden**: Notification service communicates asynchronously, meaning users may see delayed notification state — a UX regression during message loss scenarios.
- **Split debugging experience**: Support team now deals with correlated logs across two systems during incidents, requiring distributed tracing investment.
- **Potential for premature optimization**: If total user count doesn't grow as projected, the independent notification service may be unnecessary overhead.

### Risks
- **Migration scope creep**: Without strict scope boundaries, the extraction effort could balloon beyond 8 weeks if the team tries to refactor adjacent domains simultaneously. *Mitigation*: Lock the extraction scope to notification module boundaries only; defer other domain evaluations to a formal review gate after go-live.
- **Inter-service coupling becomes accidental tightness**: If the notification service starts making synchronous HTTP calls into the Rails app for data lookups, we've built a distributed monolith. *Mitigation*: Enforce async-first communication via Kafka; require explicit design review for any synchronous cross-service call.
- **Talent gap on Go**: Team has zero Go experience. *Mitigation*: Partner with a senior Go contractor for the first sprint; pair-program to transfer knowledge; choose a library subset narrow enough for rapid competence building (standard library http + sarama/kafkajs only).
- **Leadership impatience**: VP Engineering may push back on the hybrid approach, preferring the perceived cleanliness of a full rewrite. *Mitigation*: Pre-align on reversal triggers (Section: Reversal Triggers) as shared success criteria before project start. Present the 8-week milestone roadmap with explicit validation gates.

## Reversal Triggers

This decision remains valid until any of the following conditions are met. Detection of any trigger initiates a formal architecture review re-evaluating toward full microservices or alternative decomposition:

1. **Cross-domain coupling exceeds threshold**: When more than 40% of all new domain-to-domain calls happen via external HTTP APIs rather than in-process method calls (measured via OpenTelemetry span analysis over a rolling 30-day window), the modular monolith's internal coupling has grown so large that extracting additional modules becomes more efficient than managing inter-module dependencies in-process.

2. **Individual module outgrows decomposability**: When any single remaining domain's codebase exceeds 150k SLOC AND has a deployment footprint larger than 20 engineers actively committing to it within a quarter, the signal suggests that module should stand on its own rather than compete for shared infrastructure.

3. **Business scale shifts unit economics**: When monthly active users exceed 2 million OR daily concurrent WebSocket connections exceed 50,000, the cost of maintaining in-process domain isolation becomes harder to justify versus full service decomposition — at this scale, independent team autonomy across ALL domains (not just notifications) generates measurable throughput gains that a modular monolith cannot support.
