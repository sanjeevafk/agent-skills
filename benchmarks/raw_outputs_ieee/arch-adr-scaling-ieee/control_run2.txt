## ADR-042: Modular Monolith Strategy Over Microservices Rewrite

**Status:** Accepted
**Date:** 2026-08-26
**Authors:** Engineering Lead
**Deciders:** Engineering Team (12 engineers), CTO

---

### Context

Our codebase is a single Rails application backed by Postgres. The team of 12 engineers currently deploys **2 times per week** with a combined cycle time of ~4 hours from commit to production. This is workable but not fast enough for our growth trajectory.

**The forcing factors driving this discussion:**

| Factor | Current State | Target |
|---|---|---|
| Deploy frequency | 2/week | Daily+ |
| Notification throughput | Scaled with entire app; wastes 60% compute on non-WS workers during low traffic | Scale web vs. WS independently |
| Team allocation | ~3 engineers (25%) constantly context-switched into realtime notification bugs | Dedicated subteam ownership |
| Blast radius of incidents | Any deploy risks the notification pipeline (and vice versa) | Isolate failure domains |

Leadership has proposed a **full microservices rewrite** across all modules. Several senior engineers have voiced strong reservations — citing precedent from comparable rewrites at similar-stage companies — but lack a structured alternative proposal.

This ADR documents the team's decision on how to proceed.

---

### Concerns

- **Deploy pain** must decrease; the current 2-deploys-weekly cadence is causing release-day toil and preventing feature velocity
- **Notification scalability** is a real problem — WebSocket connections consume memory and CPU, inflating costs when the rest of the app is idle
- **Team coordination overhead** scales superlinearly with service count; a 12-person team cannot efficiently maintain 15+ services without heavy DevOps investment
- **Migration risk** — any rewrite carries delivery delay risk that directly impacts revenue commitments
- **Reversibility** — if the wrong path is chosen, how easily can we pivot later?

---

### Decision

We adopt a **modular monolith first, surgical extraction second** strategy:

1. **Immediately:** Restructure the Rails monolith into explicit, test-isolated modules using the modularity patterns described by Martin Fowler (sealed modules with defined interfaces, no cross-module direct DB access, each module owns its schema namespace). Apply this to the notification module first as a pilot.

2. **Extract only the notification service** within 90 days — the one module that demonstrably requires independent scaling. Deploy it separately, communicate via message queue (Redis Streams or RabbitMQ), and run both the monolith and the extracted service from the same repo (monorepo).

3. **Defer all other service boundaries.** Do not decompose users, payments, content, search, or any other domain. If a second extraction is warranted after 90 days, it must pass the same forcing-factor review that justified notifications.

4. **Run both from the same repository** under `app/modules/notifications` (monolith) → `services/notifications` (extracted). Shared dependencies go in a gemspec (`lib/notifications_client`). No fork-and-forget.

This is not a "never do microservices" decision. It is a "don't boil the ocean" decision — bounded experimentation with actual extraction, not theoretical decomposition.

---

### Alternatives Considered

#### Alternative 1: Full Microservices Rewrite (Proposed by Leadership)

Decompose every domain into independently deployed services (users, auth, payments, content, search, notifications, analytics, admin, plus shared infrastructure). Each gets its own database, deployment pipeline, and monitoring stack.

#### Alternative 2: Extract Only the Notification Module (Chosen)

Restructure the monolith modularly while keeping everything in one deployable unit, then extract only the notification subsystem as a separate process. All other modules remain co-located.

#### Alternative 3: Stay as Monolith, Improve CI/CD Only

Keep the existing flat Rails structure. Invest exclusively in faster CI pipelines, blue-green or canary deployments, and operational discipline to reduce deploy friction without architectural change.

---

### Consequences

#### Positive

- **Deploy frequency increases** — modular boundaries give us clear integration-test contracts. Even within one repo, we can parallelize testing per-module and achieve daily-ish deploys without extracting anything
- **Notification scaling becomes real** — the extracted service runs horizontally on its own, sized purely for WebSocket connections. Estimated 40–60% cost reduction on notification infra
- **Team ownership aligns** — the 2-person realtime squad owns the notification service end-to-end. Other teams touch their modules without needing realtime-domain knowledge
- **Blast radius shrinks** — a notification outage doesn't take down payments; a payment deploy doesn't restart WebSocket servers
- **Low migration risk** — no rip-out-and-rebuild timeline. We keep delivering features while iterating toward this state incrementally
- **Reversible** — the extracted service stays in the same repo. We can re-merge it into the monolith if the data shows it wasn't worth the complexity, or extract further modules if needed

#### Negative

- **Dual-run complexity** — for ~60–90 days we operate both the monolith and an extracted service, adding integration-testing surface and deployment orchestration
- **Cross-process calls are slower** — replacing in-process module calls with message-queue communication introduces latency (~5–15ms p99 additional per call). We mitigate by keeping synchronous paths in-process where possible
- **Dev environment heaviness** — `docker-compose up` must start Rails + notification worker + Redis/RabbitMQ. Onboarding new engineers takes ~15 minutes longer until they're green
- **Not a silver bullet for all teams** — only 2 of 12 engineers benefit immediately from reduced context-switching. The remaining 10 see incremental improvement (better tests, module isolation) but don't get dedicated ownership yet
- **Architecture drift risk** — without continued discipline, the extracted service could become another tangled mess that's hard to move or merge. Requires deliberate interface design reviews
- **Doesn't satisfy leadership's preferred path** — some stakeholders expected the "big bang" rewrite. Pushback may arise if they perceive this as insufficient ambition

---

### Reversal Triggers

This decision is conditional and will be reviewed automatically when any of the following occur:

| Trigger | Measurement | Threshold |
|---|---|---|
| Extracting a **second module** hits >3 months of engineering effort due to tight coupling | Estimation from modular architecture audit | Coupling score above threshold |
| Deployment frequency does not reach **≥5/week** after 6 months of modularization | CI/CD metrics | Below 5 deploys/week at month 6 |
| Notification service **cost exceeds 15%** of total infra spend** | Cloud provider billing | Above 15% |
| Cross-service integration defects cause **P1/P2 incidents >2/month** consistently over a quarter | Incident tracking | More than 2/month average |
| The team grows beyond **20 engineers** and communication overhead correlates with decreased throughput | DORA metrics + team surveys | Throughput drops >30% |

Any trigger fires → automatic architecture review within 2 weeks. New options (including broader decomposition or a partial rewrite) will be evaluated by a fresh ADR.
