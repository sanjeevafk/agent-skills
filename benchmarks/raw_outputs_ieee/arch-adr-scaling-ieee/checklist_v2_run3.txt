# ADR-0001: Extract Only Notification Module Instead of Full Microservices Rewrite

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering leadership, principal engineers, DevOps lead

## Context

The codebase is a Rails modular monolith backed by PostgreSQL. Two forcing factors are creating pressure:

1. **Deployment friction.** At 2 deploys/week the team feels pain around coordination overhead, deployment windows, and rollback risk across the entire codebase. Every change requires redeploying all modules together, even when only the notification handler changed.

2. **Notification module cannot scale within the monolith.** Realtime WebSocket connections (~500 concurrent at peak), high-throughput background job processing, and connection pool exhaustion during traffic spikes mean the notifications layer must scale independently of the rest of the application. The shared database connection pool and Ruby process model create hard ceiling constraints.

Leadership has proposed a full microservices rewrite to solve both problems simultaneously. However, decomposing the entire monolith introduces distributed systems complexity, data consistency challenges, and an estimated 6–9 months of engineering effort before incremental value returns. The actual scaling bottleneck lives exclusively in the notification module; the remaining modules function adequately.

## Decision

We will **extract only the notification module into its own service**, deployed and scaled independently from the rest of the monolith. The remainder stays as a cohesive Rails monolith.

### Architectural boundaries

- Notifications becomes a standalone Rails service with its own deployment unit, process pool, and horizontal scaling configuration.
- Database: the notification module owns its own `notifications` schema with clear foreign-key relationships. Read replicas serve cross-module queries; writes go through the monolith's transactional boundary.
- Inter-service communication: the monolith publishes domain events via a message queue (Sidekiq → Redis Streams / RabbitMQ). The notification service subscribes and persists deliveries asynchronously.
- Shared dependencies (models, validations, auth) extracted into a gem (`monolith-shared`) to avoid duplication without sharing a git repo.

### Concrete changes

1. Create the `notification_service/` directory with its own Gemfile, Docker image, and CI pipeline.
2. Implement an event-driven interface between monolith and service (e.g., `UserRegistered`, `MessageSent`, `SystemAlert`).
3. Migrate existing notification data and jobs with a zero-downtime migration script that backfills and replays missing events.
4. Deploy behind API Gateway or nginx routing `/notifications/*` and WebSocket `/ws/notifications` to the extracted service; everything else hits the monolith.

### What we explicitly do NOT do

- Decompose other modules (billing, user management, content, search) into separate services.
- Replace PostgreSQL with a polyglot persistence strategy.
- Adopt Kubernetes unless operational necessity later demands it.

### Risks

- **Eventual consistency gaps.** Cross-module reads may see stale data until the queue drains. Mitigation: use idempotent consumers and accept that notification delivery timing has an inherent tolerance window (seconds, not seconds required).
- **Operational complexity increases.** Managing two services means two CI pipelines, two monitoring dashboards, and inter-service failure modes. Mitigation: containerize identically, share Grafana/Prometheus stack, start with 2 developers owning both.
- **Database coupling remains.** Both services read the same Postgres instance. Mitigation: plan read replica setup within 3 months; partition large tables; add indexes for notification queries.

## Alternatives Considered

### Alternative 1: Full microservices rewrite

Decompose the entire monolith into independently deployable microservices based on bounded contexts (user mgmt, billing, content, search, notifications, etc.), each with its own database and technology stack.

**Rejected because:**
- Timeline: 6–9 months before measurable ROI vs. 4–6 weeks for notification extraction alone.
- Risk: every decomposition introduces data consistency bugs, network failures, and debugging complexity across all modules — most of which don't need it.
- Cost: roughly 5× more engineer-months than extracting one module. Opportunity cost includes delayed feature development across the core product.
- Premature: there is no evidence that other modules face scaling bottlenecks or organizational fragmentation that would justify their independence.

### Alternative 2: Stay fully monolithic — invest in deployment tooling instead

Keep everything in one deployment unit but improve the developer experience: better CI/CD pipelines, canary deployments, database migration automation, faster build times, pre-deploy test optimization. Add horizontal scaling for the entire monolith via container orchestration.

**Rejected because:**
- Does not solve the notification scaling problem. Scaling the whole monolith horizontally just to handle notifications wastes resources (non-notification traffic gets duplicated compute).
- Deployment pain is a symptom, not the root cause. Even with faster deploys, the connection pool contention and Ruby process limits remain hard boundaries for notification throughput.
- Cost-effective for reducing deploy pain, but ignores the genuine architectural constraint: WebSockets and async job processing behave fundamentally differently from typical HTTP request/response patterns that the monolith handles well.

### Alternative 3: Extract only notifications using plugin architecture within the monolith

Keep a single deployment but architecturally isolate the notification module using Rails engines/pluggable architecture, allowing independent vertical scaling via worker processes without horizontal service decomposition.

**Partially rejected because:**
- Solves some scaling (worker processes) but not the fundamental WebSocket concurrency issue. Rails' synchronous request handling means you still fight the global mutex in Puma/Monit against thousands of open WebSocket upgrades.
- Worker isolation helps background jobs but not the real-time connection layer, which requires dedicated node.js / Go / Elixir processes with persistent connections.
- We chose Option 1 over this because the notification layer genuinely needs a different runtime profile for WebSockets (long-lived connections, async I/O, event loops), which the extracted-service approach enables cleanly.

## Consequences

### Positive

- **Targeted scaling.** The notification service scales independently (WebSocket connections, job queues) without inflating compute costs for unrelated traffic.
- **Faster feedback loop.** Extraction takes 4–6 weeks vs. 6–9 months for full rewrite. We get value quickly and can validate the approach.
- **Reduced blast radius.** A failure in notification handling doesn't take down the monolith's primary business logic.
- **Proven stack preserved.** 95% of functionality stays in the well-understood Rails + Postgres pattern. Team skills aren't diluted across new languages and frameworks.
- **Clear decomposition precedent.** If another module later shows scaling pressure, the pattern is established and repeatable.
- **Deploys.** The monolith continues at ~2 deploys/week for its scope. Notifications get their own rapid iteration cycle without waiting for the larger release train.

### Negative

- **Two services to manage.** Operational overhead roughly doubles for the notification lifecycle (CI/CD, monitoring, logging, alerting, incident response).
- **Distributed systems complexity.** Network calls replace method invocations. Timeouts, retries, circuit breakers, and idempotency become necessary concerns for previously-simple interactions.
- **Data consistency shifts.** Previously local transactions become distributed. Some operations now have eventual consistency; callers must design around delays (e.g., "notification sent" confirmation is asynchronous).
- **Testing burden increases.** Integration tests now span service boundaries. End-to-end flows require mocked inter-service communication or integration test environments.
- **Migration risk.** Zero-downtime migration of existing notification data and replay of missed events carries non-trivial risk during execution.

## Reversal Triggers

This decision remains valid as long as the following conditions hold. If any trigger fires, we re-evaluate whether broader decomposition is warranted:

1. **Two additional modules show independent scaling pressure** within 6 months of this decision — signals we underestimated system boundaries and should re-evaluate multi-module decomposition.
2. **Cross-service latency adds >200ms p95** to core user-facing flows measured over two consecutive sprint cycles — indicates our API contracts need tightening or the split was too fine-grained; consider consolidating.
3. **Operational overhead exceeds 30% of engineering capacity** (measured as developer-hours/month spent on infrastructure vs. features) — suggests we've overshot and should either automate heavily or consolidate.
4. **The notification service develops distinct ownership requirements** (different teams, different update cadences, different compliance requirements) after 6 months — this would make the partial split defensible as a step toward broader organizational-aligned decomposition rather than a stopgap.
5. **PostgreSQL read replica setup resolves the scaling concern** without extraction — if database-level improvements meet notification throughput targets, we could roll back to a fully monolithic deployment.

Re-evaluation happens quarterly or when any trigger condition is met, whichever comes first.
