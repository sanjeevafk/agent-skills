## ADR-001: Modular Monolith + Single-Module Extraction for Realtime Notifications

**Status:** ⛔ Proposed (pending team review & leadership alignment)  
**Date:** 2026-08-26  
**Authors:** Engineering Team (12-engineer squad)  
**Deciders:** Tech Lead, Engineering Manager, VP Engineering  

---

## Context

Our Rails + Postgres modular monolith currently averages **one hot module (realtime notifications)** requiring independent horizontal scaling due to WebSocket/connection-heavy workloads, while the rest of the platform scales adequately at current compute allocation. This forces us to either over-provision the entire application or accept notification degradation under load.

Deployment velocity has degraded to **one deploy every five days** (approximately two deploys per week, one planned and one emergency fix average). The full-monolith deployment pipeline takes **22 minutes** end-to-end, with database migration checks, asset compilation, and integration tests forming the bottleneck. Every change — even those touching only the billing module — requires building, testing, and deploying the entire monolith.

Leadership has proposed a **full microservices rewrite** across all modules, motivated by the desire to eliminate deployment coupling entirely and enable independent scaling of every bounded context. The team consists of 12 engineers organized into three squads of four, working on roughly equal functional domains within the monolith.

### Forcing Factors

| # | Factor | Weight | Evidence |
|---|--------|--------|----------|
| F1 | Notification module handles ~40% of persistent WebSocket connections independently | High | Load test data, Q2 2026 |
| F2 | Current deploy time is 22 min; target SLA is <5 min per domain | High | CI metrics (last 30 deploys) |
| F3 | 12-engineer team with 3 squads creates merge-conflict friction in a shared codebase | Medium | Git history analysis, monthly conflict report |
| F4 | Postgres schema is heavily normalized with cross-module joins (orders ↔ users ↔ notifications) | High | Database profiling, ERD v3.1 |
| F5 | No DevOps/SRE dedicated infrastructure team; services would need to be self-operated | High | Org chart, bandwidth survey |
| F6 | Revenue-critical checkout flow must remain zero-downtime during deploys | High | SLO document §4.2, incident budget constraints |
| F7 | Migration budget allows zero new-headcount initiatives | Critical | FY2026 capex approval |

---

## Decision

**We will extract only the realtime notifications module into an independent service, leaving the remaining modules in the modular monolith.**

The notification service will:
- Run as a separate Rails process with its own Postgres schema (`notifications_v2`)
- Communicate via async event publishing to the monolith through a PostgreSQL `LISTEN/NOTIFY` channel and occasional message queue (RabbitMQ, starting minimal)
- Have its own CI/CD pipeline with independent deployment gates
- Be operable by the existing "platform" squad (4 engineers) without new headcount
- Share no codebase with the monolith but can reuse gems from a private gem repository

All other modules (**users, billing, orders, catalog, search**) remain in the monolith. Deployment orchestration for the monolith will continue as-is but will be optimized separately (parallel test execution, build caching) to bring deploy times toward the 5-minute SLA. The extraction is scoped as a **9-week effort** consuming approximately 2 engineer-months per week (distributed across the platform squad and a rotating contributor from another squad).

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite

Extract every bounded context into independently deployable, independently scalable services. Each service owns its database, API contract, and CI/CD pipeline. Requires defining service boundaries, implementing inter-service communication (gRPC/API gateways), distributed tracing, and saga patterns for cross-service transactions.

**Rejection rationale:** Given forcing factors F4 (heavy cross-module SQL joins), F5 (no dedicated DevOps), and F7 (zero new headcount), a full rewrite would require 8–12 months of focused engineering work with an unknown boundary definition process. Every cross-module transaction would need saga compensating logic, increasing failure surface area. The return on investment for extracting low-traffic modules (catalog, search) that don't face scaling pressure is negligible compared to the operational complexity cost. Risk of the "distributed monolith" pattern — getting all the worst properties of both architectures without gaining independence.

### Alternative 2: Extract Only Notifications (Selected)

Extract only the realtime notifications module into an independent service. Optimize the monolith deployment pipeline in parallel through CI improvements (concurrent test suites, dependency caching). Keep all other modules together.

**Selection rationale:** Directly addresses F1 (the single scaling pain point) and F2 (partial deployment independence for the most frequently changed module) without triggering the risks of F4/F5/F7. Lowest engineering cost (~18 engineer-months total vs. ~90+ for full rewrite). Preserves the performance advantage of SQL joins for high-value queries. Enables validation of service-extraction patterns before committing to further extractions if needed.

### Alternative 3: Stay Fully Monolithic, Invest in Polyglot Scaling Only

Keep the entire system as a single deployable unit. Address the notification scaling problem at the infrastructure level using connection pooling proxies (PgBouncer, Sidekiq clustering), CDN-level websocket relays, and read replicas — without any code-level service boundaries. Continue investing in monolith optimization: squibbed gems, isolated test suites, improved staging environments.

**Rejection rationale:** Does not address F2 (deployment coupling remains). Connection-proxy approaches only mitigate the *symptom* of the scaling problem, not the root cause: the notification handling code cannot be deployed or scaled independently of the rest of the monolith. Would also mean continued 22-minute deploys, which is unsustainable as the codebase grows. Over time, the technical debt of delayed deploys compounds through feature-blocking and emergency outages (F6).

### Alternative 4: Vertical Split by Feature Domain, Horizontal Extraction Later

Define clear feature-domain boundaries inside the monolith using explicit interface contracts between modules, then extract each module to its own process on an *as-needed* basis (triggered by actual scaling or deployment pain). Implement internal gRPC boundaries between modules from day one.

**Rejection rationale:** The "as-needed" timeline is unclear and leaves the current critical path (notifications + deployment) unresolved for an indefinite period. Defining module boundaries post-hoc is significantly harder than doing it intentionally now. Adding gRPC contracts prematurely (for modules that won't be extracted soon) adds overhead with no immediate benefit (violation of YAGNI principle). Notifications needs action *now*, not "eventually."

## Consequences

### Positive

1. **Immediate deploy-time reduction for notifications.** The notification module goes from ~22-min deploy to ~3–4 min, addressing the highest-urgency stakeholder concern.
2. **Independent scaling of the hot module.** Notifications can scale horizontally based on WebSocket connection count without provisioning idle capacity for the rest of the monolith. Estimated cloud cost savings: 30–40% of the compute footprint.
3. **Low-risk, bounded scope.** Only one module changes architecture. If the approach fails, reverting to monolith-only is a matter of deleting the extracted service and merging back the notification schema.
4. **Learning pathway for future extractions.** The team validates inter-service communication, database splitting, and deployment practices on the lowest-risk module first. Findings inform whether billing or orders should be next (if ever).
5. **Preserved query performance for core flows.** Orders, users, and billing remain able to use SQL JOINs across their schemas — eliminating N+1 query patterns and saga orchestration for the revenue-critical checkout path.
6. **No additional hiring required.** Existing platform squad (4 engineers) absorbs the work. Private gem repo and PostgreSQL native features minimize new infrastructure dependencies.

### Negative

1. **Dual-operation burden briefly intensifies.** During the 9-week transition, the team operates both the monolith and the new service simultaneously. On-call rotation expands temporarily until knowledge transfer completes.
2. **Eventual consistency introduced for cross-module reads.** Features that join notifications with orders/users now span a service boundary. These queries become eventual-consistent via published events rather than instant SQL results, requiring application-level reconciliation where previously none existed.
3. **Deployment orchestration complexity increases marginally.** Release coordination between the monolith and the notification service adds a handoff step ("notify-svc must be deployed first, then monolith"). This is a minor procedural cost but introduces a new potential failure mode during rollbacks.
4. **Partial value realization.** Modules beyond notifications still suffer from 22-minute deploys. The CI pipeline improvement effort (separate initiative) may not fully close the 5-minute SLA gap without further architectural changes later.
5. **Code duplication risk.** Shared domain concepts (user identifiers, subscription status) are duplicated as plain types/gems across the two codebases. Without active governance, drift between the notification service's understanding of user state and the monolith's can occur silently.
6. **Operational observability fragmentation.** Logging, metrics, and tracing now span two codebases. The team must invest in centralized log aggregation and distributed tracing (OpenTelemetry) to maintain debugging visibility — a non-trivial upfront cost.

## Reversal Triggers

This decision will be re-evaluated (and potentially reversed or extended) when any of the following conditions materialize:

| # | Trigger | Measurement | Review Cadence |
|---|---------|-------------|----------------|
| R1 | Notification module exceeds 30% of total engineer capacity (>0.5 engineer-months/month) after extraction | Sprint burndown, capacity reports | Monthly squad planning |
| R2 | Monolith deploy time does not drop below 10 minutes after 6 weeks of CI optimization effort | CI metric dashboard | Biweekly tech lead review |
| R3 | Any two additional modules (from users, billing, orders, catalog, search) hit the same scaling pressure as notifications did pre-extraction | Load-test p99 latency spikes correlating with module-specific traffic | Quarterly architecture review |
| R4 | Cross-module eventual-consistency bugs in notification-order interactions exceed 2 incidents per quarter | Incident tracking, severity ≥ P3 | Monthly incident retrospective |
| R5 | Team hires a dedicated DevOps/SRE member (headcount approved) | HR system record | At time of hire |
| R6 | Inter-service communication costs (latency, retries, serialization errors) for notification queries exceed acceptable thresholds (>50ms added to notification read paths) | APM tracing, error budgets | Continuous monitoring |

**Default review date:** 90 days after initial deployment of the notification service. An open architecture review meeting will assess whether to: (a) extend the extraction model to the next most-pressured module, (b) stabilize at this configuration indefinitely, or (c) revert if the extraction proved more harmful than beneficial.

## Notes & Open Questions

- **Database split strategy:** Will we use a single shared Postgres instance with separated schemas (`app_main`, `notifications_v2`) or spin up a second Postgres instance? First pass uses shared instance for simplicity; second phase evaluates separation based on backup/restore requirements.
- **Message broker selection:** Starting with PostgreSQL `LISTEN/NOTIFY` for immediate availability. RabbitMQ is identified as the fallback for higher-throughput scenarios post-validation.
- **Who owns the notification service?** Designated to the platform squad (currently 4 engineers), with a rotating secondary owner from another squad to prevent knowledge siloing.
