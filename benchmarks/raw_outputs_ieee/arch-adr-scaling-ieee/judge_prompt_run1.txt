# ADR-001: Retain Modular Monolith, Extract Realtime Notifications Module Independently

**Status:** Proposed  
**Date:** 2026-08-26  
**Authors:** Architecture Review Board  
**Deciders:** Engineering Leadership, CTO  

---

## Decision

Retain the modular monolith architecture for the core Rails application. Extract **only** the realtime notifications module into an independent service (Node.js + Redis Streams + WebSockets) while keeping the remaining Rails + Postgres stack as a single deployable unit. Defer any broader microservices transition until clear business value justifies it.

## Context

The current architecture delivers measurable pain points:

1. **Deploy friction**: 2 deploys/week across a shared Rails codebase with 14 modules means merge conflicts and deployment coordination costs ~4 engineer-hours per week. Database migrations occasionally stall deployments requiring rollback.
2. **Scaling mismatch**: The realtime notifications module consumes ~65% of worker memory but only handles ~8% of request volume. It requires horizontal WebSocket connections that the Rails sidecar model doesn't scale efficiently — connection limits force us to over-provision the entire app.
3. **Team autonomy pressure**: 12 engineers across 3 teams share one codebase. Two teams actively work on notifications; they're blocked by change-freeze windows dictated by the other teams' deploy schedule.
4. **No proven failure of the monolith itself**: Core Rails modules compile, test, and run reliably together. The database layer performs within SLA. The problem isn't architectural coherence — it's resource contention and deployment coupling between one hot module and the rest.

The proposal for a **full microservices rewrite** introduces risk without addressing whether those risks yield commensurate benefit. Historical precedent shows such rewrites consume 6-12 months, temporarily halt feature velocity, and rarely deliver isolation benefits proportional to the cost unless individual services have distinct scaling, language, or update-frequency requirements.

## Decision

Extract **only** the notifications module as an independent service. Everything else stays in the Rails modular monolith.

**Boundary definition:**
- Notifications module exposes: event ingestion API (HTTP), notification delivery webhook, admin query endpoint
- Shared state eliminated: notifications store its own PostgreSQL schema on a separate database instance; reads from the core via read replicas or materialized views, never writes back
- Deployment: CI/CD pipeline split into two — core app pipeline (unchanged rhythm) and notifications pipeline (independent deploy gate)
- Tech stack: Node.js + Fastify + Redis Streams for message ordering; PostgreSQL for persistence

**What this is NOT:** A general authorization for future extractions. Each subsequent extraction requires its own ADR review.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
Decompose all 14 modules into individually deployable, independently scaled services with inter-service gRPC/REST communication, distributed tracing, and a service mesh.

**Trade-off:** Highest engineering investment (estimated 9-12 months, 6-8 FTEs). Eliminates cross-module coupling but introduces network latency, eventual consistency complexity, observability overhead, and deployment orchestration across N services. Most modules handle <5% of traffic — over-provisioning each would cost more than current under-utilization.

**Verdict rejected because:** The scaling problem is isolated to one module. Spreading the same operational complexity across all modules amplifies cost without proportional benefit.

### Alternative 2: Extract Only Notifications Module (CHOSEN)
Isolate the hot module into its own service with clean boundaries. Keep the remaining 13 modules in the Rails monolith.

**Trade-off:** Moderate effort (~2-3 months, 2-3 FTEs). Solves the scaling problem directly. Reduces deploy coupling between the notifications team and the rest. Introduces one additional service to operate, monitor, and fund. Preserves monolith benefits for modules that are working well.

**Verdict chosen because:** It targets the specific constraint (notifications scaling + deployment interference) without inflating scope. The cost-to-benefit ratio is favorable: we fix the problem causing burnout without taking on enterprise-scale distributed system complexity.

### Alternative 3: Stay Pure Modular Monolith, Invest in Tooling
Keep all 14 modules in a single deployable unit. Address deploy pain with improved CI/CD (parallel test suites, canary deployments), stricter module boundaries enforced by linters/tests, and database migration decoupling.

**Trade-off:** Minimal new infrastructure. Preserves simplicity and fast inter-module calls. But does not solve the WebSocket scaling issue — the notifications module will continue to force over-provisioning of the entire app. Team autonomy improves partially through process changes but structural blocking remains (change freezes, shared dependency management).

**Verdict rejected because:** It addresses only half the problem. Deploy tooling improvements reduce friction but don't enable independent horizontal scaling for a stateful WebSocket server.

### Alternative 4: Platform Migration (Rails → Go/Java Polyglot Refactor)
Rewrite the entire application in a performance-oriented language with native concurrency support (Go or Java Spring), leveraging goroutines/pools for the WebSocket handling within the same binary.

**Trade-off:** Massive rewriting effort (12+ months, 8-10 FTEs). Potentially better raw throughput and memory efficiency. But forces learning curve, destroys existing institutional knowledge base, migrates risk without solving the deployment coupling problem (still one binary to deploy).

**Verdict rejected because:** Language choice is a solution in search of a problem. The issue isn't Ruby's performance — it's stateful long-lived connections competing with short-lived request handlers for resources. Separation of concerns beats rewriting.

## Consequences

### Positive
- **Independent scaling:** Notifications service scales horizontally based on WebSocket connection count; core Rails app scales based on request throughput. Resource allocation becomes cost-efficient.
- **Reduced deploy interference:** The notifications team can deploy without coordinating with the core app teams. Change freeze windows shrink from covering 14 modules to covering 13.
- **Preserved simplicity:** 13 modules retain monolith benefits — fast iteration, simple debugging, single database transaction, no network serialization, no distributed tracing debt.
- **Incremental path forward:** If future extractions prove valuable, the team now has a reference pattern (boundary design, deployment pipeline, monitoring conventions) to follow. Failure of one extraction doesn't endanger the whole.
- **Lower migration risk:** ~2-3 month timeline vs. 9-12 months for full rewrite. Shorter projects have statistically higher success rates and learn faster.

### Negative
- **Hybrid operational burden:** Slightly increased operational complexity managing two codebases, two languages, two databases, and inter-service communication. The team must maintain both patterns until/unless further extractions occur.
- **Inter-service latency:** Notification events now travel over HTTP/network instead of in-process method calls. Latency increases from ~1ms to ~10-50ms (acceptable for the use case but measurable).
- **Eventual consistency edge cases:** Cross-module queries (e.g., "show me all recent activity for user X") require joining data from two databases. Requires materialized views or read-side aggregation to avoid N+1 cross-service queries.
- **Potential slippery slope risk:** This precedent may create organizational pressure to extract more modules without formal review. Mitigated by making each future extraction ADR-gated.
- **Notification team capability shift:** Engineers who are primarily Ruby developers now maintain a Node.js codebase. Training and pairing time required in first sprint.

# ADR-0010: Modular Monolith Over Full Microservices Rewrite

**Date**: 2026-08-26
**Status**: proposed

The codebase is a Rails modular monolith backed by PostgreSQL, currently organized into domains (core API, billing, notifications, search, reporting) within a single application. We've hit three compounding problems:

1. **Deploy pain**: With changes touching multiple domains, we have merge conflicts and brittle integration test suites. Our current deployment frequency is ~2 deploys/week because we can't release domains independently — every domain change requires a full application redeploy and risk-assessment cycle.
2. **Realtime notifications needs independent scaling**: The notification hot module handles WebSockets, push notifications, and email queues under spiky traffic patterns (e.g., batch notification blasts during billing cycles). Scaling it means duplicating the entire Rails process and DB connection pool, consuming 3-4x more resources than necessary.
3. **Leadership is pushing a full microservices rewrite** based on the assumption that microservices solve these problems. This pressure came from VP Engineering citing competitors' distributed architectures and stakeholder anxiety about "technical debt accumulation."

The forcing function is concrete: our last production incident took 6 hours of coordinated rollback across all domains because a change in billing crashed the monolith-wide deployment pipeline. Team velocity has dropped 40% over six months, and one engineer quit citing "unbearable coupling stress."

We have ~18 months runway before our Series B funding cliff. Any architectural decision must balance speed-to-market against long-term maintainability. The cost of a full rewrite (estimated 9-12 months engineering time for zero incremental product features) directly threatens fundraising milestones.

## Decision

We reject the full microservices rewrite and instead adopt a **strangler-pattern evolution**: extract the realtime notifications module as an independently deployable service while keeping the rest of the application as a well-bounded modular monolith.

Notifications will be extracted as a small Go service communicating via asynchronous event bus (Kafka) and direct HTTP API calls for webhook delivery. The core Rails application publishes `NotificationSent` events; the new service consumes them and scales the WebSocket/push layer independently.

All other domains remain modularly decoupled within Rails using the Service Layer pattern and explicit domain boundaries enforced through rspec integration tests per domain. We establish clear criteria for when future modules *must* be extracted (see Reversal Triggers below).

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite

Re-architect the entire application as a suite of independently deployable services, each with its own database and API surface. Rebuild authentication, billing, search, and reporting as separate services.

- **Cons**: Estimated 9-12 months with zero product value delivered during rebuild; massive operational overhead (distributed tracing, saga coordination, eventual consistency handling, service mesh); team would lose velocity entirely for a year+; introduces network failure modes the monolith never had; high risk of partial rewrite abandonment (the "partial rewrite graveyard" anti-pattern).
- **Why not**: The rewrite buys us nothing the strangler approach won't deliver faster, and introduces systemic risk. If half the rewrite gets cut due to funding pressures, we have two broken systems instead of one working one.

### Alternative 2: Extract Only the Notifications Module (Chosen)

Extract the realtime notifications module as a standalone service behind a feature flag boundary, leaving the rest of the Rails application intact. Use an event bus for async communication.

- **Pros**: Solves the immediate scaling problem (notifications scale independently); eliminates deployment contention between notifications and other domains (~30% of our deploy conflicts involve notifications); low-risk migration with a clear rollback path via feature flags; delivers visible architectural progress in <8 weeks instead of invisible progress over 9 months; demonstrates the extraction pattern so other teams can replicate it for future module extractions.
- **Cons**: We maintain two deployments (Rails app + notification service) and their interop; creates a precedent that may increase extraction requests; some cross-domain queries still require internal HTTP calls; temporary dual-stack increases CI complexity until all modules are evaluated.
- **Why not**: These are manageable trade-offs that decrease over time as more modules stabilize. The concerns are implementation-level, not architectural blockers.

### Alternative 3: Stay Fully Monolithic — Fix Deploy Pain at Application Level

Keep everything in one Rails app but improve the development workflow: implement trunk-based development, add parallelized per-domain test suites, use CI sharding, and invest heavily in the test infrastructure to reduce false-positive integration failures.

- **Pros**: Zero architectural change; lowest immediate cost; team stays focused on product delivery rather than infrastructure work.
- **Cons**: Does not solve the notifications scaling problem (still requires full-process duplication); deploy contention persists because Rails middleware and initializers load globally — even without code changes, a bad deployment of any module brings down everything; CI improvement has diminishing returns once the integration test matrix exceeds ~5,000 examples; doesn't address leadership's strategic concern about scalability constraints.

Invest in strong domain boundaries within Rails, enforce strict dependency rules with tools like `marginalia` or custom linters, and accept that notifications will share the same deploy pipeline and scaling strategy. - **Why not**: Resource waste alone makes this untenable for a funded startup where cloud spend is scrutinized. The human cost (developer frustration, attrition) is equally hard to justify.

# ADR-0001: Retain Modular Monolith Architecture; Avoid Full Microservices Rewrite

**Date**: 2026-08-26
**Status**: proposed
**Deciders**: Engineering Lead, CTO, Product Manager, DevOps Lead

## Context

The team operates a Rails + PostgreSQL modular monolith with 12 engineers shipping at 2 deploys/week. This cadence has been stable and predictable for over six months. However, two forcing factors are creating pressure to restructure:

1. **One hot module (realtime notifications) needs independent scaling.** Notification throughput spikes 5-10x during peak hours while the rest of the application sees flat or declining load. The monolith currently scales the entire application to serve notification demand, wasting approximately 70% of compute resources on non-notification paths.

2. **Deployment pain is growing from code coupling in shared models.** The notifications module and the billing module both touch `User` model validations and transactions. Changes in one frequently break CI in the other, contributing to a regression rate of ~12% on each deploy cycle. This is not a novel problem — it's well-documented as an issue with monolithic deployments where module boundaries are logical but implementation boundaries are not.

Leadership has proposed a full microservices rewrite across all modules. This would mean extracting every module into independently deployed services with separate databases, message queues, and deployment pipelines. The estimate ranges from 6-9 months of engineering effort (one engineer-quarter per major module) plus ongoing infrastructure complexity overhead of approximately 0.5 FTE dedicated to service mesh, observability, and inter-service communication.

This decision addresses whether to pursue that full rewrite or consider alternatives that preserve the operational stability of the current architecture while addressing the scaling and coupling concerns.

## Decision

We retain the modular monolith architecture. We do not extract individual modules into separate services. Instead, we address the specific problems through three targeted interventions within the monolith boundary:

### 1. Enforce Module Boundaries Within the Monolith

Apply strict dependency isolation between modules using a port-and-adapter pattern. Each module exposes interfaces through defined ports; internal implementations cannot leak into other modules. We enforce this with a `modular_monolith_lint` gem that validates interface usage at build time. No shared mutations of domain models across module boundaries. If a module needs another module's data, it calls through the public interface, not by reaching into private classes.

### 2. Extract Notifications as a Sidecar Process

Extract *only* the realtime notification delivery pipeline into a sidecar process running alongside the Rails application in the same deployment unit. The sidecar subscribes to notification events via PostgreSQL `LISTEN/NOTIFY` (not Kafka, not RabbitMQ — keep the plumbing simple). It handles WebSocket connections, push notification dispatch, and email fallback. It shares the same database but runs on its own worker pool with independent horizontal scaling. This gives us the scaling we need for the hot path without introducing distributed transaction complexity or inter-service networking.

Sidecar process interface:
```
┌─────────────────────────────────────┐
│         Rails Application            │
│                                      │
│  ┌──────────┐  LISTEN/NOTIFY    ┌──────────┐
│  │  Modules  │──────────────────→│ Sidecar   │
│  │  (core)   │                   │ Process   │
│  │           │  ←─── ack ─────── │ (notify)  │
│  └──────────┘                    └──────────┘
│       │                              │
│       ↓ postgres                     ↓ external APIs
│  ┌──────────┐                  ┌──────────┐
│  │PostgreSQL │               │WebSockets│
│  │  (shared) │               │ Push/SMS │
│  └──────────┘               └──────────┘
└─────────────────────────────────────┘
         Same deployment unit, independent scale
```

### 3. Deploy Frequency Target

Maintain the current deployment target of ≤4 deploys/week across the combined Rails + sidecar unit. The sidecar uses zero-downtime migrations with feature flags for backward-compatible schema changes. Database migrations are handled by Rails migrations exclusively; the sidecar only reads new columns or tables after migration is complete.

### Risks

- **Shared database coupling persists.** Both the main app and sidecar share PostgreSQL. A lock contention event in notifications could theoretically slow the main app. Mitigation: use connection pooling separation (PgBouncer or dedicated Postgres pools), prioritize notification queries, and set statement timeouts.
- **Development confusion.** Engineers may not know which module owns which piece of logic at module boundaries. Mitigation: maintain a `MODULE_BOUNARIES.md` file documenting ownership and required interaction patterns. Audit quarterly.
- **Sidecar process management adds ops surface area.** One more process to monitor, restart, and update. Mitigation: manage both processes in a single systemd/service unit file with health checks, treat it as part of the existing deploy, not a separate release.

## Consequences

### What Becomes Easier

- Independent scaling of the notification module without paying for idle capacity on other paths
- Fast iteration speed preserved — single codebase, single deploy, no service mesh debugging
- Low infrastructural overhead — no Kubernetes operators, no Istio, no distributed tracing stack needed initially
- Regression rate reduces as module boundaries are enforced and cross-module refactors become impossible
- Deployment predictability maintained — one artifact, one rollback point

### What Becomes Harder

- If the decision reverses later, the sidecar code lives inside the monolith repository, meaning a future microservices extraction will require splitting code that was intentionally co-located
- Debugging issues that span the sidecar and main app requires correlating logs across two processes rather than one
- New teams joining the project face a slightly less common architecture than plain Rails
- Adding a second sidecar later (e.g., for image processing or payment retries) means repeating this pattern — we should document it generically before doing so

### Open Questions

- Should the sidecar run as a separate container even though it deploys together? (Currently decided: single Docker image, two entrypoints, same orchestration.)
- Will PgBouncer be sufficient for connection pooling, or do we need a more sophisticated pooler when traffic doubles again?

## Reversal Triggers

This decision remains valid until any of the following conditions occur. When triggered, a new ADR initiating review is mandatory:

| Trigger | Threshold | Action |
|---------|-----------|--------|
| Notification sidecar hits >100 concurrent WebSocket connections | Sustained for >1 week, requiring more than 4 sidecar replicas | Evaluate full extraction to evaluate whether standalone service mesh justifies the infra cost |
| Inter-process latency (main → sidecar → DB → sidecar response) exceeds 200ms p99 | Measured over any 48-hour window | Assess whether shared DB access patterns justify separating notification data stores |
| Two or more additional modules independently request extraction | Confirmed by product roadmap requests | Treat as evidence that the modular monolith pattern is insufficient; escalate to full architecture review |
| Team grows beyond 20 engineers working in the same codebase | Active contributors exceeding threshold in last 90 days | Re-evaluate whether independent deployment velocity is worth the ops complexity |

If none of these triggers fire, the status reverts to accepted in 90-day increments automatically — no re-review required unless a trigger fires.
