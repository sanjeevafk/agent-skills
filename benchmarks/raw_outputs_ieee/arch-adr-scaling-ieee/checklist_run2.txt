# ADR 0001: Resist Full Microservices Rewrite; Extract Only Realtime Notifications Module

**Status:** Accepted  
**Date:** 2026-08-26  
**Deciders:** Engineering leadership, Tech leads  

---

## Context

We are a team of 12 engineers operating a **modular monolith** built on Ruby on Rails + PostgreSQL. Two forcing factors are driving a proposal from leadership to undertake a **full microservices rewrite**:

1. **Deploy pain — 2 deploys/week.** Our current CI/CD pipeline can safely handle this cadence without incident, but we're hitting a practical ceiling. Developers report that even small changes carry disproportionate coordination cost due to our single-deploy model. This is a *process* problem, not necessarily an *architecture* problem.

2. **Realtime notifications module needs independent scaling.** The notifications handler is CPU-bound (WebSocket fan-out, push notification dispatching, rate-limit checks) and has different load characteristics than the rest of the app. Scaling it horizontally within the monolith means over-provisioning everything else.

Leadership's instinct is a full rewrite into microservices. We need to evaluate whether that's the right move versus targeted extraction.

---

## Decision

We choose to **extract only the realtime notifications module as an independent service** while keeping the remainder of the application as a modular monolith. This balances the two forcing factors without paying the full cost of a distributed-systems rewrite.

Specifically:

- The notifications module runs as its own process, deployed independently, with its own database schema (can share the same Postgres cluster initially).
- Inter-service communication uses async events via Sidekiq / Redis pub-sub — no synchronous HTTP calls between the service and the monolith.
- The remaining ~95% of the codebase stays in the Rails monolith, preserving developer velocity and reducing cognitive overhead.
- We invest parallel effort in improving deployment automation (blue-green or canary) to increase our safe deploy frequency beyond 2/week.

---

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite

Re-architect the entire application into independently deployable services, each with its own database, technology stack chosen per-service, orchestrated by an API gateway.

**Rejected because:**

- **Cognitive cost scales super-linearly with team size.** For a 12-engineer team, tracking inter-service contracts, distributed tracing, eventual consistency, and deployment orchestration across 8-12 services adds a significant overhead tax on every feature. This is the well-documented Conway's Law trap.
- **Deploy pain persists after rewrite** unless you also build a robust deployment platform (service mesh, CI/CD pipelines per service, rolling update strategy). The tools cost is real. We'd spend 3-4 months building infrastructure before shipping our first business-facing service.
- **Data consistency becomes hard.** Every domain event that currently crosses a method boundary now requires sagas, compensating transactions, or outbox patterns. Bug surface area grows significantly.
- **The core issue — deploy frequency — is solvable without rewriting.** Blue-green or canary deployment for a monolith gets us to daily deploys without breaking the data layer.
- **Opportunity cost is enormous.** Those 3-4 months could ship real features or solve other scaling bottlenecks.

### Alternative 2: Extract Only Realtime Notifications (Chosen)

Pull the notifications module into its own thin service while leaving the rest of the monolith intact. Use async messaging for cross-cutting concerns.

**Accepted because:**

- **Addresses the actual scaling bottleneck.** Notifications are the only module with truly different resource profiles. Isolating it solves the over-provisioning problem.
- **Minimal blast radius.** Only one service boundary to design, test, and operate. The rest of the team continues working in familiar territory.
- **Proves the extraction pattern.** If we later need to split another module (say, billing or search), we already have the playbook.
- **Deploy pain improves incrementally.** Two deployments (monolith + notifications) vs twelve is still manageable for a 12-person team. We gain confidence before committing to more splits.
- **Low migration complexity.** Notifications is already loosely coupled internally. The extraction is mostly configuration and wiring, not re-architecture.

### Alternative 3: Big Ball of Mud — Stay Monolithic, Add Connection Pooling & Horizontal Scaling at App Tier

Keep everything in one Rails app, scale vertically (larger instances) and add horizontal app-tier scaling via load-balanced containers sharing the same database. Use connection pool tuning and read replicas for performance.

**Rejected because:**

- **Doesn't solve the notifications scaling problem.** Notification workers consume memory and CPU in the same process as API handlers. You can't scale them independently without over-provisioning the rest of the app unnecessarily.
- **Database connection pooling hits diminishing returns.** With many long-lived WebSocket connections from the notifications subsystem, pgbouncer or Heroku-style pooling struggles with connection exhaustion during traffic spikes.
- **Still capped at one deploy unit.** Doesn't address the root cause of deploy friction.

### Alternative 4: Modularize Within the Monolith Using Railways/Separeted Concerns Pattern

Use strong modular boundaries inside Rails (e.g., `app/modules/notifications`, engine isolation) without extracting to a separate process. Isolate the module through dependency injection and interface contracts.

**Rejected because:**

- **Helpful for code organization but does nothing for scaling.** All code still shares the same process, same resources, same deployment. The notifications module would still drag down the whole app under load.
- **Deploy frequency remains unchanged.** Still one artifact, one deploy window, one rollback scope.
- **Partial value.** Better code hygiene than doing nothing, but insufficient against the stated forcing factors.

---

## Consequences

### Positive

- **Targeted scaling works.** Notifications scale independently without wasting resources on unrelated request handling.
- **Team velocity preserved.** The 12 engineers work in one dominant codebase, avoiding the coordination tax of a full service sprawl.
- **Incremental learning path.** We validate our service-extraction instincts and tooling with low risk before splitting more modules.
- **Simpler operations.** Fewer running processes, fewer databases, fewer observability headaches than a full microservices architecture.
- **Easier debugging.** One trace ID crosses fewer network boundaries. No need for distributed tracing tooling yet.

### Negative

- **One hybrid boundary to manage.** We now maintain both monolith conventions and one service contract. The edge case is: what if the notifications service fails? The monolith must degrade gracefully.
- **Shared data access temptation.** There will be pressure to have the notifications service query the monolith's primary tables directly, which creates a coupling anti-pattern. This must be enforced rigorously.
- **Not a forever answer.** Eventually, further module extractions may require similar decisions. That's fine — each one should be evaluated when it arrives.
- **Deploy frequency won't reach "daily" overnight.** Two weekly deploys → two daily deploys (monolith + notifications) is progress but may still feel slow. We must pair this decision with CI/CD investment.

---

## Reversal Triggers

This decision stands until one or more of these conditions materializes:

1. **We attempt to extract a second or third module from the monolith and find the shared data layer or inconsistent APIs make clean extraction painful repeatedly**, indicating the underlying architectural debt warrants deeper re-evaluation.
2. **Our deploy frequency fails to improve above 5-7 deploys/week within 6 months of implementing blue-green/canary deployment**, suggesting the monolith itself has become too large or complex for effective deployment practices.
3. **A business requirement emerges that demands technology-specific optimization for a non-notification module** (e.g., a search module needing Elasticsearch-native indexing, or a payments module requiring Go/Fintech-grade concurrency patterns that Rails cannot provide).
4. **The team grows beyond 25 engineers**, where the communication overhead of maintaining a single codebase begins exceeding the benefits of shared context and rapid iteration.
5. **Observability data shows that >40% of production incidents are caused by the notifications service crashing dependent parts of the monolith**, despite isolation, indicating that the failure-domain boundary isn't sufficient.

Any of these conditions should trigger a new ADR evaluating a broader architectural shift.
