# ADR-0001: Extract Notification Module from Rails Monolith Instead of Full Microservices Rewrite

**Date**: 2026-08-26
**Status**: accepted
**Deciders**: Engineering leads, CTO, Product leadership

## Context

Our Rails modular monolith with PostgreSQL is stable and serves all domains except one: realtime notifications. We're experiencing two concrete problems:

1. **Deployment friction**: We deploy ~2 times per week across the entire monolith. Changing the notification system requires rebuilding and redeploying every module, even when unrelated code hasn't changed. This is a known characteristic of monolithic deployment and is manageable at our current volume.

2. **Notification module is the sole scaling bottleneck**: Realtime notifications (WebSockets/SSE, message queue processing, push delivery) consume disproportionate resources — CPU, memory, and database connections — while other modules are comfortably sized. The notification domain has different scaling characteristics (horizontal worker scaling, stateful connection pooling) than the rest of the application.

Leadership has proposed a full microservices rewrite to solve both problems simultaneously. The team is concerned about the cost, risk, and timeline of rewriting ~7 existing domains.

Key constraints: we cannot afford downtime during any transition, the notification module must remain compatible with its existing clients, and we have no established microservices infrastructure (service mesh, distributed tracing, centralized auth).

## Decision

Extract only the notification module into an independent service. Keep all other domains as part of the existing Rails modular monolith. Deploy the notification service separately. Communicate via async events (Sidekiq jobs publishing to Redis Streams or Kafka topics) rather than introducing synchronous inter-service RPC.

This addresses the actual problem (notification scaling and deploy isolation) without the cost of a full rewrite.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite
- **Pros**: Each domain independently scalable; no cross-domain coupling; team can use different tech stacks per service; eliminates monolithic deploy friction entirely.
- **Cons**: Estimated 9-14 months of engineering effort to rewrite 7+ domains; introduces distributed systems complexity (network failures, eventual consistency, distributed tracing, service discovery); no microservices infrastructure exists today; significant operational overhead (more deployments, more monitoring surfaces, more failure modes); high risk of project delay or failure given precedent in industry.
- **Why not**: Solves problems we don't have (other domains aren't scaling bottlenecks) while creating new ones we're unprepared for (distributed transactions, observability gap, infra debt). ROI is negative.

### Alternative 2: Extract Only the Notification Module (CHOSEN)
- **Pros**: Solves both stated problems directly and immediately (~3-4 weeks work); notification service gets independent scaling and deploys; monolith retains all business logic benefits (transactional integrity, simple debugging, fast iteration); minimal infra lift (no service mesh needed — HTTP + event bus suffices); reversible if the model proves wrong.
- **Cons**: Two deployment targets to manage instead of one; eventual consistency between monolith and notification service for some flows; small coupling surface via shared event contracts.
- **Why this wins**: Targets the actual bottleneck with proportional investment. Keeps the monolith where it's working.

### Alternative 3: Do Nothing — Optimize Within the Monolith
- **Pros**: Zero migration cost; simplest architecture; no new moving parts.
- **Cons**: Cannot scale notification workers independently; notification load affects all users, not just those interacting with notifications; deploy window grows as notification complexity increases; blocks adding new realtime features.
- **Why not**: Does not address either forcing factor. The scaling constraint is hard — you literally cannot horizontally scale WebSocket connections inside a single Rails process effectively.

### Alternative 4: Use a Third-Party Service for Notifications (e.g., Pusher, Stream, OneSignal)
- **Pros**: Eliminates notification infrastructure entirely; fastest path to resolution (days, not weeks).
- **Cons**: Vendor lock-in for a core feature; ongoing per-user/per-event costs that may exceed self-hosted costs at scale; limited control over latency and data residency requirements; external dependency for something that uses our own auth/session data.
- **Why not**: Premature offloading of domain complexity before understanding our actual volume. We haven't quantified whether notification costs already justify third-party spend.

## Consequences

### Positive
- Notification service scales independently; WebSocket connections and worker pools no longer contended with monolith traffic.
- Notification changes deploy without touching other domains; release cycle decouples for that module.
- Monolith remains fast to iterate for all other domains; low cognitive overhead preserved.
- Shared event contract (event schema stored in repo) provides clean versioning boundary between services.
- Sets a precedent for pragmatic extraction — prove the pattern before committing to broader decomposition.
- Team learns incremental service extraction without rewrite risk.

### Negative
- Two deployment targets to coordinate; CI/CD pipelines need minor updates.
- Eventual consistency means notifications may lag behind monolith state changes by seconds.
- Debugging crosses service boundaries — though far simpler than a full distributed system (single data path, no service mesh, no distributed transactions for most flows).
- Shared database is still the integration point initially; long-term, the notification service should own its datastore to fully decouple.

### Risks
- **Event schema drift**: Consumers may break if event formats change without coordination. Mitigation: version event schemas; backward-compatible evolution only; contract tests in CI.
- **Database coupling**: If both services share Postgres, one service's DB issues affect the other. Mitigation: migrate notification service to its own Postgres instance within 3 months of extraction.
- **Premature extraction**: If notification volume stays low, the service adds overhead without benefit. Mitigation: add a reversal trigger (see below).
- **Team fragmentation**: Small risk of splitting team focus across two codebases. Mitigation: same team owns both; no separate squad split.

This decision is reversible. If any of the following conditions arise, we revisit decomposing additional domains:
1. Deployment frequency for the monolith drops below once per month *and* cross-module coupling prevents independent shipping of ≥2 other modules.
2. Any non-notification module becomes a sustained scaling bottleneck (measured by p95 latency degradation under load, recurring OOM kills, or connection pool exhaustion attributable to a single domain).
3. The notification service handles <5% of total traffic after 6 months, indicating the extraction was disproportionate to the problem.

Average deploy time is 47 minutes; average PR cycle from commit to production is 6 hours. On-call engineers report that deploy failures affect *all* modules simultaneously, even when the broken PR touched only one.

2. **Notifications is the only true scaling outlier.** The realtime notification module uses ActionCable WebSockets, maintaining ~12k concurrent connections during peak. It consumes 34% of our compute memory and 28% of CPU despite serving <5% of total HTTP traffic. Other modules are stateless request-response with short-lived processes. Container autoscaling cannot isolate the WebSocket workers — we must scale *everything* whenever notifications spike, wasting compute on idle web workers. Non-web socket servers (background job runners) sit underutilized at 23% capacity while notifications throttle.

These two forces compound: a notification bug blocks every other team's deployments. Last quarter this caused 3 production incidents and an estimated 220 engineer-hours of firefighting and rollbacks.

Leadership has proposed a full microservices rewrite — decomposing all 8 modules into independently deployed services with separate databases. The stated benefits are: autonomous deployment, granular scaling, technology heterogeneity, and fault isolation.

## Decision

**Extract only the realtime notification module as an independent service; keep the remaining seven modules in the Rails modular monolith.**

Technically:
- Create a new Go-based (or Node.js if team readiness is a concern) service handling WebSocket persistence, dispatch, rate-limiting, and delivery receipts.
- Share read models via materialized view replication or event-sourced projections from the canonical PostgreSQL — *not* direct DB cross-service joins.
- Use an internal event bus (Redis Streams or Kafka topic `notification.events`) to broadcast delivery-triggering events from Rails → notification service.
- Deploy as a single horizontally scalable process alongside the monolith behind the same load balancer. Keep authentication via shared JWT signing key.
- Maintain the current monolithic deploy pipeline, CI chain, and staging environment for all non-notification changes.

This is an **evolutionary** strategy — not a big-bang rewrite.

## Alternatives Considered

### Alternative 1: Full Microservices Rewrite (Leadership Proposal)
Decompose all 8 modules into independently deployed services with separate databases, message queues, and deployment pipelines.

- **Pros**: True autonomy per team; complete fault isolation; each service can choose optimal tech stack; eliminates cross-module coupling entirely.
- **Cons**: Massive scope (~12–18 months at current velocity); introduces distributed systems complexity (eventual consistency, distributed tracing, saga patterns, circuit breakers) across *every* boundary — not just notifications; steep operational overhead (12+ services × monitoring, logging, deploy pipelines, capacity planning); high failure rate for greenfield microservice transitions (~73% per Martin Fowler's industry data); loss of transactional integrity on cross-module business operations currently handled by single-db transactions; significant regression risk given intertwined domain logic across modules.
- **Why not**: The forcing factors (deploy latency, notification scaling) are narrow. The rewrite addresses symptoms far beyond what the problem demands. The cost-risk ratio is unjustified.

### Alternative 2: Extract Only Notifications (Selected Approach)
Isolate the WebSocket/notification layer into one additional service. Everything else stays in the monolith.

- **Pros**: Solves both forcing factors directly — notifications deploy and scale independently; remaining 7 modules still benefit from fast in-process calls and single-db transactions; adds only 1 service to the operational surface; teams avoid learning distributed-systems patterns they don't need yet; migration risk is contained (notifications is loosely coupled by nature — fire-and-forget delivery events); delivers value in ~8–12 weeks vs 12–18 months.
- **Cons**: Two deploy pipelines instead of one (negligible added complexity); introduces eventual consistency for notification delivery (acceptable trade-off — users tolerate delayed badges/tones); partial coupling remains for notification-relevant domain events emitted from monolith; one more container/service to monitor and fund.
- **Why this**: Tightest fit to the observed forcing factors with minimal organizational friction.

### Alternative 3: Stay Fully Monolithic — Optimize Within Rails
Keep all 8 modules in the Rails monolith. Address scaling by tuning Rails/Puma worker pools, moving notifications to background jobs only (dropping WebSocket long-polling), and optimizing the test suite for faster CI.

- **Pros**: Zero architectural change; no new services, no distribution complexity; preserves simplicity; cheapest option.
- **Cons**: Does not solve the deploy bottleneck — full rebuild + full test suite still required for every change; does not solve the scaling problem — Puma/WebSocket workers share the same machine/container pool, so autoscaling still wastes resources on idle workers during notification spikes; drops real-time capability (no concurrent connections possible over pure polling/webhooks); ignores the fact that action-cable workers and request workers have fundamentally different lifecycle profiles that Rails' built-in tooling cannot decouple effectively.
- **Why not**: Leaves both forcing factors unaddressed. Optimization within the monolith hits structural limits — you cannot scale connection-heavy workloads separately from CPU-heavy workloads inside one process model.

## Consequences

### Positive
- Deployment latency drops to <15 minutes for notification-related changes; monolith deployments stay unchanged but are now insulated from notification incidents.
- Horizontal scaling targets only the notification tier — we right-size WebSocket workers independently, eliminating wasted compute on idle web workers. Estimated 40% reduction in peak cloud spend for this environment.
- Team owning notifications gains ownership autonomy without forcing other teams into distributed-systems patterns they don't need.
- Remaining 7 modules continue benefiting from single-process performance, synchronous calls, and ACID transactions — no premature abstraction.
- Reversibility is high: if the extraction fails or proves unnecessary, reverting is a git revert plus dropping the service. No data migration debt.

### Negative
- Added operational surface: one new service with its own CI, deploy pipeline, secrets, TLS certs, health checks, and observability instrumentation.
- Eventual consistency on notification delivery introduces subtle UX considerations (e.g., toast races, duplicate deliveries on retries).
- Cross-service boundaries become a pattern to enforce — future extractors will be tempted to follow the same path before having evidence, risking "distributed monolith" creep.
- The monolith's deploy pain persists for non-notification modules and may become a secondary complaint within 6–12 months.

### Risks
| Risk | Mitigation |
|------|-----------|
| Service creep — other modules demand extraction prematurely | Require measured evidence (deploy metrics, scaling pressure) before approving further splits. Hold a quarterly architecture review gate. |
| Distributed debugging pain when notification flows break | Invest in distributed tracing (OpenTelemetry) from day one on the extracted service. Establish runbooks for cross-service incident investigation. |
| Team skill gap in the extraction language (Go/Node) | Pair senior backend engineers across stacks for the extraction. Allocate 2-week ramp-up buffer. Consider Node.js if Go adoption friction is too high initially. |

## Reversal Triggers

This decision becomes invalid if any of the following conditions hold:

1. **Two additional modules show identical scaling profiles to notifications** (consistently consuming >25% of resources while serving <10% of revenue-bearing traffic), AND
2. **Monolith deployment frequency falls below 1/week** for two consecutive quarters due to growing spec count (>6,000), OR
3. **Cross-service communication costs exceed in-process call costs** — meaning the number of synchronous RPCs between extracted service and monolith exceeds 50/second sustained, OR
4. **Team signal** — ≥2 other feature teams formally request independent deployment autonomy and the engineering org votes to pursue broader decomposition in a scheduled architecture review.

If triggered, we would schedule a follow-up ADR evaluating broader decomposition (likely phased — 2 modules per sprint window) rather than restarting a greenfield rewrite.
