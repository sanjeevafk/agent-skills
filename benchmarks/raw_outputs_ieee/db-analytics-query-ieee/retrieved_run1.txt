## 1. Reconstructed Query

Based on the symptoms described, here's the likely original query:

```sql
WITH ranked_events AS (
    SELECT 
        e.*,
        RANK() OVER (
            PARTITION BY e.tenant_id, e.event_type 
            ORDER BY e.created_at DESC
        ) as rk
    FROM events e
    WHERE e.tenant_id = 'acme-corp'
      AND e.event_type = 'page_view'
      AND e.created_at BETWEEN '2024-06-01' AND '2024-07-01'
)
SELECT 
    re.*,
    u.name,
    u.email
FROM ranked_events re
JOIN users u ON u.id = re.user_id
WHERE re.rk <= 100
ORDER BY re.created_at DESC;
```

## 3. Node-by-Node Diagnosis

### 🔴 Node 1: Seq Scan on events (rows=800M, planning_rows=100)

**What happened:** The planner scanned every row of the 800M-row table, filtering down to 2M after applying three predicates.

**Why it happened:** No index exists whose leading column matches `tenant_id`. The planner also got completely wrong cardinality—it estimated 100 rows would match, but 2M actually did (off by factor of 20,000×).

**Root causes:**
- Missing composite index on `(tenant_id, event_type, created_at)`
- Stale/hot `pg_stats`: histograms haven't been updated since the last ANALYZE, which for a table growing at millions of rows/day means yesterday's stats tell today's planner lies

**Cost to fix:** A single `CREATE INDEX CONCURRENTLY` eliminates this entirely—the same operation becomes an Index Scan/Bitmap Index Scan that touches only the relevant leaf pages.

---

### 🔴 Node 2: WindowAgg (rows=2M processed)

**What happened:** `RANK()` was computed for all 2M matched rows, even though only 100 would survive the final filter.

**Why it happened:** The CTE `ranked_events` caused the optimizer to **materialize** the entire CTE result before applying `WHERE rk <= 100`. Pre-PG16, all CTEs were implicitly materialized regardless of cost. The window function had no choice but to rank every row first.

**Fix:**
1. Use an unmaterialized CTE (PG16 default for non-recursive, non-aggregate CTEs can be inlined)
2. Or restructure as a plain derived subquery where the planner *can* push the filter down past the window function in certain patterns
3. Better yet: apply the index ordering to reduce the volume entering the window function so dramatically that ranking fewer rows is cheap

---

### 🔴 Node 3: Sort → External Merge (disk spill)

**What happened:** The sort required 384 MB of temp files because `work_mem` (default 4 MB) was far too small for sorting 2M wide rows.

**Why it happened:**
- `work_mem = 4MB` is the default—adequate for queries returning hundreds/thousands of rows, but catastrophically undersized for intermediate sorts of millions of rows
- The sort spilled to disk as `external merge`, making it orders of magnitude slower than an in-memory sort

**Fix (two layers):**
1. **Short-term:** Set `work_mem = 256MB` or higher for this session/connection:
   ```sql
   SET LOCAL work_mem = '256MB';
   ```
   But beware: `work_mem` allocates per-sort, per-hash-per-query. High values under concurrency cause OOM.
   
2. **Long-term:** Remove the sort entirely. An index ordered by `created_at DESC` serves the sort positionally—zero sort cost. This is why index column order matters (covered next).

---

### 🟡 Node 4: Planner Estimate (expected 100, got 2M)

**What happened:** `pg_statistic` said predicate selectivity implied 100 rows from 800M total, but 2M actually matched—a 20,000× discrepancy.

**Root causes:**
- **Histogram saturation:** By default, PG stores 100 histogram buckets. If `tenant_id` is heavily skewed (say one tenant owns 80% of traffic), bucket sampling misrepresents tail distributions
- **Autovacuum analyze threshold:** Default `autovacuum_analyze_scale_factor = 0.1` means PG waits until 80M rows change before re-analyzing. For active tables this means stats are weeks old
- **No explicit stat targets:** Default target of 100 stat entries per column is low for highly selective columns

**Fix hierarchy:**

```sql
-- Layer 1: Immediate fix
ANALYZE events;
ANALYZE users;

-- Layer 2: Higher precision for skewed columns
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;
ALTER TABLE events ALTER COLUMN event_type SET STATISTICS 1000;
ANALYZE events;

-- Layer 3: More aggressive autoanalyze for high-churn table
ALTER TABLE events 
  SET (autovacuum_analyze_scale_factor = 0.01,
       autovacuum_analyze_threshold = 50000);
```

With 800M rows: `0.01 × 800M = 8M` — analyze triggers after just 8M new rows instead of 80M. Stats stay fresh enough for accurate estimates.

## 4. Index Strategy: Why Column Order Matters

### The Rule: Equality First, Range Last

```
WHERE col_a = $eq    ← equality predicate
  AND col_b = $eq    ← equality predicate  
  AND col_c >= $gte  ← range predicate  (goes LAST)
```

**Why?** A B-tree index is a sorted structure. Once you enter the leaf level for `col_a = X`, you can drill into `col_b = Y`. But once you hit `col_c > start_date`, the rest of the index contains values greater than the start date including those outside your desired range—you must scan forward until the end boundary. That's how range predicates work in any B-tree index.

If you put the range column first (`(created_at, tenant_id, event_type)`), you'd lose the ability to efficiently narrow by tenant_id *within* the date range, because different dates branch into different subtrees.

### Recommended Index

```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_created
ON events (tenant_id, event_type, created_at DESC);
```

| Predicate Type | Index Columns Used | Why |
|---|---|---|
| `tenant_id = $1` | ✅ Leading column | Exact match jumps straight to correct subtree |
| `event_type = $2` | ✅ Second column | Narrows further within tenant subtree |
| `created_at BETWEEN $3 AND $4` | ✅ Third column, DESC | Sequential scan through leaves in reverse timestamp order |
| `ORDER BY created_at DESC` | ✅ Already sorted | **Zero sort cost** — index traversal provides the sort order natively |

### Estimated Size

```sql
SELECT pg_size_pretty(pg_total_relation_size('idx_events_tenant_type_created'));
-- Likely: ~30–50 GB for 800M rows depending on tuple width
-- Acceptable trade-off vs. 40s seq scan
```

### Partial Index (When It Helps)

```sql
CREATE INDEX CONCURRENTLY idx_events_hot_tenants
ON events (tenant_id, event_type, created_at DESC)
WHERE tenant_id IN ('acme-corp', 'globex', 'initech');
```

**Use only if:** Every query filters on a known small set of tenants, AND those tenants represent <20% of total rows. The savings are proportional to the excluded fraction—but partial indexes complicate query planning and increase maintenance overhead. Generally avoid unless profiling proves necessary.

### Covering Index (Usually Not Worth It Here)

```sql
CREATE INDEX CONCURRENTLY idx_events_covering
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, event_data, status, request_id);
```

**Pros:** Eliminates heap fetches entirely for covered columns.
**Cons:** Index balloons proportionally—could become 80–100GB+. Each insert/update must update the index. Maintenance costs multiply.

**Verdict:** Only add INCLUDE if you've confirmed via `EXPLAIN ANALYZE` that heap fetches are significant (check `Heap Fetches` count in bitmap heap scan). Most of the time, the composite index alone reduces the scan to so few rows that heap lookups are negligible.

## 5. Partitioning Decision Framework

### Should You Partition by Month?

**Partitioning is justified IF all of these are true:**

| Criteria | Status | Impact |
|---|---|---|
| Queries always filter on `created_at >= X` | ✅ Yes | Prefix matches partition key → partition pruning works |
| Old data is dropped/archived regularly | Maybe | `DROP PARTITION` beats `DELETE/VACUUM` for TB-scale deletions |
| Write throughput needs isolation | Sometimes | New partition gets its own WAL buffer temporarily |
| You need multi-month scans frequently | ❌ No | Pruning only prunes **non-matching** months; scanning across many partitions defeats the benefit |
| Current index can solve the problem | ⚠️ Borderline | A good composite index often makes partitioning unnecessary |

**My recommendation:** Skip partitioning for now. Build the composite index + fix statistics + tune `work_mem`. Measure. Only partition if:

1. You're doing regular bulk deletes of data older than 6–12 months (partition-level `DROP` is instant vs. `DELETE` generating massive WAL)
2. After index optimization, queries spanning quarters still exceed acceptable latency
3. Table maintenance (VACUUM FULL, CLUSTER) is causing operational issues

**If you DO partition later**, it's additive—indexes inherit. The composite index above works identically on partitioned tables in PG 15+:

```sql
-- Partitioned table (add later if needed)
ALTER TABLE events DETACH PARTITION events_2024_01;
DROP TABLE events_2024_01;  -- Instant vs. DELETE

-- Same composite index works across partitions automatically
CREATE INDEX ON events (tenant_id, event_type, created_at DESC);
-- Creates one index per partition in PG 15+
```

## 6. Query Rewrite Options

### Option A: Simplest — Inline Subquery (Recommended for PG 16)

PostgreSQL 16 changed CTE materialization: non-recursive, non-aggregate CTEs are **not** automatically materialized. The planner can push down filters. An inline subquery achieves the same effect:

```sql
SELECT 
    ranked.user_id,
    ranked.event_type,
    ranked.created_at,
    ranked.event_data,
    u.name,
    u.email
FROM (
    SELECT 
        e.user_id,
        e.event_type,
        e.created_at,
        e.event_data,
        ROW_NUMBER() OVER (
            PARTITION BY e.tenant_id, e.event_type 
            ORDER BY e.created_at DESC
        ) as rn
    FROM events e
    WHERE e.tenant_id = $1
      AND e.event_type = $2
      AND e.created_at >= $3
      AND e.created_at < $4
) ranked
JOIN users u ON u.id = ranked.user_id
WHERE ranked.rn <= 100
ORDER BY ranked.created_at DESC;
```

**Key changes:**
- `ROW_NUMBER()` instead of `RANK()` — `RANK()` ties produce duplicate rows; `ROW_NUMBER()` gives strict top-N per group
- Removed `BETWEEN` in favor of `>= / <` — avoids inclusive-end confusion with timestamps that have microsecond precision
- CTE removed entirely → planner can push `rn <= 100` predicate toward the window function, potentially limiting input

**Expected improvement:** Index scan replaces seq scan (orders of magnitude faster), sort eliminated (index provides ordering), minimal intermediate result size (well-bounded by LIMIT before window agg).

---

### Option B: Two-Phase Approach (When Result Set Still Large Before Ranking)

If even with the index, 500K+ rows match the time range, ranking all of them is wasteful. Two-phase limits the ranking set:

```sql
-- Phase 1: Pull top candidate rows using index-sorted scan (cheap, bounded)
-- Phase 2: Rank within that subset (small set = fast window agg)

WITH candidates AS (
    -- Index scan with LIMIT caps the dataset before ranking
    SELECT 
        e.user_id,
        e.event_type,
        e.created_at,
        e.event_data
    FROM events e
    WHERE e.tenant_id = $1
      AND e.event_type = $2
      AND e.created_at >= $3
      AND e.created_at < $4
    ORDER BY e.created_at DESC
    LIMIT 10000  -- Heuristic: grab generous buffer above final N
),
ranked AS (
    SELECT 
        c.*,
        ROW_NUMBER() OVER (
            PARTITION BY event_type 
            ORDER BY created_at DESC
        ) as rn
    FROM candidates c
)
SELECT 
    r.user_id,
    r.event_type,
    r.created_at,
    r.event_data,
    u.name,
    u.email
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 100;
```

**Trade-off:** Slight correctness risk—if there are >10,000 events per type within the time range, you miss rows beyond the buffer. Tuning LIMIT to account for expected variance per type is necessary. Only use when you've verified the index scan still returns too many rows post-index.

---

### Option C: MATERIALIZED CTE (When Plan Gets Regressed)

If PG 16's automatic inlining produces a worse plan (sometimes happens with complex joins), force materialization:

```sql
WITH ranked AS MATERIALIZED (
    SELECT 
        e.user_id,
        e.event_type,
        e.created_at,
        e.event_data,
        ROW_NUMBER() OVER (
            PARTITION BY e.tenant_id, e.event_type 
            ORDER BY e.created_at DESC
        ) as rn
    FROM events e
    WHERE e.tenant_id = $1
      AND e.event_type = $2
      AND e.created_at >= $3
      AND e.created_at < $4
)
SELECT 
    r.user_id,
    r.event_type,
    r.created_at,
    r.event_data,
    u.name,
    u.email
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 100
ORDER BY r.created_at DESC;
```

**When `MATERIALIZED` helps:** When the base result set is small enough to materialize cheaply (say <50K rows) but the optimizer's attempt to "push down" the rank filter causes redundant re-evaluation of the window function across multiple joins. `MATERIALIZED` is an override when the planner's choices are suboptimal.

**When NOT to use it:** If the filtered set exceeds millions of rows—materialization becomes the bottleneck itself. Test both versions.
