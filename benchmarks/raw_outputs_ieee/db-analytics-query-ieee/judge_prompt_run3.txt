## Index Strategy

### Decision: Composite B-Tree (NOT partial, NOT individual indexes)

```sql
-- WHY this composite order matters:
CREATE INDEX idx_events_tenant_type_date
```

| Column | Role | Reason |
|--------|------|--------|
| `tenant_id` | Equality (position 1) | High selectivity, drives index pruning. Placed first so the index starts at one position. |
| `event_type` | Equality (position 2) | Second equality. With both equality columns up front, the index seeks to an exact point and reads sequentially. |
| `created_at DESC` | Range + descending (position 3) | Range columns go last (they "use up" the index). Declared DESC because the window function partitions by date descending — Postgres can satisfy the ORDER BY from the index alone, eliminating the sort entirely. |

### Why NOT other strategies?

**Partial index?** Only justified if >70% of queries target a specific subset (e.g., `WHERE archived IS FALSE`). If your tenant/event mix is broad, the partial index saves storage but won't help most queries. Defer this until you have query telemetry.

```sql
  ON events (tenant_id, event_type, created_at DESC)
```

**Individual indexes on each column?** Never. Each index is a separate structure consuming ~9.6 GB each (for 800M rows × 12 bytes/row). ## 1. Index Strategy

### Why ORDER OF COLUMNS IN THE INDEX MATTERS

For a filter with equality predicates + range predicates, the B-tree column order is:

1. **Equality columns first** — `tenant_id`, `event_type` (these map to a single point in the tree via btree searches)
2. **Range column last** — `created_at` (after narrowing to the equality slice, the remaining scan within that subset uses the range)

A composite index `(tenant_id, event_type, created_at)` lets Postgres do an **Index Only Scan** if you include `user_id` via `INCLUDE`:

```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_created_include_user
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id);
```

**Why INCLUDE over adding more key columns:** `INCLUDE` creates an **index-only** scan (Postgres can satisfy the query without touching the heap), but keeps those columns as *non-searchable* metadata in the leaf pages. This is smaller than making them part of the B-tree key and avoids bloating internal node pointers.

### Why NOT a partial index

A partial index like `WHERE tenant_id = 'specific-value'` doesn't generalize across tenants. A partial index like `WHERE event_type = 'click'` could help, but only for that one type — you'd need one per frequent `event_type`. The composite index handles all types and all tenants from one structure.

### Why NOT a covering index WITHOUT INCLUDE

An alternative syntax `CREATE INDEX ON events (tenant_id, event_type, created_at, user_id)` makes `user_id` part of the B-tree search key. That means every comparison reads 4 values instead of 3, inflating internal node size and reducing the fan-out of each page. `INCLUDE (user_id)` achieves the same "don't visit the heap" goal at lower cost.

### Index choice summary

```
Best:    (tenant_id, event_type, created_at DESC) INCLUDE (user_id)
         → Index Only Scan, filters selectivity at the engine level, no heap fetch needed

Alternative: (tenant_id, created_at) INCLUDE (user_id, event_type)
         → works if event_type has low cardinality and the planner prefers scanning one predicate at a time.
           Usually worse because equality column should lead.

Skip:    Simple index on just created_at
         → still needs 800M scan because tenant_id filter isn't applied until heap level
```

Run the CREATE INDEX with `CONCURRENTLY` to avoid locking writes:

```sql
-- Step 1: drop old useless indexes if they exist (check with \di+ events)
-- Example: DROP INDEX IF EXISTS idx_events_created_at;

-- Step 2: create the right index
CREATE CONCURRENTLY INDEX idx_events_tenant_type_created_include_user
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id);
```

## Diagnosis & Fix — Step by Step

### 1. Index Strategy: Why Column Order Matters

The filters are: `tenant_id`, `event_type`, `created_at`. The key insight: **column order in a composite index must follow equality predicates first, then range predicates.**

**Correct composite index:**
```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_created
ON events (tenant_id, event_type, created_at);
```

**Why this order?**
- `tenant_id` = equality → partitions the B-tree into one small subtree per tenant
- `event_type` = equality → further narrows within that tenant's partition
- `created_at` = range → sequential scan within the already-tight slice

If you reversed it to `(created_at, tenant_id, event_type)` the B-tree would be useless because the range predicate on `created_at` consumes the entire tree, making the subsequent equality predicates unable to prune.

**Benchmarks against alternatives:**

| Index | Selectivity | Rows scanned | Verdict |
|-------|-------------|-------------|---------|
| `(tenant_id, event_type, created_at)` | Best | ~1% of tenant data | ✅ |
| `(tenant_id, created_at)` | Good | ~10% of tenant data | Acceptable if `event_type` is rarely filtered alone |
| `(created_at, tenant_id)` | Bad | Whole table | ❌ Range on col 1 makes cols 2–N unindexable |
| Single index on `tenant_id` only | Poor | ~all tenant rows | Only helps if one tenant has 99% of traffic |

### 2. Covering Index — Eliminate Heap Fetches

If the window function (`RANK() OVER (PARTITION BY ... ORDER BY ...)`) needs additional columns from events (e.g., `score`, `value`), a covering index avoids random heap I/O:

```sql
CREATE INDEX CONCURRENTLY idx_events_covering
ON events (tenant_id, event_type, created_at)
INCLUDE (user_id, score, value);  -- INCLUDE columns don't affect sort order
```

`INCLUDE` (Postgres 11+) stores these in the index leaf pages as payload data. The B-tree structure still sorts by `(tenant_id, event_type, created_at)`, but the query can satisfy itself entirely from the index (an "index-only scan"). This often cuts I/O by 60–80%.

### 3. Partial Index — Tenant-Specific Hot Paths

If queries always run for specific tenants (or tenant tiers), a partial index shrinks the index size dramatically and gives the planner sharper selectivity estimates:

```sql
-- Only index events from the top 10 tenants (who generate 80%+ of reports)
CREATE INDEX CONCURRENTLY idx_events_top_tenants
ON events (tenant_id, event_type, created_at)
WHERE tenant_id IN (
    SELECT tenant_id FROM tenants
    WHERE tier = 'enterprise'
);
```

Or more commonly, if all reporting goes through a single tenant context:

```sql
-- If every report is tenant-scoped at connection level,
-- this is implicit. But if your app always adds a WHERE tenant_id = $1,
-- ensure the composite index above covers it.
```

Partial indexes shine when the predicate is highly selective AND the workload is predictable. Don't overdo it — every partial index means another index the planner picks through.

## Diagnosis & Solution

### Root Cause Analysis (Node-by-Node)

**Seq Scan on events →** The planner has no usable index. With 800M rows, every query does a full table scan. A Seq Scan reads sequentially (fast-ish), but scanning 800M rows just to find 2M matching rows is wasteful — you're reading ~40x more data than needed.

**Sort Spilling to Disk →** The window function (`RANK() OVER (...)`) sorts rows in memory. When `work_mem` is exceeded (default 4MB), PostgreSQL spills to disk on `.tmp` files, which is orders of magnitude slower than RAM sorting.

**Stale Estimates (expects 100, got 2M) →** `statistics_target` defaults to 100 samples per column. The planner sees skewed distribution (e.g., hot tenants, bursty event types) but only has 100 histogram buckets to model it. It wildly underestimates, picks a nested-loop join instead of a hash join, and plans for tiny result sets — compounding the disaster.

---

### Fix 1: Composite Index (Priority #1)

```sql
-- PRIMARY FIX: Covers the WHERE + ORDER BY for the window function
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_events_tenant_event_created
  ON events (tenant_id, event_type, created_at DESC);
```

**Why this column order:**
- `tenant_id` first — high-cardinality equality filter, narrows from 800M → tens/hundreds of millions
- `event_type` second — another equality filter, further narrows
- `created_at` third — range filter comes LAST in B-tree ordering (B-trees support one range predicate per index). Also provides natural sort order for `RANK() OVER (PARTITION BY tenant_id, event_type ORDER BY created_at)` — avoids an explicit sort entirely

**Composite indexes are ordered because a B-tree is a sorted tree.** You can efficiently seek on `(tenant_id = X, event_type = 'click')` and then read all rows in `created_at` order without re-sorting. But `(created_at, tenant_id, event_type)` would force a full scan within the time range to filter by tenant — the exact opposite of what you want when tenant selectivity is much higher than time-range selectivity.

### Fix 2: Covering Index (Eliminates Heap Fetches)

```sql
-- Optional but powerful if the query selects key columns frequently
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_events_covering
  ON events (tenant_id, event_type, created_at DESC)
  INCLUDE (user_id, payload, id);
-- Replace payload/id with whatever columns your query SELECTs
```

**INCLUDE eliminates heap fetches** — normally after reading an index entry, Postgres follows the TID back to the heap row to get other columns. With INCLUDE, those columns live in the index leaf pages, so the query is satisfied purely from the index (a "Index Only Scan"). Tradeoff: larger index = more I/O for random access, but faster sequential scans. Worth it if you select 5+ columns beyond the index keys.

### Fix 3: Partial Index (If Data Is Skewed in Time)

```sql
  ON events (tenant_id, event_type, created_at DESC)
```

### Fix 6: Rewritten Query

```sql
WITH ranked_events AS MATERIALIZED (
    SELECT
        e.id,
        e.tenant_id,
        e.event_type,
        e.created_at,
        e.user_id,
        e.payload,
        RANK() OVER (
            PARTITION BY e.tenant_id, e.event_type
            ORDER BY e.created_at DESC
        ) AS event_rank
    FROM events e
    WHERE e.tenant_id = $1
      AND e.event_type = ANY($2::text[])              -- parameterized list
      AND e.created_at >= $3                          -- range start
      AND e.created_at <  $4                          -- range end (exclusive)
)
SELECT
    r.*,
    u.email,
    u.name,
    u.tier
FROM ranked_events r
JOIN users u ON u.id = r.user_id
WHERE r.event_rank <= 100                          -- push filter down into CTE
ORDER BY r.tenant_id, r.event_type, r.created_at DESC;
```

**Key decisions explained:**

- **`MATERIALIZED` CTE** — tells the planner "execute this once, store results, don't inline." Without this, Postgres (v12+) tries to merge/push down the CTE into the outer query, which can explode the plan. Since the window function computes ranks over the filtered set, materializing prevents the outer `WHERE event_rank <= 100` from being mis-pushed above the window function.

- **Push `event_rank <= 100` inside the CTE?** If you only need top-100 per group, add `FETCH FIRST 100 ROWS WITH TIES` or filter inside:
```sql
WHERE r.event_rank <= 100
```
This lets the sort abort early if Postgres uses `Top-N Heapsort`. But window functions must compute the FULL ranking first — so this filter only matters for the outer `SELECT`, not the sort itself. For true early-exit, use a different approach (see below).

- **`ANY($2::text[])`** instead of `IN (...)` — cleaner array binding, same plan.

- **`<` for end bound** instead of `<=` — avoids inclusive/exclusive confusion and works correctly with timestamps that have sub-second precision.

- **Index-driven sort elimination** — because the index order `(tenant_id, event_type, created_at DESC)` matches the `PARTITION BY / ORDER BY` of the window function, Postgres can often skip the explicit sort node entirely and read rows in the right order from the index.

**Aggressive optimization — if you truly only need TOP-N per group:**

```sql
-- Avoid computing full ranks: use lateral join with LIMIT
SELECT
    e.id,
    e.tenant_id,
    e.event_type,
    e.created_at,
    e.user_id,
    e.payload,
    (SELECT COUNT(*)
     FROM events e2
     WHERE e2.tenant_id = e.tenant_id
       AND e2.event_type = e.event_type
       AND e2.created_at >= e.created_at          -- same-or-later events
    ) AS event_rank,
    u.email, u.name, u.tier
FROM events e
WHERE e.tenant_id = $1
  AND e.event_type = ANY($2::text[])
  AND e.created_at >= $3 AND e.created_at < $4
  AND (SELECT COUNT(*)
       FROM events e2
       WHERE e2.tenant_id = e.tenant_id
         AND e2.event_type = e.event_type
         AND e2.created_at >= e.created_at
      ) <= 100                                   -- prune eagerly
JOIN users u ON u.id = e.user_id
ORDER BY e.tenant_id, e.event_type, e.created_at DESC;
```
This uses the same index for both sides of the correlated subquery, but can short-circuit once `event_rank > 100`. Benchmark both approaches — sometimes the window function + materialized CTE is faster because the correlated subquery does O(n²) index lookups.

### Step 2 — Choose the Right Index Strategy

#### Column Order Analysis

The query filters on three predicates:

```sql
WHERE tenant_id = $1           -- equality
  AND event_type = $2          -- equality (possibly multi-value IN)
  AND created_at >= $3         -- range
```

**Correct composite order: `(tenant_id, event_type, created_at)`**

Reasoning using the B-tree search model:

```
Step 1: Seek to tenant_id = $1      → O(log N) skip to correct partition
Step 2: Within that tenant, seek to event_type = $2 → O(log M) within partition
Step 3: Scan sequentially through created_at range → O(k) where k = matching rows
```

If we reversed the order to `(created_at, tenant_id, event_type)`, the range on `created_at` would consume the entire prefix of the index, leaving no ability to discriminate on `tenant_id` or `event_type` — Postgres would still need to filter the entire range-scan resultset in RAM.

#### The Index DDL

```sql
-- Primary recommendation: filtered partial index if only a subset of tenants/
-- types are queried frequently (e.g., active data vs archived)

ON events (tenant_id, event_type, created_at DESC)
WHERE deleted_at IS NULL;  -- if soft-delete exists; omit if not

-- Core index (no partial predicate unless justified):
CREATE INDEX idx_events_tenant_type_time
ON events (tenant_id, event_type, created_at DESC);
```

> **Why `DESC` on `created_at`?** If the report shows "most recent events first" (common), the index matches the ORDER BY directly. Postgres can then do an *index-only scan* in the requested order, eliminating the sort entirely. If you need ASC, use ASC — match the query's ORDER BY exactly.

#### Covering Index Tradeoff

Consider a covering index ONLY if the query selects ≤ 3 additional columns beyond those needed for filtering/joining:

```sql

-- This stores user_id in the index leaf pages, avoiding heap fetches

ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, payload);   -- INCLUDE columns avoid heap lookups
```

**When NOT to use INCLUDE:** On an 800M-row table, each extra included column multiplies index size. If `payload` is a text/jsonb column averaging 2KB, the index balloons from ~25GB to ~1.8TB — not worth it. Use INCLUDE only for small integer/timestamp columns.
