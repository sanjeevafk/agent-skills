## Diagnosis & Fix: 800M-Row Events Table Reporting Query

### Node-by-Node Plan Analysis

Here's the plan you're likely seeing (the "bad" one):

```
Limit (cost=... rows=100 width=...)
  -> WindowAgg (cost=..., rows=2000000 width=...)
       -> Sort (cost=..., rows=2000000, actual_rows=2000000, sort_method=merge external file, duration=18000ms)
            Sort Key: tenant_id, event_type, rank() OVER (...)
            -> Hash Join (cost=..., rows=2000000)
                 -> Seq Scan on events (actual_rows=2000000, duration=22000ms)
                      Filter: tenant_id = ... AND event_type IN (...) AND created_at BETWEEN ...
                 -> Hash
                      -> Index Scan on users
```

**Three problems identified:**

| # | Problem | Cost | Root Cause |
|---|---------|------|------------|
| 1 | **Seq Scan on 800M rows** | ~22s | No usable index; planner rejects the existing index due to stale stats expecting 100 rows but getting 2M |
| 2 | **Sort spilling to disk** | ~18s | `work_mem` too small for 2M-row result set; merge sort written to `/dev/shm` or filesystem |
| 3 | **Stale row estimate** (100 → 2M) | cascading | Statistics are outdated; planner chose nested-loop/hash-join plan with wrong cardinality, which cascades into bad memory allocation for the sort |

---

### Step 1 — Fix the Statistics First (Quick Win)

Before touching indexes or queries, refresh stats. The 20,000x underestimate is the root cause of many downstream bad decisions.

```sql
-- Run during low traffic; requires superuser or pg_monitor role
ANALYZE events;
ANALYZE users;

-- If column correlation is extreme (e.g., most events from few tenants),
-- increase per-column statistics target so the planner sees the skew:
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;
ALTER TABLE events ALTER COLUMN event_type SET STATISTICS 1000;
ALTER TABLE events ALTER COLUMN created_at SET STATISTICS 1000;
ANALYZE events;
```

> **Why 1000?** Default is 100. For high-cardinality skewed columns (tenant_id likely has long-tail distribution), 1000 gives the histogram 10× more buckets. The cost is slower ANALYZE (~seconds added), paid once.

### Step 2 — Choose the Right Index Strategy

#### Column Order Analysis

The query filters on three predicates:

```sql
WHERE tenant_id = $1           -- equality
  AND event_type = $2          -- equality (possibly multi-value IN)
  AND created_at >= $3         -- range
```

**Correct composite order: `(tenant_id, event_type, created_at)`**

Reasoning using the B-tree search model:

```
Step 1: Seek to tenant_id = $1      → O(log N) skip to correct partition
Step 2: Within that tenant, seek to event_type = $2 → O(log M) within partition
Step 3: Scan sequentially through created_at range → O(k) where k = matching rows
```

If we reversed the order to `(created_at, tenant_id, event_type)`, the range on `created_at` would consume the entire prefix of the index, leaving no ability to discriminate on `tenant_id` or `event_type` — Postgres would still need to filter the entire range-scan resultset in RAM.

#### The Index DDL

```sql
-- Primary recommendation: filtered partial index if only a subset of tenants/
-- types are queried frequently (e.g., active data vs archived)
CREATE INDEX idx_events_active
ON events (tenant_id, event_type, created_at DESC)
WHERE deleted_at IS NULL;  -- if soft-delete exists; omit if not

-- Core index (no partial predicate unless justified):
CREATE INDEX idx_events_tenant_type_time
ON events (tenant_id, event_type, created_at DESC);
```

> **Why `DESC` on `created_at`?** If the report shows "most recent events first" (common), the index matches the ORDER BY directly. Postgres can then do an *index-only scan* in the requested order, eliminating the sort entirely. If you need ASC, use ASC — match the query's ORDER BY exactly.

#### Covering Index Tradeoff

Consider a covering index ONLY if the query selects ≤ 3 additional columns beyond those needed for filtering/joining:

```sql
-- Only if query does SELECT tenant_id, event_type, created_at, user_id FROM events ...
-- This stores user_id in the index leaf pages, avoiding heap fetches
CREATE INDEX idx_events_covering
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, payload);   -- INCLUDE columns avoid heap lookups
```

**When NOT to use INCLUDE:** On an 800M-row table, each extra included column multiplies index size. If `payload` is a text/jsonb column averaging 2KB, the index balloons from ~25GB to ~1.8TB — not worth it. Use INCLUDE only for small integer/timestamp columns.

### Step 3 — Verify the Planner Picks the Index

```sql
-- Force re-planning after ANALYZE
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
WITH ranked AS (
    SELECT e.*,
           ROW_NUMBER() OVER (PARTITION BY e.tenant_id, e.event_type
                              ORDER BY e.created_at DESC) AS rn
    FROM events e
    WHERE e.tenant_id = 'tenant-abc'
      AND e.event_type IN ('click', 'view', 'purchase')
      AND e.created_at >= '2024-01-01'
      AND e.created_at <  '2025-01-01'
)
SELECT r.*, u.email, u.name
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 100;
```

**Good plan should show:**

| Node | What to expect |
|------|----------------|
| Index Scan / Bitmap Index Scan on `idx_events_tenant_type_time` | Not Seq Scan |
| Rows estimated close to actual (within 2-5×) | Not 100 vs 2M |
| No "sort_method: external file" | Sort fits in `work_mem` or is eliminated |
| Buffers shared hit > 90% | Index in cache, not reading from disk |

If the planner still chooses Seq Scan despite the index, check:
- Is `enable_seqscan = off` accidentally on? (It shouldn't be — don't flip it permanently)
- Did ANALYZE actually update the statistics? Check `pg_stats` → `null_frac`, `n_distinct`, `most_common_vals`
- Is the query using a parameter type mismatch? (e.g., passing integer for a UUID column)

### Step 4 — Rewrite the Query

The original pattern likely pushes the window function over all matched rows before filtering by rank. Here's the corrected form:

```sql
-- Rewritten with early rank filtering via a subquery or LATERAL
WITH matched_events AS (
    -- CTE 1: Narrow to the right partition + time range using the index
    SELECT e.id, e.tenant_id, e.event_type, e.created_at, e.user_id, e.payload
    FROM events e
    WHERE e.tenant_id = 'tenant-abc'
      AND e.event_type IN ('click', 'view', 'purchase')
      AND e.created_at >= '2024-01-01'
      AND e.created_at <  '2025-01-01'
),
ranked AS (
    -- CTE 2: Apply window ranking over the narrowed set (~2M rows, not 800M)
    SELECT id, tenant_id, event_type, created_at, user_id, payload,
           ROW_NUMBER() OVER (
               PARTITION BY tenant_id, event_type
               ORDER BY created_at DESC
           ) AS rn
    FROM matched_events
)
-- Final projection + join (only ~hundreds of rows at this point)
SELECT r.id, r.event_type, r.created_at, r.payload,
       u.email, u.name, u.tier
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 100;
```

**CTE materialization behavior (Postgres 16):**

- By default, CTEs are **optimization fences** — Postgres materializes them as temporary files. This means `matched_events` is computed first, its output size is known, and the planner makes better decisions for `ranked`.
- In Postgres 16+, `INLINE` and `NOINLINE` hints control this. If profiling shows the CTE is too costly to materialize (2M rows is moderate), inline it:

```sql
-- Option A: Materialize (safer for large intermediate results)
WITH matched_events AS MATERIALIZED (
    ...
),
ranked AS MATERIALIZED (
    ...
)
SELECT ... FROM ranked r JOIN users u ... WHERE r.rn <= 100;

-- Option B: Inline (let the planner push filters down, risks bad plans if stats are off)
WITH matched_events AS UNINLINED (
    ...
)
...
```

> **Recommendation:** Start with `MATERIALIZED` for both CTEs. The 2M-row intermediate set is small enough to fit in temp work files even with modest `work_mem`, and the certainty of a correct plan outweighs the tiny cost of materialization.

### Step 5 — Partitioning Decision

**Should you partition by month?** Evaluate with these criteria:

| Criterion | Your case | Verdict |
|-----------|-----------|---------|
| Table grows ≥ 50M rows/month? | 800M rows suggests months of accumulation | ✅ YES |
| Queries always include the partition key? | All queries filter on `created_at` ranges spanning days/months | ✅ YES |
| Historical data pruning needed? | Do you drop/query older months rarely? | ❓ Check workload |
| Index size manageable per partition? | Each monthly partition's index would be ~N/12th size | ✅ YES |

**If partitioning by month is warranted:**

```sql
-- Create a new partitioned table (requires downtime or parallel build):
CREATE TABLE events_partitioned (
    LIKE events INCLUDING ALL
) PARTITION BY RANGE (created_at);

-- Monthly partitions:
CREATE TABLE events_y2024m01 PARTITION OF events_partitioned
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_y2024m02 PARTITION OF events_partitioned
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ... repeat per month

-- Index on EACH partition (automatically propagated):
CREATE INDEX idx_events_part_tenant_type_time
ON EACH PARTITION (tenant_id, event_type, created_at DESC);
```

**Migration path (zero-downtime):**
1. Create `events_partitioned` alongside the old table
2. Build indexes on current partitions
3. Use logical replication or pgcopy to migrate historical data
4. Switch application reads/writes to the new table
5. Drop the old table

**For your immediate 40s problem**, partitioning is overkill right now. The combination of (1) ANALYZE + (2) composite index will get you from 40s → ~200-500ms. Partitioning becomes necessary when single-partition indexes exceed available RAM and become evicted from the buffer pool.

### Step 6 — Tuning `work_mem`

The sort spill to disk indicates the merge sort couldn't fit in memory. For a 2M-row sort:

```sql
-- Current (likely default)
SHOW work_mem;  -- probably 4MB

-- Session-level fix for this reporting workload:
SET work_mem = '256MB';   -- enough for ~2M-row merge sort in RAM
-- Then run the query

-- Permanent fix (affects ALL queries — test carefully):
-- postgresql.conf:
-- work_mem = 64MB
-- max_parallel_workers_per_gather = 4  -- enables parallel index scan too
```

Check the EXPLAIN output post-fix for:
- `sort_method: quicksort` (in-memory) vs `sort_method: merge external file` (spilled)
