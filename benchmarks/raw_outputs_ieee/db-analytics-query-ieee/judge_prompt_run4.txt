## 2. Node-by-Node EXPLAIN ANALYZE Breakdown

### `Seq Scan on events`
- **Why**: No index matches the column combination `(tenant_id, event_type, created_at)` in the right order, OR the planner thinks scanning 800M rows + filtering will return fewer rows than walking the index.

### `Sort (spilling to disk)`
- **Why**: The `ORDER BY created_at DESC` inside a window function requires sorting ~2M rows. Default `work_mem` (4 MB) isn't enough for a 2M-row sort — Postgres writes temporary merge-sort files to disk.

### `Window Function Rank()`
- **Why expensive**: `RANK() OVER (PARTITION BY tenant_id, event_type ORDER BY created_at DESC)` needs all matching rows sorted by `tenant_id, event_type, created_at`. If the index already provides that order, Postgres can stream through it without a separate sort node.

- **Why slow**: The join happens *after* the window function, meaning you materialize ranked results from millions of rows before joining. A better strategy joins *first*, then ranks on the smaller intermediate set.

## 6. Rewritten Query

Here's the optimized query with explanations embedded:

```sql
-- ============================================================
-- STRATEGY: Join early, rank late. Minimize rows before window.
-- ============================================================

WITH filtered_events AS MATERIALIZED (
    -- Materialize forces a plan node boundary. Without it, Postgres might push the
    -- join back into the CTE, re-doing work. MATERIALIZED is a Postgres 12+ hint
    -- that prevents unwanted inlining. We want the join result small before ranking.
    
    SELECT e.event_id, e.tenant_id, e.event_type, e.created_at, e.user_id
    FROM events e
    WHERE e.tenant_id = $1              -- Equality — narrows to one tenant's slice
      AND e.event_type IN ($2, $3)      -- Multiple types? IN > OR for better plans
      AND e.created_at BETWEEN $3 AND $4  -- Range — uses the last column of our composite index
    
    -- Alternative if you know the exact type:
    -- AND e.event_type = $2
)

SELECT
    fe.*,
    RANK() OVER (
        PARTITION BY fe.tenant_id, fe.event_type
        ORDER BY fe.created_at DESC
    ) AS event_rank,
    u.name AS user_name,                  -- From users table
    u.email AS user_email
FROM filtered_events fe
JOIN users u ON u.user_id = fe.user_id   -- Join BEFORE ranking — far fewer rows
WHERE RANK() <= 10                       -- Filter top-ranked per group AFTER join
ORDER BY
    fe.tenant_id,
    fe.event_type,
    fe.created_at DESC;
```

### Key Changes Explained:

| Change | Why |
|--------|-----|
| **CTE with `MATERIALIZED`** | Creates a plan boundary. Prevents Postgres from pushing the join deep into the CTE which would re-scans events. Forces 2-phase execution: (1) filter events, (2) join to users, (3) rank. |
| **Join to users BEFORE ranking** | If you rank on 2M rows then join, you're ranking everything. Join first: 2M events × N tenants → maybe 500K joined rows → rank those. Fewer operations. |
| **`IN` instead of `OR`** | Postgres 16 optimizes `IN (...)` with multiple values better than chained `OR` predicates for index usage. |
| **`BETWEEN` instead of `>= AND <=`** | Identical in Postgres, but cleaner. The critical part is the index column order matching this pattern. |
| **Selected columns only** | Don't `SELECT *`. Pull only what you need so the covering index can satisfy the scan. Each extra byte multiplies across 800M rows. |

### What About `NOT MATERIALIZED` (inline)?

In Postgres 16, the planner often ignores `MATERIALIZED` and inlines the CTE anyway unless there's a reason not to (aggregation, `DISTINCT`, `UNION`). If your CTE has none of these, you can drop the keyword — the planner will inline it and potentially choose a better combined plan. Test both ways:

```sql
EXPLAIN (ANALYZE, BUFFERS) WITH ...   -- with MATERIALIZED
EXPLAIN (ANALYZE, BUFFERS) WITH ...   -- without
```

Pick whichever gives lower actual cost. In most reporting cases with heavy joins, `MATERIALIZED` wins because it limits the join input size.

### Materialized View Alternative (For Dashboard/Report Pages)

If this query runs repeatedly on a dashboard with fresh-enough data (< 5 min lag):

```sql

    tenant_id, event_type, created_at::date AS report_date,

### Index Strategy Decision

#### Column Order Rationale

```
(tenant_id, event_type, created_at DESC)
   │           │            │
   │           │            └── Range/sort column last among filter columns
   │           └── Equality filter (optional ENUM-like cardinality)
   └── Highest-cardinality equality filter (primary partition key)
```

Column order matters because a B-tree is a sorted structure. After filtering on `tenant_id`, the index narrows to that tenant's entries. Within that subset, filtering on `event_type` further reduces to one type. `created_at` comes third because:

- It's a **range predicate** (`BETWEEN`). Once you pass through the range in index order, you stop scanning — efficient termination.
- If `created_at` came before `event_type`, the planner couldn't skip unrelated types within the date range (it would scan all types across the entire date window, then filter in-memory).

For per-tenant queries, `tenant_id` dominates cardinality — it's always first. For cross-tenant reports, the order would differ.

#### Final Index Recommendation

**Primary index — index-only scan coverage:**
```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_date_user
  ON events (tenant_id, event_type, created_at DESC)
  INCLUDE (user_id);
```

`INCLUDE` places `user_id` in the leaf pages without affecting B-tree traversal cost. This enables an **index-only scan**: Postgres reads only the index, never touches the 800M-row heap. For the join condition `events.user_id = users.id`, this eliminates random I/O against the main table entirely.

Index size estimate: ~9 bytes (tenant_id) + 4 bytes (event_type hash/int) + 8 bytes (timestamptz) + 8 bytes (included user_id) = ~29 bytes/entry × 800M = **~23 GB**. Manageable. Worth the storage vs. sequential heap scans.

**Optional secondary index — if JOIN is still the bottleneck after fixing estimates:**
```sql
CREATE INDEX CONCURRENTLY idx_events_user_id
  ON events (user_id);
```
This enables Hash Join by allowing Postgres to build the hash table from an index-only scan on `user_id` rather than a full table scan. Add only if profiling shows the nested loop remains suboptimal even with correct estimates.

**Why not partial indexes?** A partial index like `WHERE tenant_id = 'specific'` would save space per tenant but doesn't generalize across tenants. With 800M rows across many tenants, maintaining N partial indexes is impractical unless you have one mega-tenant (>10% of total rows).

**Composite with INCLUDE vs. separate covering index:** Single composite with INCLUDE is superior to two separate indexes because it serves the WHERE clause AND the JOIN in one structure. The INCLUDE column adds ~8 bytes/leaf entry but saves a heap fetch — net positive for any result set > few hundred rows.

## Index Strategy

### The Core Decision: Composite vs Single vs Partial

You have three tools; each solves different problems. The right choice depends on your access patterns.

**Single-column indexes don't work here.** An index on only `tenant_id` narrows from 800M down to (say) 10M, but you still Seq Scan on `event_type` and `created_at`. Same problem — just smaller.

**Covering index avoids heap fetches but bloats the index.** With 800M rows and 5+ included columns, the index grows to 50-80GB. Worth it if the query runs hundreds of times per day; not worth it if it runs once daily.

**Partial indexes are niche.** Only justified when the predicate excludes >90% of rows permanently (e.g., `WHERE event_type IN ('signup', 'purchase')`). Don't partial-index unless you've proved the selective filter dominates your workload.

### Recommended Index

```sql
-- Primary composite index - matches the common access pattern
CREATE INDEX CONCURRENTLY idx_events_tenant_type_time
  ON events (tenant_id, event_type, created_at DESC);
```

**Why this column order:**

1. **`tenant_id` first** — Equality filter. Multi-tenant systems typically isolate one tenant per request. This is the most selective equality column. If you had <10 tenants total, flip the order to start with `created_at`, but multi-tenant apps have thousands of tenants.

2. **`event_type` second** — Second equality filter. Narrowed further within each tenant.

3. **`created_at DESC` third** — Range filter. Placed last because range predicates "consume" the rest of the index. Including `DESC` means the index scan already satisfies the `ORDER BY` for most window functions (top-N by recency), avoiding the post-index sort step.

**What queries this serves:**

| Pattern | Matches? | Why |
|---------|----------|-----|
| `WHERE tenant_id = X AND event_type = Y AND created_at BETWEEN A AND B` | Full range scan | All three columns drive the search |
| `WHERE tenant_id = X AND created_at BETWEEN A AND B` | Prefix match | Uses first two columns for equality, scans created_at range |
| `WHERE tenant_id = X AND event_type = Y` | Prefix match | Two-column prefix; may still need filter for created_at |
| `WHERE tenant_id = X` | Prefix match | Single-column prefix; broader scan but indexed |
| `WHERE event_type = Y AND created_at BETWEEN A AND B` | ❌ | Missing leading tenant_id; cannot use prefix |

## Step 2: Index Strategy — Column Order Matters

### Understanding B-tree Ordering Rules

PostgreSQL B-trees are ordered lexicographically. For a composite index `(A, B, C)`:

- **Efficient for**: filters starting from the leftmost column → `WHERE A = ?`, `WHERE A = ? AND B > ?`, etc.
- **Inefficient for**: skipping ahead → `WHERE B = ?` alone, `WHERE C = ?` alone
- **Range on middle column breaks subsequent columns**: `WHERE A = ? AND B > ?` means C cannot use the index (B's range destroys C's ordering within each A group)

### Recommended Index Designs (ranked)

#### Priority 1: Composite covering index with INCLUDE (primary fix)

```sql
-- Exact match on tenant_id (highest selectivity), then range on created_at,
-- plus filter on event_type as equality
CREATE INDEX CONCURRENTLY idx_events_tenant_created_included
    ON events (tenant_id, created_at)
    INCLUDE (event_type, user_id)
    WHERE tenant_id IS NOT NULL;
```

**Why this order?**
- `tenant_id` first: typically highest selectivity in SaaS multi-tenant setups. Filtering by tenant alone should reduce 800M down to a reasonable subset.
- `created_at` second: range filter uses the index for the initial position, then reads forward sequentially for the date range.
- `INCLUDE (event_type, user_id)`: makes this a **covering index**. The query can be satisfied entirely from the index (index-only scan) without touching the heap — eliminating random I/O and enabling faster sorts since the data is already clustered by `tenant_id, created_at` on disk.

**What about `event_type` in the key columns?** Two options depending on selectivity:

If `tenant_id` has high cardinality but `event_type` further reduces the result set significantly (e.g., only 1 of 50 event types matters):

```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_created
    ON events (tenant_id, event_type, created_at DESC)
    INCLUDE (user_id);
```

This puts `event_type` between tenant and created_at because:
- Both are equality predicates → order doesn't affect which rows we find
- But sorting `created_at DESC` in the index eliminates the need for a separate sort step entirely
- The `DESC` here directly serves window-function `RANK() OVER (ORDER BY created_at DESC)` without any in-memory sorting

If `event_type` filters are rarely used together, keep them out of the key and instead put them in a where-clause partial index (see below).

#### Priority 2: Partial indexes for common queries

If you frequently run "top N users for tenant X by last N events":

```sql
-- Only materialize for active tenants or recent data
CREATE INDEX CONCURRENTLY idx_events_active_tenant_recent
    ON events (tenant_id, created_at DESC)
    INCLUDE (event_type, user_id)
    WHERE created_at >= NOW() - INTERVAL '6 months';
```

Use sparingly though — partial indexes multiply the maintenance cost and PostgreSQL can pick multiple partial indexes per query, leading to "BitmapOr" overhead.

#### Priority 3: Users table

```sql
-- Verify this exists (or recreate)
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_id
    ON users (id)
    INCLUDE (tenant_id, email, name);  -- if your SELECT needs these columns
```

Make sure the users table index matches what your join and projection need. Prefer hash joins over nested loops when both sides are large.

#### What NOT to do

```sql
-- DON'T create one massive index on every column combination
CREATE INDEX ON events (tenant_id, event_type, user_id, created_at, ...) ;

-- DON'T include all selected columns in the index — INCLUDE is for point lookups,
-- not for stuffing every column into the index bloat factory
```

## Step 1: The Right Index Strategy

### Why Column Order Matters

For a composite index `(a, b, c)`, Postgres uses left-prefix matching: queries filtering on `a`, then `a+b`, then `a+b+c` all benefit. Filtering on `b` alone or `c` alone does not use the index efficiently.

In this query we have three filters: `tenant_id = ?` (very selective), `event_type = ?` (moderate), `created_at BETWEEN ? AND ?` (range). The key insight: **the most selective equality filter goes first**, then the secondary equality, then the range — because once you narrow to one tenant, the remaining filters are applied against a much smaller set.

```sql

ON events (tenant_id, event_type, created_at DESC);

WHERE EXISTS (  -- only include users who actually have matching events

### CTE Materialization Decision

| Approach | When to Use |
|---|---|
| `WITH ... AS MATERIALIZED` (Option A) | The CTE result is large (>100K rows) but used only once, OR the window function produces results that benefit from being materialized before the join |
| Plain `WITH` (unmaterialized) | Results are small (<10K rows), and predicate pushdown can optimize the join |
| `LATERAL` + `LIMIT` (Option B) | You're ranking per-group and only want top-N — this is usually fastest because Postgres stops scanning after N rows per group |
| Temp table | 800M row dataset, ad-hoc reporting, multiple downstream CTEs reuse the same filtered result |

**Recommendation: Start with Option A** (`AS MATERIALIZED`). It's the lowest-risk change. If EXPLAIN ANALYZE still shows a sort spilling to disk, move to Option B where the `LIMIT 3` in the lateral subquery prevents ranking every row.
