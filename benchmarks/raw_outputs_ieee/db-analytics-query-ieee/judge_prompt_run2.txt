## 1. Index Strategy — Column Order Matters

### Why column order matters

For `WHERE tenant_id = $1 AND event_type = $2 AND created_at > $3`:
- **Equality columns go first** (tenant_id, event_type) → B-tree narrows to exact prefix
- **Range column goes last** (created_at) → can still use index for range scan after equality prefix

A composite index `(tenant_id, event_type, created_at)` makes ALL three predicates indexable. Reversing `created_at` before the equality columns wastes the index entirely for range scans.

### Recommended indexes

```sql
-- Primary index for the filtering pattern
CREATE INDEX CONCURRENTLY idx_events_tenant_type_time
  ON events (tenant_id, event_type, created_at DESC);

-- Covering index if the window function only needs specific columns
-- Eliminates heap fetches for SELECT-only queries (no UPDATE/DELETE on these columns)
CREATE INDEX CONCURRENTLY idx_events_covering
  ON events (tenant_id, event_type, created_at DESC)
  INCLUDE (user_id, payload, session_id);
  -- INCLUDE adds columns WITHOUT increasing index size impact on search;
  -- enables index-only scans for typical reporting SELECTs
```

### When to use PARTIAL indexes

Partial indexes (`WHERE ...`) make sense when you filter on a constant predicate that excludes most rows. For example:

```sql
-- Only if 95%+ of queries exclude archived events
CREATE INDEX CONCURRENTLY idx_events_active
  ON events (tenant_id, event_type, created_at DESC)
  WHERE archived_at IS NULL;
```

**Verdict:** Don't start here. It multiplies maintenance cost and complicates query planning. A single well-tuned composite index handles 99% of cases. Add partial indexes only after measuring that a specific predicate dominates traffic and causes bloat on the main index.

### Verdict on Partitioning

Partition by month is justified IF:
- Queries typically span ≤ 1 quarter but touch many months (partition pruning kicks in)
- Old data gets dropped/archived regularly (DROP partition > DELETE millions of rows)
- You can tolerate partition maintenance overhead (VACUUM per-partition, DDL lock on one partition)

Given 800M rows, if events span 24 months (~33M/month):

```sql
-- Consider this ONLY if the above criteria are met.
-- For a fresh start:
CREATE TABLE events_partitioned (LIKE events INCLUDING ALL)
PARTITION BY RANGE (created_at);

-- Month-level partitions
CREATE TABLE events_2024_01 PARTITION OF events_partitioned
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_2024_02 PARTITION OF events_partitioned
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ... repeat monthly

-- Same composite index on each partition (Postgres auto-applies via inheritance)
CREATE INDEX ON events_partitioned (tenant_id, event_type, created_at DESC);
```

**Practical advice:** Migrate to composite indexes FIRST. If performance is still unacceptable, benchmark partitioning against the same workload. Most 800M-row tables perform fine with good indexes + proper `work_mem`. Partitioning adds operational complexity (migrations, cross-partition queries, VACUUM management).

## 3. Index Strategy — What Kind, Why Column Order Matters

### Option A: Composite Index (equality → range ordering)

```sql
CREATE INDEX CONCURRENTLY idx_events_report
  ON events (tenant_id, event_type, created_at DESC)
  WHERE tenant_id IS NOT NULL;   -- partial index optimization
```

**Why this order:**
- `tenant_id` — equality predicate, highest selectivity usually; goes first for exact match
- `event_type` — equality (IN list); groups rows within tenant so created_at range scan is fast
- `created_at DESC` — range predicate goes last; DESC matches `ORDER BY created_at DESC` in the window function, eliminating the sort entirely

**Trade-off:** Partial index (`WHERE tenant_id IS NOT NULL`) reduces size if some events have NULL tenants (~5–10% typical). For 800M rows, a full composite index on 3 columns might be ~80–120 GB; partial could save that fraction.

### Option B: Covering Index (INCLUDE columns we need later)

If the query selects columns beyond the filter keys, make them covering:

```sql
CREATE INDEX CONCURRENTLY idx_events_report_covering
  ON events (tenant_id, event_type, created_at DESC)
  INCLUDE (user_id)
  WHERE tenant_id IS NOT NULL;
```

**Why INCLUDE matters:** Without it, after scanning the index, Postgres must fetch each of the 2M rows from the heap (table) for `user_id`. With INCLUDE, `user_id` is stored inline in the index leaf pages, eliminating heap lookups. On 800M rows, this can save tens of millions of random I/O operations.

**When to use:** Only when you're selecting those extra columns. If you only need `tenant_id`, `event_type`, `created_at`, and compute `user_id` via join, skip INCLUDE and let the join handle it. The COVERING variant helps if you project `user_id` in a CTE before joining.

### Option C: Partitioning (when is it justified?)

For 800M rows, monthly RANGE partitioning on `created_at`:

```sql
-- Only worth it if you:
-- 1. Regularly query single-month ranges
-- 2. Can prune partitions during scans
-- 3. Benefit from faster vacuum/maintenance per partition
```

**Verdict:** Don't add partitioning as the *first* fix. It adds schema complexity and constraint-expansion overhead. Start with the composite index + stats fix. If monthly reports consistently outperform, add `CREATE TABLE ... PARTITION BY RANGE (created_at)` with monthly subdivisions as Phase 2. The index strategy works equally well on partitioned tables (local indexes auto-benefit from pruning).

```sql
SET random_page_cost = 1.1;

WITH filtered_events AS (

    SELECT e.tenant_id,
           e.user_id,
           e.event_type,
           e.created_at
    FROM   events e
    WHERE  e.tenant_id = 'target-tenant'
      AND  e.event_type IN ('click', 'view', 'purchase')
      AND  e.created_at >= '2024-01-01'
      AND  e.created_at <  '2024-02-01'    -- month-bound if partitioned; otherwise wider range
),
ranked_events AS (
    -- Window function ranks within each (tenant, user) by recency
    -- Index already provides created_at DESC ORDER, so NO SORT needed
    SELECT tenant_id,
           user_id,
           event_type,
           created_at,
           ROW_NUMBER() OVER (
               PARTITION BY tenant_id, user_id
               ORDER BY created_at DESC
           ) AS rn
    FROM   filtered_events
),
top_events AS (
    -- Keep only top N per group
    SELECT tenant_id,
           user_id,
           event_type,
           created_at
    FROM   ranked_events
    WHERE  rn <= 10
),
users_lookup AS (
    -- Single-pass lookup of user details via index scan on PK
    SELECT u.id AS user_id,
           u.name,
           u.email
    FROM   users u
    JOIN   top_events t ON t.user_id = u.id
)
SELECT te.tenant_id,
       ul.name  AS user_name,
       ul.email AS user_email,
       te.event_type,
       te.created_at
FROM   top_events te
JOIN   users_lookup ul ON ul.user_id = te.user_id
ORDER BY te.tenant_id, te.created_at DESC;
```

### CTE / Materialization Choices Explained

| CTE | Behavior | Why |
|---|---|---|
| `filtered_events` | **Not materialized** (planner inlines) | This is a pure filter; Postgres will push predicates into the index scan. Inlining avoids temp storage. |
| `ranked_events` | **Could be materialized** | Window functions don't benefit from inlining on older PG versions. In PG 16, the planner may choose to materialize it automatically. Explicit `WITH (MATERIALIZED)` can help if the optimizer chooses poorly. |
| `top_events` | **Materialized** | After filtering to top-N per group, the dataset shrinks dramatically (from 2M to perhaps 200K). Materializing here gives the next join a small input. |
| `users_lookup` | **Not materialized** | Small result set; inline join is fine. |

If the optimizer still struggles, force materialization explicitly:

```sql
WITH ranked_events AS MATERIALIZED (
    SELECT ..., ROW_NUMBER() OVER (...) AS rn
    FROM   filtered_events
)
```

In PG 16, the planner sometimes refuses to push joins into CTEs — `MATERIALIZED` forces it. Use it selectively; don't mark everything as materialized (that wastes memory and time).

## 2. Index Strategy — What and Why

### The Composite Index

```sql
CREATE INDEX CONCURRENTLY events_tenant_type_date_idx
  ON events (tenant_id, event_type, created_at DESC);
```

**Column order matters because of selectivity and predicate type:**

1. **`tenant_id` first** — equality filter (constant lookup). This is the highest-cardinality dimension. In a multi-tenant system, tenant_id alone can be >99% selective, reducing 800M → potentially 10M or fewer rows depending on tenant distribution. B-tree indexing works best when equality columns come first.

2. **`event_type` second** — also equality (another constant). With tenant_id already narrowing the range, event_type further slices it. Together they're compound-selective. If you swapped them (`event_type, tenant_id, ...`), queries that only filter on tenant_id would NOT use this index (the B-tree is sorted by event_type *within* the key — after locking on event_type, tenant_id can be filtered via a bitmap scan, but not as cleanly). Since `tenant_id` is almost always the leading WHERE clause constraint, it MUST come first.

3. **`created_at DESC` third** — range filter. Range predicates consume their slot in the B-tree index and cannot be followed by another indexable column. Using `DESC` aligns with `ORDER BY created_at DESC` in the window function — the index delivery order matches the sort order, eliminating an explicit sort step entirely.

### Optional: INCLUDE Column (Covering Index)

If the query only reads `user_id`, `event_type`, and `created_at`, make it a covering index:

```sql
CREATE INDEX CONCURRENTLY events_covering_idx
  ON events (tenant_id, event_type, created_at DESC)
  INCLUDE (user_id);
```

This allows an **index-only scan** — no heap fetch at all. But note: with 800M rows, bloat from UPDATEs/DELETEs could make index-only scans slower than a plain index scan due to visibility map checks. Monitor with `pg_stat_user_indexes`. Only use COVERING if:
- The table is append-only (no UPDATEs)
- Vacuum keeps up (auto-vacuum is healthy)
- Heap fetches are confirmed to be zero in EXPLAIN ANALYZE

### Partial Index Option

If a specific `event_type` accounts for 90%+ of traffic, a partial index pays off:

```sql
CREATE INDEX CONCURRENTLY events_purchase_only_idx
  ON events (tenant_id, created_at DESC)
  WHERE event_type = 'purchase';
```

But this is brittle — one new event_type and the index is useless. Only recommend if the workload is truly static. For general use, stick with the composite index above.

## 4. Partitioning Assessment — Is Monthly Worth It?

**Verdict: Yes, for an 800M-row table where queries filter on `created_at`.**

### When to partition:
- Table exceeds ~500M rows ✅ (you have 800M)
- Queries routinely filter on a time range ✅ (your `BETWEEN $3 AND $4`)
- Old data is rarely queried ✅ (event analytics typically look back 3-12 months)
- You can handle maintenance complexity ⚠️ (trade-off)

### How it helps:

With monthly partitioning on `created_at`, Postgres performs **partition pruning** at planning time — if your query filters `created_at BETWEEN '2026-03-01' AND '2026-05-31'`, it only scans 3 partitions instead of 800M rows across one monolithic table. The planner narrows the scan set by orders of magnitude.

### Schema:

```sql
-- Create parent table with partition key
CREATE TABLE events (
    id            bigserial PRIMARY KEY,
    tenant_id     uuid NOT NULL,
    user_id       uuid NOT NULL,
    event_type    varchar(64) NOT NULL,
    payload       jsonb,
    created_at    timestamp NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

-- Create monthly partitions (example for current year)
CREATE TABLE events_2026_01 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- ... repeat for each month

-- Add indexes on each partition (automatically inherit from child definitions)
CREATE INDEX events_2026_01_tenant_type_date
    ON events_2026_01 (tenant_id, event_type, created_at DESC);
CREATE INDEX events_2026_02_tenant_type_date
    ON events_2026_02 (tenant_id, event_type, created_at DESC);
-- Each partition is smaller — faster index builds, faster sequential scans
```

### Automation script for partition creation:

```sql
-- Run monthly (crontab or pg_cron)
DO $$
DECLARE
    next_start DATE := date_trunc('month', now()) + interval '6 months';
    part_name text := 'events_' || to_char(next_start, 'YYYY_MM');
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_class WHERE relname = part_name
    ) THEN
        EXECUTE format(
            'CREATE TABLE %I PARTITION OF events FOR VALUES FROM (%L) TO (%L)',
            part_name,
            next_start,
            next_start + interval '1 month'
        );
        
        EXECUTE format(
            'CREATE INDEX events_%s_tenant_type_date ON %I (tenant_id, event_type, created_at DESC)',
            replace(part_name, '_', '-'),
            part_name
        );
    END IF;
END $$;
```
