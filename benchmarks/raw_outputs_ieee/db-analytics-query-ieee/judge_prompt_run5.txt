## Step 1: Index Strategy

### Why Column Order Matters

Filter predicates: `tenant_id = ?`, `event_type = ?`, `created_at BETWEEN ? AND ?`

The order must follow the "equality first, range last" rule:

```sql
-- ✅ Correct: equality columns before range column
-- B-tree is sorted ascending. Equality probes land at one position.
-- Range scans forward from there — contiguous I/O.

    ON events (tenant_id, event_type, created_at DESC);

-- ❌ Wrong: puts range column first, kills selectivity

    ON events (created_at, tenant_id, event_type);
-- B-tree on created_at narrows the range, then does nested lookups
-- for tenant_id within that range — no index-only benefit for
-- filtering. Essentially a sorted seq scan with extra memory overhead.
```

### Partial Index vs Covering Index

Two layers of indexing:

```sql
-- Layer 1: Targeted partial index if a single tenant dominates
-- Only create if ONE tenant has >10% of all events:
CREATE INDEX idx_events_major_tenant
    ON events (tenant_id, event_type, created_at DESC)
    WHERE tenant_id = 'specific-major-tenant';
-- This index is ~10% the size of the full index but answers
-- queries for that tenant alone. Skip for now — you likely
-- have multiple tenants needing coverage.

-- Layer 2: Full composite index (required)
CREATE INDEX idx_events_tenant_type_date
    ON events (tenant_id, event_type, created_at DESC);

-- Layer 3: Covering index if most queries only need a few
-- additional columns (avoids heap fetches):
CREATE INDEX idx_events_covering
    ON events (tenant_id, event_type, created_at DESC)

-- access for those columns. Trade-off: index is ~2-3x larger
-- but sequential-scan-friendly in its entries.
```

## Step 4: Rewritten Query

Without seeing the exact original query, here's the pattern for what it almost certainly looks like and how to rewrite it:

```sql
-- ===== ORIGINAL (slow, ~40s) =====
SELECT u.name, e.tenant_id, e.event_type, e.created_at,
       RANK() OVER (PARTITION BY e.tenant_id ORDER BY e.created_at DESC) AS rn
FROM events e
JOIN users u ON u.id = e.user_id
WHERE e.tenant_id = 'abc123'
  AND e.event_type = 'pageview'
  AND e.created_at BETWEEN '2024-01-01' AND '2024-06-30'
ORDER BY e.created_at DESC
LIMIT 100;
```

```sql
-- ===== OPTIMIZED (~<2s expected) =====
WITH ranked AS MATERIALIZED (
    -- CTE with MATERIALIZED forces a materialization step, preventing
    -- the planner from pushing limit/sort down into the join. This is
    -- crucial because the window function operates ONLY on the filtered
    -- event subset, not the entire joined result.
    SELECT
        e.user_id,
        e.tenant_id,
        e.event_type,
        e.created_at,
        RANK() OVER w AS rn
    FROM events e
    WHERE e.tenant_id = 'abc123'
      AND e.event_type = 'pageview'
      AND e.created_at BETWEEN '2024-01-01' AND '2024-06-30'
    WINDOW w AS (PARTITION BY e.tenant_id ORDER BY e.created_at DESC)
)
SELECT r.tenant_id, r.event_type, r.created_at, r.rn,
       u.name
FROM ranked r
JOIN users u ON u.id = r.user_id
WHERE r.rn <= 100   -- Push LIMIT into WHERE for clarity
ORDER BY r.created_at DESC;
```

### Why `MATERIALIZED` vs Default?

By default in PG 12+, CTEs are **inlined** — the planner may push predicates from outside the CTE into it, which can break window-function semantics. With `MATERIALIZED`, the CTE executes as an independent plan node, producing exactly the filtered + ranked event rows, then joins against `users`.

### Window Function Optimization Note

The window frame here defaults to `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Since we're partitioning by `tenant_id` and ordering by `created_at DESC`, identical timestamps produce tied ranks. That's correct behavior for reporting. If you need strict row numbering regardless of ties, switch to `ROW_NUMBER()`.

```sql
WITH tenant_filter AS MATERIALIZED (

  SELECT e.user_id, e.created_at, e.payload
```

## Index Strategy

### Why Composite Order Matters

A B-tree index is ordered on its leading column(s). The planner uses an index scan only when the query's WHERE clause matches the index from left to right:

```
INDEX: (a, b, c)
WHERE a = ?              → index scan ✓ (uses full index)
WHERE a = ?, b = ?       → index scan ✓ (uses full index)
WHERE a = ?, c > ?       → index scan ✓ (b is skipped, c still usable)
WHERE b = ?              → seq scan ✗  (can't use b or c without a)
WHERE c > ?              → seq scan ✗  (no prefix match)
```

Column order must follow this priority:

1. **Equality predicates** first (`tenant_id = X`) — eliminates entire subtrees
2. **Range predicates** last (`created_at BETWEEN A AND B`) — used for scanning within the equality-matched subtree
3. **High-selectivity columns** second when no equality exists
4. **INCLUDE columns** at the end — stored in the index leaf but not used for ordering/searching

### Recommended Indexes

**Primary index — covers the WHERE clause + window function ORDER BY:**

```sql
CREATE INDEX CONCURRENTLY idx_events_tenant_type_created
ON events (tenant_id, event_type, created_at DESC);
```

This gives us:
- Equality lookup on `tenant_id` ( narrows from 800M → ~O(tenant's rows))
- Equality on `event_type` (further narrow)  
- Range scan on `created_at DESC` (produces descending order natively)
- The descending `created_at` means the window function `ROW_NUMBER() OVER (PARTITION BY tenant_id ORDER BY created_at DESC)` gets pre-sorted input → **eliminates the first sort entirely**

**Covering variant — if you SELECT additional columns beyond keys:**

If your query does `SELECT e.*, u.name FROM events e JOIN users u ON ...` and you frequently select the same columns, add an INCLUDE:

```sql
CREATE INDEX CONCURRENTLY idx_events_covering
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, status, metadata);
```

Trade-off analysis:
- **Pros**: Index-only scans avoid heap fetches entirely. With 800M rows, avoiding 2-byte page pointers + visibility map lookups per row saves meaningful I/O.
- **Cons**: Each INSERT/UPDATE writes more data to the index, slowing writes 15-25%. Index size grows ~3-4×.
- **Verdict**: Use INCLUDE only for columns accessed in 90%+ of reads. Don't blanket-cover wide JSONB/json fields.

**Partial index — for the most common access pattern:**

```sql
CREATE INDEX CONCURRENTLY idx_events_active_tenants
ON events (tenant_id, event_type, created_at DESC)
WHERE tenant_id IS NOT NULL;
```

Actually, for a stronger partial: if 80% of queries target `event_type IN ('page_view', 'click', 'submit')`:

```sql
CREATE INDEX CONCURRENTLY idx_events_common_types
ON events (tenant_id, created_at DESC)
WHERE event_type IN ('page_view', 'click', 'submit');
```

This index is ~30% smaller and serves the majority of queries. Postgres will choose it automatically when the WHERE matches.

**Don't create this anti-pattern:**

```sql
-- BAD: separates range predicate, destroys sort benefit
CREATE INDEX idx_events_bad ON events (tenant_id, created_at, event_type);
-- WHERE tenant_id = ? AND event_type = ? AND created_at BETWEEN ...
-- Gets an index scan but created_at is NOT ordered → still needs a sort!
```

### Users Table Index

The 2M-row users table needs a proper join index:

```sql
CREATE INDEX CONCURRENTLY idx_users_tenant_id
ON users (tenant_id) INCLUDE (name, email, created_at);
```

Without this, the Merge Join does nested-loop-like behavior over unsorted users. With it, users are scanned sequentially in tenant_id order matching the ranked events.

## Step 2: Index Strategy — Choose the Right Shape

### Column Selectivity Determines Order

| Column | Approx Selectivity | Cardinality Estimate |
|--------|-------------------|---------------------|
| `tenant_id` | HIGH (millions of tenants) | Single value ≈ few hundred rows |
| `event_type` | MEDIUM (dozens of types) | Single type ≈ thousands–hundreds of K |
| `created_at` | LOW (continuous) | Range filter dominates I/O |
| `user_id` (FK to users) | Medium | Used for join + window |

The key principle: **equality columns first, then range columns, then covering columns via INCLUDE**.

### The Primary Index (Covering Composite)

```sql
CREATE INDEX idx_events_tenant_type_created ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, id);
-- Explanation:
--   tenant_id  → equality filter (highest selectivity single-column)
--   event_type → equality filter (second equality)
--   created_at DESC → range scan in descending order; matches most reporting
--                        queries that want recency-first ranking
--   INCLUDE (user_id, id) → avoids heap fetch for the window function and join key.
--                           This turns the entire filtered-and-sorted result set
--                           into an index-only scan.
```

**Why INCLUDE over adding user_id to the leading keys:** Adding `user_id` before `created_at` would destroy the range-scannability of `created_at`. INCLUDE keeps the column in the index leaf pages but outside the B-tree sorting structure — it's metadata for index-only scans, not a sort key.

### Partial Index (If Hot-Tenanted Reporting)

If 90% of queries target the top 5 tenants:

```sql
CREATE INDEX idx_events_top_tenants
ON events (tenant_id, event_type, created_at DESC)
INCLUDE (user_id, id)
WHERE tenant_id IN ('tenant_a', 'tenant_b', 'tenant_c', 'tenant_d', 'tenant_e');
-- Smaller, fits in cache, auto-updated only for these tenants.
```

### Secondary Index for User-Id Window Queries

If you frequently do window functions scoped per-user within a tenant:


## Step 3: Partitioning — Is It Worth It?

### Decision Framework

| Criterion | Verdict |
|-----------|---------|
| Queries typically span ≤ 3 months? | **Yes** — partition pruning cuts 800M → ~50–200M scanned rows |
| Table receives > 1M inserts/day? | **Yes** — younger partitions benefit from fresher autovacuum stats |
| Cross-month aggregate queries are common? | **No** — partial merge adds overhead; consider quarterly instead |
| Backup/restore per-tenant isolation needed? | **Yes** — logical backup one month at a time |

### Implementation (Monthly Range Partitioning)

```sql
-- 1. If not already partitioned:
ALTER TABLE events DROP CONSTRAINT events_pkey;  -- Must drop PK first
-- Recreate PK on partition level only.

CREATE TABLE events_partitioned (
    id          bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id   text        NOT NULL,
    event_type  text        NOT NULL,
    user_id     bigint      NOT NULL,
    payload     jsonb,
    created_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at)  -- Partition key included in PK
) PARTITION BY RANGE (created_at);

-- 2. Create current & upcoming partitions
DO $$
DECLARE
    start_date date;
    end_date   date;
    part_name  text;
BEGIN
    FOR start_date IN
        SELECT generate_series(
            date_trunc('month', min(created_at))::date,
            date_trunc('month', now() + interval '3 months')::date,
            interval '1 month'
        ) FROM events
    LOOP
        end_date   := start_date + interval '1 month';
        part_name  := 'events_' || to_char(start_date, 'YYYY_MM');
        EXECUTE format(
            'CREATE TABLE %I PARTITION OF events_partitioned
             FOR VALUES FROM (%L) TO (%L)',
            part_name, start_date, end_date
        );
        -- Apply the covering index on each new partition
        EXECUTE format(
            'CREATE INDEX %I ON %I (tenant_id, event_type, created_at DESC)
             INCLUDE (user_id, id)',
            part_name || '_tenant_type_idx', part_name
        );
    END LOOP;
END $$;

-- 3. Attach a future partition proactively (avoids lock during INSERT)
ALTER TABLE events_partitioned
ATTACH PARTITION events_2025_08 FOR VALUES FROM ('2025-08-01') TO ('2025-09-01');
```

**Key notes:**
- Including `created_at` in the primary key is required for range-partitioned tables (the partition key must be part of every unique constraint).
- Each partition gets its own index — smaller indexes fit in shared buffer pool, improving hit ratio dramatically.
- Autovacuum now operates per-partition: the hot current month gets frequent vacuuming while historical data stays stable.

If cross-month aggregation is dominant, switch to **quarterly** partitions — fewer partitions, still meaningful pruning.
