# Hardened Constant-Product AMM Audit & Implementation

## Vulnerability Analysis

### 1. Reentrancy + CEI Violation — Severity: **Critical** (Exploitability: High)

The swap flow updates the user's USD-balance credit *before* reducing reserves, violating the Checks-Effects-Interactions pattern. An attacker who has deposited ERC-20 tokens with a reentrant callback (e.g., an ERC-777 token, or a token whose transfer callback executes external calls) can call `swap()` again while inside the first transfer's callback, reading stale (inflated) reserves. Each recursion inflates the attacker's credit by calling `updateBalance` again, each time crediting against the original, unchanged reserve state.

```
// VULNERABLE ORDER (inside swap):
// Step A: creditUser(msg.sender, amountOut)    ← Effects
// Step B: _transferTokens(tokenB, msg.sender, amountOut) ← Interactions
// Step C: reserves[tokenB] -= amountOut         ← Effects (TOO LATE)

// REENTRANCY WINDOW: Between Step A and Step C,
// step B's callback re-enters swap() and reads stale reserves.
```

**Exploit flow:**
1. Deposit collateral → gets LP shares
2. Call `swap(A→B)` for a large output
3. Inside `transfer()` callback of token B, recurse into `swap()` again
4. Each recursion credits more B because `reserves[B]` hasn't been decremented yet
5. Repeat until reserves are drained or gas runs out

**Proof-of-concept outline:**
```solidity

    function executeSwap(IAMM pool, address tokenA, address tokenB, uint256 amountIn) external {
        // Approve and swap large amount
        IERC20(tokenA).approve(address(pool), type(uint256).max);
        pool.swap(tokenA, tokenB, amountIn, 0); // 0 outMin = trust us
    }

    // Called by the reentrant token during transfer
    function tokensReceived(address operator, address from, address to,
                           uint256 amount, bytes calldata data, bytes calldata extra) external {
        IAMM(pool).swap(tokenB, tokenA, smallAmount, 0); // Recurse — stale reserves!
    }
}
```

### 2. Balance-of Pricing Manipulation — Severity: **Critical** (Exploitability: High)

Using `token.balanceOf(address(pool))` as the price source for swaps lets any entity temporarily pump the pool's reported balance via a flash loan or direct transfer, then trade at a favorable rate.

```
// VULNERABLE PRICING:
uint256 spotPrice = tokenB.balanceOf(address(pool)) / tokenA.balanceOf(address(pool));
uint256 expectedOutput = amountIn / spotPrice;  // Manipulatable!
```

**Exploit flow:**
1. Flash-loan 1,000,000 token B
2. Deposit token B into the pool (or use any mechanism to inflate balance)
3. Spot price now appears to massively favor token A
4. Swap token A → massive output of token B
5. Withdraw/return flash-loan, pocket the difference

**Another variant — directional manipulation:**
1. Transfer a tiny amount of token B into the pool (cheap)
2. Swap large amount of token A using the artificially inflated B ratio
3. Pool thinks there's tons of B, sells A cheaply
4. Return the borrowed B token, profit on the spread

### 3. First-Depositor Inflation — Severity: **High** (Exploitability: Medium-High)

When a pool bootsstraps with zero initial liquidity, the first depositor sets both the initial reserves AND receives LP shares based on their deposit. If the initial prices don't reflect true market rates (because no prior trades exist), or if the first depositor strategically times their deposit, they capture disproportionate value.

Even more critically: if the pool mints `totalSupply += depositAmount` for the first depositor but the "real" value of reserves is lower (because other users' tokens were donated/injected without corresponding minting), the first depositor's shares represent a larger claim on the pool than they should.

**Attack scenarios:**
- **Front-run a large market move:** Wait for news that sends token X up, immediately deposit both tokens at outdated prices
- **Donation sandwich:** Have accomplice donate token A to distort the ratio, then deposit at the distorted ratio
- **Liquidity theft via donation mismatch:** If `deposit()` accepts donations but doesn't mint proportional shares (or mints less than it should), early LP holders steal value from all future LP holders

**Exploit outline:**
```solidity

function donateTokenA(address token, uint256 amount) external onlyOwner {
    IERC20(token).safeTransferFrom(msg.sender, address(this), amount);
    // No LP shares minted — pure free liquidity injection!
}

// Then attacker deposits normal liquidity:
function deposit(address tokenA, address tokenB) external {
    uint256 shares = ... // calculated based on now-inflated reserves
    // These shares claim a % of the pool that includes donated funds!
}
```

### 4. Unrestricted Token Donations — Severity: **High** (Exploitability: Medium)

Accepting arbitrary token donations without minting corresponding LP shares is a direct vector to dilute existing LP holders.

```
// VULNERABLE:

    // Reserves increase but NO new shares are minted
    // Existing LP holders are diluted!

// Subsequent legitimate deposit:
function deposit(...) external {

    // All old LP holders lose percentage ownership

**Exploit:** An attacker with no desire to LP can donate tokens to inflate reserves, making future LP deposits cheap (they'd get lots of shares for little). Meanwhile, existing LP holders' percentages shrink. The attacker might then help a friend deposit and split the stolen value.

### 5. No Slippage Bounds (Frontend Quoting) — Severity: **High** (Exploitability: Medium-High)

Quoting trades without `amountOutMin` exposes users to:
- **MEV sandwich attacks:** Bot sees pending buy, buys ahead (front-run), user executes at worse price, bot sells after (back-run)
- **State changes between quote and execution:** Price moves because of other traders
- **Explicit front-running of the swap transaction itself**

Without `amountOutMin`, there is literally no protection — the contract will execute regardless of how unfavorable the outcome.

### 6. Missing Deadline Protection — Severity: **Medium** (Exploitability: Medium)

No deadline means an attacker can hold a transaction in mempool for extended periods (via gas bumping tools or just waiting), executing when conditions are most favorable. This is particularly dangerous during volatile markets or right after manipulation.

---

### 7. No Emergency Pause — Severity: **Medium** (Exploitability: Medium)

Once an exploit is discovered, without a pause mechanism attackers have unlimited time to extract value. Even if the bug is fixed, past transactions remain valid. A well-tested pause allows incident response.

---

### 8. Access Control Gaps — Severity: **Medium** (Exploitability: Variable)

If fee setters, pausers, or token listings are not properly access-controlled (not using OpenZeppelin's `Ownable2Step` or roles), any address could:
- Set fees to 0% (attracting volume) then back to maximum (harvesting from LPs)
- Whitelist/remove arbitrary tokens
- Pause/unpause at will

---

### 9. No Flash-Loan / TWAP Oracle — Severity: **Medium** (Exploitability: Low-Medium)

Without a time-weighted average price mechanism, spot-price readings are trivially manipulable within a single block. Any pool relying on instantaneous ratios is subject to oracle manipulation attacks within the same tx.

---

### 10. Overflow Underflow Risk — Severity: **Low** (Exploitability: Low, but catastrophic)

In pre-Solidity 0.8.0 code (or manually computed divisions/multiplications), reserve math involving `(reserveA * amountIn)` could overflow uint256. Similarly, `totalSupply - mintAmount` underflows if mintAmount > totalSupply due to bad logic.

---

### 11. Integer Division Truncation — Severity: **Low** (Exploitability: Low)

Constant-product math involves division that truncates. Without careful implementation (using `mulDiv` with sufficient precision), repeated small swaps cause cumulative drift that benefits one party and harms LPs.

### Attack Paths Enumerated & Ranked

#### 🔴 CRITICAL 1: Donation/Inflation Attack (Exploitability: TRIVIAL)

**Mechanism:** Attacker sends unrelated or worthless tokens to the pool, inflating `reserveIn`. The spot price formula `(reserveIn * FIXED_POINTS) / reserveOut` now shows an artificially high price for the output token. The attacker then swaps at the manipulated rate, extracting genuine value. A second variant — the "first-depositor inflation" — occurs when the attacker provides a small amount of LP tokens but the first depositor's deposit is calculated against the inflated reserve, minting far fewer shares than fair.

**Impact:** 90%+ drain possible with minimal capital.

**Proof sketch:** Pool holds 100k USDC / 100k DAI. Attacker donates 1M fake tokens → reserveIn becomes ~1.1M → price shifts → attacker swaps 10k USDC for ~11k DAI instead of ~10k → repeats until price resets.

---

#### 🔴 CRITICAL 2: Flash-Loan Oracle Manipulation (Exploitability: TRIVIAL)

**Mechanism:** If pricing relies on any on-chain DEX spot price read at block time, a single transaction can flash-loan enormous liquidity, push the price to any desired level, trade against the manipulated price in your AMM, and unwind the flash loan in the same transaction.

**Impact:** Complete price extraction; identical to the bZx, Harvest Finance, and Sushiswap flash-loan exploits.

---

#### 🟠 HIGH 3: Reentrancy During Swap Settlement (Exploitability: MODERATE)

**Mechanism:** Updating `userBalances` before transferring tokens means the user's state is out of sync if a malicious token's `transfer` hook calls back into the contract. The attacker enters `swap()` again while the first call hasn't settled reserves, potentially double-withdrawing or corrupting reserve math.

**Impact:** Selective drain depending on callback design.

---

#### 🟠 HIGH 4: Slippage-Free Quoting (Exputability: HIGH)

**Mechanism:** Front-end quotes trades without `amountOutMin` bounds. During high volatility or MEV front-running, users' transactions execute at far worse rates than quoted. An attacker can also sandwich-attack by positioning between the quote and execution.

**Impact:** Economic loss per trade; compounding with volume.

---

#### 🟡 MEDIUM 5: Integer Underflow/Overflow in Reserve Math (Exploitability: LOW-MODERATE)

**Mechanism:** Naive `(a * b) / c` arithmetic overflows at large values (e.g., reserves > 2^128). Without `FullMath.mulDiv` or similar safe primitives, intermediate multiplication wraps.

**Impact:** Price calculation returns garbage; potential for free swaps.

---

#### 🟡 MEDIUM 6: Unrestricted Admin Controls (Exploitability: CONDITIONAL)

**Mechanism:** If fee setters or pause functions exist without proper access control (or using simple `msg.sender == owner` without ownership transfer confirmation), the admin key compromise leads to full fund drain.

**Impact:** Full protocol compromise if admin key is exposed.

A constant-product AMM maintains `x * y = k` where `x` and `y` are the reserves of two ERC-20 tokens. A correct swap prices against internal reserve state, preserves CEI (Check-Effects-Interactions) ordering, and rejects external manipulations of those reserves.

## 2. Attack Path Enumeration & Exploitability Ranking

### Attack 1 — Donation-Inflation Price Manipulation (CRITICAL / Trivial)

**Mechanism.** The swap function reads price from `IERC20(token).balanceOf(pool)` as if that equals the pool's reserve. An attacker donates (or buys then donates) large amounts of one token to the pool address. The inflated balance makes the pool appear deeper than it is, so the swap function calculates an exchange rate that heavily favors the attacker.

Concrete flow:
```
1. Attacker has 1 ETH, pool has 100 USDC, 100 ETH
2. Attacker calls donate(5000 ETH) → pool balance now shows 5010 ETH
3. Attacker swaps 1 USDC → contract thinks pool has tons of ETH, mints ~5000 "shares" for 1 USDC worth
4. Pool's true reserves still 100/100; LPs' claims diluted massively

**Impact:** Complete drain of LP value through inflation-share math.  
**Exploitability:** ★★★★★ Trivial — requires only calling `transfer` to self. No oracle or flash loans needed.  
**Root cause:** Share calculation depends on `balanceOf(address(this))` instead of actual deposited amount at call time.

### Attack 2 — Reentrancy Drain via Pre-Interaction State Mutation (CRITICAL / Trivial)

**Mechanism.** The vulnerable swap follows:

```solidity
function withdraw(uint256 amount) external {

**Impact:** Unbounded withdrawal up to the pool's total liquidity.  
**Exploitability:** ★★★★★ Trivial — standard reentrancy primitive.

**Exploitability:** ★★★★☆ Requires understanding front-end flow; exploit window narrow but repeatable.

**Exploitability:** ★★★☆☆ Requires MEV infrastructure.
