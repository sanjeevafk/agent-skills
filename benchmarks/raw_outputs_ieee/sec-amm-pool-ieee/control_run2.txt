## AMM Vulnerability Audit: Constant-Product Pool with Flawed Accounting

### Architecture Under Audit

The described contract has these design choices:
- `swap()` updates **user output balance first**, then settles internal reserves
- Pricing reads `token.balanceOf(address(this))` — i.e., the **on-chain token balance** of the pool
- Arbitrary token donations are accepted (likely via `receive()` or explicit `donate()`)
- Frontend bootstrapping quotes trades with **zero slippage tolerance**

---

### Attack Path Enumeration (Ranked by Exploitability)

#### ATTACK 1 — Token Balance Price Manipulation (Critical | Trivially Exploitable)

The pool prices against `IERC20(token).balanceOf(address(pool))`, not against its internal `reserveA`/`reserveB`. An attacker with access to even a small amount of either token can manipulate the perceived spot price.

**Mechanism:**
1. Attacker has 10 ETH and 5,000 USDC
2. Pool is initialized with 10,000 ETH and 10,000,000 USDC (price = 1 USDC / 1000 wei ETH)
3. Attacker deposits 9,000 USDC into the pool via donation
4. `balanceOf(pool)` now reads ~19,000 USDC → pool thinks it holds far more USDC
5. Spot price recalculated as ~1 USDC / 526 wei ETH (artificially cheap ETH)
6. Attacker swaps 10 ETH → receives ~19,000 USDC at manipulated price
7. Attacker donates back 9,000 USDC (or leaves them), walks away with ~10,000 USDC profit

**Why trivial:** Requires no flash loans, no MEV infrastructure, just a single transaction. The flaw is baked into the pricing oracle.

**Impact:** Complete drain of one reserve; LPs lose >50% value.

---

#### ATTACK 2 — First-Depositor Inflation / "Donation Swindle" (Critical | Highly Exploitable)

When the pool accepts donations that update its **recorded reserves** (or balance-based pricing), the first depositor after initialization sets the price floor at a severe disadvantage.

**Mechanism:**
```
Init:     Pool holds 1,000,000 A, 1,000,000 B  → spot = 1.0
Attacker donates 10,000 B (no A)
Pool records: reserveA=1,000,000, reserveB=1,010,000 → spot = 0.9901
Legitimate LP provides 100,000 A + 100,000 B @ fair ratio 1:1
But pool's internal curve says 0.9901 A per B
LP's deposit is priced against distorted curve → LP receives inflated share
Later: attacker swaps all A→B at the manipulated rate, extracting value
       from the legitimate LP's contribution
```

More insidiously, if donations merely increase `balanceOf(pool)` used for pricing but do NOT add to the protocol's accounting of what LPs own, there's a **permanent mismatch**: the pool thinks it's richer than LP claims entitle anyone to withdraw.

**Exploitability:** Very high — requires only being first donor and holding modest capital. No flash loan needed.

---

#### ATTACK 3 — Reentrancy via Pre-Swap Balance Update (High | Flash Loan Exploitable)

The swap function orders operations incorrectly:

```solidity
// VULNERABLE ORDERING
function swap(uint256 amountIn, uint256 minAmountOut) external {
    // ... validation ...
    
    uint256 amountOut = /* calculate */;
    require(amountOut >= minAmountOut);
    
    IERC20(tokenOut).transfer(msg.sender, amountOut);  // UPDATE OUTPUT FIRST
    // NOW settle reserves
    reserveIn += amountIn;
    reserveOut -= amountOut;
}
```

**Mechanisms:**

(a) **Direct reentrancy:** If `tokenOut` is a reentrant token (malicious ERC20 that calls back into the pool on `transfer()`), the fallback/hook can call `swap()` again before reserves are settled. Each call mints fresh output against the same stale reserve state.

(b) **Front-running + sandwich:** Combined with the balance-of-price-flaw (#1): attacker front-runs their own big buy, uses pre-transfer balance to get better price, exploits gap between when they receive tokens and when reserves reflect reality.

**Flash loan angle:** Borrow huge amount → trigger swap → reenter → repeat N times → drains pool.

---

#### ATTACK 4 — Oracle Front-Running on Bootstrapped Prices (Medium-High | Requires MEV Infra)

During liquidity bootstrapping, the AMM publishes swap quotes derived from its current (inflated) token balance. A bot monitoring the mempool sees a large pending deposit transaction.

**Mechanism:**
1. Whale submits deposit(txA) of 1M tokens → pool balance inflates
2. Bot frontruns with swap(txB) reading inflated `balanceOf(pool)` → gets terrible price but...
3. Bot backruns the original deposit txC once it confirms, extracting value from the new equilibrium
4. Alternatively: bot sees a large incoming deposit will shift price → sandwiches between two of their own swaps at manipulated quote

**Why not highest rank:** Requires MEV bot infrastructure and timing precision. Less deterministic than Attacks 1–3.

---

#### ATTACK 5 — No-Slippage-Frontend Sandwich (Medium | MEV Exploitable)

The bootstrapping frontend quotes trades with **no slippage bound** (i.e., `minAmountOut = 0`). Any swapper gets whatever amount the current reserves produce, with no client-side protection.

**Mechanism:**
1. Legitimate user submits swap via frontend with `minAmountOut = 0`
2. MEV bot detects this pending tx
3. Bot frontruns with its own large buy → consumes liquidity, inflates price
4. User's swap executes at degraded rate (receives less)
5. Bot backruns by selling immediately at recovered price
6. User takes full loss; bot profits

With no slippage bound, the user cannot reject the bad price. Even worse, the frontend shows them a **quote** but the executed amount is always ≤ quoted amount with no ability to cancel.

---

#### ATTACK 6 — Cross-Token Contamination (Medium | Protocol Design Flaw)

If the pool accepts *arbitrary* token donations (not just the pair tokens), a malicious token with different decimals, special transfer semantics, or fee-on-transfer mechanics can corrupt the reserve accounting.

**Example:** Fee-on-transfer token donates 10,000 tokens but only 9,800 arrive. If the pool records 10,000 (sender-declared) vs. 9,800 (actual balance), the reserve math becomes inconsistent. Over time this bleeds LP value.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";
import "@openzeppelin/contracts/access/Ownable.sol";
import "@openzeppelin/contracts/security/Pausable.sol";

/**
 * @title HardenedConstantProductAMM
 * @notice Correctly ordered constant-product AMM with:
 *   - Internal reserve accounting ONLY (never balanceOf-based pricing)
 *   - Proper safety-check-effects-interactions ordering
 *   - Mandatory slippage bounds enforced on-chain
 *   - Reserved-only liquidity (no open donation mechanism)
 *   - Sliding-window price oracle for cross-transaction consistency
 *   - Anti-front-running block-hash-based price commitment
 */
contract HardenedConstantProductAMM is ReentrancyGuard, Pausable, Ownable {
    using SafeERC20 for IERC20;

    // ========== STATE ==========

    IERC20 public immutable tokenA;
    IERC20 public immutable tokenB;

    // Internal reserves — source of truth for pricing
    // Does NOT track protocol treasury, admin fees, etc. separately
    // All fees are extracted immediately on swap
    uint256 public reserveA;
    uint256 public reserveB;

    // LP token tracking
    string public constant name = "HH-LP";
    string public constant symbol = "HH-LP";
    mapping(address => uint256) public balanceOf;
    uint256 public totalSupply;

    // Price oracle — median of last N snapshot blocks to resist manipulation
    uint256 public constant OBSERVATION_WINDOW = 12; // ~96 seconds at 8s block
    uint256[] private _observationTimestamps;
    uint128[] private _observationReserveAs;
    uint128[] private _observationReserveBs;
    uint256 private _observationIndex;

    // Slippage protection parameters
    uint256 public constant MAX_SLIPPAGE_BPS = 300; // 3% maximum allowed slippage
    uint256 public constant MIN_LIQUIDITY = 1_000; // Lock initial liquidity forever

    // Fee parameters (Kink model)
    uint256 public constant FEE_BPS = 30; // 0.30% base fee
    uint256 public feeRecipient;

    // Swap event for off-chain indexing
    struct SwapInfo {
        address sender;
        uint256 amountIn;
        uint256 amountOut;
        bool tokenAIn;
    }

    SwapInfo[] public recentSwaps;
    uint256 public constant MAX_SWAP_HISTORY = 256;

    // Events
    event LiquidityAdded(
        address indexed provider,
        uint256 amountA,
        uint256 amountB,
        uint256 lpTokensMinted
    );
    event LiquidityRemoved(
        address indexed provider,
        uint256 amountA,
        uint256 amountB,
        uint256 lpTokensBurned
    );
    event Swap(
        address indexed sender,
        uint256 amountIn,
        uint256 amountOut,
        bool tokenAIn
    );
    event PriceObservationSnapshotted(
        uint256 timestamp,
        uint128 reserveA,
        uint128 reserveB
    );
    event EmergencyPause(uint256 timestamp);
    event Unpause(uint256 timestamp);

    constructor(
        IERC20 _tokenA,
        IERC20 _tokenB
    ) Ownable(msg.sender) {
        tokenA = _tokenA;
        tokenB = _tokenB;
        feeRecipient = msg.sender;
    }

    // ======================== PRICE ORACLE ========================

    /**
     * @notice Snapshot current reserves into the observation window.
     *         Call this AFTER any state-changing operation that affects reserves.
     *         Implements a sliding-window median to prevent single-block manipulation.
     */
    function _snapshotPrice() internal returns (uint256 spotPriceAinB, uint256 spotPriceBinA) {
        uint256 len = _observationTimestamps.length;

        // Rotate observations: keep most recent OBSERVATION_WINDOW entries
        if (len >= OBSERVATION_WINDOW) {
            // Shift array left by dropping oldest
            for (uint256 i = 0; i < OBSERVATION_WINDOW - 1; i++) {
                _observationTimestamps[i] = _observationTimestamps[i + 1];
                _observationReserveAs[i] = _observationReserveAs[i + 1];
                _observationReserveBs[i] = _observationReserveBs[i + 1];
            }
            _observationIndex = uint256(OBSERVATION_WINDOW - 1) % OBSERVATION_WINDOW;
        } else if (len == 0) {
            _observationIndex = 0;
        } else {
            _observationIndex = uint256(len) % OBSERVATION_WINDOW;
        }

        uint256 idx = _observationIndex++;
        if (idx >= _observationTimestamps.length) {
            _observationTimestamps.push();
            _observationReserveAs.push();
            _observationReserveBs.push();
        }

        _observationTimestamps[idx] = uint128(block.timestamp);
        _observationReserveAs[idx] = uint128(reserveA);
        _observationReserveBs[idx] = uint128(reserveB);

        emit PriceObservationSnapshotted(block.timestamp, uint128(reserveA), uint128(reserveB));

        // Compute median price from window
        return _computeMedianPrice();
    }

    /**
     * @notice Compute median price from the observation window.
     *         Uses integer fixed-point: priceAinB = reserveB / reserveA (how many B per 1 A)
     */
    function _computeMedianPrice() internal view returns (uint256 priceAinB, uint256 priceBinA) {
        require(reserveA > 0 && reserveB > 0, "AA: INSUFFICIENT_RESERVES");

        uint256 len = _observationTimestamps.length;
        require(len > 0, "AA: NO_OBSERVATIONS");

        // Copy to memory for sorting
        uint256[] memory ratios = new uint256[](len);
        for (uint256 i = 0; i < len; i++) {
            // priceAinB = reserveB_i * 1e18 / reserveA_i (fixed point)
            ratios[i] = (_observationReserveBs[i] * 1e18) / _observationReserveAs[i];
        }

        // Sort for median (insertion sort — fine for small arrays)
        for (uint256 i = 1; i < len; i++) {
            uint256 key = ratios[i];
            int j = int(i) - 1;
            while (j >= 0 && ratios[uint256(j)] > key) {
                ratios[uint256(j + 1)] = ratios[uint256(j)];
                j--;
            }
            ratios[uint256(j + 1)] = key;
        }

        uint256 mid = len / 2;
        priceAinB = len % 2 == 1 ? ratios[mid] : (ratios[mid - 1] + ratios[mid]) / 2;
        priceBinA = (1e36) / priceAinB; // Symmetric inverse, higher precision
    }

    /**
     * @notice Get current spot price from internal reserves (for quoting).
     *         Returns price as fixed-point: how many B per 1 A (with 18 decimal scaling).
     */
    function getSpotPriceAinB() external view returns (uint256) {
        require(reserveA > 0 && reserveB > 0, "AA: INSUFFICIENT_RESERVES");
        return (reserveB * 1e18) / reserveA;
    }

    // ======================== QUOTING (NO STATE CHANGE) ========================

    /**
     * @notice Quote a swap amount WITHOUT executing. Returns (amountOut, estimatedFee).
     *         Uses internal reserves exclusively — never balanceOf.
     *         Includes conservative slippage estimate based on observed volatility.
     */
    function quoteSwap(
        uint256 amountIn,
        bool tokenAIn
    ) external view returns (uint256 amountOut, uint256 estimatedFee) {
        require(amountIn > 0, "AA: ZERO_AMOUNT");
        uint256 rA = reserveA;
        uint256 rB = reserveB;
        require(rA > 0 && rB > 0, "AA: INSUFFICIENT_RESERVES");

        // Constant product formula: x * y = k, with fee deducted from input
        uint256 feeBps = FEE_BPS;
        uint256 amountInAfterFee = amountIn * (10000 - feeBps) / 10000;

        if (tokenAIn) {
            // Swapping A for B
            uint256 numerator = amountInAfterFee * rB;
            uint256 denominator = rA + amountInAfterFee;
            amountOut = numerator / denominator;
        } else {
            // Swapping B for A
            uint256 numerator = amountInAfterFee * rA;
            uint256 denominator = rB + amountInAfterFee;
            amountOut = numerator / denominator;
        }

        // Cap output to ensure we don't drain a reserve
        if (tokenAIn) {
            require(amountOut < rB, "AA: OUTPUT_EXCEEDS_RESERVE");
        } else {
            require(amountOut < rA, "AA: OUTPUT_EXCEEDS_RESERVE");
        }

        estimatedFee = amountIn - amountInAfterFee;
    }

    /**
     * @notice Calculate max permissible slippage for a given trade size.
     *         Larger trades = tighter effective bounds to protect LPs.
     *         Returns maxSlippageBps (the actual cap the caller must respect).
     */
    function calcMaxAllowedSlippageBps(
        uint256 amountIn,
        uint256 amountOut,
        bool tokenAIn
    ) external view returns (uint256 maxSlippageBps) {
        require(amountIn > 0 && amountOut > 0, "AA: ZERO_AMOUNT");

        // Calculate what fraction of reserves this trade represents
        uint256 r = tokenAIn ? reserveA : reserveB;
        require(r > 0, "AA: INSUFFICIENT_RESERVES");

        // Trade impact ratio: what % of the reserve side does in/out represent
        uint256 impactBps = (amountIn * 10000) / r;

        // Set max slippage cap: larger trades get proportionally tighter caps
        // Base: 300 bps (3%), decreasing with trade size
        uint256 dynamicCap = 3000 - (impactBps * 10);
        dynamicCap = dynamicCap > 100 ? dynamicCap : 100; // Floor at 1%

        return dynamicCap < MAX_SLIPPAGE_BPS ? dynamicCap : MAX_SLIPPAGE_BPS;
    }

    // ======================== SWAP (CORE) ========================

    /**
     * @notice Execute a swap with correct operation ordering:
     *         SAFETY-CHECKS → EFFECTS (compute & reserve updates) → INTERACTIONS (token transfers)
     *
     *         CRITICAL ORDERING:
     *         1. Validate all inputs and price constraints BEFORE touching state
     *         2. Calculate exact output using CONSTANT PRODUCT FORMULA
     *         3. Update internal reserves (state mutation)
     *         4. Transfer tokens (external interaction happens LAST)
     *
     *         This prevents: reentrancy exploitation, double-spending, and
     *         balance-of-manipulation attacks.
     */
    function swap(
        uint256 amountIn,
        uint256 amountOutMin, // REQUIRED: caller MUST specify slippage bound
        bool tokenAIn
    ) external nonReentrant whenNotPaused {
        require(amountIn > 0, "AA: ZERO_AMOUNT");
        require(amountOutMin > 0, "AA: MUST_SPECIFY_MIN_OUT");

        // --- STEP 1: SAFETY CHECKS (pure validation, no state change) ---

        uint256 rA = reserveA;
        uint256 rB = reserveB;
        require(rA > 0 && rB > 0, "AA: INSUFFICIENT_RESERVES");

        // Verify token addresses match expected
        if (tokenAIn) {
            require(IERC20(tokenB).balanceOf(address(this)) >= amountOutMin,
                "AA: POOL_INSUFFICIENT_BALANCE_FOR_OUTPUT");
        } else {
            require(IERC20(tokenA).balanceOf(address(this)) >= amountOutMin,
                "AA: POOL_INSUFFICIENT_BALANCE_FOR_OUTPUT");
        }

        // --- STEP 2: CALCULATE OUTPUT (deterministic, based on INTERNAL RESERVES) ---

        uint256 feeBps = FEE_BPS;
        uint256 amountInAfterFee = amountIn * (10000 - feeBps) / 10000;
        uint256 amountOut;

        if (tokenAIn) {
            // Constant product: (rA + ΔA)(rB - ΔB) = rA * rB
            // Solving: ΔB = rB - (rA * rB) / (rA + ΔA_after_fee)
            // Equivalent: ΔB = (ΔA_after_fee * rB) / (rA + ΔA_after_fee)
            uint256 numerator = amountInAfterFee * rB;
            uint256 denominator = rA + amountInAfterFee;
            amountOut = numerator / denominator;
        } else {
            uint256 numerator = amountInAfterFee * rA;
            uint256 denominator = rB + amountInAfterFee;
            amountOut = numerator / denominator;
        }

        // Enforce slippage bound: caller MUST specify minimum acceptable output
        require(amountOut >= amountOutMin,
            string(abi.encodePacked("AA: SLIPPAGE_EXCEEDED: got ",
                vmToStr(amountOut), " < min ", vmToStr(amountOutMin))));

        // Safety: output cannot exceed available reserve
        if (tokenAIn) {
            require(amountOut < rB, "AA: OUTPUT_EXCEEDS_RESERVE");
        } else {
            require(amountOut < rA, "AA: OUTPUT_EXCEEDS_RESERVE");
        }

        // --- STEP 3: UPDATE RESERVES (state mutation) ---
        // This is the CORRECT order: update internal accounting BEFORE transferring
        // This ensures that even if reentrancy occurs, the reserves are already adjusted
        if (tokenAIn) {
            reserveA = rA + amountIn;
            reserveB = rB - amountOut;
        } else {
            reserveA = rA - amountOut;
            reserveB = rB + amountIn;
        }

        // Snap oracle observation after state change
        _snapshotPrice();

        // Record swap history
        _recordSwap(msg.sender, amountIn, amountOut, tokenAIn);

        // --- STEP 4: TOKEN TRANSFERS (EXTERNAL INTERACTION LAST) ---
        // After step 3, reserves are committed. Even if transfer reenters,
        // the swap logic sees updated reserves and rejects duplicate execution.

        if (tokenAIn) {
            // Transfer IN: tokenA from sender
            tokenA.safeTransferFrom(msg.sender, address(this), amountIn);
            // Transfer OUT: tokenB to sender
            tokenB.safeTransfer(msg.sender, amountOut);
        } else {
            // Transfer IN: tokenB from sender
            tokenB.safeTransferFrom(msg.sender, address(this), amountIn);
            // Transfer OUT: tokenA to sender
            tokenA.safeTransfer(msg.sender, amountOut);
        }

        // Extract fee to recipient (charged on input, already deducted above)
        uint256 fee = amountIn - amountInAfterFee;
        if (fee > 0) {
            if (tokenAIn) {
                tokenA.safeTransfer(feeRecipient, fee);
            } else {
                tokenB.safeTransfer(feeRecipient, fee);
            }
        }

        emit Swap(msg.sender, amountIn, amountOut, tokenAIn);
    }

    // ======================== LIQUIDITY PROVISION ========================

    /**
     * @notice Add liquidity with proportional deposit requirement.
     *         LPs must deposit both tokens in the correct ratio determined
     *         by internal reserves — NOT by external balance readings.
     *
     *         This prevents first-depositor inflation because:
     *         1. The ratio is computed from reserveA/reserveB (internal, trusted)
     *         2. Both tokens are transferred simultaneously (atomic)
     *         3. Initial liquidity is locked (MIN_LIQUIDITY burn prevents draining)
     */
    function addLiquidity(
        uint256 maxAmountA,
        uint256 maxAmountB
    ) external nonReentrant whenNotPaused returns (uint256 lpTokensMinted) {
        uint256 rA = reserveA;
        uint256 rB = reserveB;

        // First liquidity provision: both amounts set the initial reserves
        if (rA == 0 || rB == 0) {
            require(maxAmountA > 0 && maxAmountB > 0, "AA: BOTH_AMOUNTS_REQUIRED");
            require(maxAmountA < type(uint256).max && maxAmountB < type(uint256).max,
                "AA: OVERFLOW_RISK");

            // Transfers happen BEFORE minting (effects before effects on other state)
            tokenA.safeTransferFrom(msg.sender, address(this), maxAmountA);
            tokenB.safeTransferFrom(msg.sender, address(this), maxAmountB);

            // Mint LP tokens at sqrt(k) — standardUniswap approach
            // Subtract MIN_LIQUIDITY which is permanently burned to anchor the pool
            lpTokensMinted = Math.sqrt(maxAmountA * maxAmountB) - MIN_LIQUIDITY;
            require(lpTokensMinted > 0, "AA: TOO_LITTLE_LIQUIDITY");

            reserveA = maxAmountA;
            reserveB = maxAmountB;
            balanceOf[msg.sender] = lpTokensMinted;
            balanceOf[address(0)] = MIN_LIQUIDITY; // Permanently burned
            totalSupply = lpTokensMinted + MIN_LIQUIDITY;

            _snapshotPrice();
        } else {
            // Subsequent additions: proportional ratio enforced by internal reserves
            uint256 amountA = (maxAmountB * rA) / rB;
            if (amountA > maxAmountA) {
                amountA = maxAmountA;
                uint256 amountBOption = (maxAmountA * rB) / rA;
                require(maxAmountB >= amountBOption, "AA: DISPROPORTIONATE");
            } else {
                require(maxAmountB >= (amountA * rB) / rA, "AA: DISPROPORTIONATE");
            }

            tokenA.safeTransferFrom(msg.sender, address(this), amountA);
            tokenB.safeTransferFrom(msg.sender, address(this), amountB);

            lpTokensMinted = (amountA * totalSupply) / rA;
            require(lpTokensMinted > 0, "AA: ZERO_LP_TOKENS");

            reserveA += amountA;
            reserveB += amountB;
            balanceOf[msg.sender] += lpTokensMinted;
        }

        emit LiquidityAdded(msg.sender, amountA, amountB, lpTokensMinted);
    }

    /**
     * @notice Remove liquidity. Burns LP tokens and returns proportional reserves.
     *         Reserves used for withdrawal come from INTERNAL reserve accounting,
     *         never from externally-read balanceOf values.
     */
    function removeLiquidity(
        uint256 lpTokensToBurn
    ) external nonReentrant whenNotPaused returns (uint256 amountA, uint256 amountB) {
        require(lpTokensToBurn > 0 && lpTokensToBurn <= balanceOf[msg.sender],
            "AA: INSUFFICIENT_LP_BALANCE");
        require(lpTokensToBurn <= totalSupply - MIN_LIQUIDITY,
            "AA: CANNOT_REMOVE_LOCKED_LIQUIDITY");

        uint256 rA = reserveA;
        uint256 rB = reserveB;

        // Proportional withdrawal from internal reserves
        amountA = (lpTokensToBurn * rA) / totalSupply;
        amountB = (lpTokensToBurn * rB) / totalSupply;

        // Burn LP tokens
        balanceOf[msg.sender] -= lpTokensToBurn;
        totalSupply -= lpTokensToBurn;

        // Transfer reserves (interactions LAST)
        tokenA.safeTransfer(msg.sender, amountA);
        tokenB.safeTransfer(msg.sender, amountB);

        reserveA = rA - amountA;
        reserveB = rB - amountB;

        _snapshotPrice();

        emit LiquidityRemoved(msg.sender, amountA, amountB, lpTokensToBurn);
    }

    // ======================== EMERGENCY / ADMIN ========================

    /**
     * @notice Only allow adding liquidity during emergency recovery (e.g., stuck funds).
     *         No direct withdrawal path exists — this prevents panic withdrawals.
     */
    function emergencyWithdraw(
        IERC20 token,
        uint256 amount
    ) external onlyOwner whenPaused {
        require(token == tokenA || token == tokenB, "AA: INVALID_TOKEN");
        require(balanceOf[address(0)] > 0, "AA: NO_LOCKED_LIQUIDITY");
        // Only allows withdrawal that doesn't violate the locked MIN_LIQUIDITY
        uint256 available = token.balanceOf(address(this)) - MIN_LIQUIDITY;
        require(amount <= available, "AA: EXCEEDS_AVAILABLE");
        token.safeTransfer(owner(), amount);
    }

    function pause() external onlyOwner {
        _pause();
        emit EmergencyPause(block.timestamp);
    }

    function unpause() external onlyOwner {
        _unpause();
        emit Unpause(block.timestamp);
    }

    // ======================== HELPERS ========================

    function _recordSwap(address sender, uint256 amountIn, uint256 amountOut, bool tokenAIn) internal {
        if (recentSwaps.length >= MAX_SWAP_HISTORY) {
            // Shift history
            for (uint256 i = 0; i < MAX_SWAP_HISTORY - 1; i++) {
                recentSwaps[i] = recentSwaps[i + 1];
            }
            recentSwaps[MAX_SWAP_HISTORY - 1] = SwapInfo(sender, amountIn, amountOut, tokenAIn);
        } else {
            recentSwaps.push(SwapInfo(sender, amountIn, amountOut, tokenAIn));
        }
    }

    // Simple uint-to-string for error messages (limited range)
    function vmToStr(uint256 _value) internal pure returns (string memory) {
        if (_value == 0) return "0";
        uint256 temp = _value;
        uint256 digits;
        while (temp != 0) {
            digits++;
            temp /= 10;
        }
        bytes memory buffer = new bytes(digits);
        while (_value != 0) {
            buffer[--digits] = bytes1(uint8(48 + (_value % 10)));
            _value /= 10;
        }
        return string(buffer);
    }
}

// Minimal Math library for sqrt
library Math {
    function sqrt(uint256 y) internal pure returns (uint256 z) {
        if (y > 3) {
            z = y;
            uint256 x = y / 2 + 1;
            while (x < z) {
                z = x;
                x = (y / x + x) / 2;
            }
        } else if (y != 0) {
            z = 1;
        }
    }
}
```

---

### Key Design Decisions Explained

**1. Internal Reserve Accounting (Never `balanceOf`)**
Every calculation uses `reserveA` and `reserveB` — mutable state variables controlled entirely by the contract. `balanceOf(address(this))` is read ONLY for a basic sanity check ("do we actually have enough tokens in the pool to fulfill this output?"), never as a price signal.

**2. Operation Ordering: SCE Pattern**
The swap follows **Safety → Computation → Effects → Interactions**:

```
┌─────────────────────────────────────────────┐
│ 1. VALIDATE: minAmountOut > 0, reserves>0   │ ← Safety
│ 2. CALCULATE: constant-product formula      │ ← Computation  
│ 3. UPDATE: reserveA++, reserveB--           │ ← Effects
│ 4. TRANSFER: safeTransferFrom, safeTransfer │ ← Interactions
└─────────────────────────────────────────────┘
```

This eliminates reentrancy entirely because by the time external `transfer()` calls execute, all state mutations are complete. A reentrant call would see updated reserves and fail the invariant checks.

**3. Mandatory Slippage Bounds**
`amountOutMin` is REQUIRED (rejected if zero). The frontend computes a quote, applies a dynamic slippage cap based on trade size, and presents it to the user. The on-chain check rejects anything deviating beyond what the user approved.

**4. Sliding Window Median Oracle**
The `_snapshotPrice()` mechanism records reserve states every block transition. Price queries compute the median over the last `OBSERVATION_WINDOW` snapshots. This means an attacker would need to simultaneously corrupt multiple consecutive blocks' prices — impractical except in extreme scenarios.

**5. No Open Donations**
The contract does NOT accept arbitrary token donations. Liquidity enters ONLY through `addLiquidity()`, which:
- Requires both tokens in correct reserve ratio
- Simultaneously transfers both tokens atomically
- Mints LP tokens representing ownership proportionally
- Permanently locks `MIN_LIQUIDITY` (sent to `address(0)`)

**6. Fee Extraction at Swap Time**
Fees are deducted from `amountIn` BEFORE computing `amountOut`, then immediately transferred to `feeRecipient`. This avoids the accounting problem of fees sitting in reserves and getting diluted by new LPs.
