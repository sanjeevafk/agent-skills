## Concrete Attack Audit: Constant-Product AMM Pool

### Architecture Under Review

| Component | What It Does | Why It's Dangerous |
|---|---|---|
| **Swap ordering** | User balance credited *before* reserve transfer | Reentrancy can consume swapped funds repeatedly |
| **Price oracle** | `token.balanceOf(address(this))` read at runtime | Donations shift the pool's apparent reserves → price manipulation |
| **Donation sink** | Any ERC-20 sent to pool address increases reserve count | A single deposit inflates one side of the pair → permanent arbitrage profit for attacker |
| **Frontend quoting** | Trades shown with zero slippage tolerance | Users sign/execute assuming best execution; MEV bots front-run by 1-2% |

### Ranked Attack Paths

#### 1. Donation-Driven Reserve Inflation (CVSS-like severity: Critical — Exploitability: Trivial)

**Attack flow:**

```
attacker deploys TokenB (or sends existing B) directly to the pool:   10,000 B
pool's on-chain reserve_of(B) jumps from 1,000 → 11,000              ← no trade event
attacker swaps tiny amount A → B at now-artificially-rich B price:    0.01 A gets ~9.09 B
arbiter notices mispricing, drains rest of A-side at manipulated rate
attacker profits; legitimate users get brutal slippage
```

**Why it works:** The constant-product formula `x · y = k` is evaluated over stale `balanceOf` reads that conflate pool assets with donations. The invariant was never meant to include non-contribution tokens.

**Fix:** Never derive reserves from `balanceOf`. Use internally tracked `_reserveA` / `_reserveB` that only advance through explicit deposit/swap events. Reject or explicitly ignore incoming transfers that don't come through a typed function.

---

#### 2. First-Depositor Inflation / Ghost Liquidity (Critical — Exploitability: Easy)

**Attack flow:**

```
deployer provides 1,000 A + 1,000 B → receives 1,000 LP shares
(implicit k = 1,000,000)
removes ALL deposited tokens via a "withdraw" that burns LP at face value
→ pool retains 0 actual tokens but k = 1,000,000 is embedded in every swap quote
next depositor provides 100 A, gets quoted ~100 B but pool has nothing to pay
collapses entirely
```

Even without an explicit withdraw, if the pool mints LP tokens equal to min(reserveA, reserveB), a malicious first depositor who already holds a large off-chain position can:

```
deposits 1 A + 1 B → LP = 1
on-chain price now looks like 1:1
drains all real A liquidity by swapping B→A at inflated price
```

This is the classic "first mover exploits initial liquidity ratio" seen in early Uniswap forks and Sushiswap ghost liquidity.

**Fix:** Enforce minimum initial liquidity thresholds; track deposits atomically in a single `addLiquidity(tx.aIn, tx.bIn)` call; do not mint more LP than mathematically justified by the smaller reserve.

---

#### 3. Reentrancy in Swap (High — Exploitability: Easy)

**Attack flow:**

```solidity
// Current (broken) swap ordering
function swap(uint amountIn) external {
    // ... calculate amountOut ...
    
    // BUG: credit buyer FIRST
    balances[msg.sender].tokenB += amountOut;   // user state modified
    
    // Then pull from seller
    tokenA.transferFrom(msg.sender, address(this), amountIn);
    reserves.tokenA += amountIn;                 // reserve update last
}
```

If `balances[msg.sender].tokenB += amountOut` triggers a callback (e.g., `msg.sender` is a contract with `afterSwap()` hook, or the recipient is the caller itself via a self-referential pattern), the reentering call computes `amountOut` against reserves that haven't yet been updated — yielding extra tokens per iteration.

**Fix:** State mutations after external calls. Push, don't pull. Update reserves *before* transferring out.

---

#### 4. Oracle Spot-Price Manipulation via Sandwiched Donations (Medium-High — Exploitability: Moderate)

**Attack flow:**

```
block N: attacker deposits 500K TokenB to pool
block N: attacker calls swap(A→B). Price read uses balanceOf = 500K B
         vs 1K A → ratio skewed 500:1 instead of 1:1
block N+1: attacker removes donation (if donate() exists) or lets it sit
           other LPs bear perpetual dilution
```

Unlike a flash-loan sandwich (which is mitigated by slippage bounds), this permanently distorts the pool's internal accounting until the next round of trading corrects it — but correction costs are socialized across all LPs.

---

#### 5. Frontend Zero-Slippage MEV Extraction (Medium — Exploitability: Trivial for bots)

Any interface showing "you will receive exactly X" without enforcing on-chain slippage gives MEV bots perfect front-running targets. They insert a buy order ahead of the user's transaction, inflating the price, then let the user's trade slip into the worse rate. Result: user gets 0.5-2% less than quoted.

//   user callback fires → read stale balances/reserves → duplicate payout

Outputs to the user must always be written back to storage *before* any `transfer` call that might trigger a callback.

Server-side quoting without `amountOutMin` lets any user submission become a free sandwich target. Bot frontruns, user fills, bot back-runs — zero friction.

On an empty pool (`_totalAssets == 0`), the first depositor sets initial pricing. A frontrunner can capture a small edge, but this is bounded and far less impactful than P1–P3.

# Solidity Constant-Product AMM — Attack Surface Audit & Hardened Implementation

## Vulnerabilities Identified

### 1. Reserve Denominator Inflation via Donations *(Critical — Exploitability: 9/10)*

The pool prices against `token.balanceOf(address(this))`. Anyone can send tokens (donate) to the contract, inflating the reported reserve count, depressing the effective exchange rate on every subsequent swap, and stealing value from legitimate traders.

**Attack:**
1. Deposit fair amount → gets fair shares at correct ratio.
2. Attacker sends 100× the pool's token balance as a "donation."
3. `balanceOf(address(this))` now reflects the injected supply.
4. Every new depositor's shares are minted against this bloated denominator — they receive far fewer shares than they should.
5. The attacker redeems first at the true underlying ratio, pocketing the spread.

The same mechanism destroys LP value if applied to either side of a two-token pool.

### 2. Flash-Lone Spot-Price Manipulation *(Critical — Exploitability: 8/10)*

Swaps priced off the current `balanceOf` snapshot is the classic XY=k AMM oracle problem. An attacker with minimal capital can flash-loan funds to move the price curve mid-swap, then unwind at an advantage on-chain or bridge the displaced value off-chain.

**Attack (two-sided pool):**
1. Flash-loan TokenA.
2. Swap huge amount → drives `price = reserveB / reserveA` massively in attacker's favor.
3. Execute the "real" trade the victim intended at the manipulated price.
4. Reverse the flash-loan; profit = delta between manipulated and fair price.

### 3. Reentrancy — User Balance Updated Before Reserve Settlement *(High — Exploitability: 7/10)*

Updating `userBalances[msg.sender]` *before* adjusting internal reserves violates Check-Effects-Interactions ordering. If the token being transferred is ERC-6900-like (rebasing) or the recipient implements a fallback that calls back into the AMM, the second call reads stale reserves.

**Attack:**
1. Attacker calls `swap()` — function credits their output balance.
2. During the `transfer`, the attacker's contract reenters `swap()`.
3. On re-entry, `reserveA` / `reserveB` still reflect pre-call state → double-spends reserves.
4. Repeat until pool is drained.

### 4. No Slippage Bounds / Deadline *(Medium-High — Exploitability: 6/10)*

Frontend quotes blind trades. Without `amountOutMin` or a `deadline`, MEV bots can sandwich the transaction — front-run with a large buy to inflate price, let the victim's trade execute at a worse rate, then back-run.

### 5. First-Depositor Inflation *(Medium — Exploitability: 5/10)*

If `totalShares` and `_totalAssets` initialize at zero, the first depositor effectively sets the peg. A malicious first depositor can under-deposit (e.g., send only 1 token but claim 1,000 shares), then subsequent depositors inherit an inflated ratio.

## Attack Path Enumeration

### A1: First-Depositor Inflation / Donation Attack — **Exploitability: HIGH**

**Mechanism.** The `deposit()` shares formula divides by `token.balanceOf(address(this))`. Because the pool accepts arbitrary donations, any attacker sends tokens directly to the contract (or tricks users into doing so), inflating the denominator. When legitimate liquidity providers call `deposit()`, their share mint is computed against the inflated balance, so they receive fewer LP shares than their deposited assets warrant. Conversely, if existing LPs can withdraw based on those same inflated reserves, the donor effectively steals value from LPs.

**Concrete example.** Pool: 100k USDC in reserves, 100k shares. Attacker donates 900k USDC → reserve math now reads 1M. LP deposits 10k USDC expecting ~1k shares (1% of pool), gets `10k * 100k / 1M = 1k` shares — correct only if the donated tokens are still in the pool. But when the LP tries to withdraw their 1k shares proportional to 1/101 of the pool, the *real* usable reserve is back to 100k (donated funds are trapped or inaccessible). The LP withdraws ~1k USDC that should have gone to cover the donation, netting profit at other LPs' expense.

**Impact:** Theft from liquidity providers; dilution.  
**Complexity:** Low — requires one donation transaction plus a deposit/withdraw cycle.

### A2: Spot-Price Oracle Manipulation via Flash Loan — **Exploitability: HIGH**

**Mechanism.** The swap prices against `token.balanceOf(address(this))`, a spot read that reflects all tokens held by the contract, including donations and stuck balances. An attacker flash-loans massive amounts of one asset, pushes them into the pool (triggering a donate or direct transfer if the token allows), reads the manipulated spot price, executes the swap at the artificial rate, then unwinds the flash loan. The pool's real reserves are far less than the oracle suggests.

**Concrete example.** Pool has 50k WETH and 50M USDC (1:1000 price). Attacker flash-loans 5M USDC, transfers to pool. Pool balance: 10M USDC (real usable: 5M + 5M borrowed). **Impact:** Direct theft from LP reserve pool proportional to swap size.  
**Complexity:** Low-Medium — standard flash-loan pattern well-documented across DeFi.

**Mechanism.** The swap updates user balances *before* settling internal reserves. If `_executeSwap` calls into the user contract (or if the token used is reentrant), the user can recursively call `swap()` again before reserves are updated, reading stale reserve state each time.

**Impact:** Multi-extraction from a single tx; up to full reserve drain on poorly constrained paths.  
**Complexity:** Medium — requires a malicious receiver contract implementing reentrancy.

**Mechanism.** The liquidity bootstrapping front-end displays trade output computed against current reserves but imposes no `amountOutMin` on-chain. **Impact:** Sandwich losses for honest users; mass extraction during oracle manipulation.  
**Complexity:** Low for sandwiches; requires coordination for front-end exploitation.

### A5: Reserve Underflow / Overflow in Share Math — **Exploitability: LOW**

**Mechanism.** Naive `(assets * totalShares) / balanceOf(...)` arithmetic can overflow on large values before division, especially if the token has high decimals or the pool scales rapidly. **Impact:** Shares mispricing, potential over-withdrawal.  
**Complexity:** Medium — requires specific value ranges and timing.

1. Flash borrow tokens → dump them into the pool to manipulate `balanceOf(address(this))`

3. Repay flash loan from remaining tokens

**Example**: Pool has 100 TOKEN_A, 1000 TOKEN_B. Spot ratio = 1:10. Attacker flash-borrows 50 TOKEN_A, sells into pool. New balance A ≈ 150, new balance B ≈ 667. Effective price degraded to ~1:4.44. Swaps TOKEN_B to TOKEN_A at manipulated price, repays 50 TOKEN_A + fees.
