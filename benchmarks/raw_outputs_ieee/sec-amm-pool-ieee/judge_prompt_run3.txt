### Attack Path 1: First-Depositor Inflation (via Donation Denominator Manipulation)

**Attack flow:**

### Attack Path 2: Oracle Spot-Price Manipulation via Flash Loans

**Severity:** CRITICAL | **Exploitability:** LOW-COST

1. Borrow 10M Token A via Aave or dYdX flash loan.
2. Deposit borrowed tokens into the pool (or simply send them as a donation that inflates `balanceOf`). Pool's reported reserves shift massively.

**Root cause:** Price computation must decouple from instantaneous balance. Use TWAP over ≥15 minutes or a time-weighted average of internal reserves.

**Attack flow:**
1. User initiates swap requesting Token B output.
2. Contract increments `userBalance[msg.sender] += amountOut` and transfers Token B to user.
3. Receiver's fallback fires, calling `getUserBalance(msg.sender)` and triggering a second withdrawal using the still-pending balance credit.

## Vulnerability Inventory

The described pool has **five distinct vulnerability classes**:

1. **Front-run / No Slippage Bounds** — The front-end quotes at mid-price with zero slippage tolerance. Any trade can be MEV-sniped by bots sandwiching legitimate orders.

5. **Unbounded Donation Drift** — Arbitrary token donations that aren't accounted in `reserveA`/`reserveB` create off-chain balance drift. The invariant still operates on stale reserves while the contract actually holds more tokens.

        address tokenIn,
        uint256 amountIn,
        uint256 minAmountOut,
        address recipient

            _reserveB -= amountOut;

## ATTACK PATHS RANKED BY EXPLOITABILITY

### 1. Donation-Driven Inflation Attack (CRITICAL — Trivial to exploit)

An attacker sends tokens directly to the pool contract outside any deposit flow. Because price is derived from `balanceOf(address(this))`, this inflates the reserve denominator without issuing any shares. The attacker then swaps at a massively favorable rate using their "real" input tokens while the price formula thinks there's far more liquidity than actually exists.

```

attacker_donates(1_000_000 tokens)   // inflates balanceOf denominator
swap(give_500_tokens, get_residue)    // pays real value, receives manipulated price
```

### 2. Flash Loan Oracle Manipulation (HIGH — Very easy to execute)

If the pool uses its own `balanceOf(address(this))` as the oracle source for spot price (a classic constant-product trap), an attacker borrows massive amounts of token A via a flash loan, deposits it into the pool (or triggers any function that affects the balance), reads the inflated/deflated price, executes the swap, then reverses everything in the same transaction. The price spike gives them deeply out-of-the-money output tokens before the balance is restored.

Even if the pool claims to use an external pool's spot price, if that external pool is also a thin constant-product pool, the same flash-loan sweep applies.

### 3. Reentrancy + CEI Violation (HIGH — Direct drain)

The swap function updates `userBalances[msg.sender] += amountOut` **before** updating `_reserveB`. When the `safeTransfer` fires, the recipient's fallback (if it's a malicious contract) can call back into `swap()` reentrantly, reading stale reserve state each time and draining the pool until the reentrant call fails with an underflow/insufficient-balance check.

The compound damage comes from the fact that every reentrant call sees the *same* `reserveA / reserveB` ratio because reserves haven't been updated yet. This allows multiplicative extraction beyond the true swap value.

### 4. Front-End Quote Manipulation (MEDIUM — Requires social engineering)

The front-end calculates expected output using the raw on-chain reserve ratio without accounting for slippage or the donation vulnerability. Users following quotes will trade against a manipulated price. Combined with attacks 1–3, this makes the exploitation surface much wider but doesn't create value by itself. An attacker could front-run their own donation by broadcasting a quote-based swap to all users simultaneously.

### 5. Integer Underflow / Overflow in Reserve Math (LOW-MEDIUM — Depends on Solidity version)

Naive `reserveA * amountIn / reserveB` without checked arithmetic overflows on very large inputs before Solidity 0.8.0, or silently wraps in older versions. Not practical in 0.8+ but worth guarding against with `mulDiv` for precision.
