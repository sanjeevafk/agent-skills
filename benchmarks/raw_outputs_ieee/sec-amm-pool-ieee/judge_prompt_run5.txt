### 🟠 Rank 4 — Reordering Bug: User Balance Updated Before Reserve Settlement (Exploitable)

**Mechanism:** The swap function does:
```solidity
// VULNERABLE ORDERING
userBalances[msg.sender][tokenB] += amountOut;   // step 1: committed
// steps 2-3 happen later...

**Exploitability: MODERATE-HIGH.** Requires either reentrancy susceptibility in the withdrawal path, or a transaction failure mid-swap that leaves state inconsistent.

The swap uses `token.balanceOf(address(this))` as the price oracle. The front-end quotes based on current reserves; by the time the user's tx lands, a bot frontruns with a large buy (inflating the price), the user's swap executes at a worse rate, and the bot backruns. This is low-code-exploitability (requires no contract interaction) but high economic impact. It compounds with #3 since a manipulated spot price makes the sandwich even wider.

**5. First-Depositor Inflation (Medium exploitability)**

During bootstrapping, the first depositor gets all LP shares at a minted rate rather than proportional to actual reserves. If the protocol seeds reserves with a mismatched amount (e.g., mints 10,000 shares for 10 ETH but only deposits 5 ETH worth of the paired token), the first depositor overpays. Exploitability depends on how much "free" liquidity the deployer injects vs. what is legitimately deposited.

# Constant-Product AMM Audit — Attack Enumeration & Hardened Implementation

## Threat Model Summary

The contract described has four compounding design flaws:

| Flaw | What it enables |
|---|---|
| User balance updated before reserves | Price calculated on stale/incorrect state; allows sandwich-like re-ordering attacks |
| Spot `balanceOf(address(this))` as price source | Any donor inflating the pool's raw token balance manipulates effective exchange rate |
| Arbitrary token donations accepted | Denominator blow-up in share/math math — the **first-depositor inflation** primitive |
| Front-end quoting without slippage bounds | Users sign/submit trades at prices the MEV extractor will ruthlessly arbitrage |

---

## 1. First-Depositor Inflation Attack (CVSS ~9.0 / Critical)

**Mechanism.** In a constant-product AMM the swap price derives from `(reserveX, reserveY)`. When the contract reads `token.balanceOf(address(this))` to set reserves, an attacker sends tokens from an external wallet *to the contract address* outside the deposit flow. This inflates the balance but does not create corresponding LP shares. The next legitimate depositor then calculates their minted shares against an artificially large denominator, receiving fewer shares than they should—or worse, the next swap reads an inflated reserve, distorting price.

**Concrete scenario:**

```
Pool initial state:  X_reserve = 100_000,  Y_reserve = 100_000   → price = 1.0
Attacker donates:    +500_000 X tokens to address(pool)
Contract sees:       balanceOf = 600_000 ← used as reserve in swap calc
Legitimate trader swaps: gets priced as if deep liquidity exists
LP holder withdraws:  pool actually holds only 100_000 X tokens internally — shortfall exposed
```

**Exploitability: trivial.** No flash loan required; anyone can call a fallback or use `transfer()` into the pool address.

**Fix:** Never derive reserves from `balanceOf`. Track internal accounting (`_reserveX`, `_reserveY`) and reconcile on `deposit()` / `withdraw()` using deltas. Reject unmanaged incoming transfers (see §4 "Receive Guard").

---

## 2. Oracle Spot-Price Manipulation via Flash Loans (CVSS ~8.5 / High)

**Mechanism.** If any function (swap, exit, governance vote) uses `token.balanceOf(address(this))` — i.e., the current pool balance — as the oracle for price, an attacker flash-loans one side of the token pair into the pool, skewing the balance ratio near-instantly, then executes the protected action against the manipulated ratio.

Example — an admin fee withdrawal:

```solidity
// VULNERABLE
uint256 totalValue = xReserve + yReserve; // read from balanceOf
uint256 adminCut   = (adminTax * totalValue) / 1e18;
tokenX.transfer(adminWallet, adminCut);
```

Flash-loan 1 M units of X → pool temporarily looks heavily skewed → adminCut is calculated at a grossly artificial ratio → admin (or attacker impersonating admin logic) walks away with excess tokens. After the tx reverts/reclaims the flash loan, the residual imbalance stays because the admin already received funds.

**Exploitability: high.** Requires flash-loan provider integration (Aave / Uniswap v2), which is standard practice and available for hundreds of millions of dollars.

**Fix:** Use TWAP over multiple periods (≥30 min on Ethereum L1, ≥5 min on L2s) or a Chainlink feed. If on-chain-only, use a *post-swap checkpoint* stored in-state rather than live balance.

---

## 3. Balance-Update-Ordering Reversal (CVSS ~7.8 / High)

**Mechanism.** The swap updates `msg.sender`'s outbound balance *before* deducting from internal reserves:

```solidity
// VULNERABLE ORDER
userOutBalance += amountOut;        // (a) update user state
totalReserveX -= amountIn;          // (b) update reserves
totalReserveY -= amountOut;
_xFee(amountIn);                    // (c) fee taken after user already committed
```

This ordering exposes two problems:

1. **Reentrancy on the user balance credit.** If `amountOut` is paid via `call()` instead of `transfer()`, a malicious receiver's fallback can call back into `swap()` before reserves are decremented, effectively draining more out than was credited. Even with `transfer()`, any future caller replacing transfer with a call inherits this bug.

2. **Stale price between steps.** Any view function called during the interim (by a reentrant call or a nested callback) returns incorrect reserves → the second invocation computes output based on pre-deduction state → the attacker extracts extra tokens.

**Exploitability: medium-high.** Reentrancy requires a payable receiver; pure ordering bugs within a single tx still allow arithmetic edge cases around rounding (see §6).

**Fix:** CEI (Check → Execute → Update) — verify inputs and slippage, perform token transfers last, update internal state before transferring out.

---

## 4. Sandwich Exploit on Front-End Quotes Without Slippage Bounds (CVSS ~7.0 / Medium-High)

**Mechanism.** The front-end fetches the pool spot rate (computed from manipulated reserves per §1–§2) and presents a trade quote. The user submits the transaction with no `amountOutMin` guard or deadline. An MEV bot detects the pending tx, inserts a front-run swap that moves the pool ratio unfavorably, lets the user's trade execute at a worse price, then back-runs the pool to capture the spread.

Without `amountOutMin` and `deadline`, the user's tx is a guaranteed loss to the sandwich — but the protocol itself isn't directly drained. However, compounded across many users, this erodes trust and liquidity. It also means the protocol's off-chain indexer/frontend cannot guarantee quote accuracy.

**Exploitability: high** (MEV bots operate continuously). Protocol-level damage depends on volume; individual-user damage is direct and quantifiable.

**Fix:** Every public swap must require `amountOutMin > 0` and `deadline >= block.timestamp`. The front-end should compute its own expected output and pass the tighter bound.

---

## 5. Arbitrary Donation / Token-Siphoning Injection (CVSS ~7.5 / High)

**Mechanism.** The pool accepts donations of *any* ERC-20 via an unrestricted `receive()` or a generic `donate(address token)` function. Beyond inflating the balance (feeding §1 and §2), this enables:

- **Liquidity poisoning.** Donating a non-standard token (one that charges fees on transfer, returns less than claimed, or lacks a return-code) can corrupt any function that blindly sums or compares balances of accepted donation tokens.
- **Double-spend illusion.** A donation token with broken `balanceOf` semantics makes internal accounting diverge from on-chain reality.

**Exploitability: medium.** Requires sending tokens to the pool; most ERC-20 holders can do this easily. Damage scales with what the pool *does* with donated balances.

**Fix:** Reject all unrecognized tokens. Explicitly whitelist which assets the pool manages, and never touch them unless transferred through the deposit path.

---

## 6. Rounding / Share-Minting Theft (CVSS ~6.5 / Medium)

**Mechanism.** Naive integer division truncates. In a mint flow:

```solidity
// VULNERABLE
shares = (assets * totalShares) / totalAssets;  // truncates DOWN
```

If every deposit truncates down even 1 unit, and there are thousands of deposits, the difference accumulates to significant value lost to whoever controls the remaining numerator — typically the first minter or the protocol treasury. The symmetric bug is in burn, where truncation up causes the protocol to lose asset value.

**Exploitability: low-medium.** Subtle; requires volume or precise timing. Often caught by fuzzer.

**Fix:** Use OpenZeppelin's `FullMath.mulDiv` or equivalent for round-trip-safe math, and prefer ceiling-round for outputs received by users, floor-round for values retained by the protocol. Document rounding direction explicitly.

---

## 7. Missing Access Controls on Fee/Parameters (CVSS ~6.0 / Medium)

**Mechanism.** If the fee setter, pause button, or reserve adjuster is unprotected, anyone can:

- Set fees to 100 % → steal all outgoing tokens
- Pause indefinitely → lock all liquidity
- Call `updateReserves()` to set arbitrary numbers → instantly reprice and drain the pool

**Exploitability: medium-high** if truly permissionless, lower if only `onlyOwner` but owner is EOA (single point of failure).

**Fix:** `Ownable2Step` (explicit acceptOwnership), or multi-sig / timelock for parameter changes.

# AMM Security Audit Report

## 1. Vulnerability Enumeration & Attack Paths

### V1 — CEI Ordering Violation (Critical)

**Location:** Swap function updates user balances/shares *before* reducing internal reserves.

**Attack:** Attacker triggers reentrant call from their token's `transfer` hook between writing their new balance and deducting reserves. In the reentrancy callback they read stale reserve state and execute another swap paying with depleted reserves.

**Exploitability:** HIGH — if the transferred token has a fallback/receive hook (or any mechanism for recursive calls), one swap drains half the pool. Even without a malicious token, the logical invariant (`reserveA * reserveB = k`) breaks mid-swap allowing free arbitrage.

**Severity:** CRITICAL

---

### V2 — Spot Price Oracle Manipulation via Balances (High)

**Location:** `price = token.balanceOf(pool)` used as spot price source for swap pricing.

**Attack:** An attacker with capital sends a large deposit of Token A immediately before calling swap. This inflates `balanceOf(pool)` for A, depressing the reported price of B. They swap B→A at an artificial discount, extracting value proportional to the imbalance they created vs. their swap size.

Concrete example: Pool has 100 A, 100 B. Attacker deposits 900 A → pool reads 1000 A. Spot price says B = 1/10 A (instead of true 1:1). Attacker swaps 50 B → gets priced at 500 A instead of ~50 A. Net: extracted 450 A worth of value.

**Exploitability:** HIGH — single transaction, no special token required, straightforward math.

**Severity:** HIGH

---

### V3 — First-Depositor Inflation / Donation Attack (High)

**Location:** Share minting uses `token.balanceOf(address(this))` (raw balance) rather than tracking actual deposited amount. Arbitrary donations accepted into the pool contract.

**Attack (First Depositor):** Pool starts empty (zero total assets). First depositor puts in 100 tokens but receives shares calculated against zero-or-near-zero supply, getting massive share allocation relative to contribution. Or conversely, if there's an initial liquidity event, someone can front-run to capture disproportionate share ownership.

**Attack (Ongoing Donations):** Any non-participant can send tokens to the pool address. These tokens inflate the denominator (`balanceOf(pool)`) without inflating `_totalAssets`. New depositors' shares are calculated against inflated reserves, meaning they get fewer shares per token. Meanwhile old shareholders retain claims over now-unproductive donated tokens — effectively a transfer of wealth from newcomers to early shareholders.

**Exploitability:** MEDIUM-HIGH — requires two accounts (pool+donor) but costs almost nothing. Damage compounds with pool size.

**Severity:** HIGH

---

### V4 — Missing Slippage Bounds (Medium-High)

**Location:** Frontend quotes trades without requiring `amountOutMin` or `deadline`. On-chain swap likely lacks both checks entirely.

**Attack:** Market moves between transaction submission and block inclusion. MEV bots sandwich the trade. Or an off-chain oracle drifts significantly, making the executed price far worse than quoted. With no `deadline`, stale transactions execute indefinitely.

**Exploitability:** HIGH — automatic via sandwich MEV. Every user swap is potentially exploitable.

**Severity:** MEDIUM-HIGH

---

### V5 — No Access Control on Admin Functions (Medium)

**Location:** Fee parameters, pause state, and pool parameters modifiable by anyone.

**Attack:** Any caller sets fees to 0% (extracting all value) or enables/disables trading. No emergency stop mechanism exists.

**Exploitability:** MEDIUM — trivially executable by any account.

**Severity:** MEDIUM

## Attack Paths (Ranked by Exploitability)

### Critical Severity

#### 1. Token Donation / Balance Inflation Attack (Exploitability: Trivial, cost: ~$0 gas on attacker side if batched)

**Vector:** The contract uses `token.balanceOf(address(this))` as its reserve denominator in share/price math. An attacker (or any external actor) can send an arbitrary number of tokens to the contract address outside the intended deposit flow. This inflates the reported balance while no corresponding shares are minted.

When price = `reserveA / reserveB` and `reserveB` reads from `balanceOf(address(this))`, flooding the contract with token B artificially lowers the price of A in terms of B. Any subsequent swap then exchanges cheap A for expensive B at the stale, manipulated ratio.

Even worse, the deposit function itself becomes vulnerable:

```solidity
// VULNERABLE — denominator includes injected tokens
shares = (assets * totalShares) / token.balanceOf(address(this));
```

An attacker deposits normally at fair price, then floods the contract with tokens, then another honest depositor arrives. The honest depositor pays inflated input but receives shares priced against the inflated (inflated-with-donations) denominator, effectively transferring value from the honest depositor to the already-deposited LPs — including the attacker's position.

**Exploit sequence:**
1. Attacker deposits 100 A / 100 B at fair price → gets 100 shares
2. Attacker sends 10,000 B to the contract (a "donation")
3. Now `balanceOf(address(this))` reports 10,100 B instead of actual usable 100 B
4. Price is computed as `A/B = reserveA / 10100` instead of `reserveA / 100`
5. Attacker (or bot) swaps A → B at the manipulated ratio, getting far more B than fair

**Economic impact:** Full drain proportional to protocol TVL. First-mover advantage compounds since other LPs' withdrawals are also priced at manipulated ratios.

**Severity: CRITICAL** — requires no flash loan, no special permissions, trivially executable.

---

#### 2. Flash Loan + Spot-Price Manipulation (Exploitability: High, cost: modest flash loan fee)

**Vector:** When price is derived from `token.balanceOf(address(this))` rather than an external oracle or tracked reserves, it is identical to using an on-chain spot price. A single flash loan of either token can swing the balance arbitrarily.

```
price_A_in_B = balanceOf(A) / balanceOf(B)
```

Attacker takes a $1M flash loan of B, deposits into the contract (increasing `balanceOf(B)`), executes swap when the price is skewed, repays flash loan, keeps the difference.

This is the exact same mechanic as a Uniswap v1 sandwich but simpler because there is no automated market maker curve protecting you — the pool price IS the balance ratio.

**Severity: CRITICAL** — standard flash-loanable vector; any ETH-denominated AMM is exposed.

---

#### 3. Missing Slippage Bounds / Front-Running (Exploitability: Guaranteed for large trades)

**Vector:** The front-end quotes trades without `amountOutMin` or `deadline`. A user submits a swap for 10 ETH worth of A and the front-end calculates expected output without enforcing a minimum return. During the block window, a MEV bot sees the pending transaction, front-runs with a small buy to shift the price, lets the user's trade execute at a worse rate (extracting value), then back-runs to rebalance.

Without client-side slippage tolerance, even a well-implemented contract cannot protect users. But combined with the reserve-tracking bug (#1), every trade is a free lunch for frontrunners.

**Severity: HIGH** — not a contract vulnerability per se, but guarantees MEV extraction on all non-trivial swaps. Makes the protocol unusable for anything but tiny trades.

---

#### 4. Reentrancy via User-Balance-First Update Pattern (Exploitability: High if swap has external call chain)

**Vector:** If `swap()` updates `balances[user] += amountOut` *before* updating `reserves`, and the update triggers a callback (e.g., if `amountOut` is paid via a transfer to a contract that implements `receive()` or `fallback()`), the reentrant call can read stale reserve state.

Standard ERC-20 `transfer()` does not call back, so this requires the recipient to be a contract or the payment mechanism to involve an external call (like a bridge payout). However, many AMMs have multi-hop effects or integrations where this materializes.

More concretely, if the swap function transfers tokens out *before* debiting reserves:

```solidity
// Vulnerable ordering
userBalances[msg.sender] += amountOut;    // Step 1: state update
token.transfer(msg.sender, amountOut);     // Step 2: external call ← reentry point
_reserves[A] -= amountIn;                 // Step 3: never reached on reenter
```

On re-entry, `_reserves` hasn't been decremented, so the attacker can loop infinitely.

**Severity: HIGH** — depends on whether recipients are contracts, but the pattern is a footgun that will trigger once someone integrates the pool with a contract wallet.

---

#### 5. First-Depositor Ratio Capture (Exploitability: Medium-High at launch)

**Vector:** In a new pool with no liquidity, the first depositor sets the initial price ratio. They can deposit an imbalanced pair (e.g., 1000 A + 1 B) establishing a terrible initial rate, then wait for arbitrageurs to correct the price. Once corrected, the first depositor's LP tokens are under-collateralized, and when they burn their shares they withdraw the corrected reserves — profiting disproportionately.

Alternatively, if the first depositor provides balanced liquidity and the protocol distributes rewards proportionally, having a large initial share at a manipulated ratio means later LPs absorb the dilution.

**Severity: MEDIUM** — only relevant at genesis; mitigated by timelock or multi-sig for first liquidity addition.
