## Concrete Attack Paths (Ranked by Exploitability)

### P0 — First-Depositor Inflation / Donation Manipulation

**Root cause:** The pool prices swaps against `token.balanceOf(address(this))`. An attacker sends raw ERC-20 tokens directly to the pool contract address (or exploits `receive()`/fallback to accept non-native donations). This inflates the reported reserve denominator without issuing LP shares.

**Impact:** Every subsequent depositor/swapper gets pricing that includes the donated tokens. If token B is overpriced because of inflated reserve_B, the attacker swaps B for A at an artificially favorable rate, extracting value proportional to the donation amount.

**Exploitability:** Trivial. Any EOA can send tokens to the contract. No flash loans or MEV bot required for setup.

### P1 — Oracle Spot-Price Manipulation via Flash Loans

**Root cause:** Swaps are priced against instantaneous `balanceOf(address(this))` rather than a TWAP. The constant-product formula `x * y = k` means a single large swap moves the price instantly.

**Attack chain:**
1. Flash loan 10M USDC
2. Swap into ETH through the pool, pushing ETH price up 500%+
3. Sell inflated ETH on external DEXes (Uniswap, Sushi, etc.) or use as collateral
4. Repay flash loan

**Impact:** Arbitrage profit equal to the price difference between manipulated pool price and true oracle price on other venues. Scales with pool depth.

**Exploitability:** High but requires MEV-bot infrastructure. Commonly automated.

### P2 — Reordering Attack (Balance Update Before Reserve Settlement)

**Root cause:** The swap function credits `msg.sender` their output tokens before updating `reserveA`/`reserveB`.

**Attack vector:** Between crediting the user and updating reserves, any callback or external call the user makes sees outdated reserves. Combined with reentrant calls through `safeTransfer` callbacks (ERC-777 tokens) or `transfer` hooks (BEP-20), the attacker can trigger multiple swaps at stale pricing.

**Example:** Attacker's first swap credits them 100 tokens. Before reserves update, they reenter and swap again—the pool calculates output against old (lower) reserves, issuing another 100 tokens for free.

**Exploitability:** Medium-high if target tokens support callbacks/reentrancy; medium otherwise.

### P3 — Slippage-Free Front-End Quote Manipulation

**Root cause:** The front-end displays quoted output amounts with no `amountOutMin` enforced on-chain. A user who signs/approves based on the quote gets executed at any price the transaction malleator extracts.

**Attack vector:** Transaction sandwiching in the mempool. Bot sees the pending swap, fronts it by buying the sold token first, lets the user's swap execute (which hits the now-worse spot price shown by the front-end), then dumps the bought token.

**Impact:** User loses value; pool liquidity degrades as users abandon a front-end that systematically executes worse than displayed.

**Exploitability:** Very high — every sandwichable trade in the mempool. Automated bots run this perpetually.

### P4 — Round-Trip Fee Escape

**Root cause:** Fees accumulate in pool reserves but the fee mechanism uses integer division (`mulDiv`) without proper rounding, allowing accumulated fees to be lost ("rounding drift"). Conversely, if rounding always favors the trader, arbitrageurs extract free value on micro-swaps.

**Impact:** Gradual expropriation of LP value; depends on exact math direction.

**Exploitability:** Low-medium. Requires sustained operation; not a single-exploit payout.

## 1. Attack Path Enumeration

### A1 — Donation Share Inflation (First-Depositor/Flash Donation)
**Priority:** `CRITICAL` | **Exploitability:** `TRIVIAL`

```
Any address sends N tokens directly to the pool.
The pool counts those tokens as its balance, so internal reserve r' = r + N.
When a liquidity provider calls withdraw(), the pool computes their share ratio
using the inflated r', paying them fewer tokens than fair value.
Every legitimate depositor loses proportional value.
The attacker only needs one token to make the math noticeably wrong.
```

This breaks the fundamental AMM invariant: `x * y = k` must hold against honest reserves, not against an external treasury that accepts random charity.

### A2 — Spot Oracle Manipulation via Flash Loan
**Priority:** `CRITICAL` | **Exploitability:** `HIGH`

```
Step 1: Flash loan tokenA → balance spikes on-chain
Step 2: Call swap(tokenB → tokenA): priceOut = (reserveB * amountIn) / (reserveA + amountIn)
        The denominator inflates because reserveA == balanceOf(address(this)),
        so the computed priceOut is artificially low → attacker gets MORE tokenB
Step 3: Repay flash loan
Profit = (tokenB received) − (flash loan fee)
```

Even one token moved creates a 0.01–0.1% price distortion; multi-million-dollar pools yield hundreds of dollars per flash. This works because `balanceOf(address(this))` is a *real-time snapshot*, not a TWAP.

### A3 — Deposit Measurement Bypass (More Shares Than Deposited)
**Priority:** `CRITICAL` | **Exploitability:** `HIGH`

```
If deposits are calculated from token.balanceOf(address(this)) BEFORE the transfer
completes (e.g., allowance-based vs transferFrom race), or if the contract does NOT
use safeTransferFrom + event logging, an attacker can:
  - Use a rebasing/fee-on-transfer token that transfers less than approved
  - Exploit insufficient allowance checking
Result: receives mint(shares) based on expected transfer, but actual balance delta
is smaller → attacker underpays, over-mints.
```

### A4 — Reentrancy Theft in Swap
**Priority:** `HIGH` | **Exploitability:** `MEDIUM`

```
Swap flow:
  1. transferFrom(user, addr, amountIn)    // external call ✓
  2. compute amountOut                      // OK
  3. userBalances[msg.sender] += amountOut  // internal update ← OUT OF ORDER
  4. safeTransfer(tokenOut, msg.sender, amountOut) // external call ✗

Between step 2 and step 4, a malicious recipient can re-enter swap() because:
  - No nonReentrant guard
  - Internal balance was already updated (step 3), so the re-entered call sees
    inflated balance AND can trigger another transfer before reserves are settled
```

Actually the worst case here: if the receiving contract has fallback that calls back into swap, it can drain tokens if reserves aren't locked between the two transfers.

**Priority:** `HIGH` | **Exploitability:** `MEDIUM`

```
Frontend shows quote: "You'll receive ~X tokens"
User submits tx with NO amountOutMin.
Bot sees pending tx, front-runs it: swaps ahead, moves price → user's tx fills
at terrible rate. User receives 90% of quoted amount.
At scale, this is a continuous tax on all users.

Not a contract vulnerability per se, but a systemic loss vector.

**Priority:** `LOW` | **Exploitability:** `NONE (operational risk)`

If the protocol accepts "arbitrary token donations", it may accumulate tokens it

drains everything. If it doesn't exist, LP funds are partially stuck.
```

## Vulnerability Audit: Constant-Product AMM Pool

### Vulnerable Pattern Summary

The contract exhibits four interrelated structural failures across three categories: **state ordering**, **price discovery**, and **input validation**. They compound — a flash-loan donor can corrupt pricing, then front-run real users against corrupted prices.

---

### Attack Paths (Ranked by Exploitability)

#### 1. Donation-Inflation Swap Abuse [Critical]

**How it works.** An attacker uses a flash loan to donate 10,000 USDC to the pool right before calling `swap()`. The swap prices output using `token.balanceOf(address(this))` as a reserve snapshot, so the massive donation makes the pool appear vastly deeper than it is. The attacker sells a modest amount of ETH at a massively favorable rate, drains real value, then unwinds the flash loan.

**Concrete scenario:**
- Real pool: 1,000 USDC, 1 ETH → fair price 1 USDC per 0.001 ETH
- Attacker flash-loans 90,000 USDC, donates them
- Pool now reports 91,000 USDC effective reserve (if balanceOf is used as the quote)
- Attacker swaps 0.01 ETH → receives ~0.91 USDC instead of the fair ~0.01 USDC
- Unwinds flash loan, pockets the delta (~0.90 USDC profit)

**Exploitability: trivial.** Single tx, fully automatic, zero capital at risk beyond gas.

**Root cause:** Using `token.balanceOf(address(this))` as a price input instead of tracking `_totalAssets` internally.

#### 2. First-Depositor Inflation (LP Mint Attack) [High]

**How it works.** On initial deployment the pool has zero reserves and zero LP tokens. A "first depositor" provides liquidity at what appears to be fair terms. But if the contract accepts donations (or a deployer strategically donates), the first depositor's share mint is calculated against an inflated balance. Subsequent depositors receive disproportionately fewer shares for the same asset contribution.

**Concrete scenario:**
- Deployer donates 10,000 USDC + 10 ETH to start
- Legitimate first depositor contributes 100 USDC + 0.1 ETH
- Contract mints shares = (100 × totalShares) / balanceOf(...)
- Because balance includes the donated 10,000, the first depositor gets very few shares relative to their actual proportional claim
- The deployer effectively steals ~99% of the deposited value

**Exploitability: high.** Requires one upfront deposit but requires no flash loans or external coordination.

#### 3. Sandwich/Front-Running via Unsigned Quotes [Medium-High]

**How it works.** The front-end quotes trades without `amountOutMin` or deadline bounds. An attacker monitors the mempool, sees a large pending swap, and sandwiches it: buys before (pushing price worse), lets victim's swap execute at bad price, sells after (pulling price back). The absence of slippage checks means the victim's tx always executes regardless.

**Exploitability: medium-high.** Standard MEV bot pattern. Works against any swap without slippage bounds. Profit scales with trade size.

#### 4. Flash-Lone Oracle Spot Price Manipulation [High]

**How it works.** If the AMM derives its exchange rate from `token.balanceOf(address(this))` as a spot oracle (rather than a TWAP or time-weighted source), the attacker can manipulate the pool's own ratio via flash loans. Buy/sell cycles within a single block shift the spot ratio arbitrarily because there is no time component.

**Relationship to #1:** Attacks #1 and #4 are the same mechanism viewed from different angles. #1 focuses on the donation vector; #4 generalizes to any flash-loan-driven imbalance (including rapid alternating swaps).

**Exploitability: trivial** — identical mechanics to #1.

#### 5. Reentrancy via Incorrect State Ordering [Medium]

**How it works.** The swap function updates the caller's balance/withdrawable amount *before* updating internal reserves and transferring output tokens. If the output token is a backdoored ERC-20 whose `transfer()` invokes a callback on the recipient, the reentrant call reads stale reserve state:

```solidity
// Vulnerable ordering
userBalances[msg.sender] += amountOut;    // State change 1
outputToken.transfer(msg.sender, amountOut); // Callback happens here — reserves haven't updated!
_reserves[tokenB] -= amountOut;            // State change 2 — too late
```

A reentrant `amountOutMin` check or balance read during the callback sees outdated reserves, allowing over-withdrawal up to the loop limit.

**Exploitability: medium.** Requires the traded token to implement a malicious callback. Backdoored/suspicious tokens on testnets make this non-hypothetical.

#### 6. Arbitrary Donation Flooding [Low-Medium]

**How it works.** A hostile actor donates a wildly mismatched token pair (e.g., 1M USDC + 100 ETH) creating a grossly imbalanced pool. Users interacting with the pool trade at severely distorted prices in the donor's favor. Unlike flash loans, this burns the donor's capital permanently, limiting attack scale.

**Exploitability: low-medium.** Self-financed by the attacker. Profit depends on post-donation trading volume. Useful as a persistent pollution vector.

---

### Attack Chain: How It All Composes

The most damaging scenario chains #1, #4, and #5:

1. Attacker flash-loans $10M USDC
2. Donates 9M USDC into the pool (inflating `balanceOf`)
3. Calls `swap(ETH→USDC)` — priced against the inflated USDC balance, receives enormous output
4. Output token has a reentrancy callback that reads reserves mid-swap
5. Attacker loops the callback to drain additional tokens
6. Unwinds flash loan, returns 1M USDC, keeps ~9M+ profit
7. Cleans up — the pool has only 1M USDC and half its ETH

### Architecture Under Audit

The described contract has these design choices:
- `swap()` updates **user output balance first**, then settles internal reserves
- Pricing reads `token.balanceOf(address(this))` — i.e., the **on-chain token balance** of the pool

### Attack Path Enumeration (Ranked by Exploitability)

#### ATTACK 1 — Token Balance Price Manipulation (Critical | Trivially Exploitable)

The pool prices against `IERC20(token).balanceOf(address(pool))`, not against its internal `reserveA`/`reserveB`. An attacker with access to even a small amount of either token can manipulate the perceived spot price.

**Mechanism:**
1. Attacker has 10 ETH and 5,000 USDC
2. Pool is initialized with 10,000 ETH and 10,000,000 USDC (price = 1 USDC / 1000 wei ETH)
3. Attacker deposits 9,000 USDC into the pool via donation
4. `balanceOf(pool)` now reads ~19,000 USDC → pool thinks it holds far more USDC
5. Spot price recalculated as ~1 USDC / 526 wei ETH (artificially cheap ETH)
6. Attacker swaps 10 ETH → receives ~19,000 USDC at manipulated price
7. Attacker donates back 9,000 USDC (or leaves them), walks away with ~10,000 USDC profit

**Why trivial:** Requires no flash loans, no MEV infrastructure, just a single transaction. The flaw is baked into the pricing oracle.

**Impact:** Complete drain of one reserve; LPs lose >50% value.

---

#### ATTACK 2 — First-Depositor Inflation / "Donation Swindle" (Critical | Highly Exploitable)

When the pool accepts donations that update its **recorded reserves** (or balance-based pricing), the first depositor after initialization sets the price floor at a severe disadvantage.

**Mechanism:**
```
Init:     Pool holds 1,000,000 A, 1,000,000 B  → spot = 1.0
Attacker donates 10,000 B (no A)
Pool records: reserveA=1,000,000, reserveB=1,010,000 → spot = 0.9901
Legitimate LP provides 100,000 A + 100,000 B @ fair ratio 1:1
But pool's internal curve says 0.9901 A per B
LP's deposit is priced against distorted curve → LP receives inflated share
Later: attacker swaps all A→B at the manipulated rate, extracting value
       from the legitimate LP's contribution
```

More insidiously, if donations merely increase `balanceOf(pool)` used for pricing but do NOT add to the protocol's accounting of what LPs own, there's a **permanent mismatch**: the pool thinks it's richer than LP claims entitle anyone to withdraw.

**Exploitability:** Very high — requires only being first donor and holding modest capital. No flash loan needed.

---

#### ATTACK 3 — Reentrancy via Pre-Swap Balance Update (High | Flash Loan Exploitable)

The swap function orders operations incorrectly:

```solidity
// VULNERABLE ORDERING
function swap(uint256 amountIn, uint256 minAmountOut) external {
    // ... validation ...
    
    uint256 amountOut = /* calculate */;
    require(amountOut >= minAmountOut);
    
    IERC20(tokenOut).transfer(msg.sender, amountOut);  // UPDATE OUTPUT FIRST
    // NOW settle reserves
    reserveIn += amountIn;
    reserveOut -= amountOut;
}
```

**Mechanisms:**

(a) **Direct reentrancy:** If `tokenOut` is a reentrant token (malicious ERC20 that calls back into the pool on `transfer()`), the fallback/hook can call `swap()` again before reserves are settled. Each call mints fresh output against the same stale reserve state.

(b) **Front-running + sandwich:** Combined with the balance-of-price-flaw (#1): attacker front-runs their own big buy, uses pre-transfer balance to get better price, exploits gap between when they receive tokens and when reserves reflect reality.

**Flash loan angle:** Borrow huge amount → trigger swap → reenter → repeat N times → drains pool.

---

#### ATTACK 4 — Oracle Front-Running on Bootstrapped Prices (Medium-High | Requires MEV Infra)

During liquidity bootstrapping, the AMM publishes swap quotes derived from its current (inflated) token balance. A bot monitoring the mempool sees a large pending deposit transaction.

**Mechanism:**
1. Whale submits deposit(txA) of 1M tokens → pool balance inflates
2. Bot frontruns with swap(txB) reading inflated `balanceOf(pool)` → gets terrible price but...
3. Bot backruns the original deposit txC once it confirms, extracting value from the new equilibrium
4. Alternatively: bot sees a large incoming deposit will shift price → sandwiches between two of their own swaps at manipulated quote

**Why not highest rank:** Requires MEV bot infrastructure and timing precision. Less deterministic than Attacks 1–3.

---

#### ATTACK 5 — No-Slippage-Frontend Sandwich (Medium | MEV Exploitable)

The bootstrapping frontend quotes trades with **no slippage bound** (i.e., `minAmountOut = 0`). Any swapper gets whatever amount the current reserves produce, with no client-side protection.

**Mechanism:**
1. Legitimate user submits swap via frontend with `minAmountOut = 0`
2. MEV bot detects this pending tx
3. Bot frontruns with its own large buy → consumes liquidity, inflates price
4. User's swap executes at degraded rate (receives less)
5. Bot backruns by selling immediately at recovered price
6. User takes full loss; bot profits

With no slippage bound, the user cannot reject the bad price. Even worse, the frontend shows them a **quote** but the executed amount is always ≤ quoted amount with no ability to cancel.

---

#### ATTACK 6 — Cross-Token Contamination (Medium | Protocol Design Flaw)

If the pool accepts *arbitrary* token donations (not just the pair tokens), a malicious token with different decimals, special transfer semantics, or fee-on-transfer mechanics can corrupt the reserve accounting.

**Example:** Fee-on-transfer token donates 10,000 tokens but only 9,800 arrive. If the pool records 10,000 (sender-declared) vs. 9,800 (actual balance), the reserve math becomes inconsistent. Over time this bleeds LP value.

Let me map out every concrete attack path from the described vulnerabilities.

### Attack Path 1: First-Depositor Inflation / Donation Attack (CRITICAL — Exploitability: Highest)

**Vulnerability:** The deposit function uses `token.balanceOf(address(this))` as the reserve denominator. An attacker donates tokens *before* the first depositor arrives.

```

**Root cause:** Deposits use snapshot of `balanceOf(address(this))` which includes donated/external tokens, making the share issuance ratio wrong. The `_totalAssets` tracking prevents this.

---

### Attack Path 2: Oracle Spot-Price Manipulation via Swap (CRITICAL — Exploitability: High)

**Vulnerability:** Pricing swaps against `token.balanceOf(address(this))` — a single large swap moves the pool's own spot price, which then prices subsequent swaps. This is the classic "self-manipulated oracle" problem.

```
Pool: 100 WETH, 300,000 USDC (price = 3,000 USDC/WETH)
Attacker swaps 10 WETH → gets ~27,273 USDC (AMM price)
New pool state: 110 WETH, 272,727 USDC → spot price now ≈ 2,479

If the contract quotes external trades off its own `balanceOf`, 
the next trade uses this manipulated spot, not an independent oracle.
```

**Root cause:** Using internal `balanceOf` as a price source instead of an independent TWAP oracle creates a feedback loop where swaps move the price reference.

---

### Attack Path 3: Reentrancy in Withdrawal (HIGH — Exploitability: Medium-High)

**Vulnerability:** Transfer-before-balance-update violates CEI (Check-Effects-Interact) ordering.

```solidity
// VULNERABLE ORDER
token.transfer(msg.sender, amount);    // INTERACT - external call first
balances[msg.sender] -= amount;         // EFFECT - update after
```

An attacker with a fallback that re-enters `withdraw()` drains funds:

```
User balance: 100 ETH
Call #1: transfer(100) → triggers fallback
Fallback: calls withdraw(50) [still unchecked because balance not yet updated]
Transfer(50) triggers fallback again → withdraw(50) → drain complete
Final effect: balance -= 100 only once (but 200 transferred).
```

---

### Attack Path 4: Slippage-Free Frontend Quoting (HIGH — Exploitability: Medium)

**Vulnerability:** A front-end quotes trades without `amountOutMin` or deadline. MEV bots sandwich legitimate transactions.

```
User submits: swap(10 WETH, 0 USDC min, block.timestamp + 3600)
Bot sees tx: buys WETH before user (pushes price up),

Spread captured: 5-15% typical in low-liquidity pools
```

Without `deadline`, stale transactions can also be replayed at unfavorable prices after hours/days.
