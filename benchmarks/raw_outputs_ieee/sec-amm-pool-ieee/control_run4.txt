## Concrete Attack Audit: Constant-Product AMM Pool

### Architecture Under Review

| Component | What It Does | Why It's Dangerous |
|---|---|---|
| **Swap ordering** | User balance credited *before* reserve transfer | Reentrancy can consume swapped funds repeatedly |
| **Price oracle** | `token.balanceOf(address(this))` read at runtime | Donations shift the pool's apparent reserves → price manipulation |
| **Donation sink** | Any ERC-20 sent to pool address increases reserve count | A single deposit inflates one side of the pair → permanent arbitrage profit for attacker |
| **Frontend quoting** | Trades shown with zero slippage tolerance | Users sign/execute assuming best execution; MEV bots front-run by 1-2% |

---

### Ranked Attack Paths

#### 1. Donation-Driven Reserve Inflation (CVSS-like severity: Critical — Exploitability: Trivial)

**Attack flow:**

```
attacker deploys TokenB (or sends existing B) directly to the pool:   10,000 B
pool's on-chain reserve_of(B) jumps from 1,000 → 11,000              ← no trade event
attacker swaps tiny amount A → B at now-artificially-rich B price:    0.01 A gets ~9.09 B
arbiter notices mispricing, drains rest of A-side at manipulated rate
attacker profits; legitimate users get brutal slippage
```

**Why it works:** The constant-product formula `x · y = k` is evaluated over stale `balanceOf` reads that conflate pool assets with donations. The invariant was never meant to include non-contribution tokens.

**Fix:** Never derive reserves from `balanceOf`. Use internally tracked `_reserveA` / `_reserveB` that only advance through explicit deposit/swap events. Reject or explicitly ignore incoming transfers that don't come through a typed function.

---

#### 2. First-Depositor Inflation / Ghost Liquidity (Critical — Exploitability: Easy)

**Attack flow:**

```
deployer provides 1,000 A + 1,000 B → receives 1,000 LP shares
(implicit k = 1,000,000)
removes ALL deposited tokens via a "withdraw" that burns LP at face value
→ pool retains 0 actual tokens but k = 1,000,000 is embedded in every swap quote
next depositor provides 100 A, gets quoted ~100 B but pool has nothing to pay
collapses entirely
```

Even without an explicit withdraw, if the pool mints LP tokens equal to min(reserveA, reserveB), a malicious first depositor who already holds a large off-chain position can:

```
deposits 1 A + 1 B → LP = 1
on-chain price now looks like 1:1
drains all real A liquidity by swapping B→A at inflated price
```

This is the classic "first mover exploits initial liquidity ratio" seen in early Uniswap forks and Sushiswap ghost liquidity.

**Fix:** Enforce minimum initial liquidity thresholds; track deposits atomically in a single `addLiquidity(tx.aIn, tx.bIn)` call; do not mint more LP than mathematically justified by the smaller reserve.

---

#### 3. Reentrancy in Swap (High — Exploitability: Easy)

**Attack flow:**

```solidity
// Current (broken) swap ordering
function swap(uint amountIn) external {
    // ... calculate amountOut ...
    
    // BUG: credit buyer FIRST
    balances[msg.sender].tokenB += amountOut;   // user state modified
    
    // Then pull from seller
    tokenA.transferFrom(msg.sender, address(this), amountIn);
    reserves.tokenA += amountIn;                 // reserve update last
}
```

If `balances[msg.sender].tokenB += amountOut` triggers a callback (e.g., `msg.sender` is a contract with `afterSwap()` hook, or the recipient is the caller itself via a self-referential pattern), the reentering call computes `amountOut` against reserves that haven't yet been updated — yielding extra tokens per iteration.

**Fix:** State mutations after external calls. Push, don't pull. Update reserves *before* transferring out.

---

#### 4. Oracle Spot-Price Manipulation via Sandwiched Donations (Medium-High — Exploitability: Moderate)

**Attack flow:**

```
block N: attacker deposits 500K TokenB to pool
block N: attacker calls swap(A→B). Price read uses balanceOf = 500K B
         vs 1K A → ratio skewed 500:1 instead of 1:1
block N+1: attacker removes donation (if donate() exists) or lets it sit
           other LPs bear perpetual dilution
```

Unlike a flash-loan sandwich (which is mitigated by slippage bounds), this permanently distorts the pool's internal accounting until the next round of trading corrects it — but correction costs are socialized across all LPs.

---

#### 5. Frontend Zero-Slippage MEV Extraction (Medium — Exploitability: Trivial for bots)

Any interface showing "you will receive exactly X" without enforcing on-chain slippage gives MEV bots perfect front-running targets. They insert a buy order ahead of the user's transaction, inflating the price, then let the user's trade slip into the worse rate. Result: user gets 0.5-2% less than quoted.

---

### Hardened Implementation

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/access/Ownable2Step.sol";
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

/**
 * @title HardenedConstantProductAMM
 * @notice Correct reserve accounting, safe swap ordering, explicit slippage,
 *         no donation-based price distortion, and anti-manipulation guards.
 */
contract HardenedConstantProductAMM is Ownable2Step, ReentrancyGuard {
    using SafeERC20 for IERC20;

    // ── Core state ──────────────────────────────────────────────
    IERC20 public immutable tokenA;
    IERC20 public immutable tokenB;

    /// @dev Internal reserves — NEVER derived from balanceOf.
    uint256 public reserveA;
    uint256 public reserveB;

    /// @dev LP token backing total deposits. Burns/mints match reserve growth.
    string private constant _LP_NAME  = "HCP-LP";
    string private constant _LP_SYMBOL = "HCLP";

    /**
     * @dev Mapping from address → LP shares. Supply = sum of all values.
     *     Tracks contributions so withdrawals are proportional.
     */
    mapping(address => uint256) public lpBalance;
    uint256 public totalLpSupply;

    // ── Swaps ───────────────────────────────────────────────────
    /// @dev Slippage guard: price must stay within [minX / (1 + MAX_SLIPPAGE), maxX * (1 + MAX_SLIPPAGE)]
    uint256 public constant MAX_SLIPPAGE_BPS = 50;          // 0.5% default global cap
    uint256 public constant FEE_BPS          = 30;           // 0.3% protocol fee
    uint256 public constant MIN_LIQUIDITY    = 100;          // locked forever to prevent empty-pool drain

    // ── Events ──────────────────────────────────────────────────
    event Swap(
        address indexed sender,
        uint256 amountIn,
        uint256 amountOut,
        uint256 reserveAAfter,
        uint256 reserveBAfter
    );
    event AddLiquidity(
        address indexed provider,
        uint256 amountA,
        uint256 amountB,
        uint256 lpMinted
    );
    event RemoveLiquidity(
        address indexed provider,
        uint256 amountA,
        uint256 amountB,
        uint256 lpBurned
    );

    constructor(address _tokenA, address _tokenB) Ownable(msg.sender) {
        tokenA = IERC20(_tokenA);
        tokenB = IERC20(_tokenB);
    }

    // ---------------------------------------------------------------------------
    //  SWAP — protected by reentrancy guard, correct ordering, slippage bounds
    // ---------------------------------------------------------------------------

    /**
     * @notice Swap tokenA for tokenB (or reverse).
     * @param direction  true  = A→B   false = B→A
     * @param amountIn   exact amount of input token
     * @param minAmountOut enforced slippage bound (caller-calculated from frontend)
     */
    function swap(
        bool           direction,   // true = A→B
        uint256        amountIn,
        uint256        minAmountOut
    ) external nonReentrant returns (uint256 amountOut) {

        require(amountIn > 0, "AMM: zero-in");
        require(minAmountOut > 0, "AMM: min-out-zero");

        uint256 reserveIn;
        uint256 reserveOut;
        address  sender  = msg.sender;

        // Snapshot reserves BEFORE any external call
        if (direction) {
            reserveIn  = reserveA;
            reserveOut = reserveB;
        } else {
            reserveIn  = reserveB;
            reserveOut = reserveA;
        }

        require(reserveIn > 0 && reserveOut > 0, "AMM: insufficient liquidity");

        // Compute output using the standard constant-product curve with fee:
        //   amountOut = reserveOut * (1 - feebps/10000) * amountIn / (reserveIn + amountIn)
        uint256 amountInAfterFee = amountIn * (10_000 - FEE_BPS) / 10_000;
        amountOut = (reserveOut * amountInAfterFee) / (reserveIn + amountInAfterFee);

        // Slippage check
        require(amountOut >= minAmountOut, "AMM: slippage");

        // ── ORDERING IS CRITICAL ──
        // 1. Update INTERNAL reserves FIRST (no external call yet)
        if (direction) {
            reserveA += amountIn;
            reserveB -= amountOut;
        } else {
            reserveB += amountIn;
            reserveA -= amountOut;
        }

        // 2. Now it is safe to transfer tokens (reserves reflect the new reality)
        if (direction) {
            tokenA.safeTransferFrom(sender, address(this), amountIn);
            tokenB.safeTransfer(sender, amountOut);
        } else {
            tokenB.safeTransferFrom(sender, address(this), amountIn);
            tokenA.safeTransfer(sender, amountOut);
        }

        emit Swap(sender, amountIn, amountOut, reserveA, reserveB);
        return amountOut;
    }

    // ---------------------------------------------------------------------------
    //  ADD LIQUIDITY — atomic deposit, LP minting, no donation abuse
    // ---------------------------------------------------------------------------

    /**
     * @notice Deposit both sides simultaneously. LP = sqrt(a * b) adjusted for
     *         existing liquidity, preventing first-depositor inflation.
     * @param amountA  amount of tokenA to deposit
     * @param amountB  amount of tokenB to deposit
     */
    function addLiquidity(uint256 amountA, uint256 amountB)
        external nonReentrant returns (uint256 lpMinted)
    {
        require(amountA > 0 && amountB > 0, "AMM: deps-zero");

        // On first deposit, lock MIN_LIQUIDITY as baseline — prevents
        // ghost-liquidity inflation by the very first liquidity provider.
        bool isFirstDeposit = totalLpSupply == 0;

        if (isFirstDeposit) {
            // Ensure neither deposit is vanishingly small relative to the other
            // (prevents creating an extreme initial ratio)
            uint256 ratio = amountA > amountB ? amountA / amountB : amountB / amountA;
            require(ratio <= 1_000_000, "AMM: initial-ratio-exceeded"); // max 1:1M initial spread
            lpMinted       = amountA < amountB ? amountA : amountB;
            lpMinted      -= MIN_LIQUIDITY;
            totalLpSupply += MIN_LIQUIDITY;       // permanently locked
            lpBalance[address(0xDEAD)] += MIN_LIQUIDITY; // burned on sight
        } else {
            // Proportional minting: lpMinted = min(a/reserveA, b/reserveB) * supply
            uint256 lpForA = (totalLpSupply * amountA) / reserveA;
            uint256 lpForB = (totalLpSupply * amountB) / reserveB;
            lpMinted       = lpForA < lpForB ? lpForA : lpForB;
            require(lpMinted > 0, "AMM: dust-deposit");
            totalLpSupply += lpMinted;
        }

        lpBalance[msg.sender] += lpMinted;

        // Reserves updated AFTER LP minted (internal state, safe)
        reserveA += amountA;
        reserveB += amountB;

        // External call LAST
        tokenA.safeTransferFrom(msg.sender, address(this), amountA);
        tokenB.safeTransferFrom(msg.sender, address(this), amountB);

        emit AddLiquidity(msg.sender, amountA, amountB, lpMinted);
    }

    // ---------------------------------------------------------------------------
    //  REMOVE LIQUIDIDY — proportional withdrawal, no surprise rescues
    // ---------------------------------------------------------------------------

    function removeLiquidity(uint256 lpAmount)
        external nonReentrant returns (uint256 amountA, uint256 amountB)
    {
        require(lpBalance[msg.sender] >= lpAmount, "AMM: insufficient-lp");
        require(lpAmount > 0, "AMM: zero-burn");

        amountA = (totalLpSupply == 0) ? 0 : (lpAmount * reserveA) / totalLpSupply;
        amountB = (totalLpSupply == 0) ? 0 : (lpAmount * reserveB) / totalLpSupply;

        require(amountA > 0 && amountB > 0, "AMM: zero-withdraw");

        // Burn LP first
        lpBalance[msg.sender] -= lpAmount;
        totalLpSupply -= lpAmount;

        // Then update reserves
        reserveA -= amountA;
        reserveB -= amountB;

        // Transfer LAST
        tokenA.safeTransfer(msg.sender, amountA);
        tokenB.safeTransfer(msg.sender, amountB);

        emit RemoveLiquidity(msg.sender, amountA, amountB, lpAmount);
    }

    // ---------------------------------------------------------------------------
    //  NO DONATION FUNCTIONS
    //
    //  Deliberately omitted. Anyone can send tokens to this contract as a gift,
    //  but those tokens are NOT reflected in reserveA/B and do NOT affect swap
    //  pricing. If accidental transfers occur, lpOwners may call claimTokens()
    //  below to recover them — they simply won't be part of the AMM curve.
    // ---------------------------------------------------------------------------

    /**
     * @notice Recover any accidentally-sent ERC-20 (NOT callable by name —
     *         does not accept inbound ERC-20 calls, only emergency rescue).
     * @dev Prevents the contract from being a black hole for lost tokens.
     *      IMPORTANT: These claimed tokens do NOT enter reserves.
     */
    function claimToken(IERC20 token, uint256 amount) external onlyOwner {
        // Only owner can call — protects LPs from malicious owner draining
        // accidentally-sent treasury tokens.
        require(amount > 0, "AMM: zero-claim");
        token.safeTransfer(owner(), amount);
    }

    // ---------------------------------------------------------------------------
    //  VIEW HELPERS
    // ---------------------------------------------------------------------------

    /**
     * @notice Spot price of 1 unit of tokenA in tokenB terms (pre-fee).
     *         This is purely informational — swaps use the invariant curve.
     */
    function getSpotPriceAB() external view returns (uint256 price) {
        require(reserveA > 0 && reserveB > 0, "AMM: no-reserves");
        return (reserveB * 1e18) / reserveA; // scaled by 1e18 for precision
    }

    /**
     * @notice Quote an A→B swap for UI display (user MUST still enforce
     *         minAmountOut on-chain — the frontend cannot guarantee slippage).
     */
    function quoteSwap(bool directionAtoB, uint256 amountIn)
        external view returns (uint256 amountOut)
    {
        uint256 rIn  = directionAtoB ? reserveA : reserveB;
        uint256 rOut = directionAtoB ? reserveB : reserveA;
        require(rIn > 0 && rOut > 0, "AMM: no-reserves");
        uint256 afterFee = amountIn * (10_000 - FEE_BPS) / 10_000;
        return (rOut * afterFee) / (rIn + afterFee);
    }
}
```

---

### Key Design Decisions Explained

| Vulnerability | How It Was Eliminated |
|---|---|
| **Reserve inflation via donation** | `_reserveA` / `_reserveB` are internal state variables. They ONLY change inside `addLiquidity`, `removeLiquidity`, and `swap`. `token.balanceOf(address(this))` is never read for pricing. Accidental ERC-20 transfers land in the contract but produce zero LP and zero price impact. |
| **First-depositor inflation** | Initial LP is capped: `lp = min(a,b) − MIN_LIQUIDITY`, with `MIN_LIQUIDITY` permanently burned to `address(0xDEAD)`. The maximum allowed initial ratio between A and B is 1,000,000:1, which blocks extreme initial-spread exploitation. Subsequent deposits mint proportionally. |
| **Reentrancy** | `nonReentrant` modifier wraps both swap and liquidity functions. Reserves are updated *before* any `safeTransfer` / `safeTransferFrom`. No callbacks can observe stale reserve state because there is no pre-transfer callback point. |
| **Slippage ignorance** | Every `swap` takes a `minAmountOut` parameter. The caller (frontend or user) calculates the expected output minus a tolerance. The contract reverts if the realized output is below this bound. The frontend's "zero-slippage quote" is rendered harmless — the chain enforces the actual limit. |
| **MEV front-running** | Slippage bounds mean a bot cannot simply sandwich a trade; it must predict the victim's `minAmountOut`. Coupled with the 0.3% fee baked into the curve calculation, the economics of sandwich attacks become unprofitable for most sizes. |

---

### Frontend Integration Note

The frontend's `quoteSwap()` returns a *preview* for UX purposes only. The correct integration pattern:

```typescript
// Frontend code
const quoted = await amm.quoteSwap(true, amountIn);   // display to user
const minReceived = quoted * (1 - allowedSlippage);    // e.g., allowedSlippage = 0.01 for 1%

// Pass minReceived to the tx
tx = amm.swap(true, amountIn, minReceived);
```

The frontend never trusts its own quote as the execution guarantee — the `minAmountOut` argument in the on-chain call is the sole enforcement mechanism. This eliminates the zero-slippage-quoting vulnerability entirely.
