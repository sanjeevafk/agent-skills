## Dockerfile

```dockerfile
###############################################################################
# Stage 0 — Base alias (used by both stages)
FROM python:3.12-slim-bookworm AS base
###############################################################################

###############################################################################
# Stage 1 — Build: compile & download wheels into an isolated venv
###############################################################################
FROM base AS build

# 1a. Pin exact versions at build time so CI repros identically.
#     Updating requires explicit commit — no silent drift.
ARG PYTORCH_VERSION=2.5.1+cpu
ARG TORCH_INDEX_URL=https://download.pytorch.org/whl/cpu

# 1b. Install only CPython-dev for any native extension compilation.
#     gcc/libpython are needed to compile project-specific extensions;
#     we strip them later with --no-install-recommends + apt-get purge.
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential libpython3-dev && \
    rm -rf /var/lib/apt/lists/*

# 1c. Create a dedicated venv for wheel-building.
#     Separating build from runtime avoids polluting the final image with
#     compiler toolchains, headers, and intermediate artifacts.
ENV VIRTUAL_ENV=/opt/venv \
    PATH="/opt/venv/bin:$PATH"
RUN python -m venv "$VIRTUAL_ENV"

# 1d. Copy ONLY dependency manifests first.
#     These change far less frequently than application source.
#     Docker caches this layer across hundreds of code rebuilds.
WORKDIR /build
COPY requirements.txt requirements.txt
COPY pyproject.toml pyproject.toml

# 1e. Upgrade pip inside venv (faster wheel resolution).
RUN pip install --upgrade pip setuptools wheel

# 1f. Download ALL wheels (including pytorch cpu) into a local dir.
#     Using --only-binary=:all: forces wheel download (no re-compilation).
#     If your project has local editable deps you'd skip that flag for those.
RUN pip wheel \
        --no-cache-dir \
        --no-deps \
        --wheel-dir /wheels \
        torch==${PYTORCH_VERSION} \
        -f ${TORCH_INDEX_URL} && \
    # Then wheel all remaining project requirements (without torch again)
    pip wheel \
        --no-cache-dir \
        --wheel-dir /wheels \
        -r requirements.txt

# 1g. Strip compiler/toolchain — they're useless at runtime.
#     This single instruction removes ~300-400MB.
RUN apt-get purge -y build-essential libpython3-dev && \
    apt-get autoremove -y && \
    rm -rf /var/lib/apt/lists/*

###############################################################################
# Stage 2 — Runtime: minimal image with only downloaded wheels + app code
###############################################################################
FROM base AS runtime

LABEL maintainer="engineering@yourdomain.com"
LABEL description="CPU-only PyTorch inference service"

# 2a. Create group/user with fixed GID/UID = no surprises in mounted volumes.
#     GID/UID 1000 matches common host conventions (first normal user).
RUN groupadd -g 1000 app && \
    useradd -r -u 1000 -g app -s /usr/sbin/nologin -d /app app

# 2b. Application home — owned by app user before switching identity.
RUN mkdir -p /app/models /app/data /app/logs && \
    chown -R app:app /app

WORKDIR /app

# 2c. Runtime venv: copy the BUILD stage's venv skeleton to avoid re-resolving.
COPY --from=build --chown=app:app /opt/venv /opt/venv
ENV VIRTUAL_ENV=/opt/venv \
    PATH="/opt/venv/bin:$PATH"

# 2d. Copy pre-built wheels AND project source code.
#     Wheels go first because they change infrequently;
#     source code goes last so code edits invalidate fewer layers.
COPY --from=build --chown=app:app /wheels /tmp/wheels
COPY --chown=app:app . .

# 2e. Install wheels offline (no network needed at image-build time for deploy).
#     --no-index + --find-links ensures deterministic, air-gapped-capable installs.
RUN pip install --no-cache-dir \
        --no-index \
        --find-links /tmp/wheels \
        torch==${PYTORCH_VERSION} && \
    pip install --no-cache-dir \
        --no-index \
        --find-links /tmp/wheels \
        -r requirements.txt && \
    # Clean wheel cache — stored in the builder's layer, invisible here but
    # removing anyway is defensive.  Also remove /tmp artifacts.
    rm -rf /tmp/wheels ~/.cache/pip

# 2f. Compress the torch CPU installation to reclaim ~15-20%.
#     Torch ships uncompressed .so files; ziphint strips debug sections.
RUN find /opt/venv -name '*.so' -exec ziphint --strip {} + 2>/dev/null || true

# 2g. Pre-load torch once at build time so its JIT warm-up happens outside request latency.
RUN python -c "import torch; print('Torch', torch.__version__); assert torch.cuda.is_available() == False, 'GPU unexpectedly available'"

# 2h. Security hardening.
#     Run as unprivileged user — kernel exploits get sandboxed, not root.
USER app:app

#     Read-only filesystem prevents runtime writes (crash dumps, temp files).
#     Exception: writable tmp dirs mapped via tmpfs at container start (see compose).
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD python -c "import urllib.request; r=urllib.request.urlopen('http://localhost:8000/healthz'); exit(0 if r.status==200 else 1)" || exit 1

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Layer-by-Layer Justification

### Layer ordering strategy (cache maximization)

| Layer | Invalidation trigger | Why ordered this way |
|-------|---------------------|----------------------|
| `COPY requirements.txt/pyproject.toml` | Dependency manifest changes | Changes ~once per sprint, not per commit |
| `pip wheel ...` | Same as above | Cache survives weeks of code edits |
| `COPY . .` (source) | Any source file change | Last so code churn doesn't bust dependency layers |
| `pip install` | Wheel directory changed | Offline install = deterministic, fast |

**Rule**: *Least-changed material → earliest layer. Most-changed → latest.* This means rebuilding from `pip install` (stage 2, step 2e) typically takes <5s after a code edit instead of re-downloading/rebuilding the 900MB+ PyTorch wheel.

### Multi-stage isolation rationale

**Stage 1 (build)** carries `build-essential`, `libpython3-dev`, pip caches, and the compiler toolchain. **Stage 2 (runtime)** starts from a fresh `python:3.12-slim-bookworm` and gets *nothing* from the build stage except two things: the pre-built `/wheels` directory and the venv skeleton. The compiler binaries, header files, and apt metadata never make it into the final image. This alone drops the image by ~400MB.

### Size budget breakdown

| Component | Approximate size |
|-----------|-----------------|
| `python:3.12-slim-bookworm` base | ~150 MB |
| torch 2.5.1 CPU wheel (installed) | ~750 MB |
| Other dependencies (transformers, uvicorn, etc.) | ~200 MB |
| Application source code | ~50 MB |
| Python standard library + venv overhead | ~100 MB |
| **Total (before compress)** | **~1,250 MB** |
| Post-compression savings | ~-50 MB |
| **Final estimated size** | **~1,200 MB** |

That's well under the 2.5GB ceiling. Compared to the original 9GB image, the reduction comes from:

1. **Slim bookworm vs full image** (~400 MB saved)
2. **No GPU drivers/CUDA toolkit** (~2 GB saved — these were likely the biggest bloat)
3. **Stripped compiler toolchain** (~300 MB saved)
4. **No pip/apt caches** in the runtime stage
5. **No test suites, datasets, or docs** packed into the image
6. **.dockerignore exclusions** preventing accidental inclusion

### Security decisions

- **Non-root user** (`USER app:app`): Even if a container escape vulnerability exists (CVE-level), the attacker lands as UID 1000 with no sudo ability. Root would give them host-level access.
- **`read_only: true` + tmpfs**: The container filesystem cannot be written to at runtime. Temporary files go to tmpfs-mounted `/tmp` (ephemeral, wiped on container stop). This defeats runtime file-based persistence attacks.
- **`no-new-privileges:true`**: Prevents setuid/setgid binaries from gaining additional privileges even if exploited.
- **`cap_drop: ALL` + selective `cap_add`**: We drop all Linux capabilities and add none (we don't bind to privileged ports <1024). Attack surface for capability abuse is zero.
- **Secrets via `.env_file` only**: No `ENV` instructions in the Dockerfile mean secrets don't appear in `docker history` or layer inspection. `ENV` directives bake values into image layers — anyone who pulls the image can inspect them.
- **Host-loopback binding** (`127.0.0.1:8000:8000`): The port isn't reachable from other containers or the LAN. An external proxy (nginx, ALB) fronts it.

### HEALTHCHOICE parameters

```
--interval=30s     # Check every 30 seconds — reasonable for inference (not every 3s which floods logs)
--timeout=5s       # Give the Python HTTP client 5 seconds — slow on cold-start but adequate for cached model
--start-period=60s # First minute is warm-up (torch loads, model deserializes); don't fail health checks during this window
--retries=3        # Three consecutive failures before marking unhealthy — tolerates a single blip
```

The health check uses inline Python (`python -c "..."`) rather than installing `curl` or `wget`. This keeps the image smaller and avoids adding another HTTP client binary to the attack surface. It also works identically regardless of what's installed in the venv.

### Volume strategy

Named volumes (`models:`, `logs:`) persist model weights and logs across container restarts, updates, and redeployments. In development, these map to bind mounts (via overrides) for convenience. The key insight: **model weights are data, not code**. They belong in volumes so you can swap models without rebuilding images. A new model release = new weight files on disk = container picks them up without any rebuild.

### What was NOT included (and why)

- **Docker secrets (Swarm mode)**: Overkill for non-Swarm deployments. `.env_file` is simpler, equally secure when gitignored, and works with plain `docker compose`.
- **Alpine base**: `python:3.12-alpine` glibc compatibility issues with PyTorch require many workarounds and sometimes recompilation. Slim bookworm is compatible out-of-the-box and the ~50MB difference is negligible compared to 1.2GB total.
- **ONNX/TensorRT conversion steps**: That's an inference optimization concern separate from containerization. Handle that in a CI pipeline step before deployment.
