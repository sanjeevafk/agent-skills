### Layer-by-layer justification

**Stage 1 (Builder):**

| Decision | Why |
|---|---|
| `python:3.12-slim-bookworm` base | Smallest official Debian bookworm Python image (~150MB). No Alpine glibc mismatch issues with PyTorch. |
| Separate `build-essential` + `curl` install | One combined `apt-get` layer, immediately cleaned (`rm -rf /var/lib/apt/lists*`). These tools vanish when the final stage uses a different FROM — zero blast radius. |
| `requirements.txt` copied *before* source code | Dependency-only changes (pinning a package) only bust this one layer, not the whole build. Source edits below don't trigger recompilation. |
| Virtual env at `/opt/venv` | Isolated from system Python. The entire venv directory becomes the copy target into runtime — atomic, no partial state. |
| `pip freeze > frozen.txt` then `pip install -r frozen.txt` | Second-pass install from the exact resolved resolution prevents drift between what was compiled and what runs. Every transitive dependency gets pinned. |
| Bytecode compilation stripped | `find ... __pycache__ ... rm -rf` removes caches so the final image doesn't carry redundant `.pyc` files — runtime generates them fresh, which is free and avoids stale-bytecode bugs across builds. |

**Stage 2 (Runtime):**

| Decision | Why |
|---|---|
| `ARG` for UID/GID | Default to 1000 but overridable via `--build-arg APP_UID=...`. Avoids hardcoded UIDs that collide with host users or orchestration labels. |
| `tini` installed | PID 1 zombie reaping. Without init, child Python processes leak zombies under Kubernetes. |
| Separate `COPY --from=builder /opt/venv` and `COPY src/` layers | **This is the biggest cache win.** The venv layer is typically 2–4GB and changes rarely (only when deps change). Source code changes (every commit) only bust the `src/` COPY layer. Without this split, every code edit forces reinstalling torch (~500MB) and all deps. |
| `chown` in its own layer | The `USER` directive takes effect immediately. All prior COPY commands run as root; the chown layer flips ownership once, minimizing per-file permission overhead. |
| `ENV USER "$APP_USER:$APP_USER"` comes *after* all COPYs | Docker applies USER directives from that line forward. If USER appeared earlier, all following COPYs would fail (non-writable root dirs). |
| Single `HEALTHCHECK` hitting `/healthz` | `-t 5s` (short check), `--start-period=60s` (torch warmup time before model loads), `--retries=3` (graceful recovery), interval every 30s (reasonable detection cadence without overwhelming the endpoint). |
| `tini -- python -u ...` entrypoint | `-u` forces unbuffered stdout so logs stream to container orchestrator in real-time instead of being batched. |

## Layer-by-Layer Justification

### 1. Two-stage build (`builder` → `runtime`)
The builder stage downloads and verifies PyTorch wheels. The runtime stage copies **only** the compiled venv from `builder` — no wget, no CA certs, no build tools. This cuts ~300MB of transient tooling from the final image. Without multi-stage, all build artifacts persist in the final image, contributing to the original 9GB problem.

### 2. `ARG TORCH_HASH` (not `ENV`)
`ARG` values exist **only during build**. They are stripped from the final image metadata. An equivalent `ENV` directive would embed the hash in every container's environment (visible via `docker inspect` and `printenv`), leaking potentially sensitive information into logs, debug output, and any error message from the process.

### 3. Layer ordering for cache preservation

| Layer order | Rationale |
|---|---|
| `apk add wget` | Changes rarely — cached forever unless Alpine packages update |
| `wget PyTorch wheels` | Biggest layer (≈800MB). Only invalidates when PyTorch version changes — usually monthly or less |
| `venv + pip install --no-deps` | Fast layer, invalidated only when wheel content changes (tied to the download above) |
| `apk add curl + gosu` | Small, static — virtually never changes |
| `COPY --from=builder /opt/venv` | Matches previous layer exactly unless PyTorch rebuilt |
| `requirements.txt` + pip install | Invalidates on dependency changes — fast recompile of just this layer |
| `models/` | Large, rarely changes — separated from code so model updates skip recompilation |
| `src/` + app code | Changes on every deploy — placed **last** so none of the expensive prior layers are invalidated when code changes |

This ordering ensures that a routine code push (the most frequent operation) invalidates **one small layer** and skips rebuilding PyTorch, recreating the venv, or reinstalling system packages.

### 4. `COPY --no-deps --no-cache-dir`
`--no-deps` tells pip to skip resolving and downloading transitive dependencies — they're already resolved during the builder stage. `--no-cache-dir` prevents pip from writing its download cache to disk inside the layer, saving ≈50–200MB of ephemeral data that would otherwise pollute the image.

### 5. Non-root user with `addgroup -S` / `adduser -S`
Alpine's `-S` flag creates system accounts (UID/GID < 1000, no home directory, no login shell). This minimizes attack surface:
- The `appuser` cannot authenticate via SSH or interactive shells
- No writable home directory means no path injection attacks
- `chown -R appuser:appgroup` runs **after** all COPY operations, so we don't need to repeat ownership on every file layer (single layer instead of three)

### 6. HEALTHCHECK design

```
--interval=15s     Check every 15 seconds (catches hangs quickly without excessive load)
--timeout=5s       Fail if no response within 5 seconds (avoids false positives on slow startups)
--start-period=30s Allow 30 seconds for model loading before counting failures
--retries=3        Three consecutive failures before marking unhealthy (prevents flapping)
```

The health check uses inline Python (`urllib.request.urlopen`) rather than installing an extra HTTP client, keeping the image lean. The `/healthz` endpoint should return `200 OK` when the model is loaded and the server is accepting requests.

### 7. Size budget (target <2.5GB)

| Component | Approximate size |
|---|---|
| python:3.12-alpine base | ~90 MB |
| curl + gosu | ~2 MB |
| PyTorch CPU (unpacked) | ~800 MB |
| Python standard library | ~180 MB |
| numpy + scipy + scikit-learn | ~200 MB (some overlap with torch deps) |
| FastAPI + uvicorn + dependencies | ~50 MB |
| Application code + models | ~100–300 MB (varies) |
| **Total** | **~1.4–1.6 GB** |

Well under the 2.5GB target with comfortable headroom.

## Layer Decisions, Justified

| Decision | Rationale |
|---|---|
| **Two stages (build → runtime)** | Build pulls compilers, source distributions, full setuptools. Runtime gets pre-built `.whl` files only. Cuts the final image from ~9GB → ~2-2.4GB because `gcc`, `make`, and source trees are gone. |
| **`pip wheel` in build stage** | Compiles native extensions against the host architecture once, stores binaries in `/opt/wheels`. The runtime `pip install --no-index --find-links` reuses those wheels without any compiler toolchain. |
| **`requirements.txt` copied before other files** | Any change to application code does not invalidate the dependency installation layer. You get full `pip download` cache hits when redeploying code tweaks without touching `requirements.txt`. |
| **Wheels copied as a single blob** | `COPY --from=build /opt/wheels /tmp/wheels` is one layer. Then `pip install` produces one more. This avoids per-package COPY noise and keeps the dependency layer contiguous for maximum cache reuse. |
| **`rm -rf /tmp/wheels` in the same RUN** | Prevents orphaning wheel files as their own layer. Combining install + cleanup in one `RUN` means the layer size reflects only what ends up in `site-packages`, not the temporary wheel cache. |
| **tini as PID 1 entrypoint** | Container SIGTERM propagation requires a proper init process. `tini` reaps zombie processes and forwards signals correctly so graceful shutdown works for inference workers. |
| **Non-root `appuser`** | No SUID binaries, no world-writable paths. `chown -R appuser:appgroup /opt/app` is done before `USER appuser` so the container starts with correct permissions. Follows CIS Docker Benchmark 4.1. |
| **`HEALTHCHECK` with `--start-period=10s`** | Torch loads take 3-7 seconds on cold start. A 10s grace period prevents flapping health checks during initialization. 30s interval + 5s timeout is aggressive enough to detect hangs without overwhelming the endpoint. |
| **No ENV for secrets** | Secrets (API keys, model registry tokens, DB passwords) are passed via `--secret` mounts at runtime or environment variables injected by the orchestrator (`docker run -e`, Kubernetes `envFrom`). `ENV` instructions bake values into image layers where `docker history` exposes them. |
| **`.dockerignore` excludes `.venv`, `datasets/*.pt`** | Virtual environments leak local machine state. Datasets are gigabytes of immutable binary blobs that belong mounted as volumes, not baked in. Both would bloat the context and final image. |
| **`slim-bookworm` base** | Debian 12 slim (~75MB) vs full Ubuntu (~160MB). Fewer packages = smaller attack surface and less patch churn. Python 3.12 from the official `python:` image already includes shared libs needed by NumPy/torch. |
| **CPU-only torch pin** | Since there's no GPU, installing `torch-cpu` instead of the default CUDA build saves ~3GB alone. The assertion in the runtime stage catches misconfigurations at build time rather than first inference request. |
| **Layer ordering: system deps → wheels → app code** | System deps and wheels rarely change. Application code changes every deploy. By putting `COPY . .` last, any code-only rebuild skips dependency resolution entirely. |

```dockerfile
# Stage 0 — Base alias (used by both stages)
FROM python:3.12-slim-bookworm AS base
###############################################################################

###############################################################################
# Stage 1 — Build: compile & download wheels into an isolated venv
###############################################################################
FROM base AS build

# 1a. Pin exact versions at build time so CI repros identically.
#     Updating requires explicit commit — no silent drift.

ARG TORCH_INDEX_URL=https://download.pytorch.org/whl/cpu

# 1b. Install only CPython-dev for any native extension compilation.
#     gcc/libpython are needed to compile project-specific extensions;
#     we strip them later with --no-install-recommends + apt-get purge.
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential libpython3-dev && \
    rm -rf /var/lib/apt/lists/*

# 1c. Create a dedicated venv for wheel-building.
#     Separating build from runtime avoids polluting the final image with
#     compiler toolchains, headers, and intermediate artifacts.
ENV VIRTUAL_ENV=/opt/venv \
    PATH="/opt/venv/bin:$PATH"
RUN python -m venv "$VIRTUAL_ENV"

#     Docker caches this layer across hundreds of code rebuilds.

COPY pyproject.toml pyproject.toml

        --no-deps \

        --no-cache-dir \
        --wheel-dir /wheels \
        -r requirements.txt

    apt-get autoremove -y && \

###############################################################################

LABEL description="CPU-only PyTorch inference service"

#     GID/UID 1000 matches common host conventions (first normal user).

    useradd -r -u 1000 -g app -s /usr/sbin/nologin -d /app app

# 2b. Application home — owned by app user before switching identity.
RUN mkdir -p /app/models /app/data /app/logs && \
    chown -R app:app /app

WORKDIR /app

# 2c. Runtime venv: copy the BUILD stage's venv skeleton to avoid re-resolving.
COPY --from=build --chown=app:app /opt/venv /opt/venv
ENV VIRTUAL_ENV=/opt/venv \
    PATH="/opt/venv/bin:$PATH"

# 2d. Copy pre-built wheels AND project source code.
#     Wheels go first because they change infrequently;
#     source code goes last so code edits invalidate fewer layers.
COPY --from=build --chown=app:app /wheels /tmp/wheels
COPY --chown=app:app . .

#     --no-index + --find-links ensures deterministic, air-gapped-capable installs.

        --no-index \
        --find-links /tmp/wheels \
        torch==${PYTORCH_VERSION} && \

    # removing anyway is defensive.  Also remove /tmp artifacts.

RUN python -c "import torch; print('Torch', torch.__version__); assert torch.cuda.is_available() == False, 'GPU unexpectedly available'"

#     Run as unprivileged user — kernel exploits get sandboxed, not root.

#     Exception: writable tmp dirs mapped via tmpfs at container start (see compose).
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
```

## Layer-by-Layer Justification

### Layer ordering strategy (cache maximization)

| Layer | Invalidation trigger | Why ordered this way |
|-------|---------------------|----------------------|
| `COPY requirements.txt/pyproject.toml` | Dependency manifest changes | Changes ~once per sprint, not per commit |
| `pip wheel ...` | Same as above | Cache survives weeks of code edits |
| `COPY . .` (source) | Any source file change | Last so code churn doesn't bust dependency layers |
| `pip install` | Wheel directory changed | Offline install = deterministic, fast |

**Rule**: *Least-changed material → earliest layer. Most-changed → latest.* This means rebuilding from `pip install` (stage 2, step 2e) typically takes <5s after a code edit instead of re-downloading/rebuilding the 900MB+ PyTorch wheel.

### Multi-stage isolation rationale

**Stage 1 (build)** carries `build-essential`, `libpython3-dev`, pip caches, and the compiler toolchain. **Stage 2 (runtime)** starts from a fresh `python:3.12-slim-bookworm` and gets *nothing* from the build stage except two things: the pre-built `/wheels` directory and the venv skeleton. The compiler binaries, header files, and apt metadata never make it into the final image. This alone drops the image by ~400MB.

### Size budget breakdown

| Component | Approximate size |
|-----------|-----------------|
| `python:3.12-slim-bookworm` base | ~150 MB |
| torch 2.5.1 CPU wheel (installed) | ~750 MB |
| Other dependencies (transformers, uvicorn, etc.) | ~200 MB |
| Application source code | ~50 MB |
| Python standard library + venv overhead | ~100 MB |
| **Total (before compress)** | **~1,250 MB** |
| Post-compression savings | ~-50 MB |
| **Final estimated size** | **~1,200 MB** |

That's well under the 2.5GB ceiling. Compared to the original 9GB image, the reduction comes from:

1. **Slim bookworm vs full image** (~400 MB saved)
2. **No GPU drivers/CUDA toolkit** (~2 GB saved — these were likely the biggest bloat)
3. **Stripped compiler toolchain** (~300 MB saved)
4. **No pip/apt caches** in the runtime stage
5. **No test suites, datasets, or docs** packed into the image
6. **.dockerignore exclusions** preventing accidental inclusion

## Dockerfile — Python 3.12 + PyTorch Inference Service

```dockerfile
# =============================================================================
# Stage: builder — compile/install wheels, never present in final image
# =============================================================================
FROM python:3.12-slim-bookworm AS builder

WORKDIR /build

# Layer 1 — system packages (rarely changes).
# These are only needed for compiling C extensions (numpy, scipy, etc.).
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential gcc g++ pkg-config cmake wget && \
    rm -rf /var/lib/apt/lists/*

# Layer 2 — virtualenv (tiny, changes every time Python updates).
# Isolated venv ensures nothing leaks into the runtime stage.
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# Layer 3 — pip + setuptools wheel cache (stable across code changes).
# Upgrading pip/setuptools/wheel once; subsequent runs hit cache.
RUN pip install --no-cache-dir --upgrade pip setuptools wheel

# Layer 4 — application requirements (changes infrequently).
# Copy only requirements files first → pip cache survives app code changes.
COPY requirements.txt requirements-bundle.txt ./

# Layer 5 — install all wheels from requirements bundles.
# requirements.txt: your app deps (fastapi, uvicorn, requests, etc.)
# requirements-bundle.txt: explicit pinned torch + companion packages
#   e.g. torch==2.5.1+cpu -f https://download.pytorch.org/whl/torch_stable.html
#       torchvision==0.20.1+cpu -f https://download.pytorch.org/whl/torch_stable.html
# Using +cpu variant (no CUDA, no cuDNN, no NCCL — saves ~5-6 GB immediately).
# Pinned hashes via pip-tools/mypipdeps to prevent supply-chain tampering.
RUN pip install --no-cache-dir -r requirements-bundle.txt && \
    pip install --no-cache-dir -r requirements.txt

# Layer 6 — strip torch to remove CUDA stubs, test suites, and profiling tools.
# Even CPU-only torch ships extra binaries (~180 MB) we don't need.
RUN python - <<'STRIP'
import shutil, pathlib
base = pathlib.Path("/opt/venv/lib/python3.12/site-packages/torch")
for d in ("test", "binaries/cmake", "binaries/ccache", "utils/shared_memory"):
    p = base / d
    if p.exists(): shutil.rmtree(p, ignore_errors=True)
# Remove unused shared libraries (~30 MB of CUDA-aware libs)
for f in base.rglob("*cuda*"): f.unlink(missing_ok=True)
for f in base.rglob("*cudnn*"):  f.unlink(missing_ok=True)
for f in base.rglob("*nccl*"):   f.unlink(missing_ok=True)
STRIP

# =============================================================================
# Stage: runtime — minimal, non-root, < 2.5 GB
# =============================================================================
FROM python:3.12-slim-bookworm AS runtime

LABEL maintainer="engineering@yourteam.com" \
      description="CPU-only PyTorch inference service"

# --- Security: create dedicated non-root user --------------------------------
RUN groupadd --system --gid 1001 appgroup && \
    useradd --system --uid 1001 --gid appgroup --no-create-home --shell /usr/sbin/nologin appuser

# --- Runtime system deps (minimal, no build tools) --------------------------
# Only lib variants needed at runtime, not -dev headers.
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        libgomp1 libatomic1 && \
    rm -rf /var/lib/apt/lists/* && \
    apt-get purge -y --auto-remove

# --- Install wheels from builder (wheels only, never torch source/build) ----
COPY --from=builder /opt/venv/lib/python3.12/site-packages \
    /opt/venv/lib/python3.12/site-packages

# Virtualenv bin scripts (python binary comes from base image).
COPY --from=builder /opt/venv/bin /opt/venv/bin

# Keep ownership info from builder for chown.
RUN chown -R appuser:appgroup /opt/venv

ENV PATH="/opt/venv/bin:$PATH"

# --- Application code (LAST — changes most often, maximizes layer cache) -----
WORKDIR /srv/app

# Copy dependency manifests (for verification/reinstall if needed).
COPY requirements*.txt ./

# Application source.
COPY src/ ./src/
COPY config/ ./config/
COPY app.py ./

# Fix ownership for app directory.
RUN chown -R appuser:appgroup /srv/app

# --- Health probe ------------------------------------------------------------
# Lightweight: loads the model state dict (not the full pipeline) to verify
# PyTorch and model weights are intact. Falls back to port check only if
# model loading is slow. Runs as non-root.
COPY --chown=appuser:appgroup scripts/healthcheck.py /srv/app/healthcheck.py

# No ENV variables carrying secrets. All sensitive values passed at runtime
# via --env-file, Kubernetes secrets, or Docker secrets.

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD ["python", "/srv/app/healthcheck.py"]

ENTRYPOINT ["/opt/venv/bin/python", "-u", "app.py"]
```

## Layer-by-Layer Justification

| # | Layer | Why This Order? | Cache Impact |
|---|-------|----------------|-------------|
| **Builder L1** | System packages (`build-essential`, `gcc`, `cmake`) | Needed once for compiling native extensions (numpy/scipy/etc.). Never changes unless you upgrade compilers. | Stable — rebuilds only when system toolchain changes |
| **Builder L2** | Virtualenv | Creates `/opt/venv` directory structure. Changes only when Python base image tags change. | Stable |
| **Builder L3** | pip + setuptools + wheel upgrade | Pip bumps occasionally. Separated so it doesn't invalidate dependency install on code changes. | Stable |
| **Builder L4** | Copy requirements files | Two COPY directives before install enables pip to hit its download/cache layer. When app code changes but requirements don't, this layer (and all downstream) is cached. | High-value breakpoint |
| **Builder L5** | `pip install` wheels | Downloads and installs all packages. Longest layer (~2-5 min depending on bandwidth). If requirements don't change, Docker caches this entire layer — **this is the biggest win**. | Critical: code-only changes skip this |
| **Builder L6** | Strip torch extras | Removes test suites, CUDA stubs, profiling tools. Deterministic after L5. | Fast (~5 sec), only reruns if torch version changes |
| **Runtime** | Copy from builder | Copies installed wheels only. The torch wheel tarball was downloaded inside `builder` but never enters `runtime`. Size difference: ~780 MB wheel removed from final image. | N/A — always fast copy |
| **Runtime sys-deps** | `libgomp1`, `libatomic1` | OpenMP and atomics required for PyTorch CPU threading. Much smaller than `-dev` headers. | Rarely changes |
| **Runtime app code** | Copy src/, config/, app.py | Placed LAST because these files change on every deployment. With earlier layers cached, this COPY layer (plus HEALTHCHECK/CMD) takes ~1-2 seconds to rebuild. | Maximum cache hit rate for developer loop |

### Size Budget (estimated)

| Component | Size |
|-----------|------|
| `python:3.12-slim-bookworm` base | ~150 MB |
| System runtime libs (`libgomp1`, `libatomic1`) | ~3 MB |
| `torch==2.5.1+cpu` (stripped) | ~650 MB |
| torchvision (stripped) | ~50 MB |
| numpy, scipy, pandas, etc. | ~300 MB |
| App framework (fastapi, uvicorn, etc.) | ~50 MB |
| Application code + configs | ~10 MB |
| Overhead / tmpfs reserve | ~30 MB |
| **Total** | **~1,243 MB (~1.2 GB)** |

That's well under the 2.5 GB target — roughly a **6x reduction** from the original 9 GB monolithic image.

## Key Design Decisions

**Why `slim-bookworm` over `alpine`?**
PyTorch's official pre-built wheels are compiled against glibc. Alpine uses musl, which requires recompiling torch from source (a 45+ minute build and zero official support). Bookworm gives us binary compatibility at the cost of ~150 MB vs Alpine's ~7 MB — not worth the pain.

**Why virtualenv instead of system-wide pip?**
Keeps `/opt/venv` cleanly copyable between stages. System-wide pip pollutes `/usr/lib/python3/dist-packages` which we can't easily control or transfer.

**Why copy `requirements.txt` files but not `requirements-dev.txt`?**
Dev-only deps (pytest, mypy, black) inflate the image and aren't needed at inference time. Keep them separate in your repo; reference only `requirements.txt` and `requirements-bundle.txt` in the Dockerfile.

**Why strip torch post-install instead of selectively installing?**
PyTorch doesn't offer a "core-only" pip install. The programmatic strip approach removes ~180 MB of dead weight deterministically. An alternative is using `find /opt/venv -name "*.so" ! -name "*torch*" ! -name "*numpy*" -delete` for aggressive .so pruning if sizes are still too high.
