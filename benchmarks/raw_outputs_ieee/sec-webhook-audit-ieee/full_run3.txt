I'll analyze this systematically. The described architecture has several critical issues layered on top of each other.

## Vulnerabilities (Ordered by Severity)

### 1. CRITICAL — Signature Verification After JSON Parsing

This is a denial-of-service and potential bypass vector. An attacker sends a request with:
- Invalid payload that causes the parser to hang/memory blow up → server never reaches the HMAC check
- Malformed UTF-8 or deeply nested structures → resource exhaustion before auth

The raw body MUST be read, the HMAC verified against that exact byte sequence, AND THEN parsed. The signature covers the raw bytes; if you parse first, you've already consumed resources unauthenticated.

```python
# What it does (WRONG):
body = await request.json()           # ← parses everything, blows RAM on attack
sig = compute_hmac(body_bytes, secret) # ← too late, already paid CPU cost
```

### 2. CRITICAL — In-Memory Replay-ID Ledger

Three compounding failures:
- **Lost on restart**: Every reboot wipes all seen event IDs. Duplicate webhooks processed post-deploy = double-charged customers.
- **No cross-worker sharing**: With Uvicorn's multi-worker setup, worker A sees the ID but worker B doesn't. Concurrency doubles processing.
- **Unbounded memory**: No eviction policy. Long-running service grows until OOM.

A payment processor retrying deliveries over 24 hours will find every old ID gone and reprocess stale events.

### 3. HIGH — Secret Rotation Creates Unprocessable Requests

If the secret rotates and the old secret is immediately discarded, any delivery that arrives during network retries (common with Stripe/Plaid/etc.) using the old signature fails. There should always be a window where both `current` and `previous` secrets are accepted, with clear documentation of the overlap period.

### 4. HIGH — Missing Constant-Time Comparison on HMAC

Python's `==` operator short-circuits on the first differing byte. Given enough requests, an attacker can deduce the correct HMAC byte-by-byte via timing oracle. Use `secrets.compare_digest()`.

### 5. HIGH — No Concurrent Idempotency Control

Without a database-level UNIQUE constraint or advisory lock, two identical webhooks arriving simultaneously on different workers will both pass the "has this event_id been seen?" check (both see it as absent), then both process the charge. This creates a race condition. The check must be atomic and persisted.

### 6. MEDIUM — Processor Errors Leaked to Clients

Returning the raw exception message from the internal ledger write or signature computation gives attackers insight into the internal system. All external responses must be generic.

### 7. LOW — No Content-Length or Rate Limits

Missing headers mean no protection against extremely large payloads (even though HMAC should reject them, you're doing work before that). Rate limits prevent abuse of the endpoint itself.

def _ensure_secret_cache() -> None:
    """Pop _active_secrets with current + valid previous secret."""

    existing_keys = {s.key for s in _active_secrets}

    keys_to_add: list[str] = []

        keys_to_add.append(PREVIOUS_SECRET)

    _active_secrets.extend(_SecretEntry(key=k, expires_at=now + SECRET_TTL_SECONDS)
                           for k in keys_to_add)

    # Expire stale entries
    _active_secrets[:] = [s for s in _active_secrets if s.expires_at > now]


def verify_hmac(raw_body: bytes, provided_sig: str) -> bool:
    """Verify HMAC-SHA256 signature against ALL active secrets.

    Uses constant-time comparison via hmac.compare_digest.
    Returns True if ANY secret produces a match.
    """
    _ensure_secret_cache()
    for entry in _active_secrets:
        expected = hmac.new(
            entry.key.encode(), raw_body, hashlib.sha256
        ).hexdigest()
        if hmac.compare_digest(provided_sig, expected):
            return True
    return False

        conn = _get_db()
        now = time.time()
        conn.execute(
            "INSERT INTO event_ledger (event_id, received_at) VALUES (?, ?)",
            (event_id, now),

        return False, True  # new event

        return False, False  # unknown — reject to be safe

## Summary of Fixes

| Vulnerability | Fix |
|---|---|
| Parse before HMAC | Raw bytes read → HMAC checked → then parsed |
| In-memory replay store | SQLite table with `PRIMARY KEY` constraint |
| No cross-worker sync | Shared SQLite file (or swap to Postgres `INSERT ... ON CONFLICT` in production) |
| Memory bloat on replay table | Startup cleanup of entries > 24 h old |
| Secret rotation drops old sigs | `_active_secrets` tracks both current and previous with TTL expiry |
| Timing oracle on HMAC | `hmac.compare_digest()` (constant-time) |
| Race condition on duplicates | `UNIQUE` constraint makes check+insert atomic at DB level |
| Leaked processor errors | Generic `{"detail": "..."}` responses; `logger.exception()` for internal stack traces |
| Unlimited payload size | 256 KB `Content-Length` gate before HMAC work |
| No security headers | CSP + nosniff added to all error responses |
