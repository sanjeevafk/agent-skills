## Security Review: FastAPI Payment Webhook Endpoint

### Vulnerabilities Identified (Ordered by Severity)

#### 1. SECRET — Signature Verified After Body Parsing (Re DoS / Bypass Risk)

Verifying the HMAC *after* parsing the JSON body means every request—legitimate or malicious—gets fully deserialized before rejection. An attacker can hammer the endpoint with massive or malformed payloads, consuming CPU and memory for requests that will ultimately fail auth. Worse, if the parser raises an exception mid-parse, the handler might crash rather than return 401, giving the attacker free information about internal structure.

**Fix**: Verify the HMAC signature *before* touching the body. Read raw bytes, compute the digest, reject immediately on mismatch, then parse.

#### 2. HIGH — In-Memory Dict for Replay Prevention (State Loss / No Scale / No Durability)

An `in_memory_dict` has multiple failure modes:
- **Server restarts lose all recorded event IDs**, enabling replay of any previously delivered webhook after downtime.
- **Multi-process/container deployments** each have their own dict — a duplicate arriving at a different worker passes unchecked.
- **Unbounded growth** — no TTL or eviction strategy means eventual OOM.
- **Race conditions** — non-atomic check-then-insert allows concurrent duplicates to slip through.

**Fix**: Persist delivered event IDs to a database (PostgreSQL recommended) with a uniqueness constraint and automatic cleanup (e.g., retention window). Use the DB as the source of truth.

#### 3. HIGH — No Idempotency Under Concurrency (Race Condition)

Even with a DB ledger, there's a classic TOCTOU race: two concurrent identical webhooks both see "event X not yet seen" → both pass the check → both execute the payment logic. A plain `INSERT ... ON CONFLICT` needs to happen atomically with the business transaction, ideally via a DB-level unique index + advisory lock.

**Fix**: Wrap replay-check + business processing in a single DB transaction with explicit row-level locking (`SELECT FOR UPDATE` or advisory lock). The unique constraint is necessary but not sufficient; it must be part of the same atomic unit as the business logic.

#### 4. MEDIUM — No Constant-Time Signature Comparison (Timing Attack)

Using Python's `==` operator to compare HMAC digests leaks character-by-character timing information. While less critical than the above, it still gives an attacker measurable feedback during brute-force attempts against rotated secrets.

**Fix**: Use `hmac.compare_digest()` for all signature comparisons.

#### 5. MEDIUM — Error Leakage to Client

If the payment processor logic throws (e.g., DB down, external service error), exposing stack traces, SQL snippets, or internal error messages to the caller reveals architecture details. Even generic "Internal Server Error" responses can leak info via response time differences between success/failure paths.

**Fix**: Catch all domain errors at the top level, log them internally with full detail, and return only a generic 200 (for re-delivery safety) or 500 to the client. Include no error detail in responses.

#### 6. LOW — No Timestamp/Window Validation for Replayed Deliveries

Some processors re-send old events (hours/days later) for reconciliation. Without checking the event timestamp against an acceptable window, you may process stale financial events. Conversely, accepting events too far in the future is equally risky.

**Fix**: Reject events outside a configurable window (e.g., ±15 minutes for live events, plus a separate reconciliation window).

#### 7. LOW — Secret Rotation Timing Window

During secret rotation, both old and new keys are active. If the signing library defaults to one key during partial overlap, early/late events get rejected. Also, computing HMAC with the wrong key doesn't distinguish between "wrong key" and "tampered payload."

**Fix**: Maintain a key store keyed by version ID. Include the key version in the HMAC header so the verifier tries the right candidate. Log which key was tried for audit purposes.

### CRITICAL — CVE-class issues

| # | Vulnerability | Files Affected | Impact |
|---|---|---|
| **C1** | **HMAC verified AFTER JSON parsing** | All four files parse JSON *after* verifying, but `payment_webhook_secure.py` (the "corrected" one) never captures the raw body at all — it calls `request.json()` inside `handle_payment_webhook`, consuming the stream. The HMAC must be computed on the exact wire bytes BEFORE any `.json()` or `.body()` call. Two files (`*_fixed.py`, `*_secured.py`) attempt raw-body capture but their FastAPI dependency wiring is broken (uses ad-hoc `DependsRawBody()` class that doesn't integrate). |
| **C2** | **Replay detection via persistent store — still racy due to connection-per-request** | All versions open a fresh SQLite connection per request via `async with ReplayLedger(...)`. While WAL + atomic INSERT helps, each request creates/destroys a connection. In production under high concurrency this can hit SQLite `too many open files` or cause connection timeouts. The ledger should be a long-lived singleton. |
| **C3** | **No body-size ceiling before HMAC computation** | `*_secure.py` and `*_hardened.py` do NOT enforce `_MAX_BODY_BYTES` at all — an attacker sends a 2GB payload, the server buffers it to compute HMAC, OOM kills the process. Only `*_fixed.py` and `*_secured.py` implement it. |

### HIGH — Exploitable weaknesses

| # | Vulnerability | Files Affected | Impact |
|---|---|---|
| **H1** | **Timing side-channel in fallback key iteration** | All files. When `key_id` is absent or unknown, each version iterates `all_keys` with early `break`. This leaks how many keys exist (stop-counting) and whether an expired key was reached. An attacker distinguishes 1 valid key from 2 valid keys via elapsed time. |
| **H2** | **Expired key accepted after signature match** | `*_hardened.py` and `*_secured.py`. When `key_id` matches an entry and the signature verifies, expiry is checked correctly in those two files. BUT `*_secure.py` does NOT check `expires_at` at all — expired keys remain permanently valid. |
| **H3** | **Error responses leak internal state** | `*_hardened.py`: logs `f"Payment processing failed for event {event_id}: {exc}"` where `{exc}` may contain DB connection strings, internal stack traces. `*_secure.py` catches silently but its generic `ProcessingResult` is good; however `*_hardened.py` exposes the exception object to its own logs AND some paths return raw Python exceptions that FastAPI converts to verbose HTML. |
| **H4** | **Secret-ring mutation not concurrency-safe** | `*_hardened.py` and `*_secure.py` use plain `list.append()` on `SecretRing._ring` without any lock. Concurrent key rotation (e.g., admin API triggers rotation while webhook handler reads `all_keys`) can cause corrupted iteration or lost keys. |

### MEDIUM — Operational risk

| # | Vulnerability | Files Affected | Impact |
|---|---|---|
| **M1** | **Deprecated `asyncio.get_event_loop()`** | `*_hardened.py` lines 104, 120, 139. Uses `__import__("asyncio").get_event_loop()` which raises `DeprecationWarning` in Python 3.10+ and will become an error in 3.12+. Use `asyncio.get_running_loop()`. |
| **M2** | **Log leakage of sensitive payload fields** | `*_secure.py` does not mask any fields. `*_hardened.py` includes `order_id` and potentially other fields unmasked in logs. Should mask fields like `customer_email`, `card_number`, `cvv`. |
| **M3** | **No CORS / trusted-origin validation** | No origin checking whatsoever. Any external site can POST to `/webhooks/payment`. Webhook endpoints should validate `Origin` or `Referer` headers against known processor domains. |
| **M4** | **Background cleanup task may not start reliably** | All files use `@app.on_event("startup")` which is deprecated. Should use `lifespan` context manager. Under certain deployment configs (gunicorn workers > 1), the cleanup task may not fire at all if it attaches to the wrong worker. |

### LOW — Hardening

| # | Vulnerability | Files Affected |
|---|---|---|
| **L1** | Rate limiting not wired through actual `slowapi` limiter decorator | All files |
| **L2** | No Content-Security-Policy or other security headers on webhook responses | All files |
| **L3** | Missing `X-Content-Type-Options: nosniff` and `Cache-Control: no-store` | All files |
| **L4** | No audit logging of successful vs rejected deliveries | Some files partially cover this |

        async with self._lock:

            self._ring.sort(key=lambda s: s.activated_at, reverse=True)

## Security Review: FastAPI Payment Webhook Endpoint

### Vulnerabilities (Ordered by Severity)

**CRITICAL-1: Signature Verification After Body Parsing (Replay & Resource Exhaustion)**
Verifying HMAC *after* parsing the full JSON body lets attackers send massively inflated payloads to consume CPU/memory/Disk before rejection. The signature check gates nothing because processing begins before authentication. An attacker can exhaust server resources with tiny amounts of bandwidth — a classic slowloris/body-flood vector.

**CRITICAL-2: In-Memory Replay-ID Ledger (State Loss & Concurrent Race)**
Storing event IDs in an `in_memory_dict` means: (a) all dedup state vanishes on restart, opening the door to replays after any deployment/crash; (b) concurrent duplicate webhooks hit different worker processes and see different dicts, so both get processed — defeating the entire idempotency guarantee.

**CRITICAL-3: Non-Idempotent Concurrent Handling (Double-Charge Risk)**
Without atomic check-then-insert guards on the event ledger, two simultaneous identical webhooks pass the replay check simultaneously (neither sees the other's insertion), causing duplicate payment execution. This is a textbook TOCTOU race.

**HIGH-4: No Timestamp / Window Validation (Replay Window Unlimited)**
No timestamp validation means a captured webhook can be replayed indefinitely. Even if replay-IDs worked, there's no defense-in-depth via time-bounded validity windows (e.g., reject events older than 5 minutes).

**HIGH-5: No Rate Limiting on Webhook Endpoint**
Any unauthenticated or poorly-gated webhook targetable endpoint becomes an openDoS vector if rate-limited only at the reverse-proxy level (which may not see through TLS termination).

**MEDIUM-6: Secret Rotation Without Old-Key Support**
Rotating the HMAC secret invalidates pending legitimate webhooks delivered during propagation. A rotating-key scheme must accept either current OR previous secrets for a grace period.

**MEDIUM-7: Error Detail Leakage**
Processor errors (stack traces, SQL details, upstream status codes) exposed in HTTP responses give attackers reconnaissance data about internal architecture, dependency versions, and database schema.

**LOW-8: Missing Timing-Safe Comparison on HMAC**
Using `==` instead of `hmac.compare_digest()` enables byte-by-byte timing attacks against the expected signature. Attractive only when an attacker has high-precision latency measurement, but trivially mitigable.

**LOW-9: No Content-Type Enforcement**
Accepting non-JSON content types wastes parsing effort and could trigger unexpected deserialization paths in some frameworks.

def _compute_hmac(body_bytes: bytes, secret: str) -> str:
    """Return hex-encoded HMAC-SHA256 using the configured secret."""
    return hmac.new(
        secret.encode("utf-8"),
        body_bytes,
        hashlib.sha256,
    ).hexdigest()


def _verify_hmac_timing_safe(computed: str, provided: str) -> bool:
    """Timing-safe comparison of two hex HMAC digests."""
    return hmac.compare_digest(computed.encode("ascii"), provided.encode("ascii"))


def _validate_timestamp(ts_header: str) -> bool:
    """Reject events outside the allowed time window."""
    try:
        ts_epoch = float(ts_header)
    except (ValueError, TypeError):
        return False
    now = time.time()
    return abs(now - ts_epoch) <= WEBHOOK_TIMESTAMP_TOLERANCE_SEC
