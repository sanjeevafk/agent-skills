## Security Review: FastAPI Payment Webhook Endpoint

### Vulnerabilities Identified (Ordered by Severity)

#### 1. SECRET — Signature Verified After Body Parsing (Re DoS / Bypass Risk)

Verifying the HMAC *after* parsing the JSON body means every request—legitimate or malicious—gets fully deserialized before rejection. An attacker can hammer the endpoint with massive or malformed payloads, consuming CPU and memory for requests that will ultimately fail auth. Worse, if the parser raises an exception mid-parse, the handler might crash rather than return 401, giving the attacker free information about internal structure.

**Fix**: Verify the HMAC signature *before* touching the body. Read raw bytes, compute the digest, reject immediately on mismatch, then parse.

#### 2. HIGH — In-Memory Dict for Replay Prevention (State Loss / No Scale / No Durability)

An `in_memory_dict` has multiple failure modes:
- **Server restarts lose all recorded event IDs**, enabling replay of any previously delivered webhook after downtime.
- **Multi-process/container deployments** each have their own dict — a duplicate arriving at a different worker passes unchecked.
- **Unbounded growth** — no TTL or eviction strategy means eventual OOM.
- **Race conditions** — non-atomic check-then-insert allows concurrent duplicates to slip through.

**Fix**: Persist delivered event IDs to a database (PostgreSQL recommended) with a uniqueness constraint and automatic cleanup (e.g., retention window). Use the DB as the source of truth.

#### 3. HIGH — No Idempotency Under Concurrency (Race Condition)

Even with a DB ledger, there's a classic TOCTOU race: two concurrent identical webhooks both see "event X not yet seen" → both pass the check → both execute the payment logic. A plain `INSERT ... ON CONFLICT` needs to happen atomically with the business transaction, ideally via a DB-level unique index + advisory lock.

**Fix**: Wrap replay-check + business processing in a single DB transaction with explicit row-level locking (`SELECT FOR UPDATE` or advisory lock). The unique constraint is necessary but not sufficient; it must be part of the same atomic unit as the business logic.

#### 4. MEDIUM — No Constant-Time Signature Comparison (Timing Attack)

Using Python's `==` operator to compare HMAC digests leaks character-by-character timing information. While less critical than the above, it still gives an attacker measurable feedback during brute-force attempts against rotated secrets.

**Fix**: Use `hmac.compare_digest()` for all signature comparisons.

#### 5. MEDIUM — Error Leakage to Client

If the payment processor logic throws (e.g., DB down, external service error), exposing stack traces, SQL snippets, or internal error messages to the caller reveals architecture details. Even generic "Internal Server Error" responses can leak info via response time differences between success/failure paths.

**Fix**: Catch all domain errors at the top level, log them internally with full detail, and return only a generic 200 (for re-delivery safety) or 500 to the client. Include no error detail in responses.

#### 6. LOW — No Timestamp/Window Validation for Replayed Deliveries

Some processors re-send old events (hours/days later) for reconciliation. Without checking the event timestamp against an acceptable window, you may process stale financial events. Conversely, accepting events too far in the future is equally risky.

**Fix**: Reject events outside a configurable window (e.g., ±15 minutes for live events, plus a separate reconciliation window).

#### 7. LOW — Secret Rotation Timing Window

During secret rotation, both old and new keys are active. If the signing library defaults to one key during partial overlap, early/late events get rejected. Also, computing HMAC with the wrong key doesn't distinguish between "wrong key" and "tampered payload."

**Fix**: Maintain a key store keyed by version ID. Include the key version in the HMAC header so the verifier tries the right candidate. Log which key was tried for audit purposes.

class KeyRing:
    """Manages rotating HMAC secrets keyed by version ID."""

    def __init__(self, keys: dict[str, bytes]):
        self._keys: dict[str, bytes] = dict(keys)
        self._current_version: str | None = next(iter(self._keys)) if self._keys else None

    def compute_hmac(self, message: bytes, version: str | None = None) -> bytes:
        """Sign a message with the current or specified key."""
        if version is None:
            version = self._current_version or self._keys["v1"]  # fallback
        key = self._keys.get(version)
        if key is None:
            raise ValueError(f"Unknown key version: {version}")
        return hmac.new(key, message, hashlib.sha256).digest()

    def verify_hmac(self, message: bytes, version: str, expected_sig: bytes) -> bool:
        """Constant-time comparison against a specific key version."""
        try:
            actual_sig = self.compute_hmac(message, version)
            return hmac.compare_digest(actual_sig, expected_sig)
        except Exception:
            return False

    def find_key_version(self, version_str: str) -> Optional[bytes]:
        return self._keys.get(version_str)

async def _enforce_idempotency(db: AsyncSession, event_id: str, processor: str) -> bool:
    """
    Atomically claim an event_id. Returns True if ALREADY processed (replay detected).

    Pattern: INSERT ... ON CONFLICT WHERE NOT processed_ok DO UPDATE sets a flag,
    but simpler: ON CONFLICT DO NOTHING + count rows. With asyncio we use:
    """
    query = text(
        """INSERT INTO delivered_events (event_id, processor_name, received_at, processed_ok)
           VALUES (:eid, :proc, NOW(), TRUE)
           ON CONFLICT (event_id)
           DO UPDATE SET received_at = EXCLUDED.received_at
           RETURNING id IS NULL AS inserted"""
    )
    result = await db.execute(query, {"eid": event_id, "proc": processor})
    row = result.fetchone()
    inserted = row[0] if row else None
    await db.commit()
    # If inserted is True (or None meaning conflict resolved), it's not a new insertion
    # We want: True = replay detected
    return not bool(inserted)

    Secure webhook endpoint — all security gates run BEFORE body processing.

        return JSONResponse(status_code=400, content={"error": "invalid_request"})

    # ---------------------------------------------------------------
    # GATE 2: Validate timestamp window
    # ---------------------------------------------------------------
    try:
        event_ts = datetime.fromisoformat(timestamp_str.replace("Z", "+00:00"))
    except (ValueError, AttributeError):
        logger.warning("Invalid timestamp header: %s", timestamp_str)
        return JSONResponse(status_code=400, content={"error": "invalid_request"})

    now_utc = datetime.now(timezone.utc)
    age = abs((now_utc - event_ts).total_seconds())

    # Live window: reject very old events (not reconciliation)
    if age > WEBHOOK_TIMESTAMP_WINDOW_SECONDS:
        logger.warning("Event too old: age=%.0fs id=%s", age, event_id)
        return JSONResponse(status_code=400, content={"error": "stale_event"})

    # GATE 3: Verify HMAC signature BEFORE parsing body
    # ---------------------------------------------------------------
    raw_body = await request.body()

    # Compute: hmac_sha256(secret, version_id + "." + timestamp + "." + body)

    try:
        key_bytes = KEY_RING.find_key_version(secret_version)
        if key_bytes is None:
            logger.warning("Unknown key version during signature verify: %s", secret_version)
            return JSONResponse(status_code=401, content={"error": "unauthorized"})

        expected_sig = hmac.new(key_bytes, signing_input, hashlib.sha256).digest()
        sig_valid = hmac.compare_digest(expected_sig, bytes.fromhex(hmac_signature))
    except Exception as exc:

        logger.warning("Invalid HMAC signature: event_id=%s", event_id)

### Architecture Summary

| Layer | Mechanism | Protects Against |
|---|---|---|
| **Ordering** | Headers → HMAC → body | Re DoS, bypass, resource exhaustion |
| **Auth** | `hmac.compare_digest()` + key-versioned secrets | Timing attacks, wrong-key confusion |
| **Timestamps** | ±15 min live window | Stale/future event injection |
| **Replay** | PostgreSQL `UNIQUE(event_id)` + atomic INSERT | Server restart, multi-instance |
| **Concurrency** | Same DB transaction owns claim + processing | Race conditions between workers |
| **Errors** | Catch-all handler returns `{"error": "internal_error"}` | Info disclosure, stack trace leaks |
| **Retention** | Background pruner removes records after 90 days | Unbounded disk growth |
| **Defense-in-depth** | Business logic is also idempotent | Edge cases (crash between claim + business) |

### Key Design Decisions Explained

1. **HMAC-before-parse is mandatory.** Reading raw body bytes for signature verification costs ~microseconds. Full JSON deserialization of a 10MB crafted payload costs megabytes of RAM and milliseconds of CPU. On a high-throughput endpoint, this difference is the delta between healthy operation and a simple DDoS.

2. **The atomic claim pattern.** `ON CONFLICT DO NOTHING` isn't enough by itself — you need to detect whether the insert took or hit a conflict. The `RETURNING id IS NULL` clause gives us a single-row boolean: `False` = conflict (replay), `True` = fresh insert. This entire operation is a single round-trip to the database and runs within the ACID boundary of the surrounding transaction.

3. **Returning 200 on business errors** is intentional for payment webhooks. Processors expect a 2xx to stop retrying. Returning 500 triggers exponential-backoff retries that waste resources and can create cascading retries. Instead, return 200 (stop the loop), log critically, and alert your ops team for manual review. See [Stripe's webhook best practices](https://stripe.com/docs/webhooks/best-practices) — they recommend exactly this pattern.
