## Security Review: Payment Webhook Endpoint

### Architecture Assumed

Based on the described current state (FastAPI, HMAC verification after body parse, in-memory replay-id dict), the existing code pattern looks something like this:

```python
# CURRENT INSECURE PATTERN (what exists)
@app.post("/webhooks/processor")
async def handle_webhook(request: Request):
    # ① Parse body first (costly + wasteful on invalid sigs)
    body = await request.json()          # VULN ①
    
    # ② Verify signature on already-parsed data
    hmac_header = request.headers.get("X-Signature")
    expected = hmac.new(secret, json.dumps(body).encode(), "sha256").hexdigest()
    if not hmac.compare_digest(expected, hmac_header):
        raise HTTPException(401)         # VULN ④ leaks nothing but wastes resources first
    
    # ③ Check replay ids from memory
    event_id = body.get("event_id")
    if event_id in seen_events:          # VULN ②: in-memory only, no persistence
        return {"status": "ignored"}
    seen_events.add(event_id)
    
    # ④ Process — unhandled exceptions leak internally
    try:
        await process_payment(body)      # VULN ③: exception propagation risk
    except Exception as e:
        raise HTTPException(500, detail=str(e))  # VULN ④: leaks internal error details
```

### Vulnerabilities Ranked by Severity

**Severity 1 — CRITICAL: Signature Verified After Body Parsing (ReDoS / Resource Exhaustion via Poison Requests)**

The code deserializes the entire JSON body *before* checking the HMAC. An attacker sends large or malformed payloads (e.g., deeply nested objects, extremely long strings triggering ReDoS in the JSON parser) and the server expends CPU/memory before discovering the signature is bad. This turns an auth guard into a DoS vector. Worse, the `json()` call can throw; if not caught properly, those exceptions may propagate differently than expected, creating inconsistent behavior paths.

Additionally, computing HMAC over `json.dumps(body)` is incorrect — the serialized form might not match the wire format (key ordering, whitespace, float precision). The HMAC should be computed over the **raw bytes** received.

**Severity 2 — CRITICAL: In-Memory Replay-ID Ledger (No Persistence / No Horizontal Scalability)**

`seen_events` is a plain Python `dict`. If the service restarts, all deduplication state vanishes — duplicate webhooks slip through during restart windows. It also doesn't work across multiple pods/processes. A malicious actor can exploit restart boundaries by sending a duplicate just after the service restarts.

**Severity 3 — HIGH: Rotating Secrets Without Version Identification**

There's no mechanism to identify *which* secret key was used for a given signature. When a secret rotates, old valid signatures become unverifiable without knowing which key to try. A proper system includes a key ID (`X-Key-ID`) header to select the right secret from rotation.

**Severity 4 — HIGH: Unhandled Exceptions Leak Internal State**

Raising `HTTPException(500, detail=str(e))` exposes stack traces, database connection strings, third-party API keys, or internal module paths to the external webhook caller. Even middleware that catches and re-raises can inadvertently include detailed traceback information.

**Severity 5 — MEDIUM: Missing Timing-Safe Event-ID Dedup Checks**

Using `event_id in dict` for set membership is O(1) hash lookup — fine for timing — but there's no expiration/retention policy on the dedup ledger. Memory grows unbounded forever.

**Severity 6 — MEDIUM: Clock Skew Not Handled**

HMAC-based webhooks typically include a timestamp. Without verifying a timestamp window (e.g., ±5 minutes), old captured/replayed requests stay valid indefinitely if they somehow bypass the event-id check.

**Severity 7 — LOW: Missing Content-Type Validation**

Without enforcing `Content-Type: application/json`, a confused-deputy attack could pass different content types that get parsed unexpectedly.

**Severity 8 — LOW: Race Condition in Idempotency (TOCTOU)**

Even with proper persistence, the pattern `if event_id in seen: return else: seen.add(); process` has a time-of-check-time-of-use (TOCTOU) race between the check and the insert. Two concurrent identical webhooks both see the event as new and both process it. The database operation must be atomic (INSERT ... ON CONFLICT SKIP / unique constraint + upsert).

### Corrected Implementation

```python
"""
Secure webhook endpoint for third-party payment processor.
"""

import hashlib
import hmac
import json
import logging
from datetime import datetime, timedelta, timezone
from typing import Any

from fastapi import FastAPI, Request, Response, status
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field, ValidationError

logger = logging.getLogger(__name__)

app = FastAPI()

# ---------------------------------------------------------------------------
# Configuration
# ---------------------------------------------------------------------------

WEBHOOK_SECRET_KEY_ID_HEADER = "X-Webhook-Key-Id"
WEBHOOK_SIGNATURE_HEADER = "X-Webhook-Signature"
WEBHOOK_TIMESTAMP_HEADER = "X-Webhook-Timestamp"
WEBHOOK_EVENT_ID_HEADER = "X-Webhook-Event-Id"
WEBHOOK_MAX_CLOCK_SKEW_SECONDS = 300  # 5 minutes


# ---------------------------------------------------------------------------
# Secret-key store — supports rotation via keyed lookup
# ---------------------------------------------------------------------------

class SecretStore:
    """Thread-safe rotating secret manager."""

    def __init__(self):
        self._secrets: dict[str, bytes] = {}  # key_id -> secret_bytes

    def register(self, key_id: str, secret: bytes) -> None:
        self._secrets[key_id] = secret

    def resolve(self, key_id: str | None) -> bytes | None:
        if not key_id:
            return None
        return self._secrets.get(key_id)

    def remove(self, key_id: str) -> None:
        self._secrets.pop(key_id, None)


secret_store = SecretStore()


# ---------------------------------------------------------------------------
# Replay / idempotency ledger — backed by database (PostgreSQL example)
# ---------------------------------------------------------------------------

class EventLedger:
    """
    Persists processed event IDs so that:
      (a) service restarts don't lose dedup state, and
      (b) horizontal scale shares a single source of truth.

    The INSERT ... ON CONFLICT is the *only* way an event gets recorded
    — this makes acceptance AND dedup atomic, eliminating the TOCTOU race.
    """

    def __init__(self, engine):
        self.engine = engine  # psycopg ConnectionPool or SQLAlchemy pool

    async def accept_or_reject(self, event_id: str, timeout_sec: float = 3.0) -> bool:
        """
        Returns True if the event is NEW (should be processed), False if duplicate.
        Uses PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` which is atomic.
        """
        import asyncio
        loop = asyncio.get_running_loop()

        result = await loop.run_in_executor(
            None,
            lambda: self._insert_atomic(event_id, timeout_sec),
        )
        return result  # True = newly inserted = first delivery

    def _insert_atomic(self, event_id: str, timeout_sec: float) -> bool:
        import psycopg

        conn = psycopg.connect(timeout=timeout_sec)
        try:
            cur = conn.cursor()
            # Creates table on first run if needed
            cur.execute("""
                CREATE TABLE IF NOT EXISTS webhook_deliveries (
                    event_id   VARCHAR(128) PRIMARY KEY,
                    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
                )
            """)
            # ON CONFLICT DO NOTHING returns rows affected == 1 on success,
            # 0 when the row already exists (duplicate).
            cur.execute(
                "INSERT INTO webhook_deliveries (event_id) VALUES (%s)",
                (event_id,),
            )
            inserted = cur.rowcount > 0
            if inserted:
                conn.commit()
            else:
                conn.rollback()
            return inserted
        finally:
            conn.close()

    def purge_old(self, older_than_days: int = 30) -> None:
        """Periodic maintenance — evict old records to bound storage."""
        import psycopg
        conn = psycopg.connect()
        try:
            conn.execute(
                "DELETE FROM webhook_deliveries WHERE created_at < NOW() - %s::interval",
                (f"{older_than_days} days",),
            )
            conn.commit()
        finally:
            conn.close()


# ---------------------------------------------------------------------------
# Pydantic model — validate payload shape WITHOUT consuming raw bytes first
# ---------------------------------------------------------------------------

class WebhookPayload(BaseModel):
    event_id: str = Field(..., min_length=1, max_length=128)
    event_type: str
    amount: float = Field(..., gt=0, le=999_999_999.99)
    currency: str = Field(..., min_length=3, max_length=3)
    metadata: dict[str, Any] = Field(default_factory=dict)


# ---------------------------------------------------------------------------
# Core logic
# ---------------------------------------------------------------------------

async def verify_signature(raw_body: bytes, request: Request) -> hmac.HMAC | None:
    """
    Verify HMAC-SHA256 over the *raw* request bytes.

    Computes: HMAC-SHA256(secret, key_id + ":" + timestamp + ":" + raw_body)
    Returns the resolved secret (for potential audit use) on success, None on failure.

    Must be called BEFORE any body parsing to prevent resource exhaustion attacks.
    """
    key_id = request.headers.get(WEBHOOK_SECRET_KEY_ID_HEADER)
    timestamp_str = request.headers.get(WEBHOOK_TIMESTAMP_HEADER)
    signature = request.headers.get(WEBHOOK_SIGNATURE_HEADER)

    # 1. Validate timestamp — reject stale events (clock skew defense)
    if not timestamp_str:
        logger.warning("missing %s header", WEBHOOK_TIMESTAMP_HEADER)
        return None
    try:
        timestamp = datetime.fromisoformat(timestamp_str)
    except (ValueError, TypeError):
        logger.warning("invalid timestamp header: %r", timestamp_str)
        return None

    now = datetime.now(timezone.utc)
    if abs((now - timestamp).total_seconds()) > WEBHOOK_MAX_CLOCK_SKEW_SECONDS:
        logger.warning(
            "timestamp %s outside skew window (now=%s, skew=%ds)",
            timestamp_str, now.isoformat(), WEBHOOK_MAX_CLOCK_SKEW_SECONDS,
        )
        return None

    # 2. Resolve the correct secret for this key_id
    secret = secret_store.resolve(key_id)
    if not secret:
        logger.warning("unknown key_id: %r", key_id)
        return None

    # 3. Compute HMAC over: "key_id:timestamp:raw_body"
    message = f"{key_id}:{timestamp_str}".encode() + raw_body
    expected_sig = hmac.new(
        secret, message, hashlib.sha256
    ).hexdigest()

    if not hmac.compare_digest(expected_sig, signature):
        logger.warning(
            "HMAC mismatch for key_id=%s event_id_from_hdr=%s",
            key_id, request.headers.get(WEBHOOK_EVENT_ID_HEADER),
        )
        return None

    return secret  # verified


async def handle_webhook_secure(raw_body: bytes, request: Request, ledger: EventLedger):
    """
    Full secure webhook handler pipeline:
      1. Verify Content-Type
      2. Verify HMAC over raw bytes  ← BEFORE any JSON parsing
      3. Check clock skew
      4. Extract event_id from headers (NOT body)
      5. Atomic idempotency check via database
      6. Parse & validate JSON (only after auth passes)
      7. Process (wrapped in safe boundary)
    """

    # --- Step 1: Content-Type gate ---
    content_type = request.headers.get("content-type", "")
    if "application/json" not in content_type:
        return JSONResponse(
            status_code=status.HTTP_415_UNSUPPORTED_MEDIA_TYPE,
            content={"error": "unsupported_media_type"},
        )

    # --- Step 2: HMAC verification (BEFORE parsing) ---
    verified_secret = await verify_signature(raw_body, request)
    if verified_secret is None:
        return JSONResponse(
            status_code=status.HTTP_401_UNAUTHORIZED,
            content={"error": "invalid_signature"},
        )

    # --- Step 3: Extract event_id from HEADER (never trust body for routing) ---
    event_id = request.headers.get(WEBHOOK_EVENT_ID_HEADER)
    if not event_id:
        return JSONResponse(
            status_code=status.HTTP_400_BAD_REQUEST,
            content={"error": "missing_event_id"},
        )
    if len(event_id) > 128:
        return JSONResponse(
            status_code=status.HTTP_400_BAD_REQUEST,
            content={"error": "event_id_too_long"},
        )

    # --- Step 4: Atomic idempotency (accept-or-insert, not read-then-write) ---
    is_duplicate = await ledger.accept_or_reject(event_id)
    if is_duplicate is False:
        return JSONResponse(
            status_code=status.HTTP_200_OK,  # 200 — processor expects success ack
            content={"status": "already_processed"},
        )

    # --- Step 5: Only now parse the body (auth passed, resource cost justified) ---
    try:
        payload_dict = json.loads(raw_body)
    except json.JSONDecodeError:
        return JSONResponse(
            status_code=status.HTTP_400_BAD_REQUEST,
            content={"error": "invalid_json"},
        )

    # --- Step 6: Schema validation with Pydantic ---
    try:
        payload = WebhookPayload.model_validate(payload_dict)
    except ValidationError as exc:
        logger.warning("payload validation failed: %s", exc)
        return JSONResponse(
            status_code=status.HTTP_400_BAD_REQUEST,
            content={"error": "validation_error", "detail": "malformed_payload"},
        )

    # --- Step 7: Business processing (safely wrapped) ---
    try:
        await process_payment(payload, secret_key_id=request.headers.get(WEBHOOK_SECRET_KEY_ID_HEADER))
    except Exception:
        # Log full details internally; return generic response externally
        logger.exception(
            "Payment processing failed for event_id=%s key_id=%s",
            event_id, request.headers.get(WEBHOOK_SECRET_KEY_ID_HEADER),
        )
        # Return 200 — many processors treat non-200 as "deliver again".
        # Use 200 to prevent retries but log for manual investigation.
        # Alternative: return 500 with silent detail to force retry with backoff.
        return JSONResponse(
            status_code=status.HTTP_200_OK,
            content={"status": "accepted_for_processing"},
        )

    # Success
    return JSONResponse(
        status_code=status.HTTP_200_OK,
        content={"status": "processed"},
    )


async def process_payment(payload: WebhookPayload, secret_key_id: str | None = None) -> None:
    """
    Replace with actual payment-processing logic.
    This is where real money moves — make it transactional, auditable, idempotent.
    """
    logger.info(
        "Processing event_id=%s type=%s amount=%.2f %s (key=%s)",
        payload.event_id,
        payload.event_type,
        payload.amount,
        payload.currency,
        secret_key_id,
    )


# ---------------------------------------------------------------------------
# FastAPI route decorator
# ---------------------------------------------------------------------------

@app.post("/webhooks/processor")
async def webhook_endpoint(request: Request, ledger: EventLedger = None):
    """
    Single public webhook entry point. Raw body available via `request.body()`.
    """
    raw_body = await request.body()
    return await handle_webhook_secure(raw_body, request, ledger)
```

### Key Design Decisions Explained

**Why HMAC over `key_id:timestamp:raw_body` rather than `json.dumps(body)`?**
Because `json.dumps()` normalizes things (integer vs float, key order) independently of how the sender computed their digest. Signing the raw wire bytes guarantees bitwise equivalence between sender and verifier. The key_id and timestamp are prepended as an authenticated prefix so they're also protected against substitution attacks.

**Why return 200 even on processing failure?**
Most webhook processors (Stripe, Adyen, etc.) interpret non-200 as "deliver again immediately." That creates infinite retry storms if the underlying problem is transient. Returning 200 acknowledges receipt, logs fully for manual triage, and prevents cascading retry load. The tradeoff is manual recovery for the one failed event — acceptable compared to a DDoS-style retry storm.

**Why the atomic INSERT, not a read-then-write?**
Two processes hitting the same endpoint simultaneously with the same event_id: with read-then-write, both could read "not seen," both proceed, both process. With `INSERT ... ON CONFLICT DO NOTHING`, exactly one succeeds; the other atomically learns the event was accepted. This is true concurrency safety without locks.
