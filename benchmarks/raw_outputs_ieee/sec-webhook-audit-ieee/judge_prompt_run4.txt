## Vulnerability Analysis (Ordered by Severity)

### VULN-1 [CRITICAL] — HMAC Verified After JSON Parsing

**What happens:** `request.json()` is called first, consuming the request body stream. The HMAC is then computed against a *re-serialized* version of the parsed-and-re-emitted payload, not the exact bytes that traversed the wire.

**Impact:** An attacker can modify the raw HTTP body in transit (e.g., inject a new field, reorder keys, strip whitespace) and receive a valid-looking re-serialized JSON that still produces a passing HMAC check — or more insidiously, the parser itself may canonicalize in unpredictable ways depending on the library/version. Even if re-serialization appears identical today, it creates a fragile invariant that any framework update can silently break. Worse, malformed bodies that cause the JSON parser to throw get caught *after* a potentially partial computation, creating a TOCTOU window.

**Fix:** Capture raw body bytes *before* any parsing. Use the exact byte string for the HMAC calculation. Only parse JSON after the signature is proven valid.

### VULN-2 [CRITICAL] — In-Memory Dict for Replay IDs (No Persistence + No Concurrency Safety)

**What happens:** `seen_events: dict[str, bool] = {}` lives in process memory only.

**Three distinct sub-vulnerabilities here:**

| Sub-issue | Impact |
|---|---|
| **Process restart loses state** | A deployment, crash, or OOM kill wipes the entire ledger. Every webhook re-delivered post-restart is treated as new — enabling duplicate charge processing. |
| **Multi-process / multi-worker blind spot** | With Gunicorn/Uvicorn workers, each worker has its own dict. Worker-A processes event `E`, Worker-B receives the same delivery and writes/reads its own empty dict — both process the charge. This is a classic race condition with real financial consequences. |
| **No bounded storage** | The dict grows unboundedly. Under high throughput (or an attacker flooding unique event IDs), memory consumption becomes a denial-of-service vector. |

**Fix:** Persistent SQLite (WAL mode for concurrent-reader safety) with atomic `INSERT OR IGNORE` via PRIMARY KEY conflict detection. This single statement guarantees that two concurrent callers cannot both claim the same event ID, regardless of worker count. Add periodic cleanup to bound size.

### VULN-3 [HIGH] — Missing Body-Size Ceiling Before Signature Check

**What happens:** The raw body is consumed without limit. An attacker sends a 2 GB payload; the server allocates it into memory before even reaching the HMAC check.

**Impact:** Memory-exhaustion DoS pre-authentication. This is trivially exploitable and requires no credentials.

**Fix:** Enforce a configurable ceiling (e.g., 256 KB) during body capture. Return 413 immediately if exceeded.

### VULN-4 [HIGH] — Expired Secrets Accepted If Signature Matches

**What happens:** When rotating secrets, old keys are kept in the ring for graceful migration but there's no expiry enforcement. A key that should be retired still verifies signatures indefinitely.

**Impact:** Once a secret is compromised and rotated out, the attacker retains indefinite access. There is no revocation mechanism.

**Fix:** Each secret carries `expires_at`. Even if the HMAC matches, reject if `time.time() > expires_at`. Log the expiry violation for audit.

### VULN-5 [HIGH] — Timing Side-Channel on Key Iteration

**What happens:** During fallback iteration over the secret ring, the code does:

```python
for cand in candidates:
    if hmac_check(cand, sig):
        matched = cand; break   # ← stops early if found
```

This means unknown keys finish faster than known keys, leaking information about which keys exist in the ring.

**Impact:** An attacker can enumerate active secret-key IDs by measuring response latency across thousands of requests. While this doesn't directly reveal the secret value, knowledge of which keys are active narrows the attack surface for other vectors.

**Fix:** Always iterate all keys and always call `hmac.compare_digest` for each one. Never `break` early — do constant work regardless of whether a match was found mid-ring.

### VULN-6 [HIGH] — Internal Errors Leaked to Caller

**What happens:** Payment-processing exceptions bubble up unhandled, or FastAPI's default exception handler serializes the traceback into the response body.

**Impact:** Stack traces, internal database paths, third-party API error messages, and transaction details become visible to the processor (and anyone intercepting traffic). This provides reconnaissance-grade intelligence for targeted attacks.

**Fix:** Catch all processing exceptions. Log full details server-side. Return a generic `"Internal processing error"` to the caller. Add a global exception handler as an outer safety net.

### VULN-7 [MEDIUM] — Sensitive Fields Logged in Plain Text

**What happens:** Full payloads are logged for debugging: customer emails, card tokens, account numbers.

**Impact:** Logs become an insecure data store for PII/PCI data. Compromised log aggregation exposes sensitive customer data, violating PCI-DSS and GDPR obligations.

**Fix:** Explicitly mask fields like `customer_email`, `card_number`, `cvv` before logging. Only log non-sensitive fields (`amount`, `currency`, `event_id`).

### VULN-8 [MEDIUM] — No Thread/Await Guard on Secret-Ring Mutations

**What happens:** Concurrent calls to `secret_ring.add()` during key rotation mutate the underlying list without synchronization.

**Impact:** Race conditions on list append/sort/pop can corrupt the ring, causing either missed keys (accepting invalid webhooks) or duplicated entries.

**Fix:** Use `asyncio.Lock` around mutations. Makes `add()` async and properly guarded.

### VULN-9 [MEDIUM] — `asyncio.get_event_loop()` Deprecation

**What happens:** Code calls `asyncio.get_event_loop()` instead of `asyncio.get_running_loop()`. The former warns on Python 3.10+ and raises `DeprecationWarning`; on event-loop-policy changes it can return the wrong loop.

**Impact:** Silent bugs where DB connections bind to the wrong event loop, causing intermittent crashes under load.

**Fix:** Always use `asyncio.get_running_loop()`.

### VULN-10 [LOW] — No Rate Limiting on Webhook Endpoint

**What happens:** No throttling on incoming POSTs.

**Impact:** A misconfigured or compromised processor could flood deliveries, consuming compute and DB resources. Not catastrophic alone, but removes an important defense-in-depth layer.

**Fix:** Integrate `slowapi` rate limiting with per-IP caps. Graceful degrade if the package is absent.

# Security Review: FastAPI Payment Webhook

## Vulnerabilities (Ordered by Severity)

### 1. HIGH — Signature Verified After Body Parsing
Checking HMAC *after* deserializing JSON means you process untrusted payload data before confirming authenticity. This opens two vectors:
- **CPU/memory DoS**: An attacker floods your server with gigabytes of bogus payloads per second, forcing expensive JSON parsing and validation for every one.
- **Type confusion / parser exploits**: Malformed bytes can crash Python's `json` module or trigger billion-laughs-style expansion in certain parsers.

**Fix:** Compute and verify the HMAC against the *raw request body bytes* *before* calling `await request.json()`. Reject early if the MAC doesn't match.

### 2. CRITICAL — In-Memory Replay-ID Dict
An in-memory `dict` used as the replay-event ledger has three fatal flaws:
- **Lost across worker processes** — with multiple uvicorn workers, Worker B never sees IDs stored by Worker A, so duplicate events slip through on one worker while another rejects them.
- **Lost on restart** — a deploy, crash, or OOM kill wipes the entire ledger, creating a replay window.
- **Unbounded memory growth** — the dict grows monotonically until eviction kicks in. No TTL, no cap, no cleanup.

**Fix:** Use a persistent table (`webhook_events`) with a periodic cleanup task. Accept either a DB-level UNIQUE constraint or SELECT…FOR UPDATE to enforce idempotency.

### 3. CRITICAL — No Idempotency Under Concurrency
If the same webhook fires twice simultaneously and both arrive before either finishes, two independent request handlers could both pass validation, check the ID (still not yet committed), and execute the payment handler twice. That's a double-payout.

**Fix:** Acquire a row lock on the event record *before* running the handler, ensuring only one coroutine proceeds past the INSERT/SELECT gate.

### 4. MEDIUM — Secret Rotation Has No Transition Period
If "rotating" means overwriting the active secret atomically, you'll reject legitimate post-broadcast deliveries from the processor, which may be delayed in transit.

**Fix:** Maintain a secrets list ordered by expiry, validate against the latest, but *verify* against all non-expired entries. Only promote new entries.

### 5. MEDIUM — Error Leaking
Processor errors or stack traces sent back in HTTP responses let an attacker fingerprint your internals and debug infrastructure.

**Fix:** Catch all exceptions, log internally, return `500 {"error": "Processing failed"}` with no details.

## Security Review: FastAPI Payment Webhook Endpoint

### Vulnerabilities Identified (by severity)

---

**VULN-1: Process-then-validate (HIGH)**

Verifying the HMAC *after* parsing the JSON body means every request — malicious or not — gets deserialized before authentication. Attackers can send massive payloads or deeply nested objects to exhaust CPU/memory on every request. This defeats the purpose of having a signature check: untrusted data must never be trusted until proven authentic.

**Fix: verify the signature first, then parse.**

---

**VULN-2: In-memory replay-ID storage with no concurrency guards (HIGH)**

An `in_memory_dict` has multiple failure modes:
- **Not durable**: process restart → all replay history lost → accepts replays after crash.
- **Race condition**: two identical webhooks arriving concurrently both see an empty dict, both pass. Race between `if id not in seen` and `seen.add(id)` lets duplicates through.
- **No eviction**: grows monotonically until OOM.

**Fix: use a database-backed set (PostgreSQL `events_processed` table) with a unique constraint for atomicity, plus a TTL index for cleanup.**

---

**VULN-3: Error messages leak processor internals to clients (MEDIUM)**

If payment processing fails, returning raw exceptions (stack traces, SQL fragments, internal service URLs) gives attackers reconnaissance material. Even generic "processing failed" can confirm valid payloads reached your system.

**Fix: return 200 on successful idempotent dedup, return a generic message on processing errors, log internally.**

---

**VULN-4: No request-size limit (MEDIUM)**

Without `Content-Length` checking, an attacker sends a 1GB body. The server still tries to buffer it before any auth check. Combined with VULN-1, this is an easy DoS.

**Fix: enforce a strict max content length (e.g., 64KB).**

---

**VULN-4: Secret-key versioning blind spot (MEDIUM)**

When rotating HMAC secrets, there must be a clear key-version in the signing header so the server can try each active version. Without a `key-id` field, you either support one-at-a-time rotation (downtime risk) or compare signatures sequentially (timing attack surface). Use constant-time comparison per key.

---

**VULN-6: Clock-skew not handled in timestamp validation (LOW)**

If the webhook includes a timestamp component, accepting arbitrary windows enables window-shopping attacks. Clamp to ±5 minutes.

---

**VULN-7: Missing Content-Type enforcement (LOW)**

Accepting `application/octet-stream` or other types alongside `application/json` opens up content-sniffing edge cases. Strictly require `Content-Type: application/json`.

def verify_hmac(payload_raw: bytes, headers: dict, expected_algo: str = "sha256") -> bool:
    """
    Verify the HMAC signature by checking ALL active secret versions.
    
    Signature is expected in X-Signature header, formatted as:
      v{version}-{hex-hmac}
    
    Uses hmac.compare_digest for constant-time comparison against each key.
    Returns False if no version matches.
    
    Also validates timestamp if present in X-Timestamp header.
    """
    sig_header = headers.get("X-Signature", "")
    ts_header = headers.get("X-Timestamp", "")

    # Parse key version from signature prefix
    if not sig_header.startswith("v") or "-" not in sig_header:
        return False
    
    parts = sig_header.split("-", 1)
    key_version = int(parts[0][1:])
    provided_mac = parts[1].lower()

    secret = SECRET_STORE.get(str(key_version))
    if secret is None:
        return False  # unknown key version

    expected_mac = hmac.new(
        secret, payload_raw, getattr(hashlib, expected_algo)
    ).hexdigest().lower()

    if not hmac.compare_digest(provided_mac, expected_mac):
        return False

    # VULN-6: Validate timestamp window
    if ts_header:
        try:
            msg_ts = datetime.fromisoformat(ts_header).replace(tzinfo=timezone.utc)
            now = datetime.now(timezone.utc)
            if abs(now - msg_ts) > timedelta(seconds=CLOCK_SKEW_SECONDS):
                return False
        except (ValueError, TypeError):
            return False

    return True

### Vulnerabilities Ranked by Severity

**Severity 1 — CRITICAL: Signature Verified After Body Parsing (ReDoS / Resource Exhaustion via Poison Requests)**

The code deserializes the entire JSON body *before* checking the HMAC. An attacker sends large or malformed payloads (e.g., deeply nested objects, extremely long strings triggering ReDoS in the JSON parser) and the server expends CPU/memory before discovering the signature is bad. This turns an auth guard into a DoS vector. Worse, the `json()` call can throw; if not caught properly, those exceptions may propagate differently than expected, creating inconsistent behavior paths.

Additionally, computing HMAC over `json.dumps(body)` is incorrect — the serialized form might not match the wire format (key ordering, whitespace, float precision). The HMAC should be computed over the **raw bytes** received.

**Severity 2 — CRITICAL: In-Memory Replay-ID Ledger (No Persistence / No Horizontal Scalability)**

`seen_events` is a plain Python `dict`. If the service restarts, all deduplication state vanishes — duplicate webhooks slip through during restart windows. It also doesn't work across multiple pods/processes. A malicious actor can exploit restart boundaries by sending a duplicate just after the service restarts.

**Severity 3 — HIGH: Rotating Secrets Without Version Identification**

There's no mechanism to identify *which* secret key was used for a given signature. When a secret rotates, old valid signatures become unverifiable without knowing which key to try. A proper system includes a key ID (`X-Key-ID`) header to select the right secret from rotation.

**Severity 4 — HIGH: Unhandled Exceptions Leak Internal State**

Raising `HTTPException(500, detail=str(e))` exposes stack traces, database connection strings, third-party API keys, or internal module paths to the external webhook caller. Even middleware that catches and re-raises can inadvertently include detailed traceback information.

**Severity 5 — MEDIUM: Missing Timing-Safe Event-ID Dedup Checks**

Using `event_id in dict` for set membership is O(1) hash lookup — fine for timing — but there's no expiration/retention policy on the dedup ledger. Memory grows unbounded forever.

**Severity 6 — MEDIUM: Clock Skew Not Handled**

HMAC-based webhooks typically include a timestamp. Without verifying a timestamp window (e.g., ±5 minutes), old captured/replayed requests stay valid indefinitely if they somehow bypass the event-id check.

**Severity 7 — LOW: Missing Content-Type Validation**

Without enforcing `Content-Type: application/json`, a confused-deputy attack could pass different content types that get parsed unexpectedly.

**Severity 8 — LOW: Race Condition in Idempotency (TOCTOU)**

Even with proper persistence, the pattern `if event_id in seen: return else: seen.add(); process` has a time-of-check-time-of-use (TOCTOU) race between the check and the insert. Two concurrent identical webhooks both see the event as new and both process it. The database operation must be atomic (INSERT ... ON CONFLICT SKIP / unique constraint + upsert).
