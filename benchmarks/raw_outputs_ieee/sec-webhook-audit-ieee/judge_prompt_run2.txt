## Vulnerabilities in Order of Severity

### 1. Signature Verification After Body Parsing (HIGH — Resource Exhaustion + Bypass)

Parsing the JSON body before verifying the HMAC signature is a resource exhaustion vulnerability. An attacker can flood the endpoint with multi-megabyte fake payloads, each of which gets fully deserialized by `json.loads()` or Pydantic before the signature check rejects it. Beyond DoS, there's a subtle bypass risk: some parsers have quirks where differently-encoded equivalent bodies produce different parsed results, and if an attacker controls the parser's behavior they may confuse server vs client interpretations.

**Fix**: Read the raw request body first (`await request.body()`), verify the HMAC against that exact byte sequence, then parse JSON from the verified bytes.

### 2. In-Memory Dict for Replay-ID Ledger (HIGH — State Loss + Memory Leak)

An in-memory dict has three fatal flaws:
- **Crash = replay window resets.** A process restart wipes all seen event IDs, so duplicate deliveries arrive after every deploy/restart.
- **No scaling.** Multi-worker deployments (Uvicorn gunicorn, multiple pods) each maintain their own dict; one worker may see an event while another doesn't, causing duplicate processing.
- **Unbounded growth.** No TTL, eviction, or size limit — the dict grows forever until OOM.

**Fix**: Store event IDs in PostgreSQL with a `UNIQUE` constraint and a `deleted_at` TTL (e.g., 24h). The uniqueness constraint guarantees idempotency across all workers and survives restarts.

### 3. Race Condition on Concurrent Duplicate Webhooks (MEDIUM — Double Processing)

Even with a replay ledger, the check-and-insert must be atomic. Two concurrent requests with the same `event-id` could both read "not found," both insert, and both process the payment twice. Standard ORMs don't protect you here without explicit locking.

**Fix**: Use `INSERT ... ON CONFLICT DO NOTHING` and only proceed if the insert was successful. As a belt-and-suspenders measure, wrap the operation in an advisory lock on the event ID hash.

### 4. Processor Error Leakage to Clients (MEDIUM — Information Disclosure)

If the downstream payment processor throws during idempotent re-processing, stack traces, SQL errors, or internal service names can end up in the HTTP response. This reveals infrastructure details to potential attackers.

**Fix**: Catch all exceptions during webhook processing, log internally, and return a generic `200 OK` (or `202 Accepted`) — webhooks are best-effort; the processor will retry. Never return 5xx for internal failures during idempotent re-delivery handling.

### 5. Rotating Secret Without Key Versioning (MEDIUM — Signature Verification Gap)

A "rotating secret" needs a clear key version identifier so old signatures signed with previous keys can still be validated during the rotation window. Without key versioning, a rotation causes a brief period where valid signatures fail verification. Conversely, accepting both old and new keys indefinitely defers the rotation.

**Fix**: Require the webhook header to include `x-secret-version` (or similar), and verify against the current key AND the immediately preceding key. Archive old keys with a hard expiration date.

### 6. Missing Content-Type Validation (LOW — Parser Confusion)

Not validating that the `Content-Type` is exactly `application/json` leaves room for MIME-type sniffing attacks or confusion between `application/json` and `text/plain`.
