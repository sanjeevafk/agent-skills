## Part 1: Characterization / Golden-Master Tests

### Strategy: Test-the-output, not the implementation

You don't have tests. Adding unit tests that mock internals requires extracting collaborators first — which is what we're trying to plan. So the ordering is:

1. **Record current observable behavior** (golden master)
2. **Build thin wrapper API** around existing class (no behavioral changes yet)
3. **Replace the wrapper with new implementations behind identical signatures**
4. **Verify outputs match golden master at every step**

### How to capture SQL side effects

The challenge is raw SQL scattered through methods. Two approaches:

**Approach A — Database-level query interceptor (preferred)**

If using a standard ORM or connection pool, intercept at the lowest level so you don't need to know where SQL lives in the code:

```python
class SqlSnapshotInterceptor:
    """Wraps a DB connection to record every query + params + result."""
    
    def __init__(self, connection):
        self.connection = connection
        self.queries = []
    
    def execute(self, sql, params=None):
        result = self.connection.execute(sql, params)
        self.queries.append({
            'sql': self._normalize_sql(sql),
            'params': params,
            'rowcount': result.rowcount,
            'description': result.description  # column metadata
        })
        return result
    
    def fetchall(self):
        data = self.connection.fetchall()
        return data
    
    @staticmethod
    def _normalize_sql(sql):
        """Collapse whitespace, remove timestamps/hints for stable diffs."""
        import re
        sql = re.sub(r'\s+', ' ', sql).strip()
        return sql
    
    def __enter__(self):
        return self
    
    def __exit__(self, *args):
        pass
```

Usage in a test:

```python
def test_order_creation_golden():
    input_order = make_test_input("order_create_happy_path")
    
    with SqlSnapshotInterceptor(original_db_connection) as sql_snap:
        with EmailSnapshotInterceptor(original_email_client) as email_snap:
```

**Approach B — Monkey-patch the raw SQL call**

If the SQL is via direct cursor.execute calls and there's no abstraction layer:

```python
import unittest.mock as mock

# In each test, monkey-patch the known function/class that executes SQL
with patch('src.db.cursor_execute', wraps=real_cursor_execute) as mock_exec:
    order_service.create_order(test_input)
    recorded_queries = [(call[0][0], call[0][1]) 
                       for call in mock_exec.call_args_list]
```

Approach A is better because it's transparent — you don't need to discover every SQL location in the code. Just wrap the connection once and everything gets recorded.

### How to capture email side effects

```python
class EmailSnapshotInterceptor:
    """Intercepts email sending without actually delivering."""
    
    def __init__(self, real_smtp_client):
        self.real_client = real_smtp_client
        self.emails = []
        self._original_send = None
    
    def start(self):
        # Patch wherever OrderService calls send
        self._original_send = self.real_client.send
        self.real_client.send = self._capture_send
        return self
    
    def _capture_send(self, recipient, subject, body, **kwargs):
        self.emails.append({
            'to': recipient,
            'subject': subject,
            'body': body,
            'headers': kwargs.get('headers', {}),
            'attachments': kwargs.get('attachments', [])
        })
        # Don't actually send — comment out next line to suppress
        # self.real_client._real_send(recipient, subject, body, **kwargs)
    
    def stop(self):
        if self._original_send:
            self.real_client.send = self._original_send
```

### DbStateSnapshot utility

```python
class DbStateSnapshot:
    """Capture full state of relevant tables before/after execution."""
    
    TABLES = ['orders', 'order_items', 'tax_entries', 'audit_log', 'pricing_rules']
    
    def __init__(self, connection):
        self.connection = connection
        self.before = {}
        self.after = {}
    
    def __enter__(self):
        for table in self.TABLES:
            self.before[table] = self._select_all(table)
        return self
    
    def capture(self):
        snapshot = {}
        for table in self.TABLES:
            snapshot[table] = self._select_all(table)
            diff = self._diff(self.before[table], snapshot[table])
            if diff:
                snapshot[f'{table}_changes'] = diff
        return snapshot
    
    @staticmethod
    def _select_all(table):
        rows = []
        cursor = self.connection.cursor()
        cursor.execute(f"SELECT * FROM {table} ORDER BY id")  # ordered for stability
        columns = [desc[0] for desc in cursor.description]
        for row in cursor.fetchall():
            rows.append(dict(zip(columns, row)))
        return rows
```

## Part 2: Seam Extraction Order

After golden master tests exist (proving baseline behavior), extract seams. The order matters because each seam should expose the minimum surface area while enabling the most internal decoupling.

### The Extractor's Dilemma

Three candidate seams to cut first:

1. **Persistence (SQL)** — Remove raw SQL from methods; replace with repository interface
2. **Email** — Extract notification collaborator
3. **Tax/Pricing engines** — Isolate calculation domain

### Decision: Cut Persistence FIRST

**Why:**

- Raw SQL is the most tightly coupled dependency. Every method reaches into SQL.
- Once SQL is abstracted behind a Repository interface, you can test pricing/tax/logic *without* a database — dramatically increasing test productivity.
- The repository pattern lets you swap the impl: first use the existing SQL-backed repo (zero behavior change), later replace it with ORM/migration.
- Email can wait — it's already isolated conceptually and doesn't block refactoring the core flow.
- Tax and pricing are *called* by methods — they become testable once persistence is extracted.

### Extraction Sequence Diagram

```
Phase 1 (Characterization) ──▶ Phase 2 (Seam Extraction) ──▶ Phase 3 (Domain Splitting)
       │                              │                               │
  Record golden data          Extract Repo interface          Extract Pricing/Tax modules
  Snapshot SQL/Email          Extract Notification iface      Replace monolith methods  
  Verify golden tests pass    Wrap existing SQL in repo       Split OrderService classes
       │                              │                               │
  ✓ All paths covered     ✓ Existing API unchanged        ✓ Old service delegates to new pieces
                                    │                               │
                             Phase 4 (Strangler)                 Phase 5 (Cutover)
                             Route new code behind           Delete OrderService,
                             old facade methods              migrate clients
```

### Key architectural decisions baked into the boundaries

1. **No cross-cutting dependencies** between `pricing/`, `tax/`, `notification/`, `auditing/` — they only depend on `models.py` and each other's protocols/interfaces.

2. **`persistence/` owns all SQL.** After Step 1, no SQL leaks outside this package.

3. **Models in a flat namespace.** Value objects (Money, Order, OrderItem) go in `models.py` — shared by all domain packages. This prevents circular imports.

4. **Repository protocols (interfaces) in the package root**, concrete SQL implementations in `persistence/sql/`. This means switching from SQL to ORM later only requires changing `persistence/sql/*`, not touching calling code.

5. **Event-driven audit trail eventually.** `AuditLogger.log()` produces domain events rather than direct inserts. Opens door to event sourcing later without refactoring the service.

## Part 5: Proving Behavior Preservation at Every Commit

### The invariant chain

Every commit MUST satisfy one or more of these checks:

```
Commit Pipeline:
──────────────────────────────────────────────────────────────
Step 1: Golden test subset runs                            [MANDATORY]
        │ Only tests relevant to changed public methods
        │ Checks: return value, SQL produced, email sent, DB state
        │ Pass? → continue. Fail? → commit rejected.
        ├───────────────────────────────────────────────────────
Step 2: Golden diff comparison                             [AUTOMATED]
        │ Before running, save current golden output as "pre-refactor snapshot"
        │ After running, compare post-refactor output to pre-refactor snapshot
        │ Assert: pre_snapshot == post_snapshot (deep equality on all fields)
        │ This catches behavior shifts that golden files might miss
        ├───────────────────────────────────────────────────────
Step 3: Contract test between old path and new path        [DURING TRANSITION]
        │ While both old and new code coexist:
        │ Execute SAME input through both paths
        │ Compare ALL outputs (return, SQL, email, DB delta)
        │ If paths diverge → immediate regression detected
        ├───────────────────────────────────────────────────────
Step 4: Static analysis gate                                [OPTIONAL BUT RECOMMENDED]
        │ Cyclomatic complexity per method: max 15
        │ File length: max 300 lines (after extraction)
        │ No raw SQL strings in non-persistence/ packages
        │ Import graph acyclical (dependency validator)
──────────────────────────────────────────────────────────────
```

### The rollback guarantee

If golden tests fail after a refactoring commit:

1. **Revert that single commit** — golden tests catch it immediately
2. **Check the diff** between old and new implementation — usually obvious where behavior diverged
3. **Add a failing golden test** for the edge case that broke — makes the fix intentional, not accidental

This is why golden master tests are phase 0. Without them, the rollback safety net doesn't exist.
