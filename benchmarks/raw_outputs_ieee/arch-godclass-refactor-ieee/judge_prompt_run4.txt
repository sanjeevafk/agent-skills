### Capturing SQL without modifying domain logic

**Option A (preferred): DB-layer hook.** Hook into whatever ORMs/connection pool you use:

```java
// Pseudocode — adapt to your ORM
public class SqlCaptureInterceptor implements ConnectionInterceptor {
    private final List<CapturedStatement> buffer = new ArrayList<>();

    @Override
    public void beforeExecute(Connection conn, PreparedStatement ps) {
        String sql = ps.toString();
        Object[] params = collectBoundParameters(ps); // driver-specific
        buffer.add(new CapturedStatement(sql, params));
    }

    @Override
    public void afterExecute(...) {}

    public List<CapturedStatement> drain() {
        return Collections.unmodifiableList(new ArrayList<>(buffer));
    }
}
```

Register this interceptor for the test transaction only (scoped to the thread/transaction). No code path in the production OrderService changes.

**Option B: Proxy the repository layer.** If your app uses a DAO/repository pattern:

```java
public class SqlCaptureRepositoryProxy implements OrderRepository {
    private final OrderRepository delegate;
    private final AtomicReference<List<String>> capturedSql = new AtomicReference<>(new ArrayList<>());

    @Override
    public void save(Order order) {
        capturedSql.get().add("INSERT INTO orders ...");
        delegate.save(order);
    }
    // ... proxy every method, appending SQL strings
}
```

Option A is better because it requires zero changes to the Service class itself. It's a wiring swap, not a code edit.

##### SQL Snapshot Strategy

Use a wrapper that records every executed statement with its parameters:

```python
class DevSqlExecutor(sql_executor_type):
    """Wraps the real executor used during tests, recording all SQL."""
    
    def __init__(self, real_executor: Executor):
        self._real = real_executor
        self.executed_statements: list[dict[str, Any]] = []
    
    def execute(self, sql: str, params=None):
        record = {"sql": normalize_sql(sql), "params": params}
        try:
            record["result"] = self._real.execute(sql, params)
            record["success"] = True
        except Exception as e:
            record["error"] = str(e)
            record["success"] = False
        self.executed_statements.append(record)
        if not record["success"]:
            raise
    
    def replay(self, sqlite_connection):
        """Replay statements against an empty SQLite db for diff-based verification."""
        for stmt in self.executed_statements:
            sqlite_connection.execute(stmt["sql"], stmt.get("params"))
```

`normalize_sql()` strips whitespace/line-endings and replaces literal values with `$1`, `$2` etc. so assertions compare structure, not data:

```python
def normalize_sql(sql: str) -> str:
    sql = re.sub(r"--.*$", "", sql, flags=re.MULTILINE)  # strip comments
    sql = re.sub(r"\b\d+\b", "?", sql)                    # replace literals
    sql = re.sub(r"\s+", " ", sql).strip()                # collapse whitespace
    return sql
```

### What gets characterized

SQL strings and SMTP calls are **not** the observable contract — they're implementation detail. The contract is: given this order payload, the customer sees this total; given this shipment address, they receive this confirmation email body. That's what the characterization test pins down.

### Snapshotting SQL side effects

Directly executing SQL in methods means queries leak into the request/response cycle. You cannot stub them without rewriting the methods first. Instead:

1. **Query-level observability hook**: Create a lightweight query logger that intercepts raw SQL strings at the lowest point where they're materialized (e.g., wrap the DB driver's `execute()` method or use an AOP interceptor). Log each query + parameters as JSON into a test-only buffer keyed by test ID.
2. **Extract the SQL traces**: After running the characterization test, snapshot the captured queries into a fixture file (`tests/fixtures/sql_traces/__init__.py`). These traces are *not* assertions — they're documentation of what the current system does. You revisit them only if behavior appears to change unexpectedly.
3. **Never assert on SQL content in tests**. SQL is brittle and changes with minor refactorings. Assert on domain outcomes only.

```python
# Pseudostructure of the SQL capture mechanism
class QueryCapture:
    _buffer = defaultdict(list)
    
    def capture(self, sql: str, params: tuple):
        self._buffer[thread_id()].append({"sql": sql, "params": params})
    
    def snapshot(self) -> list[dict]:
        return self._buffer.pop(thread_id(), [])
```

### Snapshotting email side effects

SMTP calls similarly shouldn't be asserted directly. Use a **TestTransport** that intercepts all `send_email()` calls:

@fixture

## Phase 2: Seam Extraction Order

The extraction order follows two principles:
1. **Highest blast radius first** — isolate the thing used everywhere so downstream changes become trivial
2. **Lowest risk first** — start with seams that require no logic changes, only wiring

### Extraction Order

#### Step 2.1: Repository Abstraction (highest leverage seam)

Rationale: With 34 fields and direct SQL scattered throughout methods, the repository seam touches *every* method. Extract it first because:
- It eliminates the most coupling (SQL strings embedded in business logic)
- Every subsequent refactor benefits from having clean entity boundaries
- Data access becomes mockable, enabling unit tests to isolate business rules

Pattern: **Repository pattern** with a simple interface:

**Risk assessment**: Low mechanical change (find-and-replace SQL statements with repository calls), but dangerous because mixing old and new patterns in the same class makes verification hard. Mitigation: migrate method-by-method, never leave a partially-migrated method.
