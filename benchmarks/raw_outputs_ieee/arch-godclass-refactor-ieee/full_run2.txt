## Refactoring Campaign: OrderService

### Current State

A 1,400-line God class managing **validation, pricing, tax calculation, persistence (direct SQL), email notifications, and audit logging** across **34 fields**. No tests. Direct SQL embedded throughout methods.

### Phase 1: Characterization Tests (Golden Master)

The goal here is to build a safety net that captures *everything* the class currently does — including side effects — so every subsequent commit has a verification hook.

#### 1.1 Snapshot SQL Side Effects

Direct SQL makes behavioral preservation tricky because you can't mock at the DB layer without first extracting the abstraction. Instead, snapshot against the actual database.

```python
# characterization/snapshot_sql.py
import json, hashlib
from contextlib import contextmanager

@contextmanager
def transaction_snapshot(db_conn):
    """Capture all state before and after, diff the result."""
    tables_to_audit = ["orders", "order_items", "payments", "audit_log"]
    snapshots_before = {}
    for table in tables_to_audit:
        # Hash each row deterministically: sort columns, serialize row tuple
        rows = db_conn.execute(f"SELECT * FROM {table} ORDER BY id")
        snapshots_before[table] = hash_rows(rows)
    yield snapshots_before
    # caller compares: assert snapshots_before == hash_after(db_conn)
```

Key insight: use **row-level hashing** rather than raw diffs. You want the test to fail only when business-logical data changes, not when auto-increment IDs shift. Sort by primary key, include all non-monotonic columns, produce a SHA256 per table.

For INSERT-only paths (e.g., `audit_log` appends), compare length plus content hash. For UPDATE/DELETE paths, also track deleted IDs.

#### 1.2 Snapshot Email Side Effects

Same pattern — intercept at the transport boundary before sending anything out.

```python
class EmailCaptureTransport:
    """Drop-in replacement that records instead of sending."""
    def __init__(self):
        self.sent_emails = []
    def send(self, to, subject, body):
        self.sent_emails.append({"to": to, "subject": subject, "body": body})

# Wrap the order creation, then assert email capture matches golden master:
email_snapshots = [json.dumps(e, sort_keys=True) for e in captured.sent_emails]
```

If the service uses SMTP directly, monkey-patch `smtplib.SMTP.send_message`. If it calls a third-party API, stub the HTTP client. The principle: capture at the last possible moment.

### Phase 2: Seam Extraction Order

Here's the dependency graph driving extraction priority. Each step extracts one concern behind an interface, introduces no behavior change, and keeps the public API intact.

**Extraction Order:**

| Step | Extract | Why First/Later |
|------|---------|-----------------|
| 1 | **Persistence (Repository)** | Removes the most structural coupling — direct SQL is everywhere. Once extracted, tests can use an in-memory fake without spinning up a real DB. |
| 2 | **Validation** | Pure function of input → list of errors. Easiest to extract and test independently. Can live as free functions initially. |
| 3 | **Pricing** | Also pure computation given inputs. Often depends on repository for product catalog lookups, which now exist as interface stubs from step 1. |
| 4 | **Tax Calculation** | Another pure computation. Similar treatment to pricing. May need configuration extracted later if tax rules vary. |
| 5 | **Audit Logging** | Write-only side effect. Straightforward interface (`IAuditLogger.log(event)`). Low risk to extract. |
| 6 | **Email Notification** | Most complex side-effect path (templating, transport config). Leave for last because it's coupled to domain events whose shape changes during other extractions. |

#### Detailed Steps:

**Step 1: Persistence → IOrderRepository**

Find all direct SQL calls. Group them into three patterns: `find_by_*`, `save_*`, `delete_*`. Extract an interface:

```python
class IOrderRepository(Protocol):
    def get(order_id: str) -> OrderDTO: ...
    def save(dto: OrderDTO) -> str: ...
    def find_by_customer(customer_id: str) -> list[OrderDTO]: ...
    # etc.
```

Replace inline SQL with repository method calls. Initially, `OrderRepository` still holds all the SQL logic — you're just moving it to its own class. No behavioral change.

After extracting, swap in `FakeOrderRepository` backed by `dict[str, OrderDTO]` for unit tests. Run characterization tests against both.

**Step 2: Validation → validate_order()**

Pull validation logic out of `create_order()` and `update_order()`:

```python
def validate_order(data: dict) -> list[str]:
    errors = []
    if not data.get("customer_id"): errors.append("missing customer_id")
    # ... rest of rules
    return errors
```

Tests for this are trivial — feed invalid dicts, assert error lists. Swap original validation calls in OrderService to delegate to this module. Behavior unchanged.

**Step 3 & 4: Pricing + Tax → iprice_calculator / ITaxCalculator**

Same pattern. Both are pure compute given an `OrderContext` (items, customer tier, region). Extract interfaces:

```python
class IPricingCalculator(Protocol):
    def calculate(ctx: OrderContext) -> Money: ...

class ITaxCalculator(Protocol):
    def calculate(region: str, items: list[Item]) -> Money: ...
```

Extract configuration separately if prices/tax rates come from env or DB — pull those into a `PricingConfig` / `TaxConfig` dataclass passed into the calculators.

**Step 5: Audit → IAuditLogger**

```python
class IAuditLogger(Protocol):
    def log(event: AuditEvent) -> None: ...
```

Simple. All SQL insert calls become `self.audit_logger.log(...)`.

**Step 6: Email → INotificationService**

This is the hardest because templates and transport configuration mix together:

```python
class INotificationService(Protocol):
    def notify_order_placed(order_id: str, customer_email: str) -> None: ...
    def notify_order_shipped(order_id: str, tracking_number: str, customer_email: str) -> None: ...
```

Behind the interface, keep the existing template rendering and SMTP logic. Just wrap it.

### Phase 3: Target Module Boundaries

After all seams are extracted, the code reorganizes into these modules:

```
order_service/
├── __init__.py          # Public API: OrderService (thin coordinator)
├── model/
│   ├── __init__.py      # Order, OrderItem, OrderStatus enums
│   └── value_objects/   # Money, Address (DDD-style)
├── validation/

│   ├── calculator.py    # IPricingCalculator impl
│   └── config.py        # PricingConfig
├── tax/
│   ├── calculator.py    # ITaxCalculator impl
│   └── config.py        # TaxConfig
├── persistence/
│   ├── repository.py    # IOrderRepository impl (SQL lives here now)
│   └── mappers.py       # Domain model ↔ DTO conversion
├── notification/
│   ├── notifier.py      # INotificationService impl
│   └── templates/       # Email templates
└── audit/
    └── logger.py        # IAuditLogger impl
```

The `OrderService.__init__` becomes constructor injection of all interfaces:

```python
class OrderService:
    def __init__(
        self,
        repo: IOrderRepository,
        validator: typing.Callable[[dict], list[str]],
        pricing: IPricingCalculator,
        tax: ITaxCalculator,
        audit: IAuditLogger,
        notifications: INotificationService,
    ):
        self._repo = repo
        self._validator = validator
        self._pricing = pricing
        self._tax = tax
        self._audit = audit
        self._notifications = notifications
```

| 10 | Remove deprecated aliases, clean up dead imports | Lint passes, all tests green |

**Behavior preservation proof at every commit:**

1. **Characterization test suite runs** — if any golden hash differs, the commit fails CI.
2. **Integration test runs against staging database** — queries match expected pre/post states for each scenario.
3. **Diff-based review** — every commit contains a comment block listing "side effects verified: X tables, Y email types."

The killer constraint is the characterization test. If you don't have that baseline, nothing in phases 2-4 is defensible. Start there. Ship phase 1 as a standalone commit, then proceed.

### Key Risk: Testing Without Existing Infrastructure

Since there are zero tests today, the characterization phase itself is work. Budget time for:
- Creating test database fixtures (Docker container or SQLite in-memory fallback)
- Building the email capture mechanism
- Curating realistic test inputs covering all branching paths in the 1,400 lines

Do not skip phase 1. A 34-field monolith without a characterization net will be fragile enough that even correct refactors break things silently.
