## Refactoring Campaign: 1,400-Line OrderService → Module Boundaries

### Phase 0: Baseline

Before touching a single line, capture what exists. Run `git stash` + `git status` baseline so you can diff every commit afterward. If the project already has CI, run it green once and note the passing state as "baseline commit."

### Phase 1: Characterization / Golden-Master Tests (3–5 shippable commits)

**Goal:** Cover the public API so that when each subsequent change lands, you have an oracle telling you if behavior regressed. You don't need unit-perfect tests — you need *executable specifications* of current behavior.

#### What to test first (in priority order):

1. **The main entry methods** — whatever the public surface area is (e.g., `placeOrder()`, `cancelOrder()`, `updatePrice()`). These are the only methods callers outside the class touch, so they're the cheapest regression net with the highest ROI.
2. **Validation-only paths** — inputs that get rejected today should keep getting rejected. A few bad-input calls against the same entry points catch regressions in guard logic.
3. **Pricing/tax edge cases** — the methods most likely to be subtly altered during extraction (rounding, currency conversion, tax exemption thresholds). Pick 3–5 inputs with known expected outputs from production data or sample orders.

#### How to characterize side effects without modifying production behavior:

**SQL side effects — snapshot approach:**

- Wrap every entry-point call in a real or integration transaction. Use an in-memory database (H2, SQLite, or PostgreSQL Docker container depending on the stack) seeded with production-equivalent fixtures.
- After calling `placeOrder(order)`, extract the resulting DB state into a golden struct: all rows in `orders`, `order_items`, `inventory_adjustments`, `audit_log` affected by that call. Serialize to JSON/YAML. Store as a test resource file (`tests/fixtures/golden/place_order_1.golden.json`).
- On the next run, re-execute the same call, query the same tables, compare golden vs actual. Any row count mismatch, field drift, or missing foreign key is a failure.
- For SQL *query* correctness (not just mutations), snapshot the result sets of any read queries the method performs before the mutation. Price lookups, tax rate resolution, inventory checks — those matter because refactoring can silently change which indexes are hit or which columns are selected.
- **Key insight:** Don't try to assert raw SQL strings. Assert the *resulting domain state*. That survives table renames, JOIN rewrites, ORM migrations.

**Email side effects — interceptor approach:**

- Do NOT send real emails during tests. Instead, intercept at the mail transport layer.
- If using Java/Spring: wrap the `JavaMailSender` in a test double that captures outgoing `MimeMessage`s into a thread-local list. Assert headers, recipients, subject templates, body placeholders.
- If using Node/NestJS: replace the email service with a spy via DI. Capture call args. Compare captured payloads against golden email templates (store the expected template + interpolated variables in a fixture).
- If there's no injection point: add a transient test hook — e.g., set an env var `EMAIL_LOG_DIR=/tmp/test-emails` that the production email code respects when present (or use an AOP/aspect in testing config). Even better: if the email sender is a constructor parameter (even if injected via framework), swap it in tests with zero code changes.
- **Golden email format:** `{to: string[], subject: string, bodyTemplate: string, interpolationVariables: {orderId: "...", total: "..."}}`. Assert equality of this struct, not rendered HTML.

**Fixture management pattern:**

```
tests/fixtures/
  golden/
    place_order_with_tax_exemption.golden.json
    cancel_partial_shipment.golden.json
    update_quantity_below_minimum.golden.json   # rejection case
    reorder_fully_cancelled.golden.json           # idempotency
  seeds/
    basic_order_scenario.sql                      # shared seed fixtures
    multi_item_inventory_scenario.sql
```

Each golden file contains: the input DTO, pre-condition DB seed hash, expected post-state, and expected email payload(s). Tests compare current output against these files and fail fast with a unified diff.

#### Commit hygiene per test addition:

Every characterization test commit contains ONLY tests and fixtures — zero production code changes. This proves the test suite itself is the baseline oracle before you start extracting seams.

### Phase 2: Seam Extraction — Target Module Boundaries

After the characterization suite passes, define where the monolith should fracture. Here are the natural module boundaries based on responsibility:

| Current Role | Proposed Module | Rationale |
|---|---|---|
| Validation rules (input sanitization, business-rule checks) | `OrderValidator` / `validation` package | Pure functions, no I/O. Can be extracted first because it has zero dependencies and no side effects. |
| Pricing calculation (line item math, discounts, promotions) | `PricingEngine` | Self-contained arithmetic. No persistence, no networking. Replaceable formula logic. |
| Tax computation (jurisdiction lookup, exemption handling) | `TaxCalculator` | Deterministic given jurisdiction + items. Domain-specific but isolated. |
| Email dispatch (notifications, confirmations) | `OrderNotifier` (interface-based) | I/O boundary. Needs a port/adapter shape from day one. |
| Audit logging | `AuditLogger` (interface-based) | Write-side effect. Simple append operation. |
| Persistence (SQL operations, transactions) | `OrderRepository` (interface + impl) | All direct SQL goes here. Once this interface is defined, the rest of OrderService becomes orchestrator. |

#### Seam extraction order — and why:

**Step 1: Extract `OrderValidator` (pure, no-risk)**

- Grep for validation logic (`throw new ValidationError`, `if (!valid)...`) scattered through OrderService methods.
- Pull each validation check into dedicated validator methods in a new class. Parameterize with input DTO, return structured error collection.
- Inject into OrderService via constructor (add a new ctor param, wire up in DI container / factory).
- **Why first:** Zero side effects. You can refactor validators test-by-test within the characterization suite. Every validation path stays covered; you're moving code out, not changing behavior.

**Step 2: Extract `PricingEngine` and `TaxCalculator` (deterministic, high-value)**

- These are the two heaviest computation domains in the class. They share no I/O — they operate on in-memory data.
- Create interfaces now (`IPricingEngine`, `ITaxCalculator`) even if the first implementation lives inside the old class. Pass OrderService's own results through them to prove equivalence via characterization tests.
- Swap in the extracted implementations method-by-method. Each pricing/tax call site becomes `pricingEngine.calculate(item)` instead of inline math.
- **Why second:** High complexity density, pure computation = high confidence refactor. Characterization tests validate every price/tax combination. This alone removes ~300 lines from OrderService.

**Step 3: Extract `OrderRepository` (the critical seam — persists everything)**

- This is the hardest and most important extraction. Every direct SQL statement gets pulled into repository methods.
- Define the interface first (`IOrderRepository`): `save(Order)`, `findById(id)`, `findOpenByCustomer(customerId)`, `persistAudit(AuditEntry)`, `adjustInventory(itemId, qty)`.
- Create a migration adapter: the new repository's first implementation wraps the existing SQL in methods. But here's the key — **define the interface before replacing any SQL calls**. Have OrderService call `repository.save(order)` instead of executing SQL directly. Then implement `save` with the existing SQL behind the interface.
- **Why third:** Repository is the I/O bottleneck. It touches both DB and often coordinates with other collaborators (inventory, audit). You need the validation and pricing layers already stable so you can trust the in-order data flowing into persistence. Also, repository extraction forces you to confront transaction boundaries explicitly — something buried in a 1,400-line class.

**Step 4: Extract `OrderNotifier` (email, notifications)**

- Interface: `INotifier.sendOrderConfirmation(Order)`, `.sendCancellationNotice(Order)`, etc.
- Production impl wires up to SMTP. Test impl captures sent messages (as characterized in Phase 1).
- **Why fourth:** Notifier depends on the order being fully formed (priced, taxed, validated, persisted). It's the last step in the orchestration chain, so it makes sense to extract last. Email template logic is messy and low-confidence — best to deal with after the core flow is clean.

**Step 5: Extract `AuditLogger` (append-only side channel)**

- Interface: `IAuditLogger.log(AuditEvent)`. Simplest collaborator — one method signature.
- **Why fifth:** Minimal complexity, purely additive. Doesn't affect order semantics. Safe cleanup pass.

#### Visual seam architecture:

```
                    ┌──────────────┐
                    │  OrderFacade │ ← new thin coordinator (replaces OrderService)
                    └──────┬───────┘
             ┌─────────────┼─────────────┬──────────────┬──────────┐
             ▼             ▼             ▼              ▼          ▼
        OrderValidator PricingEngine TaxCalculator  Notifier   Repository
                                    ^                 ^           ^
                              (pure math)     (SMTP adapter) (SQL adapter)
```

The old `OrderService` becomes `OrderFacade` — a 80-line orchestrator that composes the five collaborators and calls them in sequence. This facade IS the replacement for the existing public API. Zero caller changes.

### Phase 4: Behavior Preservation Strategy at Every Commit

**Every commit MUST include:**

1. **Characterization test coverage increment.** Each commit adds at least one new golden-master assertion. You never land a refactor commit without a new test proving what changed is equivalent to what existed.

2. **Diff review against golden state.** Before committing, dump current output state (DB rows, emails, audit logs) for the exercised scenarios and diff against the golden files stored in the repo. Automated in CI: `golden-compare --fixtures tests/fixtures/golden/ --output /tmp/current`. Fail on any non-empty diff.

3. **Code-level parity check.** For each extracted module, verify the new code produces identical outputs to the original. When migrating pricing, for example, run `assertEqual(originalPricingMath(input), newPricingEngine.calculate(input))` for a comprehensive input matrix. Same for tax rates applied to 50+ jurisdictions.

4. **No-new-dependencies rule.** Each extraction introduces exactly one new constructor dependency. The wiring change is mechanical (DI container registration) and reversible in one line.

5. **Zero-API-change contract.** The public method signatures of the service/facade never change until the final commit. Parameters, return types, exception types — all stay identical. Callers cannot tell the difference.

6. **Rollback safety.** Each step is independently revertible. If a commit breaks production, reverting it restores the old behavior without cascade failures (because the characterization suite on the previous commit proves nothing else was broken).

7. **CI gate:** `test-characterization && golden-compare && test-integration`. All three must pass. If the golden suite is red, the commit is held — no exceptions.
