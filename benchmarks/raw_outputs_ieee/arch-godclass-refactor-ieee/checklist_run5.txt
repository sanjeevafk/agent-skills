#### 1a. Snapshotting SQL Without Code Changes

**Option A — Database-level logging (zero app changes):**

```python
# PostgreSQL approach
def setup_sql_capture(session):
    session.execute("SET log_statement = 'all'")
    # Read pg_stat_statements or pgbouncer logs after execution
    sql_log = read_log_lines(last_5_seconds=True)
    normalize(sql_log)  # parameterize literals: ORDER BY created_at DESC
    return sql_log
```

**Option B — Connection-intercept proxy (small wiring change):**

Create a decorator around the raw connection object used by the service:

```python
class SqlCaptureConnection:
    """Wraps the existing DB connection; forwards everything, logs .execute() calls."""
    def __init__(self, delegate):
        self._delegate = delegate
        self.queries = []

    def execute(self, sql, params=None):
        self.queries.append({"sql": sql, "params": params})
        return self._delegate.execute(sql, params)

    # proxy every other method via __getattr__
    def __getattr__(self, name):
        return getattr(self._delegate, name)
```

Inject into the service through whichever DI mechanism exists (constructor injection point, singleton getter, or a thin factory wrapper). This is a **wiring-only change**, not business-logic modification.

## Phase 2 — Seam Extraction Order

Extract collaborators **first**, in dependency order so that the most coupled concerns get isolated earliest. Rationale: the more internal state a concern touches, the riskier to extract it. Get those out of the way while golden-master coverage protects you.

### Extract Order (by priority)

#### 1. Persistence / SQL Layer (highest priority)

**Why first:** Direct SQL is the single largest source of fragility. The service currently contains raw queries inline across multiple methods. Isolating persistence gives you a clear boundary where SQL can be replaced (ORM, DDD repository, CQRS) without touching validation/pricing logic. Every method that mutates state goes through this seam.

**Before:**

```python
class OrderService:
    def place_order(self, customer_id, items, shipping_addr):
        self.validate(...)
        pricing = self.compute_pricing(items)
        tax = self.db.execute(
            f"SELECT rate FROM tax_rates WHERE jurisdiction = '{jurisdiction}'"
        )
        total = pricing.total * (1 + tax)
        self.db.execute(
            f"INSERT INTO orders VALUES ({customer_id}, {total}, ...)"
        )
        self.mail.send(...)
        self.audit.log(...)
```

**After (seam extracted):**

```python
class OrderRepository:
    def save(self, order: Order) -> OrderId: ...
    def get_by_id(self, id: OrderId) -> Order: ...

class OrderService:
    def __init__(self, repo: OrderRepository, ...):
        self.repo = repo  # injected seam

    def place_order(self, customer_id, items, shipping_addr):
        self.validate(...)
        pricing = self.compute_pricing(items)
        total = pricing.apply_tax(jurisdiction)  # tax moved next
        order = Order(customer_id, items, total, shipping_addr)
        order_id = self.repo.save(order)
        ...
```

**Verification:** Golden-master compares SQL-capture output against baseline before merging. Any difference fails the commit.

#### 2. Tax Calculation Service

**Why second:** Tight coupling to SQL/jurisdiction lookup sits alongside persistence. Once the repository seam exists, tax becomes a pure function on pricing data — clean separation.

```python
class TaxService:
    def calculate_for(self, total, jurisdiction, items) -> Money: ...

# Usage in OrderService:
tax = self.tax_service.calculate_for(pricing.total, jurisdiction, line_items)
```

#### 3. Pricing / Discount Engine

**Why third:** Contains coupon logic, discount rules, promotions. Self-contained domain behavior that benefits from being a pluggable strategy rather than conditionals inside the service.

```python
class PricingEngine:
    def compute(self, items: list[LineItem]) -> PricingResult: ...
    def apply_coupon(self, code: str, result: PricingResult) -> PricingResult: ...
```

#### 4. Validation Service

**Why fourth:** Validation rules (stock checks, customer eligibility, order constraints) are pure domain predicates. Easiest to extract once surrounding seams are in place because it has no side effects.

```python
class OrderValidator:
    def validate_placement(self, order_context: OrderContext) -> ValidationResult: ...
```

#### 5. Notification / Email Service

**Why fifth:** Already loosely coupled conceptually. Just swap the concrete SMTP sender for an interface. After extracting this, you can add new channels (SMS, push) without touching OrderService.

```python
class NotificationService:
    def send_confirmation(self, order: Order, customer: Customer) -> None: ...
    def send_cancellation_notice(self, order: Order, customer: Customer) -> None: ...
```

#### 6. Audit Logging Service

**Why last:** Lowest-risk extraction. Mostly a fire-and-forget append operation. Can even keep it synchronous initially and move to async messaging later.

```python
class AuditLogger:
    def log(self, event: AuditEvent) -> None: ...
```

## Behavior Preservation Verification at Every Commit

Every incremental step follows the same discipline:

### Commit Checklist

1. **Golden-master regression passes** — All baseline fixtures rerun against modified code; comparison must be exact for outputs, prices, and error messages
2. **SQL equivalence check** — Parameterized SQL strings compared token-by-token; differences only in formatting/comments
3. **Mail parity** — Every email captured and diffed against baseline (header-by-header)
4. **Audit completeness** — Same count, same content, same ordering
5. **Performance gate** — Regression test ensures no >5% latency degradation (benchmark key endpoints before/after)

### Automated Guard Rails

Add to CI:

```yaml
# .github/workflows/refactor-guard.yml
jobs:
  characterize:
    runs-on: ubuntu-latest
    services:
      postgres: {image: postgres:15}
      smtp: {image: mailhog/mailhog}
    steps:
      - run: pip install -r requirements.txt
      - run: pytest tests/characterization/ --strict-golden-mastery
      # fails on any deviation from committed fixtures
```

### Manual Review Trigger

For each PR, require:
- Diff shows ONLY structural changes (extracted methods, new files, injected dependencies)
- No changes to visible return values, error messages, or HTTP status codes
- New files include their own golden-master test covering the extracted component

### Post-Deployment Safety Net

Deploy the refactored version to staging with feature flag toggles:
- If any metric diverges (error rate, price miscalculation), flip back to previous binary immediately — the public API contract guarantees zero rollback friction for callers.
