# Refactoring Campaign: OrderService (1,400-line God Class)

## Context Summary

A monolithic 1,400-line class with 34 fields handling validation, pricing, tax, persistence, email, and audit logging, with raw SQL scattered throughout. Zero tests. Behavior must never change.

---

## Phase 0: Characterization / Golden-Master Tests

**Goal:** Establish a safety net before touching production code. Prove 100% behavior preservation at every subsequent commit.

### 0.1 Map the Public API Surface

First thing I need to do is catalog every public/protected method — these form the unchanging contract. For a 34-field class, the surface area is finite.

```python
# Inventory script — run once, output becomes the test matrix
import ast, inspect
methods = [m for m in dir(OrderService) if not m.startswith('_')]
# Write to tests/characterization/order_service_api_surface.txt
```

Every one of those methods gets a characterization test. That's the commitment for Phase 0.

### 0.2 Snapshot Current SQL Side Effects

For every method that executes SQL, I need to capture what it actually does against a **stable, known dataset**. This means:

1. Create a seeded test database (SQLite preferred — same dialect patterns, no external dependency)
2. Before each test invocation, seed exactly N rows with known values
3. After the method runs, capture:
   - All executed SQL statements (via connection-level query log or interceptor)
   - The resulting row state post-execution (SELECT * on affected tables)

```
tests/characterization/sql_snapshots/
├── create_order.sql              # INSERT INTO orders ... + row snapshot
├── update_line_item_price.sql    # UPDATE line_items SET ... + row snapshot
├── calculate_tax.sql             # SELECT from tax_rates JOIN ... + result set
└── archive_order.sql             # INSERT INTO order_archive ... + row snapshot
```

Each `.sql` file contains the exact query, parameters, and expected post-state JSON. These are **golden masters** — generated once by running the current code and captured verbatim.

**How to intercept SQL without modifying OrderService:**
- Use an AOP-style aspect or wrapper around the connection object
- In Python: override `cursor.execute()` via monkey-patching the injected connection
- In Java/C#: use Hibernate proxy interceptor or EF Core execution interceptor
- Store every call as `(SQL, params) → result` tuples

### 0.3 Snapshot Email Side Effects

Email is typically fire-and-forget. To characterize it:

1. Inject a test mail sender that records messages instead of sending:
   ```python
   @contextmanager
   def capture_emails():
       original_sender = service.mailer
       captured = []
       service.mailer = TestMailer(captured)
       try: yield captured
       finally: service.mailer = original_sender
   ```
2. If there's no DI point for the mailer, wrap the SMTP/socket layer itself
3. For each public API method, invoke it under `capture_emails()` and record:
   ```json
   {
     "to": ["customer@example.com"],
     "subject": "Order Confirmation #ORD-12345",
     "template": "order_confirmation.html",
     "placeholders": {"order_number": "ORD-12345", "total": "$99.99"}
   }
   ```

## Phase 1: Seam Extraction Order

With the characterization suite green, I extract seams in the following order. Each seam exposes an interface that decouples one concern from OrderService, reducing its field count and responsibility chain.

### Seam 1: Persistence Layer (Highest leverage, lowest risk)

**Why first?** Direct SQL scattered through methods is the deepest tangle. Decoupling persistence early simplifies every subsequent step because test doubles for repository interfaces isolate the class from DB concerns entirely. It also immediately cuts down the field count (no need for raw connection/pool references in OrderService).

**Extract:** One interface per aggregate root:
```java
interface OrderRepository {
    Order findById(String orderId);
    void save(Order order);
    void delete(String orderId);
}

interface LineItemRepository {
    List<LineItem> findByOrderId(String orderId);
    void saveAll(List<LineItem> items);
}

interface TaxRateRepository { /* ... */ }
interface InventoryRepository { /* ... */ }
```

**Migration strategy:** Replace each `ORDER BY id LIMIT 1` direct query with `orderRepo.findById(id)`. Verify with characterization tests. Repeat method-by-method until all SQL is gone from OrderService.

**Result:** OrderService drops ~300–400 lines of SQL string literals and connection management. Field count drops by removing raw db connections, cursors, transaction handles.

### Seam 2: Pricing Calculator

**Why second?** Pricing is pure computation — no side effects, no I/O. Extracting it gives immediate confidence (deterministic outputs) and removes a major logic block from OrderService.

```java
interface PriceCalculator {
    Money computeSubtotal(List<LineItem> items);
    Money applyDiscount(PromoCode code, Money subtotal);
    Money computeShipping(Money subtotal, Address destination);
}
```

**Migration:** Extract the pricing method bodies into a standalone `PriceCalculator` class. Wrap OrderService's pricing calls in delegation. Verify characterization results match exactly.

### Seam 3: Tax Engine

**Why third?** Tax involves lookups (tax rates, nexus determination) plus computation. By now we have OrderRepository as a double available, making tax unit-testing straightforward.

```java
interface TaxEngine {
    Money calculateTax(Address billingAddress, List<LineItem> items, Money subtotal);
    NexusDetermination determineNexus(Address address);
}
```

### Seam 4: Notification/Messaging

**Why fourth?** Email is the most fragile side effect. Now that persistence and pricing/tax are isolated, the remaining email logic in OrderService is concentrated enough to extract cleanly.

```java
interface NotificationService {
    void sendOrderConfirmation(Order order, EmailRecipient recipient);
    void sendCancellationNotice(Order order);
    void sendInventoryLowAlert(String productId, int threshold);
}
```

Characterize existing email templates during this extraction — you may discover hardcoded HTML fragments that deserve template files.

### Seam 5: Audit Logger

**Why fifth?** Audit logging is the last cross-cutting concern. With other seams established, it's just a matter of extracting `AuditLogger.log(Event event)` calls into their own handler or, ideally, moving audit into an event-driven interceptor/AOP aspect.

```java
interface AuditLogger {
    void log(AuditEvent event);  // CREATE_ORDER, UPDATE_PRICE, CANCEL_ORDER
}
```

At this point OrderService should be down to ~300–400 lines focused purely on orchestration.

## Phase 2: Incremental Strangler Steps

Each step ships behind the existing public API. No client changes. The public API surface from Phase 0.1 never changes.

### Ship 1: Repository Interface Stubs (Backward Compatible)

Add the repository interfaces as private inner classes within OrderService, routing through the existing SQL. Then swap implementations method-by-method.

```java
// New, behind existing API — zero visibility breakage
public class OrderService {
    private OrderRepository orderRepo;  // replaces raw SQL strings
    
    // Constructor injection — existing callers unaffected
    @Autowired
    public OrderService(OrderRepository orderRepo, ...) {
        this.orderRepo = orderRepo;
    }
}
```

Each characterizable method is converted. Run `--goldens` after each conversion commit. Green → ship.

### Ship 2: Separate Concern Classes (No API Changes)

Once all SQL is routed through repositories, split the monolith into collaborating objects. Move each extracted class body into its own file:

```
src/orders/
├── OrderService.java          # Orchestration only (~250 lines)
├── PriceCalculator.java       # Pure functions (~120 lines)
├── TaxEngine.java             # Tax computation + rate lookup (~80 lines)
├── EmailNotifier.java         # Template rendering + delivery (~60 lines)
├── AuditLogger.java           # Event recording (~40 lines)
├── OrderValidator.java        # Validation rules extracted earlier (~70 lines)
└── model/
    ├── Order.java
    ├── LineItem.java
    └── OrderStatus.java       # Enums/constants separated out
```

The composition root wires them together. OrderService constructor now takes injected dependencies instead of managing internal state. The public API surface remains identical.

After each class file moves, run the full characterization suite. If it passes, the commit ships.

### Ship 3: Entity Model Cleanup (The 34 Fields)

Now refactor the internal state. Many of the 34 fields are likely transient, derived, or belong elsewhere.

Strategy:
1. Identify fields used in only one method → move to local variables or extract into a dedicated DTO/value object
2. Identify fields that represent a separate entity (e.g., `shippingAddress`, `billingAddress`) → promote to domain models
3. Identify computed/derived fields → replace with getter methods
4. Collapse status/state fields into a proper enum with behavior

```java
// Before: OrderService has these scattered fields
private String orderNumber;       // belongs to Order entity
private LocalDateTime createdAt;  // belongs to Order entity  
private BigDecimal subtotal;      // computed from lineItems
private BigDecimal discountAmount;// computed from appliedPromo
private String shippingMethod;    // belongs to ShippingPreference value object
// ... 30 more fields

// After: clean domain models
public class Order {
    private final String orderId;
    private final String orderNumber;
    private final List<LineItem> lineItems;
    private final Money subtotal;    // computed
    private final Money discount;    // computed
    // ... fields owned by the Order aggregate
}
```

Run characterization tests after each field group migration.

### Ship 4: Validation as Standalone Component

Extract validation rules that were embedded in business methods:

```java
class OrderValidator {
    ValidationResult validateCreation(OrderCreationRequest request);
    ValidationResult validateCancellation(Order order, User actor);
    ValidationResult validatePriceChange(Order order, BigDecimal newPrice);
}
```

Replace inline validation blocks in OrderService with `validator.validateX(...)`. This eliminates nested conditionals deep in the 1,400-line methods and makes rules independently maintainable.

### Ship 5: Event-Driven Audit (Final Polish)

Replace explicit `auditLogger.log(...)` calls sprinkled throughout OrderService with an event system. OrderService publishes events, the audit subsystem subscribes. This removes the last cross-cutting coupling.

```java
// Instead of:
orderRepo.save(order);
auditLogger.log(new AuditEvent(CANCEL_ORDER, order.getOrderId(), currentUser));

// Become:
eventPublisher.publish(new OrderCancelledEvent(order.getOrderId(), currentUser));
// Audit subscriber listens automatically
```

## Behavior Preservation Proof Strategy

At every commit, two checks must pass:

### 1. Golden Master Diff (`pytest --goldens`)

Compares golden files byte-for-byte:

```
commit abc123 | characterization-passed | sql-snapshots-match | email-captures-match
```

If ANY golden file differs, the commit fails CI. The diff output shows:
- Which query changed and why (if it's a deliberate rewrite, the golden file is updated with justification comment)
- Which email content diverged
- What DB row changed

### 2. Integration Test Smoke Suite

A minimal set of end-to-end scenarios that exercise the full public API surface:

```python
def test_create_order_flows_end_to_end():
    """Validates happy-path: creation → pricing → tax → persist → confirm email"""

def test_cancel_order_properly_audited():
    """Validates cancellation: state transition → archive → cancel email → audit entry"""

def test_invalid_promo_code_rejected():
    """Validates error path: promo validation failure returns correct error type"""
```

These complement characterization tests by checking semantic correctness rather than byte-for-byte identity.

### Commit Discipline

```bash
# Every commit follows this pattern:
git add . && git commit -m "refactor(persistence): route createOrder through OrderRepository

  - Removed 47 lines of raw SQL from createOrder()
  - Added in-memory OrderRepository stub (backward-compatible)
  - Golden master verification passed: sql-snapshots/createOrder_match

Co-authored-by: CommandCodeBot <noreply@commandcode.ai>"
```

Message format ensures:
- Scope tag identifies which seam/concern was touched
- Delta summary quantifies lines removed/adds
- Verification proof is cited inline
- Co-author trailer standardizes attribution

## Risk Mitigations

| Risk | Mitigation |
|------|-----------|
| Golden files drift due to non-determinism (timestamps, IDs) | Sanitize non-reproducible fields in golden serialization: replace UUIDs with deterministic keys, normalize timestamps to fixed values |
| Characterization misses a branch | Run coverage tool (`gcov`/`coverage.py`) against characterization suite; target ≥95% branch coverage on OrderService pre-refactor |
| SQL equivalence hard to prove across dialects | Keep SQLite seed data; run characterization against SQLite during dev, PostgreSQL during CI |
| Email template regression | Generate golden email files as HTML snapshots; diff renders visually in PR |
| Accidental behavior change in validation | Validation is the highest-risk seam; run characterization after each validation rule edit before proceeding |
