#### 0b. Record SQL Statements Per Call Path

Create a decorator that intercepts `execute()` / `cursor.execute()` calls and logs them with the calling method name:

```python
# characterization/sql_snapshotter.py
from unittest.mock import patch

def capture_sql(order_instance, method_name, *args):
    """Patch the DB layer, invoke one method, record every SQL executed."""
    executed_statements = []
    original_execute = order_instance.db.cursor().execute
    
    def recording_execute(sql, params=None):
        executed_statements.append((sql, params))
        return original_execute(sql, params)
    
    with patch.object(type(order_instance.db.cursor()), 'execute', recording_execute):
        result = getattr(order_instance, method_name)(*args)
    
    return result, executed_statements
```

For each public method, record `(method_name, args → results, sql_statements)`. Save as JSON snapshots:

```json
// golden/master/create_order.json
{
  "input": {"product_id": "abc", "qty": 2, "email": "test@x.com"},
  "result": {"order_id": "ORD-001", "total": 49.98},
  "sql": [
    ["INSERT INTO orders ...", ["abc", 2]],
    ["SELECT price FROM products WHERE id=? LIMIT 1", ["abc"]],
    ["UPDATE inventory SET qty=qty-? WHERE product_id=?", [2, "abc"]]
  ],
  "email_sent_to": "test@x.com",
  "email_subject": "Order ORD-001 Confirmed"
}
```

Do this for every public method — `create_order`, `update_quantity`, `apply_promo_code`, `cancel_order`, `get_order_summary`, etc. This gives you ~15–30 golden files depending on public API breadth.

### Phase 1 — Extract Collab Interfaces (No Behavior Change)

**Order of extraction matters.** Each step adds an interface without touching existing callers (except injection).

#### Seam 1: Repository Pattern for Persistence

**Why first:** Direct SQL is the most tightly coupled concern. Every method reaches into SQL. Isolating it gives the biggest immediate win for readability.

1. Define the interface that mirrors current persistence calls:

```python
# domain/orders/repo.py
class OrderRepository(Protocol):
    def save(self, order: Order) -> str: ...
    def get_by_id(self, order_id: str) -> Order | None: ...
    def update(self, order: Order) -> bool: ...
    def delete(self, order_id: str) -> bool: ...
    def list_for_customer(self, customer_id: str) -> list[Order]: ...
```

2. Implement an adapter over the existing SQL:

```python
# infrastructure/persistence/sql_order_repo.py
class SqlOrderRepository:
    def __init__(self, db_connection):
        self._db = db_connection
    
    def save(self, order):
        cursor = self._db.cursor()
        cursor.execute("INSERT INTO orders (customer_id, ...) VALUES (...)", [...])
        return cursor.lastrowid
```

3. Inject it into OrderService constructor (add a new parameter with `None` default → breakage-free):

```python
class OrderService:
    def __init__(self, db, smtp_server, tax_rate=0.1, repo=None):
        self._db = db
        self._smtp = smtp_server
        self._tax_rate = tax_rate
        self._repo = repo or SqlOrderRepository(db)  # backward compat
```

4. Replace scattered SQL statements in each method with `self._repo.save()` etc. Do this **one method at a time**, golden master passing after each swap.

### Behavior Preservation Proof at Every Commit

```
pre-commit hook or CI gate:
  1. checkout commit SHA
  2. run characterization/run_golden_master.py
     → loads each golden/*.json case
     → replays input through current OrderService
     → asserts result, SQL, emails match stored snapshots
  3. grep for patterns that should be gone:
     - direct .execute( in application/
     - string-literal "SELECT" or "INSERT" outside infrastructure/
  4. diff --stat against baseline branch
     → must show ONLY structural changes, not behavior differences
```

**Key invariant:** If golden master passes AND SQL is absent from non-infrastructure modules AND no new direct SQL appeared, behavior is preserved by construction. The snapshots capture output, side effects (SQL + email), so any deviation in computation, data mutation, or notification is caught.

**Edge case coverage:** Ensure golden cases include:
- Valid paths (happy path for every public method)
- Boundary conditions (empty cart, max quantity, zero-price item)
- Error paths (invalid product, insufficient stock, invalid email format, failed payment simulation)
- Tax edge cases (zero-tax jurisdiction, exempt customer)
- Promo code combos (overlapping discounts, expired codes)

Capture these as separate golden JSON files. They prove negative behaviors (errors thrown, rollback happened) are identical.
