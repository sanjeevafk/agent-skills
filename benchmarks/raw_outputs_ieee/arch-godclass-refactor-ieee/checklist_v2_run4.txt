# OrderService Refactoring Campaign

## Phase 1: Characterization Tests (Behavioral Baseline)

**Goal**: Prove you understand the observable behavior before touching a single line of implementation logic.

### What gets characterized

Every *public method* on OrderService needs one or more characterization test that captures input → observable output:

| Input Category | Observable Output |
|---|---|
| Order creation parameters | Return value, HTTP status code |
| Existing order + mutations | Updated entity state |
| Pricing scenarios | Final price breakdown sent back |
| Tax jurisdictions | Tax calculation result |
| Invalid input | Error type + message |
| Side-effect trigger (payment) | Email subject/body snippet + recipient |
| Audit-triggering event | Audit log entry structure |

SQL strings and SMTP calls are **not** the observable contract — they're implementation detail. The contract is: given this order payload, the customer sees this total; given this shipment address, they receive this confirmation email body. That's what the characterization test pins down.

### Snapshotting SQL side effects

Directly executing SQL in methods means queries leak into the request/response cycle. You cannot stub them without rewriting the methods first. Instead:

1. **Query-level observability hook**: Create a lightweight query logger that intercepts raw SQL strings at the lowest point where they're materialized (e.g., wrap the DB driver's `execute()` method or use an AOP interceptor). Log each query + parameters as JSON into a test-only buffer keyed by test ID.
2. **Extract the SQL traces**: After running the characterization test, snapshot the captured queries into a fixture file (`tests/fixtures/sql_traces/__init__.py`). These traces are *not* assertions — they're documentation of what the current system does. You revisit them only if behavior appears to change unexpectedly.
3. **Never assert on SQL content in tests**. SQL is brittle and changes with minor refactorings. Assert on domain outcomes only.

```python
# Pseudostructure of the SQL capture mechanism
class QueryCapture:
    _buffer = defaultdict(list)
    
    def capture(self, sql: str, params: tuple):
        self._buffer[thread_id()].append({"sql": sql, "params": params})
    
    def snapshot(self) -> list[dict]:
        return self._buffer.pop(thread_id(), [])
```

### Snapshotting email side effects

SMTP calls similarly shouldn't be asserted directly. Use a **TestTransport** that intercepts all `send_email()` calls:

```python
@fixture
def mail_capture(mocker, transport_registry):
    captured = []
    fake_transport = MockTransport(captured.append)
    transport_registry.register("smtp", fake_transport)
    yield captured
    assert len(captured) == expected_count, f"Expected {expected_count} emails, got {len(captured)}"
```

For each public method that sends email, verify:
- **Count**: How many emails were dispatched
- **Recipient address pattern** (not specific addresses — e.g., matches `{order_email}` template)
- **Subject line structure**
- **Body key variables** (order_id, total, shipping_address) — not byte-for-byte body comparison, which breaks on formatting changes

The TestTransport replaces the real SMTP socket entirely, so no network traffic occurs during tests.

### Building the characterization suite

Organize by public method, not by collaborator:

```
tests/integration/test_order_service_characterization/
├── test_create_order.py          # Inputs → returned Order DTO + emails + SQL traces
├── test_update_order.py          
├── test_cancel_order.py          
├── test_get_order_pricing.py     
├── test_apply_tax.py             
└── fixtures/
    ├── sql_traces/               # Captured queries per scenario
    └── email_snapshots/          # Key/val snapshots of email content
```

**Order of writing tests**: Start with the most frequently-called path (likely `create_order`). Run the existing code once under instrumentation, capture outputs, then write the characterization test from that snapshot. Once the test passes, the baseline is locked. Repeat for each public method.

**Completion criterion**: All 8-12 public entry points have ≥1 passing characterization test that runs against production code without mocks. This proves the baseline exists before any refactoring begins.

## Phase 2: Seam Extraction Order

The extraction order follows two principles:
1. **Highest blast radius first** — isolate the thing used everywhere so downstream changes become trivial
2. **Lowest risk first** — start with seams that require no logic changes, only wiring

### Extraction Order

#### Step 2.1: Repository Abstraction (highest leverage seam)

Rationale: With 34 fields and direct SQL scattered throughout methods, the repository seam touches *every* method. Extract it first because:
- It eliminates the most coupling (SQL strings embedded in business logic)
- Every subsequent refactor benefits from having clean entity boundaries
- Data access becomes mockable, enabling unit tests to isolate business rules

Pattern: **Repository pattern** with a simple interface:

```python
# Target interface (extracted)
class OrderRepository(Protocol):
    def get_by_id(self, order_id: UUID) -> OrderEntity: ...
    def save(self, entity: OrderEntity) -> None: ...
    def find_open_orders_by_customer(self, customer_id: UUID) -> list[OrderEntity]: ...
    # Only these — nothing else

class OrderEntity:
    """Plain data carrier. 34 fields, no behavior beyond getters/setters."""
```

Migration:
1. Add `__init__(self, repository: OrderRepository)` parameter
2. In *each* method, replace direct SQL with repository calls
3. Do one method at a time, verifying against characterization tests after each replacement
4. Keep the old SQL methods temporarily — rename to `_deprecated_*`, delegate to repository internally

**Risk assessment**: Low mechanical change (find-and-replace SQL statements with repository calls), but dangerous because mixing old and new patterns in the same class makes verification hard. Mitigation: migrate method-by-method, never leave a partially-migrated method.

#### Step 2.2: Pricing Strategy Interface

Once entities are cleanly separated from persistence, extract pricing as a strategy:

```python
class PricingStrategy(Protocol):
    def calculate(self, order: OrderEntity, items: list[LineItem]) -> PriceBreakdown: ...
```

Benefits:
- Pricing rules often vary by product category, region, or promotion tier
- Strategy swap is configuration-driven, not code-driven
- Each pricing variant gets its own focused class instead of conditional branches inside OrderService

Migration: inject `PricingStrategy` via constructor. Add a factory that reads config to select the active strategy. Backward-compatible: the default strategy replicates existing pricing logic verbatim.

#### Step 2.3: Tax Engine Interface

Parallel to pricing but simpler — tax calculation is usually a single function with jurisdiction lookup:

```python
class TaxEngine(Protocol):
    def compute_tax(self, jurisdiction: str, taxable_amount: Decimal, 
                    items: list[LineItem]) -> TaxDetail: ...
```

Migrate after pricing since tax depends on a correctly-priced subtotal. No dependency relationship between pricing and tax themselves, but ordering matters for reading comprehension of changes.

#### Step 2.4: Email Service Abstraction

Now that business logic separates from data access and calculations, the email concern stands alone:

```python
class EmailService(Protocol):
    def send_order_confirmation(self, order: OrderEntity) -> ConfirmationSent: ...
    def send_payment_receipt(self, order: OrderEntity) -> ReceiptSent: ...
    def send_cancellation_notice(self, order: OrderEntity) -> CancellationNoticed: ...
```

Why here? Because until entities are cleaned up (step 2.1), email templates reference messy ORM objects. With clean `OrderEntity`, templates become straightforward data mappings.

#### Step 2.5: Audit Logger Decoupling

```python
class AuditLogger(Protocol):
    def log(self, actor: str, action: str, entity_type: str, 
            entity_id: UUID, changes: dict[str, Any]) -> None: ...
```

Audit logging is typically fire-and-forget. Isolating it prevents audit failures from crashing order operations (add async dispatch or at-least-once retry later).

#### Step 2.6: Validation Framework Extraction

Validation lives closest to the public API surface. Extract it last among collaborators because:
- It's tightly coupled to input DTOs, which don't change during refactoring
- Moving it doesn't unlock other refactorings
- It's easiest to do once the service's core responsibilities are clear

```python
class OrderValidator:
    """Pure functions. No dependencies. Stateless."""
    @staticmethod
    def validate_creation(payload: OrderCreateRequest) -> ValidationResult: ...
    @staticmethod  
    def validate_transition(order: OrderEntity, transition: str) -> ValidationResult: ...
```

#### Step 2.7: Event Bus / Message Publisher (if applicable)

If the service publishes domain events (OrderCreated, OrderCancelled), abstract behind:

```python
class EventBus(Protocol):
    def publish(self, event: DomainEvent) -> None: ...
```

Add this seam before strangler phase because published events become part of the observable contract characterizations must capture.

#### Why this order isn't parallelizable

Each step produces a cleaner intermediate class that the next step operates on. Running them in parallel creates merge conflicts and inconsistent intermediate states. Sequential migration ensures each commit leaves the codebase in a working, tested state.

## Phase 3: Incremental Strangler Pattern

The strangler pattern gradually shifts responsibility from OrderService to new modules while keeping the public API stable. Feature toggles gate the switch-over, allowing rollback at any point.

### Architecture of the strangler

```
                    ┌─────────────────────┐
   Request →        │   OrderFacade       │  ← Public API stays identical
   Public API        └────────┬────────────┘
          │                   │
    ┌─────▼─────┐      ┌─────▼─────┐
    │ Legacy    │      │ New       │
    │ OrderSvc  │      │ Orchestrate│
    │ (shrinks) │      │ r classes │
    └───────────┘      └───────────┘
         ▲                    ▲
         │                    │
    Feature toggle           Feature toggle
```

The facade delegates each method call to either the legacy service or the new orchestration chain based on a toggle. Toggles default to `false` (legacy path) — flip to `true` per-method as confidence builds.

### Strangler Steps (each shippable)

#### Strangler Step S1: Wiring foundation

**What ships**: DI container updated to inject collaborator interfaces (repositories, strategies, services) into OrderService. Nothing functional changes. OrderService is now constructed differently but behaves identically.

**Verification**: All characterization tests pass against unmodified behavior. The only difference is how the object graph is assembled.

**Toggle**: None needed — this is pure wiring.

#### Strangler Step S2: Repository seam complete

**What ships**: All SQL replaced with repository calls. OrderService still has 1,400 lines but zero SQL strings. Entities are plain data carriers.

**Verification**: Same characterization tests pass. Additionally, run the application with a **test database mirror** for one hour of live traffic shadow-mode (optional, high-confidence boost).

**Toggle**: None — data access is internal.

#### Strangler Step S3: `create_order` method strangled

**What ships**: 
- New `OrderCreationOrchestrator` handles the creation flow using injected collaborators
- `OrderService.create_order()` delegates to orchestrator when toggle is enabled
- Toggle defaults to `false`

**New module created**: `domain/order_creation/` containing:
- `OrderCreator` (aggregate root, enforces invariant: order transitions valid only)
- `CreationCommandHandler` (orchestrates validators → pricing → tax → persistence → email → audit)
- `OrderCreatedDomainEvent`

**Verification**: 
- Toggle OFF: all existing characterization tests pass (no behavior change)
- Toggle ON: feed the same test inputs through both paths simultaneously, diff outputs, assert equality
- After N hours with toggle ON for internal users showing no diff, enable for external traffic

**Commit message format**: `refactor: move create_order to OrderCreationOrchestrator [toggle:false]`

#### Strangler Step S4: `update_order` + `cancel_order` strangled

**What ships**: 
- `OrderLifecycleManager` handles state transitions
- Same toggle pattern per method

**New module**: `domain/order_lifecycle/` containing state machine logic.

**Verification**: State transition matrix exhaustively tested. Each transition has a characterization test proving old → new equivalence.

#### Strangler Step S5: `get_order_pricing` strangled

**What ships**: Pricing calculation moves to `PricingCalculator` with configurable `PricingStrategy`.

**New module**: `domain/pricing/` containing strategies and calculator.

**Verification**: Price math comparison — new output equals old output to the cent for all captured tax/jurisdiction combos.

#### Strangler Step S6: Remaining read/query methods strangled

**What ships**: `OrderQueryService` handles all retrieval/read operations separately from command/write operations. This is the CQR split.

**New module**: `infrastructure/query/` containing read-model projections.

**Verification**: Result set comparison against original queries.

#### Strangler Step S7: Legacy OrderService deletion

**What ships**: After all toggles have been ON for sufficient observation period (recommend 2 weeks minimum in production), delete the legacy OrderService class entirely. Update the facade to route everything to new handlers. Remove feature flag framework.

**Final state**: OrderService is gone. Domain classes are small (<200 lines each), focused, fully tested.

## Behavior Preservation Proof Strategy

At **every commit**, behavior preservation is proven by one or more of these gates:

### Gate 1: Characterization test suite (passes/fails — binary check)

Every commit must have all characterization tests passing. This is the non-negotiable baseline. CI runs this suite on every PR and every push.

### Gate 2: Dual-path execution (toggle ON)

When a method has been strangulated (toggle ON), run the same inputs through both legacy and new codepaths simultaneously:

```python
# Inside the strangler facade when toggle is ON
def create_order(self, payload: OrderCreatePayload) -> OrderDTO:
    legacy_result = self._legacy_service.create_order(payload)
    new_result = self._new_orchestrator.create_order(payload)
    
    diff = self._comparator.diff(legacy_result, new_result)
    assert diff.is_empty(), f"Behavior drift detected:\n{diff}"
    
    return legacy_result  # Return legacy for now (same data)
```

This catches silent behavior drift that characterization tests might miss (edge cases not covered by test inputs).

### Gate 3: Golden master comparison for emails

Email outputs from the new path are compared against previously-captured email snapshots. Structural equality on key variables, not exact string matching.

### Gate 4: Integration smoke test against live traffic shadow

For high-value paths, redirect incoming production requests to both old and new implementations and log divergences. This catches edge cases that unit/integration tests miss. Requires:
- Read-only copy of production DB
- Rate-limited replay (start at 1% of traffic)
- Automatic alerting on mismatch

### Gate 5: SQL query equivalence (informational only)

After each migration step, compare the SQL generated by repository implementations against the original SQL strings in the legacy code. Not an assertion — documentation. If the queries differ structurally but produce identical results, that's fine (index-friendly rewrites are desirable). This check exists only to catch accidental logic changes in WHERE clauses or JOIN conditions.

## Risk Register & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Characterization tests miss an edge case | High | Medium | Shadow-mode dual-path execution catches misses |
| Repository abstraction loses a join condition | Medium | High | SQL comparison + integration tests against production dataset |
| Toggle complexity becomes unmanageable | Medium | Medium | Delete toggle branches immediately after verification, never accumulate |
| New orchestrator introduces new bugs | Certain | Medium | Each handler starts as a thin delegation to legacy + adds new logic incrementally |
| Entity design doesn't fit all use cases | Low-High | High | Design entities collaboratively with team, review before extracting repository |
