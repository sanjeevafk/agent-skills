## Refactoring Campaign: Splitting a God Class Behind Its Own Public API

### Phase 0 — Baseline Understanding & Characterization Tests

Before changing a single line of production code, you need behavioral guarantees. The goal is to turn the class's current observable behavior into an executable spec.

#### 0a — Inventory the Public Surface

Extract every public method signature along with representative input/output pairs. For each method, collect at least 3 call variants (happy path, boundary conditions, error paths). Example inventory:

```python
class OrderService:
    def create_order(self, items: List[OrderItem], customer_id: str, promo_code: str | None) -> OrderDTO
    def calculate_total(self, order: Order) -> Decimal
    def apply_tax(self, order: Order, jurisdiction: str) -> Decimal
    def finalize_order(self, order_id: UUID) -> OrderStatus
    def cancel_order(self, order_id: UUID, reason: str) -> bool
    # ... plus any other public methods
```

Build a matrix: rows = methods, columns = inputs → expected outputs. Fill it by tracing real production data (sanitized) or synthetic-but-realistic fixtures.

#### 0b — Golden-Master Test Harness

Write a thin test driver that calls every public method with each fixture set and captures all observable side effects. The harness serializes results into deterministic JSON fixtures stored under `tests/fixtures/golden/`.

**Key principle:** You are not asserting domain rules yet. You are recording *what happens now*. If the current code applies a 8.75% flat tax regardless of jurisdiction, the golden master records that exact behavior — even if it should be parameterized later.

```python
# Structure of a characterization test
@pytest.mark.parametrize("fixture", load_golden_fixture_sets())
def test_create_order_matches_golden(fixture):
    service = make_service_with_all_deps_real()
    
    result = service.create_order(
        items=fixture["items"],
        customer_id=fixture["customer_id"],
        promo_code=fixture.get("promo_code")
    )
    
    # Capture: returned DTO, written SQL params, emails sent, audit entries
    captured = capture_all_side_effects(result)
    assert snapshots_equal(captured, fixture["golden"])
```

**`snapshots_equal`** does structural comparison — key ordering must be enforced via deterministic serialization (`sort_keys=True`, stable iteration over dicts).

#### 0c — Snapshotting SQL Side Effects

Direct SQL is scattered through methods. To capture it characteristically:

**Approach 1 — Query log interceptor** (non-invasive, works today with zero changes):

```python
class SQLCaptureLogger(logging.Handler):
    """Intercepts raw SQL emitted by the ORM/connection pool."""
    executed_queries: list[dict] = []
    
    def emit(self, record):
        self.executed_queries.append({
            "sql": record.msg,
            "params": record.args if hasattr(record, 'args') else (),
            "timestamp": datetime.utcnow().isoformat()
        })
```

Attach to the connection's logger before each test run:

```python
@pytest.fixture(autouse=True)
def capture_sql():
    handler = SQLCaptureLogger()
    logging.getLogger("sqlalchemy.engine").addHandler(handler)
    logging.getLogger("sqlalchemy.engine").setLevel(logging.DEBUG)
    yield handler.executed_queries[:]
    handler.executed_queries.clear()
```

Include the ordered query list in the golden snapshot alongside the method return value.

**Approach 2 — Mock the underlying DBAPI cursor.** If direct raw `cursor.execute()` calls exist, wrap the connection factory in a test-time proxy that logs every call. This catches queries that bypass the ORM logging layer.

#### 0d — Snapshotting Email Side Effects

Same pattern — intercept the SMTP/send call before it leaves the process:

```python
class EmailCaptureBackend(BaseEmailBackend):
    sent_messages: list[dict] = []
    
    def send_messages(self, messages):
        for msg in messages:
            self.sent_messages.append({
                "to": msg.to,
                "subject": msg.subject,
                "body_trunc": str(msg.body)[:200],  # truncate long bodies
                "template_used": getattr(msg, "_template_name", "<unknown>")
            })
        return len(messages)  # still actually sends unless you also mock SMTP
```

In tests, swap this backend into Django/email config. If using a custom mailer, inject a stub transport that captures instead of connecting.

Both captures go into the same golden fixture per test case. A fixture for `create_order_with_promo` might look like:

```json
{
  "input": { "items": [...], "customer_id": "cust_42", "promo_code": "SAVE10" },
  "golden": {
    "return_dto": { "order_id": "...", "total": "99.50", "status": "created" },
    "queries": [
      {"sql": "INSERT INTO orders (...) VALUES (...)", "params": [...]},
      {"sql": "UPDATE inventory SET qty = qty - ? WHERE sku = ?", "params": [...]}
    ],
    "emails_sent": [
      {"to": ["customer@example.com"], "subject": "Order Confirmed", "template_used": "order_confirmation"}
    ],
    "audit_entries": [
      {"action": "ORDER_CREATED", "actor": "system", "details": {...}}
    ]
  }
}
```

Run these golden tests **before any refactoring** to establish baseline — they should all pass against the current code. Commit them. They are your safety net.

### Phase 1 — Define Target Module Boundaries

The 34 fields and mixed concerns map cleanly to six bounded modules:

```
OrderService (current)
│
├── ValidationModule          # Input validation, business rule checks
├── PricingModule             # Line-item pricing, discounts, promos
├── TaxModule                 # Jurisdiction-based tax computation
├── PersistenceModule         # All DB access, CRUD, transactions
├── NotificationModule        # Email dispatch, templates, retries
└── AuditModule               # Audit logging, event publishing

Cross-cutting (remain in Service shell initially):
├── orchestration              # Method-call sequencing
└── transaction_coordination   # Unit-of-work / session mgmt
```

Each module has exactly one public interface. The OrderService becomes an orchestrator that delegates to collaborator interfaces.

#### Module Contracts (target state)

| Module | Public Interface | Single Responsibility |
|--------|-----------------|----------------------|
| `ValidationModule` | `validate(order_input: RawOrderInput) → ValidatedOrder` | Validate inputs, reject invalid requests early |
| `PricingModule` | `compute_line_items(items: PricedItems[]) → ComputedLines[]` | Unit prices, quantities, promotional discount math |
| `TaxModule` | `compute_tax(lines: ComputedLines[], jurisdiction: string) → TaxLine[]` | Rate lookup, rounding, jurisdiction logic |
| `PersistenceModule` | `save_order(dto: OrderDTO) → SavedOrder` + `find_by_id(UUID) → OrderDTO?` | All SQL, mapping, transactions |
| `NotificationModule` | `send_confirmation(customer_id, order) → void` + batch ops | Template resolution, SMTP/dequeue dispatch |
| `AuditModule` | `log(event: AuditEvent) → void` | Write audit records, publish domain events |

Note: The original 34 fields collapse. Each module owns its own private state. The service shell holds no field beyond constructor-injected collaborators.

### Phase 2 — Seam Extraction Order

The critical question: which collaborator to extract first? This determines whether each step reduces risk or amplifies it.

#### Guiding Principle: Extract the highest-coupling, lowest-risk-to-isolate concern first.

**Start with `PersistenceModule`.** Here is why:

1. **Highest blast radius of coupling:** SQL is scattered across multiple methods. The more methods that touch the DB directly, the more entangled the object graph. Isolating this first creates clear seams on the most shared resource.
2. **Cleanest separation of concerns:** Database access is a cross-cutting orthogonal concern — it has nothing to do with pricing math or validation rules. The interface is naturally decidable.
3. **Enables future testing gains:** Once persistence is interfaced, unit tests can exercise pricing and validation with in-memory or mock stores, dramatically improving testability even before full test coverage exists.
4. **Low behavioral risk during extraction:** The current methods already have a natural boundary where they transition from computation to mutation. You cut at that boundary. No behavioral change — just routing the SQL through a collaborator.

**Second: `AuditModule`.** Why:

- Audit calls are additive side effects, never branch-point decisions. Removing them from business logic methods is trivially safe.
- Audit logging has no impact on the core computation chain (it doesn't affect returns, control flow, or downstream collaborators).
- Doing this next is a low-effort cleanup that builds confidence.

**Third: `NotificationModule` (Email).** Why:

- Like audit, email dispatch is an additive side effect.
- But it introduces non-determinism (SMTP failures, retries, template rendering). Separating it next lets you address reliability concerns in isolation.
- Email templates often leak into the service as string interpolation. Moving them into a dedicated module gives you a place to centralize template resolution.

**Fourth: `PricingModule` and `TaxModule`.** Why:

- These contain the actual domain-computation complexity — decimal math, promotion logic, rate tables. They benefit most from having characterized tests around them (the golden masters already cover the combined output, but now you'll get fine-grained assertions).
- Extract these together because pricing feeds directly into tax computation — they form a dependency chain (pricing → subtotal → tax → total). Extract both in a single refactor window to avoid breaking the chain mid-stream.

**Fifth: `ValidationModule`.** Why:

- Validation logic is woven throughout many methods as guards. It is the last to extract because removing guard clauses from existing code touches the most methods simultaneously.
- By the time you get here, the other collaborators are clean interfaces, so validation extraction is purely about moving conditional checks — the hard part (proving nothing broke) was solved in earlier phases.

**Summary of extraction order with rationale:**

```
1. PersistenceModule    ← Highest coupling, cleanest seam, enables testability gains
2. AuditModule          ← Additive side effect, zero control-flow impact
3. NotificationModule   ← Additive side effect, addresses reliability next
4. PricingModule        ← Domain computation, depends on being above it
5. TaxModule            ← Depends on PricingModule; extract together
6. ValidationModule     ← Scattered guards, done last when rest is stable
```

### Phase 3 — Incremental Strangler Steps

Each step shippable on its own, each exposing no new public API surface. The service's existing public methods keep their signatures; internally they delegate to extracted collaborators.

#### Step 1: Introduce the Persistence Repository Interface

**What changes:** Create `OrderRepository` interface and a concrete adapter wrapping the current inline SQL. Refactor each method so its SQL calls go through the repository instead of the service.

```python
# NEW interface (exists first, implemented second)
class OrderRepository:
    def save(order: OrderDTO) -> UUID
    def find_by_id(id: UUID) -> OrderDTO | None
    def update_status(id: UUID, status: OrderStatus) -> bool
    def decrement_inventory(sku: str, quantity: int) -> bool

# Adapter implementation wraps current inline SQL — drop-in replacement
class LegacySQLOrderRepository(OrderRepository):
    def __init__(self, raw_connection):
        self._conn = raw_connection
    
    def save(self, order: OrderDTO) -> UUID:
        cur = self._conn.cursor()
        cur.execute("INSERT INTO orders ...", ...)  # current inline SQL
        cur.execute("INSERT INTO order_items ...", ...)  # current inline SQL
        return order.order_id
```

**Characterization check before committing:** Run golden tests. The repository adapter reproduces identical SQL, identical returns, identical side effects. Green → commit.

**Public API impact:** Zero change. Existing callers still call `service.create_order(...)`. Internally, the service now calls `self.repository.save(order)`.

#### Step 2: Inject Dependency (Constructor Injection Pattern)

**What changes:** Add `OrderRepository` as a constructor parameter. Use a default argument or factory to maintain compatibility if needed (though ideally, wiring happens at application entry point).

```python
class OrderService:
    def __init__(self, repository: OrderRepository, ...) -> None:
        self.repository = repository
        # other fields...
```

This is still pure extraction — no behavior change. The golden tests must pass.

#### Step 3: Extract Audit Logging

**What changes:** Create `AuditService` (or `AuditModule` collaborator). Move all audit `execute("INSERT INTO audit_log ...")` calls out of service methods and into `audit.log(AuditEvent(...))`.

```python
class AuditService:
    def log(self, event: AuditEvent) -> None:
        self.repo.insert("audit_log", {...})  # possibly another repository internally
```

Then wire it into `OrderService`:

```python
class OrderService:
    def __init__(
        self, 
        repository: OrderRepository,
        audit: AuditService,    # NEW
        ...
    ): ...
    
    def create_order(self, ...):
        validated = self.validate(input)
        # ... compute pricing ...
        self.audit.log(AuditEvent(action="ORDER_CREATED", details={...}))  # moved here
```

**Golden test check:** The audit entries in the snapshot must match exactly — same events, same timing-order (if order matters for downstream consumers). If audit writing has no downstream read-path dependency, reordering within a method is fine; otherwise preserve call-site semantics.

#### Step 4: Extract Email Dispatch

**What changes:** Similar extraction — create `NotificationService` interface, move email-sending code out of service methods.

```python
class NotificationService:
    def send_order_confirmation(customer_id: str, order: OrderDTO) -> None
    def send_cancellation_notice(customer_id: str, order: OrderDTO, reason: str) -> None
```

Move each `send_email(...)` or `_render_template_and_send(...)` call.

#### Step 5: Extract Pricing Calculation

**What changes:** This is the first computational extraction. Move the price-math lines into `PricingService`.

```python
class PricingService:
    def compute_lines(items: RawOrderInput.items) → ComputedLine[]
    def apply_promotion(computed: ComputedLine[], promo_code: str | None) → ComputedLine[]
    def subtotal(lines: ComputedLine[]) → Decimal
```

This is higher-risk because decimal arithmetic must match byte-for-byte. The golden master covers the combined pricing+tax output, but you should add targeted unit tests for pricing edge cases once it's isolated — e.g., floating-point accumulation across N items, rounding at different precision levels, negative amounts from large discounts.

#### Step 6: Extract Tax Calculation

**What changes:** `TaxService` receives pre-priced lines and computes tax lines.

```python
class TaxService:
    def compute_tax(lines: ComputedLine[], jurisdiction: str) → TaxCalculation
```

This follows immediately after pricing because the interface contract between them (subtotal feeds into tax base) needs to be verified in a single change set.

#### Step 7: Extract Validation

**What changes:** Pull guard clauses and validation logic into `ValidationService`.

```python
class ValidationService:
    def validate_order_input(raw: RawOrderInput) → ValidatedOrder | ValidationError
    def validate_cancel(reason: str, status: OrderStatus) → ValidationResult
```

At this point the service should be mostly an orchestrator. Remove remaining inline helper methods that became redundant.

#### Step 8: Field Cleanup

**What changes:** The original 34 fields were shared across all responsibilities. Now delete the fields that belong exclusively to extracted modules. Keep only:
- Constructor-injected collaborators
- Any genuinely transient orchestration state (session IDs, request-scoped context)

Verify golden tests still pass. Fields deleted ≠ behavior changed (the extracted modules use their own fields).

### Phase 4 — Prove Behavior Preservation at Every Commit

For each commit (each increment above), apply this verification gate:

#### Gate Checklist

| Check | How | Pass Criteria |
|-------|-----|---------------|
| **Golden regression suite** | Run characterization test suite against current code | All golden comparisons pass (same DTOs, same SQL, same emails, same audit) |
| **Integration smoke** | Hit real endpoints / call public methods with staging-data payloads | Return codes match, response shape matches |
| **SQL diff review** | Diff captured queries before/after migration step | Same SQL statements, same parameter values, same execution order (for committed transactions) |
| **No new public contracts** | Diff public method signatures | Identical (or strictly backward-compatible additions) |
| **Static analysis** | Type checker, linter, cyclomatic complexity check | No regressions vs. pre-refactor baselines |

#### Concrete Golden Comparison Logic

```python
import json

def snapshots_equal(actual, expected, path=""):
    """Deep structural comparison enforcing deterministic keys."""
    if type(actual) != type(expected):
        raise AssertionError(f"{path}: type mismatch {type(actual).__name__} vs {type(expected).__name__}")
    
    if isinstance(actual, dict):
        assert set(actual.keys()) == set(expected.keys()), f"{path}: key mismatch"
        for k in sorted(actual.keys()):  # deterministic iteration
            snapshots_equal(actual[k], expected[k], f"{path}.{k}")
    elif isinstance(actual, list):
        assert len(actual) == len(expected), f"{path}: length mismatch {len(actual)} vs {len(expected)}"
        for i, (a, e) in enumerate(zip(actual, expected)):
            snapshots_equal(a, e, f"{path}[{i}]")
    elif isinstance(actual, Decimal):
        assert str(actual) == str(expected), f"{path}: decimal mismatch '{actual}' vs '{expected}'"
    elif isinstance(actual, datetime):
        assert actual.isoformat() == e.isoformat(), f"{path}: datetime mismatch"
    else:
        assert actual == expected, f"{path}: mismatch {actual!r} vs {expected!r}"
```

#### When Golden Tests Are Not Enough

Some behaviors are inherently hard to characterize (e.g., "how does the current tax rounding behave for exactly 3 items at $9.99 and $14.50?"). In those cases, add a **direct unit assertion** the moment you extract the corresponding module:

```python
# After extracting PricingService, immediately test it
def test_pricing_3_item_accumulation():
    lines = pricing.compute_lines([
        Item(sku="A", qty=3, unit_price=Decimal("9.99")),
        Item(sku="B", qty=2, unit_price=Decimal("14.50")),
    ])
    assert lines.subtotal == Decimal("58.97")  # exact golden number from characterization
```

These aren't redesign assertions — they're fidelity assertions confirming the extracted computation equals the old inline computation digit-by-digit.

#### Staging/Data Validation (Non-Golden Safety Net)

Once the entire pipeline is refactored, run against anonymized production data or staging database traffic. Compare output summaries: order count, sum totals, error rates. If something is off by even 1 cent at scale, roll back that increment and debug. This is the final "does the whole system still work" check.
