## 1. Module Boundaries (Target State)

Before touching anything, define where things should land. I'm drawing lines along **reasons to change**, not technology:

| Module | Responsibilities | Why It Stays Separate |
|---|---|---|
| `OrderValidator` | Input validation, business rule checks (min/max/limits/status transitions) | Rules change without touching pricing or persistence |
| `PricingEngine` | Line-item totals, discounts, promotions, shipping cost calculation | Pricing logic changes independently of tax rates |
| `TaxCalculator` | Tax jurisdiction lookup, rate application, exemption handling | Tax laws change on their own schedule; different team often owns it |
| `OrderRepository` | All SQL, ORMs, DB calls, transactions, batch inserts/updates | Data access changes when schema/driver changes |
| `NotificationSender` | Email assembly, queueing, template rendering, retry | Channel strategy shifts (email → SMS → push) without affecting order creation |
| `AuditLogger` | Write audit records, timeline tracking, compliance snapshots | Compliance requirements evolve independently |
| `OrderService` (remaining) | Orchestration: validate → price → tax → persist → notify → audit | Pure coordination after extraction |

The 34 fields split across these modules — no module owns more than ~6-8. This immediately makes each one testable in isolation.

## 2. Characterization / Golden-Master Tests

The single biggest risk in extracting from a God class is behavioral drift. Golden-master tests lock down current behavior. I'd take this approach:

### What to Snapshot Per Public Method

For each public method (`createOrder`, `updateOrder`, `cancelOrder`, etc.), I need three kinds of outputs captured as golden data:

**A. Return values** — what the caller gets back. This is the easiest snapshot.

**B. Database state after execution** — query the same tables/order IDs that the method modifies, serialize them to JSON. This proves the SQL side effects are preserved through refactoring.

**C. Outbound messages queued/sent** — intercept emails and audit log writes, capture their content as JSON blobs.

### How to Capture Each

**Return values:** Straightforward serialization.

```python
def characterize_create_order(order_input):
    """Run current service, capture all observable outputs."""
    result = order_service.create_order(order_input)
    
    # A) Return value
    return_value = json_serializable(result)
    
    # B) DB state — snapshot relevant rows for the created order
    db_state = {
        'orders': db.query("SELECT * FROM orders WHERE id = ?", [result.id]),
        'order_items': db.query("SELECT * FROM order_items WHERE order_id = ?", [result.id]),
        'tax_records': db.query("SELECT * FROM tax_records WHERE order_id = ?", [result.id]),
        'audit_log': db.query("SELECT * FROM audit_log WHERE order_id = ? ORDER BY created_at", [result.id]),
    }
    
    # C) Side effects — we'll need an interceptor (see below)
    emails_sent = email_interceptor.get_all()
    audit_entries = audit_log_interceptor.get_all()
    
    return {
        'method': 'create_order',
        'input': order_input,
        'output': {
            'return': return_value,
            'db_state': db_state,
            'emails': emails_sent,
            'audit_logs': audit_entries,
        },
    }
```

**SQL side effects:** Don't just snapshot what the service does — snapshot *what ends up in the database*. After running the method, run the same SELECT queries the code produces. Store the results. On future test runs, compare the new snapshot against the golden JSON. If they match, SQL behavior is preserved regardless of how the SQL got there.

**Email side effects:** Since the service directly sends emails (probably via SMTP), I can't easily intercept without modifying code. Strategy: wrap the SMTP connection or use an environment variable to point at a test/mailcatcher instance, then read its inbox. Better yet, extract the email dependency into an interface *first*, then run the characterization tests through that interface. That means two phases:

1. **Characterize through the existing direct calls** — run the real service, capture everything that happens, save it. Accept that email/network calls are part of "current behavior" even if fragile.
2. **After extracting the NotificationSender interface**, re-run characterization tests. The golden output is the same. If they pass, behavior is preserved.

### Test Suite Structure

```
tests/characterization/
  test_create_order_golden.py      # createOrder with 5-7 realistic inputs
  test_update_order_golden.py      # updateOrder with status transitions
  test_cancel_order_golden.py      # cancelOrder with refunds/tax reversal
  test_bulk_operations_golden.py   # bulkCreateOrder if applicable
  fixtures/
    valid_orders.json              # diverse but valid inputs
    edge_cases.json                # boundary conditions, invalid states
  goldens/                       # committed baseline snapshots
    create_order/
      input_simple_order.json       # golden return + db state + emails
      input_complex_promotions.json
    update_order/
      ...
```

Each golden file contains the input and the expected output tuple (return value, db_state, emails). Tests deserialize the golden, run the real service, then diff actual vs golden with structural comparison (ignoring timestamps where appropriate).

## 3. Seam Extraction Order

The key insight: **extract collaborators in reverse dependency order**. I don't start with the most-used field — I start with the seams that require the *least* change to the calling code and give the *most* immediate benefit.

### Phase 0: Foundation — Make Current Behavior Observable (Safe)

Before extracting anything, add observability hooks that don't change behavior:

1. **Wrap the raw SQL/connection behind an interface.** Create `DatabaseConnection` interface with methods matching current calls (`execute_query`, `begin_transaction`, `commit`, `rollback`). Use constructor injection or a setter to swap in a mock later. Currently it delegates to the existing connection. This is pure refactoring — zero behavioral change possible since it's a passthrough.

2. **Add an audit wrapper.** Create an `AuditLogger` interface. Replace inline `INSERT INTO audit_log (...) VALUES (...)` with `audit_logger.log(...)`. Same pattern — currently delegates to the existing inline call, so nothing changes. But now it's replaceable.

Why these two first? Because audit logging and SQL execute *at multiple points* throughout the class. Extracting them early gives me visibility into every place the service touches external systems. If I wait until later, I'll miss intermediate behavioral differences during partial refactorings.

### Phase 1: Email — Highest ROI, Lowest Risk

Extract email sending into `NotificationSender.send_order_confirmation(order)`. Email is:
- Called in only 1-2 methods (create, maybe update/cancel)
- Has clear boundaries (one method call, well-defined parameters)
- Easy to mock (no network needed in tests)

Replace `smtp.send_email(...)` with `notification_sender.send(...)`. Run characterization tests — they should pass immediately because the implementation is a passthrough. Now email is swappable.

### Phase 2: Persistence Layer

With email extracted, tackle the 34-field persistence. Create `OrderRepository` with CRUD operations:

```
save_order(order)
get_order(id)
update_status(order_id, new_status)
insert_items(items)
delete_order_items(order_id)
find_orders_by(customer_id, date_range)
```

Pull all SQL out of OrderService into OrderRepository. OrderService now only has `repository.save_order(self.to_domain_object())` style calls. Still one giant method internally, but the SQL is gone and in a single place.

Run characterization tests. The DB golden master validates that every INSERT/UPDATE/DELETE produces identical end-state.

### Phase 3: Business Logic Clusters (Validation → Pricing → Tax)

Now the orchestrator method still looks like one big waterfall, but the heavy lifting is distributed:

```python
class OrderService:
    def create_order(self, input):
        self.validator.validate(input)           # moved to OrderValidator
        line_items = self.pricer.calculate(input.items)  # moved to PricingEngine
        tax = self.tax_calculator.compute(line_items, input.shipping_address)  # TaxCalculator
        order = self.build_order(input, line_items, tax)
        self.repository.save(order)             # already extracted
        self.notification_sender.send_confirmation(order)  # already extracted
        self.audit_logger.log('order.created', order)  # already extracted
        return order.to_response()
```

Extraction order within this phase:

1. **Validation first** — it's self-contained, returns booleans or throws, affects nothing else. Easiest mental model shift. Move all the `if x < 0 raise...` blocks to `OrderValidator`.

2. **Pricing next** — it computes values and returns them. Cleanly separable: input is line items, output is total amounts. Move to `PricingEngine`. 

3. **Tax last** — this is usually the trickiest piece (jurisdiction rules, exemptions, mixed-rate items). By the time I get here, I have characterizing tests passing, a clean repository, clean email, and the orchestration method is simple enough to reason about. Tax becomes the hardest remaining problem and I'm ready for it.

### Phase 4: Field Deletion

Now the 34 fields are spread across 6 modules. Go through and delete the ones no longer used by OrderService. Typically you're left with just:
- Repository reference
- Validator reference  
- Pricer reference
- Tax calculator reference
- Notification sender reference
- Audit logger reference

That's ~6 fields. Delete the remaining 28+ that were being used only by internal helper methods you've now moved elsewhere.

## 5. Proving Behavior Preservation at Every Commit

This is the discipline that makes strangulation safe. Every merge commit must pass:

**A. Golden-master test suite** — all characterization tests must pass. These are non-negotiable gates.

**B. Delta testing** — for each commit, only the extracted concern needs unit tests. The rest of the suite provides the regression net. For example, when extracting `PricingEngine`, I write new targeted unit tests for the pricer AND run the full golden-suite. If the golden-suite passes, the pricing output is identical to before.

**C. SQL fingerprinting** — as a belt-and-suspenders measure, I can capture the actual SQL statements produced (not just the results). When extracting to `OrderRepository`, I add a test that compares the SQL strings before and after. Same SQL strings = same database behavior guaranteed. This catches cases where different SQL happens to produce the same result (edge case but worth checking once during extraction).

```python
def verify_sql_fingerprint_extracted(old_method, new_repository, sample_input):
    """Ensure SQL hasn't changed semantically during extraction."""
    old_calls = capture_sql_queries(lambda: old_method(sample_input))
    new_calls = capture_sql_queries(lambda: new_repository.save(sample_input))
    
    # Compare SQL structure (not exact string equality due to parameter binding)
    assert normalize_sql(old_calls) == normalize_sql(new_calls)
```

**D. Integration smoke test** — one happy-path integration test against a real database that exercises the full `create_order → confirm_email` flow. Runs on CI before deployment. Fast failure mode.

**E. Pre-commit hook checklist** — mandatory script:
```bash
#!/bin/bash

echo "All golden assertions passed."
```

## Summary

The strategy is: **observe → intercept → extract → delete**. You can't safely extract what you haven't characterized. The characterization step is the investment that pays off across every subsequent extraction. Starting with audit and database interfaces (passthrough) gives you the widest observation window with zero risk. Then work outward: email (simple, bounded), repository (heavy lifting), validation/pricing/tax (business logic clusters). Each milestone ships behind the existing public API — consumers never see a breaking change. Behavior is proven by golden masters that capture return values, database state, and outbound messages as structured data, compared structurally at every commit gate.
