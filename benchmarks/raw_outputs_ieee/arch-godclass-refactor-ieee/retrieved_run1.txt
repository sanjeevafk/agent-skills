```typescript
// sql_capture_hook.ts — wraps the DB connection before tests run
class SQLCaptureHook {
  private originalExecute;
  private capturedSQL: string[] = [];

  constructor(dbInstance) {
    this.originalExecute = dbInstance.execute.bind(dbInstance);
    dbInstance.execute = (...args) => {
      this.capturedSQL.push(args[0]);  // first arg is SQL string
      return this.originalExecute(...args);
    };
  }

  getCaptured(): string[] { return [...this.capturedSQL]; }
  
  restore() { 
    this.dbInstance.execute = this.originalExecute; 
  }
}
```

### Phase 2: Seam Extraction Order

**Strategy:** Extract collaborators from least risky to most risky. Start with interfaces that have no external side effects, then work outward toward I/O-heavy collaborators.

**Every commit MUST include these gates:**

| Golden Master | `npm run test:characterization` | 100% green |

| Size reduction | `wc -l src/orders/order.service.ts` | Decreasing each group |
| Coverage regression | `npm run test -- --coverage` | New commits don't reduce coverage below baseline |

**Regression contract:** The characterization test suite defines the behavior contract. A new test is considered "characterization" when:
1. It exercises a public method with a real (or near-real) input
2. It asserts on observable output: return values, SQL captured, emails sent, DB state delta
3. It does NOT assert on implementation details (method call counts, private member values)

If a characterization test fails after a refactoring commit, the developer must determine whether:
- **A genuine behavior change occurred** → fix the refactoring
- **The test was brittle/implementation-dependent** → relax the assertion
- **The original behavior was a bug** → document the bug, update the test to reflect intended behavior, tag commit as "behavior correction"

### Risk Mitigation

1. **Rollback point:** Keep a branch `refactor/before-characterization` pointing at the commit just before tests were written. If characterization testing takes longer than expected, the base code is untouched.

2. **Parallel test branches:** For the first week, keep both the original `OrderService` and the refactored version instantiated in tests, feeding them identical inputs in parallel, and diffing results. Only remove the original instance once characterizing tests stabilize.

3. **Staggered rollout:** Ship each group (A through E) on separate days, never multiple groups in the same release. Characterization tests run on CI for every PR touching any file under `src/orders/`.

4. **Code review focus:** Reviewers should skip looking for style issues and focus exclusively on: did the git diff change any conditionals, arithmetic, or control flow? Diff should show only delegation moves and interface boundaries being drawn.
