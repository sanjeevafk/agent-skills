### Phase 1 — Characterization / Golden-Master Tests

These are **production-demonstrating tests**, not new behavior. They assert current output so you can refactor safely. You prove `refactored_behavior(new) == original_behavior(old)` at every commit.

#### 1a. Snapshot Current Behavior (Functional Output)

For each public method, create a characterization test that captures:

```python
def test_calculate_total_for_electronics_order():
    """Golden master: records the exact total, line-item breakdown, 
     shipping cost, tax amount, discounts applied."""
    order = build_test_order(category="electronics", items=3, region="CA")
    result = order_service.calculate_total(order)
    
    # Golden value captured once from current behavior
    assert result.total == Decimal("249.97")
    assert result.line_items == [
        LineItem(sku="ELEC-001", qty=1, unit_price=Decimal("99.99"), ext=Decimal("99.99")),
        ...
    ]
    assert result.shipping == Decimal("12.50")
    assert result.tax == Decimal("18.67")
    assert result.discount_applied == Discount(code="WAREHOUSE10", pct=Decimal("10.0"))
```

**Strategy:** Run these against production-like fixture data first to capture golden values, then hard-code them. Use a seedable test data builder so each test uses the same input set every run.

#### 1b. Snapshot SQL Queries

Since SQL is scattered through methods, extract it as part of the characterization layer:

```python
def test_checkout_saves_correct_sql_statements():
    """Captures the exact INSERT/UPDATE/DELETE statements executed during checkout,
    including parameterized values."""
    queries = QueryCapture.start()       # intercept at driver/connection level

    statements = queries.stop()
    
    # Hard-coded snapshot — proves we execute the same queries post-refactor
    expected = [
        ("INSERT INTO orders (..., status) VALUES (%s, %s)", ("ORD_001", "CONFIRMED")),
        ("INSERT INTO order_line_items (...) VALUES (...)", (...)),
        ("UPDATE inventory SET quantity = quantity - %s WHERE sku = %s", (2, "SKU-X")),
        ("INSERT INTO audit_log (..., action) VALUES (%s, %s)", ("ORDER_CHECKOUT", "ORD_001")),
```

**How to intercept:** Wrap the database connection or use a mock/spy at the DAO/repository boundary. For raw JDBC/ADO.NET, inject a spy around `execute()` / `Connection.createStatement()`. For ORM-based raw SQL, intercept the command builder or use a profiler hook.

### Phase 2 — Seam Extraction Order

Extract interfaces at seams where **collaborators are instantiated directly**. Do the extraction starting from the most-coupled, highest-risk dependencies, working outward toward least-coupled ones.

**Recommended order:**

```
1. DatabaseRepository (or RawSqlGateway)    ← FIRST. Highest blast radius.
   └─ 34-field class + direct SQL = pure spaghetti if changed second
   
2. TaxCalculator                          ← Domain-logic isolatable
   └─ Pure function semantics (input → output), minimal state
   
3. PricingEngine                          ← Similar to TaxCalculator
   └─ Separate business rules (discounts, promotions)
   
4. EmailNotifier / NotificationService     ← I/O side effect
   └─ Easy to swap; good early-win for proving seams work
   
5. AuditLogger                            ← Lowest coupling concern
   └─ Append-only log; safest place to start extraction if unsure
```

**Why this order?**
- The **database collaborator** is the single biggest risk — if you get it wrong, SQL breaks silently. Get it behind an interface *first*, then you can refactor everything else without worrying about data persistence changing.
- **Tax/Pricing** are pure-ish domain logic. Once the DB seam exists, these become easy to move to their own classes because they only need immutable order state as input.
- **Email/Audit** are the safest to extract — they're already isolated by nature (fire-and-forget, append-only). These serve as practice extractions to validate your pattern before tackling harder boundaries.

#### Interface Sketches

```java
// 1. Database seam (most critical)
interface OrderDataStore {
    OrderEntity findByOrderId(String orderId);
    void saveOrder(OrderEntity entity);
    void updateInventory(List<InventoryAdjustment> adjustments);
    void insertAuditEntry(AuditLogEntry entry);
}

// 2. Tax calculator
interface TaxCalculator {
    TaxResult compute(OrderContext context);
}

// 3. Pricing engine
interface PricingEngine {
    PriceResult calculate(OrderContext context);
}

// 4. Notification
interface NotificationService {
    void sendOrderConfirmation(OrderContext context);
    void sendCancellationNotice(OrderContext context);
}

// 5. Audit
interface AuditLogger {
    void log(AuditAction action, String entityId, String details);
}
```

### Phase 3 — Incremental Strangler Steps

Each step ships **behind the existing public API** — no caller outside OrderService changes. Each step is its own commit, each verified by the golden-master suite.

#### Step 1 — Pull Database Repository Behind an Interface
**Shippable artifact:** Same SQL execution, same persistence behavior. Zero functional change.

```
Actions:
├── Create OrderDataStore interface (from Phase 2)
├── Move all SQL execution into RawSqlOrderRepository implementing it
│   ├── Extract each statement block into a dedicated method on the repo
│   ├── Keep parameter binding exactly as-is (no query rewriting)
│   └── Transaction management stays on OrderService (initially)
├── Inject Repo into OrderService constructor
└── Verify: All golden tests pass, especially test_checkout_saves_correct_sql_statements()
```

#### Step 2 — Extract Tax Calculation Into Its Own Class
**Shippable artifact:** Identical tax computation, moved to `DefaultTaxCalculator`.

```
Actions:
├── Create TaxCalculator interface
├── Move tax-computation logic from OrderService into DefaultTaxCalculator.compute()
│   ├── Extract the tax rate lookup table / configuration
│   ├── Keep jurisdiction rules identical (copy, don't rewrite yet)
│   └── Pass a lightweight OrderContext DTO instead of the 34-field OrderService instance
├── Inject into OrderService
└── Verify: test_recalculateTax produces identical amounts
```

**Key detail:** Use an immutable `OrderContext` record/value-object/dto derived from the order state. This severs the dependency on the bloated service itself and enables independent testing of tax rules.

Validation logic often has its own lifecycle. Extract `OrderValidator` with its own golden tests for error conditions (negative qty, invalid SKU, out-of-stock).

#### Step 8 — Remove Legacy Patterns, Apply Target Design
Now that behavior is verified at every step:
- Replace raw SQL with a proper mapper/query builder if desired

### Behavior Preservation Proof — At Every Commit

Every single commit must be verifiable. This is non-negotiable:

```
Commit verification checklist:
├── [ ] Full golden-master suite passes (all behavioral snapshots green)
│       └── Specifically: functional output + SQL snapshot + email snapshot
├── [ ] No new integration tests fail (if any existed before)
├── [ ] Public API signature unchanged (compile-time proof — diff the .class/.jar or header files)
│       └── Method signatures, parameter types, return types must match exactly
├── [ ] No new dependencies added to production scope
└── [ ] Code review diff shows ONLY structural movement — zero logic changes
        └── If the diff shows logic changes, the refactor is too large. Split it smaller.
```

**Automate the proof:** Hook the golden-master suite into CI. Block merges on failures. Treat it as the regression contract. Since it exercises real business paths (not mocks), passing it means nothing broke.

**SQL/even stricter proof:** For the SQL golden test, also compare the execution plan hash or the exact parameterized query text at the wire level. If someone accidentally rewrites a JOIN or changes a WHERE clause, the character-for-character comparison catches it.
