# Refactoring Campaign: OrderService (1,400 LOC)

## The Problem Statement

You're staring at the God Object anti-pattern — validation, pricing, tax calculation, persistence, email dispatch, and audit logging all fused into one class with 34 fields and inline SQL. There are zero tests and you can't change observable behavior. This is the canonical case for the **Strangler Fig pattern paired with Characterization Testing**.

Here's the full campaign.

## Phase 1: Golden-Master Characterization Tests

### Why characterization tests first

You have no spec other than "behavior doesn't change." Every existing input-output pair IS the spec. You capture it before you refactor anything. If a test fails after a refactor, the refactor is broken. Period.

### Test structure

Create `tests/characterization/test_order_service_golden.py`. Each public method gets a test that runs the real code against real inputs and snapshots outputs + side effects.


### Side-effect capture mechanisms

These are the infrastructure pieces that make golden testing possible without real databases or SMTP servers:

**Database query interception (for SQL snapshotting)**

```python
class DbSnapshot:
    """Wraps the real DB connection. Records every query so we can 
    assert exact SQL was generated, even though we won't diff SQL strings
    (fragile). Instead we assert structural properties.
    """
    
    def __init__(self, real_connection):
        self._conn = real_connection
        self._queries = []
    
    def execute(self, sql, params=None):
        self._queries.append({"sql": sql, "params": params})
        return self._conn.execute(sql, params)
    
    def get_executed_queries(self):
        return list(self._queries)
    
    def rollback_all(self):
        # Rollback every transaction so each test is isolated
        for q in reversed(self._queries):
            try:
                self._conn.rollback()
            except Exception:
                pass
```

Assertion helper for create order queries:

```python
def _assert_create_order_queries(self, queries):
    """Capture the ACTUAL number of INSERTs, UPDATEs, and which
    tables are touched. We snapshot this once, save it as golden JSON,
    then assert shape matches on every run."""
    
    inserts = [q for q in queries if "INSERT" in q["sql"].upper()]
    updates = [q for q in queries if "UPDATE" in q["sql"].upper()]
    
    # These numbers come from running the test once against production
    # data and recording the result as golden.json
    assert len(inserts) >= 1, "Should insert into orders table"
    assert any("orders" in q["sql"] for q in inserts)
    assert any("order_items" in q["sql"] for q in inserts)
    # Audit + inventory checks happen after the main insert
    assert len(queries) >= 4  # captures current coupling level
```

**Email capture**

```python
class MailCapture:
    """Intercepts smtplib.SMTP.sendmail by wrapping it."""
    
    def __init__(self):
        self._sent = []
        self._real_smtp = None
    
    def wrap(self, smtp_instance):
        original_sendmail = smtp_instance.sendmail
        def captured_sendmail(from_addr, to_addrs, msg):
            self._sent.append({
                "from": from_addr,
                "to": to_addrs,
                "body": msg if isinstance(msg, str) else msg.as_string(),
                "subject": self._extract_subject(msg)
            })
            return original_sendmail(from_addr, to_addrs, msg)
        smtp_instance.sendmail = captured_sendmail
        return self
    
    def get_sent_emails(self):
        return list(self._sent)
```

**Audit log capture**

Same pattern — intercept whatever `logAuditEvent` writes to (database, file, queue) and record it in memory. Assert events appear in the expected sequence.

## Phase 2: Seam Extraction — Collaborator Order

### The extraction philosophy

Extract interfaces starting from the **outward-facing dependencies** (side effects) inward toward core logic. Why? Because:

1. **Side effects are the hardest to test** — SQL, email, audit logging introduce mutable external state. Isolating them first makes everything below easier to test.
2. **Behavior stays the same** — replacing a concrete dependency with an interface + adapter doesn't change logic. It just makes the dependency injectable.
3. **Each seam is independently reversible** — you can always drop back to the monolith because nothing has been deleted yet.

### Extraction order (with rationale)

```
Step 1: DatabaseRepository (THE BIG ONE)
├─ Extracts ALL SQL from OrderService into a repository interface
├─ Rationale: SQL is embedded in createOrder, updateOrder, getOrderByNumber,
│             submitForFulfillment — roughly 60% of the class. Getting this out
│             is the highest leverage move. It also eliminates the "direct SQL in
│             business logic" smell immediately.
├─ New interface:
│    interface OrderRepository {
│        insert(order: Order): OrderId
│        selectById(id: OrderId): Order | null
│        selectByOrderNumber(number: string): Order | null
│        update(order: Order): void
│        deleteOrCancel(orderId: OrderId, newStatus: string): void
│    }
└─ Adapter: SqlOrderRepository wraps raw SQL with parameterized queries

Step 2: EmailNotifier
├─ Extracts sendOrderConfirmationEmail into an interface
├─ Rationale: ~30 lines. Pure side effect. Once Step 1 is done and tests pass,
│           this is a surgical removal. Small win. Builds confidence.
├─ New interface:
│    interface EmailNotifier {
│        sendOrderConfirmation(order: Order, recipient: string): void
│    }
└─ Adapter: SmtpEmailNotifier implements the interface

Step 3: AuditLogger
├─ Extracts logAuditEvent into an interface  
├─ Rationale: Another pure side effect, similar effort to EmailNotifier.
│           Can be done in the same PR as Step 2 (both are thin extractions).
├─ New interface:
│    interface AuditLogger {
│        log(eventType: AuditEventType, payload: AuditPayload): void
│    }
└─ Adapter: DatabaseAuditLogger (wraps another SQL call, now in its own class)

Step 4: PricingEngine (DOMAIN LOGIC — THE PAYOFF)
├─ Extracts validatePricing + applyTaxRules into domain classes
├─ Rationale: THIS is where the real value lives. After steps 1-3, the remaining
│           OrderService is mostly orchestration. Pull out PricingEngine and
│           TaxCalculator as testable, pure-ish domain classes.
├─ New interfaces:
│    interface PricingEngine {
│        validatePrice(sku: string, price: Money, quantity: number): boolean
│        calculateLineTotal(item: LineItem): Money
│    }
│    interface TaxCalculator {
│        calculateTax(items: LineItem[], region: string): Money
│    }
└─ These become freely testable without any DB/email/audit

Step 5: OrderValidator
├─ Extracts validation logic from createOrder/updateOrder entry points
├─ Rationale: Validation is usually the highest cyclomatic complexity in a
│           controller-like class. Separating it gives you clear error types
│           (ValidationFailure vs DomainError) and composable validators.
├─ New interface:
│    interface OrderValidator {
│        validateCreate(dto: CreateOrderDto): ValidationResult
│        validateUpdate(dto: UpdateOrderDto): ValidationResult
│    }
```

### What each seam looks like in practice

**Step 1 example — extracting the database:**

Before:

After (same behavior, extracted seam):

```python
class OrderService:
    def __init__(self, repository: OrderRepository, email: EmailNotifier,
                 auditor: AuditLogger, pricing: PricingEngine,
                 tax: TaxCalculator, validator: OrderValidator):
        self._repository = repository
        self._email = email
        self._auditor = auditor
        self._pricing = pricing
        self._tax = tax
        self._validator = validator
    
    def createOrder(self, dto):
        self._validator.validateCreate(dto)
        order = self._buildOrder(dto)
        order.id = self._repository.insert(order)  # <-- seam
        self._auditor.log(AuditEventType.ORDER_CREATED, {"orderId": order.id})
        self._email.sendOrderConfirmation(order, dto.customerEmail)
        return order.id
```

The `SqlOrderRepository` constructor takes the same `self.db` that `OrderService` had:

```python
class SqlOrderRepository(OrderRepository):
    def __init__(self, connection):
        self._conn = connection
    
    def insert(self, order):
        cursor = self._conn.cursor()
        cursor.execute(
            "INSERT INTO orders (customer_id, status, created_at) VALUES (%s, %s, NOW())",
            (order.customer_id, order.status)
        )
        order.id = str(cursor.lastrowid)
        for item in order.items:
            cursor.execute(
                "INSERT INTO order_items (order_id, sku, quantity, unit_price) VALUES (%s, %s, %s, %s)",
                (order.id, item.sku, item.quantity, float(item.unit_price))
            )
        return order.id
```

Same SQL, different class. Behavior is identical. The golden master test validates this.

## Phase 3: Incremental Strangler Steps

Each step ships **behind the existing public API**. Consumers don't change. The old `OrderService` calls increasingly fewer internal methods directly — more of them are delegated to injected collaborator interfaces. At no point does the monolith disappear; it shrinks until it's just wiring + routing.

### Shippable milestones

| Milestone | What changes | Public API | Risk | Deliverable |
|---|---|---|---|---|
| M0 | Golden-master tests pass against current code | ✅ No change | Low | Tests covering all 6 public methods |
| M1 | DatabaseRepository extracted, SqlOrderRepository wired in | ✅ No change | Medium | All SQL moved to repository; 6 golden tests still pass |
| M2 | EmailNotifier + AuditLogger extracted | ✅ No change | Low | Both sides-effect interfaces live; adapters wired |
| M3 | PricingEngine + TaxCalculator extracted | ✅ No change | High (domain logic) | Core math is testable in isolation; golden tests still pass |
| M4 | OrderValidator extracted | ✅ No change | Medium | Validation errors are typed; golden tests still pass |
| M5 | OrderService is now ~80 lines of wiring/delegation | ✅ No change | Low | Delete OrderService, replace with composition root |
| M6 | New bounded contexts form: `orders.core`, `orders.pricing`, `orders.domain.events` | ⚠️ New endpoints added gradually | Managed | Old API deprecated, new endpoints on parallel paths |

### Strangler gate — proving behavior at every commit

Every milestone follows this commit discipline:

```
commit: feat: extract DatabaseRepository from OrderService
├── Changes:
│   ├── Added: src/orders/repository.py (OrderRepository interface)
│   ├── Added: src/orders/adapters/sql_repository.py (SqlOrderRepository)
│   ├── Modified: src/orders/service.py (inject repository, delegate SQL calls)
│   └── Moved: SQL strings from service.py → sql_repository.py
├── Tests:
│   ├── Unit: tests/unit/test_sql_repository.py (insert/select/update/delete)
│   ├── Golden: ALL 6 characterization tests in 
│               tests/characterization/test_order_service_golden.py STILL PASS
│   └── Integration: tests/integration/test_order_flows.py (happy + edge paths)
├── Proof of preservation:
│   ├── Diff shows NO change to OrderService public method signatures
│   ├── Golden master tests verify return values, query count, email count,
│   │   audit event count are IDENTICAL
│   └── Coverage report shows same branch coverage (or better)
└── Merge criteria: CI green + manual smoke test on staging
```

### Specific strangling tactics per milestone

**M1 (Database):** Use find-and-replace carefully. The SQL fragments live inside string concatenations inside method bodies. Replace each `self.db.execute(...)` call with `self._repository.xxx(...)`. Keep the SQL text EXACTLY the same — copy-paste, don't rewrite. After all calls are migrated, verify with grep that zero `self.db.` calls remain in OrderService.

**M2 (Email + Audit):** Straightforward extract-class. Cut the two private methods, paste them into new classes implementing interfaces, wire through `__init__`. Three-character method renames in the old class (`sendOrderConfirmationEmail` → delegates to `self._email.sendOrderConfirmation`). Zero logic moves.

**M3 (Pricing + Tax):** This is the hardest because the logic is interwoven with field reads. Strategy:
1. Extract pricing computation into its own method on PricingEngine (same algorithm, receives parameters instead of reading `self`)
2. In OrderService, replace `self.computePrice(x)` with `self._pricing.computePrice(x, y, z)`
3. Repeat until zero local variable reads reference OrderService fields for pricing
4. Same for tax rules

**M4 (Validation):** Extract each validation rule into a `ValidationError` with a message. The old code raises exceptions; the new code returns a structured failure object. The gateway method (`createOrder`) checks the result. Behavior is identical from the caller's perspective.

**M5 (Cleanup):** By now OrderService has ~80 lines. It's literally a factory + delegation router. Delete it. Move the factory logic into the application layer's dependency injection setup. All consumers now depend on `OrderServiceInterface` which resolves to the composition.

## Phase 4: Target Module Boundaries

After strangling, the codebase should split into these modules:

```
src/orders/
├── core/                    # The bounded context: order lifecycle
│   ├── models/
│   │   ├── order.py         # Value objects, aggregates
│   │   ├── line_item.py
│   │   └── money.py
│   ├── services/
│   │   ├── order_service.py     # Thin orchestrator (~50 lines)
│   │   └── order_query_service.py  # For read paths (getOrderByNumber)
│   ├── repository/
│   │   ├── order_repository.py  # Interface
│   │   └── sql_order_repository.py  # Implementation
│   └── port/                  # Infrastructure adapters
│       ├── sql_connection.py
│       └── order_mapper.py    # Row → Aggregate mapping
├── pricing/                   # Bounded context: pricing logic
│   ├── engine.py              # PricingEngine
│   ├── calculator.py          # TaxCalculator
│   ├── coupon.py              # Coupon/discount logic
│   └── validation.py          # Price validation rules
├── notification/              # Bounded context: outbound events
│   ├── email_notifier.py      # EmailNotifier + SmtpAdapter
│   └── audit_logger.py        # AuditLogger + DbAdapter
└── api/                       # External contracts
    ├── handlers/
    │   ├── create_order_handler.py
    │   ├── update_order_handler.py
    │   └── ...
    └── dtos/
        ├── create_order_dto.py
        └── ...
```

Why these boundaries?

- **`core`** owns the order aggregate and its lifecycle transitions. The repository sits here because it persists the aggregate.
- **`pricing`** is a separate bounded context because pricing rules change independently (sales, coupons, tax law). Different team, different release cadence.
- **`notification`** is separate because email channels and audit storage medium can swap without affecting order logic.
- **`api`** is the anti-corruption layer — converts HTTP/DTO shapes into domain commands. Stays thin.

```
│  Layer 1: Static                               │
```

### The golden file diff review

When a golden test fails after a refactor, you get a structured diff:


If the `orders` → `orders_v2` change wasn't intended, roll back that part of the refactor. If it was (migration), update the golden file AND add a comment explaining why.

## Risk Register

| Risk | Likelihood | Mitigation |
|---|---|---|
| Golden master misses a hidden code path | Medium | Run golden baseline generation against diverse staging data (edge cases from bug reports, known tricky scenarios) |
| SQL differs due to driver/DB version | Low | Pin DB version in CI; run golden against exact version mirror |
| Floating-point rounding differences between extracts | Low | Capture exact decimal values, not computed intermediates |
| Email body format drifts slightly | Medium | Compare subject + presence/absence of key tokens, not full body string |
| Extracting PricingEngine breaks invariant assumptions | High | Extract conservatively — keep all field reads local, pass them as arguments. Don't reorder computations. |

## Summary: The Campaign in One Sentence

**Write golden tests against the existing God Service, then extract five collaborator interfaces outward-to-inward (repo → email → audit → pricing → validator), each behind a commit where every golden test passes and the public API surface remains byte-for-byte identical, until the service shrinks to a thin orchestrator that gets replaced by the composed module boundaries.**
