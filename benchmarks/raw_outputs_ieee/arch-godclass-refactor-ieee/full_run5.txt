## Refactoring Campaign: OrderService (1,400 LOC, 34 Fields)

### Phase 0 — Baseline & Safety Net

**Goal**: Prove you can run the current system end-to-end before touching anything.

1. **Characterization tests first, NOT unit tests.** Pick one representative scenario (e.g., "valid cart from Europe") and record every observable output — return value, DB rows touched, emails sent, audit log entries, side-channel metrics.

2. **Golden-master snapshots:**
   - **SQL side effects**: Instrument before the DB driver commits. Intercept via a thin proxy over SQLAlchemy/Django ORM/raw cursor: override `execute()` to capture the raw SQL string + bound parameters into a JSON file keyed by method name. Example pattern:

     ```python
     # In tests — inject during setup
     class SQLCapture:
         def __init__(self):
             self.calls = []
         def execute(self, sql, params=None):
             self.calls.append({"sql": sql.strip(), "params": params})
             return original_execute(sql, params)
     ```

   - **Email side effects**: Replace `smtp.sendmail()` with a captor that stores `(to, subject, body)` tuples per call. No real SMTP connection needed.

   - **Return values**: Serialize the full return state of each public method (`order.to_dict()`, etc.) using `json.dumps(sort_keys=True)`.

3. **Run all captured scenarios once against the existing service.** Save artifacts in `tests/snapshots/` — one `.golden.json` per scenario with `{"method": "...", "args": {...}, "snapshot": {"returns": ..., "sql": [...], "emails": [...]}}`.

4. **Verification at every commit going forward**: Each characterization test replays the scenario against the refactored system and diff-snapshot. A single new SQL statement, a missing email, or an altered return field breaks CI. This is your invariant harness.

```
commit guard: ALL characterization_tests pass → green light to proceed
fail fast: any divergence stops the campaign immediately
```

### Phase 2 — Extract Collaborators (Interfaces First)

Now you have pure functions tested. Next, decouple the side-effecting concerns. The key insight: **extract interfaces BEFORE extracting implementations**. This lets you swap behavior gradually.

#### Seam 3: OrderRepository (Persistence Layer)

**Why this next:** It's the largest coupling — direct SQL scattered throughout `create_order`, `update_status`, `get_by_id`, etc. Every method that touches `cursor.execute()` goes here. If you get this right, the rest flows.

```python
# Interface — extracted first
class OrderRepository(ABC):
    @abstractmethod
    def save(self, order: Order) -> None: ...
    @abstractmethod
    def find_by_id(self, id: int) -> Order | None: ...
    @abstractmethod  
    def find_by_customer(self, customer_id: int) -> list[Order]: ...
    @abstractmethod
    def update_status(self, id: int, status: str) -> None: ...
```

| Step | What | How | Proof |
|------|------|-----|-------|
| 3a | Create interface in `src/domain/order_repository.py` | ABC with methods matching current SQL calls | Compile passes (abstract methods not yet implemented) |
| 3b | Implement `SqlOrderRepository` | Copy-paste existing SQL methods into concrete impl. Point service to it. | **Characterization test**: capture SQL calls → diff against golden snapshot. If SQL differs by even a semicolon, you failed. |
| 3c | Inject via constructor | `OrderService.__init__` accepts `OrderRepository` instead of creating it | Same SQL snapshot = behavior preserved |
| 3d | Verify | Full characterization suite passes | All golden snapshots match |

**Critical detail**: The SQL capture from Phase 0 becomes the oracle for every commit in this seam. If `save(order)` produces different SQL than the golden, rollback immediately.

### Phase 3 — Domain Modeling & Code Organization

With all collaborators behind interfaces, the remaining ~800 lines of OrderService are just orchestration and state management. Now you can do the structural work.

#### Target Module Boundaries

```
src/orders/
├── domain/
│   ├── order.py                    # Order aggregate root (data-only)
│   ├── order_state_machine.py      # State transition rules (pure)
│   └── exceptions.py               # ValidationError, OrderNotFoundError, etc.
├── pricing/
│   ├── calculator.py               # PricingCalculator (from Seam 2)
│   └── discounts.py                # Discount computation
├── tax/
│   ├── calculator.py               # TaxRate lookup + computation (extracted)
│   └── jurisdiction.py             # Tax rules per region (if any)
├── infrastructure/
│   ├── repositories/
│   │   └── order_repository.py     # SqlOrderRepository (from Seam 3)
│   └── notifications/
│       ├── notification_service.py # SmtpNotificationService (Seam 4)
│       └── audit_logger.py         # DbAuditLogger (Seam 5)
├── application/
│   └── order_service.py           # Orchestrator — thin now (~200 lines)
└── api/
    └── order_controller.py        # HTTP entry points, if applicable
```

**Key design decisions baked in:**
- Order aggregate owns its own state machine — no status updates from outside
- Tax is extracted separately because rate changes need redeployment but not code changes
- Pricing supports strategy pattern for future discount engines
- Application layer (OrderService) is purely orchestration — creates order → calculates → persists → notifies → audits, nothing more

### Behavior Preservation Strategy Across All Commits

```
Every commit checklist:
  ✅ Characterization tests compile and pass
  ✅ SQL golden snapshot matches (zero new queries, zero dropped queries)
  ✅ Email golden snapshot matches (same recipients, subjects, bodies)
  ✅ Return values deserialize identically
  ✅ No regression in the 3 public API signatures
```

**The progression guarantees**: Each step only changes internals. Public API surface never changes. Characterization tests run on every PR. If any snapshot diverges, the pipeline fails — you know *exactly* which behavior changed and revert in seconds.

**Risk ordering rationale** (why this specific sequence):
1. **Validation/Pricing first** → easiest seams, pure functions, instant feedback loop, proves the testing approach works
2. **Repository second** → biggest blast radius (SQL everywhere), tackle it while the service is still intact and you have the golden baseline
3. **Email/Audit third** → lower blast radius, similar pattern, builds momentum
4. **Domain model last** → structural cleanup when all dependencies are already resolved

After Phase 3 you have: a clean hexagonal-ish architecture, 100% characterization coverage of all existing paths, zero behavioral changes, and every collaborator swap-able behind interfaces. Adding tests on top of this is trivial because the system is now deterministic and queryable.
