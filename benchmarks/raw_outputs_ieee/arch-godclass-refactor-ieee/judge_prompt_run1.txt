```python
import re
from collections import defaultdict

def map_order_service(filepath: str) -> dict:
    source = open(filepath).read()
    
    dependencies = {
        'sql_calls': [],          # method -> [(statement, line)]
        'email_calls': [],        # method -> [call_description]
        'audit_calls': [],        # method -> [call_description]
        'field_usage': {},        # field_name -> set(method_names)
        'public_methods': [],     # list of public method signatures
        'internal_calls': []      # (caller, callee) pairs
    }
    
    # Extract method boundaries first
    methods = re.finditer(
        r'def\s+(\w+)\s*\(self(?:\s*,[^)]*)?\)\s*:',
        source
    )
    method_ranges = []
    for i, m in enumerate(methods):
        start = m.start()
        next_start = methods[i+1].start() if i+1 < len(list(methods)) else len(source)
        method_ranges.append((m.group(1), start, next_start))
    
    # Now analyze each method body
    for method_name, start, end in method_ranges:
        body = source[start:end]
        
        # SQL patterns
        sql_lines = [(line.strip(), idx + start + line.rfind('\n') + 1)
                      for idx, line in enumerate(body.split('\n'))
                      if re.search(r'(SELECT|INSERT|UPDATE|DELETE|EXEC)', line)]
        dependencies['sql_calls'].extend(sql_lines)
        
        # Email patterns
        email_matches = re.findall(r'self\._?mail\.send[_a-z]*\(', body)
        dependencies['email_calls'].append((method_name, email_matches))
        
        # Audit patterns
        audit_matches = re.findall(r'self\._?audit\.(log|record|track)[_a-z]*\(', body)
        dependencies['audit_calls'].append((method_name, audit_matches))
        
        # Field usage
        fields = re.findall(r'self\.(\w{2,})\b', body)
        for f in fields:
            dependencies['field_usage'].setdefault(f, set()).add(method_name)
        
        # Internal calls
        internal_calls = re.findall(r'self\.(\w+)\(', body)
        for call in internal_calls:
            if call.startswith('_'):
                dependencies['internal_calls'].append((method_name, call))
    
    return dependencies
```

### 0b. Identify the "Seams" — Entry Points for Extraction

Not all seams are equal. Rank them by ease of isolation:

| Seam | Why It's Good First Target | Risk |
|------|--------------------------|------|
| **Persistence layer** | Highest cohesion, clearest boundary | Medium (SQL integration) |
| **Email notification** | Loose coupling target exists | Low |
| **Audit logging** | Pure side-effect, easy to swap | Low |
| **Validation rules** | Business logic, harder to separate early | High |
| **Pricing/discount engine** | Complex domain logic, depends on persistence | Very high |

**Priority order**: Persistence → Email → Audit → Validation → Pricing. Here's why:

1. **Persistence** first because it removes `self.connection`, `self.cursor`, raw SQL from EVERY other seam. Once data access is encapsulated in a repository interface, every subsequent refactor gains a clean contract.
2. **Email** second because it's pure side-effect with an obvious external collaborator. A `Notifier` interface is trivial to introduce.
3. **Audit** third — same as email but even simpler. A `Logger` interface is 10 lines.
4. **Validation** fourth — validation lives close to pricing logic; better to have the infrastructure stable first.
5. **Pricing/discount** last — it depends on both persistence AND validation AND complex tax calculations. By this point the scaffolding will support it cleanly.

### 0b. How to Actually Capture Side Effects

**SQL injection via query interceptor (no source changes):**

| Database | Technique | Cost |
|----------|-----------|------|
| PostgreSQL (asyncpg/psycopg) | Monkey-patch `Connection.execute()` or wrap it with a context-manager that delegates to the real execute but appends `(query, params)` to a thread-local list | ~20 LOC, zero src edits |
| MySQL (aiomysql/mysql-connector) | Same pattern — intercept `.execute()` / `_cursor.execute()` | Same |
| Generic | Set up the database's own logging/profiling layer (e.g., `pg_stat_statements`-style hooks) | Zero code changes |

```python
# Pattern for Python asyncpg
@contextmanager
def sql_capture():
    queries = []
    orig_execute = connection.execute
    async def tracing_execute(query, *args, **kwargs):
        queries.append((query, args, kwargs))
        return await orig_execute(query, *args, **kwargs)
    connection.execute = tracing_execute   # type: ignore[assignment]
    try:
        yield queries
    finally:
        connection.execute = orig_execute     # type: ignore[assignment]
```

## Phase 1: Seam Extraction — Interface First, Class Later

### The Seam Strategy

Don't rewrite the class. **Add interfaces at the edges of concerns**, then gradually replace internal implementations with ones that delegate to the interfaces. Start from the concern with the **tightest coupling and least cohesion** — that's usually the persistence/data-access layer, because SQL strings are embedded in business methods, making everything else hostage to schema changes.

### Extraction Order & Rationale

| Step | Concern | Interface Name | Why First? |
|------|---------|---------------|------------|
| 1 | **Persistence / SQL** | `OrderRepository` | Highest cyclomatic cost; direct SQL scattered everywhere; easiest to swap without changing signatures (method names stay the same, bodies move) |
| 2 | **Pricing engine** | `PricingService` | Pure function style (line items + rules → prices); low risk, high clarity gain |
| 3 | **Tax calculation** | `TaxCalculator` | Also mostly pure (jurisdiction + amount → tax); often tied to pricing |
| 4 | **Coupon/discount** | `DiscountEngine` | Business rules isolated from pricing; may overlap with PricingService |
| 5 | **Email/notification** | `OrderNotifier` | Already somewhat separated (probably a method), but sending logic (templates, retries) is messy |
| 6 | **Audit logging** | `AuditLogger` | Cross-cutting; becomes trivial after step 1 (we already track DB operations) |
| 7 | **Validation** | `OrderValidator` | Currently sprinkled across create/update; move into its own pipeline |

### Per-Step Mechanics

For each concern, follow this exact pattern — no method signature changes on `OrderService`:

1. **Create the interface.**
2. **Create a *passthrough adapter*** that wraps the old implementation (the inline code currently inside OrderService).
3. **Add a setter / private field** on OrderService pointing to the new collaborator.
4. **Wire the passthrough** into that field (no constructor change needed if OrderService uses a simple factory or is instantiated in one place).
5. **Refactor the relevant methods** to delegate through the collaborator.
6. **Re-run characterization tests.** Green → ship the commit.

```
Commit 1: Add OrderRepository interface + PassthroughOrderRepository
Commit 2: Move SQL from OrderService.create() → PassthroughOrderRepository.insert()
Commit 3: Re-point OrderService._repo to PassthroughOrderRepository
         Run characterization suite. ✅ → Push
```

If OrderService is constructed in multiple places, use a dependency property instead of constructor injection so callers keep working:

```python
# Before
self.repo = SomeOldRepo()

# After (still works identically)
_repo = None
@property
def repo(self):
    if self._repo is None:
        self._repo = PassthroughOrderRepository()  # default passthrough
    return self._repo
```

Each step is independently shippable and keeps the full public API intact. Below is the sequence with what moves, what stays, and how behavior is preserved.

### Step 1 — Persistence (Repository Layer)
**Moves out:** All raw SQL → `OrderRepository`
**Stays in OrderService:** orchestration (call repo, handle results, chain to next concern)

```
Before                              After
─────────                         ─────────

    def _save(self):                  def save_order(order):
        cursor = …                      self.repository.insert(order)
        cursor.execute(...)             self.notifier.send_confirmation(order)
        ...                             self.audit.log("created", ...)
```

### Step 2 — Pricing
**Moves out:** Price computation from line-items → `PricingService.calculate(items, customer_tier)`
**Stays:** The decision flow (when to price, when to recalculate)

### Step 3 — Tax
**Moves out:** Jurisdiction resolution + tax computation → `TaxCalculator.compute(amount, jurisdiction_code, items)`
**Stays:** When/how tax is applied in the order lifecycle

### Step 4 — Validation
**Moves out:** Field-level + cross-field validation → `OrderValidator.validate(dto)` returns `ErrorList | Success<Order>`
**Stays:** Where validation is invoked in create/update flows

### Step 5 — Discounts/Coupons
**Moves out:** Coupon lookup, stackability rules, discount application → `DiscountEngine.apply(coupons, cart)`
**Stays:** Whether/how discounts integrate into the pricing total

### Step 6 — Email
**Moves out:** Template rendering, retry logic, batch sending → `OrderNotifier.send(order, events)`
**Stays:** Which events trigger which emails

### Step 7 — Audit
**Moves out:** Structured audit-entry creation → `AuditLogger.record(event, metadata)`
**Stays:** Where events are emitted

### Step 8 — Remove the Passthrough Adapters
Now that every collaborator has a clean implementation, delete the passthrough adapters and have OrderService depend on real implementations. The API surface hasn't changed — only the wiring behind it.

```typescript
// sql_capture_hook.ts — wraps the DB connection before tests run
class SQLCaptureHook {
  private originalExecute;
  private capturedSQL: string[] = [];

  constructor(dbInstance) {
    this.originalExecute = dbInstance.execute.bind(dbInstance);
    dbInstance.execute = (...args) => {
      this.capturedSQL.push(args[0]);  // first arg is SQL string
      return this.originalExecute(...args);
    };
  }

  getCaptured(): string[] { return [...this.capturedSQL]; }
  
  restore() { 
    this.dbInstance.execute = this.originalExecute; 
  }
}
```

### Side-effect capture mechanisms

These are the infrastructure pieces that make golden testing possible without real databases or SMTP servers:

**Database query interception (for SQL snapshotting)**

```python
class DbSnapshot:
    """Wraps the real DB connection. Records every query so we can 
    assert exact SQL was generated, even though we won't diff SQL strings
    (fragile). Instead we assert structural properties.
    """
    
    def __init__(self, real_connection):
        self._conn = real_connection
        self._queries = []
    
    def execute(self, sql, params=None):
        self._queries.append({"sql": sql, "params": params})
        return self._conn.execute(sql, params)
    
    def get_executed_queries(self):
        return list(self._queries)
    
    def rollback_all(self):
        # Rollback every transaction so each test is isolated
        for q in reversed(self._queries):
            try:
                self._conn.rollback()
            except Exception:
                pass
```

```python
class MailCapture:
    """Intercepts smtplib.SMTP.sendmail by wrapping it."""
    
    def __init__(self):
        self._sent = []
        self._real_smtp = None
    
    def wrap(self, smtp_instance):
        original_sendmail = smtp_instance.sendmail
        def captured_sendmail(from_addr, to_addrs, msg):
            self._sent.append({
                "from": from_addr,
                "to": to_addrs,
                "body": msg if isinstance(msg, str) else msg.as_string(),
                "subject": self._extract_subject(msg)
            })
            return original_sendmail(from_addr, to_addrs, msg)
        smtp_instance.sendmail = captured_sendmail
        return self
    
    def get_sent_emails(self):
        return list(self._sent)
```

```python
"""tests/harness/side_effect_harness.py"""
from __future__ import annotations
import json
import smtplib
from pathlib import Path
from unittest.mock import MagicMock, patch
from datetime import datetime


class QueryLog:
    """Captures raw SQL strings + params so golden-masters can diff them."""
    def __init__(self) -> None:
        self.calls: list[tuple[str, tuple]] = []
    def record(self, sql: str, params: tuple) -> None:
        self.calls.append((sql, params))
    def as_json(self) -> str:
        return json.dumps(
            [{"sql": s, "params": p} for s, p in self.calls],
            indent=2, sort_keys=True, default=str,
        )


class EmailSnapshot:
    """Sucks up SMTP calls into JSON for golden-matching."""
    def __init__(self) -> None:
        self.sent: list[dict] = []
    def capture_sendmail(self, from_addr: str, to_addrs: list[str], msg: str) -> None:
        self.sent.append({
            "from": from_addr,
            "to": to_addrs,
            "subject": _extract_header(msg, "Subject"),
            "body_preview": msg.split("\n\n")[1][:200] if "\n\n" in msg else "",
        })
    def as_json(self) -> str:
        return json.dumps(self.sent, indent=2, sort_keys=True, default=str)


def _extract_header(raw_msg: str, header_name: str) -> str:
    for line in raw_msg.splitlines():
        if line.lower().startswith(header_name.lower() + ":"):
            return line.split(":", 1)[1].strip()
    return ""


# Factory used by each characterization test
def snapshot_harness(db_conn_mock: MagicMock) -> tuple[QueryLog, EmailSnapshot]:
    queries = QueryLog()
    emails = EmailSnapshot()

    def fake_execute(sql: str, params: tuple):
        queries.record(sql, params)
        return []  # stub row result

    db_conn_mock.cursor.return_value.execute = fake_execute
    db_conn_mock.commit = MagicMock()

    with patch("smtplib.SMTP") as smtp_cls:
        mock_smtp = MagicMock()
        smtp_cls.return_value = mock_smtp
        mock_smtp.sendmail.side_effect = emails.capture_sendmail
        yield queries, emails
```

**Why a harness, not just mocks?** Because the harness captures *every* outgoing query and email instead of asserting individual calls. The golden master file is the serialized JSON blob from one run. Future runs fail the test if the JSON differs.
