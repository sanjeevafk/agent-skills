## Phase 0: Baseline & Guardrails (Days 1-2)

**Goal**: Create an unbreakable safety net before touching any production code.

### 0a. Characterization Tests via Golden Master

The core insight: you can't refactor what you can't measure. But you *can* characterize behavior by intercepting its outputs.

**Strategy: Test-Driven Development of the Refactor (TDDR)** — characterization tests first, then extract.

Characterization tests fall into three categories based on what OrderService touches:

#### Direct Unit Interception (No Mocks on Service Itself)

Since there are no tests today, I need to test the public API surface as-is. The key is to **parameterize real collaborators behind thin interfaces**, run the current system against realistic fixtures, and capture every observable output.

| What to Characterize | How |
|---|---|
| **Order state transitions** (create → validate → price → tax → persist → email → audit) | Pass fixture orders through `createOrder()` / `processOrder()` and assert final persisted state |
| **Validation rules** | Feed valid/invalid payloads; assert error types and messages match exactly |
| **Pricing logic** | Fixture with known line items, quantities, discounts; assert computed total matches expected |
| **Tax calculation** | Fixture by jurisdiction; assert tax amount, rate applied, tax code used |
| **Email side effects** | Intercept the mailer/sendGrid/SesClient at the constructor level; collect sent emails' recipients, subjects, bodies |
| **Audit log entries** | Query the audit table after each operation; snapshot row count + change deltas |
| **SQL queries executed** | Use `pg_stat_statements` or MySQL query log wrapper; record exact SQL text per method call |

#### Snapshotting SQL Side Effects

```python
class SqlCaptureMixin:
    """Drop-in replacement that records every query OrderService executes."""
    
    def __init__(self, delegate, captured_queries=None):
        self._delegate = delegate
        self._captured = captured_queries if captured_queries is not None else []
    
    def execute(self, sql, params=None):
        # Normalize whitespace for comparison stability
        normalized = ' '.join(sql.split())
        self._captured.append({'sql': normalized, 'params': params})
        return self._delegate.execute(sql, params)
    
    # proxy all other methods to _delegate
```

In the characterization test setup:

```python
def test_order_create_sql_determinism():
    original_db = order_service._db_connection
    captures = []
    order_service._db_connection = SqlCaptureMixin(original_db, captures)
    
    result = order_service.create_order(fixture_simple_order)
    
    # Assert SQL set is stable — next refactoring pass must reproduce it
    assert captures == golden_master['create_order_sql']
```

Store golden SQL in JSON fixtures alongside characterizing test inputs.

#### Snapshotting Email Side Effects

```python
class EmailCapture:
    """Intercepts send_email() calls, collects them for assertion."""
    
    def __init__(self):
        self.sent_emails = []
    
    def send(self, recipient, subject, body, **kwargs):
        self.sent_emails.append({
            'recipient': recipient,
            'subject': subject,
            'body': body,
            'headers': kwargs.get('headers', {}),
        })

# In test setup, replace the email collaborator:

```

The same approach applies for SMS notifications, Slack alerts, or webhook dispatchers.

#### What Not to Test

Don't write golden tests for:
- Internal helper methods (private implementation details)
- Third-party library internals
- Timing-related behavior (use clock abstraction instead)

### 0b. Execution Strategy for Tests

1. **Identify the public method boundary** — list every `public`/`@api` method on OrderService
2. **For each method, build one positive and one negative test case** using minimal realistic data
3. **Run the whole suite against the untouched 1,400-line class** — green = baseline locked
4. **Commit with message**: `test(characterization): lock order service behavior before refactor`
5. **Every subsequent commit runs this suite** — red = broken invariant, revert immediately

CI gate: this characterization suite MUST pass on every PR before integration tests even run.

## Phase 1: Seam Extraction Order

The extraction order follows **dependency minimization** — extract interfaces for collaborators that have the fewest callers first, so extracting others becomes trivially easy.

### Layered Dependency Map

Visualize the 1,400-line class as a graph. Based on your description:

```
┌─────────────────────────────┐
│         OrderService        │
│   (34 fields, direct SQL)   │
├─────────────────────────────┤
│ ┌──────────┐  ┌──────────┐ │
│ │Validator │  │ Pricing  │ │
│ │(pure fn) │  │(has rule │ │
│ └──────────┘  │ deps?)   │ │
├───────────────┼──────────┤ │
│ ┌──────────┐  ┌──────────┐ │
│ │ TaxCalc  │  │ Persist  │ │ ← DatabaseRepository
│ │(pure fn) │  │          │ │
│ └──────────┘  └──────────┘ │
├─────────────────────────────┤
│ ┌──────────┐  ┌──────────┐ │
│ │ Email    │  │ Audit    │ │ ← NotificationSender, AuditLogWriter
│ └──────────┘  └──────────┘ │
└─────────────────────────────┘
```

### Extract Sequence (Optimal Order)

| Step | Extract | Why First? | Effort | Risk |
|------|---------|------------|--------|------|
| **1** | `DatabaseRepository` (or `OrderGateway`) | Most invasive — direct SQL scattered everywhere. Few external callers besides OrderService itself. High blast radius but clear interface. | Medium-High | High (if wrong) |
| **2** | `NotificationSender` (unified email/SMS/webhook) | Pure interface, zero internal dependencies. Can swap implementations instantly. | Low | Low |
| **3** | `OrderValidator` (extract validation rules from inline checks) | Mostly pure functions. Easiest extraction because it's likely embedded conditionals. | Low | Very Low |
| **4** | `PricingEngine` | May depend on validator; extract after validator so pricing can receive validated input cleanly. | Medium | Medium |
| **5** | `TaxCalculator` | Usually pure function (input: item, jurisdiction → output: tax). Safe to extract once pricing is clean. | Low-Medium | Low |
| **6** | `AuditLogWriter` | Simple append-only; may share DB connection with step 1 (so do after DB repo is extracted). | Low | Very Low |

### Why This Order?

1. **Database first** gives us a clean `persistOrder(Order)` and `findOrderById(id)` — every other layer now talks to an interface, not raw SQL strings. This is the highest-risk move, but also the highest-reward: it isolates the most violation of single responsibility.

2. **Notifications second** is low-risk and gives a visible early win. The interface is dead-simple: `send(Notification)`. No branching logic needed inside the interface contract.

3. **Validator third** decomposes the most tangled inline `if` blocks across all methods. Once these are separate, the main flow methods read like a pipeline.

4. **Pricing fourth** often has domain-specific rules (promotions, bulk discounts, geo-rules). With validation cleaned up, pricing receives clean DTOs.

5. **Tax fifth** is the simplest domain logic — usually a lookup table or formula. Cleanest when pulled last because it depends on finalized pricing context.

6. **Audit last** because audit logging is a cross-cutting concern that should ideally use the repository interface (step 1) rather than raw DB connections.

## Phase 2: Incremental Strangler Steps

Each step ships as a mergeable change behind the existing public API. No customer-visible breaking changes ever.

### Strangler Step 1: Database Repository Boundary

```
Before:                          After:
OrderService                     OrderService
  ├─ _db.execute("SELECT...")     ├─ _db: DatabaseRepository  
  ├─ _db.execute("INSERT...")     │  └─ findOrderById(id) -> OrderDTO
  └─ _db.execute("UPDATE...")     ├─ _validator: Validator
                                   ├─ _pricing: PricingEngine
                                   ├─ _tax: TaxCalculator  
                                   ├─ _repository: DatabaseRepository  ← NEW
                                   │  └─ save(order), update(order)
                                   └─ _notifications: NotificationSender

Public API unchanged: createOrder(), processOrder(), cancelOrder()
```

**What changes inside**: All `_db.execute()` calls become `_repository.findX()` and `_repository.saveX()`. SQL moves into the repository implementation (initially still OrderService internals, then migrated out).

**Verification**: Characterization tests confirm the SQL executed is identical (via SqlCaptureMixin). If SQL differs, commit is reverted.

**Shippability**: The repository is injected via a default factory that wraps the old `_db` connection. Zero config change needed.

class PricingEngine:
    def compute(self, line_items: List[LineItem], promotions: List[Promotion]) -> PriceResult:
        subtotal = sum(item.price * item.quantity for item in line_items)
        discount = self._apply_promotions(subtotal, promotions)

### Module Dependencies (Directional — No Circular)

```
application → domain → ports → infrastructure
           ↗         ↖
    infrastructure ← ports
```

**Key rules enforced by static analysis** (e.g., `pytest-dependency-graph`, `deptry`, or `cyclonedx`):
- `domain` package imports NO infrastructure code
- `application` may import both `domain` AND `infrastructure` (for dependency injection)
- `infrastructure` only imports `ports` (interfaces), never concrete `domain` types beyond DTOs
- `tests/*` may break all rules (it's allowed to know everything)

## Behavior Preservation: Proof at Every Commit

### Guarantee Mechanism Stack (Layered Defense)

| Layer | What Catches | Automation Level |
|-------|-------------|------------------|
| **Golden-master characterization suite** | Any behavioral deviation in public API | CI-gated, runs on every commit |
| **SQL diff assertion** (SqlCaptureMixin) | Queries changed between runs | Included in characterization tests |
| **Email snapshot assertion** | Emails sent/to/body changed | Included in characterization tests |
| **Static analysis** (mypy/pylint) | Type regressions, lint violations | CI-gated |
| **Property-based smoke** (hypothesis/faker) | Edge-case regressions missed by fixtures | Nightly or PR gate |
| **Integration tests** (against test DB) | Real query correctness | Runs on staging deploy |

### The Core Assertion Loop (Per Commit)

```
Code Change (1 commit)
  → git add + git commit
  → pre-commit hook: format check + lint
  → CI runs:
      1. Characterization tests (must match golden master EXACTLY)
      2. Static analysis (type check, lint)
      3. Unit tests for newly extracted modules (greenfield coverage)
  → If ANY step fails: auto-revert suggested, PR blocked
```

### Proving Equivalence, Not Just "Green"

Passing tests isn't proof — it's evidence. For true equivalence:

1. **SQL fingerprint comparison**: Hash the sequence of normalized SQL parameters per method call. If `hash(new_sql_sequence) != hash(golden_sql_sequence)`, investigate the difference. A different query is OK if the result is semantically identical, but the hash check forces explicit reasoning about every deviation.

2. **Diff-first review**: PR template requires a section called "Behavior Diff" where the developer explicitly states what changed and why. If empty (claiming no behavioral change), the golden-master suite is the arbiter.

3. **Canary deployment**: After merging, route 5% of production traffic to the new code path while monitoring. Compare email send counts, order success rates, and latency p99 against the previous release window. Alert if any metric deviates > 1%.

### When You Know You're Done

The refactor is shippable when:
- [ ] Characterization suite passes with 0 deviations from golden master
- [ ] Each extracted module has > 80% test coverage independently
- [ ] OrderService orchestrator is < 150 lines

## Risk Register & Mitigations

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| Hidden coupling between inline helpers | Wrong seam → refactor reverts | Medium | Start with DB and notification seams (least coupled) |
| Email/SQL non-determinism (timestamps, UUIDs) | Golden master breaks on rerun | High | Exclude volatile fields from comparisons |
| Performance regression from abstraction layers | Latency increase | Low | Profile once, accept 1-hop delegation overhead (~microseconds) |
| Domain event ordering in multi-step flows | Business logic breaks silently | Low | Keep execution order identical to original sequential flow |
| Team impatience cuts characterization short | No safety net | High | Lock characterization as mandatory WIP1; manager signoff required |
