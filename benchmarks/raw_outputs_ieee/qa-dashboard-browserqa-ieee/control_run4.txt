# Analytics Dashboard QA — Staged Test Plan

## Pre-flight Setup

Before running anything, pin these three viewport configurations:

| Viewport | Width | User-Agent Simulation | DPR |
|---|---|---|---|
| Desktop | 1440×900 | `Mozilla/5.0 ... Chrome/126.0` | 1x |
| Tablet | 768×1024 | `iPad Pro` media query profile | 2x |
| Mobile | 390×844 | `iPhone 15` media query profile | 3x |

Run each stage against **all three viewports** sequentially, using Playwright device descriptors (no manual resizing).

```typescript
// playwright config snippet — add once if not present
import { devices } from '@playwright/test';

const viewports = [
  { name: 'desktop', ...devices['Desktop 1440'] },
  { name: 'tablet',  ...devices['iPad Pro 11'] },
  { name: 'mobile',  ...devices['iPhone 15'] },
];
```

Dark-mode flag: toggle via `@media (prefers-color-scheme: dark)` emulation or app-level class. Run each full stage twice — once per mode. That's 6 combinations total.

## STAGE 1 — Read-Only Smoke Crawl

**Goal:** Land on the dashboard URL and record every client-side symptom without interacting. No clicks, no input.

### Execution steps

1. **Navigate + wait-for-stable**
   - Open page at `/dashboard/analytics`.
   - Wait for `network-idle` (all XHR/Fetch done) AND `document.idle`.
   - Set a hard timeout of **15s**. If exceeded, fail immediately (page isn't loading).

2. **Console-error collection**
   - Capture all `console.error`, `console.warn`, `unhandledrejection`, and JS exceptions.
   - Allow-list known benign patterns (third-party widget SDK boot noise). Anything else is a **fail**.

3. **Network-failure audit**
   - Assert zero HTTP responses with status ≥ 400.
   - Verify all chart-data API calls return `{ code: 200, data: Array }` structure within 2s.
   - Check that CSS/JS bundles return gzip/brotli-compressed responses.

4. **Render snapshot**
   - Take a baseline screenshot at each viewport + dark/light combination (12 snapshots stored as `smoke/{viewport}-{mode}.png`).

### Pass / Fail

| Condition | Severity |
|---|---|
| Zero console errors (after allow-list) | BLOCKER |
| Zero HTTP 4xx/5xx | BLOCKER |
| All chart endpoints < 2s p95 | WARNING |
| First Contentful Paint > 2s | WARNING |

## STAGE 2 — Interaction Tests

**Goal:** Validate filter selection → chart update → table reflow → drill-down flow end-to-end.

### Filter row → chart update flow

```
Step 1: Click "Date Range" dropdown
Step 2: Select "Last 30 days"
Step 3: Click "Apply Filters"
Step 4: Assert:
  - Chart tooltip shows dates matching selected range
  - Table rows reflect same date range filter
  - Network log contains exactly ONE XHR with ?date_start=…&date_end=…
Step 5: Assert no new console errors
Step 6: Repeat with "This Quarter" and "Custom Range"
```

### Cross-filter interference

| Action | Expected |
|---|---|
| Select region="EMEA", then category="SaaS" | Both filters persist; chart shows EMEA ∩ SaaS |
| Reset region only | Category stays active; chart recalculates |
| Toggle all filters off | Dashboard returns to default (all regions, all categories) with original data |

### Drill-down

```
Step 1: On bar chart, click a specific bar segment
Step 2: Assert a modal/slide-over appears showing detail rows
Step 3: Assert URL updates (e.g. ?drilldown=bar:segment:3)
Step 4: Click "Back" or close button
Step 5: Assert URL reverts to previous state
Step 6: Assert chart returns to non-drilled state
```

### Edge-case interactions

| Scenario | Validation |
|---|---|
| Type invalid text into numeric filter field | Field rejects or clamps; no crash |
| Select date range where start > end | Inline error message; form does not submit |
| Rapidly click Apply while request pending | Debounces/cancels stale request; last selection wins |
| Resize window mid-request | In-flight XHR aborts; no memory leak |

## STAGE 3 — Visual Regression

**Goal:** Pixel-diff every view but mask out time-sensitive widgets so runs are comparable across days.

### Baseline capture

```bash
# One-time: seed baselines
npx playwright test --update-screenshots --grep="visual"
```

### Masking strategy

Masked selectors (these regions are replaced with a solid color before diff):

```css
/* Time stamps on charts */
chart-axis--datetime-labels
.drilldown-timestamp
[data-testid="updated-at"]

/* Live-updating counters */
.live-counter
.metric-kpi--sparking

/* User-specific avatars/names */
.user-avatar
.user-name-cell
```

Implementation (Puppeteer helper):

```javascript
function maskElements(page, selectors) {
  await page.evaluate((sels) => {
    sels.forEach(sel => {
      document.querySelectorAll(sel).forEach(el => {
        el.dataset.originalBg = el.style.backgroundColor || getComputedStyle(el).backgroundColor;
        el.style.setProperty('background-color', '#CCCCCC', 'important');
      });
    });
  }, selectors);
}
```

### Diff configuration

```javascript
// playwright visual-regression.config.ts
module.exports = {
  threshold: 0.001,       // 0.1% diff tolerance
  blur: 0.5,              // sub-pixel jitter margin
  masks: ['chart-axis--datetime-labels', '.live-counter', '.user-avatar', '.user-name-cell'],
  viewports: ['desktop', 'tablet', 'mobile'],
  modes: ['light', 'dark'],
};
```

### What gets compared

| Element | Include? | Reason |
|---|---|---|
| Chart area (excluding timestamps) | Yes | Core layout & rendering |
| Data table (excluding live user names) | Yes | Column alignment, truncation |
| Filter bar | Yes | State persistence |
| Sidebar navigation | Yes | Collapsed vs expanded states |
| Footer / legal text | No | Irrelevant to dashboard quality |

### Failure handling

Diff exceeding 0.1% → screenshot comparison shown inline in CI report. Developer must approve by re-running `--update-screenshots` on a green build.

## STAGE 4 — Accessibility Pass

### 4a — Color Contrast (WCAG AA minimum)

Audit computed contrast ratios for every text-on-background pair visible in both light and dark themes:

| Context | Minimum Ratio | Tool |
|---|---|---|
| Normal text (< 18pt) | 4.5 : 1 | axe-core `color-contrast` rule |
| Large text (≥ 18pt bold / ≥ 24pt normal) | 3.0 : 1 | Same |
| Chart label text | 4.5 : 1 (against its own background) | Manual spot-check via chromatic.js hex extraction |

Manual spot-check for chart colors (common failure point when palette shifts between themes):

```javascript
// verify chart labels against their backgrounds
const chartCanvas = await page.$('canvas.chart-renderer');
const ctx = chartCanvas?.context(); // use chromatic.js or canvas.toDataURL()
// Extract foreground hex vs legend-item background hex
// Assert ratio >= 4.5
```

### 4b — Focus Order & Keyboard Navigation

```
Step 1: Navigate to dashboard (mouse-free)
Step 2: Press Tab repeatedly through ALL interactive elements
Step 3: Assert focus ring visible on every tab stop (outline-width ≥ 2px)
Step 4: Assert logical order matches visual left→right, top→bottom:
        DateDropdown → RegionDropdown → CategoryDropdown → ApplyFilters
        → ChartArea (focusable container if clickable) → DataTable → Footer
Step 5: Enter key activates buttons; Space selects dropdown options; Escape closes them
Step 6: Verify focus trapping inside drill-down modal (Tab loops within it)
Step 7: Verify Escape closes modal and focus returns to triggering element
Step 8: Repeat entire sequence in dark mode (focus ring must remain visible)
```

No element should ever be reached via arrow-key navigation without also being reachable via Tab.

### 4c — ARIA Roles & States

Verify via axe-core programmatic checks + manual DOM assertions:

| Element | Required ARIA Attribute | Validation |
|---|---|---|
| Filter dropdown menus | `role="listbox"` | Each `<option>` has `role="option"` |
| Active filter chips | `aria-pressed="true"` | Toggling a chip flips the attribute |
| Chart (canvas/svg wrapper) | `role="img"` + `aria-label` | Label describes what chart shows |
| Chart tooltip popup | `role="tooltip"` | Appears only on hover/focus; hidden otherwise |
| Tooltip host element | `aria-describedby="<tooltipId>"` | ID references the tooltip div |
| Loading skeleton | `role="progressbar"` + `aria-busy="true"` | Removed when data loads |
| Empty-state message | `aria-live="polite"` | Screen readers announce it |
| Sortable column headers | `aria-sort="ascending\|descending\|none"` | Updates on click |
| Drill-down overlay | `role="dialog"` + `aria-modal="true"` | Backdrop traps focus |
| Alert/banner | `role="alert"` or `role="status"` | Appropriate urgency level |

Programmatic check (axe-core fixture):

```javascript
const results = await axe.run(page, {
  runOnly: ['cat.name', 'cat.keyboard', 'cat.color'],
});
const violations = results.violations.filter(v => v.nodes.length);
if (violations.length > 0) throw new Error(`A11y violations: ${violations.length}`);
```

## BLAST-RADIUS RULES (What Never Gets Clicked)

These paths and actions are **out of scope** and must never appear in test scripts. Touching them risks data corruption or external side-effects.

| Rule | Detail |
|---|---|
| 🚫 **No real user writes** | Do not POST/PUT/PATCH to `/api/users`, `/api/exports`, or any mutation endpoint |
| 🚫 **No financial transactions** | Never touch billing, invoicing, Stripe/webhook handlers, or payment APIs |
| 🚫 **No production email triggers** | Avoid unsubscribe links, newsletter toggles, notification preference saves |
| 🚫 **No admin operations** | Skip role changes, feature flags, database resets, cache clears |
| 🚫 **No third-party account linking** | Never authenticate to Google, Salesforce, Slack integrations |
| 🚫 **No OAuth consent screens** | Redirect URLs like `/auth/oauth/authorize` must not be visited |
| 🚫 **No file uploads/downloads** | Skipping CSV export buttons, image uploaders, PDF downloads |
| 🚫 **No webhook firing** | Leave any POST to `/api/webhooks/*` untouched (they call external systems) |
| ✅ **Safe zones** | GET-only data queries, dropdown selections that trigger read-only filtering, chart tooltips, visual regression captures, keyboard nav traversal |

If any test requires mutating state, use a **pre-seeded mock dataset** served by an API mock server instead.

## BASELINE STRATEGY FOR DARK MODE

Dark-mode testing needs special care because colors change between themes, which breaks naive pixel diffs and can introduce contrast bugs.

### Approach

```
1. Single codebase, dual-theme toggle
   - The dashboard uses a CSS class (.dark) or @media query on <html>
   - Playwright sets this BEFORE navigating: await page.emulateMedia({ colorScheme: 'dark' })

2. Dark-mode-specific baselines
   - Baseline images are stored separately: baselines/dark/ or baselines/light/
   - Never mix themes in the same baseline folder — diff will always fail

3. Contrast validation runs second after dark-mode screenshots
   - First capture baseline images with .dark applied
   - Then run axe-core color-contrast assertion on the same DOM
   - Any violation blocks sign-off even if the visual diff passes

4. Theme toggle interaction test (separate from regression)
   - Click the theme switcher component
   - Assert: page flashes briefly (acceptable), CSS custom properties update,
     chart colors shift, table background swaps, no broken borders/gradients
     appear during transition

5. Known visual differences that are ACCEPTED (do not diff):
   - Card elevation shadows darken slightly
   - Divider lines shift from #E5E7EB → #374151
   - Scrollbar track color changes
```

### Storage layout

```

├── smoke/
│   ├── desktop-light.png
│   ├── desktop-dark.png
│   ├── tablet-light.png
│   ├── tablet-dark.png
```

## EXIT CRITERIA — When We Sign Off

All conditions below must be true. No overrides.

| # | Criterion | Measured By |
|---|---|---|
| 1 | Zero BLOCKER severity issues across all 6 viewport×theme combos | Stage 1+2+3 reports |
| 2 | Console error count == 0 (post-allow-list) | Stage 1 automated log |
| 3 | All visual regressions ≤ 0.1% diff threshold (masked) | Stage 3 diff engine |
| 4 | All filter flows produce correct data in every viewport | Stage 2 assertions |
| 5 | Drill-down opens/closes cleanly with correct URL state in all 6 combos | Stage 2 assertions |
| 6 | Zero WCAG AA violations (contrast, keyboard, ARIA) | Stage 4 axe-core output |
| 7 | No forbidden blast-radius paths were triggered | Audit log review |
| 8 | All Lighthouse scores ≥ 90 on Performance, Accessibility, Best Practices | One run per mode |
| 9 | Dark mode toggle transitions without layout shift (CLS < 0.1) | Web Vitals metrics |
| 10 | Page load < 2s FCP at all viewports on simulated 3G throttling | Stage 1 timing |

### Decision matrix

```
Exit Criteria met? → YES → Sign off → Release ready
Exit Criteria not met? → Identify highest-severity blocker → Fix → Full regression re-run
                        (never cherry-pick fixes and skip unrelated stages)
```
