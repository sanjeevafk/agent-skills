# Analytics Dashboard QA Plan

## Prerequisites

Before any phase runs, confirm these gate checks:

- Target URL is staging/preview (never hit production for destructive paths)
- Test account credentials available in CI secrets (never commit them)
- Visual baseline repo configured (images stored under `test-baselines/<url-slug>/`)
- No active deployment mid-test (freeze during execution window)

---

## Blast-Radius Rules — What Never Gets Clicked

These boundaries protect data integrity during automated QA:

| Category | Rule | Rationale |
|---|---|---|
| **Destructive actions** | Never click Delete, Export to CSV/PDF, Send Invite, Approve/Reject workflows | Mutates real data |
| **Billing/monetization** | Never touch checkout flows, subscription toggles, payment webhooks | Financial liability |
| **External integrations** | Do not trigger Slack webhook sends, email digests, third-party API calls | Side effects in production |
| **Time-bound mutations** | Skip "Reset date range to last 90 days" if it triggers background re-aggregation jobs | Heavy server work |
| **Auth tokens** | Never screenshot pages after login until auth cookie/token is redacted from DevTools | PII/security |

**Hard rule:** All phases are read-only against the target URL unless the tester explicitly overrides with `--force-mutating` AND the URL contains `staging.` or `preview.` in the hostname.

## Phase 1: Smoke Crawl (Read-Only)

### Objective
Catch showstoppers before investing effort in interaction testing.

```
For each dashboard viewport (1440, 768, 390):

1. Navigate to dashboard root URL
2. Collect ALL console messages for 10 seconds post-load
   - Filter out known noise: Google Analytics (`https://www.google-analytics.com/collect`, `gtag.dataLayer`), Hotjar, Mixpanel, Segment
   - Classify remaining errors as CRITICAL (JS runtime error) or WARNING (deprecation, CORS preflight)
3. Intercept all network requests; flag any 4xx or 5xx
   - Whitelist: favicon.ico 404s, dead social meta-image links
   - Blacklist: API endpoint failures, chunk loads returning 404, font loading 500s
4. Capture above-the-fold screenshot at full page height for each viewport
5. Inject `web-vitals` library; report LCP, CLS, INP
   - Thresholds: LCP < 2.5s, CLS < 0.1, INP < 200ms (per web.dev recommendations, post-March 2024 FID deprecation)
```

### Smoke Pass Checklist

- [ ] Zero CRITICAL console errors
- [ ] Zero 4xx/5xx on API endpoints
- [ ] Above-the-fold renders at 1440px, 768px, 390px
- [ ] LCP ≤ 2.5s, CLS ≤ 0.1, INP ≤ 200ms on all viewports
- [ ] No unhandled promise rejections visible in console

### Exit Criterion for Phase 1
If ANY of the above fail → **HALT**. Log results, file bugs, do not proceed to Phase 2.

## Phase 2: Interaction Tests

### Objective
Verify filter logic, drill-down flows, and state transitions. These are still read-only against the default dashboard, but include one mutating journey (login → logout) using test credentials.

### Test Matrix

| Flow | Actions | Expected Outcome |
|---|---|---|
| **Filter — Date Range** | Set custom range (e.g., last 7 days) → Apply | Charts update, table refreshes, no stale data overlay |
| **Filter — Dimension** | Switch dimension dropdown (e.g., Platform → OS) | Chart series changes, label axis updates, tooltip reflects new dimension |
| **Filter — Combo** | Set date range + dimension + segment simultaneously | All three apply; no filter conflict UI bug |
| **Filter — Reset** | Click "Clear all filters" | Returns to default state; data matches fresh load |
| **Drill-Down — Chart** | Click a bar/column/donut slice in top chart | Detail panel slides in or navigates; breadcrumbs reflect path |
| **Drill-Down — Table** | Click a row value in metrics table | Opens detail sub-view with same filters applied; back button works |
| **Navigation** | Click sidebar nav items (Overview, Funnels, Retention) | Page navigates; filters persist where appropriate |
| **Dark Mode Toggle** | Click dark/light theme switch | Theme persists; all widgets render correctly in new mode |

### Implementation Notes (Playwright-style pseudocode)

```javascript
// Example: date range filter interaction
await page.setViewportSize({ width: 1440, height: 900 });
await page.locator('[data-testid="date-range-picker"]').click();
await page.locator('[data-testid="date-input-start"]').fill('2026-08-19');
await page.locator('[data-testid="date-input-end"]').fill('2026-08-26');
await page.locator('[data-testid="apply-filters"]').click();
await expect(page.locator('[data-testid="chart-container"]')).toBeVisible();
// Verify chart updated by checking DOM for new metric values
const chartMetrics = await page.locator('[data-testid="metric-value"]').allTextContents();
expect(chartMetrics).not.toEqual(staleMetricsSnapshot);
```

### Exit Criterion for Phase 2
All 8 flows pass. If any flow fails → file issue, fix, re-run blocked flows.

## Phase 3: Visual Regression

### Strategy

#### Baseline Management

- Store reference screenshots in version-controlled directory: `test-baselines/analytics-dashboard/{breakpoint}/{page}.png`
- Breakpoints: `desktop-1440.png`, `tablet-768.png`, `mobile-390px.png`
- First run against a clean deploy establishes the golden baseline (commit it, mark baseline=true in comparison config)
- If no baseline exists → verdict is **INCONCLUSIVE** (never silently pass)

#### Diff Configuration

| Parameter | Value | Rationale |
|---|---|---|
| **Pixel threshold** | 0.1% structural diff | Accounts for anti-aliasing variance between headless and rendered engines |
| **Masking regions** | Live clock widget, timestamp footers, real-time counters | Time-dependent content changes every frame |
| **Blur tolerance** | Sub-pixel blur disabled | We compare exact pixels; disable renderer blur |

#### Masking Pattern (CSS-based)

```css
/* Applied during screenshots only via --visual-test flag */
[data-mask="time-sensitive"],
.live-clock,
.realtime-indicator,
.timestamp-footer {
  visibility: hidden !important;
}
```

#### Screenshots Per Page

Take screenshots at all 3 breakpoints for each of these views:
1. Default overview (no filters applied)
2. After applying date range filter
3. After clicking into a drill-down detail view
4. Dark mode variant of each (see below)

### Dark Mode Baseline Strategy

```
For EACH page/view:
  1. Screenshot in light mode at all 3 breakpoints
  2. Toggle dark mode
  3. Wait 500ms for CSS transition to settle
  4. Screenshot in dark mode at all 3 breakpoints
  
Comparison rules:
  - Light-mode baselines are compared ONLY against light-mode runs
  - Dark-mode baselines are compared ONLY against dark-mode runs
  - NEVER compare light vs dark across runs (this is intentional design, not a regression)
  - Check for: inverted colors correct? images readable? overlay backgrounds opaque enough?
  
Manual spot-check:
  - Confirm WCAG contrast ratios hold in dark mode too (see Phase 4)
  - Flag any element that loses text legibility in dark mode
```

### Exit Criterion for Phase 3
Diff score ≤ 0.1% for all comparisons against committed baselines. Higher diffs flagged as visual regressions requiring review.

## Phase 4: Accessibility Audit

### Automated Pass (axe-core)

Run axe-core `wcag2aa` standards profile against each dashboard view:

```javascript
// Axe-core integration (via Playwright)
import axe from 'axe-playwright';

await page.evaluate(async () => {
  const results = await axe.run(document, {
    runOnly: ['wcag2a', 'wcag2aa'],
    // Tag filtering for our app structure
    ancestry: true,
    reporter: 'v2'
  });
  return JSON.stringify(results.violations);
});
```

Flag violations for:

| WCAG 2.2 AA Criterion | Focus Area for Dashboard |
|---|---|
| **1.4.3 Contrast (Minimum)** | All text must be ≥ 4.5:1 against its background; large text ≥ 3:1 |
| **1.4.11 Non-text Contrast** | Interactive chart elements, icons, borders ≥ 3:1 against adjacent colors |
| **2.1.1 Keyboard** | All filters, dropdowns, sort controls operable via Tab/Enter/Space/Arrow keys |
| **2.4.3 Focus Order** | Logical Tab order follows visual reading order (sidebar → filters → charts → tables) |
| **4.1.2 Name, Role, Value** | Chart elements expose accessible names via `aria-label` or role attributes |

### Specific Checks Beyond axe-core

axe-core covers ~30–40% of WCAG. Manual verification needed for:

1. **Chart Tooltips**
   - Open tooltip on hover → verify `role="tooltip"` present
   - Verify tooltip content is announced by screen reader (read aloud manually using NVDA/VoiceOver)
   - Verify tooltip closes on escape key press

2. **Table Accessibility**
   - Verify `<table>` has proper `<caption>` or `aria-label` describing what the table shows
   - Verify sortable column headers use `role="columnheader"` with sort direction ARIA attributes
   - Verify pagination controls have `role="navigation"` with labeled prev/next buttons

3. **Focus Indicators**
   - Tab through entire filter panel → verify visible focus ring on every interactive element
   - Minimum 2px outline or box-shadow equivalent; color must contrast ≥ 3:1 with surrounding background
   - No removal of `outline` without replacement

4. **Landmarks & Navigation**
   - `<main>` wraps dashboard content
   - `<nav>` or `role="navigation"` around sidebar
   - `<aside>` or `role="complementary"` for detail panels
   - No duplicate landmark roles on page

5. **Screen Reader Walkthrough**
   - Use VoiceOver (macOS) or NVDA (Windows) tab through the page
   - Verify each chart announces its type and current metric name
   - Verify filter controls announce their current selected state

### Exit Criterion for Phase 4
Zero violations for Critical/Medium severity WCAG 2.2 AA. Low-severity warnings documented but non-blocking.

## Overall Verdict Framework

| Condition | Verdict |
|---|---|
| All 4 phases pass, zero blockers | **SHIP** |
| Any low-severity WCAG warning OR minor visual diff < 0.1% that is cosmetic | **SHIP WITH FIXES** |
| Any Phase 1 failure (CRITICAL console error, 5xx responses, CWV > thresholds) | **DO NOT SHIP** |
| Any Phase 2 interaction flow failing | **DO NOT SHIP** until fixed and re-tested |
| Visual regression diff > 0.1% on any element other than masked areas | **REVIEW REQUIRED** (designer sign-off needed) |
| No visual baseline exists | **INCONCLUSIVE** (establish baseline first, then re-evaluate) |
