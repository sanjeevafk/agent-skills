## Analytics Dashboard QA Plan — Staged Browser Automation

### Target Scope

| Area | Components |
|---|---|
| Charts | Line/bar/area charts, heatmaps, donut charts, tooltips |
| Tables | Paginated data tables, sorting, inline editing, row expand |
| Filters | Date range picker, multi-select dropdowns, toggle groups, clear-all |
| Dark Mode | Full theme switch, persisted preference, chart color adaptation |

**Viewports:** 1440px desktop · 768px tablet · 390px mobile

---

### Phase 1 — Smoke Test (Read-Only Crawl)

**Goal:** Confirm nothing is catastrophically broken before touching any interaction.

```
Step  Action                                          Expected
───────────────────────────────────────────────────────────────────
1     Navigate to https://staging.example.com/dashboard 200 OK within 3s
2     Capture console logs                              Filter: analytics, gtag, fbq, hotjar → reject only errors from app bundles
3     Intercept network                                 Reject any 4xx/5xx except known stubs (/api/__health)
4     Screenshot above-the-fold @ 1440px                Render check — header, nav, first chart visible
5     Screenshot above-the-fold @ 390px                 No horizontal overflow, text readable
6     Run web-vitals audit                              LCP < 2.5s · CLS < 0.1 · INP < 200ms
7     Check initial dark-mode state                     Follows system preference or stored token
```

**Filters to ignore (noise):**
- `fonts.googleapis.com` loading failures
- `*.analytics.*` beacon post-failures
- Chrome extensions injecting scripts
- DevTools-polyfill warnings

**Exit gate:** If console has ≥1 critical error OR any route returns 5xx → STOP. Do not proceed to interaction testing.

---

### Phase 2 — Interaction Tests

#### 2A. Navigation & Link Integrity

```
For every clickable element in the nav bar and sidebar:
  Click → verify new URL matches expected route → screenshot → back
Count: total links clicked / successful navigations
Threshold: 100% non-broken-links (dead links are blockers)
```

#### 2B. Filter Interactions (Core Flow)

| Test | Action | Validate |
|---|---|---|
| **Date range** | Set "Last 30 days" | Table/chart reflect new date; URL params updated |
| **Multi-select** | Pick 3+ values in category dropdown | Chips render; count badge accurate |
| **Toggle group** | Switch metric from "Revenue" → "Sessions" | Chart re-renders with correct axis labels |
| **Clear all** | Click filter reset button | All filters revert to defaults; URL cleared |
| **Invalid combo** | Date end < start + zero items selected | Error banner renders (not a silent empty state) |
| **URL shareability** | After filtering, copy URL → paste in incognito | Identical filtered view loads |

#### 2C. Drill-Down Flows

| Flow | Steps | Verify |
|---|---|---|
| **Chart → detail** | Click a bar segment | Modal/sheet slides in; shows breakdown table |
| **Table → row expand** | Click "+" on a row | Expanded section reveals child rows |
| **Breadcrumb nav** | From drill-down page, click breadcrumb | Returns to filter state exactly as set |
| **Back button** | Browser back from drilled view | Filters preserved (don't reset) |

#### 2D. Sorting & Pagination

```
Click each column header twice (asc → desc)
  → verify aria-sort updates
  → verify dataset actually sorts
  → verify sort persists across pagination clicks
Click last page → verify no blank rows
Search input + filter combination → verify consistent results
```

### 🔒 Blast-Radius Rules

These actions are **NEVER** permitted during automated QA:

| Forbidden Action | Reason | Alternative |
|---|---|---|
| Submitting actual forms (export CSV, email report) | Mutates backend state | Simulate click → expect modal with "coming soon" |
| Triggering delete/discard actions | Destructive | Hover element → assert disabled icon |
| Modifying saved filters/views that other users depend on | Cross-user contamination | Use test-user-only workspace |
| Running queries that hit rate limits or cost money | Infrastructure impact | Cap at staging DB with synthetic data |
| Auth with production credentials | PII exposure | Seeded `qa-bot@staging.example.com` account only |
| Navigating away from `/dashboard/*` paths | Unknown blast radius | Restrict URL pattern to `https://staging*/dashboard*` |

**Opt-in mutation rule:** A mutating journey can only execute if:
1. URL is explicitly `staging.*` or `preview.*` (never `example.com` without subdomain qualifier)
2. You provide explicit verbal/text confirmation: "APPROVE MUTATION ON STAGING"
3. Sensitive fields are redacted from all screenshots/logs

### Phase 3 — Visual Regression

#### Baseline Strategy

```
Baseline storage location: benchmarks/checklists_v2/dashboards/visual/
Naming convention:   {page}_{viewport}_v{N}.png

v1 baselines are CREATED on first run → flagged INCONCLUSIVE until committed
On subsequent runs → diffed against committed baseline → PASS/FAIL determined
```

#### Masking Time-Dependent Widgets

Time-sensitive content must be masked before diff comparison:

| Widget | Masking Technique |
|---|---|
| Live timestamp counters | CSS class `.mask-live` → overlay with solid color matching background |
| Real-time activity feed | Replace top 3 items with `[activity-feed]` text placeholder |
| Dynamic numbers (users online, etc.) | Regex replacement: `/\d+,?\d+/g` → `#####` |
| Randomized seed data | Deterministic mock factory seeded by viewport size |

**Diff threshold:** 0.1% pixel difference allowed (accounts for anti-aliasing, font rendering). Anything above triggers a flag with diff report showing exact mismatched pixels.

#### Breakpoint Checklist

For **each** of these pages × viewports = ~15 snapshots per run:

| Page | 1440px | 768px | 390px |
|---|---|---|---|
| Main dashboard (all charts) | ✓ | ✓ | ✓ |
| Drill-down modal | ✓ (close after) | ✓ (close after) | ✓ (close after) |
| Filter panel open/collapsed | ✓ | ✓ | ✓ |
| Table full + expanded row | ✓ | ✓ | ✓ |
| Empty state (no data) | ✓ | ✓ | ✓ |
| Dark mode mirror of above | ✓ | ✓ | ✓ |

#### Dark Mode Baseline Strategy

```
Dark baselines live in a parallel directory: dashboards/dark_mode/
Same naming convention, same N index as light-mode baselines

Switch mechanism:
  1. Check localStorage('theme') — prefer user setting
  2. If null, match prefers-color-scheme media query
  3. Force toggle via JS: document.documentElement.setAttribute('data-theme', 'dark')
  
Validation:
  - Every light-mode snapshot has a corresponding dark-mode pair
  - Diff dark pair independently — never cross-compare light vs dark
  - Flag any element that inherits wrong colors (text bg ratio fails WCAG)
  - Chart palettes must shift: blue→cyan, red→pink, green→mint (design spec check)
```

#### Visual Failure Criteria

| Issue | Severity | Threshold |
|---|---|---|
| Layout shift > 5px between baseline and current | BLOCKER | Any |
| Element missing entirely | BLOCKER | Any |
| Overflow / clipped content | WARNING | Any |
| Color regression (wrong palette) | WARNING | Any |
| Text overlap or truncation | WARNING | Any |
| Pixel diff > 0.1% outside masked zones | INFO | Per-frame |

### Phase 4 — Accessibility Pass

#### Automated Scanning (axe-core injection)

Run axe-core on every page variant. Filter out false positives from third-party chart libraries (render canvas/SVG elements that need semantic fallbacks).

| Check | What to Validate |
|---|---|
| **Contrast ratios** | All text ≥ 4.5:1 normal, ≥ 3:1 large; check both light AND dark palettes |
| **ARIA roles** | `<figure>` wrapping chart has `role="img"` + `aria-label` describing what's shown; tooltip containers use `role="tooltip"`; tables have `role="grid"` or `role="table"` with proper `aria-rowcount` |
| **Focus order** | Tab through filter → chart → table should follow visual reading order (left→right, top→bottom) |
| **Keyboard nav** | All filters operable via Enter/Space; arrow keys navigate chart segments; Escape closes modals |
| **Screen reader landmarks** | `<main>`, `<nav>`, `<aside>` used correctly; chart area has descriptive label |
| **Interactive elements** | Buttons have `aria-pressed` when toggled; inputs have associated `<label>` (not just placeholder) |

#### Manual Checks (automated coverage is ~30-40%, insufficient alone)

```
□ Tab key end-to-end: focus ring visible on every interactive element? No traps?
□ VoiceOver / NVDA: read a chart title, verify tooltip content announced?
□ Zoom to 200%: dashboard usable without horizontal scroll?
□ Color-blind simulation (Deuteranopia): chart segments still distinguishable?
```

### Exit Criteria — Sign-Off Gates

All gates must pass to reach **SHIP**:

| Gate | Condition | Blocker if Failed By |
|---|---|---|
| **Smoke** | 0 critical console errors, 0 server errors, Core Web Vitals within thresholds | ≥1 critical error OR ≥1 5xx |
| **Navigation** | 100% nav links resolve to valid routes | ≥1 dead link |
| **Filter flows** | All 6 filter tests pass, URL shareable | Any filter doesn't update UI or breaks URL |
| **Drill-down** | Modals open/close correctly, state preserved on back | Lost filter state on navigation |
| **Visual regression** | Pixel diff ≤ 0.1% on ALL unmasked regions across all breakpoints | Shift > 5px OR missing element |
| **Dark mode** | Mirror baselines exist, no cross-contamination, contrast AA compliant | Missing dark baseline OR low-contrast text |
| **Accessibility** | 0 critical WCAG 2.2 AA violations, keyboard nav works | Any inaccessible interactive element |

### Verdict Matrix

```
SHIP                          → 0 blockers, ≤2 info/warnings, all exit criteria met
SHIP WITH FIXES               → 0 blockers, but fixable issues remain (logged with severity)
DO NOT SHIP                   → ≥1 blocker in any phase
INCONCLUSIVE                  → No visual baseline exists yet; visual regression cannot be scored
```

---

### Execution Notes

- **Run sequence:** Smoke → (exit gate?) → Interaction → (exit gate?) → Visual → Accessibility
- **Parallelization:** Each viewport can run its suite in parallel once smoke passes
- **Re-run on fix:** Only re-run the failing breakpoint/page, not the entire suite
- **Baseline commit workflow:** First run creates v1 → human review → git commit → all future runs are deterministic
- **Integration:** Pair with `/canary-watch` post-deploy to catch regressions in production traffic
