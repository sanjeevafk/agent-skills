# Systematic Debugging Analysis: Intermittent Test Suite Failures

## Evidence Summary

| Symptom | What it tells us |
|---------|------------------|
| Passes in CI | Environment or timing difference — not pure logic error |
| Fails ~3/240 tests intermittently | Low-probability race / environmental dependency per test |
| Reruns go green | Timing or environment-dependent; no persistent state corruption |
| Correlates with machine load | Async/scheduling race conditions |
| Correlates with developer timezone | Timestamp formatting depends on local TZ offset |

---

## Hypothesis Ranking (by Likelihood)

### Test 1 — Formatted Timestamp Assertion

**Rank 1 (95%): UTC-localization leak**
> The test asserts on a string like `2025-06-15 14:30:00` produced from `datetime.now()` or `strftime()` without explicit `.timezone.utc`. In CI the image runs as UTC. On a dev machine with `TZ=America/New_York`, the same moment formats to `09:30:00`. Assertion fails by exactly the TZ offset.

**Rank 2 (4%): Timezone-naive object treated as UTC**
> A naive datetime is passed to a formatter that assumes UTC. If `os.environ["TZ"]` differs, the interpretation shifts. Same fix territory.

**Rank 3 (1%): System clock drift**
> Unlikely — would cause consistent failures, not intermittent ones correlated with *timezone*.

---

### Test 2 — Async Worker Polling with `sleep(2)`

**Rank 1 (85%): Fixed-sleep polling is inherently racy under load**
> The test calls `worker.submit()`, then loops with `sleep(2); if done: break` for some max iterations. Under high machine load, task execution or IPC can take >2 seconds, so the loop exits before the worker finishes. Rerun with lower load → green. CI (lighter load) → green.

**Rank 2 (12%): Race on shared mutable result store**
> Two concurrent writes without synchronization, only visible when threads interleave at specific points. Load changes scheduling cadence, exposing the interleaving.

**Rank 3 (3%): Event loop starvation**
> The async worker never gets scheduled within the poll window because CPU-heavy processes starve it. Essentially #1 expressed in asyncio-specific terms.

---

### Test 3 — Dict Iteration Order Over Set of Fixture IDs

**Rank 1 (90%): Hash-randomized set iteration yields non-deterministic dict construction**
> Python seeds `PYTHONHASHSEED` randomly per-process (since Py3.3). Constructing `{k: v for k in some_set}` produces different insertion orders across runs. When downstream code relies on the first key or positional index, the assertion flaps.

**Rank 2 (8%): Fixture setup order non-deterministic due to set comprehension in pytest fixture generation**
> Similar mechanism: pytest iterates over a set when generating fixture variants, yielding different combinations across runs.

**Rank 3 (2%): Dictionary hashing collision edge case**
> Extremely rare; would fail every run once triggered, not intermittently.

def reproduce_timestamp_bug():

        os.environ["TZ"] = "America/New_York"

Key insight: this will fail **deterministically** once — proving TZ is the variable.

## Deterministic Fixes

### Fix 1 — Timestamp Comparison (Root Cause: TZ-Naive Formatting)

```python
# BEFORE (fragile)
def test_format_timestamp():
    dt = datetime.now()                    # ← naive, uses local TZ
    assert format_dt(dt) == "2025-06-15T14:30:00Z"  # ← hardcoded expected

# AFTER (deterministic)
from freezegun import freeze_time       # pip install freezegun
from datetime import timezone, datetime

def test_format_timestamp():
    with freeze_time("2025-06-15T14:30:00Z"):  # ← frozen wall clock in UTC
        dt = datetime.now(timezone.utc)          # ← always UTC
        assert format_dt(dt) == "2025-06-15T14:30:00Z"
```

**Why this works:** Freezes the clock to a known value and forces UTC. The formatter receives a timezone-aware UTC datetime → output is identical regardless of local TZ, machine load, or rerun count.

**Dependency:** `freezegun` (pin in `requirements-dev.txt`).

### Fix 2 — Async Worker Polling (Root Cause: Fixed Sleep ≠ Progress Check)

```python
# BEFORE (racy)
async def test_worker_completes():
    handle = await worker.submit(task)
    for _ in range(10):                   # 10 × 2s = 20s total budget
        await asyncio.sleep(2)            # ← blind wait; no progress awareness
        if handle.done:
            break                           # ← may exit too early under load
    assert handle.done                     # ← fails intermittently when load > delay

# AFTER (deadline-driven with jitter)
import random, asyncio

async def test_worker_completes():
    handle = await worker.submit(task)
    deadline = asyncio.get_event_loop().time() + 30.0  # generous budget
    while asyncio.get_event_loop().time() < deadline:
        await asyncio.sleep(random.uniform(0.5, 2.0))  # jitter breaks alignment
        if handle.done:
            return                                 # success path
    raise AssertionError("Worker did not complete within 30s")
```

If the worker itself exposes a proper `done` coroutine/event:

```python
# BETTER — use the API the worker already provides
async def test_worker_completes():
    handle = await worker.submit(task)
    await asyncio.wait_for(handle.result(), timeout=30.0)  # cancellation-safe
```

**Why this works:** Deadline-based waiting eliminates hard-coded alignment assumptions. Jitter prevents systematic lockstep with scheduler ticks. Using `asyncio.wait_for` (or similar blocking-wait primitive) removes the poll-loop entirely — the strongest fix.

### Fix 3 — Dict Iteration Order (Root Cause: Non-Deterministic Set Ordering)

```python
# BEFORE (non-deterministic)
@pytest.fixture(params={"task_A", "task_B", "task_C", "task_D"})
def task_id(request):
    return request.param                        # ← iterates over a set

def build_lookup(task_ids):
    return {tid: status for tid in task_ids}     # ← inserts in set-order

def test_lookup_consistency(build_lookup):
    keys = list(build_lookup.keys())
    assert keys[0] == "task_A"                  # ← position depends on hash seed
    assert keys.index("task_B") < keys.index("task_D")  # ← arbitrary ordering assumption
```

```python
# AFTER (sorted, stable order)
@pytest.fixture(params=["task_A", "task_B", "task_C", "task_D"])  # ← ordered list
def task_id(request):
    return request.param

def build_lookup(task_ids):
    sorted_ids = sorted(task_ids)         # ← explicit ordering
    return {tid: status for tid in sorted_ids}

def test_lookup_consistency(build_lookup):
    keys = list(build_lookup.keys())
    assert keys == ["task_A", "task_B", "task_C", "task_D"]  # ← exact comparison
```

If sorting isn't possible (e.g., data genuinely unordered):

```python
# Alternative: compare sets/multisets, not positions
def test_lookup_consistency(build_lookup):
    lookup = build_lookup
    assert set(lookup.keys()) == {"task_A", "task_B", "task_C", "task_D"}
    assert all(status in lookup.values() for status in expected_statuses)
```

**Why this works:** Lists preserve insertion order deterministically. `sorted()` produces stable ordering independent of hash seed. Comparing sets rather than positional lists sidesteps ordering entirely.

## Root Cause Summary Table

| Test | Symptom | Root Cause | Fix | Category |
|------|---------|------------|-----|----------|
| Timestamp assertion | String mismatch by exact TZ offset | Naive datetime in local TZ vs hardcoded UTC expectation | `freeze_time` + `timezone.utc` | Temporal |
| Worker polling | Timeout/race under load | Blind `sleep(2)` poll loop with insufficient budget | `asyncio.wait_for` with deadline | Concurrency |
| Dict order assertion | Flapping key order / position | Set → dict construction with hash-randomized iteration | Sorted keys / list params / set comparison | Determinism |

All three failures share a single underlying pattern: **relying on external non-determinism** (system timezone, OS scheduler timing, process-level hash seeds) instead of constraining them inside the test boundary.
