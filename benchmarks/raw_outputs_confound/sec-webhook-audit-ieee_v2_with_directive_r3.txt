I'll analyze the architecture-level vulnerabilities in the described webhook pattern and present a complete remediated implementation.

## Vulnerability Analysis (Ordered by Severity)

### 1. Signature Verification Happens After JSON Parsing — Resource Exhaustion (Critical)

The body is parsed before the HMAC is verified. An attacker sends thousands of malformed bodies, forcing expensive deserialization for each one. This is a cheap denial-of-service vector. The signature must be checked first using only the raw body bytes and the `X-Hmac-Signature` header.

### 2. In-Memory Replay-Id Dict — Data Loss & Concurrent Race Conditions (Critical)

- **Lost on restart**: A server restart wipes all seen event IDs, enabling full replay of every past webhook.
- **No atomicity under concurrency**: Two identical webhooks arriving simultaneously both pass the `event_id not in seen` check, then both process, defeating idempotency entirely.
- **Unbounded memory**: No eviction strategy means eventual OOM.

### 3. No Idempotency Guard for Concurrency (High)

Even with an in-memory set, there's no lock or atomic insert-or-check. Concurrent duplicate deliveries slip through. The real idempotency store must be the same durable ledger used by the processor itself, checked with a transaction or upsert.

### 4. Error Leaks / Stack Traces to Client (Medium)

A naive exception handler in FastAPI will propagate internal traceback, library names, or even DB connection strings to the HTTP client that triggered the webhook failure.

### 5. Clock Skew Not Accounted For HMAC Validation (Low)

Rotating secrets without a time-window tolerance makes legitimate deliveries fail during key rotation overlap windows.

    """Return hex-encoded HMAC-SHA256 of *body* keyed by *secret*."""
    return hmac.new(

class RotatingSecretStore:
    """Thread-safe rotating-hmac secret manager backed by the app database
    or an in-memory cache that is populated once at startup and refreshed
    via a configurable TTL.  In production this table should hold a
    ``current`` flag plus an ``expires_at`` column."""

    def __init__(self, current_secret_b64: str | None = None):
        # Accept a single bootstrap secret from env so the app starts
        self._current_secret: Optional[bytes] = (
            current_secret_b64.encode() if current_secret_b64 else None
        )
        self._history: list[tuple[bytes, datetime]] = []

    @property
    def active_secret(self) -> bytes:
        if self._current_secret is None:
            raise RuntimeError("No HMAC secret configured — set WEBHOOK_HMAC_SECRET_B64")
        return self._current_secret

    def activate_rotation(self, new_secret_b64: str) -> None:
        """Called at key-rotation time. Keeps the old secret alive for the
        skew window so in-flight deliveries are still verifiable."""
        if self._current_secret:
            self._history.append((self._current_secret, datetime.now(timezone.utc)))
        self._current_secret = new_secret_b64.encode()

    def try_all_secrets(self, body: bytes, expected_sig: str) -> bool:
        """Check the signature against the current secret and any recent
        historical secrets (within ROTATION_SKEW_SECONDS, default 300 s)."""
        skew_seconds: int = int(
            os.environ.get("ROTATION_SKEW_SECONDS", "300")
        )
        candidates: list[bytes] = [self.active_secret]
        cutoff = datetime.now(timezone.utc) - timedelta(seconds=skew_seconds)
        for secret_bytes, activated_at in reversed(self._history):
            if activated_at > cutoff:
                candidates.append(secret_bytes)

        for secret in candidates:
            actual = _hmac_hex("", secret, body)
            if hmac.compare_digest(actual, expected_sig):
                return True
        return False

    This runs BEFORE json() is called on the request, preventing
    deserialization DoS.

async def acquire_event_id(session: AsyncSession, event_id: str) -> bool:
    """Try to INSERT the event_id. On conflict returns False (already seen).

    Uses INSERT … ON CONFLICT DO NOTHING which is atomic at the DB level,
    solving the concurrent-race problem that the in-memory dict had."""

        INSERT INTO webhook_event_ledger (event_id, processor_status)
        VALUES (:eid, 'received')
        ON CONFLICT (event_id) DO NOTHING
    """)
    result = await session.execute(stmt, {"eid": event_id})
    return result.rowcount > 0  # True when we inserted, False on conflict

        text(
            "UPDATE webhook_event_ledger SET processor_status = :st, "
            "processed_at = now() WHERE event_id = :eid"
        ),
        {"eid": event_id, "st": status},
    )

@app.post("/api/webhooks/payment")
async def payment_webhook(request: Request):
    # ── Step 1: Read RAW body FIRST (no parsing) ──────────────────
    raw_body = await request.body()
    if not raw_body:
        raise HTTPException(status_code=400, detail="Empty request body")

    # ── Step 2: Verify HMAC BEFORE parsing → blocks deserialization DoS
    await verify_hmac(raw_body, request)

    # ── Step 3: NOW safe to parse (signature verified, trusted origin)
    try:
        payload = await request.json()
    except Exception:
        raise HTTPException(status_code=400, detail="Invalid JSON")

    event_id: Optional[str] = payload.get("event_id")
    if not event_id or not isinstance(event_id, str):
        raise HTTPException(status_code=400, detail="Missing or invalid event_id")

    # ── Step 4: Validate payload size early (cheap guard)
    if len(raw_body) > 1_048_576:  # 1 MB hard cap
        raise HTTPException(status_code=413, detail="Payload too large")

    # ── Step 5: Idempotency gate (DB-level atomic) ────────────────
    async with AsyncSessionLocal() as session:
        acquired = await acquire_event_id(session, event_id)
        if not acquired:
            # Duplicate delivery — already processed or being processed.
            # Return 200 to avoid processor back-off retries.
            LOG.info("Duplicate webhook event_id=%s — returning 200", event_id)
            return JSONResponse(status_code=200, content={"status": "already_processed"})

        try:
            # ── Step 6: Process the webhook ───────────────────────
            processor_result = await process_webhook_payload(payload)

            # ── Step 7: Mark successful ───────────────────────────
            await mark_processed(session, event_id, "processed")
            await session.commit()

        except ProcessorTimeoutError:
            await session.rollback()
            # Signal the processor to retry later
            raise HTTPException(status_code=503, detail="Processor unavailable — retry later")
        except Exception as exc:
            await session.rollback()
            # Log internally (handled by exception handler above)
            LOG.error("Webhook processing failed event_id=%s: %s", event_id, exc)
            # Still return 200 — the ledger record prevents infinite retries
            # while keeping our books accurate.
            return JSONResponse(
                status_code=200,
                content={"status": "processing_error"},
            )

    return JSONResponse(status_code=200, content={"status": "ok"})

## Key Design Decisions Explained

| Problem | Old Pattern | Fixed Pattern | Why It Matters |
|---|---|---|---|
| **DoS via deserialization** | Parse JSON → verify HMAC | Read raw body → verify HMAC → parse JSON | Malformed payloads never reach the parser |
| **Replay after restart** | In-memory `set()` | PostgreSQL `UNIQUE` constraint on `event_id` | Persistence survives crashes/restarts |
| **Concurrent duplicates** | Dict lookup then add (non-atomic) | `INSERT … ON CONFLICT DO NOTHING` (DB-atomic) | ACID guarantees exactly-one delivery |
| **Error leaks** | Raw exception → client | Generic `JSONResponse` + server-side `LOG.exception()` | Attackers get zero internal context |
| **Key rotation gaps** | Single static secret | `try_all_secrets()` checks current + history within skew window | Legitimate deliveries during overlap aren't rejected |
| **No input size guard** | Unchecked body | Hard 1 MB cap after HMAC verification | Cheap rejection of oversized payloads |
| **Secrets in code** | Hardcoded API keys | All via `os.environ` (`WEBHOOK_HMAC_SECRET_B64`, `DATABASE_URL`) | Compliant with standard practice |
