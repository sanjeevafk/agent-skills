## Test #1 — Asserts on a Formatted Timestamp

### Phase 1: Root Cause Investigation

**Trace data flow**:
```
datetime.now() ─→ strftime("%Y-%m-%dT%H:%M:%S") ─→ assert == "expected_format"
```

The timezone correlation is the smoking gun. `datetime.now()` returns wall-clock time in the *local* TZ. If the expected value was computed or written with UTC timestamps (or vice versa), assertions drift when the developer runs in a different offset. Under load, scheduling jitter pushes execution across minute/hour boundaries where `strftime` output changes.

CI uses Docker containers running in UTC (`TZ=UTC`) — hence it always passes.

**Evidence to gather**:
```bash
# Check if the test source embeds timezone assumptions
grep -n 'datetime\.\|timezone\|utc\|tzinfo' tests/test_something.py

# Check if CI sets explicit TZ
cat .github/workflows/*.yml | grep -i timezone || echo "No TZ override in CI"
```

### Phase 2: Pattern Analysis

Working example: a properly tested timestamp function freezes time:
```python
@pytest.mark.freeze_time("2026-01-01T00:00:00Z")
def test_timestamp_format():
    result = format_event_timestamp()
    assert result == "2026-01-01T00:00:00Z"
```

**Differences between broken and working code**:
- Broken: uses `datetime.now()` / `datetime.utcnow()` directly → depends on system state
- Working: freezes time via `timefreeze`, `pytest-time-machine`, or mocks

### Phase 3: Minimal Reproduction

Force the failure by setting a different timezone:
```bash
TZ=America/New_York python -m pytest tests/test_something.py::test_formatted_timestamp -v --tb=short
```

This will reproduce the failure deterministically if the timezone hypothesis is correct.

### Phase 4: Deterministic Fixes

**Fix A — Freeze time (production best practice)**:

**Fix C — In the production code itself (the real fix)**:
```python
# BEFORE (broken — timezone-sensitive):
def format_event_timestamp() -> str:
    now = datetime.now()  # ← Uses local TZ!
    return now.strftime("%Y-%m-%dT%H:%M:%S")

# AFTER (fixed — timezone-independent):
from datetime import datetime, timezone

def format_event_timestamp() -> str:
    now = datetime.now(timezone.utc)  # ← Always UTC
    return now.strftime("%Y-%m-%dT%H:%M:%SZ")  # Note trailing Z
```

## Test #2 — Polls an Async Worker with `sleep(2)`

### Phase 1: Root Cause Investigation

**Trace data flow**:
```
start_worker_async() 
  └→ sleep(2)  ← "wait enough?" (guesswork)
     └→ assert worker.done()  ← flaky: sometimes not done at t+2s under load
```

Under high machine load, context switches delay thread scheduling. A fixed `sleep(2)` assumes the worst-case latency is <2s. On a loaded dev box, the worker might need 3-4s. In CI (isolated, low load), 2s is sufficient.

The **machine load correlation** is definitive evidence here.

### Phase 2: Pattern Analysis

Working example: condition-based waiting, not timer-based:
```python
async def poll_worker_complete(worker, timeout=30.0, check_interval=0.1):
    deadline = asyncio.get_event_loop().time() + timeout
    while asyncio.get_event_loop().time() < deadline:
        if await worker.is_done():
            return True
        await asyncio.sleep(check_interval)
    raise TimeoutError("worker did not complete within timeout")
```

Key differences:
- **Broken**: Fixed sleep → magic number, breaks under load
- **Working**: Condition predicate + adaptive polling + hard timeout

### Phase 4: Deterministic Fixes

**Fix A — Replace `sleep(n)` with condition-wait + timeout (recommended)**:
```python
import asyncio
import pytest

@pytest.mark.asyncio
async def test_async_worker_completes_successfully():
    """Wait for worker completion using condition polling, not fixed sleep."""
    MAX_WAIT_SECONDS = 30
    CHECK_INTERVAL_SECONDS = 0.1
    
    worker = AsyncWorker()
    task = asyncio.create_task(worker.run())
    
    # Condition-based wait: poll the actual completion predicate
    deadline = asyncio.current_event_loop().time() + MAX_WAIT_SECONDS
    completed = False
    
    while asyncio.current_event_loop().time() < deadline:
        if task.done():
            completed = True
            break
        await asyncio.sleep(CHECK_INTERVAL_SECONDS)
    
    assert completed, f"Worker did not complete within {MAX_WAIT_SECONDS}s"
    assert not task.cancelled(), "Worker was unexpectedly cancelled"
    assert task.exception() is None, f"Worker raised: {task.exception()}"
    
    result = task.result()
    assert result.status == "success"
```

**Fix B — Use `asyncio.wait_for` (concise variant)**:
```python
import asyncio
import pytest

@pytest.mark.asyncio
async def test_async_worker_with_wait_for():
    """Use asyncio.wait_for instead of manual sleep/poll loop."""
    worker = AsyncWorker()
    task = asyncio.create_task(worker.run())
    
    # wait_for raises TimeoutError after the deadline — handle it explicitly
    try:
        result = await asyncio.wait_for(task, timeout=30.0)
    except asyncio.TimeoutError:
        task.cancel()
        pytest.fail(f"Worker did not complete within 30s timeout")
    
    assert result.status == "success"
```

**Fix C — Fix the production code if it exposes no completion signal**:
```python
# BEFORE (no way to know when done):
class AsyncWorker:
    async def run(self):
        # Does work, returns final result — but nothing else

# AFTER (exposes a status predicate for callers to poll safely):
class AsyncWorker:
    _status: str = "running"
    
    async def run(self):
        try:
            self._status = "running"
            await self._do_work()
            self._status = "success"
            return self._result
        finally:
            self._status = "completed"
    
    @property
    def is_done(self) -> bool:
        return self._status in ("success", "error", "cancelled")
    
    @property
    def status(self) -> str:
        return self._status
```

## Test #3 — Relies on Dict Iteration Order Over a Set of Fixture IDs

### Phase 1: Root Cause Investigation

**Trace data flow**:
```
fixture_ids = {"a", "b", "c"}          # ← SET (unordered!)
results = {fid: compute(fid) for fid in fixture_ids}  # ← Dict over set
assert results[list(results.keys())] == expected_list  # ← Implicitly relies on iteration order
```

**Key insight**: In CPython 3.7+, `dict` maintains insertion order. BUT — and this is critical — **sets do NOT have defined iteration order**. When you iterate a set to build a dict, the dict's iteration order becomes arbitrary. Python randomizes hash seeds for sets of strings via `PYTHONHASHSEED` (default: randomized per-process since Python 3.3).

This explains the **machine load correlation** too: heavier load means more variability in OS scheduling, which can interact with hash collision patterns that differ based on memory layout, allocator state, etc.

CI likely runs with `PYTHONHASHSEED=0` (deterministic), explaining why it always passes there.

### Phase 2: Pattern Analysis

Working example: sets must be explicitly sorted before iteration:
```python
fixture_ids = {"a", "b", "c"}
results = {fid: compute(fid) for fid in sorted(fixture_ids)}
```

**Differences**:
- Broken: iterates `set` directly → undefined order, hash-seed dependent
- Working: sorts the set first → deterministic iteration

### Phase 3: Minimal Reproduction

Force the failure by varying `PYTHONHASHSEED`:
