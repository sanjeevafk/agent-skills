## Vulnerabilities — Ordered by Severity

### 1. Signature Verification After Body Parsing (CRITICAL)

The endpoint parses `request.json()` *before* checking the HMAC-SHA256 signature. This gives an attacker free computation cycles and exposes the internal JSON-deserialization layer to unauthenticated input. Malformed payloads trigger parse errors and potentially leak stack traces, library versions, or validation rules. It also enables resource exhaustion attacks — the server pays the CPU/memory cost of parsing before knowing the request isn't genuine.

**Fix:** Verify the signature using only the raw body bytes (`await request.body()`) and the `X-Hmac-Signature` header *first*. Only after passing auth do you parse the JSON for business logic.

###

### 2. In-Memory Dict for Replay Protection (CRITICAL)

An in-memory `set()` / dict has four fatal flaws:

- **Volatile:** All state is lost on process restart, rolling deployments, or OOM kills. During the gap between restarts and cache-warming, every webhook arrives as "new" — creating duplicate charges.
- **Multi-process blind:** Behind any container orchestration (Kubernetes, Docker Swarm) each worker gets its own dict. Instance A accepts an event; instance B has no record and reprocesses it.
- **Unbounded growth:** No TTL, eviction, or size limit means eventual memory exhaustion. A single processor can fill your heap with garbage event IDs.
- **Race condition:** Even within a single process, two simultaneous requests with the same event ID can both check `if event_id not seen`, both pass, and both process. You need atomic "check-and-insert" semantics.

**Fix:** Use Redis (or PostgreSQL with a unique constraint) with a TTL and atomic `SETNX`-style insertion. For single-process development, still enforce idempotency via database constraints.

### 3. No Timestamp / Nonce Validation in HMAC (HIGH)

If the HMAC includes a timestamp but the endpoint never checks it, replay attacks remain feasible within the secret's rotation window. If no timestamp is included at all, the attacker has infinite replay time.

**Fix:** Require a `X-Timestamp` header. Reject anything outside a 5–15 minute skew window. Include it in the signed payload.

### 4. Missing Rate Limiting (MEDIUM)

Webhook endpoints have no built-in rate limiting. An attacker who discovers the endpoint URL can flood it with requests, causing CPU waste (signature verification per-request) and database churn from idempotency checks.

**Fix:** Apply IP-based and per-origin rate limiting before authentication. Stricter limits on paths that don't match expected patterns.

### 5. Error Leaking (MEDIUM)

Processor errors (e.g., DB connection failures, malformed event schemas, unknown event types) must not bubble into HTTP responses because they reveal internal architecture, schema expectations, or infrastructure details.

**Fix:** Catch all processing exceptions, log them internally with full context, and return a generic `500 Internal Server Error` to the caller. The third-party processor will retry, which is correct behavior on transient failures.

### 6. Missing Content-Type Validation (LOW)

Accepting arbitrary content types opens doors to deserialization surprises. Webhooks should expect `application/json`.

**Fix:** Validate `Content-Type: application/json` in middleware or at the start of the handler.

### 7. No Secret Rotation Grace Period (MEDIUM)

When the HMAC signing secret rotates, old secrets become invalid immediately, causing legitimate webhooks to fail during the transition window (especially if the processor caches connections).

**Fix:** Maintain a list of the current secret plus one previous secret. Accept HMACs verified against either. Clean up the old secret once all pending deliveries should have landed (typically 24–48 hours).

def verify_hmac_signature(raw_body: bytes, signature_header: str, timestamp: int) -> bool:
    """Verify HMAC-SHA256 signature over the raw request body.

    Expected header format:  "sha256=<hex_digest>"

    Also validates the timestamp falls within the allowed skew window
    to prevent indefinite replays.
    """
    if not WEBHOOK_SECRET:
        logger.critical("HMAC secret not configured — rejecting all webhooks")
        return False

    if not signature_header.startswith("sha256="):
        return False

    expected_signature = signature_header[7:]  # strip "sha256=" prefix

    # Build the message: timestamp + newline + body
    message = f"{timestamp}\n{raw_body.decode('utf-8', errors='replace')}"

    computed = hmac.new(
        WEBHOOK_SECRET.encode("utf-8"),
        message.encode("utf-8"),
        hashlib.sha256,
    ).hexdigest()

    # Constant-time comparison prevents timing attacks
    if not hmac.compare_digest(computed, expected_signature):
        return False

    # Check timestamp freshness
    now = int(time.time())
    if abs(now - timestamp) > WEBHOOK_TIMESTAMP_SKEW_SECONDS:
        logger.warning(
            "Timestamp skew exceeded: now=%d received=%d skew=%ds",
            now, timestamp, abs(now - timestamp),

        return False

    return True

## Architecture Summary — What Changed

| Concern | Before (Broken) | After (Fixed) |
|---|---|---|
| **Auth order** | Parse JSON → verify HMAC | Verify HMAC on raw bytes → parse JSON |
| **Replay protection** | In-memory dict (volatile, single-process, unbounded) | Redis `SETNX` with TTL (distributed, atomic, bounded) |
| **Concurrent dedup** | `dict.get()` check-then-set (race condition) | Atomic Redis `nx=True` (single operation, cross-process) |
| **Body size** | Unlimited | Configurable ceiling (default 64 KB) |
| **Timestamp validation** | None | Rejects messages older than configurable skew (15 min default) |
| **Secret rotation** | Single static secret | Current + previous secret support via env vars |
| **Content-Type** | Not checked | Must be `application/json` |
| **Error leakage** | Errors propagate to HTTP response | All caught; generic 500 returned; full context logged internally only |
| **Processing model** | Synchronous in handler | Async background task — fast acknowledgment, resilient processing |
| **Rate limiting** | Absent | Can be layered with a reverse proxy (nginx, Cloudflare) or FastAPI middleware |

## Additional Recommendations (Not in Code, But Needed)

1. **Rate limiting at the edge:** Place the webhook behind nginx, Cloudflare, or a service mesh rate limiter. FastAPI alone won't protect against IP-based flooding across multiple instances. Target: ~50 req/s per origin IP as a starting point.

2. **Dead-letter queue:** When `process_payment_event_safely` fails, the event is marked deduplicated (so retries won't re-engage) but never actually processed. Store failing events in a dead-letter queue (Redis list, SQS, Kafka topic) for manual inspection and replay.

3. **CORS configuration:** If this endpoint is ever hit from browser scripts (it shouldn't be), restrict origins. Better yet, ensure only the processor's IP ranges can reach it — configure at the firewall/VPC level.

4. **HTTPS-only:** Deploy behind TLS. Webhooks containing financial data must never traverse plaintext connections.

5. **IP allow-listing at the network layer:** Your cloud provider likely supports VPC peering or ingress IP restrictions. Layer this beneath the application to reduce attack surface.
