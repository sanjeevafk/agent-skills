# Systematic Debugging Analysis

## Phase 1: Root Cause Investigation

### Symptoms & Correlations

| Symptom | Likely Root Cause | Evidence |
|---------|-------------------|----------|
| Passes in CI, fails on dev machines | Environment difference | CI typically uses UTC; devs span many timezones |
| Fails correlate with machine load | Timing-sensitive code | Load increases latency, widening gaps in timing assumptions |
| Fails correlate with timezone | Time-dependent assertions | Wall-clock values differ between UTC (CI) and local TZ |
| Reruns usually go green | Race / non-determinism | Retry may cross a threshold (time, hash seed, completion) |

### Hypothesis Ranking

**H1 — Test 1: Formatted Timestamp Assertion Depends on Current Clock + Implicit UTC Assumption** ⭐ Most Likely
- CI runs in UTC (`TZ=UTC`)
- Dev machines run in their local timezone
- Code asserts `assert formatted == expected_string` where `expected_string` was computed once or hard-coded
- A single offset boundary (midnight, DST, or hourly edge) flips the result
- Machine load doesn't directly cause this, but pushes execution across the boundary → observed correlation

**H2 — Test 2: Async Worker Poll Uses `sleep(2)` Instead of Proper Await** ⭐ Very Likely
- `sleep(2)` is a blind wait — it neither detects early completion nor waits long enough when load increases latency
- Two failure modes: (a) worker hasn't finished when assert fires, (b) assertion fires twice because retry-loop uses `while True: ... sleep(2)` without bounded retries or event notification
- Directly explains load correlation

**H3 — Test 3: Dict Iteration Over a Set Has Non-Deterministic Order** ⭐ Certain
- Python sets have no defined iteration order; order is determined by hash seed (randomized by default since Python 3.3)
- Between test runs (or across dev machines with different seeds), iteration order can differ
- Explains why "reruns usually go green" — the same seed may repeat

**Ranking:** H1 > H2 > H3 (by frequency/intensity of correlation evidence)

## Deterministic Fixes

### Fix 1 — Freeze Time on the Timestamp Test

**Root cause:** The assertion compares a formatted timestamp produced at "runtime" against a value computed under a different time assumption. CI's UTC vs. local TZ shifts the wall-clock into a bucket where `.strftime('%Y-%m-%dT%H:%M:%S%z')` produces a different string.

**Strategy:** Freeze the clock to a deterministic point inside the test. Don't rely on `datetime.now()`. Use `freezegun` (lightweight, works with pytest) or `unittest.mock.patch`.

#### Broken Test (What It Looks Like)

```python
import datetime

def test_format_timestamp():
    """Formats the current timestamp — flaky because CI is UTC,
       developer machines use local TZ."""
    now = datetime.datetime.now(datetime.timezone.utc)
    # Expected was captured during development in a different TZ
    expected = "2025-01-15T00:45:00+00:00"  # captured at "midnight UTC"
    actual = now.strftime("%Y-%m-%dT%H:%M:%S%z")
    assert actual == expected
```

#### Fixed Test

```python
import datetime
from freezegun import freeze_time  # pip install freezegun

@freeze_time("2025-01-15 00:45:00+00:00")
def test_format_timestamp():
    """Timestamp formatting is deterministic when the clock is frozen."""
    now = datetime.datetime.now(datetime.timezone.utc)
    expected = "2025-01-15T00:45:00+00:00"
    actual = now.strftime("%Y-%m-%dT%H:%M:%S%z")
    assert actual == expected
```

**Why this works:** `freezegun.monkey_patch_datetime_classes()` redirects every call to `datetime.now()`, `time.time()`, etc., inside the decorated function. No TZ differences matter — the clock is pinned to exactly 2025-01-15 00:45:00 UTC.

**Alternative (stdlib only, no extra deps):**

```python
from unittest import mock
import datetime

def test_format_timestamp_stdlib():
    frozen = datetime.datetime(2025, 1, 15, 0, 45, 0, tzinfo=datetime.timezone.utc)
    with mock.patch.object(datetime, 'datetime', wraps=datetime.datetime) as mocked:
        mocked.now.return_value = frozen
        now = datetime.datetime.now(datetime.timezone.utc)
        expected = "2025-01-15T00:45:00+00:00"
        actual = now.strftime("%Y-%m-%dT%H:%M:%S%z")
        assert actual == expected
```

**Even better — decouple the test from `now()` entirely.** If the function being tested is `format_timestamp(dt)`, pass the datetime *in* rather than having the function call `now()`:

```python
# SUT (production code)
def format_timestamp(dt: datetime.datetime) -> str:
    return dt.strftime("%Y-%m-%dT%H:%M:%S%z")

# Test — zero dependence on current time
def test_format_timestamp_pass_in_dt():
    dt = datetime.datetime(2025, 1, 15, 0, 45, 0, tzinfo=datetime.timezone.utc)
    assert format_timestamp(dt) == "2025-01-15T00:45:00+00:00"
```

> **Preference:** Rewrite the SUT to accept a `dt` argument. This is the cleanest fix — no mocking, no extra dependencies, fully deterministic.

### Fix 2 — Replace `sleep(2)` with Event-Driven Polling (or `asyncio.wait_for`)

**Root cause:** The test polls an async worker using a blind `time.sleep(2)` (or `await asyncio.sleep(2)`) in a loop. Under low load, the worker finishes well within 2 seconds and the assertion passes. Under high load, the worker takes longer → assertion fires prematurely and fails. Conversely, if the loop has no upper bound, it may hang. Either way, the test outcome is a function of external factors.

**Strategy:** Use a proper bounded-polling loop with adjustable timeout and short check intervals, or — if the worker exposes an `asyncio.Event` / queue sentinel / future — await that signal directly.

#### Broken Test

```python
import time
import asyncio

async def test_async_worker_completes():
    handle = start_async_worker()  # starts background task
    # Blind wait — may be too short under load, or may hang forever
    time.sleep(2)
    assert handle.result_ready()
    results = await handle.get_results()
    assert len(results) > 0
```

#### Fixed Test — Bounded Polling

```python
import asyncio

async def test_async_worker_completes():
    handle = start_async_worker()

    # Poll with short interval and bounded total timeout
    deadline = asyncio.get_event_loop().time() + 10.0  # max 10 seconds
    poll_interval = 0.1  # check every 100 ms

    while asyncio.get_event_loop().time() < deadline:
        if handle.result_ready():
            break
        await asyncio.sleep(poll_interval)
    else:
        raise AssertionError("Async worker did not complete within 10 s")

    results = await handle.get_results()
    assert len(results) > 0
```

#### Fixed Test — Best Case (Await a Signal)

If the worker exposes any signaling mechanism, await it directly:

```python
import asyncio

class WorkerHandle:
    done_event = asyncio.Event()

    async def on_done(self):
        await self.done_event.wait()

async def test_async_worker_completes_signal():
    handle = start_async_worker()
    # Wait until the worker *actually* signals completion
    await asyncio.wait_for(handle.on_done(), timeout=10.0)

    results = await handle.get_results()
    assert len(results) > 0
```

**Key principle:** Never use blind `sleep` as synchronization. Always wait for a *signal* (event, future, queue message) or, if impossible, use bounded adaptive polling.

### Fix 3 — Replace Set with Sorted List for Ordered Iteration

**Root cause:** The test iterates over a `set` of fixture IDs and asserts on iteration order (e.g., `assert list(ids) == expected_ids`). Python sets have no guaranteed order — their iteration order depends on the internal hash table layout, which changes based on the process-level hash seed (`PYTHONHASHSEED`). CI runs with a fixed seed (often `0`); dev machines get random seeds via `PYTHONHASHSEED=random`. Different seeds → different orderings → intermittent failure.

**Strategy:** Convert the set to a sorted list (or an ordered container) so iteration order is deterministic regardless of hash seed. Alternatively, convert the assertion to a set-equivalence check if order shouldn't matter.

#### Broken Test

```python
@pytest.mark.parametrize("fixture_id", [{"fix-001", "fix-002", "fix-003"}])
def test_fixture_order_matters(fixture_id):
    # fixture_id is a set; iteration order is random
    ids = list(fixture_id)
    # This assertion assumes a specific order that only happens
    # to match when PYTHONHASHSEED lands on a particular value
    assert ids == ["fix-001", "fix-002", "fix-003"]
```

#### Fixed Test — Option A: Assert Unordered Equality (If Order Doesn't Actually Matter)

```python
@pytest.mark.parametrize("fixture_id", [{"fix-001", "fix-002", "fix-003"}])
def test_fixture_set_equality(fixture_id):
    ids = set(fixture_id)
    expected = {"fix-001", "fix-002", "fix-003"}
    # Membership check — order-independent
    assert ids == expected
```

#### Fixed Test — Option B: Sort Before Comparing (When Order Is Intentional)

```python
@pytest.mark.parametrize("fixture_id", [{"fix-001", "fix-002", "fix-003"}])
def test_fixture_ordered_comparison(fixture_id):
    ids = sorted(fixture_id)  # deterministic lexicographic order
    expected = ["fix-001", "fix-002", "fix-003"]
    assert ids == expected
```

#### Fixed Test — Option C: Use a Tuple/List in Fixture Definition (Preferred)

Don't use a `set` as the fixture value if you care about order. Define it as a tuple or list:

```python
@pytest.mark.parametrize(
    "fixture_id", [("fix-001", "fix-002", "fix-003")]  # tuple preserves order
)
def test_fixture_list_preserves_order(fixture_id):
    ids = list(fixture_id)
    expected = ["fix-001", "fix-002", "fix-003"]
    assert ids == expected
```

## Summary of All Fixes

| Test | Root Cause | Fix | Category |
|------|-----------|-----|----------|
| **Timestamp** | `datetime.now()` picks up the machine's timezone; CI runs in UTC, devs run in local TZ | Pass `dt` into the SUT; or freeze time with `@freeze_time(...)`. Prefer dependency-injection. | **Time** |
| **Async Worker** | Blind `sleep(2)` is a race — under load the worker exceeds the sleep duration | Replace with bounded polling loop (`poll_interval=0.1, timeout=10s`) or await a direct completion signal (`asyncio.Event`) | **Timing/Race** |
| **Fixture Order** | Iterating over a `set` has undefined order controlled by `PYTHONHASHSEED` | Use `sorted(set)` before comparison, or define the fixture as a `tuple`/`list` instead of a `set` | **Non-determinism** |
