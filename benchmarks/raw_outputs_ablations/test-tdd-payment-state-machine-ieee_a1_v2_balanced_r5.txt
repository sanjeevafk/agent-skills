### Domain Model Correctness

Transition table enforced by the code:

```
Draft      ──pending──► Pending ──activate──► Active ──past_due──► PastDue
                                                                      │         │
                                                                   resume      cancel
                                                                      ▼         ▼
                                                                   Pending  Canceled
Pending ────────────────────────cancel────────────────────────────────────┘         │
                                                                                   └──(terminal)
```

**CANCELED is a terminal sink state** — no outgoing transitions. Good design.

### Thread Safety

- `RLock` serializes all `transition()` calls — safe for concurrent producers
- Concurrent test verified: exactly one of two racing threads succeeds, the other gets `InvalidTransitionError` — confirmed stable across 5 runs with no deadlocks

### Design Patterns Used

1. **Domain Events**: `TransitionEvent(source, target, timestamp)` — frozen dataclass, timestamped at creation, appended to immutable history copy
2. **Configuration-over-code rules**: `_TRANSITION_RULES` and `_ACTION_TARGETS` are plain dicts (not classes/methods) — changing the lifecycle means editing data, not touching logic
3. **Reentrant lock (`RLock`)**: Allows re-entry by the same thread (defensive) without requiring caller coordination
