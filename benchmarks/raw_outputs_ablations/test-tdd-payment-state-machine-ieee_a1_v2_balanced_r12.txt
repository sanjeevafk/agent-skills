## Subscription Billing FSM — Implementation Review

### Architecture
The FSM at `skills/billing/fsm.py` is a **deep module** — a small public interface hiding significant complexity behind simple abstractions.

### States & Valid Transitions

```
DRAFT ──(pending)──> PENDING ──(activate)──> ACTIVE ──(past_due)──> PAST_DUE
   │                    │                                  │              │
   │                    ├──(cancel)──> CANCELED     ────────┘        │
   │                    │                                          │
   └──(X: rejected)                          (resume)──> PENDING ←┘
```

Key design decisions:
- **Active cannot cancel directly** — must flow through PAST_DUE first (real-world payment processing constraint)
- **Resume returns to PENDING, not ACTIVE** — requires payment verification, not instant reactivation
- **PAST_DUE cannot activate directly** — enforces the resume-first pattern

### Domain Event System

The `TransitionEvent` dataclass captures every state change with:
- Source/target state strings
- UTC timestamp
- Optional metadata dict (e.g., `{"reason": "grace_period_expired"}`)

Callbacks registered via `on_transition()` receive every event; `remove_transition_handler()` unregisters cleanly. History is exposed as an immutable copy (`list(self._history)`).

### Concurrency Model

Uses `threading.RLock` for serialization:
- Concurrent identical transitions: first wins, second observes new state and rejects
- Different actions from same state: serialized safely, no deadlock
- Reentrant property allows nested calls on same thread (e.g., handler-triggered transitions)

### Timeout System

`trigger_transition("auto_cancel", now=...)` enables external schedulers:
- Only applies to PENDING subscriptions
- Grace period configurable via `TIMEOUT_GRACE_PERIOD_SECONDS` (default: 24h)
- Before expiry: raises `InvalidTransitionError` with remaining seconds
- After expiry: cancels with `extra={"reason": "grace_period_expired"}`
