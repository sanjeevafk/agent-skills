## Architecture

**Transition graph (5 states):**
```
DRAFT →(pending)→ PENDING →(activate)→ ACTIVE →(past_due)→ PAST_DUE →(resume)→ PENDING
PENDING/PAST_DUE →(cancel)→ CANCELED  [terminal]
ACTIVE has no direct cancel — must flow through PAST_DUE first
```

**Key design decisions:**
- **Data-driven rules**: `_TRANSITION_RULES` maps actions to allowed source states; `_ACTION_TARGETS` maps actions to target states. Adding a new state or transition is just adding entries to these dicts.
- **Event-sourced history**: Every state change (including `__init__`) appends a `TransitionEvent` to an internal list. The public `history` property returns a copy.
- **Thread-safe**: `RLock` serializes all mutations. Concurrent racers are safe — one wins, the other sees the updated state and rejects.
- **Auto-cancel timeout**: `trigger_transition("auto_cancel", now=...)` checks elapsed time against a 24-hour grace period before allowing cancellation. Only applicable from PENDING.
- **Callback system**: `on_transition(handler)` / `remove_transition_handler(handler)` for event pub-sub. Handlers run independently — exceptions in one don't break others.
