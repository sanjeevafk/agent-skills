### Implementation (`skills/billing/fsm.py`) — Key Quality Points

**What's solid:**
- **Data-driven transition rules**: `_TRANSITION_RULES` maps action → allowed source states as `frozenset`s; `_ACTION_TARGETS` maps action → target state. Easy to extend without touching logic.
- **Thread safety via `RLock`**: Serialization on all transitions + callback registration. Race conditions handled (first wins, second sees new state and rejects).
- **Immutable history**: `history` property returns `list(self._history)` — callers get a copy. Mutation of returned list can't corrupt internal state.
- **Domain events**: `TransitionEvent` is an immutable `@dataclass(frozen=True)` with source, target, timestamp, and extra metadata dict.
- **Grace period enforcement**: `auto_cancel` only fires from PENDING after 24h elapsed, with precise seconds-remaining error messages.
- **Clean public API**: `SubscriptionStateMachine` exposes only `transition()`, `trigger_transition()`, `on_transition()`, `remove_transition_handler()`, `current_state`, and `history`.

**One minor observation:**
- `TransitionEvent.__repr__()` relies on default dataclass repr, producing `TransitionEvent(source='draft', target='pending')`. The test asserts `"draft"` is in the repr, which passes — but adding a `__repr__` with uppercase state names (like `DRAFT → PENDING`) would be cleaner. This is cosmetic, not functional.

### Architecture Pattern

This follows the deep module pattern well:
- **Simple interface**: 5 methods, clear semantics
- **Deep internals**: Data-driven rules, lock management, event publishing — hidden behind the public API
- **Behavioral tests**: Tests verify *what* happens (transitions succeed/fail), not implementation details (lock types, data structures)
