## Subscription Billing FSM — TDD Implementation Review

### Architecture

The FSM uses a **data-driven transition model** — rules are declarative dicts, not nested conditionals. Adding a new state or transition requires only adding entries to `_TRANSITION_RULES` and `_ACTION_TARGETS`.

```
DRAFT  ──pending──▶  PENDING  ──activate──▶  ACTIVE  ──past_due──▶  PAST_DUE
                                              │                              │
                                              │                              ├──cancel──▶ CANCELED ◀──────┘
                                              │                              │
                                              └──cancel──────────────────────┘
                                                    (also from PENDING)
```

### Public Interface

Tests verify through **public APIs only** — `transition()`, `trigger_transition()`, `history`, `current_state`, `on_transition()` — never internals. If you refactor the transition table to use an adjacency map, these tests still pass.

### Key Design Decisions

- **Thread safety**: `threading.RLock()` serializes all mutations. Race conditions produce one-wins-one-rejects semantics documented in the docstring.
- **Immutable events**: `TransitionEvent` is a frozen dataclass. History returns a copy (`list(self._history)`) so callers can't corrupt it.
- **Handler isolation**: Bad handlers log their error but don't crash subsequent handlers or the FSM. Tested explicitly.
- **No auto-timeout polling**: Timeout checks require explicit `trigger_transition("auto_cancel", now=...)`. The FSM itself doesn't self-trigger — external schedulers query `current_state` and decide when to call the trigger.
- **Grace period**: 86400 seconds (24h). Configurable constant `TIMEOUT_GRACE_PERIOD_SECONDS` for easy tuning.
