## Architecture Walkthrough

### Dockerfile — Four-Stage Build

**Stage 0 (base)**: Alpine with Node 22 + tini (PID 1 init) + ca-certificates. ~50MB baseline.

**Stage 1 (deps)**: Copies only `package.json` + `package-lock.json`, runs `npm ci`. This layer is cached unless manifests change — the most effective caching trick for monorepos where source changes frequently but dependencies don't.

**Stage 2 (builder)**: Copies full source tree, runs `next build --no-lint` (standalone output). Produces `./out/standalone/` containing:
- The Next.js server binary (`server.js`)
- Only the production node_modules it actually needs (dynamically analyzed via `moduleResolution: "bundler"`)
- `.next/static` assets

**Stage 3 (runner)**: Final image copies ONLY the standalone output from builder. Non-root user `appuser` (UID 10001), read-only filesystem, tmpfs mounts, tini entrypoint.

### Size Analysis

```
node:22-alpine          ~120MB   ← base stage alone (too big for production)
+ node_modules           ~150MB   ← deps stage (devDeps included)
+ source + build         ~200MB   ← builder stage
└───────────────────────────────────
standalone copy         ~70-90MB  ← runner stage (what actually ships)
+ tini + certs            ~5MB
= **~75-95MB total**        ✅ under 120MB target
```

The key savings come from Next.js standalone mode, which uses `require('next/dist/server/lib/router/utils/route matcher'). parseRoute()` to dynamically determine which modules the server actually loads at runtime, then prunes everything else from `node_modules`. Combined with Alpine Linux as the base, we stay well under 120MB.

### Security Hardening Summary

| Control | Where | Details |
|---------|-------|---------|
| Non-root user | Dockerfile `RUN adduser` | UID 10001, GID 10001, nologin shell |
| Capabilities dropped | docker-compose `cap_drop: [ALL]` | Zero capabilities by default |
| Capabilities added | docker-compose `cap_add: [NET_BIND_SERVICE]` | Only if needed for <1024 ports |
| Read-only root FS | Compose `read_only: true` | All three services hardened |
| Tmpfs mounts | Compose `tmpfs:` | `/tmp`, `/run`, cache dirs — noexec, nosuid |
| No-new-privileges | Compose `security_opt` | Prevents setuid/setgid escalation |
| Secrets injection | `env_file: .env` | Never committed; loaded at runtime |
| Network isolation | Two-tier network (`frontend-net` / `backend-net`) | DB/redis on internal-only subnet |

### Service Mesh / Networking

```
[External] → :3000 → frontend-net → [app] → backend-net → [db, redis]
                                             ↕
                                     (app bridges both tiers)

backend-net has internal: true → no internet access for db/redis
```

DB and Redis are only reachable by hostname (`db:5432`, `redis:6379`) from within the `backend-net` network. They're not routable from external networks or the frontend tier.

### Usage Commands

```bash
# Development (auto-loads override)
docker compose up --build

# Production
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build

# Inspect
docker compose ps
docker compose logs -f app
docker compose exec app sh          # Shell into running container

# Clean slate
docker compose down -v              # ⚠️ destroys all volume data
```

### Known Trade-offs & Recommendations

1. **`internal: true` on `backend-net`**: Prevents DB/Redis from making any outbound connections. This is correct for security but means database migration scripts that fetch packages from npm won't work inside the container. Run migrations externally.

2. **`app-data:/app/.next` named volume**: Persists the `.next` directory across restarts so incremental compilation survives. In stateless/container-orchestrated deployments (ECS, K8s), omit this and accept cold-start rebuilds for faster rollouts.

3. **No orchestration layer**: docker-compose is fine for single-host or small-scale setups. For production at scale, migrate to ECS, Kubernetes, or Docker Swarm where you get rolling updates, self-healing, and horizontal scaling.

4. **Postgres credentials**: The base compose uses `postgres/postgres` defaults. Set actual values in `.env` before production deployment:
   ```env
   POSTGRES_USER=myapp
   POSTGRES_PASSWORD=<use a strong random password>
   POSTGRES_DB=myapp_production
   DATABASE_URL=postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
   ```

5. **Next.js config prerequisite**: The `next.config.ts` (or `.js`) must include:
   ```typescript
   export default {
     output: 'standalone',
     // ... other config
   }
   ```
   Without `output: 'standalone'`, the builder stage produces nothing useful for the runner stage.
