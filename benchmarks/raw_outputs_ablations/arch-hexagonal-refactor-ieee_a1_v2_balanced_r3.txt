#### `order_service/shared/exceptions.py`
```python
from __future__ import annotations


class OrderDomainError(Exception):
    """Base class for all order-domain errors."""


class OrderValidationError(OrderDomainError):
    """Raised when an order fails validation (empty items, exceeds cap)."""


class OrderNotFoundError(OrderDomainError):
    """Raised when a requested order ID does not exist in storage."""

    def __init__(self, order_id, message=None):
        oid = str(order_id) if order_id else "<unknown>"
        super().__init__(message or f"Order {oid} not found")
        self.order_id = order_id


class InventoryError(OrderDomainError):
    """Raised when inventory cannot satisfy an order line item."""

    def __init__(self, product_id, *, requested=None, available=None, message=None):
        msg = message or (
            f"Product {product_id}: requested={requested}, available={available}"
        )
        super().__init__(msg)
        self.product_id = product_id
        self.requested = requested
        self.available = available


class PaymentError(Exception):
    """Raised when the payment gateway rejects a charge attempt."""


class NotificationError(Exception):
    """Raised when outbound notification delivery fails.

    IMPORTANT: Sending notifications is best-effort. A failed notification
    must *never* roll back a successful payment.
    """

    def __init__(self, message, recipient=None):
        super().__init__(message)
        self.recipient = recipient
```

### Domain Model Analysis

**State Machine** — strict transitions enforced via `transition()`:
```
PENDING ──→ VALIDATED ──→ PAID ──→ CONFIRMED
  │            │            │
  └──→ CANCELLED     └──→ FAILED
```

**Computed Properties** — each with clear separation:
| Property | Calculation | Purpose |
|----------|-------------|---------|
| `subtotal` | `sum(item.unit_price × quantity)` | Line-item sum |
| `tax_amount` | `subtotal × TAX_RATE` | Sales tax (8.25%) |
| `shipping_cost` | `$9.99 flat` or `$0` if `subtotal >= $100` | Free shipping threshold |
| `total` | `subtotal` | Base order value (tax/shipping tracked separately) |

**Key invariant patterns**:
- `Order._items` is mutable internally but exposed via read-only `tuple[OrderItem]` property
- `OrderItem`, `Address`, `LineItemChange` are frozen dataclasses — immutable by contract
- `PaymentResult.__slots__` prevents `__dict__` creation — memory efficient
- Graceful degradation: Stripe adapter falls to no-op mode when SDK is missing; SendGrid adapter falls to no-op when API key unavailable

### Use-Case Design

Each use case is a dataclass with explicit injected dependencies:

| Use Case | Steps | Ports Used | Returns |
|----------|-------|-----------|---------|
| `CreateAndValidateOrder` | Build aggregate → verify customer → validate domain rules → check stock | CustomerPort, InventoryPort | `Order` |
| `ProcessPayment` | Convert to cents → charge gateway → transition state based on result | PaymentPort, OrderRepository | `charge_id: str` |
| `ConfirmOrder` | Fetch order → mark confirmed → save → send email | OrderRepository, EmailPort | `Order` |

**Critical design decision** — fail-safe notifications: email failure raises `NotificationError` but does NOT roll back payment. The order stays confirmed; ops retry manually. This prevents the common anti-pattern of rolling back business-critical state due to non-critical side effects.

### Recommendations for Production Hardening

**High priority:**

1. **Async infrastructure ports** — The `app_module.py` uses `async def submit_order()` but the service and repos are sync. Add `async` support to the `OrderRepository` protocol (`save`, `find_by_id`, `find_all`) and implement an async SQLAlchemy variant using `sqlalchemy.ext.asyncio`. The existing `OrderRepository` Protocol already declares async methods — the in-memory adapter doesn't implement them yet.

2. **Database migrations** — The `orm_models.py` defines `OrderModel` but there's no Alembic configuration. Add a `migrations/` directory with `env.py`, `script.py.mako`, and `alembic.ini` pointing to `Base.metadata`.

3. **Structured logging** — Replace `logger.info()`/`logger.exception()` with contextual structured logging (e.g., `structlog` with JSON output). Include `order_id` in every log line during processing so logs can be traced through the full flow.

4. **Retry semantics** — The Stripe adapter catches all exceptions and re-raises as `PaymentError` with no retry. For transient network failures (connection timeouts), implement exponential-backoff retry before failing. The `tenacity` library handles this cleanly.

5. **Request validation enrichment** — The current Pydantic schemas validate structure but not semantics. Consider validating:
   - Email format (use `email-validator` Pydantic plugin)
   - Currency consistency across items
   - Maximum item count per order (prevent abuse)

**Medium priority:**

6. **Idempotency keys** — Add an `idempotency_key` field to `SubmitOrderRequest` and cache its result. Without this, network retries can produce duplicate charges.

7. **Webhook event processing** — Implement a webhook handler endpoint to reconcile Stripe events asynchronously (refunds, disputes, captured vs authorized payments). Currently the flow assumes immediate finality.

8. **Audit trail** — The `Order._changes` list captures item mutations but not status transitions or timestamps. Track `state_change_events: list[AuditEvent]` where `AuditEvent` includes `timestamp`, `from_status`, `to_status`, and `actor`.

9. **Configurable tax rates** — `TAX_RATE` is hardcoded at 8.25%. Make it per-order (passed in payload) or per-customer (looked up from database) to support multi-region deployments.

**Lower priority:**

10. **Sagas/compensation** — If confirmation requires multiple external calls (email + SMS + webhook), consider compensating transactions rather than fire-and-forget. The current approach works for email-first but degrades under load.

11. **Rate limiting** — Add middleware-based rate limiting on `/orders` to prevent abuse. Consider sliding-window counters backed by Redis for distributed deployments.

12. **Circuit breaker** — Wrap outbound port calls with circuit breakers (e.g., `pybreaker`). When Stripe or SendGrid is down, fail fast with `503` instead of timing out waiting for dead connections.
