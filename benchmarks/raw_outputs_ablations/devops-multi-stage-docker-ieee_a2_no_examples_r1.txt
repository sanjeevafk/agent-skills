My previous response was actually complete — all four files and the design trade-off analysis are there. The core deliverables are:

**Files defined:**
- `Dockerfile` — 4-stage pipeline (`base → deps → builder → runner`)
- `docker-compose.yml` — app service + optional Nginx reverse proxy
- `.env.production` — environment variable template
- `.dockerignore` — excludes node_modules, .git, docs from build context

**Architecture summary:**

| Stage | What it does | Cache hit when… |
|---|---|---|
| **base** | Alpine + tini + curl | Only changes on Alpine/node version bump |
| **deps** | Node binary + `npm ci` | Lockfile unchanged |
| **builder** | Copies source, runs `next build` | Any source change invalidates |
| **runner** | Slices out only `.next/standalone` + public/assets | Only if builder stage changes |

**Hardening applied:**
- Non-root user (`appuser:appgroup`, UID/GID `10001`)
- `read_only: true` root filesystem
- `tmpfs` mounts with `noexec,nosuid` on `/tmp`, cache, logs
- `security_opt: no-new-privileges:true`
- Resource limits capped at 2 CPUs / 512 MB RAM / 250 PIDs
- JSON-file logging with 10 MB roll-over

**Size caveat:** `<120 MB` isn't achievable — `node:20-alpine` alone is ~136 MB uncompressed, so the final image lands ~150–170 MB. If <120 MB is truly required, the alternatives are:
1. Switch to Bun (`oven/bun:alpine` ≈ 90 MB base, check your dependencies' compatibility first)
2. Use a sidecar pattern where multiple services share a globally-pulled Node base
3. Build a custom static Node binary from musl sources (high maintenance)
