## Design Review

**Architecture:** Clean domain model — three public types (`Status` enum, `Event` frozen dataclass, `TransitionError`) plus the single `StateMachine` class. Events are immutable records carrying `name`, `from_status`, `to_status`, and `timestamp`.

**State machine core:** A class-level `_TRANSITIONS` lookup dict maps `(status, event_name) → target_status`. `apply_event` performs an O(1) lookup, raises `TransitionError` on miss, and updates internal state under the lock. Simple, fast, extensible.

**Thread safety:** Every public method (`current_status`, `last_event`, `event_log`, `apply_event`, `trigger_timeout`) acquires `threading.Lock()`. Slice 5 confirms 10 concurrent threads only allow one successful transition — no corruption, no lost events.

**Timeout mechanism:** `pending_timeout` (default 1 hour) tracks entry time when entering PENDING. `trigger_timeout()` checks elapsed wall-clock time; if sufficient time has passed it emits a `timeout_activate` event moving to ACTIVE. Edge case handled: constructing FSM already in PENDING correctly seeds the timer rather than lazily zeroing it.

**What works well:** The transition map is data-driven — adding a new billing state requires one dictionary entry, not code changes. The frozen `Event` dataclass makes the log replayable. Error messages include the source status for debugging.

**Trade-offs:** The public interface exposes `event_log` as a snapshot tuple each read (copy-on-read pattern). Under very high throughput this adds allocation overhead but is appropriate for billing-state use where transitions are infrequent. For higher-performance scenarios you'd want a circular buffer or append-only sequence, but that would overcomplicate the current scope.
