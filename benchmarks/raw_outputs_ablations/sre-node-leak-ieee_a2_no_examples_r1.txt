## Phase 1 — Capture & Diff Heap Snapshots in Production Safely

### 1.1 Snapshot Collection Strategy

```bash
# Generate heap snapshot via SIGUSR2 (no restart needed; does NOT trigger GC)
kill -SIGUSR2 <PID>

# Node.js writes /tmp/heap.<TIMESTAMP>.heapsnapshot to the default temp dir
# Verify location overrides:
export NODE_OPTIONS="--heapsnapshot-signal=SIGUSR2"
```

To **safely automate** this without manual `kill`:

```js
// Add to your service startup (once):
'use strict';

let snapshotCount = 0;
const MAX_SNAPSHOTS = 5; // rotate early to limit disk pressure

process.on('SIGUSR2', () => {
  snapshotCount++;
  if (snapshotCount > MAX_SNAPSHOTS) {
    console.error('[memory] max snapshots reached, skipping');
    return;
  }
  const fs = require('fs');
  const path = `/app/heap-${Date.now()}-${snapshotCount}.heapsnapshot`;
  const writer = fs.createWriteStream(path);
  process.emitHeapSnapshot(writer);
  writer.on('finish', () => {
    console.error(`[memory] snapshot written: ${path}`);
  });
});
```

Inject via env var in your Kubernetes Deployment:

```yaml
env:
  - name: NODE_OPTIONS
    value: "--heapsnapshot-signal=SIGUSR2 --max-old-space-size=3500"
  - name: DEBUG_MEMORY
    value: "true"
```

Add a CronJob or Prometheus alert + webhook to fire `SIGUSR2` every 6 hours instead of relying on ad-hoc kills.

### 1.2 Safe Rotation & Storage

Snapshots can be 200–800 MB each. Without rotation, you fill `/tmp` and crash harder.

```js
// In the same module, add cleanup:
const CLEANUP_MAX_AGE_MS = 3600_000; // 1 hour
setInterval(() => {
  const dir = '/app';
  fs.readdir(dir, (err, files) => {
    if (err) return;
    files.forEach(f => {
      if (!f.startsWith('heap-') || !f.endsWith('.heapsnapshot')) return;
      const stat = fs.statSync(path.join(dir, f));
      if (Date.now() - stat.mtimeMs > CLEANUP_MAX_AGE_MS) {
        fs.unlinkSync(path.join(dir, f));
        console.error(`[memory] cleaned old snapshot: ${f}`);
      }
    });
  });
}, 30 * 60 * 1000); // every 30 min
```

Upload to object storage (S3/GCS) after writing, not just keep locally:

```bash
# Orchestrate with a sidecar or init container:
aws s3 cp /app/heap-TIMESTAMP.heapsnapshot s3://your-bucket/memleaks/
```

### 1.3 Diffing Snapshots

Use `clinic heap` (part of nearForm Clinic, zero impact), `chrome://inspect`, or the `heapsnapshot` npm package:

```bash
# Using chrome devtools:
# 1. open chrome://inspect → Profile → Take Heap Snapshot
# 2. Drag two .heapsnapshot files in
# 3. Compare → "Summary" mode → sort by "Shown Size" descending

# Using node built-in CLI (Node 20+):
npx clinic heap --node-options="--heapsnapshot-signal=SIGUSR2"
```

Sort by **"Retainers"** tab, not "Self Size." Self-size is misleading because it doesn't account for what's holding references. The retainer tree tells you *why* an object survives.

### 1.4 Supplement with Sampling Profiler

Before and during heap analysis, run the sampling profiler over a 10-minute window:

```bash
# Sample every 1ms (~1kHz) for 10 minutes while load tests the app
node --prof --print-all profile.log --log-node-events=all server.js &
NODE_PID=$!
sleep 600
kill $NODE_PID
node --prof-process profile.log > processed.txt
# Sort by callframes to see dominant allocation sites
grep -A50 'Top' processed.txt | head -100
```

This surfaces hot allocation paths that correlate with heap growth.

### 2.2 Programmatic Retainer Query

For automated, repeatable diagnostics, add this utility to your codebase temporarily:

```js
// lib/memory-diagnostic.js
'use strict';

const { registerInfo, finalize } = require('v8');

/**
 * Track all created objects by wrapper class so we can inspect finalization order.
 * Useful for confirming a leak vs normal GC pressure.
 */
const leakedObjects = [];
const tracker = new FinalizationRegistry((heldValue) => {
  leakedObjects.push({ ref: heldValue, time: Date.now() });
});

function trackForLeaks(label, obj) {
  tracker.register(obj, label);
  return obj;
}

```

Then wrap suspect object creations:

```js

// Instead of:  emitter.on('event', callback)
// Use:
const safeListener = trackForLeaks(
  `response-logger/${requestId}`,
  (res, data) => { /* original logic */ }
);
emitter.on('response', safeListener);
```

### 2.3 Targeting the Two Suspects

**Closures retained by event-emitter registry:**

In Chrome DevTools Memory panel:
1. Heap snapshot → Search bar: type `closure` → select all results
2. Right-click → **"Filter by retained size"** → Sort by **Shown Size (Descending)**
3. Pick the top-3 closures → open their **Retainers** tab
4. You will see a chain like: `Global → EventEmitter._events → [NamedFunction] → arguments`
5. If `_events[key]` contains functions whose closure scope includes `req`, `res`, or large response bodies, that's your leak.

**Buffers from response-logging middleware:**

Same flow, but filter by `JSBuffer` (or `Buffer`):
1. Search `JSBuffer` → sorted by retained size
2. Check retainer chains. Typical culprit: middleware pushes `{ raw: buffer, ... }` onto an in-memory array that never drains.
3. Look for arrays growing unbounded: `Array → [...] → Buffer[]` where Array has no consumer removing items.

## Phase 3 — Confirm Whether the Emitter Registry Leaks Listeners

### 3.1 Diagnostic Checklist

| Step | Command / Action | What It Proves |
|------|------------------|---------------|
| 3.1 | Count listeners per event: `emitter.listenerCount('key')` | Growing count = leak |
| 3.2 | Log emitter registry size periodically | Confirms timeline of leak |
| 3.3 | Replace `emitter.once` → verify cleanup | Tests hypothesis that `.on()` should be `.once()` |
| 3.4 | Add `removeAllListeners()` at request lifecycle end | Observes if memory stabilizes |
| 3.5 | Enable debug flag: `NODE_DEBUG=events,node:buffer` | Shows internal events tracking |

### 3.2 Listener Audit Code

Drop this into your service temporarily:

```js
// lib/listener-audit.js
'use strict';

const { EventEmitter } = require('events');
const origOn = EventEmitter.prototype.on;
const origEmit = EventEmitter.prototype.emit;
const origRemove = EventEmitter.prototype.removeListener;

const activeListeners = new Map();
let auditInterval = null;

function getRegistryKey(emitter) {
  const id = emitter[kId] || (emitter[kId] = ++counter);
  return id;
}

let counter = 0;
const kId = Symbol('_auditId');

EventEmitter.prototype.on = function (...args) {
  const key = args[0];
  const listener = args[1];
  const regId = getRegistryKey(this);
  const entry = activeListeners.get(regId) || { map: new Map(), emitter: this };
  entry.map.set(listener, { event: key, registeredAt: Date.now(), stack: new Error().stack });
  activeListeners.set(regId, entry);
  return origOn.apply(this, args);
};

EventEmitter.prototype.removeListener = function (...args) {
  const listener = args[1];
  const regId = getRegistryKey(this);
  const entry = activeListeners.get(regId);
  if (entry) entry.map.delete(listener);
  return origRemove.apply(this, args);
};

/** Call this in a periodic interval */
function runAudit() {
  for (const [regId, entry] of activeListeners) {
    if (entry.map.size === 0) continue;
    // Report listeners that were registered but never removed
    for (const [listener, meta] of entry.map) {
      console.error(
        `[listener-audit] REGISTRY LEAK suspected: emitter[${regId}] event="${meta.event}" ` +
        `listener=${listener.name || '<anonymous>'} age=${Date.now() - meta.registeredAt}ms`
      );
    }
  }
}

module.exports = { runAudit, startAudit: (intervalMs = 30_000) => {
  auditInterval = setInterval(runAudit, intervalMs);
}};
```

### 3.3 Emission Timeline Correlation

Create a histogram showing listener count vs. time:

```js
// In your main service file:
const { startAudit } = require('./lib/listener-audit');
startAudit(30_000); // every 30 seconds

// Additionally, wire Prometheus metrics:
prometheus.register.gauge('emitter_listener_count', 'Number of registered listeners').labels('event');
```

If listener counts grow monotonically without ever decreasing, the leak is confirmed. If they plateau or fluctuate, the issue may be elsewhere (e.g., closures captured accidentally but eventually collected).

### 3.4 Quick Fix Test

Temporarily patch the suspected emitter usage with `.once()` or explicit cleanup:

```js
// BEFORE (suspected leak):

// AFTER (test fix):
emitter.once('response', handleResponse);
// OR
const handler = function handleResponse(data) { /* ... */ };
emitter.on('response', handler);
req.on('close', () => emitter.removeListener('response', handler));
```

Run a 4-hour load test. If RSS stabilizes, you've identified the root cause.

## Phase 4 — Likely Root Causes & Fixes

### 4.1 Root Cause A: Event Emitter Listener Leak

**Pattern:** An Express middleware or controller registers listeners with `.on()` (not `.once()`) for events like `response`, `finish`, `end`, `error`, but never calls `removeListener()`. Each incoming request adds a new listener that captures `req`/`res` in its closure scope. Over thousands of requests per hour, listeners accumulate.

```js
// ❌ LEAK — listener accumulates across requests
app.use((req, res, next) => {
  bus.on('metrics', (data) => {
    // Closure captures req and res (entire request/response objects!)
    data.method = req.method;
    data.url = req.url;
    bus.emit('collect', data);
  });
  next();
});

// ✅ FIX — use .once() if firing once, or explicit removal
app.use((req, res, next) => {
  const handler = (data) => {
    data.method = req.method;
    data.url = req.url;
    bus.emit('collect', data);
  };
  bus.once('metrics', handler);
  res.on('finish', () => bus.removeListener('metrics', handler));
  next();
});
```

**Why it escalates to 4 GB:** Each listener closure holds references to `req` (query params, body) and `res` (headers, writeHead state). At 10k RPS over 48 hours, that's hundreds of millions of listener instances. V8's GC cannot collect closures whose functions still exist in `EventEmitter._events[eventName]`.

### 4.2 Root Cause B: Response-Logging Middleware Buffer Accumulation

**Pattern:** A middleware captures full HTTP response bodies into an array of Buffers for logging/tracing, but the array only appends — it never trims, rotates, or expires entries.

```js
// ❌ LEAK — unbounded log buffer
const responseLog = [];
app.use((req, res, next) => {
  const originalEnd = res.end.bind(res);
  res.end = function (chunk, encoding) {
    // Stores entire response body buffer in perpetuity
    responseLog.push(Buffer.from(chunk, encoding));
    if (responseLog.length > 1000000) { /* never reaches this */ }
    return originalEnd(chunk, encoding);
  };
  next();
});

// ✅ FIX — bounded ring buffer with size cap
const MAX_LOG_ENTRIES = 1000;
const ringBuffer = [];
let head = 0;

app.use((req, res, next) => {
  const originalEnd = res.end.bind(res);
  res.end = function (chunk, encoding) {
    if (ringBuffer.length >= MAX_LOG_ENTRIES) {
      ringBuffer[head % MAX_LOG_ENTRIES] = { chunk: Buffer.from(chunk, encoding), ts: Date.now() };
    } else {
      ringBuffer.push({ chunk: Buffer.from(chunk, encoding), ts: Date.now() });
    }
    head++;
    // Also flush to async sink (winston/pino/File) instead of keeping in memory
    return originalEnd(chunk, encoding);
  };
  next();
});
```

Or better yet, stream logs to disk/instrumentation backends instead of buffering in-memory.

### 4.3 Root Cause C: Combined Effect

When both patterns coexist, they compound: each closure stored in the emitter registry *itself* holds a reference to one of those buffered responses (because the logger middleware closure captures the response body). So even if you fix one, the other continues leaking.

```
retainer chain:
  Global (root)
    └── EventEmitter._events["response"] (array)
          └── anonymous closure (from middleware A)
                ├── captures `req` (Request object, ~10 KB)
                ├── captures `res` (Response object, ~50 KB)
                └── closes over `responseLog` (Array[Buffer])
                      └── Buffer[0] = 500 KB response body
                      └── Buffer[1] = 500 KB response body
                      └── ...
                      └── Buffer[N] = 500 KB response body
```

Both must be fixed simultaneously.

### 4.4 Definitive Fix Checklist

| # | Action | Priority |
|---|--------|----------|
| 1 | Replace all `.on(event, fn)` inside request handlers with `.once()` or tracked `.on()` + explicit `.removeListener()` on response finish/request close | CRITICAL |
| 2 | Cap response-log buffer to N entries (ring buffer, LRU) or stream to async logger | CRITICAL |
| 3 | Add `res.on('close', handler)` cleanup for any lingering event bindings per-request | HIGH |
| 4 | Set `NODE_OPTIONS="--max-old-space-size=3500"` as a soft ceiling so K8s OOM-Kill gives you time (not instant kill) | MEDIUM |
| 5 | Deploy `--inspect` with healthcheck endpoint `/debug/heap` that triggers snapshots via `process.emitHeapSnapshot()` | MEDIUM |
| 6 | Add Prometheus gauge `jemalloc_allocated_bytes` or `process.memoryUsage().rss` with alert at 2 GB (before OOM) | MEDIUM |
| 7 | Run nightly load test with heap profiling enabled to validate the fix persists under sustained traffic | LOW |
