## Review: Subscription FSM Implementation

### Architecture
The design follows a proper **deep module** pattern:
- **Simple interface**: `transition(action) → TransitionEvent` — one method, clear contract
- **Deep internal complexity**: validation rules + concurrency control hidden behind that single method
- Domain event (`TransitionEvent`) is immutable (`frozen=True` dataclass), preventing mutation after the fact
- Custom exception (`InvalidTransitionError`) extends `ValueError` with context-rich messages

### Public API Surface
```python
SubscriptionState   # str Enum: DRAFT, PENDING, ACTIVE, PAST_DUE, CANCELED
TransitionEvent     # frozen dataclass: source, target, timestamp
InvalidTransitionError  # custom exception
SubscriptionStateMachine  # core FSM with transition(), state, history, current_state
```

All 24 tests exercise behavior through this public surface only — they read like specs:
- `"user can checkout with valid cart"` equivalent: `test_full_chain_draft_to_active` chains `pending → activate`
- `"invalid input rejected"` equivalent: `test_rejects_cancel_from_draft` verifies rejection via exception
- Concurrent race condition: `test_concurrent_races_on_active_to_past_due` ensures exactly one wins

### Thread Safety
Uses `threading.RLock()` inside the FSM. The RLock handles nested calls (same thread) while serializing concurrent access. Tests confirm:
- Exactly one thread succeeds in a race (line 175-178)
- No deadlocks under contention (lines 206-208, 232-234)
