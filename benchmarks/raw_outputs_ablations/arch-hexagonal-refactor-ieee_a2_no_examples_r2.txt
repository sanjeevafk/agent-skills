## Code Review: `order_service_refactor` — Issues & Improvements

### Architecture Overview

The codebase is a partially-refactored attempt to move from a monolithic FastAPI service into Hexagonal (Ports-and-Adapters). It has:
- **Domain layer**: models, events, errors
- **Ports layer**: inbound requests/responses + outbound gateway interfaces
- **Application layer**: use-case orchestration
- **Infrastructure layer**: SQLAlchemy adapter, Stripe adapter, SendGrid adapter, API routes

The core intent is sound, but there are serious problems preventing this from being production-ready.

### CRITICAL ISSUES (Block Production)

#### 1. Domain Events Are Defined Twice in Two Incompatible Formats

`domain/models.py` defines `OrderSubmitted`, `PaymentCompleted`, `PaymentFailed`, `OrderShipped`, `OrderCancelled` as simple frozen dataclasses with only an `occurred_at` field.

`domain/events.py` redefines them with richer fields (`attempt_number`, `estimated_delivery_date`, `refund_amount_cents`, `InventoryReserved`) and adds a non-frozen base class with `__post_init__`.

Worse, `events.py` imports `Money` from `models.py` but then defines `DomainEvent` as **non-frozen** while all subclasses are frozen — this violates Python dataclass inheritance rules. The `DomainEvent.__post_init__` reference to `uuid.uuid4()` runs at class definition time, not per-instance.

**Fix needed:** Pick one location (preferably `events.py`) and define domain events consistently. Make the base class a proper ABC or protocol rather than mixing `dataclass(frozen=True)` with `__post_init__`:

```python
# events.py — single source of truth
import uuid
from dataclasses import dataclass, field
from datetime import datetime, timezone
from typing import ClassVar

@dataclass(frozen=True)
class DomainEvent:
    event_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    occurred_at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))

@dataclass(frozen=True)
class OrderSubmitted(DomainEvent):
    order_id: uuid.UUID
    customer_email: str
```

Then delete `models.py`'s event definitions entirely and import from `events.py` everywhere.

#### 2. Money.from_dollars Uses Float Multiplication (Rounding Bug)

```python
# models.py line 26
@classmethod
def from_dollars(cls, dollars: float, currency: str = "USD") -> Money:
    return cls(amount_cents=round(dollars * 100), currency=currency)
```

This is a textbook floating-point precision bug. `from_dollars(19.99)` produces `1998` cents instead of `1999`. Use `Decimal`:

```python
@classmethod
def from_dollars(cls, dollars: float | Decimal, currency: str = "USD") -> Money:
    if isinstance(dollars, float):
        dollars = Decimal(str(dollars))
    return cls(amount_cents=int(dollars * 100), currency=currency)
```

#### 3. grand_total Accumulation Starts from Zero Wrongly

```python
@property
def grand_total(self) -> Money:
    total = Money.from_dollars(0)          # <-- creates Money(0, USD)
    for item in self.items:
        total = total + item.total
    return total
```

This works correctly by accident (starting from zero money), but it's fragile — if any item list is empty, it returns `Money(0, "USD")` which could silently differ from multi-currency orders. Better pattern:

```python
@property
def grand_total(self) -> Money:
    if not self.items:
        return Money(amount_cents=0, currency=self._items_currency() if self.items else "USD")
    return reduce(lambda acc, item: acc + item.total, self.items, Money(amount_cents=0))
```

Or simply: `total = Money(amount_cents=0, currency="USD")` since you already know the currency.

#### 4. Order.aggregate_mutability Is Violated

The `Order` aggregate exposes its state through direct attribute assignment in multiple places. The `_require_status` pattern gates transitions, but nothing prevents external mutation:

```python
# application/order_service.py line 93
order.status = OrderStatus.PAYMENT_PENDING  # bypasses transition guard
```

The application layer sets status directly instead of calling a domain method. This means the same invariant checks that `submit()` performs aren't run here. Every transition path must go through a domain method.

**Fix:** Remove all direct `status =` assignments from the application layer. Route through `order.submit()`, `order.confirm_payment()`, etc., even when the app orchestrates the transition. For the submit→payment_pending case:

```python
# Instead of setting status directly:
def prepare_for_payment(self) -> None:
    self._require_status(OrderStatus.SUBMITTED)
    self.status = OrderStatus.PAYMENT_PENDING
    self._emit(OrderSubmitted(order_id=self.id, ...))  # keep event semantics
```

#### 5. Event Emission Is Fire-and-Forget (Lost Events)

```python
# models.py lines 256-262
def _emit(self, event: DomainEvent) -> None:
    self._events.append(event)

@property
def events(self) -> list[DomainEvent]:
    snapshot = list(self._events)
    self._events.clear()   # <-- drained on read!
```

The `confirm_payment` application flow calls `_repo.save(order)` but never reads `order.events`. The emitted events (`PaymentCompleted`, etc.) are silently discarded because the transaction boundary in `_to_row` never drains them. Events should be persisted atomically alongside the order, and the application service should handle them after the save commits:

```python
async def confirm_payment(self, request: ConfirmPaymentRequest) -> OrderResponse:
    order = await self._must_exist(request.order_id)
    order.confirm_payment(...)
    await self._repo.save(order)
    for evt in order.events:  # drain now, after commit
        await self._handle_domain_event(evt)
    return self._to_response(order)
```

#### 6. Stripe Adapter Mixes Sync and Async incorrectly

```python
# stripe_payment_adapter.py line 62
self._client.send(message)   # sync call inside async function
```

And the Stripe calls like `stripe.PaymentIntent.a_create()` exist only in newer versions of the Stripe SDK (≥3.x) where they added native async methods. If the environment uses an older version, these will crash at runtime. There's no version guard.

**Fix:** Wrap Stripe in a task executor or explicitly check SDK version, or better yet, use `anyio.to_thread.run_sync` for sync calls:

```python
import anyio
import anyio.to_thread

async def _run_stripe(func, *args, **kwargs):
    return await anyio.to_thread.run_sync(lambda: func(*args, **kwargs))
```

#### 7. SendGrid Sends Synchronously Inside Async Handlers

```python
# sendgrid_email_adapter.py line 62
self._client.send(message)  # blocks the event loop
```

This blocks the entire async event loop. SendGrid's `SendGridAPIClient.send()` is a synchronous HTTP call. Run it off the event loop:

```python
import asyncio

async def _send(self, to_email: str, subject: str, html_content: str) -> None:
    message = Mail(from_email=self._from_email, to_emails=to_email, ...)
    try:
        await asyncio.get_running_loop().run_in_executor(None, self._client.send, message)
    except Exception:
        log.exception("Failed to send email to %s", to_email)
        raise
```

### MEDIUM SEVERITY (Should Fix Before Merge)

#### 8. Composition Root Is Missing Entirely

There is zero wiring code. Routes use `getattr(router, "_service")` — a monkey-injected attribute set nowhere visible in the files provided. A real composition root should assemble dependencies at startup:

```python
# infrastructure/di_container.py — doesn't exist
from .adapters.stripe_payment_adapter import StripePaymentAdapter
from .adapters.sendgrid_email_adapter import SendGridEmailAdapter
from .adapters.sqlalchemy_order_repository import SQLAlchemyOrderRepository
from ..application.order_service import OrderApplicationService
from .config import settings

def build_app_dependency_graph():
    repo = SQLAlchemyOrderRepository(settings.database_url)
    payments = StripePaymentAdapter(secret_key=settings.stripe_secret_key)
    emails = SendGridEmailAdapter(api_key=settings.sendgrid_api_key)
    service = OrderApplicationService(repo, payments, emails)
    return service
```

#### 9. API Router Uses Service Injection via Monkey-Patching

```python
svc: OrderApplicationService = getattr(router, "_service")  # type: ignore
```

This is untestable and opaque. The FastAPI way is to use dependency injection with `Depends`:

```python
from fastapi import Depends

async def get_order_service() -> OrderApplicationService:
    """FastAPI DI provider."""
    return router.dependency_overrides.get(OrderApplicationService) \
        or _app_service  # fallback to singleton built at startup

@router.post("", response_model=OrderSummary, status_code=201)
async def create_order(payload: CreateOrderPayload, svc: OrderApplicationService = Depends(get_order_service)):
```

#### 10. No Pagination Tokens — Offset-Based Pagination Is Unsafe for Concurrent Workloads

```python
# ports/inbound.py line 78-85
async def list_orders(..., limit: int = 50, offset: int = 0) -> Sequence[OrderResponse]:
```

Offset pagination causes duplicate/skipped results under concurrent inserts/deletes. Use cursor-based pagination or at minimum accept that this is a management console endpoint (not customer-facing) and document that constraint. At minimum, add a `max_limit` cap to prevent DoS via large offsets:

```python
@router.get("")
async def list_orders(limit: int = Query(50, ge=1, le=200), ...):
```

Already present (line 139 in api_router.py) — good. But still, consider cursor-based for production scale.

#### 11. Repository Pattern Opens/Closes Connections Per Method Call

```python
# sqlalchemy_order_repository.py line 77
async def save(self, order: Order) -> None:
    async with self._session_factory() as session:
        ...await session.commit()
```

Each method opens its own session. The `save → list_orders` flow in the application layer fires separate connections. The correct approach is to inject a session from the application layer (which owns the transaction boundary):

```python
class OrderRepository(ABC):
    @abstractmethod
    async def save(self, session: AsyncSession, order: Order) -> None: ...
    @abstractmethod
    async def get_by_id(self, session: AsyncSession, order_id: uuid.UUID) -> Order | None: ...
```

Or use a unit-of-work pattern:

```python
class UnitOfWork(ABC):
    @abstractmethod
    async def __aenter__(self) -> OrderRepository: ...
    @abstractmethod
    async def __aexit__(self, *exc) -> None: ...
    @abstractmethod
    async def commit(self) -> None: ...
    @abstractmethod
    async def rollback(self) -> None: ...
```

#### 12. Error Handling Is Inconsistent Across Adapters

| Adapter | Error Handling | Problem |
|---------|---------------|---------|
| `StripePaymentAdapter` | No error handling | Any Stripe network error bubbles up unhandled |
| `SendGridEmailAdapter` | Generic `except Exception` | Swallows specific error types |
| `SQLAlchemyOrderRepository` | No explicit error handling | ORM errors bubble up without context |

Standardize with domain-level exceptions:

```python
class PaymentGatewayError(OrderBusinessError): ...
class GatewayTimeout(PaymentGatewayError): ...
class GatewayDeclined(PaymentGatewayError): ...

class EmailDeliveryError(OrderBusinessError): ...
class EmailProviderDown(EmailDeliveryError): ...
```

Then catch upstream SDK errors and re-raise with domain semantics.

#### 13. `InvalidEmailAddress` Is Defined but Never Used

`domain/errors.py` exports `InvalidEmailAddress` but neither validation logic nor port contracts reference it. Either implement email validation in the application layer or remove it.

#### 14. No Validation of Input Beyond Pydantic Schema

The `CreateOrderPayload` validates quantity >= 1 and price > 0, but business-level validation (e.g., max order items, max amount, allowed SKUs) lives nowhere. Add a validator step in the application layer before calling `Order.create_draft`:

```python
async def validate_order_request(self, request: CreateOrderRequest) -> None:
    if len(request.items) > 100:
        raise ValueError("Maximum 100 items per order")
    for item in request.items:
        if item.quantity < 1:
            raise NegativeQuantityError(...)
    # TODO: cross-reference with inventory catalog
```

#### 15. Application Layer Has DTO Logic Mixed With Business Logic

```python
# order_service.py line 42-47
def _to_money_cents(data: dict) -> int:
    if "unit_price_cents" in data:
        return int(data["unit_price_cents"])
    return round(float(data["unit_price"]) * 100)  # float bug again
```

This converter function handles two input formats (cents vs dollars) — that belongs at the API boundary (in the route handler or a Pydantic model validator), not in the application service. The application layer should receive well-typed requests, not raw dicts. Replace the `dict[str, Any]` in `CreateOrderRequest` with typed dataclasses:

```python
@dataclass(frozen=True)
class OrderItemInput:
    sku: str
    description: str
    quantity: int
    unit_price_cents: int

@dataclass(frozen=True)
class ShippingAddressInput:
    street: str
    city: str
    state: str
    postal_code: str
    country: str = "US"

@dataclass(frozen=True)
class CreateOrderRequest:
    customer_name: str
    customer_email: str
    items: tuple[OrderItemInput, ...]
    shipping_address: ShippingAddressInput
```

Then the route handler converts Pydantic models to domain-aligned requests, and the application service works entirely with structured types.


Type annotations on local variables assigned immediately serve no purpose — they're inferred. The `# type: ignore` suppresses the actual type checker warning about `hasattr` returning `Any`. Use `Depends()` injection instead.

#### 18. Missing Tests

There are no test files under the `order_service_refactor` package. Even with a mock-based architecture, you need at minimum:
- Unit tests for domain model transitions (all state machine paths)
- Mock adapter tests for the application service
- Integration tests with a SQLite in-memory database
- Contract tests for the API router

#### 19. Database Migration Scripts Missing

The `infrastructure/database.py` file likely contains the ORM Base and engine setup, but there's no Alembic migration scaffolding. Without migrations, schema changes are manual DDL executed by hand — a production anti-pattern.
