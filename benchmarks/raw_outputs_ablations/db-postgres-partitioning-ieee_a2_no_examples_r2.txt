## Zero-Downtime Declarative Partitioning for 500M Rows

Below is the complete production package. I'm covering four layers: **DDL scaffold**, **migration engine**, **pruning verification**, and **pg_partman automation**.

---

### 1. Table Schema & Monthly Range Partition DDL

```sql
-- ─────────────────────────────────────────────
-- STEP 0: Ensure we have a dedicated tablespace
--         for frequently-written current partitions.
-- ─────────────────────────────────────────────

CREATE TABLESPACE IF NOT EXISTS ts_audit_current OWNER :db_owner;
ALTER TABLESPACE ts_audit_current SET maintenance_work_mem TO '512MB';

-- ─────────────────────────────────────────────
-- STEP 1: Define the partitioned table
--         (no rows yet — acts as the schema contract)
-- ─────────────────────────────────────────────

CREATE TABLE audit_logs_partitioned (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id       bigint        NOT NULL,
    actor_id        bigint,                          -- null = system actions
    action          varchar(64)   NOT NULL,           -- e.g. 'user.created'
    resource_type   varchar(128)  NOT NULL,
    resource_id     bigint,
    old_values      jsonb,                             -- diff tracking
    new_values      jsonb,
    meta            jsonb     DEFAULT '{}'::jsonb,
    ip_address      inet,
    user_agent      text,
    correlation_id  uuid,                              -- request tracing
    occurred_at     timestamptz NOT NULL DEFAULT now(),
    created_at      timestamptz NOT NULL DEFAULT now()
);

-- Cluster the parent by (tenant_id, occurred_at) so child
-- partitions benefit from locality when scanning a single tenant.
ALTER TABLE audit_logs_partitioned CLUSTER ON audit_logs_partitioned_pkey;

-- ─────────────────────────────────────────────
-- STEP 2: Helper function — creates one monthly partition
-- ─────────────────────────────────────────────

CREATE OR REPLACE FUNCTION create_audit_partition(p_start timestamptz, p_end   timestamptz)
RETURNS void LANGUAGE plpgsql AS $$
BEGIN
    EXECUTE format(
        $f$CREATE TABLE audit_logs_%s PARTITION OF audit_logs_partitioned
            FOR VALUES FROM (%L) TO (%L)$f$,
        to_char(p_start, 'YYYY_MM'),
        p_start, p_end
    );
END;
$$;

-- ─────────────────────────────────────────────
-- STEP 3: Build partitions covering
--         [oldest_row .. NOW() + 12 MONTHS]
-- ─────────────────────────────────────────────

DO $body$
DECLARE
    r          RECORD;
    v_start    timestamptz;
    v_end      timestamptz;
    v_latest   timestamptz;
    v_future   timestamptz := date_trunc('month', now()) + interval '12 months';
    v_month    interval    := '1 month';
BEGIN
    -- Find actual oldest row from the legacy table so we don't
    -- waste cycles on empty partitions before it.
    EXECUTE 'SELECT min(occurred_at)::timestamptz FROM audit_logs INTO v_start';
    v_start := coalesce(v_start, date_trunc('month', now()));

    v_start := date_trunc('month', v_start);

    RAISE NOTICE 'Building partitions % → %', v_start, v_future;

    WHILE v_start < v_future LOOP
        v_end := v_start + v_month;
        -- Skip if partition already exists (idempotency after restart)
        IF NOT EXISTS (
            SELECT 1 FROM pg_class c
            JOIN pg_namespace n ON n.oid = c.relnamespace
            WHERE n.nspname = CURRENT_SCHEMA
              AND c.relname = 'audit_logs_' || to_char(v_start, 'YYYY_MM')
        ) THEN
            PERFORM create_audit_partition(v_start, v_end);
        END IF;
        v_start := v_end;
    END LOOP;
END;
$body$;
```

#### Per-Partition Index Strategy

Every child partition inherits `PRIMARY KEY (id)` automatically. Add these **non-inherited** indexes so queries filter on common columns without touching every partition:

```sql
-- Partial index: current 90-day window (smaller, faster)
CREATE INDEX idx_audit_current_window
    ON audit_logs_partitioned (occurred_at)
    WHERE occurred_at >= now() - interval '90 days';

-- Tenant-scoped lookup index on each partition at creation time
-- (shown inside the partition builder loop below — run once)
DO $body$
DECLARE
    r RECORD;
BEGIN
    FOR r IN
        SELECT c.relname
        FROM pg_class c
        JOIN pg_namespace n ON n.oid = c.relnamespace
        WHERE n.nspname = CURRENT_SCHEMA
          AND c.relkind = 'p'        -- partition type
          AND c.relname LIKE 'audit_logs_%'
    LOOP
        BEGIN
            EXECUTE format(
                $i$CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_%I_tenant_occurred
                    ON %I (tenant_id, occurred_at)$i$,
                r.relname, r.relname
            );
        EXCEPTION WHEN duplicate_table THEN
            -- partition was dropped concurrently; skip silently
            NULL;
        END;
    END LOOP;
END;
$body$;
```

> **Why partial indexes?** The 90-day partial keeps the most-hot path index lean (~2% of total rows). Queries outside that window fall through to the full scan but are rare.

### 2. Zero-Downtime Migration Engine

The core problem: copying 500M rows while allowing concurrent DML. The pattern is:

1. **Shadow table** already partitioned (created above)
2. **Triggers** replicate live mutations from old → new
3. **Batch backfill** catches up historical data with lock timeouts
4. **Cutover** renames tables under a short ACCESS EXCLUSIVE lock

#### Phase A — Trigger-Based Replication (catches deltas)

```sql
-- ─────────────────────────────────────────────
-- PHASE A: Start replaying live changes immediately
-- ─────────────────────────────────────────────

CREATE OR REPLACE FUNCTION fn_replicate_audit_log()
RETURNS TRIGGER LANGUAGE plpgsql AS $func$
BEGIN
    IF TG_OP = 'DELETE' THEN
        DELETE FROM audit_logs_partitioned
         WHERE id = OLD.id;
        RETURN OLD;
    ELSIF TG_OP = 'UPDATE' THEN
        UPDATE audit_logs_partitioned SET
            tenant_id        = NEW.tenant_id,
            actor_id         = NEW.actor_id,
            action           = NEW.action,
            resource_type    = NEW.resource_type,
            resource_id      = NEW.resource_id,
            old_values       = NEW.old_values,
            new_values       = NEW.new_values,
            meta             = NEW.meta,
            ip_address       = NEW.ip_address,
            user_agent       = NEW.user_agent,
            correlation_id   = NEW.correlation_id,
            occurred_at      = NEW.occurred_at,
            created_at       = NEW.created_at
          WHERE id = OLD.id;
        RETURN NEW;
    ELSE
        INSERT INTO audit_logs_partitioned (*) VALUES (NEW.*);
        RETURN NEW;
    END IF;
END;
$func$;

CREATE TRIGGER tg_audit_replay
    AFTER INSERT OR UPDATE OR DELETE ON audit_logs
    FOR EACH ROW EXECUTE FUNCTION fn_replicate_audit_log();
```

At this point, *every* write to `audit_logs` is also flowing into `audit_logs_partitioned`. The backlog is zero.

#### Phase B — Batch Historical Backfill

```sql
-- ─────────────────────────────────────────────
-- PHASE B: Catch up historical data in lock-safe batches
-- ─────────────────────────────────────────────

DO $migrate$
DECLARE
    v_batch_size  int          := 50000;     -- tune: ~50k balances throughput / lock duration
    v_total_copied int         := 0;
    v_last_id     bigint       := 0;
    v_elapsed     interval;
    v_start       timestamptz  := clock_timestamp();
    v_loop_limit  int          := 200;       -- safety cap per session run
BEGIN
    RAISE NOTICE '=== Batch backfill started ===';

    <<outer_loop>>
    LOOP
        EXIT outer_loop WHEN v_total_copied >= 500000000;  -- hard cap — adjust to your count
        EXIT outer_loop WHEN v_loop_limit <= 0;

        -- Select batch ordered by id for sequential scan efficiency
        -- and to ensure no row is skipped due to concurrent inserts
        WITH batch AS (
            SELECT id, tenant_id, actor_id, action,
                   resource_type, resource_id,
                   old_values, new_values, meta,
                   ip_address, user_agent,
                   correlation_id, occurred_at, created_at
              FROM audit_logs
             WHERE id > v_last_id
             ORDER BY id
             LIMIT v_batch_size
        )
        INSERT INTO audit_logs_partitioned (*)
        SELECT * FROM batch
        ON CONFLICT (id) DO NOTHING;              -- handles duplicates from trigger replay

        GET DIAGNOSTICS v_total_copied = ROW_COUNT;   -- cumulative via repeat runs

        SELECT max(id) INTO v_last_id FROM audit_logs_partitioned;

        v_elapsed := clock_timestamp() - v_start;
        RAISE NOTICE 'Copied %, last_id=%, elapsed %, rate % rows/sec',
            v_total_copied, v_last_id,
            v_elapsed,
            ROUND(v_total_copied / EXTRACT(EPOCH FROM v_elapsed)::bigint);

        -- Yield to let other backfills and triggers make progress
        v_loop_limit := v_loop_limit - 1;

        -- IMPORTANT: sleep briefly to avoid CPU starvation and reduce WAL pressure
        PERFORM pg_sleep(0.1);

        -- CRITICAL: If you want to enforce lock timeout, wrap in a subtransaction
        -- Note: LOCK TIMEOUT only applies to lock waits, not to the SELECT itself.
        -- For write-side safety, we rely on the ON CONFLICT DO NOTHING above.
    END LOOP;

    RAISE NOTICE '=== Batch backfill completed: %, elapsed % ===',
        v_total_copied, clock_timestamp() - v_start;
END;
$migrate$;
```

#### Phase C — Verification Before Cutover

Run the equality check in the next section before proceeding. Once validated:

```sql
-- ─────────────────────────────────────────────
-- PHASE C: Atomic cutover — brief ACCESS EXCLUSIVE
--          Duration should be <5 seconds on a healthy cluster
-- ─────────────────────────────────────────────

-- Step 1: Pause new writes to the old table (application can handle retries)
-- ALTER TABLE audit_logs NO INHERIT;   -- optional if app stops writes

-- Step 2: Wait until trigger backlog drains (the function above ensures near-realtime)
-- Verify gap:
SELECT count(*) AS pending_replications
FROM audit_logs o
LEFT JOIN audit_logs_partitioned n USING (id)
WHERE n.id IS NULL;
-- Must return 0 before proceeding.

-- Step 3: Atomic swap (renames are catalog-level ops — essentially instant)
BEGIN;

    -- Drop triggers to prevent accidental writes during rename
    DROP TRIGGER IF EXISTS tg_audit_replay ON audit_logs;

    -- Rename tables
    ALTER TABLE audit_logs        RENAME TO audit_logs_staging;
    ALTER TABLE audit_logs_partitioned RENAME TO audit_logs;

    -- Optional: recluster the renamed table against its primary key
    -- REINDEX INDEX CONCURRENTLY audit_logs_pkey;   -- run separately later

COMMIT;

-- Step 4: Verify counts match
SELECT 'staging' AS source, count(*) FROM audit_logs_staging
UNION ALL
SELECT 'live', count(*) FROM audit_logs;

-- Step 5: If everything checks out, drop the old table
-- After N hours/days of verified operation:
DROP TABLE audit_logs_staging;
```

#### Alternative Fast-Path: ATTACH PARTITION (if migrating in-place)

If you don't want a shadow table and can tolerate **~5 seconds** of `ACCESS SHARE` per partition:

```sql
-- 1. Create a standalone "flat" table that holds the entire 500M-row dataset
--    (already exists as audit_logs today)

-- 2. Make it a partition of the partitioned parent
ALTER TABLE audit_logs_partitioned ATTACH PARTITION audit_logs
    FOR VALUES FROM (minvalue) TO (maxvalue);

-- This acquires ACCESS SHARE on the child (readers proceed) and then
-- VALIDATE CONSTRAINT internally. With a 500M table expect ~30-120s.

-- 3. Drop the identity sequence if needed, since audit_logs already has one
```

> **ATTACH PARTITION is dramatically simpler** than the trigger+batch approach. It's the recommended PostgreSQL-native path for most workloads because `VALIDATE CONSTRAINT` scans sequentially and doesn't block readers. Reserve the trigger approach only when even a few seconds of metadata lock is unacceptable.

### 3. Partition Pruning Verification Queries

```sql
-- ───────────────────────────────────────────────────
-- VERIFY: Partition Pruning Works Correctly
-- ───────────────────────────────────────────────────

-- Q1: Confirm planner actually prunes (EXPLAIN should show only relevant partition(s))
EXPLAIN (COSTS OFF, FORMAT TEXT)
SELECT *
  FROM audit_logs
 WHERE occurred_at >= '2026-08-01' AND occurred_at < '2026-09-01'
   AND tenant_id = 42;
-- EXPECTED: Plan lists ONLY audit_logs_2026_08 (or similar), not all children.

-- If you see "Append" listing every partition, pruning is disabled:
-- SET enable_partition_pruning = on;        -- default is on in PG 12+

-- Q2: Dynamic query — verify pruning with a parameterized predicate
EXPLAIN (COSTS OFF, FORMAT TEXT)
SELECT *
  FROM audit_logs
 WHERE occurred_at >= clock_timestamp() - interval '7 days';

-- Q3: Check that partition bounds are correct
SELECT
    c.relname                        AS partition_name,
    pg_get_expr(c.relpartbound, c.oid) AS bound_expression,
    c.relpages                       AS approx_pages,     -- 8KB pages
    pg_total_relation_size(c.oid)    AS total_bytes,
    pg_relation_size(c.oid)          AS live_bytes,
    (SELECT count(*) FROM ONLY pg_catalog.pg_inherits i
     WHERE i.inhrelid = c.oid)        AS child_count        -- always 1 for leaf
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = CURRENT_SCHEMA
  AND c.relkind = 'p'                     -- partition
  AND c.relname LIKE 'audit_logs_%'
ORDER BY c.relname;

-- Q4: Measure pruning effectiveness at runtime
SET track_io_timing = on;
SET client_min_messages = 'LOG';

-- Run the targeted query — observe which partitions appear
SET log_statement = 'all';
SELECT * FROM audit_logs
 WHERE occurred_at BETWEEN '2026-03-01' AND '2026-03-31'
   AND action = 'payment.processed';
-- Check pg_stat_statements to confirm single-partition scan cost

-- Q5: Verify index usage per partition (run ANALYZE first)
ANALYZE audit_logs_partitioned;

SELECT
    schemaname, tablename, indexname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE tablename LIKE 'audit_logs_%'
ORDER BY idx_scan DESC;

-- Q6: Detect unpartitioned scans (full-table scans across all partitions)
-- Run pg_stat_progress_copy / pg_stat_database metrics before and after
-- to confirm reduction in I/O throughput
```

### 4. Automated Future Partition Management (pg_partman)

```sql
-- ─────────────────────────────────────────────
-- STEP 1: Install pg_partman extension
-- ─────────────────────────────────────────────

-- Debian/Ubuntu:
-- sudo apt install postgresql-16-partman    (or appropriate version)

-- Then in-database:
CREATE EXTENSION IF NOT EXISTS pg_partman SCHEMA partman;

-- If the extension is already installed but not enabled, load it:
-- LOAD 'pg_partman';
-- (No CREATE EXTENSION needed in that case.)

-- ─────────────────────────────────────────────
-- STEP 2: Register audit_logs as a partman-managed parent
-- ─────────────────────────────────────────────

SELECT partman.create_parent(
    p_parent_table   := 'public.audit_logs_partitioned',
    p_control        := 'occurred_at',
    p_type           := 'range',
    p_interval       := '1 month',
    p_premake        := 6                  -- pre-create 6 months ahead
);

-- This creates:
--   - partman.part_config row controlling lifecycle
--   - Any missing partitions from [earliest_data..now()+6months]
--   - Scheduled partition creation via pg_partman's cron or external scheduler

-- ─────────────────────────────────────────────
-- STEP 3: Retention — archive/purge old partitions
-- ─────────────────────────────────────────────

-- Option A: Hard-drop partitions older than 2 years
-- Update existing config row:
UPDATE partman.part_config
   SET retention          = '2 years',
       retention_keep_table = false,    -- true = move to archive table
       retention_keep_index = true     -- keep indexes for queries
 WHERE parent_table = 'public.audit_logs_partitioned';

-- Option B: Move to cold storage tablespace
-- ALTER TABLE partman.part_config
-- SET CONFIG: add a hook script that executes:
--   ALTER TABLE audit_logs_2024_01 SET TABLESPACE ts_audit_archive;

-- ─────────────────────────────────────────────
-- STEP 4: Schedule automatic maintenance
-- ─────────────────────────────────────────────

-- Method 1: pg_cron (built-in extension)
CREATE EXTENSION IF NOT EXISTS pg_cron;

SELECT cron.schedule(
    'partman-audit-partitions',
    '0 0 * * *',                           -- daily at midnight
    $$SELECT partman.run_maintenance('public.audit_logs_partitioned')$$
);

-- Method 2: External systemd timer calling psql
-- See /etc/systemd/system/pg-partman-maintenance.timer

-- ─────────────────────────────────────────────
-- STEP 5: Partition management monitoring
-- ─────────────────────────────────────────────

-- Check what partitions exist and their ages:
SELECT
    child.relname               AS partition,
    CASE
        WHEN child.relname ~ '_20[0-9]{2}_[0-9]{2}$'
        THEN split_part(child.relname, '_', 3)::int * 10000
               + split_part(child.relname, '_', 4)::int
    END                         AS year_month_int,
    pg_relation_size(child.oid) AS size_bytes,
    c.relpages                  AS estimated_pages,
    (SELECT count(*) FROM audit_logs_partitioned ONLY child) AS row_estimate
FROM pg_inherits
JOIN pg_class child  ON child.oid  = inhrelid
JOIN pg_class parent ON parent.oid = inhparent
WHERE parent.relname = 'audit_logs_partitioned'
ORDER BY child.relname;

-- Check partman configuration summary:
SELECT *
FROM partman.part_config
WHERE parent_table = 'public.audit_logs_partitioned';

-- Manually trigger partition creation for upcoming months:
SELECT partman.run_maintenance('public.audit_logs_partitioned');

-- ─────────────────────────────────────────────
-- STEP 6: Storage tiering hook (optional cloud-native)
-- ─────────────────────────────────────────────

-- For AWS RDS Aurora / Cloud SQL: use pg_fileseg or storage classes
-- For self-hosted: move old partitions to cheaper disk

DO $tier$
DECLARE
    r RECORD;
BEGIN
    FOR r IN
        SELECT c.oid, c.relname
        FROM pg_class c
        JOIN pg_namespace n ON n.oid = c.relnamespace
        WHERE n.nspname = CURRENT_SCHEMA
          AND c.relkind = 'r'                     -- plain table (child partition)
          AND c.relname LIKE 'audit_logs_20[0-9][0-9]_[0-9][0-9]'
          AND c.relname < to_char(now() - interval '18 months', 'audit_logs_YYYY_MM')
    LOOP
        ALTER TABLE partman.__temp_ownership_rls_check ALTER TABLE __PG_PARTMAN_NO_LOGGING__ ON ONLY r.relname
        EXECUTE format('ALTER TABLE %I SET TABLESPACE ts_audit_archive', r.relname);

        RAISE NOTICE 'Tiered: % → ts_audit_archive', r.relname;
    END LOOP;
END;
$tier$;
```

### Runbook Summary

| Step | Command | Expected Duration | Risk |
|------|---------|-------------------|------|
| 1. Create partitioned table + partitions | DDL (Section 1) | <1s (metadata only) | None |
| 2. Deploy trigger replay | Section 2 Phase A | <1s | None |
| 3. Run batch backfill | Section 2 Phase B | ~2-6 hrs (50k/batch) | Low — `ON CONFLICT DO NOTHING` prevents data loss |
| 4. Verify row counts match | Section 3 Q2/Q6 | <30s | None |
| 5. Atomic rename cutover | Section 2 Phase C | <5s | Brief `ACCESS EXCLUSIVE` — must pause app writes |
| 6. Install pg_partman + schedule | Section 4 | <10s | None |
| 7. Drop staging table | Post-verification | <1s | Irreversible — wait 24-48h minimum |

### Tuning Parameters to Adjust Per Environment

| Parameter | Default | Tuning Guidance |
|-----------|---------|----------------|
| `batch_size` | 50,000 | Higher = faster but longer lock windows on trigger replays. Cap so backfill never exceeds 1s CPU spike. |
| `premake` | 6 months | Increase if partition creation has latency issues. Don't exceed 12 — stale partitions bloat the catalog. |
| `retention` | 2 years | Align with compliance requirements. Older data moves to archive tablespace. |
| `maintenance_work_mem` | 256MB | Raise to 1–2 GB for faster index builds on large partitions. |
| `work_mem` | 4MB | Temporarily increase to 64MB during backfill if sorts/hashes dominate. |
