## Hexagonal / Ports-and-Adapters Architecture — Order Processing Service

### Top-Level Structure

```

├── config.py                    # Configuration aggregate
```

### 1. DOMAIN LAYER — Pure Business Logic

**`domain/entities.py`** — The `Order` aggregate root enforces all lifecycle invariants:

```python
class OrderStatus(Enum):
    DRAFT → CONFIRMED → PAYMENT_PENDING → PAYMENT_COMPLETED → FULFILLED
                                   ↘ PAYMENT_FAILED
    FULFILLED → REFUNDED
    Any payable status → CANCELLED
```

Key design decisions:
- **Factory method** `Order.create()` validates items, prices (0 < price ≤ $100k), totals ($1T cap), emptiness — raises `InvalidOrderError` before an object can be created in an invalid state.
- **State transitions** go through `_transition_from(expected, target)` which rejects any illegal edge. E.g., you cannot fulfill an unconfirmed order.
- **Computed properties** (`total_amount_cents`, `total`) derive from items at runtime — no stale cache risk.
- Uses `object.__setattr__` internally to bypass immutability constraints during state mutations on dataclass fields.

**`domain/value_objects.py`** — Immutable, identity-less primitives:

| VO | Invariant |
|---|---|
| `Currency` | Frozen, ISO 4217 lookup enforced at construction |
| `Money` | Stored in cents (no float drift), arithmetic requires currency match, range -999T…+999T cents |
| `CustomerEmail` | Lowercased, RFC-ish validation: length limits, no consecutive dots, valid char set for local part |
| `OrderId` | ≥10 chars, factory produces 20-char hex UUID |
| `Quantity` | 1–10,000 inclusive, addition/subtraction validated |
| `PaymentIntentId` | Must start with `pi_` |

All VOs are `frozen=True, slots=True` dataclasses — memory efficient and hashable.

**`domain/exceptions.py`** — Flat hierarchy under `DomainError`:

```
DomainError
├── InvalidOrderError   (business invariant violation)
├── NotFoundError       (aggregate missing)
└── PaymentError        (gateway failure)
```

### 2. PORTS — Abstract Contracts

**Incoming ports** (`ports/incoming.py`):

| Port | Purpose | Key Methods |
|---|---|---|
| `OrderControllerPort` | What callers invoke | `create_order()`, `get_order()`, `confirm_order()`, `cancel_order()` |
| `WebhookInboundPort` | What external services push | `handle_incoming_webhook()` — signature verify → dedupe → dispatch |

Request/response types (`CreateOrderRequest`, `GetOrderResponse`, etc.) are frozen dataclasses — pure DTOs bridging layers.

**Outgoing ports** (`ports/outgoing/`):

| Port | Type | Contract |
|---|---|---|
| `OrderRepositoryPort` | Protocol | `save(order) → Order`, `find_by_id(id) → Order \| None`, `find_many(email, limit) → list[Order]` |
| `EventLedgerPort` | Protocol | `reserve_event(id) → bool`, `mark_processed(id, type, data)`, `get_reservation(id) → (exists, processed)` |
| `PaymentGatewayPort` | ABC | `create_intent(inp) → PaymentIntentResult`, `confirm_intent(inp) → ConfirmPaymentResult`, `refund_intent(inp) → RefundPaymentResult` |
| `EmailServicePort` | ABC | `send_order_confirmation(to, id, total)`, `send_payment_failed_notification(to, id, reason)`, `send_fulfillment_update(to, id, tracking_url?)` |

### 3. APPLICATION LAYER — Use Case Coordinators

Each use case follows the same pattern: **load → validate → mutate domain → persist → respond**:

```python
class CreateOrderCase:
    def __init__(self, repository: OrderRepositoryPort) -> None:
        self._repository = repository

    async def execute(self, request: CreateOrderRequest) -> GetOrderResponse:
        customer_email = CustomerEmail(request.customer_email)
        order = Order.create(customer_email, request.items, request.currency_code)
        persisted = await self._repository.save(order)
        return _to_response(persisted)
```

Notable use cases:

- **`ProcessPaymentCase`** — Cross-port: reads order from repo, calls `gateway.create_intent()`, mutates order with intent ID, persists.
- **`FulfillOrderCase`** — Cross-port: mutates order, then fires fire-and-forget email notification (swallows exceptions).
- **`WebhookInboundImpl`** — Handles signature verification (optional injected callback), event deduplication via ledger reservation, and dispatches to success/failure handlers with email notifications.

The `_to_response()` helper centralizes serialization from domain entity to response DTO so every use case produces identical output shapes.

### 4. ADAPTERS — Concrete Implementations

**Outgoing adapters** implement the outgoing ports:

| Adapter | Implements | External System |
|---|---|---|
| `SQLAlchemyOrderRepository` | `OrderRepositoryPort` | PostgreSQL via async SQLAlchemy ORM. Upsert logic: UPDATE first, fall back to INSERT ON CONFLICT DO NOTHING. Separate session-per-call by default; supports shared-session mode for transactional multi-repo ops. |
| `PostgresEventLedger` | `EventLedgerPort` | Append-only table with `event_id UNIQUE`. `reserve_event` uses `INSERT ... ON CONFLICT DO NOTHING` then verifies row outcome (already-processed vs newly-inserted). `mark_processed` uses direct UPDATE with RETURNING. |
| `StripePaymentAdapter` | `PaymentGatewayPort` | Sets `stripe.api_key`, creates/retrieves PaymentIntents, issues Refunds. Maps `StripeError` → `PaymentError`. |
| `SendGridEmailAdapter` | `EmailServicePort` | Wraps sync SendGrid library in `loop.run_in_executor()`. Dynamic template substitution. Returns boolean success; logs exceptions without raising. |

**Incoming adapter** (`adapters/incoming/fastapi_router.py`):

Mounts an `APIRouter(prefix="/api/v1/orders")` with routes for CRUD, payment, fulfillment, and webhook reception. Converts Pydantic request bodies → port request DTOs → controller/port → port response DTOs → Pydantic responses. Error messages are sanitized via `_safe_error_message()` to never leak internals.

Two injection modes:
1. **Direct port injection** — pass `controller` and `webhook_handler` explicitly (ideal for tests).
2. **Container mode** — pass a `Container` instance; router fetches dependencies lazily via `Depends()`.

### 5. COMPOSITION ROOT — Dependency Injection

```python
class Container:
    """Singleton DI container."""

    @property
    def order_repo(self) -> SQLAlchemyOrderRepository:
        self._ensure_db(); return self._order_repo

    @property
    def stripe_gateway(self) -> StripePaymentAdapter:
        returns singleton with api_key + webhook_secret from AppConfig

    @property
    def controller(self) -> OrderControllerImpl:
        wires CreateOrderCase(GetOrderCase, ConfirmOrderCase, CancelOrderCase) together

    @asynccontextmanager
    async def lifespan(self, app: FastAPI):
        startup: create_async_engine → sessionmaker → repos → create_all tables
        shutdown: engine.dispose()

def create_app(config: AppConfig) -> FastAPI:
    container = Container(config)
    app = FastAPI(); app.lifespan_context = container.lifespan
    router = build_order_router(controller=container.controller, webhook_handler=...)
    app.include_router(router)
    return app
```

`AppConfig.from_env()` loads all settings from environment variables (`DATABASE_URL`, `STRIPE_API_KEY`, `SENDGRID_API_KEY`, etc.). Supports `AppConfig.from_dict()` for YAML/config-file loading.

### Architecture Strengths

1. **True dependency inversion** — Domain has zero imports outside stdlib. All frameworks (FastAPI, SQLAlchemy, Stripe, SendGrid) are isolated in adapters. You could swap the DB driver or payment provider without touching domain code.

2. **State machine integrity** — The `Order` aggregate enforces its own lifecycle. No use case can call `fulfill()` on a draft order; `_transition_from()` checks the expected source state.

3. **Webhook idempotency** — `EventLedger.reserve_event()` uses atomic upsert with verification. Duplicate webhooks are silently acknowledged (returns `True`).

4. **Signature verification** — `WebhookInboundImpl` delegates signature checking to an injectable callback (`signer_verify`), supporting key rotation via dual secret fallback in the container.

5. **Session management flexibility** — Repositories support both standalone sessions (simplest case) and caller-managed shared sessions (for transactions spanning multiple repositories).

6. **Money handled correctly** — `Money` stores in integer cents, arithmetic enforces currency matching, `from_decimal()` and `format()` handle presentation.

### Areas for Improvement

1. **Missing test coverage** — There are no unit/integration tests in the `tests/` directory for this module. Every use case, state transition, and edge case needs tests against mock ports.

2. **`ProcessPaymentCase` and `FulfillOrderCase` not wired into controller** — They exist in `use_cases.py` but aren't included in `OrderControllerImpl.__init__` or mounted in the router via a proper endpoint in the non-container mode. The payment endpoint exists but relies on container-mode `Depends()`.

3. **Missing `StartPayment`/`Fulfill` incoming port methods** — `OrderControllerPort` only declares `create_order`, `get_order`, `confirm_order`, `cancel_order`. Payment initiation and fulfillment lack incoming port declarations.

4. **`save()` race condition** — The two-phase update-then-insert strategy could still have edge-case races under high concurrency. A single UPSERT with conditional logic would be more robust.

5. **No pagination** — `find_many()` hardcodes `limit=50` with no offset/cursor support.

6. **`_to_response()` duplicates `Order.to_dict()`** — Both serialize identically. Consider consolidating or using a dedicated mapper.
